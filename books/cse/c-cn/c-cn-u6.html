6.1 Client-server and peer-to-peer architectures

Client‑server is one main way and peer‑to‑peer is the other main way an application can exchange data. In client‑server the client asks a server for a service and the server replies. In peer‑to‑peer every participant can act as both client and server, so data can flow directly between peers. These models shape how web browsers, mobile apps, video‑sharing services and many other applications are built and how they perform.

You need: the OSI model and the transport layer concepts from Unit 5.

Client‑server architecture

A client is a program that initiates a request. A server is a program that waits for requests and sends responses. The interaction follows a request‑response pattern. The client may be a web browser, a mobile app, or a command‑line tool. The server may host web pages, a database, or a train‑status service.

  • Client sends a request packet to the server’s IP address and port.
  • Server processes the request, possibly accessing storage or other services.
  • Server sends a response packet back to the client’s IP address and port.

RT = T_req + T_proc + T_resp + 2·T_prop

RT is total round‑trip time; T_req is time to send the request; T_proc is server processing time; T_resp is time to send the response; T_prop is one‑way propagation delay.

The model is stateless when the server does not keep any client‑specific data between requests. It is stateful when the server stores a session, for example a shopping‑cart on an e‑commerce site.

Peer‑to‑peer architecture

In peer‑to‑peer (P2P) every participant is called a peer. A peer can both request data and serve data to other peers. Direct connections avoid a central server for the bulk data transfer, reducing latency and bandwidth cost for the service provider.

  1. Peer A discovers Peer B (by a tracker or a distributed hash table).
  2. Peers negotiate a direct channel (TCP or UDP).
  3. Data is exchanged directly between the two peers.
  • P2P is used by video‑sharing apps, file‑sharing tools, and some multiplayer games.
  • The control plane (search, signalling) may still use a server, but the data plane is peer‑driven.

P2P can be either stateful (peers keep a list of known neighbors) or stateless (each transfer is independent).

Worked example

Question. A Chennai user shares a 5 MB video with a friend using a peer‑to‑peer link that has a bandwidth of 20 Mbps. The protocol adds a fixed overhead of 0.15 s before the data transfer starts. Compute (a) the pure transfer time and (b) the total time including overhead. Show your work.

C program.

#include <stdio.h>
int main() {
    double size_mb = 5.0;          // video size in megabytes
    double bandwidth_mbps = 20.0;   // link bandwidth in megabits per second
    double overhead_s = 0.15;       // fixed protocol overhead in seconds
    double transfer = (size_mb * 8.0) / bandwidth_mbps; // seconds
    double total = transfer + overhead_s;
    printf("Transfer time = %.3f s\n", transfer);
    printf("Total time    = %.3f s\n", total);
    return 0;
}
  1. Convert the video size to bits: 5 MB × 8 = 40 Mbit.
  2. Transfer time = size (Mbit) ÷ bandwidth (Mbps) = 40 ÷ 20 = 2.0 s.
  3. Add the overhead: total time = 2.0 s + 0.15 s = 2.15 s.

  • Writing that the server initiates the connection in a peer‑to‑peer scenario.
  • Confusing megabytes (MB) with megabits (Mb) when converting video size.
  • Adding overhead before converting units, which gives a wrong total time.
  • Assuming that a client‑server interaction is always stateful; many web services are stateless.

Apply A mobile app sends a 2 KB request to a train‑status server and receives a 1 KB JSON response in 150 ms. If the round‑trip time formula is RT = T_req + T_proc + T_resp + 2·T_prop, estimate the processing time at the server assuming the network propagation time is 30 ms each way and the transmission speed is 1 Mbps. 6 marks

Convert sizes to bits: 2 KB = 16 kbit, 1 KB = 8 kbit. Transmission time request = 16 kbit ÷ 1 Mbps = 0.016 s = 16 ms. Transmission time response = 8 kbit ÷ 1 Mbps = 0.008 s = 8 ms. Propagation total = 30 ms + 30 ms = 60 ms. RT = 150 ms = 0.150 s. T_proc = RT – (T_req + T_resp + 2·T_prop) = 0.150 – (0.016 + 0.008 + 0.060) = 0.066 s = 66 ms.

Analyze Compare the scalability of client‑server and peer‑to‑peer models when the number of users grows from 1 000 to 1 000 000. Mention at least two factors that affect each model. 6 marks

Client‑server: scalability is limited by server capacity (CPU, memory, bandwidth). As users increase, the server must handle more concurrent connections, leading to higher latency or need for load‑balancers and multiple servers. Peer‑to‑peer: scalability improves because each new peer contributes its own upload bandwidth, distributing load. However, factors such as peer churn (peers joining/leaving) and the need for discovery mechanisms can affect performance.

Remember Define a stateless interaction in the client‑server model. 2 marks

A stateless interaction is one where the server does not retain any information about the client between separate requests.

Apply If a peer‑to‑peer file of 10 MB is transferred over a link with 5 Mbps bandwidth and a fixed handshake delay of 0.2 s, compute the total transfer time. 4 marks

Size in bits = 10 MB × 8 = 80 Mbit. Transfer time = 80 ÷ 5 = 16 s. Total time = 16 s + 0.2 s = 16.2 s.

Understand Why might a video‑sharing service still use a central server even if it employs peer‑to‑peer data transfer? 3 marks

The central server can provide indexing, peer discovery, authentication, and metadata services, while the actual video chunks are exchanged directly between peers.

6.2 Socket programming with TCP and UDP

Sockets are the programming interface that lets an application talk to another over a network using TCP or UDP. They hide the details of IP addresses and ports, letting developers send and receive data as if it were a local file descriptor. Sockets are used in web browsers, chat apps, online gaming, and any client‑server service on the Internet.

You need: Transport basics and Client‑server and peer‑to‑peer architectures.

What is a socket?

A socket is an endpoint for communication identified by an IP address and a port number. The IP address locates the host on the network, while the port (0‑65535) identifies the process on that host. The operating system maps the socket to a protocol (TCP or UDP) and provides system calls such as socket(), bind(), send(), recv() etc.

0 ≤ p ≤ 65535

p is a port number; values 0‑1023 are well‑known ports, 1024‑49151 are registered, 49152‑65535 are dynamic.

  • TCP sockets give reliable, ordered byte streams.
  • UDP sockets give connectionless datagrams with no guarantee of delivery.

TCP socket programming steps

A TCP server creates a listening socket, waits for a client to connect, and then exchanges data on a new connected socket. The client creates a socket, connects to the server, and then reads or writes.

  1. socket() – create an endpoint of type SOCK_STREAM.
  2. bind() – associate the socket with a local IP address and a port.
  3. listen() – mark the socket as passive and set a backlog.
  4. accept() – block until a client connects; returns a new socket for the session.
  5. send() – transmit bytes on the connected socket.
  6. recv() – receive bytes from the connected socket.
  7. close() – release the socket.

C program.

#include <stdio.h>
#include <string.h>
#include <arpa/inet.h>
#include <unistd.h>

int main() {
    int listen_sock = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in serv;
    serv.sin_family = AF_INET;
    serv.sin_port = htons(6000);
    serv.sin_addr.s_addr = INADDR_ANY;
    bind(listen_sock, (struct sockaddr *)&serv, sizeof(serv));
    listen(listen_sock, 1);
    struct sockaddr_in client;
    socklen_t cl_len = sizeof(client);
    int conn_sock = accept(listen_sock, (struct sockaddr *)&client, &cl_len);
    char buf[64];
    recv(conn_sock, buf, sizeof(buf)-1, 0);
    buf[63] = '\0';
    printf("Server received: %s
", buf);
    const char *reply = "ACK";
    send(conn_sock, reply, strlen(reply), 0);
    close(conn_sock);
    close(listen_sock);
    return 0;
}

Output

Server received: Hi
  • Blocking mode: each call waits until it can complete.
  • Non‑blocking mode: set O_NONBLOCK flag; calls return -1 with EAGAIN if not ready.

UDP socket programming steps

A UDP socket does not need a connection. The same socket can send to many destinations and receive from any. Because there is no handshake, the programmer must handle lost packets.

  1. socket() – create an endpoint of type SOCK_DGRAM.
  2. bind() – optional for a client; required for a server to fix the listening port.
  3. sendto() – specify destination address and port with each call.
  4. recvfrom() – receive a datagram and learn the sender’s address.
  5. close() – release the socket.

C program.

#include <stdio.h>
#include <string.h>
#include <arpa/inet.h>
#include <unistd.h>

int main() {
    int sock = socket(AF_INET, SOCK_DGRAM, 0);
    struct sockaddr_in serv;
    serv.sin_family = AF_INET;
    serv.sin_port = htons(5000);
    serv.sin_addr.s_addr = inet_addr("127.0.0.1");
    const char *msg = "Hi";
    sendto(sock, msg, strlen(msg), 0, (struct sockaddr *)&serv, sizeof(serv));
    char buf[64];
    struct sockaddr_in from;
    socklen_t fromlen = sizeof(from);
    recvfrom(sock, buf, sizeof(buf)-1, 0, (struct sockaddr *)&from, &fromlen);
    buf[63] = '\0';
    printf("Received: %s
", buf);
    close(sock);
    return 0;
}

Output

Received: Hi
  • Because UDP is connectionless, sendto() must include the destination each time.
  • Using send() on a UDP socket is a common trap; it fails to specify the peer.

Worked example

Exam traps

  • Using send() instead of sendto() on a UDP socket; send() does not specify the destination address.
  • Calling bind() on a client TCP socket to a port already in use; the call fails with EADDRINUSE.
  • Assuming recv() returns the full message; TCP may deliver data in fragments, so a loop is needed.
  • Setting a socket to non‑blocking and forgetting to handle EAGAIN, causing the program to think data is lost.

6.3 Domain Name System (DNS)

The Domain Name System (DNS) turns the human‑friendly names we type, like www.irctc.co.in, into the numeric IP addresses that routers need. It exists because remembering numbers is hard and because IP addresses can change while names stay the same. DNS is used by every web browser, email client, and mobile app that accesses the Internet.

You need: IP addressing from Chapter 2 and the basics of sockets from socket‑programming with TCP and UDP.

DNS hierarchy and zones

DNS is organized as a tree that starts at the root servers. The root points to top‑level domain (TLD) servers such as .com, .in, .org. Each TLD delegates authority to second‑level domains (e.g., irctc.co.in). A zone is the part of the name space for which a server holds authoritative records. The root zone, the .in zone, and the irctc.co.in zone are examples.

  • Root zone – managed by a set of globally distributed root servers.
  • TLD zone – managed by the registry for that TLD (e.g., .in).
  • Second‑level zone – managed by the domain owner (e.g., irctc.co.in).

remaining_TTL = TTL – elapsed

remaining_TTL is the time left before a cached record expires; TTL is the Time‑to‑Live value set by the authoritative server; elapsed is the time already spent since the record was cached.

Resource records and query types

A DNS response contains resource records (RR). The most common RR types are A (IPv4 address), CNAME (canonical name alias), MX (mail exchange server), and NS (name server). When a client asks for www.irctc.co.in, it typically sends a recursive query to its local resolver.

  1. Resolver checks its cache. If a valid record exists, it returns it.
  2. If not, the resolver sends an iterative query to a root server.
  3. Root returns the NS records for the .in TLD.
  4. Resolver queries a .in server, which returns NS records for irctc.co.in.
  5. Resolver finally queries an irctc.co.in authoritative server, which returns the A record.
  • Recursive query – client asks resolver to do all the work and return the final answer.
  • Iterative query – resolver asks one server at a time and follows referrals.

Caching, TTL, and transport details

Resolvers cache answers to reduce traffic and latency. Each record carries a TTL in seconds. While the TTL has not expired, the cached copy is used; after expiration the resolver must fetch a fresh copy.

  • Typical TTL values: 300 s for dynamic records, 86400 s (24 h) for static records.
  • Cache size is limited; least‑recently‑used entries are evicted first.

DNS uses UDP port 53 for most queries because it is fast and fits in a single packet. If the answer does not fit (e.g., DNSSEC or many records), the server sets the TC (truncated) flag and the client retries over TCP port 53.

Only a few universities teach dynamic update, where a client can add, delete, or modify records in a zone using the UPDATE operation over TCP with authentication.

Exam traps

  • Confusing an authoritative name server with a recursive resolver; the former only answers for its own zone, the latter performs the whole lookup.
  • Assuming DNS always uses TCP; most queries use UDP unless the response is too large.
  • Treating the TTL as a fixed global value; each record carries its own TTL and the remaining time depends on when it was cached.
  • Thinking that a CNAME record replaces the original name; the client must still follow the CNAME to the final A record.
  • Believing that a cache entry is removed immediately after TTL expires; many resolvers keep the stale entry until a new query is made.

In a recursive query the resolver does all the steps and returns the final answer; in an iterative query the resolver asks one server, receives a referral, and must query the next server itself.

When the first query is answered, the resolver stores the records with their TTL. Subsequent queries within the TTL are answered from the cache, so no additional messages travel to the authoritative servers, reducing network traffic and latency.

The client re‑issues the same query over TCP port 53. TCP can carry larger messages, allowing the full answer (often needed for DNSSEC or many records).

6.4 World Wide Web and HTTP

The World Wide Web uses the HyperText Transfer Protocol (HTTP) to let a browser ask a server for a resource and to receive the resource back. HTTP is a request‑response protocol that works over TCP. It is the backbone of web browsing, mobile apps, and many cloud services. Understanding URLs, methods, status codes, headers and the stateless nature of HTTP lets you build clients, debug traffic, and design efficient web services.

You need: transport services from socket programming and name resolution from DNS.

Uniform Resource Locator and request line

A Uniform Resource Locator (URL) tells the browser where a resource lives. The general form is scheme://host[:port]/path?query#fragment.

scheme is usually http or https. host is a domain name such as example.com. host may be a domain name or an IP address (e.g., 93.184.216.34). port is optional; the default for http is 80 and for https is 443.

path identifies the file on the server, for example /index.html. query is a string after ?, used to pass parameters. fragment after # is processed only by the browser.

When the browser wants a resource it creates a request line. The line has three parts: METHOD SP REQUEST-URI SP HTTP-VERSION CRLF.

GET /index.html HTTP/1.1

GET is the method; /index.html is the request‑URI; HTTP/1.1 is the protocol version.

  • METHOD is a verb such as GET, POST, PUT, DELETE.
  • SP is a single space character.
  • CRLF is carriage‑return followed by line‑feed.

Methods, status codes and idempotence

GET asks the server to return a representation of the target resource without changing server state.

POST sends data to the server, often causing a change such as creating a new record.

PUT replaces the entire target resource with the supplied representation.

DELETE removes the target resource.

  • GET, PUT and DELETE are idempotent – repeating the same request has the same effect as a single request.
  • POST is not idempotent – each repeat may create a new record.

HEAD and OPTIONS are also idempotent because they do not modify server state.

After the request line the server sends a status line: HTTP-VERSION SP STATUS-CODE SP REASON-PHRASE CRLF.

  • 200 OK – request succeeded and response contains the requested data.
  • 404 Not Found – the target resource does not exist.
  • 500 Internal Server Error – server failed to fulfil a valid request.

Headers, statelessness and persistent connections

Headers are key‑value pairs that appear after the request or status line and before an empty line.

Common request headers: Host, User-Agent, Accept, Content-Type. Common response headers: Content-Type, Content-Length, Set-Cookie.

HTTP is stateless. The server does not remember previous requests from the same client unless the client sends a cookie or uses authentication tokens.

HTTP/1.0 opened a new TCP connection for each request. HTTP/1.1 introduced persistent connections by default.

In HTTP/1.1 the connection is persistent by default; the Connection: keep-alive header is only needed for HTTP/1.0 or to override a default close behavior.

  • Connection: keep-alive tells the server to keep the socket open after the response.
  • Connection: close forces the server to close the socket after the response.

A persistent connection reduces latency because the TCP three‑way handshake is performed only once.

Total time = 2×RTT + (Size×8) ÷ Bandwidth

RTT is round‑trip time in seconds; Size is object size in bytes; Bandwidth is link capacity in bits per second.

HTTPS adds TLS encryption on top of HTTP. Only a few syllabi cover it, so it is mentioned here as a future topic.

Worked example

Question. A laptop requests http://example.com/index.html. The network RTT is 120 ms. The server sends a 1.2 KB HTML page. The link bandwidth is 2 Mbps. Compute the total time from sending the request to receiving the complete page using a persistent connection.

C program.

#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>
#include <netdb.h>
int main(){
    const char *host = "example.com";
    const char *path = "/index.html";
    struct hostent *he = gethostbyname(host);
    if(!he){ perror("gethostbyname"); return 1; }
    int sock = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in addr;
    addr.sin_family = AF_INET;
    addr.sin_port = htons(80);
    memcpy(&addr.sin_addr, he->h_addr_list[0], he->h_length);
    if(connect(sock, (struct sockaddr*)&addr, sizeof(addr))<0){ perror("connect"); return 1; }
    char request[256];
    snprintf(request, sizeof(request), "GET %s HTTP/1.1\r\nHost: %s\r\nConnection: close\r\n\r\n", path, host);
    send(sock, request, strlen(request), 0);
    char buffer[1024];
    ssize_t n = recv(sock, buffer, sizeof(buffer)-1, 0);
    if(n>0){ buffer[n]='\0'; printf("%s", buffer); }
    close(sock);
    return 0;
}
  1. Convert the object size to bits: 1.2 KB × 1024 B/KB × 8 bits/B = 9 830 bits.
  2. Transmission time = size ÷ bandwidth = 9 830 bits ÷ 2 000 000 bits/s = 0.004915 s = 4.915 ms.
  3. Two RTTs are needed (request and first byte of response): 2 × 120 ms = 240 ms.
  4. Total time = 240 ms + 4.915 ms ≈ 244.9 ms.

Exam traps

  • Assuming all HTTP methods are idempotent; only GET, HEAD, PUT, DELETE and OPTIONS are.

  • Treating the URL fragment (#section) as part of the request sent to the server; it is processed only by the browser.

6.5 File transfer with FTP

File Transfer Protocol (FTP) moves files between a client and a server using two TCP connections: one for control messages and one for the actual file data. The control channel stays open for the whole session and carries commands such as USER, PASS, RETR and STOR. The data channel is opened only when a file is transferred, either by the server (active mode) or by the client (passive mode). FTP is used for uploading website assets, backing up databases, and sharing large media files in many Indian enterprises and educational institutions.

You need: socket programming and basic TCP knowledge.

Control and data connections

When an FTP client starts, it opens a TCP connection to the server’s port 21. This is called the control connection. All commands and replies travel on this channel. The server replies with three‑digit codes, for example 220 means “Service ready”.

A separate TCP connection carries the file bytes. In active mode the server opens a connection from its port 20 to a client port that the client has announced. In passive mode the client asks the server to listen on a random high port; the server replies with the chosen port and the client connects to it.

T_total = T_data + T_cmd

T_total is total transfer time; T_data is time to move the file bytes; T_cmd is time spent on command exchange.

  • Port 21 – always the control port.
  • Port 20 – used by the server for active data connections.
  • Passive data port – chosen by the server, usually >1023.

FTP command flow

  1. Client → Server: USER <username>
  2. Server → Client: 331 User name ok, need password.
  3. Client → Server: PASS <password>
  4. Server → Client: 230 User logged in.
  5. Client → Server: PASV (for passive) or PORT (for active).
  6. Server → Client: 227 Entering Passive Mode (h1,h2,h3,h4,p1,p2).
  7. Client → Server: RETR <filename> to download or STOR <filename> to upload.
  8. Server opens data connection, transfers file, then sends 226 Transfer complete.

Active mode often fails behind firewalls because the server must connect to a client‑side port that the firewall may block. Passive mode moves the connection initiation to the client, which is usually allowed.

  • USER – tells the server which account to use.
  • PASS – sends the password in clear text.
  • PASV – asks the server to listen for a data connection.
  • PORT – tells the server which client port to connect to (active).
  • RETR – request a file download.
  • STOR – request a file upload.

Programming a simple FTP client

Using the socket API, a client can implement the command flow shown above. The steps are: create a TCP socket, connect to port 21, read the 220 greeting, send USER and PASS, request PASV, parse the server’s 227 reply to obtain the data IP and port, open a second socket to that address, send RETR or STOR, read the file data, and finally close both sockets.

Python program.

import socket, re

def ftp_get(host, user, pwd, remote, local):
    ctrl = socket.create_connection((host, 21))
    ctrl.recv(1024)                           # 220 greeting
    ctrl.sendall(f'USER {user}\r\n'.encode())
    ctrl.recv(1024)                           # 331 response
    ctrl.sendall(f'PASS {pwd}\r\n'.encode())
    ctrl.recv(1024)                           # 230 response
    ctrl.sendall(b'PASV\r\n')
    resp = ctrl.recv(1024).decode()
    nums = list(map(int, re.search(r'\((\d+,\d+,\d+,\d+,\d+,\d+)\)', resp).group(1).split(',')))
    ip = '.'.join(map(str, nums[:4]))
    port = nums[4]*256 + nums[5]
    data = socket.create_connection((ip, port))
    ctrl.sendall(f'RETR {remote}\r\n'.encode())
    ctrl.recv(1024)                           # 150 opening data connection
    with open(local, 'wb') as f:
        while True:
            chunk = data.recv(4096)
            if not chunk:
                break
            f.write(chunk)
    data.close()
    ctrl.recv(1024)                           # 226 transfer complete
    ctrl.sendall(b'QUIT\r\n')                # end session gracefully
    ctrl.recv(1024)                           # 221 goodbye (optional)
    ctrl.close()

6.6 Electronic mail and SMTP

SMTP (Simple Mail Transfer Protocol) moves electronic mail from the sender’s client to the recipient’s mailbox using a store‑and‑forward model. It exists because email must travel across many administrative domains that may not be directly reachable. SMTP is used by every major mail service, by corporate mail servers, and by mobile apps that send notifications via email.

You need: basic socket use from socket programming with TCP and UDP and the request‑response idea from HTTP.

SMTP Overview and Ports

SMTP is an application‑layer protocol defined in RFC 5321. It runs on top of TCP because reliable delivery is required. The standard port is 25 for plain SMTP. Port 587 is used for submission with STARTTLS, which upgrades the connection to TLS after a plain handshake. Port 465 is reserved for implicit TLS, where the TLS handshake starts immediately.

  • MUA – Mail User Agent, the client program (e.g., Outlook, Thunderbird).
  • MTA – Mail Transfer Agent, the server that forwards mail (e.g., sendmail, Postfix).
  • MDA – Mail Delivery Agent, stores mail in the final mailbox (e.g., Dovecot).

When a user clicks Send, the MUA opens a TCP connection to its configured MTA on port 587. After STARTTLS, the MUA issues a series of SMTP commands. Each command receives a numeric reply (e.g., 250 OK). The MTA may store the message locally and forward it to another MTA until the final MDA delivers it to the recipient’s mailbox.

  1. Open TCP connection to MTA on port 587.
  2. Issue STARTTLS and complete TLS handshake.
  3. Send HELO/EHLO with the client domain.
  4. Send MAIL FROM:<sender@example.com>.
  5. Send RCPT TO:<receiver@example.org>.
  6. Send DATA, then the message headers and body, end with a single period on a line.
  7. Close the connection with QUIT.

SMTP Command Sequence

The command set is deliberately small. HELO or EHLO starts the session and tells the server the client’s domain name. MAIL FROM identifies the envelope sender; it may differ from the header From field. RCPT TO lists each envelope recipient; multiple RCPT commands are allowed. DATA begins the transfer of the message content; the server replies 354 to indicate it is ready. The client terminates the data with a line containing only a period.

  • Each command line ends with CRLF (carriage‑return and line‑feed).
  • Server replies are three‑digit codes; 2xx means success, 4xx temporary failure, 5xx permanent failure.
  • If any command fails, the client may abort with RSET or QUIT.

T_total = T_cmd + (Size × 8) ÷ Rate

T_total is total transfer time; T_cmd is cumulative command latency in seconds; Size is message size in bytes; Rate is link bandwidth in bits per second.

MIME for Attachments

SMTP can carry only 7‑bit ASCII data. MIME (Multipurpose Internet Mail Extensions) defined in RFC 2045‑2049 allows binary files, Unicode text, and multiple parts inside a single message. The MUA encodes each attachment with Base64, adds a Content‑Type header, and separates parts with a boundary string.

  • Content‑Type: image/jpeg; name="photo.jpg"
  • Content‑Transfer‑Encoding: base64
  • Content‑Disposition: attachment; filename="photo.jpg"

When the message reaches the recipient’s MDA, the mail client decodes the Base64 blocks and presents the original file. MIME is also used for HTML mail, calendar invites, and signed messages.

Worked example

6.7 Basics of network security

Application‑layer traffic can be read or altered if it travels in clear text. firewalls and NAT operate at the network edge, while encryption protects the data payload before it traverses the network. The most common protection is TLS, which adds a cryptographic layer over protocols like HTTP and FTP. Understanding these concepts helps you design safe client‑server programs and avoid simple attacks on web and file‑transfer services.

You need: socket programming basics (socket-programming-with-tcp-and-udp) and the idea of client‑server interaction (client-server-and-peer-to-peer-architectures).

Basic security building blocks

A firewall examines packets at the network border and decides whether to allow or block them based on rules such as source IP, destination port, or protocol. NAT (Network Address Translation) hides internal private addresses by mapping many hosts to a single public address, making direct attacks on internal machines harder.

  • Firewall – rule based packet filter at network edge.
  • NAT – translates private IPs to a public IP and keeps a table of active connections.
  • Encryption – transforms readable data into ciphertext using a secret key.

Encryption can be symmetric (same key for encrypt and decrypt) or asymmetric (public‑private key pair). In web security the asymmetric part authenticates the server, while a symmetric session key encrypts the actual data because it is faster.

Latency = 2 × RTT + Processing

RTT is round‑trip time in ms; Processing is the time to generate the request in ms.

TLS handshake and HTTPS

  1. Client sends **ClientHello** with supported TLS version, cipher suites, and a random number.
  2. Server replies with **ServerHello**, chooses a cipher suite, sends its certificate, and a server random.
  3. Both compute a pre‑master secret; the client encrypts it with the server’s public key and sends it.
  4. Each side derives the symmetric session key from the pre‑master secret and the two random numbers.
  5. Secure application data can now be exchanged encrypted with the session key.

HTTPS is simply HTTP layered on top of TLS. The browser (client) and the web server perform the handshake before any HTTP GET or POST is sent. This prevents eavesdropping and man‑in‑the‑middle attacks.

C program.

#include <stdio.h>
int main() {
    double rtt = 30.0; // ms per round trip
    double proc = 0.1; // ms request processing
    double total = 2 * rtt + proc;
    printf("Total latency = %.1f ms\n", total);
    return 0;
}

Common attacks and simple defenses

  • Eavesdropping – listening to traffic; prevented by TLS encryption.
  • Spoofing – forging source IP or identity; mitigated by authentication and firewalls.
  • Denial‑of‑Service (DoS) – overwhelming a server; reduced by rate‑limiting and firewalls.

Only a few universities cover the full TLS certificate‑validation process in detail. For most B.Tech exams it is enough to know that the server’s public key comes from a trusted certificate and that the client checks the signature.

FTPS works like FTP but adds TLS to the control connection. In implicit FTPS TLS starts immediately on connection (usually port 990). In explicit FTPS the client first establishes a plain FTP control connection and then upgrades it to TLS by sending an AUTH TLS command before any file‑transfer commands are issued. The data connection is also encrypted after the handshake, protecting file contents during transfer.

Apply Explain how FTP uses separate control and data connections. Include a diagram of active and passive modes. 13 marks

Control connection on port 21 (commands); Data connection on a separate port (active: server connects to client; passive: client connects to server); Show sequence of PORT or PASV command; Explain why two connections are needed.

Apply Describe the SMTP store‑and‑forward process for sending an email from a user in Chennai to a recipient in Delhi. Mention the role of MX records. 14 marks

User's client contacts local MTA using SMTP; Local MTA looks up MX record of recipient domain; Mail is queued and forwarded to remote MTA; Remote MTA delivers to recipient's mailbox; Possible intermediate MTAs.

Apply Write a short pseudo‑code for a TCP server that accepts multiple client connections using the select() system call. 14 marks

Create listening socket; Initialize fd_set and add listening socket; Loop: call select(); If listening socket ready, accept new client and add to set; If client socket ready, read data, process, possibly close.

Glossary

A record
DNS resource record that maps a hostname to an IPv4 address
Active mode FTP
FTP mode where server initiates data connection to client
Client
Software that initiates a request for a service
Control connection
FTP TCP connection on port 21 for commands
Data connection
Separate FTP connection used to carry file data
DNS
Domain Name System, a hierarchical system that maps domain names to IP addresses
Encryption
Process of converting data into a form that cannot be understood without a key
Firewall
Network device or software that filters traffic based on security rules
FTP
File Transfer Protocol, used to transfer files between client and server
Handshake
Initial exchange of messages to establish a connection
HTTP
Hypertext Transfer Protocol, the protocol used by web browsers and servers
HTTPS
HTTP secured with TLS, providing encryption and integrity
Integrity
Assurance that data has not been altered during transmission
MTA
Mail Transfer Agent, software that routes email using SMTP
MX record
Mail exchange record that specifies the mail server for a domain
NAT
Network Address Translation, rewrites IP addresses and ports for outbound traffic
Passive mode FTP
FTP mode where client initiates data connection to server
Peer‑to‑Peer
Network model where each node can act as both client and server
Port
A 16‑bit number that distinguishes applications on the same host
Port 443
Default port for HTTPS and often used for QUIC
Port 80
Default port for unencrypted HTTP
QUIC
Quick UDP Internet Connections, a transport protocol built on UDP
Request line
First line of an HTTP request containing method, URI and version
Resolver
Client‑side component that queries DNS servers
REST
Architectural style that uses standard HTTP methods for CRUD operations
Select()
System call that monitors multiple file descriptors for readiness
Server
Software that provides a service to clients
SMTP
Simple Mail Transfer Protocol, used to send email between servers
Socket
An endpoint for inter‑process communication identified by IP address and port
Status code
Three‑digit number in an HTTP response indicating result
Store‑and‑forward
Message handling where a server stores mail before forwarding it
TCP
Transmission Control Protocol, a reliable, connection‑oriented transport protocol
Three‑way handshake
TCP connection setup sequence: SYN, SYN‑ACK, ACK
TLS
Transport Layer Security, a protocol that provides encryption for other protocols
UDP
User Datagram Protocol, a connection‑less transport protocol
URL
Uniform Resource Locator, a textual address of a web resource
Zero‑RTT
QUIC feature that allows data to be sent in the first packet
