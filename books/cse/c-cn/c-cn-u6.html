6.1 Client-server and peer-to-peer architectures

Every network application is a pair of processes in two places: one asks for something, the other provides it. The asking side is the client, the providing side is the server. Choosing which side holds the data, who stays awake, and whether any single machine is in charge decides how the application scales, what it costs in rupees, and what breaks when one machine dies. This chapter sets out those choices; HTTP, DNS, mail and file transfer in the rest of the unit are just particular answers to them.

You need: Unit 1 for layering and protocol suites, and Unit 5 for ports and processes; chapter 6.2 turns these two roles into running code.

A client asks, a server answers

A network application is two programs in two processes on two hosts. One asks for something, the other provides it. That is the whole client-server idea; everything else is detail about how the asking is arranged.

The client starts the conversation. It knows the server's address, which is an IP address plus a port number (Unit 5), and it sends the first message. A client is usually started by a person, runs for a short while, and may sit behind an address that DHCP changes.

The server is the other role. It runs all the time, waits at a fixed address and a well-known port, and answers whoever knocks. The client must not need to know the server's schedule.

Traffic is lopsided. The request is small, like a name, a URL or a command; the reply is large, like a page, a file or a mailbox. So the server's upload link decides how many clients it can serve, not its download link.

HTTP, FTP, SMTP and DNS all follow this pattern. Only a few universities also teach SNMP, a client-server protocol for managing routers and switches. Each protocol has its own chapter later.

Stateless, stateful, and how many tiers

A stateless server keeps no memory of earlier requests. Every request carries everything needed to answer it. Restart the server and nothing is lost. Put ten copies behind a load balancer and send each request to any copy. HTTP works this way.

A stateful server remembers the session: who logged in, what is in the cart, which transfer is half done. The memory makes the conversation simpler but ties the client to one machine. Restart it and the session dies; share it across machines and you need a common store.

Tiers count the machines behind the client. In a two-tier design the server talks straight to a database. In a three-tier design a logic layer sits between them: the web server checks the request, the application server applies the business rules, the database stores rows. Three tiers cost more machines and more hops, but each layer can be scaled or replaced alone.

  • Stateless is cheap to replicate; stateful is cheap to design.
  • Two-tier is quick to build; three-tier survives growth.
  • The more layers, the more places a request can wait.

Peer-to-peer: every node serves

In peer-to-peer (P2P) there is no fixed server. Every peer is both client and server: it downloads pieces of a file from others and uploads pieces it already holds. The role depends on the moment, not on the machine.

Finding those pieces happens in one of two ways. A central directory (a tracker) keeps an index of which peer holds which piece. Peers ask the tracker, then exchange data directly. Lookup is fast, but the tracker is a single point of failure and an easy thing to block. A fully decentralised overlay has peers form their own network on top of the Internet and find each other by passing queries along, or by a distributed hash table that maps a file key to the peer responsible for it. Nothing central exists to fail, but lookups are slower and the overlay costs extra signalling.

Scalability is the real difference. In client-server the server's upload rate us is fixed, so extra users only add queueing. In P2P every new peer brings its own upload rate ui, so supply grows with demand. The cost moves too: one big server means a capital bill in rupees and a bandwidth contract; P2P spends the upload capacity users already pay for.

T<sub>cs</sub> = max(N·F/u<sub>s</sub>, F/d)    and    T<sub>p2p</sub> = max(F/u<sub>s</sub>, F/d, N·F/(u<sub>s</sub> + Σu<sub>i</sub>))

N is the number of peers, F is the file size in Mbit, us is the server upload rate, ui is each peer's upload rate and d is each peer's download rate, all in Mbps; Tcs and Tp2p are the distribution times in seconds.

Worked example

Question. A 10 Mbit file must reach 3 peers. The server's upload rate is u_s = 2 Mbps, each peer uploads at u_i = 1 Mbps, and each peer downloads at d = 2 Mbps. Find the distribution time for (a) client-server and (b) peer-to-peer.

  1. Write the data: F = 10 Mbit, N = 3 peers, u_s = 2 Mbps, u_i = 1 Mbps per peer, d = 2 Mbps per peer.
  2. (a) The server must send N copies, so the server's upload sets a floor: N·F/u_s = 3 × 10 ÷ 2 = 15 s.
  3. (a) Each peer must receive F bits at rate d, so the download sets another floor: F/d = 10 ÷ 2 = 5 s.
  4. (a) Both floors must hold, so T_cs = max(15, 5) = 15 s. The server's upload is the binding term.
  5. (b) The server must upload at least one full copy: F/u_s = 10 ÷ 2 = 5 s.
  6. (b) Each peer's download still applies: F/d = 10 ÷ 2 = 5 s.
  7. (b) Total upload capacity in the swarm = u_s + Σu_i = 2 + 3 × 1 = 5 Mbps. Total bits to move = N·F = 3 × 10 = 30 Mbit. So the swarm needs 30 ÷ 5 = 6 s.
  8. (b) T_p2p = max(5, 5, 6) = 6 s.

Answer. The client-server distribution time is 15 s and the peer-to-peer time is 6 s, so P2P finishes 9 s earlier.

Exam traps

  • Writing the client-server time as F/u_s alone. The server uploads N copies, so N·F/u_s is usually the binding term.
  • Taking the sum of the three P2P terms instead of the maximum. All three limits act at the same time, so the slowest one decides.
  • Thinking a server is a type of hardware. It is a role played by a process; one machine can run a web server, a mail server and a P2P client at once.
  • Calling HTTP stateful because logins seem to be remembered. HTTP itself is stateless; cookies and sessions put the memory back on top.
  • Confusing a tracker with a file server. The tracker holds only the index of who has which piece; the file data moves between peers.

Check yourself

Remember In the client-server model, which side sends the first message, and which side must be always on? 2 marks

The client sends the first message. The server must be always on and reachable at a fixed IP address and port.

Understand Why is a stateless server easier to scale than a stateful one? 3 marks

Each request carries all the information needed, so any copy of the server can answer it. Copies can be added behind a load balancer, restarted freely, and no shared session store is needed. A stateful server must keep the client's session on one machine or in a shared store, which adds coordination.

Apply A 20 Mbit file is shared with 5 peers. u_s = 4 Mbps, u_i = 1 Mbps each, d = 2 Mbps each. Find the client-server and peer-to-peer distribution times. 4 marks

N·F/u_s = 5 × 20 ÷ 4 = 25 s and F/d = 20 ÷ 2 = 10 s, so T_cs = max(25, 10) = 25 s. For P2P: F/u_s = 5 s, F/d = 10 s, and N·F/(u_s + Σu_i) = 100 ÷ (4 + 5) = 11.1 s, so T_p2p = max(5, 10, 11.1) = 11.1 s.

Analyze A tracker-based P2P system and a fully decentralised overlay each fail in a different way. Compare them on one strength and one weakness each. 5 marks

Tracker: lookups are fast and the index is easy to keep accurate, but the tracker is a single point of failure and a single target to block, so the whole swarm stops finding peers if it goes down. Fully decentralised: no single node can be removed to kill the system, but queries must be flooded or routed through a distributed hash table, so lookups are slower and the overlay spends bandwidth on signalling.

Understand What separates a two-tier design from a three-tier design? 3 marks

In two-tier the server talks directly to the database. In three-tier a logic or application layer sits between the web server and the database, so business rules live in one place and each layer can be scaled or replaced separately.

Analyze In the client-server model the server's upload link limits growth; in P2P it does not. Explain why, using the formula terms. 4 marks

In client-server the whole file set must pass through u_s, so the term N·F/u_s grows with N while u_s stays fixed. In P2P the same term appears as N·F/(u_s + Σu_i); each new peer adds u_i to the denominator, so capacity rises with the number of peers and the time levels off instead of growing.

Beyond the syllabus

Not for the exam. Real deployments mix the two models: a content delivery network puts client-server caches near users, while the caches fetch from each other in a peer-like way. BitTorrent-style swarms carry game and operating-system updates because the publisher's bandwidth bill does not grow with the number of downloaders. Blockchains push the fully decentralised idea to record keeping, with no tracker at all. Edge computing moves the server closer to the client to cut round-trip time, a trend that shows up in 5G and IoT syllabi. Search for content delivery networks, distributed hash tables, and edge computing to go further.

6.2 Socket programming with TCP and UDP

A program reaches the network by calling the socket API. A socket is one end of a conversation, named by an IP address and a port. Two sockets, one at each end, form a connection, and four numbers name it uniquely. TCP sockets carry a reliable byte stream; UDP sockets carry separate datagrams. Web pages, chat, video calls — every application in this unit sits on these calls. This chapter gives the exact order of calls for each protocol and the mistakes that order prevents.

You need Unit 5 for ports, the UDP datagram and TCP connection setup, and chapter 6.1 for which side starts the conversation.

A socket is one end of a conversation

Two processes on two machines want to exchange data. The transport layer delivers to ports, but a program cannot touch a port directly; it asks the operating system through the socket API. A socket is a handle — a small integer, like a file descriptor — standing for one end of a conversation.

That end is named by a socket address: an IP address plus a port, written 192.168.1.7:50000. The address picks the machine, the port picks the process. A connection is named by four numbers: source IP, source port, destination IP, destination port. No two connections on the Internet share a four-tuple at the same time, which is how one server serves thousands of clients on port 80 — every client differs in its own address.

socket(family, type, protocol) creates one. family is AF_INET for IPv4. The type is the real decision: SOCK_STREAM gives TCP, SOCK_DGRAM gives UDP. Protocol 0 means the default for that type. After the call the transport behaviour is fixed for the life of the socket.

TCP: the server listens, the client connects

The two sides make different calls, in a fixed order.

  1. socket() — create an unbound TCP socket.
  2. bind() — attach it to the server's address, say 10.0.0.5:80.
  3. listen() — mark it passive and give it a backlog queue for clients arriving while the program is busy.
  4. accept() — block until a client's handshake finishes, then return a new socket for that one connection. The listening socket stays open.
  5. recv() and send() — read and write bytes on the new socket.
  6. close() — end it; the peer's recv() then returns 0.

The client calls socket(), then connect(). connect() sends the SYN and returns only when the three-way handshake completes. The client does not bind: the kernel picks its IP address and an ephemeral port at connect time.

The socket that accept() returns carries the same local port as the listening socket. That is legal because the four-tuple differs.

TCP is a byte stream with no message boundaries. Two send() calls of 100 bytes can arrive as one recv() of 200. recv() returns what is available now, up to the buffer size. The application must frame its own messages with a length field or a delimiter.

UDP: one call per datagram

A UDP server makes three calls: socket(AF_INET, SOCK_DGRAM, 0), bind() to its port, then recvfrom() in a loop. recvfrom() fills the buffer and also reports the sender's address, because there is no connection to remember it. Replies go out with sendto(), which carries the destination address every time. No listen(), no accept().

Each sendto() is exactly one datagram. The receiver gets it whole or not at all — the boundary is preserved. UDP itself may drop it, deliver it twice or deliver two out of order, and the socket API does not hide that. A file transfer adds sequence numbers and acknowledgements of its own; a video call accepts the loss.

Ports are divided by number. Binding a well-known port needs administrator rights on Unix.

Many clients, and the lab

One accept() followed by a recv() loop serves one client at a time. Two standard fixes.

  • One thread per client: the main thread accept()s and hands each new socket to a thread that loops on recv(). Simple, but each thread costs stack memory, so a few thousand clients is the practical ceiling on one machine.
  • One loop over select() or poll(): you pass the kernel a list of sockets, it returns the ready ones, and one thread handles them. It scales further and is harder to write; only a few universities teach it in the networks course.

Write the server before the client; a server you can test with a browser is easiest. Lab work for this unit builds in that order: ping, to watch a round trip; a web server returning one fixed page; a two-user chat; and the same web server behind SSL, where the socket is wrapped before the first byte (see 6.7).

Worked example

Question. A client at 192.168.1.7 with port 50000 opens a TCP connection to a web server at 10.0.0.5, port 80, and sends 5000 bytes. Give the socket pair at each end and the number of TCP segments on the wire if the maximum segment size is 1500 bytes (ignore headers).

Python program.

data, mss = 5000, 1500
full, rem = divmod(data, mss)
segs = full + (1 if rem else 0)
print("client", ("192.168.1.7", 50000), "->", ("10.0.0.5", 80))
print("server", ("10.0.0.5", 80), "->", ("192.168.1.7", 50000))
print("full", full, "last", rem, "segments", segs)
  1. Client side: local end 192.168.1.7:50000, remote end 10.0.0.5:80, so the pair is (192.168.1.7:50000, 10.0.0.5:80).
  2. Server side: local end 10.0.0.5:80, remote end the client, so the pair is (10.0.0.5:80, 192.168.1.7:50000). Same four numbers, mirrored.
  3. Full segments: 5000 ÷ 1500 = 3, carrying 3 × 1500 = 4500 bytes.
  4. Leftover: 5000 − 4500 = 500 bytes, which needs one more segment.
  5. Total segments: 3 + 1 = 4.

Exam traps

  • Assuming TCP keeps message boundaries. Two send() calls of 100 bytes each can arrive in one recv() of 200 bytes; without a length field or a delimiter the receiver misreads the next message.
  • Calling UDP connectionless and therefore portless. A UDP server still binds a port before recvfrom(); without bind the kernel picks a random port and no client can find it.
  • Confusing the listening socket with the connected one. accept() returns a new socket, and reading from the listening socket instead is the classic lab bug.
  • Believing the port number identifies the connection. A port identifies one endpoint; the connection is the four-tuple.

Beyond the syllabus

Not for the exam. Production code rarely calls sockets by hand: asyncio in Python, Netty in Java and Node.js wrap the same calls and hide select() behind callbacks. Kernel-bypass frameworks such as io_uring and DPDK push the classic API aside for high-throughput servers. QUIC moves reliable streams into userspace over UDP, which is why browsers now open UDP port 443. Search 'Berkeley sockets', 'epoll vs select' and 'io_uring networking'.

6.3 Domain Name System (DNS)

DNS is a distributed database that turns a readable name such as www.example.com into an IP address. It exists because people remember names, while routers forward packets using numbers. The database is split into a tree of zones, each served by authoritative name servers, and resolvers walk that tree for you. Caching keeps the walk from repeating. DNS is used before almost every network action: opening a web page, sending mail, or an app calling its server.

You need: Unit 4 for IPv4 and IPv6 addresses, and chapter 6.2 for the UDP socket a DNS query uses.

The name space is an inverted tree

DNS names form an inverted tree. The root is a dot (.). Below it sit top-level domains (TLDs): generic ones such as com, org and net, and country-code ones such as in for India. Each node carries a label. A full name is read from the node upward: www.example.com. means host www inside example inside com inside the root. The final dot is the absolute name; everyday use drops it.

Each node holds resource records (RRs). An RR is a typed value with a time to live (TTL) in seconds. The common types:

  • A: name → IPv4 address.
  • AAAA: name → IPv6 address.
  • CNAME: alias name → canonical name.
  • MX: domain → mail server name, with a preference number.
  • NS: zone → name server that is authoritative for it.

Authority is delegated downward. The com zone does not store the address of www.example.com; it stores an NS record that points to the name server for example.com. That server holds the A record. This division is why no single computer holds the whole name space.

Resolvers, recursive and iterative queries

Your device does not walk the tree. It asks a resolver, also called the local, default or caching name server. The resolver address is set in the operating system, often learnt from DHCP (see Unit 4).

Queries come in two styles. A recursive query puts the full job on the receiver: it must return the final answer or an error, not a referral. An iterative query lets the receiver return the best it has: the answer, or an NS referral to a server closer to the name.

Your host sends a recursive query to its resolver. The resolver sends iterative queries to the tree. For www.example.com with an empty cache:

  1. Host → resolver: recursive query for www.example.com.
  2. Resolver → root server: iterative query. The reply is an NS record for com.
  3. Resolver → com server: the reply is an NS record for example.com, usually with a glue A record for that server's address.
  4. Resolver → example.com authoritative server: the reply is the A record for www, with its TTL.
  5. Resolver caches the answer for the TTL and returns it to the host.

That is three server contacts and six messages, because each exchange is one query and one reply. A later request for the same name hits the cache and costs no name-server messages.

Zones, zone transfer and port 53

A zone is a contiguous part of the tree whose records one organisation manages. example.com is a zone; its zone file lists every RR. Each zone has a primary (master) server, where changes are made, and one or more secondary (slave) servers that copy the zone. The copy is a zone transfer.

Ordinary DNS queries use UDP port 53. One datagram out and one back, with no connection setup. TCP port 53 is used for zone transfers and for replies too large for UDP; a truncated UDP reply makes the client retry over TCP.

A zone can be updated dynamically: a host or DHCP server adds or deletes an RR with a DNS update message, without editing the file by hand. In practice the update is authenticated. Security belongs to chapter 6.7.

TTL controls caching. Short TTLs allow quick changes but raise query load; long TTLs do the opposite. DNS runs before HTTP (chapter 6.4) opens its TCP connection and before SMTP (chapter 6.6) finds a mail server.

Worked example

Question. A host with an empty cache asks its resolver for www.example.com. The resolver uses iterative queries. (a) How many name servers does the resolver contact, and how many DNS messages does the resolver exchange with them before the answer arrives? (b) The same name is asked again after 200 s and the TTL is 300 s. How many new resolver-to-name-server messages are needed? (c) After the record has been cached for 300 s, how many messages does the next lookup need?

  1. The resolver contacts 3 servers: a root server, the com server and the example.com authoritative server.
  2. Each contact is one query plus one reply, so 2 messages per server.
  3. Total for (a): 3 × 2 = 6 messages.
  4. The A record is cached with TTL = 300 s. At 200 s the remaining life is 300 − 200 = 100 s.
  5. 100 s > 0, so the cached record is still valid. New messages for (b): 0.
  6. At 300 s the remaining life is 0, so the record has expired. The resolver repeats the three contacts: 3 × 2 = 6 messages for (c).

Answer. The resolver contacts 3 name servers and exchanges 6 messages; after 200 s it needs 0 new messages, and after 300 s it needs 6 messages again.

Exam traps

  • Saying DNS always uses TCP. Ordinary lookups use UDP port 53; TCP appears for zone transfers and oversized answers.
  • Mixing the query styles. The host asks its resolver recursively; the resolver asks the root, TLD and authoritative servers iteratively.
  • Confusing A and AAAA, or CNAME with NS. A gives IPv4, AAAA gives IPv6; CNAME is an alias, NS names an authoritative server.
  • Treating TTL as a timeout for the query. TTL is how long a cached record may be reused, in seconds.
  • Forgetting that the root has 13 named server identities, not 13 physical machines; each identity is served by many anycast copies.

The host wants one final answer and does not walk the tree. The resolver takes the job, follows referrals from server to server, and returns the final address.

Analyze A site lowers its TTL from 86400 s to 60 s before changing its IP address. Why? 4 marks

Old cached A records expire within at most 60 s after the change, so fewer users reach the old address. The cost is a higher query rate because caches refresh more often.

Analyze Why is a zone transfer sent over TCP while an ordinary query uses UDP? 4 marks

A zone transfer is bulk data that must arrive complete and in order, so TCP's reliability and flow control matter. An ordinary query is one small request and one small reply, so UDP avoids connection setup.

Ordinary query: UDP port 53. Zone transfer: TCP port 53.

Beyond the syllabus

Not for the exam. DNS now often travels inside HTTPS (DoH) or TLS (DoT) to stop eavesdropping and tampering. Large sites use anycast so one name resolves to a nearby copy. DNSSEC adds signatures to records, and service discovery uses SRV and TXT records. Search next: DNS over HTTPS, anycast, DNSSEC, SRV records.

6.4 World Wide Web and HTTP

The World Wide Web is a set of documents named by URLs and fetched on demand. The protocol that fetches them is HTTP, the HyperText Transfer Protocol. A browser sends a short request written in plain text; the server answers with a status line, a few headers and the object itself. That is the whole idea, and it is why you can debug a web server from a terminal. HTTP runs on top of TCP, so bytes arrive in order and none are lost. It is stateless: each request is answered with no memory of the ones before.

You need: socket programming and DNS from earlier in this unit, and the TCP connection from Unit 5.

The URL and the message

A URL (Uniform Resource Locator) names one object on the web. Take https://www.example.com:443/books/net.html?page=2. Read it left to right: https is the scheme, www.example.com is the host, 443 is the port, /books/net.html is the path, and page=2 is the query.

  • The scheme picks the protocol and its default port: 80 for http, 443 for https.
  • The host is a name; DNS turns it into an IP address before anything else can happen.
  • The port is left out of the URL when it is the default, which is the usual case.
  • The path names a file or a program on that server; the query is data handed to that program.

An HTTP message is text with three parts: a start line, header lines, and an optional body after a blank line. That blank line is the separator. Miss it and the receiver treats the headers as body.

GET /books/net.html HTTP/1.1
Host: www.example.com

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 5120

<h1>Networks</h1>

The request start line is method, path and version: GET /books/net.html HTTP/1.1. The reply start line is version, status code and reason: HTTP/1.1 200 OK. The path in a request to a server holds only the part after the host, never the full URL.

Content-Length states the body size in bytes. Without it, or a chunked encoding, the receiver cannot tell where one message ends and the next begins on a reused connection.

Methods, status codes, headers

The method is the verb. It says what to do with the named resource.

  • GET asks for the object and must not change anything on the server.
  • HEAD asks for the headers only, with no body; use it to check size or freshness.
  • POST sends data in the body, typically a form, and the server decides what to do with it.
  • PUT stores the body at the URL, replacing what is already there.
  • DELETE removes the resource at the URL.

The status code is three digits. The first digit gives the class: 1xx information, 2xx success, 3xx redirection, 4xx client error, 5xx server error. Only the common ones matter for an exam.

Headers carry the metadata the body cannot. Host names the site, which is how one IP address serves many sites. Content-Type tells the browser how to read the body, for example text/html or image/png. Content-Length gives its size in bytes. Connection: keep-alive or close decides what happens to the TCP connection next. Cookie carries a small identifier the server handed out earlier.

Connections, caches and cookies

HTTP/1.0 opened a fresh TCP connection for each object and closed it afterwards. Every object therefore paid for the TCP three-way handshake on top of its own request and reply.

Persistent connections (keep-alive, the default in HTTP/1.1) leave the TCP connection open and send the next request on it. The handshake is now paid once per page instead of once per object.

Pipelining goes further: the client sends several requests back to back without waiting for the replies, and the server answers them in order. On a slow link this removes several round trips.

A proxy cache is a server on your side of the link that keeps copies of objects. Before reusing a stored copy it asks the origin server with a conditional GET carrying If-Modified-Since or If-None-Match. If the object has not changed, the origin replies 304 Not Modified with no body, and the proxy sends its stored copy. One short round trip replaces the whole object.

HTTP is stateless: the server does not remember your previous request. Cookies fix that. The server sends Set-Cookie: id=a7f3 in a reply. The browser stores it for that host and sends Cookie: id=a7f3 in every later request to that host. The state lives in the browser and in the server's table, not in the protocol. Login sessions, shopping carts and "welcome back, Ravi" all work this way.

HTTPS is HTTP carried inside TLS, so the same messages travel encrypted; the handshake and certificates belong to chapter 6.7. HTTP/2 and HTTP/3 change the wire format to multiplex many requests over one connection; only a few universities teach them.

Worked example

Question. A web page is one base HTML file plus 3 images. The round-trip time between client and server is 100 ms and transmission time is negligible. Find the time to load the whole page when (a) HTTP/1.0 non-persistent connections are used with no parallel connections, (b) HTTP/1.1 persistent connections with pipelining are used.

  1. Count the objects: 1 base file + 3 images = 4 objects.
  2. Non-persistent: each object needs its own TCP connection. One RTT opens the connection (three-way handshake) and one more RTT carries the request and brings the reply. So 2 RTT per object.
  3. Non-persistent total = 4 objects × 2 RTT = 8 RTT.
  4. Time = 8 × 100 ms = 800 ms.
  5. Persistent with pipelining: one TCP connection, so the handshake costs 1 RTT.
  6. The base file costs 1 RTT for request and reply.
  7. The three images are requested back to back without waiting, so all three replies arrive in 1 more RTT.
  8. Total = 1 + 1 + 1 = 3 RTT.
  9. Time = 3 × 100 ms = 300 ms.

Answer. The page loads in 800 ms with non-persistent HTTP and in 300 ms with persistent HTTP and pipelining.

Exam traps

  • Forgetting the TCP setup round trip in the non-persistent case. Each object costs two round trips, not one, because the handshake comes before the request.
  • Counting one round trip per image when pipelining is allowed. Pipelined requests share a single round trip, so all three images finish together.
  • Calling HTTP stateful because a site greets you by name. The cookie carries the state; the protocol itself remembers nothing.
  • Swapping 403 and 404. 403 means the server found the resource and refuses to give it; 404 means there is nothing at that URL. 400 is a malformed request, not a missing page.
  • Writing the full URL in the request line. A request to a server carries only the path; the host goes into the Host header.

The client or proxy sends a conditional GET with If-Modified-Since or If-None-Match. If nothing changed, the server answers 304 Not Modified with an empty body, so only a few header bytes cross the network instead of the whole object.

6.5 File transfer with FTP

FTP, the File Transfer Protocol, copies files between two computers over TCP. Its defining habit is that it runs two TCP connections at once: a long-lived control connection that carries only short commands and replies, and a fresh data connection opened for each file. Splitting them keeps commands out of the way of bulk bytes, so a huge upload never blocks a cancel or a status check. FTP is used to publish web pages to a hosting server, to push firmware to devices on a LAN, and to move large data sets between machines inside an organisation.

You need: Chapter 6.2 for TCP sockets, ports and connection setup, and Chapter 6.4 to compare FTP with HTTP's single connection.

One session, two connections

FTP copies a file from one computer to another over TCP, so the bytes arrive in order and nothing is lost. One design choice shapes everything else: FTP uses two TCP connections at the same time.

The control connection is opened once, when the session starts. The client picks a temporary port, say 50000, and connects to the server's port 21. This connection stays open until the user logs out. It carries only short text lines: commands one way, three-digit replies the other. Every line ends with CRLF, a carriage return followed by a line feed.

The data connection is opened fresh for each file. It carries the raw bytes of that file and nothing else, and it is closed the moment the file ends. A directory listing also travels on this second connection, because a listing is just another stream of bytes.

Why split them? The control stays out of band, on a separate path. A 2 GB upload cannot block your ability to send ABOR or to ask for progress, because commands never queue behind file data. Compare HTTP in Chapter 6.4, which puts headers and body on one connection and simply waits.

Active mode and passive mode

The data connection has to be opened by one side or the other, and FTP allows both arrangements.

In active mode the client sends PORT with its own IP address and a port it has chosen, written as six comma-separated numbers. The server then opens the data connection from its port 20 to that port. This breaks behind NAT and firewalls: the address the client announced is a private one, and the incoming connection from the server is blocked.

In passive mode the client sends PASV. The server replies 227 with its address and a high port it has picked, and the client connects out to it. Because the client starts the connection, NAT creates a mapping and the firewall sees an ordinary outbound flow. This is why passive mode is the default in most clients and browsers today.

The reply 227 encodes the port in two bytes. Given (10,0,0,5,195,80), the port is 195 × 256 + 80 = 49 920 + 80 = 50 000.

Commands, replies and transfer type

  1. Client connects to server port 21; server replies 220 service ready.
  2. USER alice → 331 need password; PASS secret → 230 logged in.
  3. CWD /pub and PWD to move around and confirm the directory.
  4. TYPE I for binary, TYPE A for text.
  5. PORT 192,168,1,7,195,81 (active) or PASV → 227 (passive).
  6. RETR report.pdf to download, STOR upload.zip to upload, LIST for a directory listing.
  7. Server sends 150 opening data connection, the bytes flow on the data connection, then 226 transfer complete on the control connection.
  8. QUIT → 221 goodbye; control connection closes.

Every reply is three digits plus optional text. The first digit gives the class: 2xx success, 3xx need more information, 4xx temporary failure (retry), 5xx permanent failure (do not retry). So 331 means the user name was accepted and a password is wanted.

TYPE A treats the file as text and translates line endings, which corrupts a .zip or .jpg; TYPE I sends the bytes untouched. Always use TYPE I for anything that is not plain text.

Anonymous FTP lets anyone log in with USER anonymous and any email address as the password, for public software archives.

The password crosses the control connection as plain text. Anyone who can watch the path reads it. Chapter 6.7 covers the encrypted replacements.

Worked example

Question. A client at 192.168.1.7 downloads a 20 MB file from 10.0.0.5 using active FTP. The control connection runs from client port 50000, and the client announced client port 50001 with PORT. (a) Give the ports at both ends of the control connection and of the data connection. (b) The data connection runs at 8 Mbps; how long does the download take if overhead is ignored?

  1. (a) The control connection is started by the client, so its client end is the temporary port 50000 and its server end is the well-known port 21.
  2. The data connection in active mode is started by the server from its port 20, to the port the client named in PORT, which is 50001.
  3. So control = 50000 → 21, data = 20 → 50001.
  4. (b) Convert the file size to bits: 20 MB = 20 × 8 = 160 Mbit.
  5. The link delivers 8 Mbit every second.
  6. Time = size ÷ rate = 160 Mbit ÷ 8 Mbit/s = 20 s.

Answer. Control connection: client port 50000 to server port 21. Data connection: server port 20 to client port 50001. The 20 MB file takes 20 s at 8 Mbps.

Exam traps

  • Writing port 20 for every FTP connection. Port 20 belongs only to the server end of an active-mode data connection; in passive mode the server uses a high port and the client opens the connection.
  • Thinking the data connection lasts the whole session. It exists only while one file or listing is being transferred.
  • Using TYPE A for a .zip, .jpg or .exe. The line-ending translation corrupts the file; use TYPE I.
  • Reading a PASV reply as a single port number. The last two numbers are two bytes: port = first × 256 + second.
  • Assuming FTP is safe because it asks for a password. The password travels in clear text on the control connection.

Analyze A user behind a home NAT can download with passive FTP but not with active FTP. Explain why. 5 marks

In active mode the server opens a connection to the private address and port the client announced; the NAT has no mapping for that inbound connection and a firewall may block it. In passive mode the client opens the connection outward to the server's high port, which makes the NAT create a mapping, so the replies come back normally.

Apply A 5 MB file is downloaded over a data connection running at 4 Mbps. Ignoring overhead, how long does the transfer take? 4 marks

The attacker reads the USER and PASS lines in clear text, and can also read and modify file bytes. Encrypting the session, for example with FTPS or by switching to SFTP, removes the exposure, because the same data is then inside a protected channel.

Beyond the syllabus

Not for the exam. Most modern file movement has moved away from FTP: SFTP over SSH and HTTPS-based object storage APIs carry the same job with encryption built in. Web browsers dropped FTP support, so the protocol now lives mostly in build scripts, embedded devices and legacy backup tools. Researchers care about FTP as a clean example of a protocol that separates control from data, an idea reused in SIP and in some media streaming setups. Search for FTPS versus SFTP, and for the FTP reply code list, if you meet one of these systems at work.

6.6 Electronic mail and SMTP

Email is a push then pull system. Your mail client pushes a message to your outgoing mail server over SMTP. That server pushes it to the receiver's mail server, which keeps it in a mailbox. Later the receiver's phone or laptop pulls the message out with POP3 or IMAP. This split exists because the two computers are rarely awake at the same time: the receiving server is always on, so it can hold mail. Every mail you send, from a UPI alert to an IRCTC ticket, follows this path.

You need: TCP sockets and ports from Chapter 6.2, DNS name lookup from Chapter 6.3, and the separate-control-and-data idea from Chapter 6.5.

Four roles, two directions

Four pieces take part. The user agent (UA) is the program you type into: Gmail in a browser, Outlook, or a phone mail app. The mail server stores and forwards mail. Each user has a mailbox on a server, holding incoming messages, and an outgoing queue, holding messages not yet delivered.

Sending is a push. The UA opens a TCP connection to its own mail server and hands over the message. That server looks up the receiver's domain with DNS, finds the receiver's mail server, and opens a second TCP connection to push the message there. So SMTP runs twice: client to own server, then server to server.

If the second transfer fails, the message stays in the outgoing queue. The server retries later, often for a few days, then returns a bounce message to the sender. The receiver's UA never contacts the sender; it pulls from its own server. SMTP is push-only. It cannot ask a server for your mail. That is why a separate pull protocol exists.

SMTP commands, replies, and the 7-bit limit

SMTP is a text protocol on TCP port 25; port 587 is the submission port a mail client uses to hand over outgoing mail. The client sends commands, the server sends three-digit replies. A short session:

EHLO opens the session and names the client. MAIL FROM gives the sender, RCPT TO gives one receiver (repeat for more), DATA starts the message, a line with a single dot ends it, and QUIT closes. Replies: 220 service ready, 250 command okay, 354 send the message, 550 no such mailbox or rejected. A 550 at RCPT TO makes the sender's server bounce the mail.

SMTP was built for 7-bit ASCII only: each character must fit in 7 bits. Photos, PDFs and Hindi text do not. MIME fixes this by adding headers. Content-Type says what the part is, such as image/jpeg or text/plain; charset=UTF-8. Content-Transfer-Encoding says how it was made ASCII-safe: base64 for binary, quoted-printable for mostly text. A multipart message uses a boundary string to separate parts.

encoded size = original size × 4 ÷ 3

original size is the binary attachment in bytes; encoded size is the base64 text in bytes, about one third larger.

Pull: POP3 and IMAP

Reading is a pull. POP3, TCP port 110, downloads messages to the client and usually deletes them from the server. It is simple and works offline, but a second device sees nothing. IMAP, TCP port 143, keeps mail on the server and synchronises folders, read and unread flags, and deletions across devices. Your phone and laptop show the same inbox.

6.7 Basics of network security

Network security is the set of tools that keep a message secret, unchanged and from the right sender. Every tool serves one of three goals: confidentiality (only the receiver can read), integrity (no one can alter silently) and authentication (the sender is who they claim). A fourth goal, availability, keeps the service running. You meet these goals daily: HTTPS on a bank page, a UPI payment, an IRCTC login. This chapter lists the attacks, then shows how keys, hashes, certificates and firewalls each cover a goal.

You need: Chapter 6.4 for HTTP and Chapter 6.2 for sockets; see Unit 1 for where security sits in the stack.

Attacks and the goals they break

An attacker can do five basic things. Eavesdropping: read packets on the wire, such as a password sent in plain HTTP. Tampering: change bytes in transit. Masquerading: pretend to be another host, such as a fake Wi-Fi hotspot. Replay: send a recorded valid message again, such as a repeated “pay ₹500” request. Denial of service (DoS): flood a server so real users are refused.

Each attack breaks a goal. Confidentiality stops eavesdropping. Integrity stops tampering. Authentication stops masquerading. Non-repudiation stops a sender denying a message later. Availability keeps service during DoS. No single tool covers all five. A key gives confidentiality; a hash or MAC gives integrity; a signature gives authentication and non-repudiation; firewalls and capacity planning protect availability.

Symmetric and asymmetric keys

Encryption turns plaintext M into ciphertext C; decryption turns C back into M. A key K controls the transformation. Symmetric encryption uses one shared key: C = E(K, M) and M = D(K, C). It is fast and used for bulk data. The hard part is key distribution: how do two sides get the same K without an attacker reading it?

Asymmetric encryption gives each user a public key that anyone may know and a private key kept secret. RSA is the classic example. For modulus n = p·q and public exponent e, encryption is C = Me mod n; decryption is M = Cd mod n. Here p and q are secret primes, n is public, e is public, and d is the private exponent with e·d ≡ 1 mod φ(n), where φ(n) = (p−1)(q−1). The exponent e must satisfy gcd(e, φ(n)) = 1, which guarantees that d exists. It is slow, so it sends a small key or a signature, not a whole file.

To hide a message, encrypt with the receiver's public key and decrypt with the receiver's private key. To sign, do the opposite: sign with your own private key and verify with your public key. Diffie–Hellman agrees a shared secret over an open channel. Each side picks a secret random exponent (x for one side, y for the other) and sends gx mod p and gy mod p over the open channel; p and g are public, x and y stay secret, and both sides compute the shared secret gxy mod p.

Hashes, signatures, certificates and TLS

A cryptographic hash H maps any message M to a fixed digest h = H(M). It is one-way and collision-resistant. A hash alone gives integrity only if h arrives through a trusted path. A MAC adds a shared key: MAC = H(M || K). The receiver recomputes it with K. It gives integrity and authentication between parties that share a key.

A digital signature hashes the message and encrypts the hash with the sender's private key; anyone verifies with the sender's public key. It gives integrity, authentication and non-repudiation. A certificate binds a name to a public key and is signed by a certificate authority (CA) that clients trust. Without it, a client cannot tell a real bank server from a masquerader.

TLS wraps HTTP (HTTPS) and can wrap a plain socket. It uses certificates, asymmetric key exchange, then symmetric encryption for data. A lab web server with SSL accepts TCP, wraps the socket with an SSL context, reads HTTP and replies.

Firewalls and where they fail

A firewall sits between networks and allows or blocks traffic by rule. A stateless packet filter checks each packet alone: source and destination IP addresses, ports, and TCP flags such as SYN or ACK. One rule may allow inbound TCP port 443 to the web server and drop other inbound traffic. A stateful firewall keeps a connection table. It allows a reply from a server only if an outgoing request opened the connection.

An application proxy ends the connection and inspects the application data, such as HTTP requests. A DMZ is a separate subnet for public servers. The internet reaches the DMZ, but the DMZ has limited access to the internal LAN, so a break-in does not expose payroll machines. A firewall fails against an inside attacker with a trusted address. It also fails to see encrypted malware inside port 443 HTTPS traffic.

Worked example

Question. In a toy RSA system p = 3, q = 11 and public exponent e = 3. Find n and φ(n). Find the private exponent d. Encrypt the message M = 5 to ciphertext C, then decrypt C and show that M returns.

  1. n = p·q = 3 × 11 = 33.
  2. φ(n) = (p−1)(q−1) = 2 × 10 = 20.
  3. d solves e·d ≡ 1 mod φ(n). 3 × 7 = 21 ≡ 1 mod 20, so d = 7.
  4. C = Me mod n = 53 mod 33 = 125 mod 33 = 26, since 33 × 3 = 99 and 125 − 99 = 26.
  5. Decrypt: M = Cd mod n = 267 mod 33. Take 262 = 676 ≡ 16 mod 33; 264 ≡ 162 = 256 ≡ 25 mod 33; 267 = 264 × 262 × 26 ≡ 25 × 16 × 26. Now 25 × 16 = 400 ≡ 4, and 4 × 26 = 104 ≡ 5 mod 33.

Answer. n = 33, φ(n) = 20, d = 7, ciphertext C = 26, and decryption returns M = 5.

Exam traps

  • To hide a message, encrypt with the receiver's public key and decrypt with the receiver's private key. To sign, sign with your own private key and verify with your public key. Keep φ(n) and d secret; n and e are public.
  • A hash is not encryption. It has no key in its basic form, cannot be reversed, and gives integrity, not confidentiality. A MAC adds a shared key for integrity and authentication.
  • Symmetric encryption is fast and suits bulk data; asymmetric encryption is slow and suits key exchange or signatures. Do not say public-key encryption replaces symmetric encryption.
  • A digital signature does not hide the message. It proves origin and integrity; for secrecy you must also encrypt.
  • A firewall guards the perimeter. It cannot stop an inside attacker with a trusted address. No packet-filtering firewall, stateless or stateful, can inspect malware hidden inside encrypted HTTPS traffic on port 443; it can only allow or block the connection.

  3. DNS resolves names through a hierarchy of servers and uses caching to cut repeated round trips.
  4. HTTP is a short, stateless request-reply protocol; cookies add remembered state.
  5. FTP keeps commands on a control connection and sends each file on a separate data connection.
  6. Email is pushed by SMTP to the receiver's mail server and pulled out by POP3 or IMAP.
  7. Network security aims at confidentiality, integrity and authentication.
  8. Firewalls range from stateless filters to stateful firewalls and application proxies, with a DMZ for public servers.

Exam question bank

Long answers usually ask for protocol flows, socket calls, message formats and a clear mapping from attacks to security controls.

Remember and understand

Understand Compare client-server and peer-to-peer application architectures. Explain two-tier and three-tier designs, the role of a central directory, and when a server is stateless or stateful. 12 marks

client asks, server provides; peer can be both; two-tier: client to server/database; three-tier: client, application server, data server; central directory helps peers find each other; stateless vs stateful affects cookies, sessions and scaling.

Understand Explain a socket as an IP address plus port. Describe the main calls for a TCP server and client, and how UDP socket calls differ. 10 marks

socket endpoint, port identifies process; TCP calls: socket, bind, listen, accept, connect, read/write, close; UDP calls: socket, sendto, recvfrom; no connection setup; blocking and message boundaries differ.

Understand Describe the DNS name space and the steps of name-to-address resolution. Distinguish recursive and iterative queries and explain caching. 12 marks

tree: root, top-level domains, authoritative servers; resolver asks root, then TLD, then authoritative server; recursive server does work; iterative server returns referral; cache with TTL reduces lookups.

Understand Explain HTTP as a request-reply protocol over TCP. Include request line, headers, methods, status codes, statelessness and cookies. 12 marks

TCP connection carries readable request and reply; method, path, version; headers; body; status code classes 2xx, 3xx, 4xx, 5xx; HTTP keeps no state; cookies and server sessions add state.

Understand Explain FTP control and data connections. Compare active and passive modes and give one reason each is used. 12 marks

control connection stays open for commands; data connection opened per file transfer; active: server connects back to client; passive: client connects to server; helps with NAT and firewalls.

Understand Explain how email moves from sender to receiver using SMTP, POP3 and IMAP. Show the role of MIME and the main SMTP commands. 12 marks

user agent to mail server; SMTP between servers; commands: EHLO, MAIL FROM, RCPT TO, DATA, QUIT; MIME carries non-text content; POP3 downloads; IMAP keeps server state and folders.

Apply

Apply Trace what happens when a user types a URL and presses Enter, from DNS lookup through TCP connection to HTTP response. Where can caching occur? 14 marks

parse URL; DNS cache and resolver lookup; TCP connect to server IP and port 80 or 443; send HTTP request; server returns status, headers, body; caches at browser, DNS resolver and HTTP proxy or CDN.

Apply Write pseudocode for a TCP echo server and client. Explain why the receiver still needs message framing even though TCP is reliable. 10 marks

server: socket, bind, listen, accept, read, write; client: socket, connect, write, read; TCP is a byte stream, not message records; use length prefix or delimiter to find message ends.

Apply An FTP client is behind a NAT. Explain why passive mode often works better than active mode, using control and data connections. 12 marks

control connection is client to server; active mode: server opens data connection to client port; NAT may block inbound connection to client; passive mode: client opens data connection to server data port.

Apply Describe the SMTP dialogue for sending one message from alice@a.example to bob@b.example, then how Bob retrieves it with IMAP. List commands in order. 12 marks

EHLO, MAIL FROM, RCPT TO, DATA, message, period, QUIT; server queues and delivers to bob's mail server; IMAP login, select mailbox, fetch message; MIME headers identify content type.

Analyze and evaluate

Analyze Map confidentiality, integrity and authentication to eavesdropping, tampering, masquerading and replay. Which tool serves each goal? 14 marks

eavesdropping countered by encryption; tampering countered by integrity check or MAC; masquerading countered by authentication and certificates; replay countered by nonces, timestamps or sequence numbers.

Evaluate Compare stateless packet filter, stateful firewall and application proxy. Where does a DMZ fit and what does each control cost? 12 marks

packet filter uses header fields only; fast but limited; stateful firewall tracks connections; better return traffic control; proxy inspects application data; slower and more complex; DMZ holds public servers between internet and internal network.

Analyze HTTP is stateless. Analyse how cookies and server-side sessions add state, and the privacy and scaling tradeoffs. 12 marks

cookie stores identifier at client; session state stored at server or in token; scaling needs shared session store; privacy risks from tracking and stolen cookies.

Evaluate Compare TCP and UDP for HTTP, DNS, live video and a chat app. Justify each choice with reliability, delay and connection overhead. 14 marks

HTTP uses TCP for reliable ordered bytes; DNS uses UDP for short queries and TCP for large or zone transfer; live video may use UDP and tolerate loss; chat needs reliability; TCP or reliable UDP layer.

Glossary

Active mode
FTP mode where the server opens the data connection back to the client.
Anonymous FTP
Public FTP service that accepts a generic anonymous login.
Application proxy
Firewall that terminates and inspects application protocol sessions.
Asymmetric encryption
Encryption with public and private keys; the public key encrypts and the private key decrypts.
Central directory
Shared index that peers use to find other peers or resources.
DATA
SMTP command that starts the message body and ends with a line containing only a period.
Denial of service
Attack that makes a service unavailable by exhausting resources.
DMZ
Network segment between the internet and internal network that holds public-facing servers.
Eavesdropping
Passive reading of messages on the network.
EHLO
SMTP command that opens a session and asks for supported extensions.
Fully decentralised overlay
Peer-to-peer network with no central index or control point.
IMAP
Mail access protocol that keeps messages on the server and supports folders and synchronised state.
MAIL FROM
SMTP command that names the sender.
Mail server
Host that stores mailboxes and runs SMTP and mail access protocols.
Mailbox
Server-side storage area for a user's email.
Masquerading
Pretending to be another party or host.
Outgoing queue
Messages waiting for SMTP delivery attempts.
POP3
Simple mail access protocol that usually downloads messages to one client.
RCPT TO
SMTP command that names one recipient.
Replay
Re-sending a valid captured message later.
Stateless packet filter
Firewall that decides each packet alone from header fields.
Tampering
Unauthorised change of data in transit.
Tiers
Separate logical layers in an application architecture, such as client, application server and data server.
TYPE A
FTP transfer type for ASCII text with end-of-line conversion.
TYPE I
FTP transfer type for raw binary with no line conversion.
User agent
Mail program the user reads and composes messages with.
