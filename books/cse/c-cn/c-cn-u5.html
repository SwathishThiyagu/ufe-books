5.1 Transport services: ports, multiplexing and demultiplexing

IP delivers a packet to a host. A host runs many programs, so the packet must still reach the right process. The transport layer adds a 16-bit port number to the IP address and uses that pair to hand data to the correct application. This is process-to-process delivery. It is why a phone can run a web browser, a DNS lookup and a video call at the same time. Ports appear whenever you type a URL, configure a firewall, or read that a service listens on port 443.

You need: Unit 1 for layering and the TCP/IP suite, and Unit 4 for IPv4 addresses and datagram delivery.

From host delivery to process delivery

The network layer carries a datagram from one host to another host. Its address identifies an interface on a host. The transport layer goes one step further: it delivers data to a process, meaning a running program. To do that it uses port addressing and a socket address.

  • Process-to-process delivery: identify the receiving program.
  • Port addressing: carry a 16-bit port number.
  • Segmentation and reassembly: split an application message into segments and put it back together.
  • Connection control: for TCP, open and close a connection; for UDP, no connection.

An IP address alone cannot name a process, because many processes share one host. A port number is a 16-bit unsigned integer, so it ranges from 0 to 65535. A socket address is an IP address plus a port number, written 192.0.2.10:80. Some syllabi call the port a TSAP, Transport Service Access Point, and call the IP-plus-port pair a socket.

Port ranges and socket addresses

The 16-bit port space is divided by convention, not by hardware. The ranges below are the standard assignment.

RangeNameTypical use
0-1023Well-knownStandard services
1024-49151RegisteredStable user services
49152-65535DynamicTemporary client ports

A client asking a server usually gets an ephemeral source port from its operating system. Ephemeral means short-lived; the port is freed after the connection closes. The server uses a well-known port such as 80 for HTTP or 53 for DNS. Registered ports are used by applications that need a stable number without being part of the standard set. The pair of IP address and port is the socket address.

A server has a listening socket on its well-known port. When a client connects, TCP creates a separate connection socket for that client. Both sockets can show port 80 at the server, but they are different sockets.

Multiplexing and demultiplexing

Multiplexing happens at the sender: the transport layer collects data from several processes, adds a port number to each segment, and passes the segments to IP. Demultiplexing happens at the receiver: the transport layer reads the port fields and delivers each segment to the right process. The lookup rule differs between UDP and TCP.

For a connectionless protocol such as UDP, demultiplexing uses the destination port. The receiving socket may be bound to a local IP address, but there is no per-connection four-tuple. A UDP server on port 53 receives all DNS queries addressed to that port and uses the source fields only if it needs to reply.

For connection-oriented TCP, demultiplexing uses the four-tuple: source IP, source port, destination IP, destination port. Two browsers on one client talking to one web server have the same server IP and port. Only the client source port separates their connections. A server that demultiplexed by destination port alone would mix the two connections. The four-tuple also identifies the connection during connection setup and release.

Worked example

Question. A web server at 192.0.2.10:80 is serving two browsers on the same client host 203.0.113.7, using source ports 52000 and 52001. Write the four-tuple the server transport layer uses to demultiplex each arriving segment, and say why the pair (192.0.2.10, 80) is the same for both.

  1. Server socket address: IP 192.0.2.10, port 80.
  2. Client host: IP 203.0.113.7. First browser source port: 52000.
  3. Four-tuple order is source IP, source port, destination IP, destination port. Connection 1: (203.0.113.7, 52000, 192.0.2.10, 80).
  4. Second browser source port: 52001. Connection 2: (203.0.113.7, 52001, 192.0.2.10, 80).
  5. Both segments have destination IP 192.0.2.10 and destination port 80 because they go to the same server service. The source port differs, so TCP treats them as two connections.

Answer. Connection 1 is (203.0.113.7, 52000, 192.0.2.10, 80) and connection 2 is (203.0.113.7, 52001, 192.0.2.10, 80); the shared server socket address means the source port separates the two connections.

Exam traps

  • Demultiplexing TCP by destination port alone; two clients of one server then look like one connection.
  • Calling port 80 the connection; it is only one field. The TCP connection is the four-tuple.
  • Mixing up multiplexing at the sender with demultiplexing at the receiver.
  • Forgetting that a port is 16 bits: 0 to 65535, not 0 to 65536.
  • Treating the listening socket as the connection socket; accept creates a new socket per client.

5.2 User Datagram Protocol (UDP)

UDP is the smallest transport protocol that still does the transport layer's one essential job: it adds port numbers so the receiving host can hand a packet to the right process. It opens no connection, keeps no state, retransmits nothing and slows down for nobody. For file transfer that is a bad deal. For a DNS lookup, a DHCP request, an SNMP poll or a live voice packet it is exactly right: one short question, one short answer, and a retry costs less than a delay.

You need: Chapter 5.1 for ports and demultiplexing, and the IPv4 header and MTU from Unit 4.

Eight bytes, four fields

A UDP datagram is an 8-byte header followed by the application's data. There is no options field, no padding and no variable part.

Source port (16 bits) identifies the sending process. A host that expects no reply may put zero here, but the receiver copies this value into the destination port of its reply, so it is normally filled.

Destination port (16 bits) selects the receiving process. This field together with the destination IP address is what demultiplexes the datagram, as Chapter 5.1 explains.

Length (16 bits) counts the header and the data together. The smallest legal value is 8 and the largest is 65535, so the data can be at most 65535 − 8 = 65527 bytes.

max UDP data = 2¹⁶ − 1 − 8 = 65527 bytes

2¹⁶ − 1 = 65535 is the largest value a 16-bit field can hold, and 8 is the fixed header size in bytes.

That is the field's limit. Over IPv4 the IP total length caps the whole datagram at 65535 bytes, so with a 20-byte IP header the largest payload an application can really send is 65535 − 20 − 8 = 65507 bytes.

Checksum (16 bits) covers a pseudo-header, the header and the data. It is optional in IPv4 and mandatory in IPv6.

What UDP leaves out

Connectionless. There is no handshake, no state at either end and no teardown. Each datagram is independent, and the first one to arrive may be the only one.

Unreliable. UDP does not acknowledge, retransmit, reorder or detect duplicates. A lost or corrupted datagram is dropped silently and the sender is never told. An application that cares supplies its own timer and retry.

Message-oriented. One send produces one datagram, and one receive returns exactly that datagram with its boundaries intact. TCP hands the application a byte stream instead, where two writes may come back as one read (Chapter 5.3).

No flow control, no congestion control. UDP sends as fast as the application asks. A slow receiver's buffer can overflow and a busy network can be pushed further into loss, and UDP will not slow down.

Checksum and pseudo-header

The checksum protects more than the datagram. Before summing, the sender builds a 12-byte pseudo-header from IP fields: source IP address (4 bytes), destination IP address (4 bytes), a zero byte, the protocol number 17 (1 byte) and the UDP length (2 bytes). It is never transmitted; it exists only for the arithmetic.

The sender adds, in 16-bit one's complement arithmetic, the pseudo-header, the 8-byte UDP header with the checksum field set to zero, and the data. The one's complement of that sum is written into the checksum field.

The receiver runs the same sum over what arrived plus its own pseudo-header. A result of all ones means accept; anything else means discard silently.

The pseudo-header catches a datagram delivered to the wrong host or the wrong upper-layer protocol, because the addresses would no longer match. It also catches a wrong length.

In IPv4 a checksum field of all zeros means not computed and the receiver skips verification. IPv6 allows no such escape: the checksum is mandatory there, because IPv6 dropped its own header checksum.

Where UDP is the right choice

Query-response protocols whose whole exchange fits one datagram: DNS, DHCP, SNMP and RIP.

DHCP is the cleanest example. The client has no IP address yet, so it sends from 0.0.0.0 to the broadcast address. A connectionless protocol needs no reachable server and no handshake; TCP could not start here.

TFTP carries small file transfers over UDP and adds its own stop-and-wait acknowledgements in the application.

Real-time voice and video: a late packet is worse than a lost one, so a retransmission would only add delay.

Multicast and broadcast: UDP is the transport such traffic uses, because TCP needs exactly two endpoints and a handshake.

Worked example

Question. A DNS query carries 40 bytes of application data inside a UDP datagram. (a) What value goes into the UDP length field? (b) The datagram then leaves on an Ethernet link whose MTU is 1500 bytes, and the IPv4 header is 20 bytes. What is the largest UDP payload that fits in one frame without IP fragmentation?

  1. The length field counts the 8-byte header plus the data: length = 8 + 40 = 48 bytes.
  2. The MTU is the largest IP datagram the frame can carry: at most 1500 bytes.
  3. Subtract the 20-byte IPv4 header. Space left for the UDP datagram = 1500 − 20 = 1480 bytes.
  4. That 1480 bytes includes UDP's own 8-byte header, so payload = 1480 − 8 = 1472 bytes.

Answer. (a) length = 48 bytes; (b) the largest UDP payload is 1472 bytes.

Exam traps

  • Length counts header plus data. A 40-byte DNS query gives a length of 48, not 40, because the field describes the whole datagram.
  • The pseudo-header is never on the wire, yet it must be added when computing or checking the checksum. Leaving it out makes every sum wrong.
  • A zero checksum is an IPv4-only escape. In IPv6 the checksum is always required, and a zero field is an error.
  • UDP does not fragment or reassemble; IP does. A 3000-byte write on a 1500-byte-MTU link becomes fragments, and one lost fragment loses the whole datagram.
  • UDP keeps message boundaries and TCP does not. A question saying the sender wrote 100 bytes twice and the receiver read 200 bytes once is describing a byte stream, not UDP.

Understand IP already carries a total length field. Why does UDP need its own length field? 3 marks

IP's total length counts the whole IP datagram, header included, and after reassembly spans every fragment, so it does not by itself give the size of one UDP datagram. Analyze A sender sets the UDP checksum field to 0000 in a datagram carried over IPv4. What does the receiver do, and what risk follows? Would this be legal in IPv6? 4 marks

In IPv4 a zero field means no checksum was computed, so the receiver skips verification and delivers the datagram. Corrupted data, or even corrupted port numbers sending the datagram to the wrong process, then reach the application unnoticed. Understand Why is UDP a better fit than TCP for a DHCP client? 3 marks

The client has no IP address yet, so it sends from 0.0.0.0 to the broadcast address. UDP needs no connection state, no reachable server address and no handshake, so a broadcast request and a broadcast reply work. TCP would need a known peer and a completed handshake before any data.

Analyze An application calls send() with 70000 bytes on a UDP socket. Describe the outcome. If the application instead splits the data into 1000-byte datagrams sent over a link with a 1500-byte MTU, what does IP do to them? 5 marks

70000 exceeds both the 65527-byte field limit and the 65507-byte IPv4 limit, so the call fails with an error and nothing is sent. Split into 1000-byte pieces, each becomes a 1008-byte UDP datagram and a 1028-byte IP datagram, under the 1500-byte MTU, so no fragmentation happens. Each datagram arrives or is lost independently.

Remember Name two services UDP does not provide. 2 marks

Any two of: connection setup, reliability (acknowledgement and retransmission), ordering, duplicate detection, flow control, congestion control.

Beyond the syllabus

Not for the exam. QUIC, the transport behind HTTP/3, is built on UDP: it adds reliability, ordered streams and congestion control in user space, so browsers and servers can improve without waiting for the operating system's TCP to change. UDP-Lite carries a partial checksum, letting a voice codec accept a few corrupted bits instead of losing the whole packet. DTLS adds TLS-style security to datagram traffic. Search for QUIC, UDP-Lite, DTLS and head-of-line blocking to see why the datagram model came back into fashion.

5.3 TCP services and segment format

TCP is the transport protocol behind web pages, email and file downloads. It turns the unreliable packet service of IP into a reliable, ordered stream of bytes between two processes. It does this with a connection, sequence numbers and acknowledgments. The 20-byte TCP header carries the two 32-bit numbers that make the whole thing work: the sequence number says which byte this segment starts at, and the acknowledgment number says which byte the receiver wants next. This chapter opens that header field by field.

You need chapter 5.1 for ports and the four-tuple, and chapter 5.2 for the checksum and pseudo-header.

Services: a reliable byte stream

TCP sits directly above IP. IP moves packets between hosts; TCP turns that into a connection between two processes, using the port numbers of chapter 5.1. The connection is identified by four values: source IP, source port, destination IP and destination port.

  • Connection-oriented. Both ends agree to talk before any data byte moves.
  • Reliable. Every byte is acknowledged; bytes that do not arrive are sent again.
  • Ordered byte stream. The receiver reads the same bytes in the same order. A write of 5000 bytes may arrive as three segments.
  • Full duplex. Data flows both ways at once; each direction has its own sequence numbers.
  • Flow control. The receiver advertises how much buffer space it has (chapter 5.5).
  • Congestion control. The sender probes the network and backs off when loss appears (chapter 5.6).

One connection carries one logical byte stream. TCP does not keep application message boundaries: if the program needs records, it must mark them itself.

Sequence numbers count bytes, not segments

TCP numbers every byte in the stream, not every segment. The two directions are numbered independently. Each side chooses an initial sequence number when it opens the connection (chapter 5.4). The SYN that opens the connection consumes one sequence number; after that, data bytes follow.

seq = S₀ + B

seq is the sequence number field of this segment; S₀ is the sequence number of the first data byte in this direction; B is the number of data bytes sent earlier in this connection.

The acknowledgment number is the next byte the receiver expects. It is cumulative: it confirms every byte below that number. If bytes 5000 to 7499 have arrived in order, the receiver sends acknowledgment number 7500. It does not send 7499.

ack = S₀ + R

ack is the acknowledgment number; S₀ is the sequence number of the first data byte; R is the number of data bytes received in order so far.

  • Segment carrying bytes 5000–5999: sequence number 5000.
  • Segment carrying bytes 6000–6999: sequence number 6000.
  • After both arrive, acknowledgment number is 7000.
  • SYN and FIN each consume one sequence number; their handling belongs to chapter 5.4.

The header, field by field

Every TCP segment begins with a fixed 20-byte header. Options may add up to 40 bytes, so the header is 20 to 60 bytes. The fields are:

FieldSizeWhat it holds
Source port16 bitsSender process port.
Destination port16 bitsReceiver process port.
Sequence number32 bitsNumber of the first data byte in this segment.
Acknowledgment number32 bitsNext byte expected from the other direction.
Data offset4 bitsHeader length in 32-bit words; 5 means 20 bytes.
Reserved + flags12 bitsURG, ACK, PSH, RST, SYN, FIN, plus later CWR and ECE.
Window16 bitsReceiver's advertised window for flow control.
Checksum16 bitsMandatory; covers header, data and pseudo-header (same as UDP).
Urgent pointer16 bitsPoints to urgent data when URG is set.

The data offset counts 32-bit words, not bytes. A header of 24 bytes has data offset 6.

  • SYN starts a connection and FIN ends it.
  • ACK says the acknowledgment number is valid.
  • RST aborts the connection.
  • PSH asks the receiver to deliver data promptly.
  • URG marks urgent data; CWR and ECE support congestion notification.

Options carry MSS (maximum segment size, the largest TCP payload this side can receive), window scale, SACK permitted, and timestamp. If no MSS option is sent, the default MSS is 536 bytes. The option field is padded to a multiple of 4 bytes.

Worked example

Question. A TCP sender's first data byte is numbered 5000. It sends three segments carrying 1000, 1000 and 500 bytes of data. (a) Give the sequence number field of each segment. (b) Give the acknowledgment number the receiver returns after all three arrive in order. (c) Give the data offset value when the header carries a 4-byte MSS option.

  1. Segment 1 starts at byte 5000 and carries 1000 bytes, so its sequence number is 5000.
  2. Segment 2 starts after 1000 bytes: 5000 + 1000 = 6000.
  3. Segment 3 starts after 2000 bytes: 5000 + 2000 = 7000.
  4. Total data = 1000 + 1000 + 500 = 2500 bytes.
  5. Acknowledgment number = 5000 + 2500 = 7500, the next byte expected.
  6. Header length = 20-byte fixed part + 4-byte MSS option = 24 bytes.
  7. Data offset is in 32-bit words: 24 ÷ 4 = 6.

Answer. The sequence numbers are 5000, 6000 and 7000; the acknowledgment number is 7500; the data offset is 6.

Exam traps

  • Counting segments instead of bytes: sequence numbers advance by the number of data bytes, not by one per segment.
  • Reading the acknowledgment number as the last byte received. It is the next byte expected, so it is one more than the last in-order byte.
  • Reading the data offset as bytes. It is in 32-bit words; 5 means 20 bytes, 6 means 24 bytes.
  • Confusing MSS with MTU. MSS is the largest TCP payload; MTU is the largest IP packet. The default MSS when no option is sent is 536 bytes.
  • Assuming TCP keeps message boundaries. A single application write can be split across segments, and one segment can carry bytes from two writes.

Analyze Why is the TCP checksum mandatory while the UDP checksum is optional in IPv4? 4 marks

Understand What is the purpose of the window field in the TCP header? 3 marks

The window field tells the sender how many bytes the receiver can accept beyond the acknowledgment number. It is the receiver's flow-control limit, so the sender must not have more unacknowledged bytes in flight than this window.

Beyond the syllabus

Not for the exam. In real stacks the TCP header is often compressed: a 20-byte header can shrink to a few bytes on a phone link, because most fields change little from packet to packet. Modern kernels also use TCP segmentation offload, so the header you read in a capture may be built by the network card, not the CPU. QUIC moves reliability and ordering into a new protocol above UDP, but it still carries the same ideas of sequence numbers, acknowledgments and windows. 5.4 TCP connection establishment and release

TCP is a byte stream, but it starts and ends like a phone call: both sides must agree they are ready before data flows, and both must agree when the conversation is over. It opens with three segments, the three-way handshake, which synchronises two initial sequence numbers. It closes with four segments, one FIN and one ACK from each side, then waits in TIME-WAIT. Every UPI payment, IRCTC booking and web page load that uses TCP depends on this connection management.

You need: the sequence number, acknowledgment number and flag fields from Chapter 5.3.

Opening: the three-way handshake

TCP is connection-oriented, so before any byte of data the two processes must agree on two starting points for their byte streams. Each side chooses an initial sequence number (ISN): a 32-bit starting value for the sequence numbers it will use. The SYN itself uses that number, so the first data byte is ISN+1. The ISN is not zero because a delayed segment from an earlier connection between the same port pair could otherwise be mistaken for new data. Modern stacks also randomise it for security.

The exchange uses the SYN flag. A SYN segment carries no data but uses one sequence number. The client sends SYN with seq = x. The server answers with SYN + ACK, seq = y and ack = x+1; the ack says "I got x, next I expect x+1". The client sends ACK with ack = y+1. The connection is now ESTABLISHED at both ends.

  1. Client to Server: SYN, seq = x. Client state SYN-SENT.
  2. Server to Client: SYN + ACK, seq = y, ack = x+1. Server state SYN-RECEIVED.
  3. Client to Server: ACK, ack = y+1. Both ends ESTABLISHED. This third segment may carry data, with seq = x+1.
  4. Simultaneous open: both send SYN, each replies SYN+ACK; the same states apply.

Closing: FIN, ACK and TIME-WAIT

TCP closes each direction separately. The side that finishes sending sends FIN, which uses one sequence number. The other side ACKs it. That half is closed, but the other side may keep sending: this is a half-close. When it also finishes, it sends its own FIN, which is ACKed. So a normal close is four segments: FIN, ACK, FIN, ACK. A server often sends its ACK first, lets the application finish, then sends FIN.

The side that sends the final ACK enters TIME-WAIT and stays there for twice the maximum segment lifetime (2×MSL). MSL is the longest time a segment can survive in the network. TIME-WAIT has two jobs. If the final ACK is lost, the other side retransmits its FIN, and this side can resend the ACK. It also lets old duplicate segments from this connection die before the same port pair is reused.

  • RST aborts a connection or refuses one. A host with no listener on a port answers SYN with RST.
  • CLOSING covers simultaneous close: both sides send FIN before receiving the other side's FIN.

States to recognise

You do not need to memorise the full state-transition diagram for most exams, but you should know these eleven states and one line about each.

StateMeaning

Worked example

Question. A client opens a TCP connection to a server. The client's ISN is x = 2000 and the server's ISN is y = 5000. The client sends 1000 bytes of data, then closes; the server closes after ACKing the data. List the sequence number and acknowledgment number of every segment from SYN to the final ACK, and state which flag each carries.

  1. SYN: seq = 2000. The SYN uses one sequence number, so the next client sequence number is 2001.
  2. SYN + ACK: seq = 5000, ack = 2001. The server's next sequence number is 5001.
  3. ACK: ack = 5001. The client can now send data starting at seq = 2001.
  4. Data: seq = 2001, ack = 5001, length 1000 bytes. It covers sequence numbers 2001 to 3000, so the next client sequence number is 3001.
  5. Server ACK: ack = 3001.
  6. Client FIN: seq = 3001. The FIN uses one sequence number, so the next client sequence number is 3002.
  7. Server ACK: ack = 3002.
  8. Server FIN: seq = 5001. The FIN uses one sequence number, so the next server sequence number is 5002.

  • Using FIN when you mean RST: FIN is an orderly close; RST aborts or refuses a connection.

5.5 TCP flow control

TCP is reliable, but a fast sender can still drown a slow receiver. Flow control is the receiver's brake: each acknowledgment carries a window, the number of free bytes in the receiver's buffer, and the sender may not have more unacknowledged bytes in flight than that. This stops data being dropped when a slow phone pulls a file from a fast server. Only a few universities teach it as a separate topic.

You need: the TCP header window field (Chapter 5.3) and an established connection (Chapter 5.4).

The advertised window

The receiver buffers bytes that have arrived but not yet been read by the application. Two numbers fix its state: LastByteRcvd, the last byte received, and LastByteRead, the last byte the application has taken. The gap between them is data waiting in the buffer.

rwnd = BufSize − (LastByteRcvd − LastByteRead)

rwnd is the free space in bytes, the receive window; BufSize is the receive buffer in bytes; LastByteRcvd and LastByteRead are byte counts.

The receiver writes rwnd into the 16-bit window field of every segment it sends: how many bytes past the acknowledged byte it can still accept. It is not the buffer size.

Sixteen bits cap the field at 65535 bytes, about 64 KB, too small for long fast links. The window scale option, agreed in the handshake, shifts it: real window = field × 2^S, with S from 0 to 14.

Zero window, probes, and silly window syndrome

When the application reads nothing and the buffer fills, rwnd = 0. The sender stops and starts a persist timer. On expiry it sends a window probe, one byte of new or already-acknowledged data, and the receiver's reply carries the current window. If that is still zero the timer doubles. Without probes, one lost window update would deadlock both sides.

The opposite fault is silly window syndrome: a nearly full buffer with a byte-at-a-time reader makes the receiver advertise tiny windows and the sender emit 41-byte packets carrying one byte of data.

  • Receiver side (Clark's solution): never advertise less than min(half the buffer, one maximum segment size); advertise zero instead.
  • Sender side (Nagle's algorithm): while earlier data is unacknowledged, hold small segments until a full one is ready.

Each rule trades a little delay for far fewer packets.

rwnd is not cwnd

The sender may have at most min(rwnd, cwnd) unacknowledged bytes in flight. rwnd is the receiver's free buffer and shrinks when the application is slow. cwnd is the sender's estimate of network capacity and shrinks when segments are lost.

A receiver that never reads can drive rwnd to zero on a perfect network; a congested network can cut cwnd while the receiver has gigabytes free. The first is flow control; the second is congestion control (Chapter 5.6).

The window slides with every acknowledgment: if the ACK covers byte M and advertises W, the sender may send up to byte M + W. It costs nothing extra on the wire, riding in a field every ACK already carries. Both numbers move continuously, rwnd as the application reads, cwnd as ACKs and losses arrive.

Worked example

Question. A TCP receiver has an 8000-byte buffer. At one instant LastByteRead = 0 and LastByteRcvd = 3000. (a) What window is advertised? (b) The sender fills it: what is rwnd now, and what does the sender do? (c) The application reads all 8000 bytes: what is advertised?

  1. Bytes waiting = 3000 − 0 = 3000.
  2. (a) rwnd = 8000 − 3000 = 5000 bytes.
  3. (b) LastByteRcvd = 8000, so rwnd = 8000 − 8000 = 0 bytes.
  4. The sender stops and starts its persist timer; on expiry it sends a one-byte probe.
  5. (c) LastByteRead = 8000, so rwnd = 8000 − (8000 − 8000) = 8000 bytes.
  6. The receiver sends a window update of 8000; the sender resumes.

Answer. rwnd goes 5000 bytes, then 0 bytes, then 8000 bytes.

Exam traps

  • Calling the buffer size the window: an 8000-byte buffer holding 3000 unread bytes advertises 5000, not 8000.
  • Swapping rwnd and cwnd: rwnd is receiver buffer space, cwnd is the network estimate, and the limit is min of the two.
  • Forgetting window scaling: a field value of 65535 means 64 KB only when the scale factor S = 0.
  • Treating rwnd = 0 as a closed connection: it is open, and probes keep it alive until a window update arrives.

5.6 TCP congestion control: slow start, fast retransmit

TCP congestion control decides how many bytes a sender may keep in the network without overloading it. It keeps a congestion window, cwnd, separate from the receiver's flow-control window. A lost segment is treated as a congestion signal: TCP grows cwnd from a small initial value, doubling each round trip (exponential), then linearly in congestion avoidance, and cuts it on loss. The main mechanisms are slow start, congestion avoidance, timeout, fast retransmit and fast recovery. The same logic runs in every TCP connection, from a UPI payment to a web page load.

You need: Chapter 5.3 for the TCP header and Chapter 5.5 for rwnd, so cwnd is not confused with the receiver's window.

The congestion window and the threshold

IP routers have finite queues. If TCP senders send faster than a link can carry, queues fill and packets drop. TCP congestion control is sender-side: each sender estimates safe load from ACKs and losses.

Each connection keeps two variables. The congestion window, cwnd, limits the sender's unacknowledged bytes in the network. It is measured in bytes or in MSS; 1 MSS is one maximum segment size, for example 1000 bytes. The slow-start threshold, ssthresh, is the cwnd value where TCP leaves slow start. Both are per connection.

The send limit is min(cwnd, rwnd). rwnd is the receiver's advertised free buffer from flow control. cwnd protects the network; rwnd protects the receiver. A sender with cwnd = 8 MSS and rwnd = 5 MSS may have at most 5 MSS unacknowledged.

TCP treats ACKs as permission to send more and losses as congestion signals. This gives additive increase, multiplicative decrease (AIMD): rise about one MSS per round trip, cut on loss.

Slow start and congestion avoidance

Slow start begins with cwnd = 1 MSS. For every ACK of new data, add one MSS. With no loss, cwnd doubles each round trip: 1, 2, 4, 8 MSS. The name is historical; this phase is exponential and fills an empty pipe quickly.

When cwnd reaches ssthresh, TCP enters congestion avoidance. Growth becomes roughly linear: about one MSS per round trip. The per-ACK rule is:

cwnd ← cwnd + (MSS × MSS) ÷ cwnd

cwnd is the current congestion window in bytes; MSS is the maximum segment size in bytes; the addition is done for each ACK of new data. In MSS units, cwnd ← cwnd + 1 ÷ cwnd per ACK, so cwnd ACKs add about 1 MSS.

The usual test is: if cwnd < ssthresh, stay in slow start; otherwise use congestion avoidance. In the example, cwnd = 8 MSS equals ssthresh = 8 MSS, so round 5 adds one MSS, not doubles.

AIMD keeps many connections probing upward by one MSS per RTT. On loss each halves cwnd, so total load falls. The rise is gentle; the cut is sharp. This is approximate fairness, not an exact guarantee.

Loss: timeout, fast retransmit, fast recovery

TCP has two loss signals. A retransmission timeout (RTO) means no ACK arrived before the timer. It is a strong signal. Set ssthresh = cwnd ÷ 2, set cwnd = 1 MSS, and re-enter slow start. Some stacks use max(cwnd ÷ 2, 2 MSS); the halving is the key.

Duplicate ACKs are weaker. If one segment is lost but later segments arrive, the receiver repeats an ACK with the same expected sequence number. After three duplicate ACKs, the sender assumes one segment is lost. Fast retransmit resends it at once, without waiting for the RTO. Three duplicate ACKs mean four ACKs with the same number: the original plus three copies.

Fast recovery, as in TCP Reno, avoids cwnd = 1. Set ssthresh = cwnd ÷ 2 and cwnd = ssthresh, then continue in congestion avoidance. TCP Tahoe, older, sets cwnd = 1 MSS after fast retransmit. Reno keeps more data in flight on long paths. Some textbooks write cwnd = ssthresh + 3 MSS during fast recovery; this chapter uses the simplified convention cwnd = ssthresh.

The cycle is: slow start doubles cwnd; congestion avoidance adds about one MSS per RTT; a loss halves ssthresh; cwnd drops to ssthresh (Reno with duplicate ACKs) or 1 MSS (timeout or Tahoe). Fast retransmit needs three later segments, so tiny windows may still rely on the RTO.

Some syllabi add router-side signals. In DECbit, a router sets a congestion bit when its average queue is above a threshold. The receiver copies the bit into the ACK, and the sender slows down. Random Early Detection (RED) keeps an average queue length. Below a minimum threshold it drops nothing. Between minimum and maximum it drops or marks arriving packets with a probability that rises with the average queue. Above the maximum it drops all arrivals. The aim is early, randomized signalling, not a synchronized drop by many TCP flows. Modern data centres also use ECN, which marks instead of drops. Router queue management is only named here; scheduling and reservation belong to Chapter 5.7.

Worked example

5.7 Quality of service and integrated services

Best-effort delivery gives every packet the same treatment: no promise of bandwidth, no limit on delay. Quality of service (QoS) turns that into a contract. Packets are classified into flows, shaped to a rate, queued per flow and scheduled so each flow gets its promised share. Integrated Services goes further and reserves resources for a flow end to end, using RSVP to carry the request and admission control to accept or reject it. You meet this whenever a voice call must not wait behind a file download — a UPI payment, a hospital monitor, a live cricket stream.

You need: Chapter 5.6 for why TCP alone cannot promise delay, and the queueing basics from Unit 3, Data Link Layer and Medium Access.

The four parameters of quality of service

QoS is described by four parameters. Reliability is how much data is lost — the fraction of packets that never arrive. Delay is the time a packet takes from source to destination, in milliseconds. Jitter is the variation in that delay: if packet 1 takes 20 ms and packet 2 takes 55 ms, the jitter is 35 ms. Bandwidth is the rate the flow needs, in bits per second.

Different applications care about different parameters. A file transfer needs reliability and bandwidth and can wait seconds. A voice call needs low delay (under about 150 ms one way), low jitter and only about 64 kbps, but tolerates a little loss. Video needs bandwidth and jitter control. A stock ticker needs reliability and delay together.

Plain IP gives best effort: first come, first served, no guarantee for anyone. Adding bandwidth does not fix jitter, because a bigger pipe still lets one large packet push a small one aside at a router. QoS is the set of mechanisms that fixes this deliberately, by classifying packets and treating classes differently.

Scheduling and shaping inside a router

A router with QoS classifies each packet into a flow, polices the flow's rate, queues it, and schedules it. Scheduling decides which queued packet leaves next.

  • FIFO (first in, first out): one queue, arrival order, no QoS.
  • Priority queueing: several queues with priorities; the highest non-empty priority always wins. Strict priority can starve low-priority traffic.
  • Weighted fair queueing (WFQ): every flow gets its own queue and is served in proportion to a weight wᵢ. Flow i gets roughly wᵢ ÷ Σwⱼ of the link rate. With weights 1, 1, 2 on a 4 Mbps link, the third flow gets 2 Mbps and the other two get 1 Mbps each.

Shaping delays excess packets; policing drops or marks them. The leaky bucket drains at a constant rate r, so its output rate never exceeds r whatever the input burst — bursty traffic becomes a smooth stream. The token bucket stores tokens that arrive at rate r, up to a depth b, and a packet of L bits leaves only if L tokens are present.

bits sent ≤ b + r × t

b is the bucket depth in bits (the largest burst allowed at once); r is the token rate in bits per second (the long-run average); t is the elapsed time in seconds, starting with a full bucket.

So a token bucket limits the average rate and permits a burst of b bits; a leaky bucket permits no burst at all.

Integrated Services: reserving per-flow resources

Integrated Services (IntServ) makes a reservation before sending. Each flow is described by a TSpec (traffic specification), five numbers: token bucket rate r, token bucket depth b, peak rate p, minimum policed unit m, and maximum packet size M. This book writes r and p in bits per second and b in bits. The standard TSpec (RFC 2210) defines r, b, p, m and M all in bytes, with r and p in bytes per second. Convert before comparing with link rates.

The sender states a service class and its TSpec. RSVP (Resource Reservation Protocol) carries the request hop by hop to every router on the path. Each router runs admission control: it adds the new TSpec to what is already promised and checks whether link capacity and queue budget still suffice. If yes, the flow is admitted and resources are committed; if no, the request is rejected and the sender is told. Existing flows keep their promises either way — that is the whole point.

Two classes exist. Guaranteed service promises a firm upper bound on queueing delay for a flow that stays inside its TSpec. Controlled load promises only that the flow will see a lightly loaded network — very low loss and delay, but no firm number.

The scaling problem: a core router may carry millions of flows, and per-flow state plus a reservation message per flow does not fit. DiffServ answers this by marking each packet with a DSCP (Differentiated Services Code Point) in the IP header and giving per-class, not per-flow, treatment.

Worked example

Question. A token bucket at a router's ingress has depth b = 16 000 bits and token rate r = 2 Mbps. The bucket is full at t = 0 and the flow always has data ready. (a) How many bits can the flow send in the first 4 s? (b) What is the largest burst it can hand over at t = 0?

5.8 Stream Control Transmission Protocol (SCTP)

SCTP is a transport protocol that carries several independent streams inside one association. A lost message blocks only its own stream, not the others. Each endpoint may also list several IP addresses, so a broken path is replaced without restarting anything. It keeps message boundaries instead of a byte stream, and it uses a four-message handshake with a cookie, so a server stores no state for a request that may be fake. Telephone signalling over IP is where it is most used. This chapter covers the association, the common header, the chunks and the cookie handshake.

You need: ports and multiplexing from Chapter 5.1, header fields and checksum from 5.2 and 5.3, and the TCP handshake from 5.4.

Association, streams and addresses

TCP calls its end-to-end state a connection. SCTP calls it an association, because the state is larger: one association carries many streams and may span many address pairs.

A stream is a one-way logical channel inside the association, numbered from 0. Each direction has its own stream numbers, agreed at setup. Data on stream 3 is ordered only with respect to other data on stream 3. A lost DATA chunk on stream 1 stalls stream 1 and nothing else. TCP, with a single byte stream, would stall everything; that is head-of-line blocking.

SCTP is message-oriented. If the application writes one 3000-byte message, the receiver's read returns exactly 3000 bytes, never a merged or split message. The sender marks each message ordered (deliver in sequence within its stream) or unordered (deliver as soon as it arrives). Unordered service suits signalling, where each message stands alone.

Multihoming: at setup each endpoint supplies a list of IP addresses. One address pair is the primary path; the others are alternates. SCTP sends normal traffic on the primary, retransmits lost chunks on an alternate when the primary looks dead, and probes every path with heartbeats. It does not spread load across paths by default.

The common header and the chunk

Every SCTP packet starts with a 12-byte common header.

FieldSizeJob
Source port16 bitssender's process
Destination port16 bitsreceiver's process
Verification tag32 bitsnames the association
Checksum32 bitsCRC-32C over the packet

Ports do the multiplexing of Chapter 5.1. The verification tag is chosen by each end during setup; a packet whose tag does not match the association is silently discarded, which kills stale packets and blind off-path injection. The checksum is CRC-32C, computed over the whole packet with the checksum field zeroed; the arithmetic is the CRC of Unit 3.

Everything after the common header is a chunk. A chunk has a 4-byte header: type (8 bits), flags (8 bits), length (16 bits). The length counts the chunk header and the payload but not the padding that rounds the chunk to a multiple of 4 bytes. Several chunks may be bundled into one packet.

A DATA chunk (type 0) adds four fields after the chunk header.

  • TSN, 32 bits: transmission sequence number. It counts DATA chunks across the whole association and is what SACK acknowledges and what retransmission uses.
  • Stream identifier, 16 bits: the stream this chunk belongs to.
  • Stream sequence number, 16 bits: position of the message inside that stream; this is what orders stream 3 against stream 3.
  • Payload protocol identifier, 32 bits: tells the receiving application what kind of payload it is.

The DATA flags carry I (immediate, deliver without waiting for ordering), U (unordered), B (first fragment) and E (last fragment), so a large message is split and reassembled.

SACK (type 3) acknowledges TSNs and reports gaps, so the sender sees exactly which chunks are missing. HEARTBEAT (4) and HEARTBEAT-ACK (5) probe paths. SHUTDOWN (7), SHUTDOWN-ACK (8) and SHUTDOWN-COMPLETE (9) close the association. Other chunk types exist; read the list once.

Four messages and a cookie

Setup takes four messages, not three.

  1. INIT from the client: initiate tag, number of outbound and inbound streams, initial TSN, list of its IP addresses.
  2. INIT-ACK from the server: its own tag, stream counts, its address list, and a state cookie.
  3. COOKIE-ECHO: the client returns the cookie byte for byte.
  4. COOKIE-ACK: the server accepts, and the association is up.

The cookie holds everything the server would otherwise have to remember (tags, TSNs, stream counts, addresses) plus a timestamp and a signature made with a secret only the server knows. After sending INIT-ACK the server keeps no per-association state; only the secret key used to sign and verify cookies is retained. A flood of INITs with forged source addresses therefore does not grow its memory; when a real COOKIE-ECHO returns, the cookie is verified and state is created then. COOKIE-ECHO may also carry DATA chunks, so the first message needs no extra round trip.

Teardown is a three-message exchange: SHUTDOWN, SHUTDOWN-ACK, SHUTDOWN-COMPLETE.

Worked example

The path MTU is 1500 bytes including the 20-byte IP header, the common header is 12 bytes and each DATA chunk header is 16 bytes. (a) How many DATA chunks carry a single 3000-byte message? (b) The primary path fails after chunk 1 is acknowledged and chunk 2 is lost. What happens?

  1. Payload room per packet = MTU − IP header − common header − DATA chunk overhead = 1500 − 20 − 12 − 16 = 1452 bytes, where DATA chunk overhead = 4-byte chunk header + 12 bytes of DATA fields = 16 bytes. Staying at this size avoids IP fragmentation (Unit 4).
  2. Two full chunks carry 2 × 1452 = 2904 bytes.
  3. Remaining = 3000 − 2904 = 96 bytes, so a third chunk carries 96 bytes. Total = 3 chunks.
  4. Chunk 2's TSN is missing from the SACK gap blocks, so the retransmission timer fires for it (later SACKs can also trigger fast retransmit).
  5. SCTP retransmits that DATA chunk on 10.0.0.2 and marks 10.0.0.1 inactive. Heartbeats keep probing 10.0.0.1; when they are answered, the path can become active again.

Answer. (a) Three DATA chunks with 1452, 1452 and 96 bytes of payload. (b) The lost chunk goes out on the backup path 10.0.0.2, and the primary is marked inactive until heartbeats succeed.

Exam traps

  • Calling the association a TCP connection with a three-way handshake. SCTP uses four messages and the state cookie is the whole point.
  • Expecting a lost message on stream 1 to hold up stream 2. TCP does that; SCTP orders per stream only.
  • Thinking multihoming balances load across paths. One path is primary; the rest are for retransmission and failover.
  • Confusing the verification tag with the checksum. The tag names the association; CRC-32C catches corruption.
  • Forgetting that the chunk length field includes the 4-byte chunk header but excludes the padding.

Check yourself

Remember What is a stream in SCTP? 2 marks

A one-way logical channel inside the association, numbered from 0, with ordering kept only within that stream.

Remember List the four fields of the SCTP common header with their sizes. 2 marks

Source port 16 bits, destination port 16 bits, verification tag 32 bits, checksum 32 bits (CRC-32C). Total 12 bytes.

Understand Why does SCTP need a stream sequence number when it already has a TSN? 3 marks

The TSN orders DATA chunks across the whole association for acknowledgment and retransmission. The stream sequence number orders messages inside one stream, so each stream can be delivered independently.

Understand Why does the state cookie protect a server against an INIT flood? 3 marks

The server puts all needed state into the signed cookie and keeps nothing after INIT-ACK. Memory is used only when a valid COOKIE-ECHO returns, so forged INITs with fake source addresses create no state.

Apply MTU is 1200 bytes including a 20-byte IP header, the common header is 12 bytes and a DATA chunk header is 16 bytes. How many chunks carry a 2500-byte message? 4 marks

Room = 1200 − 20 − 12 − 16 = 1152 bytes. Two full chunks = 2304 bytes, remainder 196 bytes, so 3 chunks: 1152, 1152, 196.

Apply A DATA chunk carries 100 bytes of payload. What is its chunk length field, and how big is the whole SCTP packet if this is the only chunk? 3 marks

Length field = 4-byte chunk header + 12 bytes of DATA fields + 100-byte payload = 116. Packet = 12-byte common header + 116 = 128 bytes, already a multiple of 4, so no padding.

Analyze Stream 1 loses the chunk with TSN 5 while stream 2 chunks with TSN 6 and 7 arrive safely. Does the receiver hold everything? 5 marks

No. Stream 2 messages are delivered once complete and in stream-sequence order, because TSN 5 belongs to stream 1 only. TSN 5 is retransmitted and only stream 1 waits, which is the head-of-line blocking SCTP removes.

Beyond the syllabus

Not for the exam. WebRTC data channels run SCTP over DTLS over UDP inside browsers, so this header and these streams run on ordinary phones. Telephony signalling networks moved SS7-style messages onto SCTP because a lost message on one stream must not delay call setup on another. Search RFC 4960, "SCTP multihoming" and "SCTP streams versus TCP head-of-line blocking" to go further.

Takeaways

  1. The transport layer uses port numbers to extend IP host delivery to process delivery; UDP and TCP differ in reliability and state.
  2. UDP adds only ports, length and checksum; it suits short, loss-tolerant messages and applications that build their own reliability.
  3. TCP sequence and acknowledgment numbers turn an unreliable packet service into an ordered, reliable byte stream.
  4. TCP connection setup and release use flag exchanges and states; TIME-WAIT protects the close from old duplicates.
  5. Flow control protects the receiver's buffer, while congestion control protects the network.
  6. TCP congestion control uses slow start, congestion avoidance, fast retransmit and fast recovery; loss is treated as congestion.
  7. QoS mechanisms classify and schedule traffic, while integrated services can reserve resources per flow using RSVP and TSpec.
  8. SCTP supports multi-streaming and multi-homing, avoiding head-of-line blocking across independent messages.

Glossary

ACK
TCP flag or number that acknowledges received bytes or a control segment.
Advertised window
Receiver's free buffer space in bytes, carried in the TCP window field.
Best effort
Network service with no guarantee of delay, loss or bandwidth.
Checksum
Arithmetic check over header and data to detect bit errors.
Congestion avoidance
TCP phase that grows cwnd by about one MSS per RTT after ssthresh.
Congestion window
Sender's estimate of how many unacknowledged bytes the network can carry.
Controlled load
QoS class that looks like an unloaded best-effort network under normal conditions.
Demultiplexing
Using a port number to deliver an arriving segment to the right process.
Fast recovery
TCP state after fast retransmit that avoids returning to slow start for one loss.
FIFO
Queue discipline that sends packets in arrival order.
Flow control
Receiver-driven limit that prevents a fast sender from overflowing the receiver.
Guaranteed service
Integrated services class with firm bandwidth and delay bounds.
Jitter
Variation in packet delay; large jitter hurts real-time audio and video.
MSS
Maximum segment size; largest TCP data payload a sender may put in one segment.
Multiplexing
Combining many process flows into one IP stream using port numbers.
Port number
16-bit identifier for a process or service on a host.
Priority queueing
Scheduler that serves higher-priority queues before lower-priority ones.
RTT
Round-trip time; time for a segment to reach the receiver and for the ACK to return.
Shaping
Delaying or pacing traffic to keep it within a rate profile.
Slow start
TCP opening phase where cwnd doubles each RTT until ssthresh or loss.
Socket
Endpoint identified by IP address and port number.
Three-way handshake
SYN, SYN-ACK, ACK exchange that opens a TCP connection.
TIME-WAIT
TCP state after active close that lasts 2×MSL and protects against old duplicates.
TSpec
Traffic specification that describes a flow's rate and burst parameters for reservation.
