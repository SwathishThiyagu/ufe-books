5.1 Transport services: ports, multiplexing and demultiplexing

The transport layer lets many applications share a single host. It does this by assigning a 16‑bit port number to each process. The pair (IP address, port) is called a socket address; a socket is the tuple (IP address, port, transport protocol). The operating system reads the port in every incoming segment and delivers the payload to the correct application. This mechanism is called multiplexing at the sender and demultiplexing at the receiver. It is used for web browsing, video streaming, online payments and any client‑server communication on the Internet.

You need: Unit 1 (layering) and Unit 4 (IP addressing).

Port numbers and sockets

A port number identifies a transport endpoint on a host. It is an unsigned 16‑bit integer, so the range is 0 ≤ port ≤ 65535. Values 0‑1023 are well‑known ports reserved for standard services such as HTTP (80) and DNS (53). Values 1024‑49151 are registered ports used by applications. Values 49152‑65535 are dynamic or private ports assigned temporarily by the OS.

Port range = 2¹⁶ = 65536

2¹⁶ is the number of distinct values a 16‑bit field can hold

A socket is the tuple (IP address, port number, transport protocol). The protocol part distinguishes UDP from TCP when the same port number is used by both.

  • Port 0 is reserved; it is not used as a destination port in normal communication, but it may be used as a source port to request an OS‑assigned ephemeral port or as a wildcard in certain socket APIs.
  • Port numbers are stored in network byte order (big‑endian).
  • The OS maintains a table mapping each active port to a process identifier (PID).

Multiplexing and demultiplexing

When an application sends data, the transport layer attaches the source and destination ports to the segment. This is multiplexing because the same physical link can carry segments for many applications simultaneously.

  1. Application calls sendto() with destination IP and port.
  2. Transport adds source port (chosen by OS) and destination port.
  3. Network layer encapsulates the segment in an IP packet.
  4. Link layer transmits the frame on the medium.

At the receiver, the OS extracts the destination port from the incoming segment. It looks up the port in its socket table. If a match is found, the payload is copied to the buffer of the owning process. This is demultiplexing.

  • If no process owns the port, the OS discards the segment and may send an ICMP “port unreachable”.
  • Both UDP and TCP use the same port field for demultiplexing, but TCP also uses the connection tuple (source IP, source port, dest IP, dest port).

Alternative names in syllabi

Some textbooks call a socket an endpoint, a service access point (SAP), or a demultiplexer. The term “transport service” refers to the set of operations offered to the application, such as reliable byte stream (TCP) or best‑effort datagram (UDP).

  • Endpoint – the same as socket.
  • Service Access Point – emphasizes the role of the port as an access point to the transport service.
  • Demultiplexer – the function that selects the correct process based on the port.

Worked example

Question. Host A runs App 1 on port 5000 and App 2 on port 5001. Host B runs App 3 on port 6000 and App 4 on port 6001. App 1 sends a 120‑byte UDP datagram to App 3. Show how the OS on Host B processes the incoming packet and state which process finally receives the payload.

C program.

#include <stdio.h>
int main(){
    int dest_port = 6000;
    int payload_len = 120;
    printf("Destination port: %d\n", dest_port);
    printf("Payload length: %d bytes\n", payload_len);
    return 0;
}
  1. The IP packet arrives at Host B and is handed to the UDP module.
  2. UDP reads the destination port field, which is 6000.
  3. The OS looks up port 6000 in its socket table and finds it bound to App 3 (process ID 3124).
  4. UDP removes its header and copies the 120‑byte payload into the receive buffer of process 3124.
  5. App 3 reads the buffer and obtains the 120‑byte message.

Output

Destination port: 6000
Payload length: 120 bytes

Answer. App 3 (process 3124) receives the 120‑byte payload.

Exam traps

  • Mistaking the port number for the IP address of the host.
  • Assuming that a port number is unique across the entire Internet; it is only unique per host.
  • Confusing the source port with the destination port when tracing a packet flow.

5.2 User Datagram Protocol (UDP)

User Datagram Protocol (UDP) gives applications a way to send packets without establishing a connection. It uses a fixed 8‑byte header, so the overhead is very small. Because there is no hand‑shaking, UDP is useful for time‑critical services such as DNS, video streaming, or simple control messages where occasional loss is acceptable.

You need: Transport services: ports, multiplexing and demultiplexing.

UDP header fields

A UDP segment starts with a 16‑bit source port field. The source port identifies the sending process on the host. The next 16‑bit destination port tells the receiving host which process should get the data. The length field is also 16 bits and holds the total number of bytes in the UDP segment, header plus payload. The final 16‑bit checksum field allows the receiver to detect errors in the header and data.

  • Source Port – 0 to 65535, 0 is reserved and not used for normal application ports.
  • Destination Port – 0 to 65535, 0 is reserved and should not be used; must be known by the receiver.
  • Length – header (8 bytes) + data size, minimum value 8.
  • Checksum – optional in IPv4, mandatory in IPv6; computed over a pseudo‑header, UDP header, and data.

Length = 8 bytes + DataSize

Length is the value stored in the Length field; DataSize is the number of payload bytes.

Because UDP does not keep state, each segment is independent. The receiver uses the destination port to select the correct socket, then passes the payload to the application.

Some syllabi call this service a datagram service because each packet is a self‑contained unit.

Length calculation and checksum role

When an application wants to send 32 bytes of data, the UDP layer adds the 8‑byte header and stores 40 in the Length field. The checksum is computed over a pseudo‑header that contains the source IP, destination IP, protocol number (17 for UDP), UDP length, and the UDP header plus data. The result is placed in the checksum field. If the receiver computes a different checksum, the segment is discarded.

  1. Form the pseudo‑header with source IP, destination IP, zero, protocol, and UDP length.
  2. Append the UDP header (source port, destination port, length, checksum set to zero).
  3. Append the data payload.
  4. If the total length is odd, pad with one zero byte.
  5. Add all 16‑bit words using one's complement arithmetic.
  6. Take the one's complement of the sum; this is the checksum.

The checksum catches most bit‑error patterns but does not guarantee reliability. UDP still delivers the segment even if the checksum is correct but the network drops the packet.

Python program.

def udp_checksum(src_ip, dst_ip, src_port, dst_port, data):
    import struct
    pseudo = struct.pack('!4s4sBBH', src_ip, dst_ip, 0, 17, 8+len(data))
    header = struct.pack('!HHHH', src_port, dst_port, 8+len(data), 0)
    if len(data) % 2:
        data += b'\0'
    total = pseudo + header + data
    s = 0
    for i in range(0, len(total), 2):
        s += (total[i] << 8) + total[i+1]
        s = (s & 0xffff) + (s >> 16)
    return ~s & 0xffff

When to choose UDP over TCP

UDP is chosen when the application can tolerate loss and wants the lowest possible latency. DNS queries, VoIP packets, and live video streams use UDP because retransmission would add unacceptable delay. In contrast, file transfer, web page loading, and email rely on TCP, which guarantees ordered delivery, flow control, and congestion avoidance.

  • Low overhead – only 8 bytes of header.
  • No connection setup – saves round‑trip time.
  • No built‑in reliability – application must handle loss if needed.
  • Stateless – each packet can be routed independently.

If an application needs both low latency and reliability, it may implement its own acknowledgment scheme on top of UDP. This hybrid approach is common in real‑time gaming.

Worked example

Question. A client sends a DNS query of 32 bytes from UDP source port 12345 to a DNS server at IP 8.8.8.8. The destination port is 53. Compute the value stored in the UDP Length field and explain how the checksum is placed in the header (use the example checksum 0x1A2B).

  1. Data size = 32 bytes (given).
  2. Header size = 8 bytes (fixed for UDP).
  3. Length = Header size + Data size = 8 + 32 = 40 bytes. Store 40 in the Length field.
  4. Set the checksum field to zero while computing.
  5. Form the pseudo‑header with source IP, destination IP, protocol 17, and UDP length 40.
  6. Append the UDP header (source port 12345, destination port 53, length 40, checksum 0).
  7. Append the 32‑byte data payload.
  8. Compute the one's‑complement sum of all 16‑bit words; the result for this example is 0xE5D4.
  9. Take the one's complement: ~0xE5D4 = 0x1A2B. Write 0x1A2B into the checksum field.
  10. The final UDP segment header now contains Length = 40 and Checksum = 0x1A2B.

  • Assuming the UDP checksum guarantees that the packet will reach the receiver.
  • Confusing the UDP Length field (header + data) with the IP total length field (IP header + UDP segment).
  • Thinking that a source port value of zero is a valid application port.
  • Believing that UDP performs flow control or congestion control like TCP.
  • Treating the checksum as optional in IPv6; it is mandatory.

5.3 TCP services and segment format

TCP gives applications a reliable, ordered byte‑stream service. The service hides packet loss, duplication and reordering so that the program sees a continuous flow of data. It is used by web browsers, email clients, file transfer tools and many other Internet services that cannot tolerate missing or out‑of‑order bytes.

You need: basic UDP header knowledge from 5.2 and the idea of ports from 5.1.

Why TCP is needed

A TCP connection is a virtual circuit between two end‑points. It guarantees that every byte sent by the sender arrives at the receiver exactly once and in the same order. The guarantee is achieved by sequence numbers, acknowledgments, retransmission timers and flow control. Applications that need reliability – such as HTTP, SSH or database replication – use TCP instead of UDP.

  • Ordered delivery: the receiver reassembles bytes by sequence number.
  • Reliability: lost segments are retransmitted until ACKed.
  • Congestion and flow control: prevent network overload and receiver overflow.

Some syllabi call TCP a connection‑oriented transport protocol because a three‑way handshake creates state at both ends before any user data is exchanged.

TCP segment header fields

Every TCP segment begins with a 20‑byte mandatory header. The fields are listed in the figure and described below.

  • Src Port: 16‑bit number identifying the sending application (e.g., 34567).
  • Dst Port: 16‑bit number identifying the receiving application (e.g., 80 for HTTP).
  • Seq No: 32‑bit number of the first byte in this segment. It starts with a random value during connection setup.
  • Ack No: 32‑bit number of the next byte the sender expects; valid only if the ACK flag is set.
  • Data Offset: 4‑bit field giving the header length in 32‑bit words; value 5 means 20 bytes, no options.
  • Flags: 9‑bit control field. The original six bits are URG, ACK, PSH, RST, SYN, FIN. Modern TCP adds three ECN‑related bits: NS, CWR, ECE. The SYN flag starts a connection; FIN ends it.
  • Window: 16‑bit receiver‑advertised flow‑control window, expressed in bytes. If the Window Scale option is used, the effective window size is Window × 2^scale_factor.
  • Checksum: 16‑bit one's‑complement of the pseudo‑header and segment data; detects corruption.
  • Urgent Pointer: 16‑bit offset from the sequence number indicating urgent data; used only if URG flag is set.
  • Options: variable‑length field; may carry timestamps, maximum‑segment‑size, etc.

The header fields together enable reliable delivery, flow control and connection management. When a segment is received, the TCP stack checks the checksum, uses the sequence number to place data in the correct order, and updates the acknowledgment number and window for the peer.

Using the header during connection setup

  1. Client sends a SYN segment: Src Port = 34567, Dst Port = 80, Seq No = 1000, Ack No = 0, Offset = 5, Flags = SYN, Window = 65535, Checksum calculated over the pseudo‑header and the 20‑byte header.
  2. Server replies with SYN‑ACK: Src Port = 80, Dst Port = 34567, Seq No = 2000 (its own random number), Ack No = 1001 (client’s Seq No + 1), Window = 65535, Flags = SYN,ACK.
  3. Client sends ACK: Src Port = 34567, Dst Port = 80, Seq No = 1001, Ack No = 2001, Flags = ACK.

After the three‑way handshake both ends have agreed on initial sequence numbers and know each other’s receive windows. All subsequent data segments carry ACK flag and use the sequence and acknowledgment numbers to provide reliability.

Worked example

It sends a SYN segment with the following values: Src Port = 34567, Dst Port = 80, Seq No = 1000, Ack No = 0, Offset = 5, Flags = SYN, Window = 65535, Checksum = 0xB1C2.   2. Offset = 5 → header length = 5 × 4 bytes = 20 bytes.
  3. Thus the segment header occupies exactly one TCP header without options.

Exam traps

  • Reading the Offset field as the total segment length instead of the header length in 32‑bit words.
  • Assuming the Ack No field is always non‑zero; it is zero in the initial SYN segment.
  • Treating the Flags field as a single decimal number; it is a bit mask where each bit has a separate meaning.
  • Forgetting that the checksum must be computed over the pseudo‑header; using only the TCP header gives a wrong value.

5.4 TCP connection establishment and release

TCP uses a three‑way handshake to start a reliable connection and a four‑step exchange to close it. The handshake synchronises sequence numbers and confirms both sides are ready. The termination ensures all data is delivered before resources are released. This connection management is used by web browsers, online banking, and any application that needs guaranteed delivery.

You need: TCP segment fields and port numbers.

Three‑Way Handshake

The client starts by sending a SYN segment. The SYN flag tells the server that the client wants to open a connection. The client chooses an initial sequence number (ISN) and places it in the seq field.

The server replies with a SYN‑ACK segment. The SYN flag carries the server's ISN in the seq field. The ACK flag acknowledges the client's ISN plus one, because the SYN consumes one sequence number.

The client sends a final ACK segment. This ACK acknowledges the server's ISN plus one. After this exchange both sides have agreed on the initial sequence numbers and the connection is established.

  1. Client → Server: SYN, seq = ISNc
  2. Server → Client: SYN‑ACK, seq = ISNs, ack = ISNc+1
  3. Client → Server: ACK, seq = ISNc+1, ack = ISNs+1

ack = seq_sent + 1

In general, ack = seq_sent + length_of_data. For SYN or FIN segments, length = 1, so ack = seq_sent + 1. The +1 accounts for the SYN or FIN flag which occupies one sequence number.

Four‑Step Termination

When one side has finished sending data it sends a FIN segment. The FIN flag also consumes one sequence number.

The peer acknowledges the FIN with an ACK. The connection then enters the CLOSE‑WAIT state on the peer.

When the peer also finishes sending, it sends its own FIN. The original side acknowledges this FIN with a final ACK.

After sending its FIN, the active closer moves to FIN_WAIT_1, then FIN_WAIT_2, then LAST_ACK after receiving the final ACK. The passive closer moves to CLOSE_WAIT, then after sending its FIN goes to TIME_WAIT.

  1. Client → Server: FIN, seq = f1
  2. Server → Client: ACK, seq = s1, ack = f1+1
  3. Server → Client: FIN, seq = f2
  4. Client → Server: ACK, seq = f1+1, ack = f2+1
  • Both sides must send a FIN to close their sending direction.
  • Each FIN is acknowledged separately.
  • After sending the final ACK the side enters TIME_WAIT for 2 MSL.

5.5 TCP flow control

TCP flow control prevents a fast sender from overrunning a slow receiver. The receiver tells the sender how much buffer space is free using the receive‑window field. The sender limits the amount of unacknowledged data to this advertised size. If the window becomes zero, the sender sends a zero‑window probe (a 1‑byte segment) to learn when space is available again. This mechanism is used in all reliable TCP connections, for example when a mobile phone downloads a video over a 4G link that occasionally stalls.

You need: TCP connection establishment and release.

Receive window field

The TCP header contains a 16‑bit receive‑window field. The field value, called rwnd, is the number of bytes the receiver can accept without overflow. rwnd is the number of bytes of free space in the receiver buffer, i.e., the amount of data the receiver can accept without overflow.

rwnd is sent in every ACK. The sender reads the value and treats it as an upper bound on the amount of data that may be outstanding.

sendable ≤ rwnd

sendable is the total number of bytes transmitted but not yet acknowledged; rwnd is the advertised receive window in bytes.

  • rwnd = 0 means the receiver buffer is full.
  • rwnd > 0 allows the sender to transmit up to rwnd bytes.

Sender limit and zero‑window probing

The sender maintains a variable called outstanding, the sum of all transmitted bytes that have not been ACKed. Before sending a new segment the sender checks outstanding + segment size ≤ rwnd.

  1. Read rwnd from the latest ACK.
  2. Compute allowed = rwnd – outstanding.
  3. If allowed ≥ MSS, send floor(allowed/MSS) full‑size segments.
  4. If rwnd == 0 (i.e., allowed = 0 because the advertised window is zero), send a 1‑byte zero‑window probe.
  5. If allowed = 0 but rwnd > 0, wait for ACKs; do not send a probe.

A zero‑window probe forces the receiver to send an ACK that contains an updated rwnd. The probe carries only one byte so it does not fill the buffer.

Worked example

Question. A TCP sender has a congestion window (cwnd) of 5 KB and receives a receive‑window advertisement (rwnd) of 3 KB. The maximum segment size (MSS) is 1 KB. How many full‑size segments can the sender transmit before it must wait for a new ACK? If the receiver later advertises a zero window, what does the sender do?

C program.

#include <stdio.h>
int main(){
    int cwnd = 5*1024; // bytes (congestion window)
    int rwnd = 3*1024; // bytes (receive window)
    int mss  = 1*1024; // bytes (maximum segment size)
    int allowed = (cwnd < rwnd) ? cwnd : rwnd; // apply both limits
    int seg = allowed / mss; // number of full‑size segments
    printf("%d\n", seg);
    return 0;
}
  1. Read rwnd = 3 KB.
  2. Compute allowed = min(cwnd, rwnd) = 3 KB.
  3. Number of full‑size segments = floor(allowed / MSS) = floor(3 KB / 1 KB) = 3.
  4. The sender transmits three 1 KB segments.
  5. If rwnd becomes 0, the sender sends a 1‑byte zero‑window probe.
  6. The probe elicits an ACK that may contain a non‑zero rwnd.

  • Using the advertised window in bytes but subtracting the segment header size, which the protocol does not require.

5.6 TCP congestion control: slow start, fast retransmit

TCP congestion control limits how fast a sender can inject data into the network. It prevents packet loss caused by overloaded routers. The algorithm uses slow start to probe available bandwidth, then switches to congestion avoidance for steady growth. When loss is signaled by three duplicate ACKs, fast retransmit reduces the sending rate and sets a new threshold. This mechanism is used by most Internet applications such as video streaming, online gaming, and UPI payments.

You need: flow control from TCP flow control and basic TCP segment concepts from TCP services and segment format.

Slow start

When a TCP connection begins, the sender does not know the network capacity. It starts with a congestion window (cwnd) of one maximum‑segment size (MSS).

Each round‑trip time (RTT) the sender can transmit cwnd segments without waiting for ACKs. After all ACKs arrive, cwnd is doubled.

cwnd_next = 2 × cwnd_current

cwnd is measured in MSS; the update happens once per RTT during slow start.

  1. Set cwnd = 1 MSS.
  2. Send cwnd segments.
  3. Wait for ACKs of all sent segments.
  4. Double cwnd and repeat.

If the network can carry the traffic, cwnd grows exponentially: 1, 2, 4, 8 … MSS. In India, a mobile video stream may start with low quality (small cwnd) and quickly reach higher resolution as the network proves it can handle more data.

Congestion avoidance and loss detection

When cwnd reaches a threshold called ssthresh, the sender changes to congestion avoidance. The growth becomes linear to avoid overwhelming the network.

cwnd_next = cwnd_current + MSS

The addition occurs each RTT; MSS is the segment size.

Loss is detected in two ways. A timeout indicates severe loss. Three duplicate ACKs (same ACK number) indicate a single packet loss while other packets are still arriving.

  • Timeout → assume all outstanding packets lost; go to slow start.
  • Triple duplicate ACKs → fast retransmit; cwnd is reduced to ssthresh and the connection continues in congestion avoidance.

In a UPI transaction burst, a few duplicate ACKs may appear when a packet is dropped due to temporary congestion, triggering fast retransmit without resetting the whole connection.

Fast retransmit and setting ssthresh

When three duplicate ACKs arrive, the sender immediately retransmits the missing segment. This is called fast retransmit.

After fast retransmit, the sender reduces cwnd to ssthresh, where ssthresh is set to half of the cwnd value that existed before the loss was detected.

ssthresh = ⌊cwnd_before_loss ÷ 2⌋

cwnd_before_loss is the cwnd measured in MSS just before the loss event; ⌊ ⌋ denotes floor to an integer MSS.

The sender then continues in congestion avoidance, increasing cwnd linearly from the new ssthresh value.

If the loss occurs during slow start, the algorithm switches to congestion avoidance immediately after setting ssthresh.

Worked example

5.7 Quality of service and integrated services

Quality of Service (QoS) lets a network treat different traffic classes in different ways. It exists because video, voice and interactive games need low delay while file downloads can tolerate delay. QoS is used by ISPs, campus networks and mobile operators to keep streaming smooth, to honour service‑level agreements, and to avoid congestion on shared links.

You need: basic transport concepts from Transport services and TCP congestion control.

QoS model and traffic classes

QoS divides traffic into classes. A class can be *voice*, *video*, *interactive* or *best‑effort*. Each class has a set of requirements such as maximum delay, jitter or loss. The network marks every packet with a class identifier so that routers and switches can apply the appropriate treatment.

  • Delay‑sensitive: voice, video conference, interactive gaming.
  • Throughput‑sensitive: file transfer, backup.
  • Best‑effort: web browsing, email.

The identifier lives in the IP header. In IPv4 it is the 6‑bit Differentiated Services Code Point (DSCP) field. In IPv6 the same field is called Traffic Class. A DSCP value of 46 (binary 101110) denotes Expedited Forwarding (EF) for low‑delay traffic. A DSCP of 0 denotes the default Best‑Effort class.

Total reserved bandwidth = Σ R_i

R_i is the reserved rate (in Mbps) for class i; the sum must not exceed the link capacity.

  1. Identify the traffic classes needed on the link.
  2. Assign a DSCP value to each class.
  3. Reserve a rate R_i for each class that requires guarantee.
  4. Check that Σ R_i ≤ link capacity.

Integrated Services (IntServ) and resource reservation

IntServ provides per‑flow guarantees using the RSVP (Resource Reservation Protocol). A sender sends an RSVP PATH message describing the flow. The receiver replies with a RESV message that carries the required bandwidth and delay. Each router along the path reserves buffer space and token‑bucket parameters for that flow.

  • Fine‑grained control – each flow gets its own reservation.
  • Scales poorly – routers must keep state for every flow.
  • Used in campus VoIP or video‑conferencing backbones.

The token‑bucket model is common for policing. It has two parameters: a token rate C (Mbps) and a bucket depth B (Mbits). Tokens arrive at rate C. A packet can be sent only if enough tokens exist; otherwise it is marked or dropped.

Available tokens after time t = min(B, B₀ + C·t)

B₀ is the initial token count (Mbits). C is token rate, B is bucket depth, t is elapsed time in seconds.

If the bucket starts full (B₀ = B) the token count stays at B until tokens are consumed.

Differentiated Services (DiffServ) and bandwidth allocation

DiffServ aggregates many flows into a few classes. Routers examine the DSCP value and apply a Per‑Hop Behavior (PHB). The common PHBs are Expedited Forwarding (EF) for low‑delay traffic and Assured Forwarding (AF) for traffic that should get a minimum loss rate.

  • No per‑flow state – scales to millions of users.
  • Traffic shaping at the edge enforces the reserved rates.
  • Core routers only need to schedule packets by class.
  1. Edge router classifies packets and sets DSCP.
  2. Edge router shapes traffic to the reserved rate using a token bucket.
  3. Core routers give strict priority to EF traffic and use weighted‑fair queuing for AF and best‑effort classes.

Consider an ISP link of 10 Mbps. It offers a video service with DSCP = 46 and a guaranteed rate of 4 Mbps, and a web service with DSCP = 0 and a guaranteed rate of 1 Mbps. The remaining 5 Mbps is left for best‑effort traffic.

5.8 Stream Control Transmission Protocol (SCTP)

Stream Control Transmission Protocol (SCTP) is a transport‑layer protocol that gives reliable, message‑oriented delivery while allowing several independent streams inside one association and the use of multiple network addresses for the same endpoint. It was created to overcome limitations of TCP (single stream, single address) in applications such as telephony signalling, video streaming and financial transaction systems where head‑of‑line blocking or path failure must be avoided.

You need: reliable byte‑stream concepts from TCP services and segment format and basic connection concepts from TCP connection establishment and release.

Service model and key terminology

SCTP offers a reliable, message‑oriented service. Unlike TCP, data is delivered as distinct messages called chunks. Each chunk is either a control chunk (e.g., INIT, COOKIE‑ECHO) or a data chunk. The protocol guarantees that a transmitted chunk arrives intact or is retransmitted, and it preserves the order of chunks within a single stream but not across different streams.

  • Association – the term for an SCTP connection between two endpoints.
  • Association ID – a 32‑bit identifier assigned by the server after the handshake.
  • Stream – an ordered sub‑channel inside an association; each stream has its own sequence numbers.
  • Multi‑homing – each endpoint may advertise several IP addresses; the association can switch to a backup address if the primary fails.

Because messages are bounded, the receiver can discard a lost chunk without stalling other streams. This property removes the head‑of‑line blocking problem that TCP suffers from when a single lost segment blocks all subsequent data.

Four‑step handshake with cookie

SCTP does not use the three‑way handshake of TCP. Instead it performs a four‑step handshake that protects the server from SYN‑flood attacks. The client first sends an INIT chunk containing its Initial Sequence Number (ISN). The server replies with INIT‑ACK and a secret cookie. The client returns the cookie in a COOKIE‑ECHO chunk. If the cookie is valid, the server sends COOKIE‑ACK together with the association ID. After this exchange the association is established and data may be sent.

  1. Client → Server: INIT, ISN = 5000
  2. Server → Client: INIT‑ACK, cookie = 0x9A
  3. Client → Server: COOKIE‑ECHO, cookie = 0x9A
  4. Server → Client: COOKIE‑ACK, assoc‑id = 100

The cookie contains a cryptographic MAC of the client’s IP address, the ISN and a timestamp. The server does not allocate resources until the cookie is returned, which prevents it from being overwhelmed by bogus INIT requests.

Multi‑streaming and multi‑homing

An association may contain up to 65535 streams. Each stream has its own Stream Sequence Number (SSN). When a data chunk is lost, only the missing SSN in that stream is retransmitted; other streams continue uninterrupted. This is useful for applications that send control messages on one stream and bulk data on another.

  • Example: a video call uses stream 0 for audio, stream 1 for video, and stream 2 for screen‑share control.
  • If a video packet on stream 1 is lost, audio on stream 0 is still heard without pause.

Multi‑homing lets each endpoint list several IPv4 or IPv6 addresses in the INIT chunk. During the association the transport can switch to a secondary address if the primary path fails, providing resilience without tearing down the connection.

C program.

#include <netinet/sctp.h>
#include <stdio.h>
#include <string.h>
int main() {
    int sock = socket(AF_INET, SOCK_STREAM, IPPROTO_SCTP);
    struct sockaddr_in serv = {0};
    serv.sin_family = AF_INET;
    serv.sin_port   = htons(5000);
    serv.sin_addr.s_addr = inet_addr("192.0.2.10");
    sctp_initmsg initmsg = {0};
    initmsg.sinit_num_ostreams = 4;   // four streams
    initmsg.sinit_max_instreams = 4;
    setsockopt(sock, IPPROTO_SCTP, SCTP_INITMSG, &initmsg, sizeof(initmsg));
    connect(sock, (struct sockaddr *)&serv, sizeof(serv));
    const char *msg = "Hello";
    sctp_sendmsg(sock, msg, strlen(msg), NULL, 0, 0, 0, 1, 0, 0);
    printf("Sent on stream 1\n");
    return 0;
}

Output

Sent on stream 1

Reliability vs. loss tolerance; Impact of retransmission on latency; Header overhead; Typical industry choices.

Evaluate Explain how sliding‑window flow control and congestion control work together to avoid network overload. Use a numerical example with window sizes. 15 marks

Flow‑control window (receiver side); Congestion window (sender side); Effective send window = min(flow, congestion); Example showing window growth and reduction.

Evaluate Discuss the role of Quality of Service (QoS) in supporting real‑time services such as VoIP over a congested network. Mention IntServ and DiffServ briefly. 13 marks

QoS objectives; Resource reservation (IntServ); Class‑based scheduling (DiffServ); Effect on jitter and packet loss.

Analyze Explain how SCTP’s multi‑streaming feature can prevent head‑of‑line blocking compared to TCP. 12 marks

Definition of multi‑streaming; Independent sequencing per stream; Contrast with TCP’s single byte‑stream ordering.

Glossary

Acknowledgment Number
Number indicating the next byte expected by the receiver
Congestion Window
TCP variable that limits the amount of data in the network
Demultiplexing
Separating received data to deliver to correct processes
DiffServ
QoS model that classifies traffic into priority bands
Fast Retransmit
Immediate resend after three duplicate ACKs
FIN Flag
Used to gracefully close a TCP connection
IntServ
QoS model that reserves resources per flow
Multiplexing
Combining multiple data streams into one transmission
Multi‑homing
Using multiple IP addresses for a single SCTP endpoint
Port
Numeric identifier for an application process on a host
Quality of Service
Techniques to prioritize certain traffic types
RST Flag
Resets a TCP connection abruptly
SCTP
Transport protocol offering reliable, message‑oriented delivery
Sequence Number
Number that orders bytes in a TCP connection
Sliding Window
Flow‑control mechanism that allows multiple unacknowledged packets
Slow Start
Phase where TCP increases the congestion window exponentially
SYN Flag
Used to initiate a TCP connection
TCP
Connection‑oriented transport protocol providing reliable byte stream
UDP
Connection‑less transport protocol with minimal overhead
Window Size
Amount of data the receiver is willing to accept
