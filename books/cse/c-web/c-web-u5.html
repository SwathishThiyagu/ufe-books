5.1 React basics: JSX, rendering and components

React is a JavaScript library for building a web page as a tree of small functions called components. Each component returns JSX, a syntax that looks like HTML. React turns that JSX into real DOM elements. The library exists because hand-written DOM updates become hard to track when many parts of a page depend on the same data. You describe the screen for the current data, and React does the DOM work. React is used in dashboards, e-commerce sites, UPI payment pages and admin consoles.

You need: Unit 2 (HTML elements and attributes) and Unit 3 (ES6 functions, arrow functions and modules).

The problem and the entry point

In Unit 3, a page changes through DOM methods. After a cart item is removed, you update the count span, the total div and the checkout button yourself. Every new feature must remember every affected node. One missed node leaves stale text on screen. React flips that responsibility: when data changes, React calls the component function again and updates the DOM from the new result.

  • CDN setup: load React, ReactDOM and Babel with script tags. Babel compiles JSX inside the browser.
  • Vite or create-react-app: a bundler compiles JSX before the browser runs it. npm create vite@latest starts a Vite project.
  1. index.html contains a mount element: <div id="root"></div>.
  2. ReactDOM.createRoot(document.getElementById("root")) creates a React root on that element.
  3. root.render(<App />) mounts the App tree: React builds elements and inserts the first DOM output under the root.

The one-line entry is ReactDOM.createRoot(document.getElementById("root")).render(<App />). Mount means the first render of a React tree into a DOM node. Later data changes re-render affected components; props and state cover that.

JSX rules and React.createElement

JSX looks like HTML but is not HTML. A browser cannot run it. Babel, or a bundler such as Vite, transforms each JSX element into a function call before the code runs.

  • Return one parent element, or an empty fragment <>...</>, around siblings.
  • Curly braces hold a JavaScript expression: {title}. They cannot hold a statement such as if.
  • Use className for HTML class, and htmlFor for HTML for.
  • Close every tag. Self-closing tags end with a slash: <img />.
  • A capital first letter means a component, as in <Greeting />. A lowercase first letter means an HTML tag, as in <div>.

React.createElement(type, props, ...children)

type is an HTML tag name as a string or a component function; props is an object of attributes or null; children are strings or nested React.createElement results.

For example, <h2>{title}</h2> becomes React.createElement("h2", null, title) when title is a variable. The classic transform is what exams ask for; newer React versions may use an automatic JSX runtime, but the element tree is the same.

Components and the page tree

A function component is a JavaScript function whose name starts with a capital letter and which returns JSX. function Header() { return <h1>Shop</h1>; } is a component. React calls it like any function and uses the returned element.

A class component extends React.Component and has a render() method: class Header extends React.Component { render() { return <h1>Shop</h1>; } }. Some syllabi call these React Classes. Function components are the default in new code.

Compose components by nesting them. App can return <div><Header /><PostList /><Footer /></div>. React calls App, then each child component. The result is a component tree. A stateless component has no state; it only uses props, covered in Chapter 5.2.

Styling and the ES6 pieces you reuse

  • External CSS: import a .css file once and apply classes with className.
  • Inline style: use a JavaScript object with camelCase keys, as in style={{color: "teal", fontSize: "16px"}}. The outer braces are JSX; the inner braces are the object.
  • CSS modules: import styles from "./Card.module.css", then className={styles.card}; class names are scoped to that file.
  • styled-components writes CSS inside JavaScript; Reactstrap gives Bootstrap 4 components such as <Button color="primary">.

Five ES6 features carry most React code. let and const give block scope. Arrow functions shorten callbacks and keep this from the enclosing scope. Destructuring pulls values out of props or objects. Spread copies arrays or objects into a new one. Modules split components across files with import and export. Unit 3 treats each fully.

5.2 Props, state and component lifecycle

Props are read-only data a parent sends into a child component. State is data a component owns and changes; changing it makes React render that component again. Lifecycle methods and the useEffect hook run code at fixed moments: after mount, after updates and before unmount. These three ideas separate data flow from data ownership. Every real screen, from a UPI balance card to an IRCTC seat list, uses them. This chapter shows the rules, the batching trap and the lifecycle order.

You need 5.1 for components and JSX, and Unit 3 for arrow functions and array destructuring.

Props: data from the parent

A component receives props (properties) as one object argument. A parent component renders another component, called its child. The parent writes <Greeting name='Asha' />; inside, the child reads props.name. Destructuring in the parameter list is the common style: function Greeting({ name, city }). Props flow down the tree. A child cannot assign to props; if it needs to change a value, the parent passes a function prop such as onSave and the child calls it.

  • The special prop children is whatever sits between the opening and closing tags: <Card>Hello</Card> gives children = 'Hello'.
  • Default values: function Badge({ color = 'grey' }) uses grey when the parent omits color.
  • PropTypes is a development-only runtime check: Greeting.propTypes = { name: PropTypes.string }. It warns in the console during development and is removed from production builds.
  • Read-only rule: never write props.name = 'B'. Change the source value in the parent.

State: data the component owns

A hook is a function that lets a component use React features; built-in hooks start with use, and custom hooks must follow that naming convention. State is a value a component remembers between renders. The hook useState returns a pair: const [count, setCount] = useState(0); Here count is the current value, setCount is the setter function, and 0 is the initial value. React uses array destructuring to give you these two positions. The initial value is used only on the first render; later renders keep the stored state. Initial value can be computed lazily: useState(() => buildRows()) calls buildRows only on the first render, not on every render. Some syllabi call this lazy initial state.

Calling setCount does not change count immediately. React queues the update and batches several calls into one render. So the line after setCount(1) can still read the old count. If the new value depends on the old value, pass an updater function: setCount(c => c + 1). React runs the queued updaters in order, 0 → 1 → 2.

  • Objects and arrays in state must be replaced, not mutated. Copy first: setItems([...items, newItem]).
  • Mutating with items.push(x) keeps the same reference, so React may see no change and skip the render.
  • For a form value, state controls the input; see 5.3.

Composition, keys and lifecycle

A presentational component only receives props and returns JSX; it is stateless. A container component holds state and passes data and callbacks down. To share one value between two siblings, lift state up to their closest common parent. The parent owns the state and passes it to both children. Dynamic composition uses children plus conditional rendering: {isOpen && <Panel />} renders Panel only when isOpen is true.

For a list, items.map(item => <li key={item.id}>{item.name}</li>); the key must be stable and unique among siblings. Prefer a database id over the array index when the list can reorder.

A class component has lifecycle methods: constructor, render, componentDidMount, componentDidUpdate(prevProps, prevState), componentWillUnmount. render runs on every mount and update. componentDidMount runs after the first render. componentDidUpdate runs after later renders and receives previous props and state. componentWillUnmount runs before removal. The hook version is useEffect(fn, deps). With an empty array [], fn runs once after mount; the returned cleanup function runs on unmount. With no second argument, fn runs after every render.

One component pattern: a Dashboard has const [rows, setRows] = useState([]) and const [loading, setLoading] = useState(true). Inside useEffect(() => { let live = true; fetch(url).then(r => r.json()).then(d => { if (live) { setRows(d); setLoading(false); } }); return () => { live = false; }; }, []). The empty array fetches once on mount; the cleanup stops a late response from updating an unmounted component. Fetching details are in 5.9 and Unit 6.

Exam traps

  • Mutating state keeps the same reference: arr.push(x) or this.state.count = 5 fails silently because React compares references.
  • Reading count on the line after setCount still gives the old value; the update is queued, not applied.

5.3 Event handling and forms in React

React does not use HTML's onchange attribute. It gives you camelCase event props such as onClick and onChange, and each prop holds a JavaScript function. For forms, React goes further: the input's value is kept in state, and every keystroke updates that state. The browser shows what state says. This one-way flow gives a single source of truth for login forms, search boxes, checkout pages, and child components that must report a value upward.

You need Chapter 5.1 for JSX and Chapter 5.2 for state and the updater form.

Events are props that hold functions

JSX event props are camelCase: onClick, onChange, onSubmit. The value is a function, not a string. onClick={handleClick} passes the function, and React calls it on click. onClick={handleClick()} calls it during render and passes the result, usually undefined. That is the classic bug in the traps below.

React hands your handler a synthetic event object e. It wraps the browser event, so the same code works across browsers. e.target is the element that fired the event. e.target.value is an input's current text. e.target.name is its name attribute. e.preventDefault() stops the browser's default action, such as reloading the page when a form is submitted.

To pass an argument, wrap the call in an arrow: onClick={() => remove(id)}. The arrow is created during render; remove(id) runs only on click.

Events also carry data from child to parent. The parent passes a function prop, for example onChange={handleName}. The child calls props.onChange('R') when its value changes. The parent stores R in state and re-renders.

Controlled inputs: state holds the value

A controlled input takes its value from state and reports every change back to state: const [name, setName] = useState(''); and <input value={name} onChange={e => setName(e.target.value)} />. The user types R. onChange fires, setName('R') updates state, React re-renders, and the input receives value='R'. State, not the browser, holds the text. If you set value but forget onChange, the input is read-only: typing changes nothing and React warns in the console.

For many fields, keep one object and use the field's name: const [form, setForm] = useState({email: '', password: ''}); and const change = e => setForm({...form, [e.target.name]: e.target.value});. [e.target.name] is a computed property, so one handler updates email or password. The spread ...form copies the other field.

textarea uses value, not child text. select puts value on the select, not selected on each option. A checkbox uses checked={agree} with onChange={e => setAgree(e.target.checked)}. A radio group gives every radio the same name and uses checked={choice === 'male'}. A file input is always uncontrolled: read e.target.files.

For a small uncontrolled form, use useRef: const ref = useRef(); <input ref={ref} />, then read ref.current.value on submit. Controlled inputs are preferred when you need live validation.

Child reports upward, and the form submits

Child-to-parent communication uses a callback prop. The parent owns state and passes a function: function PasswordField({value, onChange}) { return <input type='password' value={value} onChange={e => onChange(e.target.value)} />; }. The parent renders <PasswordField value={form.password} onChange={v => setForm({...form, password: v})} />. The child never edits the parent's state directly; it calls the function it was given. The parent updates state, and both parent and child re-render with the new value.

Submit handling goes on the form: <form onSubmit={handleSubmit}>. In the handler call e.preventDefault() first. Without it the browser sends a GET request, the page reloads, and your state is lost. Then validate: if (password.length < 6) setError('Password too short'); else setError('');. Show {error && <p>{error}</p>}. The check runs again on the server, because browser validation can be bypassed (see Unit 4, form processing).

Validation messages live in state, usually a separate string. Render them next to the field, and clear them when the user edits.

Exam traps

  • onClick={handleClick()} runs during render, not on click. Use onClick={handleClick} or onClick={() => handleClick(id)}.
  • An input with value but no onChange is read-only, and React prints a warning in the console.

  • Forgetting e.preventDefault() in onSubmit reloads the page and wipes the state.
  • A file input cannot be controlled; setting value is ignored. Read e.target.files instead.

5.4 Client-side routing with React Router and Angular Router

A single-page app loads one HTML file and then swaps views inside the browser. A client-side router connects each URL path to a component, so the back and forward buttons work, and a bookmarked or refreshed URL shows the right view. A refresh does send a request for that path, so the server must be told to return index.html (Section 3). React Router and Angular Router are two implementations of the same idea. You meet this in any dashboard, e-commerce site or admin panel where clicking a product opens a detail view but the page does not blink.

You need 5.1 for components and 5.2 for state; Unit 1 covers URLs and HTTP requests.

What a client-side router does

A single-page app (SPA) loads one HTML file. After that, JavaScript builds and replaces the page content. If every click asked the server for a fresh HTML file, the browser would throw away the running app and load everything again. That is slow and it loses state such as a filled form or a scroll position.

A client-side router fixes this. It reads the URL path — the part after the domain, such as /posts/42 — and matches it against a route table. A route is one rule: a path pattern and the component to show. A dynamic segment starts with : and captures one part of the path. The pattern /posts/:id matches /posts/42 and stores 42 under the name id. A wildcard route (written * in React Router and ** in Angular Router) matches any path that no other rule matched, so it usually shows a 404 page.

The router then renders the matched component into a stand-in, called an outlet. When the user clicks a router link, the router changes the URL with the browser's History API and renders the new component. It does not send a new document request. The back and forward buttons still work because the router listens for popstate events.

The figure shows the matching step. The URL is the input; one branch of the component tree is the output.

React Router in practice

Install the package with npm install react-router-dom. In main.jsx, wrap the app in BrowserRouter. Inside, declare Routes and Route. In React Router v6 and later, each Route takes path and element. Older versions used Switch in place of Routes and component={Home} or render={() => <Home />} in place of element. Both styles appear in syllabi, so read the version.

<BrowserRouter>
  <Routes>
    <Route path="/" element={<Home />} />
    <Route path="/posts" element={<PostList />} />
    <Route path="/posts/:id" element={<PostDetail />} />
    <Route path="*" element={<NotFound />} />
  </Routes>
</BrowserRouter>

A child Route written with index (and no path) is the index route, matched at the parent's URL. Nested routes render through <Outlet /> in the parent component. A layout route is a parent Route, with or without its own path, whose only job is to keep shared UI such as a header or sidebar mounted while its children change.

Read /posts/:id with const { id } = useParams(). The value is a string, so convert it before arithmetic. Use <Link to="/posts"> instead of <a href="/posts">. Link calls the router and prevents the browser's normal navigation. NavLink adds an active class when its path matches. After a form submit, call navigate('/posts') from useNavigate(). To redirect during render, return <Navigate to="/login" replace />. A <Route path="*" /> catches every unmatched URL.

Lazy loading keeps the first bundle small: const PostDetail = React.lazy(() => import('./PostDetail')); then render it inside <Suspense fallback={<Loading />}>.

Angular Router and the server rule

Angular declares routes as an array of objects. In a module-based app, import RouterModule.forRoot(routes). In a standalone app, call provideRouter(routes). Each entry has path and either component or loadComponent for lazy loading.

const routes: Routes = [
  { path: '', component: HomeComponent },
  { path: 'posts', component: PostListComponent },
  { path: 'posts/:id', component: PostDetailComponent },
  { path: '**', component: NotFoundComponent }
];

The template puts <router-outlet></router-outlet> where the matched component appears. routerLink replaces href: <a routerLink="/posts" routerLinkActive="active">Posts. The wildcard is '**'. A redirect uses { path: '', redirectTo: '/home', pathMatch: 'full' }. Read the id from ActivatedRoute: this.route.snapshot.paramMap.get('id'). A guard is one line in the route: canActivate: [authGuard].

Two URL modes. History routing uses clean paths such as /posts/42 and needs server help. Hash routing puts the route after #: /#/posts/42. The browser sends only / to the server, so hash routing works on any static host. With history routing, the web server must return index.html for every path that is not a real file. Otherwise a hard refresh of /posts/42 asks the server for a file that does not exist and gets 404. The app never starts. In Express, that fallback is a final route that sends index.html; Express details are in Unit 6.

5.5 TypeScript fundamentals

TypeScript is JavaScript plus type annotations. A compiler reads the annotations before the code runs, reports mismatches, then removes type annotations. Interfaces and type aliases leave no run-time trace; a non-const enum does become a JavaScript object. The browser receives plain JavaScript. It exists because JavaScript waits until run time to show a wrong argument or a misspelled property; TypeScript moves those mistakes to the editor and the build. Angular projects use it by default, and React projects often add it. You write .ts files, run tsc, and get .js files. Types help autocomplete and refactoring, but they leave no trace at run time.

You need Unit 3 for variables, functions, ES6 classes and modules.

Compiling: tsc, tsconfig and erasure

JavaScript checks types when a line runs. A wrong argument can sit in a rarely used branch until a user reaches it. TypeScript adds annotations and a compiler, tsc, that reads the whole file first. A mismatch is reported before you run. tsc exits with a non-zero status; with noEmitOnError in tsconfig.json it also skips writing app.js. For an exam answer, the call fails to compile — it is a type error.

You write app.ts and run npx tsc. The compiler reads tsconfig.json. Two settings matter. target says which JavaScript version to emit, for example ES2017. strict turns on a group of checks, including strictNullChecks, which keeps null and undefined out of types unless you allow them. The output is app.js. Interfaces, type aliases and annotations leave no run-time trace, but a non-const enum does: it becomes an ordinary JavaScript object, so Size.Small exists at run time. A const enum is inlined and leaves nothing. That is why most types cannot be tested at run time.

The editor uses the same information. After you type user., it offers id, name and email. A misspelled user.nmae is marked before you save. Plain JavaScript would run add('2', 3) and return '23'; TypeScript rejects the call because a string is not assignable to a number. The check is static: it happens before execution.

Annotations, unions and functions

An annotation follows a name with a colon: let n: number = 7. Common types are number, string, boolean, number[] or Array<number> for an array of numbers, and [string, number] for a tuple whose first item is a string and second is a number. The angle-bracket form is the generic form; both array forms are equivalent. A tuple fixes order and length.

any turns checking off for that value. Avoid it: it spreads, because every property access on an any is allowed. unknown is the safe version. You may store any value in an unknown, but you must narrow it with typeof or a check before use. never is the type of a function that cannot return, such as one that always throws. void is the return type of a function that returns nothing.

A union lists allowed types: 'small' | 'large' accepts only those two strings. A literal type is a single value used as a type. An optional property carries ?: email?: string means the property may be missing or undefined. readonly stops assignment after creation: readonly id: number. Under strictNullChecks, null and undefined are not members of every type. string does not include null. You add | null when null is legal and check for it before use.

A function annotation gives parameter types and a return type: function add(a: number, b: number): number { return a + b; }. a and b are numbers; the value after the colon is the return type. Optional parameters use ? and must come after required ones: greet(name: string, title?: string). Default parameters use =: greet(name: string, title = 'Mr'). A function type is written (a: number, b: number) => number. It describes a value that is a function.

Interfaces, classes and generics

An interface names the shape of an object: interface User { id: number; name: string; email?: string }. A value satisfies it by having the required properties with the right types. TypeScript is structural: the name User does not matter, the shape does. A class or object literal with id: number and name: string is accepted wherever User is expected. This differs from Java, where a class must declare implements.

A type alias gives a name to any type: type Id = number | string. Interfaces can extend: interface Admin extends User { role: string }. An index signature allows extra keys of one type: interface Scores { [name: string]: number }. An enum names a set of constants. enum Size { Small, Large } gives Small = 0 and Large = 1. A string enum writes the values: enum Size { Small = 'small', Large = 'large' }.

A class can mark members public, private, protected and readonly. public is the default. private is visible only inside the class. protected is visible in subclasses too. readonly is set once. A class implements an interface and must provide its members: class Person implements User { constructor(public id: number, public name: string) {} }. The public in the constructor creates and assigns a property.

Generics let one function or class work with many types while keeping the link: function identity<T>(x: T): T { return x; }. The angle brackets declare T as a type parameter. identity<number>(5) returns 5 as a number; TypeScript can infer it from identity(5). A simple Box<T> stores one value: class Box<T> { constructor(public value: T) {} }. TypeScript infers types from values: let n = 7 infers number. Annotate at boundaries, such as exported functions, parameters and shared object shapes. Do not annotate what is already clear; do annotate an empty array, const names: string[] = [], because [] alone infers never[] under strict settings.

5.6 Angular: components, templates, directives and data binding

Angular is a TypeScript framework for single-page apps, and its unit of work is the component: a class that holds data and behaviour, plus an HTML template that displays it, joined by a decorator. Bindings keep the two sides in step. Read this chapter and you can open any Angular component file and say which decorator makes it a component, how {{ }} and [ ] push values into the page, how ( ) and [( )] bring clicks and typing back, and how directives and pipes reshape markup without extra class code.

You need: 5.5 for classes, interfaces and decorators, and Unit 2 for HTML attributes, CSS classes and styles.

A class plus a template, joined by a decorator

A component is a TypeScript class plus an HTML template. The class alone shows nothing on screen. A decorator joins the two.

@Component is that decorator. Its object has four common keys. selector is the CSS tag the component answers to, such as app-product-card. templateUrl points to the HTML file. styleUrls lists CSS files whose rules apply only inside this template. imports lists what the template needs, such as FormsModule or another component.

The CLI puts components in src/app; main.ts starts the app and angular.json describes the build. Older Angular (2 to 14) declared every component in an @NgModule declarations array. Newer Angular marks the component standalone: true and imports it directly. Some syllabi call the first module-based and the second standalone; both appear on question papers.

AngularJS is not Angular. AngularJS means version 1.x: plain JavaScript, ng-app, ng-controller, and a $scope object shared with the view. Angular means version 2 and later: a rewrite in TypeScript built on components. An answer about $scope in an Angular 2+ question scores nothing.

Binding: moving values both ways

Data binding is how the class and the template exchange values. The direction of the arrow is the thing to remember.

Directives and pipes

A directive changes DOM that already exists in the template, or decides whether it exists at all. Two kinds matter.

Structural directives add or remove elements, so they carry a leading *. *ngIf="ok" keeps the element only while ok is true. For an else branch, name a template: *ngIf="ok; else loading" with <ng-template #loading>…</ng-template>. *ngFor="let p of products; index as i" repeats the element once per item. Add trackBy: byId with a method byId(i, p) { return p.id; } so Angular moves existing rows instead of rebuilding the list. [ngSwitch]="status" with *ngSwitchCase and *ngSwitchDefault picks one block from many.

Attribute directives restyle or rewire an element that stays in place: ngClass, ngStyle, ngModel. Write your own with @Directive({selector: '[appHighlight]'}) and a @HostListener('mouseenter') method that runs when the mouse enters the host element.

A pipe reshapes a value for display only; the class field is unchanged. {{ price | currency:'INR' }} prints ₹2,499.00, {{ name | uppercase }} prints FILTER COFFEE, and {{ today | date:'dd/MM/yyyy' }} prints the date in that pattern. Leave out the currency code and the pipe falls back to dollars.

Inputs, outputs and lifecycle

@Input() product marks a field the parent fills: <app-product-card [product]="p">. @Output() add = new EventEmitter<Product>() marks a field that fires events upward; the parent listens with (add)="onAdd($event)", and add.emit(product) puts product into $event.

Lifecycle hooks run at fixed moments. ngOnChanges runs before ngOnInit and again on every input change. ngOnInit runs once, after the first inputs arrive, which is where you load data. ngOnDestroy runs just before removal, where you stop timers and unsubscribe. This is the same idea as mounting and unmounting in 5.2.

Angular Material gives ready-made Material Design widgets such as toolbar, table, dialog and snackbar. Older projects use Flex-Layout attributes like fxLayout="row" and fxFlex; that package is deprecated, so newer code writes the same layout in plain CSS with flexbox or grid.

5.7 Progressive web apps and server-side rendering

A progressive web app (PWA) is an ordinary website that also installs on a phone and opens offline. It adds two files: a web app manifest that supplies the name and icon, and a service worker that stores files in the browser cache. Server-side rendering (SSR) solves a different first-screen problem. A single-page app often sends an almost empty index.html, so the user waits for JavaScript before seeing content. SSR sends finished HTML from the server, then React hydrates it. Shops use PWAs for repeat visits on slow networks; news and product pages use SSR for fast first paint and search engines.

You need HTTP requests, responses and HTTPS (see Unit 1) and single-page apps from 5.4.

What makes a site installable

A PWA must be served over HTTPS. It needs a web app manifest, a JSON file linked from the page. The manifest gives name, icons, start_url and display (for example standalone). Display says how the installed app appears: standalone hides the browser address bar. The browser uses these values for the home-screen icon and splash screen. Older Lighthouse audits checked HTTPS, the manifest and the service worker; current browsers decide installability with their own criteria, so check the actual install prompt on a real phone.

A PWA also needs a service worker. This is a JavaScript file that runs in its own thread, so it has no DOM access and cannot touch window or document. It sits between the page and the network and can answer fetches from a cache. When the criteria pass, the browser may show an install prompt. The user can also choose Add to Home Screen. The app then opens in its own window without the address bar.

  1. install: the browser downloads the worker and fires install; the app shell is stored with cache.addAll.
  2. activate: runs after install; old caches are deleted here. The worker controls pages opened after it activates. Pages already open stay with the old worker until they reload, unless the worker calls skipWaiting and clients.claim.
  3. fetch: the worker hears each request and chooses cache or network.

Caching strategies and the offline fallback

cache.addAll([...]) fetches each URL and stores the response. If one URL fails, the whole call fails, so the app shell list must be correct. A cache-first rule checks Cache Storage first and goes to the network only on a miss; it is good for versioned static files. A network-first rule tries the network and falls back to cache; it is good for fresh data. Stale-while-revalidate serves the cached copy at once, then fetches a new copy in the background and stores it.

Use a versioned cache name such as shell-v2. On activate, delete caches whose names are not in the current list. Without this, a deploy leaves an old index.html in the cache and users keep the old app.

An offline fallback page is a cached HTML page shown when the network fails and the requested URL is not cached. For API calls, show the last stored value with a clear label; do not pretend it is live.

Server-side rendering and hydration

A single-page app sends one index.html that is nearly empty, plus a large JavaScript bundle. The browser must download, parse and run the bundle before the first meaningful paint. Until then the user sees a blank screen. A crawler that does not run JavaScript sees almost nothing.

SSR runs the React tree on the server. The server calls ReactDOMServer.renderToString on the app element and gets an HTML string. The server sends that string, so the first paint shows real content. The same JavaScript bundle then loads, and hydrateRoot attaches event handlers to the existing DOM instead of rebuilding it.

CSR is client-side rendering, SSR is server-side rendering and SSG is static site generation. They differ in when the HTML is made.

getServerSideProps runs on each request; getStaticProps runs at build time. Next.js gives routing plus server rendering out of the box, so it is a common example of SSR and SSG. Angular Universal renders an Angular app to HTML on the server for the first request, then the client app takes over.

5.8 State management with Redux and Flux

One shared store holds every value that many parts of the screen need. Only a plain function called a reducer may replace that state, and only in response to a plain object called an action. So every change has a name, a recorded before and after, and a reason. Redux, built on the earlier Flux architecture, is used in React carts, dashboards and admin panels where a bug report says "the count is wrong after I press back". This chapter builds a cart reducer and traces three dispatches through it.

You need: 5.2 for props, state and lifting state up, and 5.3 for the event handlers that dispatch actions.

Why shared state needs one home

In 5.2 state lived inside one component. That works until two far-apart components need the same value: a header shows a cart badge, a product list adds items, a checkout page reads the total. Lift the state to a common parent and every component in between receives props it never uses. That is prop drilling. Three symptoms follow: long prop chains, sibling components drifting out of sync, and bugs that are hard to reproduce because many setState calls spread the truth across the tree.

Flux is the architecture Facebook described for React. Data moves one way only. A view creates an action, a dispatcher sends it to the stores, the stores update, and the views re-render from the stores. Nothing writes back into a view or into another store.

Redux is Flux with two simplifications. One store for the whole app instead of several. And no dispatcher: the store hands each action straight to a pure function called the reducer. Fewer moving parts, the same one-way loop.

Store, action and reducer

The store is one object that holds the whole state tree. It has three methods: getState() returns the current state, dispatch(action) sends an action in, and subscribe(listener) registers a function the store calls after every change.

An action is a plain object: {type: 'ADD_ITEM', payload: {id: 1, name: 'Masala dosa', price: 60}}. type is a required string, payload carries the data, and Redux throws an error when type is undefined. An action creator is a small function that returns this object, so the string 'ADD_ITEM' is typed in one place only.

A reducer is a pure function (state = initialState, action) => newState. Pure means the same inputs give the same output, with no mutation of the argument, no fetch, no Date.now() and no Math.random(). It switches on action.type, and the default branch returns state unchanged, so unknown actions cost nothing. combineReducers({cart: cartReducer, user: userReducer}) joins small reducers into the shape {cart: ..., user: ...}.

nextState = reducer(currentState, action)

reducer is the pure function; currentState is the object inside the store before the dispatch; action is {type, payload}; nextState is a new object and the store replaces currentState with it.

  1. A component calls dispatch({type: 'ADD_ITEM', payload: item}).
  2. The store passes the current state and the action to the reducer.
  3. The reducer matches the type and returns a new object, leaving the old one untouched.
  4. The store saves the new object and calls every subscribed listener, so React re-renders the components whose selected slice changed.

React-Redux, immutability and the lighter option

React-Redux joins the store to React. Wrap the app once in the Provider component from react-redux, with the prop store={store}, where store is the object returned by createStore or configureStore. Every component below it can then read a slice with const count = useSelector(state => state.cart.count) and send actions with const dispatch = useDispatch(). Older code uses connect() with mapStateToProps and mapDispatchToProps; the idea is the same.

Never edit state in place. push and state.count++ change the existing object, and Redux compares old and new by reference: the same reference means "nothing changed", so no re-render. Copy first, then change.

const initial = { items: [], count: 0, total: 0 };
function cartReducer(state = initial, action) {
  switch (action.type) {
    case 'ADD_ITEM':
      return { ...state, items: [...state.items, action.payload],
               count: state.count + 1,
               total: state.total + action.payload.price };
    case 'REMOVE_ITEM':
      return { ...state, items: state.items.filter(i => i.id !== action.payload.id),
               count: state.count - 1,
               total: state.total - action.payload.price };
    default:
      return state;
  }
}

Async work: redux-thunk is one middleware that lets an action creator return a function instead of an object, so it can fetch and then dispatch the real action. Redux Toolkit's createSlice writes action types and reducers together and copies state for you. Middleware sits between dispatch and the reducer: redux-thunk for async work, redux-logger for logging. The Redux DevTools time-travel slider comes from a store enhancer, applied through the devTools option of configureStore or composeWithDevTools, not from middleware.

The Context API is React's built-in version: createContext, a Provider, and useContext, with no library. It suits a theme, a language or the logged-in user. It has no action log and no time travel. Redux is overkill when one value is shared, or when the state belongs to a single form — keep that in useState.

Worked example

Question. A cart reducer starts from {items: [], count: 0, total: 0}. ADD_ITEM appends payload to items, adds 1 to count and payload.price to total. REMOVE_ITEM drops the item whose id equals payload.id, subtracts 1 from count and payload.price from total. The app dispatches in order: (1) ADD_ITEM {id: 1, name: 'Masala dosa', price: 60}; (2) ADD_ITEM {id: 2, name: 'Filter coffee', price: 40}; (3) REMOVE_ITEM {id: 1, price: 60}. Trace the state after each dispatch and give the final items, count and total.

  1. Before any dispatch: items = [], count = 0, total = 0 rupees.
  2. Dispatch 1, ADD_ITEM dosa at 60 rupees: items = [...[], dosa] = 1 item; count = 0 + 1 = 1; total = 0 + 60 = 60 rupees. The initial object is not edited.
  3. Dispatch 2, ADD_ITEM coffee at 40 rupees: items = [dosa, coffee] = 2 items; count = 1 + 1 = 2; total = 60 + 40 = 100 rupees.
  4. Dispatch 3, REMOVE_ITEM id 1 at 60 rupees: items = the 2 items filtered to id not equal to 1 = [coffee] = 1 item; count = 2 − 1 = 1; total = 100 − 60 = 40 rupees.
  5. Final state: {items: [{id: 2, name: 'Filter coffee', price: 40}], count: 1, total: 40 rupees}.
  6. The badge shows 1 and the total shows 40 rupees, because the store handed React a new object at every step.

Answer. After three dispatches the cart holds one item, Filter coffee at 40 rupees, with count = 1 and total = 40 rupees.

Exam traps

  • A reducer that does state.items.push(item) or state.count = state.count + 1 returns the same object reference. React-Redux sees no change and the badge stays stale.
  • An action must be a plain object with a string type. dispatch({payload: x}) throws 'Actions may not have an undefined type property'.
  • Reducers must stay pure. An API call, Date.now() or Math.random() inside gives different states for the same action, so tests and DevTools time travel lie.
  • count is not items.length once you allow the same product twice with a quantity. Fix the rule in the question before you trace it.
  • Dispatching during render, instead of inside an event handler, re-renders, dispatches again, and loops forever.

5.9 Angular services, dependency injection, RxJS and HTTP client

A component should display data, not fetch it. Angular puts fetching and shared logic into a service: a plain class marked @Injectable that the injector builds once and hands to every component that asks for it in its constructor. The service calls Angular's HttpClient, which returns an RxJS Observable rather than a Promise. The Observable stays silent until someone subscribes, then emits the JSON from your REST API, possibly many times. Every Angular app that talks to a backend uses this split. It keeps components thin and puts the HTTP logic in one testable place.

You need: Chapter 5.6 for Angular components and constructors, Chapter 5.5 for generics like Observable<Product[]>, and Unit 6 for REST endpoints and JSON.

A service is one shared class the injector hands out

Two components often need the same data: the product list on the home page and the same list inside the cart. If each writes its own fetch, the URL and the JSON type appear twice, and a change means two edits. A service moves that code into one class that both components call.

A service is a TypeScript class marked with the @Injectable() decorator. The decorator makes the class available to Angular's injector, the part of the framework that creates objects and passes them to whoever asks. Writing @Injectable({providedIn: 'root'}) registers it with the root injector. Here providedIn is the metadata key and 'root' is its value: Angular builds one instance the first time a class needs it, keeps it, and hands that same instance to everyone afterwards. One instance is what lets the service hold a cached list that every screen sees.

A component receives the service by constructor injection: constructor(private productService: ProductService) {}. The private keyword declares a class field and assigns the argument into it, so the rest of the component writes this.productService.getProducts(). You never write new ProductService(); the injector reads the parameter type, creates the object and passes it in.

Every component also has an injector. If a component lists providers: [ProductService] in its @Component metadata, that component and its children get a fresh instance instead of the root one. That is the hierarchical injector in one line, and it explains why a service can be app-wide or per-screen. In a unit test you pass the component a fake service object, so no HTTP runs.

HttpClient turns a REST call into an Observable

HttpClient is Angular's wrapper over the browser's HTTP machinery. A standalone app enables it with provideHttpClient() in the providers of app.config.ts; an NgModule app imports HttpClientModule. Then inject it with constructor(private http: HttpClient) {}.

get<T>(url) returns an Observable<T>, where T describes the JSON the server sends, such as Product[]. post(url, body), put(url, body) and delete(url) each return an Observable too. The Observable is cold: no request leaves until something subscribes. subscribe(next, error) takes two callbacks; error receives an HttpErrorResponse whose status is 404 or 500, or 0 when the network itself failed.

In a template the async pipe subscribes for you: with products$ | async, the subscription starts when the view appears and ends when the component is destroyed.

@Injectable({ providedIn: 'root' })
export class ProductService {
  url = '/api/products';
  constructor(private http: HttpClient) {}
  getAll(): Observable<Product[]> { return this.http.get<Product[]>(this.url); }
  add(p: Product): Observable<Product> { return this.http.post<Product>(this.url, p); }
}

// inside the component
ngOnInit(): void {
  this.svc.getAll().subscribe({
    next: d => this.products = d,
    error: e => this.error = 'status ' + e.status
  });
}

An interceptor is a function placed in front of every HttpClient call; it can add a header, log the URL or retry centrally instead of in each service.

RxJS operators shape the stream

A Promise and an Observable both deliver asynchronous data, but they differ in three ways. A Promise starts at once and holds one value. An Observable is lazy, may emit many values over time, and can be cancelled by unsubscribing. That suits a search box, a chat feed or a stream of clicks.

Operators go inside .pipe(), and each takes an Observable and returns a new one. map(x => ...) transforms each value, filter drops values, tap runs a side effect such as console.log, and retry(2) resubscribes up to two more times after an error, giving three attempts in total.

catchError handles failure: catchError(() => of([])) replaces the error with an Observable that emits an empty array. The subscriber's next callback receives [] and the error callback never runs, so a 500 leaves an empty list instead of a crash.

A search box may call search(term) on every keystroke. debounceTime(300) waits for 300 ms of silence. switchMap cancels the previous request and subscribes the new one, so a slow old reply cannot overwrite a fresh one.

this.searchControl.valueChanges.pipe(
  debounceTime(300),
  switchMap(term => this.svc.search(term)),
  catchError(() => of([]))
).subscribe(list => this.results = list);

For shared state, a Subject is a multicast channel that replays nothing: subscribers get only values emitted after they subscribe. A BehaviorSubject needs an initial value and replays the latest value to each new subscriber, which suits a current-user or current-filter store.

To stop a subscription when the component dies, keep a Subject named destroy$, emit in ngOnDestroy, and add takeUntil(this.destroy$) to the pipe. The async pipe does the same job automatically.

Worked example

Question. A product search box is wired as searchControl.valueChanges.pipe(debounceTime(300), switchMap(t => svc.search(t))). A user types dosa with keystrokes at 0 ms, 120 ms, 250 ms and 400 ms. (a) How many GET requests go out with no operators at all? (b) With debounceTime(300) alone, how many GETs go out and when does the last one fire? (c) With switchMap but no debounceTime, how many GETs go out and how many are cancelled? (d) The final GET returns 500 and the pipe has catchError(() => of([])). How many items does the list hold?

  1. Count the keystrokes: four letters, so four values pass through valueChanges: d, do, dos, dosa. Without operators, each value triggers a request at once, so 4 GETs go out: q=d, q=do, q=dos, q=dosa.
  2. Gaps between keystrokes: 120 - 0 = 120 ms, 250 - 120 = 130 ms, 400 - 250 = 150 ms. All three gaps are below 300 ms, so each new letter restarts the debounce timer before it can fire.
  3. With debounceTime(300) the timer runs from the last letter only, at 400 ms. It fires at 400 + 300 = 700 ms with q=dosa. Total: 1 GET.
  4. switchMap alone does not wait. All 4 GETs still go out. Assuming each response takes longer than the gap to the next keystroke, 3 inner requests are still in flight and are cancelled; otherwise fewer are cancelled. The GET for q=dosa is the one that completes.
  5. A 500 reaches catchError, which returns of([]). The next callback runs with an empty array, so the list holds len([]) = 0 items and no error is shown.

Answer. 4 GETs with no operators; 1 GET fired at 700 ms with debounceTime(300); 4 GETs under switchMap alone, with 3 cancellations assuming each response takes longer than the gap to the next keystroke (otherwise fewer are cancelled); and 0 items listed after the 500.

Exam traps

  • An Observable does nothing until it is subscribed. Writing this.svc.getProducts(); and stopping there sends no request and fills no list; the GET happens inside subscribe or behind the async pipe.
  • A subscription started in ngOnInit keeps running after the component is destroyed. Opening that screen five times leaves five live subscriptions holding dead components: unsubscribe, add takeUntil(this.destroy$), or use the async pipe.
  • catchError must return an Observable, so write of([]) and not []. Returning a bare array is a type error, and catchError catches errors thrown by operators above it in the pipe, not below it, so it usually goes last.
  • debounceTime alone does not stop an old slow response from arriving last and overwriting the new one. switchMap cancels the previous inner request; mergeMap and concatMap keep it alive.
  • Each subscribe on an HttpClient Observable sends a new request. Two components subscribing to the same getProducts() return 2 GETs, not 1, unless the service shares the stream.

React is a library for the view layer; Angular is a full framework with router, forms, HTTP and DI built in; React uses JSX in JavaScript; Angular uses HTML templates plus TypeScript classes; React data flow is one-way by default; Angular offers two-way binding with ngModel; Both have client-side routers and lazy loading; Angular ships more structure and convention; React leaves choice of libraries open; Judgement: team size, TypeScript use, long-term maintenance.

Evaluate A team's single-page React app has slow first load and poor search-engine visibility. Evaluate server-side rendering and a progressive web app as remedies, and state which problem each one actually solves. 15 marks

SSR sends finished HTML so the first screen paints before JavaScript loads; also helps crawlers; Hydration attaches React to the server HTML without rebuilding the DOM; PWA with manifest and service worker gives installability and offline use, and can speed repeat visits through caching; PWA does not fix first-paint or SEO; SSR does not give offline support; Cost: SSR needs a Node server and careful data fetching; PWA needs cache-version discipline; Recommendation should match the stated problem.

Analyze Explain prop drilling, then compare lifting state up, the Context API and Redux as ways to share state in a large React application. 15 marks

Prop drilling = passing props through intermediate components that do not use them; Lifting state up works for shallow trees and small scope; Context API avoids drilling for low-frequency values such as theme and logged-in user; Redux gives one store, pure reducers, devtools time travel, middleware for async; Trade-off: boilerplate and indirection versus predictability and traceability; Recommendation depends on update frequency and number of consumers.

Analyze Trace the life of an HTTP request in an Angular app from a button click in the template to the rendered list, naming every Angular feature involved. 13 marks

Event binding calls a method in the component class; Component calls an @Injectable service obtained through constructor injection; HttpClient returns a cold Observable; nothing happens until subscribe; RxJS operators such as map or catchError transform or handle errors; Template renders the result through *ngFor, the async pipe or a subscription with a stored value; Unsubscribe on destroy where a manual subscription is used.

Glossary

Action
A plain object with a type field, and optional payload, that describes a state change in Redux.
Client-side router
A library that maps URL paths to components and updates the view without a full page request.
Controlled component
A form field whose displayed value is driven by React state and updated through an onChange handler.
Data binding
The link that keeps a component class and its template in sync in one or both directions.
Decorator
A TypeScript syntax starting with @ that attaches metadata to a class or member, used heavily by Angular.
Dependency injection
A pattern where a framework creates a class's dependencies and supplies them, instead of the class creating them itself.
Directive
An Angular class or template marker that changes the DOM, either structurally or by altering an existing element.
Hook
A function such as useState or useEffect that gives a function component state or lifecycle behaviour.
Hydration
Attaching client-side framework code to server-rendered HTML so it becomes interactive without being rebuilt.
JSX
A syntax extension that lets HTML-like tags appear inside JavaScript, compiled into function calls before the code reaches the browser.
Middleware
A function that sits between dispatch and the reducer, used in Redux for logging, async calls or crash reporting.
Observable
A lazy stream object from RxJS that emits values over time to each subscriber.
props
The read-only object of values a parent passes into a child component.
Pure function
A function whose output depends only on its inputs and which changes nothing outside itself.
Reconciliation
React's diffing process that compares two virtual trees and applies the minimum set of DOM updates.
Redux store
The single object holding application state, with getState, dispatch and subscribe methods.
Server-side rendering
Rendering the first HTML of a page on the server so the browser can paint before any JavaScript runs.
Service worker
A background script that intercepts network requests for a site and can answer them from a cache.
Single-page application
A web app that loads one HTML document and swaps views in the browser as the URL changes.
state
Values a component owns, changes through a setter, and re-renders itself when they change.
Synthetic event
React's normalised wrapper around the browser event, passed to handlers as e.
Type inference
The compiler working out a type from the assigned value, so an annotation is not always needed.
TypeScript
A superset of JavaScript that adds optional static types, checked at compile time and then removed.
Virtual DOM
An in-memory tree of plain objects that React keeps and compares with the next tree to decide which real DOM nodes to change.
