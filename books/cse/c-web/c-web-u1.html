1.1 Internet, World Wide Web and DNS: how the web works

You tap a link and a page appears. Between the tap and the page, three things happen: the browser turns a name into a numeric address, it opens a connection to that address, and it asks for one resource. The name-to-address step is the Domain Name System, or DNS. It exists because people remember names like shop.example.com while routers need numbers like 203.0.113.10. Every UPI payment, every IRCTC ticket check, every video load begins this way. This chapter follows one URL from the browser to the server and back.

The Internet is the road, the web is one kind of traffic

The Internet is a global network of networks. It moves data as packets: small chunks of bytes, each with a header holding a source address and a destination address. An IP address is that number, for example 203.0.113.10. IPv4 addresses are 32 bits, written as four numbers from 0 to 255. IPv6 addresses are 128 bits, written in hexadecimal.

Routers are the machines in between. A router reads the destination address on a packet and forwards it on one of its links. The packet moves hop by hop, and no single machine knows the whole path.

The World Wide Web is a service that runs on the Internet. It is a set of resources, each named by a URL, fetched with HTTP and usually written in HTML. Email, video calls and file transfer also use the Internet but are not the web.

DNS: one name, one address, found by asking in steps

The browser knows a name; the network needs an address. DNS (Domain Name System) is a distributed database that maps names to addresses. No single machine holds every name, so an answer is found by asking a short chain of servers, as the figure shows.

  1. The browser asks its configured resolver, usually run by the ISP or a public service.
  2. The resolver asks a root server. The root does not know the address; it refers the resolver to the servers for the top-level domain, here .com.
  3. The resolver asks the TLD (top-level domain) server. It refers the resolver to ns1.example.com, the domain's own authoritative server.
  4. The resolver asks the authoritative server. It answers with the record, for example A 203.0.113.10, plus a TTL.
  5. The resolver returns the answer to the browser and keeps a copy for the TTL.
  • A record: name to IPv4 address, for example 203.0.113.10.
  • AAAA record: name to IPv6 address.
  • CNAME record: name to another name, an alias, for example www.example.com to shop.example.com.
  • MX record: name to a mail server, with a preference number.

TTL (time to live) is the number of seconds a cached answer stays valid. With TTL 300, a resolver may answer from its cache for 300 s and then must ask again. So an answer is held in caches for its TTL and can still change later, once the TTL runs out and a fresh answer is fetched.

The parts of a URL

A URL (Uniform Resource Locator) names one resource. Take https://shop.example.com:443/items?id=7#top. Each part has one job.

When the port is left out, the scheme supplies it: 80 for http and 443 for https. The query string is sent to the server; the fragment never is.

One URL from tap to page

  1. Parse the URL into scheme, host, port, path and query.
  2. Check the browser cache, then the operating system cache, then ask the resolver for the host.
  3. Open a TCP connection to the returned IP address on the port: 443 for https, 80 for http. TLS runs on top of it for https, see 1.4.
  4. Send an HTTP request, for example GET /items?id=7, with a Host header.
  5. The server returns a status code and the resource; see 1.3 for what kind of server answers.
  6. The browser reads the HTML and requests CSS, JavaScript and images, each repeating these steps but usually served from cache.
  7. It builds the page and paints it; the markup and the scripting belong to Unit 2 and Unit 3.

Fetching the main resource is one request-response round trip; the sub-resources the page needs each add their own round trip. Knowing the order tells you where a failure sits: a wrong name is a DNS problem, a refused connection is a port or server problem, a 404 is a path problem.

Worked example

Question. A browser opens https://shop.example.com:443/items?id=7. Trace the DNS lookup and the connection. State the host, port, path and query. How many servers are asked on the chain, and how long may a cache keep the answer? Which TCP port does the browser use after DNS?

  1. Step 1: split the URL. Scheme is https, host is shop.example.com, port is 443, path is /items, query is id=7. There is no fragment.
  2. Step 2: the browser asks its resolver for shop.example.com.
  3. Step 3: the resolver asks a root server, which refers it to the .com TLD servers. That is server 1.
  4. Step 4: the resolver asks the .com TLD server, which refers it to ns1.example.com. That is server 2.
  5. Step 5: the resolver asks the authoritative server ns1.example.com, which answers A 203.0.113.10 with TTL 300 s. That is server 3. So three name servers were asked on the chain — root, TLD and authoritative — in addition to the browser's own resolver.
  6. Step 6: the resolver caches the record for 300 s, so any cache may answer with 203.0.113.10 for up to 300 s.
  7. Step 7: the scheme is https, so the browser opens a TCP connection to 203.0.113.10 on port 443 and sends GET /items?id=7.

Output

3
300

Answer. Host shop.example.com, port 443, path /items, query id=7; 3 servers are asked on the chain; the answer may be cached for 300 s; the browser then opens TCP port 443.

Exam traps

  • A cached DNS answer skips root, TLD and authoritative servers until the TTL expires. The full walk happens only on a cache miss.
  • Port 443 is HTTPS and port 80 is HTTP. A URL with no port takes the default from its scheme, so an https URL with no port written means 443 and an http URL with no port means 80. A port written in the URL overrides the default, e.g. https://api.example.org:8443 uses 8443.
  • The query string (?id=7) is sent to the server; the fragment (#top) is not. Marks are lost by naming the fragment as server data.
  • A CNAME gives another name, not an address. An MX record points at mail servers, so a domain's mail can live on a different machine from its web site.
  • The World Wide Web is not the Internet. The web is one service running on the Internet's packet network.

Beyond the syllabus

Not for the exam. In production, DNS is also a traffic tool: weighted answers split traffic between servers in set proportions, and latency-based answers send each user to the data centre with the shortest measured delay. Anycast puts one IP address on many machines. DNS over HTTPS encrypts the query inside the connection, so the ISP can see who you are talking to but not which names you asked for. DNSSEC signs answers so a forged reply is rejected. Cloud platforms tie DNS to load balancers, so a host name often points at a service, not a single machine. 1.2 Client-server and multi-tier web architecture

A client-server system splits work between a requester and a responder. The client shows pages and sends requests. The server accepts requests, runs logic and asks a database for stored data. Splitting these duties into tiers lets each part be built, scaled and replaced on its own. A small app may use one machine. A busy exam portal may use many servers behind a load balancer. The same request path carries normal page loads and Ajax calls.

You need: 1.1 Internet, World Wide Web and DNS for the URL, DNS lookup and first client-server request.

Tiers are duties, not machines

A tier is one job in a web system. The same physical server can run more than one tier; a large system can run one tier across many machines.

A two-tier design has the client on one side and a server or database on the other. The client may send SQL queries directly to a database. This is simple for a small internal tool. It is hard to secure and scale because every client needs database access and business rules live in client code.

A three-tier design separates three jobs:

  • Presentation tier: the browser page, mobile screen or server-side template. It shows data and collects input.
  • Application tier: the business logic. It checks rules, calculates, calls other services and decides what to save.
  • Data tier: the database or file store. It keeps state.

The general name is n-tier or multi-tier. A web tier that only serves static files and forwards dynamic requests is often placed before the application tier; see 1.3 Web browsers, web servers and application servers. Tiers let teams build, scale and replace parts alone.

The request path from browser to database

A browser sends an HTTP request to a host name. DNS gives an IP address, as in 1.1. The request reaches a load balancer first. A load balancer is a server that receives traffic and forwards each request to one of many app servers. It may use round robin, least connections or a hash of the client address.

Behind it sit app servers. An app server runs business logic. It may read or write a database, call a payment API or check a login. The database is the data tier. The reply goes back along the same path.

Two optional positions matter. A cache stores copies of answers close to the user or close to the app, so repeated reads avoid the database. Middleware is software that sits in the request path and does a shared job: logging, authentication, compression or routing.

In the figure, 20 requests/s arrive. The load balancer sends 10 requests/s to each of two app servers. Each app server has a tested limit of 15 requests/s, so 10 is safe. Both query one database. The database must handle their combined query rate.

This is the same path Ajax uses: a page's JavaScript sends a small request in the background while the page stays open; see Unit 3.

Stateless requests and cloud service models

HTTP is stateless; message details are in 1.4 HTTP and HTTPS. Stateless means the server does not keep memory of one request when the next request arrives. Each request must carry enough information to be understood. This is why a session cookie is sent on every request.

A session is the server's memory of a logged-in user across requests. If app server 1 stores the session only in its own memory, the next request may go to app server 2 and fail. So sessions need shared storage: a session database, a Redis-style store or a signed token that the client sends back. Shared storage keeps login state independent of which app server answers.

Cloud service models name who manages the layers. Infrastructure as a Service (IaaS) gives virtual machines, storage and networks. Platform as a Service (PaaS) gives a runtime for your app and manages the servers below it. Software as a Service (SaaS) gives a finished application over the web. These are service models, not tiers. Deployment with Docker, cloud hosting and CI/CD is in Unit 6.

Worked example

Question. An exam portal has 600 students. Each student sends 20 requests in the first 10 minutes (600 s). Find the average request rate. Each app server handles 15 requests/s. How many app servers are needed at that average, and what rate does each get?

  1. Total requests = 600 students × 20 requests per student = 12,000 requests.
  2. Time = 10 minutes × 60 seconds per minute = 600 s.
  3. Average rate = 12,000 requests ÷ 600 s = 20 requests/s.
  4. Servers needed = ⌈20 ÷ 15⌉ = ⌈1.333...⌉ = 2.
  5. Requests per server = 20 ÷ 2 = 10 requests/s. Each server is below its 15 requests/s limit.

Answer. The average rate is 20 requests/s. Two app servers are needed, and each gets about 10 requests/s.

Exam traps

  • A tier is a logical duty, not one machine. A three-tier design can run on one laptop or across many containers.
  • A load balancer does not run business logic; it chooses an app server and may check server health.
  • Stateless does not mean no sessions. It means each request carries its own context; shared storage keeps session data.
  • Two-tier is not always client plus database. A two-tier design may be client plus a server that also stores data.
  • IaaS, PaaS and SaaS are cloud service models, not architecture tiers.

1.3 Web browsers, web servers and application servers

A browser turns HTML, CSS and JavaScript into a screen you can use. A web server answers requests for files. An application server runs the code that decides, calculates and saves data. These three roles appear in every web system, from an IRCTC ticket page to a UPI payment screen. The roles are separate ideas, but one machine or one process can play more than one role. This chapter shows what each part does and how a request moves through them.

You need: 1.2 for client, server and tiers.

Browser parts and the request path

A browser is a program that fetches web resources and renders them. It has four parts you should name. The rendering engine turns HTML and CSS into pixels; examples are Blink in Chrome and Edge, Gecko in Firefox, WebKit in Safari. The JavaScript engine runs scripts; examples are V8 in Chrome and Node.js, SpiderMonkey in Firefox. The network stack opens connections and sends HTTP requests; HTTPS is HTTP inside TLS, the encryption layer. Storage keeps cookies in small key-value records and localStorage in larger key-value records; both survive page reloads. The same-origin policy lets a page read storage and responses only from the same protocol, host and port, unless the server allows otherwise.

When you type a URL, DNS gives an IP address (see 1.1), the network stack connects to the server, and the browser asks for the page. HTTP details are in 1.4. The response may come from a web server as a stored file, or from an application server as computed output. The browser does not know which one produced it; it only reads status codes, headers and body.

Web server: files, TLS and reverse proxy

A web server is software that listens on a port, accepts connections, reads an HTTP request, and sends a response. Apache HTTP Server and Nginx are common. Public web servers listen on port 80 for HTTP and port 443 for HTTPS; port numbers are part of the address. A static request asks for a file that already exists: /logo.png, /style.css, /index.html. The web server reads the file from disk and returns it with a content type. This is fast because no program runs per request beyond the server itself.

On HTTPS, the web server often ends TLS: it decrypts the request and encrypts the response. It can also act as a reverse proxy. A reverse proxy accepts requests from clients and forwards them to another server, usually on an internal port such as 3000 for a Node.js app or 8080 for Tomcat. Clients see one public address; the back-end ports stay private. Nginx may serve 700 static requests per minute and proxy 300 requests per minute to an Express app. A dynamic request needs code to run: read a form, check a login, query a database. The web server forwards it; the application server handles it.

Application server, middleware and request lifecycle

An application server runs application code for dynamic requests. It may be a Java process in Tomcat, a Node.js process running Express, or a Python process running Django. It loads routes, runs handlers, talks to a database, and builds a response. In small systems the same Node.js process can serve static files and run app code; the roles are roles, not always separate machines.

Middleware is code that runs between the request and the final handler. It can log a request, parse JSON, check a session cookie, add CORS headers, or reject a bad request. Express calls these functions middleware; Java servlet filters do similar work. Some syllabi call the application server the middleware host because middleware runs inside it.

Request lifecycle: 1 accept the TCP connection; 2 read and parse the HTTP request; 3 route by method and path; 4 run middleware; 5 run the handler and database queries; 6 build status, headers and body; 7 send the response; 8 log and close or reuse the connection. A web server does steps 1-2 and then either serves a file or forwards to an app server. The app server does 3-7. Logging can happen in both. If the database is slow, the handler waits; the server must handle other requests in parallel, by threads or an event loop.

Worked example

Question. Nginx receives 1,000 requests/min. 70% are static and 30% are proxied to Express. Find static and dynamic requests per minute and per second. Express handles 25 requests/s. Is it enough?

  1. Total load = 1,000 req/min.
  2. Static requests per minute = 0.70 × 1,000 = 700 req/min.
  3. Dynamic requests per minute = 0.30 × 1,000 = 300 req/min.
  4. Static requests per second = 700 ÷ 60 = 11.666... ≈ 11.7 req/s.
  5. Dynamic requests per second = 300 ÷ 60 = 5 req/s.
  6. Express capacity = 25 req/s. 25 req/s is greater than 5 req/s, so it is enough. Spare capacity = 25 − 5 = 20 req/s.

Answer. Static is 700 req/min (11.7 req/s), dynamic is 300 req/min (5 req/s), and Express is enough, with 20 req/s spare.

Exam traps

  • A web server is a role, not always a separate machine. One Node.js process can serve files and run API handlers.
  • Port 80 is HTTP and port 443 is HTTPS. Ports 3000 and 8080 are common internal app ports, not public web ports.
  • Static does not mean cached by the browser. Static means the file exists before the request; caching is a separate header decision.
  • A reverse proxy sits in front of servers for clients. A forward proxy sits in front of clients for servers.
  • Middleware is not the final handler. It runs before or after the handler and often calls next() to continue.

1.4 HTTP and HTTPS: URLs, requests, responses and methods

HTTP (HyperText Transfer Protocol) is how a browser and server talk: the client sends a request, the server replies, and the server remembers nothing between messages. That statelessness is why every request must carry all the server needs. HTTPS is the same conversation inside TLS, so the path cannot read it. Every app — IRCTC, UPI, a result page — is a stream of these messages. This chapter reads one request and response line by line, then sorts methods and status codes by their promises.

You need: 1.1 for URLs and DNS, and 1.2 for the client-server exchange.

One URL, one request, one response

A URL (Uniform Resource Locator) names one resource on one host. In https://api.example.com/items/7?expand=price the scheme is https; host api.example.com is resolved by DNS (1.1); port is omitted and defaults to 443 for HTTPS, 80 for HTTP; path /items/7 names the resource; query ?expand=price carries input. A #fragment stays in the browser.

In HTTP/1.1 the message is plain text (ASCII headers); HTTP/2 sends the same information in a binary frame format, covered in Section 4. A request has four parts: request line (method, path with query, version), header lines Name: value, one compulsory empty line, then optional body. A response has a status line (version, three-digit code, reason phrase), headers, empty line, optional body.

GET /items/7?expand=price HTTP/1.1
Host: api.example.com
Accept: application/json
// empty line; GET has no body

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 84
// empty line, then 84 bytes of JSON

HTTP is stateless: the server keeps no memory of earlier requests, so each one must carry its own identity, format and parameters. Cookies, sessions and tokens add memory on top (Unit 4, Cookies and session tracking).

Methods: the verb of the request

The method names the action. A method is safe when it only reads and does not change server state. A method is idempotent when sending the same request twice leaves the same end state as sending it once.

MethodSafeIdempotentUse

The table's safe methods are GET, HEAD and OPTIONS; the standard also defines TRACE as safe, rarely used in app code. GET is the everyday read: typing an address, clicking a link, an HttpClient.get() call (Unit 5) sends GET. POST submits data and changes state, so it is neither safe nor idempotent — a double click on Pay in a UPI app can create two orders. PUT replaces the whole resource, so repeating it is harmless. DELETE repeated is harmless; the second call may answer 404. PATCH sends a partial update and is not idempotent in general. HEAD returns headers with no body. OPTIONS asks which methods a resource allows; browsers use it before a cross-origin request.

Status codes: the result

The status code is three digits; the first digit is the class.

  • 1xx — informational; the request is still in progress (100 Continue).
  • 2xx — success; the request was understood and done.
  • 3xx — redirection; the resource is elsewhere or unchanged.
  • 4xx — client error; the request itself is wrong.
  • 5xx — server error; the request was fine and the server failed.
CodeMeaning

The reason phrase is for humans and may say anything; only the code is guaranteed. The class tells you who must act: on a 4xx fix the request, on a 5xx retry later or report a bug.

HTTP versions and HTTPS

HTTP/1.1 keeps the TCP connection open after a response — a persistent connection — so requests reuse it one after another. Pipelining proved fragile, so browsers open about six connections per host.

HTTP/2 multiplexes many independent streams on one TCP connection, compresses headers and is binary, which cuts latency. TCP still delivers bytes in order, so one lost packet stalls every stream.

HTTP/3 runs on QUIC over UDP, so a lost packet stalls only its own stream and the handshake is shorter.

HTTPS is HTTP inside TLS on port 443. TLS encrypts bytes, detects tampering, and proves server identity with a certificate, so an OTP on café Wi-Fi is unreadable on the path.

For live traffic — chat, a cricket score ticker, a game — request-response is clumsy. WebSockets keep one two-way connection open; WebRTC carries peer-to-peer media and data.

Worked example

Question. A client sends GET /items/7?expand=price HTTP/1.1 to api.example.com on port 443. The reply is HTTP/1.1 200 OK, Content-Type: application/json, Content-Length: 84. Then POST /items returns 201 Created; then DELETE /items/7 returns 204 No Content. (a) Classify each status code. (b) Is GET safe and idempotent? (c) Give the body length of the GET and DELETE replies.

  1. First digits 2, 2, 2: all three are 2xx success.
  2. 200 OK has a body; 201 Created reports a new resource with Location; 204 No Content sends no body by design.
  3. GET reads only, so it is safe; repeating gives the same state, so it is idempotent.
  4. Content-Length: 84 means GET body is 84 bytes; 204 forbids a body, so DELETE body is 0 bytes.

Output

GET body = 84 bytes
DELETE body = 0 bytes

Answer. All three are 2xx success; GET is safe and idempotent; GET body = 84 bytes, DELETE body = 0 bytes.

Answer. 301 is 3xx redirection; 204 is 2xx success; Location names the new URL; 204 body = 0 bytes.

Exam traps

  • Safe is not zero side effects: GET may be logged or counted but must not change the resource. The table's safe methods are GET, HEAD and OPTIONS; the standard also defines TRACE as safe, rarely used in app code.
  • POST and PATCH are the common methods that are neither safe nor idempotent. Retrying a POST after a timeout can create a duplicate order; PATCH may also give a different result when repeated. Retrying PUT or DELETE cannot create a duplicate.
  • 401 and 403 look alike: 401 means you are not authenticated or your credentials are wrong; 403 means you are known but not allowed. A login page often returns 401.
  • 404 is a client-side problem (wrong URL); 500 is the server failing after a valid request. Never blame the client for a 5xx.
  • 301 and 304 both start with 3 and involve the browser: 301 sends you to a new URL, 304 tells you to reuse your cached copy with no body sent.

Check yourself

Remember Name the table's safe methods and say what safe means. Which other standard method is safe but rare in app code? 2 marks

GET, HEAD, OPTIONS; the standard also defines TRACE as safe. Safe means reads only, no change to server state.

Remember What does a 5xx status code mean? 2 marks

Server error: the request was valid but the server failed, as in 500 Internal Server Error.

Understand Why must a stateless protocol resend the login token on every request? 3 marks

The server keeps no memory between requests, so each request must carry its own identity, usually a cookie or token header.

Understand Why does HTTP/2 need multiplexing when HTTP/1.1 already has persistent connections? 3 marks

Persistent connections still handle requests one after another; a slow response blocks the queue. Multiplexing interleaves many streams on one connection.

Apply A script sends PUT /items/7 three times after timeouts, then DELETE /items/7 twice. What is the end state and why is retry safe? 4 marks

PUT is idempotent: three replacements equal one. DELETE is idempotent: the item ends removed; the second may answer 404. No duplicate resources.

Apply A request reaches a server with a wrong path, then the database crashes. Which single code fits each case? 4 marks

Wrong path: 404 Not Found, a 4xx client error. Database crash: 500 Internal Server Error, a 5xx server error.

Analyze A mobile app retries every failed request once. Which methods can duplicate data? How do you stop that? 5 marks

POST and PATCH can duplicate: two POSTs create two orders, repeated PATCH may differ. Retry only safe or idempotent methods, or send POST with a unique idempotency key the server checks first.

Analyze A page uses HTTPS, yet a colleague says traffic can still be modified on public Wi-Fi. What does TLS guarantee and what does it not? 5 marks

TLS encrypts bytes, detects tampering, and authenticates the server by certificate, so the path cannot read or silently change the request. It does not protect a compromised device, a wrong host name, or data after the server.

Beyond the syllabus

Not for the exam. Large content networks serve over HTTP/3 on QUIC because the shorter handshake copes with lossy mobile links. gRPC requires HTTP/2 framing; GraphQL is transport-agnostic but is usually sent as a single POST to one endpoint, so the methods and status codes still apply. WebSockets carry chat and live scores; WebRTC carries video calls in the browser. Search RFC 9110 for HTTP semantics and RFC 9000 for QUIC. TLS 1.3 and post-quantum key exchange are where transport security is heading.

1.5 Front end, back end and full stack roles; MERN stack

One click on a shopping page passes through three kinds of work: the interface the user touches, the server logic that decides what to do, and the database that stores the answer. Each kind of work is a role. A front-end developer owns the first, a back-end developer the second, and a full stack developer can move across all three. MERN is one common combination, in which JavaScript runs in both the browser and the server. Job ads at Indian product companies and startups are written in exactly these words, so you need to know what each one promises.

You need: 1.2 for client, server and data tiers, 1.3 for what browsers and application servers do, and 1.4 for HTTP methods and status codes.

Front end, back end and the data store

A web system is split into tiers so each part can be built and replaced on its own. Each tier needs people who know it well, and the common job titles follow that split.

  • Front end. The code that runs in the browser: HTML for structure, CSS for appearance, JavaScript for behaviour, plus a UI framework such as React or Angular. This person also cares about accessibility (can a screen reader use the page?) and browser performance (how soon does the page become usable?).
  • Back end. The code that runs on the application server: the server language, URL routing, business logic, authentication, and the queries that reach the database. It answers requests; it does not draw screens.
  • Database. The store and its query language. This person designs the schema, writes queries and chooses indexes.

DevOps supports all three tiers and is sometimes counted as an extra layer of the stack. DevOps covers build, test, deploy and monitor. It is a real role in industry and is taught later (see Unit 6, Node.js, Express and Databases).

What the full stack developer actually does

A full stack developer can write the React component, add the Express route, and change the MongoDB query that feeds it. The value is not being the best at each layer. The value is that one person can carry a feature from the button to the disk and back.

A user reports that an order total is wrong. The work then goes down the request path, one layer at a time.

  1. Open the browser console and check the value React received.
  2. Open the network tab and read the JSON the API returned.
  3. Check the server log to confirm which route ran and what it returned.
  4. Query the database to see the stored document.
  5. Fix the first layer where the number is already wrong, then re-check at the API boundary.

Small teams and startups rely on this role because one person can ship a whole feature. Large teams split it again into specialists. Do not read full stack as expert in everything; it means working knowledge across the path, with depth in one or two layers.

MERN: one language on both sides

MERN is a named stack, four technologies that fit together because all four speak JavaScript.

  • MongoDB — the database. It stores documents, which are JSON-shaped records, inside collections.
  • Express — the web framework on the server. It maps an HTTP method and path to a handler function.
  • React — the front-end library. It renders the UI from data and updates it when the data changes (see Unit 5, Front-End Frameworks: React and Angular).
  • Node.js — the runtime that runs JavaScript outside the browser, so the server code is JavaScript too.

Node.js is a runtime, not a framework. Express is the framework that runs on top of it.

  1. The user clicks Add to cart, and a React event handler runs in the browser.
  2. React calls fetch with method POST and path /api/cart, sending a JSON body.
  3. Node.js accepts the connection and hands the request to Express.
  4. Express matches the method and path to a route handler.
  5. The handler validates the request and queries MongoDB.
  6. MongoDB returns the matching document.
  7. Express sends a JSON response with status 200.
  8. React updates its state and the browser repaints the cart count.

Other stacks do the same work with different parts. PHP with MySQL, or Java with Spring and a relational database, are equally full stack (see Unit 4, Server-Side Scripting: PHP and Java). The tiers stay the same; only the languages change.

Worked example

Question. A MERN product page loads 20 products. Each product is sent as 0.6 KB of JSON. MongoDB holds 250 products. Express can serve up to 40 requests per second, and peak traffic is 8 requests per second. (a) Find the JSON size of the product list. (b) Find the spare capacity in requests per second and express it as a multiple of peak traffic. (c) Name the layer that owns a product document.

  1. JSON size = number of products × size per product = 20 × 0.6 KB.
  2. 20 × 0.6 = 12, so the response carries 12 KB of JSON.
  3. Spare capacity = capacity − peak = 40 − 8 = 32 requests/s.
  4. As a multiple of peak: 32 ÷ 8 = 4, so the server has 4 times the peak load spare (its total capacity is 5 times peak).
  5. Ownership: MongoDB stores the product document. Express reads it and returns JSON; React only renders what it receives.

Answer. The product list is 12 KB of JSON, 32 requests/s of spare capacity remain (4 times peak traffic), and MongoDB owns the product document.

Worked example 2

Question. A page loads 30 products, each sent as 0.8 KB of JSON. The server handles up to 50 requests per second, and peak traffic is 10 requests per second. Find the JSON size and the spare capacity as a multiple of peak.

  1. JSON size = 30 × 0.8 KB = 24 KB.
  2. Spare capacity = 50 − 10 = 40 requests/s.
  3. Multiple of peak = spare ÷ peak = 40 ÷ 10 = 4 times.

Answer. The list is 24 KB of JSON and 40 requests/s of spare capacity remain, which is 4 times peak traffic (total capacity is 5 times peak).

Exam traps

  • MERN is not required for full stack work. A developer using PHP with MySQL, or Java with Spring, is just as full stack.
  • Node.js is a runtime, not a web framework. Express is the framework. Writing Node framework in an answer loses the mark.
  • MongoDB stores documents in collections. Rows and tables belong to relational databases such as MySQL.
  • React never talks to MongoDB directly. Every read and write crosses the HTTP API.
  • Full stack does not mean expert in every layer. The safe phrasing is breadth across the request path with depth in one or two layers.

Check yourself

Remember Name the four technologies in MERN and state the job of each in one phrase. 2 marks

MongoDB — document database. Express — server web framework and routing. React — browser UI library. Node.js — JavaScript runtime on the server.

Remember Which layer owns a product document, and which layer renders it? 2 marks

MongoDB owns and stores the document. React renders whatever the API returns for it.

Understand Why is Node.js called a runtime and not a framework? 3 marks

A runtime is the environment that executes code and provides APIs such as file system and network access. A framework supplies structure and calls your code. Express is that framework, and it runs on the Node.js runtime.

Apply A page loads 30 products at 0.8 KB of JSON each. The server handles 50 requests per second, and peak traffic is 10 requests per second. Find the JSON size and the spare capacity as a multiple of peak. 4 marks

JSON size = 30 × 0.8 = 24 KB. Spare capacity = 50 − 10 = 40 requests/s. Multiple of peak = spare ÷ peak = 40 ÷ 10 = 4 times (total capacity is 5 times peak).

Analyze An order total shows ₹0 in the browser, but the database holds the correct amount. Which layer do you inspect first, and why? 5 marks

Inspect the network tab first, because it separates browser from server. If the API returned the right number, the bug is in React state or rendering. If the JSON is wrong, move to the Express handler and then to the MongoDB query. The first layer where the value is already wrong owns the bug.

Understand A teammate says: we use MERN, so we are a full stack team. Is that correct? 3 marks

Not by itself. Full stack is a role that spans front end, back end and data. MERN is one set of tools that fills those three places; PHP with MySQL or Java with Spring fill them equally.

Beyond the syllabus

Not for the exam. Frameworks that merge the two sides are now common: Next.js renders React on the server, and serverless functions replace a long-running Express server for small APIs. TypeScript has become the default language for new Node projects because it catches type errors before deployment. DevOps — containers, CI and CD, monitoring — is often described as an extra layer alongside front end, back end, database and the runtime. Interviews for MERN roles usually walk the whole request path rather than testing one framework. Search for React server components, Next.js API routes, and the Node.js event loop to go further.

1.6 Developer tools: VS Code, Git and browser consoles

Three tools close the edit-run-inspect loop. VS Code is the editor: it holds your files, runs a terminal and pauses code at breakpoints. Git records the history of those files as commits, so you can go back or work on a branch. The browser console and DevTools report what actually happened: JavaScript errors, and the URL, method, status and size of every request. Used together they replace guesses with measurements. This chapter wires the three into one habit; deployment and branching strategy come later.

You need 1.3 for who renders and who answers, and 1.4 for the status codes and headers you will read in the Network panel.

VS Code: edit, run and pause in one window

Visual Studio Code is a free source-code editor from Microsoft. It runs on Windows, macOS and Linux. You open a folder as a workspace; the file explorer on the left lists that folder, and a click opens a file in a tab.

The editor is not a compiler and not a web server. It does not build or serve your page by itself. It gives you an integrated terminal (Ctrl+`) that runs the same commands a shell would: node app.js, python manage.py, git status. The output appears beside your code, so you never switch windows.

Extensions add language support. Live Server serves a folder over HTTP and reloads the browser on each save. Prettier reformats code. ESLint marks JavaScript problems as you type. Extensions run with your permissions, so install only what you need.

A breakpoint is a red dot set in the gutter left of a line number. Start the debugger with F5 and execution pauses at that line. The Variables panel shows the variables in the current scope and the scopes above it; the debug console lets you evaluate any expression you type. Step over runs the next line without entering a function; step into goes inside it. You read the real value instead of guessing with print statements.

Git: three places a file can live

Git is a version control system. A repository is a folder Git watches, plus a hidden .git directory that stores every saved version. Inside it a file passes through three places.

  • The working tree is the folder as you see it, including your unsaved-in-Git edits.
  • The staging area, also called the index, is the set of changes chosen for the next save.
  • The repository is the permanent record: the chain of commits.

git status prints which file is in which place. Two commands move a file forward. git add app.css copies the current content into the staging area. git commit -m "fix navbar colour" records the staged content as a commit, carrying a hash id, the author, the time and the message.

A commit is local. It writes to .git on your own disk and touches no network. That is the most examined point in this chapter: commit saves, push uploads.

A branch is a movable name pointing at one commit. git branch login creates one, git switch login moves onto it, and git merge login, run from main, brings those commits into main. A remote is a copy of the repository on another machine. git remote add origin https://github.com/yourname/yourrepo.git names that copy origin; git push -u origin main uploads your commits; git pull downloads and merges other people's.

.gitignore is a plain text file of patterns Git must not track: node_modules/, .env, *.log. Secrets and generated files then stay out of history.

Browser DevTools: what the page really did

DevTools is built into every major browser; F12 or Ctrl+Shift+I opens it. It attaches to the page you are on and reports facts, not intentions.

PanelQuestion it answers
ElementsWhat is the DOM now, and which CSS rule wins?
ConsoleWhich JavaScript error or log message appeared?
NetworkWhich URL, method, status, size and time per request?
ApplicationWhich cookies and storage keys are stored?

Elements shows the live DOM, the tree the browser built from your HTML after JavaScript changed it. Editing a value in the Styles pane updates the page at once, which is useful for trying a colour before typing it into the CSS file.

Console lists your console.log output and every uncaught JavaScript error, with file and line. A red line here is the fastest explanation for a button that does nothing.

Network records every request with its URL, method (GET, POST), status code, transferred size and time. Tick Disable cache while testing. A row marked (from cache) shows 0 bytes transferred. A 304 response transfers only headers, and a 404 often carries a small error body; their transferred size is a few hundred bytes at most, small enough to count as 0 in exam arithmetic but not literally zero. So the total is not the page weight.

Application shows what the site stored on your machine: cookies, localStorage, sessionStorage and service workers.

Worked example

Question. A page loads index.html of 4 KB, app.css of 12 KB and app.js of 30 KB. app.css is already in the browser cache; the other two are downloaded. git status shows app.css modified and logo.svg untracked. The DevTools Console shows a 404 for /favicon.ico. Find (a) the bytes transferred, (b) the number of files to stage, and (c) whether git commit uploads the code.

  1. Transferred size counts only bytes that crossed the network. index.html is downloaded: 4 KB.
  2. app.css is served from cache, so it contributes 0 KB to transferred size even though the page uses it.
  3. app.js is downloaded: 30 KB.
  4. Total transferred = 4 KB + 30 KB = 34 KB. The 404 for favicon.ico transfers only headers and possibly a tiny error body, small enough to count as 0 KB in exam arithmetic, but not literally zero. It is still a failed request worth fixing.
  5. git status lists two changes: app.css is modified (tracked) and logo.svg is new (untracked). Both must be staged, so run git add app.css logo.svg.
  6. Files to stage = 2.
  7. git commit -m "..." writes a new commit into the local .git directory only. Nothing leaves the machine until git push origin main runs.
  8. So commit does not upload; push does.

Exam traps

  • git commit saves to the local repository only. It does not upload. Without git push the teammate sees nothing.
  • Transferred size in Network is not page weight. Files served from cache show 0 bytes; a 304 transfers only headers, and a 404 may carry a tiny error body, so count them as 0 in exam arithmetic but not as a literal measurement. The total is smaller than the sum of the file sizes.
  • Saving a file in the editor is not a commit. Ctrl+S writes the working tree; git add copies to staging; git commit records it. Three separate steps.
  • A 404 is a completed HTTP exchange: the server answered. It is not 'no response' and it is not a JavaScript syntax error, which would appear in Console as a different message.
  • .gitignore stops untracked files only. A file already committed stays tracked; you must run git rm --cached to untrack it.

Takeaways

  1. Every web page begins with a name-to-address lookup in DNS, then a connection, then one HTTP request and one response.
  2. DNS answers are cached for their TTL, which is why a changed record takes time to reach everyone.
  3. Splitting a system into client, application and data tiers lets each tier be scaled, tested and replaced on its own.
  4. A web server serves files and forwards dynamic work; an application server holds the business logic and talks to the database.
  5. HTTP is stateless, so state such as a login is carried by cookies or tokens, not by the server remembering you.
  6. HTTPS is ordinary HTTP inside a TLS tunnel, so the methods and status codes are unchanged but the bytes are encrypted.
  7. GET is safe and idempotent, PUT and DELETE are idempotent, POST is neither — this decides when a retry is harmless.
  8. MERN uses one language, JavaScript, from the browser to the server, which is why it is popular for teaching full stack work.
  9. The edit-run-inspect loop — VS Code, Git, browser console and network tab — is where most real debugging happens.

A numeric label, IPv4 or IPv6, that identifies a network interface so packets can reach it.
MERN
A JavaScript stack: MongoDB for data, Express for the server framework, React for the interface, Node.js as the runtime.
Method
The verb at the start of an HTTP request line stating the action, such as GET, POST, PUT or DELETE.
Middleware
Software between two tiers that provides common services such as authentication, logging or message queuing.
Packet
A small unit of data with a header holding source and destination addresses, forwarded independently across a network.
Persistent connection
Keeping one TCP connection open for many HTTP exchanges, saving the cost of repeated handshakes.
Recursive resolver
The DNS server your device asks first; it does the chasing through root, TLD and authoritative servers and returns the final answer.
Router
A device that forwards packets towards their destination network using routing tables.
Server
A program that listens for requests and returns responses or resources.
Stateless
A property of HTTP meaning each request is independent and no earlier request is remembered by the protocol.
Status code
A three-digit number in the response line telling the result, such as 200 OK, 404 Not Found or 500 Server Error.
Three-tier architecture
A design with a client tier, an application or server tier and a data tier, each independently deployable.
TLD
The top-level domain, the last label of a domain name such as .com, .net, .org or .in.
TLS
Transport Layer Security, the protocol that encrypts a connection after a certificate-based handshake.
TTL
The number of seconds a DNS answer may be cached by resolvers and browsers.
URL
The full address of a resource on the web, made of a scheme, a host, an optional port, a path, a query and a fragment.
WebRTC
Browser APIs and protocols for direct real-time audio, video and data transfer between peers.
WebSocket
A protocol that upgrades an HTTP connection into a persistent two-way channel for live data.
World Wide Web
The collection of linked resources, addressed by URLs and fetched over HTTP, that a browser displays.
