6.1 Node.js architecture, event loop and modules

Node.js lets you run JavaScript outside the browser, on a server, using one thread for JavaScript and a helper thread pool behind it. The idea exists because waiting is slow: reading a file or calling a database can take milliseconds that one thread cannot afford to waste. So Node hands every slow job to the operating system and picks up the result later through the event loop. Every Express API, chat server and streaming service in this unit stands on this one mechanism.

You need Unit 3's asynchronous JavaScript (callbacks, promises, async/await) and Unit 1's client-server and HTTP request/response picture; within this unit, 6.3 reuses the same file calls you see here.

V8 runs the code, libuv waits for the world

Node.js is a C++ program that embeds V8, the JavaScript engine from Chrome. V8 compiles your JavaScript into machine code and executes it. Node adds a second library, libuv, which supplies the event loop and a small thread pool.

Your JavaScript runs on one thread. A thread is the sequence of instructions the CPU is currently executing. Node keeps one call stack: the list of functions that are running right now. Only the function on top of the stack executes. When the running function calls another function, the new one is pushed on top. When it returns, it is popped and the function below resumes.

Slow work does not sit on that stack. For fs.readFile, dns.lookup (the usual lookup behind HTTP requests), some crypto calls and timers, Node passes the job to libuv or to the operating system, attaches your callback, and returns at once. The stack is free for the next request. dns.lookup uses the libuv pool; dns.resolve uses the operating system resolver.

When the job finishes, libuv puts the callback into a queue. The event loop checks that queue and pushes callbacks back onto the stack, but only when the stack is empty. That is the whole architecture: one stack, one queue, one loop.

The event loop: phases and microtasks

The event loop repeats a fixed order of phases. Each phase has its own queue of callbacks.

  1. Timers: run setTimeout and setInterval callbacks whose delay has expired.
  2. Pending callbacks: run deferred system callbacks, such as a failed TCP connection.
  3. Poll: wait for I/O and run its callbacks (a file read finished, socket data arrived).
  4. Check: run setImmediate callbacks.
  5. Close: run close handlers, such as socket.on('close').
  6. After the close phase, the loop starts again at timers.

Two queues cut in between the phases: the process.nextTick queue and the promise microtask queue. After every single callback, and before the loop moves to the next phase, Node empties both. NextTick callbacks run first, then promise microtasks; the process.nextTick queue is fully drained before the promise queue is touched. So a resolved promise's .then always runs before any timer, even a 0 ms timer.

A blocking call keeps the thread busy until it finishes. fs.readFileSync, crypto.pbkdf2Sync and a long for loop are blocking. While they run, no other callback can start, so every user of your server waits. One 200 ms synchronous read on a busy evening makes every request behind it 200 ms late.

To watch this live, run node --inspect app.js and open chrome://inspect in Chrome DevTools to set breakpoints on the running stack. Some syllabi call this the Node Inspector.

Modules: core, local and third-party

A module is one file with its own scope. Nothing in it is visible to other files unless the file exports it. Node has three kinds.

  • Core modules ship inside Node: fs, path, os, http, events. You load them by bare name, const fs = require('fs'), with nothing to install.
  • Local modules are your own files. In math.js write module.exports = { add, PI }; in app.js write const m = require('./math'). require returns whatever module.exports holds. Some syllabi call a local file an export module.
  • Third-party modules are packages installed into a node_modules folder, covered in 6.2.

require() resolves a string in a fixed order:

  1. If the string starts with ./, ../ or /, it is a file path: check for that file, then that file with .js, .json, .node.
  2. Otherwise the core module list is checked first, so 'fs' always gives the built-in.
  3. Otherwise node_modules folders are searched, starting beside the file and walking up to the disk root.
  4. The result is cached by resolved path, so a second require of the same file returns the cached exports and does not run the file again.

Modern Node also supports ES modules: write import { add } from './math.js' and export const PI = 3.14159. Set "type": "module" in package.json, or name the file .mjs, and require() stops being available in that file.

Exam traps

  • Writing that setTimeout(fn, 0) runs before Promise.then(). Microtasks always run before the loop enters the next phase, so the promise callback comes first.
  • Saying Node uses one thread for everything. Your JavaScript runs on one thread, but file, dns.lookup and crypto work runs on the libuv pool, 4 threads by default; dns.resolve uses the operating system resolver.
  • Confusing require('fs') with require('./fs'). The first is the built-in file system module; the second loads your own file named fs.js.
  • Forgetting the module cache: the second require of the same resolved path returns cached exports and does not re-run the file. A counter that never increases is usually cached.
  • Passing a call instead of a function: setTimeout(fn(), 0) calls fn immediately on the stack and passes its return value to the timer.

6.2 npm and package management

npm is two things at once: a public registry of JavaScript packages and the command-line tool that fetches them. Your project keeps a wish list in package.json, written as version ranges. The installer resolves those ranges against the registry, downloads code into node_modules, and records the exact versions it chose in package-lock.json. That split lets a team share one small manifest while every machine installs a repeatable set of files. You use npm in every Node project, in Express APIs, and in CI pipelines that must build the same app twice.

You need Chapter 6.1 for how require() searches node_modules, and Unit 3 for ES modules.

package.json is the project manifest

npm init -y writes a starting package.json with default answers. The file is JSON, so keys and string values need double quotes. It records what the project is and what it needs.

  • name and version identify the package. Version follows semantic versioning.
  • main names the entry file that require() loads when another file imports this package. An app often uses index.js or server.js.
  • scripts stores short commands you run with npm run.
  • dependencies lists packages the running app needs, such as Express.
  • devDependencies lists tools needed only for development or testing, such as nodemon.

Install a runtime package with npm install express. Add -D for a development tool: npm install -D nodemon. npm edits package.json and downloads code. A local install puts packages inside the project's node_modules folder. A global install with -g puts a command on your machine for all projects. Keep libraries local; use global only for command-line tools. Put start in scripts as node server.js, then run npm start. Other scripts run as npm run dev.

Semantic versioning and version ranges

Semantic versioning writes a version as MAJOR.MINOR.PATCH. MAJOR changes when old code may break. MINOR adds features without breaking old code. PATCH fixes bugs without changing behaviour. From 4.18.2 to 4.19.0 is a minor update; 4.18.2 to 4.18.3 is a patch; 4.18.2 to 5.0.0 is a major change.

A range lets npm choose a newer version that should still work. Two ranges appear in exams.

  • ^4.18.2 means at least 4.18.2 and below 5.0.0. The caret locks the major number.
  • ~1.2.3 means at least 1.2.3 and below 1.3.0. The tilde locks the minor number.
  • An exact version such as 4.18.2 allows only that version.

Write a dependency as express set to ^4.18.2 to accept future minor and patch releases. Use ~ when you want only patch releases. Use an exact version when even a minor update is risky. npm reads these ranges, asks the registry for matching versions, and chooses one set for the project.

Lock file, installs and scripts

package-lock.json records the exact version of every installed package, plus the versions of their dependencies. package.json says ^4.18.2; the lock file may say 4.18.2 today. Commit the lock file. Then every developer and every server installs the same tree.

  • node_modules is generated. Never edit it by hand. Usually do not commit it; it is large and can be rebuilt from the manifest and lock file.
  • npm install reads package.json, may update versions inside the allowed ranges, and writes or updates the lock file.
  • npm ci deletes node_modules, installs exactly the lock file, and fails if package.json and the lock file disagree. CI pipelines use it for repeatable builds. See Chapter 6.9.
  • npx runs a package command without a permanent global install, for example npx nodemon server.js.

Run your own scripts with npm run script-name. npm start and npm test are shortcuts for the start and test scripts. Some syllabi group npm with task runners such as Grunt and Gulp; those are front-end build tools covered with the front-end unit. For a project, you need the commands above, not the whole npm CLI.

Worked example

Question. A project has express set to ^4.18.2 and tool set to ~1.2.3. For Express, test 4.17.1, 4.18.2, 4.19.0 and 5.0.0. For the tool, test 1.2.9 and 1.3.0. How many versions are allowed for each range?

  2. Test 4.17.1: it is below 4.18.2, so reject it.
  3. Test 4.18.2: it equals the lower bound, so accept it.
  4. Test 4.19.0: it is above 4.18.2 and below 5.0.0, so accept it.
  5. Test 5.0.0: it equals the upper bound, which is excluded, so reject it.
  6. Write the tilde range ~1.2.3 as 1.2.3 ≤ version < 1.3.0.

Exam traps

  • Swapping ^ and ~: the caret locks the major number, the tilde locks the minor number.
  • Treating ^4.18.2 as allowing 5.0.0. The upper bound is excluded.
  • Deleting package-lock.json and expecting the same install on every machine.
  • Running npm install on a server when the lock file must be obeyed; that is a job for npm ci.
  • Editing node_modules by hand. It is generated, so the edit is lost on the next install.

6.3 File system, streams and event emitter

Three Node tools sit between your code and the disk. The fs module opens, reads, writes and deletes files. A stream carries the same bytes in small chunks, so a 1 GB file never has to sit in RAM. EventEmitter is the base pattern both rely on: an object emits a named event, and the functions listening for that name run. You meet all three in a log-writing server, a file-upload handler, a backup script, or anywhere a program moves data bigger than its memory.

You need callbacks, the event loop and microtasks from 6.1, plus arrow functions and promises from Unit 3.

The fs module: three flavours of the same call

Every file operation in Node lives in fs. The same job is offered in three shapes, and you pick one per call site.

  • Callback: fs.readFile(path, cb). The last argument is (err, data) and it runs later, after the disk answers.
  • Synchronous: the name ends in Sync, as in fs.readFileSync(path, 'utf8'). It returns the value directly, throws on failure, and stops the single thread until the disk is done.
  • Promises: require('fs/promises'), or require('fs').promises, gives the same functions returning promises, so const text = await fs.readFile(p, 'utf8') works.

Join paths with path.join('data','logs','app.txt'). It picks the right separator for the operating system and collapses duplicate slashes. String concatenation with '/' breaks on Windows and happily produces data//logs.

Streams: move the file in chunks

A stream pushes data through in pieces instead of one big value. There are four kinds.

  • Readable: a source, such as fs.createReadStream.
  • Writable: a sink, such as fs.createWriteStream.
  • Duplex: both at once, such as a TCP socket.
  • Transform: a duplex that changes the bytes, such as gzip.

fs.createReadStream('big.mp4', {highWaterMark: 64 * 1024}) opens the file and emits a 'data' event per chunk. highWaterMark is the chunk size in bytes; the default is 64 KB = 65536 bytes.

read.pipe(write) wires the two together: each chunk is written to the destination, and the end of the source closes the destination. pipe returns the destination, so calls chain.

Backpressure makes this safe. When the write stream's internal buffer is full, write() returns false and pipe pauses the read stream until the writer emits 'drain'. A fast disk never floods a slow disk or a slow network; the reader simply waits.

pipe does not forward errors. Attach handlers yourself, or use stream.pipeline(read, write, cb), which destroys both sides and calls back once with the error.

EventEmitter: on, emit, once

require('events') gives the EventEmitter class. Streams, http servers and sockets are all EventEmitters underneath.

emitter.on('name', fn) registers a listener. emitter.emit('name', arg) calls every listener for that name at once, in registration order, passing arg. once('name', fn) runs the listener a single time and then removes it.

To build your own, extend the class. class Job extends EventEmitter {}, then const j = new Job(); j.on('done', n => console.log(n)); j.emit('done', 42); prints 42.

'error' is special. If you emit('error', err) and nobody is listening, Node throws err as an uncaught exception and the process exits. A stream that hits a disk failure emits 'error'; with no handler, your server dies.

'close' is not 'error'. It only means the file handle was released, and it can arrive after a clean end or after a failure. Never treat 'close' as proof of success.

Worked example

Question. A Node script copies a 1 GB video file to a backup disk. (a) How much RAM does fs.readFile need for this copy? (b) With createReadStream at highWaterMark: 64 * 1024, how many chunks are read and how much memory is live per step? (c) The backup disk fills up halfway. What happens if no 'error' listener is attached?

  1. 1 GB = 1024 MB, the binary unit that stat and file sizes use.
  2. readFile must hold the whole file before the write starts, so memory ≈ 1024 MB.
  3. Convert to kilobytes: 1024 MB × 1024 KB/MB = 1,048,576 KB.
  4. Chunks = 1,048,576 KB ÷ 64 KB = 16,384 chunks.
  5. Memory live per step ≈ 64 KB = 0.0625 MB. Check the ratio: 1024 MB ÷ 0.0625 MB = 16,384, the same number of chunks.
  6. (c) The write stream emits 'error'. With zero listeners on that event, Node throws it as an uncaught exception and the process exits, leaving a half-written copy.

Answer. readFile needs about 1024 MB of RAM; the stream reads 16,384 chunks of 64 KB and keeps about 64 KB live at a time; a missing 'error' listener ends the process.

Exam traps

  • readFile is asynchronous, so it does not block the event loop. Its problem is memory: the whole file is buffered. readFileSync is the one that blocks.
  • pipe() does not carry errors. If the destination disk fails, only the write stream's 'error' reports it. Listen on it, or use stream.pipeline.
  • 'error' is not 'close'. 'close' only means the handle was released, and an unhandled 'error' throws and kills the process.
  • Missing encoding. readFile without 'utf8' returns a Buffer, so logging text shows hexadecimal bytes.
  • on() when you meant once(). A completion handler registered with on() fires again the next time that same emitter emits the event.

6.4 Express.js: routing, middleware and static files

Express is a small package that wraps Node's built-in HTTP server. It lets you define routes and middleware as ordinary JavaScript functions. Every request walks down an ordered chain of functions until one function sends a response. This gives clean URL matching, body parsing, static file serving and error handling without writing the raw server code by hand. Express is used for REST APIs, server-rendered pages and the back end of full-stack apps.

You need: 6.1 for Node's http server and callbacks, and Unit 1 for HTTP methods, URLs and status codes.

The app and the middleware chain

express is a package that wraps Node's http server. You create an application object with const app = express() and start it with app.listen(3000). Port 3000 is a number, not a string. Every incoming request enters a list of functions called middleware. Each function receives (req, res, next): req is the request, res is the response, and next is a function that passes control to the following middleware. A function that sends a response ends the chain for that request.

Middleware runs in registration order. A logger can print the method and URL, then call next(). A body parser can read the request body, then call next(). A route handler matches a method and path, reads inputs, and calls res.send or res.json. If no function sends a response, the client waits until the server times out.

Express is one of several Node.js frameworks. Others include Fastify, Koa and NestJS. Express is the one exams use because its routing and middleware are small enough to trace by hand.

Routes, parameters and query strings

Routes map an HTTP method and a URL path to a handler. The methods are app.get, app.post, app.put, app.patch and app.delete. The handler signature is (req, res) => { ... }. A path can contain a named parameter: app.get('/users/:id', handler). A request for /users/42 gives req.params.id equal to the string '42'. Parameters are always strings; convert with Number(req.params.id) before arithmetic.

Query strings come after ? and are read from req.query. For /users/42?lang=en, req.query.lang is 'en'. A repeated key can become an array. Query values are also strings.

Response helpers shorten common work. res.send('text') sends text or a buffer. res.json(obj) sets the JSON content type and sends JSON. res.status(404) sets the status code and returns res, so res.status(404).json({ error: 'not found' }) works. res.redirect('/login') sends a 302 redirect by default.

Middleware, routers and static files

app.use(fn) registers middleware for every request, or for a mount path when written as app.use('/api', fn). Order matters. If express.json() is registered above a route, req.body is filled before the handler runs. If it is registered below the route, req.body is undefined inside the handler.

Body parsers: express.json() reads JSON request bodies; express.urlencoded({ extended: true }) reads HTML form bodies. The flag extended: true allows nested objects. Both parsers call next() after parsing.

express.Router() makes a mini-app. You attach routes to the router, then mount it with app.use('/api', router). A router route /users mounted at /api answers /api/users.

Static files are served with app.use(express.static('public')). A request for /logo.png returns public/logo.png if it exists. Put static middleware above routes only when you want files to win; otherwise below.

Error middleware takes four arguments: (err, req, res, next). Express identifies it by that arity. A three-argument function is ordinary middleware and is never called with an error. Database calls inside handlers are covered in 6.6.

6.5 RESTful APIs: HTTP methods, JSON and CRUD

REST is a way to design a web API around things, not actions. A book, a user and an order are resources. Each resource gets a URL made of plural nouns, and the HTTP method says what to do with it. POST /books creates a book, GET /books/7 reads book 7, and JSON carries the data in both directions. Browsers, mobile apps and React pages all call such APIs. The style exists because one small set of methods and status codes lets any client talk to any server without a private vocabulary.

You need: Express routing and handlers from 6.4, and the HTTP methods and status codes from Unit 1.

Resources, URLs and HTTP methods

A resource is a named thing: a book, a customer, an order. A collection is a resource that holds many items. /books is the collection; /books/7 is one item inside it. Use plural nouns and no verbs. /getBooks is wrong because GET already says read; /books?author=gupta is right for filtering.

Five methods cover CRUD. CRUD means Create, Read, Update, Delete.

MethodURLActionBody

The id belongs in the path. The body holds the data, not the identity. POST /books returns the new item and a Location header. A header is a name-value line in a request or response. PUT replaces the whole item; a field you leave out is cleared or set to its default. PATCH changes only the fields you send. A common exam mistake is using PUT for a partial update.

Safe, idempotent and status codes

A method is safe if the client is not asking the server to change any resource. GET is safe, even though the server may still write a log line. A method is idempotent if sending the same request twice leaves the same final state as sending it once. GET, PUT and DELETE are idempotent. PUT and DELETE are not safe because they change state. POST is neither: two POST /books calls create two books, with ids 7 and 8. PUT /books/7 twice still leaves one book 7. DELETE /books/7 twice leaves it deleted; the second call may return 404, but the state is the same. PATCH is not safe, and it is not guaranteed idempotent, because the patch document may describe a change relative to the current value (for example 'increment stock by 1').

Status codes are three-digit numbers that summarise the result.

JSON, collections and stateless requests

JSON is a text format for objects and arrays. Content-Type: application/json tells the server that the request body is JSON. Accept: application/json asks the server for a JSON response. Express needs the express.json() middleware to read JSON bodies, then res.json() sends JSON back. See 6.4.

GET /books returns an array; GET /books/7 returns one object. Query strings, the part after ?, filter and page: /books?author=gupta&page=2&limit=10. State limit and page in the API documentation. Version the path: /api/v1/books. A new incompatible shape goes to /api/v2.

REST is stateless: each request carries everything needed, such as the token. The server does not remember the previous request. This lets any server in a pool answer any request. Database work is in 6.6; protecting routes is in 6.8.

6.6 MySQL database connectivity and queries

A Node process is not a database. When an Express route needs student rows, Node opens a TCP connection to MySQL, sends SQL, and reads back rows. The mysql2 package does this. It keeps a pool of ready connections so a busy server does not reconnect for every request, and it binds values with ? stand-ins so user input can never become SQL. Rows arrive as plain JavaScript objects, ready for res.json(). This chapter covers connecting, querying, reading results and transactions.

You need: Unit 4 (SQL and CREATE TABLE) and 6.5 for the Express CRUD routes that call this code.

Install mysql2 and choose a connection or a pool

MySQL is a separate program listening on TCP port 3306. Node needs a driver to speak to it. Install it with npm install mysql2 — the package is mysql2, not mysql.

mysql.createConnection(config) opens one connection. It is fine for a script that runs once. A web server receives many requests at once; with one connection every query waits behind the one before, and a dropped socket breaks every request.

mysql.createPool(config) holds a set of open connections — 10 by default — and lends one to each query. Twenty simultaneous queries use ten connections and the other ten wait briefly. This is why a server uses a pool.

The config object holds host, user, password and database. Read them from process.env.DB_HOST and friends; a password typed into app.js reaches Git. Create the pool once at startup, not inside a route.

require('mysql2') gives callbacks: db.query(sql, params, (err, rows) => {}). require('mysql2/promise') gives a promise, so const [rows] = await pool.query(sql, params) works in an async handler. Use the promise form; it reads like the Express code in 6.5.

stand-ins and the shape of the result

Never build SQL with +: 'SELECT * FROM students WHERE id = ' + id. If id arrives as 1 OR 1=1, every row is returned. If it arrives as 1; DROP TABLE students, the table is gone. This is SQL injection.

Use a stand-in: pool.query('SELECT * FROM students WHERE id = ?', [id]). The ? marks a value. mysql2 sends the statement and the values separately; MySQL parses the statement first and then fills each value as data, never as SQL. Quotes and escaping are handled for you.

stand-ins are positional: the first ? takes params[0], the second takes params[1]. Pass an array even for a single value.

A SELECT resolves to [rows, fields]. rows is an array of plain objects keyed by column name: [{ id: 11, name: 'Asha', marks: 85 }]. Send it with res.json(rows).

INSERT, UPDATE and DELETE resolve to a result object. affectedRows is the number of rows the statement matched — for INSERT, rows added; for DELETE, rows removed. changedRows is the number of UPDATE rows whose value really changed. insertId is the first AUTO_INCREMENT id generated by an INSERT.

CRUD statements and releases

  • INSERT: INSERT INTO students (name, marks) VALUES (?, ?) with ['Asha', 85]. For many rows in one round trip use VALUES ? with [['Asha', 85], ['Bala', 72]].
  • SELECT: SELECT name FROM students WHERE marks >= ? with [80].
  • UPDATE: UPDATE students SET marks = ? WHERE id = ? with [90, 11]. The WHERE is not optional; without it every row changes.
  • DELETE: DELETE FROM students WHERE id = ? with [11].

pool.query() borrows a connection, runs the statement and returns the connection, even when the query fails. If you need several statements on one connection, call const conn = await pool.getConnection() and put conn.release() in a finally block. A transaction is three calls: await conn.beginTransaction(), the statements, then await conn.commit(); if anything throws, await conn.rollback().

On shutdown call await pool.end() once, so open sockets close and Node exits. Never call it inside a request handler.

6.7 MongoDB and NoSQL: documents, collections, queries

MongoDB is a NoSQL database: JSON-like documents inside collections, with no fixed schema. You give it a filter document, and it returns matching documents. It suits data whose shape changes, such as catalogs, profiles, chat and logs. A Node back end uses the official driver.

You need JSON objects and arrays from Unit 3, and the CRUD routes of 6.5. The routes stay the same; only storage changes.

NoSQL families and the MongoDB hierarchy

NoSQL means not only SQL. The common families are listed below.

  • Document store — MongoDB. The unit is a JSON-like document.
  • Key-value store — Redis. The unit is a key mapped to a value.
  • Column store — Cassandra. Rows have many sparse, wide columns.
  • Graph store — Neo4j. The unit is a node and its edges.

A server is one mongod process, default port 27017. Inside it sit databases, such as shop. Inside a database sit collections, such as books. Inside a collection sit documents. A collection is roughly a SQL table; a document is roughly a row.

A document is a set of field-value pairs, written like a JSON object. It is stored as BSON, short for Binary JSON. BSON adds dates, integers, binary data and ObjectId.

Every document has an _id field. It is unique in its collection and immutable. If you do not supply one, the driver creates an ObjectId. An ObjectId is 12 bytes: a timestamp, a random value and a counter, so it sorts roughly by creation time.

There is no fixed schema. Only _id is compulsory. A catalog can hold one book with an isbn field and another without it.

CRUD with the official driver

Install the driver with npm i mongodb, connect with a URL, then pick a database and a collection. The calls that talk to the server — connect, insertOne, insertMany, find, updateOne, deleteOne, countDocuments — return promises, so you await them inside an async function, as in 6.1. Picking the database and collection is synchronous.

const { MongoClient } = require('mongodb');
const client = new MongoClient('mongodb://127.0.0.1:27017');
await client.connect();
const books = client.db('shop').collection('books');

await books.insertOne({ title: 'MongoDB Basics', price: 450 });
const res = await books.insertMany([
  { title: 'Express Guide', price: 300 },
  { title: 'Node in Action', price: 600 }
]);
res.insertedCount; // 2

const cursor = books.find({ price: { $gte: 400 } }, { title: 1, _id: 0 })
  .sort({ price: -1 }).limit(5);
const docs = await cursor.toArray();

for await (const doc of books.find({ price: { $lt: 400 } })) {}

await books.updateOne({ title: 'Express Guide' }, { $set: { price: 350 } });
await books.updateOne({ title: 'Express Guide' }, { $inc: { price: 50 } });
await books.deleteOne({ title: 'MongoDB Basics' });
const n = await books.countDocuments({ price: { $gte: 400 } });

insertOne returns insertedId. insertMany takes an array and returns insertedCount.

find(filter, projection) returns a cursor, not an array. A cursor fetches documents in batches. Use await cursor.toArray() to load everything, or for await (const doc of cursor) to process one at a time. findOne(filter) returns one document, or null.

The filter is a document. A plain value means equality. Operators include $gt, $gte, $lt, $lte, $ne and $in. { marks: { $gte: 80 } } keeps marks 80 or more. Two fields are joined by AND; $or gives alternatives.

A projection uses 1 to include and 0 to exclude; you cannot mix them except for _id. { name: 1, _id: 0 } returns names only. Chain .sort({ marks: -1 }) and .limit(2). updateOne returns matchedCount (documents the filter matched) and modifiedCount (documents actually changed). deleteOne returns deletedCount. deleteMany returns deletedCount too. The route in 6.4 can report these as JSON.

Update operators, shapes and choosing MongoDB

The second argument of updateOne is usually an update document with operators. $set changes fields, $inc adds to a number, $unset removes a field, $push appends to an array.

A plain document with no operator means replacement. updateOne({ name: 'Asha' }, { marks: 88 }) discards the other fields: only _id and marks remain. Write { $set: { marks: 88 } } to change one field.

Embed when the child is small, always read with the parent, and bounded — an order holding line items in an array. Reference when the child is shared or large — store authorId in the book and keep authors separately. A reference costs a second query. MongoDB has no SQL join, only the $lookup stage of the aggregation pipeline.

Mongoose adds schemas and models on top of the driver: defaults, validation, type casting. The database itself still has no schema; Mongoose enforces rules only in your Node process.

Pick MySQL when columns are fixed, answers need joins across many tables, and money movement must be transactional across many tables and the team wants transactions on a single standalone server. That side is in 6.6. MongoDB also offers multi-document transactions on replica sets, but they cost more round trips and are used sparingly. Pick MongoDB when documents change shape and most reads fetch one document with its children.

Analyze A team must move money between two accounts in one all-or-nothing step, and later report with joins over six tables. Should they use MongoDB or MySQL, and why? 5 marks

MySQL. It supports strict multi-statement transactions on one standalone server, so debit and credit both apply or neither does. It also joins six tables in one query. MongoDB suits evolving document shapes and single-document reads, not this case.

Beyond the syllabus

Not for the exam. The aggregation pipeline replaces WHERE, GROUP BY and JOIN with $match, $group and $lookup. Atlas, change streams and Mongoose middleware are common next stops. Search for MongoDB aggregation pipeline, compound index and replica set.

6.8 Authentication and web security: sessions, JWT, XSS

Authentication answers one question: who is this user? A session keeps the answer on the server and gives the browser only a random session id in a cookie. A JWT keeps the answer in a signed token that the client sends back. Passwords are stored as bcrypt hashes, never as plain text. XSS is the opposite problem: attacker script runs inside your page and acts as the user. Every login on IRCTC, a UPI app or a college portal depends on these ideas.

You need: Express middleware and the request chain (6.4); user records from MySQL or MongoDB (6.6, 6.7); and HTTP headers (Unit 1, HTTP and HTTPS).

Passwords and server-side sessions

Never store a password as plain text. Store a slow hash made by bcrypt. bcrypt adds a random salt and repeats the work for a cost factor, usually 10 to 12 rounds. The salt is stored inside the hash string, so no separate salt column is needed. On login, fetch the stored hash and call bcrypt.compare(enteredPassword, storedHash). It returns true or false. The cost makes one check cheap for the server and millions of guesses expensive for an attacker.

A session keeps the login proof on the server. express-session creates a session object, gives it a random id, and sends that id in a cookie. Session data lives in a store: memory for a demo, a database or Redis for production. Each later request carries the cookie; middleware finds the session and sets req.session.user. Logout calls req.session.destroy(), so the same cookie stops working.

  1. Look up the user row by email or username.
  2. Compare the entered password with the stored bcrypt hash.
  3. Create the session and set the session cookie.
  4. On each later request, load the session from the cookie.

Cookie flags matter. HttpOnly stops JavaScript from reading the cookie, so an XSS bug cannot steal the session id. Secure sends the cookie only over HTTPS. SameSite=Lax or Strict stops another site from making the browser send the cookie on a cross-site request, which reduces CSRF. Use sessions for a browser app on one domain: the server can revoke access at once, and the cookie is small. A session id is a random key to server state, so use at least 32 random bytes and rotate the id after login.

JWT: three parts, signed not encrypted

A JWT has three parts separated by dots: header.payload.signature. The header and payload are base64url-encoded JSON. Base64url is encoding, not encryption: anyone who copies the token can decode and read the payload. The signature is computed with a secret key known only to the server. The server checks the signature and the exp claim on every request; if either fails, it returns 401 Unauthorized.

token = base64url(header) + '.' + base64url(payload) + '.' + base64url(HMAC-SHA256(secret, base64url(header) + '.' + base64url(payload)))

header names the signing algorithm; payload carries claims such as sub, iat and exp; secret is the server key; HMAC-SHA256 is the signing function; base64url is URL-safe base64 encoding, not encryption.

Standard claims are sub (user id), iat (issued at, seconds since 1970-01-01T00:00:00Z) and exp (expiry, same clock). The client sends the token as Authorization: Bearer <token>. Middleware verifies it and sets req.user. Services can verify a token without a shared session store, so JWT suits mobile apps and several APIs. Logout is weaker: the client drops the token, but a copied token works until exp. A server-side blacklist of token ids (jti) or short-lived tokens with refresh tokens limits that. Do not store a JWT in localStorage: any XSS script can read it. Keep it in memory or in an HttpOnly cookie.

Choose sessions for a browser app on one domain; choose JWT for mobile clients and multiple services. Neither replaces HTTPS: a token or cookie on plain HTTP can be copied in transit.

XSS and the wider security net

XSS (cross-site scripting) happens when attacker-controlled script runs inside your page origin. The script can read the DOM, call your APIs as the user, and steal anything JavaScript can reach. There are three common types. Stored XSS saves the script in your database, for example in a comment, and serves it to every reader. Reflected XSS puts the script in the current request and echoes it back in the response. DOM XSS happens when your own client code writes user text into the page, such as element.innerHTML = userText.

Defend on output. Escape text for the context where it appears, or use textContent instead of innerHTML. Never build HTML by joining user strings. Add a Content-Security-Policy header, for example default-src 'self', so injected inline script is blocked. Validate input on the server as well; client checks can be skipped. The helmet middleware sets several security headers, but it is not a substitute for escaping.

Other attacks are easy to mix up. SQL injection changes a query through unescaped input; use ? stand-ins (see 6.6). CSRF tricks the browser into sending an authenticated request to your site; SameSite cookies and a CSRF token reduce it. HTTPS encrypts the whole exchange, and Secure cookies refuse to travel on HTTP. XSS runs code in your origin; CSRF sends a request from another origin with your cookie.

Worked example

Question. A JWT is issued with iat = 1700000000 and exp = 1700003600. (a) Find its lifetime in seconds and in minutes. (b) A request arrives at 1700004200. How many seconds after expiry is it, and what should the server return?

  1. Lifetime = exp − iat = 1700003600 − 1700000000 = 3600 s.
  2. In minutes: 3600 ÷ 60 = 60 min.
  3. The token is valid only while now < exp. At now = 1700004200, now − exp = 1700004200 − 1700003600 = 600 s.
  4. 600 s = 10 min past expiry, so the server must reject the token with 401 Unauthorized.

Answer. Lifetime 3600 s (60 min); the request is 600 s after expiry, so the server returns 401 Unauthorized.

Exam traps

  • A JWT is signed, not encrypted; base64url decodes to readable JSON, so never put secrets in the payload.
  • Storing a JWT in localStorage exposes it to any XSS script; keep it in memory or an HttpOnly cookie.
  • A server must check both the signature and exp; decoding the payload alone proves nothing.
  • XSS injects script into your page origin; CSRF makes the browser send a request from another site with your cookie.
  • bcrypt cost 10-12 is not the salt; the salt is inside the hash and is not secret.

6.9 Deployment: Docker, cloud hosting and CI/CD

A Docker image packs your Express app, Node runtime and exact dependencies into one file. A container runs that image the same way on your laptop and on a cloud server. CI/CD turns a git push into install, test, build, push and deploy steps without a human copying files. This chapter shows the Dockerfile order that keeps builds fast, how secrets arrive as environment variables, the main cloud hosting choices, and a pipeline you can trace from push to a container listening on port 3000.

You need: 6.4 for the Express app being shipped and 6.2 for package.json, npm ci and scripts.

Image, container and Dockerfile order

An image is a frozen file system plus a start command. A container is that image running as a process. The image is the recipe; the container is the cooked dish. One image can start many containers, like one class can create many objects. The same image behaves the same on a laptop and a cloud server because it carries Node and the exact packages from package-lock.json.

A Dockerfile lists instructions in order. Each instruction creates a layer, and Docker caches a layer until its inputs change. Read this file from top to bottom:

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

FROM picks node:20-alpine as the base. WORKDIR /app makes /app the working directory. The first COPY brings only package.json and package-lock.json, so RUN npm ci is cached until those two files change. The second COPY brings your source code; editing server.js does not reinstall packages. EXPOSE 3000 documents the intended port. CMD is the foreground process that keeps the container alive. A .dockerignore file keeps node_modules, .git, .env and logs out of the image.

docker build -t shop . builds an image named shop from the current directory. docker run -p 8080:3000 shop maps host port 8080 to container port 3000. Host port comes first. Open http://localhost:8080; the app still listens on 3000 inside.

Configuration, Compose and hosting

Passwords and database URLs are configuration, not code. Put them in environment variables at run time: docker run -e DATABASE_URL=... shop, or an env_file in Compose. Never write them in the Dockerfile or an ENV line; layers keep old values and anyone who pulls the image can read them.

Docker Compose describes several services in one YAML file. A typical file has app and db services: app builds from ., starts after db, and gets DATABASE_URL pointing at the service name db. Compose starts db before app, but does not wait for the database to be ready; add a health check with a depends_on condition, or make the app retry the connection. db uses a named volume so data survives a container restart. Compose creates one private network, so app reaches db by name, not by localhost.

  • IaaS: a VPS with root access; you install Docker and manage updates.
  • PaaS: a platform builds from your Git push and runs the container for you.
  • Managed database: the provider runs MySQL or MongoDB with backups and failover.
  • SaaS: ready software you use, not a place to deploy your code.

In production a reverse proxy such as Nginx listens on ports 80 and 443 and forwards requests to 127.0.0.1:3000. Keep port 3000 off the public internet. Logs go to three places: docker logs for app stdout/stderr, Nginx access.log and error.log for requests, and your cloud log viewer if the platform collects them.

The CI/CD pipeline

CI/CD is one automatic path from commit to live container. A CI runner starts on every push.

  1. Checkout the commit and run npm ci; it installs exactly package-lock.json, the same as local.
  2. Run npm test. A failing test stops the pipeline before any image is built.
  3. Build the image and tag it with the commit SHA: docker build -t registry.example.com/shop:${SHA} ..
  4. Push that tag to a registry.
  5. On the deploy host, pull the tag, inject environment variables, stop the old container, start the new one on port 3000, and check /health.
  6. Keep the previous tag. If the health check fails, redeploy the previous tag: that is the rollback.

A tag like latest is not a version; the commit SHA is. A registry stores images (public or private), not source commits like a Git repository. One run takes install 40 s, test 25 s, build 30 s and deploy 15 s. A manual copy-and-restart can take 20 min.

Exam traps

  • Writing COPY . . before RUN npm ci throws away the layer cache on every code change and reinstalls everything.
  • Reversing the port mapping: -p 3000:8080 is wrong when the app listens on 3000 and you want host 8080; use -p 8080:3000.
  • Putting passwords in the Dockerfile or an ENV line; they stay inside image layers even if a later line deletes them.
  • Thinking EXPOSE publishes the port. EXPOSE only documents it; docker run -p or Compose ports is needed.
  • Running a daemon in CMD such as a background process; when PID 1 exits, the container stops.

Takeaways

  1. Node is fast because a single JavaScript thread never waits: files, network and timers go to the operating system and come back as callbacks.
  2. package.json holds the version ranges you asked for; package-lock.json holds the exact versions you actually got, and only the lockfile makes installs repeatable.
  3. Streams beat readFile for large data because chunks flow through with flat memory, and pipe() alone will not report a failure of the source.
  4. In Express the request walks a fixed, ordered chain of middleware until one function sends a response or calls next(err).
  5. REST is a naming discipline: URLs are nouns, HTTP methods are verbs, status codes are the result, and JSON is the body format.
  6. SQL safety comes from ? stand-ins that bind values separately; string concatenation is what turns user text into executable code.
  7. MongoDB swaps tables for collections and rows for schemaless documents, and a query is just a filter document each candidate must match.
  8. Sessions keep the proof on the server behind a cookie id; a JWT keeps the proof in a signed token on the client and cannot be revoked easily.
  9. XSS defeats any token stored in localStorage; HttpOnly cookies keep the credential out of reach of injected script.
  10. Docker fixes the environment, CI/CD fixes the human step, and together they make a deploy the same repeatable command every time.

Glossary

Backpressure
A stream telling its writer to slow down because the internal buffer is full, so memory does not grow without limit.
bcrypt
A deliberately slow password hashing function that adds a random salt, so identical passwords give different hashes.
Blocking call
Code that keeps the JavaScript thread busy, so no other callback can run until it returns.
BSON
Binary JSON, the storage format MongoDB uses; ObjectId is its 12-byte identifier type for documents.
Core modules
Modules shipped inside Node itself, such as fs, http and path, loaded by bare name with require('fs').
CORS
Cross-origin resource sharing: response headers that tell the browser which other origins may call your API.
CSRF
Cross-site request forgery: another site makes the browser send a request that carries the victim's cookie automatically.
devDependencies
Packages needed only for testing, linting or building, which a production install can skip.
Dockerfile
The recipe file listing base image, copied files, dependency install and start command used to build an image.
Environment variable
Configuration passed to a process at run time, such as PORT or DATABASE_URL, so the same image works in every environment.
Error-handling middleware
A four-argument Express function (err, req, res, next) that runs only when some earlier middleware called next(err).
HttpOnly cookie
A cookie the browser sends with requests but hides from document.cookie, so injected script cannot read the session id.
Idempotent
A request that can be repeated with the same server state resulting, which is true of GET, PUT and DELETE but not POST.
libuv
The C library that gives Node its event loop, worker thread pool and cross-platform async file and network calls.
Local modules
Your own project files, loaded by relative path such as require('./utils') and exported with module.exports.
Mongoose
An ODM library that adds schemas, casting and validation on top of the plain MongoDB driver.
next()
The third argument of an Express middleware; calling it hands the request to the next matching function in the chain.
node_modules
The folder where npm installs packages; bare-name require() searches it upward from the current file.
Non-blocking I/O
An operation Node hands to the operating system and continues past; the result arrives later through a callback or promise.
pipeline()
A stream helper that connects streams in order and destroys all of them, forwarding errors, when any one fails.
req.body
The parsed request body; it stays undefined unless express.json() or a similar parser middleware ran first.
Route parameter
A named slot such as :id in a path pattern, readable inside the handler as req.params.id.
setImmediate
Schedules a callback to run in the check phase, after the current poll phase finishes.
Thread pool
libuv's small set of worker threads, four by default, that perform file system, DNS and crypto work away from the main thread.
