4.1 Syntax-directed definitions: synthesized and inherited attributes

A grammar says which strings are legal. It says nothing about what they mean. A syntax-directed definition adds the meaning: each grammar symbol carries attributes, and each production carries semantic rules that compute them. A value built up from a node's children is a synthesized attribute; a value pushed down from the parent or across from a sibling is an inherited attribute. Compilers use these rules to compute values, types, addresses and code while parsing. This chapter separates the two kinds of attribute, fixes the order in which they may be evaluated, and shows the restricted S-attributed and L-attributed forms that real parsers accept.

You need: context-free grammars, derivations and parse trees from Unit 2, so that a node in a tree and a production instance are the same thing to you.

Attributes and semantic rules

A grammar symbol can carry attributes. An attribute is a named property of that symbol at one node of the parse tree: a number, a type, an address, or a piece of code. A syntax-directed definition (SDD) pairs every production with semantic rules that compute attributes. A rule has the form b = f(c1, c2, …): b is an attribute of the production's head, and each c is an attribute of a symbol in that same production. Some syllabi call an SDD an attribute grammar and call the rules semantic actions.

ProductionSemantic rule
E → E1 + TE.val = E1.val + T.val
E → TE.val = T.val
T → T1 * FT.val = T1.val × F.val
T → FT.val = F.val
F → digitF.val = digit.lexval

Subscripts only separate two instances of one symbol. In E → E1 + T, the symbols E and E1 are both the nonterminal E, sitting at the parent and at the left child.

An attribute is synthesized when the rule at node N reads only attributes of N and of N's children. Values flow upward: leaves first, root last. F.val = digit.lexval is synthesized, and digit.lexval is not computed by any rule — the lexical analyzer supplies it with the token. In E → E1 + T with E.val = E1.val + T.val, both children must be finished before the parent can be computed.

Inherited attributes and evaluation order

An attribute is inherited when the rule at node N reads attributes of N's parent or of N's siblings: values flow downward or sideways. Reading a decimal number needs each digit's place value. The place value is 10 raised to the number of digits to the right, which is the length of the remaining suffix. So we compute the suffix length as a synthesized attribute:

  • N → D: N.val = D.val
  • D → digit D1: D.len = D1.len + 1, D.val = digit.lexval × 10D1.len + D1.val
  • D → ε: D.len = 0, D.val = 0

Read the string 3 4 5. The rightmost digit 5 sits above the empty suffix, so D1.len = 0 and its value is 5 × 10⁰ + 0 = 5. Moving left, digit 4 has one digit to its right, so D1.len = 1 and its value is 4 × 10¹ + 5 = 45. Digit 3 has two digits to its right, so D1.len = 2 and its value is 3 × 10² + 45 = 345. The upward pass carries both len and val.

Which rule runs first? Draw a dependency graph whose nodes are the attribute instances in the parse tree, and add an edge c → b whenever the rule that computes b reads c. Any topological order of that graph is a legal evaluation order, and most definitions allow several. A cycle means the definition is circular, no order exists, and the rules must be rewritten.

S-attributed and L-attributed definitions

Two restricted forms matter, because a parser can evaluate them in one pass without holding the whole tree.

A definition is S-attributed when every attribute in it is synthesized. Evaluation is bottom-up, and it matches LR parsing exactly: when the parser reduces by A → X Y Z the three children are already on the stack, so A's attributes can be computed at once. Attribute values sit on the parser's value stack beside the grammar symbols. Most YACC actions are of this kind.

A definition is L-attributed when attributes may be synthesized or inherited, and every inherited attribute of a right-side symbol depends only on the parent and on symbols to its left. In A → B C D, C may read attributes of A and of B, never of D. One left-to-right depth-first walk then suffices: enter A, pass values down to B, finish B, pass to C, and so on. Recursive-descent compilers use this form, placing actions in the right side where their inputs are ready. Every S-attributed definition is L-attributed; the converse fails.

The number grammar above is S-attributed: both len and val are synthesized. Definitions that build syntax trees or emit three-address code are usually written L-attributed because a place to put the result must be passed down.

Worked example

Question. The grammar is E → E + T | T, T → T * F | F, F → digit, with the rules E.val = E1.val + T.val, E.val = T.val, T.val = T1.val × F.val, T.val = F.val, F.val = digit.lexval. Give every attribute value needed to evaluate 3 * 4 + 5, in a legal evaluation order, and state the final value.

  1. Parse 3 * 4 + 5: the rule E → E + T splits it into the left expression 3 * 4 and the right term 5. The left part uses E → T → T * F; the right part uses T → F → digit 5.
  2. Leaf F → digit 3: F.val = digit.lexval = 3.
  3. T → F above it: T.val = F.val = 3.
  4. Leaf F → digit 4: F.val = digit.lexval = 4.
  5. Multiplication node T → T * F: T.val = T1.val × F.val = 3 × 4 = 12.
  6. E → T on the left: E.val = T.val = 12.
  7. Right side: F → digit 5 gives F.val = 5, then T → F gives T.val = 5.
  8. Root E → E + T: E.val = E1.val + T.val = 12 + 5 = 17.

Answer. The expression 3 * 4 + 5 evaluates to 17, and since every attribute here is synthesized the definition is S-attributed, so this order is exactly the bottom-up reduction order.

Exam traps

  • An inherited attribute of a node may not take its value from that node's children or from a right sibling — such a value is synthesized, and if a right-side symbol's inherited attribute depends on a symbol to its right the definition stops being L-attributed.
  • digit.lexval is supplied by the lexer, not by a semantic rule. Writing F.val = F.lexval, or calling lexval a synthesized attribute of this grammar, loses marks.
  • A single inherited attribute disqualifies a definition from being S-attributed. When asked 'S-attributed or L-attributed?', check every rule before answering.
  • Evaluation follows the dependency graph, not the drawing order of the tree. Computing the root before the leaves gives a wrong number even though the rules look right.
  • In A → B C D, letting C.inh depend on D.val is a legal SDD but not an L-attributed one. The restriction is about evaluation order, not about meaning.

Analyze A definition contains A → B C with the rule B.inh = C.val. Is it L-attributed? Justify in two lines. 5 marks

No. B.inh depends on a symbol to its right, so a single left-to-right depth-first walk cannot compute it. The SDD is still meaningful, but it needs a different evaluation order or a rewritten grammar.

Analyze Two rules read X.a = Y.b + 1 and Y.b = X.a × 2. What goes wrong, and what is the fix? 6 marks

The dependency graph has the cycle X.a → Y.b → X.a, so no topological order exists and the definition is circular. Rewrite so the value is computed once and passed down, or split the symbol.

4.2 Syntax trees and DAGs for expressions

A parse tree shows every grammar step, including nonterminals that carry no value. A syntax tree keeps only the operators and operands, so the expression's structure is easy to read. If the same subexpression appears twice, a syntax tree still stores it twice. A directed acyclic graph (DAG) stores it once and lets two parents point to the same node. Compilers build these forms before emitting intermediate code, because the DAG exposes repeated work that can be computed once. Some syllabi call this an expression DAG.

You need attributes from 4.1 and the parse-tree idea from Unit 2.

Drop grammar punctuation

A parse tree for an expression has an interior node for every nonterminal used in the derivation. Many of those nodes are punctuation: they show which production was used, not which value is computed. A syntax tree removes them. Each interior node is an operator, and each leaf is an identifier or a constant. The children are the operands.

Build a syntax tree with two constructors. mkleaf(name) makes a leaf for a variable or constant. mknode(op, left, right) makes an operator node with a left child and a right child. For unary minus, use a node with one child. For a function call, the node holds the function name and its argument list.

For (a + b) * c, the root is *. Its left child is + with leaves a and b. Its right child is c. Parentheses do not appear as nodes; they only decide the shape. The syntax tree has 2 operator nodes and 3 leaves, so 5 nodes.

Semantic rules from 4.1 can return these nodes as synthesized attributes. The parser builds bottom-up: leaves first, then the operator above them.

Share equal subexpressions

Two occurrences of a + b in one expression compute the same value if a and b do not change between them. A DAG merges the two occurrences into one node. A DAG is a directed graph with no cycles. Leaves are variables or constants. Interior nodes are operators. An edge from a node to a child means "this operator uses that child". A node may be used more than once, and that is the whole point.

The value-number method builds the DAG in one pass. Give every distinct leaf a unique value number. For an operator node with operator op, left value number L and right value number R, look up the triple (op, L, R) in a table. If it exists, reuse that node. If not, create a node, give it the next value number, and record the triple. The value number is the node's identity. Equal numbers mean the same expression, so the compiler shares the node.

For (a + b) * (a + b) - c, the two plus nodes have the same triple (+, number of a, number of b). The second one is not created. The multiplication has the same plus node as both children. The DAG has 6 nodes instead of 9. The plus node is shared: the multiplication uses it as both children.

Sharing is common subexpression elimination at expression level. It saves evaluation time and storage. It is safe for pure arithmetic; with side effects or changing variables, the compiler must prove the value is unchanged.

Read the DAG correctly

A syntax tree and a DAG answer different questions. The syntax tree answers "how was this expression written?" The DAG answers "which values must be computed, and which results are reused?" Every DAG can be expanded into a syntax tree by copying a shared node once for each use. The reverse is also always possible: fold a syntax tree into a DAG by merging nodes that have the same operator and the same children. The fold saves nodes only when equal subtrees actually repeat.

Do not confuse this expression DAG with the basic-block DAG used in optimization. A basic-block DAG covers many statements and must respect assignments and side effects; that topic belongs to Unit 6. Here the DAG covers one expression.

The DAG is also a compact input to later stages. You can list its nodes in postfix order and emit three-address code from that list, or use the postfix list directly as stack-machine code. If a shared node is used several times, compute it once and let each use read the saved result.

Exam traps

  • Do not merge a + b and b + a automatically. The triples (+, L, R) and (+, R, L) are different unless the compiler applies a commutative canonical order.
  • A DAG is not a syntax tree with missing labels. A shared node is used more than once (indegree ≥ 2); a syntax-tree node is used at most once (indegree ≤ 1). If no node in your drawing is used more than once (indegree ≤ 1 for every node), you drew a syntax tree.
  • Value numbers identify expressions within one pass. Two different variables can hold the same runtime value; the DAG must not share them just because their names look similar.
  • Do not count grammar nonterminals or parentheses in a syntax tree. Single-child chains from E to T to F are not nodes.
  • This expression DAG is not the basic-block DAG of Unit 6. Do not add assignment effects or statement order here.

4.3 Semantic analysis: type expressions and type checking

A type expression is a small tree or term that describes the values a name can hold. Semantic analysis builds these terms from declarations and checks every operator and assignment against them. This catches errors such as adding a pointer to a float or storing a string in an int before any code runs. Compilers for C, Java and TypeScript all contain a version of this pass. The same terms also guide later code generation, because the type of a[i] decides the address arithmetic. Type checking is the part of semantic analysis that proves the program respects its declared types.

You need: semantic rules from 4.1 and the symbol-table idea from Unit 5, Symbol tables, scope and binding.

Type expressions

A type expression is a term that names a set of values and the operations allowed on them. Basic types are int, real, char and bool. Constructors build larger types. An array type records a bound and an element type. A pointer type records the type pointed to. A product type records a record or parameter list. A function type records parameters and result.

τ → int | real | char | bool | array(n, τ) | ptr(τ) | τ₁ × τ₂ | τ₁ → τ₂

τ, τ₁ and τ₂ are type expressions; n is a positive integer bound; int, real, char and bool are basic types; array(n, τ) is an array of n elements each of type τ; ptr(τ) points to a value of type τ; τ₁ × τ₂ is a product; τ₁ → τ₂ is a function from τ₁ to τ₂.

Read int a[10] as array(10, int): the constructor is array, the first child is the bound 10, the second child is the element type int. In Figure 4.3.1 this type expression is the type written under the leaf a. The symbol table stores the expression so later checks can look it up by name.

Checking expressions and assignments

Checking follows the shape of the expression. For E1 + E2, both operands need numeric type; the result has the common numeric type. For E1[E2], E1 must be array(n, τ) and E2 must be int; the result has type τ. The bound n gives valid indices 0 to n−1 but does not change the result type. For assignment x = E, x must be a variable and the type of E must be compatible with the declared type of x. A strict checker uses equality; a language with subranges uses compatibility.

type(E1 + E2) = int if type(E1) = int and type(E2) = int

E1 and E2 are expressions; type(E) is the type expression of E; int is the integer type.

Static checking runs before execution and stops code generation on an error. A bottom-up pass over the syntax tree is enough: each node gets a type from its children. The semantic rules from 4.1 can compute a type attribute at each node.

Structural and name equivalence

Structural equivalence compares type expressions by shape, recursively. array(10, int) equals array(10, int); it does not equal array(10, real). Name equivalence compares declared type names. Two variables match only when declared with the same type name. A typedef in C gives a new spelling, not a new type. Two struct tags with identical fields are still different types in C, a name-like rule. Java classes use name equivalence: two classes with the same fields are different types. The common exam question shows two identical-looking declarations and asks whether an assignment is legal; the answer depends on the language's rule.

Static checking and type inference

Static checking proves type correctness from declarations and rules. Type inference fills in missing types from use. If x = 1 and x has no declared type, a checker can infer x: int. If f(x) = x + 1 and + is integer addition, it can infer f: int → int. Inference is common in functional languages; only some syllabi teach the full algorithm. A simple method gives each unknown a fresh type variable and solves equality constraints. Overloading breaks a naive solver because + may mean integer or real addition. Runtime type checks belong with runtime environments in Unit 5.

Worked example

Question. The declarations are int a[10]; int i; int x; (a) Write the type expression of a. (b) Check the statement x = a[i] + 1; state the type of each subexpression. (c) For i = 3 and a[3] = 7, give the stored value and the number of elements in a.

  1. The bound is 10 elements and the element type is int, so type(a) = array(10, int).
  2. The declarations give type(i) = int and type(x) = int.
  3. The index rule uses type(a) = array(10, int) and type(i) = int. The result is type(a[i]) = int. The valid index range is 0 to 9.
  4. The literal 1 has type int. The addition rule gives type(a[i] + 1) = int.
  5. The assignment rule compares int with type(x) = int. The statement x = a[i] + 1 is type-correct.
  6. For the run take i = 3 and a[3] = 7. Then a[i] + 1 = 7 + 1 = 8, so x stores 8. The array has 10 elements.

Answer. a has type array(10, int), a[i] is int, the sum is int, and the assignment is type-correct; with i = 3 and a[3] = 7 the stored value is 8 and the array has 10 elements.

Exam traps

  • Structural and name equivalence are different tests. Do not call two identical field lists equal without checking the language rule.
  • The array bound is part of the type. array(10, int) and array(20, int) are different types, even though both elements are int.
  • For a function type, parameter order and count matter: (int × bool) → int is not (bool × int) → int.
  • Type checking is not evaluation. x = a[i] + 1 can be type-correct even when i is out of range; range is a separate check.
  • Inference is not the same as checking. Checking uses declared types; inference creates types for names that lack declarations.

4.4 Intermediate languages and postfix notation

An intermediate representation (IR) is a form of the program that sits between the source text and the machine code. The front end writes it, the back end reads it, and neither side needs to know the other. Because the IR hides the source language and the target machine at once, one front end can feed several machines and one back end can serve several languages. Postfix is the smallest member of this family: every operator follows its operands, so a stack evaluates it with no brackets and no precedence table. Calculators, JVM bytecode and many compiler back ends use this idea.

You need: 4.2 Syntax trees and DAGs for expressions for the tree-shaped forms, and Unit 1, Compiler Structure and Lexical Analysis, for the order of the phases.

Why a compiler builds an intermediate form

Source languages are many and machines are many. A translator written directly for one source language and one machine forces a new program for every pair: m source languages and n machines need m × n compilers.

m × n → m + n

m is the number of source languages and n the number of target machines; writing each front end and each back end once against a shared IR gives m + n halves instead of m × n whole compilers.

An IR is a form of the program that keeps the meaning and drops the surface. The front end — lexer, parser, semantic checks — builds it; the back end — optimiser and code generator — consumes it. Inside a single compiler the IR still pays: an optimisation written once against the IR works for every source language, and the IR is simpler than the source, with no comments, no brackets and no synonyms.

  • Machine independent: no registers and no instruction sizes.
  • Unambiguous: one shape, one meaning.
  • Compact: small enough to stay in memory.
  • Cheap to walk: easy to build from the parse tree and easy to turn into target code.

Four common intermediate representations

Four IRs cover most of this unit. They differ in shape, not in meaning; all four can be built from the same syntax tree using the semantic rules of 4.1.

IRShapeUsed for

DAGtree with repeated subtrees sharedfinding common subexpressions
Postfixflat list: operands, then operatorone-pass stack evaluation
Three-address codelist of x = y op zoptimisation, code generation
  • Tree-shaped forms keep nesting visible; the syntax tree and the DAG are covered in 4.2.
  • Linear forms are read left to right in a single pass.
  • Postfix keeps operator symbols, so it stays close to the written expression.
  • Three-address code gives a name to every intermediate value, which is what the optimiser needs; its tables are in 4.5.

The choice trades convenience for use. Trees suit analysis, because a routine can be called on each node. Linear forms suit code generation, because the generator only moves forward. Many real compilers keep two: a tree or graph while checking and optimising, then a linear form for the back end.

Prefix, postfix and the stack

Infix puts the operator between its operands: a + b. Prefix, also called Polish notation, puts it before: + a b. Postfix, also called reverse Polish notation, puts it after: a b +.

postfix(E₁ op E₂) = postfix(E₁) postfix(E₂) op

E₁ and E₂ are the operand subexpressions and op is a binary operator; apply the rule from the innermost operator outwards, using the precedence of the grammar.

Because position fixes the order, postfix needs no brackets and no precedence table. (a + b) × c becomes a b + c ×, and a + b × c becomes a b c × +. The brackets of the first version are not lost; they are encoded in where the + sits.

  1. Read the tokens from left to right and keep one stack of values.
  2. A number: push its value.
  3. A binary operator: pop the right operand, then the left, apply the operator and push the result.
  4. At the end exactly one value remains on the stack; it is the answer.

Order matters for − and ÷. In a − b the string is a b −: the first pop gives b, the second gives a, and the result is a − b. Popping in the other order would compute b − a.

A valid postfix string with k operands has exactly k − 1 binary operators. Read the string left to right: after every prefix except the whole string, the number of operands seen is at least one more than the number of operators seen; the difference may be larger than one. Only when the whole string has been read is the difference exactly one, with one value left on the stack. Counting is a quick check in an exam.

Worked example

Question. Using the grammar E → E + T | T, T → T * F | F, F → num, convert 3 + 4 * 2 to postfix. Then evaluate the string with a stack, showing the stack after every token, and state the value of the multiplication and the value of the whole expression.

  1. The grammar makes * bind tighter than +, so 4 * 2 is one subexpression. Its postfix form is 4 2 *.
  2. Replace that subexpression inside the sum: the postfix string is 3 4 2 * +.
  3. Push 3: stack is [3].
  4. Push 4: stack is [3, 4].
  5. Push 2: stack is [3, 4, 2].
  6. Read *: pop 2 as the right operand, pop 4 as the left, 4 × 2 = 8, push 8. Stack is [3, 8].
  7. Read +: pop 8 as the right operand, pop 3 as the left, 3 + 8 = 11, push 11. Stack is [11].
  8. One value remains, so the expression's value is 11.

Answer. The postfix form is 3 4 2 * +, the product 4 × 2 is 8, and the whole expression evaluates to 11.

Exam traps

  • For a − b the postfix string is a b −, never b a −. The first pop is the right operand, the second is the left.
  • Reversing a postfix string does not give its prefix form. a + b is + a b in prefix and a b + in postfix; reversing a b + gives + b a, which means b + a.
  • Postfix carries no brackets, so writing (a b +) c × in an answer is wrong.
  • Postfix is not three-address code: three-address code has names and one operator per instruction, postfix is still one expression.
  • Examiners give strings with the wrong operator count. A string with k operands must have exactly k − 1 binary operators; check the count before you evaluate.

Remember Define prefix and postfix notation in one line each. 2 marks

Understand Why can postfix be evaluated without a precedence table? 3 marks

The order of the tokens already fixes the evaluation order. Each operator appears exactly when the values of its two operands are on top of the stack, so no token ever waits for a later, higher-precedence operator.

Apply Convert (a + b) * (c - d) to postfix. 4 marks

a b + c d - * . The left bracket group gives a b +, the right group gives c d -, and the outer * joins the two results.

Apply Evaluate the postfix string 6 2 3 * - 4 + with a stack and give the final value. 5 marks

Push 6, 2, 3 → [6, 2, 3]. * replaces 2 and 3 by 2 × 3 = 6 → [6, 6]. - gives 6 − 6 = 0 → [0]. Push 4 → [0, 4]. + gives 0 + 4 = 4. Final value 4.

Analyze A postfix string has 5 operands and 3 binary operators. Is it valid? Why? 5 marks

No. A valid string with k operands needs exactly k − 1 operators, here 4. With only 3 operators, two values would still be on the stack at the end, so the string is malformed.

Analyze Give one reason a compiler may prefer three-address code over postfix for optimisation. 4 marks

In postfix a repeated subexpression has to be recomputed, because no name refers to its value. Three-address code names each value (t1 = b * c), so a common subexpression is computed once and reused, and dead instructions are easy to spot.

4.5 Three-address code: quadruples, triples, indirect triples

Three-address code is a linear intermediate form. Each instruction does at most one operation and names at most three operands. A compiler can store these instructions in a table instead of drawing a tree. The three common tables are quadruples, triples and indirect triples. They differ in how the result of an instruction is named: quadruples put a new temporary name in a result field, triples use the row number itself as the name, and indirect triples use the same triple numbers but keep execution order in a separate pointer list of row numbers. Compilers use these tables before code generation and during optimization.

You need: 4.4 Intermediate languages and postfix notation for the place of three-address code among IRs, and 4.2 Syntax trees and DAGs for how expressions produce temporaries.

Instructions and temporaries

A three-address instruction has the general form x = y op z. Here x is the result, y and z are the two operands, and op is one binary operator. An operand can be a variable name, a constant, or a compiler-made temporary. A temporary is a name such as t1 that holds an intermediate value and usually does not appear in the source program.

Other common forms are x = op y for a unary operation, x = y for a copy, x = y[i] for an array load, x[i] = y for an array store, goto L, if x relop y goto L (relop is a relational operator such as < or ==), param x, call p, n (p is the callee and n is the argument count), and return x. Each form still has at most one operator. This is why the order of work is explicit: one instruction, one job.

For x = a + b * c - d, multiplication has higher precedence than addition and subtraction. The compiler emits t1 = b * c, then t2 = a + t1, then t3 = t2 - d, then x = t3. The names t1, t2 and t3 are temporaries. A later pass may reuse a temporary after its last use, but the table normally gives each new value a fresh name so that data flow stays visible. Postfix notation, covered in 4.4, is the stack-based linear form of the same code.

Quadruples

A quadruple writes every part of an instruction in its own field: op, arg1, arg2, result. The row number is the instruction's position. For x = a + b * c - d the figure shows four rows: row 0 is (*, b, c, t1), row 1 is (+, a, t1, t2), row 2 is (-, t2, d, t3), and row 3 is (=, t3, blank, x).

arg1 and arg2 are the two operands. For a binary operator both are used. For a unary operator arg2 is blank. For a copy or assignment, arg1 is the source and arg2 is blank; the destination sits in result. A blank field is not zero and not an empty string value; it means 'this field is not used'.

Quadruples are easy to rearrange. Take two rows with no dependence between them, say row 0 is (*, b, c, t1) and row 1 is (*, e, f, t4). Neither row uses the other's result, so an optimizer may swap them. Only rows with no dependence between them may be moved. After a legal move the temporary names still travel with their rows, so later uses do not have to be rewritten. The cost is four fields per instruction. Each temporary gets a name in the result column and is written again in later arg fields, so names are repeated.

Triples and indirect triples

Triples remove the result field. A triple has three fields: op, arg1, arg2. The result of a triple is the triple's number. To use that result in a later triple, write the number in parentheses. For the same example the triple table is:

  • 0: (*, b, c)
  • 1: (+, a, (0))
  • 2: (-, (1), d)
  • 3: (=, x, (2))

The temporaries t1, t2 and t3 do not appear. (0) means 'the value produced by triple 0'. For the assignment triple, arg1 is the target x and arg2 is (2). There is no result column to hold x, so the assignment must name its target in an operand field.

Note the swap. In a quadruple the assignment names the source in arg1 and the target in result; in a triple there is no result column, so the target moves into arg1 and the source into arg2: (=, t3, blank, x) becomes (=, x, (2)).

Indirect triples keep the triple table unchanged and add a pointer list. Each pointer is an index into the triple table, and the pointer list gives the execution order. For this straight-line code the pointer list is [0, 1, 2, 3]. If an optimizer wants to move a statement, it moves a pointer, not a triple. The triple numbers stay fixed, so references such as (0) and (1) do not change.

Space for n instructions: quadruples use 4n fields, triples use 3n fields, and indirect triples use 3n fields plus n pointers. If a pointer is one word, indirect triples use 4n words, the same as quadruples. Triples are the smallest. Reordering: quadruples move rows but must keep result names consistent; triples must renumber and rewrite references; indirect triples avoid renumbering by moving pointers.

Worked example

Question. Translate the assignment x = a + b * c - d into three-address code. Show the quadruple table, the triple table and the indirect-triple representation. Then evaluate the code with a = 5, b = 2, c = 3, d = 4 and give the final value of x.

  1. 1. Precedence: multiplication binds tighter than addition and subtraction, and + and - group left to right. So compute b * c first.
  2. 2. Emit t1 = b * c. With a = 5, b = 2, c = 3, d = 4, t1 = 2 × 3 = 6.
  3. 3. Emit t2 = a + t1, so t2 = 5 + 6 = 11.
  4. 4. Emit t3 = t2 - d, so t3 = 11 - 4 = 7.
  5. 5. Emit x = t3, so x = 7.
  6. 6. Quadruples (op, arg1, arg2, result): row 0 (*, b, c, t1); row 1 (+, a, t1, t2); row 2 (-, t2, d, t3); row 3 (=, t3, blank, x).
  7. 7. Triples (op, arg1, arg2): 0 (*, b, c); 1 (+, a, (0)); 2 (-, (1), d); 3 (=, x, (2)). The result of triple 0 is (0), not t1.
  8. 8. Indirect triples: same triple table, pointer list [0, 1, 2, 3]. The list gives the execution order; here no reordering is possible because each triple uses the previous result.
  9. 9. Numeric result: x = 7.

Answer. Three-address code: t1 = b * c; t2 = a + t1; t3 = t2 - d; x = t3. It gives 4 quadruples, 4 triples with results (0), (1), (2), and indirect triples with pointer list [0, 1, 2, 3]; with a = 5, b = 2, c = 3, d = 4, x = 7.

Exam traps

  • In a triple table the result is the triple number, written (0), (1), not a temporary name such as t1. Writing t1 in a triple loses the link to the row.
  • A quadruple for a copy or assignment has a blank arg2, not a zero and not a repeat of arg1. The blank field still occupies a column.
  • Indirect triples are not a fourth field added to each triple. They are a triple table plus a separate pointer list; the pointer entries are indices into the triple table, not final machine addresses.
  • For n instructions, indirect triples use 3n fields plus n pointers, which is 4n words with one-word pointers. They are not smaller than quadruples in that accounting; triples alone use 3n fields.

Analyze An optimizer wants to move the first triple of a triple table below the second. Reordering triples carries a bookkeeping cost. What is that cost, and how do indirect triples remove it? 5 marks

Moving a triple changes its number, so references such as (0) in later triples now point to the wrong instruction; every reference must be rewritten. Indirect triples move pointer entries instead, leaving triple numbers and all references unchanged. Either way the move is allowed only when no dependence is violated: a triple that uses (0) can never be placed above triple 0.

4.6 Translating declarations and assignment statements

Syntax-directed translation puts semantic actions on grammar productions. A declaration action enters a name, type and width into the symbol table. An assignment action looks up names, computes storage addresses, converts types where needed, and emits three-address code. The idea exists because later phases need exact facts: where a variable lives, how many bytes it occupies, and what operation each instruction performs. Compilers use it for every scalar variable, every array index, and every mixed-type assignment, from a C program that stores daily power units in an array to a Java loop that totals UPI payments.

You need: 4.1 attributes, 4.3 type checking, and 4.5 three-address code.

Declarations enter the symbol table

Declarations create symbol-table entries. For a simple declaration grammar, the production D → T id ; has a type T and a name id. The action after id computes the entry and advances the offset. The offset is the byte position of the next free cell in the current scope. The width is the number of bytes the object occupies. For T → int, set T.type = int and T.width = 4 if int is 4 bytes. For T → int [ num ], set T.type = array(0..num−1, int) and T.width = num × 4. The element width is 4 bytes; the whole array width is 40 bytes for 10 elements.

  1. Compute T.type and T.width from the type production.
  2. Enter id.name with T.type, T.width and the current offset.
  3. Set id.place to that offset.
  4. Add T.width to offset.
NameTypeWidth (bytes)Offset
aarray(0..9, int)40 (4 per element)0
iint440
xint444

For int a[10]; int i; int x; the table holds these entries. This table is the declaration result; the assignment uses it. A name not in the table is an undeclared-variable error.

Assignments: l-values and r-values

An assignment needs a place to store and a value to store. The l-value is the location named on the left. The r-value is the value computed on the right. For a scalar id, the symbol-table entry gives the location directly. For an array element, no per-element address is stored. The compiler computes it from the base address, the index and the element width.

addr(a[i]) = base(a) + (i − low) × w

base(a) is the byte address of the first element; i is the index; low is the first legal index; w is the element width in bytes.

If low is 0, the formula is base(a) + i × w. For a two-dimensional row-major array A[l1..u1, l2..u2], the same idea adds a row stride: addr(A[i,j]) = base(A) + ((i − l1) × (u2 − l2 + 1) + (j − l2)) × w. The table stores the base, bounds and element width, not every address.

Emitting three-address code for the assignment

For S → id = E ;, look up id, check that the assignment respects the types from 4.3, and emit id.place = E.place. For E → E1 + E2, make a new temporary t and emit t = E1.place + E2.place; then set E.place = t. For E → id, set E.place to the name. For E → id [ E1 ], compute the address into a temporary, then load: t = *addr. The star means load the value stored at that address.

If x is real and E is int, emit a conversion before the store: t = inttofloat(E.place), then x = t. If x is int and E is real, use realtoint; that truncates toward zero in many languages. The emitted code is linear three-address code: each instruction has at most one operator and three names.

Worked example

Question. Assume int is 4 bytes, a has byte base address 1000, i = 4 and a[4] = 20. Translate the declarations int a[10]; int i; int x; and the assignment x = a[i] + 1. Show the symbol-table facts used, the element address, and the three-address code. What is x?

  1. Enter a: type array(0..9, int), element width 4 bytes, total width 40 bytes, base address 1000.
  2. Enter i and x as int, width 4 bytes each.
  3. Look up a and i. The address of a[i] is base(a) + (i − 0) × w = 1000 + 4 × 4 = 1016 bytes.
  4. Emit t1 = i * 4 = 4 × 4 = 16.
  5. Emit t2 = 1000 + t1 = 1000 + 16 = 1016.
  6. Emit t3 = *t2 = a[4] = 20.
  7. Emit t4 = t3 + 1 = 20 + 1 = 21.
  8. Emit x = t4, so x = 21.

Answer. The element address is 1016 bytes; the temporaries are t1 = 16, t2 = 1016, t3 = 20, t4 = 21, so x = 21.

Exam traps

  • Array address uses index × element width, not index alone.
  • Do not put total array width where element width is needed: int a[10] has element width 4 bytes and total width 40 bytes.
  • Subtract the lower bound before multiplying; for a[1..10] the first element is at base, not base + 4.
  • Conversion direction matters: inttofloat changes int to real; realtoint changes real to int.
  • Lookup must happen before emit; an undeclared name should produce an error, not code.

4.7 Boolean expressions, flow of control and procedure calls

Programs decide, and decisions become jumps. A compiler turns a boolean expression into two lists of jump instructions — one taken when the expression is true, one when it is false — and turns if, while and case statements into labels and gotos. The target label often does not exist yet when the jump is emitted, so the compiler records the jump's position and fills the target in later; that is backpatching. A procedure call adds param, call and return instructions plus a link back to the caller's activation record.

You need: three-address code (4.5) and assignment translation (4.6); activation-record layout is in Unit 5.

Boolean expressions become jumps

A boolean expression E is often used as a condition. The compiler can compute its value as 0 or 1, but for a condition it is faster to translate E into jumps: control reaches one label when E is true and another when E is false.

The truelist of E is the list of positions of jump instructions that must be completed with the label where E is true. The falselist does the same for the label where E is false. A position is the index of an instruction whose target is still blank.

For a test a < b, emit two instructions: if a < b goto _ and goto _. The first position goes into the truelist, the second into the falselist.

E1 &amp;&amp; E2: backpatch(E1.truelist, start of E2); E.truelist = E2.truelist; E.falselist = merge(E1.falselist, E2.falselist)

merge joins two lists of jump positions. A true E1 continues to E2, so E1.truelist is backpatched to the start of E2; a false E1 joins the false exits.

Short-circuit rules follow from the meaning of the operators. If E1 is false in E1 && E2, the whole expression is false and E2 is never evaluated; the false exits of E1 join the false exits of the whole expression. For E1 || E2 the mirror rule holds: backpatch E1.falselist to the start of E2; E.truelist = merge(E1.truelist, E2.truelist); E.falselist = E2.falselist. For !E, swap the two lists.

if, while, for and case statements

Every statement gets a start label and a next label from a counter. newlabel() returns 101, 102, ... in order. A label is an instruction number, and goto L sets the program counter to L.

  1. if (B) S1 else S2: translate B, then backpatch B.truelist to the first instruction of S1, and emit S1.
  2. Emit goto _ with a blank target; this jump is the end of the then-branch.
  3. Backpatch B.falselist to the first instruction of S2, then emit S2.
  4. Backpatch the blank goto from step 2 to the instruction after S2.

This is the shape of the figure: a false a < b jumps straight past the test c > d. Without an else, B.falselist is patched to the next label.

while (B) S: record the instruction number L1 before translating B. Backpatch B.truelist to the start of S and B.falselist to the label after the loop. S ends with goto L1. A for loop is rewritten first: for (init; test; step) body becomes init; while (test) { body; step; }.

case: evaluate the selector once into a temporary t, compare t with each case constant and jump to that case's label. break is a goto to the exit label; without break, C falls through into the next case. When the constants are dense, a jump table of labels indexed by t − low is cheaper.

Backpatching

A jump is emitted before its target label is known. Backpatching keeps the jump with a blank target and remembers its position in a list.

FunctionEffect
makelist(i)returns a new list holding only i, the position of one jump
merge(p1, p2)joins two lists and returns the result
backpatch(p, i)writes i, an instruction number, into the target of every jump in p

The marker nonterminal M carries one synthesized attribute, M.instr = nextinstr. In S → if (B) M S1, M records where S1 starts, so B.truelist can be backpatched to M.instr. Lists are needed because a condition such as a < b || c < d produces jumps from more than one place, and all of them go to the same target.

Emit stand-in jumps with target 0. Instruction 0 is never a real target, so a forgotten backpatch shows up at once during testing.

Procedure calls

A procedure call must return to the instruction after the call, so it needs more than a jump.

  • param x passes the actual parameter x; the compiler usually copies it into the callee's frame.
  • call p, n calls procedure p with n actual parameters and saves the return address.
  • return y returns the value y; in three-address code the value may be written as y = call p, n.

Each live call owns an activation record on the stack: actual parameters, return address, saved registers, local variables, temporaries and links. The control link points to the caller's record. The static link points to the record of the enclosing scope, which is how a nested procedure reaches a non-local variable. Layout and parameter passing are in Unit 5.

Recursion works because every call gets a fresh record. The callee stores the return value at the agreed place, sets the stack pointer back and jumps to the saved return address.

Worked example

Question. Translate if (a < b && c > d) x = 1; else x = 0; into three-address code. Instruction numbers start at 100. Show the truelist and falselist after each step.

  1. The condition is E1 && E2 with E1 = a < b and E2 = c > d. Instruction 100 is the first emitted.
  2. E1: emit 100: if a < b goto _ and 101: goto _. E1.truelist = {100}, E1.falselist = {101}.
  3. Mark the start of E2: M.instr = 102. Backpatch E1.truelist to 102, so instruction 100 reads if a < b goto 102.
  4. E2: emit 102: if c > d goto _ and 103: goto _. E2.truelist = {102}, E2.falselist = {103}.
  5. Combined condition: truelist = {102}; falselist = {101, 103}.
  6. Mark the start of the then-branch: 104. Backpatch the condition's truelist to 104, so instruction 102 reads if c > d goto 104. Emit 104: x = 1.
  7. Emit 105: goto _ for the end of the then-branch. Backpatch the condition's falselist to the start of the else part, 106. Emit 106: x = 0.
  8. Emit label 107: next. Backpatch instruction 105 to 107.

Answer. 100: if a < b goto 102; 101: goto 106; 102: if c > d goto 104; 103: goto 106; 104: x = 1; 105: goto 107; 106: x = 0; 107: next.

Exam traps

  • Short-circuit && must not evaluate the right side after a false left side; place the code for E2 after the jump taken on a false E1.
  • A truelist holds instruction positions, not labels. Writing truelist = {Ltrue} is wrong.
  • Backpatching a list twice silently moves the earlier jumps; check the merge order.
  • In a while loop the falselist is patched after the body, never at the body start, or the loop never ends.
  • In call p, n the n is the number of actual parameters, not the procedure's number.

Beyond the syllabus

Not for the exam. Real compilers keep this idea and change the data structures: LLVM IR uses labelled basic blocks with br instructions, and SSA form adds phi nodes wherever control flows merge. Switch statements on dense integers become jump tables, while sparse cases become a tree of comparisons. Java bytecode uses tableswitch and lookupswitch for the same reason. Search 'backpatching', 'LLVM switch lowering' or 'SSA phi node construction' to go further.

Unit summary

Key terms and formulas

TermMeaning or formulaChapter
Syntax-directed definition (SDD)A context-free grammar with a semantic rule attached to each production; the rules say how each attribute of each grammar symbol is computed.4.1
Semantic ruleThe expression attached to a production that computes an attribute value, e.g. E.val = E₁.val + T.val.4.1
Synthesized attributeAn attribute whose value at a node is computed from the attribute values of that node's children; information flows upward.4.1
Inherited attributeAn attribute whose value at a node is computed from the parent's or siblings' attribute values; information flows downward or sideways.4.1
Annotated parse treeA parse tree in which every node shows the values of its attributes.4.1
Dependency graphA graph whose nodes are attributes and whose edges say 'this attribute needs that one'; a topological order of it gives a safe evaluation order.4.1
Syntax tree (abstract syntax tree)A parse tree with keywords, semicolons, parentheses and single-child chains removed; each interior node is an operator, each leaf is an operand.4.2
DAG for expressionsA syntax tree in which two nodes with the same operator and the same children point to one shared node, so each distinct subexpression appears once.4.2
Type expressionA term naming a type, built from basic type names, type variables and type constructors such as array, ↑ (pointer) and → (function).4.3
Type systemThe collection of rules that assign a type expression to every part of a program and decide whether each construct is well typed.4.3
Type checkingVerifying that every operator, assignment and call receives operands whose type expressions are allowed by the language rules.4.3
Intermediate representation (IR)A machine-independent form of the program produced by the front end and consumed by the back end.4.4
Postfix notationA linear form in which each operator follows its operands, e.g. ab+; no parentheses and no precedence rules are needed.4.4
Three-address codeA sequence of instructions of the form x = y op z, where each instruction has at most one operator and at most three names.4.5
QuadrupleA four-field row (op, arg1, arg2, result) that stores one three-address instruction in a table.4.5
TripleA three-field row (op, arg1, arg2) where a result is referred to by its row number instead of a name.4.5
Indirect tripleAn array of triples plus a separate list of pointers to them, so the triples can be reordered without rewriting their references.4.5
Symbol tableA table mapping each declared name to its type expression, width in bytes and relative address.4.6
BackpatchingLeaving a jump target blank, keeping that instruction on a list, and filling in the real label number later when it is known.4.7
Short-circuit evaluationEvaluating a && b or a || b from left to right and stopping as soon as the result is fixed.4.7

Takeaways

  1. An SDD is a grammar plus semantic rules; synthesized attributes move information up the tree, inherited attributes move it down or across.
  2. Attribute evaluation must follow the dependency graph, and a topological order of that graph always gives a legal order.
  3. Dropping punctuation from a parse tree gives a syntax tree; additionally sharing identical subexpressions gives a DAG.
  4. A DAG is worth building because every shared node is a common subexpression that the later code need not recompute.
  5. Type expressions let the compiler store types as small trees and check each use by structural comparison.
  6. Postfix is the simplest linear intermediate form: it is evaluated with one stack and needs no parentheses.
  7. Three-address code is the usual middle form because it is linear like machine code but free of machine details.
  8. Quadruples name their results, triples do not, and indirect triples add a pointer array so that instructions can be moved.
  9. Declarations only build the symbol table; assignment statements are the first place real code is emitted, and array elements need an address formula.
  10. Boolean expressions are translated as jumps, and backpatching fills in jump targets in one forward pass without going back.

Exam question bank

Long answers here almost always ask you to take a given grammar or code fragment, write the semantic rules or the three-address code, and show the intermediate table or the patched jumps — so practise full worked traces, not just definitions.

Remember and understand

Understand Define synthesized and inherited attributes. Explain, with a small grammar, how each is computed and in what order attributes can be evaluated. 13 marks

Definition of an attribute as a property of a grammar symbol; Synthesized: value from children only; bottom-up evaluation; Inherited: value from parent or siblings; needs top-down or left-to-right order; Worked SDD for E → E + T with a val attribute; Dependency graph and topological order as the general evaluation rule.

Understand Explain how a syntax tree is obtained from a parse tree and how a DAG is obtained from a syntax tree. Illustrate with the expression (a + b) * (a + b) * c. 13 marks

Parse tree contains nonterminals, keywords and punctuation; Remove single-child chains and punctuation; operators become interior nodes; DAG: merge nodes with identical operator and identical children; Worked drawing showing the shared (a + b) node; Why sharing saves work later (common subexpression elimination).

Understand What is a type expression? Give the type expressions for a two-dimensional integer array, a pointer to a real, and a function from integer to integer. Explain how type checking uses them. 13 marks

Type expression built from basic types, type variables and constructors; array(2, array(3, integer)) for a 2×3 integer array; pointer(real) and integer → integer; Structural equality of type expressions; Rules for expressions, assignment compatibility and error reporting.

Understand Compare quadruples, triples and indirect triples with the same set of three-address instructions. 13 marks

Quadruple: op, arg1, arg2, result; results are named temporaries; Triple: op, arg1, arg2 with result referred to by row position; Indirect triple: array of pointers into the triple table; Effect of inserting or reordering an instruction in each scheme; Space and ease-of-optimisation trade-off.

Remember Write postfix equivalents for a + b * c, (a + b) * (c − d) and −a + b. State two advantages of postfix as an intermediate form. 8 marks

abc*+; ab+cd−*; a−b+ (unary minus first); No parentheses and no precedence needed; Direct evaluation with a stack; easy to generate from a bottom-up parse.

Apply

Apply For the grammar E → E + T | T, T → T * F | F, F → (E) | id, write an SDD and show the annotated parse tree for id + id * id. 13 marks

Semantic rule for each production, with val and lexval; Nodes annotated with values or with pointers to symbol-table entries; Correct left-to-right order of evaluation; Final tree with the root attribute value.

Apply Generate three-address code for the statement a[i][j] = b + c, assuming row-major layout, 4 bytes per element, and i, j starting at 1. Show every temporary. 13 marks

Formula base + ((i − low₁) × n₂ + (j − low₂)) × w; Compute t1 = i − 1, t2 = j − 1, t3 = t1 × n₂, t4 = t3 + t2, t5 = t4 × 4; Address t6 = base_a + t5, then a[t6] = t7; Fetch b and c, add into a temporary; Correct use of widths and of the lower bounds.

Apply Translate if x < y then s1 else s2 and while x < y do s into three-address code using backpatching. Show the lists truelist, falselist and nextlist at each step. 16 marks

Boolean test compiled as conditional and unconditional jumps; if: test, jump-if-false to the else part, then part, jump to end; while: label at the test, body, jump back to the test; makelist, merge and backpatch operations on the lists; Final code with every label filled in.

Apply Show the quadruple table for the code d = (a + b) * (a + b) − c. How would the same code look as triples and as indirect triples? 13 marks

Three temporaries named with the arithmetic; Quadruples with op, arg1, arg2, result; Triples referencing (1) or (2) in the argument fields; Indirect triples with row 35 pointing to triple 1 and so on; Note that the repeated (a + b) is computed once.

Apply Write the semantic actions that enter a declaration such as int a[10][20]; into the symbol table, and state what is stored for the name a. 13 marks

Actions after the type and after each declarator; Type expression array(10, array(20, integer)); Width = 10 × 20 × 4 = 800 bytes; Relative address from the current offset, offset then increased; Storage class, base, and low/high bounds kept in the entry.

Analyze and evaluate

Analyze Why is backpatching preferred over a two-pass generation of jump targets? Explain the list operations makelist, merge and backpatch with an example. 13 marks

One forward pass over the syntax tree; Targets unknown when the jump is emitted; Each instruction carries a list of incomplete jumps; makelist creates a one-element list, merge concatenates, backpatch fills label numbers; Example with while and short-circuit and/or showing saved lists.

Analyze Discuss the properties a good intermediate representation should have. Compare postfix, syntax trees and three-address code against those properties. 13 marks

Machine independence, ease of generation, ease of optimisation, compactness; Postfix: linear, stack-friendly, weak for reordering; Tree/DAG: exposes structure and sharing, not linear; Three-address code: linear like machine code, exposes temporaries and control flow; Choice depends on the optimiser and the target.

Evaluate Take the grammar of a small language with declarations, assignment, an if-else and a while. Write syntax-directed rules and produce the complete three-address code for one sample program that uses all four constructs. 16 marks

Declaration rules update the symbol table and offset; Assignment rules emit address and value code; Conditional rules build truelist and falselist; Loop rules emit a label at the test and a backward jump; A clean final listing with labels L1, L2 and temporaries t1, t2.

Evaluate Explain the rules for type checking expressions and statements in a language with integer, real, array and pointer types. Discuss one case where the checker must insert a conversion and one where it must report an error. 13 marks

Type expressions and structural equality; Rules for arithmetic with widening from integer to real; Assignment compatibility and the narrowing question; Array index must be an integer, pointer dereference must be a pointer; Error example a[i] where a is integer; conversion example x = y + 1 with x real.
