2.1 Role of the parser and syntax error handling

The parser is the compiler phase that checks whether a token stream follows a grammar and builds a parse tree. It exists because later phases need structure, not a flat list of tokens. Its input is the token stream from the lexer; its output is a parse tree or a trace of productions. When the stream breaks the grammar, the parser reports a syntax error and recovers instead of crashing. Every compiler, from a small student project to a production toolchain, has this phase; the same ideas drive editor syntax checkers and query parsers.

You need: Unit 1 for tokens, lexemes and the compiler phase diagram.

The parser's two jobs

After lexical analysis, the source program is a stream of tokens. A token is a pair: a kind (keyword, identifier, number, operator) and a lexeme (the actual characters). The parser is the next phase. Its input is this token stream. Its output is a parse tree, or a trace of the productions used. Some syllabi call this the syntax analyzer.

The parser has two jobs. Recognition: decide whether the token stream follows the grammar. Tree building: record which production matched at each step, so later phases can walk the tree. The grammar is a set of rules; a rule like D → type id = num ; says a declaration is a type token, an identifier token, an equals token, a number token, and a semicolon. The parser does not scan characters; it asks the lexer for the next token and matches token kinds. It also consults the symbol table for names. See 2.2 for grammars and trees.

D → type id = num ;

D is a declaration; type, id, =, num and ; are terminal token kinds; the arrow means 'rewrites to'.

Lexical, syntactic and semantic errors

Errors near the parser fall into three groups. A lexical error is a bad character or a misspelled keyword, for example whle where while is expected. The lexer may return an identifier token for whle; the parser then sees an identifier where a keyword was required. A syntactic error is a token sequence that no rule allows: a missing semicolon, an unmatched parenthesis, or int = 3; where the identifier is missing. A semantic error is a well-formed string with a wrong meaning: int x = "hi"; may parse if the grammar allows any expression, but the type checker rejects it. Semantic checks belong to Unit 4, not to the parser.

Do not call a parser error a compiler crash. The parser should report the error and continue, because one mistake should not hide later mistakes. A parser that silently guesses a missing token is also wrong: it must say what it expected and where.

What error handling must do

An error handler has three goals. Report clearly: give the line, the column or token position, the token found, and the set of tokens that would have been accepted. Recover: change the state so parsing can continue far enough to find more errors. Make progress: every recovery step must consume a token, insert a token, or pop a grammar symbol. If none of these happens, the parser repeats the same error forever.

Recovery should be local. A common rule is to skip tokens until a synchronising token, such as ; or }, then resume. The parser must not delete a large block of code to hide one missing comma. The error handler is a separate module called by the parser. Keeping it separate lets the parser stay simple and lets the handler choose the message and the recovery action.

Four recovery strategies

Four strategies are standard. Panic mode skips tokens until a token in a synchronising set, then resumes at a safe point. Phrase-level recovery makes a small local repair: delete one token, insert one token, or replace one token. Error productions add grammar rules for common mistakes, so the parser recognises the mistake and reports it with a tailored message. Global correction finds the smallest sequence of edits that turns the bad token stream into a valid one; it is expensive and rarely used in production compilers. Details and FOLLOW-set synchronising appear in 2.7.

Exam traps

  • Blaming the parser for a type error such as int x = "hi";. The grammar can accept the tokens; the type checker in Unit 4 rejects the meaning.
  • Treating a parser error as a compiler crash. A parser must report the error, recover, and keep going far enough to find more errors.
  • Confusing a lexical error with a syntactic error. A misspelled keyword may be lexed as an identifier, so the parser reports an unexpected identifier.
  • Writing a recovery routine that does not consume a token, insert a token, or pop a symbol. That routine repeats the same error forever.
  • Assuming every parser prints a full parse tree. Some parsers only accept or reject, and some print a trace of productions instead.

2.2 Context-free grammars, derivations and parse trees

A context-free grammar is a small set of rules that rewrites one named symbol, a nonterminal, at a time. It exists because a parser needs a precise description of legal token sequences, not a list of every program. From the start symbol, each rewrite makes a sentential form; when only terminals remain, the grammar has generated a string. A parse tree draws the same rewrites as a tree. Compilers use this model for expressions and statements; the same model appears in XML, query languages and protocol message formats.

You need: Unit 1 tokens and basic sets and strings; see 2.1 for the parser's job.

The four parts of a CFG

A context-free grammar (CFG) is a four-tuple G = (V, T, P, S). V is a finite set of nonterminals: names for syntax still to be expanded, written in capitals here. T is a finite set of terminals: the actual tokens, such as id, +, *, (, ). V and T do not overlap. P is a finite set of productions. S is the start symbol, one member of V.

G = (V, T, P, S)

V is the finite set of nonterminals; T is the finite set of terminals; P is the finite set of productions; S ∈ V is the start symbol.

A production is written A → α. A is one nonterminal from V. α is a string of symbols from V ∪ T; it may be empty. The arrow means A may be rewritten as α. The left side is a single symbol, so the rewrite of A does not depend on symbols around it. That is the context-free condition.

For expressions, one common grammar is E → E + T | T, T → T * F | F, F → id | ( E ). The bar is an alternative: E → E + T and E → T are two productions. Here V = {E, T, F}, T = {id, +, *, (, )}, S = E, and there are six productions.

A sentential form is any string that appears during rewriting; it may mix nonterminals and terminals. The language is L(G) = { w ∈ T* | S ⇒* w }. T* is zero or more terminals, S ⇒* w means w is reachable from S in zero or more steps, and w is a terminal string. A parser asks whether one token string is in L(G), and which tree proves it.

Derivations: rewriting from the start symbol

A derivation is a sequence of sentential forms. It starts at S; each step replaces one nonterminal by the right side of a production. Write ⇒ for one step and ⇒* for zero or more steps. E ⇒ E + T is one step using E → E + T.

A leftmost derivation always rewrites the leftmost nonterminal in the current form. A rightmost derivation always rewrites the rightmost one. The two orders can reach the same string; a question that asks for leftmost wants only that order.

  1. Start with S.
  2. Choose the leftmost nonterminal, or the rightmost one if the question asks for rightmost.
  3. Replace it by the right side of one production.
  4. Stop when no nonterminal remains; the result is the yield.

A derivation step is a rewrite, not a tree node. It records a production choice at one position. The yield is the final terminal string.

Parse trees and the one-to-one link

A parse tree is a rooted tree. The root is S. Each internal node is a nonterminal. Its children are the symbols of the right side of the production used to rewrite that nonterminal. A leaf is a terminal, or ε in some conventions. The yield is the string of leaves read left to right.

A leftmost derivation and a parse tree correspond one-to-one. Given the tree, expand the leftmost unexpanded nonterminal at each step; that produces the leftmost derivation. Given a leftmost derivation, draw each rewrite as a node with its right side as children; that produces the tree. A rightmost derivation reads the same tree in a different order.

Keep two objects apart. The grammar defines a language: all terminal strings derivable from S. A parse tree proves membership for one string. One grammar can give several trees for one string; that is ambiguity, covered in 2.3. Operator precedence is fixed by the grammar. Changing E → E + T to E → T + E changes the tree while the same terminals remain.

Worked example

Question. Using the grammar E → E + T | T, T → T * F | F, F → id | ( E ), give the leftmost derivation of id + id * id, draw its parse tree, and count derivation steps, leaf terminals, nonterminals and productions.

  1. Start with E.
  2. E ⇒ E + T, using E → E + T.
  3. ⇒ T + T, using E → T on the leftmost E.
  4. ⇒ F + T, using T → F.
  5. ⇒ id + T, using F → id.
  6. ⇒ id + T * F, using T → T * F.
  7. ⇒ id + F * F, using T → F on the left T.
  8. ⇒ id + id * F, using F → id.
  9. ⇒ id + id * id, using F → id.
  10. Parse tree: root E has children E, +, T. The left E gives T then F then id. The right T gives T, *, F; its left T gives F then id, and its F gives id.

Answer. The leftmost derivation has 8 steps, the parse tree has 5 leaf terminals, and the grammar has 3 nonterminals and 6 productions.

Exam traps

  • A derivation step is not a parse tree node: the step is one rewrite; the node is one nonterminal with children for the chosen right side.
  • Leftmost and rightmost are orders, not different languages. If the question says leftmost, do not show rightmost steps.
  • Count terminals and nonterminals correctly: id, +, *, (, ) are terminals; E, T, F are nonterminals.
  • The grammar's language is not the parse tree for one string. One string can have many trees under an ambiguous grammar.
  • Changing the grammar changes operator precedence and the tree, even for the same input string.

2.3 Writing a grammar: ambiguity, left recursion, left factoring

A top-down parser reads a grammar from the start symbol and tries productions in order. Three grammar faults break that plan: ambiguity (two parse trees for one string), left recursion (A → Aα makes the parser call A before consuming a token), and a common prefix (A → αβ₁ | αβ₂ makes the parser guess). This chapter rewrites the grammar into an equivalent one for the same language. The new grammar is easier for recursive descent (one procedure per nonterminal) and LL(1) tables (one-token lookahead).

You need 2.2 for productions and parse trees.

Ambiguity: one string, two trees

Ambiguity means one terminal string has two different parse trees. The classic example is the dangling else. Take S → if E then S | if E then S else S | a, where S is a statement nonterminal, E is a Boolean expression nonterminal, and a is a terminal. For the string if E then if E then a else a, the else can attach to the inner if or the outer if. Both trees follow the productions, so the grammar is ambiguous. A parser cannot choose without a rule.

Removing ambiguity is not algorithmic in general. For expressions, encode precedence and associativity: use separate nonterminals for factors, terms and expressions, as in E → E + T | T and T → T * F | F. For the dangling else, restructure with matched and unmatched statements: S → M | U, M → if E then M else M | a, U → if E then S | if E then M else U. The language is the same; the parse tree shape changes.

Removing left recursion

Left recursion is a production of the form A → Aα | β, where A is a nonterminal, α and β are strings, and β does not begin with A. A recursive descent parser calls A, which immediately calls A again before reading a token, so it loops.

A → βA′ A′ → αA′ | ε

A is the nonterminal being rewritten; α and β are grammar strings; β does not start with A; A′ is a new nonterminal; ε is the empty string.

The β alternative is the base case. A′ repeats α zero or more times.

For indirect left recursion, order the nonterminals A₁, A₂, …, Aₙ. For i from 1 to n, for j from 1 to i−1, replace every production Aᵢ → Aⱼγ with Aᵢ → δ₁γ | δ₂γ | …, where γ is a grammar string and Aⱼ → δ₁ | δ₂ | … are all current Aⱼ productions. Then remove immediate left recursion from Aᵢ. This process removes all left recursion.

The transformation preserves the language. It does not preserve the shape of parse trees; the new grammar may have different trees.

Left factoring

Left factoring removes a common prefix from alternatives. If A → αβ₁ | αβ₂, where α is the longest common prefix and β₁, β₂ are different suffixes, rewrite as:

A → αA′ A′ → β₁ | β₂

A is the nonterminal; α is the longest common prefix; β₁ and β₂ are the different suffixes; A′ is a new nonterminal.

The parser reads α once, then decides between β₁ and β₂ with one lookahead token. This helps FIRST sets stay disjoint; FIRST(α) is the set of terminals that can begin strings derived from α (see 2.5).

Apply the rule to every group of alternatives that shares a prefix, not just the first two. Repeat until no two alternatives for a nonterminal start with the same terminal string. For S → i E t S | i E t S e S | a, the common prefix is i E t S. So S → i E t S S′ | a and S′ → e S | ε. The first old alternative becomes S′ → ε; the second becomes S′ → e S.

These rewrites preserve the language but not the parse tree shape. They prepare the grammar for 2.4 and 2.6.

Worked example

Question. Consider the grammar: E → E + T | T; T → T * F | F; F → id; S → i E t S | i E t S e S | a. Remove immediate left recursion from E and T. Left-factor S. Give the final grammar. State the number of productions, ε-productions, and nonterminals.

  1. For E, α = + T and β = T. Replace E → E + T | T with E → T E′ and E′ → + T E′ | ε.
  2. For T, α = * F and β = F. Replace T → T * F | F with T → F T′ and T′ → * F T′ | ε.
  3. For S, the alternatives i E t S and i E t S e S share prefix i E t S. Replace with S → i E t S S′ | a and S′ → e S | ε.
  4. Final grammar: E → T E′; E′ → + T E′ | ε; T → F T′; T′ → * F T′ | ε; F → id; S → i E t S S′ | a; S′ → e S | ε.
  5. Count productions: E 1, E′ 2, T 1, T′ 2, F 1, S 2, S′ 2, total 11. ε-productions: E′ → ε, T′ → ε, S′ → ε, total 3. Nonterminals: E, E′, T, T′, F, S, S′, total 7.

Answer. The final grammar has 11 productions, 3 ε-productions, and 7 nonterminals.

Exam traps

  • Dropping the ε production from A′: then A cannot stop repeating α, so the parser loops or the language changes.
  • Left-factoring only the first two alternatives and leaving a third with the same prefix: the parser still cannot choose with one lookahead token.
  • Removing left recursion from a rule that is not left-recursive, or choosing β that begins with A: the rewrite is invalid.
  • Thinking ambiguity can always be removed by a general algorithm: it cannot; use precedence, associativity or restructuring for the case at hand.
  • Confusing left recursion with left factoring: one is a self-call at the start of a production, the other is a shared prefix between alternatives.

2.4 Top-down parsing and recursive descent parsers

A recursive descent parser is a set of functions, one for each nonterminal. Each function chooses a production and consumes tokens while it builds the parse tree from the root down. This design exists because it mirrors the grammar closely: the code for E looks like the productions for E. It is used in hand-written compiler front ends and in small language tools, usually with one token of lookahead so the parser never backtracks.

You need: 2.2 for grammars, derivations and parse trees, and 2.3 for removing left recursion and left factoring.

One procedure per nonterminal

Top-down parsing starts at the start symbol and expands nonterminals until the leaves are tokens. Recursive descent writes one procedure for each nonterminal. The body of the procedure tries the productions of that nonterminal. The lookahead is the current input token, meaning the next token not yet consumed.

match(t) checks the lookahead. If lookahead equals terminal t, match advances the input pointer and returns true. If not, it returns false and leaves the pointer unchanged in a backtracking parser. In a predictive parser, a failed match is a syntax error.

  1. Call the procedure for the start symbol.
  2. Inside each procedure, inspect the lookahead and select a production.
  3. For each symbol on the right side: if it is a terminal, call match on it; if it is a nonterminal, call its procedure.
  4. When all procedures return successfully and the lookahead is the end marker, accept the input.

The code shape follows the grammar. For E → T E′ and E′ → + T E′ | ε, write E() { T(); Eprime(); } and Eprime() { if lookahead == + { match(+); T(); Eprime(); } }. The ε production means the procedure simply returns without consuming a token.

Backtracking and predictive choice

A backtracking recursive descent parser tries productions in order. Before trying a production, it saves the token position. If a later match fails, it restores the saved position and tries the next production. A backtracking parser can handle any grammar without left recursion, at the cost of rescanning tokens; the worst case is exponential. Left recursion must still be removed first, because the procedure calls itself before consuming any token.

A predictive parser chooses without backtracking by using FIRST sets. For A → α | β, if the lookahead is in FIRST(α), choose α. If it is in FIRST(β), choose β. If one alternative is ε, choose it when the lookahead cannot begin any other alternative. FIRST sets are covered in 2.5.

A → α | β is predictive when FIRST(α) ∩ FIRST(β) = ∅

FIRST(α) is the set of terminals that can begin a string derived from α; ∅ is the empty set. Disjoint FIRST sets let one lookahead token pick one production. When an alternative can derive ε, the parser picks it only when the lookahead is in FOLLOW(A); the disjoint-FIRST rule alone does not cover nullable alternatives. Section 3 gives the FOLLOW check.

  • Backtracking parser: saves and restores token positions, tries alternatives in order.
  • Predictive parser: reads one lookahead token and selects the unique production whose FIRST set contains it.
  • Left factoring in 2.3 helps because alternatives with a common prefix have overlapping FIRST sets.

Left recursion and LL(1)

Direct left recursion such as A → A α | β makes A() call A() before any token is consumed, so recursion never stops. The repair from 2.3 rewrites it as A → β A′ and A′ → α A′ | ε. Indirect left recursion must also be removed before writing recursive descent code.

LL(1) means left-to-right scan of the input, leftmost derivation, and one token of lookahead. An LL(1) grammar has no left recursion, and its alternatives have disjoint FIRST sets, with ε choices checked against FOLLOW sets. The table-driven form of the same idea is in 2.6; error recovery is in 2.7.

Some syllabi call recursive descent and predictive parsing separately: recursive descent may backtrack, while a predictive parser is the non-backtracking version. In practice, a hand-written predictive recursive descent parser is the common case.

Worked example

Question. Using E → T E′, E′ → + T E′ | ε, T → F T′, T′ → * F T′ | ε, F → id | ( E ), trace a predictive recursive descent parser on the token string id + id * id. State the final result and the number of tokens matched.

  1. Start E(); lookahead is id.
  2. E calls T(); T calls F(); F sees id, so match(id) consumes token 1; lookahead becomes +.
  3. T calls T′(); lookahead is +, not *, so T′ chooses ε and returns.
  4. E calls E′(); lookahead is +, so E′ chooses + T E′; match(+) consumes token 2; lookahead becomes id.
  5. E′ calls T(); T calls F(); F sees id, so match(id) consumes token 3; lookahead becomes *.
  6. T calls T′(); lookahead is *, so T′ chooses * F T′; match(*) consumes token 4; lookahead becomes id.
  7. T′ calls F(); F sees id, so match(id) consumes token 5; lookahead becomes the end marker $.
  8. T′ calls T′(); lookahead is $, not *, so T′ chooses ε and returns.
  9. The outer E′ calls E′(); lookahead is $, so E′ chooses ε and returns.
  10. End of input is reached; the parser accepts. Tokens matched: 5.

Answer. The parser accepts id + id * id after matching five tokens; no backtracking is needed.

Exam traps

  • Writing A() { A(); ... } for a left-recursive grammar: the procedure calls itself before consuming any token, so recursion never stops. Remove left recursion first.
  • Forgetting to advance the input pointer inside match: the same token is matched forever and the parser may loop.
  • Choosing an alternative by guessing without FIRST sets: alternatives with a common prefix may be selected wrongly, so left factoring is not optional.
  • Thinking LL(1) scans from the right or uses one token per production: LL(1) means left-to-right scan, leftmost derivation, one token lookahead.
  • Restoring the token position after a successful match in a backtracking parser: restore only on failure, or tokens get consumed twice.

Three match calls succeed: id, +, id. The first id is matched by F, + by E′, and the second id by F.

Analyze Why must FIRST sets of alternatives be disjoint for a predictive recursive descent parser? 4 marks

The parser reads only one lookahead token. If a token lies in FIRST of two alternatives, the parser cannot choose uniquely without backtracking or more lookahead.

Understand Give one difference between backtracking recursive descent and predictive recursive descent. 3 marks

Backtracking saves and restores token positions and may try several productions. Predictive parsing uses FIRST sets and one lookahead token, so it chooses one production and never backtracks.

Analyze A grammar has A → a B | a C. What repair makes it suitable for predictive parsing, and why? 4 marks

Left factor it as A → a A′ and A′ → B | C. The common prefix a no longer creates overlapping FIRST sets for the original alternatives.

Remember Expand LL(1). 2 marks

Left-to-right scan of the input, leftmost derivation, and one token of lookahead.

Not for the exam. Recursive descent is the usual shape of hand-written parsers in production compilers because the code is readable and easy to extend with error messages. Parser combinators in functional languages use the same idea as small functions that consume input. Modern parser generators often build table-driven LL or LR parsers, but the recursive descent form remains common for language servers and configuration formats. 2.5 FIRST and FOLLOW sets

FIRST(α) is the set of terminals that can begin a string derived from α. FOLLOW(A) is the set of terminals that can appear immediately after nonterminal A in some sentential form. A predictive parser uses these sets to pick one production without guessing, and to recover from errors. Only a few universities teach FIRST and FOLLOW as a separate exam topic; most fold it into LL(1) table construction. You meet them again in <a href='#predictive-ll-1-parsing-tables'>2.6.

You need: <a href='#context-free-grammars-derivations-and-parse-trees'>2.2 for derivations, <a href='#writing-a-grammar-ambiguity-left-recursion-left-factoring'>2.3 for grammar form, and the idea of a nullable symbol.

Nullable symbols and FIRST

ε is the empty string. A nonterminal A is nullable if A ⇒* ε. In the grammar below, E′ and T′ are nullable.

  • Terminal X: FIRST(X) = {X}.
  • If X → ε, add ε to FIRST(X).
  • If X → Y₁Y₂…Yₖ, add FIRST(Y₁) − {ε}. If Y₁ is nullable, add FIRST(Y₂) − {ε}, and continue while symbols are nullable. If all symbols are nullable, add ε.

For a string α, scan left to right. Stop at the first non-nullable symbol. ε is in FIRST(α) only if every symbol is nullable. Example: FIRST(T E′) = FIRST(T) = {(, id}; T is not nullable. FIRST(E′) = {+, ε}. FIRST(+ T E′) = {+}. FIRST(ε) = {ε}.

ε is a flag that the string can vanish. It is not a terminal. Never put ε into FOLLOW.

FOLLOW and the fixed point

FOLLOW(A) is defined only for a nonterminal A. It holds terminals that can appear right after A in a sentential form, plus $, the end marker. If A can be last, $ is in FOLLOW(A).

  1. Put $ in FOLLOW(S) for start symbol S.
  2. For A → α B β, add FIRST(β) − {ε} to FOLLOW(B).
  3. If β is nullable, add FOLLOW(A) to FOLLOW(B). This includes β = ε.
  4. Repeat rules 2 and 3 until no set changes. One pass can add a set that enables another addition; this is the fixed point. A loop over all productions until stable is enough.

Example: E → T E′ adds FIRST(E′) − {ε} = {+} to FOLLOW(T). E′ is nullable, so FOLLOW(E) also goes to FOLLOW(T). F → ( E ) adds ) to FOLLOW(E).

FOLLOW never contains ε. Nullability changes what you add; ε itself is not a member.

Worked example

Question. For the grammar E → T E′, E′ → + T E′ | ε, T → F T′, T′ → * F T′ | ε, F → id | ( E ), compute FIRST and FOLLOW for every nonterminal. The start symbol is E.

  1. Terminals: id, +, *, (, ), $. Nonterminals: E, E′, T, T′, F. Nullable: E′, T′.
  2. FIRST(F) = {(, id}; FIRST(T) = {(, id}; FIRST(E) = {(, id}.
  3. FIRST(E′) = {+, ε}; FIRST(T′) = {*, ε}.
  4. Start FOLLOW(E) = {$}. F → ( E ) adds ), so FOLLOW(E) = {), $}.
  5. E → T E′ adds + to FOLLOW(T); E′ nullable adds FOLLOW(E) to FOLLOW(E′) and FOLLOW(T). So FOLLOW(E′) = {), $}; FOLLOW(T) = {+, ), $}.
  6. T → F T′ adds * to FOLLOW(F); T′ nullable adds FOLLOW(T) to FOLLOW(T′), so FOLLOW(T′) = {+, ), $}.
  7. T′ → * F T′ adds * to FOLLOW(F); T′ nullable adds FOLLOW(T′) to FOLLOW(F), so FOLLOW(F) = {*, +, ), $}.

Answer. FIRST(E) = FIRST(T) = FIRST(F) = {(, id}; FIRST(E′) = {+, ε}; FIRST(T′) = {*, ε}; FOLLOW(E) = FOLLOW(E′) = {), $}; FOLLOW(T) = FOLLOW(T′) = {+, ), $}; FOLLOW(F) = {*, +, ), $}.

Exam traps

  • Putting ε in FIRST but not treating the nonterminal as nullable when computing FOLLOW; you then miss a whole FOLLOW set.
  • Writing ε in FOLLOW. FOLLOW holds terminals and $; absence is not a member.
  • Forgetting $ on the start symbol, so every FOLLOW set that depends on the start is wrong.
  • Stopping after one pass. FOLLOW can need several rounds before no set changes.

FOLLOW lists terminals that can follow a nonterminal. ε is the absence of a symbol, not a terminal.

2.6 Predictive LL(1) parsing tables

An LL(1) parser is a stack machine with a two-dimensional table. The table M[A,a] says which production to apply when the stack top is nonterminal A and the next input token is a. The parser needs no backtracking: one token is enough to choose. This chapter builds that table from FIRST and FOLLOW sets and runs the parser on the expression grammar. The same idea drives hand-written predictive parsers and table-driven front ends in compilers, query engines, and configuration-file readers.

You need: 2.5 FIRST and FOLLOW sets, 2.3 repaired grammar, and 2.4 procedure view.

The parser loop

An LL(1) parser reads input left to right, builds a leftmost derivation, and uses one lookahead token. It keeps a stack and a table M[A,a]. A is a nonterminal; a is a terminal or $. Entry M[A,a] is the production to apply, or it is empty for an error. The stack starts with $S, where S is the start symbol and $ marks the bottom. Input ends with $.

At each move X is the stack top and a is the lookahead. If X = a = $, accept. If X = a, pop X and advance the input. If X is a nonterminal and M[X,a] = X → α, pop X and push α reversed so its first symbol is on top. If X is a terminal and X ≠ a, report a syntax error. An empty entry for a nonterminal is a syntax error; recovery is in 2.7. The stack is written bottom to top, so the top symbol is on the right.

  1. Set the stack to $S and the input to w$, where w is the token string.
  2. Let X be the stack top and a the current input token.
  3. If X = a = $, accept.
  4. If X = a, pop X and advance the input.
  5. If X is a nonterminal and M[X,a] = X → α, pop X and push α reversed.
  6. If X is a terminal and X ≠ a, report a syntax error.
  7. If X is a nonterminal and M[X,a] is empty, report a syntax error.

Some syllabi call this a predictive parser, an LL(1) parser, or a table-driven parser. “Predictive” means the table predicts the production from one token; the parser never backtracks.

Building the table

For each production A → α, fill cells from FIRST(α). If α can derive ε, also fill cells from FOLLOW(A). A cell must receive at most one production. Two different productions in one cell is a conflict, and the grammar is not LL(1).

M[A,a] = {A → α | a ∈ FIRST(α)} ∪ {A → α | α is nullable and a ∈ FOLLOW(A)}

M[A,a] is the table entry; A is a nonterminal; a is a terminal or $; α is a production right side; nullable means α derives ε.

  • For A → α, put A → α in M[A,a] for every terminal a in FIRST(α).
  • If α is nullable, put A → α in M[A,b] for every b in FOLLOW(A), including $.
  • Do not use ε as an input column. ε is not a token; nullable productions go under terminals from FOLLOW(A).
  • If the same production arrives from both rules, it is not a conflict.
  • If two different productions arrive in one cell, stop: the grammar is not LL(1).

A grammar is LL(1) when every cell has at most one production. Ambiguous grammars cannot be LL(1). Left recursion and common prefixes that are not left factored usually create conflicts, so repair the grammar first (2.3).

Conflicts and what they mean

A conflict means the parser cannot choose with one lookahead token. Common causes are a common prefix not left factored, left recursion, and a nullable production whose FOLLOW set overlaps the FIRST set of another production for the same nonterminal. Rewriting the grammar often removes the conflict; some languages need a stronger parser.

The table is small: its width is the number of terminals plus $, and its height is the number of nonterminals. A programming language may need a few hundred rows, which is easy to store. An empty M[X,a] also gives a precise error message: the parser expected a token that can begin some production of X (or, if X is nullable, a token in FIRST(X) ∪ FOLLOW(X)), but saw a. A recursive descent parser stores the same choices in code; the table stores them as data.

Worked example

Question. Grammar: E → T E′, E′ → + T E′ | ε, T → F T′, T′ → * F T′ | ε, F → id | ( E ). (a) Compute FIRST and FOLLOW. (b) Construct the LL(1) table. (c) Parse id + id * id $ and give the first six rows of stack, remaining input, and action.

  1. FIRST sets: FIRST(E) = FIRST(T) = FIRST(F) = {id, (}; FIRST(E′) = {+, ε}; FIRST(T′) = {*, ε}.
  2. FOLLOW sets: FOLLOW(E) = {$, )}; FOLLOW(E′) = {$, )}; FOLLOW(T) = {+, $, )}; FOLLOW(T′) = {+, $, )}; FOLLOW(F) = {+, *, ), $}.
  3. Filled cells (13): M[E,id] = M[E,(] = E → T E′; M[E′,+] = E′ → + T E′; M[E′,)] = M[E′,$] = E′ → ε; M[T,id] = M[T,(] = T → F T′; M[T′,*] = T′ → * F T′; M[T′,+] = M[T′,)] = M[T′,$] = T′ → ε; M[F,id] = F → id; M[F,(] = F → ( E ). All other cells are empty; conflicts = 0.
  4. Trace rows, stack bottom to top with top at right. In every row the stack is shown before the action of that row is applied; the input column is the unconsumed input, ending in $.
  5. 1. Stack $E; input id + id * id $; action output E → T E′.
  6. 2. Stack $E′T; input id + id * id $; action output T → F T′.
  7. 3. Stack $E′T′F; input id + id * id $; action output F → id.
  8. 4. Stack $E′T′id; input id + id * id $; action match id, pop, advance.
  9. 5. Stack $E′T′; input + id * id $; action output T′ → ε.
  10. 6. Stack $E′; input + id * id $; action output E′ → + T E′.

Answer. FIRST and FOLLOW are as listed, the table has 13 filled entries and 0 conflicts, so the grammar is LL(1); the first six moves are rows 1–6 above.

Exam traps

  • Put a nullable production under FIRST only and forget FOLLOW(A); then M[A,b] stays empty for b ∈ FOLLOW(A), and valid input fails.
  • Write two different productions into M[A,a] and ignore the conflict. An LL(1) table must have at most one production per cell.
  • Use ε as an input column. ε is not a token; nullable productions go under terminals from FOLLOW(A), including $.
  • Forget $ in FOLLOW of the start symbol, so an input ending after a nullable tail has no table entry.
  • Assume every context-free grammar has an LL(1) table. Ambiguous or left-recursive grammars must be rewritten first (see 2.3).

2.7 Error recovery in predictive parsing

A predictive parser reads tokens with a stack and a table. If M[X, a] is empty, or the top terminal X ≠ a, the input cannot continue. The parser reports an error. Programmers want several mistakes per run, so recovery resumes near the fault using FOLLOW sets, token skipping and small grammar changes, without looping or discarding good input.

You need: FIRST and FOLLOW sets (2.5) and the LL(1) table and its algorithm (2.6).

Detection: the empty table entry

The parser of 2.6 works on X, the symbol on top of the stack, and a, the current lookahead token. M[X, a] is the table entry for that pair.

A production in M[X, a] replaces X by its right side. An empty M[X, a] means no production of X can start with a, so the input cannot be derived from X. Report the error at a.

When X is a terminal and X ≠ a, the parser expected X and got a. That is also an error.

LL(1) detects errors early: one lookahead token fixes the production, so the parser stops at the first token with no table entry and never reads past it. Detection is easy; the rest is recovery.

Panic mode: FOLLOW sets and skipping

Panic mode discards input until a token that can legally come next, then carries on. FOLLOW(X) holds terminals that may follow X, so it is the stopping rule.

  1. Report the error at the lookahead a.
  2. Let X be the top of the stack. If X is a nonterminal and a is in FOLLOW(X), pop X; a is not consumed.
  3. If X is a terminal b, FOLLOW does not apply: discard tokens until the lookahead is b, then match b and continue; if no usable token appears, give up on the statement and restart at the next ; or end of file.
  4. Otherwise discard a, read the next token, and repeat.
  5. Stop after a fixed number of errors, so one bad file does not flood the screen.

In the expression grammar, FOLLOW(T) = {+, ), $}. A parser inside T that sees * knows * cannot follow T, so it drops * and checks the next token.

Some implementations also stop skipping when the lookahead is in FIRST(Y) for the topmost nonterminal Y on the stack, because the parser is about to need a token that Y can start with.

Phrase-level recovery and error productions

Panic mode resumes parsing but repairs nothing. Phrase-level recovery makes one local fix, as if one token were typed wrongly.

  • Insert a token. The parser wants terminal b and sees a. It prints "missing b", matches b as if present, and continues with a untouched.
  • Delete a token. It prints "unexpected a", discards a, and continues.

Take S → id = E ; . The input x = 1 y = 2 has no semicolon. The parser finishes x = 1 expecting ; and sees id. It reports "missing ;", inserts the semicolon and matches it, then parses y = 2 normally. One message, no real token lost.

Error productions move the repair into the grammar. Add A → error α, where error matches no input. The table entry for A → error α is filled only for lookaheads a in FIRST(α) (plus FOLLOW(A)); for any other a the parser falls back to panic mode. At such an entry the parser prints a message and pushes α. The grammar and table grow, but the recovery point is written once by the grammar author.

Global correction finds the shortest insertions and deletions that turn the input into a valid string. It needs a search over many strings and is too slow for a compiler, so it is named here and not used.

Recovery must make progress

A recovery step can loop for ever. If it removes nothing from the stack and consumes no token, the next iteration reads the same M[X, a], fails the same way, and repeats.

Every step must change the stack or the input: popping X changes the stack, skipping a changes the input position, and inserting a token lets the parser match the expected terminal without reading input, so that terminal leaves the stack. Taking an error production A → error α pushes α, which also changes the stack.

The second rule: never discard a token the parser can use. Skipping while a is in FIRST(Y) for the topmost nonterminal Y on the stack throws away good input and sets off false errors.

A debug build checks both rules cheaply: assert that the pair (stack contents, input position) differs from the previous iteration.

Worked example

Question. Grammar: E → T E′, E′ → + T E′ | ε, T → F T′, T′ → * F T′ | ε, F → ( E ) | id, with FIRST(T) = {id, (} and FOLLOW(T) = {+, ), $}. Parse id + * id $ with the LL(1) table and panic mode. Show the error and how parsing resumes.

  4. Accept: F → id, match id, T′ → ε at $, E′ → ε at $, final $ matches $.

Exam traps

  • Skipping a token without changing the stack or input, so the same empty entry repeats for ever.
  • Using FIRST(X) instead of FOLLOW(X) to pop X; panic mode uses FOLLOW(X).
  • Skipping a token in FIRST of a nonterminal still on the stack, losing valid input and causing false errors.
  • Mixing panic mode (skip input, no repair) with phrase-level recovery (insert or delete one token).
  • Treating the recovered tree as correct; a skipped token is missing, so suppress code generation for that construct.

Takeaways

  1. The parser turns a flat token stream into a tree and is the phase that reports syntax errors; it does not fix the program on its own.
  2. A context-free grammar is a generating device, a derivation is one way it generates a string, and a parse tree is the record of that derivation.
  3. Three rewrites make a grammar usable by a top-down parser: remove ambiguity, remove left recursion, apply left factoring.
  4. A recursive descent parser is just code: one function per nonterminal, with a token pointer that only moves forward when the grammar is predictive.
  5. FIRST tells you which production can start with the lookahead; FOLLOW tells you what may legally come next, and it is also what error recovery uses.
  6. An LL(1) table entry M[A, a] = A → α means: with A on top of the stack and a as lookahead, replace A by α.
  7. A cell with two productions proves the grammar is not LL(1); a cell that is empty is the moment a syntax error is detected.
  8. Error recovery in predictive parsing is mechanical: report, then skip input until a token in FOLLOW(A) appears and pop A from the stack.

Long answers here are almost always a full worked construction — clean up a given grammar, compute FIRST and FOLLOW, build the LL(1) table and then trace the parse of a sample string — so the syllabi reward showing every step with the table drawn, not just the final answer.

Remember and understand

Understand Define a context-free grammar as a four-tuple. For the grammar E → E + T | T, T → T * F | F, F → ( E ) | id, give a leftmost derivation and the corresponding parse tree for id + id * id. 10 marks

State G = (V, T, P, S) and name each component; Write the leftmost derivation step by step, always expanding the leftmost nonterminal; Draw the parse tree with the same structure; leaves read left to right give the input; Point out that the same string has only one leftmost derivation here, so this grammar is unambiguous.

Remember Explain the role of the parser in a compiler and describe four general strategies for syntax error recovery. 8 marks

Parser obtains tokens from the lexer, verifies the grammar, builds the parse tree, passes it to the next phase; Detects and reports errors with line number; must recover to find further errors; Panic mode: skip tokens to a synchronising set; Phrase level: local repair by inserting or deleting a token; Error productions: grammar rules written to absorb common mistakes; Global correction: minimum-cost repair, rarely used in practice.

Understand Explain ambiguity and left recursion in grammars. Why does a top-down parser fail on each, and how is each removed? 10 marks

Definition of ambiguous grammar: two parse trees for one string; Example grammar E → E + E | E * E | id and two trees for id + id * id; Precedence and associativity declarations or a layered grammar remove ambiguity; Definition of left recursion A → Aα | β; Elimination rule: A → βA′ , A′ → αA′ | ε; Show the rewritten grammar derives the same language.

Apply

Apply Remove left recursion and apply left factoring to the grammar: S → i E t S | i E t S e S | a, E → b. Show the resulting grammar and state whether it is LL(1). 12 marks

Factoring the common prefix i E t S gives S → i E t S S′ | a, S′ → e S | ε; No left recursion is present, so only factoring is needed; Compute FIRST and FOLLOW of S, S′, E; Build the table and show no cell holds two productions, hence it is LL(1); Mention that the original grammar is ambiguous for the dangling-else input.

Apply For the grammar S → A a | b, A → b d | ε, compute FIRST and FOLLOW for every nonterminal. 10 marks

Mark A as nullable since A → ε; FIRST(A) = {b, ε}; FIRST(S) = {b, a}; FOLLOW(S) = {$}; FOLLOW(A) = {a} because A appears before terminal a in S → A a; Show the rules used for each set explicitly.

Apply Construct the LL(1) predictive parsing table for a given grammar and trace the parse of the string id * id + id using the stack algorithm. 14 marks

Compute FIRST and FOLLOW, showing the sets; Place A → α in M[A, a] for each a in FIRST(α); for ε in FIRST(α) use each b in FOLLOW(A); Draw the full table with rows nonterminals and columns terminals plus $; Write each move as (stack, input, action) triples; End when both stack and input hold $ and report acceptance.

Apply Write a recursive descent parser in pseudo-code for a small expression grammar. State the FIRST sets that justify the order of the if-conditions in each procedure. 12 marks

One procedure per nonterminal: E(), T(), F(); Each procedure checks the lookahead token against FIRST of its alternatives; Include match(token) that advances the input pointer on success; Show error calls when no alternative matches; Explain that FIRST sets make backtracking unnecessary.

Apply Show that the grammar S → S a | b is not LL(1), rewrite it, and rebuild the table to prove the new grammar is LL(1). 12 marks

Left recursion makes the table construction loop; S appears in FIRST(S a); Apply A → βA′ , A′ → αA′ | ε to get S → b S′ , S′ → a S′ | ε; FOLLOW(S′) = {$}; Table cells M[S, b] and M[S′, a] and M[S′, $] are the only entries; Conclude one entry per cell, so LL(1).

Analyze and evaluate

Analyze A predictive parser finds M[A, a] empty. Explain, with an example trace, how FOLLOW-based synchronisation and token deletion let parsing continue and report more than one error. 12 marks

Empty cell means the lookahead cannot start any production of A; Panic-mode recovery: report the error, then discard input tokens until one is in FOLLOW(A); Then pop A from the stack and resume; Alternative: if a is in FIRST of some production of A, push a dummy symbol or skip the token; Show a trace with two errors to prove parsing restarts and reports both; Mention the risk of endless loops and how popping A avoids it.

Analyze Compare recursive descent parsing with table-driven LL(1) parsing: structure, memory use, speed, error handling and grammar restrictions. 14 marks

Recursive descent: code per nonterminal, uses the call stack, easy to debug and to attach semantic actions; Table-driven: one loop plus an explicit stack and a table, table size is |V| × (|T|+1); Both need LL(1) grammar, hence no left recursion and no common prefixes; Recursive descent can backtrack on non-LL(1) grammars; LL(1) cannot; Error reporting is usually better in hand-written recursive descent because line context is known; Table size can be compressed but the loop is slightly slower per token.

Analyze Given a grammar for a small language, carry out the full top-down pipeline: remove ambiguity, remove left recursion, left factor, compute FIRST and FOLLOW, build the LL(1) table, and state every conflict you meet. 16 marks

Original grammar listed and its ambiguity or left recursion identified; Step-by-step rewrites with reasons; FIRST and FOLLOW table for every nonterminal; LL(1) table drawn completely; Conflicts, if any, named by their cell and the two competing productions; Conclusion: grammar is LL(1) or a further rewrite is needed.

Analyze Why can no LL(1) parser handle a left-recursive grammar or a grammar with a common prefix? What are the limits of LL(1) compared with LR parsing? 13 marks

Left recursion means A is in FIRST(Aα), so M[A, a] gets two entries; Common prefix makes FIRST(αβ₁) and FIRST(αβ₂) overlap; LL(1) uses one token of lookahead and never looks at the stack below the top; LL(1) cannot handle left-associative operators without rewriting; LR parsers postpone the decision and accept a larger class of grammars; LL(k) with k>1 or LR(1) costs more table space.

Glossary

Ambiguous grammar
Grammar in which at least one string has two distinct parse trees.
Backtracking
Retrying an earlier production choice after a mismatch; predictive parsers avoid it entirely.
Dangling else
Classic ambiguity where an else can attach to either of two nested if statements.
FIRST set
For a string α, the set of terminals that can begin a string derived from α, plus ε if α derives ε.
FOLLOW set
For a nonterminal A, the set of terminals that can appear immediately to the right of A in some sentential form.
Left factoring
Delaying the choice between alternatives that share a prefix by pushing the common part out and choosing later.
Left recursion
Production A → Aα in which the nonterminal is the first symbol on its own right side.
Leftmost derivation
Derivation in which the leftmost nonterminal is always the one rewritten next.
LL(1)
Grammar readable left to right, producing a leftmost derivation, with one token of lookahead.
Lookahead
The next input token the parser examines without consuming it.
Nonterminal
Grammar symbol that must be rewritten by a production before it can become terminals.
Nullable
A nonterminal A is nullable when A ⇒ ε in one or more steps.
Panic mode
Recovery that abandons the current construct and skips input until a safe token appears.
Parse tree
Ordered tree whose yield is the input string and whose internal nodes record the productions used.
Parsing table
Array M[A, a] giving the production to use when nonterminal A is on top of the stack and a is the lookahead.
Phrase-level recovery
Recovery that performs a small local repair such as inserting a missing semicolon or deleting a stray token.
Predictive parsing
Top-down parsing in which the next production is chosen from the lookahead token alone, with no backtracking.
Production
Rule of the form A → α saying nonterminal A may be replaced by the string α.
Recursive descent
Parser written as mutually recursive procedures, one for each nonterminal.
Sentential form
Any string of terminals and nonterminals reachable from the start symbol in zero or more steps.
Start symbol
The designated nonterminal from which every derivation begins.
Synchronising set
Set of tokens, usually FOLLOW(A), at which the parser may discard input and resume parsing.
Terminal
Symbol that appears in the input string itself, written in a grammar as a literal or a token class.
Token
Classified unit of input such as id, number or the keyword if, produced by the lexer and consumed by the parser.
