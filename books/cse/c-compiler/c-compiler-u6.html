6.1 Code generator design issues and a simple code generator

A code generator is the compiler pass that turns intermediate code into target instructions. Its input is three-address code from Unit 4. Its output may be assembly, relocatable machine code, or code for a virtual machine. The pass must pick instructions, choose registers, order evaluation, and address memory without wasting moves. A simple code generator does this one instruction at a time using two tables: a register descriptor and an address descriptor. The same ideas appear in student compilers, JIT back ends, and embedded toolchains.

You need three-address code from Unit 4 and variable addresses from activation records in Unit 5; basic blocks come next.

Input, output and design issues

Target code has three common forms: assembly text for an assembler, relocatable machine code for a linker, and bytecode for a virtual machine. Relocatable machine code is object code whose addresses are relative to the start of a block, so a linker can move it. The input is a list of three-address instructions such as t1 = a * b. Each instruction names at most three operands, so the generator can treat it as a small pattern. Some syllabi call this target code generation.

  • Instruction selection: the target may offer ADD R1, R2 or ADD R1, mem; pick the form that fits the addressing mode.
  • Register allocation: registers are few; keep frequent names in them and spill when full.
  • Evaluation order: reordering can cut loads, but data dependencies must stay.
  • Memory addressing: a name may live at a fixed offset from a frame pointer or at a global label.
  • Cost: every instruction and memory access has a cost; avoid redundant loads and stores.

These issues interact. A choice that saves a load may cost a register or force a store.

The simple code generator

For each instruction x = y op z, the generator calls getreg(x = y op z). getreg returns a register R for the result. It first looks for an empty register. If none is empty, it picks a register whose current value is not live, or whose next use is farthest away. If that register holds a dirty value, it first emits a store. A dirty register holds a value that differs from the memory copy.

  1. Find a register Ry holding y. If none, use y as a memory operand when the opcode allows it; otherwise emit LD R, y.
  2. Find a register Rz holding z. If none, use z as a memory operand when allowed; otherwise emit LD R, z.
  3. Emit OP Ry, Rz (the result overwrites y's register), or OP Ry, z when z can be a memory operand. If getreg returned a register R that holds neither y nor z, first emit MOV R, Ry and then OP R, Rz. In the worked example this is why ADD R0,R1 is correct: R0 already holds t1.
  4. Set the register descriptor of R to {x}; remove x from every other register descriptor; set the address descriptor of x to {R}.
  5. Mark the memory copy of x as stale until a store writes it.

For a copy x = y, if y is in a register and y is dead, rename that register to x. Otherwise emit a move or a load. For an unconditional jump, emit BR label; live values at the label must be in memory or in registers agreed by both sides. Calls are left to Unit 5, where activation records fix the addresses.

Descriptors, next-use and control flow

A register descriptor says which names currently have their value in each register. An address descriptor says where each name can be found: in a register, in memory, or both. After every emitted instruction, update both tables. If R0 holds t1 and ADD R0, R1 makes it hold t3, then t1 disappears from R0's descriptor and t3 appears. R1 may become free if t2 is dead.

Next-use information says whether a name is read later in the block. It lets getreg free a register without a store when the value is dead. It also chooses the victim with the farthest next use, so the spill is cheap. At a jump or label, the generator stores live values to memory unless both sides agree on a register. Worked example

Question. Generate target code for the basic block t1 = a * b; t2 = c * d; t3 = t1 + t2; x = t3 using a simple code generator with registers R0 and R1. Show the register descriptor and address descriptor after each instruction. State the instruction count, register count and store count.

  1. Start: R0 and R1 are empty; a, b, c, d and x are in memory.
  2. Instruction 1: t1 = a * b. getreg returns R0. Emit LD R0, a. R0 descriptor = {a}; R1 descriptor = {}.
  3. Emit MUL R0, b. R0 descriptor = {t1}; a is no longer in R0; R1 descriptor = {}.
  4. Instruction 2: t2 = c * d. getreg returns R1. Emit LD R1, c. R0 descriptor = {t1}; R1 descriptor = {c}.
  5. Emit MUL R1, d. R0 descriptor = {t1}; R1 descriptor = {t2}.
  6. Instruction 3: t3 = t1 + t2. Both operands are in registers. Emit ADD R0, R1. R0 descriptor = {t3}; R1 descriptor = {} because t1 and t2 are dead.
  7. Instruction 4: x = t3. t3 is dead and R0 holds it, so rename R0 to x: R0 descriptor = {x}; address descriptor of x = {R0}; memory x stays stale; no target instruction is emitted for this copy. At the end of the block emit ST x, R0. Memory x now holds t3; R0 holds x; R1 is free.

Answer. The code is LD R0,a; MUL R0,b; LD R1,c; MUL R1,d; ADD R0,R1; ST x,R0: 6 target instructions, 2 registers, and 1 store. At the end R0 holds x and x is also in memory.

Exam traps

  • Do not let getreg return a register that still holds a live value; the old value would be overwritten with no store.
  • Update both descriptors after every emitted instruction. A stale address descriptor makes the next getreg think a name is in a register when it is not.
  • A register descriptor lists names in a register; an address descriptor lists places for a name. Swapping them is a common exam error.
  • After x = t3, memory x is stale until a store. Do not claim x is in memory just because the assignment exists in the source.

Analyze What goes wrong if getreg returns a register that holds a live value and no store is made? 4 marks

The new result overwrites the old value. Any later use of the old name reads the wrong value. The address descriptor may still claim the old name is in that register, so later decisions are also wrong.

Understand What does next-use information tell getreg? 3 marks

It tells whether a name is read later in the block. A dead value can be overwritten without a store. Among live values, the one with the farthest next use is the cheapest to spill.

Apply For x = y, y is in R1 and y is dead. What do the descriptors become? 3 marks

R1's register descriptor becomes {x}; the address descriptor of x becomes {R1}; y is removed from all descriptors. No load or store is needed if memory x can stay stale until a later store.

Analyze Why must live values be stored at the end of a basic block before a jump? 3 marks

The next block may expect the value in memory or in a different register. A store makes the value visible on both paths unless the generator has an agreement about registers across the edge.

6.2 Basic blocks and flow graphs

A basic block is a run of three-address statements with one entry at the top and one exit at the bottom. Inside it, control never branches. Real programs are mostly straight-line runs joined by jumps, so splitting the code at jump points gives a small set of blocks. A flow graph then draws those blocks as nodes and the possible jumps as edges. Compilers use this split to optimize each block locally and to reason about loops and branches across the whole program.

You need three-address code and the jump instructions from see Unit 4, Syntax-Directed Translation and Intermediate Code, and see Unit 3, Bottom-Up Parsing and LR Parsers, for how conditional and unconditional jumps are written.

Leaders: where a block must begin

Control normally moves from one statement to the next. A jump breaks that order. A basic block is a maximal run of consecutive three-address statements where control enters only at the first statement and leaves only after the last. Maximal means you cannot add the next statement without breaking the rule. Inside the block there is no branch, and no jumped-to label sits in the middle.

B = { sk, sk+1, …, sm }

sk is the leader that starts the block, and sm is the statement just before the next leader, or the last statement of the program.

Every block starts at a leader. Three rules mark the leaders, and nothing else does:

  • The first statement of the program is a leader.
  • Any statement that is the target of a goto or a conditional jump is a leader.
  • Any statement immediately after a jump, conditional or unconditional, is a leader.

The second rule is needed because control can enter a statement from far away. The third rule is needed because a block may contain a branch only as its last statement, so the branch ends the block and the next statement must start a new one. A target can lie above the jump, as with a goto that closes a loop, so leaders are not only forward.

Building blocks and flow-graph edges

Some syllabi call this step 'partitioning the code into basic blocks'. Sort the leaders by statement number, then cut the listing at those points.

  1. List the leaders in increasing statement number.
  2. Block 1 runs from the first leader to the statement just before the second leader. Block 2 runs from the second leader to the statement before the third, and so on. The last block ends at the last statement.
  3. Draw one node per block. Add a directed edge B → C whenever C can run immediately after B.

The edge rules follow from the last statement of a block:

  • If the last statement is goto L and C is the block whose first statement is L, add B → C. There is no fall-through edge.
  • If the last statement is if … goto L, add B → C for the target block and also B → C′ for the next block in the listing, which is the fall-through when the test is false.
  • If the last statement is not a jump (an assignment, a copy, a call), add the fall-through edge B to the next block in the listing.
  • If the last statement is a return, or a jump out of the program, add no edge: the block has no successors.

B is a predecessor of C when the edge B → C exists; C is a successor of B. The entry block contains the first statement of the program and usually has no predecessors. The exit block has no successors: it ends in a return or a jump out of the program. A block ending in a conditional jump has two successors, and a block reached from two places has two predecessors.

Two levels: block by block, then across the graph

Optimization works at both levels. Inside a block the compiler can build a DAG, fold constants, and delete repeated subexpressions (see 6.3). These rewrites are safe because no jump enters or leaves the middle of the block, so the statements always run together.

Across blocks the graph shows where facts must be combined. A fact at a block boundary must hold on every edge entering that block, which is why the predecessors matter. Global data-flow analysis starts exactly here (see 6.6); loop optimization uses the same graph to find the loops (see 6.5).

A loop appears as a cycle: a path that returns to its starting block. In the worked example the edges B2 → B3 and B3 → B2 make B2 → B3 → B2 a cycle, and the loop test sits in B2. A block with two successors is a branch point; a block with two predecessors is a merge point. Drawing these edges turns a flat listing into a map of the program's control flow.

Worked example

Question. Partition this three-address code into basic blocks, draw its flow graph, and state how many times the loop body runs: 1 i = 1; 2 t1 = 4 * i; 3 if t1 > 100 goto 7; 4 A[i] = 0; 5 i = i + 1; 6 goto 2; 7 return.

  1. Leaders, by the three rules: statement 1 (first statement); statement 7 (target of the jump at 3); statement 2 (target of the goto at 6); statement 4 (immediately after the conditional jump at 3); statement 7 again (immediately after the goto at 6). The leader set is {1, 2, 4, 7}, so there are four leaders.
  2. Blocks: B1 = {1}; B2 = {2, 3}; B3 = {4, 5, 6}; B4 = {7}. There are four blocks.
  3. Edges: B1 ends in an assignment, so it falls through to B2, giving B1 → B2. B2 ends in if t1 > 100 goto 7, giving B2 → B4 on the true branch and B2 → B3 on the false fall-through. B3 ends in goto 2, giving B3 → B2. B4 ends in return, so nothing leaves it. There are four edges.
  4. Predecessors and successors: pred(B2) = {B1, B3} and succ(B2) = {B3, B4}; pred(B3) = {B2} and succ(B3) = {B2}; pred(B4) = {B2} and succ(B4) = {}. B1 is the entry block and B4 is the exit block.
  5. Loop: B2 → B3 → B2 is a cycle, so B2 and B3 form the loop.
  6. Iteration count: the test is t1 = 4 × i > 100, that is i > 25. For i = 1 to 25 the test is false, so B3 runs. At i = 26, t1 = 104 > 100 and control goes to B4. So B3 executes 25 times, and B2 executes 26 times: 25 false exits plus the final true exit.

Answer. Leaders are {1, 2, 4, 7}; the blocks are B1 = {1}, B2 = {2, 3}, B3 = {4, 5, 6}, B4 = {7}; the edges are B1 → B2, B2 → B3, B2 → B4, B3 → B2; and the loop body B3 runs 25 times.

Exam traps

  • Marking only the targets of jumps. The statement after a conditional jump is a leader even when no jump targets it, because the branch must end the block.
  • Assuming every jump target lies below the jump. A backward goto that closes a loop makes an earlier statement a leader.
  • Forgetting that an unconditional goto has exactly one successor (its target) and no fall-through edge.
  • Counting statement 3's test as part of the loop body. The test runs one more time than the body; here 26 tests against 25 executions of B3.

Understand Why does a conditional jump produce two successors but an unconditional goto only one? 3 marks

A conditional jump can either take the branch or fall through, so control reaches the target block or the next block. An unconditional goto always goes to its target, so fall-through is impossible.

Analyze A block has two predecessors. What does that tell you about the program's control flow, and why does it matter for optimization? 5 marks

Control reaches the block from two different places, so it is a merge point: an if-join or the top of a loop. A fact placed before the block must hold on both incoming edges, otherwise an optimization that assumes it is true would be wrong on one path.

Analyze Explain in two parts why splitting code into basic blocks helps optimization: inside a block, and across blocks. 5 marks

Inside a block, no jump enters or leaves the middle, so the statements always run in order; local rewrites such as common-subexpression elimination or constant folding are safe. Across blocks, the flow graph lists the possible jumps and merges, so the compiler can see loops and combine facts coming along different edges.

Beyond the syllabus

Not for the exam. Production compilers build a control-flow graph of basic blocks as an early internal form: LLVM's IR is a list of basic blocks joined by branches, and GCC's GIMPLE works the same way. Binary analysis tools rebuild this graph from machine code to find loops and check control-flow integrity. Fuzzers such as coverage-guided ones track which edges of the graph a test input reaches. 6.3 DAG representation of basic blocks

A basic block is straight-line code. Within it, the same expression may be computed twice, some assignments only copy a value, and some results are never used. A DAG representation of the block is a directed acyclic graph that makes these facts visible. Leaves are variables entering the block; each interior node is one operation, labelled with the statements that define it. Compilers use it to remove repeated computation, propagate copies and drop dead statements before generating target code.

You need 6.2 Basic blocks and flow graphs for the basic block, and Unit 4's syntax trees and DAGs for expressions.

Building the DAG

Process the statements of the block in order. Keep a table that maps each name to the node that currently holds its value.

  1. For a statement x = y op z, find the leaves or nodes for y and z. Create an interior node labelled op with those two children in that order. Give the node the statement number of x = y op z. Record x as a label on the node.
  2. Before creating the node, look for an existing node with the same operator and the same ordered children. If it exists, add x as another label on that node. Do not create a second node. That merge is one common subexpression removed.
  3. For a copy x = y, create no node. Add x as a label on the node of y. The value is not computed again.
  4. For an array assignment a[i] = y, treat the array as changed. Later reads of a must not reuse an earlier node for a, because a[i] and a[j] may name the same cell.

A leaf can carry several variable names if copies put them there. An interior node can carry several statement numbers. Every edge points from an operand to the operation that uses it, so the graph has no cycles.

Merging, copies and array kills

Merging is strict. Two nodes merge only when the operator is the same and the ordered children are the same. a − b and b − a stay separate. a + b and b + a also stay separate under this rule; an implementation may canonicalise commutative operands, but the safe textbook rule is ordered children.

A copy x = y adds x as a label to the node of y. It creates no interior node. If x is later used, it reads the same value. Copy assignments are cheap to remove when the source y is not changed before the use.

Deadness is local. A node with no parent and no live label at block exit is dead. A variable redefined before use kills its earlier label.

An array assignment a[i] = y changes the array. It kills earlier nodes that read or write a. A later a[j] cannot reuse them, because i and j may be equal at run time. Only a proof that the indices differ allows reuse.

Reading optimisations and limits

Common subexpressions: a node with labels t1 and t2 on the same plus node was computed once. Later uses read one value.

Copies: a label added by x = y marks x as another name for y. If y is unchanged before a use of x, replace that use with y. The copy often becomes dead.

Dead code: a node with no parent whose labels are not live at exit can be removed, along with the statements that computed it. Removal is safe only if those statements have no side effects.

Reordering: the DAG forgets statement order for independent operations. You may reorder pure arithmetic. Do not reorder calls, stores, array writes or loads that may fault; their order can change behaviour.

The DAG is local. It sees one basic block. Facts that cross blocks, such as a value available at the start of a loop, need global analysis (see 6.6).

Worked example

Question. For the basic block t1 = a + b; t2 = a + b; t3 = t1 * c; d = t3; e = t2 − d, draw the DAG. Then state the total number of nodes, the number of interior nodes, the number of common subexpressions removed and the number of copy assignments.

  1. Leaves: a, b, c. These are three nodes.
  2. t1 = a + b creates a + node with children a and b, labelled t1.
  3. t2 = a + b finds the same operator and ordered children. Merge: add t2 to the + node. Common subexpressions removed = 1.
  4. t3 = t1 * c uses the + node for t1. Create a * node with children + and c, labelled t3.
  5. d = t3 is a copy. Add d as a label to the * node. No new node. Copy assignments = 1.
  6. e = t2 − d uses the + node for t2 and the * node for d. Create a − node with children + and *, labelled e.
  7. Count: 6 total nodes = 3 leaves + 3 interior nodes (+ , * , −). Interior nodes = 3. Common subexpressions removed = 1. Copy assignments = 1.

Answer. The DAG has 6 nodes in total, with 3 interior nodes. It removes 1 common subexpression and shows 1 copy assignment.

Exam traps

  • Do not merge a − b with b − a: subtraction is not commutative, and the ordered children differ.
  • Do not forget that an array assignment a[i] = y kills earlier nodes for the array a; a later a[j] may read the same cell.
  • A copy x = y adds a label to an existing node; it is not a new computation, so do not count it as an interior node.
  • The DAG is within one basic block; it does not prove a value available across blocks or loop iterations.
  • Reordering is safe only for operations without side effects; calls, stores and array writes must keep their order.

6.4 Principal sources of optimization

Optimizers do not invent a clever trick for each statement. They apply a small set of repeated sources: work that is repeated, work that is useless, work that is known in advance, and work that is too costly. Each source names one pattern in the intermediate code and one rewrite that removes it. Learn the eight sources and you can spot them in any program and check whether a compiler found them. These eight are the classical core that most optimizers contain; other transformations, such as inlining and loop unrolling, exist and build on them. They are the raw material for the loop work in 6.5.

You need: 6.2 and 6.3 for basic blocks and block DAGs, and the three-address code of Unit 4, Syntax-Directed Translation and Intermediate Code.

Two labels for every source

A source of optimization is a pattern plus a rewrite. Every source gets two labels, and exam questions ask for both.

A machine-independent source looks only at the intermediate code, so any target benefits. Constant folding, constant propagation, common subexpression elimination, copy propagation, dead-code elimination and algebraic simplification are machine-independent.

A machine-dependent source uses facts about the target. Strength reduction is the standard example: a multiply becomes a shift or an add only if that is cheaper on that machine. Register allocation and instruction selection are also machine-dependent.

A local optimization works inside one basic block, and the block DAG of 6.3 is enough to drive it. A global optimization needs facts that cross block boundaries, which come from data-flow analysis in 6.6.

Practical order inside a compiler: machine-independent local passes, then global passes, then machine-dependent work during code generation.

The eight sources, one by one

These eight cover what the syllabi call the principal sources. Each definition below is followed by one rewrite.

  • Common subexpression elimination (CSE): if the same expression is evaluated twice and no operand changes in between, evaluate it once. a = b + c; d = b + c becomes d = a.
  • Copy propagation: after e = d, replace later uses of e by d until e or d is redefined. For example f = e + 1 becomes f = d + 1, and you stop at the first redefinition of e or d. Note that e = d * 1 → e = d is algebraic simplification, not copy propagation.
  • Dead-code elimination: delete an assignment whose target is never read afterwards. If y is never used, y = 6 goes.
  • Constant folding: evaluate a constant expression at compile time. 2 * 3 becomes 6.
  • Constant propagation: put the known value of a variable in place of the variable. x = 6; y = x + 0 becomes y = 6 + 0.
  • Algebraic simplification: apply identities of the type. x + 0 becomes x, x * 1 becomes x, x - 0 becomes x.
  • Strength reduction: replace a costly operation by a cheap one. i * 2 becomes i + i.
  • Code motion: move an expression to a place where it runs fewer times, usually out of a loop. The loop-specific forms are in 6.5.

Safety: the results must not change

A transformation is function-preserving when the new code gives the same outputs and the same side effects as the old code for every input. Function-preserving and semantics-preserving mean the same thing; use either name.

  1. List what each statement reads and writes.
  2. For CSE, confirm that no operand was redefined between the two evaluations.
  3. Keep every call, every input or output, and every assignment to a volatile name; they have effects beyond their result.
  4. Check the type before an algebraic identity: x * 0 becoming 0 is false for floating point, where 0 * ∞ is not 0.
  5. Recompute the block DAG before and after, and compare the surviving outputs.

The word optimization is loose. A compiler reduces cost by a heuristic; it rarely finds the true optimum, and it must stop after a bounded number of passes.

Worked example

Question. A basic block contains seven statements: 1 x = 2 * 3 2 y = x + 0 3 a = b + c 4 d = b + c 5 e = d * 1 6 f = i * 2 7 print(a, e, f) Apply constant folding, constant propagation, common subexpression elimination, copy propagation, algebraic simplification, strength reduction and dead-code elimination. Show the block after each pass and state how many statements remain.

  1. Constant folding: 2 * 3 is a constant expression, so statement 1 becomes x = 6.
  2. Constant propagation: x holds 6, so y = x + 0 becomes y = 6 + 0.
  3. Constant folding again: 6 + 0 is constant, so statement 2 becomes y = 6.
  4. Common subexpression elimination: statements 3 and 4 both compute b + c, and neither b nor c is redefined between them. Replace statement 4 by d = a.
  5. Algebraic simplification: d * 1 is d, so statement 5 becomes e = d.
  6. Copy propagation: d is a copy of a, so every use of d becomes a use of a, giving e = a.
  7. Strength reduction: i * 2 costs a multiply; i + i costs an add, so statement 6 becomes f = i + i.
  8. Dead-code elimination: y is never read after statement 2, so delete y = 6. With y gone, x = 6 is never read, so delete x = 6. After copy propagation d is never read, so delete d = a as well. Nothing else is dead: a, e and f are printed.
  9. Count the statements: the block started with 7 and now has a = b + c, e = a, f = i + i, print(a, e, f), that is 4.
  10. Final block: a = b + c; e = a; f = i + i; print(a, e, f). Same printed values as the original block, so every step was function-preserving.

Answer. Final block: a = b + c; e = a; f = i + i; print(a, e, f). The constants folded are x = 6 and y = 6, both dead, and the block shrinks from 7 statements to 4.

Exam traps

  • A repeated expression stops being a common subexpression if any variable inside it is reassigned between the two evaluations. Recheck the operands before you reuse.
  • Dead-code elimination must not delete calls, input or output, or assignments to volatile names, because their effect survives even when the result is unused.
  • Algebraic simplification is not always safe for floating point: x * 0 → 0 fails when x is NaN or infinity, and x + 0 → x fails at x = −0.0, because −0.0 + 0.0 gives +0.0. The compiler may apply these rewrites only when it knows the value is finite and its zero sign does not matter.
  • Constant propagation is unsafe if the variable is reassigned on a path between the definition and the use; a constant known in one block is not known everywhere until data-flow analysis proves it.
  • Function-preserving and semantics-preserving are the same property. An answer that lets an optimization change output on a defined program loses marks.

Check yourself

Remember Name any three machine-independent sources of optimization. 2 marks

Constant folding, common subexpression elimination and dead-code elimination (constant propagation, copy propagation and algebraic simplification are also correct).

Understand Why is strength reduction called machine-dependent while dead-code elimination is machine-independent? 3 marks

Strength reduction replaces an operation by a cheaper one on a particular target, so it needs the target's instruction costs and timings. Dead-code elimination only needs to know which results are never read, which is a property of the intermediate code alone.

Apply For this block: a = 4; b = a * a; c = a * a; d = b + c; print(d), apply constant propagation with folding, common subexpression elimination, copy propagation and dead-code elimination. Give the final block and the value printed. 4 marks

a = 4 is known, so b = 16 and c = 16 by folding. CSE gives c = b, and copy propagation turns d = b + c into d = b + b. Final block: b = 16; d = b + b; print(d). After the folding, a = 4 is dead, and c is dead after CSE. b is 16, so d = 32 and the printed value is 32.

Analyze A block has e = d * 1, then d = d + 1, then f = e. Can copy propagation replace f = e by f = d? Justify. 4 marks

No. e holds the old value of d, and d was redefined after the copy. Replacing f = e by f = d would read the new value and change the result, so the transformation is not function-preserving.

Apply Simplify z = (x * 1) + 0 by algebraic simplification and state when the second step is unsafe for floating point. 3 marks

x * 1 gives x, then x + 0 gives x, so the statement becomes z = x. The first step is safe for floating point except that a signalling NaN is quieted. The second step fails at x = −0.0, because −0.0 + 0.0 gives +0.0, so the compiler may apply x + 0 → x only when it knows the sign of zero does not matter.

Understand State the difference between constant folding and constant propagation with one example each. 2 marks

Constant folding evaluates an expression whose operands are already constants, for example 2 * 3 becomes 6. Constant propagation replaces a variable by a constant value it is known to hold, for example y = x + 0 becomes y = 6 + 0 when x is known to be 6.

Beyond the syllabus

6.5 Function-preserving transformations and loop optimization

An optimizer may rewrite a program only if the program still does the same thing. A function-preserving transformation keeps every output, side effect and termination the same while making the code smaller or faster. Common subexpression elimination, constant folding, copy propagation, dead-code elimination and strength reduction are the everyday examples. Loops repay this work best, because a loop body runs many times. This chapter applies the transformations inside loops through loop-invariant code motion and strength reduction, then finishes with peephole optimization, the small-window cleanup over target instructions.

You need: 6.4 for the list of optimization sources, 6.2 for flow graphs and loops, and Unit 4 for three-address code.

Function-preserving transformations

A function-preserving transformation rewrites a program without changing what an observer can see: the same outputs, the same side effects in the same order, and the same termination. The optimizer may make the code faster or smaller, but it may not change the meaning. Every rule below carries a proof obligation: on every path where the original ran, the new code computes the same values.

  • Constant folding: 2 * 3 * 4 becomes 24 at compile time.
  • Constant propagation: after x = 5, the use in y = x + 1 becomes y = 6.
  • Copy propagation: after b = a, the use in c = b + 1 becomes c = a + 1.
  • Common subexpression elimination: if b * c is computed twice with no assignment to b or c between, the second computation reuses the first result.
  • Dead-code elimination: delete x = 10 when x is never read again, provided the right side cannot fail or call a function.
  • Algebraic simplification and strength reduction: x * 1 becomes x, x + 0 becomes x, and x * 4 becomes x << 2 for a non-negative integer x.

Each rule needs a local proof. The DAG of 6.3 gives common subexpression elimination inside one block; copy propagation needs the copy to reach the use with no redefinition on the way. A rewrite is illegal if it drops a side effect, swaps the order of two side effects, or moves an operation that can trap (division by zero, null dereference, array bounds) to a place where it runs when the original did not.

Loop optimization

A loop body that runs a thousand times repays any saving a thousand times. Loop optimization first finds the loop in the flow graph, then applies the function-preserving rules where they pay most.

  1. Find the loop blocks and the header in the flow graph.
  2. Mark an expression invariant when every operand is a constant or is defined only outside the loop.
  3. Create a preheader: a new block on the single edge entering the header.
  4. Move the invariant expression to the preheader and replace the loop use by the new temporary.
  5. Check that the new definition dominates all uses, and that the move cannot add a trap on a path where the loop runs zero times.

An induction variable changes by a fixed amount each iteration, such as i = i + 1. If the body uses i * 4, introduce t = 4 * i before the loop and t = t + 4 at the end of the body; the multiply disappears. This is induction-variable strength reduction. Induction-variable elimination then deletes i if it is dead. The iteration count must stay the same, so the bound is scaled too:

N = (t_last − t_first) ÷ step + 1

N is the number of iterations; t_first and t_last are the first and last values of the induction variable; step is the constant added each turn.

Unrolling copies the body k times and steps the counter by k; it cuts branch overhead and exposes independent work, at the cost of code size. Jamming (fusion) puts two loops with the same trip count into one body, saving loop overhead and improving cache reuse. Jamming is legal only when the two bodies do not write what the other reads. The hoist of x * y is invalid if x or y is assigned inside the loop.

Peephole optimization

A peephole optimizer looks at a window of two to five target instructions, recognises a pattern, and replaces it with a shorter or faster sequence. It runs after code generation and needs no flow graph, so it is fast and local.

  • Store then load of the same address: drop the load and keep the register value.
  • Jump to a jump: goto L1 where L1 holds goto L2 becomes goto L2, after retargeting every other jump to L1.
  • Unreachable code: instructions after an unconditional jump with no label on them are removed.
  • Constant folding on target instructions: MOV R1, 2; ADD R1, 3 becomes MOV R1, 5.
  • Redundant push and pop of the same register in a pair: delete both.

The window is small, so peephole misses facts that need the whole flow graph; global redundancy is the job of 6.6. It must also respect labels and branches that enter the middle of a window, because such a branch can make an instruction reachable that the window alone thinks is dead.

Worked example

Question. The loop below stores a constant into every fourth element of A. Apply loop-invariant code motion, induction-variable strength reduction and induction-variable elimination. Use x = 3 and y = 7. Give the transformed code, the values t1 takes, the number of iterations, and the sum of the stored values. for i = 0 to 99 do { t1 = 4 * i; t2 = x * y; A[t1] = t2 }

C program.

#include <stdio.h>
int main(void) {
    int x = 3, y = 7, t2 = x * y, t1 = 0, sum = 0, n = 0;
    while (t1 <= 396) { sum += t2; n++; t1 += 4; }
    printf("%d %d %d\n", t2, n, sum);
    return 0;
}
  1. Find invariants: x and y are not assigned in the loop, so t2 = x * y = 3 * 7 = 21 is invariant.
  2. Create a preheader on the edge into the loop header and move the invariant there: t2 = 21, computed once.
  3. Strength-reduce t1 = 4 * i. Introduce an induction variable t1 that starts at 4 * 0 = 0 and adds 4 each turn.
  4. Scale the bound: i runs from 0 to 99, so t1 runs 0, 4, 8, ..., 4 * 99 = 396. The test becomes t1 ≤ 396.
  5. Eliminate i: after step 3 nothing reads i, so delete i and its increment.
  6. Count iterations: N = (396 − 0) ÷ 4 + 1 = 100. Each turn stores 21, so the sum is 100 × 21 = 2100.
  7. Final code: t2 = 21; t1 = 0; while t1 ≤ 396 do { A[t1] = t2; t1 = t1 + 4 }.

Exam traps

  • Hoisting x * y is wrong when x or y is assigned inside the loop, because the preheader computes a stale value.
  • Hoisting a division or an array access is wrong when the loop may run zero times and the operation can trap.
  • Strength reduction must scale the bound too: t1 ≤ 396, not t1 ≤ 99, or the loop runs 25 times instead of 100.
  • Common subexpression elimination across a call or a pointer write is unsafe, because the call may change the value.
  • Dead-code elimination must keep an expression with a side effect, such as a function call or a faulting division.

6.6 Global data flow analysis

Global data-flow analysis finds a fact at every basic-block boundary, not just inside one straight-line run. It sets up equations: a meet operator combines facts from paths, and each block has a transfer function that changes the fact. The equations are solved by iteration over the flow graph until values stop changing. Compilers use the result to fold constants, remove repeated expressions, delete dead assignments and place loop invariants. This chapter links the block graph from 6.2 to the optimizations of 6.4 and 6.5.

You need: flow graphs and basic blocks from Chapter 6.2, and set union, intersection and difference.

Facts, meet operators and transfer functions

Global data-flow analysis computes a property at every block boundary. A fact is may if it can be true on some path, and must if it is true on every path. A forward analysis moves facts from entry to exits. A backward analysis moves facts from exits to entry.

For reaching definitions, a definition d of a variable reaches a point if some path from d to that point does not redefine the variable. A block B has two sets. gen[B] contains definitions inside B that reach the end of B. kill[B] contains every definition in the whole flow graph of a variable that B redefines, including definitions in later blocks.

IN[B] = ∪ OUT[P] over predecessors P; OUT[B] = gen[B] ∪ (IN[B] − kill[B])

IN[B] is the fact on entry to block B; OUT[B] is the fact on exit; gen[B] and kill[B] are the block's transfer sets; P ranges over predecessor blocks.

The meet operator is union because one path is enough. For a must analysis such as available expressions, the meet operator is intersection: IN[B] = ∩ OUT[P]. Available expressions are expressions computed on every path to B and not killed before the end of B.

Solving the equations: iterative and worklist

The simple solver starts with every IN and OUT set empty for reaching definitions. It walks the blocks in a fixed order, recomputes IN from predecessor OUT sets, then OUT from IN, gen and kill. If any set changes, it makes another pass. It stops when a full pass changes nothing. The sets only grow, and the flow graph has finitely many definitions, so the process ends.

  1. Put every block on a worklist for the worklist solver.
  2. Remove one block B and recompute IN[B] and OUT[B].
  3. If OUT[B] changes, add every successor of B to the worklist for a forward analysis.
  4. Do not add a block already on the list.
  5. Stop when the worklist is empty.

This worklist version is the efficient data-flow algorithm some syllabi mention. The same pattern handles other analyses. Live variables is backward and may: IN[B] = use[B] ∪ (OUT[B] − def[B]) and OUT[B] = ∪ IN[S] over successors S. Available expressions is forward and must: IN[B] = ∩ OUT[P], OUT[B] = gen[B] ∪ (IN[B] − kill[B]). Here gen[B] is the expressions computed in B and not killed before the end of B.

From data-flow facts to optimization

Reaching definitions build def-use chains. A def-use chain links a definition d to every use that d may reach. The reverse, a use-def chain, lists the definitions that may reach one use. These chains are the input to global optimizations.

Constant propagation: if a use has exactly one reaching definition and that definition assigns a literal, replace the use by the literal. In the worked example x has two reaching definitions at d4, so x is not constant. Common subexpression elimination: if an expression is available at a point, its earlier value can be reused. Available expressions give the cross-block condition. Live variables show that a definition has no later use, so dead-code elimination removes it.

A conservative solution keeps every fact that might be true. It may miss an optimization but never changes the program's result. Optimizers prefer this. The transformations themselves are in Chapter 6.4 and Chapter 6.5.

Worked example

Question. A flow graph has blocks B1, B2, B3. B1 contains d1: x = 1 then d2: y = 2. B2 contains d3: x = 3. B3 contains d4: z = x + y. Edges are B1→B2, B1→B3, B2→B3. Compute gen and kill for each block. Compute IN and OUT reaching-definition sets by iteration. Is x a constant at d4?

  1. Definitions: d1 defines x, d2 defines y, d3 defines x, d4 defines z.
  2. Kill sets contain every definition of the same variable in the whole graph: kill[B1] = {d3}, kill[B2] = {d1}, kill[B3] = {}.
  3. Gen sets: gen[B1] = {d1,d2}, gen[B2] = {d3}, gen[B3] = {d4}.
  4. Start: IN[B1]=IN[B2]=IN[B3]={} and OUT[B1]=OUT[B2]=OUT[B3]={}.
  5. Pass 1, B1: no predecessors, so IN[B1]={}. OUT[B1]={d1,d2} ∪ ({} − {d3}) = {d1,d2}.
  6. Pass 1, B2: predecessor B1, so IN[B2]=OUT[B1]={d1,d2}. OUT[B2]={d3} ∪ ({d1,d2} − {d1}) = {d2,d3}.
  7. Pass 1, B3: predecessors B1 and B2, so IN[B3]=OUT[B1] ∪ OUT[B2]={d1,d2} ∪ {d2,d3}={d1,d2,d3}. OUT[B3]={d4} ∪ ({d1,d2,d3} − {})={d1,d2,d3,d4}.
  8. Pass 2 repeats the same values, so no set changes. The solution is final.
  9. At d4, x has two reaching definitions: d1 gives x=1 and d3 gives x=3. Therefore x is not a constant at d4. y has only d2.

Answer. IN/OUT are {} / {d1,d2} for B1, {d1,d2} / {d2,d3} for B2, and {d1,d2,d3} / {d1,d2,d3,d4} for B3; their sizes in order IN B1, OUT B1, IN B2, OUT B2, IN B3, OUT B3 are 0, 2, 2, 2, 3, 4, and x is not constant at d4 because d1 and d3 both reach it.

Exam traps

  • Use union for reaching definitions and intersection for available expressions. Swapping them loses facts or invents facts.
  • The kill set contains every definition of a variable in the whole flow graph, not just definitions seen before the block.
  • May facts use union over paths; must facts use intersection. Reaching definitions is may, available expressions is must, and live variables is backward may.
  • Direction matters: reaching definitions and available expressions are forward; live variables is backward. Reversing predecessors and successors gives wrong equations.
  • A conservative solution may keep extra facts. It is safe for optimization but can block a transformation; it is not the same as an incorrect solution.

Glossary

Basic block
A maximal straight-line sequence of statements with one entry and one exit.
Code motion
Moving an expression to a place where it is executed less often.
Common subexpression
An expression already computed whose operands have not changed.
Constant folding
Computing constant expressions during compilation instead of at run time.
Constant propagation
Replacing a variable use by a constant known to reach that use.
Copy propagation
Replacing a use of a copied variable by the original variable.

A directed acyclic graph used for a basic block; nodes are values or operations and edges show operand use.

A computation whose result is never used on any possible execution path.

A compiler table entry used by a simple code generator to track register contents or variable locations.

A stable data-flow solution reached when another iteration changes no block fact.

A directed graph with basic blocks as nodes and control-transfer edges.
Function-preserving transformation
A program rewrite that keeps the same input-output behavior for all inputs.
Leader
The first statement of a basic block.
Live variable
A variable is live at a point if some path from that point uses its current value before redefining it.
Loop-invariant computation
An expression inside a loop whose value does not change across loop iterations.
Peephole optimization
A local rewrite of a small instruction window into a cheaper equivalent sequence.
Predecessor
A block with an edge into the given block.
Register allocation

Choosing the exact register for each allocated value.
Strength reduction
Replacing a costly operation by a cheaper equivalent operation.
Successor
A block with an edge from the given block.
Target instruction
A machine instruction of the chosen target architecture.
Three-address code
Intermediate code with at most one operator per instruction and explicit temporaries.
Transfer function
A function that maps data-flow facts at block entry to facts at block exit.
