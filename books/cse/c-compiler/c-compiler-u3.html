3.1 Shift-reduce parsing and handle pruning

Bottom-up parsing builds a parse tree from the leaves up. A shift-reduce parser keeps a stack and a remaining input string, both ending in $, the end marker. It shifts the next token onto the stack or reduces a handle, the right-hand side that reverses one step of a rightmost derivation. This model is the base of LR parsers and parser generators such as YACC. It is also the idea behind small expression evaluators in calculators and spreadsheet cells.

You need Unit 2: context-free grammars, derivations, rightmost derivations and parse trees.

The shift-reduce machine

A configuration has two parts: the stack and the remaining input. The stack holds grammar symbols and starts with $. The input holds tokens and ends with $, the end marker. The parser repeats one of four actions.

  • shift: push the next input token; move the input forward.
  • reduce: the top k symbols match the right-hand side X1...Xk of A → X1...Xk; pop k symbols and push A.
  • accept: the stack is $S and the input is $, where S starts the grammar.
  • error: no action fits.

Without a table or precedence rule the parser is nondeterministic. More than one action can fit. A table-driven LR parser removes this choice with states; see 3.2. In a teaching shift-reduce parser you choose the action that continues the reverse rightmost derivation.

The next action depends on the handle, not on the whole stack. The handle is the part to replace. The next section defines it.

Handles and handle pruning

A right sentential form is any string in a rightmost derivation. The handle is the substring that matches the right-hand side of the production used in the last step of that rightmost derivation. Replacing the handle by the left-hand side gives the previous right sentential form.

Handle pruning is repeating this replacement until only the start symbol remains. Some syllabi call handle pruning 'reduction of the right sentential form'. In a shift-reduce parser the handle sits at the top of the stack. Among the symbols already shifted, it is the rightmost substring that can be reduced next.

Not every right-hand side is a handle. It must be the right-hand side of the production that the reverse rightmost derivation actually uses. A matching substring in another position may reduce to a valid sentential form but not the previous one. Example: in id + id * id the first handle is the left id, because the reverse rightmost derivation starts by undoing F → id there. Reducing the right id first would not follow that derivation.

Operator precedence and conflicts

An operator precedence grammar has no ε-production, no right-hand side with two adjacent nonterminals, and no two productions with the same right-hand side. For nonterminal A and terminal a, a is in LEADING(A) if A ⇒* a β, or A ⇒* B a β for some nonterminal B and string β. Symmetrically, a is in TRAILING(A) if A ⇒* β a, or A ⇒* β a B. Here β is any string of grammar symbols.

For E → E + T | T, T → T * F | F, F → id, LEADING(F) = TRAILING(F) = {id}; LEADING(T) = TRAILING(T) = {*, id}; LEADING(E) = TRAILING(E) = {+, *, id}. The parser uses three relations between terminals. a ⋖ b means shift: some production has a immediately followed by nonterminal B and b is in LEADING(B). a ⋗ b means reduce: a is in TRAILING(B) and some production has B immediately followed by b. a =· b if some production has a and b adjacent, or has a B b with exactly one nonterminal B between them.

Exam traps

  • A handle is not just any right-hand side. It must be the production used in the reverse rightmost derivation; a matching substring elsewhere is not the handle.
  • Without a table or precedence rule, a shift-reduce parser is nondeterministic. A shift and a reduce may both be possible at the same configuration.
  • LEADING and TRAILING sets contain terminals only. Do not put E, T or F into them.
  • Shift/reduce means one token can be shifted or one handle reduced. Reduce/reduce means two different productions can reduce the same handle. Do not swap the names.
  • Accept needs stack $S and input $. Seeing $ alone is not enough.

3.2 LR(0) items, closure and LR parsing

An LR parser reads tokens from left to right and builds a rightmost derivation in reverse. To do this it must remember which production is being recognised and how much of that production is already on its stack. An LR(0) item stores exactly that: a production with a dot showing the current position. Closure and goto turn a grammar into a finite automaton of item sets. The parser uses this automaton as a table. Parser generators such as YACC build such tables from a grammar, so the same idea powers real compilers.

You need: Chapter 3.1 for shift-reduce parsing and handles, and Unit 2 for context-free grammars, derivations and parse trees.

LR(0) items and closure

An LR(0) item is a production with a dot (.) in its right side: A → α . β. A is a nonterminal; α and β are strings of grammar symbols. The dot separates symbols already matched (α) from symbols still expected (β). If the dot is at the end, A → α ., the production is complete and can be reduced. A dot before a terminal calls for a shift. A dot before a nonterminal may start that nonterminal's productions.

Closure completes an item set. For a set I, closure(I) is the smallest set containing I and following this rule: if A → α . B β is in the set and B → γ is a production, add B → . γ. Repeat until no new item appears. The dot does not move.

Add the augmented production S' → S. S' is a new start nonterminal; S is the original start symbol. For S → C C, C → c C | d, start from S' → . S. Closure adds S → . C C, then C → . c C and C → . d. This is state I0.

Goto and the canonical collection

Goto(I, X) moves the dot past one symbol X. Take every item in I with X just after the dot, make a new item with the dot after X, then take closure: goto(I, X) = closure({ A → α X . β | A → α . X β ∈ I }). If no item has X after the dot, goto is empty. Closure adds items; goto moves the dot one place.

Build the canonical collection this way. Start with I0 = closure({S' → . S}). For every state and grammar symbol X, compute goto(I, X). If the result is nonempty and new, make it a new state. Repeat. Finitely many items means this stops.

For the example, the states are I0 to I6. I0 is S' → . S, S → . C C, C → . c C, C → . d. I1 is S' → S .. I2 is S → C . C, C → . c C, C → . d. I3 is C → c . C, C → . c C, C → . d. I4 is C → d .. I5 is S → C C .. I6 is C → c C .. The figure shows the transitions.

ACTION, GOTO, and conflicts

ACTION maps state and terminal to shift, reduce, accept or error. GOTO maps state and nonterminal to a state. Suppose state i has a shift item A → α . a β for terminal a, and goto(Ii, a) = Ij. Then ACTION[i, a] = shift j, written s j. The parser pushes a and state j. If state i has a complete item A → α . with A ≠ S', then ACTION[i, a] = reduce A → α, written r j, for every terminal a and for $. LR(0) ignores the next token in a reduce. If the item is S' → S ., ACTION[i, $] = accept. Blank means error. For nonterminal A, GOTO[i, A] = j when goto(Ii, A) = Ij.

LR(0) tables can conflict. A shift/reduce conflict means one cell wants shift and reduce; it happens when a state has a complete item and a shift item on the same terminal. A reduce/reduce conflict means two complete items give two reductions for the same terminal. The example has no conflicts: states I0, I2, I3 shift; I4 reduces C → d; I5 reduces S → C C; I6 reduces C → c C; I1 accepts.

Exam traps

  • Closure adds items; it never moves the dot. Goto moves the dot past exactly one symbol and then closes. If you close after moving several symbols, the states are wrong.
  • A dot before a nonterminal starts closure. A dot before a terminal causes a shift; it does not add productions.
  • In LR(0), a reduce item is reduced for every terminal and $, not only for FOLLOW(A). That is why LR(0) tables conflict; SLR fixes this in Chapter 3.3.
  • The completed item S' → S . gives accept on $, not a reduce action. Never reduce by the augmented start production.
  • GOTO columns exist only for nonterminals; ACTION columns only for terminals. A shift entry is s j, a reduce entry is r j; blank means error, not state 0.

3.3 Simple LR (SLR) parsing tables

The SLR parser is an LR parser that adds one lookahead token to the LR(0) automaton. An LR(0) item with the dot at the end says “reduce now” but does not say on which input. SLR fixes this: a production A → α is reduced only when the next token is in FOLLOW(A). That single check removes many conflicts and keeps tables small. SLR tables drive simple bottom-up parsers and prepare the ground for the stronger LR(1) and LALR methods.

You need: Chapter 3.2 for LR(0) items, closure and goto, and the FIRST and FOLLOW sets from Unit 2.

The FOLLOW check in SLR

An LR(0) item with the dot at the end, such as T → id., records that a handle may be on top of the stack. The LR(0) table has no lookahead, so it puts a reduce action in every terminal column. That creates conflicts. In the expression grammar, state I1 would both shift + and reduce E' → E on +.

SLR adds one terminal of lookahead. A reduce by A → α is allowed only when the next input token is in FOLLOW(A). FOLLOW(A) is the set of terminals that can come immediately after A in some sentential form, plus $ at the end of input.

action[I, a] = reduce A → α  when  [A → α.] ∈ I and a ∈ FOLLOW(A)

I is an LR(0) state, a is the next input terminal, A → α is a completed production, and FOLLOW(A) is the set of terminals allowed after A.

Shift entries still come from the LR(0) automaton: if goto(I, a) = J for terminal a, action[I, a] = shift J. The accept entry is action[I, $] = accept when [S' → S.] is in I. The 1 in SLR(1) means one lookahead token, not one state.

Building the SLR(1) table

  1. Augment the grammar with a new start production S' → S, where S is the original start symbol.
  2. Build the canonical collection of LR(0) item sets I0, I1, …, In using closure and goto.
  3. Compute FIRST and FOLLOW for the nonterminals. FIRST is used while computing FOLLOW; the SLR table itself uses FOLLOW.
  4. For each state I, add shift entries: if [A → α.aβ] is in I, a is a terminal, and goto(I, a) = J, set action[I, a] = shift J.
  5. For each completed item [A → α.] with A ≠ S', add action[I, a] = reduce A → α for every a in FOLLOW(A).
  6. If [S' → S.] is in I, set action[I, $] = accept.
  7. For each item [A → α.Bβ] in I with goto(I, B) = J, set goto[I, B] = J.
  8. If two actions land in one cell, the grammar is not SLR(1); report a conflict.

How the FOLLOW check fills the sample table

Read the figure as a parser table. Row I0 shifts id to state 3 and goes to E in state 1 and T in state 2. Row I1 shifts + to state 4 and accepts on $. Row I4 shifts id to state 3 and goes to T in state 5. Rows I2, I3 and I5 are reduce rows.

State I1 has two items: E' → E. and E → E. + T. On lookahead +, LR(0) wants both to reduce E' → E and to shift +. SLR checks FOLLOW(E') = {$}; the reduce is allowed only on $, so + shifts. On $ it accepts. The same FOLLOW check removes the false reduce of E → T on id in state I2.

A grammar that still has a conflict after this check is not SLR. Canonical LR(1) adds item-specific lookaheads in Chapter 3.4.

Exam traps

  • SLR looks at FOLLOW of the left-hand side of the reduce production, not at a lookahead attached to an LR item. Writing reduce under every terminal after the dot is an LR(0) mistake.
  • A completed item for the augmented start E' → E gives accept only on $, not a reduce on every terminal.
  • The 1 in SLR(1) means one lookahead token. It does not mean one state, one production or one symbol of stack.
  • A grammar can be SLR even when its LR(0) table has a conflict; the FOLLOW restriction can delete the conflicting reduce entry.
  • If a shift/reduce or reduce/reduce conflict remains after the FOLLOW check, the grammar is not SLR. Do not choose one action by intuition.

3.4 Canonical LR(1) parsers

Canonical LR(1) parsing removes a weakness of SLR. SLR decides a reduction by FOLLOW of the left-hand side, a set that is often too wide. An LR(1) item carries one lookahead terminal, so a reduction is allowed only when that exact terminal comes next. This extra detail lets the parser handle grammars that SLR rejects, such as assignment with pointers. Some syllabi call it CLR or canonical LR. Parser generators use the same idea, though many merge states to save space.

You need LR(0) items and closure, SLR tables, and FIRST sets from Unit 2.

The LR(1) item and its closure

An LR(1) item is a pair [A → α . β, a]. A → αβ is a production; the dot shows how much of the right side the parser has matched; a is one terminal called the lookahead. The item means: we are trying to complete A → αβ, and after A the next input symbol must be a. For example, [S → L . = R, $] says the parser has matched L, expects = next, and after the whole S the input must end ($).

Closure adds items until no new ones appear. If [A → α . B β, a] is in I and B → γ is a production, then for every terminal b in FIRST(β a) add [B → . γ, b]. FIRST(β a) is FIRST of the string β followed by a; if β derives ε, then a itself is included. This is the only place lookaheads are created. Do not use FOLLOW(B).

  1. Start with closure({ [S' → . S, $] }).
  2. For each set I and each grammar symbol X, compute goto(I, X) as the closure of all [A → α X . β, a] such that [A → α . X β, a] is in I.
  3. Add every new set; repeat until no new sets appear.
  4. Record each goto as an edge of the automaton.

The LR(1) parsing table

For each state i and terminal a, fill ACTION. If [A → α . a β, b] is in I_i and goto(I_i, a)=I_j, set ACTION[i,a] = shift j. If [A → α ., a] is in I_i, set ACTION[i,a] = reduce A→α, unless A = S'. If [S' → S ., $] is in I_i, set ACTION[i,$] = accept. For each nonterminal A, if goto(I_i, A)=I_j, set GOTO[i,A]=j. A blank entry is an error.

Because the reduce action is tied to one lookahead, the table can have fewer conflicts than SLR. The cost is more states: canonical LR(1) does not merge states that differ only in lookaheads. Two states with the same LR(0) core but different lookahead sets are separate. This is why the automaton can be large. The parsing algorithm itself is the same as in Chapter 3.2: use the stack, consult ACTION, shift or reduce, and follow GOTO after a reduce. LALR (Chapter 3.5) merges such states and keeps most of the power.

Where the conflict goes

In the SLR table, the state with [S → L . = R] and [R → L .] reduces R → L on every terminal in FOLLOW(R). For this grammar FOLLOW(R) = {=, $}. The terminal = also calls for a shift, so the state has a shift/reduce conflict on =. In the LR(1) table the same state contains [S → L . = R, $] and [R → L ., $]. The reduce entry is written only under $, not under =. The shift on = and the reduce on $ are different columns, so the conflict is gone. The lookahead narrows the reduce action to the context that actually produced the item. The same lookahead is propagated by closure, so the table entry is not guessed after the fact.

Worked example

Question. Grammar: S → L = R | R, L → * R | id, R → L. (a) Compute FIRST and FOLLOW. (b) Show the SLR shift/reduce conflict in the state with S → L . = R and R → L . (c) Give the LR(1) items for that state and the ACTION entries, and count conflicts.

  1. FIRST(L) = {*, id}. FIRST(R) = {*, id}. FIRST(S) = FIRST(L) ∪ FIRST(R) = {*, id}.
  2. FOLLOW(S) = {$}. From S → L = R, = ∈ FOLLOW(L) and $ ∈ FOLLOW(R). From R → L, FOLLOW(R) ⊆ FOLLOW(L), so $ ∈ FOLLOW(L). From L → * R, FOLLOW(L) ⊆ FOLLOW(R), so = ∈ FOLLOW(R). Hence FOLLOW(L) = {=, $} and FOLLOW(R) = {=, $}.
  3. SLR state I2 has items S → L . = R and R → L . . ACTION on = has both shift (to the state with S → L = . R) and reduce R → L because = ∈ FOLLOW(R). ACTION on $ has reduce R → L. So I2 has 1 shift/reduce conflict, on =.
  4. LR(1) closure at the start: [S' → . S, $] adds [S → . L = R, $] and [S → . R, $]. The first adds L items with lookahead =; the second adds [R → . L, $], which adds L items with lookahead $. After goto on L, state I2 contains [S → L . = R, $] and [R → L ., $].
  5. LR(1) ACTION for I2: on = shift to the state with [S → L = . R, $]; on $ reduce R → L. No reduce entry on =. The counts are: |FIRST(S)| = 2, |FOLLOW(L)| = 2, SLR conflicts = 1, LR(1) conflicts = 0.

Answer. SLR has 1 shift/reduce conflict on = in state I2; LR(1) has 0 because R → L reduces only on $, so the grammar is LR(1) but not SLR.

Exam traps

  • Using FOLLOW(A) for reduce lookaheads is SLR, not LR(1). LR(1) uses the lookahead written in the item.
  • In closure, FIRST(β a) includes a when β can derive ε. Leaving out a loses valid reductions.
  • The lookahead is not the symbol after the dot. Shift entries use the symbol after the dot; reduce entries use the item's lookahead.
  • Canonical LR(1) keeps states with the same core and different lookaheads separate. Merging them is LALR.
  • A state may contain the same production with different lookaheads; their reduce sets must be combined in that state, not treated as a conflict with each other.

3.5 LALR parsers

LALR is a middle ground between SLR and canonical LR(1). It keeps the small LR(0)-sized automaton but adds lookahead terminals to reductions. The trick is to merge LR(1) states that have the same core, then union their lookaheads. The result is often called LALR(1), for LookAhead LR. Parser generators such as YACC use it because it is compact and handles most programming-language grammars. The cost is risk: merging can create a reduce/reduce conflict that canonical LR(1) would not have.

You need: Chapter 3.4 on canonical LR(1) items and states, plus the LR(0) automaton from Chapter 3.2.

Core of a state and the merge

An LR(1) item is [A → α . β, a]. A is the left-hand side; α and β are strings of grammar symbols; the dot shows how far parsing has moved; a is one lookahead symbol: a terminal or the special end-of-input marker $. The core of an LR(1) state is the set of items with the lookahead removed: {[A → α . β]}. Two states can have the same core and different lookaheads.

core(I) = { [A → α . β] | [A → α . β, a] ∈ I for some a }

I is an LR(1) state; A → αβ is a production; a is a lookahead symbol (a terminal or $).

LALR takes every group of LR(1) states with one core and replaces the group by one state. For each item, the new lookahead set is the union of the lookaheads from all states in the group. This is why LALR has LR(0)-size state counts but uses more precise lookaheads than SLR.

  1. Build the canonical LR(1) states using Chapter 3.4.
  2. Group states that have the same core.
  3. Keep one state per group; the core does not change.
  4. For each item, union the lookaheads from all states in the group.
  5. Rebuild reduce actions from the unioned lookaheads and check for conflicts.

When merging creates a conflict

Merging can combine two reductions that were safe in separate states. Consider S → a A d | b B d | a B e | b A e, A → c, B → c. In the canonical LR(1) state reached after a and c, the items are A → c., d and B → c., e. On d only A reduces; on e only B reduces. No conflict.

In the canonical LR(1) state reached after b and c, the items are B → c., d and A → c., e. Again there is no conflict. Both states have the same core, {A → c., B → c.}, so LALR merges them.

The merged state has A → c., d/e and B → c., d/e. On d both A → c. and B → c. are possible reductions. On e both are also possible. That is a reduce/reduce conflict. This grammar is LR(1) but not LALR(1). Merging states with the same core does not create new shift/reduce conflicts here; it can create reduce/reduce conflicts.

Size and place in the LR family

For the grammar above, including the augmented start state, canonical LR(1) has 14 states. LR(0), SLR and LALR each have 13 states. LALR has the same number of states as LR(0) because merging by core exactly undoes the lookahead split. Some syllabi call this method LookAhead LR or LALR(1).

SLR uses FOLLOW sets, while LALR uses item lookaheads produced by merging. Canonical LR(1) is stronger. Its table can be larger because it may keep separate states with the same core; LALR has no more states than canonical LR(1). LALR is the usual choice when table size matters and the grammar is almost LR(1). Parser generators report the remaining conflicts, as covered in Chapter 3.6.

Worked example

Question. Grammar: S → a A d | b B d | a B e | b A e, A → c, B → c. Build the canonical LR(1) states reached on c from the states after a and after b. Merge them into one LALR state. State the number of items in each LR(1) state, the number of reduce entries after merging, and the number of reduce/reduce conflict cells. Show the conflict.

  1. After a: items S → a . A d, $ and S → a . B e, $. Closure adds A → . c, d and B → . c, e.
  2. Goto on c gives state I5: A → c., d and B → c., e. It has 2 items. On d only A reduces; on e only B reduces. No conflict.
  3. After b: items S → b . B d, $ and S → b . A e, $. Closure adds B → . c, d and A → . c, e.
  4. Goto on c gives state I8: B → c., d and A → c., e. It has 2 items. On d only B reduces; on e only A reduces. No conflict.
  5. The core of I5 is {A → c., B → c.}. The core of I8 is {A → c., B → c.}. The cores are equal, so LALR merges I5 and I8.
  6. The merged LALR state I58 has A → c., d/e and B → c., d/e. Each item has lookahead set {d, e}.
  7. Reduce entries in I58: A on d, A on e, B on d, B on e. That is 4 entries.
  8. On d, both A → c. and B → c. reduce. On e, both reduce. That is 2 reduce/reduce conflict cells.

Answer. Each LR(1) state has 2 items; the merged LALR state has 4 reduce entries and 2 reduce/reduce conflict cells, on d and e.

Exam traps

  • LALR has LR(0)-size state counts, not canonical LR(1)-size counts. The lookaheads are more precise than SLR but the state count is not larger.
  • Merging unions lookaheads. Do not intersect lookaheads and do not keep only one state's lookahead.
  • New conflicts caused by merging are reduce/reduce, not new shift/reduce. A shift action depends on the core, which is identical in the merged states.
  • A grammar can be LR(1) and not LALR(1). The standard example is S → a A d | b B d | a B e | b A e, A → c, B → c.
  • SLR uses FOLLOW sets, LALR uses item lookaheads from merged LR(1) states. Do not replace an LALR lookahead with FOLLOW.

3.6 Parser generator: YACC

YACC is a parser generator. You give it a context-free grammar with small C actions, and it writes a C program that parses according to LALR tables. It exists so you do not hand-build tables for every language. The file also carries token declarations, precedence lines, and a link to the lexer through yylex(). The output is ordinary C: compile it with cc and run. It is used for calculators, config readers, small language front ends, and as the standard example of parser generators in compiler courses.

You need LALR parsers and the LEX interface from Unit 1.

The .y file has three parts

YACC (Yet Another Compiler Compiler) reads a .y file and writes a C parser that uses LALR tables. The file has three parts separated by %% lines. The declarations part holds C code in %{ ... %} and token declarations such as %token NUM. It also holds precedence lines. The rules part has productions with actions: expr: expr '+' expr { $$ = $1 + $3; }. The third part is C code: main calls yyparse(), and yyerror reports errors. At run time the parser calls yylex() for the next token. yylex returns the token number and stores the token value in yylval. yacc -d writes y.tab.c and y.tab.h; y.tab.h gives the lexer the token numbers. Compile with cc y.tab.c lex.yy.c -o calc. In an action, $$ is the value of the left side; $1, $2, $3 are values of right-side symbols. Bison accepts the same files with bison -y.

Precedence declarations resolve conflicts

An ambiguous expression grammar has a shift/reduce conflict: after expr '+' expr, a lookahead '+' can be shifted or the rule reduced. YACC reports shift/reduce conflicts. With no declaration, YACC chooses shift. That makes the operators right-associative: for '-', 5-2-1 becomes 5-(2-1)=4, not 2. Precedence lines change the table choice, not the grammar. Lines are listed low to high: %left '+' '-' then %left '*' '/' means * and / bind tighter. Tokens on one line share a level; %left means left-associative, %right right-associative. A rule's precedence is its last terminal. At a conflict compare lookahead token with rule: higher wins; equal uses associativity; left reduces, right shifts, %nonassoc gives an error. If either lacks precedence, shift/reduce defaults to shift. Reduce/reduce defaults to the earlier rule. %nonassoc rejects chains such as a < b < c.

Build steps and the calculator file

The build path is short. The parser executable is linked with the lexer, then reads tokens at run time.

  1. Write calc.y with declarations, rules and actions.
  2. Run yacc -d calc.y (or bison -y -d calc.y). It prints conflict counts and writes y.tab.c and y.tab.h.
  3. Write a lexer whose yylex returns NUM for integers and character codes for '+', '-', '*', '/', '(' and ')', setting yylval for NUM.
  4. Compile: cc y.tab.c lex.yy.c -o calc.
  5. Run ./calc and type expressions, one per line.
%{
#include <stdio.h>
int yylex(void);
void yyerror(char *s);
%}
%token NUM
%start top
%left '+' '-'
%left '*' '/'
%%
top: top expr '\n' { printf("%d\n", $2); }
   | expr '\n' { printf("%d\n", $1); }
   ;
expr: expr '+' expr { $$ = $1 + $3; }
    | expr '-' expr { $$ = $1 - $3; }
    | expr '*' expr { $$ = $1 * $3; }
    | expr '/' expr { $$ = $1 / $3; }
    | '(' expr ')' { $$ = $2; }
    | NUM { $$ = $1; }
    ;
%%
int main(void) { return yyparse(); }
void yyerror(char *s) { fprintf(stderr, "%s\n", s); }

Worked example

Question. Using the YACC specification in the section, what does the program print if you type 2+3*4 and (2+3)*4 on separate lines? Explain the conflict choice for the '*' lookahead.

$ ./calc
2+3*4
(2+3)*4
14
20
  1. The declarations give '+' and '-' level 1 with left associativity, and '*' and '/' level 2 with left associativity. Higher level binds tighter.
  2. The rule expr '+' expr takes the precedence of '+', level 1. When the parser has read 2+3 and sees '*', the lookahead '*' has level 2, higher than the rule. Shift wins, so 3*4 is grouped first.
  3. Therefore 2+3*4 = 2+(3*4) = 2+12 = 14. The top rule prints 14.
  4. For (2+3)*4, parentheses force the inner expr to be 2+3 = 5. Then 5*4 = 20. The top rule prints 20.
  5. If the %left '*' '/' line is removed, '*' has no precedence. At the conflict after 2+3 with lookahead '*', the lookahead lacks precedence, so the default is shift. The parser still groups 3*4 first and 2+3*4 gives 14, but this now relies on the default, not on declared precedence.

Dry run

InputDecisionValue

Answer. The program prints 14 then 20. The '*' lookahead shifts because its declared precedence is higher than '+'. If the '*' precedence line is removed, the same input still gives 14 by the default shift, but the choice is no longer controlled by precedence.

Exam traps

  • Precedence declarations do not rewrite the grammar or remove its ambiguity. They only resolve table conflicts by assigned levels and associativity.
  • Declaration order matters. Later lines have higher precedence, so writing %left '*' '/' before %left '+' '-' makes * and / bind looser, not tighter.
  • Without precedence, a shift/reduce conflict defaults to shift, not reduce. For subtraction this makes the parser right-associative and gives wrong answers such as 5-(2-1)=4.
  • A rule's precedence comes from its last terminal, not its first. In expr '+' expr, the rule gets the precedence of '+'.
  • %nonassoc is not the same as no precedence. It makes a chain such as a < b < c a syntax error instead of choosing shift or reduce.

Takeaways

  1. Bottom-up parsing reduces handles to build a parse tree from leaves to root.
  2. The stack plus input is a right sentential form; a correct reduction keeps a viable prefix.
  3. LR(0) items and goto build a finite automaton that records possible parser stack states.
  4. SLR uses FOLLOW to limit reductions, but FOLLOW is too coarse for some grammars.
  5. Canonical LR(1) adds exact lookaheads and removes many conflicts at the cost of large tables.
  6. LALR merges same-core LR(1) states, giving small tables and most of CLR power.
  7. YACC turns an LALR grammar into a C parser and resolves conflicts using precedence or default choices.
  8. Conflict reports matter: default shift or an earlier rule can hide a grammar error.

A terminal examined by the parser before choosing a reduce action.
LR(0) item
A production with a dot marking the position reached by the parser.
Nonkernel item
An item added to a state by closure because a nonterminal follows the dot.
Parser generator
A tool that reads a grammar specification and writes parser source code.
Parsing table
A table of shift, reduce, goto and accept actions that drives an LR parser.
Precedence declaration
A YACC statement that assigns priority and associativity to operators to resolve conflicts.
Reduce-reduce conflict
A parse table cell that contains two different reduce actions.
Rightmost derivation
A derivation in which the rightmost nonterminal is expanded at every step.
Semantic action
Code attached to a grammar rule that runs when the parser reduces that rule.
Shift-reduce conflict
A parse table cell that contains both a shift action and a reduce action.
Shift-reduce parser
A bottom-up parser that uses a stack and chooses between shifting the next token and reducing a handle.
SLR parser
An LR parser that uses LR(0) states and FOLLOW sets to decide reduce actions.
Viable prefix
A prefix of a right sentential form that can appear on a shift-reduce parser stack without immediate error.
YACC
A parser generator that reads a grammar with actions and writes a C parser using LALR tables.
