5.1 Runtime environments and source language issues

A compiler cannot give a name an address until it knows which run of a procedure that name belongs to. Source languages supply procedures, parameters, scope rules and binding rules; the compiler turns them into a tree of activations and a stack of live records. This chapter settles the questions the compiler must answer before it generates code: what an activation is, how activations form a tree, which records stay live on the control stack, and how scope differs from lifetime. The answers fix the shape of every runtime environment in the rest of this unit.

You need: Unit 1 (the phases of a compiler) and Unit 4 (translating procedure calls into three-address code); 5.2 then places these records in memory.

Procedures, definitions and activations

A procedure is a named piece of code that takes parameters and does work on behalf of its caller; it may or may not return a result. Functions in C, methods in Java and subroutines in Fortran are all procedures. The procedure is the unit of abstraction: the caller says what it wants done and the body hides how.

A definition supplies the body and asks the compiler to produce code. A declaration only announces the name, the parameter types and the result type, so that calls elsewhere can be checked. In C, int fare(int); is a declaration; int fare(int n) { return 30 * n; } is a definition. A program may declare a procedure many times and define it once.

An activation is one execution of a procedure, from entry to return. Each activation keeps its own copies of the parameters and the locals. Recursion shows why: when a procedure calls itself, the second activation gets a fresh copy of every local, so it cannot overwrite the first one's. The first activation is suspended, not finished, and its values must survive intact until it resumes.

The activation tree and the control stack

Put one node for the activation of the main program. When an activation calls a procedure, add a child node for the new activation; siblings sit left to right in call order. The result is the activation tree, and its preorder traversal lists the activations in the order in which they begin.

At any instant, the activations that have begun and not yet returned lie on a single path from the root to the activation that is running. They are held in the control stack: a record is pushed on entry and popped on return, so the stack always holds exactly that path. The depth of the activation tree — the number of nodes on the longest root-to-leaf path — is the largest number of records alive at once, and it sizes the stack. 5.4 shows what each record contains.

The call graph has one node per procedure and an edge wherever one procedure can call another. The activation tree has one node per activation, so a recursive procedure appears in it as many times as it is called.

Scope, binding, lifetime and aliasing

With lexical scope, also called static scope, a use of a name is resolved from the program text: look in the enclosing block, then in the block around that, and so on outward. The position is fixed by the text alone. 5.6 covers the symbol table that implements this.

The environment is the map from a name to a storage location; the state is the value currently at that location. Under lexical scope the distance from a use to its declaration never changes. The compiler stores that distance as a pair (nesting depth, offset) and emits code that starts from the running activation's record and follows that many access links to reach the frame holding the declaration. The distance is static; the address is computed at run time with no search of the stack.

Lifetime is the time between allocation and release of storage. Scope is the part of the text where a declaration is visible. They are independent. A C function that returns the address of its local ends the lifetime of that storage when its record is popped, while the pointer in the caller is still in scope and now dangles. In the other direction, an inner block's storage may still exist after its name has gone out of scope. Text controls the name; the run controls the storage.

Two names denote one location: a pointer and its target, a reference parameter, a union in C. A write through one name changes what the other sees, so the compiler cannot trust a copy held in a register across a call.

Dynamic scoping, procedure parameters and closures

Dynamic scoping resolves a name through the chain of callers at run time, not through the text. The same name then refers to different declarations on different calls, so its depth is unknown at compile time and every non-local access becomes a run-time search. A few older languages and some shell languages work this way; it makes fast access and static type checking harder, which is why lexical scope dominates.

A procedure may be passed to another procedure and called through the parameter. To make that call, the callee needs the code address and, under lexical scope, the environment where the procedure was defined. That pair is a closure. Only a few universities teach closures in the compiler course.

Worked example

Question. A program has procedures main, a, b and c. main calls a(1) and then c. a(x) calls b() and then a(x − 1) when x > 0. b() calls c(). c() does nothing. Draw the activation tree for the call main(), give the order in which the activations begin, and give the largest number of records on the control stack.

  1. main begins: activation 1, depth 1, the root of the tree.
  2. main calls a(1): activation 2, a child of main, depth 2.
  3. Inside a(1), x = 1 > 0, so it calls b(): activation 3, a child of a(1), depth 3.
  4. b() calls c(): activation 4, a child of b, depth 4. c returns at once.
  5. b returns. a(1) now calls a(0): activation 5, a second child of a(1), depth 3.
  6. In a(0), x = 0, so the condition fails and the body makes no calls. It returns.
  7. a(1) returns. main calls c: activation 6, a child of main, depth 2. It returns.
  8. Preorder of the tree gives the order of beginning: main, a(1), b, c, a(0), c — six activations.
  9. The longest root-to-leaf path is main → a(1) → b → c, which has 4 nodes, so at most 4 records are live at once.

Answer. Six activations begin in the order main, a(1), b, c, a(0), c, and the control stack holds at most 4 records.

Exam traps

  • Drawing the call graph and calling it the activation tree. The call graph has one node per procedure; the activation tree has one node per activation, so a recursive procedure appears many times.
  • Saying a name is in scope, therefore its storage exists. Scope is text, lifetime is the run. A name is in scope in a block not yet entered, while its storage does not exist yet; and storage can linger while a pointer to it is in scope after the name itself has gone out of scope. A local's name is not in scope in the caller after the call returns.
  • Counting the depth of the activation tree in edges instead of nodes. The number of live records equals the number of nodes on the path, not the number of edges.
  • Treating a declaration as a definition. A declaration only fixes the type; code and storage appear only at the definition.
  • Assuming dynamic scoping can be resolved at compile time. The declaration a use binds to depends on the caller chain, so the depth is unknown until the call happens.

5.2 Storage organization and runtime data layout

Run-time memory is not one flat pool. The compiler cuts a process into a few regions: target code, static data, heap, free space and stack. Each datum goes to the region whose lifetime rule fits it. A global lives for the whole run; a local lives while its call is active; a dynamically created object lives until it is freed. This chapter shows the regions, the usual stack and heap directions, and the byte-level layout of records and arrays. Address arithmetic in the compiler depends on these sizes and offsets, so they must be exact.

You need Unit 4 for declarations and type sizes, and chapter 5.1 for activations.

Regions of one process

When a program runs, the operating system gives the process a block of memory. The compiler divides that block into regions. Target code holds the machine instructions and has a fixed size. Static data holds globals, constants and string literals; its size is fixed at compile time. The heap holds objects created while the program runs. The stack holds activation records for calls, including parameters and locals. Free space sits between the heap and the stack.

State the machine convention before computing any offset. On most machines the stack grows toward lower addresses: a push subtracts from the stack pointer. The heap grows toward higher addresses. So the free gap shrinks from both sides. A few machines grow the stack upward, so the compiler's target description must record the direction.

The stack region is not the same as the data structure stack. It is the call stack of activation records. Each call gets a new record; return removes it. The heap has no such call order. An object there stays until the program frees it or the process ends.

Static and dynamic allocation

A compiler prefers fixed addresses when it can. If the size of an object is known at compile time, the compiler can reserve space in the static data region. A global int count; gets one fixed address for the whole run. A local with a fixed size is placed at a fixed offset inside its activation record; the record moves, but the offset does not. This is static allocation in the simple sense: address or offset fixed before the program starts.

When the size is not known at compile time, the compiler cannot use a fixed offset. The object is allocated dynamically, usually on the heap, at run time. The program receives a pointer or reference. The same happens when an object must outlive the call that created it: a local variable dies at return, so a returned object cannot be that local.

Scope and lifetime are different. Scope is the part of the program text where a name is visible. Lifetime is the time interval in which the storage exists. A global name has whole-program scope and whole-run lifetime. A local name has block scope and activation lifetime. A heap object can have lifetime longer than the scope of the pointer that names it.

Source languages offer storage classes: global, local and dynamically created. Chapter 5.3 gives the three allocation strategies that implement them.

Data layout: bytes, alignment and arrays

Memory is byte-addressable: an address names one byte. A word is the natural unit for a load or store, often 4 bytes or 8 bytes. A type such as int or double has a size in bytes and an alignment. If an object of size S has alignment A, its address must be a multiple of A. The compiler inserts padding bytes so every field of a record, also called a struct, meets its alignment. It may also pad the end of the record so an array of records keeps every element aligned. The size of a record is not the sum of its field sizes.

For a two-dimensional array a[R][C], row-major order stores row 0, then row 1, and so on. Column-major order stores column 0, then column 1. Let base be the address of a[0][0], R the number of rows, C the number of columns, and S the size of one element in bytes.

addr(a[i][j]) = base + (i × C + j) × S in row-major order; addr(a[i][j]) = base + (j × R + i) × S in column-major order

i is the row index and j is the column index, both counted from 0; R is rows, C is columns, S is element size in bytes, and base is the address of a[0][0].

A union is a record whose fields overlap: all fields start at offset 0, and the size is the largest field size rounded up to the union's alignment. Every address the compiler computes uses these sizes. If a size is unknown, the compiler cannot turn a[i] into a byte offset. See Unit 6 for array address arithmetic in the code generator.

Worked example

Question. An int is 4 bytes. A local array is declared int a[3][4]; and its base address is 2000. (a) Give the address of a[2][1] in row-major order. (b) Give the same element in column-major order. (c) Give the total size of the array in bytes. (d) Give sizeof(struct { char c; int i; double d; }) when the alignment of double is 8 bytes.

  1. Identify R = 3 rows, C = 4 columns, S = 4 bytes per int, base = 2000, i = 2, j = 1.
  2. Row-major offset = (i × C + j) × S = (2 × 4 + 1) × 4 = 9 × 4 = 36 bytes. Address = 2000 + 36 = 2036.
  3. Column-major offset = (j × R + i) × S = (1 × 3 + 2) × 4 = 5 × 4 = 20 bytes. Address = 2000 + 20 = 2020.
  4. Total size = R × C × S = 3 × 4 × 4 = 48 bytes.
  5. Struct layout: char c at offset 0, size 1. The int needs alignment 4, so 3 padding bytes, then i at offset 4, size 4, ending at 8. The double needs alignment 8, so d at offset 8, size 8, ending at 16. Total struct size = 16 bytes.

Answer. (a) 2036 (b) 2020 (c) 48 bytes (d) 16 bytes.

Exam traps

  • Adding field sizes and forgetting padding: char, int and double are not 1 + 4 + 8 = 13 bytes when alignment forbids that layout.
  • Swapping the index order or using C where R belongs in a two-dimensional address formula; row-major uses columns and column-major uses rows.
  • Assuming every machine grows the stack downward; write the convention down before computing any offset.
  • Confusing scope with lifetime: a heap object can outlive the local pointer whose scope has ended.
  • Using the wrong element size, such as 4 bytes for int where the target uses 2, or bytes for words.

Not for the exam. Real processors add alignment rules that go beyond a simple C ABI; cache lines are often 64 bytes, so padding can change speed as well as size. Heap allocators keep metadata and may round sizes, so the address returned is not the whole cost of an allocation. 5.3 Storage allocation strategies: static, stack and heap

Every datum in a running program needs an address, and the compiler must choose how that address is fixed. Static allocation fixes every address before the program starts. Stack allocation ties an address to a call and releases it at return. Heap allocation hands out blocks on demand and takes them back when the program asks. These three strategies answer different lifetime questions, so each forbids some programs and makes others easy. The choice is made name by name from the source language's storage rules.

You need Chapter 5.2 for the run-time memory regions.

Static allocation: fixed before the run

Static allocation gives a name one address for the whole run. The compiler knows every size at compile time, so it can place globals, constants, string literals and fixed tables at fixed addresses. The linker fixes those addresses before execution. Code loads the address directly; no stack pointer or free list is involved.

The rule cannot bend. A recursive procedure needs a new activation record for each live call. Under static allocation the second call would reuse the first call's address and overwrite its data. A variable-size array needs an address that depends on a run-time size. An object made by malloc or new needs space chosen while the program runs. None fits.

Static allocation is cheap to address and expensive in space: a block stays reserved even when the program is not using it. Use it for data whose lifetime is the whole program and whose size is fixed.

Stack allocation: one frame per live call

Stack allocation ties storage to calls. Each call pushes an activation record: the block holding parameters, locals and the return address. The stack pointer (SP) marks the current top. On entry the callee lowers SP by the record size; on return SP is restored to its old value, so the record is popped. The discipline is last-in, first-out.

Recursion works because every live call has its own record. If f calls itself three times, three records of f exist; each call reads and writes its own locals. The figure shows this: main's record, then three 48-byte records of f, with SP on the newest.

The same rule creates the dangling pointer. A pointer to a local variable points into a record. When the call returns, the record is popped and its bytes may be reused by the next call. The pointer still holds the old address, so using it is an error. The compiler cannot stop every such use; the language rules must.

Stack allocation suits locals, parameters and compiler temporaries whose lifetime ends at return. See Chapter 5.4 for the record's internal layout.

Heap allocation: blocks on demand

Heap allocation gives blocks whose lifetime is not tied to a call. The program calls malloc in C or new in C++ and Java when it needs an object at run time. The allocator takes a block from its free list, a list of free regions. free in C or delete in C++ returns the block; Java and similar languages use a garbage collector instead.

Blocks may be fixed size or variable size. A fixed-size pool is simple and fast, but a request for a different size needs another pool. Variable-size allocation matches requests, but leaves fragmentation. Internal fragmentation is wasted space inside an allocated block, for example a 210-byte request rounded up to a 256-byte block. External fragmentation is many small free blocks that are each too small for a request, though their total is large. Coalescing adjacent free blocks helps external fragmentation.

Placement picks which free block to use. First-fit takes the first block in list order that is large enough. Best-fit takes the smallest block that is large enough, which may leave a tiny remainder. Next-fit starts the search where the last placement stopped. The buddy system splits and merges power-of-two blocks, so a block and its buddy can coalesce.

Automatic reclamation has three standard names: reference counting, mark-and-sweep and copying collection. Their algorithms belong to a later unit.

The compiler's decision for each name

The compiler chooses a strategy for each name. Its symbol table records the storage class: static, automatic or heap. A global variable or a C static local gets static storage. A local whose address is not taken may live in a register; if its address is taken, it goes on the stack. A pointer variable may be automatic while the object it points to is on the heap.

Language rules override simple names. In Java, an object made by new lives on the heap, while the reference that names it may be a stack local. A C static local keeps one fixed address across calls, so it behaves like a global for allocation but is visible only in its block. See Chapter 5.6 for how the symbol table stores these attributes.

Worked example

Question. A function f has an activation record of 48 bytes. The stack pointer is 8000 just before the first call, and the stack grows toward lower addresses. main calls f, and f calls itself twice, so three records of f are live. (a) Give SP after each of the three calls. (b) Give total stack space used by those three records. (c) A free list holds blocks of 200, 400, 300 and 600 bytes in that order; a request for 300 bytes arrives. Which block does first-fit take, and which does best-fit take? Give the remainder in each case.

  1. One call subtracts 48 bytes: 8000 − 48 = 7952.
  2. Second call: 7952 − 48 = 7904.
  3. Third call: 7904 − 48 = 7856.
  4. Three records use 3 × 48 = 144 bytes. The pointer values alone do not add; this is the f records only.
  5. First-fit scans 200 (too small), 400 (large enough), so it takes 400 bytes and leaves 400 − 300 = 100 bytes.
  6. Best-fit compares all blocks that are at least 300: 400, 300, 600. The smallest is 300, an exact fit, leaving 0 bytes.

Answer. SP after the calls is 7952, then 7904, then 7856; the three records use 144 bytes; first-fit takes 400 bytes leaving 100, and best-fit takes 300 bytes leaving 0.

Exam traps

  • Do not put recursion under static allocation. A recursive call needs a fresh activation record; one fixed address would be overwritten.
  • Static storage is not the same as the static keyword in C, C++ or Java. Here it means fixed before the run; a C static local is one example, a Java static field is another.
  • In first-fit, list order decides. Read the free list left to right; the first block large enough wins even if a later block is a better fit.
  • Internal fragmentation is wasted space inside an allocated block; external fragmentation is free space outside blocks that is too scattered to use.
  • A heap block is not freed when its pointer goes out of scope. free or delete must run, or a garbage collector must prove the block unreachable.

5.4 Activation records and implementing function calls

Every call needs a small private bundle of memory: arguments, the return point, saved registers, and the caller's frame pointer. That bundle is one activation record, also called a frame. One call means one record, pushed when the call starts and popped when it returns. C, C++ and Java compilers use this scheme. It explains stack overflow, debugger backtraces and why deep recursion crashes an app.

You need: Chapter 5.2 for run-time memory regions and Chapter 5.3 for why call data goes on the stack.

What one activation record holds

An activation record is the stack memory for one execution of a procedure. Other names are frame, stack frame and call frame. One call, one record: pushed at entry, popped at return.

Fix the convention first. Here one word is 4 bytes, the stack grows towards lower addresses, and after the callee sets FP = SP, FP points at the saved old FP. Parameters sit at FP + 8 and above; locals sit at FP - 4 and below.

  • Actual parameters: caller evaluates these and places them at FP + 8 and above.
  • Return-value slot, unless the value comes back in a register.
  • Control link, also called dynamic link: caller's FP, saved by callee at FP + 0.
  • Access link, also called static link: FP of the lexically enclosing procedure's record. Present only when the language nests procedures.
  • Saved machine status: return address at FP + 4, plus registers and condition codes the callee must preserve.
  • Local data: variables declared in the body, at FP - 4 and below.
  • Temporaries: intermediate values the compiler needs while evaluating an expression, also below FP.

Keep every field word-aligned. A misaligned field costs extra loads and shifts every later offset.

Calling sequence: caller's turn, then callee's turn

The work splits at a fixed line: caller prepares, callee builds and owns the frame. The agreement about who places what where and who saves which register is the calling convention. Code that ignores it cannot call library functions.

  1. Caller evaluates every actual parameter and places each value in its slot or in a register, in the order the convention fixes.
  2. Caller saves the caller-saved registers whose values it still needs after the call returns.
  3. Caller stores the return address, the address of the next instruction, and jumps to the callee's entry point. On many machines one call instruction does both.
  4. Callee decrements SP by one word and saves the old frame pointer there; this address becomes FP + 0 once FP is set.
  5. Callee copies SP into FP. The frame no longer moves, so every local gets a fixed offset.
  6. Callee saves the callee-saved registers it will use.
  7. Callee moves SP down by the size of locals plus temporaries, reserving that space.

The callee fixes the frame before touching any local variable.

Return sequence and who saves which register

The return sequence undoes the call in reverse.

  1. Callee places the returned value in its slot or in the agreed register.
  2. Callee restores the callee-saved registers, then reloads the old FP from FP + 0.
  3. Callee sets SP to FP + 4, dropping old FP, locals and temporaries in one move, and jumps to the return address.
  4. Caller restores its own saved registers and moves SP past the parameter slots, so its frame is exactly as before.

A register is caller-saved if a call may destroy its value, so the caller must save it first. A register is callee-saved if the callee must restore it before returning, so the caller may keep a value there across the call. Real machines have some of each. The split saves work: a value the caller never needs again is destroyed for free.

Frame pointer, stack pointer and variable-size frames

FP stays fixed for the whole body. A local's address is one addition away, and a debugger walks the chain of control links to print main called f called g without a symbol table.

SP moves whenever the procedure pushes a temporary or calls another procedure. If the frame size is known at compile time, locals are addressed from FP and SP is only bookkeeping. If the frame size can change, as with alloca or a variable-length array, the growing area must be addressed from SP, and the compiler tracks the SP offset at every point in the body.

Nested procedures need the access link. It points at the record of the lexically enclosing procedure, fixed by the scope rules of the source text, not by who called whom. A display is an array holding a pointer to the current record of each nesting level, so a non-local reference costs one array lookup instead of a walk along the links; only a few universities teach it.

Exam traps

  • Swapping the control link and the access link. The control link follows the call chain and points at the caller's record; the access link follows the source text and points at the lexically enclosing record.
  • Giving the callee the caller's jobs, such as saying the callee evaluates the actual parameters or stores the return address.
  • Quoting offsets without stating the convention. A stack that grows up, or a different word size, changes every number.
  • Forgetting the return address when counting words, giving 16 bytes instead of 20 for the worked example.

Understand Why is the return address kept in the activation record rather than in one fixed register? 3 marks

Calls nest. f calls g calls h: each call must remember its own return point. A single register would hold only the latest one. Storing it in the record gives each activation its own copy, so returns unwind correctly.

Apply A function has three int parameters, two int locals, 4-byte words, a downward stack, and FP at the control link. Give the offset of each field and the record size rounded to a multiple of 8. 4 marks

Analyze A procedure calls alloca partway through its body. Why must the growing area be addressed from SP? 5 marks

FP cannot change, otherwise every fixed offset for parameters and saved registers breaks. The block alloca returns has a size known only at run time, so the compiler cannot give it a fixed FP offset. It addresses it relative to the current SP instead, and keeps track of SP's value at each program point so the offset used is correct.

Analyze A recursive function overflows the stack at depth 50000 while a loop doing the same work runs fine. Explain using activation records. 4 marks

Each call pushes a new record and none is popped until the call returns, so depth d means d live records. Total stack is d × record size, which is bounded. A loop reuses one record, so its stack use is constant. The fix is to reduce the record size or convert the recursion to iteration or an explicit heap stack.

5.5 Parameter passing mechanisms

When main calls swap(x, y) with x = 3 and y = 7, one rule leaves x = 3 and another leaves x = 7. That rule is the parameter passing mechanism: it fixes what the callee's activation record holds for each parameter, and what a write inside the callee does to the caller's data. A language may copy the value, copy the address, or substitute the argument text. The choice costs words in the record, shows up in the program's output, and is fixed by the compiler at every call site.

You need: Chapter 5.4 for where parameters sit in the activation record.

Copy or address: the two basics

The caller evaluates each argument and places the result in the parameter slot of the callee's activation record. The mechanism decides what goes into that slot.

In call by value the slot holds a copy of the argument's value. For an int that is one word; for a struct it is a whole block, copied before the call. Inside the callee the parameter is a fresh variable, so a = b changes the copy and the caller's variable is untouched. C does this for scalars.

In call by reference the slot holds the address of the argument, so the caller must pass something that has an address: a variable or an array element. The compiler emits one extra load on every use. Reading the parameter means load the address, then load the word at it. Writing stores through the address, so the caller's variable changes. Only one word is copied per call.

Cost rule: call by value copies the object, call by reference copies one word.

Copy-out, text and memo

  • Call by value-result (copy-restore): the value is copied in, the callee works on its own copy, and at return the final value is copied back into the caller's variable. Copy-in and copy-out both cost a block.
  • Call by result: nothing is copied in; the callee must assign the parameter before using it, and the value is copied out at return. A read before the first write sees an uninitialised word.
  • Call by name: the caller passes a thunk, a small piece of code that evaluates the argument text. Every use re-evaluates the text, so side effects repeat and the value can change between two uses. Jensen's device is the classic use: Sum(i, 1, n, a[i]) passes both the loop variable i and the term a[i] by name, so the callee's loop drives the caller's i and a[i] is re-evaluated for each value of i.
  • Call by need: like call by name, but the first evaluation is stored and later uses read the stored value. Haskell works this way; a use that never happens costs nothing.
  • With reference or value-result, two formals can name the same variable. For reference the order of the writes decides the answer; for value-result the order of the copy-outs at return decides it.

What C, C++, Java and Python do

C passes every argument by value. For an array, the array name decays to the address of its first element, so passing it copies one word, a pointer, not the array; the callee can still change the elements through that pointer. A struct passed by value is copied in full. C++ adds const T&, a reference the callee cannot write through: no copy, and the write is blocked. Java passes primitives by value and object references by value, so the callee can change the object's fields but cannot rebind the caller's variable. Python passes the object reference by value in the same way.

An overloaded method is resolved at compile time from the signature: the method name plus the parameter types. The call site gets a fixed entry point, so resolution costs nothing at run time. A C++ template method is instantiated once per type it is used with, one copy of the code for int and another for String. A Java generic method is erased instead: a single copy of the code serves all type arguments, with casts inserted at the call sites.

Worked example

Question. procedure swap(int a, int b) { int t = a; a = b; b = t; } is called as swap(x, y) with x = 3 and y = 7. Give x and y after the call under (a) call by value, (b) call by reference, (c) call by value-result. (d) main also has i = 1 and A = [10, 20, 30, 40], and procedure f(int p) { i = 3; p = p + 1; } is called as f(A[i]). Give A[1] and A[3] under call by value, call by reference and call by name.

  1. (a) Call by value: a and b are copies, a = 3 and b = 7. t = 3, then a = 7, then b = 3. On return the copies are discarded, so x = 3 and y = 7.
  2. (b) Call by reference: the slot for a holds the address of x and the slot for b holds the address of y. t = 3. The write a = b stores 7 into x, so x = 7. The write b = t stores 3 into y, so y = 3.
  3. (c) Call by value-result: copy in a = 3, b = 7. The swap gives a = 7, b = 3 on the copies. Copy out at return: x = 7 and y = 3.
  4. (d) Call by value: p = A[1] = 10. Then i = 3. Then p = 11. Nothing is copied back, so A[1] = 10 and A[3] = 30; only i changed, to 3.
  5. (d) Call by reference: the address of A[1] is fixed at the call. Then i = 3. The write p = p + 1 stores 11 into A[1]. So A[1] = 11 and A[3] = 30.
  6. (d) Call by name: p means the text A[i]. The statement p = p + 1 becomes A[i] = A[i] + 1, and by then i = 3, so A[3] = 30 + 1 = 31. A[1] stays 10.

Answer. (a) x = 3, y = 7. (b) x = 7, y = 3. (c) x = 7, y = 3. (d) value: A[1] = 10, A[3] = 30. reference: A[1] = 11, A[3] = 30. name: A[1] = 10, A[3] = 31.

Exam traps

  • Call by reference and call by value-result print the same answer unless a formal aliases storage the callee also writes. Example: a global g and procedure f(int a) { g = 5; a = a + 1; } called as f(g) - by reference g = 6, by value-result g = (old g) + 1. When two formals alias one variable, as in p(x, x) with body a = 1; b = 2, the copy-out order decides the value. Call by name is the mechanism that changes swap(i, A[i]), because A[i] is re-evaluated after i changes.
  • Java passes an object reference by value: the callee may change the object's fields, but an assignment to the parameter does not rebind the caller's variable.
  • Call by name re-evaluates the argument text at every use, so a change to i between uses changes which array element is touched.
  • Overload resolution uses the signature, which includes the parameter types. Dropping them in your answer turns a compile-time choice into a guessed run-time one.

5.6 Symbol tables, scope and binding

A symbol table is the compiler's map from a name to its attributes. It answers: what is this name, what type, where does it live, and which declaration does this use mean? Scope and binding rules decide the answer. The table is used in every phase after lexical analysis: declaration processing, type checking, code generation and debugging. Without it, the compiler cannot tell a local variable from a global function, or an inner x from an outer x. Hash tables make lookup fast; a stack of tables handles nested blocks.

You need: the symbol table idea from Unit 1, parsing from Units 2 and 3, semantic analysis from Unit 4, and the runtime picture in 5.1 and 5.4.

Entries, operations and four structures

One symbol table entry holds the attributes of one declared name: name, kind (variable, function, type, label), type, size, offset or address, scope, storage class (automatic, static, extern), and source line. The source line helps error messages. A symbol table supports three operations: insert a declaration, lookup a use, and delete when a scope ends. Lookup returns the entry or a not-found result. For n entries, where n is the number of names stored, the structure decides the cost.

StructureLookup costNote
Unordered listn comparisonssimple, slow for many names
Sorted listabout log₂ nbinary search; insert shifts entries
Balanced BSTabout log₂ nn if it becomes a chain
Hash tableO(1) averageneeds a good hash and collision handling

A binary search tree is balanced when its height stays near log₂ n; an unbalanced tree can become a list. The compiler chooses the structure by the language and the number of names. Small teaching compilers often use a list for clarity; production compilers use hash tables.

Hashing: buckets and collisions

Most compilers use a hash table. A hash function h(name) turns the name into an index from 0 to m−1, where m is the number of buckets. Each bucket holds a chain of entries. On insert, compute the bucket. If it is empty, store the new entry. If it is occupied, walk the chain and compare names. If no entry has the name, add the new entry at the end of the chain. Do not replace the old entry: a collision is not a duplicate.

h(name) = (Σ position(letter)) mod m

position(a)=1, ..., position(z)=26; m is the number of buckets; h(name) is the bucket index.

Lookup computes the same bucket and compares names along the chain. Open addressing is an alternative: on collision, probe other slots in a fixed order. It saves pointers but needs a load factor below 1 and careful deletion. Chaining is simpler and common in teaching compilers. A good hash spreads names evenly; a bad hash puts many names in one bucket and lookup degrades to a list.

Block scope, shadowing and binding times

Block-structured languages use a stack of tables. When a block opens, push a new table or record a marker equal to the current table size. Insert its declarations. A use is looked up from the innermost table outward; the first match wins. This is static scoping, also called lexical scoping. An inner declaration shadows an outer declaration of the same name while the inner scope is active. When the block ends, delete entries back to the marker; the outer declaration becomes visible again. A simple compiler can also keep one table and store the scope depth in each entry. Visibility analysis asks which names are visible at a program point; scope resolution finds the matching declaration.

Binding is the step that fixes a meaning to a name. Binding times: language design time fixes the meaning of built-in operators and types; compile time fixes a local variable's type and offset; link time fixes an external function's address; load time fixes a static variable's absolute address; run time fixes a local variable's location in an activation record and a virtual method's target. Dynamic scoping is the other rule: a use finds the declaration in the most recent active call. It can use deep access along the control chain or a shallow association list. Only a few universities go deeper.

Worked example

Question. A symbol table uses m = 11 buckets and h(name) = (sum of alphabet positions of the letters) mod 11, with collisions handled by chaining. Insert sum, max, min, avg, tmp in that order and show the buckets. Then, for int x = 1; void f() { int a = 2; { int x = 3; print(x + a); } print(x); } give the two printed values under static scoping.

  1. Use alphabet positions a=1, b=2, ..., z=26. The hash is the letter sum modulo 11.
  2. sum: s=19, u=21, m=13; sum 19+21+13 = 53; 53 mod 11 = 9. Bucket 9 is empty, so store sum there.
  3. max: m=13, a=1, x=24; sum 13+1+24 = 38; 38 mod 11 = 5. Bucket 5 is empty, so store max there.
  4. min: m=13, i=9, n=14; sum 13+9+14 = 36; 36 mod 11 = 3. Bucket 3 is empty, so store min there.
  5. avg: a=1, v=22, g=7; sum 1+22+7 = 30; 30 mod 11 = 8. Bucket 8 is empty, so store avg there.
  6. tmp: t=20, m=13, p=16; sum 20+13+16 = 49; 49 mod 11 = 5. Bucket 5 already holds max, so chain tmp after max; do not overwrite max.
  7. Buckets: 3 holds min; 5 holds max then tmp; 8 holds avg; 9 holds sum.
  8. Under static scoping, print(x + a) uses the inner x = 3 and a = 2, so it prints 3 + 2 = 5.
  9. After the inner block ends, its x is gone. The final print(x) uses the global x = 1, so it prints 1.

Answer. Buckets: 3 holds min, 5 holds max then tmp, 8 holds avg, 9 holds sum; the two printed values are 5 then 1.

Exam traps

  • On a hash collision, putting the new name in place of the old one destroys the old entry; the new entry joins the chain and lookup compares names along it.
  • After a block ends the inner declaration stops shadowing, so the outer name is visible again.
  • Static scoping is decided from the program text, not from the call order; dynamic scoping follows the call chain.
  • A symbol table entry is not the variable's value; it stores attributes such as type, offset and scope.
  • Do not confuse binding time with lookup time: binding fixes a meaning, while lookup finds an entry during compilation.

Takeaways

  1. The compiler can only place a name correctly once it knows which activation of which procedure the name belongs to; scope and binding rules give that answer.
  2. Run-time memory is carved into code, static, stack and heap regions, and each datum goes to the region that matches its lifetime.
  3. Static allocation is fast but forbids recursion; stack allocation follows calls naturally; heap allocation is the only one that lets data outlive its creator.
  4. One call of a procedure equals one activation record, and the caller and callee split the work of building, filling and destroying it.
  5. The control link restores the caller on return; the access link lets a nested procedure reach the variables of its enclosing procedure.
  6. The parameter passing mechanism decides whether the callee sees a copy or the original storage, and that single decision can change the printed output.
  7. Call by value is safe but costs a copy; call by reference is cheap but creates aliases; call by value-result and call by name exist for special needs.
  8. The symbol table plus scope rules are what turn a name in the source into a specific storage offset in a specific frame.

Evaluate Compare static and dynamic scoping for a program with nested and non-nested procedures. Evaluate how each affects the compiler's symbol table and the run-time access cost. 13 marks

Static scope resolved at compile time, offsets fixed; Dynamic scope needs deep access or shallow access at run time; Shallow access keeps a save stack per name; Deep access searches the control link chain; Effect on readability, separate compilation and speed.

Evaluate Evaluate stack versus heap allocation for objects whose lifetime is not known at compile time, and explain how closures force escape of local variables to the heap. 13 marks

Stack fits strict LIFO lifetimes only; Escaping data must move to the heap; Closure keeps captured environment alive after return; Cost of heap: slower allocation, garbage collection; Escape analysis to keep some objects on the stack.

Evaluate For passing a large array of 10⁶ integers to a procedure, evaluate call by value against call by reference and call by value-result, in terms of copy cost, aliasing and safety. 13 marks

Call by value copies 4 MB per call (10⁶ × 4 bytes); Call by reference passes one address, but callee can modify caller's data; Value-result copies in and out, doubling copy cost but blocking aliasing during the call; Aliasing hazards when two formals refer to the same array; Practical recommendation and the const qualifier.

Glossary

Access link
Pointer in an activation record to the record of the textually enclosing procedure.
Activation
One execution of a procedure, from the call to the return, with its own copy of local data.
Activation record
The stack block holding the parameters, links, saved state, locals and temporaries of one activation.
Alias
Two or more names that refer to the same storage location.
Binding time
The moment at which a name is associated with a meaning, a type or a storage location.
Call by name
Parameter passing in which the argument text replaces each use of the formal and is re-evaluated every time.
Call by need
Call by name in which the thunk is evaluated once and its value cached for later uses.
Call by reference
Parameter passing in which the address of the argument is given to the callee.
Call by result
Parameter passing in which no value goes in but the callee's final value is copied back to the caller's argument.
Call by value
Parameter passing in which a copy of the argument's value is placed in the callee's frame.
Call by value-result
Copy in at call and copy back at return, combining isolation during the call with an output value.
Calling sequence
The instructions split between caller and callee that build and destroy an activation record.
Closure
A procedure together with the environment in which it was created, so its free names stay reachable.
Control link
Pointer in an activation record to the caller's record, used to restore state on return.
Display
An array of frame pointers indexed by nesting depth, giving constant-time access to non-local names.
Dynamic link
Another name for the control link.
Environment
The mapping from names in force at a program point to storage locations.
Frame pointer
Register holding the base address of the current activation record, so locals sit at fixed offsets from it.
Heap
The memory region from which storage is allocated and freed at arbitrary times.
Lifetime
The interval between allocation and release of a datum's storage.
Scope
The region of program text in which a declaration of a name is visible.
Static link
Another name for the access link.
Symbol table
The compiler's table mapping each name to its attributes such as type, kind, scope and offset.
Thunk
A small piece of code plus its environment that computes an argument's value on demand, used for call by name.
