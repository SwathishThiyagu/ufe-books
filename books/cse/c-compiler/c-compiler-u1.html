1.1 Language processors: compilers, interpreters and assemblers

A language processor is software that reads a program written in one language and prepares it to run or runs it. A translator converts source text into another form. A compiler translates the whole source into a target program, usually machine code, before any run. An interpreter reads and executes source or intermediate code statement by statement, so its output is the running result. An assembler translates assembly mnemonics into machine instructions, usually one mnemonic to one instruction. These tools exist because humans write in C, Python or assembly, while the processor executes only its own instruction set.

Two execution models

A language processor is any program that takes a source program and turns it into a form that can execute, or executes it. A translator is a language processor that rewrites the source into another language. A compiler is a translator: it reads the complete source, checks it, and emits a target program. In a C workflow, the compiler produces machine code; the user runs that code later, many times if needed. A assembler is also a translator, but it works at a lower level: it maps assembly mnemonics such as MOV and ADD to machine instructions, usually one-to-one. An interpreter is different. It does not hand the user a target program. It reads the source or an intermediate form and performs the actions of each statement as it goes; the output appears during interpretation. Python commonly works this way: the Python system executes your file and prints results, rather than leaving a standalone machine-code file for you to run. Hybrid systems exist. Java compiles source to bytecode, and a virtual machine interprets that bytecode or compiles it further just in time. The central question is timing: does translation finish before execution, or does execution drive translation?

What each one produces

The output tells you which tool you are looking at. A compiler's output is a target program: an executable, an object file, or assembly text, depending on the compiler. An interpreter's output is the result of the program: values printed, files changed, a service started. An assembler's output is object code: machine instructions plus information the linker needs. The same source can be handled either way. C is normally compiled. Python is normally interpreted, with internal compilation to bytecode first. Assembly is assembled, then linked with other object files to form an executable. Compile-then-run favours repeated runs: you pay translation once, then run a fast target program. Interpret-as-you-go favours quick starts and portability: no separate machine-code file is needed, and the interpreter can run wherever it is installed. The price is repeated work on every run, because the interpreter must examine statements again. The worked example below turns this trade-off into arithmetic.

Cousins of the compiler

A compiler rarely works alone. Around it sit other language processors, often called the cousins of the compiler; some syllabi call the whole group a language processing system. A preprocessor prepares source before compilation. In C it handles #include, #define and conditional compilation. A macro processor replaces macro calls by their defined bodies; it is a general text-substitution tool, while the C preprocessor is a specialised one. A linker joins object files and library code into one executable, resolving names that one file uses and another defines. A loader places that executable in memory and starts it, setting up addresses at load time. A compiler may also call an assembler to turn its assembly output into object code. These tools matter because real builds chain them: source → preprocessor → compiler → assembler → linker → loader → running process. The compiler is the central translator, not the whole factory.

Worked example

Question. A program has 100 statements. An interpreter costs 0.03 s per statement on every run. A compiler costs 4 s once, and the compiled code costs 0.10 s per run. Find the smallest number of runs after which compiling is cheaper.

  1. Interpreted cost per run = 100 × 0.03 s = 3 s.
  2. Compiled cost for r runs = 4 + 0.10r seconds. Here 4 s is the one-time compile cost and 0.10 s is the per-run code cost.
  3. Set 4 + 0.10r < 3r. Subtract 0.10r: 4 < 2.90r.
  4. Divide: r > 4 ÷ 2.90 = 1.379... .
  5. r is a whole number of runs, so the smallest r is 2.
  6. Check r = 2: compiled cost = 4 + 0.10×2 = 4.2 s; interpreted cost = 3×2 = 6 s. At r = 1, compiled cost = 4.1 s and interpreted cost = 3 s, so compiling is not cheaper.

Answer. The smallest number is 2 runs; at 2 runs the compiled cost is 4.2 s and the interpreted cost is 6 s.

Exam traps

  • Both a compiler and an interpreter translate, so the difference is when. A compiler produces a target program before execution; an interpreter executes source or intermediate code during the run.
  • An assembler is not a compiler. It maps assembly mnemonics to machine instructions, usually one-to-one; a compiler translates a high-level language and may emit many instructions per statement.
  • Do not say an interpreter produces machine code for later runs. Its output is the result of execution. Hybrid bytecode systems blur the boundary, but the interpreter still executes.
  • In break-even problems, compile cost is once and run cost is per run. Set one-time cost + per-run compiled cost < per-run interpreted cost, and round up because runs are whole.

1.2 Structure and phases of a compiler

A compiler does not translate a program in one jump. It pushes the program through a pipeline of phases, and each phase changes the representation: characters become tokens, tokens become a tree, the tree becomes machine-independent instructions, and those become target instructions. The pipeline exists because the whole job is too big for one step, and because the front half depends on the source language while the back half depends on the machine. GCC, javac and a small student compiler all follow this shape, sometimes with several phases merged into one pass.

You need: Chapter 1.1, which explains what a compiler is and how it differs from an interpreter and an assembler.

Each phase rewrites the program

The input is a string of characters, the output is a string of machine instructions. In between, the compiler keeps rewriting the program into a form that is easier to work on. Read the phases in the order a source file meets them.

  1. Lexical analysis reads characters and produces tokens, the smallest meaningful units: an identifier, a keyword, an operator, a constant. Full detail is in Chapter 1.4.
  2. Syntax analysis, or parsing, checks the token stream against the grammar and builds a parse tree. See Unit 2, Syntax Analysis and Top-Down Parsing.
  3. Semantic analysis checks meaning: every name is declared, types match, scope rules hold. It also inserts conversions such as int to float. See Unit 4.
  4. Intermediate code generation turns the tree into simple machine-independent instructions, usually three-address code of the form x = y op z.
  5. Optimization rewrites the intermediate code to run faster or use less memory while keeping the same meaning. See Unit 6.
  6. Code generation maps intermediate code to the target machine: instruction selection, register use and addressing modes.
  7. Machine-dependent optimization improves target code using facts about the machine, for example deleting a load that repeats the previous one.

Some syllabi call the intermediate code the intermediate representation, or IR. The optimizer and the code generator both read it, which is why it is the natural boundary between the two halves of the compiler.

The symbol table and the error handler serve every phase

Two components cut across the pipeline. Neither one is a phase: they are shared services that every phase calls.

  • Symbol table manager. The table keeps one record per name: the name itself, its type, its scope, its storage location and the line where it was declared. The lexer inserts identifier names, semantic analysis fills in types, code generation reads the address. Unit 5 covers the table in full.
  • Error handler. Each phase detects its own kind of error and reports it with a line number, then repairs just enough to continue. The lexer skips a bad character, the parser drops tokens until a safe symbol, semantic analysis records a type mismatch and carries on. A compiler that gives up at the first error annoys every programmer who uses it.

One shared symbol table keeps all phases agreeing on what a name means, so the type recorded by semantic analysis is exactly the type the code generator acts on.

Grouping the phases: front end and back end

The phases split into two halves at the intermediate code. The front end is also called analysis: lexical, syntax and semantic analysis plus intermediate code generation. It depends on the source language and not on the machine, so one front end can feed many targets. The back end is also called synthesis: optimization, code generation and machine-dependent optimization. It depends on the target machine and not on the source language, so one back end can serve many languages.

Single pass or many passes. A single-pass compiler interleaves the phases and reads the source once: the parser asks the lexer for the next token, and code is emitted as each construct is recognised. It is fast and needs little memory, but it never sees the whole program, so it optimizes weakly and struggles when a name is used before it is declared. A multi-pass compiler runs each phase to completion, stores the intermediate code, then optimizes. Most modern compilers are multi-pass, because memory is cheap and optimization matters.

Worked example

Question. Trace the assignment position = initial + rate * 60 through all phases of a compiler. Show the token stream, the shape of the parse tree, the three-address code and what the optimizer does to it.

  1. Lexical analysis groups the characters into 7 tokens: id1 = id2 + id3 * 60, where id1 is position, id2 is initial, id3 is rate, and 60 is a constant. The operators =, + and * are tokens too.
  2. Syntax analysis builds the tree from the grammar and operator precedence. The root is =, with id1 as its left child. The right child of = is +; the children of + are id2 and *; the children of * are id3 and 60. Multiplication sits below addition because it binds tighter.
  3. Semantic analysis looks up id1, id2 and id3 in the symbol table and finds all three declared as float. The integer 60 is widened to the real constant 60.0. The expression type is float and the assignment is type-correct, so no error is reported.
  4. Intermediate code generation emits three-address code with 2 temporaries: t1 = id3 * 60.0; t2 = id2 + t1; id1 = t2. That is 3 instructions.
  5. Optimization checks for common subexpressions, dead code and constant folding. There is none: t1 and t2 are each used once, and 60.0 cannot be folded with an unknown value. The code stays the same.
  6. Code generation picks instructions and registers. One possible output: LD R1, rate; MUL R1, R1, #60.0; LD R2, initial; ADD R1, R2, R1; ST position, R1.

Answer. The assignment produces 7 tokens, 2 temporaries and 3 three-address instructions, and the optimizer leaves the code unchanged because there is no common subexpression to remove.

Exam traps

  • Phases are logical stages, not always separate programs. A real compiler may merge lexical and syntax analysis, or optimization and code generation, into one pass.
  • The symbol table and the error handler are not phases. They are shared tables and routines that every phase uses, and examiners often ask you to place them beside the phases in a block diagram.
  • The optimizer must not change the meaning of the program. It is also optional for correctness: a simple compiler that skips it still produces a correct target program.
  • Front end versus back end is about language dependence and machine dependence. Do not mix it up with the order of execution in a single-pass compiler, where the phases run interleaved.
  • A common slip: saying the parser removes comments and whitespace. The lexical analyzer does that; the parser never sees comments or spaces.

1.3 Compiler construction tools and applications

Compiler-construction tools are programs that write parts of a compiler for you. You give a specification: token rules for a scanner, a grammar for a parser, or translation rules for a code generator. The tool produces source code for that part. The idea exists because hand-writing a scanner or parser is slow and error-prone. The same compiler techniques also drive tools beyond compilers: domain-specific languages, program analysers, security checkers and hardware design tools. The main tools and main applications follow.

You need: Chapter 1.2, the phase pipeline, because each construction tool builds one phase's component.

Tools that generate compiler parts

Compiler-construction tools take a declarative specification and emit a working component. A declarative specification states what to recognise or translate, not the loops and tables that do it.

  • Scanner generator: input is a set of regular definitions and rules, one per token class; output is a scanner, usually in C. LEX is the common example. See Chapter 1.9.
  • Parser generator: input is a context-free grammar with semantic actions; output is a parser. YACC is the common example. See Unit 3, Parser generator: YACC.
  • Syntax-directed translation engine: input is a grammar with attributes and translation rules; output is code that walks a parse tree and computes values or emits intermediate code. See Unit 4, Syntax-Directed Translation and Intermediate Code.
  • Automatic code generator: input is intermediate code plus a machine description or instruction templates; output is assembly or machine code. See Unit 6, Code Generation and Optimization.
  • Data-flow analysis engine: input is a control-flow graph and data-flow equations; output is facts such as reaching definitions or live variables, used by optimisers. See Unit 6.
  • Compiler construction toolkit: a bundle of these generators with symbol-table and error-reporting support.

Applications of compiler technology

Compiler techniques appear wherever a program must be checked, translated or improved. Some syllabi call this 'applications of compiler technology'. The techniques travel; the compiler code need not.

  • High-level language implementation: C, C++, Java and Python runtimes use parsing, type checking, intermediate code and code generation.
  • Domain-specific languages: a shop's query language, regular expressions and spreadsheet formulas need small scanners and parsers; compiler tools generate them quickly.
  • Program analysis and verification: type checkers, static analysers and model checkers use control-flow graphs and data-flow analysis to find null dereferences, races or unreachable code.
  • Optimisation and parallelisation: compilers analyse loops and data dependences, then vectorise or parallelise code. See Unit 6.
  • Format translation: source-to-source converters, pretty printers and binary translators read one representation and emit another.
  • Security checking: taint analysis, bounds checking and sandboxing use compiler-style data flow to track unsafe values.
  • Hardware design: tools for hardware description languages parse modules, elaborate them and synthesise circuits; this is compiler technology applied to hardware.

The same idea explains why compiler courses are useful outside compiler jobs: the phase pipeline is a pattern for any tool that reads structured input, checks it and writes a new form.

What the tools do not do

A scanner generator builds a scanner. A parser generator builds a parser. Neither builds a complete compiler.

A complete compiler still needs a symbol table, semantic analysis, intermediate-code generation, optimisation and target-code generation. Some of these have their own generators, but someone must connect them and define the language semantics. See Unit 4, Unit 5 and Unit 6.

A parser generator also needs the right input. It consumes a context-free grammar, not a list of token patterns. The token patterns belong to the scanner generator. The parser asks the scanner for the next token; it never reads characters directly.

Applications reuse compiler techniques, not compiler source code. A static analyser may contain a parser and a data-flow engine without ever producing machine code. That is still compiler technology at work.

Keep the boundary clear: a generator is a tool that builds one part; the compiler is the assembled system around it.

Worked example

Question. A shop writes a small query language with 42 keywords and 16 token patterns. Which compiler-construction tools generate the scanner and the parser, and what input does each take?

  1. Scanner input: 16 regular-expression rules, one per token pattern, plus a table of 42 keyword strings mapped to token codes. A scanner generator such as LEX reads this specification and writes a scanner, say scanner.c.
  2. Parser input: a context-free grammar for the query language, with semantic actions attached to productions. A parser generator such as YACC reads the grammar and writes a parser, say parser.c.
  3. Connection: the scanner returns one token code at a time for the 16 patterns and 42 keywords; the parser consumes those tokens and checks the grammar.
  4. Count of generator tools used: 2. Remaining work: symbol table, type checks, query plan or code generation are not produced by LEX or YACC.

Answer. LEX with 16 token-pattern rules and 42 keyword entries generates the scanner, and YACC with the query-language grammar generates the parser; the 2 generator tools do not form a complete compiler.

Exam traps

  • LEX produces a scanner, not a whole compiler; YACC produces a parser, not a whole compiler.
  • A parser generator takes a grammar. A list of token patterns is input for a scanner generator.
  • Applications reuse compiler techniques, not compiler code; a checker can use data-flow analysis without generating machine code.
  • A syntax-directed translation engine is not just a parser generator: it adds attributes and actions to compute values or emit code.
  • A code generator needs a machine description or templates; it does not invent the meaning of the intermediate code.

1.4 Role of the lexical analyzer: tokens, patterns, lexemes

A lexical analyzer, or lexer, reads the source program as characters and returns the next token to the parser. It hides spaces, comments and line endings. Three terms keep the job clear: a lexeme is the exact text, a pattern describes the set of lexemes for one class, and a token is the class name plus any value needed later. The parser then works with a small set of token names instead of raw characters. Compilers, formatters, linters and syntax highlighters all use the same idea.

You need: the phase pipeline in Chapter 1.2.

From characters to tokens

The lexer scans source text from left to right. At each step it skips whitespace and comments, then groups characters into the next lexeme. It finds which token class matches that lexeme and returns the token. The parser calls the lexer whenever it needs a token, so the lexer behaves like a subroutine of the parser.

A token is a pair: a token name and an optional attribute value. Some syllabi call the token name the token class or token type. A lexeme is the actual character string. A pattern is the rule that says which strings belong to a token class. An attribute carries extra information, such as the numeric value of a number or the name of an identifier.

token = ⟨token-name, attribute⟩

token-name identifies the class, such as ID or NUM; attribute is optional extra data used by later phases.

For example, in count = 10, count and 10 are lexemes. The token for count is ID with attribute count; the token for 10 is NUM with attribute 10.

Why separate lexical analysis from syntax analysis? Lexical rules are regular and simple. Syntax rules need nesting and recursion. Separating them keeps both parts small, lets the lexer run fast with finite automata, and allows one lexer to serve a parser generator.

Token names, attributes and the symbol table

Common token names are id, num, if, relop and assign. Many texts write them in capitals: ID, NUM, IF, RELOP, ASSIGN. The lexer returns ID for every identifier. The attribute tells the parser which identifier it is. For a number, the attribute is the value, not the digits. For an operator, the token name already says which operator, so the attribute may be absent.

When the lexer sees an identifier, it may enter the name in the symbol table and return a pointer or index as the attribute. Later phases use that entry for type, scope and storage. Whitespace and comments are not tokens. The lexer skips them, but it still tracks line numbers for error messages.

Two rules decide choices. The longest-match rule: choose the longest prefix that forms a lexeme. In x1, read x1 as one ID, not x then 1. In <=, read one RELOP, not < then =. Keyword reservation: keywords such as if are reserved before identifiers. If if matched the ID pattern first, the parser would never see IF.

What the parser receives

The parser's input is a stream of tokens, not characters. For the line if (count <= 10) count = count + 1; the lexer returns token names in order: IF, LPAREN, ID, LE, NUM, RPAREN, ID, ASSIGN, ID, PLUS, NUM, SEMI. The parser does not care that three lexemes are count; it sees ID each time. It uses the attributes when it builds the syntax tree.

Token names depend on the grammar. A language may call <= LE, RELOP or LEQ. The name is for the parser; the lexeme is for the source. Errors at this stage are simple: an illegal character, an unterminated string or a malformed number. The lexer reports the line and column and may skip to a safe point. A lexer error is not a syntax error; it means no token can be formed at that point.

Input buffering is covered in Chapter 1.5. Patterns are written with regular expressions in Chapter 1.6. Parsing is Unit 2; symbol table organisation is Unit 5.

1.5 Input buffering

A lexer must look at one character at a time, but reading each character from disk or a terminal is slow. Input buffering reads a large block of source text into memory and lets the lexer scan it quickly. The common two-buffer scheme uses two half-buffers of N characters each, a sentinel at the end of each, and two pointers: lexemeBegin marks where the current lexeme starts, and forward scans ahead. This chapter shows how forward moves, how a refill works, and why a lexeme can safely cross a buffer boundary.

You need: Chapter 1.4 for tokens, patterns and lexemes.

Why the lexer needs a buffer

The lexical analyzer asks for characters one after another. A disk read or a terminal read is much slower than a register or cache access. If the lexer made one operating-system call per character, most time would go in waiting, not in scanning.

Input buffering reads a block of source text into memory once. The lexer then serves characters from that block. A large block reduces the number of slow reads. The operating system supplies the block; file handling itself belongs to an operating systems course.

The buffer also makes lookahead cheap. A scanner often needs the next character to decide whether an identifier has ended, whether = is part of ==, or whether < is part of <=. With characters already in memory, that lookahead is a pointer move, not another slow read.

Two half-buffers and two pointers

The standard arrangement is two buffers, each of N characters. N is the buffer size in characters; a common choice is a few thousand. The two buffers are used as halves of one logical input stream. At the end of each half sits one extra cell called a sentinel. The sentinel is a marker, not a source character. Some syllabi call this the two-buffer input scheme; the sentinel is also called an EOF marker.

Two pointers move over the buffers. lexemeBegin points to the first character of the lexeme being built. forward points to the next character to examine. Each pointer is a position in one of the two half-buffers: forward is an index into the half-buffer currently being scanned, and lexemeBegin is an index into whichever half-buffer the current lexeme started in, which may be the other half.

The scanner starts with lexemeBegin and forward on the first character. It reads the character at forward and advances forward. When forward reaches a sentinel, the scanner switches to the other half-buffer. If that half still holds characters from the previous block that have already been scanned, it refills it with the next block from the source and sets forward to its first cell. If it already holds the newly loaded next block (as after the initial fill in the example), the scanner only switches. lexemeBegin is not changed during this switch. That is what allows a lexeme to cross a buffer boundary: its start stays in the old half while its end is found in the new half.

Sentinels and boundary crossing

Sentinels turn two boundary tests into one. Without them, the scanner would test for the end of the current buffer and for the end of the input at every character. With a sentinel, it sees one marker value at the buffer end. The marker cannot be part of any token.

The scanning loop has five steps:

  1. Set lexemeBegin and forward to the first character of the input.
  2. Read the character at forward.
  3. If the character is a sentinel: if the source is exhausted, stop; otherwise switch half-buffer (refilling it if it holds already-scanned text), set forward to the first cell of the new block, and go to step 2. If it is not a sentinel, go to step 4.
  4. If the character can extend the current lexeme, advance forward and go to step 2.
  5. If it cannot extend the lexeme, accept the lexeme from lexemeBegin to forward - 1, set lexemeBegin to forward, and go to step 2 for the next token.

A refill must not lose a lexeme. Keep lexemeBegin where it is, copy the next block into the other half-buffer, and move forward to the first cell of that block. If the lexeme began in the old half, the accepted text is still the range from lexemeBegin to forward - 1. The example below uses N = 5, so each half holds five characters plus one sentinel.

1.6 Specification of tokens with regular expressions

A lexical analyzer must decide, for every lexeme, which token class it belongs to. A regular expression is a compact formula that describes exactly the set of strings in one token class. It replaces a long list of examples with a rule the scanner can follow. Compiler writers use regular expressions to specify identifiers, numbers, operators, keywords and comments before any automaton is built. The same notation appears in tools such as LEX, in text search, and in input validation. This chapter shows how to write those specifications and how to read them.

You need Chapter 1.4 for tokens, patterns and lexemes.

Languages and regular operations

An alphabet, written Σ, is a finite set of characters. A string is a finite sequence of characters from Σ. The empty string is ε, the string of length 0. A language is any set of strings over Σ. A regular expression is a pattern, and the language it denotes is a set of strings. The expression a|b denotes {a, b}; it is not the string "a|b".

Three operations build regular expressions. Union: R|S denotes every string in R or in S. Concatenation: RS denotes a string from R followed by a string from S. Kleene closure: R* denotes zero or more copies of a string from R, including ε. Positive closure R+ denotes one or more copies; R+ = RR*. Precedence is closure first, then concatenation, then union. So ab*|c means (a(b*))|c.

Read L(L|D)* as a parse tree. L is a letter or underscore; D is a digit. The root is concatenation. Its right child is closure of the union L|D. So the expression means: one L, then any number of characters that are each L or D.

1.7 Recognition of tokens with transition diagrams

A transition diagram is a flow chart that recognises one token class. Its circles are states; its arrows consume one input character each. The lexer starts at the start state, follows arrows labelled with the current character, and accepts at a double circle. These diagrams turn a regular expression into a step-by-step recogniser for identifiers, numbers, operators and keywords. A scanner uses them, or a table built from them, to cut source text into tokens for the parser.

You need: Chapter 1.6 for regular expressions and token patterns.

States, transitions and accepting states

A state records how much of a token has been read. The start state is where every attempt begins. An accepting state is drawn as a double circle and marks a complete lexeme of that token class. A transition edge from state p to state q labelled c means: in state p, if the next character is c, consume it and move to q. If no edge carries the current character, the attempt fails. A diagram for a single rule recognises one token class. A scanner joins several rules into one diagram by branching from a common start state. It is not a parser and does not check grammar.

Labels use L for any letter, D for any digit, and _ for underscore. A label such as L, D, _ means any one of those characters. Some syllabi call these lexical transition diagrams. Read one by walking it: from the start state, each input character chooses one outgoing edge. Arriving at an accepting state means the characters read so far form a lexeme. The same diagram can be stored as a table, which is how a scanner program runs it.

Diagrams for identifiers, integers, operators and keywords

An identifier begins with a letter or underscore and continues with letters, digits or underscores. Start at q0. An edge labelled L or _ goes to q1. State q1 loops on L, D, _. State q1 is accepting. This accepts rate2 and _x, but not 2rate as one identifier.

An unsigned integer is simpler: q0 on any digit D goes to q2; q2 loops on D; q2 accepts. This accepts 0, 7 and 2024. Relational operators need branching. For <, <= and <>: q0 on < goes to q1. q1 on = goes to an accepting state for LE. q1 on > goes to an accepting state for NE. State q1 is itself accepting, for LT. The lexer backs up to q1 when the next character is not = or >.

A keyword such as if is a short chain: q0 on i to q1, q1 on f to accepting q2. A scanner may instead recognise an identifier and then look the spelling up in a keyword table. Figure 1.7.1 combines identifier and integer recognition from one start state.

Longest match, backup and rule order

Try diagrams in a fixed order: longest match wins, then the earlier rule.

  1. Set state to the start state and last_accept to none.
  2. Read the next character. If an edge from the current state carries it, consume the character, move along the edge, and continue. Record the input position whenever the state is accepting.
  3. When no edge carries the character, or input ends, stop.
  4. If the current state is accepting, return the token ending at the current position. Otherwise return the token ending at last_accept and reset the input to just after that position. If there is no last_accept, report an error.

This rule is the longest match or maximal munch. It explains why rate2 is one identifier, not rate followed by 2, and why <= is one operator, not < then =. Order matters when two diagrams accept the same text. if matches both the keyword diagram and the identifier diagram. List keywords before identifiers, and longer operators before their prefixes. A combined diagram avoids some ordering: separate branches from one start state, and choose the accepting branch with the longest match.

1.8 Finite automata: NFA, DFA, conversion and minimization

A finite automaton is a machine with a fixed set of states. It reads one input symbol at a time and changes state. A DFA allows exactly one move per symbol; an NFA allows several moves and ε-moves. Both recognise the same class, the regular languages. A lexer needs a fast recogniser for token patterns. So we build an NFA from a regular expression, convert it to a DFA, and minimise the DFA.

You need: regular expressions and transition diagrams from 1.6 and 1.7.

DFA and NFA: the two machines

A deterministic finite automaton (DFA) is a 5-tuple (Q, Σ, δ, q₀, F). Q is a finite set of states. Σ is the input alphabet. δ: Q × Σ → Q is the transition function. q₀ ∈ Q is the start state. F ⊆ Q is the set of accepting states. For every state and every symbol there is exactly one next state. To run a DFA, start at q₀, read the input left to right, and follow δ. Accept the string if the last state is in F.

A nondeterministic finite automaton (NFA) is (Q, Σ, δ, q₀, F) with δ: Q × (Σ ∪ {ε}) → 2Q. The symbol 2Q means the set of all subsets of Q. So δ(q, a) is a set of states, not one state. An ε-move changes state without reading a symbol. An NFA accepts a string if some path from q₀ to a state in F spells that string. The NFA may have many paths; the DFA has one.

For a set S of NFA states, ε-closure(S) is every NFA state reachable from a state in S by zero or more ε-moves. For a symbol a, move(S, a) = ⋃p∈S δ(p, a). The next subset after reading a is ε-closure(move(S, a)).

Regular expression to NFA, then to DFA

Thompson construction builds an NFA from a regular expression using small pieces. A symbol a becomes two states with one edge labelled a. For R|S, add a new start with ε-edges to the starts of R and S, and ε-edges from their accept states to a new accept state. For RS, connect the accept state of R to the start of S with an ε-edge. For R*, add a new start and accept; ε-edges go from the new start to the start of R and to the new accept, and from the accept of R back to its start and to the new accept.

Subset construction, also called the powerset construction, turns an NFA into a DFA. Each DFA state is a set of NFA states.

  1. Compute the start DFA state S₀ = ε-closure({q₀}).
  2. For an unmarked DFA state S and each symbol a in Σ, compute T = ε-closure(move(S, a)). If T is new, add it as a DFA state.
  3. Add a transition S --a--> T. Mark S when all symbols are done. Repeat until no unmarked state remains.
  4. A DFA state is accepting if its set contains at least one NFA accepting state.

The DFA can have at most 2n states for an NFA with n states, because each state is a subset. In practice only reachable subsets appear. LEX uses this recogniser to scan tokens; see 1.9.

Minimising a DFA

Minimisation reduces a DFA to the smallest DFA for the same language. The minimal DFA is unique up to renaming states. Fewer states mean a smaller transition table and a faster lexer.

  1. Remove states that cannot be reached from the start state.
  2. Split the remaining states into two groups: accepting states F and non-accepting states Q − F.
  3. For one group, write for each state a tuple with one entry per symbol: the old group that the symbol's transition lands in. States with the same tuple stay together in one new group; states with different tuples go to different new groups. Replace the old group by these new groups. Repeat until no group changes.
  4. Each final group is one state of the minimal DFA. Transitions go to the group of the original target state.

A table-filling method does the same job. Mark pairs of states that are distinguishable. Initially mark a pair if one state is accepting and the other is not. Then mark a pair if some symbol sends them to an already marked pair. Unmarked pairs are equivalent and can be merged.

Do not merge all accepting states automatically. Two accepting states are equivalent only when every symbol sends them to equivalent states. The same rule applies to non-accepting states.

Drop E for the partial DFA.
  8. Minimal DFA: A --a--> B; B --b--> F; B --c--> F; F is accepting.

Answer. The partial DFA has 4 states A, B, C, D. With the dead state E the complete DFA has 5 states. The minimal partial DFA has 3 states A, B, F.

Exam traps

  • Take ε-closure before and after every move. Forgetting the closure after move(S, a) misses NFA states that are reachable without reading input.
  • A subset-construction state is a set of NFA states, not one NFA state. Write braces around it in the transition table.
  • Minimisation merges only equivalent states. Two accepting states are not automatically equivalent; compare where each symbol sends them.
  • A DFA is formally complete: every state has a move for every symbol. If you omit the dead state for a drawing, say that the DFA is partial.
  • The powerset construction can create up to 2n states, but only reachable subsets are built. Do not list all subsets by hand.

Check yourself

Remember Define ε-closure(S) for an NFA. 2 marks

ε-closure(S) is the set of all NFA states reachable from any state in S by zero or more ε-moves.

Understand Why is an NFA usually easier to build from a regular expression than a DFA? 2 marks

An NFA allows several moves and ε-moves, so union, concatenation and star can be built with small local changes. A DFA would need those choices resolved immediately.

Apply NFA: start state 0; 0 --a--> 0; 0 --a--> 1; accept state 1. Use subset construction to build the DFA states and transitions. 4 marks

Start A = {0}. On a, move(A, a) = {0, 1}, so B = {0, 1}. B is accepting. A --a--> B. B --a--> B. The DFA has two states.

Apply Minimise this DFA: states A, B, C; start A is non-final; B and C are final. A --a--> B; A --b--> C; B --a--> B; B --b--> C; C --a--> B; C --b--> C. 4 marks

B and C are both final and have the same targets for a and b, so merge them into F. Minimal DFA: A --a--> F; A --b--> F; F --a--> F; F --b--> F. Two states.

Analyze Two final states in a DFA have the same outgoing symbol labels. Does that prove they are equivalent? Explain. 5 marks

No. They are equivalent only if each symbol sends them to states that are themselves equivalent. Same labels are not enough; compare the target groups.

Remember What is the maximum number of DFA states produced from an NFA with n states by subset construction? 2 marks

At most 2n DFA states, because each DFA state is a subset of the NFA states.

Beyond the syllabus

Not for the exam. Lexer generators such as LEX build a DFA from token regular expressions and then run it as a table-driven scanner. Modern regular-expression engines often use NFAs or hybrids because NFAs avoid the worst-case subset blow-up. Hopcroft's algorithm and Brzozowski's method are standard ways to minimise automata efficiently. Search next for Thompson construction, Hopcroft DFA minimisation, and powerset construction.

1.9 Lexical analyzer generator: LEX

LEX is a lexical analyzer generator. You write rules that pair a regular expression with a C action. LEX turns those rules into a C function, yylex, that reads characters and returns tokens. This removes the hand-work of building a DFA for every scanner. LEX is used in compiler courses and in real tools where a language has many token classes. Flex is a modern compatible version. Two rules decide a match: longest match first, then the earlier rule.

You need: Chapter 1.8 for DFA recognition and Chapter 1.6 for token patterns.

The three sections of a LEX program

A LEX file ends in .l and has three sections separated by %%. The definitions section holds options, name definitions and C declarations. C code inside %{ and %} is copied near the top of lex.yy.c. A name definition looks like DIGIT [0-9]; later you write {DIGIT}+. The rules section is a list of pattern-action pairs. Each pattern is a regular expression; each action is C code inside braces. The user code section holds C functions such as main and yywrap.

LEX supplies variables and functions. yylex() is the scanner function. Calling it returns the next token code or 0 at end of input. yytext is a pointer to the matched lexeme. yyleng is its length as an int. yyin is the input FILE*; yyout is the output FILE*. The default yyin is stdin and default yyout is stdout. A rule with an empty action, such as [ \t\n]+ ;, skips the match because the action does nothing. If no rule matches a character, the default rule ECHO copies that character to yyout. ECHO is useful while testing, but in a finished scanner it can hide a missing rule.

The generated yylex reads characters and runs the longest-match logic. LEX compiles the patterns into a DFA table, so the scanner does not try rules one by one at run time in the simple sense; the table encodes the decision. The rule order still matters when two patterns match the same longest length.

Longest match and rule order

Suppose two rules can match at the current position. LEX takes the one with the longest lexeme. If the lengths are equal, it takes the rule written earlier. This is why a keyword rule should come before a general identifier rule. If if and [a-z]+ are both rules and the input starts with if, both match length 2. The earlier rule wins. If [a-z]+ is earlier, if is an ID and the IF action never runs for that input.

The same logic applies at every position. LEX does not stop at the first rule that can match. It keeps the longest match and then breaks a tie by rule order. A whitespace rule such as [ \t\n]+ ; should be present in a working scanner; otherwise spaces, tabs and newlines hit the default ECHO rule. Remember that yytext points into an internal buffer and is valid only until the next call to yylex. Copy the lexeme if you must keep it.

A small scanner in LEX

This scanner prints token names for keywords, identifiers and integers. The keyword rule is before the identifier rule. The whitespace rule has an empty action, so it skips spaces, tabs and newlines.

%{
#include <stdio.h>
%}
%%
[ \t\n]+      ;
if            { printf("IF\n"); }
[a-z]+        { printf("ID %s\n", yytext); }
[0-9]+        { printf("NUM %s\n", yytext); }
%%
int main(void) { yylex(); return 0; }
int yywrap(void) { return 1; }

Output

IF
ID x
NUM 12

Run lex scanner.l to produce lex.yy.c, then cc lex.yy.c -o scanner. Flex is a compatible modern version; the same file usually works with small changes. The scanner prints IF for if, ID x for x, and NUM 12 for 12. Parser generation with YACC is covered in Unit 3.

Worked example

Question. A LEX scanner has rules in this order: (1) if action IF; (2) [a-z]+ action ID; (3) [0-9]+ action NUM. A whitespace rule [ \t\n]+ ; skips blanks. The input is if x 12. (a) List the tokens and the length of each matched lexeme. (b) Give the number of tokens and the total number of lexeme characters. (c) If rule (2) is moved before rule (1), what token is produced for the first lexeme, and which rule is unused for this input?

  1. At the first character i, rule (1) matches the literal lexeme if with length 2, and rule (2) also matches if with length 2. The longest length is 2, and rule (1) is earlier, so the token is IF with yytext = if and yyleng = 2.
  2. At the next non-blank character x, rule (1) cannot match. Rule (2) matches x with length 1. Rule (3) cannot match. The token is ID with yytext = x and yyleng = 1.
  3. The next non-blank characters are 1 and 2. Rule (3) matches 12 with length 2. The token is NUM with yytext = 12 and yyleng = 2.
  4. The token count is 3. The lexeme lengths are 2, 1 and 2.
  5. The total lexeme length is 2 + 1 + 2 = 5 characters.
  6. If rule (2) is moved before rule (1), at the first character both rules still match if with length 2. The earlier rule is now rule (2), so the token is ID with text if. Rule (1), the IF rule, is unused for this input.

Answer. There are 3 tokens with lexeme lengths 2, 1 and 2, and 5 total lexeme characters. With the identifier rule first, if becomes ID because both rules match length 2 and the earlier identifier rule wins; the IF rule is unused for this input.

Exam traps

  • LEX chooses the longest match first; only when two matches have equal length does it choose the earlier rule. Do not say the first matching rule always wins.
  • The default ECHO rule copies unmatched characters to yyout. A missing rule can therefore look like correct output instead of an error.
  • yytext is a pointer into a buffer that changes on the next yylex call. Copy the string if the token value must be stored.
  • Put keyword rules before the general identifier rule. Otherwise a keyword of the same length is classified as an identifier.
  • yywrap returning 1 means end of input; returning 0 means LEX should get another input file. Mixing these up ends scanning too early or never ends.

Both can match the same keyword with the same length. LEX uses the earlier rule for equal-length matches, so the keyword rule must come first to produce the keyword token.

Analyze A scanner has [0-9]+ action NUM first, then [0-9]+[a-z]+ action ALNUM. The input is 12x. Which rule wins and why? 3 marks

The ALNUM rule wins. At the start, [0-9]+ matches 12 with length 2, while [0-9]+[a-z]+ matches 12x with length 3. Longest match is checked before rule order.

Remember What do yyin and yyout mean in a LEX scanner? 2 marks

yyin is the input FILE* and yyout is the output FILE*. Their defaults are stdin and stdout.

Understand What does the default rule ECHO do, and why can it hide a bug? 3 marks

ECHO copies the unmatched character to yyout. A missing or wrong rule then prints text instead of reporting an error, so the scanner may look as if it is working.

Apply If yytext points to the lexeme 12, what is yyleng? 2 marks

yyleng is 2, the number of characters in the matched lexeme.

Analyze Why should a scanner copy yytext before storing a token value in a symbol table? 3 marks

yytext points into a buffer that LEX reuses on the next call to yylex. Without a copy, the stored pointer can later show a different lexeme.

Takeaways

  1. A compiler translates the whole program before it runs; an interpreter executes it as it reads, so errors show up at different times.
  2. The phases of a compiler form a pipeline: characters become tokens, tokens become a parse tree, the tree is checked and lowered, and finally target code is emitted.
  3. Only the front end depends on the source language and only the back end depends on the target machine, which is why compilers can be retargeted.
  4. The lexical analyzer hides character-level detail from the parser and returns one token per call, with an attribute when the token has a value.
  5. Two half-buffers with sentinels cut the cost of the end-of-buffer check, which matters because a lexer examines every character once.
  6. Regular expressions specify tokens; finite automata recognise them; the two are tied together by Thompson's construction and subset construction.
  7. An NFA is easy to build from a regular expression, a DFA is fast to run, so scanners are generated by converting NFA to DFA and minimising it.
  8. LEX removes the hand-coding of scanners: rules are tried longest-match first, and conflicts are settled by rule order.

Glossary

Assembler
A translator from assembly language mnemonics and labels to machine code and relocatable addresses.
Attribute
Extra information attached to a token, such as the value of a number or a pointer to a symbol-table entry.
Back end
The synthesis part of a compiler: optimisation and target code generation for a particular machine.
Compiler
A program that translates a whole source program into an equivalent target program before execution.
Cousins of the compiler
Other language processors such as the preprocessor, assembler, linker, loader and macro processor.
DFA minimisation
Merging indistinguishable DFA states by partition refinement until no block can be split.
Finite automaton
A five-tuple of states, alphabet, transitions, start state and accepting states used to recognise regular languages.
Front end
The analysis part of a compiler: lexical, syntax and semantic analysis plus intermediate code generation.
Interpreter
A program that executes source or intermediate code directly, without first producing a target program.
LEX
A tool that converts regular-expression rules and actions into a C lexical analyzer.
Lexeme
The concrete character string in the source that matches a token pattern.
Lexical analyzer
The compiler phase that reads characters and returns tokens to the parser, skipping whitespace and comments.
Linker
A program that merges object files and library code into one executable and resolves external symbols.
Loader
A program that places an executable image in memory, relocates it and transfers control to it.
Macro processor
A processor that replaces a named macro call by its body, with arguments substituted.
Object code
The relocatable machine-code output of an assembler or compiler, not yet linked into an executable.
Pass
One complete reading of the source program or its intermediate representation.
Pattern
A rule, normally a regular expression, describing all lexemes of one token class.
Preprocessor
A text-level processor that expands macros and includes files before the compiler proper sees the source.
Regular expression
A notation using symbols, union, concatenation and closure to describe a set of strings.
Sentinel
A special end-of-buffer character that removes one comparison from the per-character scan loop.
Subset construction
The NFA-to-DFA conversion in which each DFA state is a set of NFA states.
Token
A token name with an optional attribute value, the unit of input to the parser.
ε-closure
The set of states reachable from a state using epsilon transitions only.
