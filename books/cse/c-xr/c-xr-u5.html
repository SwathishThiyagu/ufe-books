5.1 3D manipulation tasks and techniques

3D manipulation lets a user select a virtual object and change its position, orientation or size. The task is what changes; the technique is how the user changes it; the constraint is what motion is allowed. Good manipulation keeps the hand-to-object mapping predictable, adds constraints so motion stays useful, and gives feedback at once. It is used in VR design reviews, surgical rehearsal, AR furniture placement and telerobotics. This chapter separates task, technique and constraint, then gives the ray-selection calculation and the main design rules.

You need: input device characteristics from Unit 2 and transformation matrices from Unit 4; the scene-graph view of transforms is in 5.4.

Manipulation tasks and degrees of freedom

3D manipulation has two parts: the task and the technique. The task says what must change. Selection identifies an object. Translation changes position. Rotation changes orientation. Scaling changes size. A full rigid object has six degrees of freedom, 6 DOF: three translations along x, y, z and three rotations about x, y, z.

Degrees of freedom (DOF) count the independent quantities a user can change. A door hinge is a 1 DOF rotation. A slider on a rail is a 1 DOF translation. Dragging on a table top is a 2 DOF task. Scaling adds up to three values, one per axis. More DOF gives freedom but makes control harder.

A constraint removes some DOF: lock motion to an axis, to a surface or to a plane. Snap replaces continuous motion with fixed steps, such as a 0.10 m grid or 15° rotation steps. Constraints and snap make precise placement possible with a noisy hand tracker.

The user confirms the change by releasing a trigger, pressing a button or making a gesture. Until confirmation, the object is held. Undo must be available because a wrong transform is easy to make.

Techniques: direct hand, ray, Go-Go and HOMER

Direct virtual hand maps the tracked hand position to a virtual hand. The object follows when the hand touches it. It is natural for objects within arm reach. It fails for distant objects.

Ray casting shoots a ray from the hand or controller. The ray selects the first object it hits. After selection, the user can pull the object along the ray, or attach it and then move. Ray casting works at a distance but gives poor depth judgement.

t = (c − p)·u, q = p + t u, d = ||c − q||

p is the ray origin, u is the unit ray direction, c is the object centre, t is the projection along the ray, q is the closest point on the ray, and d is the perpendicular distance from the ray to c. A sphere of radius R is selected when t ≥ 0 and d ≤ R.

Go-Go extends reach with a threshold D_th and gain k. For real hand distance D_r from the tracking origin, the virtual hand distance is D_v = D_r when D_r ≤ D_th, and D_v = D_th + k(D_r − D_th) when D_r > D_th. Beyond the threshold the virtual hand moves faster than the real hand.

HOMER combines ray selection and hand manipulation. The user selects with a ray, then the object attaches to the hand at a fixed offset. Moving the hand moves the object with better control than ray dragging. The offset must stay constant, otherwise the object jumps at pick-up.

World-in-miniature, props, haptics and design rules

World-in-miniature (WIM) shows a small copy of the whole scene in front of the user. The user moves the miniature object or the miniature viewpoint; the change applies to the full-size world. WIM is good for large scenes and for objects out of reach. The mental mapping between small and large must be clear.

Props are tracked physical objects, such as a pen, a handle or a cube. A haptic handle adds force feedback, so the user feels a stop at a limit or the weight of a tool. Props reduce fatigue because the arm can rest, and they give passive haptic cues. They need calibration to the virtual object.

Two-handed manipulation uses one hand to anchor or select and the other to rotate or scale. This is useful for inspection and assembly. Design rules: give immediate visual feedback (highlight, ghost, shadow); set gain so small hand motions make large object motions only when needed; use a threshold or dead zone to stop jitter; avoid long mid-air holds that tire the shoulder; keep the mapping between hand and object stable.

Input device choice follows Unit 2. A 6 DOF controller suits 6 DOF transforms; a data glove suits direct hand interaction; a haptic device suits guided assembly. Usability checks for these choices are in 5.8.

Worked example

Question. A controller ray starts at (0, 0, 0) and points along (0, 0, −1). A sphere has centre (0.10, 0, −2.00) m and radius 0.15 m. Find the perpendicular distance from the ray to the centre and say whether the ray selects the sphere.

  1. Ray origin p = (0, 0, 0), unit direction u = (0, 0, −1), sphere centre c = (0.10, 0, −2.00) m, radius R = 0.15 m.
  2. Vector from ray origin to centre: w = c − p = (0.10, 0, −2.00) m.
  3. Projection along the ray: t = w·u = 0.10×0 + 0×0 + (−2.00)×(−1) = 2.00 m. t is positive, so the centre is in front of the ray.
  4. Closest point on the ray: q = p + t u = (0, 0, 0) + 2.00(0, 0, −1) = (0, 0, −2.00) m.
  5. Offset from the ray to the centre: c − q = (0.10, 0, 0) m.
  6. Perpendicular distance: d = √(0.10² + 0² + 0²) = 0.10 m.
  7. Compare d = 0.10 m with R = 0.15 m. d ≤ R, so the ray intersects the sphere and selects it.

Answer. The perpendicular distance is 0.10 m; the ray selects the sphere because 0.10 m < 0.15 m.

Exam traps

  • Ray selection tests perpendicular distance d, not the distance t along the ray. A far object on the ray can be selected; a near object off the ray cannot.
  • 6 DOF means three translations plus three rotations. Scaling is a separate transform with up to three values.
  • Go-Go is 1:1 only up to the threshold; beyond it the gain k applies.
  • HOMER keeps a fixed offset after ray selection; the object is not dragged by the ray for the whole task.
  • A constraint limits motion; snap forces discrete values. They solve different precision problems.

5.2 Travel and wayfinding techniques

Travel changes the viewpoint through a virtual world. Wayfinding is the user's plan for where to go and how to stay oriented. The two work together: a fast travel method is useless if the user cannot decide the next turn. Virtual campuses, VR training rooms and AR walking guides all need both. Some syllabi call the whole topic navigation; this chapter keeps travel, the movement, separate from wayfinding, the knowledge and aids that guide movement.

You need Chapter 5.1 for manipulation versus travel, and Unit 2 for trackers that measure head and hand motion.

Travel tasks and techniques

Travel is the control of the viewpoint. The user moves through the scene, while objects stay fixed. A travel technique has a selection method (where to go) and a motion method (how to get there). Three travel tasks cover most exercises. Exploration has no fixed target; the user learns the layout. Search has a target, such as a fire exit. Manoeuvring is small, precise motion, such as lining up with a door handle.

  • Physical walking maps real steps to virtual motion. It feels natural but needs tracked floor space.
  • Steering gives continuous control through a joystick, hand direction or gaze. It is like driving.
  • Fly adds vertical control. It suits open 3D scenes but can cause discomfort.
  • Gaze-directed travel moves where the head or eyes point. Hands stay free, but small gaze shifts cause drift.
  • Point-and-go selects a far point and then moves the user there. It reduces continuous input.
  • Teleport jumps to a marked place. It is fast and reduces motion sickness, but it weakens the sense of continuous space.
  • World scaling changes the apparent size of the world or the user, so a small tracked area can cover a large virtual campus.

Choose by task. Use teleport or point-and-go for long searches; use physical walking or slow steering for precise manoeuvring. The worked example below uses a simple map, not a headset, to show route length versus straight-line distance.

Wayfinding: knowledge, support and evaluation

Wayfinding is the cognitive side of navigation. The user decides a route, keeps orientation and recognises the destination. Three ideas from spatial cognition help. A landmark is a salient object used as a reference. Route knowledge is a sequence of turns along a path. Survey knowledge is a map-like view of the whole area. Users often learn route knowledge first and survey knowledge later, so a virtual world should support both.

  • Maps and minimaps show position; a north-up map is stable, a forward-up map matches the view.
  • Signs and labels at decision points give the next action, such as 'Exit B, 20 m'.
  • Guides, arrows, audio cues or a virtual agent point the way; they must be removable.
  • Layout with clear paths, open sightlines and short decision points reduces wrong turns.
  • Lighting makes exits, stairs and landmarks visible without glare.
  • Distinct landmarks and district colours at junctions help users build survey knowledge.

Evaluate aids by time to target, wrong turns, map checks, layout recall and confidence. Test new users, not only the design team. A minimap may shorten perceived effort while the physical path stays the same. Keep signs consistent, show 'you are here', do not rely on colour alone, and allow aids to be switched off.

Matching travel and wayfinding aids

Match the travel method to the wayfinding aid. A large campus with many destinations suits teleport plus a minimap and repeated landmarks. A training bench suits physical walking or slow steering, because small hand and body motions matter. A search task suits point-and-go plus a sign at the target. Reduce discomfort by using snap turns, teleport or limited acceleration, and see Chapter 5.7 for health checks. Keep one aid per decision point. Too many arrows hide the landmarks that users need for survey knowledge. The worked example compares the walked route with the straight-line distance; the dashed edge in the figure is that shorter distance.

Design the world and the interface together. If the map shows a shortcut, the world must allow it. If a sign says 'East Wing', the east wing must be visible from that point. Test the aid with a new user who has not seen the map. Ask the user to point to the start after reaching the target; this checks survey knowledge, not just route following.

Worked example

Question. A virtual campus has the user at (0, 0) m on a map. The user walks 3 m east, then 4 m north. Compute the straight-line distance from start to final point and compare it with the route length.

  1. Start S = (0, 0) m. After walking east, E = (3, 0) m. After walking north, F = (3, 4) m.
  2. Route length = 3 m + 4 m = 7 m.
  3. Horizontal change Δx = 3 − 0 = 3 m. Vertical change Δy = 4 − 0 = 4 m.
  4. Straight-line distance d = √(Δx² + Δy²) = √(3² + 4²) m = √(9 + 16) m = √25 m = 5 m.
  5. Route is longer by 7 − 5 = 2 m. Route divided by straight-line distance is 7 ÷ 5 = 1.4.

Answer. The straight-line distance is 5 m; the walked route is 7 m, which is 2 m longer.

Exam traps

  • Route length is not straight-line distance. A 3 m + 4 m walk has route 7 m but straight-line 5 m.
  • Travel is movement; wayfinding is the decision of where to move. A map does not move the user.
  • Physical walking is natural but limited by tracked space; teleport covers large distances but can break continuous spatial knowledge.
  • User-centred aids are added to the interface (map, sign, guide). Environment-centred aids are built into the world (layout, lighting, landmarks).
  • Gaze-directed travel uses head or eye direction continuously; point-and-go selects a target and then moves. Do not swap them.

5.3 System control: menus, voice and gesture commands

System control changes the application itself, not a scene object. It loads a scene, saves work, changes a mode, opens help or quits. Menus, voice commands, gesture commands and mixtures of these carry such commands. The idea exists because a user must run the whole XR application, not only move a virtual cube. You meet it in a VR training app that switches lessons, in an AR repair guide that jumps to the next step, and in a headset home screen that changes settings. Some syllabi call this command and control.

You need: Chapter 5.1 for selection and object manipulation, and Unit 2 for input devices and gesture hardware.

System control versus scene control

System control is a command that changes the application state. Examples are load scene, save work, change a setting, open help, undo and quit. It does not change a scene object. Chapter 5.1 covers object selection and manipulation. Chapter 5.2 covers travel. The same hardware can do both jobs. In an AR repair guide, pinching a virtual bolt turns the model: scene control. Saying “next step” changes the lesson: system control. The meaning of the command decides the class, not the device. Classify system control by channel: graphical menus, voice, gesture and multimodal. A small command set may use one channel. A large set needs menus or a mix. A command may open a menu, and the menu item is a second command. Keep system commands few and named clearly. Some syllabi call this command and control.

Graphical menus

Graphical menus show commands as visible choices. A 2D menu sits on a flat panel in the headset or on a controller screen. It is stable, legible and familiar; use it for settings. A 3D menu places choices in space around the user or on a virtual object. It uses depth and spatial memory, but watch occlusion, reach and text size. A pie menu puts items around a circle. The user points or flicks toward a sector; the chosen sector highlights. Pie menus are fast for small sets. A marking menu is a pie menu that can hide labels after the user learns stroke directions. A novice presses and sees the pie; an expert draws the mark directly. Steps for a pie menu: open with a button or gesture; aim at a sector; release to choose. Give feedback on the highlighted item before release.

Voice and gesture commands

Voice commands use a grammar: a list of allowed words and patterns, such as “open scene” or “set mode”. Keep phrases short and distinct. Use push-to-talk or a wake word to avoid false activation. Ask for confirmation before destructive commands: “delete all, yes or no”. For error recovery, show the recognised text, repeat the prompt, offer alternatives and allow undo. Speech recognition returns a confidence score; a low score should trigger a retry. Gesture commands are either pose or motion. A pose is a static hand shape, such as a thumbs-up. A motion is a path over time, such as a swipe. Delimiting marks the start and end: a dwell, a pinch, a button press or a fixed start pose. Without delimiting, normal hand movement triggers commands. Choose gestures that are distinct from object manipulation gestures. Tools include menu toolkits, speech SDKs and gesture recognisers.

Multimodal fusion and design rules

Multimodal system control uses more than one channel. Fusion combines the evidence into one command. Complementary input: voice says “move this” while the hand points to the target. Redundant input: say “confirm” and press a button. Late fusion combines channel decisions inside a short time window. If channels disagree, use a priority rule or ask the user; show the fused command before it runs. Weight by command counts; do not average rates across unequal counts. Design rules: show the current mode; give visual and audio feedback; make commands discoverable with help and hints; stop false activation with thresholds, confirmation and undo.

S = Σ c_i s_i, r = S / Σ c_i

c_i is the number of commands on channel i; s_i is that channel’s success rate; S is the total number of successful commands; r is the overall success rate.

Worked example

Question. An app accepts voice and gesture. In 100 commands, 70 are voice, 20 gesture and 10 menu. Voice succeeds 90% of its commands, gesture 80%, menu 100%. Compute total successful commands and overall success rate.

  1. Voice successes = 70 × 90/100 = 63 commands.
  2. Gesture successes = 20 × 80/100 = 16 commands.
  3. Menu successes = 10 × 100/100 = 10 commands.
  4. Total successes = 63 + 16 + 10 = 89 commands.
  5. Overall success rate = 89/100 × 100 = 89%.

Answer. The app completes 89 successful commands, so the overall success rate is 89%.

Exam traps

  • Do not average success percentages across unequal command counts. Weight by the number of commands on each channel, as in 70 voice, 20 gesture and 10 menu commands.
  • System control changes the application; object manipulation changes a scene object. Rotating a virtual bolt is scene control, while saying “next step” is system control, even if both use a hand gesture.
  • A pie menu shows items around a circle. A marking menu uses a remembered stroke direction and may hide labels. They are related but not the same exam answer.
  • Voice grammar is not the speech recogniser itself. The grammar limits allowed phrases; the recogniser maps audio to words and returns confidence.
  • Pose and motion gestures differ: a pose is a static hand shape, while a motion is a path over time. Delimiting is needed for both to avoid false activation.

5.4 VR toolkits and scene graphs

A scene graph is a tree that stores a virtual world as nodes. Each node holds a transform, geometry, material, camera or light. A toolkit walks the tree, combines parent and child transforms, and draws only what the current camera can see. The idea exists because a flat list of objects makes transforms, state changes and culling hard to manage. It is used in VR engines, AR SDKs, simulators and 3D modelling tools. The tree gives one clear order for updates, drawing and collision checks.

You need: object hierarchies and transformation matrices from Unit 4, Kinematics modeling, plus basic vectors and coordinates.

Scene graph as a retained tree

A scene graph is a retained-mode description of a world. The application builds nodes once, keeps them, and the toolkit redraws the world from those nodes every frame. A node is a record. It may be a group, a transform, a geometry mesh, a material, a camera or a light. Group and transform nodes have children; leaf nodes hold drawable data or view data.

  • Group node: orders children and applies no geometry itself.
  • Transform node: stores translation, rotation and scale for its subtree.
  • Geometry node: stores vertices and faces; material node stores colour, texture and shader state.
  • Camera and light nodes: define view and illumination.

The toolkit traverses depth first. It pushes a parent transform, composes it with the child transform, reaches a geometry node, sets its material and draws it. The same order fixes state changes: if node A sets a red material and node B does not set a material, B may inherit red. Toolkits save and restore state or use state sorting to avoid this leak. Each node can also carry a bounding volume, a simple box or sphere around its contents. A camera frustum test rejects whole subtrees, so culling is cheap.

Local and world transforms

Local coordinates are measured in a node's own frame. World coordinates are measured in the scene frame. A point p local in node M becomes world by applying every transform from the root down to M, in that order.

p_world = T_T × T_M × p_local

p_world is the point in world coordinates; p_local is the point in M's local frame; T_T is the transform of T, M's parent; T_M is the transform of M.

  1. Start with the scene root. Here the root is identity, so its frame is the world frame.
  2. Apply T's translation of +2 m on x: T's origin is at world x = 2 m.
  3. Apply M's translation of +3 m on x: M's origin is at world x = 2 + 3 = 5 m.
  4. Add the point's local x = 1 m: world x = 5 + 1 = 6 m.

For pure translations the numbers add, so this example checks frame order, not arithmetic order. With rotation or non-uniform scale, matrix order changes the result.

Toolkits and scene models

Unity uses a scene made of GameObjects. A GameObject has a Transform and components. Components attach geometry, materials, cameras, lights and scripts. A prefab is a reusable saved GameObject subtree. Instantiating a prefab copies the tree and keeps links to the asset. Unity and Unreal are engines in Chapter 5.5.

Unreal Engine uses a level made of Actors. An Actor is an object with a transform and components. A level is the scene graph; Blueprints and C++ classes define behaviour. Scripts attach behaviour, covered in Chapter 5.6.

OpenSceneGraph is a C++ toolkit built directly around a scene graph. Nodes include group, transform, geode and state set. It is used in simulators and visualisation where a program needs explicit control of traversal and culling.

VRML and X3D are file formats that describe a scene graph for web or interchange. A VRML or X3D file stores nodes for transforms, shapes, materials, lights and viewpoints. Only a few universities teach X3D in detail; most teach the same tree idea through an engine. AR SDKs such as ARCore, ARKit and Vuforia also keep a retained graph of trackables, anchors and models. Their tracking and display details are in Unit 6.

Worked example

Question. A scene graph has root S. S has child T with translation +2 m on x and child Camera. T has child M with translation +3 m on x. M has a point P at local coordinates (1, 0, 0) m. The scene root has identity transform. Compute the world x coordinate of P.

  1. Root S is identity, so its frame is the world frame.
  2. T translates +2 m on x relative to S. T's origin is at world x = 2 m.
  3. M translates +3 m on x relative to T. M's origin is at world x = 2 + 3 = 5 m.
  4. P has local x = 1 m in M. World x = 5 + 1 = 6 m.

Answer. The world x coordinate of P is 6 m.

Exam traps

  • Parent transform applies before child transform. Write T_T × T_M × p_local, not T_M × T_T × p_local.
  • Local coordinates belong to the node's own frame; world coordinates belong to the scene root. Do not mix them in one vector.
  • A scene graph is not the rendering pipeline. The graph stores the world; the pipeline turns triangles into pixels.
  • Inherited state can leak between siblings. A material set in one branch may affect a later sibling unless the toolkit saves and restores state.
  • A bounding volume must enclose the real geometry. A box that is too small culls visible objects; a box that is too large wastes draw calls.

5.5 Game engines: Unity and Unreal Engine

A game engine is a software suite that turns models, textures, scripts and lights into a running VR or AR application. Unity and Unreal Engine are two common choices. Each gives an editor, a scene or level model, an asset pipeline, lighting tools, a scripting system and a build path to a headset or phone. The engine does not replace modelling or rendering theory; it packages those steps so a small team can assemble, test and ship an interactive 3D scene. This chapter compares their main objects and workflow, then shows how batching affects draw calls.

You need: Chapter 5.4 for scene graphs and Unit 4 for the rendering pipeline.

The engine as an editor and a scene model

A game engine is the workshop, not the theory. The editor is the authoring window where you place objects and set values. Unity organises a scene as a tree of GameObjects. A GameObject is a named object in the scene; it has no visible shape by itself. A Component is a block of data or behaviour attached to a GameObject. The Transform component stores position, rotation and scale. A Mesh Renderer component draws a mesh. A C# script component adds custom behaviour. A Prefab is a saved GameObject template that you can reuse across scenes. A Scene is one level or environment. The Asset Store is a marketplace of ready-made assets and tools. Unreal Engine uses a Level as the scene, an Actor as an object placed in it, and Components attached to the Actor. A Blueprint is a visual script graph; C++ is used for custom or performance-critical code. The editor runs the scene, updates components each frame, feeds input to scripts and sends draw commands to the GPU. A scene graph from Chapter 5.4 is the underlying idea; the engine adds editing, assets and build tools. Some syllabi call this game engine development.

Assets, materials, lighting and build

An asset pipeline moves a model from a modelling tool into the engine. Export a mesh from Maya, 3ds Max or Blender, usually as FBX or glTF. A mesh is the object's geometry. Import it into the engine. The engine creates a mesh asset and a material slot list. A material is a shader plus values: base colour, roughness, metalness and textures. A shader is a small GPU program that computes surface shading. Shading decides how light reflects from the surface. Lighting can be real-time or baked. Baked lighting precomputes light falling on static objects and stores it in lightmaps; it is cheap at run time but does not move. Real-time lights update every frame and cost more. A camera projects the 3D scene to a 2D image. In perspective projection, distant objects look smaller and parallel lines meet at a vanishing point. In orthographic projection, parallel lines stay parallel and size does not fall with distance. VR uses two perspective cameras, one per eye, with a small eye separation to give stereo depth from two slightly different images. AR on a phone uses the rear camera image plus a virtual perspective camera matched to the phone camera. Build settings choose the target: a standalone headset, a PC-tethered headset or a phone. The build step compiles scripts, packs textures, selects the graphics API, the interface to the GPU, and produces an installable app.

Workflow and performance: draw calls and batching

Unity workflow: create a Scene, import assets, drag a Prefab into the Scene, attach C# scripts, set materials and lights, bake static lighting, then build. Unreal workflow: create a Level, place Actors, add Components, write Blueprint logic or C++, set materials and lights, build lighting, then package. Unity is often chosen for quick iteration, mobile AR and a large Asset Store. Unreal is often chosen for high-fidelity rendering and visual Blueprint prototyping. Both can target VR headsets through OpenXR, a cross-vendor XR API; for phones, AR is built with ARCore or ARKit (Unity AR Foundation, Unreal's ARCore/ARKit plugins). Performance is dominated by draw calls, fill rate and CPU work. Fill rate is pixels shaded per second. A draw call is one command from the CPU to the GPU to draw a mesh with a material and render state. Render state includes depth and blend settings. Batching combines meshes that share material and state into fewer draw calls. If a batch can hold at most B objects of one material, and nᵢ objects use material i, then:

draw calls = Σ ceil(nᵢ / B)

Σ means sum over materials i; nᵢ is the number of objects with material i; B is the maximum objects per batch; ceil rounds up to a whole batch. Perfect batching means all objects with the same material fit into the fewest possible batches.

Perfect batching needs shared material and compatible render state. If materials differ, the engine must split batches. The worked example below applies this formula.

Worked example

Question. A Unity scene has 60 cubes in 3 materials, 20 cubes per material. A batch holds at most 15 cubes of one material. Find the number of draw calls with perfect batching and with no batching.

  1. Cubes per material: nᵢ = 60 ÷ 3 = 20 cubes.
  2. Batches per material: ceil(20 ÷ 15) = ceil(1.333) = 2 batches.
  3. Total batched draw calls: 3 materials × 2 batches per material = 6 draw calls.
  4. With no batching, each cube needs its own draw call: 60 cubes × 1 draw call per cube = 60 draw calls.

Answer. With perfect batching the scene needs 6 draw calls, and with no batching it needs 60 draw calls.

Exam traps

  • Draw calls are not one per object when batching works; batching needs a shared material and compatible render state.
  • Batch capacity applies per material, not to the whole scene: 20 cubes of one material with capacity 15 need 2 batches.
  • A GameObject or Actor is not the visible mesh; the mesh is an asset drawn by a renderer component.
  • Baked light is not live: baked lights do not move or change at run time.
  • Orthographic projection does not make far objects smaller; perspective projection does.

5.6 Scripting interactions and physics in C#

A C# script is code attached to a scene object in Unity; C# is the language Unity uses for behaviour. The script reads input, decides what should happen, and asks the physics engine to move objects under rules. Animation alone repeats a fixed path. Scripts react to the user and to collisions, so a virtual ball can be thrown, a door can open, or a controller can buzz when a tool hits a wall. The physics engine owns mass, force and collision; the script owns intent. This chapter explains that loop and the units that keep it correct.

You need: Chapter 5.5 on Unity, and Unit 4 kinematics on force, mass and collisions.

Lifecycle and input: when code runs

Unity calls methods on a MonoBehaviour script in a known order. Awake runs once when the object is loaded, before Start; use it to cache references. Start runs once before the first frame. Update runs once per rendered frame; read input and move non-physics visuals there. FixedUpdate runs on a fixed physics step, 0.02 s by default (50 Hz); apply forces there. OnTriggerEnter runs when another collider enters a trigger. A collider is the shape used for contact; a trigger is a collider that reports overlap without blocking.

Input polling reads a device every frame: Input.GetButtonDown("Fire1") is true on the frame the button goes down. Events invert this: one script raises a C# event or UnityEvent, and listeners react without checking every frame. A coroutine is a method that can pause: yield return null waits one frame, yield return new WaitForSeconds(0.1f) waits 0.1 s. A raycast tests a line against colliders; Physics.Raycast(origin, direction, out hit, distance, layerMask) returns the first hit. A layer mask includes only chosen layers, so a controller ray can ignore the user's hands or a menu. Selection and travel use these tools; see 3D manipulation and travel.

Physics: mass, force and collision

A Rigidbody is the component that lets the physics engine move an object. It stores mass in kg, velocity in m/s and drag. A collider gives the body a shape for contact: box, sphere, capsule or mesh. A trigger collider reports overlap but applies no push. A joint connects two bodies, for example a hinge for a door or a fixed joint for a grabbed tool.

Force changes momentum. For a constant force over a short contact time, impulse is J = F Δt. For a body of mass m starting at rest, J = m v, so v = J/m. Unit check: 1 N·s = 1 kg·m/s. The engine detects contacts in FixedUpdate, computes contact impulses from mass and material properties, then updates positions. Call AddForce in FixedUpdate; AddForce in Update gives different motion at different frame rates. Use ForceMode.Impulse for a kick and ForceMode.Force for a steady push.

J = F Δt = m Δv

J is impulse in N·s; F is force in N; Δt is contact time in s; m is mass in kg; Δv is change in velocity in m/s.

A small interaction script

Small script, clear jobs. The script reads the trigger, applies one impulse, and fires haptics on contact. It does not set position every frame, because that fights the physics engine.

using UnityEngine;

public class PushCube : MonoBehaviour
{
    public float impulse = 1.6f;
    Rigidbody rb;
    bool fire;

    void Start()
    {
        rb = GetComponent<Rigidbody>();
    }

    void Update()
    {
        if (Input.GetButtonDown("Fire1"))
            fire = true;
    }

    void FixedUpdate()
    {
        if (fire)
        {
            rb.AddForce(Vector3.forward * impulse, ForceMode.Impulse);
            fire = false;
        }
    }

    void OnTriggerEnter(Collider other)
    {
        if (other.CompareTag("Wall"))
        {
            // call the toolkit's haptic pulse here
        }
    }
}

Start caches the Rigidbody. Update sets a flag when Fire1 is pressed. FixedUpdate applies the 1.6 N·s kick once and clears the flag, so the force is applied in physics time, not frame time. OnTriggerEnter checks the tag and calls haptics. For a repeated buzz, start a coroutine that sends a pulse, waits, then sends zero. Keep haptic calls short; long vibration hides other feedback and drains the controller. Some syllabi call this VR programming; the pattern is input, script, physics, display.

Worked example

Question. A Rigidbody cube of mass 0.8 kg starts from rest. A horizontal impulse of 1.6 N·s is applied. Find its speed just after the impulse and the distance it travels in the next 0.5 s with no friction.

  1. Given: mass m = 0.8 kg, impulse J = 1.6 N·s, initial speed u = 0 m/s, time t = 0.5 s.
  2. Impulse changes momentum: J = m(v − u). With u = 0, J = m v.
  3. Solve for speed: v = J / m = 1.6 / 0.8 = 2.0 m/s.
  4. After the impulse there is no horizontal force and no friction, so speed stays 2.0 m/s.
  5. Distance at constant speed: s = v t = 2.0 × 0.5 = 1.0 m.

  • Impulse is force × time, not force. Its unit is N·s, and 1 N·s = 1 kg·m/s.
  • Use FixedUpdate for AddForce. Applying the same force in Update gives different motion when the frame rate changes.
  • A trigger collider reports overlap but does not block motion. Use a non-trigger collider when you need collision response.

5.7 Human factors, health and safety in VR

VR can make users uncomfortable or unsafe. A headset covers the eyes, adds weight to the head, and shows a moving scene that may not match the body's sense of balance. Latency, flicker, wrong interpupillary distance and focus conflicts can cause eye strain, headache or nausea. Shared headsets add hygiene risk. Cables and standing use add falls and collisions. Designers therefore check comfort, set a safety boundary, plan breaks and provide an emergency stop. Some syllabi call this health and safety. The same checks are used in training, therapy, games and virtual meetings.

You need: stereoscopic displays and the human visual system from Unit 3, and travel from Chapter 5.2.

Discomfort has physical causes

Cybersickness is a set of symptoms such as nausea, sweating, headache, eye strain and dizziness that some users feel in VR. It is close to motion sickness. The common cause is a conflict between senses: the eyes see motion, but the body feels no motion. Long latency, flicker and a narrow field of view make it worse. Motion-to-photon latency is the time from a real head movement to the matching change of light from the display. A useful target is 20 ms or less. Above that, the virtual world lags behind the head and the brain notices.

Vergence-accommodation conflict (VAC) happens because each eye turns to a virtual distance (vergence) while the lens focuses on the fixed screen distance (accommodation). The brain expects these distances to agree. Objects placed far from the display focus plane strain the eyes. Interpupillary distance (IPD) is the distance between pupil centres, about 63 mm for many adults. A headset must match it; a wrong IPD gives blur, double images and tired eyes. Field of view (FOV) is the angular width the display covers. A small FOV feels like looking through a tube and can increase disorientation. Fatigue comes from headset weight, tight straps, long fixed focus and repeated arm movement.

Safety, hygiene and session control

Set a physical safety boundary before use: clear about 2 m × 2 m for standing, or mark a seated zone. A safety boundary (some systems call it a guardian or chaperone) shows walls or a grid when the user nears the edge. Seated use removes walking risks but not arm collisions. Standing use needs a clear floor, no loose cables, and a spotter for first-time users. Start with 10 to 15 minutes of use. A simple 45-minute plan is 5 minutes setup, 15 minutes VR use, a 5-minute break, 15 minutes VR use and 5 minutes rest. Stop at the first sign of sweat, nausea or headache.

Tracking loss means the headset cannot find its position or orientation. If tracking is lost, freeze the view, show a message and ask the user to stand still. Never let the scene jump. An emergency stop is a visible button, voice command or hand gesture that pauses the app at once and shows a message asking the user to stop moving and remove the headset. The physical action of taking the headset off is done by the user or the spotter, not by the app. Hygiene matters for shared headsets: use disposable face masks, wipe the facial interface with alcohol, and clean hands before and after use. Do not share earphones without covers. Check the boundary and the stop control before every session.

Worked example: latency budget

Latency is a budget. Each stage adds delay, and the user feels the sum. Render time alone is not the full delay.

L = t<sub>sensor</sub> + t<sub>sim</sub> + t<sub>render</sub> + t<sub>display</sub>

L is motion-to-photon latency in ms; tsensor is tracking sample and transfer delay in ms; tsim is simulation and interaction update delay in ms; trender is scene drawing and GPU work delay in ms; tdisplay is panel response and scan-out delay in ms.

Worked example

Question. A VR system has sensor delay 3 ms, simulation 6 ms, render 9 ms and display 2 ms. Compute motion-to-photon latency. Does it meet a 20 ms target?

  1. List the four delays: sensor = 3 ms, simulation = 6 ms, render = 9 ms, display = 2 ms.
  2. Add sensor and simulation: 3 ms + 6 ms = 9 ms.
  3. Add render: 9 ms + 9 ms = 18 ms.
  4. Add display: 18 ms + 2 ms = 20 ms.
  5. Compare with the target: 20 ms ≤ 20 ms, so the system meets the target exactly. If the rule were strictly below 20 ms, it would fail.

Answer. Motion-to-photon latency is 20 ms, so it meets a 20 ms target exactly; it has no margin.

Exam traps

  • Motion-to-photon latency is the sum of sensor, simulation, render and display delays. Render time alone is only one part.
  • A 90 Hz display has a frame period of about 11.1 ms, but that is not the same as latency. Frame rate and latency are different numbers.
  • Cybersickness is not a sign of weak character. It is a sensorimotor conflict, and it can appear in experienced users after a new scene or a tracking fault.
  • A wrong IPD causes blur and eye strain. It does not cause tracking drift; drift comes from tracking sensors and calibration.
  • A break is not a substitute for a safety boundary. The user can still hit a wall or a person during the first minute.

5.8 Usability guidelines and evaluation of 3D interfaces

Usability evaluation checks whether a 3D interface is learnable, efficient and comfortable. It asks real users to do real tasks and records what happens. The aim is not to prove a design is good but to find where it fails before release. VR menus, AR assembly guides, surgery simulators and training applications all use it. A design can look impressive and still be slow, confusing or tiring. Evaluation turns opinion into evidence: task success, time, errors and comfort. This chapter covers guidelines, methods and metrics, and ends with a small comparison of two menu designs.

You need: selection and manipulation, travel, system control, and human factors, plus basic averages.

Guidelines for a 3D interface

A usability guideline is a design rule that protects the user from a known failure. In 3D it must cover the body as well as the screen. The six rules below are a practical checklist.

  • Visibility: the user can see what can be done. Menus sit in a readable place, targets are large enough, and current state is visible. In a VR menu, keep the selected item highlighted and within the field of view.
  • Feedback: every action gives a reply. A grabbed object follows the hand, a button changes colour, and a failed selection gives a short sound or vibration. Delay above about 100 ms starts to feel disconnected.
  • Consistency: the same gesture means the same thing. If the trigger grabs in one scene, it should not teleport in the next. Use the same menu layout across tasks.
  • Error prevention: make slips hard. Use snapping, confirm delete, and avoid tiny targets at arm's length. A wrong command should be easy to undo.
  • User control: the user can stop, undo or change mode. Do not trap the user in an animation. Provide a clear exit from every menu.
  • Fatigue: design for short, supported actions. Avoid long arm raises, repeated pinch gestures and heavy head movement. Place controls in a comfortable zone.

These guidelines are cheap to check in a review. They do not replace a user test, but they catch many faults before users arrive.

Formative and summative evaluation

Formative evaluation happens while the design is still changing. The aim is to find problems and fix them. It uses few users, rough prototypes and close observation. Summative evaluation happens when the design is stable. The aim is to measure performance and compare options. It uses more users, a fixed task and agreed metrics.

Three common methods:

  • Expert review: a trained reviewer checks the interface against the guidelines and lists likely problems. It is fast and cheap, but it predicts user problems; it does not measure them.
  • Think-aloud: the user speaks while doing the task. The tester notes confusion, silence and workarounds. It is strong for formative work. It can slow the user, so do not use its timings as final performance data.
  • Task-based test: each user gets the same task, such as 'place the red block in the tray'. The tester records success, errors, time and comments. This is the backbone of summative evaluation.

An A/B comparison is a task-based test with two designs. Half the users see A first, half see B first. This counterbalancing reduces learning effects. The same task, instructions and scene must be used for both. A difference in completion or errors then points to the design, not to the order. Some syllabi call this whole activity evaluation of 3D user interfaces.

Metrics and what they mean

A metric is a number that answers one question. Choose metrics before the test, not after. The common set is:

completion rate = users who complete ÷ users who start × 100%

users who complete is the count of people who finish the task; users who start is the count who began it.

error rate = errors ÷ attempts × 100%

errors is the count of wrong actions; attempts is the count of task attempts, so one user can add more than one attempt.

  • Task time: seconds from start to success. Report median when a few users are very slow.
  • SUS (System Usability Scale): a 10-item questionnaire scored 0 to 100. It is a usability score, not a percentage of users. A higher score is better.
  • NASA-TLX (Task Load Index): a workload questionnaire with mental, physical and time demands. It is useful when two designs are equally fast but one feels harder.
  • Presence: a questionnaire score for the feeling of being inside the virtual world. It matters for training and entertainment, but it does not replace task success.

Report the denominator with every rate. '80% completion' means 16 of 20 users. '15% error rate' means 6 errors in 40 attempts. These two rates use different units: users and attempts.

Reading a comparison without fooling yourself

A/B results are only useful if the test is fair. Use the same task, same starting state and same time limit. Counterbalance the order. Keep the instructions neutral. Do not help one group more than the other. Record every attempt, including failed ones.

Look at the pattern, not one number. Design B in the figure has higher completion and lower error rate. That is a consistent win. A design with faster time but more errors may still be worse for a medical or industrial task. A design with equal success but higher NASA-TLX may tire users sooner.

Small tests are common in formative work. A result from 5 users can reveal major faults but cannot prove a small difference. For a summative claim, use enough users and report the count. Do not turn a 2-user difference into a general law.

Worked example

Question. Two VR menu designs are tested by 20 users each. The test records 40 attempts per design. Design A: 16 users complete the task; its 40 attempts contain 6 errors. Design B: 18 users complete; its 40 attempts contain 3 errors. Compute completion rate and error rate for each design. Compare them.

  1. For design A, completion rate = users who complete ÷ users who start × 100% = 16 ÷ 20 × 100% = 0.80 × 100% = 80.0%.
  2. For design A, error rate = errors ÷ attempts × 100% = 6 ÷ 40 × 100% = 0.15 × 100% = 15.0%.
  3. For design B, completion rate = 18 ÷ 20 × 100% = 0.90 × 100% = 90.0%.
  4. For design B, error rate = 3 ÷ 40 × 100% = 0.075 × 100% = 7.5%.
  5. Compare: B has 10.0 percentage points more completion and 7.5 percentage points fewer errors. Both metrics favour B.

Answer. Design A: completion 80.0%, error 15.0%; design B: completion 90.0%, error 7.5%, so B performs better on both metrics.

Exam traps

  • Completion rate uses users as the denominator. Error rate uses attempts. Mixing them gives a number that is neither.
  • A user who completes after many errors is still a completion. Report errors separately; do not subtract them from completions.
  • SUS is a 0–100 score, not a percentage of users. A SUS of 68 does not mean 68% success.
  • Think-aloud slows users. Do not compare task times from a think-aloud test with times from a silent test.
  • Presence and preference are not performance. A design can feel immersive and still be slow or error-prone.

Feedback prevents the user not knowing whether an action worked. Fatigue prevention stops long arm raises or repeated gestures from exhausting the user.

Understand Why should think-aloud timings not be used as final performance data? 3 marks

Speaking while working adds mental load and slows the task. The timing then measures the talking as well as the interface. Use think-aloud to find problems, and measure time in a silent task test.

Analyze Two designs have equal completion and equal task time. Design B has a higher NASA-TLX score. What does this suggest? 3 marks

B feels harder in mental, physical or time demand. Equal speed does not mean equal comfort. B may cause more fatigue or errors in longer sessions, so investigate the load before choosing it.

Research adds eye tracking, hand-motion logs and physiological sensors to see where users hesitate or tire. Longitudinal studies ask whether gains last after a week of training. Takeaways

  1. 3D manipulation is selection plus a transform, and a good technique always trades reach against precision.
  2. Constraints (axis, plane, snap) do most of the work of making 3D manipulation accurate on a phone-sized target.
  3. Travel moves the viewpoint; wayfinding tells the user where to go, and confusing the two creates lost users.
  4. Continuous travel suits small worlds, teleportation suits large worlds and comfort-sensitive users.
  5. System control must be cheap to invoke and hard to trigger by accident, so voice and gesture need confirmation.
  6. A scene graph exists so the renderer can cull, sort and draw a tree of nodes instead of tracking thousands of objects by hand.
  7. Unity and Unreal differ more in workflow and scripting language than in the VR concepts they expose.
  8. C# scripts plus a physics engine give interaction rules and stable collisions, not hand-authored animation.
  9. Most VR sickness is predicted by latency, frame rate, acceleration and field-of-view; measure before shipping.
  10. Usability in 3D is measured with task time, errors, SUS and NASA-TLX, and read together with think-aloud comments.

Exam question bank

Long answers here are judged on definition plus technique comparison plus a design decision for a stated scenario, so always name the task, the constraint and the comfort or usability consequence.

Remember and understand

Understand Define 3D manipulation and break it into its subtasks. Explain how a constraint reduces the degrees of freedom of a manipulation. 10 marks

Definition: select an object, then change position, orientation or scale; Subtasks: selection, positioning, rotation, scaling; 6 DOF for a rigid body; constraint restricts to a subset; Examples: move on plane, rotate about one axis, snap to surface; Why: tracked-hand accuracy is poor, constraints remove ambiguity and jitter; Effect on precision and on error recovery.

Understand Compare the virtual hand, Go-Go and ray-casting techniques for object selection and manipulation. State one scene where each is the best choice. 12 marks

Virtual hand: direct, 1:1 mapping, natural, limited reach; Go-Go: nonlinear gain past threshold, extends reach, still proprioceptive; Ray-casting: works at any distance, poor for rotation and depth control; HOMER hybrid as an improvement; Best cases: nearby assembly, mid-range shelf, far control panel; Cost: tracking accuracy, arm fatigue, selection ambiguity.

Understand Distinguish travel from wayfinding. Describe three travel techniques and three wayfinding aids with their trade-offs. 12 marks

Travel = viewpoint motion; wayfinding = deciding the route and staying oriented; Travel techniques: physical walking, steering, teleportation, ride-along; Steering: continuous, good for small worlds, causes sickness; Teleportation: comfortable, breaks presence continuity; Wayfinding aids: grid floor with compass, landmarks, embedded map, guided tours, breadcrumbs; Trade-offs: immersion versus comfort versus cognitive load.

Understand Classify system control techniques in VR and explain each class with a short example. 10 marks

Definition: changes the application, not a scene object; Graphical: list menu, Tring menu, pie menu; hand or wand placement; Voice commands: hands-free, needs vocabulary, feedback and error handling; Gestural commands: quick, must avoid accidental matches with manipulation gestures; Tools: virtual tool belt; Multimodal: one channel selects, another confirms; Design points: cheap invocation, clear feedback, undo.

Understand Explain what a scene graph is, what a node stores, and how a toolkit uses the tree when drawing a frame. 10 marks

Tree of nodes with parent-child transforms; Node contents: local transform, geometry, material and state, children; World transform = product of transforms up to the root; Traversal: cull by bounding volume, then draw; state inherited unless overridden; Efficiency: grouping, instancing, matrix reuse, sorting; Shared subtrees and dynamic nodes for tracked head and hands.

Apply

Apply A user must place a small bolt into a hole 2 m away in a VR assembly trainer. Choose a manipulation technique and a set of constraints, and justify each choice. 13 marks

Far object, high precision, so start with ray-casting or HOMER; Constraint: move along the bolt axis, then snap-to-hole on approach; Reduction from 6 DOF to 1 DOF near the target; Haptic or audio confirmation on snap; Feedback: ghost preview of the target position; Comparison with plain virtual hand, which cannot reach 2 m; Comfort: avoid large arm extension for long sessions.

Apply Design a locomotion and wayfinding scheme for a virtual walkthrough of a large heritage site. Give the travel technique, the aids and the comfort settings. 13 marks

World is large and continuous, so teleportation plus short-range steering; Point-and-teleport target marker with valid/invalid colouring; Wayfinding: overview map, landmark monuments, compass on the hand, guided tour mode; Floor grid or subtle vignette during motion; Speed limits, snap turning instead of smooth turning; Prevent teleporting through walls; Measure: task time to reach a named monument, number of lost events.

Apply Write the structure of a C# script that lets a grabbed object follow the controller while collisions stay stable, and explain each part. 12 marks

MonoBehaviour class, serialised fields for speed, grabbed flag; OnTriggerEnter or XR interaction events to set grabbed state; Update reads controller pose; FixedUpdate moves the Rigidbody with MovePosition or force; Keep interpolation on, disable gravity while held; Constraints on the Rigidbody to lock unneeded axes; OnRelease restore velocity and gravity; Why FixedUpdate, not Update, for physics.

Apply A headset runs at 90 frames per second. Compute the frame budget and explain how latency, physics timestep and script cost share it. 8 marks

Frame time = 1/90 s ≈ 11.1 ms; Budget split: tracking, simulation, rendering, compositor; Physics timestep independent of frame rate; interpolation; Heavy script work in Update misses the frame; Latency beyond about 20 ms is felt as lag; Fix: reduce draw calls, bake lighting, profile first.

Analyze and evaluate

Analyze Analyse the causes of simulator sickness in VR and evaluate four mitigations against them. 13 marks

Cause: sensory conflict between visual motion and vestibular signal; Cause: latency and low or unstable frame rate; Cause: vergence-accommodation conflict in stereo displays; Cause: wide field of view with high optic flow; Mitigations: teleportation or snap turn, motion vignette, high frame rate and low latency, fixed reference frame or cockpit; Evaluate each against comfort, presence and task cost; Session limits, breaks, user screening.

Evaluate Design a usability evaluation for a 3D menu system and justify your choice of measures. 13 marks

Task-based test with defined tasks: open menu, change mode, undo; Metrics: task time, error rate, NASA-TLX for load, SUS for satisfaction; Think-aloud during learning, silent during timed trials; Expert review first to remove obvious faults; Fatigue measure over a longer session, arm and shoulder; Presence questionnaire if immersion matters; Compare against a baseline menu, counterbalance order, minimum sample size.

Evaluate Evaluate whether voice, gesture or a graphical menu is the better system control channel for a hands-busy surgical training application. Justify with error, fatigue and feedback arguments. 13 marks

Hands busy sterilisable context favours voice; Voice problems: recognition error, vocabulary size, no private speech, delay; Gesture: no device needed but conflicts with manipulation gestures; Graphical menu: precise and visible but needs a hand or dwell; Multimodal: voice command with visual confirmation; Feedback required for every channel; Fatigue and error recovery, undo for all channels.

Evaluate Trace the full path from a scene graph node to a lit stereo frame on the headset, and evaluate where latency and where bugs enter. 15 marks

Scene graph node, local and world transforms; Culling and sorting, draw call submission; Engine script updates from input before rendering; Eye transforms from head tracking, per-eye view and projection; Stereo rendering, distortion correction and compositing; Latency sources: tracking, simulation, render queue, display scan-out; Bugs: stale transforms, double transform application, update order; Measure with a profiling tool, not by eye.

Evaluate You must build a VR training app in one semester with a small team. Choose Unity or Unreal and justify the choice across scene model, scripting, asset pipeline and build path. 15 marks

Engine components: editor, scene model, asset pipeline, lighting, physics, build; Unity: C#, component model, prefabs, wide XR plugin support, fast iteration; Unreal: Blueprints plus C++, stronger default rendering, heavier hardware; Team skill and hardware are the deciding factors; Asset import and texture and lightmap budget; Device SDK and store requirements; Prototype first, measure build time and frame rate before committing.

Glossary

3D manipulation
The interaction task of selecting an object in 3D space and changing its position, orientation or size.
Constraint
A restriction that cuts the allowed degrees of freedom, such as moving only along one axis.
Degrees of freedom (DOF)
The count of independent motions a body can make; a free rigid body has six.
Game engine
Software providing an editor, scene model, rendering, physics and build path for interactive applications.
Go-Go
A virtual-hand technique that stretches the reach nonlinearly once the hand passes a distance threshold.
HOMER
A hybrid that selects a distant object with a ray and then manipulates it with the hand.
MonoBehaviour
The Unity base class for scripts that attach to game objects and receive update and collision callbacks.
Motion-to-photon latency
The time from a real head movement to the matching change of light leaving the display.
Multimodal interaction
Using two or more input channels, such as voice plus gesture, in one command.
NASA-TLX
A six-subscale questionnaire that scores perceived workload on a task.
Pie menu
A radial menu where items sit around a circle and are chosen by direction rather than by distance.
Prefab
A reusable object template in Unity that can be instantiated and edited in one place.
Presence
The feeling of being located inside the virtual environment rather than observing it.
Ray-casting
Selection and manipulation by shooting a ray from the hand or head and acting on the first object hit.
Rigidbody
A Unity component that subjects an object to the physics engine's forces, gravity and collisions.
Scene graph
A tree that stores the virtual world as nodes carrying transforms, geometry and state.
Selection
Choosing one object out of many as the target of the next action.
Simulator sickness
Discomfort, nausea and eyestrain caused by conflicting visual and bodily motion cues.
System control
Interaction that changes the application or its mode rather than an object in the scene.
System Usability Scale (SUS)
A ten-item questionnaire that yields a single 0 to 100 usability score.
Teleportation
Travel by jumping the viewpoint to a pointed-at target instead of gliding there.
Transform
The position, rotation and scale of a node, inherited by its children.
Travel
The task of moving the user's viewpoint through the virtual world.
Vergence-accommodation conflict
The disagreement between the eye's focus distance and its convergence distance in a stereo headset.
Virtual hand
A manipulation technique that maps the tracked hand directly to a virtual hand that grasps objects.
Wayfinding
The cognitive task of choosing a route and keeping track of position and heading.
