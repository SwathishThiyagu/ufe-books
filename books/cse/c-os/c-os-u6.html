6.1 Goals and principles of protection

Every file, every page of memory and every device in a computer is shared by many processes, and some of those uses must be stopped. Protection is the part of the kernel that answers one question for every access: may this subject use this object in this way? It compares the request with the rights the process holds, then allows or denies it. The same check protects an exam cell's results file, a bank's ledger on a shared server, and your UPI app's data on a phone where other apps also run.

You need Unit 1 on dual mode operation and the role of the kernel, and Unit 5 on file attributes and access methods.

What protection does

A subject is the active thing that asks for something, normally a process acting for a user. An object is anything the kernel can name and hand out: a file, a page of memory, a printer, a network socket. A right (also called a permission or an access right) is one permitted way of using that object: read, write, execute, append, delete. Protection is the mechanism that binds the three together.

Protection exists for three goals. Controlled access: a process touches only the objects it is allowed to touch, and only in allowed ways. Detection of programming errors: a bug that would write past the end of an array into another program's memory is stopped at the moment of the write, instead of silently corrupting data. Prevention of misuse of rights: a user who may read a file cannot quietly pass that right on, and cannot use a right for a purpose it was never meant for.

Protection is wider than files. It covers memory segments, CPU time, devices, and the message queues two processes share. Files are only the easiest place to see it.

  1. The process issues a request: a system call naming an object and a mode, such as open("results.dat", "r").
  2. The kernel's reference monitor looks up the domain of the process, which is the set of rights it holds at this moment (see 6.2).
  3. If the domain contains read on results.dat, the access proceeds. If not, the call fails with an error (EACCES in Linux) and the object is not touched.

Protection is not security

Protection and security are not the same word. Protection is internal and mechanical: the kernel decides each access from stored rights, and the decision can be read off the code. Security is trust against a deliberate attacker: whether the mechanism, the people who hold the passwords, and the network around the machine can keep an intruder out.

A file with mode 600 is protected: only its owner may read or write it. If the owner's password is 1234, the file is still not secure. The protection decision is right; the assumption behind it is false.

So protection is a mechanism, and security is the property you hope the whole system has. Security needs protection plus authentication, patching, physical locks and audit (see 6.6). The check itself behaves the same whether the request is honest or hostile, which is why one reference monitor serves both.

Seven principles of protection

These seven principles are the classic design rules for protection systems. Some syllabi call them the design principles of protection.

  • Least privilege. Give each process the smallest set of rights that lets it finish its job, and take them back when it finishes. The exam cell program below needs read on one file and append on another, nothing more.
  • Need-to-know. Give a process access only to information it has a reason to use. This is the data version of least privilege: that same program has no business reading other sections' mark files even for a moment.
  • Fail-safe defaults. The default answer is deny; access is granted explicitly. A newly created file is readable by its owner only, not by everyone, until the owner widens it.
  • Separation of privilege. Require two independent conditions rather than one. A transfer above a set limit needs the operator's approval and the manager's, so one stolen password is not enough.
  • Economy of mechanism. Keep the checking code small and simple, because every extra line is a place where a check can be skipped. One reference monitor that all calls pass through beats checks scattered across the kernel.
  • Least common mechanism. Share as little state between users as possible, because shared state is a channel between them. Give each user a private temporary directory instead of one world-writable /tmp.
  • Separation of policy from mechanism. The mechanism is the check; the policy is the rule it enforces. Changing "interns may not read salary files" should mean editing an access list, not rewriting kernel code.

Worked example

Question. An exam cell runs a program called check_marks. Its directory holds 12 files: results.dat, audit.log, and 10 mark files belonging to other sections. The program must only read results.dat and append to audit.log. (a) Write its rights under least privilege and count them. (b) A programmer instead grants read and write on all 12 files. Count the rights granted and the excess over the needed set. (c) Name the two principles that (b) breaks.

  1. Needed set: read on results.dat is 1 right; append on audit.log is 1 right. Total under least privilege = 2 rights.
  2. Append and not write on audit.log: write would also allow overwriting earlier entries, so append is the smallest right that does the job.
  3. Wide grant: 2 rights (read and write) on each of 12 files, so 2 × 12 = 24 rights.
  4. Excess over the needed set = 24 − 2 = 22 rights the program never uses.
  5. (b) breaks least privilege, because write on files it never writes is more than it needs, and need-to-know, because it can now read the 10 mark files of other sections.

Answer. Least privilege gives 2 rights; the wide grant gives 24 rights, which is 22 more than needed.

Exam traps

  • Protection and security are not the same. Protection is the kernel's internal check; security is whether that check, the people and the network can be trusted. A comparison question needs both halves.
  • Protection is not only about files. Memory, CPU time, devices and inter-process messages are objects too, and a question about 'objects' expects you to list them.
  • Least privilege and need-to-know look alike but answer different questions: how much a process may do (rights) versus how much it may know (information).
  • Fail-safe defaults means deny until something is allowed, not allow until something goes wrong. A new file readable by everyone is the classic wrong answer.

6.2 Domain of protection

A domain is the set of rights a process holds at one moment, written as pairs: each object and the rights on it. It stops a process carrying its user's full power all the time. UNIX-like systems switch domains daily: passwd, sudo, containers, phone app permissions.

You need the meaning of a right from 6.1 and the process control block from Unit 2.

A domain is a set of pairs

A domain D is a set of pairs (o, r). o is an object: file, printer, memory segment, socket. r is a set of rights: read, write, execute, delete.

D = {(notes.txt, {read, write}), (printer, {print}), (/etc/shadow, {})}

D is the domain; each pair names an object and its rights; {} means no access.

Static domains are fixed at start; simple but coarse. Dynamic domains change as the process runs, each change by a rule. Rights belong to the domain, not the pid, so the kernel stores a pointer to it.

How a domain changes

A switch happens only through an entry point set up by someone with authority.

new domain = switch(old domain, object, right)

object is the program or file called; right permits the call; the result is the domain afterwards.

  • setuid exec. The file means 'run as owner'; on exec the process enters the owner's domain.
  • sudo. Password check, then one command in the root domain.
  • Guarded procedure. A user process calls a fixed entry point; hardware switches to a privileged ring. MULTICS had 8 rings; x86 has 4, ring 0 kernel, ring 3 user.

The kernel saved old rights at the entry point and restores them on return from the trap; the user takes no action.

UNIX maps a domain to (uid, gid)

In UNIX a domain is (uid, gid) plus supplementary groups. File mode bits give read, write and execute to owner, group, others. A uid 1000 process reads a 644 file owned by uid 1000, but gets only 'other' bits on a file owned by uid 0. exec of a setuid file replaces the effective uid for the life of the new image. The kernel records the old uid in the saved set-user-id, so the program can call setuid(1000) to drop back and setuid(0) to regain root while running.

Worked example

Question. uid 1000, gid 1000 runs /usr/bin/passwd (setuid root). Before, the process may read/write notes.txt but not /etc/shadow. After, it can write /etc/shadow. Write both domains and say how it returns to the first.

  1. Objects: notes.txt, /usr/bin/passwd, /etc/shadow.
  2. D1: notes.txt {read, write}; /usr/bin/passwd {read, execute}; /etc/shadow {}; uid 1000, gid 1000.
  3. exec sees the setuid bit on /usr/bin/passwd; effective uid becomes 0. That is the switch.
  4. D2: notes.txt {read, write}; /etc/shadow {read, write}; all files get uid 0 rights.
  5. At exec the kernel recorded 1000 in the saved set-user-id. exec replaces the image, and effective uid is 0 for its life. The program may call setuid(1000) to drop to D1, then setuid(0) to return. When it finishes, the process ends; the parent shell stayed in D1.
  6. The shell forked a child before exec; no exit restore is involved.

Answer. D1 = {(notes.txt, {read, write}), (/usr/bin/passwd, {read, execute}), (/etc/shadow, {})}; D2 = {(notes.txt, {read, write}), (/etc/shadow, {read, write}), (any file, uid 0 rights)}. The program drops back with setuid(1000) using the saved set-user-id, or simply ends; the parent shell never left D1.

Exam traps

  • A domain changes only by an explicit mechanism — setuid exec, sudo, ring switch. Reading a file changes nothing.
  • Rights belong to the domain, not the pid. Two processes in one domain hold identical rights.
  • setuid changes effective uid, not real uid. The saved set-user-id lets the program call setuid() to drop back or regain root; the kernel does not restore it on exit.
  • A system call trapping to a privileged ring is a domain switch; a library call in the same ring is not.

6.3 Access matrix and its implementation

The access matrix is a grid of the protection state. Each row is a domain, the rights a process holds now. Each column is an object such as a file or device. A cell lists the rights that domain has on that object: read, write, execute. One table makes every access question the same: does cell (D, F) contain the right? Real systems store only non-empty cells, as access lists or capability lists. The figure shows three domains and four objects.

You need: the domain as a row from 6.2 and the file object from Unit 5, File concept, attributes and access methods.

The matrix: domains against objects

The matrix is M[D, O] ⊆ R. M is the access matrix, D a domain, O an object, R the set of rights. If read is in M[D1, F1], a process in D1 may read F1. An empty cell means no access. The full matrix has (number of domains) × (number of objects) cells. In the figure, D1 has r on F1, rw on F2, x on F4; D2 has r on F2, rw on F3; D3 has r on F1, rw on F4. The matrix is usually sparse: most cells are empty. Three special rights extend it. Copy (r*) lets a domain pass that right to another. Owner lets a domain add or remove rights in an object's column. Control lets a domain change another domain's row. These rights change the matrix itself.

Storing only the non-empty cells

Implementation stores only non-empty cells. Four standard schemes exist.

  • Authorization table (table of triples): keep triples (domain, object, rights) for non-empty cells only. Access is a search through the table, O(E), where E is the number of non-empty cells; no empty cells are stored.
  • Access list: one list per object, holding pairs (domain, rights). To check D, scan that object's list. Space is E entries plus O headers. Access time is proportional to entries on that object.
  • Capability list: one list per domain, holding pairs (object, rights). A process presents an entry; the kernel checks the list. Space is E entries plus D headers. Access time is proportional to entries in that domain.
  • Lock and key: each object keeps a short list of locks (bit patterns), one per right or per group of domains; each domain holds a set of keys. A domain may use an object if one of its keys matches one of that object's locks. This compresses the object side like an access list while keeping keys on the domain side like capabilities.

Space and access time

Compare on sparsity. If D = 1000 domains, O = 1000 objects, and E = 5000 non-empty cells, a dense matrix array needs 1,000,000 cells but gives O(1) lookup. Each list form needs 5000 entries plus headers. The saving is large. Access time trades off. A dense array is fastest. Access list is fast when an object is shared by few domains; capability is fast when a domain touches few objects. If one object is opened by every domain, its access list is long and the check is slow; a capability per domain is short. If one domain touches every object, its capability list is long; access lists stay short. Revocation differs: deleting a right from an object's access list is one edit, while finding every copied capability is hard. That is why access lists dominate general-purpose file systems and capabilities appear in tighter designs. This trade-off is the whole design question.

Worked example

Question. Protection state: D1 has read on F1, read-write on F2, execute on F4. D2 has read on F2, read-write on F3. D3 has read on F1, read-write on F4. (a) Full matrix cells? (b) Non-empty cells? (c) Access-list entries? (d) Capability entries?

  1. D = 3, O = 4. Full cells = 3 × 4 = 12.
  2. Non-empty: D1 has 3, D2 2, D3 2, total 7.
  3. An access list stores non-empty cells per object: 7 entries.
  4. A capability list stores non-empty cells per domain: 7 entries.

Answer. 12 cells; 7 non-empty; access-list store 7; capability store 7.

Exam traps

  • Storing the whole matrix as a dense array; it is sparse and wastes space.
  • Swapping rows and columns: access lists are per object; capability lists are per domain.
  • Confusing copy and control: copy passes one right; control changes another domain's row.
  • Assuming both forms store different totals: both store E non-empty entries; headers differ.

6.4 Access control and revocation of access rights

An access list is one column of the access matrix, kept on the object it protects, and it answers every access check cheaply. Taking a right back is the hard direction. Once a right has been handed to a process, copies of it spread to children and to other machines, and the object's list no longer knows where they are. Revocation means finding and killing those copies. This chapter shows how rights are stored, why copies make revocation costly, and what each revocation scheme charges.

You need: 6.3 for the access matrix and its two list forms.

One column of the matrix, kept on the object

An access list is one column of the access matrix, stored with the object it protects. Each entry names one subject and the rights that subject holds: read r, write w, execute x. The matrix itself was set out in 6.3. The practical point here is that the list is a real data structure the kernel reads on every open.

A subject in an entry need not be a single user. It can be a named user such as raj, a group such as hr, or a wildcard such as everyone. Group entries keep the list short: one line covers two hundred HR staff, and the check expands the caller's group membership at access time.

Order matters. The kernel scans the list from top to bottom, and the first entry that names the caller decides the outcome. A wildcard entry therefore goes last, or it shadows everything below it. If no entry matches at all, the answer is default deny: the access is refused. Default deny is the safe choice, because a forgotten entry locks a user out rather than letting a stranger in.

Linux exposes the same idea through two commands. setfacl -m u:bob:r payroll adds an entry giving bob read on the file payroll, and getfacl payroll prints the whole list so you can check the order.

Why a right is hard to take back

Granting a right is a write to one place. Revoking it is a search. The moment a process is allowed to read the payroll file, the right leaves the object. The process may fork, and the child inherits it. The process may pass it over a socket. In a capability system the right is a ticket the holder can copy and carry; 6.5 covers those tickets in full.

So the object's access list stops being a complete record of who holds the right. It records what the object is willing to grant now, not what has already been granted.

Two words separate the cases. Selective revocation takes the right from one user, or from one object, and leaves everyone else untouched. Global revocation removes the right for all users at once. A system that offers only global revocation answers a complaint about one employee by disturbing everybody.

There is also a difference between deleting a right and merely denying it. Deleting removes the entry; the slot is free and the check costs less. Denying keeps the entry but marks it invalid, so the check fails while the record survives. Denial is cheaper to undo and leaves an audit trail.

Four revocation schemes and what each one costs

Four schemes appear in textbooks, and each trades a different cost.

  1. Reacquisition: the process holds no permanent right. On each access it presents its claim and the system rechecks the list. Revocation is one deletion; the price is a check on every access.
  2. Back-pointers: each object keeps a list of back-pointers, one pointer to every copy of a right held on it. To revoke, the system follows the pointers stored with the object and deletes each copy they name. The cost is one step per copy, and one missed pointer leaves a live right.
  3. Indirection by handle: the copy holds a handle, an index into a system-wide table, and the table entry points at the file. Revocation deletes or invalidates the handle. If many copies share one handle the cost is one step; if each copy has its own handle the cost is one step each.
  4. Keys and locks: each right carries a key, and the object holds a matching lock or a list of keys. Revocation changes the lock, and every old key stops matching at once. One write revokes everyone, so this scheme is global unless keys are per-user.

Back-pointers and keys are hard to keep correct across crashes and machines. The handle table is the usual compromise, because it is small and can be scanned from end to end.

Worked example

Question. The payroll file has the access list raj read-write, bob read, group hr read, root read-write. Bob's read right has been copied into processes P1, P4, P9 and P12. The auditor orders bob's read right revoked. Count the steps needed under four schemes: (a) access list, (b) capability list with back-pointers, (c) indirection with one shared handle, (d) indirection with one handle per copy.

  1. Access list: delete the bob entry, which is 1 step. Every later check by bob finds no entry and falls to default deny. The four copies already inside P1, P4, P9 and P12 are not reached: they stay live unless the system rechecks each access (reacquisition) or the copies are closed or invalidated separately.
  2. Back-pointers: the bob entry carries four pointers, to the copies inside P1, P4, P9 and P12. Follow each pointer and delete the copy it names: 4 steps. If one pointer is stale, that copy stays live.
  3. Indirection, shared handle: all four copies name the same handle h7. Delete h7 from the handle table: 1 step, and all four copies fail to resolve.
  4. Indirection, private handles: the copies name four separate entries h7, h8, h9 and h10. Delete all four: 4 steps.
  5. Compare the counts: 1 step by access list (future checks only; the four live copies remain), 4 by back-pointer, 1 by shared handle, 4 by private handles. The handle scheme is cheap only when the handle is shared.

Answer. Access list: 1 step to delete bob's entry, which blocks all later checks but does not reach the four live copies unless each access is rechecked or the copies are closed or invalidated separately. Back-pointers: 4 steps, one per copy. One shared handle: 1 step. One handle per copy: 4 steps.

Exam traps

  • Do not mix up the two directions. Rights stored per object make it easy to revoke one user from one object and hard to revoke one user everywhere; rights stored per domain do the reverse.
  • Deleting an entry from an access list does not delete rights already handed out. In a capability system those copies keep working.
  • Indirection is not automatically cheap. It costs one step per handle, so four private handles cost four steps, exactly like back-pointers.
  • A changed key or an invalidated shared handle revokes every holder at once. That is global revocation, however narrowly the request was worded.
  • Denial is not deletion. A marked-invalid entry blocks access but keeps the slot and the record, and it can be revived by clearing the mark.

6.5 Capability-based and language-based protection

A capability is an unforgeable ticket for one object plus the rights to that object. A process holds capabilities in a list and presents one to open a file, print a page, or write memory. The kernel checks the ticket, not a global table. Language-based protection gives the same guarantee in software: a compiler or virtual machine checks types and permissions before code runs. Only a few universities teach this topic. Browsers, phone apps, and Java virtual machines use these ideas.

You need: 6.3 for the row form and 6.4 for revocation.

A ticket that carries its rights

A capability is a pair (object, rights). The object is a file, printer, or memory segment. The rights are a bit vector, for example read, write, execute and copy. The process holds a capability list. Possession is proof: the kernel compares the object in the ticket with the requested object, then tests the rights bit. No separate access-list lookup. Tagged memory marks capability words so a program cannot forge one with arithmetic. A file name is not a capability: the kernel must still check the name against an access list. A capability is the row form of the access matrix, from 6.3. The copy right lets the holder give a copy to a child. Some systems, such as Hydra, add rights amplification: a trusted procedure that is handed a capability may act on the object with more rights than the caller holds, which plain copy never allows.

Copying and revocation

Copying spreads rights. If P passes C2 to a child without the copy right, the kernel must refuse. With the copy right, the child gets an independent capability for F2. Revocation is now hard: the kernel has no record of the child's copy anywhere, so searching P's own list finds nothing. A handle solves this. Each capability points to a shared entry. Revocation clears the entry or bumps a version number. Every holder fails the next check. Cost is one update plus later faults, not a scan of unknown copies. Without a handle, revocation may need a scan of all processes, or it may be impossible. This is the revocation problem from 6.4 in capability form.

Language-based protection

Language-based protection moves the check into a compiler or virtual machine. Type safety stops a program from treating an integer as a pointer. A bytecode verifier checks stack types and branch targets before the JVM runs a class. Stack inspection checks every caller: a method gets a right only if all frames on the stack hold it. Java groups classes into a ProtectionDomain by code source and gives each domain a set of Permissions. AccessController walks the call stack and tests every ProtectionDomain on it. If any domain on the stack lacks the permission, the check fails. A doPrivileged block cuts the walk short at that frame. A class from an untrusted site can be given no file-write permission. When it calls file write, the check fails. This is capability-like: code holds a permission object, and possession is proof. The runtime enforces the rule without a kernel call per access.

Worked example

Question. Process P holds C1 = (F1, read), C2 = (F2, read-write), C3 = (printer, write). A call asks for write on F2. (a) Show the check and count the comparisons. (b) P passes C2 to a child process. What must P hold for that to be legal, and what does revocation now cost?

  1. Request: object F2, right write.
  2. Entry 1: C1 object F1. F1 ≠ F2, so no match. Comparisons = 1.
  3. Entry 2: C2 object F2. Match. Comparisons = 2.
  4. Test write bit in C2 rights. Read-write contains write, bit = 1. Access allowed.
  5. (b) Copy is legal only if C2 carries the copy right. Child gets independent copy of (F2, read-write).
  6. Revocation needs a handle or back-pointer to find that copy. Without it, the kernel cannot locate the child's copy, so revocation is impossible or costs a scan of all processes.

Answer. 2 object comparisons and write bit 1; the copy needs the copy right, and revocation needs a shared handle or back-pointer.

Exam traps

  • A file name is not a capability. The kernel must still check the name against an access list, so a name is not unforgeable.
  • Possession is proof. A capability is not a user password or a login identity; holding the ticket grants the rights in it.
  • The copy right is separate from read and write. A process may read F2 but still be unable to pass C2 to a child.
  • Revocation by deleting one list entry misses copies. Use a handle or back-pointer, or the kernel cannot find every copy.

6.6 The security problem: threats and attacks

An operating system must defend itself against people who mean harm, not only against programs that make mistakes. Protection asks whether a process may read this file; security asks who is on the network and what they are trying. Authentication, authorisation, isolation and audit form a chain that is only as strong as its weakest link. You meet the chain daily: a UPI PIN, an OTP on your phone, a bank firewall that opens only port 443. This chapter names the common threats and the standard defences, without going inside the algorithms.

You need: 6.1 for the split between protection and security, and Unit 1, OS operations: dual mode and timers, for the hardware support every defence leans on.

Security is about a person, not a bug

Protection is internal and mechanical: it decides whether a process may read a file, using the access matrix of 6.3. Security asks a harder question: is a person deliberately making the system act against its owner? A faulty program makes accidents. An attacker makes plans, studies your system, and changes method when one fails.

Three goals appear in every paper. Confidentiality: data is read only by parties allowed to read it. Integrity: data is changed only in allowed ways. Availability: the service keeps answering. A denial of service attacks availability alone and never touches a byte of data.

Keep the words apart. An asset is what you protect: account data, a database, a key. A vulnerability is a weakness in design or code. A threat is a potential violation of security that could cause harm. The threat agent, or attacker, is the person or group who may carry it out. An attack is the attempt. The attack surface is everything an outsider can reach: open ports, web forms, email, USB ports, even the help-desk phone number.

Every defence rests on four pillars: authentication (who are you), authorisation (what may you do), isolation (how far can damage spread), and audit (what can we prove afterwards). The chain is only as strong as its weakest link. A 12-character password gains nothing if the server still accepts the default administrator login.

Program threats: code that misbehaves

Program threats arrive inside software you install or input you send. The standard list:

  • Trojan horse: looks useful, carries hidden harmful code. A free video converter that also opens a back door.
  • Trap door (backdoor): a secret entry left by the writer that skips normal authentication. One line in the login code is enough.
  • Logic bomb: dormant code that fires on a condition, such as a payroll script that wipes files when a dismissed employee's name disappears.
  • Virus: a fragment that copies itself into a host file or boot sector and runs when the host runs. It needs a host, and usually a user action.
  • Worm: a standalone program that spreads by itself over the network through a listening service. No host file, no user action.
  • Ransomware: encrypts files and demands money for the key; the carrier is often a trojan or a worm.
  • Buffer overflow: a program writes more bytes than a buffer holds. On the call stack the extra bytes overwrite the return address, so a crafted input makes the CPU jump into attacker code. Defences: bounds checks, a non-executable stack, address randomisation.

Network threats, and cryptography as a tool

Network threats arrive through the ports your machine is listening on.

  • Port scan: connect to many ports to learn which services answer. This is reconnaissance, not the break-in.
  • Denial of service (DoS): flood one service until real users cannot get in. A distributed denial of service (DDoS) uses thousands of hijacked machines, a botnet.
  • Spoofing: forging a source IP address, or an email sender name, so traffic looks like it came from a trusted party.
  • Man-in-the-middle: the attacker sits on the path between two parties, relays their traffic and reads or alters it.

Cryptography is the toolbox that makes the last two hard.

  • Symmetric key: one secret key both encrypts and decrypts. Fast; delivering the key is the hard part.
  • Public key: a public key encrypts and only the matching private key decrypts. Solves delivery; slow.
  • Hash: a fixed-length fingerprint of data, easy to compute and infeasible to invert. Used for integrity checks and password storage.
  • Digital signature: a hash of the message encrypted with the sender's private key. Proves origin and integrity, and the sender cannot deny it.
  • TLS: uses public key methods once to agree a symmetric session key, then symmetric encryption for the data. It is the padlock in the browser.

Defences and user authentication

User authentication uses three kinds of evidence: something you know (password, PIN), something you have (OTP on a phone, hardware token), something you are (fingerprint, iris). Multi-factor authentication (MFA) combines two different kinds; two passwords are not MFA.

Passwords are stored as a salted hash, never as text. Their strength is the size of the search space.

N = AL

N is the number of possible passwords; A is the alphabet size in characters (26 for lowercase letters, 62 with capitals and digits); L is the length in characters. An attacker who knows nothing about the user needs N ÷ 2 guesses on average.

Defences sit inside the operating system and around it.

  • Firewall: rules that drop or pass packets by address and port, like the bank firewall that opens only port 443.
  • Patching: closing the vulnerability the attacker already knows about.
  • Sandbox: run untrusted code in a restricted domain so damage is contained; the domain idea of 6.2 applied to apps.
  • Least privilege: give each process and user the smallest set of rights it needs; a capability from 6.5 carries them.
  • Audit logs: a record of logins, failures and file access, so an incident can be reconstructed.

Evaluation classes rise in assurance: D minimal protection; C1 discretionary protection with separate users; C2 controlled access with auditing; B1 labelled security; B2 structured protection; B3 security domains; A1 formally verified design. One line each is enough for an exam.

6.7 Distributed operating systems and distributed synchronization

A distributed operating system runs on many machines but looks like one computer. There is no shared memory and no single clock, so processes send messages and must order events without wall-clock time. Logical clocks do that ordering; mutual exclusion and elections decide who enters a critical section and who leads.

You need race conditions and mutual exclusion (see Unit 3, Process Synchronization and Deadlocks) and the process and message-passing model (see Unit 2, Processes, Threads and CPU Scheduling).

Many machines, one system

Two processors sharing memory are tightly coupled: each reads what the other writes, and a lock in that memory keeps them apart. Machines with their own memory and processor, talking only by messages over a network, are loosely coupled. Distributed systems are loosely coupled.

A network operating system (NOS) keeps the machines visible. Each machine runs its own OS, users log in machine by machine, and moving a file needs an explicit remote copy. A college lab with a separate account on each desktop works this way.

A distributed operating system (DOS) hides the machines: one login, one file tree, one process name space. The OS decides which machine runs a new process and where a file lives. This hiding is called transparency:

  • Location transparency: you do not know which machine holds a resource.
  • Migration transparency: a process moves without your code noticing.
  • Replication transparency: extra copies of data are invisible to you.
  • Failure transparency: a retry hides a machine that has died.

The price is coordination. Every agreement costs messages, a machine can fail, and the network can split into two halves that cannot hear each other.

No shared clock: happened-before and logical clocks

Each machine has its own quartz clock and they drift apart, so two machines reading at the same instant get different numbers. A distributed system has no global clock. Order events by causality instead. Event e1 happened before e2 (written e1 → e2) when both are in one process and e1 came first; or e1 is the send of a message and e2 is the receive of that same message; or some event e3 exists with e1 → e3 and e3 → e2. Events with no such chain are concurrent.

local event or send: C = C + 1

C is the process's own counter, starting at 0; the new value is that event's timestamp, and a send attaches it to the message as ts.

receive of a message stamped ts:  C = max(C, ts) + 1

C is the receiver's counter before the receive; ts is the timestamp carried by the message; max is the larger of the two; the +1 counts the receive itself as an event.

The second rule is the merge rule: the receiver jumps ahead of both its own past and the sender. It guarantees that e1 → e2 implies C(e1) < C(e2). The converse fails, and that is the main trap in this chapter.

A vector clock repairs the converse. Each process keeps a vector V of n counters, one per process. A local or send event adds 1 to its own entry. A receive takes the element-wise maximum with the message's vector, then adds 1 to its own entry. Then e1 → e2 exactly when V(e1) ≤ V(e2) entry by entry and the vectors differ. If neither vector is ≤ the other, the events are concurrent.

One at a time, and one leader

The race conditions of Unit 3 return in a worse form. Two machines read a shared counter, both see 5, both write 6, and one increment is lost. No hardware instruction stops this, because there is no shared bus and no shared lock. Distributed mutual exclusion has three classic shapes.

  • Centralized: one coordinator grants permission, two messages per entry, but the coordinator is a single point of failure.
  • Distributed: a process asks every other process and enters when all have replied, which is 2(n − 1) messages; timestamps break ties between simultaneous requests.
  • Token ring: a token circulates around a logical ring and only its holder enters; cheap under load, but a lost token stops everyone.

Election chooses one process as coordinator after a failure. The bully algorithm uses process ids, and the highest live id wins.

  1. A process notices the coordinator has stopped answering and sends ELECTION to every process with a higher id.
  2. If no higher process replies before the timeout, it declares itself coordinator and sends COORDINATOR to every lower id.
  3. If a higher process does reply, the lower one waits and the higher one starts its own election.
  4. The highest live process wins, and every process records its id as the new coordinator.

Worked example

Question. P1, P2 and P3 run on different machines, each counter starting at 0. Every event, including a send, adds 1 to the counter; a receive sets the counter to max(local, message timestamp) + 1. P1 runs local event a, then sends m1 to P2. P2 runs local event d, receives m1, then sends m2 to P3. P3 runs local event g, receives m2, then sends m3 to P1. P1 receives m3. Give the Lamport timestamp of every event and state which events are concurrent.

  1. P1 starts at 0. Local a: C = 0 + 1 = 1, so a = 1.
  2. P1 sends m1: C = 1 + 1 = 2. Message m1 carries ts = 2.
  3. P2 starts at 0. Local d: C = 0 + 1 = 1, so d = 1.
  4. P2 receives m1: C = max(1, 2) + 1 = 3.
  5. P2 sends m2: C = 3 + 1 = 4. Message m2 carries ts = 4.
  6. P3 starts at 0. Local g: C = 0 + 1 = 1, so g = 1.
  7. P3 receives m2: C = max(1, 4) + 1 = 5.
  8. P3 sends m3: C = 5 + 1 = 6. Message m3 carries ts = 6.
  9. P1 receives m3; its counter is still 2 from sending m1: C = max(2, 6) + 1 = 7.
  10. Concurrency: a, d and g have no message chain linking them, so they are pairwise concurrent. Equal timestamps are a hint; the causal argument is the proof.

Answer. Timestamps are a = 1, m1 sent with 2, d = 1, receive of m1 at P2 = 3, m2 sent with 4, g = 1, receive of m2 at P3 = 5, m3 sent with 6, receive of m3 at P1 = 7; events a, d and g are pairwise concurrent.

Exam traps

  • Using wall-clock time to order events on different machines. Clock skew makes that order wrong, which is why logical clocks exist.
  • Reading a smaller Lamport timestamp as proof of happened-before. Only happened-before implies a smaller timestamp, not the reverse.
  • Forgetting the +1 on a receive. The counter becomes max(local, ts) + 1, never just max(local, ts).
  • Confusing a NOS with a DOS. In a NOS the user sees many machines; in a DOS they are hidden.
  • Comparing vector clocks by one number. The comparison is element-wise, and neither being ≤ the other means concurrent.

6.8 Distributed file systems

A distributed file system lets a program open, read and write files on many servers as if they were on one local disk. It lets users share data without copying it by hand. The cost is a network: every miss is a message, and every cache copy can become old. Caching hides delay but creates a staleness window, the time a client may read an old block. Some syllabi teach NFS-style remote access and AFS-style whole-file caching.

You need: 6.7 for messages and no global clock, and Unit 5 for file blocks and caching.

Naming and two access models

Naming transparency means a path such as /data/notes.txt names the same file wherever the client runs. Location transparency goes further: the path does not say which server holds the file. A name service maps the path or file identifier to a server and file handle. The client mounts the remote directory and uses ordinary open, read and write calls through the virtual file system (VFS).

Two access models decide how much crosses the network. In remote access, each operation is sent to the server: a read for block 7 travels, the server returns block 7, and the client keeps little state. In upload/download, the client copies the whole file locally, works on it, and writes it back. Remote access suits small random reads and shared files. Upload/download suits large sequential work, but write-back can overwrite another user's changes. Neither model removes the need to validate cached data.

Cache validation, write policy and consistency

A client cache stores blocks from the server. A hit returns locally; a miss sends a remote procedure call (RPC) and fills the cache. An entry needs validation: the client asks or is told whether the server copy changed. With write-through, every write reaches the server before it is acknowledged, so the server copy is always current, but a reader's cached block stays old until it is validated. With delayed write, the client keeps dirty blocks and sends them later; writes are fast, but a crash or a second reader can see old data. The staleness window is the maximum time a client may return an unvalidated copy. Shorter windows cost more messages. Replication copies a file to several servers; consistency needs a rule for the current copy, often a version number or a lease.

Stateless servers keep no per-client open-file table. Each request carries a file handle: a server-chosen identifier for the file plus a generation number. A stateless server can restart and still answer, because the handle is enough. NFS uses remote access with file handles and client caching. AFS uses whole-file upload/download with callbacks when a cached file changes.

Worked example

Question. A client reads 1000 blocks of 4 KB. A hit costs 0.1 ms; a network fetch costs 20 ms. (a) Find the total time with no cache. (b) Find average time per block and total time with hit ratio 0.9. (c) The server changes a block while the client copy is 30 s old. What goes wrong?

  1. No cache: every block is a miss. 1000 × 20 ms = 20 000 ms = 20 s.
  2. Miss probability = 1 − 0.9 = 0.1. Average = 0.9 × 0.1 ms + 0.1 × 20 ms = 2.09 ms per block.
  3. Total = 1000 × 2.09 ms = 2090 ms = 2.09 s.
  4. With no validation the client returns its 30 s old copy, so two readers see different data for up to 30 s; only validation (a callback, a lease, or a check on open) shrinks that window. Write-through keeps the server copy current but does not refresh other clients' caches.

Answer. No cache needs 20 s; with hit ratio 0.9, average is 2.09 ms per block and total is 2090 ms (2.09 s); staleness window is 30 s.

Exam traps

  • A larger cache or a higher hit ratio means fewer server contacts, so without validation the staleness window grows; a faster hit path changes nothing.
  • Do not mix remote access (one request per operation) with upload/download (copy the whole file, then write back).
  • Write-through is slower but more consistent; delayed write is faster but can lose dirty blocks on a client crash.
  • A file handle identifies a file on a stateless server; it is not the client's open-file descriptor. It carries no explicit rights bits, but since the server needs nothing else, holding the handle is enough to reach the file, so it behaves much like a capability.
  • Replication is not backup: replicas can all be changed, and the system still needs a rule for the current version.

6.9 Case studies: Linux and Windows operating systems

Linux and Windows both store rights on the object, as 6.3 describes. They differ in what sits on the object. Linux puts nine mode bits and a user id on every file. Windows puts a security descriptor holding an access list on every object. Reading both shows how one abstract idea becomes the commands you type. Only a few universities teach this case study.

You need: rights stored as columns on objects from 6.3, and the idea of a rights ticket from 6.5.

Linux: user ids and mode bits

A Linux process carries a user id (uid) and a group id (gid). Every file records an owner uid, a group gid, and nine permission bits.

The nine bits are read (4), write (2) and execute (1), repeated for owner, group and others. A field's value is the sum: 7 = rwx, 5 = r-x, 4 = r--. The command chmod 754 file sets the three fields to 7, 5 and 4. chown alice file changes the owner. umask is a mask of bits removed when a new file is created: with umask 022 a new file of 666 becomes 644.

Three special bits. setuid makes a program run with the file owner's uid. setgid does the same for the group. The sticky bit on a directory lets a file be deleted or renamed only by the file's owner, the directory's owner or root; /tmp uses this (mode 1777).

POSIX ACLs add per-user entries beyond the nine bits. sudo runs a command as another user after a password check. Linux capabilities split root's power into named units such as CAP_NET_ADMIN. PAM handles authentication. SELinux and AppArmor add mandatory checks that even root cannot skip. Namespaces and cgroups partition and limit processes.

Windows: SIDs, tokens and DACLs

Windows names every user and group by a security identifier (SID), a variable-length number. At login the system builds an access token: the user's SID, the SIDs of the user's groups, and privileges such as SeBackupPrivilege.

Every object has a security descriptor holding two lists. The DACL holds access control entries (ACEs) that allow or deny rights. The SACL records auditing.

The system walks the DACL from the top and stops at the first ACE that matches the token and the requested right. A deny ACE therefore beats any later allow. If no ACE allows the right, access is refused.

UAC (User Account Control) gives an administrator two tokens: a filtered one for normal work and a full one after consent.

Worked example

Question. A Linux file has mode 754, owner alice, group exam. User bob is in group exam. (a) Can bob write the file? Can he execute it? (b) A Windows file has this DACL in order: deny bob write, allow exam write, allow alice full control. Bob is in exam. Can bob write?

  1. Split 754: hundreds digit 7 for owner, tens digit 5 for group, units digit 4 for others.
  2. Each digit is a sum of 4 (read), 2 (write), 1 (execute). Owner 7 = 4+2+1 = rwx. Group 5 = 4+1 = r-x. Others 4 = r--.
  3. Bob is not alice, so the owner field is skipped. Bob is in exam, so the group field r-x applies.
  4. r-x gives read = yes, execute = yes, write = no. Bob can execute, cannot write.
  5. Windows: the first ACE matching bob's write request is the deny entry. Evaluation stops there, so bob is denied.
  6. Removing the deny entry leaves allow exam write as the first match, and bob can write.

Answer. Bob cannot write the Linux file but can execute it (group field 5 = r-x); on Windows the deny ACE is reached first, so he cannot write until that entry is removed.

Exam traps

  • Reading 754 as three unrelated digits instead of 4-2-1 sums.
  • Forgetting that a process holding the file's uid skips the group and other fields entirely.
  • In Windows, forgetting that the DACL is read top to bottom and the first matching ACE decides: a deny ACE beats an allow only because deny ACEs are normally stored first in the list.
  • Mixing up setuid (run as file owner) with sudo (run as a chosen user after a password).
  • Reading mode bits as if they applied in order like a DACL; Linux picks one field, owner first, then group, then others.

Yes. The first matching ACE is allow exam full control: exam is in bob's token and that ACE covers write, so checking stops and write is granted. He would be denied only if the deny ACE came before the allow, for example deny bob write placed first.

Takeaways

  1. Protection is inside the computer and checks each access; security is about deliberate attackers outside and inside.
  2. A domain is just the current list of (object, rights) a process holds, and every domain change must pass through a guarded point.
  3. The whole protection state fits into one access matrix, and real systems store it by columns (access lists) or by rows (capabilities).
  4. Revocation is easy for access lists and hard for capabilities, because a capability can be copied without the object knowing.
  5. Least privilege and fail-safe defaults prevent most damage even when a program is buggy.
  6. Every defence is only as strong as the weakest of authentication, authorisation, isolation and audit.
  7. A distributed system has no shared memory and no global clock, so processes must order events with logical clocks instead of wall time.
  8. Caching is what makes a distributed file system fast, and also what makes it inconsistent.
  9. Linux mode bits are a short access list per file; Windows stores a full access list of SIDs, which allows far finer sharing.

Exam question bank

Long answers in this unit usually expect a drawn access matrix, a clear access-lists-versus-capabilities comparison, and then the same ideas applied to Linux and Windows in the case-study question.

Remember and understand

Remember Define protection and security. State the goals of protection and explain least privilege, fail-safe defaults and separation of policy from mechanism with one example each. 13 marks

Protection: internal mechanism that checks whether a subject may use an object in the requested way; Security: defence against deliberate attack from outside or inside; Goals: controlled access, prevention of misuse of rights, detection of programming errors; Least privilege: give only the rights needed now; Fail-safe defaults: deny when no rule grants; Policy versus mechanism: rules stored as data, kernel only enforces.

Understand Explain the access matrix model. How is it implemented by access lists and by capability lists? Give one advantage and one disadvantage of each. 13 marks

Rows = domains, columns = objects, cell = set of rights; Access list: column stored with the object; easy to see who can use a file, hard to answer what a process can use; Capability list: row stored with the domain; fast check at use time, hard to revoke; Access list used by Linux and Windows; capability list used in tagged architectures and in capability OS designs; Sparse matrix in practice, so neither form stores all cells.

Understand What is a protection domain? Explain how a process changes domain, using setuid execution and a guarded procedure. 13 marks

Domain = current set of rights of a process; Rights are (object, operations) pairs; Domain change only through controlled entry points; setuid exec: file owner's id becomes process user id, so domain changes to the owner's; sudo: a guarded program that checks the user against a configuration file and then runs the command in the root domain; Danger: a bug inside a privileged domain is a security hole.

Understand What is revocation of access rights? Why is it difficult? Explain reacquisition, back-pointers and indirection as ways of making it work. 13 marks

Revocation = withdrawing a right already granted; Difficult because copies of a capability may exist in many processes; Reacquisition: re-ask for rights periodically; Back-pointers: object keeps a list of who holds a capability, so copies can be found; Indirection: capabilities point to a table entry, deleting the entry kills all copies at once; Access lists make revocation trivial: edit the list.

Apply

Apply A system has three domains D1, D2, D3 and three objects File1, File2, Printer. D1 holds read on File1 and write on File2; D2 holds execute on File1; D3 holds write on Printer and read on File2. Draw the access matrix and write out the access lists and the capability lists. 13 marks

Matrix of 3 rows and 3 columns with empty cells left blank; Access list for each object: list the (domain, rights) entries; Capability list for each domain: list the (object, rights) entries; Point out that each form contains exactly the same non-empty cells; Note the size difference when the matrix is sparse.

Apply Using a capability machine, show how a print server can accept jobs from a program without giving that program any other right. Explain what stops the program from forging a capability for another device. 13 marks

Capability = object identifier plus rights, held in a protected area the program cannot read or write; Printer capability carries only the write-job right; Forgery prevented by tagging memory words as capability or data and by hardware checks on capability registers; Kernel creates and destroys capabilities; user code can only copy or pass them through controlled calls; Compare with access lists, where the print server checks an identity at each request.

Apply Three processes P1, P2, P3 exchange messages. P1 does a then sends m1 to P2; P2 receives m1 then does b; P3 does c then sends m2 to P2, and P2 receives m2 after b. Assign Lamport timestamps and state the resulting order of events. 13 marks

Rule: each event increments the local counter; receipt sets counter to max(local, received) + 1; a before send m1; received timestamp carried in the message; b and c are concurrent: neither happens before the other; Total order obtained by breaking ties with process id; Show the final sequence of (event, counter, process).

Apply A distributed file system lets clients cache file blocks. For a sequence where client A reads a block, client B writes it, and A reads again, explain what A may return under write-through and write-back caching, and how a lease would fix it. 13 marks

With write-through, server copy is fresh but A's cache may be stale; With write-back, B's write may not have reached the server at all; Staleness window and its length; Callbacks or leases: the server promises to recall a cached copy before allowing a conflicting write; Consistency versus availability trade-off.

Apply A Linux file has mode 754. The owner is ravi, the group is project, and the file is a program. State who can read, write and execute it, and what happens when a user outside the group runs it. 13 marks

7 = rwx for owner, 5 = r-x for group, 4 = r-- for others; Owner ravi: read, write, execute; group members: read and execute; others: read only; A user outside the group gets the others class, so the execute bit is off and the kernel returns permission denied; Show that permissions are checked at open/exec time against the process's user and group ids; Mention that a directory needs the x bit to be entered.

Analyze and evaluate

Analyze Compare Linux mode bits with Windows access lists. Why does a general-purpose server need access lists, and what does an access list cost that mode bits do not? 13 marks

Mode bits: one owner, one group, one others class, three rights, stored in the inode; Windows: each object has a discretionary access list of (SID, access mask) entries, with allow and deny entries; Need: many users, many groups, different rights per user, inheritance from folders; Cost: longer check per open, more storage, more complex administration; Both are access-list implementations of the access matrix column.

Analyze Explain program threats: Trojan horse, trap door, logic bomb, stack and buffer overflow, and virus. For each, name one defence and say what property of the defence limits it. 13 marks

Trojan horse: hidden harmful code inside a useful program; signed packages limit it, but trust in the signer remains; Trap door: secret entry left by the author; code review and rebuilds limit it; Logic bomb: code that triggers on a condition; hard to detect statically; Buffer overflow: writing past an array overflows the return address; bounds checks, non-executable stack, address randomisation; Virus: code that copies itself into other programs; antivirus signatures fail against new variants; General point: isolation and least privilege limit the damage, audit detects it.

Evaluate A distributed system has no global clock. Evaluate the consequences for mutual exclusion and for file caching, and judge when physical time synchronisation is an acceptable substitute for logical clocks. 16 marks

No shared memory, so all coordination is by messages; No global clock, so we cannot say which of two events happened first by time stamp alone; Lamport happens-before ordering and vector clocks give causal order; Distributed mutual exclusion built on logical clocks or on a token; File caching with leases needs an agreed notion of lease expiry; Physical time via NTP is acceptable when clocks stay within a known bound and the cost of an occasional wrong ordering is small.

Evaluate 'sudo and setuid programs are the biggest holes in an otherwise least-privilege system.' Evaluate this claim and suggest controls that reduce the risk. 16 marks

Least privilege says run with only the needed rights; a privileged program is a deliberate exception; Any bug in a setuid-root program runs with root rights, so it can be exploited; sudo restricts who may become root and logs it, but a misconfigured rule is equally dangerous; Controls: keep privileged programs small, audit them, drop privileges after the privileged step, log every use, prefer fine-grained capabilities over full root; Trade-off: usability versus blast radius.

Glossary

Access list
The list of domains and their rights stored with a single object.
Access matrix
A table of domains against objects whose cells hold the permitted rights.
Access right
One permitted operation on one object, for example read on a file.
Audit
Recording security-relevant events so an attack can be detected and traced.
Authentication
Proving that a subject is who it claims to be.
Authorisation
Deciding what an authenticated subject is allowed to do.
Buffer overflow
Writing past the end of an array and overwriting nearby memory, often the return address.
Cache consistency
The property that a client never acts on a cached copy that is out of date beyond the agreed rules.
Capability
A protected token naming an object together with rights to it, unforgeable by user code.
Capability register
A hardware register whose contents the running program cannot modify, used to hold a capability.
Distributed file system
A file system whose files are stored on several servers but shown to clients as one set of files.
Distributed system
A set of independent computers that appear to users as one system and cooperate by passing messages.
Domain switching
Moving a process from one set of rights to another, allowed only through a controlled entry point.
Economy of mechanism
Keep the protection code small and simple, because every extra line is a possible hole.
Happens-before relation
Event a happens before event b if a could have influenced b through program order or message passing.
Lamport timestamp
A counter value assigned to each event so that happens-before implies a smaller timestamp.
Principle of least privilege
Give each process only the rights its present task needs.
Principle of separation of privilege
Require more than one condition, or more than one party, before a sensitive operation is allowed.
Protection
The internal mechanism that decides, for each access, whether a subject may use an object in the way requested.
Revocation
Withdrawal of a right after it was granted, including every copy of it.
Security
Defence of the system and its data against deliberate attack, whether from outside or from an authorised user.
Subject
The active party asking for access, normally a process acting for a user.
Trap door
A hidden entry point left in a program that skips the normal checks.
Trusted computing base
The small part of a system that must be correct for protection to hold.
