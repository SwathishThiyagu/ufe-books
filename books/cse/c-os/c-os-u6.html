6.1 Goals and principles of protection

Protection in an operating system aims to keep data safe, keep it correct, keep services running, and keep users accountable. The goals describe what we want to achieve; the principles tell how the OS should enforce those goals. These ideas appear whenever a system stores money, personal details, or critical infrastructure.

You need: basic OS concepts from Unit 1 Foundations.

Protection goals

Three primary goals guide every security mechanism. Confidentiality means that information is only disclosed to subjects that are authorized to see it. Integrity means that data cannot be altered without detection or proper authorization. Availability means that authorized users can access resources when they need them. Some syllabi call these the security objectives.

  • Confidentiality: no unauthorized read.
  • Integrity: no unauthorized write or tampering.
  • Availability: service remains up despite failures.

A mobile wallet app illustrates the three goals. The balance must stay secret from other apps (confidentiality), only the owner may debit the account (integrity), and the app must continue to work during a city power cut (availability).

A common trap is to think that a read‑only file also guarantees integrity. Confidentiality and integrity are separate; a file may be secret but still vulnerable to unauthorized modification if write rights are given to the wrong subject.

Protection principles

Principles are design rules that help the OS achieve the goals. Least privilege says each subject should receive only the rights it needs to perform its function. Fail‑safe defaults say that the default configuration should deny access unless explicitly allowed. Open design states that security should not rely on secrecy of the design; the mechanism must be robust even if its details are known. Separation of duties requires that critical actions be split among multiple subjects so that no single subject can abuse the system.

  • Least privilege reduces attack surface.
  • Fail‑safe defaults prevent accidental exposure.
  • Open design enables peer review and long‑term trust.
  • Separation of duties stops insider abuse.

These principles appear in many real‑world policies. For example, a bank’s UPI service grants a payment app only the right to debit the user’s account, not to read the full transaction history of other users. If the app crashes, the default is to block further debits until a manual reset (fail‑safe). The design of the cryptographic protocol is public (open design). Large transfers require approval from two separate devices (separation of duties).

  1. Identify the function a subject must perform.
  2. List the minimal rights required for that function.
  3. Grant only those rights and deny everything else.
  4. Review defaults: any missing right must be denied.
  5. Check that no single subject can complete a critical transaction alone.

  • Counting a right as unnecessary when it is actually required for a future feature – always compare with the current functional specification.

6.2 Domain of protection

A protection domain groups a set of subjects, a set of objects, and the access rights that subjects may exercise on those objects. It lets the operating system decide quickly whether a request is allowed. The idea is used in all modern OSes to keep user programs separate and to protect files, devices and memory.

You need: Goals and principles of protection and basic OS concepts from Unit 1.

Protection domain definition

A protection domain is a logical container. It contains subjects, objects and the rights that link them. A subject is an active entity such as a process or a user. An object is a passive entity such as a file, a device or a memory segment. An access right is a verb like read, write or execute.

  • Subject – a running program or a user identity.
  • Object – a resource that can be protected.
  • Right – the operation that a subject may perform on an object.

Some syllabi call the same idea a security domain. Only a few universities teach the domain model in depth, so the description stays concise.

The domain is enforced by a reference monitor. The monitor is a trusted component that mediates every request.

  1. Subject sends a request to the reference monitor.
  2. Monitor looks up the subject’s rights in the domain.
  3. If the right matches, the monitor permits the access.
  4. Otherwise the monitor denies the request.

Reference monitor operation

The reference monitor must be complete, tamper‑proof and verifiable. Completeness means no request can bypass it. Tamper‑proofness means the monitor cannot be altered by a subject. Verifiable means the monitor is small enough to be examined formally, ensuring its correctness. (Being always invoked follows from completeness.)

  • All subjects are identified before the request reaches the monitor.
  • The monitor checks the domain’s access‑right table.
  • The decision is made before the object is touched.

In practice the monitor is implemented as part of the kernel. It uses data structures such as the access matrix (see Access matrix) but the matrix itself is not the domain.

Worked example

Question. Process P1 (subject) wants to read file F1 (object). The protection domain contains the following rights: P1 – read → F1, P2 – write → F1, P1 – execute → progX. Is the request allowed?

C program.

#include <stdio.h>
#include <string.h>
int main(){
    char *subject = "P1";
    char *object = "F1";
    char *op = "read";
    // simplified domain table
    if (strcmp(subject, "P1") == 0 && strcmp(object, "F1") == 0 && strcmp(op, "read") == 0)
        printf("1\n"); // allowed
    else
        printf("0\n"); // denied
    return 0;
}
  1. Identify the subject (P1) and the object (F1).
  2. Look up the rights of P1 in the domain.
  3. P1 has a read right on F1.
  4. The requested operation is read, which matches the stored right.
  5. Therefore the reference monitor permits the access.

Answer. The request is allowed (output 1).

Exam traps

  • Confusing a protection domain with the access‑matrix table – the domain is the logical grouping, the matrix is one way to store rights.
  • Assuming the reference monitor can be bypassed by a privileged user – completeness forbids any bypass.
  • Mixing up subject and object order in the rights list – the right always reads subject → operation → object.

6.3 Access matrix and its implementation

The access matrix models every right a subject has on every object. It exists to give a clear, uniform view of protection. The model is used when an OS must decide whether a process can read a file, write a device, or execute a program. Real systems cannot store the full matrix, so they implement it as Access‑Control Lists (column‑wise) or capability lists (row‑wise).

You need: basic concepts of subjects and objects from Goals and principles of protection.

Definition of the access matrix

The matrix has subjects as rows and objects as columns. Each entry contains the set of rights the subject can exercise on the object. Rights are usually read (R), write (W), execute (X) or a combination. The matrix is also called a protection matrix in some courses.

If a cell is empty, the subject has no right on that object. The matrix gives a complete picture but can be very large in a real system.

M[s][o] = {rights}

M is the matrix; s is a subject row; o is an object column; rights is the set stored in that cell.

Column‑wise implementation: Access‑Control Lists

An ACL is stored with each object. It lists all subjects that have a right on that object and the specific rights. The OS checks the ACL of the target object when a request arrives.

  1. Read the object’s ACL.
  2. Search the list for the requesting subject.
  3. If the subject appears, verify that the required right is present.
  • Efficient for objects that have few subjects (short ACLs).
  • Revocation of a right means removing the subject from the ACL.

Row‑wise implementation: Capability lists

A capability list is stored with each subject. It contains a capability for every object the subject can access. A capability is a token that proves the holder’s rights.

  1. The subject presents the required capability (a token) to the kernel, which checks the rights encoded in that token.
  2. The kernel checks whether the capability for the target object includes the needed right.
  • Efficient for subjects that access few objects.
  • Transfer of a capability can be used for delegation.

Worked example

Question. Given the matrix in the figure, list the ACL for O1 and O2 and the capability list for subject S3. Then state the total number of granted rights in the matrix.

C program.

#include <stdio.h>
int main(){
    char *M[3][2] = {{"R","-"},{"-","W"},{"R","W"}};
    int cnt=0;
    for(int i=0;i<3;i++)
        for(int j=0;j<2;j++)
            if(M[i][j][0]!='-') cnt++;
    printf("%d\n",cnt);

}
  1. Read column O1: entries are S1‑R and S3‑R. The ACL for O1 is {S1: R, S3: R}.
  2. Read column O2: entries are S2‑W and S3‑W. The ACL for O2 is {S2: W, S3: W}.
  3. Read row S3: entries are O1‑R and O2‑W. The capability list for S3 is {O1: R, O2: W}.
  4. Count non‑empty cells: R at (S1,O1), R at (S3,O1), W at (S2,O2), W at (S3,O2). Total = 4 rights.

Exam traps

  • Assuming the full matrix must be stored in RAM; real OSes use ACLs or capabilities to keep it sparse.
  • Confusing the direction: ACLs are attached to objects (columns), capabilities to subjects (rows).
  • Treating ‘-’ as a right instead of “no right”. This adds a false entry to the count.
  • Forgetting that revocation in an ACL means deleting the subject entry, not just clearing the right symbol.

6.4 Access control and revocation of access rights

Operating systems must decide who can use a resource, verify the decision, and later withdraw the permission when it is no longer needed. The mechanisms for granting, checking and revoking rights keep data safe and support policies such as user ownership, security clearance, or job role. They appear in file servers, cloud services, and mobile apps where a user may gain or lose privileges during a session.

You need: the access matrix model and its implementation from access-matrix-and-its-implementation.

Discretionary and mandatory access control

Discretionary access control (DAC) lets the owner of an object decide which subjects may access it. The owner creates an entry in an access control list (ACL). Mandatory access control (MAC) enforces a system-wide policy based on security labels. Each subject and each object receives a label such as "confidential" or "top‑secret".

  • DAC: owner‑centric, flexible, common in desktop OS.
  • MAC: label‑centric, rigid, used in government and cloud.

allow_DAC(s, o, op) = (op ∈ ACL(o, s))

allow_DAC(s, o, op) is true if the ACL for object o grants operation op to subject s.

allow_MAC(s, o, op) = (label(s) ≥ label(o))

allow_MAC(s, o, op) is true if the security label of subject s dominates the label of object o. The operation op is not consulted in a pure MAC decision.

MAC evaluation steps:

  1. When a request arrives, the kernel reads the object's label.
  2. It reads the subject's label.
  3. It compares the labels according to the policy.
  4. If the comparison succeeds, the request is granted (no ACL lookup).

DAC evaluation steps:

  1. When a request arrives, the kernel reads the object's ACL.
  2. It checks whether the requested operation appears in ACL(o, s).
  3. If the operation is listed, the request is granted.
  4. Otherwise, the request is denied.

Role‑based access control and ACLs

Role‑based access control (RBAC) groups permissions into roles such as "admin" or "cashier". Users are assigned roles, and roles hold the ACL entries. This reduces the number of entries that must be updated when a user changes job.

  • Role → set of permissions.
  • User → set of roles.

Python program.

def check(user, file, op):
    for role in user.roles:
        if op in role.acl.get(file, []):
            return True
    return False

When a role is revoked, the system removes the role assignment from the user. Any ACL entries that were generated from that role are no longer effective; in implementations that store role‑derived ACL entries, those entries are removed atomically.

Revocation techniques for capabilities

A capability is an unforgeable token that combines an object reference with a set of rights. Revocation can be done by invalidating the token or by garbage collecting it after all references disappear.

  • Invalidation: the kernel marks the capability as revoked; future checks fail.
  • Revocation list: the kernel maintains a list of revoked capability identifiers. Any check against a revoked entry fails.
  • Versioning: each capability carries a version number; the kernel increments the version when revoking, making old copies invalid.

Reference counting is used for objects, not for capabilities. Objects are freed when their reference count reaches zero.

  1. The revocation request marks the capability entry as revoked.
  2. All processes that still hold a copy see the revoked flag on next check.
  3. When no process holds a live reference, the entry is reclaimed.

A common trap is to assume that revocation instantly removes every copy. Distributed systems may still have copies in remote caches until they are garbage collected.

Worked example

  2. Count the files: 3.
  3. Each file has one ACL entry for the admin role's write right.
  4. Therefore, 3 ACL entries are removed.

  • Assuming revocation instantly deletes all distributed capability copies; remote caches may retain them until garbage collection.
  • Confusing an ACL entry (object‑subject pair) with a role; revoking a role removes multiple entries, not just one.
  • Using the word "permission" for both the right and the ACL entry; the exam expects the count of entries.

6.5 Capability-based and language-based protection

Capability‑based protection gives a process a unique, unforgeable token that describes exactly which objects it may use. The token can be passed to other processes, allowing controlled delegation of authority, and can be withdrawn to stop further use. Language‑based protection relies on the programming language to enforce safety, for example by guaranteeing type safety or sandboxing untrusted code. Both approaches limit the damage a buggy or malicious program can cause, and they are used in micro‑kernels, mobile OSes, and secure web browsers.

You need: Access control and revocation and basic process concepts from earlier units.

Capability tokens

A capability is a data structure that contains the object identifier and the set of allowed operations. The kernel creates the token and stores it in a protected memory area, so a user process cannot modify it. When a process makes a system call, it presents the capability; the kernel checks the embedded rights and grants access if they match.

  • Unforgeable: only the kernel can issue a valid token.
  • Self‑describing: the token itself lists the rights.
  • Transferable: a process can give a copy to another process.

C = (obj_id, ops)

C is a capability; obj_id uniquely identifies the object; ops is the set of permitted operations such as read, write, execute.

Delegation and revocation

Delegation works by copying a capability and giving the copy to another process. The new holder can use the same rights, but the original holder still retains them unless the kernel revokes the token. Revocation can be implemented by version numbers or by a revocation list that the kernel checks on every access.

  1. Process A receives capability C for object O.
  2. A copies C and sends the copy to Process B.
  3. Kernel records that both A and B hold C.
  4. When revocation is requested, the kernel marks C as invalid for all holders.

C program.

#include <stdio.h>
struct cap { int obj; int valid; };
int use_cap(struct cap *c) {
    if (!c->valid) {
        printf("Capability revoked\n");
        return -1;
    }
    printf("Access granted to object %d\n", c->obj);
    return 0;
}
int main(){
    struct cap token = { .obj = 42, .valid = 1 };
    use_cap(&token);          // works
    token.valid = 0;          // kernel revokes
    use_cap(&token);          // fails
    return 0;
}

Output

Access granted to object 42
Capability revoked

Language‑based protection

A language can guarantee that a program never performs illegal memory accesses. Type safety ensures that a variable is used only according to its declared type. Sandboxing runs code in a restricted runtime that blocks system calls not explicitly permitted. The object‑capability model combines both ideas: an object reference is a capability, and the language prevents the creation of forged references.

  • Java bytecode verifier checks type safety before execution.
  • WebAssembly runs in a sandbox that isolates memory.
  • Erlang processes communicate by passing messages; while this model can be used to implement capability‑like security, the messages themselves are not capabilities.

Language‑based protection does not remove logical bugs; it only stops a program from breaking the OS or other programs.

Worked example

Question. A mobile payment app (App A) receives a payment‑token capability authorizing a payment of ₹500. The vendor app (App B) forwards the token to the bank service (Service C). If the user’s account initially holds ₹2000, compute the new balance after the transaction and state whether the vendor can reuse the token after it is revoked.

  2. Deduct authorized amount 500 ₹: 2000 ₹ − 500 ₹ = 1500 ₹.
  3. The kernel revokes the token after the first use.
  4. Because the token is revoked, any further attempt by the vendor to use it will be denied.

Exam traps

  • Confusing capability revocation with object deletion – revocation stops use of the token but does not delete the underlying object.
  • Assuming language‑based protection eliminates all bugs – it only blocks illegal memory or system‑call actions.
  • Treating a capability as a password – a capability also carries the rights, not just identity.
  • Forgetting that a copied capability must be passed through the kernel; direct memory copy bypasses checks.

6.6 The security problem: threats and attacks

The security problem lists the ways an operating system can be harmed. It exists because a computer stores data, runs money transfers, and controls devices like power meters. Knowing the main threat categories helps designers add checks and helps students answer exam questions. The list is used in system design, code review, and incident response in banks, e‑commerce sites, and railway ticketing.

You need: Goals and principles of protection, Access matrix, and basic process concepts from Units 1‑5.

Program threats

Program threats arise from code that runs with user input. A buffer overflow writes beyond the allocated memory region. The extra data can overwrite a return address. When the function returns, the CPU jumps to attacker code. An injection attack places malicious commands into a data field that later becomes code, such as SQL statements sent to a database.

  • Overflow: writes past array bounds.
  • Injection: inserts code into data fields.

P_success = P_vuln × P_exploit

P_success is the overall chance of a successful attack; P_vuln is the probability that a program contains the vulnerability; P_exploit is the probability that an attacker can trigger it.

  1. Identify an input buffer.
  2. Supply data longer than the buffer size.
  3. Observe a crash or altered control flow.

These attacks are common in web servers that process HTTP headers, in embedded controllers for power meters, and in legacy banking software that still uses C strings.

System threats

System threats target the operating system itself. Privilege escalation raises a normal user to an administrator or root user. The attacker first gains a foothold, then exploits a kernel bug to execute code in kernel mode. A rootkit hides its presence by modifying kernel data structures.

  • Escalation: moves from user to kernel privileges.
  • Rootkit: conceals malicious processes and files.
  1. Find a setuid program that calls a vulnerable library.
  2. Craft input that triggers the library bug.
  3. Run the program to obtain a root shell.

System threats appear when a bank’s internal server runs outdated Linux kernels. Attackers can then install a rootkit that hides fraudulent money transfers made through UPI.

Network threats and basic cryptographic tools

Network threats travel over communication links. A denial‑of‑service (DoS) flood overwhelms a service with requests, making it unavailable to legitimate users. A man‑in‑the‑middle (MITM) attacker intercepts and possibly alters traffic between two parties.

  • DoS: exhausts bandwidth or CPU.
  • MITM: reads or modifies exchanged data.

Cryptographic tools reduce the risk. A hash function maps a message to a fixed‑size digest. The digest length is denoted by h bits. A symmetric encryption algorithm uses a secret key K to produce ciphertext C = E_K(M). The same key decrypts: M = D_K(C).

h = 256

h is the length of a SHA‑256 digest in bits.

In Indian railway ticketing (IRCTC), passwords are stored as SHA‑256 hashes. During a transaction, the client and server exchange data encrypted with AES‑128, a symmetric cipher that uses a 128‑bit key.

6.7 Distributed operating systems and distributed synchronization

A distributed operating system hides the fact that resources live on many computers. It gives the programmer a single system image. The OS must keep state consistent across nodes and let them act together. Synchronization is needed because actions on different machines can interleave. Logical clocks order events without a global timer. Distributed locks let only one node enter a critical section at a time. The ideas are used in cloud services, online gaming, and banking back‑ends that run on many servers.

You need: Unit 3 Process Synchronization and Deadlocks.

Transparency in a distributed OS

A distributed OS appears as a single machine to the user. It hides where code runs, where data lives, and how many copies exist. This is called transparency. Three main types are location, migration, and replication transparency.

  • Location transparency: a program can refer to a file without knowing which node stores it.
  • Migration transparency: a process can move to another node without changing its identifier.
  • Replication transparency: several copies of a service exist, but the user sees only one.

Transparency simplifies programming. The programmer writes code as if it runs on one computer. The OS handles message passing, data copying, and failure recovery.

  1. User issues an I/O request.
  2. OS locates the nearest replica.
  3. OS forwards the request to the replica.
  4. Result is returned as if it came from a local device.

Logical clocks and Lamport timestamps

Physical clocks on different nodes drift. Distributed algorithms use logical clocks to order events. Lamport timestamps are a simple scalar clock.

C_i = max(C_i, C_j) + 1

C_i is the clock of node i after receiving a message; C_j is the timestamp attached to the received message.

When a node sends a message, it increments its clock and attaches the value. The receiver updates its clock using the formula above. This guarantees that if event A happens before event B, then timestamp(A) < timestamp(B).

  1. Node1 increments its clock to 5 and sends a lock request.
  2. Node2 receives the request with timestamp 5, updates its clock from 7 to max(7,5)+1 = 8.
  3. Node2 replies with its new clock value.

Distributed mutex using a reference monitor

A reference monitor (RM) serialises lock requests. Nodes ask the RM for a lock. The RM grants the lock to the node with the smallest timestamp that is not currently holding the lock.

  • Node sends request with its Lamport timestamp.
  • RM compares timestamps of all pending requests.
  • RM sends "grant" to the chosen node.
  • Node releases lock; RM updates its queue.

C program.

#include <stdio.h>
int main(){
    printf("Lock granted to Node1\n");
    return 0;
}

Output

Lock granted to Node1

Worked example

Question. Node1 wants a mutex lock. Its Lamport timestamp is 5. Node2 currently holds the lock with timestamp 7. The reference monitor follows the rule: grant to the node with the smallest timestamp that is not holding the lock. Show the steps and state which node receives the lock.

C program.

#include <stdio.h>
int main(){
    int ts1 = 5, ts2 = 7;
    int grant_node = (ts1 < ts2) ? 1 : 2;   // 1 = Node1, 2 = Node2
    int new_time = (ts1 > ts2 ? ts1 : ts2) + 1; // logical time after lock release
    printf("Lock granted to Node%d at logical time %d\n", grant_node, new_time);
    return 0;
}
  1. Node1 sends request with TS=5.
  2. RM compares timestamps: Node1=5, Node2=7 (currently holding).
  3. Since Node2 holds the lock, RM queues Node1's request.
  4. Node2 finishes its critical section and releases the lock.
  5. RM now grants the lock to the queued request with smallest TS, i.e., Node1.
  6. Node1 receives the lock at logical time max(5,7)+1 = 8.

Exam traps

  • Assuming a global physical clock exists; Lamport timestamps are logical, not real time.
  • Confusing the timestamp of the lock holder with the timestamp of the request; the grant time is computed after release.
  • Forgetting to increment the clock after sending a message; the sender must advance its own clock before attaching the timestamp.
  • Treating the reference monitor as a centralized lock server only; in practice it can be replicated with consensus.

6.8 Distributed file systems

Distributed file systems (DFS) let many computers share files as if they were on one disk. They hide network latency, server failures and replication from the user. DFS is used for collaborative editing, cloud storage and video delivery.

You need: distributed operating systems and file‑system basics.

Architecture of a DFS

A DFS can be built as a client‑server system where each client talks to one or more file servers, or as a peer‑to‑peer system where every node can act as both client and server. In the client‑server model the client keeps a local cache of recent blocks. The cache reduces traffic but must stay coherent with the servers. In a peer‑to‑peer layout the same coherence protocol runs among all peers, allowing any node to store a replica.

  • Client – process that reads or writes files.
  • Cache – memory on the client that stores recent blocks.
  • Server(s) – machines that store the authoritative copy(s) of files.

P(stale) = D ÷ T

P(stale) is the probability that a read returns stale data; D is the average replication delay in ms; T is a chosen timeout window in ms (here 10 000 ms).

  1. Write request reaches Server1.
  2. Server1 stores the new block and starts asynchronous replication to Server2.
  3. Server2 acknowledges after delay D.
  4. Client reads from its cache; if the read occurs before the acknowledgment, the data may be stale.

Consistency models

Strong consistency guarantees that every read sees the most recent write. It can be achieved by having the client obtain acknowledgments from a majority (quorum) of replicas for both reads and writes; waiting for all replicas is stricter but unnecessary. Many commercial DFS choose eventual consistency to reduce write latency.

Eventual consistency relaxes the guarantee: if no new writes occur, all replicas converge after some propagation time. The stale‑read probability can be estimated with the formula shown earlier.

  • Read‑your‑writes: a client always sees its own writes.
  • Monotonic reads: a client never sees older versions after a newer one.
  • Session consistency: combines the two for a user session.

Python program.

def stale_probability(delay_ms, timeout_ms=10000):
    return delay_ms / timeout_ms
print(stale_probability(200))

Output

0.02

Replication, caching and failure handling

N = total number of replicas, W = minimum number of replicas that must acknowledge a write, R = minimum number of replicas that must be consulted for a read. Replication improves availability. A common strategy is primary‑backup: the primary accepts writes, backups receive updates asynchronously. Quorum replication requires any write to be stored on at least W replicas and any read to consult at least R replicas, with W+R > N to guarantee overlap.

Caches store file blocks locally. On a write the client must invalidate or update its cached copy. Invalidate‑on‑write is simple but can cause a brief window of stale reads. Update‑on‑write pushes the new block to the cache immediately, reducing staleness at the cost of extra messages.

If a server crashes, the client retries the operation with another replica. When the primary fails, a new primary is elected among the backups. The system detects failure via heartbeat timeout and re‑synchronizes divergent replicas before serving reads.

  • Replication delay D ≈ 200 ms in many LAN‑based DFS.
  • Stale‑read probability ≈ 0.02 with a 10 s timeout.
  • Quorum settings (N=3, W=2, R=2) give strong consistency with one failure tolerance.

  • Assuming replication delay is a latency for every read; it matters only for writes that need to propagate.
  • Assuming cache invalidation automatically gives the latest data without a subsequent read to a server.

6.9 Case studies: Linux and Windows operating systems

This chapter contrasts how Linux and Windows enforce protection and security. It shows the identifiers, access‑control models and mandatory‑policy modules each OS uses. The comparison helps you answer exam questions that ask which OS feature blocks a given operation, and it prepares you for real‑world tasks such as setting file permissions on a server or configuring UAC on a laptop.

You need: access‑matrix concepts, access‑control basics and capability ideas.

Linux protection mechanisms

Every Linux process runs with a numeric user identifier (UID) and a group identifier (GID). The kernel checks these IDs against the owner and group bits of a file’s mode. The mode is usually shown as a four‑octal digit value. The lower three digits represent read (4), write (2) and execute (1) permissions for owner, group and others. The leading digit holds the special bits: setuid (4), setgid (2) and sticky (1).

  • UID/GID – unique numbers assigned to each user and group.
  • Discretionary Access Control (DAC) – file mode bits (r, w, x) that the owner can change.
  • Capabilities – fine‑grained rights (e.g., CAP_NET_ADMIN) that can be given to a process without making it full root.
  • SELinux or AppArmor – mandatory access control (MAC) policies that restrict what a process may do regardless of DAC.
  • sudo – a program that temporarily gives a process additional capabilities after authenticating the user.

C program.

#include <stdio.h>
int main(){
    printf("UID: %d User: %s\n", 1000, "alice");
    return 0;
}

Output

UID: 1000 User: alice

Windows protection mechanisms

Windows identifies each security principal with a Security Identifier (SID), a string such as S‑1‑5‑21‑... . Objects store Access Control Lists (ACLs) that contain Access Control Entries (ACEs). Each ACE maps a SID to a set of allowed or denied rights.

  • SID – unique identifier for users, groups and services.
  • ACL – list of ACEs attached to a file, registry key or other object.
  • Integrity levels – a MAC feature that assigns Low, Medium, High and System levels and limits read, write and execute access based on the object's integrity level.
  • User Account Control (UAC) – prompts the user and creates a filtered token when an admin tries a privileged operation.
  • Access token – the collection of SIDs and privileges that the kernel checks on every request.

Python program.

import os, getpass
print('SID: S-1-5-21-1000')
print('User:', getpass.getuser())

Output

SID: S-1-5-21-1000
User: runner

Exam traps

  • Confusing Linux capabilities with Windows privileges – capabilities are per‑process rights, while Windows privileges are attached to the access token and may be filtered by UAC.
  • Assuming mode 600 blocks the owner; it actually *allows* the owner to read and write.
  • Treating an ACL entry as a Boolean allow/deny only – ACLs can contain both allow and deny ACEs that are evaluated in order.
  • Thinking that UAC always grants full admin rights; it only elevates after the user consents, otherwise a filtered token is used.

Takeaways

  1. Protection goals of confidentiality, integrity and availability guide every security decision.
