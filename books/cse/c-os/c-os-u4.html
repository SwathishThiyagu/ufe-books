4.1 Memory management strategies and address spaces

A process never touches physical memory directly. It uses its own logical addresses, numbered from zero, and a small hardware unit translates each one to a physical address after a safety check. This separation lets the OS place a program anywhere in RAM, move it later, and stop one process from reading another's data. Every phone app, UPI payment and IRCTC booking runs behind this translation. This chapter sets up the model: binding time, logical versus physical addresses, and the base-limit memory-management unit.

You need: dual-mode operation and interrupts from Unit 1, Foundations; the process and its PCB address space from Unit 2, Processes, Threads and CPU Scheduling.

Address binding and two kinds of address

Before the CPU can run an instruction, the instruction and its data must sit at some physical address in RAM. The act of fixing those addresses is called address binding. It can happen at three moments.

Compile time: the compiler knows the exact address and emits absolute code. The program must load at that address, so moving it means recompiling. Small embedded firmware often works this way.

Load time: the compiler emits relocatable code. The loader chooses a start address when the program is first loaded and adjusts addresses once. The process cannot move after that.

Execution time: the process may move while running. The CPU must translate every address at the moment of use, so this needs hardware support. General-purpose operating systems use this.

The address the CPU generates is a logical address; many syllabi call it a virtual address. The address the memory unit sees is a physical address. The set of logical addresses a process uses is its logical address space. A process's logical space starts at 0, independent of where it sits in RAM. The OS keeps the mapping private to each process, which is the base of protection.

The memory-management unit: base plus limit

Translation is done by the memory-management unit (MMU), a hardware block between CPU and memory. The simplest MMU has two registers per process.

The base register holds the smallest physical address of the process. Some syllabi call it the relocation register. The limit register holds the size of the process in bytes or words. It is a size, not the last valid address.

For every memory reference the CPU sends an offset. The MMU applies one rule.

if offset ≥ limit → trap; else physical = base + offset

base is the process start in physical memory; offset is the logical address; limit is the process length; physical is the translated physical address; trap means an address error sent to the OS.

The order matters. Check the limit first, then add the base. If you add first, a large offset can land inside another process and read or overwrite it.

The check is protection. In a multiprocessor or time-sharing machine, each process has its own base and limit. The OS loads the pair on a context switch (see Unit 2, Process scheduling queues and context switching). A trap goes to the OS, which usually terminates the offending process.

Allocation strategies and library loading

Translation answers where an address goes. Allocation answers where the OS puts each process.

Contiguous allocation gives each process one continuous block. It is simple, but free memory breaks into holes; choosing a hole is covered in 4.3, and moving a process out is 4.2.

Non-contiguous allocation splits a process. Paging cuts memory into fixed frames and the process into same-size pages, so pages can sit anywhere (4.4, 4.5). Segmentation uses variable pieces such as code, stack and heap, each with its own base and limit (4.6). Virtual memory adds demand paging later (4.7).

Three loading ideas save memory. Dynamic loading loads a routine only when it is first called. Dynamic linking postpones linking until run time: a small stub finds the library routine. A shared library is one copy on disk and in memory, mapped by many processes; the code is shared, while each process keeps its own data.

Worked example

Question. A system uses execution-time binding with a base register of 14000 and a limit register of 1000, in word addresses. For each logical address, give the physical address or state the trap: (a) 346 (b) 999 (c) 1200.

  1. Read the rule: if offset ≥ limit, trap; else physical = base + offset. Here base = 14000 and limit = 1000.
  2. (a) offset = 346. 346 < 1000, so the access is valid. physical = 14000 + 346 = 14346.
  3. (b) offset = 999. 999 < 1000, so the access is valid. physical = 14000 + 999 = 14999.
  4. (c) offset = 1200. 1200 ≥ 1000, so the access is invalid. The MMU raises a trap and no physical address is produced.

Answer. The valid physical addresses are 14346 and 14999; logical address 1200 traps with an address error.

Exam traps

  • Adding the base before checking the limit. A bad offset can then read another process; the check must come first.
  • Quoting a logical address as if it were physical. Only base + offset after a valid check gives a physical address.
  • Treating the limit register as the last valid address. It is the size, so offset equal to limit traps.
  • Assuming compile-time binding is normal. Absolute code cannot be moved; execution-time binding needs MMU hardware.
  • Swapping the base and limit. Base is the start address; limit is the length.

4.2 Swapping of processes

When memory is full and another process needs space, the operating system can copy one whole process out to disk and later copy it back. The disk area that holds these copies is the backing store, also called swap space. This is swapping: roll out, then roll in. It lets more processes take turns in a small memory than could fit at once. The catch is time. Moving a whole process costs far more than the CPU work it saves, so classic whole-process swapping has largely given way to moving individual pages.

You need: 4.1 for what lives in memory, and Unit 2 for context switching and scheduling queues.

Roll out and roll in

The memory manager wants the CPU busy. The CPU is busy only if some ready process sits in memory. When memory is full and a new or higher-priority process needs frames, one option is to move a process out of the way entirely.

Swapping does exactly that. The OS picks a victim, usually a process that is blocked or has low priority, and copies every byte of it from memory to a disk area. That is swap out, also called roll out. Later, when the process should run again, the OS copies it back: swap in, or roll in. The disk area is the backing store, also called swap space or the swap device.

The backing store must hold copies of every process that might be out at the same time, and it must allow direct access, so any process can be read back without scanning past the others.

The classic rule: a process is either entirely in memory or entirely on disk. Half-swapped processes do not exist in this scheme. So the moment a victim is chosen, all its frames become free at once, and the waiting process can be loaded into that space.

Two decisions belong to the OS: which process to swap out, and when. Swapping out a process that will be needed again soon wastes disk bandwidth and delays it.

The cost is transfer time

A swap is pure copying, so its cost is set by the disk, not the CPU. Each direction takes the process size divided by the transfer rate, plus one disk latency for the seek and rotation.

T_swap = 2 × (S ÷ R + L)

T_swap is the total swap time in seconds; S is the process size in megabytes; R is the disk transfer rate in MB/s; L is the disk latency in seconds; the factor 2 counts the copy out and the copy in.

Latency is a few milliseconds on a hard disk, so the transfer dominates for any decent-sized process. Notice what the formula says: swap time grows in a straight line with process size.

Values in the table use R = 50 MB/s and L = 10 ms. If the next process to run is not in memory, the context switch cannot finish until the copy in completes. So context-switch time is not a fixed few microseconds; it becomes proportional to process size (see Unit 2).

Why whole processes rarely swap now

Compare the two numbers. A 100 MB process costs 4.02 s to swap. On the same machine a time slice might be 10 ms. That swap is worth 402 time slices. No scheduler can win that trade, even if the swapped process would use every slice fully. Meanwhile the CPU sits idle, or at best runs the other processes, while the disk copies.

So modern systems still swap, but in much smaller units. A page is typically 4 KB. Copying a page at 50 MB/s takes about 0.08 ms, slow but survivable, especially since most needed pages are already in memory. Page-level work is covered in 4.7 and 4.8.

  • Unix-style systems keep a swap area and send pages to it only when free memory falls below a threshold; otherwise they free memory by dropping clean file pages and writing back dirty ones.
  • Windows uses page files, written page by page, sized by the system or the user.
  • Linux also has a swap partition or swap file, but it moves pages, not whole processes.
  • Android and iOS normally do not swap to disk. Android may swap into a compressed area of RAM (zram); iOS keeps no swap device. With no disk swap, both end idle background apps when memory runs short.

How swap space is laid out on disk is a file-system topic; see Unit 5.

Worked example

Question. A process of 100 MB must be swapped out of memory. The backing store transfers at 50 MB/s and has a disk latency of 10 ms per transfer. The CPU time slice is 10 ms. Find (a) the copy-out time, (b) the time for one complete swap, and (c) how many time slices that swap is worth.

  1. Copy-out transfer time = S ÷ R = 100 MB ÷ 50 MB/s = 2 s.
  2. Add one disk latency: 2 s + 0.010 s = 2.01 s to write the process to swap space.
  3. Copy in is the same size at the same rate: 2 s + 0.010 s = 2.01 s to read it back.
  4. One complete swap = 2.01 s + 2.01 s = 4.02 s.
  5. Time slices lost = 4.02 s ÷ 0.010 s per slice = 402 slices.

Answer. Copy out takes 2.01 s, one complete swap takes 4.02 s, and that is worth 402 time slices of 10 ms.

Exam traps

  • Counting the transfer only once. The process goes out and comes back, so the transfer cost doubles; 100 MB at 50 MB/s is 4 s of transfer, not 2 s.
  • Mixing MB (megabytes) with Mb (megabits). 100 MB at 50 Mb/s is 16 s, not 2 s. Divide by 8 when the sizes are in different units.
  • Thinking swap time is a small constant. It is linear in process size, which is exactly why whole-process swapping lost to paging.
  • Forgetting the disk latency, or adding it once instead of twice. Each of the two transfers pays its own latency.
  • Treating swapping and paging as the same thing. Classic swapping moves a whole process and leaves it entirely in memory or entirely on disk; paging moves individual pages and keeps the rest in memory.

4.3 Contiguous memory allocation and fragmentation

Contiguous memory allocation gives each process one continuous block of physical memory. The idea is simple: a process starts at one address and grows upward, with no gaps inside its block. Fixed partitions, made at boot, waste space inside a partition. Variable partitions create free holes at run time. The OS must choose a hole for every new process using first fit, best fit, worst fit or next fit. The choice decides how much memory is wasted. This scheme is the baseline that paging and segmentation improve on.

You need 4.1 for base and limit, and 4.2 for what happens when no hole is big enough.

Variable partitions and holes

In variable partitioning, the OS does not pre-cut memory. It starts with one large free block. When a process arrives, the OS takes a hole—a continuous free block—large enough for it and gives the process the first part. The rest of the hole stays free. When the process exits, its block becomes a hole again. The OS merges that hole with any free neighbours, so two adjacent holes become one bigger hole. Without merging, memory breaks into many small pieces.

  • First fit: scan holes from the start and take the first hole that fits.
  • Best fit: scan all holes and take the smallest hole that fits.
  • Worst fit: scan all holes and take the largest hole that fits.
  • Next fit: like first fit, but resume scanning from the hole after the last placement, not from the start.

leftover = hole size − request size

leftover is the free space left in the chosen hole, in KB here; hole size and request size are also in KB. The formula applies only when hole size ≥ request size.

Fixed partitions and internal fragmentation

In fixed partitioning, the OS cuts memory into a fixed number of partitions at boot. The partition sizes stay fixed for the life of the system. A process must fit completely inside one partition. If a 300 KB process sits in a 512 KB partition, 212 KB inside that partition is wasted. This waste is internal fragmentation: the unused space is inside the allocated block. The process cannot share the leftover with another process. The number of partitions limits how many processes can be in memory at once. Some systems use unequal partitions to fit common process sizes. Fixed partitions are simple and need no hole search, but every process that does not fill its partition pays the waste.

External fragmentation, compaction and the 50-percent rule

Variable partitions avoid internal waste but create external fragmentation. Free memory is split into holes between allocated blocks. Total free memory may be large enough for a new process, yet no single hole is big enough, so the process waits even though memory is free. Compaction fixes this by sliding allocated blocks together, leaving one large hole. Moving a running process changes its physical addresses. Compaction therefore needs execution-time relocation: the CPU must translate every logical address to a physical address at run time, and the OS updates the process's base register after the move. A program that uses absolute physical addresses cannot be moved safely.

The 50-percent rule is a rule of thumb for first fit. Over a long run, with many processes arriving and leaving, about half of memory ends up in holes, on average, and half in allocated blocks. The number of holes grows too, so searching takes longer. The rule is an average, not a limit. Fixed-size blocks, covered in 4.4, remove external fragmentation by allowing any free frame to hold any page. Variable-length logical pieces in 4.6 face a related placement problem.

Worked example

Question. Free holes in address order are 100 KB, 500 KB, 200 KB, 300 KB and 600 KB. Requests arrive in this order: 212 KB, 417 KB, 112 KB and 426 KB. For first fit, best fit and worst fit, show the hole used by each request, the leftover after each successful placement, and whether every request is placed.

  1. Start with holes H = [100, 500, 200, 300, 600] KB.
  2. First fit, 212 KB: 100 is too small; 500 fits. Take 500. Leftover = 500 − 212 = 288 KB. H = [100, 288, 200, 300, 600] KB.
  3. First fit, 417 KB: 100, 288, 200 and 300 are too small; 600 fits. Take 600. Leftover = 600 − 417 = 183 KB. H = [100, 288, 200, 300, 183] KB.
  4. First fit, 112 KB: 100 is too small; 288 fits. Take 288. Leftover = 288 − 112 = 176 KB. H = [100, 176, 200, 300, 183] KB.
  5. First fit, 426 KB: largest hole is 300 KB, which is less than 426 KB. No hole fits; request waits.
  6. Best fit, 212 KB: fitting holes are 300, 500 and 600; smallest is 300. Take 300. Leftover = 300 − 212 = 88 KB. H = [100, 500, 200, 88, 600] KB.
  7. Best fit, 417 KB: fitting holes are 500 and 600; smallest is 500. Take 500. Leftover = 500 − 417 = 83 KB. H = [100, 83, 200, 88, 600] KB.
  8. Best fit, 112 KB: fitting holes are 200 and 600; smallest is 200. Take 200. Leftover = 200 − 112 = 88 KB. H = [100, 83, 88, 88, 600] KB.
  9. Best fit, 426 KB: 600 fits. Take 600. Leftover = 600 − 426 = 174 KB. H = [100, 83, 88, 88, 174] KB. All four requests are placed.
  10. Worst fit, 212 KB: largest hole is 600. Take 600. Leftover = 600 − 212 = 388 KB. H = [100, 500, 200, 300, 388] KB.
  11. Worst fit, 417 KB: largest fitting hole is 500; 388 is too small. Take 500. Leftover = 500 − 417 = 83 KB. H = [100, 83, 200, 300, 388] KB.

Exam traps

  • Best fit is not always the best overall. It leaves the smallest leftovers, which often become tiny holes too small to use.
  • External fragmentation is holes between allocated blocks, in variable partitions. Internal fragmentation is waste inside a fixed partition or the last page of a process.
  • Next fit does not rescan from the start; it continues from the hole after the last placement, so its holes chosen can differ from first fit.
  • Compaction needs execution-time relocation. Moving a process is safe only if its addresses are translated at run time and its base register is updated.
  • The 50-percent rule is an average for first fit, not a rule that half of RAM must stay free or a fixed limit.

4.4 Paging and the translation look-aside buffer

Physical memory is cut into fixed-size frames; each process is cut into pages of the same size. A page table maps each page to any free frame, so memory need not be contiguous. Because page size is a power of two, the hardware splits an address into page number and offset by bits. A small cache called the translation look-aside buffer (TLB) keeps recent translations, avoiding a second memory read on most accesses. Every phone app, database and cloud virtual machine uses this pair: paging gives flexible placement, and the TLB makes it fast.

You need 4.1 for logical versus physical addresses and 4.3 for why contiguous allocation fails.

Pages, frames and the address split

Physical memory is cut into fixed-size blocks called frames. A process is cut into blocks of the same size called pages. Page and frame sizes are equal and always a power of two, so the hardware can split a logical address by bits instead of dividing.

p = logical address ÷ page size (integer part); d = logical address mod page size; physical address = frame × page size + d

p is the page number, d is the offset inside the page, and frame is the frame number that the page table gives for page p.

With page size 4 KB = 4096 bytes and a 32-bit logical address, the offset needs d = log₂ 4096 = 12 bits. The page number gets the remaining p = 32 − 12 = 20 bits.

Logical address 8196 = 2 × 4096 + 4, so page number p = 2 and offset d = 4. Each process has a page table with one entry per page. Entry 2 says frame 5. Physical address = 5 × 4096 + 4 = 20484.

The page-table base register (PTBR) holds the physical address of the page table; some syllabi call it the page-table pointer. Pages need not be contiguous, so any page can go in any free frame. Only the last page of a process may waste space inside its frame; this waste is internal fragmentation.

Why a TLB, and effective access time

Without a TLB every memory access costs two reads: one for the page-table entry and one for the data. The translation look-aside buffer (TLB) is a small, fast, associative memory inside the CPU. It caches recent page-table entries.

  • On a hit, the frame number is available at once and the access needs one memory read.
  • On a miss, the CPU reads the page table, then the data, and copies the entry into the TLB.
  • An address-space identifier (ASID) in each TLB entry tells which process the entry belongs to, so a context switch need not flush everything.
  • Some entries are wired: they cannot be evicted, and the kernel uses them for code that must never fault.

EAT = h(t + m) + (1 − h)(t + 2m)

h is the hit ratio (0 to 1), t is the TLB search time in ns, m is one memory access time in ns, and EAT is the effective access time in ns.

Take h = 0.8, t = 10 ns and m = 100 ns. EAT = 0.8 × (10 + 100) + 0.2 × (10 + 100 + 100) = 88 + 42 = 130 ns. The miss case has two memory reads, not one.

What page size changes

A larger page means fewer page-table entries and fewer TLB misses, but more waste in the last page of each process. A smaller page wastes less, but the table grows and the TLB holds fewer useful translations. The operating system picks a size that balances table size, TLB reach and fragmentation.

The page table itself lives in memory, so the PTBR changes on every context switch. On a TLB miss the hardware reads the entry at PTBR + p × entry size. A page-table entry usually also stores valid, protection and dirty bits; those bits are checked during translation.

Worked example

Question. A system has 32-bit logical addresses and a page size of 4 KB. (a) How many bits are used for the page number and the offset? (b) Translate logical address 8196 when the page table says page 2 is in frame 5. (c) Find the effective access time if the TLB hit ratio is 0.8, TLB search takes 10 ns and a memory access takes 100 ns.

  1. Page size = 4 KB = 4096 = 2¹² bytes, so offset bits d = log₂ 4096 = 12 bits.
  2. Page-number bits p = 32 − 12 = 20 bits.
  3. 8196 ÷ 4096 = 2 with remainder 4, so page number p = 2 and offset d = 4.
  4. Page-table entry 2 gives frame 5.
  5. Physical address = 5 × 4096 + 4 = 20480 + 4 = 20484.
  6. EAT = 0.8 × (10 ns + 100 ns) + 0.2 × (10 ns + 100 ns + 100 ns).
  7. EAT = 0.8 × 110 + 0.2 × 210 = 88 + 42 = 130 ns.

Answer. Offset bits = 12, page-number bits = 20, physical address = 20484, and EAT = 130 ns.

Exam traps

  • Do not compute offset bits as log₂(number of pages). It is log₂(page size in bytes).
  • EAT on a TLB miss includes the TLB search plus two memory reads: one for the page-table entry and one for the data.
  • A page is a logical unit and a frame is a physical unit; do not say a process is divided into frames.
  • Internal fragmentation occurs only in the last page of a process, not in every page.
  • The PTBR stores the physical address of the page table, not the page number of the current page.

4.5 Structure of the page table

A page table maps every virtual page of a process to a physical frame. For a 32-bit address space with 4 KB pages, a flat table needs about one million entries, roughly 4 MB for every process. Most entries are unused. Operating systems therefore split, hash or invert the table and keep only the parts the process actually uses. This keeps context switches and memory use under control while translation stays fast with the TLB from 4.4.

You need 4.4 for the page number p, offset d, page-table entry (PTE) and page-table base register (PTBR).

The flat table is too large

In 4.4, each process has a page table with one entry per virtual page. The page number has m − n bits when the logical address has m bits and the offset has n bits. One PTE is often 4 bytes. The table size is the number of entries times the PTE size.

PTEs = 2m − n; table bytes = PTEs × PTE size

m is the number of bits in the logical address; n is the number of offset bits, so page size = 2n bytes; one PTE is 4 bytes in the running example.

For a 32-bit address and 4 KB pages: n = 12, so m − n = 20; 2²⁰ = 1,048,576 entries; at 4 bytes each, 4,194,304 bytes = 4 MB per process. Fifty processes would need 200 MB just for page tables, and most entries point nowhere because a process uses a small part of its address space.

Two-level and multi-level paging

Two-level paging splits the page number p into p1 and p2. The first-level (outer) table is indexed by p1. Its entry points to a second-level (inner) table, which is indexed by p2. That entry gives the frame number. The offset d then picks the byte inside the 4 KB frame. The address is p1 | p2 | d.

m = p1 bits + p2 bits + d bits

m is the logical-address width; p1 indexes the outer table; p2 indexes an inner table; d is the offset inside a page.

In the running example, 20 page-number bits split as 10 + 10, so d = 12 bits. The outer table has 2¹⁰ = 1024 entries and is 4 KB. Each inner table also has 1024 entries and is 4 KB. An inner table exists only when some page in its 4 MB range is used. A process with three separate 4 MB regions needs one outer table and three inner tables: 4 KB + 3 × 4 KB = 16 KB, not 4 MB.

A three-level table splits p again. A flat 64-bit table is impossible, so common designs use four or five levels, hashed tables or inverted tables.

Hashed and inverted tables, and ASIDs

A hashed page table stores entries in buckets. The hardware hashes the virtual page number, then walks the chain in that bucket comparing stored virtual page numbers until it finds a match. The matching entry gives the frame number. A chain handles collisions. This is common for address spaces larger than 32 bits.

An inverted page table has one entry per physical frame, not per virtual page. Each entry stores the process id and virtual page number that occupy that frame, plus protection data. To translate, the OS or hardware searches the table; a hash on pid and page number makes the search short. One table serves all processes, so it is small, but a miss costs a search and sharing pages is awkward.

A translation look-aside buffer (TLB) caches recent translations. On a context switch, old entries belong to the old process. An address-space identifier (ASID) is stored with each TLB entry; the hardware compares the ASID as well as the page number. Then the OS need not flush the whole TLB at every switch.

Worked example

Question. A 32-bit logical address uses 4 KB pages and 4-byte page-table entries. (a) Find the number of entries and the size of a flat page table. 4.6 Segmentation of memory

Segmentation cuts a process into variable-length pieces the programmer wrote: machine code, global data, stack, heap and shared libraries. Each piece is a segment with number, base and length. A CPU address becomes (segment number, offset); hardware checks offset against length before adding base. Programs are unequal pieces, not fixed blocks, so this gives per-segment protection and sharing. It survives in x86, linker sections and thread-local storage.

You need logical addresses and limit checks from 4.1 and holes and external fragmentation from 4.3.

Pieces the programmer wrote

A compiled program is not one lump. Code is read-only. Global data is read-write. Stack and heap grow at run time. A shared library is separate. The compiler and linker already know these blocks and their lengths.

A segment is a variable-length block of a process's logical address space, with a number, base and limit. Limit is length in bytes. A logical address is s : d, where s is segment number and d is offset from segment start. Valid offsets are 0 to limit − 1.

  • Protection fits the block: code read and execute, data read and write.
  • Sharing fits the block: two processes can name one library copy.
  • A bad access traps instead of silently corrupting another block.
  • Programmer and linker see the structure hardware enforces.

Paging uses fixed-size units chosen by hardware and hidden from the programmer. Segmentation uses variable-length units chosen by compiler or programmer; segment numbers appear in the address.

The segment table and the limit check

Each process owns a segment table, one entry per segment. An entry holds base (physical start), limit (length in bytes) and protection bits. The segment-table base register points to the table; the segment-table length register holds entry count, so a bad segment number is caught.

  1. Split the logical address into segment number s and offset d.
  2. If s is not less than the table length, trap.
  3. Read base[s] and limit[s].
  4. If d ≥ limit[s], trap.
  5. Otherwise physical = base[s] + d.
physical = base[s] + d, valid only when 0 ≤ d < limit[s]

s is segment number, d is offset in bytes from segment start, base[s] is physical start and limit[s] is length in bytes. If the test fails, no physical address exists and the CPU traps.

Compare before add. Adding first can produce a number pointing elsewhere and hide the fault. Hardware caches recent segment entries, like the TLB in 4.4.

Sharing, protection and fragmentation

Protection bits are per segment: code can be read and execute, stack no-execute. Two processes can share a library by having entries with the same base and limit; both reach one physical copy.

Pure segmentation fragments externally. Variable-length segments leave holes of many sizes as processes come and go, as in 4.3. Compaction removes holes but copies segments and changes bases, so it is slow.

The standard fix is segmentation with paging, which some syllabi call paged segmentation. Each segment is divided into fixed-size pages. The segment-table entry holds the base address of that segment's page table plus the segment's limit (still the segment's length in bytes, used for the bounds check) and protection bits, instead of the segment's physical start address. The offset d is split into page number and page offset. The page table's size follows from limit ÷ page size, rounded up. There are no variable-length holes; waste is internal fragmentation in the last page of each segment.

Modern 64-bit x86 keeps segment registers but uses a flat model: base 0 and limit covering all addresses, so paging does translation. FS and GS still point at per-thread data.

4.7 Virtual memory, demand paging, page faults, copy-on-write

Virtual memory separates the logical address space a process uses from the physical memory installed. With paging, the OS keeps only the pages a process touches in RAM and leaves the rest on disk. Demand paging loads a page on its first reference, so a large program starts quickly and can be larger than RAM. A laptop with many tabs and a phone opening apps both rely on this. The cost is the page fault, a trap that must be handled fast.

You need: 4.4 for pages and frames, 4.5 for page-table entries, and 4.2 for disk transfer.

Virtual memory and demand paging

Virtual memory is the separation of the logical address space from physical memory. A process gets a logical address space, independent of how much RAM is installed. With paging, this space is cut into pages and RAM into frames. The page table maps each page to a frame. Virtual memory lets the OS keep only the pages in use in frames and hold the rest in a swap area on disk. A program can then be larger than physical memory, and it can start before all its pages are loaded.

Demand paging loads a page only when it is referenced. The OS acts as a pager, also called a lazy swapper: it does not swap whole processes, it brings in pages. In the page-table entry (PTE), a valid bit records whether the page is in memory. Valid 1 means the frame number is usable. Valid 0 means the page is not in memory; touching it causes a trap. In a pure demand paging system, a process starts with no pages in memory. The first instruction immediately faults, then the working pages arrive one by one.

The page fault and its cost

A page fault is a trap caused by a reference to a page whose valid bit is 0. It is normal, not a program error. The hardware raises the trap; the OS handles it in this order:

  1. Check the reference. If the address is outside the process's logical space, terminate with a segmentation fault. If legal but absent, continue.
  2. Find a free frame, usually from a free-frame list. If none is free, choose a victim page (see 4.8).
  3. If the victim page is dirty, write it back to its backing store: swap space for an anonymous page, or the mapped file for a file-backed page.
  4. Set the victim's PTE valid bit to 0 and record where the victim page now lives: its swap slot or file location. The frame is now free for reuse.
  5. Read the needed page from its backing store into the frame: swap space for an anonymous page, or the mapped file for a file-backed page.
  6. Update the needed page's PTE: set valid 1 and write the frame number.
  7. Restart the instruction that trapped. It now runs normally.

Let p be the page-fault rate, the fraction of memory references that fault. Let ta be memory access time and ts the page-fault service time. The effective access time is the average time per reference.

EAT = (1 − p) × ta + p × ts

EAT is the effective access time per memory reference; p is the page-fault rate (0 ≤ p ≤ 1); ta is memory access time; ts is page-fault service time. Use the same unit for ta and ts.

The term (1 − p) × ta is the no-fault case. The term p × ts is the fault case. Because ts is measured in milliseconds and ta in nanoseconds, p must be tiny for EAT to stay close to ta.

Copy-on-write and vfork

After fork, parent and child usually have identical pages. Copying them all is wasteful. Copy-on-write (COW) makes both page tables point to the same frames, and marks each shared writable private page read-only as a copy-on-write page. When either process writes to such a page, the write-protection fault traps. The OS allocates a new frame, copies the page into it, marks the writer's PTE writable and points it to the new frame. The other process keeps the old page. A page that was already read-only, such as a code page, is not copied on a write: writing it remains a protection fault. Pages never written stay shared. When fork is followed by exec, COW saves most of the copy.

vfork is a special case: the child uses the parent's address space, and the parent is suspended until the child calls exec or exit. Do not let the child change memory under vfork.

Memory-mapped files use the same machinery: a file is mapped into the address space and its pages are faulted in on demand. File systems and mmap are in Unit 5.

Worked example

Question. A system has memory access time 200 ns and page-fault service time 8 ms. A slowdown of at most 10 percent is allowed. Find the largest page-fault rate p that keeps the effective access time within this limit, and the average number of references per page fault at that rate.

Exam traps

  • Dropping the (1 − p) factor and using EAT = p × ts only. The no-fault case still costs one memory access.
  • Mixing milliseconds and nanoseconds. Convert 8 ms to 8,000,000 ns before putting it into the formula.
  • Treating a page fault as an error. A legal page that is merely absent from memory causes a normal trap and is loaded on demand.
  • Using p as a percentage. p = 0.1 means 10 percent of references fault, not 0.1 percent.
  • Thinking COW copies every page at fork. COW copies a page only when one process first writes to it.

4.8 Page replacement algorithms: FIFO, LRU, optimal

A page replacement algorithm decides which page to throw out when a page fault occurs and no frame is free. The choice is invisible until the next fault, but over a run it changes the fault count. This chapter counts faults for the same reference string under FIFO, LRU and optimal replacement, explains Belady's anomaly, and shows why exact LRU needs hardware help. The same ideas run in every demand-paged system, from a phone opening apps to a server under memory pressure.

You need: 4.7 for page faults and 4.4 for frames and page-table entries.

Reference string and fault counting

A reference string is the ordered list of page numbers a process asks for. Use 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5. A frame is one physical page slot. The OS starts with all frames empty. If the requested page is already in a frame, that reference is a hit: no disk read and no replacement. If it is not, the reference is a fault: the OS loads the page. A free frame is used if one exists. When every frame is full, the OS must pick a victim page, write it back if it is dirty, and load the new page into that frame. The choice of victim is the page replacement algorithm.

Count faults by walking the string left to right and recording the frames after each reference. Mark H for a hit and F for a fault. The same string must be used for every algorithm, otherwise the counts cannot be compared.

fault rate = faults ÷ references

faults is the number of F marks; references is the number of page requests in the string. For the string above there are 12 references, so FIFO's 9 faults give 9 ÷ 12 = 0.75.

FIFO and Belady's anomaly

FIFO keeps pages in a queue in arrival order. A new page joins the tail. When a victim is needed, the head page is evicted: it is the page that arrived first. With three frames and the string above, references 1, 2, 3 and 4 give four faults and evict 1. The frames become 2, 3, 4. Reference 1 then faults and evicts 2; reference 2 faults and evicts 3; reference 5 faults and evicts 4. References 1 and 2 now hit. Reference 3 faults and evicts 1; reference 4 faults and evicts 2; reference 5 hits. Total = 9 faults.

FIFO has Belady's anomaly: more frames can cause more faults. The same string under FIFO with four frames gives 10 faults, one more than with three frames. Extra frames change the eviction order, and the new order happens to miss more often. LRU and OPT do not show this anomaly; they are stack algorithms, so adding frames cannot increase their fault count.

LRU, optimal and approximations

LRU evicts the page whose last use is farthest in the past. One exact implementation keeps a stack: every reference moves that page to the top, and the bottom page is the victim. Another uses a counter in each page-table entry: a global clock is incremented on every memory access, the page's counter is set to the clock value, and the smallest counter is evicted. Aging approximates this with a shift register: the hardware sets a reference bit, the OS shifts it into the register periodically, and the smallest register value is evicted.

Exact LRU needs hardware help because a stack or counter must be updated on every memory access; doing that in software would double the cost of each access. Second-chance is a cheap approximation: it is FIFO plus a reference bit. If the oldest page has bit 0, evict it; if bit 1, clear the bit and move it to the back of the queue. Clock does the same with frames in a circle and a moving hand.

OPT (optimal, or MIN) evicts the page whose next use is farthest in the future; a page never used again is evicted first. It needs the future reference string, so it cannot run online. It is a benchmark: no real algorithm can beat it. On the same string, FIFO = 9, LRU = 10, OPT = 7. LRU is worse than FIFO here, which shows that no simple algorithm wins on every string. LFU evicts the least frequently used page and MFU the most frequently used; only a few universities teach them, because counts age badly and need extra fields.

Exam traps

  • Do not count a hit as a fault. The fault count is the number of F marks, not the number of references.
  • Belady's anomaly is a FIFO example, not a rule for every algorithm. More frames can increase FIFO faults, but not LRU or OPT faults.
  • OPT is not implementable online; it needs future page references. Use it only as a lower bound for comparing real algorithms.
  • Exact LRU needs a hardware-maintained stack or time counter. A software-only stack on every memory access is too slow.

Frames after each reference: 1 F [1]; 2 F [1,2]; 3 F [1,2,3]; 4 F [1,2,3,4]; 1 H; 2 H; 5 F evict 1 [2,3,4,5]; 1 F evict 2 [3,4,5,1]; 2 F evict 3 [4,5,1,2]; 3 F evict 4 [5,1,2,3]; 4 F evict 5 [1,2,3,4]; 5 F evict 1 [2,3,4,5]. Total = 10 faults.

Apply With three frames and string 1, 2, 3, 4, 1, 2, 5, count faults under LRU. 3 marks

After 1 [1] F; 2 [1,2] F; 3 [1,2,3] F; 4 evict 1 [2,3,4] F; 1 evict 2 [3,4,1] F; 2 evict 3 [4,1,2] F; 5 evict 4 [1,2,5] F. Total = 7 faults.

Analyze On the chapter string, LRU has 10 faults and FIFO has 9. What does this say about always using LRU? 5 marks

No replacement algorithm is best on every string. LRU can be worse than FIFO for a particular access pattern, even though LRU usually has better locality behaviour. OPT gives the lower bound, and real systems use approximations such as clock because exact LRU is costly.

Understand What does the reference bit do in the second-chance algorithm? 3 marks

Hardware sets the reference bit to 1 when a page is used. Second-chance checks the oldest page: if its bit is 0, it is evicted; if it is 1, the bit is cleared and the page is moved to the back of the queue, giving it a second chance.

Remember What is OPT and why is it not used in a real OS? 3 marks

OPT, also called MIN, evicts the page whose next use is farthest in the future. It needs the future reference string, which a real OS cannot know, so it is used only as a benchmark.

Beyond the syllabus

Not for the exam. Real kernels use variants of clock, not exact LRU: Linux keeps active and inactive page lists and moves pages between them, while Windows uses a working-set-like clock. Search for clock page replacement, second-chance algorithm, Linux page reclaim, and Belady anomaly. The same counting method—reference string, frames, fault marks—is how you test any new policy.

4.9 Frame allocation and thrashing

Frames are fixed-size slots of physical memory. A process cannot run on one frame; it needs a small set at once. If the OS gives a process too few frames, every instruction touch becomes a page fault, and the disk runs while the CPU waits. The questions are: how many frames should each process get, who may take a frame from whom, and why a machine slows down when the OS admits more processes. These choices decide whether a phone with 6 GB RAM stays smooth or starts swapping.

You need: page faults and demand paging from 4.7, and victim selection from 4.8.

Minimum, equal and proportional allocation

A process does not need all its pages in memory, but it needs a minimum number of frames. The instruction set sets this minimum. One instruction may touch the page holding the instruction, the page holding operand A, and the page holding operand B. With only two frames, the instruction faults, brings a page, restarts, faults again, and never finishes. Indirect addressing, which follows a pointer to a pointer, can touch more pages, so its minimum is larger. This minimum is a hard floor.

When m frames are free and n processes are ready, equal allocation gives each process floor(m ÷ n) frames. Leftover frames stay free or go to a shared pool. This is simple, but a 10-page process and a 600-page process get the same share. The small process hoards frames; the large one keeps faulting.

frames_i = floor(m × s_i ÷ S)

m is the number of usable frames; s_i is the number of pages in process i; S is the sum of s_i over all processes; floor rounds down to a whole frame.

Proportional allocation uses size. Let s_i be the pages of process i in memory, and S = Σ s_i. A larger process gets a larger share. Rounding leaves a few frames; the OS gives them to the largest fractional parts or keeps them free. The example below splits 100 frames.

Global and local replacement

A process's resident set is the frames it currently holds. When a page fault occurs and no frame is free, the OS picks a victim. In global replacement, the victim can come from any process. A process may take a frame from another, so its resident set grows and shrinks with load. In local replacement, the victim must come from the faulting process, so each process works inside its frame budget. This is about ownership, not the replacement policy. FIFO, LRU or optimal from 4.8 still decides which page inside the allowed set leaves.

Global replacement gives better throughput when process sizes change, and most general-purpose kernels use it. Its weakness is control: a greedy process can pull frames from quiet ones. Local replacement protects quiet processes, but a process with too few frames can thrash alone.

Thrashing and the working-set model

Thrashing is the state where a process, or the whole system, spends more time moving pages in and out than executing instructions. It starts with a shortage of frames. A loop needs a set of pages. Give the process fewer frames, and each pass faults on a page evicted on the last pass.

The feedback loop makes it worse. Page faults queue for disk, so CPU utilisation drops. The OS sees an idle CPU, concludes memory is underused, and admits another process. That process needs frames, so the OS takes frames from running processes. Their fault rates rise and CPU utilisation falls further. The machine is busy paging, not working. Plotted against the number of processes, CPU utilisation rises, peaks, then collapses.

WSS_i = |{pages referenced in the last Δ references}|

WSS_i is the working-set size of process i in pages; Δ is the window size in memory references; | | means the number of distinct pages, not references.

The working-set model stops the loop. Choose a window Δ, measured in memory references. WSS_i is the number of distinct pages that process i referenced in the last Δ references. It estimates current locality. The OS admits a new process only if Σ WSS_i ≤ m, where m is total usable frames. If the sum is above m, suspend or swap out a process. Count distinct pages, not references. Page-fault frequency (PFF) is the practical control: measure faults per second per process, set an upper bound, give frames when the rate crosses it, and take frames back when the rate is low.

Memory compression is a middle path: compress cold pages in RAM instead of writing them to disk. It saves space but spends CPU. Only a few universities teach it.

Worked example

Question. A system has m = 100 usable frames. Three processes need P1 = 10 pages, P2 = 30 pages, P3 = 60 pages. (a) Give an equal allocation, the leftover frames, the surplus for P1 and the shortfall for P3. (b) Give a proportional allocation. (c) For the reference string 2, 6, 1, 5, 7, 7, 7, 7, 5, 1 and window Δ = 4, find the working-set size at the last reference.

  1. Equal allocation: floor(100 ÷ 3) = 33 frames each.
  2. Used frames = 33 × 3 = 99, so leftover = 100 − 99 = 1 frame.
  3. P1 surplus = 33 − 10 = 23 frames. P3 shortfall = 60 − 33 = 27 frames.
  4. Total pages S = 10 + 30 + 60 = 100 pages.
  5. Proportional allocation: P1 = floor(100 × 10 ÷ 100) = 10 frames; P2 = floor(100 × 30 ÷ 100) = 30 frames; P3 = floor(100 × 60 ÷ 100) = 60 frames.
  6. The last Δ = 4 references are 7, 7, 5, 1. Distinct pages are {1, 5, 7}, so WSS = 3 pages.
  7. The sum of all working-set sizes must stay ≤ 100 frames to keep admitting processes; this window alone uses 3 pages.

Answer. Equal allocation gives 33 frames each with 1 frame left over, P1 has a surplus of 23 frames and P3 is short by 27 frames; proportional allocation gives 10, 30 and 60 frames; the last working-set window has WSS = 3 pages.

Exam traps

  • More processes always raise CPU use. Past the thrashing peak, each extra process lowers throughput.
  • The working-set size counts distinct pages in the window, not references. Repeating page 7 four times adds one page, not four.
  • Equal allocation is not the same as fair allocation. A 10-page process and a 60-page process do not need the same frames.
  • Global replacement lets a process take any frame; local replacement restricts victims to the faulting process. FIFO or LRU is a separate choice.
  • A slow machine is not always short of CPU. A high page-fault rate shows the shortage is frames.

Equal allocation gives every process the same number of frames. A small process may need only 10 pages but get 33 frames, so 23 frames stay unused while a large process remains short.

The last four references are 3, 1, 2, 4. Distinct pages are {1, 2, 3, 4}, so WSS = 4 pages.

In global replacement a victim frame may belong to any process; in local replacement the victim must belong to the process that faulted.

The new process takes frames from running processes. Their frame counts fall below their working sets, so they fault more. The extra faults can outweigh the small process's own work.

Takeaways

  1. Logical addresses isolate processes; the MMU translates them only after a limit check.
  2. Swapping frees memory by moving whole processes to a backing store, but it is slow.
  3. Contiguous allocation creates holes and external fragmentation; compaction is costly.
  4. Paging removes external fragmentation but adds page-table lookup cost and some internal fragmentation on the last page.
  5. The TLB caches recent translations and makes paging fast in practice.
  6. Large address spaces need multi-level, hashed or inverted page tables to avoid huge flat tables.
  7. Segmentation matches the programmer's view of code, stack and heap but requires base and limit checks.
  8. Demand paging loads pages lazily, so a process can start fast and be larger than physical memory.
  9. Replacement algorithms choose victim pages; LRU approximates optimal, while FIFO can show Belady's anomaly.
  10. Too few frames cause thrashing; allocation and working-set policies must give each process enough frames.

Glossary

Address space
The set of logical addresses a process may use.
Backing store
Disk area that holds swapped-out process images.
Base register
Register holding the start physical address added to a logical address.
Belady's anomaly
More page frames causing more faults under FIFO replacement.
Compaction
Moving allocated blocks to combine free memory into one large hole.
Copy-on-write
Sharing pages until a write forces a private copy.
Demand paging
Loading pages only when they are referenced.
External fragmentation
Free memory split into holes too small for a request.
Frame
Fixed-size block of physical memory in a paging system.
Hole
A free block of memory in a contiguous allocation scheme.
Internal fragmentation
Wasted space inside an allocated block larger than the request.
Inverted page table
Table with one entry per physical frame rather than per virtual page.
Limit register
Register holding the size of a process's logical address space.
MMU
Hardware unit that translates logical addresses into physical addresses.
Multi-level page table
Page table organised in levels to avoid storing unused entries.
Page
Fixed-size block of logical memory in a paging system.
Page fault
Trap raised when a referenced page is not in memory.
Page table
Per-process table mapping page numbers to frame numbers.
Page-table entry (PTE)
One entry in a page table holding a frame number and control bits.
Segment table
Table storing base and limit for each segment of a process.
Segmentation
Division of a program into variable-length logical segments.
Swapping
Moving a whole process between main memory and a backing store.
Thrashing
High paging activity that leaves little time for useful execution.
TLB
Fast cache of recent page-table translations.
Virtual memory
Technique that lets a process use more logical memory than physical memory.
Working set
Set of pages a process has used in a recent time window.
