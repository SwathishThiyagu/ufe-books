3.1 Critical-section problem and race conditions

When two or more processes access the same variable without coordination, the order of their read‑modify‑write steps can change the final result. This phenomenon is called a race condition. The critical‑section problem asks how to let only one process at a time execute such a sensitive part of code, while still allowing progress and avoiding indefinite waiting. It appears whenever shared data is used – for example, updating a bank balance, counting tickets on an IRCTC portal, or incrementing a global counter in a multiplayer game.

You need: process concepts and context switching from Unit 2.

Interleaving of instructions and race conditions

A process is a program in execution. A shared variable lives in memory that several processes can read or write. The CPU executes instructions of each process in small time slices. Because the slices are interleaved, the actual order of operations from different processes may differ each run.

  • Read: load the current value of the variable into a register.
  • Modify: compute a new value, e.g., add 1.
  • Write: store the new value back to memory.

If two processes perform these three steps on the same variable without any control, the following interleaving can happen:

  1. P1 reads x = 0.
  2. P2 reads x = 0.
  3. P1 computes x = 0 + 1 and writes 1.
  4. P2 computes x = 0 + 1 and writes 1.

Both processes intended to increase the counter by one, but the final value is 1 instead of 2. The lost update is the classic race condition.

Critical‑section problem definition

The part of a program that accesses shared data is called the critical section. The critical‑section problem asks for a protocol that satisfies three conditions.

  • Mutual exclusion – at most one process may be inside the critical section at any time.
  • Progress – if no process is in the critical section and some processes wish to enter, one of them must be allowed to enter.
  • Bounded waiting – there exists a limit on how many times other processes can enter before a waiting process gets its turn.

Some syllabi call this the "Critical‑Section Problem" and treat it as a prerequisite for all other synchronization mechanisms such as Peterson’s algorithm, mutexes, semaphores, and monitors.

The problem is purely logical; it does not depend on a particular hardware instruction set. Later chapters will show how hardware support (test‑and‑set, compare‑and‑swap) can simplify the solution.

Why naive solutions fail

A common mistake is to use a simple flag variable, e.g., "busy = 1" before entering the critical section and "busy = 0" after leaving. The flag itself is a shared variable, so the same race condition can corrupt it.

C program.

#include <stdio.h>
#include <pthread.h>

int x = 0;               // shared counter
int busy = 0;            // naive lock flag

void *increment(void *arg) {
    if (busy == 0) {      // check flag (no atomicity!)
        busy = 1;         // set flag
        int temp = x;
        temp = temp + 1;
        x = temp;
        busy = 0;         // release flag
    }
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("final x = %d\n", x);
    return 0;
}

Output

final x = 2

The program may print "final x = 1" when the first thread sets busy = 1, increments x, and resets busy = 0 before the second thread reads the flag. The second thread then sees busy = 1, skips the critical section, and leaves x unchanged, resulting in a final value of 1. If both threads read busy = 0 before either sets it, both will increment, giving final x = 2. Hence the output can be 1 or 2 depending on the interleaving.

To meet all three conditions we need an atomic operation or a protocol that guarantees ordering. The next chapter introduces Peterson’s solution, which works for two processes using only shared memory and turn variables.

For more than two processes, hardware primitives such as test‑and‑set or compare‑and‑swap are used, leading to mutex locks and semaphores.

Worked example

Question. Two processes P1 and P2 share an integer counter x initialized to 0. Each process executes the three statements: read x; x = x + 1; write x. List all possible final values of x after both processes have finished, assuming any interleaving of the six individual statements is allowed.

C program.

#include <stdio.h>
#include <pthread.h>

int x = 0;               // shared counter

void *inc(void *arg) {
    int temp = x;          // read
    temp = temp + 1;       // modify
    x = temp;              // write (no lock)
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, inc, NULL);
    pthread_create(&t2, NULL, inc, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("final x = %d\n", x);
    return 0;
}
  1. Step 1: Identify the six atomic actions – P1‑read, P1‑write, P2‑read, P2‑write, and the two compute steps (addition).
  2. Step 2: The final value depends on the relative ordering of the read and write actions of the two processes.
  3. Case A – P1 reads first, then P2 reads after P1 has written: final x = 2.
  4. Case B – P1 and P2 both read before any write occurs: both compute 1, then the first write stores 1, the second write also stores 1, final x = 1.
  5. No other ordering can produce a different result because each write overwrites the previous value.
  6. Therefore the set of possible final values is {1, 2}.

Exam traps

  • Assuming that setting a simple flag variable automatically provides mutual exclusion; the flag itself is subject to the same race condition.
  • Confusing progress with bounded waiting – a solution may allow a waiting process to eventually enter, but without a bound on how many times others can overtake it.
  • Counting the number of reads and writes incorrectly; the critical section consists of the whole read‑modify‑write sequence, not just the write.
  • Believing that a single CPU core eliminates race conditions; even on one core the OS scheduler can pre‑empt a process between the read and the write.

3.2 Peterson's solution and hardware synchronization support

Peterson’s solution gives a software way for two threads to enter a critical section without conflict. It uses two shared variables – a flag array and a turn variable – to enforce mutual exclusion, guarantee progress and bound waiting. When hardware provides atomic instructions like test‑and‑set or compare‑and‑swap, the same properties can be obtained with a single instruction, which is why modern OS kernels prefer the hardware primitives.

You need: Critical‑section problem and race conditions.

Peterson’s two‑process algorithm

Two processes are identified by indices i and j where i ≠ j and i, j ∈ {0,1}. Each process has a Boolean flag[i] that indicates its intention to enter the critical section. The shared integer turn tells whose turn it is to wait. The algorithm consists of four statements before the critical section, a busy‑wait loop, the critical section, and a single statement after the critical section.

  1. flag[i] = true // declare interest
  2. turn = j // give priority to the other process
  3. while (flag[j] && turn == j) // spin while the other wants in and it is its turn
  4. ; // empty body
  5. // critical section
  6. flag[i] = false // release the lock
  • Both flag[0] and flag[1] may be true simultaneously; the turn variable determines which process is allowed to enter the critical section.
  • If both flags are true, turn decides which process proceeds.
  • When a process leaves, it resets its flag, allowing the other to proceed.

CS_allowed(i) ⇔ ¬(flag[j] ∧ turn == j)

CS_allowed(i) is true when process i may enter; flag[j] is true if j wants the CS; turn == j means the turn variable currently holds j.

Why the algorithm satisfies the three properties

Mutual exclusion holds because the while condition blocks i whenever j is in the critical section (flag[j] = true) and turn == j. At most one process can have the condition false at any time, so both cannot be inside together.

  • Progress: If no process is in the critical section and some processes wish to enter, the turn variable eventually gives the right to one of them because each process sets turn to the other before waiting.
  • Bounded waiting: Once a process sets turn to the other, the other can enter at most once before the first process is allowed to proceed. No process can be delayed indefinitely.

The algorithm works only for two processes because the single turn variable cannot represent more than one competitor. For more than two processes, hardware primitives or more complex software (like bakery algorithm) are required.

Hardware atomic instructions as replacements

Modern CPUs provide atomic read‑modify‑write instructions. Two common primitives are test‑and‑set (TAS) and compare‑and‑swap (CAS). Both guarantee that a single memory location is accessed atomically, eliminating the need for the flag‑turn dance.

C program.

#include <stdio.h>
#include <stdbool.h>
#include <stdatomic.h>

atomic_bool lock = ATOMIC_VAR_INIT(false);

void enter(void) {
    bool expected;
    do {
        expected = false;
    } while (!atomic_compare_exchange_weak(&lock, &expected, true));
    // now inside critical section
}

void leave(void) {
    atomic_store(&lock, false);
}

int main(void) {
    printf("lock initial = %d\n", atomic_load(&lock));
    enter();
    printf("lock after enter = %d\n", atomic_load(&lock));
    leave();
    printf("lock after leave = %d\n", atomic_load(&lock));
    return 0;
}

Output

lock initial = 0
lock after enter = 1
lock after leave = 0
  • Test‑and‑set atomically reads the current value of a memory location and sets it to true (1), returning the previous value.
  • Compare‑and‑swap checks that a memory location contains an expected value and, only if it does, writes a new value. It returns true on success.

When the OS kernel uses TAS or CAS to implement mutexes, the same three properties (mutual exclusion, progress, bounded waiting) are obtained with far less code and without busy‑waiting on shared variables.

Worked example

Question. Two threads T0 and T1 share a variable balance initialized to ₹10,000. Each thread executes Peterson’s entry protocol, adds ₹500 to balance in the critical section, and then executes the exit protocol. Show the values of flag[0], flag[1] and turn after each statement of both threads, assuming T0 starts first and T1 arrives while T0 is still in the while loop.

C program.

#include <stdio.h>
#include <stdbool.h>
#include <pthread.h>

bool flag[2] = {false, false};
int turn;
int balance = 10000;

void *thread0(void *arg) {
    flag[0] = true;
    turn = 1;
    while (flag[1] && turn == 1) {}
    balance += 500;
    flag[0] = false;
    return NULL;
}

void *thread1(void *arg) {
    flag[1] = true;
    turn = 0;
    while (flag[0] && turn == 0) {}
    balance += 500;
    flag[1] = false;
    return NULL;
}

int main(void) {
    pthread_t t0, t1;
    pthread_create(&t0, NULL, thread0, NULL);
    pthread_create(&t1, NULL, thread1, NULL);
    pthread_join(t0, NULL);
    pthread_join(t1, NULL);

}

  8. T0 exit: flag[0]=false → flag=[false,true].

3.3 Mutex locks and semaphores

Mutex locks and semaphores are tools that let several processes share resources without corrupting data. They prevent race conditions by allowing only one process to enter a critical section at a time, or by limiting the number of simultaneous users of a pool. These mechanisms appear in file‑system access, printer queues, and database connections.

You need: Critical‑section problem and Peterson’s solution.

Mutex lock basics

A mutex lock is a binary flag that can be either free or held. The flag is called the lock state. A process that wants the lock executes the acquire operation. If the lock is free, the state changes to held and the process enters the critical section. If the lock is already held, the process must wait.

  1. Check the lock state.
  2. If free, set it to held and continue.
  3. If held, block until the lock becomes free.

When the process finishes the critical section it executes release. Release sets the lock state back to free and wakes one waiting process, if any. A mutex must be released by the same process (or thread) that previously acquired it; releasing it from another process leads to undefined behavior.

Lock_state = {0 (free), 1 (held)}

Lock_state is the current value of the mutex; 0 means no process owns the lock, 1 means one process owns it.

  • Only one process can hold a mutex at a time.
  • Acquire and release must be atomic.

Binary semaphore as a lock

A binary semaphore is a semaphore whose value is only 0 or 1. The two operations are called P (wait) and V (signal). P decrements the value if it is 1; otherwise the calling process blocks. V operation works as follows: if there is a blocked process, wake one of them; otherwise set S ← 1. After waking a process the semaphore value remains 0 because the woken process will immediately acquire it.

  1. P operation: if S = 1, set S ← 0 and proceed; else block.
  2. V operation: if there is a blocked process, wake one of them; otherwise set S ← 1. After waking, the semaphore value stays 0.

Because the change of S is atomic, a binary semaphore can replace a mutex lock. The main difference is naming: lock uses acquire/release, semaphore uses P/V.

Unlike a mutex, a binary semaphore does not track which process holds it; any process may execute V, so correct program logic must ensure that V is called only after a matching P.

  • Atomicity is guaranteed by hardware instructions such as test‑and‑set.
  • Blocking is usually implemented by putting the process on a waiting queue.

Counting semaphore for resource pools

A counting semaphore holds a non‑negative integer. The value represents the number of identical resources that are currently free. Each P operation claims one resource; each V operation returns one resource.

  1. Initialize semaphore S to the total number of resources.
  2. When a process needs a resource, execute P(S).
  3. If S > 0, the process proceeds and S is reduced by 1.
  4. If S = 0, the process blocks until another process executes V(S).
  5. After using the resource, the process executes V(S) to increase the count.

Counting semaphores are used for printer pools, database connections, and thread‑pool limits. They give a simple, scalable way to avoid over‑allocation.

  • The semaphore value never becomes negative.
  • All P and V operations are atomic.

Worked example

Question. Three processes P1, P2 and P3 request a pool of two identical printers. The semaphore S is initialized to 2. Show the value of S after each operation and state which process proceeds.

C program.

#include <stdio.h>
int main() {
    int S = 2; // initial semaphore value
    // P1 acquires
    if (S > 0) S--;
    printf("After P1: %d\n", S);
    // P2 acquires
    if (S > 0) S--;
    printf("After P2: %d\n", S);
    // P3 tries to acquire (blocked)
    printf("After P3 blocked: %d\n", S);
    // P1 releases
    S++;
    printf("After V by P1: %d\n", S);
    // P3 now acquires
    if (S > 0) S--;
    printf("After P3 proceeds: %d\n", S);
    return 0;
}
  1. Initial: S = 2 (both printers free).
  2. P1 executes P(S): S becomes 1, P1 proceeds to use a printer.
  3. P2 executes P(S): S becomes 0, P2 proceeds to use the second printer.
  4. P3 executes P(S): S is 0, so P3 blocks and waits.
  5. P1 finishes and executes V(S): S becomes 1, one waiting process (P3) is awakened.
  6. P3 now proceeds, S becomes 0 again after its P(S) completes.

Exam traps

  • Forgetting to execute V after using the printer leaves the semaphore at 0 and blocks later processes.
  • Assuming V can be called before any P; this would increase the semaphore above the resource count and hide bugs.
  • Treating a binary semaphore as a mutex but using V on a locked semaphore without a waiting process will set the value to 1, never to 2; the value never exceeds 1 for a binary semaphore.
  • Confusing the names acquire/release with P/V; exam questions may mix the terminology.
  • Counting semaphore initialized with the wrong number of resources leads to premature blocking.

3.4 Monitors for synchronization

A monitor groups shared data, its procedures, a lock and condition variables. It guarantees that only one process executes inside the monitor at a time. Monitors are used to write clean synchronization code for classic problems such as the bounded buffer.

You need: understanding of critical sections and mutex locks from Critical‑section problem and race conditions and Mutex locks and semaphores.

What a monitor is

A monitor is a module that contains shared variables, procedures that operate on them, a built‑in lock, and one or more condition variables. The lock is automatically acquired when a procedure is entered and released when it returns.

  • Only one process can be inside the monitor at any moment.
  • If a process cannot proceed, it calls wait on a condition variable.
  • Another process can wake it by calling signal or broadcast.

inside_monitor(p) ⇔ lock_held_by(p)

inside_monitor(p) is true when process p is executing a monitor procedure; lock_held_by(p) means p owns the monitor lock.

Condition‑variable operations

wait(cond) releases the monitor lock and places the calling process on cond’s queue. The process stays blocked until another process executes signal(cond) or broadcast(cond).

  1. The process calls wait(cond).
  2. The monitor lock is released atomically and the process is placed on cond’s queue.
  3. The process blocks.
  4. When signalled, the process re‑acquires the lock before returning.

signal(cond) wakes one waiting process, but the woken process cannot run until the signalling process releases the lock. broadcast(cond) wakes all waiting processes.

Bounded‑buffer example

Consider a buffer that can hold at most 5 items. Two procedures are defined inside a monitor: put(item) adds an item, get() removes an item. Two condition variables are used: notFull and notEmpty.

C program.

#include <stdio.h>
#define N 5
int count = 0;          // number of items in buffer
int buffer[N];
int in = 0, out = 0;

/* monitor lock is implicit */
void put(int x) {
    while (count == N) wait_notFull();   // wait if buffer full
    buffer[in] = x;
    in = (in + 1) % N;
    count++;
    signal_notEmpty();
}

int get(void) {

3.5 Deadlock system model and necessary conditions

A deadlock occurs when a group of processes each wait for a resource that another member of the group holds. The operating system models the situation with processes, resources, and allocation matrices. By checking the model we can see why deadlocks happen and what conditions must be true for them to exist. The model is used in exam questions, in OS design, and in real systems such as database lock managers or UPI transaction handling.

You need: understanding of processes and resources from Monitors for synchronization and of mutexes from Mutex locks and semaphores.

System model for deadlock analysis

The model has a set of processes P = {P1, P2, …, Pm} and a set of resource types R = {R1, R2, …, Rn}. Each resource type Rj has Ej identical instances. The total number of instances is a vector E = (E1, E2, …, En).

Two matrices describe the current state. The allocation matrix A has entry Aij = number of instances of Rj held by Pi. The request matrix Q has entry Qij = number of instances of Rj that Pi still needs to complete.

∑i Aij + Fj = Ej

For each resource type Rj, the sum of allocated instances and free instances equals the total instances Ej.

Fj = number of free (unallocated) instances of resource Rj. Since free instances plus allocated instances equal the total instances, the equality ∑i Aij + Fj = Ej always holds.

A snapshot of A and Q together forms the resource‑allocation graph. Nodes represent processes and resources. An edge Pi → Rj means Pi is requesting Rj. An edge Rj → Pi means Rj is allocated to Pi.

  • Processes are active entities that execute code.
  • Resources are physical or logical items such as CPU cores, memory pages, or database locks.
  • Allocation matrix shows who owns what now.
  • Request matrix shows what each process still needs.

Four necessary conditions for a deadlock

A deadlock can exist only if all four conditions hold simultaneously. If any one condition is broken, the deadlock cannot persist.

  • Mutual exclusion – at most one process can use a resource instance at a time.
  • Hold and wait – a process holds at least one resource while waiting for another.
  • No preemption – a resource cannot be forcibly taken away from a process; it must be released voluntarily.
  • Circular wait – there exists a circular chain of processes Pi1 → Pi2 → … → Pik → Pi1 such that each process Pi holds at least one resource needed by the next process in the chain.

To verify a deadlock in a snapshot:

  1. Step 1: Identify the resources each process currently holds (allocation matrix).
  2. Step 2: Identify the resources each process still needs (request matrix).
  3. Step 3: Check the four conditions in the current snapshot.
  4. Step 4: If all are true, the system is in a deadlocked state.
  5. Step 5: The deadlock conclusion is as above.

In many textbooks this set of conditions is called the “deadlock conditions” or “deadlock characterization”. The model helps designers decide which condition to break in order to prevent deadlocks.

The next chapter describes how to break one of the four conditions on purpose. Those techniques are called deadlock prevention and are covered in Methods for handling deadlocks; deadlock prevention.

Question. Two database transactions T_A and T_B need exclusive locks on rows X and Y. T_A currently holds lock X and now requests lock Y. T_B holds lock Y and now requests lock X. Draw the resource‑allocation graph, list the four necessary conditions, and state whether a deadlock exists.

  2. Step 2: Identify resources: R1 = lock on X, R2 = lock on Y.
  3. Step 3: Build the graph: P1 → R2 (request), R2 → P2 (allocation), P2 → R1 (request), R1 → P1 (allocation).
  4. Step 4: Check conditions:

  • Assuming that breaking any one condition automatically resolves every deadlock. In practice the system must enforce the break at the right time.
  • Missing the circular‑wait condition when the graph has a hidden cycle of length three or more.

3.6 Methods for handling deadlocks; deadlock prevention

Deadlock prevention removes at least one of the four necessary conditions. By breaking any one of the four necessary conditions, the system cannot enter a deadlock state. Only breaking the circular‑wait condition guarantees that a circular wait cannot form. This technique is used in real‑time OS, transaction servers and embedded controllers where a deadlock would halt critical services.

You need: the deadlock model and the four necessary conditions from Chapter 3.5.

Eliminate mutual exclusion for sharable resources

Mutual exclusion means a resource can be used by only one process at a time. If a resource can be shared safely, the condition disappears. Shared read‑only files, network sockets that allow multiple readers, and printers that support spooling are examples.

  • Make data structures read‑only when possible.
  • Use copy‑on‑write to let several processes hold a logical copy.
  • Replace exclusive hardware with virtualised devices.

If every resource is non‑exclusive, a cycle of waiting cannot form because no process ever blocks for a needed unit.

Prevent hold‑and‑wait by requiring all resources up front

Hold‑and‑wait occurs when a process keeps some resources while asking for others. The simplest prevention is to ask the scheduler to allocate the whole set before the process starts.

  1. Process declares the complete list of resources it will need.
  2. System checks if all are currently free.
  3. If yes, it grants the whole set and the process begins.
  4. If not, the process waits without holding any resource.

The trade‑off is lower utilisation: a process may sit idle while waiting for a large set that could be partially satisfied.

Allow preemption and enforce a total order on resources

Preemption means the OS can forcibly take a resource from a process and give it to another. When a process requests a resource that is unavailable, the OS may roll back the holder, release its resources and restart it later.

  • Preemption works well for consumable resources such as CPU time. It can also be applied to reclaim memory pages by swapping them out, though pages are not consumable in the same sense.
  • For non‑consumable devices, the OS may use a timeout and then abort the current job.

A total order assigns a unique number to each resource type. Every process must request resources in increasing order of that number. This eliminates circular wait because a cycle would require a decreasing step, which the order forbids.

R_i < R_j ⇒ request(R_i) before request(R_j)

R_i and R_j are resource types; the inequality follows the global ordering.

  • Counting the number of jobs that can run concurrently without checking the hold‑and‑wait rule leads to an over‑estimate.
  • Confusing preemption (forced release) with voluntary release; the OS must be able to rollback the process state.
  • Applying the total order incorrectly, such as requesting resources out of order in one branch of code, re‑introduces circular wait.

3.7 Deadlock avoidance and banker's algorithm

Deadlock avoidance decides whether a new resource request can be granted by checking if the system will stay in a safe state. It exists because granting a request without looking ahead can lead to a deadlock that cannot be broken later. The technique is used in operating systems that manage limited resources such as CPU cores, memory blocks, or I/O devices, especially in transaction‑heavy environments like banking servers or railway reservation systems.

You need: the deadlock‑system‑model‑and‑necessary‑conditions chapter here.

Safe and unsafe states

A state is safe if there exists an order of processes such that each can obtain its remaining needed resources and finish. If no such order exists the state is unsafe; an unsafe state may become a deadlock after further allocations.

  • Need[i] = Max[i] – Allocation[i]
  • Available = total resources – sum of Allocation

The safety test builds a work vector equal to Available and a finish flag for every process. It repeatedly finds a process whose Need ≤ work, pretends it finishes, adds its Allocation to work, and marks it finished. If all processes finish, the state is safe.

Need[i][j] = Max[i][j] – Allocation[i][j]

Need[i][j] is the remaining demand of process i for resource type j; Max[i][j] is the declared maximum; Allocation[i][j] is the currently held units.

Banker's safety algorithm

  1. Check request ≤ Need; if not, raise error.
  2. Pretend to allocate: Available' = Available – request, Allocation' = Allocation + request, Need' = Need – request.
  3. Run the safety test on the primed vectors.
  4. If the test succeeds, commit the allocation; otherwise roll back and deny.

The algorithm requires knowledge of each process’s maximum demand, which must be declared before execution. This future‑request knowledge lets the system avoid decisions that could lead to deadlock.

Python program.

def safe_state(available, alloc, need):
    n = len(alloc)
    work = available[:]
    finish = [False]*n
    while True:
        found = False
        for i in range(n):
            if not finish[i] and all(need[i][j] <= work[j] for j in range(len(work))):
                for j in range(len(work)):
                    work[j] += alloc[i][j]
                finish[i] = True
                found = True
        if not found:
            break
    return all(finish)

# Example data from the exam question

  5. Because the safety test fails, the request must be denied.

3.8 Deadlock detection and recovery

Deadlock detection finds a set of processes that are stuck waiting for each other after the system has already entered a deadlock. It exists because prevention and avoidance are not always possible or economical. Detection is used in systems where resources are shared dynamically, such as printer pools in offices, database connections in a web service, or CPU cores allocated to container workloads.

You need: the deadlock system model and necessary conditions () and the avoidance techniques ().

Detection for single‑instance resources

When each resource has only one copy, the system can be represented by a Resource Allocation Graph (RAG). Nodes are processes and resources. An edge from a process to a resource means the process is requesting that resource. An edge from a resource to a process means the resource is allocated to the process.

A cycle in this directed graph indicates a deadlock. The cycle shows that each process in the cycle holds a resource needed by the next process.

  1. Build the RAG from the current allocation and request tables.
  2. Search the graph for cycles using depth‑first search.
  3. If a cycle is found, list all processes that belong to any cycle.
  • The algorithm runs in O(P+R+E) time where P is the number of processes, R the number of resources, and E the number of edges.
  • It works only for single‑instance resources. For multiple instances the graph may have no cycle even though a deadlock exists.

Detection for multiple‑instance resources

When resources have several identical instances, the RAG cannot capture deadlocks fully. Instead we use matrices similar to the Banker's algorithm.

Let Available be a vector of free instances for each resource type. Let Allocation be a matrix where Allocation[i][j] is the number of instances of resource j held by process i. Let Request be a matrix where Request[i][j] is the number of instances of j still needed by i.

Let Finish be a boolean vector of length P, initially false for all processes, indicating whether a process can finish.

Work = Available

Work is a temporary vector of currently free instances.

  1. Initialize Work = Available and Finish[i] = false for all processes.
  2. Find a process i such that Finish[i] = false and Request[i] ≤ Work (component‑wise).
  3. If such i exists, set Work = Work + Allocation[i] and Finish[i] = true. Repeat step 2.
  4. When no such i exists, all processes with Finish[i] = false are deadlocked.
  • The test is similar to the safety check in the Banker's algorithm, but it is run only when a deadlock is suspected.
  • Complexity is O(P×R) per detection run.

Recovery actions

After detection, the OS must break the deadlock. Three common actions are used.

  • Process termination – abort one or more deadlocked processes. The chosen process must release all its resources. The OS may pick the lowest‑priority process or the one that costs least to restart.
  • Resource preemption – forcibly take resources from a deadlocked process and give them to another. The preempted process may need to be rolled back to a safe state.
  • Rollback – restore one or more processes to a previously saved checkpoint. After rollback the processes request resources again, hopefully avoiding the deadlock.

The chosen method must ensure that the system returns to a consistent state. Killing a process is simple but may lose work. Preemption requires careful handling of I/O buffers. Rollback needs checkpointing support, which many databases already provide.

    int deadlocked[] = {1,2,3,4};
    int n = sizeof(deadlocked)/sizeof(deadlocked[0]);
    printf("List of deadlocked process indices\n");
    for(int i=0;i<n;i++)
        printf("%d ", deadlocked[i]);
    printf("\n");
    return 0;
}
  1. Initialize Work = Available = (0,0,0). Set Finish[i] = false for i = 1..4.
  2. Check each process i for Request[i] ≤ Work.
  3. P1: Request = (0,1,0) > Work. Not eligible.
  4. P2: Request = (0,0,1) > Work. Not eligible.
  5. P3: Request = (1,0,0) > Work. Not eligible.
  6. P4: Request = (1,1,1) > Work. Not eligible.
  7. No process can proceed. The loop ends.
  8. All processes with Finish[i] = false are deadlocked. Hence P1, P2, P3, and P4 are in deadlock.
  9. Recovery: abort a process that actually holds a printer, e.g., P1. After termination, its allocation (1,0,0) is released, making Available = (1,0,0). The remaining processes can now obtain the needed printer and finish.

Answer. All four processes are deadlocked; aborting P1 (or P2 or P3) breaks the deadlock.

Exam traps

  • Assuming that any single process termination will always free enough resources; the chosen process must actually hold resources needed by others.
  • Confusing the request matrix with the allocation matrix; the detection algorithm uses Request ≤ Work, not Allocation.
  • Treating a zero‑available vector as a sign that no deadlock exists; a deadlock can exist even when all resources are allocated.
  • Forgetting to update the Work vector after a process finishes; this prevents the algorithm from finding subsequent safe processes.

Check yourself

Remember What does a cycle in a Resource Allocation Graph indicate? 2 marks

It indicates that the processes in the cycle are deadlocked.

Understand Explain why the single‑instance detection method cannot find deadlocks when resources have multiple instances. 3 marks

With multiple instances, a cycle may exist without a deadlock because a process can still obtain a free instance of the resource; the graph loses information about the count of instances.

Apply Given Available = (2,1), Allocation = [[1,0],[0,1]], Request = [[1,1],[1,0]], run one iteration of the multiple‑instance detection algorithm and state which processes can finish. 4 marks

Work = (2,1). Process 2 has Request (1,0) ≤ Work, so it can finish. After finishing, Work becomes (2+0,1+1) = (2,2). Process 1 now has Request (1,1) ≤ Work and can also finish.

Analyze A system uses only process termination for recovery. Discuss two drawbacks of this approach in a transaction‑processing environment. 6 marks

First, terminating a process aborts all its in‑flight transactions, causing loss of work and possible inconsistency in the database. Second, it may violate service‑level agreements because customers lose their sessions, and the system may need to roll back many dependent processes, increasing recovery time.

Apply In a system with two resource types A(3 instances) and B(2 instances), Allocation = [[2,0],[1,1],[0,1]], Request = [[0,2],[1,0],[2,0]]. Available = (0,0). Run the detection algorithm and list the deadlocked processes. 4 marks

Work = (0,0). No process has Request ≤ Work, so none can finish. All three processes are deadlocked.

Analyze Compare process termination and resource preemption as recovery actions in terms of system throughput and user impact. 5 marks

Process termination quickly frees all resources, improving throughput but may discard user work, causing dissatisfaction. Preemption keeps processes alive, preserving work, but requires extra overhead to roll back state, which can lower throughput and increase complexity.

Takeaways

  1. A race condition appears when two or more processes access shared data without proper synchronization.
  2. Peterson’s algorithm demonstrates that software alone can guarantee mutual exclusion for two processes.
  3. Hardware atomic primitives such as test‑and‑set make lock implementation efficient on multiprocessors.
  4. Mutexes and semaphores are the building blocks for synchronizing many threads in real applications.
  5. Monitors provide a structured way to combine mutual exclusion with condition synchronization.
  6. Deadlock occurs only when all four necessary conditions hold simultaneously.
  7. Prevention, avoidance, detection and recovery form a hierarchy of strategies to keep systems deadlock‑free.

Glossary

banker’s algorithm
Algorithm that simulates resource allocation to test for safety before granting

Semaphore restricted to values 0 and 1, often used as a mutex

Repeatedly checking a condition in a loop while waiting for a resource
circular wait
Condition where processes form a cycle of resource dependencies
condition variable
Object that allows threads to wait for a predicate inside a monitor
counting semaphore
Semaphore that can hold any non‑negative count, representing multiple identical resources
deadlock
Situation where a set of processes are each waiting for another to release a resource
hold‑and‑wait
Condition where a process holds one resource while requesting another
monitor
Encapsulation of shared data, procedures, and synchronization primitives
mutual exclusion
Guarantee that only one thread accesses a critical resource at a time
no‑preemption
Condition where resources cannot be taken away from a process voluntarily
preemption
Forceful removal of a resource from a process
process
An executing program instance with its own address space and resources

Graphical model showing processes, resources, and allocation/request edges
safe state
State from which the system can allocate resources to all processes without deadlock
semaphore
Integer variable accessed atomically to control access to a pool of resources

Lock implemented with busy waiting using an atomic test‑and‑set

Coordination of concurrent activities to ensure correct ordering

Lightweight unit of execution within a process sharing its address space
