3.1 Critical-section problem and race conditions

Two processes on one CPU can still touch the same memory. The CPU switches between them in the middle of a statement. A line like x = x + 1 is not one step: the CPU loads x into a register, adds 1, and stores it back. If the switch happens between the load and the store, one update disappears. A critical section is the piece of code that reads or writes such shared data, and it must run for one process at a time. Bank balance updates, IRCTC seat counters and kernel data all depend on getting this right.

You need Unit 2's processes, threads and CPU scheduling: what a process is, its states, and how a context switch saves and restores registers.

One statement hides three machine steps

Take a shared integer x in memory, starting at 5. Processes P1 and P2 each run the line x = x + 1. A process is a running program with its own registers and program counter. A CPU cannot add 1 to memory directly, so that line becomes three machine steps: load x into a register, add 1 to the register, store the register back into x.

The OS may switch processes between any two machine instructions. A race condition is when the result depends on that order. Both processes can load 5, both compute 6, both store 6. Two increments ran, yet x rose by one, because the second store threw away the first. That is a lost update.

  • A bank balance updated from two ATMs at once.
  • The last train seat: two users each see 1 seat left and both pay.
  • A kernel counter of free memory pages touched by two system calls.

The four parts of a process's code

A critical section is the part of a process that reads or writes data shared with another process. Only one process may be inside its critical section at a time. That condition is mutual exclusion. Every process using the shared data has the same four-part shape.

Pseudocode.

while (1) {
    /* entry section: ask for permission */
    /* critical section: touch shared data */
    /* exit section: give permission back */
    /* remainder section: local work */
}

The entry and exit code is called the entry protocol. A correct protocol needs more than setting a flag. Peterson's solution and hardware instructions build one from atomic reads and swaps, and mutex locks and semaphores wrap the same idea into a ready-made object.

Three requirements for a correct solution

Any solution to the critical-section problem must satisfy three requirements.

  • Mutual exclusion. No two processes are inside their critical sections at the same time.
  • Progress. If no process is inside and some want to enter, the choice of who enters next cannot be postponed forever. A process sitting in its remainder section must not block the others.
  • Bounded waiting. After a process asks to enter, there is a finite limit on how many times other processes may enter before it. So no process waits forever.

Mutual exclusion is a safety property: nothing bad happens. Progress and bounded waiting are liveness properties: something good eventually happens. A protocol with a slow release can keep mutual exclusion and still fail progress. Keep the three separate when you write an answer.

Preemptive and non-preemptive kernels

The same race lives inside the kernel, where the shared data is the ready queue, a page table or the open-file table. A kernel is preemptive if it can switch away from a process while that process is executing kernel code, for example inside a system call. A non-preemptive kernel runs kernel code until it finishes or the process blocks.

A non-preemptive kernel avoids most races on a single CPU, because kernel code is never cut in the middle. The price is response time: one long system call delays every other process, which hurts interactive and real-time work.

A preemptive kernel is more responsive, so each shared kernel structure needs its own lock. On a multicore machine, staying free of preemption is not enough at all: two CPUs run kernel code at the same instant, so locks are needed even in a non-preemptive kernel.

Worked example

Question. A shared integer x holds 5. Processes P1 and P2 each execute x = x + 1, compiled into load x into a register, add 1, store the register into x. The steps interleave as: P1 loads x, P2 loads x, P1 stores, P2 stores. (a) What is the final value of x? (b) What should it be if the two increments did not interfere? (c) How many updates are lost?

  1. Memory holds x = 5 before either process runs.
  2. P1 loads x into its register R1, so R1 = 5.
  3. P2 loads x into its register R2, so R2 = 5. Both read the old value.
  4. P1 computes R1 = 5 + 1 = 6 and stores it, so x = 6.
  5. P2 computes R2 = 5 + 1 = 6 and stores it, so x = 6 again. P2's read was stale.
  6. Without interference: 5 + 1 = 6, then 6 + 1 = 7.
  7. Lost updates = correct value − actual value = 7 − 6 = 1.

Answer. Final x = 6 instead of 7, so one update is lost.

Exam traps

  • Treating x = x + 1 as one step. It is load, add, store, and a context switch can land between any two of them.
  • Thinking mutual exclusion is the whole answer. Progress and bounded waiting are separate requirements and are examined separately.
  • Confusing a race condition with a deadlock. A race needs no waiting at all; a deadlock is a cycle of processes waiting for held resources, covered in 3.5.
  • Swapping progress and bounded waiting. Progress says some waiting process enters; bounded waiting says a particular one enters within a finite number of turns.
  • Claiming the whole process needs exclusion. Only the critical section does; the remainder section runs freely and can be preempted.

3.2 Peterson's solution and hardware synchronization support

Two processes that share data can corrupt it unless entry to the critical section is controlled. Peterson's solution does this with only two shared variables: a flag for each process and a turn variable. It is small enough to prove correct on the board, and it shows the three requirements a lock must meet. Hardware instructions such as test-and-set, compare-and-swap and swap do the same job in one atomic step and are used inside real spinlocks. This chapter explains both, their costs, and the assumptions that decide when each one works.

You need: 3.1 Critical-section problem and race conditions for the definition of a critical section and the three correctness requirements.

Peterson's two-process protocol

Peterson's solution is a software lock for exactly two processes, P0 and P1. It uses two shared variables. flag[2] is an array of booleans; flag[i]=true means Pi wants to enter its critical section. turn is an integer holding 0 or 1; it names the process that should go first when both want to enter. For process i, let j = 1 - i.

Entry protocol: set flag[i]=true, set turn=j, then spin while flag[j] is true and turn equals j. When the loop ends, enter the critical section. On exit, set flag[i]=false. The flag announces intent; turn is a polite concession to the other process. A process waits only when the other also wants entry and the turn is not its own.

Why the protocol is correct

Three requirements define a correct critical-section solution. Mutual exclusion: at most one process is inside. Progress: if no process is inside and one wants in, it must get in. Bounded waiting: a process cannot be overtaken forever.

Mutual exclusion holds because both processes cannot find the spin condition false together. Suppose both flags are true. P0 can pass only when turn=0; P1 can pass only when turn=1. Since turn has one value, at most one passes. If one process tested before the other had set its flag, the late process sees the earlier flag true and must wait.

Progress holds when only one process wants entry: the other flag is false, so the spin condition is false. When both want entry, turn is 0 or 1, so exactly one spin condition is false and that process enters.

Bounded waiting holds because after Pi exits it clears flag[i]. If Pj is waiting, Pi must set turn=j before trying again, which releases Pj. So Pj waits for at most one entry by Pi.

Costs: the spin loop burns CPU time (busy waiting). The algorithm covers only two processes. It also assumes atomic loads and stores and sequential consistency: all processes see memory operations in one global order. Modern CPUs may reorder independent loads and stores, so Peterson's solution is not a portable lock on all hardware.

Hardware synchronization instructions

Atomic hardware instructions are the practical alternative. Atomic means no other process can observe the step half done. Three common instructions follow.

Test-and-set: test_and_set(lock) returns the old value of lock and sets lock to true, as one atomic step. With lock=false meaning free, the entry is: while test_and_set(&lock) spin; critical section; lock=false. The first process gets false and enters. Others get true and spin. This is a spinlock: a lock that waits by spinning.

Compare-and-swap: compare_and_swap(&value, expected, new) returns the old value. If old equals expected, it stores new; otherwise it stores nothing. All of this is atomic. A lock can be built by expecting false and writing true.

Swap: swap(&a, &b) atomically exchanges two values. A spinlock can use a local variable key=true and repeat swap(&lock, &key) until key becomes false.

These instructions give mutual exclusion on multiprocessors. They do not by themselves give bounded waiting: a fast process can release and reacquire a test-and-set lock while another spins. Some syllabi call this synchronization hardware. Use spinlocks only for short critical sections, because spinning wastes a CPU that could run another thread.

Worked example

Question. P0 and P1 run Peterson's algorithm. Initially flag[0]=false, flag[1]=false, turn=0. The interleaving is: P0 sets flag[0]=true and turn=1. P1 sets flag[1]=true and turn=0. P0 tests while(flag[1] and turn==1). P1 tests while(flag[0] and turn==0). P0 finishes and sets flag[0]=false. Who enters the critical section next? Give flag[0], flag[1] and turn (0 for false, 1 for true) at the moment that process enters.

  1. Initial state: flag[0]=0, flag[1]=0, turn=0.
  2. P0 sets flag[0]=1 and turn=1. State: flag[0]=1, flag[1]=0, turn=1.
  3. P1 sets flag[1]=1 and turn=0. State: flag[0]=1, flag[1]=1, turn=0.
  4. P0 tests: flag[1]=1 is true, but turn==1 is false because turn=0. The while condition is false, so P0 enters.
  5. P1 tests: flag[0]=1 is true and turn==0 is true. P1 spins.
  6. P0 exits and sets flag[0]=0. State: flag[0]=0, flag[1]=1, turn=0.
  7. P1 tests again: flag[0]=0 makes the while condition false. P1 enters.

Answer. P1 enters next; at that moment flag[0]=0, flag[1]=1 and turn=0.

Exam traps

  • Writing the wait as while(flag[j] and turn==i) is wrong. P0 can set flag[0]=true and turn=1, see flag[1]=false, and enter; P1 can then set flag[1]=true and turn=0, see flag[0]=true but turn==1 false (turn=0), and enter too. Both are inside, so mutual exclusion fails.
  • Testing turn against the wrong process breaks the tie; process i must set turn=j and wait while turn==j.
  • Forgetting flag[i]=false on exit leaves the other process spinning forever; mutual exclusion still holds but progress fails.
  • Peterson assumes atomic loads and stores with sequential consistency; on CPUs that reorder stores it can fail, so it is not a portable production lock.
  • test-and-set returns the old value and sets true; it does not return true on success. compare-and-swap writes only when the old value equals expected.

3.3 Mutex locks and semaphores

A mutex lock and a semaphore both stop two processes from entering the same critical section together. A mutex has one owner: only the process that acquired it may release it. A semaphore is an integer with two atomic operations, wait and signal, so it can guard a pool of identical resources and also enforce an order between processes. The kernel's queues, the row locks behind a UPI payment, and the seat counter at IRCTC all rest on these ideas.

You need: 3.1 for the critical section and race conditions, and 3.2 for atomic test-and-set and compare-and-swap.

Mutex lock: one owner at a time

A mutex is a shared flag locked with two operations. A process calls acquire() before its critical section and release() after it. acquire() tests and sets the flag in one atomic step using hardware instructions from 3.2, so two processes cannot both see it free.

The mutex gives mutual exclusion: at most one process holds the lock. It also gives ownership: only the acquirer may release it, and the OS records the owner.

If the lock is taken, acquire() may spin in a tight loop: a spinlock. Spinning burns CPU but avoids a context switch, so it suits a few instructions on a multicore machine. On one CPU, or for a long section, the waiter should sleep in a queue instead. POSIX threads provide the blocking form as pthread_mutex_lock and pthread_mutex_unlock.

Semaphore: an integer with atomic wait and signal

A semaphore S is an integer, a queue of waiting processes, and two atomic operations. Some syllabi call wait P (proberen, to test) and signal V (verhogen, to increase); others call them down and up.

wait(S): S = S − 1, then block the caller if S < 0.   signal(S): S = S + 1, then wake one waiter if S ≤ 0.

S is set once before any process runs. |S| is the number of blocked processes when S is negative. When S ≥ 0, S is the number of free permits.

The change to S and the test must run without interruption. If two processes decrement S together, both can read the same old value and one permit is lost. The kernel disables interrupts for these instructions, or uses a spinlock inside the semaphore code. A blocked waiter joins S's queue; signal removes one and makes it ready. FIFO order is common but not promised by the definition.

  • Binary semaphore: S is only 0 or 1. It acts like a mutex but has no owner, so any process may signal it.
  • Counting semaphore: S starts at N and guards N identical resources, such as N printers.

Two uses: mutual exclusion and ordering

Mutual exclusion. Set S = 1. Each process does wait(S) before the critical section and signal(S) after it. The first leaves S = 0 and enters; the second drops S to −1 and blocks; the first's signal raises S to 0 and wakes the second.

Ordering. Set S = 0. Process A runs A1, then signal(S). Process B does wait(S), then B1. B blocks until A finishes A1. This is condition synchronisation: the semaphore carries a signal, not a lock. Starting at 1 would let B run first.

Bounded buffer (producer–consumer). There are n slots and three semaphores: mutex = 1, empty = n, full = 0.

Pseudocode.

producer:                consumer:
  wait(empty);             wait(full);
  wait(mutex);             wait(mutex);
  put item in buffer;      take item from buffer;
  signal(mutex);           signal(mutex);
  signal(full);            signal(empty);

The counting semaphores count slots and items; mutex protects the buffer. Wait on empty or full before wait(mutex). A producer that takes mutex first and sleeps on empty holds the lock, so the consumer cannot enter and both hang.

Readers–writers and dining philosophers

Readers–writers. Many readers may read together; a writer needs the data alone. Use mutex = 1, rw_mutex = 1, read_count = 0. A reader does wait(mutex), read_count++, and if read_count == 1 also wait(rw_mutex); then signal(mutex). On exit: wait(mutex), read_count−−, and if read_count == 0 signal(rw_mutex); then signal(mutex). A writer does wait(rw_mutex) … signal(rw_mutex). Continuous readers can starve a writer.

Dining philosophers. Five philosophers, five chopsticks, each a semaphore at 1. Philosopher i does wait(chopstick[i]), wait(chopstick[(i + 1) mod 5]), eats, signals both. If all five take the left chopstick, each waits forever for the right: circular wait, a deadlock (see 3.5). Fixes: allow at most four to pick up at once (counting semaphore at 4); let odd-numbered philosophers pick the right chopstick first; or use one mutex so only one picks at a time.

Worked example

Question. A counting semaphore S is initialised to 1. Processes P1, P2 and P3 call wait(S) in that order, with no signal in between. (a) Give S and the set of blocked processes after each call. (b) P1 then calls signal(S). Give S and state who can enter the critical section. (6 marks)

C program.

#include <stdio.h>
int main(void) {
    int S = 1;
    int i;
    for (i = 0; i < 3; i++) {
        S = S - 1;
        printf("%d\n", S);

    S = S + 1;

  3. P2 calls wait(S): S = 0 − 1 = −1. Is −1 < 0? Yes, so P2 blocks. S = −1, blocked = {P2}. |S| = 1 waiter.
  4. P3 calls wait(S): S = −1 − 1 = −2. Is −2 < 0? Yes, so P3 blocks. S = −2, blocked = {P2, P3}. |S| = 2 waiters.
  5. P1 calls signal(S): S = −2 + 1 = −1. Is −1 ≤ 0? Yes, so one waiter wakes; FIFO wakes P2. S = −1, blocked = {P3}.
  6. P1 has left the critical section, so P2 enters. P3 stays blocked until P2 signals.

Exam traps

  • wait tests S < 0; signal tests S ≤ 0. Mixing them loses a wake-up or wakes a process with no permit.
  • A negative S counts blocked processes, not free resources. S = −2 means two waiters, not two resources free.
  • An ordering semaphore starts at 0; a mutex semaphore starts at 1. Starting the ordering one at 1 lets the second process run first.
  • A mutex must be released by its owner; any process may signal a semaphore, so a stray signal breaks the count.
  • In the bounded buffer, wait(mutex) must come after wait(empty) or wait(full). Reversing them is the examiner's favourite deadlock question.

3.4 Monitors for synchronization

A monitor is a language-level module that holds shared data and the procedures that use it. Only one process may be active inside the monitor at a time, so the compiler or runtime supplies mutual exclusion; the programmer does not write lock and unlock calls. Condition variables let a process wait inside the monitor and release it without busy spinning. Monitors appear as Java's synchronized methods with wait and notify. Pthreads give you the same idea built by hand: a mutex plus condition variables.

You need: 3.1 Critical-section problem and race conditions and 3.3 Mutex locks and semaphores.

Monitor structure

A monitor has three parts: shared variables, procedures, and an initialization block. The shared variables hold the state that several processes need, such as a buffer and a count. The procedures are the only legal way to read or change those variables. The initialization block runs once and sets the starting values. A process calls a monitor procedure like any other procedure. The runtime checks the door: if no process is inside, the caller enters; if another process is active, the caller waits in an entry queue. This is implicit mutual exclusion. It removes the semaphore bugs of forgetting to lock or unlock the mutex, and of unlocking the wrong mutex. Condition variables still have to be waited on and signalled explicitly, so a missing or wrong condition-variable signal remains a programmer bug. See 3.3 for the explicit lock version. The monitor is a higher-level construct, not a hardware instruction. Its guarantee comes from the compiler or runtime plus a mutex and condition variables underneath. Monitor mutual exclusion does not decide which waiting process enters next; that is a scheduling choice.

Condition variables

Inside a monitor, a condition variable x is a queue of waiting processes. It has two operations. x.wait makes the calling process release the monitor and block on x. When another process later resumes it, it must reacquire the monitor before returning from wait. x.signal resumes one process waiting on x, if any. If no process waits, signal does nothing; the signal has no memory. A later wait will not see an earlier signal. Some syllabi call condition variables CVs.

The two common semantics differ in who runs after signal. Under Hoare semantics, signal-and-wait, the signalling process gives up the monitor and the signalled process runs immediately. Under Mesa semantics, signal-and-continue, the signaller keeps the monitor and the signalled process is made ready; it runs later. Java's wait and notify follow a Mesa-like style.

Because the condition can change again before the woken process runs, every wait must sit inside a while loop, not an if. Recheck the condition after wake-up. A condition variable is not a semaphore: it has no counter and no stored signal. It only answers who is waiting here now.

Bounded buffer inside a monitor

Take a buffer of capacity 2. The variable count is the number of items currently stored. The condition notFull holds producers waiting for space; notEmpty holds consumers waiting for an item. A producer calls insert: while count == 2, notFull.wait(); put the item; count = count + 1; notEmpty.signal(). A consumer calls remove: while count == 0, notEmpty.wait(); take an item; count = count - 1; notFull.signal(). The while guards are essential. If two producers wake, one may fill the last slot before the other runs; the second must test count again.

The same pattern solves the dining philosophers problem. Each philosopher has a state: thinking, hungry or eating. A philosopher who cannot get both forks waits on a condition for that philosopher. When a neighbour puts down a fork, it signals the neighbours that may now be able to eat. No busy waiting is used. If the state checks are wrong, deadlock can still appear; see 3.5. The monitor still does not choose which waiter enters; it only enforces one active process.

Worked example

3.5 Deadlock system model and necessary conditions

Two processes, each holding one resource and each waiting for the other's, will wait forever. That state is a deadlock, and you cannot see it by looking at one process — it is a property of a set of processes and the resources between them. Deadlocks appear in database transactions, file locks, device drivers and thread pools that grab two mutexes in the wrong order. This chapter builds the system model, draws the resource-allocation graph, and states the four conditions that must all be true at once before a deadlock can exist.

You need: process states from Unit 2, and the shared-resource conflict of 3.1.

Resource types, instances and the resource-allocation graph

A resource type R is a class of identical things a process may need: printers, disk drives, memory blocks, files, semaphores, mutex locks. Each type has a fixed number of instances W. A lab with two identical printers has one resource type R with W = 2; two printers on different networks are two types.

A process uses a resource in a fixed sequence.

  1. Request: ask for an instance. If none is free, the process blocks.
  2. Allocate: the OS gives one instance to the process.
  3. Use: the process works with the resource.
  4. Release: the process returns the instance.

The resource-allocation graph (RAG) is a directed graph recording the current state of all this. Nodes are of two kinds: a circle for each process P1 … Pn, and a box for each resource type R1 … Rm with W dots inside, one dot per instance. Edges mean holdings and waits.

  • Request edge P → R: process P is waiting for an instance of R.
  • Assignment edge R → P: one instance of R is held by P.
  • Total edges = pending requests + current holdings.
  • A box has one dot per instance, always, held or free. When an instance is held, the assignment edge starts at that dot and goes to the process; a dot with no outgoing assignment edge is free. Three printers with two held still show three dots, with two assignment edges leaving two of them.

A process can hold several resources and wait for several at once, so one node may have many edges in and out. The graph is a snapshot; it changes with every request and release.

Deadlock, starvation and the four necessary conditions

Deadlock: a set of processes is blocked, each waiting for a resource held by another member of the set, so none can ever release anything. Starvation (indefinite postponement) is different: a process waits a long time while others keep taking the resource, but the resource is still being released and could reach it. A deadlocked process is also starving; a starving process is not necessarily deadlocked.

In a priority scheduler with a steady stream of high-priority arrivals, a low-priority job may starve for hours while the CPU is never idle — unfair, but no deadlock. A deadlock needs a closed loop: process A holds lock L1 and waits for L2, process B holds L2 and waits for L1. Neither can proceed and neither will release, so the wait truly never ends.

Four conditions, listed by Coffman and co-authors in 1971, must all hold together for a deadlock to exist. If any one is false, deadlock is impossible.

  • Mutual exclusion: at least one resource is non-shareable, so one instance serves one process at a time. A read-only file breaks this.
  • Hold and wait: a process holds at least one resource while requesting another.
  • No preemption: a resource is released only voluntarily by its holder; the OS cannot snatch it back.
  • Circular wait: a closed chain of waits exists.
{P0, P1, …, Pn} : P0 waits for a resource held by P1, P1 waits for one held by P2, …, Pn waits for one held by P0

the P's are distinct processes and n ≥ 0; the chain must close on itself. A line of waits that ends at a free resource is not circular wait.

Cycles: always necessary, sufficient only for single instances

Look at the RAG. If it has no cycle, no process waits in a closed loop, so no deadlock exists: a cycle is necessary. It is sufficient only when every resource in the cycle has exactly one instance. Then the cycle is the deadlock, and every process on it is blocked forever.

Give R1 and R2 two instances each. P1 holds one R1 and requests one R2. P2 holds one R2 and requests one R1. P3 holds one R2. The graph contains the cycle P1 → R2 → P2 → R1 → P1, yet R1 has a free instance, so P2's request is granted; P2 finishes, releases both, then P1 runs. No deadlock. With several instances a cycle is only a warning; you must test whether free instances can break it, which is what detection in 3.8 does.

Threads deadlock the same way with locks, and a mutex is a single-instance resource, so there a cycle is a real deadlock. Thread A locks m1 then m2; thread B locks m2 then m1. If each takes its first lock before either takes its second, A waits for m2 held by B and B waits for m1 held by A. Mutex locks are from 3.3.

Breaking any one condition prevents deadlock: that is prevention, in 3.6. Granting only requests that leave a safe state is avoidance, in 3.7.

Worked example

Question. A system has two resource types, R1 and R2, with one instance each. Process P1 holds R1 and requests an instance of R2. Process P2 holds R2 and requests an instance of R1. (a) Draw the resource-allocation graph. (b) Count the request edges, the assignment edges and the total edges. (c) Is the system deadlocked? How many processes can finish?

  1. Step 1 — nodes: circles P1 and P2, boxes R1 and R2, each box with one dot because each type has 1 instance.
  2. Step 2 — P1 holds R1, so draw the assignment edge R1 → P1. P1 wants R2, so draw the request edge P1 → R2.
  3. Step 3 — P2 holds R2, so draw the assignment edge R2 → P2. P2 wants R1, so draw the request edge P2 → R1.
  4. Step 4 — count: request edges = 2 (P1 → R2, P2 → R1). Assignment edges = 2 (R1 → P1, R2 → P2). Total edges = 2 + 2 = 4.
  5. Step 5 — follow the arrows: P1 → R2 → P2 → R1 → P1. The chain closes, so there is one cycle, of length 4 edges.
  6. Step 6 — R1 has 1 instance and it is held by P1; R2 has 1 instance and it is held by P2. Free instances = 0, so neither request can be granted.
  7. Step 7 — P1 cannot get R2, P2 cannot get R1, neither releases anything. Processes that can finish = 0.

Answer. The graph has 4 edges (2 request, 2 assignment) forming one cycle; with 1 instance per resource and 0 free instances no process can complete, so the system is deadlocked and 0 processes finish.

Exam traps

  • A cycle in the resource-allocation graph is not always a deadlock. With several instances per resource the cycle can clear itself; only single-instance resources make a cycle equal to a deadlock.
  • Hold and wait is not circular wait. P1 holding R1 while waiting for R2, and P2 holding R2 while waiting for R3, is a chain that ends at free R3 — no deadlock.
  • The four conditions are necessary, not sufficient. With several instances per resource type, all four can hold and the system can still escape deadlock, because a free instance can break the circular wait.
  • No preemption is about the resource, not the CPU. Swapping a process out does not take back its file lock, so preempting the CPU does not break this condition.
  • Starvation is not deadlock. A starved process would finish once the resource reached it. A deadlocked process waits in a closed loop, so waiting longer never helps, though adding an extra instance of the contended resource type can sometimes break the cycle.

3.6 Methods for handling deadlocks; deadlock prevention

A deadlock is a set of processes waiting forever, each for a resource held by another. The OS can react in four ways: prevention, avoidance, detection with recovery, and ignoring the problem. Prevention removes one of the four necessary conditions before any request is made. This chapter explains the four handling methods and the four prevention techniques. You meet these ideas in database engines, thread pools, file servers and any program that locks more than one resource.

You need: the deadlock model and the four necessary conditions from 3.5.

Four handling methods

Prevention stops deadlock before it can start. It changes the rules so that at least one necessary condition is never true. The rule is fixed for all requests and does not look at the current state.

Avoidance also stops deadlock before it starts, but it checks each request against future claims. A request is granted only if the system remains in a safe state. A safe state means there is at least one order in which all processes can finish. See 3.7.

Detection lets deadlock happen. A detector runs later and finds a cycle or a set of processes that cannot finish. With one instance per resource type a cycle means deadlock; with several instances the detector must run a reduction to see whether any process can still finish. Recovery then kills a process or takes back a resource. See 3.8.

Ignoring assumes deadlock is rare. The OS does nothing; the user reboots or restarts the application. Some syllabi call this the ostrich algorithm. It is common on general-purpose desktop systems when the cost of prevention is higher than the expected loss.

Prevention: break one condition

Prevention attacks the four conditions from 3.5.

  • Break mutual exclusion. Make the resource shareable. Read-only files can be opened by many processes. A printer can be managed by a spooler: processes write output to disk, and one printer daemon prints jobs one by one. The physical printer is still exclusive, but processes no longer wait for it directly.
  • Break hold and wait. A process must request all resources before it starts, or release all held resources before asking for a new one. The first rule wastes resources that are reserved but unused. The second can starve a process that needs a popular resource.
  • Break no preemption. If a process holding resources asks for one that cannot be granted, the OS takes back its held resources. The process rolls back to a saved state and retries later. This works when state can be saved, such as a database transaction. It is hard for a printer or a tape drive.
  • Break circular wait. Put a global order on resource types, for example R1 < R2 < R3. Every process must request resources in increasing order. A process may hold R1 and request R2. It may not hold R2 and request R1. A cycle needs some process to wait for a lower-numbered resource while holding a higher one. The rule makes that edge impossible.

These rules lower utilisation. A process may wait even when the resource is free. Numbering can be impractical when new resource types appear. The ordering rule is simple and widely used in kernels and database locks.

Prevention compared with avoidance

Prevention is a static rule applied before the system knows the current demand. It can refuse a request that would be safe today. Avoidance is dynamic: it checks the request against each process's maximum claim and grants it only if a safe sequence still exists. The banker's algorithm in 3.7 is the standard avoidance method.

The price of prevention is lower utilisation and possible starvation. The price of avoidance is that every process must declare its maximum claim in advance, and the OS must run a safety check on every request. Detection pays nothing until the detector runs, but recovery can kill a process and lose work. A timeout is not prevention. It waits for a deadlock and then breaks it, so it belongs with detection and recovery in 3.8. Use numbering when lock order can be fixed, such as tree nodes or database tables.

  • A timeout is detection and recovery, not prevention.

3.7 Deadlock avoidance and banker's algorithm

Deadlock avoidance is the middle path between ignoring deadlock and preventing it. A process may ask for resources, but the request is granted only when the system can still finish every process in some order. That order is a safe sequence. The banker's algorithm is the standard method: it tracks each process's maximum claim, computes remaining need, and treats Available resources like a bank's cash reserve. It is used where maximum claims are known in advance, such as some batch, embedded and database resource managers.

You need: 3.5 for resources and wait-for cycles, and 3.6 for the four handling methods.

Safe state, unsafe state, safe sequence

A state is safe when there is at least one order of all processes in which each process can finish. To finish, a process needs its remaining maximum claim. The safety test gives it that claim from currently free resources plus resources released by processes earlier in the order. Such an order is a safe sequence. If no safe sequence exists, the state is unsafe.

Safety is a property of the whole set of processes, not one process. A process may be able to finish now, but the order must still let every process finish. Avoidance uses this test before granting a request: grant only if the new state is safe.

Need[i][j] = Max[i][j] − Allocation[i][j]

Need[i][j] is the remaining units of resource j that process i may still request; Max[i][j] is its declared maximum; Allocation[i][j] is what it already holds. A process i can finish when Need_i ≤ Work, compared element by element, where Work is the currently free resource vector.

  • Safe: at least one safe sequence exists.
  • Unsafe: no safe sequence exists. This does not prove deadlock.
  • Deadlocked: every process in a wait cycle is blocked and no sequence of releases can free them; a deadlocked state is always unsafe. With one instance of each resource type a cycle is enough; with multiple instances a cycle is necessary but not sufficient.

For one instance of each resource type, a resource-allocation graph shows a process's future claim as a dashed claim edge P_i → R_j, added when the process starts and only if it keeps the graph acyclic. When P_i actually requests R_j, the claim edge becomes a request edge. The request is granted only if converting that request edge into an assignment edge R_j → P_i creates no cycle; otherwise the process waits.

Banker's algorithm: safety test and request test

The banker's algorithm is the safety test for n processes and m resource types. Available[j] is the number of free units of resource j. Max[i][j] is process i's declared maximum. Allocation[i][j] is what it holds. Need[i][j] is its remaining need. Use Need = Max − Allocation.

  1. Set Work = Available and Finish[i] = false for every process i.
  2. Find an i with Finish[i] = false and Need_i ≤ Work. If none exists, go to step 4.
  3. Set Work = Work + Allocation_i, Finish[i] = true, and repeat step 2.
  4. If every Finish[i] is true, the state is safe. Otherwise it is unsafe.

The request algorithm runs the same test on a trial state. For request Req_i: if Req_i > Need_i, it is an error. If Req_i > Available, the process waits. Otherwise pretend to allocate: Available = Available − Req_i, Allocation_i = Allocation_i + Req_i, Need_i = Need_i − Req_i. Run the safety test. If safe, keep the allocation; if unsafe, restore the old vectors and make the process wait.

The simple safety test costs O(n²m): each pass scans n processes and compares m resources, and there can be n passes. A safe sequence need not be unique; any complete order is correct.

Why the maximum claim matters

Think of a bank with cash Available and customers with credit limits Max. The bank can lend only if, after the loan, it can still satisfy every customer up to the limit in some order. The banker's algorithm is exactly that check. The name sticks because the test protects the bank from running out of cash.

The algorithm needs strong information: every process's maximum claim must be known when it starts, and the process set must stay fixed. It does not handle a new process arriving with an unknown claim. If a process asks beyond its declared Max, that is a programming error, not a resource shortage. Detection and recovery are different; they act after a deadlock may already exist, as 3.8 explains.

Exam traps

  • Unsafe is not the same as deadlocked. An unsafe state has no guaranteed finishing order, but it may still finish; a deadlocked state has a cycle of waits and is always unsafe.
  • Need is Max − Allocation, not Max and not Available. Subtract component by component after the process has received its current allocation.
  • A request must satisfy both Req_i ≤ Need_i and Req_i ≤ Available. Checking only Available can grant more than the process declared as its maximum.
  • A safe sequence is not unique. The examiner may accept any full order that passes the safety test; do not reject a valid sequence just because it differs from the one in the notes.
  • Banker's algorithm assumes a fixed process set and known maximum claims. New processes with unknown maxima and processes arriving after the start break the test.

Understand What is the difference between a claim edge and a request edge in the single-instance resource-allocation graph? 3 marks

A claim edge P_i → R_j is dashed and means P_i may request R_j in future. A request edge means P_i has actually asked for R_j and is waiting. A grant changes the request edge into an assignment edge.

Beyond the syllabus

Not for the exam. Exact maximum claims are rare in real systems, so avoidance appears in specialised settings such as database lock managers, embedded avionics and some batch schedulers. Researchers study conservative approximations and runtime verification of resource claims. Search for Banker's algorithm, resource-allocation graph, safe sequence and deadlock avoidance.

3.8 Deadlock detection and recovery

Detection is for systems that do not prevent or avoid deadlock. The system runs normally, and a detector checks whether a set of processes is stuck waiting for each other. If each resource type has one instance, a wait-for graph with a cycle proves deadlock. If a resource type has several instances, an algorithm with Work and Finish marks the processes that can finish; the rest are deadlocked. Recovery then breaks the deadlock by ending processes or taking resources back. Kernels and database engines use these ideas when they choose not to forbid deadlock.

You need: 3.5 for the resource model and 3.7 for the matrix style.

Wait-for graph for single-instance resources

Draw one node per process. Add a directed edge Pi → Pj when Pi is waiting for a resource instance that Pj holds. A cycle means every process on it waits for the next, and none can release, so the system is deadlocked. No cycle means no deadlock. This test works only when every resource type has one instance.

For example, take single-instance resources R1, R2 and R3. P1 holds R1 and requests R2; P2 holds R2 and requests R3; P3 holds R3 and requests R1. The edges form P1 → P2 → P3 → P1, a cycle, so all three are deadlocked. Detect by keeping the graph current: add an edge when a request blocks, remove it when the request is granted or the process releases. Cycle search costs O(V + E) for V processes and E wait edges.

Detection with several instances per resource

Use four arrays. Available[j] is the number of free instances of resource type j. Allocation[i][j] is what process i holds. Request[i][j] is what process i is waiting for now. Work is a copy of Available; Finish[i] is false until process i is proved able to finish.

  1. Set Work = Available. Set Finish[i] = false, but set Finish[i] = true at once if Allocation[i] has no nonzero entry.
  2. Find an unfinished process i with Requesti ≤ Work for every resource type j. If none exists, stop.
  3. Add what i holds: Work = Work + Allocationi. Mark Finish[i] = true. Go back to step 2.
  4. Every process still unfinished is deadlocked.
Requesti ≤ Work means Request[i][j] ≤ Work[j] for all j

Request[i][j] is the outstanding number of instances of type j that process i is waiting for; Work[j] is the number currently free in the detector's simulation.

Use Request, not Need. Need is the maximum that may still be requested; using it turns the test into the Banker's safety check from 3.7. The detector runs in O(n²m) time for n processes and m resource types. Run it on every request for early warning, or periodically to save CPU; frequent runs cost time, rare runs let many processes pile up before recovery.

Recovery: abort processes or preempt resources

After detection, recovery must break the wait. Some syllabi call this recovery from deadlock. The first choice is to abort all deadlocked processes: simple and fast, but all their work is lost. The second is to abort one process at a time and rerun detection until the cycle breaks: less work lost, more overhead.

Pick the victim by cost: priority, CPU time already used, resources held, resources still needed, how many processes must be killed, and whether the process is interactive or batch. A low-priority process holding one resource is often cheaper to kill than a high-priority process holding many.

Resource preemption takes a resource from one process and gives it to another. It needs three pieces: victim selection, rollback to a state before the victim acquired the resource, and a limit on how often the same process is chosen, or it starves. Killing or preempting can leave files and shared memory half-updated, so a checkpoint or restart is needed. File consistency after a kill is handled in Unit 5, File Systems, Storage and I/O.

Worked example

Question. A system has resource types A (2 instances), B (1 instance) and C (1 instance). Allocation and Request matrices are: Allocation P1=[0,1,0], P2=[1,0,0], P3=[0,0,1], P4=[1,0,0]; Request P1=[0,0,1], P2=[0,0,0], P3=[0,1,0], P4=[0,0,0]. Use the multiple-instance detection algorithm to find how many processes are deadlocked and name them.

  1. Total instances = [2,1,1]. Allocated instances = [2,1,1]. Available = Total − Allocated = [0,0,0]. Set Work = [0,0,0].
  2. Every Allocation row has a nonzero entry, so Finish = [false, false, false, false].
  3. P1 requests [0,0,1] ≤ [0,0,0]? No. P2 requests [0,0,0] ≤ Work? Yes. Work = [0,0,0] + [1,0,0] = [1,0,0]; Finish[P2] = true.
  4. P3 requests [0,1,0] ≤ [1,0,0]? No. P4 requests [0,0,0] ≤ Work? Yes. Work = [1,0,0] + [1,0,0] = [2,0,0]; Finish[P4] = true.
  5. Scan again. P1 requests C, but Work[C] = 0, so no. P3 requests B, but Work[B] = 0, so no. No unfinished process fits.
  6. Unfinished processes are P1 and P3. Count = 2.
  7. P1 holds B and waits for C held by P3; P3 holds C and waits for B held by P1. P2 and P4 finished and freed both instances of A, but A does not help this B–C cycle.

Answer. 2 processes, P1 and P3, are deadlocked; P2 and P4 can finish and free [2,0,0].

Exam traps

  • The multiple-instance detector uses Request, the outstanding demand now; Need is the maximum remaining demand and belongs to Banker's safety check. Swapping them gives wrong deadlock sets.
  • An edge Pi → Pj in a wait-for graph means Pi waits for something Pj holds. Reversing the edge can invent or hide a cycle.
  • A wait-for graph cycle is necessary and sufficient only for single-instance resources. With several instances, a cycle can exist while another free instance lets a process finish.
  • Aborting a process is not free: files, locks or shared memory can be left inconsistent, so recovery needs rollback or a checkpoint.
  • Preemption without a starvation limit can keep choosing the same low-priority process and delay it forever.

Understand Why does a cycle prove deadlock only when each resource type has one instance? 3 marks

With one instance, the holder cannot release until it gets the next resource in the cycle, so there is no exit. With several instances, another free instance or a process outside the cycle can free a resource, so a cycle can exist without deadlock.

Not for the exam. Database engines often detect deadlocks with wait-for graphs and break them by aborting a transaction, then rolling it back. Distributed systems use edge-chasing or timeouts because no single machine sees the whole graph. Many modern kernels avoid full detection by enforcing lock order or using timeouts, which turns a possible deadlock into a failed request. Takeaways

  1. A race condition occurs when interleaved accesses change the result; the critical-section problem is to stop that for shared data.
  2. A correct critical-section solution must satisfy mutual exclusion, progress and bounded waiting.
  3. Peterson's solution is a two-process software protocol using flags and turn; it is mainly of conceptual value on modern hardware.
  4. Hardware atomic instructions such as test-and-set provide the primitive on which mutex locks and semaphores are built.
  5. A mutex has one owner; a semaphore is a counter with atomic wait and signal and can also order events.
  6. Monitors bundle shared data and operations and use condition variables to wait without busy spinning.
  7. Deadlock needs mutual exclusion, hold and wait, no preemption and circular wait together; prevention removes one condition.
  8. Avoidance grants requests only if a safe sequence remains; detection finds cycles and recovery kills processes or preempts resources.

Glossary

Banker's algorithm
A deadlock-avoidance algorithm that treats resources like loans and grants a request only if the state stays safe.
Binary semaphore
A semaphore whose value is only 0 or 1 and is often used like a mutex.
Bounded waiting
The guarantee that there is a finite limit on how many times other processes may enter before a waiting process gets its turn.
Circular wait
A deadlock condition where a closed chain of processes each waits for a resource held by the next.
Condition variable
A monitor queue on which a process waits and is later signalled when a condition may be true.
Counting semaphore
A semaphore that can take values above 1 and counts available resource units.
Critical section
The part of a program that accesses shared data and must not run concurrently with another process's critical section for the same data.
Deadlock
A set of processes in which each process waits for a resource held by another process in the set.
Deadlock detection
A runtime check that finds a cycle in a wait-for graph or a set of processes that cannot finish.
Hold and wait
A deadlock condition where a process holds one resource while waiting for another.
Lost update
A race where two processes read the same old value and one write overwrites the other's update.
Monitor
A synchronization construct that combines shared data and procedures with implicit mutual exclusion.
Mutex lock
A lock with acquire and release operations that has one owner at a time.
Mutual exclusion
The guarantee that at most one process is inside a given critical section at any time.
No preemption
A deadlock condition where a resource cannot be forcibly taken from its holder.
Non-preemptive
A policy where a process keeps a resource until it releases it voluntarily.
Peterson's solution
A two-process software critical-section protocol using per-process flags and a shared turn variable.
Preemptive
A scheduling or resource policy that can take a resource away from a running process.
Progress
The guarantee that a process trying to enter an idle critical section will not be blocked forever by processes outside it.
Race condition
A situation where the final result depends on the order in which concurrent operations happen.
Resource-allocation graph
A directed graph with process and resource nodes showing requests, assignments and releases.
Safe state
A state in which at least one order exists for all processes to finish without deadlock.
Semaphore
An integer accessed only by atomic wait and signal operations.
Spinlock
A lock whose waiting thread repeatedly tests the lock in a loop.
Starvation
Indefinite postponement of a process even though deadlock may not exist.
Test-and-set
An atomic hardware instruction that returns the old value of a word and sets it to a new value.
