5.1 File concept, attributes and access methods

A file is a named box of bytes that survives the process that wrote it. RAM forgets everything when power goes, so the operating system keeps data on secondary storage and gives you one simple handle for it: a name. That name maps to attributes (size, owner, times) and to bytes you can read or write. Without this abstraction every program would have to know disk geometry. With it, a photo, a database, a UPI log and a compiler's source file are all just files, opened and closed by the same calls.

You need: system calls from Unit 1, System calls and their types, and paging from Unit 4, Virtual memory, demand paging, page faults, copy-on-write for the memory-mapped paragraph.

What a file is, and what it carries

A file is a named sequence of bytes stored on secondary storage. Secondary storage means any device that keeps its contents without power: a hard disk, a solid-state drive, a USB stick. RAM does not keep contents without power; a power cut in Chennai wipes it. The file is the operating system's abstraction for data that must outlive the process. The process gives a pathname, and the OS finds the bytes.

The name is what a user types. Many systems split it into a stem and an extension, as in notes.txt or report.pdf. The extension is a convention, not a guarantee. Windows picks the program from the extension; UNIX-like systems store a type with the file and check the bytes. A renamed file opens in the wrong program, but its data is intact.

Operations and the open-file table

open() is a system call, and it does four jobs.

  1. Search the directory for the pathname and fetch the file's attributes.
  2. Check permission. If allowed, copy the attributes into a system-wide open-file table; if the file is already open, just raise its open count.
  3. Add an entry to the process's own table that points at the system-wide entry and holds a current position, the offset, starting at 0.
  4. Return a small integer, the file descriptor in UNIX or handle in Windows, which indexes the process table.

The other operations act through that descriptor.

  • create: make an entry and reserve attributes.
  • read(fd, buf, n): copy n bytes from the offset into buf, then advance the offset by n.
  • write(fd, buf, n): copy n bytes from buf at the offset, advance, and extend the size if needed.
  • seek(fd, pos): set the offset without transferring data; this is what makes direct access possible.
  • truncate: keep the attributes but set size to 0 and free the blocks.
  • delete: remove the name and free the blocks.
  • close: drop the process entry and lower the open count; at zero the system-wide entry is removed.

Two tables exist for a reason. The system-wide entry holds data every opener shares: location, size, open count. The per-process entry holds what is private: the offset and the access mode. Two processes that call open separately get separate offsets, so one reading does not disturb the other. After fork, the child shares the parent's offset because it shares the entry.

Access methods: how the OS finds a byte

Sequential access reads bytes in order: read next, write next, rewind, skip n. The OS holds the offset and moves it by the number of bytes transferred. Copying a log file, or a compiler reading source, works this way. It matches a magnetic tape and costs one pass to touch every byte once.

Direct access, called random access in some syllabi, treats the file as a numbered sequence of blocks and lets the program name any one of them: read(n), write(n). One record out of a thousand is found in one jump. With fixed-length records the offset follows from the record number.

offset = (n − 1) × L   for records numbered from 1
offset = n × L   for records numbered from 0

offset is the byte position from the start of the file, in bytes; n is the record number; L is the record length in bytes.

Indexed access adds an index: a table of keys and pointers kept inside or beside the file. The OS reads the index, gets a block pointer, then reads that block. A database with a B-tree index works this way. Cost is two reads instead of one, but the index is small and often cached.

Hashed access computes hash(key) and uses the result as the block number. An equality lookup takes one read on average. Order is destroyed, so printing records in date order becomes impossible, and collisions need a chain or an overflow block. A log keyed by UPI transaction id fits; a sorted ledger does not.

Memory-mapped files are not a fourth access method. mmap maps the file's pages into the process address space, so reads and writes become ordinary memory accesses that fault pages in. That mechanism is taught in Unit 4, Virtual memory, demand paging, page faults, copy-on-write. The file still has blocks; the program just stops calling read().

Worked example

Question. A file holds 1000 fixed-length records of 200 bytes each, numbered from 1. (a) For direct access, find the byte offset of record 250. (b) How many record reads does sequential access need to reach record 250 starting from record 1? (c) If the disk block size is 4096 bytes and block numbers start at 0, which block holds that offset?

  1. Record length L = 200 bytes, record number n = 250, numbering starts at 1.
  2. offset = (n − 1) × L = (250 − 1) × 200.
  3. 250 − 1 = 249.
  4. 249 × 200 = 49,800 bytes.
  5. Sequential access must pass records 1, 2, ..., 250 in order, which is 250 record reads.
  6. Block number = floor(offset ÷ block size) = floor(49,800 ÷ 4096) = floor(12.158) = 12, so block 12 counted from 0.

Answer. The offset is 49,800 bytes; sequential access needs 250 record reads; the byte lies in disk block 12 counted from 0, and direct access reads only the one record.

Exam traps

  • Do not confuse an access method with an allocation method. Direct access names a block of the file; where that block sits on disk is decided by contiguous, linked or indexed allocation, covered in 5.5.
  • The byte offset is not the disk address. Divide the offset by the block size and let the file system's mapping turn that logical block into a physical one.
  • Sequential access does not mean tape only. Any direct-access device can be read sequentially; the difference is whether the program may also jump.
  • An open-file offset is per process, not per file. Two independent open() calls have two offsets; only fork shares one.
  • Indexed access and indexed allocation are different things. One is a search structure for finding a record, the other is a way of placing blocks on disk.

5.2 Directory structure and implementation

A directory is a table inside a file system that maps a name to a file entry. Without it, users would remember inode numbers or disk addresses. The directory structure decides how the OS searches a path such as /home/ravi/notes.txt: it reads one directory entry at a time from the root or from the current directory. This chapter covers single-level, two-level, tree and graph directories, absolute and relative paths, path resolution, and two common directory implementations: a linear list and a hash table. The same ideas appear in Linux, Windows and phone file managers.

You need: 5.1 File concept, attributes and access methods for file attributes and the open-file table.

From a path to a directory entry

A directory is a file containing directory entries. A directory entry stores at least a name and a reference to the file's metadata. On many systems that reference is an inode number; an inode number identifies a metadata record inside one file system. The name is for people; the inode number is for the file system. In the figure, the entry notes.txt points to inode 2048. A directory block is a disk block that holds directory entries.

A path is a sequence of names separated by /. An absolute path starts at the root directory, written /. A relative path starts at the current directory, the directory a process is working in. The entry . names the current directory; .. names its parent. If the current directory is /home/ravi, then notes.txt and ./notes.txt are relative paths to the same file, while /home/ravi/notes.txt is absolute.

  1. Start at the root for an absolute path, or at the current directory for a relative path.
  2. Split the path on /.
  3. For each component except the last, search the current directory, then read the child directory.
  4. For the last component, search and return its directory entry.
  5. Treat . as the current directory and .. as its parent.

To resolve /home/ravi/notes.txt, the OS starts at the root. It searches the root's entries for home, reads that directory, searches for ravi, reads that directory, searches for notes.txt, and returns the inode. The final component names the file or directory the path identifies; earlier components must name directories. A cache of recent path lookups, often called a directory entry cache or dentry cache, can skip disk reads.

T_resolve = T_start + Σ T_read(component_i)

T_resolve is total path lookup time; T_start is the cost of reading the root or current directory before the search (0 if cached); T_read(component_i) is the cost of reading the directory block that holds component_i. Count each directory block read once: if T_start is the root/current read, start the sum at the second component; if T_start is 0, the first term is the root/current read.

Directory structures: from one list to a graph

In a single-level directory, all files sit in one directory. Names must be unique, so two users cannot both have notes.txt without renaming. It is simple and fast for a few files, but naming and grouping break down at scale.

A two-level directory gives each user one directory. The path starts with the user name, as in /ravi/notes.txt. Names now need to be unique only inside a user's directory. Sharing is awkward: one user's file is outside another user's directory, so the OS needs a search path or an explicit link. A link is another name for an existing file.

A tree directory allows directories inside directories, to any depth. Each file and directory has one parent, except the root. Some syllabi call this a hierarchical directory. Paths are unique from the root. Grouping by project, user and type becomes natural. Deletion of a directory is simple because one parent owns it.

An acyclic-graph directory allows a file or directory to appear under more than one parent, but no cycle. It supports sharing: one copy of a file can be reached by two paths. The OS must track links; deleting one name must not delete the file while another name still points to it. A reference count, a counter of how many names point to a file, does this job.

A general-graph directory allows cycles. Symbolic links can point to a parent, so a path search can loop. The OS needs a hop limit, a visited set or cycle detection during traversal, and garbage collection or cycle-aware deletion to reclaim unreachable files. General graphs are flexible but cost more bookkeeping.

Directory implementation: linear list and hash table

A directory is stored in directory blocks on disk. Implementation chooses how entries inside those blocks are found. The two classic methods are the linear list and the hash table.

A linear list stores entries one after another. To find a name, the OS scans entries and compares names. Lookup costs O(n) for n entries in the directory; O(n) means the time grows in proportion to n. Creating a file appends an entry; deleting marks a slot free or compacts. It is simple and works for small directories. A large directory can need many block reads.

A hash table stores a hash of the name and uses it to choose a bucket. Lookup computes hash(name), goes to the bucket, and compares names in that bucket. Average lookup is O(1) if hashing is good; worst case is O(n) when all names collide. Collisions are normal: two names can hash to the same bucket, so the OS must compare the full name. The table may be in memory, on disk or both; a fixed table can fill up, while a dynamic table can grow.

Exam traps

  • A path component is a directory entry, not a disk block. You search entries; a directory block is only the storage that holds them. The final entry names the file.
  • An absolute path begins at /; a relative path begins at the current directory. Do not add / to a relative path and call it absolute.
  • A tree gives every file and directory one parent. An acyclic graph allows shared files or directories with no cycle. A general graph allows cycles and needs loop control.
  • A hash collision does not mean a duplicate name. The OS must compare the full name in the bucket before declaring a match.
  • An inode number is unique inside one file system, not across all disks or all computers. A directory entry points to it; the inode is not the file's data.

5.3 File-system mounting and file sharing

Mounting makes one file system appear inside another at a directory called the mount point. Sharing lets processes, or hosts, open the same file with defined visibility of changes. The kernel uses a mount table for the first job and open-file entries plus locks for the second. A USB disk, second partition, or network share joins the directory tree this way. Only a few universities teach this chapter.

You need: path resolution from 5.2; the VFS idea appears in 5.4.

Mount point, table and unmount

A file system is a set of files and metadata on a device. Mounting attaches it at an existing directory, the mount point, such as /mnt/usb. The kernel records the pair in the mount table. Path resolution (5.2) walks names. At a mount point it consults the mount table and continues at the mounted root. Device /dev/sdb1 may hold a USB file system; /mnt/usb is its visible door. Mount order matters: mount the parent before a child beneath it. At boot the root is first, then /home or a USB disk.

Mounting does not merge directories. The old directory at /mnt/usb is hidden until unmount. After the mount, /mnt/usb/note.txt reaches USB inode 77, not local inode 101.

Unmount removes the mount-table entry and reveals the old directory. It fails if any process has an open file, current directory, or working directory inside; this is a busy mount. Close files and leave the directory first. For nested mounts, unmount the child before the parent. A lazy unmount detaches the name at once and frees the file system when the last user stops. Mounting is privileged because it changes the shared name space.

Open files, fork and locking

Each process has a file-descriptor table. A descriptor is a small integer index. It points to an open-file entry holding the current offset, flags, and a pointer to the inode. Two processes can share one open-file entry, or have separate entries for the same inode.

After fork, the child copies descriptors. Parent and child point to the same open-file entry, so they share one offset. An independent open() makes a new entry with a new offset. That is why a read after fork can surprise you.

File locks coordinate shared access. Advisory locks work only if programs check them; mandatory locks are enforced by the kernel. Sharing semantics differ: Unix shows writes immediately; session semantics shows changes after close; immutable-share forbids changes once shared. NFS is a remote Unix-style example; SMB is common on Windows. The VFS in 5.4 gives one interface.

5.4 File-system structure, implementation and virtual file systems

A file system must turn a name such as /home/ravi/notes.txt into disk blocks. It must also support several file systems on one machine: ext4 on the root disk, FAT32 on a pen drive, or a network file system. A virtual file system (VFS) gives one set of calls for all of them. The VFS holds common objects. Each concrete file system supplies methods for its own on-disk layout. The on-disk parts, the VFS objects, and pathname-to-inode lookup explain every open, read and write on Linux.

You need: 5.1 for file attributes and offsets, 5.2 for name-to-entry lookup, and 5.3 for mounts.

On-disk layout and operations

A file system on disk has a few fixed regions. The boot block is the first area. The system may use it to load an operating system. The superblock stores the file system's own metadata: block size, total blocks, free-block count, root directory location, and a magic number that identifies the type. An inode table, or a file allocation table (FAT), stores per-file metadata. Data blocks hold file content and directory content.

In an inode-based file system, each file has an inode. The inode stores file type, permission bits, owner, size in bytes, timestamps, link count, and pointers to data blocks. The inode number is a stable identifier inside that file system. A directory is a file whose data maps names to inode numbers. In a FAT file system, a directory entry stores the name, attributes, first cluster, and size. The FAT table then chains clusters: each entry gives the next cluster of the file or a mark for the last cluster.

The main operations are create, open, read, write, close, and delete. open finds the file's metadata and returns a file descriptor. read and write use a byte offset stored in the open file description. For a read of n bytes at offset o, the next offset is o + n. The bytes returned are from o to o + n − 1.

VFS objects and path lookup

The VFS is the kernel's common file-system interface. It defines four main objects. A superblock represents one mounted file system. An inode represents one file inside that file system. The VFS inode is a memory copy with operations, not the raw disk inode. A dentry represents one name-to-inode link, such as notes.txt in /home/ravi. A file represents one open file description: current offset, open flags, and a pointer to the dentry. The VFS also keeps a dentry cache so repeated lookups skip disk reads.

Path lookup walks one component at a time. Start at the root of the current process or at the current directory. For each component, ask the dentry cache. On a miss, call the parent inode's lookup method. The concrete file system reads its directory data and returns the child inode. At the end, the VFS has the target inode. open then creates a file object for that inode and returns a file descriptor to the process.

Calls such as open, read, stat and unlink enter the VFS. The VFS selects the right function through the inode's or file's operation table. The ext4 driver then reads or writes its own structures. Crossing a mount point changes the superblock and the root inode used for the next component. Some syllabi call this file-system implementation; others place the VFS under the file-system interface.

ext4 and FAT as examples

Linux ext4 is inode-based. A file is named by a directory entry that holds an inode number. The inode holds metadata and block pointers. A path lookup returns an inode number, then the VFS loads that inode. A file descriptor is not an inode number. Many descriptors can point to the same inode, and each descriptor has its own offset.

FAT is simpler. It has no inode table. A directory entry holds the file name, attributes, first cluster, and size. To read cluster k, the file system follows the FAT chain from the first cluster. The chain entry gives the next cluster number. An end-of-chain value marks the last cluster. Random access needs a walk from the start of the chain.

The VFS hides this difference. An ext4 read calls ext4's inode operations. A FAT read calls FAT's operations. Both return bytes to the same read system call. A pen drive formatted FAT32 and a root disk formatted ext4 can appear under one directory tree. Do not confuse the VFS superblock with the disk superblock. The VFS object is the in-memory handle for the mounted file system.

Worked example

Question. A process opens /home/ravi/notes.txt. The VFS maps it to inode 2048 on ext4. The file size is 4000 bytes. The process reads 100 bytes at offset 0, then reads 50 bytes. Find the offset after each read and the number of bytes left in the file.

  1. open resolves the path to inode 2048 and creates an open file description. Its offset starts at 0 bytes.
  2. First read: start offset = 0 bytes. Length = 100 bytes. End position = 0 + 100 = 100 bytes. New offset = 100 bytes.
  3. Second read: start offset = 100 bytes. Length = 50 bytes. End position = 100 + 50 = 150 bytes. New offset = 150 bytes.
  4. File size = 4000 bytes. Bytes left = file size − current offset = 4000 − 150 = 3850 bytes.

Answer. After the first read the offset is 100 bytes; after the second read it is 150 bytes; 3850 bytes are left.

Exam traps

  • The VFS is not a disk file system. It is the kernel's common interface and object layer; ext4 or FAT does the disk work.
  • An inode number is not a file descriptor. An inode names a file in one file system; a file descriptor names one open file description in one process.
  • The VFS superblock object is not the same as the on-disk superblock. One is an in-memory handle; the other is a disk region.
  • A read starts at the current offset, not at byte 0. Update the offset by the number of bytes read, not by the file size.
  • FAT has no inode table. A FAT directory entry holds the first cluster, and the FAT chain gives the later clusters.

5.5 Allocation methods: contiguous, linked, indexed

Allocation methods answer one question: which disk blocks hold a file, and how does the OS find block i? A directory entry can store a start block, a chain pointer, or an index-block number. The choice decides speed of sequential and direct access, fragmentation, and pointer overhead. Every file system uses one method or a mix: contiguous runs for small files, linked chains in FAT pen drives, and indexed inodes on Linux. The unit is the disk block, not the byte; a byte offset splits into a block number plus an offset inside that block.

You need: 5.4 file-system structures and 5.2 directory entries.

Contiguous allocation

A contiguous file occupies a run of consecutive disk blocks. The directory entry stores the first block number s and the length in blocks n. To find logical block i, where i counts from 0, the OS computes b = s + i. Here b is the physical disk block, s is the start block, and i is the block index inside the file. The mapping is arithmetic, so the block is known without reading any pointer. One seek reaches the file, and block i is a direct read: 1 disk read when the directory entry is cached.

b = s + i

b is the physical block number; s is the file's first block; i is the logical block index, starting at 0.

Contiguous allocation gives the fastest direct access and almost no per-block overhead. It suits read-only media and files that rarely grow. The cost is external fragmentation: free space breaks into gaps between files, and a new file needs one gap large enough. Compaction copies files to join free gaps and is expensive. A file that grows may have to move. The last block also has internal fragmentation: if the file is 4100 bytes and a block is 4096 bytes, the second block holds only 4 useful bytes.

  • Direct access: logical block i needs 1 disk read once the directory entry is cached.
  • Sequential access: blocks are adjacent, so few seeks.
  • Problems: external fragmentation, hard growth, internal waste in the last block.

Linked allocation and the FAT

Linked allocation puts each file block anywhere on disk. Each block stores the data and a pointer to the next block. The directory entry stores the first and often the last block number. A file is a chain: 12 → 7 → 20 → 5. The pointer costs space in every block: with 4-byte pointers and 512-byte blocks, overhead is 4/512 = 0.78%, and usable data is 508 bytes.

Sequential access is natural: read a block, follow its pointer. Direct access to logical block i needs i+1 block reads, because the OS must read block 0, then 1, and so on. The pointer is the only map. A single damaged pointer loses the rest of the file. Free space is managed as a list of free blocks, so a growing file just links a free block: no external fragmentation.

The file allocation table (FAT) variant keeps the pointers in one table in memory. The FAT holds one entry per allocation unit, called a cluster; a cluster is one or more disk blocks. Each entry holds the next cluster number of the chain, and an end-of-file value marks the last cluster. Following a chain can then avoid disk reads if the FAT is cached; the FAT itself still must be read from disk. Some syllabi call linked allocation a chain.

Indexed allocation and multilevel index

Indexed allocation collects a file's block pointers in one index block. The directory entry stores the index-block number, for example 30. Entry i of block 30 holds the data block for logical block i: entry 0 → 12, entry 1 → 7, entry 2 → 20, entry 3 → 5. Direct access reads the index block and then the data block: 2 disk reads when the index block is not cached, 1 when it is.

There is no external fragmentation, and a file can grow by adding a pointer to any free data block. The overhead is one index block per file. A tiny file wastes most of its index block; that is internal fragmentation of the index block. A very large file needs more pointers than one block holds.

Multilevel index solves that: a first-level index points to second-level index blocks, which point to data. A two-level index costs 3 reads for an uncached data block: first-level, second-level, data. The combined scheme used by UNIX-like inodes mixes direct pointers, one single indirect pointer, one double indirect pointer and one triple indirect pointer. Small files use direct pointers with no index block; large files add levels only when needed.

Worked example

Question. File F has four blocks, numbered 0 to 3. Contiguous allocation uses disk blocks 12, 13, 14, 15. Linked allocation uses 12 → 7 → 20 → 5. Indexed allocation uses index block 30 pointing to 12, 7, 20, 5. The directory entry is cached. Find the number of disk reads to fetch logical block 2 of F under each method.

  1. Logical block 2 is the third block of the file. Start with the directory entry already in memory, so the directory read is not counted.
  2. Contiguous: s = 12 and i = 2, so b = 12 + 2 = 14. Read data block 14. Disk reads = 1.
  3. Linked: start block 12 is block 0. Read block 12; it points to 7. Read block 7 (block 1); it points to 20. Read block 20 (block 2). Disk reads = 3.
  4. Indexed: directory gives index block 30. Read block 30; entry 2 points to 20. Read data block 20. Disk reads = 2.

Answer. Contiguous needs 1 disk read, linked needs 3 disk reads, and indexed needs 2 disk reads.

Exam traps

  • Do not count the directory read when the question says the directory entry is cached. Count only index-block and data-block reads.
  • Linked allocation cannot compute logical block 2 from a formula; it must follow block 0 and block 1 first. Saying 1 read is the common error.
  • FAT is not indexed allocation. It is linked allocation with the pointers moved into a table; the chain is still followed in order.
  • Internal fragmentation is waste inside an allocated block; external fragmentation is free gaps between allocated runs. Contiguous allocation suffers both: internal waste in the last block and external gaps between runs. Linked allocation suffers no external fragmentation, but its last block can still hold unused space (internal fragmentation), the same as any fixed-block scheme. Indexed allocation likewise has no external fragmentation, though its index block and its last data block can both be partly unused.
  • Index-block reads add up in a multilevel index: two-level uncached needs 3 reads (first-level, second-level, data), not 2.

5.6 Free-space management

A disk has a fixed number of blocks. Files come and go, so the OS must know which blocks are free before allocating one. Free-space management is that record plus the search that finds a free block. It must use little memory, find a block quickly, and stay correct after crashes.

You need: 5.5 Allocation methods and 5.9 Disk structure.

Bitmap: one bit per block

A bitmap gives one bit to every disk block. In this chapter 1 = free and 0 = used. A bitmap with N blocks needs N bits.

B = ⌈N / 8⌉ bytes

B is the bitmap size in bytes; N is the number of disk blocks; 8 bits = 1 byte; ⌈ ⌉ rounds up to a whole byte.

A 1 TiB disk with 4 KiB blocks has N = 228 blocks, so B = 225 bytes = 32 MiB. To allocate, the OS scans the bitmap for a 1. A word-at-a-time scan checks 64 blocks per 64-bit word. Worst-case cost is O(N) bit tests, or O(N / 64) word tests. First-fit scans from block 0; next-fit scans from the block after the last allocation and wraps at the end. A plain bitmap has no free count, so counting free blocks needs a full scan unless the OS keeps a separate counter.

Linked list, grouping and counting

A linked free list stores a pointer in each free block to the next free block. The head pointer names the first free block. No bitmap memory is used. Allocating from the head is O(1): take the head block and move the head to its stored pointer. Finding a particular free block, or testing whether block j is free, can need O(F) pointer steps, where F is the number of free blocks. Each step can be a disk read if the list is not cached.

Grouping stores, in the first free block, the addresses of k free blocks plus a pointer to the next group block. Counting stores the address of the first free block and the number of contiguous free blocks that follow it. Only a few universities teach grouping and counting; know the idea, not the detail.

A bitmap answers “is block j free?” in one bit test. A linked list needs a walk for that test. A bitmap is easier to keep consistent with a stored free count.

5.7 I/O hardware: polling, interrupts and DMA

A CPU cannot read a file directly from a disk or a network card. It talks to a device controller: a small chip with registers for command, status and data. Three mechanisms move data between controller and memory: polling, interrupts and direct memory access (DMA). Polling asks status again and again. Interrupts let the device signal the CPU. DMA lets the device write memory without per-byte CPU copying. Every read() or write() in a program ends here, in register writes, interrupt lines and DMA descriptors.

You need: interrupts and computer-system organization from Unit 1, and the layered file-system view of 5.4.

Device registers, port I/O and memory-mapped I/O

A device controller has registers. The command register receives operations such as READ or WRITE. The status register reports busy, ready and error. The data register carries bytes or a pointer to a buffer. The CPU sets these registers over the bus.

Two address styles exist. Port-mapped I/O gives registers a separate I/O address space. The CPU uses special instructions such as in and out; ordinary memory loads cannot touch them. Memory-mapped I/O maps the same registers into physical memory addresses. The CPU uses normal load and store instructions. The OS maps those physical pages into kernel virtual address space, so a driver reads a status register like a variable. Memory-mapped I/O is common on ARM and PCI devices; x86 supports both.

Polling is the simplest completion test. The driver writes a command, then loops: read status, test the busy bit, branch back if busy. This is busy-waiting: the CPU spins and does no other useful work. Polling is fine for a fast device or a short wait, because the loop has no interrupt overhead. It is poor for a slow device such as a disk or a human typing, because the CPU can spin for milliseconds. A real driver may poll briefly, then sleep and wait for an interrupt.

Interrupt request lines, vectors and ISRs

An interrupt request (IRQ) line is a hardware signal from a controller to the CPU, usually through an interrupt controller. The device raises the line when it needs service: a packet arrived, a disk sector is ready, or a DMA transfer finished. Unit 1 covers the CPU side: the CPU finishes the current instruction, saves the program counter and status, switches to kernel mode, and jumps to a handler.

The handler address comes from two tables. The interrupt vector is a small integer supplied by the interrupt controller; it identifies the source or the priority slot. The interrupt descriptor table (IDT) maps each vector to the address of its interrupt service routine (ISR). An ISR is the kernel code for that device. A correct ISR reads the device status, clears the cause so the line drops, and does urgent work. It may copy a few bytes, then mark a waiting process runnable. Long work is deferred because interrupts are disabled or nested handling is limited.

Interrupts cost more than a single poll. Entry saves registers, changes mode, and may flush pipeline state; exit restores all of it. The gain is that the CPU runs other work while the device is slow. A high interrupt rate can overwhelm the CPU, so systems coalesce interrupts or switch to polling under load.

DMA setup, completion and CPU cost

Direct memory access (DMA) moves a block without the CPU copying each byte. A DMA engine or bus-mastering device has a descriptor: memory address, byte count, direction, and control bits. The CPU checks that the device is free, writes the command and descriptor, and sets a start bit. The device then reads or writes memory directly. The CPU runs other work. When the block ends, the device raises an interrupt; the ISR checks status, updates the count, and wakes the waiting process. Some systems use a separate DMA controller; modern PCIe devices are bus masters. DMA still competes for memory bus cycles, so heavy DMA can slow CPU memory access. It also does not remove the completion interrupt; it removes per-byte CPU copying.

T = B / R

T is transfer time in seconds; B is bytes moved; R is transfer rate in bytes per second.

Npoll ≤ ⌊T / tpoll⌋ + 1

Npoll is the maximum number of polls; tpoll is the polling interval in seconds; ⌊ ⌋ rounds down.

CPU cost decides the choice. Polling pays Cpoll per poll. Interrupt pays Cint per event: entry, mode switch, ISR, exit. DMA pays Csetup plus Cint per block. For a slow device with a long wait, polling burns CPU; interrupts are better. For a very fast device with a short wait, interrupt overhead can exceed polling. For large blocks, DMA wins because per-byte copying disappears. For tiny, frequent transfers, setup overhead can dominate.

Worked example

Question. A device transfers 4 KB at 100 MB/s. Find the transfer time. If the CPU polls once per µs, find the maximum number of polls during the transfer.

  1. B = 4 KB = 4 × 1024 = 4096 bytes.
  2. R = 100 MB/s = 100 × 10⁶ bytes/s.
  3. T = B / R = 4096 / (100 × 10⁶) s = 4.096 × 10⁻⁵ s = 40.96 µs.
  4. tpoll = 1 µs. Poll instants inside 40.96 µs can be at 0, 1, 2, ..., 40 µs. Count = ⌊40.96 / 1⌋ + 1 = 40 + 1 = 41 polls.

Answer. The transfer takes 40.96 µs, and at most 41 polls fit in that time.

Exam traps

  • DMA removes per-byte CPU copying, not the completion interrupt or the setup work; a DMA block still ends with an interrupt or a poll.
  • Memory-mapped I/O is not ordinary RAM. The addresses decode to device registers, and caching those locations is wrong.
  • The interrupt vector is not the IRQ line number. The line is a hardware signal; the vector indexes the IDT to find the ISR.
  • Polling is not always bad. For a fast device with a short expected wait, it avoids interrupt entry and exit cost.
  • Unit slip: 4 KB is 4096 bytes, and 100 MB/s in I/O rates is 100 × 10⁶ B/s here. That gives 40.96 µs, not 40.96 ms.

5.8 I/O software layers, device drivers, buffering and caching

A read call looks simple to a program. Under it, the operating system turns one request into a chain of layers that talk to a controller. Each layer hides the layer below: the file system hides blocks, the driver hides device commands, the interrupt handler hides completion timing. The chain matters because it decides speed, safety and portability. Three tools make I/O faster and safer: blocking modes, buffers and caches. You meet them in every phone: a photo gallery reads thumbnails from cache, a printer queues jobs through spooling, and a music app keeps streaming while the screen stays responsive.

You need: I/O hardware: polling, interrupts and DMA and the system-call idea from Unit 1.

The four layers below the call

Read a file on a phone. The app calls read() through a user-space I/O library such as C stdio. That call crosses into the kernel through a system call, so the CPU switches to kernel mode. The kernel does not ask the disk controller directly. It passes the request down a stack of software layers. The top layer is the user process. The next is the system-call interface. Below it sits the I/O subsystem, also called the device-independent I/O software. It knows file names, permissions, buffers and caches, but not disk registers. The device driver knows one device family: it writes the controller registers. The interrupt handler runs when the device signals completion. Hardware is the controller and the device itself. On the way back, data and status climb the same stack. The driver reports success or an error. The subsystem copies data into the user buffer. The system call returns the byte count. The layering exists so a new disk needs a new driver, not a new file system. Link: virtual file systems use the same idea for file systems.

Drivers and how a process waits

A device driver is the kernel code that owns one device or one family. It hides registers, command codes and timing. A common interface has open, read, write, ioctl and close. The I/O subsystem calls these functions through a function table, so it never needs the device details. The driver's read may start DMA, then sleep. The interrupt handler wakes the driver. The driver checks status, clears the interrupt and returns. A process can wait in three ways. Blocking I/O puts the process to sleep until the data is ready; this is the usual read(). Nonblocking I/O returns at once with whatever is ready, or an error such as 'try again'; a game loop can poll a keyboard this way. Asynchronous I/O starts the transfer and returns; the process continues and later gets a signal, callback or completion queue entry. Blocking is easy to program. Nonblocking returns at once, so a process that polls in a loop keeps the CPU busy; used without polling, it lets the program do other work. Asynchronous gives overlap without busy waiting, but it is harder to code. On a phone, a blocking read of a photo file is fine in a background thread; a nonblocking read keeps the UI thread alive.

Buffers, caches and spooling

A buffer is memory that holds data while it moves. Single buffering uses one buffer: the device fills it, then the CPU empties it. Double buffering uses two: while the CPU works on buffer A, the device fills buffer B. Circular buffering uses a ring of buffers with a read pointer and a write pointer; it suits streams such as audio. Buffering absorbs speed differences and lets a slow device and a fast CPU work in steps. A cache is different. It keeps a copy of data that may be used again. A cache hit is served fast; a miss goes to the slower device. If the hit ratio is h, the average access time is T = h × T_cache + (1 − h) × T_device. Here h is the fraction of requests found in cache, T_cache is cache time and T_device is the slower device time. This assumes the miss costs only the device access; if the cache probe is also paid on a miss, the miss term becomes (1 − h) × (T_cache + T_device). Spooling is another tool. It puts jobs in a queue on disk for a device that cannot interleave, such as a printer. One job prints at a time, and users can submit more. A buffer is not a cache: a buffer holds data in transit, a cache keeps a copy for reuse. A cache may also be a buffer, but the purpose differs.

Worked example

Question. A cache has hit ratio 0.8. A cache access takes 0.1 ms; a disk access takes 10 ms. Find the average read time and the total time for 1000 reads.

  1. Given: hit ratio h = 0.8, cache time T_cache = 0.1 ms, disk time T_device = 10 ms, reads = 1000.
  2. Miss ratio = 1 − h = 1 − 0.8 = 0.2.
  3. Hit contribution = h × T_cache = 0.8 × 0.1 = 0.08 ms.
  4. Miss contribution = (1 − h) × T_device = 0.2 × 10 = 2.0 ms.
  5. Average read time = 0.08 + 2.0 = 2.08 ms.
  6. Total time for 1000 reads = 1000 × 2.08 = 2080 ms.

Answer. Average read time is 2.08 ms, and 1000 reads take 2080 ms.

Exam traps

  • A buffer is not a cache: a buffer holds data in transit, a cache keeps a copy for reuse.
  • In the hit-ratio formula, use the miss ratio 1 − h for the slow device. A common slip is to multiply the slow-device time by h.
  • The interrupt handler is not the driver. The handler is short and runs on completion; the driver contains the device logic.
  • Nonblocking is not asynchronous: nonblocking returns immediately with partial data or an error; asynchronous returns and reports completion later.
  • Spooling is not double buffering: spooling queues whole jobs on disk for a device such as a printer that cannot interleave jobs.

Hit contribution = 0.5 × 1 = 0.5 ms. Miss contribution = 0.5 × 9 = 4.5 ms. Average = 5 ms. Total = 1000 × 5 = 5000 ms.

Beyond the syllabus

Not for the exam. Real kernels expose asynchronous interfaces such as Linux io_uring and Windows overlapped I/O, which batch many requests and cut system-call overhead. Zero-copy paths use DMA and page remapping so data is not copied between kernel and user buffers. Storage caches now sit in the device, the host and the network, so hit ratios are measured at several levels. Search terms: io_uring, zero-copy I/O, page cache, spooler.

5.9 Disk structure and disk scheduling algorithms

A hard disk keeps data on spinning platters, in concentric rings called tracks. The OS must move a mechanical arm to the right ring and wait for the platter to turn before any byte is read. That movement costs milliseconds, far more than memory access. Disk scheduling orders the waiting requests so the arm travels less and average waiting time drops. Every database, file server and phone relies on it: the log a UPI payment writes and the table an IRCTC booking updates both sit on disks whose access time decides how fast the reply comes back.

You need: 5.5 allocation methods for how blocks hold a file, 5.8 I/O software for how a request reaches a driver, and Unit 4, Memory Management for swapping.

Disk geometry and access time

A magnetic disk holds one or more round platters on a single spindle. Each flat surface has a read/write head on an arm. The arm moves in and out along the radius; the platters spin at a fixed speed. Data sits in concentric rings called tracks. Each track is divided into sectors, usually 512 bytes or 4096 bytes. The set of tracks at one arm position, one per surface, is a cylinder. A physical address is (cylinder, surface, sector). Modern disks instead expose a flat logical block address and translate it inside the drive.

The cost of one request is the sum of three times.

  • Seek time: moving the arm to the target cylinder. This is the largest part, roughly proportional to the distance travelled.
  • Rotational latency: waiting for the target sector to spin under the head. It ranges from 0 to one full rotation, so 0.5 rotation on average.
  • Transfer time: reading or writing the bytes once the head is in place.
T_access = T_seek + 30 ÷ r + (b ÷ B_track) × (60 ÷ r)

T_access is the time for one request in seconds; T_seek is the seek time in seconds; r is the rotation speed in revolutions per minute, so 60 ÷ r is one full rotation in seconds and 30 ÷ r is the average rotational latency; b is the number of bytes transferred and B_track is the bytes on one track.

A large transfer is cheap per byte, because the seek and the latency are paid once and the rest of the track is read in order. That is why the OS reads ahead in large chunks.

Attachment, disk management and RAID

Disks attach in four common ways. SATA connects one disk to one host port. SCSI and SAS put many disks on one bus and are common in servers. USB carries removable disks. A network disk appears either as NAS, which shares files over NFS or SMB, or as SAN, which shares raw blocks over Fibre Channel or iSCSI. The first three look like block devices behind a device driver.

Disk management has four jobs.

  • Low-level formatting writes the sector headers and gaps on a raw disk.
  • Partitioning splits the disk into independent regions, and the boot block in the first region holds the code that loads the kernel.
  • Logical formatting writes the file-system structures described in 5.4.
  • Bad blocks are hidden by sector sparing, where a spare pool remaps the sector, or by the file system marking the cluster unusable.

Swap space is best placed on its own raw partition, so no file system sits between the page fault and the disk. A swap file also works and is easier to resize.

Disk scheduling algorithms

The driver keeps pending requests in a table, each naming a cylinder. It picks the next request to serve. Seek dominates the cost, so a good order cuts total head movement.

Total head movement = Σ |cᵢ − cᵢ₋₁|

c₀ is the starting cylinder, c₁ to cₙ are the cylinders served in the chosen order, and |cᵢ − cᵢ₋₁| is the distance moved between two consecutive requests, counted in cylinders.

  • FCFS serves requests in arrival order. It is fair and starvation-free, but the arm swings across the disk repeatedly.
  • SSTF serves the request nearest the current head position. Movement is small, but far requests can starve while near ones keep arriving.
  • SCAN moves in one direction to the last cylinder, serving everything on the way, then reverses. It behaves like a lift, so it is also called the elevator algorithm.
  • C-SCAN sweeps in one direction only. On reaching the end it returns to the other end without serving anyone, then sweeps again. Wait time becomes uniform; some syllabi call C-SCAN circular SCAN.
  • LOOK and C-LOOK are the same as SCAN and C-SCAN but reverse at the last pending request instead of at the physical disk end, saving that extra travel.
  1. Write the service order for the chosen algorithm.
  2. Subtract each consecutive pair of cylinders, including the start position.
  3. Add the absolute differences. The total is in cylinders, not in milliseconds.
  4. Divide by the number of requests for the average movement per request.

Worked example

Question. A disk has cylinders 0 to 199. The head is at cylinder 50. The pending requests, in arrival order, are 55, 90, 30, 120, 10. Compute the total head movement for FCFS, for SSTF, and for SCAN moving toward cylinder 0. State which is shortest and which is fairest.

  1. FCFS keeps the arrival order 55, 90, 30, 120, 10.
  2. FCFS distances: |50−55| = 5, |55−90| = 35, |90−30| = 60, |30−120| = 90, |120−10| = 110 cylinders.
  3. FCFS total = 5 + 35 + 60 + 90 + 110 = 300 cylinders.
  4. SSTF from 50: nearest is 55, distance 5. From 55 nearest is 30, distance 25. From 30 nearest is 10, distance 20. From 10 nearest is 90, distance 80. Then 120, distance 30.
  5. SSTF order 55, 30, 10, 90, 120 gives 5 + 25 + 20 + 80 + 30 = 160 cylinders.
  6. SCAN toward 0 serves 30 (distance 20), 10 (20), then 0 (10), then reverses and serves 55 (55), 90 (35), 120 (30).
  7. SCAN order 30, 10, 0, 55, 90, 120 gives 20 + 20 + 10 + 55 + 35 + 30 = 170 cylinders.
  8. SSTF has the least movement at 160 cylinders. SCAN moves 170 cylinders but no request waits longer than one sweep, so it is fairer.

Answer. FCFS moves 300 cylinders, SSTF moves 160 cylinders and SCAN moves 170 cylinders; SSTF is shortest but SCAN gives the bounded wait.

Exam traps

  • Forgetting the trip to cylinder 0 in SCAN. Count every movement, including travel past the last request to the disk end.
  • Reporting head movement in milliseconds when the data gives only cylinders. Movement is measured in cylinders; time needs seek time per cylinder.
  • Calling SSTF optimal. It minimises the next seek, not the total, and it can starve a far request indefinitely.
  • Forgetting that average rotational latency is half a rotation, not zero and not a full rotation.
  • Sorting the queue and calling it FCFS. FCFS keeps arrival order; only SSTF and SCAN reorder by distance.

Remember Define a cylinder on a magnetic disk. 2 marks

Understand Why can SSTF starve a request? 3 marks

It always picks the nearest cylinder. A far request keeps losing to newly arriving near requests, so it may wait forever.

Apply Head at cylinder 30, queue 10, 60, 20. Give the total head movement for FCFS and for SSTF. 4 marks

FCFS order 10, 60, 20: 20 + 50 + 40 = 110 cylinders. SSTF order 20, 10, 60: 10 + 10 + 50 = 70 cylinders.

Analyze Why does C-SCAN give a more uniform wait than SCAN? 4 marks

C-SCAN always sweeps in one direction, so a request is served within one sweep plus the return. SCAN serves the middle cylinders twice per cycle and the edge cylinders once, so edge requests wait longer.

Apply A disk spins at 7200 rpm. Find one full rotation and the average rotational latency. 3 marks

One rotation = 60 ÷ 7200 s = 8.33 ms. Average latency = half of that = 4.17 ms.

Understand What does sector sparing do with a bad block? 2 marks

The disk keeps a pool of spare sectors and remaps the bad sector to a spare, so the file system never sees the fault.

Analyze RAID 5 needs at least three disks. Why can it survive one disk failure and how much space is usable? 3 marks

Parity for each stripe is spread across all disks, so the data on a failed disk can be rebuilt from the surviving data plus parity. Usable space is n − 1 disks out of n.

Takeaways

  1. A file is a name, a set of attributes and a stream of bytes; the directory holds the name and the control block holds the rest.
  2. The access method decides whether reading block n costs one disk read or n disk reads.
  3. Directory structures trade search speed against the ability to share one file under several paths.
  4. Mounting joins separate file systems into one tree without copying any data.
  5. The VFS gives one interface, and every concrete file system supplies the operations behind that interface.
  6. The allocation method fixes three things at once: random-access speed, external fragmentation and the largest possible file.
  7. Polling burns CPU cycles, an interrupt costs a mode switch, and DMA moves a block with a single interrupt at the end.
  8. Disk scheduling exists because seek time dominates on rotating media, and SSTF can starve a far-away request.

Glossary

Absolute path name
A path that starts at the root directory and names every directory down to the file.
Blocking I/O
A call that puts the process to sleep until its data is ready, so the scheduler can run someone else meanwhile.
Boot block
The first blocks of a partition, holding the code the firmware loads to start the operating system.
Cylinder
The set of tracks at the same radius on all platters, reachable without moving the head.
Disk controller
The electronics that accept block read and write commands, position the head and transfer data to memory.
Extent
A run of consecutive blocks recorded as one (start, length) pair inside an inode.
File Allocation Table
A linked-allocation variant where all next-block pointers sit in one table kept in memory.
File descriptor
A small integer a process uses to refer to an open file in later read, write and close calls.
Hard link
A second directory entry that points to the same inode, so the file has one copy and two names.
Interrupt vector
A table of handler addresses indexed by interrupt number, used to dispatch each interrupt quickly.
Journaling file system
A file system that writes each metadata change to a log first, so recovery replays the log instead of scanning the whole disk.
Logical block address
The number the OS uses for a block on a device; the controller converts it to cylinder, track and sector.
Memory-mapped I/O
A scheme where device registers appear at ordinary memory addresses, so normal load and store instructions drive the device.
Open file table
Kernel table holding the offset and access mode of each open file, with a per-process table pointing into it.
Page cache
The kernel's memory copy of recently read file blocks, checked before any disk read is issued.
Partition
A contiguous region of a disk treated as an independent device that can hold one file system.
Relative path name
A path interpreted from the process's current working directory instead of the root.
Rotational latency
The wait for the spinning platter to bring the target sector under the head, 0 to one full rotation.
Sector
The smallest addressable unit on a disk platter, traditionally 512 bytes and now often 4096 bytes.
Spooling
Holding complete jobs in a buffer, typically on disk, so a slow device such as a printer can work through them one at a time.
Swap space
Disk area holding pages pushed out of memory; space is allocated in whole pages, not by a general file system.
Symbolic link
A small file whose contents are a path name; the OS re-resolves that path when the link is opened.
Transfer time
The time to move the requested bytes between disk and memory once the head is in place.
Volume control block
The in-memory copy of the superblock: block count, free-block count and pointers to free lists.
