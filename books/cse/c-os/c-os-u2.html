2.1 Process concept, states and process control block

A process is an executing program that owns its own CPU state, memory limits and I/O resources. The operating system must keep track of each process so it can stop it, store its state, and later resume it on any CPU core. This concept is used in every multitasking system – from a smartphone handling many apps to a server running thousands of services.

You need: basic OS structure and system‑call ideas from Unit 1.

What is a Process

A process is a program in execution. It is more than the program file; it includes the current value of the program counter, the contents of registers, the allocated address space, open file descriptors and a unique identifier called the process ID (pid). The OS creates a process when a user launches an application or when another process calls a creation system call.

  • Program code stored on disk
  • Dynamic memory (heap, stack, data segment)
  • System resources such as open files or network sockets
  • Execution context (pc, registers, flags)

Some syllabi refer to the process description as a process descriptor. The descriptor is stored in the kernel and is called the Process Control Block (PCB).

Process Life‑Cycle States

When a process is created it moves through five well‑defined states. The states describe what the process is waiting for and what the scheduler can do with it.

  • New: The process has been admitted but not yet ready to run.
  • Ready: All required resources are allocated and the process awaits CPU time.
  • Running: The CPU is executing the process instructions.
  • Waiting (or Blocked): The process cannot proceed until an external event, usually I/O, occurs.
  • Terminated: The process has finished execution and its resources are reclaimed.
  1. Event wait: Running process issues I/O → moves to Waiting.
  2. Event completion: I/O finishes → process returns to Ready.
  3. Exit: Running process finishes its last instruction → Terminated.

Total execution time = CPU₁ + I/O + CPU₂

CPU₁ and CPU₂ are the CPU bursts in milliseconds; I/O is the blocking time in milliseconds.

Scheduling actions

Scheduling actions are operations performed by the OS scheduler that move processes between life‑cycle states without the process itself initiating them.

  • Admission: OS moves a New process to Ready after allocating memory and other required resources.
  • Dispatch: Scheduler selects a Ready process and gives it the CPU, changing its state to Running.

Process Control Block (PCB)

The PCB is a kernel data structure that holds all information needed to manage a process. When the scheduler performs a context switch it saves the current process’s state into its PCB and loads the state of the next process from its PCB.

  • pid – unique process identifier
  • state – current life‑cycle state
  • pc – program counter value
  • register set – general purpose registers, status flags
  • memory limits – base and limit addresses of the address space
  • open file table – list of file descriptors
  • scheduling information – priority, CPU accounting

Because the PCB contains the complete execution context, the OS can pre‑empt a running process at any time, store its PCB, and later resume it without losing progress.

Worked example

Question. Process P arrives at time 0 ms. It needs a CPU burst of 5 ms, then performs I/O for 3 ms, and finally needs another CPU burst of 2 ms. List the state sequence of P and compute the total time from arrival to termination.

C program.

#include <stdio.h>
int main(){
    int cpu1=5, io=3, cpu2=2;
    int total = cpu1 + io + cpu2;
    printf("Total time = %d ms\n", total);
    return 0;
}
  1. At time 0 ms the process is created in the New state.
  2. Memory is allocated, so P moves to Ready.
  3. Scheduler dispatches P → Running for the first CPU burst (5 ms).
  4. At time 5 ms P issues I/O → moves to Waiting.
  5. I/O completes after 3 ms (at time 8 ms) → P becomes Ready again.
  6. Scheduler dispatches P → Running for the second CPU burst (2 ms).
  7. At time 10 ms the burst finishes → P exits → Terminated.
  8. Total time = 5 ms + 3 ms + 2 ms = 10 ms.

Output

Total time = 10 ms

Answer. The state sequence is New → Ready → Running → Waiting → Ready → Running → Terminated, and the total execution time is 10 ms.

Exam traps

  • Confusing the Waiting state (blocked for I/O) with the Ready state (waiting for CPU).
  • Assuming the PCB is stored in user memory; it resides in kernel space and is not directly accessible by the process.
  • Counting the I/O time twice when adding CPU bursts – the I/O period is already part of the total elapsed time.

2.2 Process scheduling queues and context switching

The operating system must move processes between several queues and must store and restore a process's state whenever the CPU changes hands. This movement is called scheduling, and the store‑restore operation is called a context switch. Scheduling queues keep the system organized, while the context switch lets the CPU execute another process without losing the work already done. Together they enable multitasking on phones, ATMs, and the servers that run UPI transactions.

You need: basic process concepts and the Process Control Block from Process concept, states and PCB.

Scheduling queues

A modern OS maintains several queues to hold processes at different stages. The Ready queue contains processes that have all required resources except the CPU. The Waiting queue holds processes blocked for an event such as a signal or a timer. The Device queue stores processes that are waiting for I/O completion on a specific device. Some systems also maintain a Priority queue where each entry has an associated numeric priority; the scheduler picks the highest‑priority ready process first.

  • Ready queue – processes ready to run, ordered by scheduling policy.
  • Waiting queue – processes blocked on events, not eligible for CPU.
  • Device queue – per‑device list of I/O‑waiting processes.
  • Priority queue – a view of the ready queue with priority values.

When a process blocks, the OS removes its PCB (process control block) from the Ready queue and places it in the appropriate Waiting or Device queue. When the event occurs, the PCB is moved back to the Ready queue. This movement is fast because it only requires updating the PCB’s links in the queue data structures, not copying the entire PCB.

Dispatch latency = Save time + Scheduler overhead + Load time

Save time = time to write registers to PCB; Scheduler overhead = time to select next PCB; Load time = time to restore registers from PCB.

Context switching

A context switch occurs whenever the CPU stops executing one process and starts another. The OS must preserve the state of the outgoing process and restore the state of the incoming process. The state includes the program counter, stack pointer, general‑purpose registers, and sometimes floating‑point registers.

  1. Save the current process's registers into its PCB (save step).
  2. Invoke the scheduler to choose the next ready PCB (selection step).
  3. Load the chosen PCB's registers into the CPU (restore step).
  4. Transfer control to the new process at its saved program counter.

If the save step takes 2 µs, the load step takes 2 µs, and the scheduler needs 1 µs to pick the next process, the total context‑switch time is 5 µs. This value is called the dispatch latency and is a key factor in real‑time systems.

C program.

#include <stdio.h>
int main() {
    const double save = 2.0;   // µs
    const double load = 2.0;   // µs
    const double sched = 1.0;  // µs
    double total = save + load + sched;
    printf("Total context switch time = %.1f µs\n", total);
    return 0;
}

Output

Total context switch time = 5.0 µs

Dispatcher and latency

The component that performs the three steps of a context switch is called the dispatcher. The dispatcher is invoked by the scheduler after a scheduling decision. Its job is to move the CPU from the old process to the new one as quickly as possible.

  • Dispatcher = hardware‑software module that saves the state of the outgoing process and restores the state of the incoming process. The selection of the next process is done by the scheduler.
  • Dispatch latency = total time required for a context switch, i.e., save time + scheduler overhead + load time.
  • In preemptive systems the dispatcher may be called by a timer interrupt.
  • In non‑preemptive systems the dispatcher runs only when a process voluntarily yields.

Dispatch time is the portion of the context switch that moves the process to the CPU (the save and load steps).

Because the dispatcher runs in kernel mode, its overhead directly reduces the time available for user programs. Designers therefore try to keep the save and load times small, often by using dedicated registers or hardware support such as shadow registers.

2.3 Operations on processes: creation and termination

The operating system must be able to start new programs and stop those that have finished. System calls such as fork(), exec() and clone() let a running process create another process. On Windows the system call is CreateProcess(). The POSIX library function spawn() provides similar functionality on Unix. The new process receives a unique PID and a link to its parent. When a process ends it calls exit, and the parent can retrieve the exit status with wait. If the parent does not wait, the finished process becomes a zombie, consuming a PID slot. This lifecycle is the basis for all user‑level applications, from a banking app using UPI to a server handling cricket scores.

You need: understanding of process states and PCB from Process concept, states and process control block.

System calls for creating a process

The primitive call in Unix‑like systems is fork(). It duplicates the calling process. The child receives a copy of the parent’s address space, file descriptors and environment. The return value distinguishes the two: the child gets 0, the parent gets the child’s PID.

  1. Parent executes pid = fork().
  2. Kernel creates a new PCB, assigns a fresh PID, and copies the parent’s context.
  3. Kernel returns 0 to the child and the child’s PID to the parent.
  • execve() replaces the child’s memory image with a new program.
  • CreateProcess() (Windows) creates a new process and loads a program in one call. The POSIX library function spawn() provides similar behaviour on Unix.
  • clone() (Linux) lets the child share selected resources such as memory or file tables.

In the child process fork() returns 0; in the parent process it returns the child’s PID.

Ending a process and collecting its status

A process ends by calling exit(status). The status is an 8‑bit integer supplied by the program. The kernel marks the process as terminated but keeps its PCB until the parent reads the status.

  1. Child calls exit(code).
  2. Kernel stores code in the child’s PCB and changes the state to terminated.
  3. Parent calls wait(&status) or waitpid(childPID,&status,0).
  4. Kernel copies the stored code into status and removes the PCB.

C program.

#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
#include <stdlib.h>

int main() {
    pid_t pid = fork();
    if (pid == 0) {
        printf("Child PID %d doing work...
", getpid());
        exit(42); // return code 42
    } else {
        int status;
        waitpid(pid, &status, 0);
        if (WIFEXITED(status)) {
            printf("Parent received exit code %d from child %d
", WEXITSTATUS(status), pid);
        }
    }
    return 0;
}

Output

Child PID 12345 doing work...
Parent received exit code 42 from child 12345
  • If the parent never calls wait, the child stays in zombie state.
  • A zombie still occupies a PID slot, which can exhaust the PID pool on long‑running servers.

Parent‑child hierarchy and zombie processes

Every process (except the init process) has a parent identified by PPID. The kernel maintains a tree of processes. When a process terminates, its children are re‑parented to init (PID 1) so they can still be waited on.

PPID_child = PID_parent

PPID_child is stored in the child’s PCB; it equals the PID of the process that called fork.

A zombie appears when the child has exited but the parent has not yet performed wait. The state diagram shows a transition from running → terminated → zombie → reaped.

2.4 Inter-process communication: shared memory, messages, pipes

Inter‑process communication (IPC) lets two or more processes exchange data even though each process has its own private address space. IPC is needed when a producer generates data that a consumer must use, for example a sensor process sending readings to a logger, or a web server handing a request to a worker. The main mechanisms are shared memory, message queues, and pipes (both anonymous and named). Each mechanism has its own way of handling buffers, blocking, and synchronization, and the OS provides system calls to create and use them.

You need: process concepts from Process concept, states and PCB and basic scheduling from Process scheduling queues.

Shared‑memory IPC

Shared memory creates a memory segment that multiple processes can map into their own virtual address spaces. The segment is identified by a key and attached with the shmat system call. Because the segment is a common buffer, processes must coordinate access with synchronization primitives such as semaphores or mutexes to avoid race conditions.

  • Segment size is fixed when created; typical size is a few megabytes.
  • Producer writes data into the segment, then signals the consumer.
  • Consumer reads data after receiving the signal.
  1. Create segment with shmget(key, size, IPC_CREAT|0666).
  2. Attach segment in producer with shmat.
  3. Attach segment in consumer with shmat.
  4. Use a semaphore to protect the buffer.
  5. Detach with shmdt and remove with shmctl.
Effective throughput = (Data size) ÷ (Write time + Read time + Sync overhead)

Data size in bytes; Write time and Read time are the time each process spends copying; Sync overhead is the time spent on semaphore operations.

Message‑queue IPC

A message queue stores messages in kernel space. Each message has a type (an integer) and a payload. Processes use msgsnd to enqueue and msgrcv to dequeue. The queue can be bounded; when full, the sender blocks until space becomes available.

  • Message size is limited by the system constant MSGMAX (at least 8192 bytes on POSIX systems; actual limit may be larger).
  • Multiple receivers can read messages of specific types.
  • Queue attributes (max bytes, max messages) are set at creation.
  1. Create queue with msgget(key, IPC_CREAT|0666).
  2. Define a struct with long mtype; and char mtext[SIZE];.
  3. Sender fills mtype and mtext, then calls msgsnd.
  4. Receiver calls msgrcv with the desired type.
  5. Remove queue with msgctl when done.

Pipe IPC (anonymous and named)

A pipe provides a unidirectional byte stream between a writer and a reader. An anonymous pipe is created with pipe() before a fork(); the child inherits the file descriptors. A named pipe (FIFO) is created with mkfifo() and can be opened by unrelated processes.

  • Pipe buffer size is kernel defined; on recent Linux kernels the default capacity is 64 KB (earlier systems used 4 KB).
  • Writes of size ≤ PIPE_BUF (at least 4 KB on POSIX) are atomic; they are not interleaved with writes from other processes.
  • Write blocks when buffer is full; read blocks when buffer is empty.
  • Blocking semantics implement producer‑consumer flow control.

C program.

#include <stdio.h>
#include <unistd.h>
#include <string.h>

int main() {
    int fd[2];
    pipe(fd);
    pid_t pid = fork();
    if (pid == 0) {
        // Child reads
        close(fd[1]);
        char buf[100];
        read(fd[0], buf, sizeof(buf));
        printf("Child read: %s
", buf);
    } else {
        // Parent writes
        close(fd[0]);
        const char *msg = "Hello through pipe";
        write(fd[1], msg, strlen(msg)+1);
    }
    return 0;
}

Output

Child read: Hello through pipe
  1. Call pipe(fd) to obtain two file descriptors.
  2. Fork the process; child closes the write end, parent closes the read end.
  3. Parent writes a null‑terminated string with write.
  4. Child reads with read into a buffer and prints it.

  • Assuming a pipe can hold unlimited data and therefore never blocks; the kernel imposes a fixed buffer size (often 4 KB).

  • Forgetting that the write call includes the terminating null byte when sending a string; this adds one extra byte to the transfer.

2.5 Threads, multicore programming and multithreading models

A thread is a lightweight unit of execution that lives inside a process. All threads of a process share the same address space, code segment, global variables and open files, but each thread has its own thread control block (TCB) and a private stack. Because threads reuse the process resources, they are cheaper to create and switch than full processes. Modern smartphones and laptops have multiple CPU cores, so using several threads lets an application run parts of its work in parallel, improving responsiveness and reducing perceived waiting time.

You need: process concept and process scheduling.

Thread control block and per‑thread resources

When a thread is created the OS allocates a Thread Control Block (TCB). The TCB stores the thread identifier, current register values, program counter, thread state (ready, running, blocked) and a pointer to the thread’s private stack. The stack holds the thread’s local variables, function call frames and return addresses. All threads of the same process point to the same code segment and the same global data segment, so they can read or write the same variables without extra copying.

  • TCB – metadata for scheduling and context switching.
  • Per‑thread stack – isolated call frames, prevents corruption between threads.
  • Shared code – only one copy of the executable is kept in memory.
  • Shared data – global variables, heap, open file descriptors are common.
Memory_{process} = Code + Heap + Data + Σ(Stack_i)

Code, Heap and Data are shared; Stack_i is the private stack of thread i.

All terms are in bytes (or appropriate memory units).

Threading models

Operating systems provide three classic mappings between user threads and kernel threads.

  • Many‑to‑one: many user threads are multiplexed onto a single kernel thread. The OS sees only one thread, so only one core can execute at a time. Example: early Green Threads.
  • One‑to‑one: each user thread has a dedicated kernel thread. The kernel can schedule each thread on a different CPU core. Most modern OSes (Linux, Windows) use this model.
  • Many‑to‑many: a pool of kernel threads is created and user threads are bound to any free kernel thread. This gives flexibility and limits kernel resource use. Solaris 2.5 introduced this model; it was also present in later versions such as Solaris 9.

The choice of model affects scalability. On a 4‑core phone, a many‑to‑one program cannot use more than one core, while a one‑to‑one program can run four threads in parallel, reducing total execution time.

Multicore programming and responsiveness

Mobile applications often need to perform I/O, network calls or image processing while keeping the UI smooth. By creating a separate thread for each independent task, the UI thread stays responsive. The OS scheduler places each runnable thread on any idle core, so work proceeds concurrently.

  1. Identify tasks that can run independently (e.g., downloading images).
  2. Create a thread for each task; on modern OSes the underlying one‑to‑one model maps each thread to a kernel thread automatically.
  3. Start all threads; the scheduler runs them on available cores.
  4. Join the threads or use callbacks to combine results.

C program.

#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

    int id = *(int*)arg;
    usleep(200000);               // 200 ms simulated download
    printf("Image %d done\n", id);
    return NULL;
}

    }
    for (int i = 0; i < N; ++i) {
        pthread_join(th[i], NULL);
    }
    printf("All downloads complete\n");
    return 0;

2.6 Scheduling criteria; preemptive and non-preemptive scheduling

Schedulers are judged by measurable performance criteria. The criteria tell us how well the CPU is used, how many jobs finish, and how long users wait. They are needed to compare different scheduling policies and to pick a policy that fits the system’s goals, such as keeping a web server responsive or maximizing batch throughput.

You need: process concepts and scheduling queues.

Scheduling performance metrics

CPU utilization is the percentage of time the processor is busy. It is computed as (busy time ÷ total time) × 100 %.

Throughput is the number of jobs completed per hour. Higher throughput means the system finishes more work in the same period.

Turnaround time for a process = completion time – arrival time. It measures the total time a job spends in the system.

Waiting time = total time a process spends in the ready queue. It is turnaround time minus the CPU burst time.

Response time = time of first CPU allocation – arrival time. It matters for interactive tasks where the user expects a quick reaction.

  • All metrics are expressed in milliseconds (ms) for short jobs or seconds (s) for long jobs.
  • Metrics can be averaged over many processes to obtain system‑wide values.

Preemptive vs. non‑preemptive execution

In a non‑preemptive policy the CPU runs a process until it either finishes or blocks. The scheduler cannot take the CPU away voluntarily.

In a preemptive policy the scheduler may interrupt a running process, for example when a shorter job arrives (shortest‑remaining‑time) or when a time slice expires (round robin).

  1. When a process arrives, place it in the ready queue.
  2. If the scheduler is preemptive, compare the new process with the running one.
  3. If the new process has higher priority (or shorter remaining burst), save the state of the current process and dispatch the new one.
  4. Otherwise let the current process continue until it blocks or finishes.

Non‑preemptive scheduling gives low context‑switch overhead but can cause long waiting for short, interactive jobs. Preemptive scheduling improves responsiveness at the cost of more overhead.

Avg. waiting time = Σ waiting_i ÷ n

waiting_i is the waiting time of process i; n is the number of processes.

Why the metrics matter in real life

A bank’s online portal must keep response time low so a user sees the transaction status instantly. The scheduler therefore prefers a preemptive policy that gives each request a short time slice.

A data‑center batch job that processes nightly reports cares more about throughput and CPU utilization. Here a non‑preemptive, high‑throughput policy may be chosen.

  • Mobile apps using UPI need fast response time to show payment confirmation.
  • Railway ticket booking (IRCTC) experiences many short requests; preemptive round robin keeps the queue moving.
  • A power‑cut in Chennai can be mitigated if critical control processes have high CPU utilization and low waiting time.

2.7 Scheduling algorithms: FCFS, SJF, priority, round robin

CPU scheduling decides which ready process gets the CPU next. Different policies trade off simplicity, response time, and fairness. The classic algorithms – First‑Come‑First‑Served, Shortest‑Job‑First, priority, and Round‑Robin – appear in most Indian B.Tech syllabi. They are used in desktop OSes, in transaction servers handling UPI payments, and in embedded controllers of railway ticket kiosks.

You need the concepts of process states and context switching from process scheduling queues and context switching.

First‑Come‑First‑Served and Shortest‑Job‑First

FCFS puts processes in the ready queue in order of arrival. The scheduler never changes this order. It is easy to implement but can give large waiting time if a long process arrives before short ones.

  1. When a process arrives, append it to the tail of the ready queue.
  2. When the CPU becomes idle, remove the head of the queue and dispatch it.

SJF is non‑preemptive. At each dispatch the scheduler looks at all processes that have arrived and selects the one with the smallest CPU burst. This reduces average waiting time but needs knowledge of burst length.

  • Advantage: minimum average waiting time among non‑preemptive policies.
  • Disadvantage: can starve long processes.
  • Requires either past statistics or programmer hints.

WT_avg = ( Σ WT_i ) ÷ n

WT_i is waiting time of process i; n is number of processes.

Priority Scheduling

Each process is assigned a priority number. Lower numbers mean higher priority in most Indian curricula. The scheduler always picks the ready process with the highest priority (lowest number).

  1. When a process arrives, insert it into the ready queue sorted by priority.
  2. If two processes have the same priority, break the tie by FCFS order.
  • Advantage: important jobs finish quickly.
  • Disadvantage: low‑priority jobs may starve.
  • Preemptive version can interrupt a running low‑priority process when a higher‑priority one arrives.

In many real‑time systems priority scheduling is combined with aging – gradually increasing the priority of waiting jobs – to avoid starvation.

Round‑Robin with Time Quantum

RR gives each process a fixed CPU slice called a quantum. After the quantum expires, the process is placed at the tail of the ready queue and the next process runs.

  1. Select the head of the ready queue.
  2. Run it for at most quantum ms.
  3. If the process finishes earlier, remove it; otherwise, enqueue the remaining part at the tail.
  • Advantage: good average response time, suitable for time‑sharing systems.
  • Disadvantage: too small a quantum causes many context switches; too large degrades to FCFS.
  • Quantum is often chosen as 20‑40 ms in desktop OSes.

RR is the default scheduler for many interactive services such as IRCTC ticket booking where many short requests share the CPU.

2.8 Thread, multiprocessor and real-time scheduling

When a system has more than one CPU core and some tasks must meet strict deadlines, the scheduler must decide not only which ready thread runs next, but also on which core it runs and whether the timing guarantees can be met. Multiprocessor load‑balancing, CPU affinity, and real‑time algorithms such as Rate‑Monotonic (RM) and Earliest‑Deadline‑First (EDF) provide the mechanisms to keep all cores busy while respecting hard or soft timing constraints. These techniques are used in smartphones handling UI threads, in servers running parallel services, and in embedded controllers of trains or medical devices.

You need: basic process and thread concepts from 2.1, thread basics from 2.5, and scheduling criteria from 2.6.

Multiprocessor load balancing and CPU affinity

A multiprocessor system has several identical CPUs that share main memory. The scheduler keeps a run‑queue for each CPU. When a thread becomes ready, it is placed on one of these queues. Load balancing moves threads between queues so that no CPU stays idle while another is overloaded.

  • Per‑CPU run‑queue reduces lock contention.
  • Load‑balancer runs periodically (e.g., every 10 ms) and migrates tasks.
  • CPU affinity remembers the last CPU a thread ran on; keeping it there improves cache reuse.
  • A strong affinity flag is a scheduler hint that a thread should stay on its preferred CPU unless the system is severely imbalanced.
  1. Thread becomes runnable → add to local run‑queue.
  2. Scheduler picks the highest‑priority thread from its queue.
  3. If the queue is empty, the balancer searches other CPUs and pulls a task.
  4. If a thread has a strong affinity flag, it is kept on its preferred CPU unless the system is heavily imbalanced.

Load imbalance = max_i (L_i) ÷ avg(L_i)

L_i is the number of runnable threads on CPU i; avg(L_i) is the average over all CPUs.

#include <stdio.h>

    int cpus = 4;

    int sum = 0;
    for(int i=0;i<cpus;i++){
        if(load[i]>max) max = load[i];
        sum += load[i];

    double avg = sum/(double)cpus;

Real‑time scheduling concepts

Real‑time tasks have a period T (time between releases) and a worst‑case execution time C. Utilization U = C/T expresses the fraction of CPU time a task needs. For a set of n independent periodic tasks, the total utilization is Σ C_i/T_i.

  • Hard real‑time: missing a deadline can cause system failure (e.g., airbag deployment).
  • Soft real‑time: occasional deadline miss degrades quality (e.g., video playback).
  • Jitter = variation in actual start time of a periodic job.
  1. Compute U for each task.
  2. Add them to get U_total.
  3. If using EDF, check U_total ≤ 1.
  4. If using RM, compare U_total with the Liu‑Layland bound. If U_total ≤ bound, RM guarantees that all deadlines are met. If U_total > bound, the test is inconclusive – the task set may still be feasible, and a more detailed analysis (e.g., response‑time analysis) is required.

RM bound = n × (2^{1/n} - 1)

n is the number of tasks; bound is the maximum utilization for which Rate‑Monotonic scheduling guarantees all deadlines.

Choosing the right algorithm

EDF is optimal for uniprocessor systems: if any algorithm can meet all deadlines, EDF can. It dynamically orders jobs by earliest absolute deadline. RM is a static priority scheme; tasks with shorter periods get higher priority. RM is easier to implement on small microcontrollers because priorities never change at run time.

  • Use EDF when total utilization is close to 1 and tasks have varying periods.
  • Use RM for low‑cost embedded devices with a small, fixed set of periodic tasks.
  • For multiprocessor systems, partitioned scheduling assigns each task to a single CPU and runs the chosen uniprocessor algorithm per CPU.
  1. List all tasks with C and T.
  2. Compute U_total.
  3. If U_total ≤ 1 → EDF feasible.
  4. If U_total ≤ RM bound → RM is guaranteed feasible. If U_total > RM bound, the test is inconclusive; the task set may still be schedulable with more detailed analysis.
  5. Otherwise, consider task splitting or a hybrid algorithm.

    double U_total = U_A + U_B + U_C;
    double rm_bound = 3 * (pow(2.0, 1.0/3.0) - 1);
    printf("U_total = %.3f\n", U_total);
    printf("RM bound = %.3f\n", rm_bound);
    return 0;
}
  1. Compute utilization of each task: U_A = 1/5 = 0.2, U_B = 2/10 = 0.2, U_C = 2/20 = 0.1.
  2. Add them: U_total = 0.2 + 0.2 + 0.1 = 0.5.
  3. For EDF, check U_total ≤ 1 → 0.5 ≤ 1, so EDF can meet all deadlines.
  4. For RM, n = 3 tasks. Compute RM bound = 3 × (2^{1/3} – 1) ≈ 0.779.
  5. Since U_total = 0.5 ≤ 0.779, RM also guarantees all deadlines.

2.9 Linux schedulers: O(1) and Completely Fair Scheduler

Linux must decide which runnable task runs next on each CPU. Early kernels used the O(1) scheduler that picks a task in constant time. Modern kernels use the Completely Fair Scheduler (CFS) that gives each task a share of CPU proportional to its weight. Both designs keep the system responsive and fair, especially on multi‑core phones and servers.

You need: process concept, scheduling queues and basic algorithms.

O(1) scheduler and per‑CPU runqueues

The O(1) scheduler was introduced in Linux 2.6. It keeps a separate runqueue for each CPU. A runqueue holds tasks in an array of priority lists called a priority array. The array has 140 entries, one for each static priority value from 0 (highest) to 139 (lowest).

When a task becomes runnable, the kernel inserts it into the list that matches its static priority. Insertion is O(1) because it is a simple linked‑list add at the head.

To select the next task, the scheduler scans the priority array from highest to lowest until it finds a non‑empty list. The scan is bounded by the fixed size of the array, so the selection time is also O(1).

  • Per‑CPU runqueue avoids lock contention on SMP systems.
  • Constant‑time selection makes the scheduler scalable.
  • Static priority cannot express fine‑grained fairness.

next_task = first_non_empty(priority_array[i])

i is the smallest index with a ready list; priority_array[i] holds tasks of static priority i.

The O(1) design works well for real‑time classes that need deterministic latency. However, it gives lower‑priority tasks very little CPU if higher‑priority tasks keep arriving.

Completely Fair Scheduler (CFS) and virtual runtime

CFS replaced the O(1) scheduler in Linux 2.6.23. It treats CPU as a perfectly divisible resource. Each task accumulates a virtual runtime (vruntime) that measures how much CPU time it has received, adjusted by its weight.

Weight is derived from the nice value. Nice ranges from -20 (high priority) to +19 (low priority). The kernel maps nice to a weight factor; for example nice = 0 gives weight = 1024, nice = ‑5 gives weight = 2825, nice = 10 gives weight = 102.

vruntime = actual_runtime × (1024 ÷ weight)

actual_runtime is CPU time in nanoseconds; weight is the task's weight; 1024 is the reference weight for nice = 0.

All runnable tasks are kept in a red‑black tree ordered by vruntime. The leftmost node has the smallest vruntime and is chosen to run next. After a time slice, the task's vruntime is increased, and the node is re‑inserted.

  1. Pick the leftmost node in the red‑black tree.
  2. Run the task for a slice computed from the target latency (default ≈ 20 ms) and the task's weight, with a minimum granularity of ≈ 1 ms.
  3. Update vruntime using the formula above.
  4. Re‑balance the tree with the new vruntime.

CFS guarantees that over a long period each task receives CPU proportional to its weight. If two tasks have weights 2825 and 1024, the first gets 2825/(2825+1024) ≈ 0.734 → 73.4 % of CPU.

  • Fairness is achieved without static priorities.
  • Load average is the average number of runnable tasks over a period of time. CFS uses the sum of task weights to compute a scaled load metric, but this is not the system load average.
  • CFS works on all CPUs; each CPU has its own red‑black tree.

Worked example

Question. Task A has nice = ‑5 (weight = 2825) and Task B has nice = 0 (weight = 1024). The CPU slice is 100 ms. Compute the CPU time each task receives in one slice according to CFS.

C program.

#include <stdio.h>
int main(){
    double weight_a=2825, weight_b=1024, slice=100.0;
    double total=weight_a+weight_b;
    double a = weight_a/total*slice;
    double b = weight_b/total*slice;
    printf("%0.2f %0.2f\n", a, b);
    return 0;
}
  1. Total weight = 2825 + 1024 = 3849.
  2. Share of A = 2825 ÷ 3849 ≈ 0.734.
  3. Share of B = 1024 ÷ 3849 ≈ 0.266.
  4. CPU time for A = 0.734 × 100 ms ≈ 73.4 ms.
  5. CPU time for B = 0.266 × 100 ms ≈ 26.6 ms.

Output

73.40 26.60

Answer. Task A gets about 73.4 ms and Task B gets about 26.6 ms of CPU in the 100 ms slice.

Exam traps

  • Confusing static priority (O(1) scheduler) with nice‑based weight (CFS).
  • Using actual runtime instead of weight‑adjusted vruntime in the CFS formula.
  • Assuming CFS always runs the highest‑priority task; it chooses the smallest vruntime instead.
  • Treating the priority array scan as O(n) – it is bounded by a constant size.

Each core keeps its own red‑black tree and vruntime values. Load balancing moves tasks between trees when vruntime differences exceed a threshold, keeping overall fairness.

Analyze Why did Linux replace the O(1) scheduler with CFS? 5 marks

O(1) could not express proportional sharing and suffered from priority inversion for interactive workloads. CFS provides fine‑grained fairness, better interactivity, and scales to many CPUs.

Takeaways

  1. A process is the OS abstraction for a running program and is described by its PCB.
  2. Context switching moves the CPU from one process to another by saving and restoring PCBs.
  3. Threads share the same address space, making communication cheap but requiring synchronization.
  4. Scheduling criteria guide the choice of algorithm based on system goals such as high utilization or low response time.
  5. Preemptive algorithms can improve responsiveness but add overhead from more context switches.
  6. Linux uses O(1) and CFS schedulers to balance constant‑time selection with fairness on multicore CPUs.
  7. IPC mechanisms differ in speed, complexity, and suitability for different application patterns.
