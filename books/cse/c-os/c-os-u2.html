2.1 Process concept, states and process control block

A program sitting on disk does nothing. A process is that program in execution: its code and data are in memory, its values are in the CPU registers, and a small kernel record called the process control block (PCB) keeps its identity and its state. One CPU is shared by many processes, so the OS must know at every instant what each one is doing — running, ready, waiting for a disk read, or finished. The PCB's state field answers that question, and it drives every scheduling decision in this unit.

You need: system calls and dual-mode operation from Unit 1, because a process changes state only by making a system call or by being interrupted.

Program is a file, process is a running thing

A program is a file of machine instructions on disk, such as an .exe on Windows or an ELF binary on Linux. It is passive. Nobody executes a file; the OS first copies parts of it into memory.

A process is a program in execution, plus everything the CPU needs at that moment. Open the same UPI app twice and you get two processes from one program file, each with its own memory and its own PCB.

One process's memory has four regions:

  • text: the instructions, usually read-only and shared by copies of the same program.
  • data: global and static variables.
  • heap: memory asked for at run time by malloc() or new, growing upward.
  • stack: one frame per active function call, holding parameters, the return address and locals; it grows downward.

Add the CPU context: the program counter (PC), the address of the next instruction; the stack pointer (SP), the top of the current stack; and the general-purpose registers. To stop a process and later continue it exactly where it stopped, the kernel must save all of this — into the PCB.

The five states and every legal move

A process lives through five states. Some syllabi write blocked for waiting and exit for terminated; the words mean the same.

  • New: the PCB has been created but the process is not yet ready to run.
  • Ready: able to run, waiting only for a CPU.
  • Running: its instructions are executing on a core. On a machine with n cores, at most n processes are running at once.
  • Waiting (blocked): cannot continue until an event happens — a disk read finishes, a key is pressed, a lock is freed.
  • Terminated (exit): execution is over; the PCB stays until the parent collects the exit status.
  1. new → ready (admitted): address space and other resources are allocated and the process is placed in the ready queue.
  2. ready → running (dispatch): the scheduler picks this process and restores its saved registers.
  3. running → ready (time slice over): a timer interrupt fires, or a higher-priority process arrives. The process did no wrong; it is simply preempted (chapter 2.6).
  4. running → waiting (I/O request): a system call such as read() cannot finish at once.
  5. waiting → ready (I/O done): the event happened; the process is eligible again but must still compete for a CPU.
  6. running → terminated (exit): the process calls exit().

Two rules hold: waiting never goes straight to running, and nothing returns to new. The state field, not the program, decides which queue the PCB sits in.

Worked example

Question. Process pid 1042 is playing a video. Its PCB holds state = Running, PC = 0x2A40, SP = 0x7FF0 and three open files. The program calls read() on a slow SD card. (a) Which state does it enter? (b) Which PCB fields change? (c) Where does it wait, and which state follows when the driver signals completion?

  1. Before the call: the state field reads Running and the process is on a CPU core.
  2. read() is a system call, so the CPU switches to kernel mode (Unit 1) and the kernel starts the SD card transfer.
  3. A card transfer is slow compared with CPU speed, so the process cannot continue. The state field moves Running → Waiting.
  4. The PC is saved as the address of the instruction after the call, not 0x2A40, which points at the call itself. The register set and SP = 0x7FF0 are copied into the PCB.
  5. The PCB leaves the running set and joins the device queue of that SD card (chapter 2.2).
  6. The driver's interrupt handler marks the transfer complete: state goes Waiting → Ready and the PCB moves to the ready queue. It does not go to Running, because a CPU may not be free.
  7. On a later dispatch the saved PC and registers are restored, and read() returns the byte count to the program.

Answer. The process moves Running → Waiting → Ready; the changed fields are the state plus the saved context (PC, registers, SP); it waits on the SD card's device queue.

Exam traps

  • Sending a process from Waiting straight to Running when its I/O finishes. It always goes to Ready, because the CPU may now be busy.
  • Calling a program a process. The program is a file on disk; the process is that file plus memory, registers and a PCB.
  • Thinking only one process in the whole system can be Running. On a multicore machine, one per core may run.
  • Believing a terminated process has lost its PCB. The record survives until the parent calls wait() (chapter 2.3).
  • Saving the PC as the address of the system call instruction instead of the instruction after it, which would repeat the call forever.

2.2 Process scheduling queues and context switching

A CPU runs one process at a time, but a system holds many. So the OS must park the processes that are not running and remember exactly where each one stopped. It does this by putting their process control blocks into queues — one queue for processes waiting for the CPU, one for each device — and by switching the CPU from one PCB to another. That switch is the context switch. It is what makes a single core look like it is doing many things at once, and it is pure overhead: no user work happens during it.

You need chapter 2.1: the PCB and the five process states.

Queues hold PCBs, not processes

The OS does not queue whole processes; it queues their PCBs. A PCB is the small record that holds the process state, the program counter, the register values and the memory limits. Each PCB has a next pointer, so a queue is a linked list of PCBs with a header that points to the front and the rear. Adding a process to a queue or removing it changes only a few pointers.

There are three kinds of queue, each named by the reason the process is waiting there.

  • Job queue: every process in the system, including those still on disk waiting to be allowed into memory.
  • Ready queue: PCBs of processes that are in memory and ready to run, lacking only the CPU. The CPU scheduler reads this queue.
  • Device queue: processes waiting for one particular device. Each device has its own queue, so a process blocked on a disk read sits in the disk queue, not in the ready queue.

A process migrates between these queues all its life. It is admitted from the job queue into the ready queue, dispatched to the CPU, preempted back to ready, sent to a device queue when it asks for I/O, brought back to ready when the I/O finishes, and removed when it exits. The figure traces these paths.

Three schedulers and one dispatcher

The long-term scheduler, or job scheduler, picks a process from the job queue and admits it into memory. It therefore sets the degree of multiprogramming — how many processes are in memory at once. It should admit a mix of I/O-bound and CPU-bound processes so the CPU and the devices stay busy together. It runs only when a process is admitted, perhaps once every few seconds, so it can afford to be slow and clever.

The short-term scheduler, or CPU scheduler, picks the next PCB from the ready queue. It runs at every switch, perhaps every few milliseconds, so it must be fast. If it took 10 ms to choose a process for a 10 ms time slice, half the CPU would vanish into choosing. A good implementation decides in tens of nanoseconds.

The medium-term scheduler removes a process from memory and puts it on disk to reduce load, bringing it back later. That is swapping, covered in Unit 4.

The dispatcher is the code that actually performs the switch: it loads the chosen PCB's registers, returns to user mode and jumps to the saved program counter. The time taken to stop one process and start another is the dispatch latency. Keep the roles apart: the scheduler chooses, the dispatcher performs.

What a context switch saves and restores

  1. An interrupt or trap hands control to the kernel, and the running process's registers and program counter are saved into its PCB.
  2. Its state field is changed, for example running to ready, or running to waiting.
  3. The scheduler picks the next PCB from the ready queue.
  4. Memory-management data is updated: the page-table base register, the memory limits, and cached address translations. If the address space changes, old translations must be flushed, a hidden extra cost.
  5. The chosen PCB's registers and program counter are restored, its state becomes running, and the CPU returns to user mode at that program counter.

The switched-out process later resumes at the exact instruction where it stopped, with the same register values. That is the whole purpose. But not one user instruction runs during the switch, so the time is pure overhead — cost with no output. On a general-purpose CPU a switch costs a few microseconds. The cost depends on the hardware: how many registers exist, how fast memory is, and whether the CPU has several register banks, in which case a switch is little more than changing a pointer.

Worked example

Question. A context switch saves 8 registers and restores 8 registers. Each register transfer takes 5 ns. The scheduler itself needs 200 ns to choose the next process. The time slice is 5 ms. Find the time spent on one context switch and its share of the time slice, as a percentage.

  1. Saving the old process: 8 registers × 5 ns = 40 ns.
  2. Restoring the new process: 8 registers × 5 ns = 40 ns.
  3. Scheduler cost: 200 ns — this is part of dispatch latency, so it is counted.
  4. Total cost of one switch = 40 ns + 40 ns + 200 ns = 280 ns.
  5. Convert the slice to the same unit: 5 ms = 5 × 10⁻³ s = 5,000,000 ns.
  6. Share of the slice = 280 ns ÷ 5,000,000 ns = 0.000056.
  7. As a percentage: 0.000056 × 100 = 0.0056%.

Answer. One context switch costs 280 ns, which is 0.0056% of a 5 ms time slice.

Exam traps

  • Adding the context-switch time to the burst time of the process. The burst is user work; the switch is overhead, measured separately.
  • Assuming the switch is instant. Every switch costs register saves, restores and scheduler time, and the cost is real CPU time taken from user processes.
  • Saying the dispatcher chooses the next process. The scheduler chooses; the dispatcher only performs the switch.
  • Mixing up the schedulers: the long-term scheduler picks from the job queue and admits processes into memory; the short-term scheduler picks from the ready queue.
  • Forgetting unit conversion — mixing nanoseconds and milliseconds gives an answer that is wrong by a factor of a million.

Analyze Why can a context switch cost more than the register saves and restores alone? 4 marks

Because the memory-management data must also change. A new address space means a new page-table base register, and cached address translations in the TLB may have to be flushed or tagged. Analyze Two machines switch between the same two processes. Machine A has 8 registers and no cache of translations; machine B has 64 registers and a large TLB. Which loses more time per switch, and what does this tell you about dispatch latency? 5 marks

Machine B saves and restores 64 registers instead of 8, so its save and restore time is eight times larger, and a large TLB may need more flushing. Unless B's hardware gives extra register banks or tagged TLB entries, B's switch is more expensive. Dispatch latency is therefore a property of the hardware and the memory system, not a fixed constant of the OS.

Beyond the syllabus

Not for the exam. Hardware has been fighting switch cost for decades. Some CPUs provide several register banks so that a switch changes a pointer instead of copying registers. After the Meltdown disclosure in 2018, many kernels separated kernel and user page tables, which made each entry to and exit from the kernel more expensive — a security feature paid for in dispatch latency. In user space, coroutines and green threads avoid the kernel switch entirely by switching stacks inside one process. Search for tagged TLBs, kernel page-table isolation, and the switch_to routine in the Linux kernel to go further.

2.3 Operations on processes: creation and termination

Every running process in an operating system comes from another process. A parent asks the kernel to make a copy with fork(), the child may load a new program with exec, and the parent later collects the child's result with wait(). The child ends with exit(). This chain is how a shell starts ls, how a web server starts a worker, and how your phone starts an app. This chapter shows each call, the process tree it builds, and the two leftovers: zombies and orphans.

You need 2.1 on process states and the PCB, and Unit 1 on system calls.

Creation: fork() makes a copy

fork() is a system call that creates a new process. The caller is the parent and the new process is the child. The child gets a new process identifier, or pid. A pid is a positive integer. The child is a copy of the parent: same code, same data values, same open files, and the same program counter at the instruction just after fork(). The kernel also makes a new process control block for the child (see 2.1).

fork() returns twice: once in the parent and once in the child. In the child the return value is 0. In the parent the return value is the child's pid. If the kernel cannot create the child, fork() returns −1 in the parent and no child exists. Programs branch on this value to give the parent and child different work.

  1. Parent calls fork().
  2. Kernel allocates a PCB and a copy of the address space for the child.
  3. Both processes continue after the same fork() call.
  4. The child sees return value 0; the parent sees the child's pid.

The child does not start again from main(). It continues after the call. The address spaces are separate, so a variable changed in the child is not changed in the parent. Modern systems copy pages only when one side writes to them; this is copy-on-write (see Unit 4, copy-on-write).

exec: replace the program, keep the pid

After a fork, the child often needs to run a different program. The exec family of calls replaces the process image: code, data, heap and stack. The pid does not change. The PCB stays the same. Open files usually stay open unless they were marked close-on-exec. If exec succeeds, it does not return. It starts the new program at its entry point. If it fails, it returns −1 and the old program continues.

Common forms are execl, execv, execve, execlp and execvp. They differ in how the argument list and environment are passed, and whether the shell path is searched. execve is the real system call; the others are library wrappers. A shell child might call execlp("ls", "ls", NULL). If that fails, the child calls _exit(1).

exit() is the reverse of creation. A process calls exit(status) to end. The status is an integer that the parent can read. The OS closes the process's files and frees its memory, but it keeps the PCB and the exit status until the parent collects them. exit() does not return. A process can also be ended by a signal from the kernel or another process.

wait, the process tree, zombies and orphans

A parent collects a child's end with wait() or waitpid(). wait(&status) blocks until any one child ends. waitpid(pid, &status, options) waits for a chosen child. Both return the pid of the child that ended and store its status. Macros such as WIFEXITED and WEXITSTATUS read that status.

When a child ends before its parent waits, it becomes a zombie. A zombie has finished running. Its memory and files are gone. Its PCB, pid and exit status remain so the parent can collect them. The parent's wait() removes the zombie. If the parent never waits, zombies can fill the pid table.

An orphan is different. An orphan is a running child whose parent has died. On Linux, init or systemd, usually pid 1, adopts the orphan and later reaps it. Init or systemd is at the root of the user process tree. A login shell, a service and a desktop app all descend from it.

Cascading termination is a policy in which the OS ends all descendants when a parent ends. Some systems use it for a job or a session. Linux does not kill a child just because its parent exits; the child becomes an orphan. A shell can still ask for a signal when its parent dies, but that is an extra feature.

The standard shell example ties the calls together. To run ls, the shell calls fork(). The child calls exec to load ls. The parent calls wait() and blocks. ls runs, calls exit(0), and the shell reaps it, then prints the next prompt.

Thread creation is a different operation: it makes a thread inside the same process, not a new process (see 2.5).

Worked example

Question. A program starts as one process and runs: fork(); fork(); fork();. How many processes exist in total, and how many are new children? Then the program is changed to: pid = fork(); if (pid == 0) fork();. How many processes exist now? Assume every fork succeeds.

  1. Each unconditional fork() doubles the number of processes. Start with 1 process.
  2. After the first fork: 2 processes in total, which is 1 new child.
  3. After the second fork: 2 × 2 = 4 processes in total, which is 3 new children.
  4. After the third fork: 4 × 2 = 8 processes in total, which is 7 new children.
  5. In the second program, the first fork makes parent P and child C1. P gets a positive pid and skips the if. C1 gets 0 and calls the second fork, making C2. P does not call the second fork.
  6. Total for the second program: P, C1 and C2 = 3 processes.

Answer. The first code creates 8 processes in total, 7 of them new children. The second code creates 3 processes in total.

Exam traps

  • Do not assume the parent or the child runs first after fork(). Both are ready, and the scheduler chooses.
  • In the child, fork() returns 0; in the parent, it returns the child's pid. Reversing these is the most common fork mistake.
  • A zombie has exited and is waiting to be reaped. An orphan is still running after its parent died. They are not the same.
  • exec does not create a new process and does not change the pid. It only replaces the program inside the existing process.
  • exit() frees memory and files but not the PCB and exit status. wait() removes those. If the parent never waits, the zombie remains.

2.4 Inter-process communication: shared memory, messages, pipes

Cooperating processes must exchange data, and the operating system offers three common ways: shared memory, message passing and pipes. Shared memory is fast but leaves safety to the processes. Message passing is slower but the kernel controls every copy. Pipes are byte streams with a kernel buffer that blocks a full writer or an empty reader. You meet these ideas in a shell pipeline, a database page cache, and a phone app talking to a service.

You need: 2.1 for what a process is, and 2.3 for fork, exec and wait.

Why processes cooperate, and shared memory

An independent process cannot affect another. A cooperating process shares data or work with another, so it needs a channel. Three common channels are shared memory, message passing and pipes.

Shared memory is the fastest. The OS takes one physical region of memory and maps it into the address space of both processes. Each process calls a system call to attach the region; in POSIX this is shmat. After that, a write by one process is visible to the other without any kernel copy. The catch: the kernel sets up the mapping and then steps away. Nothing stops both processes writing the same byte at the same time. The processes must guard the region with their own locks, semaphores or monitors. See Unit 3 for those tools.

  1. One process creates the region and gives it a name or key.
  2. Both processes attach the region to their address space.
  3. Both read and write it like ordinary memory.
  4. They detach when done; the creator removes the region.

Use it for large data: a video frame, a database page cache, or a game world shared by two processes.

Message passing: names, blocking and buffers

Message passing avoids shared bytes. Processes call send(destination, message) and receive(source, message). The kernel copies the message between address spaces. This is slower than shared memory but safer: no process can touch another's memory.

Naming. In direct communication the sender names the receiver process, for example send(P2, msg). In indirect communication the sender names a mailbox or port, for example send(mailbox_A, msg); any process that owns or shares the mailbox can receive. Direct links pair exactly two processes; indirect links let many senders and receivers meet at one mailbox.

Timing. A blocking send waits until the message is copied or received. A blocking receive waits until a message arrives. A non-blocking send returns at once, and a non-blocking receive returns either a message or nothing yet. Blocking is also called synchronous; non-blocking is asynchronous.

Buffering. The queue between sender and receiver can hold messages. Zero capacity means no queue: the sender must wait for the receiver, a rendezvous. Bounded capacity means a fixed number n of messages; the sender waits only when the queue is full. Unbounded capacity means the sender never waits for space. Message passing suits small control messages and machines that do not share memory.

Pipes: unnamed and named

A pipe is a one-way byte stream held in a kernel buffer. The classic unnamed pipe is made by pipe(fd); fd[0] is the read end and fd[1] the write end. It is half-duplex: bytes flow one way in one pipe. For two-way talk, make two pipes.

An unnamed pipe exists only between related processes, usually a parent and a child made by fork. The child inherits the file descriptors. It has no name in the file system, so an unrelated process cannot open it. A fixed kernel buffer sits between writer and reader. When the buffer is full the writer blocks; when it is empty the reader blocks. That blocking is what makes a pipe a synchronising channel.

A named pipe, or FIFO, has a path name in the file system. Unrelated processes open that name and exchange bytes. It is still a byte stream, not a message queue: the reader must parse boundaries itself.

Sockets generalise pipes across machines; client-server systems use them. See Unit 6 for sockets, remote procedure calls and distributed IPC.

Worked example

Question. An unnamed pipe has a 65,536-byte kernel buffer and the reader is sleeping. The writer sends 1,000-byte writes. After how many writes does the writer block? What happens on write number 66? After the reader reads 4,000 bytes, how many bytes are free?

  1. Buffer capacity = 65,536 B; each write = 1,000 B.
  2. Writes that fit = floor(65,536 ÷ 1,000) = 65. Bytes used = 65 × 1,000 = 65,000 B.
  3. Free space before write 66 = 65,536 − 65,000 = 536 B.
  4. Write 66 needs 1,000 B. 1,000 > 536, so it does not fit. The writer blocks and is queued on the pipe.
  5. The reader reads 4,000 B. Free space = 536 + 4,000 = 4,536 B.
  6. 4,536 ≥ 1,000, so the blocked writer is woken and its 1,000 bytes can be copied.

Answer. The writer completes 65 writes, blocks on write 66, and after a 4,000-byte read 4,536 bytes are free.

  • Forgetting that an unnamed pipe cannot connect two unrelated processes. A named pipe can.
  • Treating a non-blocking send as a lost message. It returns at once, but the message may still be queued.
  • Thinking one unnamed pipe gives two-way talk. It is half-duplex; use two pipes.
  • Confusing zero capacity buffering with unbounded capacity. Zero capacity forces a rendezvous; the sender waits for the receiver.

2.5 Threads, multicore programming and multithreading models

A thread is the unit of CPU use inside a process. It has its own program counter, registers and stack, but shares the process's code, data and open files. Threads exist because creating a process is heavy, and because phones and servers have several cores. A music app can keep the screen alive while decoding a song; a web server can handle many requests in one process. This chapter shows what threads share, how user and kernel threads differ, the multithreading models, and why more threads do not always mean more speed.

You need: Chapter 2.1 for the process and its PCB.

What a thread owns and shares

A process is a program in execution. A thread is the smallest unit inside that process which the CPU can schedule. Each thread keeps a thread id, a program counter, a register set and a stack. The program counter holds the address of the next instruction. The register set holds values such as loop counters and function arguments. The stack holds local variables and return addresses. These items are private because two threads may be at different points in the same code.

Everything else belongs to the process. Code, global data, the heap, open files and signal handlers are shared. A file opened by one thread can be read by another. A global variable changed by one thread is seen by another, so Unit 3 must handle locking.

  • Responsiveness: one thread can keep the interface alive while another waits for a slow disk or network.
  • Resource sharing: threads use the same code, data and files without extra shared-memory setup.
  • Economy: creating a thread and switching between threads costs less than doing the same for processes.
  • Scalability: threads can use several cores at once, if the OS supports kernel-level threads.

A process has its own address space; threads share one. Creating a thread is cheaper because no new address space is built. Threads communicate through shared variables; processes need shared memory or messages, as in Chapter 2.4. A bad write by one thread can crash the whole process.

User threads, kernel threads and three models

A user-level thread is created and managed by a library in user space. The kernel sees only the process. A kernel-level thread is created and managed by the OS, and the kernel schedules it directly.

  • Many-to-one: many user threads map to one kernel thread. Switching is fast because no kernel call is needed. If one thread makes a blocking system call, the kernel blocks the whole process, so all threads stall. All threads run on one kernel thread, so there is no true parallelism on multiple cores.
  • One-to-one: each user thread maps to one kernel thread. Linux and Windows use this. It gives true parallelism, and one blocking call blocks only its thread. Creating many threads costs kernel resources.
  • Many-to-many: m user threads map to n kernel threads, with m ≥ n. The library multiplexes threads. It avoids both limits but is complex. The two-level model also allows binding a chosen user thread to a kernel thread.

The model decides whether a blocking call stalls one thread or all threads, and whether two threads can run at the same instant on two cores.

Multicore programming and Amdahl's law

Concurrency means several threads make progress over the same period, even by time slicing on one core. Parallelism means two threads execute at the same instant on two cores. Two threads on one core are concurrent, not parallel. Data parallelism divides the same operation over different data: four threads each filter a quarter of an image. Task parallelism gives different tasks to different threads: one thread decodes audio, another draws the screen.

S(N) = 1 ÷ (s + (1 − s) ÷ N)

S(N) is the speedup with N cores; s is the serial fraction, with 0 ≤ s ≤ 1; N is the number of cores. As N → ∞, S → 1 ÷ s.

A thread library gives calls to create and join threads. Common libraries are POSIX pthreads, Windows threads and Java threads. Which thread the scheduler picks is Chapter 2.8. More threads than cores does not increase speed.

Worked example

Question. An image-filter app spends 20% of its single-core run time in code that cannot be parallelised. Find the speedup with 4 cores, and the best possible speedup with any number of cores.

  1. The serial fraction is s = 20% = 0.20. The parallel fraction is 1 − s = 0.80.
  2. For N = 4 cores, use S(N) = 1 ÷ (s + (1 − s) ÷ N).
  3. Compute (1 − s) ÷ N = 0.80 ÷ 4 = 0.20.
  4. Add s: 0.20 + 0.20 = 0.40.
  5. S(4) = 1 ÷ 0.40 = 2.5. The app runs at most 2.5 times faster on 4 cores.
  6. As N → ∞, (1 − s) ÷ N → 0, so S → 1 ÷ s = 1 ÷ 0.20 = 5. The best possible speedup is 5 times.

Answer. The 4-core speedup is 2.5 times, and the best possible speedup with any number of cores is 5 times.

Exam traps

  • A thread does not have its own address space. Threads in one process share code, data, heap and open files; only registers, program counter, stack and thread id are private.
  • Two threads on one core are concurrent by time slicing, not parallel. Parallelism needs at least two cores at the same instant.
  • In many-to-one, one blocking system call stalls every thread in the process, and there is no true parallelism.
  • User-level threads are invisible to the kernel; kernel-level threads are scheduled by the kernel. Do not say the kernel schedules user threads directly in many-to-one.
  • Amdahl's law caps speedup at 1 ÷ s, where s is the serial fraction. More cores cannot remove serial work.

2.6 Scheduling criteria; preemptive and non-preemptive scheduling

Scheduling is the choice of which ready process gets the CPU next. One CPU, many candidates, so the OS must pick, and pick again within milliseconds. Criteria are the numbers that score a choice: how busy the CPU stays, how many jobs finish per second, and how long each process waits before it starts and before it ends. Preemption decides whether a running process can be pushed off the CPU before it finishes.

You need: Chapter 2.2 for the dispatcher, ready queue and context switch, and Unit 1, OS operations: dual mode and timers, for the timer interrupt that makes preemption possible.

CPU bursts and the four decision points

A process alternates between a CPU burst, where it computes, and an I/O burst, where it waits for a disk read, a keystroke or a network reply. A program that reads a file and prints it makes several short CPU bursts with I/O waits in between.

Draw a histogram of burst lengths: burst length in milliseconds on the x-axis, number of bursts of that length on the y-axis. Most real systems give a curve tall at the left with a long tail to the right — many very short bursts, a few very long ones. That shape is why order matters: letting a short burst through early clears a whole process out of the system.

The scheduler can act only at four moments, called decision points.

  1. Running → waiting: the process asks for I/O or waits for another process.
  2. Running → ready: the process is interrupted, usually by the timer, and returns to the ready queue.
  3. Waiting → ready: an I/O operation completes and the process can run again.
  4. Running → terminated: the process finishes.

Points 1 and 4 are forced, because the process caused them itself. Points 2 and 3 are choices. A scheme is preemptive if it also switches at points 2 and 3, that is, if the OS can take the CPU from a process that could still run. It is non-preemptive if it switches only at points 1 and 4: once on the CPU, a process keeps it until it blocks or ends. Non-preemptive scheduling is also called cooperative.

Preemptive and non-preemptive scheduling

Preemption costs something. Every switch is a context switch: the kernel saves the registers and state of the old process and restores the new one. Nothing useful runs meanwhile, so dispatch latency — the delay between stopping one process and starting the next — is a real loss. That is why most kernels allow preemption in user mode but restrict it inside kernel code.

The larger cost is correctness. Suppose the kernel is halfway through updating the ready queue and a timer interrupt preempts it. The next process can find the list half-changed. In a non-preemptive kernel this cannot happen, because kernel code runs to completion. A preemptive kernel must protect every shared kernel structure with locks or by disabling interrupts around short critical sections; see Unit 3, Process Synchronization and Deadlocks.

So why preempt at all? Response. Without preemption a long compute job can hold the CPU for seconds while a user types into an editor waiting to echo the keystroke. With preemption the timer interrupt arrives after a fixed quantum, say 10 ms, and the editor gets its turn. Preemption also lets an urgent new job cut in at once, which interactive and real-time systems need.

Some systems preempt only at point 2, not point 3, so a job waking from I/O waits for the next tick. Any switching beyond points 1 and 4 is still preemption.

The scheduling criteria and their formulas

Criteria compare two schedules for the same set of processes. Measure all times from the same clock, in milliseconds.

CPU utilization = (busy time ÷ total time) × 100

busy time is the time the CPU spent running processes, total time is the length of the interval observed, and the answer is a percentage. Idle time lowers it.

Throughput = number of processes completed ÷ length of the interval

the answer is in processes per second (or per millisecond). It counts finished processes, not started ones.

Turnaround time = completion time − arrival time

for one process: from the moment it enters the system to the moment it finishes. It includes waiting, CPU time and all I/O.

Waiting time = turnaround time − burst time − I/O time

the time spent in the ready queue. With no I/O in the process, I/O time = 0, so waiting = turnaround − burst. With I/O, subtract it too, or simply add up the intervals the process actually spent in the ready queue. A process preempted twice adds both waits.

Response time = time of first run on the CPU − arrival time

how long the process waited before it started at all. Later runs do not count.

Worked example

Question. P1 arrives at 0 ms with a CPU burst of 8 ms. P2 arrives at 1 ms with a CPU burst of 4 ms. Switch time is zero. Schedule them under (a) non-preemptive FCFS and (b) preemptive shortest-remaining-time-first. Find average waiting, response and turnaround for each.

  1. (a) At time 0 only P1 is present, and the scheme is non-preemptive, so P1 runs 0–8 ms. P2 waits and runs 8–12 ms. Completion: P1 = 8 ms, P2 = 12 ms.
  2. (a) Turnaround: P1 = 8 − 0 = 8 ms; P2 = 12 − 1 = 11 ms. Average = (8 + 11) ÷ 2 = 9.5 ms.
  3. (a) Waiting = turnaround − burst: P1 = 8 − 8 = 0 ms; P2 = 11 − 4 = 7 ms. Average = 3.5 ms.
  4. (a) Response: P1 first ran at 0 ms → 0 ms; P2 first ran at 8 ms → 8 − 1 = 7 ms. Average = 3.5 ms.
  5. (b) At 1 ms P2 arrives with 4 ms of burst left while P1 has 7 ms left. P2 is shorter, so it preempts P1 and runs 1–5 ms. P1 resumes at 5 ms and runs to 12 ms.
  6. (b) Turnaround: P1 = 12 − 0 = 12 ms; P2 = 5 − 1 = 4 ms. Average = 8 ms.
  7. (b) Waiting: P1 = 12 − 8 = 4 ms; P2 = 4 − 4 = 0 ms. Average = 2 ms.
  8. (b) Response: P1 = 0 ms; P2 = 1 − 1 = 0 ms. Average = 0 ms.

Answer. Non-preemptive: average waiting 3.5 ms, response 3.5 ms, turnaround 9.5 ms. Preemptive SRTF: average waiting 2 ms, response 0 ms, turnaround 8 ms.

  • Ignoring arrival time and assuming every process starts at 0 ms.
  • Treating response time as the last run on the CPU. It is the first run only.
  • Calling a scheme preemptive because it has priorities. If it never takes the CPU from a running process, it is non-preemptive.
  • Leaving out dispatch latency. With zero switch time preemption looks free; each real switch adds to waiting and turnaround.

2.7 Scheduling algorithms: FCFS, SJF, priority, round robin

A scheduling algorithm chooses which ready process gets the CPU next. The four classic rules trade simplicity against average waiting time, fairness and starvation. FCFS is a plain queue. SJF gives the smallest average wait when all bursts are known. Priority scheduling ranks processes by importance. Round robin gives each process a short turn so nobody waits long. Exams ask you to draw the Gantt chart and compute average waiting time.

You need Chapter 2.6 for scheduling criteria and the preemptive/non-preemptive split, and Chapter 2.1 for the PCB fields a scheduler reads.

First come, first served (FCFS)

FCFS picks the process that reached the ready queue earliest. The ready queue is FIFO: the scheduler takes the head and runs it to completion. It is non-preemptive.

Numbers come from the Gantt chart, the bar chart of who holds the CPU from which time to which time.

W = T − b = C − A − b,   T = C − A = W + b. For a process that runs from first dispatch to completion without preemption, W = S − A.

W is waiting time in ms (total time in the ready queue), T is turnaround time in ms, C is completion time, A is arrival time, b is CPU burst in ms, and S is the time the process first gets the CPU.

Weakness: convoy effect. With bursts 24 ms, 3 ms and 3 ms in that order, the short jobs wait 24 ms and 27 ms, average 17 ms. One long CPU-bound job at the head freezes interactive users. FCFS suits batch systems, not time-sharing.

Shortest job first (SJF) and shortest remaining time first

SJF picks the ready process with the smallest next CPU burst and runs it to completion. SRTF is its preemptive version: it compares the running process's remaining time with each new arrival and switches when the newcomer is shorter.

When all processes arrive together, SJF minimises average waiting time. If two neighbours have bursts a > b, swapping them cuts the b job's wait by a and adds only b to the a job's wait: a net gain. Repeat until bursts are sorted.

τₙ₊₁ = α tₙ + (1 − α) τₙ

τₙ₊₁ is the predicted next burst in ms, tₙ is the last actual burst in ms, τₙ is the prediction made for that burst in ms, and α is a weight with 0 ≤ α ≤ 1.

The next burst is unknown, so predict it by this exponential average. α = 0 ignores recent history; α = 1 uses only the last burst; α = 1/2 is common. Old bursts get weights α(1−α), α(1−α)², and so on, which shrink fast. SJF gives average wait 3 ms in the example against 17 ms for FCFS, but short jobs can starve a long one.

Priority scheduling

Priority scheduling stores a priority number in each PCB and runs the highest-priority ready process. Most textbooks let a small number mean high priority, so priority 1 beats 10. State your convention.

Priorities may be internal, derived by the OS from memory need, time limit or burst ratio, or external, set by user importance or the department paying.

Preemptive priority switches on a higher-priority arrival; non-preemptive priority waits for the running process to finish. Starvation is possible: low-priority work may wait forever. Aging raises a waiting process's priority by one step every so often, so it eventually outranks newcomers.

Priority inversion: a high-priority task waits on a lock held by a low-priority task that a medium-priority task keeps preempting. Unit 3 covers the fix.

Round robin and combined queues

Round robin (RR) is FCFS with a clock. Each process gets a time quantum q, typically 10–100 ms. When q expires, a timer interrupt preempts the process, puts it at the tail of the circular ready queue, and the head runs. RR is always preemptive.

Two extremes. If q exceeds every burst, nothing is preempted and RR behaves like FCFS. If q is tiny, context switches dominate. With q = 1 ms and a switch costing 10 µs, overhead is about 1%. At q = 10 µs with a 10 µs switch, half the CPU time goes into switching; the overhead fraction is s/(q + s), which approaches 1 as q shrinks. Pick q large enough for most bursts and far larger than the switch time.

RR does not minimise average waiting time; it minimises response time and shares the CPU fairly. In the example its average wait is 5.67 ms, between SJF's 3 ms and FCFS's 17 ms.

Real schedulers combine rules. A multilevel queue gives each class its own queue and algorithm: interactive work in RR, batch work in FCFS. A multilevel feedback queue moves CPU-hungry processes to lower queues with longer quanta; aging lifts them back. Linux CFS keeps one run queue and picks the task with the smallest virtual runtime, an idea from fair queueing rather than the queue ladder (Chapter 2.9); the multilevel feedback queue is the Windows-style relative.

2.8 Thread, multiprocessor and real-time scheduling

One process may hold many threads, one machine may hold many cores, and one job may carry a deadline. The scheduler then answers three questions: which thread of the process runs, which CPU runs it, and which deadline is nearest. This chapter links those three levels. You meet them in a phone with eight cores, in a web server with a shared ready queue, and in a car's braking controller where a late answer is a wrong answer.

Thread scheduling: PCS and SCS

A user thread is created by a library. The kernel may not see it. A kernel thread is scheduled by the OS. A light-weight process (LWP) is the kernel-schedulable object that a user thread runs on. The mapping between user threads and LWPs decides who competes with whom.

Contention scope names the competition. In process-contention scope (PCS), user threads compete only inside their own process for one available LWP. The thread library picks the winner. In system-contention scope (SCS), kernel threads compete with all other kernel threads for the CPUs. The kernel picks the winner.

Example: a process has three user threads and two LWPs. Under PCS, the three threads share those two LWPs; the library chooses which two run at a time. Under SCS, the two LWPs sit in the system ready queue beside threads from other processes. A one-to-one model gives every user thread its own LWP, so SCS applies directly. A many-to-one model has many user threads on one LWP, so PCS does the real work.

Multiprocessor scheduling: symmetry, balancing, affinity

Asymmetric multiprocessing (AMP) lets one processor run the scheduler and assign work to the others. The others run only assigned threads. Symmetric multiprocessing (SMP) lets every processor run the scheduler and take work from a shared or per-CPU ready queue. General-purpose systems use SMP because it scales and has no single scheduling bottleneck.

Load balancing keeps CPUs busy. Push migration has a periodic kernel task move threads from an overloaded CPU to a light CPU. Pull migration has an idle CPU take a thread from a busy CPU's queue. Both need a measure of load: run-queue length is simple; CPU utilization is better but harder to read.

Processor affinity keeps a thread on the same CPU when possible. A warm cache and valid translation look-aside buffer entries make the next run faster. Soft affinity lets the scheduler migrate the thread but tries to avoid it. Hard affinity uses a system call to pin the thread to a set of CPUs. Hard affinity also helps when a thread must stay near its data or device.

Real-time CPU scheduling: meet the deadline

A real-time task has a deadline: the time by which its job must finish. A periodic task releases a job every period p and needs execution time t in each period. Its utilization is t/p.

U = Σ tᵢ / pᵢ

U is total CPU utilization, from 0 to 1; tᵢ is the execution time of task i per job, in ms; pᵢ is its period, in ms.

Admission control decides whether to accept a new task. It admits the task only if the set can be scheduled. Rejecting a task is better than missing a brake deadline.

Rate-monotonic scheduling (RMS) gives a static priority: shorter period gets higher priority. It is preemptive. A task set with n tasks is guaranteed schedulable if U ≤ n(2^(1/n) − 1). For n=2 the bound is 0.828; as n grows it tends to 0.693. This is a sufficient test, not a necessary one.

U ≤ n(2^(1/n) − 1)

U is total utilization; n is the number of tasks; the bound is 0.828 for n=2 and tends to 0.693 as n grows.

Earliest-deadline-first (EDF) gives a dynamic priority: the job with the nearest absolute deadline runs first. On one CPU, EDF is optimal for preemptive periodic tasks when each deadline equals its period. RMS is simpler and needs no priority change at run time. The trap is to give the shorter-period task the lower priority. Priority goes to the shorter period.

Worked example

Question. Task T1 has period 4 ms and execution time 1 ms. Task T2 has period 5 ms and execution time 2 ms. Both are released at time 0. Test rate-monotonic schedulability, draw the schedule up to 20 ms, and list completion times against deadlines.

  1. Utilization: U = t1/p1 + t2/p2 = 1/4 + 2/5 = 0.25 + 0.40 = 0.65.
  2. Bound for n=2: 2(√2 − 1) = 2(1.41421356 − 1) = 0.8284271247461903. Since 0.65 ≤ 0.8284271247461903, the RMS test passes.
  3. Priorities: T1 period 4 ms is shorter than T2 period 5 ms, so T1 has higher priority.
  4. Schedule: T1 0–1, T2 1–3; T1 4–5, T2 5–7; T1 8–9; T2 10–12, T1 12–13; idle 13–15; T2 15–16, T1 16–17, T2 17–18.
  5. T1 completions: 1, 5, 9, 13, 17 ms against deadlines 4, 8, 12, 16, 20 ms. T2 completions: 3, 7, 12, 18 ms against deadlines 5, 10, 15, 20 ms. Every completion is before its deadline.
  6. Idle times: 3–4, 7–8, 9–10, 13–15 and 18–20 ms. At 15 ms T2 starts; T1 preempts at 16 ms; T2 resumes at 17 ms and finishes at 18 ms.

Answer. U = 0.65 ≤ 0.8284271247461903, so the set passes the rate-monotonic test; T1 has higher priority and no deadline is missed up to 20 ms.

Exam traps

  • Longer period gets higher rate-monotonic priority. It is the reverse: shorter period, higher priority.
  • The utilization bound is treated as exact. It is sufficient: a set above the bound may still pass a full schedule check.
  • PCS and SCS are swapped. PCS is competition inside one process; SCS is competition among kernel threads for CPUs.
  • Hard and soft affinity are swapped. Soft tries to keep a thread on a CPU; hard pins it.
  • EDF is called static. EDF priority changes as absolute deadlines approach; RMS priority is static.

2.9 Linux schedulers: O(1) and Completely Fair Scheduler

Linux must choose the next task to run thousands of times a second, so it cannot scan a long list each time. The O(1) scheduler answered with 140 priority queues and a bitmap, finding the top task in constant time. The Completely Fair Scheduler (CFS) replaced it with a red-black tree ordered by virtual runtime, so CPU time is shared in proportion to task weights. Both live in the Linux kernel, which means the same ideas run on Android phones and on most internet servers. Only a few universities teach this in detail.

You need: Chapter 2.7 for timeslices and priority, and Chapter 2.5 for what a thread is.

The O(1) scheduler: queues and a bitmap

Every priority is a number from 0 to 139. Priorities 0–99 are reserved for real-time tasks. Priorities 100–139 serve ordinary tasks, one level per nice value: nice −20 maps to 100 and nice 19 maps to 139, so a smaller nice number means more CPU.

The runqueue holds two arrays of 140 lists: the active array and the expired array. Each list queues the tasks at one priority. A 140-bit bitmap beside the active array has bit i set whenever list i is non-empty.

Picking the next task takes three steps:

  1. A waking task is inserted at slot = its priority in the active array.
  2. A find-first-set instruction reads the bitmap and returns the highest non-empty list.
  3. The first task of that list is removed and runs for its timeslice.

After the timeslice the task drops into the expired array with a fresh slice. When the active array empties, the kernel swaps the two pointers. The pick costs the same with 10 tasks or 10,000, and that is what the name O(1) claims.

Why O(1) was replaced, and the CFS idea

O(1) guessed which tasks were interactive by watching how long they slept, and paid a bonus to the ones it judged interactive. The guesses needed hand-tuned constants. A workload that did not fit the guess, such as a long compile or a database, was treated unfairly, and fixed timeslices forced a compromise between latency and throughput.

CFS drops the guess. It records how much CPU each task has received and always runs the task with the least.

That record is the virtual runtime, vruntime: CPU time used, scaled by the task's weight, in nanoseconds. A heavy task (nice −20) has a large weight, so its vruntime grows slowly; a light task's vruntime grows fast. Always running the smallest vruntime hands more real CPU to the heavy task, with no extra rule.

CFS in practice: tree, weight and latency

Runnable tasks sit in a red-black tree keyed by vruntime. The leftmost node holds the smallest vruntime, and that task runs next. The tree stays balanced, so insert, delete and find-leftmost each cost O(log n).

A task waking from sleep is placed at the tree's current minimum vruntime, not at the value it had before sleeping. That charge stops a task from hoarding credit while asleep and then running a long burst.

CFS has no fixed timeslice. A target latency, sched_latency, is the window in which every runnable task should run once. Each task takes a share of it in proportion to weight:

slice_i = sched_latency × w_i ÷ Σ w_j

slice_i is the slice of task i in ms; w_i is its weight, a number fixed by its nice value (nice 0 → 1024, nice 1 → 820); Σ w_j is the sum of weights of all runnable tasks. If too many tasks are runnable, the window is stretched so no slice falls below sched_min_granularity.

Worked example

Question. Two CPU-bound tasks run on one core under CFS. Task A has nice 0 (weight 1024) and task B has nice 1 (weight 820). sched_latency is 24 ms. (a) Find each task's slice. (b) Find each task's vruntime growth in one window, using growth = slice × 1024 ÷ weight. (c) Comment on the result.

  1. Total weight = 1024 + 820 = 1844.
  2. A's slice = 24 ms × 1024 ÷ 1844 = 24576 ÷ 1844 = 13.33 ms.
  3. B's slice = 24 ms × 820 ÷ 1844 = 19680 ÷ 1844 = 10.67 ms. Check: 13.33 + 10.67 = 24 ms.
  4. A's vruntime growth = 13.33 × 1024 ÷ 1024 = 13.33 ms of virtual time.
  5. B's vruntime growth = 10.67 × 1024 ÷ 820 = 13.33 ms of virtual time.
  6. Both grow equally, so the two tasks stay level in the tree. The nicer task gets fewer real milliseconds for the same virtual progress, and neither starves.

Answer. A gets 13.33 ms and B gets 10.67 ms of every 24 ms window, and both virtual runtimes grow by about 13.33 ms, so the CPU is split fairly by weight.

Exam traps

  • CFS does not assign a fixed timeslice; slices are shares of sched_latency and change as runnable tasks come and go.
  • O(1) means the pick of the next task is constant time, not that the whole schedule is; inserting and expiring tasks still cost work.
  • In both schedulers a lower nice value (−20) means higher priority and more CPU; nice 19 is the least favoured. Do not reverse the scale.
  • In CFS a waking task is not credited for time slept; it starts at the tree minimum, so sleeping earns no extra CPU.
  • Priorities 0–99 belong to real-time tasks and 100–139 to normal tasks; a normal task placed in the first band outranks everything.

Check yourself

Remember How many priority levels does the O(1) scheduler have, and how are they divided? 2 marks

140: levels 0–99 for real-time tasks and 100–139 for normal tasks, one level per nice value.

Understand Why does the bitmap make choosing the next task constant time? 3 marks

A find-first-set instruction reads the 140-bit bitmap and returns the highest non-empty queue directly; no list of tasks is scanned.

Apply Two runnable tasks have nice 0 (weight 1024) and nice 5 (weight 335). sched_latency is 20 ms. Find each slice. 4 marks

Total weight = 1359. Nice 0: 20 × 1024 ÷ 1359 = 15.07 ms. Nice 5: 20 × 335 ÷ 1359 = 4.93 ms. Sum 20 ms.

Analyze A task sleeps a long time and then wakes. What does CFS do to its vruntime, and why? 5 marks

It sets vruntime to the tree's minimum, so the sleep earns no credit; otherwise a sleeper could wake and monopolise the CPU for a long burst.

Understand What is the expired array for, and when are the two arrays swapped? 3 marks

It holds tasks that used their slice, each with a fresh slice. The kernel swaps the active and expired pointers when the active array becomes empty.

Analyze Why did the O(1) interactivity bonus cause unfairness? 5 marks

It inferred interactivity from sleep time using tuned constants; tasks whose sleep pattern did not match the constants received a smaller share than their work deserved.

Beyond the syllabus

Not for the exam. The CFS weight table is a geometric series: each nice step multiplies weight by about 1.25, so one step gives roughly 25% more CPU. Linux 6.6 replaced CFS with EEVDF (Earliest Eligible Virtual Deadline First), which keeps the red-black tree but adds a virtual deadline per task so short-running tasks are picked sooner. Search 'sched_prio_to_weight' and 'EEVDF scheduler' to read the kernel source and the design notes.

Takeaways

  1. A process is a program in execution, and the OS represents it by a PCB whose state field moves New → Ready → Running → Waiting → Terminated.
  2. The long-term scheduler admits jobs, the short-term scheduler picks the next ready process on every few milliseconds, and the medium-term scheduler swaps processes to disk.
  3. A context switch is pure overhead: the dispatcher saves one CPU context and restores another, and dispatch latency is time no user process is running.
  4. Processes are created by fork, reshaped by exec, ended by exit, and the parent collects the child's status and pid through wait.
  5. Shared memory is fastest but needs the processes to synchronize themselves; message passing and pipes are slower but the kernel gives control and safety.
  6. A thread is the unit of CPU use; threads of one process share code and data but each has its own program counter, registers and stack.
  7. Scheduling criteria such as CPU utilization, throughput, waiting time and response time conflict, so choosing an algorithm is a trade-off.
  8. FCFS suffers the convoy effect, SJF gives the minimum average waiting time but needs burst lengths and can starve long jobs, and priority scheduling starves unless aged.
  9. Round robin is fair and good for time-sharing, and the time quantum decides whether it drifts towards FCFS (large q) or towards overhead (small q).
  10. Linux moved from the O(1) scheduler's active and expired priority arrays to CFS, which orders tasks in a red-black tree by virtual runtime and gives CPU in proportion to weight.

Glossary

Aging
Gradually raising the priority of a waiting process so that it eventually runs.
Context switch
The act of saving the running process's register state and loading another process's state so the CPU changes owner.
Convoy effect
The delay of many short processes behind one long CPU-bound process, as happens in FCFS.
CPU burst
The stretch of time a process runs on the CPU between two I/O requests.
Degree of multiprogramming
The number of processes currently in memory, controlled by the long-term scheduler.
Dispatch latency
The time between stopping one process and starting another; it is overhead.
Dispatcher
The kernel routine that performs the context switch, switches to user mode and jumps to the chosen process's next instruction.
Job pool
The set of all programs on disk that are waiting to be admitted into memory.
Kernel thread
A thread that the OS itself schedules on the CPU, as opposed to a user thread managed by a library.
Non-preemptive scheduling
Scheduling in which a process keeps the CPU until it blocks or terminates.
Orphan process
A process whose parent has terminated, so it is adopted by init or systemd.
Process
A program in execution, including its code, data, stack, program counter and current register values.
Process control block
The kernel data structure that stores everything the OS needs to know about one process, including its state and saved registers.
Processor affinity
Keeping a thread on the processor it last ran on, to preserve cache contents.
Program counter
The CPU register that holds the address of the next instruction to execute for a process or thread.
Ready queue
The set of processes in the Ready state, waiting for the CPU; it is normally a linked list of PCBs.
Response time
The time from a request's arrival to the first response, measured from arrival to first CPU allocation in scheduling problems.
Starvation
A situation in which a ready process waits indefinitely because other processes always have higher priority.
Throughput
The number of processes completed per unit time.
Time quantum
The maximum time a process may run in one turn under round-robin scheduling, typically a few milliseconds.
Turnaround time
The time from a process's arrival to its completion, equal to waiting time plus CPU time plus I/O time.
Virtual runtime
The weighted amount of CPU time a task has received, used by CFS to choose the least-served task.
Waiting time
The total time a process spends in the ready queue waiting for the CPU.
Zombie process
A process that has terminated but whose PCB remains because the parent has not yet called wait.
