1.1 Role of an OS and computer-system organization

An operating system (OS) is the software that sits between applications and hardware. It turns a bare machine into one that is convenient, efficient and safe to share. It manages the CPU, memory, storage and input/output devices, and gives programs clean abstractions such as processes, files and pipes. Every UPI payment, browser tab and IRCTC booking depends on it. This chapter explains what an OS is for, what resources it manages, and how the hardware-software interface is organised.

The OS as manager and virtual machine

An operating system (OS) is software that controls a computer's hardware and provides services to programs. The kernel is the core part that runs with full privilege. A graphical user interface (GUI) is only one program that asks the kernel for work; the OS is not the GUI.

The OS has two jobs. As a resource manager it decides which job gets the central processing unit (CPU), which memory stays in main memory (RAM), and which disk request goes first. As an abstraction layer it hides hardware details: a program writes bytes to a file instead of programming flash blocks. Some syllabi call this the role of the OS, or describe the OS as a virtual machine that gives each program a clean private computer.

Three goals guide the design. Convenience means a programmer need not know disk geometry to save a photo. Efficiency means the CPU and devices should not sit idle when work waits. Ability to evolve means new hardware can be supported without rewriting every app. Fairness and security cut across all three: no app should starve, and one app must not read another's memory.

Resources and the abstractions they become

The OS manages four broad resources. A process is a running program with its own state. A thread is a unit of execution inside a process, and threads in one process share memory. An address space is the set of memory addresses a process may use. A file is a named sequence of bytes on storage. A pipe is a one-way byte channel between processes. The hardware-software interface and the ISA

The system stack has layers: applications, libraries, the system call interface, the kernel, and hardware. A program calls a library function; the library enters the kernel through a system call; the kernel programs the device. Figure 1.1.1, after Section 1, shows the other job, resource management: four 2.5 GB apps competing for 8 GB of RAM. The instruction set architecture (ISA) is the contract between hardware and software. It defines the instructions a CPU can execute, registers, addressing modes, privilege levels, and how traps and interrupts work. A binary compiled for x86-64 does not run directly on an ARM phone. The OS is compiled for an ISA and for the machine's devices.

Device registers often appear as memory addresses, so the kernel uses load and store instructions to control a device. A device raises an interrupt to force the CPU into kernel code; Chapter 1.2 covers buses and interrupts. The mode bit and timer in Chapter 1.4 protect the boundary. Chapter 1.6 covers system call mechanics. Chapter 1.5 lists the services this stack provides. This hardware-software view is part of computer-system organization.

  • An app is written once per API, not once per disk model.
  • The kernel can change a device driver without changing apps.
  • A fault in one app can be contained by the kernel.

Worked example

Question. A phone has 8 GB RAM and 8 CPU cores. Four apps each ask for 2.5 GB of data to stay in RAM at the same time. (a) Can all four keep their data in RAM at once? (b) What is the shortfall? (c) How many apps can be fully resident if each needs 2.5 GB? (d) State the OS role in deciding.

  1. Total demanded RAM = 4 apps × 2.5 GB/app = 10.0 GB.
  2. Available RAM = 8 GB. Compare: 10.0 GB > 8 GB, so all four cannot keep their data resident at once.
  3. Shortfall = 10.0 GB − 8 GB = 2.0 GB.
  4. With 2.5 GB per app, floor(8 GB ÷ 2.5 GB/app) = floor(3.2) = 3 apps fit fully; they use 3 × 2.5 = 7.5 GB and leave 0.5 GB.
  5. The 8 CPU cores can run four apps in parallel, but cores do not add RAM. The OS must keep 3 resident and swap (move some data to storage) or deny the fourth, or reclaim cached memory; Unit 4 covers virtual memory.
  6. Fairness: the OS uses a policy so one app cannot hold RAM forever. Security: it keeps each app's address space separate.

Answer. No; demand is 10.0 GB against 8 GB, a 2.0 GB shortfall, so at most 3 apps of 2.5 GB can be fully resident, and the OS must swap, deny or reclaim memory for the fourth.

Exam traps

  • The OS is not the GUI and not one app; the kernel is only the core part of the OS.
  • RAM size and CPU core count are different resources. More cores do not add memory; four parallel apps can still run out of RAM.
  • A process is not a thread. A process owns an address space; threads inside it share that space.
  • The ISA is not the OS. Linux and Windows on the same ISA are different operating systems.
  • Virtual memory is not extra RAM. It uses storage to extend the address space, and it can be slower.

1.2 Computer-system architecture and interrupts

A computer is not only a CPU. It is a CPU, memory and device controllers joined by buses, and the operating system must make them cooperate. Devices are much slower than the CPU, so the CPU cannot sit and wait for each one. Interrupts let a device signal the CPU, and DMA lets a device move data without the CPU copying each byte. This chapter shows the hardware path from a key press or disk read to the kernel's interrupt handler. The same mechanism drives network cards, timers, keyboards and system calls on phones and servers.

You need: Chapter 1.1 for the OS as resource manager and abstraction layer.

CPU, memory, buses and controllers

A von Neumann computer keeps instructions and data in the same memory. The CPU fetches an instruction, decodes it, executes it, and writes a result back. This is the stored-program idea. Phones, laptops and servers all follow it.

Inside the CPU, registers hold the few values needed right now. The program counter (PC) holds the address of the next instruction. The instruction register (IR) holds the instruction being decoded. The memory address register (MAR) holds an address, and the memory data register (MDR) holds the value moving to or from memory. General registers hold operands, and the flags register holds condition bits such as zero and carry. The OS saves and restores these registers when it switches activities.

The CPU, memory and device controllers share buses. The address bus carries the address of a memory cell or device register. The data bus carries the value. The control bus carries read, write, interrupt and clock signals. A device controller is the hardware between a device and the bus. A disk controller, keyboard controller and network interface controller each have registers. The CPU writes a command to a control register, reads a status register, and moves data through a data register. On many systems these registers are memory-mapped: they appear at ordinary addresses, so the CPU uses normal load and store instructions.

The OS needs this view of the hardware because a driver is a small program that talks to controller registers. Driver layers are in Unit 5.

Polling, interrupt-driven I/O and DMA

Polling is the simplest way to wait for a device. The CPU reads a status bit in a loop. If the bit is 0, the device is not ready; if it is 1, the CPU reads the data. Polling needs no special hardware and is predictable, but the CPU burns cycles while it waits. A fast CPU polling a slow keyboard wastes almost all its time.

Interrupt-driven I/O reverses the control. The CPU starts the device and continues useful work. When the device is ready, the controller asserts an interrupt request line (IRQ). The CPU finishes the current instruction, saves enough state to return later, and jumps to kernel code. That code runs the interrupt service routine (ISR) for the device. The CPU does not spin, but every event costs an interrupt entry and exit. A device that moves one byte per interrupt can still overload the CPU.

Direct memory access (DMA) removes the CPU from the copying loop. The CPU programs a DMA controller with the source address, destination address and byte count. The DMA controller moves the block between the device and memory while the CPU runs other code. When the block is complete, the DMA controller raises one interrupt. For a 4 KiB disk block, interrupt-driven byte-by-byte I/O may cause 4096 interrupts; DMA causes one. The cost is a small setup time and one interrupt at the end.

Use polling when the wait is very short or the device is checked often. Use interrupts when events are rare and unpredictable. Use DMA for block devices: disks, network cards and graphics engines. In the figure, a 40 ms DMA transfer runs in parallel with 40 ms of application work.

Interrupts, traps and the vector table

An interrupt source is any hardware unit that can raise an interrupt: a keyboard, disk controller, network card, timer or power-failure circuit. A timer interrupt is how the OS takes back the CPU from a runaway program; dual mode and timers are covered in Chapter 1.4.

Several devices can ask at once, so an interrupt controller ranks them by priority. A power-failure interrupt can interrupt a low-priority ISR; a low-priority request waits. Each line has a mask bit; a masked line is ignored until the OS unmasks it. Intel uses an advanced programmable interrupt controller (APIC); ARM uses a generic interrupt controller (GIC) in many systems. The controller collects requests, picks the highest priority, and tells the CPU which number to service.

The CPU needs an address for each interrupt number. A vector table is an array of entry points indexed by interrupt number. Intel x86 uses an interrupt descriptor table (IDT), usually with 256 entries. Each entry gives the code address, privilege level and gate type. ARM uses an exception vector table at a fixed low address, with entries for reset, undefined instruction, supervisor call, prefetch abort, data abort, IRQ and FIQ. Some syllabi call this the interrupt descriptor table; the general name is interrupt vector table.

The interrupt sequence is short and fixed.

  1. Device asserts IRQ.
  2. CPU completes the current instruction; the controller supplies a vector number.
  3. CPU saves PC and flags, switches to kernel mode, and loads the handler address from the vector table.
  4. ISR saves other registers it will use, services the device, and acknowledges it. ISRs should be short so other interrupts are not delayed.
  5. Return-from-interrupt restores PC and flags; the interrupted code continues.

A trap is a software-generated interrupt caused by an instruction. A system call uses a trap instruction to enter the kernel; a divide by zero or a page fault also traps. Traps are synchronous: they happen at a known instruction. Hardware interrupts are asynchronous: they arrive between instructions. A trap is not a process; it is a control transfer. System calls are covered in Chapter 1.6.

Worked example

Question. A disk controller uses DMA to read a block into memory in 40 ms while the CPU runs an application. At t = 0 ms the CPU starts the application and the disk starts DMA. DMA ends and the disk raises one interrupt at t = 40 ms. The CPU spends 5 ms taking the interrupt and 10 ms running the disk ISR. Draw the CPU and disk timeline from 0 to 100 ms. Find total CPU time in the application, total interrupt-handling time, disk DMA time, and the time the application resumes.

  1. Disk DMA runs from 0 ms to 40 ms. It raises one interrupt at 40 ms. Disk DMA time = 40 ms.
  2. CPU runs the application from 0 ms to 40 ms. First application stretch = 40 ms.
  3. CPU takes the interrupt from 40 ms to 45 ms. Interrupt entry time = 5 ms.
  4. CPU runs the disk ISR from 45 ms to 55 ms. ISR time = 10 ms. Interrupt handling total = 5 + 10 = 15 ms.
  5. The application resumes at 40 + 5 + 10 = 55 ms. It runs from 55 ms to 100 ms. Second application stretch = 100 − 55 = 45 ms.
  6. Total application time = 40 + 45 = 85 ms. Check: 85 ms application + 15 ms handling = 100 ms.

Answer. The application runs for 85 ms in total, interrupt handling takes 15 ms, disk DMA lasts 40 ms, and the application resumes at 55 ms.

Exam traps

  • An interrupt is not a process. It has no process control block; the ISR runs in the context of whatever it interrupted.
  • A trap is not the same as a hardware interrupt. A trap is synchronous and caused by an instruction; an interrupt is asynchronous.
  • The IRQ number is not the ISR address. The vector table maps the number to an address.
  • DMA does not remove all CPU work. The CPU still sets up the transfer and handles the final interrupt.
  • Do not say the hardware saves every register. The CPU saves at least PC and flags; the ISR saves the rest it uses.

1.3 History, evolution and types of operating systems

An operating system changes with the machine it runs. Early computers ran one job at a time; batch systems grouped jobs to keep the CPU busy; multiprogramming and time-sharing let many jobs or users share one machine; real-time systems meet deadlines; distributed, embedded, mobile and open-source systems serve new settings. Knowing this history explains why an OS has queues, timers, protected memory and scheduling. It also helps you pick the right type: a ventilator needs real-time behaviour, a ticket server needs time-sharing, and a phone needs a mobile OS.

You need: Chapter 1.1 for what an OS does, and the basic idea of interrupts from Chapter 1.2.

Serial, batch and hardware generations

Early computers had no operating system in the modern sense. A programmer loaded a program by setting switches or plugging cables, and the machine ran one job at a time. This is serial processing: one job owns the central processing unit (CPU) from start to finish. Setup time was large and the CPU sat idle while a human prepared the next job.

Batch processing added a resident monitor, a small program that stayed in memory. The operator collected similar jobs onto a tape or disk, and the monitor loaded each job in turn. Jobs were written in job control language: a few control cards told the monitor what to run, what data to use and what to do at the end. Batch systems raised CPU use and removed the programmer from the machine room, but a user could not interact with a running job. Debugging meant reading a printed listing later.

Hardware generations shaped these designs. First-generation machines used vacuum tubes. Second-generation machines used transistors, third-generation machines used integrated circuits, and fourth-generation machines used very large-scale integration (VLSI). The fourth generation also brought the personal computer (PC). Each step gave more memory and faster input/output (I/O), which made multiprogramming practical. Some syllabi call this the 'history and evolution' part of the course. The main lesson is not the dates: each OS feature appears when hardware makes it affordable.

Multiprogramming, multitasking and time-sharing

Multiprogramming keeps several jobs in main memory at once. When the running job waits for an I/O device, the OS switches the CPU to another ready job. The CPU stays busy and throughput (completed jobs per unit time) rises. The cost is more memory, a job scheduler and careful protection between jobs. See Unit 2, Process Scheduling, for the algorithms.

Time-sharing is multiprogramming built for interaction. The OS gives each user a short turn, called a time slice, then switches. A timer interrupt forces the switch, so one user cannot keep the CPU. Each user sees a slow but responsive machine. Time-sharing needs a timer and dual mode, covered in Chapter 1.4.

Multitasking is time-sharing applied to one user's tasks: a phone plays music while a chat app checks messages. Multiprocessing uses two or more CPUs or cores to run work in parallel. Do not use the words as synonyms. Multiprogramming is about keeping the CPU busy during I/O; multitasking is about one user running several tasks; multiprocessing is about more than one processor.

Real-time, distributed, embedded, mobile and open-source

Real-time systems have a correctness condition beyond the answer: the result must arrive by a deadline. A hard real-time system fails if a deadline is missed; a ventilator or car brake controller is an example. A soft real-time system degrades when late; video streaming or online gaming is an example. Real-time OSes use priority scheduling and bounded interrupt latency, the longest time before the OS answers a device. Scheduling details are in Unit 2.

A distributed OS manages several computers so that they look like one system. Users do not care which machine holds a file or runs a process. It needs distributed synchronization and distributed file systems; see Unit 6. A network OS is weaker: each machine runs its own OS and users know the machine names.

An embedded OS runs inside a device with limited memory, power and display: a washing machine, router or drone controller. It often has real-time parts. A mobile OS is an embedded-style OS with a rich interface. It manages touch input, radio and battery, sandboxes apps and limits background work. Android and iOS are common examples.

Open-source systems publish source code under a licence that allows study, change and redistribution. Linux and Android are open source. Open source is a licensing property, not a scheduling type; an open-source OS can be batch, server, mobile or real-time. Virtualization and cloud computing now put many OS instances on one server; see Chapter 1.9.

Worked example

Question. The timeline gives batch 1950–1965, time-sharing 1965–1985, PC 1980–2000 and mobile 2000–2025. (a) Find the overlap in years between time-sharing and PC systems. (b) Find the full span from the start of batch to the end of mobile. (c) Which of the four types first allowed a user to interact directly with a running job?

  1. Write the intervals as (start, end): time-sharing (1965, 1985), PC (1980, 2000).
  2. Use overlap = max(0, min(end₁, end₂) − max(start₁, start₂)); start₁ and end₁ are the time-sharing interval's start and end, and start₂ and end₂ are the PC interval's. Here min(1985, 2000) = 1985 and max(1965, 1980) = 1980, so overlap = 1985 − 1980 = 5 years.
  3. Full span = end of mobile − start of batch = 2025 − 1950 = 75 years.

Answer. The overlap is 5 years, the full span is 75 years, and time-sharing first gave a user direct interaction with a running job.

Exam traps

  • Batch vs time-sharing: batch runs jobs without interaction; time-sharing gives each user a time slice and a terminal.
  • Multiprogramming keeps several jobs in memory; multitasking is time-sharing on one user's work; multiprocessing uses more than one CPU.
  • Hard real-time is not 'fast'. It is 'meets every deadline'. A fast system can still be soft if it has no deadline guarantee.
  • A distributed OS gives a single-system view. A network OS lets separate machines share resources while each keeps its own OS.
  • Open source is not the same as freeware. Open source gives rights to the source code; freeware may be closed and only free of charge.

1.4 OS operations: dual mode and timers

A running program must not be able to stop interrupts, write page tables, or halt the CPU. The OS uses two hardware features to stop it. A mode bit splits execution into user mode and kernel mode, and a timer interrupt returns control to the kernel after a fixed interval. Together they let an OS share one CPU safely among many programs, on a phone, a laptop or a bank server.

You need: Chapter 1.1 for the OS as resource manager, and Chapter 1.2 for how interrupts enter OS code.

User mode, kernel mode and the mode bit

The CPU has a status bit called the mode bit. It is a hardware bit, not a normal variable that a program can load or store. When the mode bit is 1, the CPU runs in user mode. When it is 0, the CPU runs in kernel mode, also called supervisor mode or privileged mode.

Kernel mode can execute every machine instruction and touch every memory address. User mode is restricted. Instructions that change the machine's protected state are privileged instructions. Examples: disable interrupts, set the timer, change the page-table base register, change the mode bit by a direct write, halt the CPU. In user mode the CPU refuses to execute them and raises an exception. This is not politeness; the hardware enforces it.

The hardware itself sets the mode bit to 0 when it takes a trap; the program cannot do it by writing the bit.

Memory protection works beside the mode bit. The kernel's code and data are marked kernel-only. A user-mode load or store to those addresses faults, even if the instruction is ordinary. So the mode bit and memory-protection bits together keep a buggy or hostile program out of the kernel.

Trap: the controlled door into kernel mode

A user program cannot set the mode bit to 0 by writing it. It must ask the hardware to trap. The usual instruction is a system call instruction; for example, read() in C becomes a trap instruction with a call number and arguments.

  1. User program places the system call number and arguments in registers.
  2. The program executes the trap instruction.
  3. Hardware saves the return address and switches to kernel mode: mode bit 0.
  4. Kernel checks the call number, runs the service, and prepares to return.
  5. Hardware restores the saved state and sets the mode bit back to 1.

A system call is not a separate mode and not a software function call. It is one instruction that enters the kernel through a fixed, hardware-checked entry point. Chapter 1.6 covers the types of calls.

The timer: forcing the CPU back

Mode protects the kernel from user instructions. It does not take the CPU away from a user program that is in an infinite loop. A user-mode loop executes only non-privileged instructions, so it is legal. The timer solves this.

The timer is a hardware counter. The OS sets it before it gives the CPU to a user program; this is a privileged operation. The counter decrements at a fixed clock rate. When it reaches zero, it raises a timer interrupt. An interrupt switches the CPU to kernel mode and jumps to the OS's timer handler, regardless of what user code is running.

The OS uses the timer interrupt to charge CPU time, update clocks and decide whether to reschedule. If it decides to switch, it saves the current process and runs another. See Unit 2 for context switching. The timer interval is a policy choice: too long and a hog keeps the CPU; too short and the OS spends its time handling interrupts.

Neither feature is enough alone. Mode alone cannot preempt a legal user loop. A timer alone cannot stop a user program from disabling the timer or changing the interrupt vector table.

Worked example

Question. A process starts at t = 0 ms in user mode on a single CPU. At t = 5 ms it calls read(); the kernel handles the call for 2 ms. At t = 10 ms a timer interrupt fires. Give the mode bit at t = 0, 5, 7 and 10 ms. State any assumption.

  1. At t = 0 ms the process has just started. No kernel service is active, so it is in user mode with mode bit = 1.
  2. At t = 5 ms the read() call executes its trap instruction. Hardware switches to kernel mode at once, so mode bit = 0.
  3. The kernel service takes 2 ms. It ends at 5 + 2 = 7 ms. The kernel returns to the user program, so mode bit = 1.
  4. From t = 7 ms to t = 10 ms the process runs in user mode, so the bit stays 1 in that interval.
  5. At t = 10 ms the timer interrupt fires. Hardware switches to kernel mode to run the timer handler, so mode bit = 0.
  6. Assumption: the trap is taken at exactly t = 5 ms, the return completes at exactly t = 7 ms, and the timer event is taken at exactly t = 10 ms. Real hardware adds small overheads at each boundary.

Answer. Mode bit: 1 at t = 0 ms, 0 at t = 5 ms, 1 at t = 7 ms, 0 at t = 10 ms.

Exam traps

  • A system call is an instruction that traps; it is not a separate 'system mode' and not just a normal function call.
  • Mode bit 1 means user, 0 means kernel. Writing '1 = kernel' reverses the standard convention.
  • The timer interrupt is asynchronous and can arrive in the middle of a user instruction sequence; it does not need the program's permission.
  • A privileged instruction is not 'any important instruction'. It is one the hardware blocks in user mode. read() is a library routine that puts a call number in registers and executes a trap instruction; the trap instruction itself is not privileged — it is the legal user-mode door into the kernel. What is privileged is everything the kernel does after the trap, such as setting the timer or masking interrupts.
  • If a user program could set the timer or mask interrupts, protection would fail; these are privileged operations.

1.5 Operating-system services

An operating system serves two groups: people and programs. It gives users a way to start work, run programs, read and write files, talk over a network, and see errors. It also manages shared resources, keeps records, and stops one user from damaging another. These offers are called operating-system services. A phone UPI payment uses many of them in one second. The idea matters because services are the visible face of the kernel; system calls, studied next, are how programs ask for them.

You need: Chapter 1.1 for the resource-manager view and Chapter 1.4 for dual mode, because services must cross the user–kernel boundary safely.

User services

An operating system offers services to the person at the keyboard and to the program that is running. The first user service is the user interface (UI). A command-line interface (CLI) takes typed commands; a graphical user interface (GUI) uses windows, icons and touch. A batch interface reads a file of jobs. The UI is how a user asks for other services.

Program execution loads a program into memory, gives it a process, runs it, and ends it cleanly. The OS must also handle abnormal ends, such as a divide by zero or a missing file.

Input/output (I/O) operations let programs read and write devices. A program should not need device-register details. It asks for a read or write, and the OS and device driver do the hardware work.

File-system manipulation creates, deletes, reads, writes and searches files and directories. It also sets permissions: who may read a salary sheet and who may only see a name.

Communication moves data between processes on one computer or across a network. It can use shared memory or message passing; Unit 2 covers those mechanisms.

Error detection notices CPU and memory faults, device failures, and program errors such as bad addresses or illegal instructions. The OS reports the error and often terminates the program.

Both lists together are titled operating-system services. The first six are the user-facing services; resource allocation, accounting, and protection and security are the system-facing ones. The point is that each service hides hardware detail behind a simple request.

System services and system programs

System services keep the whole machine usable, not just one program. Resource allocation decides which process gets the CPU, memory pages, disk bandwidth or a device. When many processes compete, the OS needs policy: first come, priority, fairness. Unit 2 and Unit 4 study CPU and memory allocation.

Accounting records what resources each user or process consumes: CPU seconds, bytes stored, pages printed. A data centre can bill a customer; a university lab can find the heavy user. Accounting is bookkeeping; it does not by itself stop a process.

Protection and security control access. Protection is internal: it stops one process from reading another process's memory or writing a file it does not own. Security defends against outside attackers, such as a stolen password or a network break-in. Chapter 1.4's dual mode is one protection tool; the access matrix and attacks are in Unit 6.

System programs are ready-made programs that sit between raw services and the user. A shell reads commands and starts programs. A file manager shows folders. A compiler turns source into an executable. An editor, backup tool or network utility is also a system program. Most run in user mode and request services through system calls, the subject of Chapter 1.6.

A GUI is a system program too: it draws windows and sends clicks as service requests. The kernel does not need to contain the look of windows; it supplies the services behind them.

Services versus system calls

A service is a promise; a system call is the door used to ask for it. The service 'read a file' is offered by the OS. The program asks with read(), a system call. The call traps into the kernel and the CPU switches to kernel mode first. The kernel then validates the arguments, runs file-system code, and returns to user mode with a byte count or an error number.

This split matters for design. The service can stay the same while the call changes. A phone OS may offer 'send data' to apps, but one phone may implement it with sockets and another with a message bus. The app still asks for a service.

The split also matters for safety. A user program cannot write disk blocks directly. It must ask the service, and the kernel checks permission. That is why dual mode from Chapter 1.4 exists: the mode bit prevents a user program from pretending to be the OS.

Some services are not system calls in every OS. Accounting may be a background daemon reading kernel counters. A GUI may be a server process. Protection may be checked in the kernel for memory, but a file server may check network permissions. Ask 'who provides the service?' and 'what entry does the program use?' separately.

1.6 System calls and their types

A system call is the legal doorway from a user program into the kernel. The program needs a file, a new process, or the time, but those operations touch shared hardware and protected data. Dual mode stops user code from doing them directly. The system call makes the CPU switch to kernel mode at one controlled point, performs the service, and returns. Every program that reads a file, sends a packet, or starts a process uses this path. The C library usually hides the details, but the kernel entry is the real service request.

You need: dual mode and traps from Chapter 1.4, and the service list from Chapter 1.5.

The trap path

A system call is a request to the kernel for a service that user mode cannot perform. The kernel runs it in kernel mode, after a controlled switch. The CPU instruction that causes the switch is a trap or a special syscall instruction. A trap is a synchronous interrupt: it happens because of the current instruction, not because a device raised a line. See Chapter 1.2 for interrupts.

Most programs call a C library wrapper, not the trap directly. For read(fd, buf, 10), the wrapper puts the system call number and the three arguments where the kernel expects them. It executes the trap. The CPU saves the return point, switches to kernel mode, and jumps to the kernel's system call handler. The handler reads the number, finds the table entry, checks the file descriptor and buffer, copies data, and puts a result in a register. It then returns to user mode and to the wrapper. The wrapper returns the result to the program.

Number, arguments and return value

The system call number is a small integer that selects the kernel routine. The kernel indexes a system call table with it. Numbers are specific to the OS and CPU architecture. In the Linux x86-64 convention used in this chapter, read is 0; on another architecture it can differ. A program should call the library, not hard-code a number.

Arguments travel in CPU registers when they fit. In x86-64 Linux, the first three arguments for read go in registers rdi, rsi, and rdx; the number goes in rax. If there are more arguments than registers, the library places them in a block in memory and passes the block's address in a register, or pushes them on the stack. The exact convention is part of the ABI. The kernel copies arguments it needs into kernel space; it does not trust user pointers.

The return value also comes back in a register. For read, a positive value is the number of bytes copied, 0 means end of file, and -1 means an error; the library then sets errno to a code that explains the error. A library function is not always a system call. strlen runs only in user space. printf may buffer and call write later. The API is what you call; the system call is the kernel entry.

The standard types

Calls are grouped by the service they request. The groups overlap, but exam answers use these names. Some syllabi call this group of calls the 'system call interface'.

  • Process control: create, end, wait for, load, and allocate memory to a process. Examples are fork, exec, wait, exit, and kill. See Unit 2 for process creation.
  • File management: create, open, read, write, close, delete, seek, and get or set file attributes. Examples are open, read, write, close, and lseek.
  • Device management: request and release a device, read or write a device, and get or set device attributes. Examples are ioctl and read or write on a device file.
  • Information maintenance: get or set time, date, system data, and process attributes. Examples are getpid, time, uname, and sysinfo.
  • Communication: create and delete a connection, send and receive messages, and share memory. Examples are pipe, shmget, mmap, socket, send, and recv. See Unit 2 for pipes.
  • Protection: get or set permissions and control access. Examples are chmod, chown, umask, and setuid. See Unit 6 for access control.

Worked example

Question. A program calls read(fd, buf, 10). The file has 6 bytes left before end of file. Trace the system call path and give the call's type. State the return value and what the next read returns.

  1. The user program calls the C library read with three arguments: fd is an open file descriptor, buf is the destination address, and 10 is the maximum number of bytes wanted.
  2. The library sets the system call number to 0 for Linux x86-64 read and places the arguments in the expected registers: fd in rdi, buf in rsi, and 10 in rdx.
  3. The library executes the trap. The CPU switches to kernel mode and enters the system call handler.
  4. The kernel uses number 0 to select the read routine, checks the descriptor, and copies bytes from the file to buf. Only 6 bytes are available, so it copies 6, not 10.
  5. The kernel puts 6 in the return register and returns to user mode. The library returns 6 to the program. The file offset has moved 6 bytes, so 4 of the requested 10 bytes were not read.
  6. A later read at the same position finds end of file and returns 0.

Answer. The call returns 6 bytes, leaving 4 of the requested 10 bytes unread, and the next read returns 0; it is a file-management system call.

Exam traps

  • A library function is not automatically a system call. strlen is pure user code; printf may call write once, many times, or not yet because of buffering.
  • read returns the count of bytes copied. 0 means end of file, not 'zero bytes read because the buffer is empty'.
  • Do not treat one system call number as universal. The number for read varies with architecture and OS.
  • A return of -1 is an error, and the real cause is in errno. A positive return is a count, not the data itself.
  • API and system call are different layers. An API can be implemented with no trap, one trap, or several traps.

1.7 OS structures: monolithic, layered, microkernel

Every operating system must decide how much of its code runs in kernel mode. That choice shapes speed, size and reliability. A monolithic kernel keeps almost everything inside one large privileged program. A microkernel keeps only the minimum privileged and pushes other services into user processes. Layered, modular and hybrid designs sit between these two extremes. Real systems such as Linux, Windows and macOS mix these ideas. This chapter explains each structure, the message passing microkernels depend on, and the trade-offs to compare.

You need: Chapter 1.4 for the mode bit, and Chapter 1.5 for the list of services a kernel provides.

Where the code runs: simple and monolithic kernels

The simple structure is the degenerate case — no separation at all. A kernel is the part of the operating system that runs in kernel mode. The mode bit decides which instructions a program may execute, and a user program reaches the kernel only through a system call (Chapter 1.6). Kernel structure answers one question: which services from Chapter 1.5 live inside kernel mode, and which live outside?

In the simple structure, applications touch hardware directly, as early personal-computer systems did. Almost nothing is privileged or checked. The cost is no protection: one program can overwrite another's memory or hang the machine.

A monolithic kernel is one large program. Scheduling, memory management, the file system and every device driver are compiled into a single address space and run in kernel mode. Calls between them are ordinary function calls in that same address space, so they cost almost nothing. The price is reliability and maintenance: any part can corrupt any other, one driver bug can halt the machine, and a kernel of millions of lines is hard to change safely. Traditional UNIX-style kernels are monolithic.

  • Monolithic gain: fast calls, because every service shares one address space and one privilege level.
  • Monolithic cost: no protection between services, so one fault spreads everywhere.
  • Simple structure: gain is direct hardware access; cost is no protection at all.

Layered kernels and the microkernel

A layered kernel is a stack of levels. Level 0 is the hardware, the top level is the user interface, and each level may call only the level directly below it through a fixed interface. Debugging becomes systematic: a failure at level n lies in level n or below. The costs are design effort and speed. Real services, such as a file read needing both a disk driver and a buffer cache, do not split into clean levels, and every level a request crosses adds checking.

A microkernel takes the opposite route. The kernel keeps only what must be privileged: inter-process communication (IPC), low-level CPU scheduling, interrupt handling and basic memory protection. Everything else — file systems, device drivers, network stacks — runs as server processes in user mode, exactly like ordinary programs.

  1. The client program makes a system call asking for a file read.
  2. The microkernel checks the request and places a message in the file server's mailbox.
  3. The scheduler switches the CPU to the file server, which still runs in user mode.
  4. The file server reads the data and sends a reply message back through the kernel.
  5. The kernel copies the reply to the client and marks the client ready to run.

Each request therefore costs four mode switches (client→kernel→server in, server→kernel→client back) and two message copies. Its gain is isolation: a crashed file server owns no kernel memory, so the kernel can kill it and restart it. QNX and the L4 family are built this way.

Modular kernels and hybrid systems

A modular kernel keeps a small core in kernel mode and adds loadable kernel modules: separately compiled pieces, such as the driver for a newly plugged USB device, that can be inserted and removed while the system runs. Module code is linked into kernel mode, so calls stay fast, but a module loads without a reboot or a full rebuild. Linux uses this design. A module is not a server: it is not a separate process and it shares the kernel's address space.

Most commercial systems are hybrids. The Windows NT family has a microkernel-style core with a layered executive above it and user-mode subsystems, yet most services run in kernel mode for speed. macOS puts a Mach microkernel and a BSD kernel into one program. The label matters less than the real question: which code runs privileged, and how does the rest of the system reach it?

1.8 OS design, implementation, building and booting

An operating system is designed, built and started in stages. Design sets goals and separates mechanism (how an action is done) from policy (what action is chosen). Implementation turns those choices into C and assembly code, linked into a kernel image. Building uses compilers, linkers and loaders. Booting uses firmware, a bootloader, the kernel and init or systemd to reach a login prompt. The same chain explains why a binary built for one OS often fails on another. Phones, laptops and servers all follow it.

You need: Chapter 1.2 for boot-time hardware and interrupts and Chapter 1.7 for kernel structures.

Design goals and policy versus mechanism

An OS design starts with goals. User goals are convenience, safety and speed: a phone should unlock quickly and not lose photos. System goals are efficiency, reliability and easy maintenance: the kernel should use few CPU cycles and be fixable. These goals conflict, so designers choose trade-offs.

A key rule is to separate mechanism from policy. A mechanism is the how: the code that can switch the CPU between processes or set a timer interrupt. A policy is the what or when: which process runs next, or how long a time slice lasts. For example, the timer hardware and interrupt handler are mechanism; the scheduler's choice is policy. Separation lets one kernel serve a phone and a server by changing policy data, not rewriting mechanism. It also makes testing easier.

Design shows in structure, covered in Chapter 1.7. Monolithic kernels put most services in kernel mode for speed. Microkernels keep only minimal mechanism in the kernel and move policy and services to user processes for isolation. Each choice changes performance and reliability.

Implementation and building

Implementation is mostly C, with small assembly parts. C gives direct memory access and predictable performance. Assembly handles instructions that C cannot express safely: switching stacks, enabling interrupts, entering kernel mode. The source tree is configured for a target machine by system generation (sysgen): selecting drivers, page size, scheduler options. This produces a kernel image, a file the bootloader can load.

A program becomes runnable in stages. A compiler turns each source file into an object file. A linker joins object files and libraries into one executable, resolving addresses of functions. A loader is OS code that reads the executable, assigns memory, and jumps to its entry point. Static linking copies library code into the file; dynamic linking leaves a reference to a shared library loaded at run time. The OS also exposes an API: functions such as read() and fork() with names and arguments. Behind them are system calls, described in Chapter 1.6. An ABI fixes the binary details: register use, stack layout, system-call numbers.

Applications are OS-specific because they depend on all three: API names, ABI conventions and executable format. A program compiled for Linux uses Linux system-call numbers and ELF; Windows uses different calls and PE. Source code can be recompiled; a binary usually cannot.

Boot sequence

Booting turns a stored kernel image into a running system. The sequence has fixed jobs.

  1. Power on. The CPU starts at a fixed address in firmware.
  2. Firmware runs POST (power-on self-test), checks RAM and devices, then finds a boot device. On modern PCs firmware is UEFI; older PCs used BIOS.
  3. The bootloader is a small program that knows how to read the disk and load the kernel. GRUB is common on PCs. It may show a menu and load an initial RAM disk with drivers.
  4. Kernel load. The bootloader places the kernel image in memory and jumps to its entry point. Early kernel code sets page tables, starts interrupts and initialises drivers. This is the kernel, not the whole OS.
  5. The kernel starts the first user process: traditionally init, today often systemd. It reads configuration and starts services.
  6. Login prompt or graphical session appears.

Times are not fixed; a slow disk extends bootloader and kernel load. The figure shows one measured run: firmware 2 s, bootloader 3 s, kernel 4 s, init 1 s, total 10 s.

Worked example

Question. A PC takes 2 s in firmware, 3 s in the bootloader, 4 s loading the kernel and 1 s in init. What is the total time to the login prompt? Draw the boot sequence.

  1. List the stages and times: firmware = 2 s, bootloader = 3 s, kernel load = 4 s, init = 1 s.
  2. Add them in boot order: 2 s + 3 s = 5 s after firmware; 5 s + 4 s = 9 s; 9 s + 1 s = 10 s.
  3. Draw the flow: Power on → Firmware POST (2 s) → Bootloader (3 s) → Kernel load (4 s) → init or systemd (1 s) → Login prompt (total 10 s).

Answer. The total time to the login prompt is 10 s.

Exam traps

  • The bootloader loads the kernel; it is not the whole OS. Firmware is not the OS kernel.
  • Mechanism is how an action is done; policy is what or when it is chosen. Do not reverse them.
  • Compiling a kernel is not booting. Compiling creates an image; booting loads and starts it.
  • A linker joins object files into an executable; a loader puts that executable into memory. Do not swap the names.
  • An API is source-level names and arguments; an ABI is binary register and stack rules. An application binary depends on the ABI.

1.9 Kernel data structures, virtualization and computing environments

A kernel must store lists of ready processes, free memory frames and open files using simple, fast data structures. Virtualization lets one machine run many isolated operating systems or containers, so the OS and hypervisor must divide CPU, memory and devices safely. Computing environments describe where that OS runs: on a desktop, a phone, a server room, a cloud data centre or a real-time controller. The same ideas of data structures and isolation appear in every environment.

You need: Chapter 1.1 for the OS as resource manager, Chapter 1.4 for dual mode, and Chapter 1.7 for kernel structure.

Kernel data structures

The kernel is a C program with no standard library and little spare memory. It reuses a small set of data structures. Each trades speed, memory and flexibility.

An array stores elements in contiguous memory. Index a[i] takes constant time; the size is fixed at creation. Kernels use arrays for the interrupt vector and per-CPU tables.

A linked list stores each item in a node with a pointer to the next node. Insertion and deletion are cheap after the node is found; search is O(n). Device lists and process lists use linked lists.

A stack is last-in, first-out: push adds at the top, pop removes from the top. A queue is first-in, first-out: enqueue at the tail, dequeue at the head. Function calls use stacks; ready and I/O request queues use queues.

A tree stores items in a hierarchy: each node has one parent and zero or more children. A balanced search tree gives O(log n) search, insert and delete; Linux CFS keeps runnable tasks in a red-black tree. A hash table maps a key to a bucket. Average search is O(1); collisions need chaining or open addressing. Kernel hash tables include the dentry (directory entry) cache, the inode cache and connection-tracking tables; the Linux page cache uses a radix tree (XArray) and routing entries use a trie.

A bitmap is an array of bits. Bit i is 1 if item i is used and 0 if it is free. Bitmaps track free memory frames, free disk blocks and CPU affinity masks. One 4 KB page holds 32768 bits.

Virtualization and containers

Virtualization creates a virtual version of a resource: a CPU, memory, disk or whole machine. A virtual machine (VM) is a software computer with virtual CPUs (vCPUs), guest RAM and virtual devices. The hypervisor or virtual machine monitor (VMM) runs VMs and controls access to real hardware.

A type 1 hypervisor runs directly on hardware, also called bare-metal. It boots first and starts guest operating systems. A type 2 hypervisor runs as an application on a host OS; the host owns hardware and the hypervisor asks it for CPU, memory and I/O. Type 1 is common in data centres; type 2 on laptops for testing.

Each VM runs its own guest kernel. The hypervisor traps privileged instructions and keeps guest memory separate. CPU overcommit is normal: the hypervisor time-slices vCPUs onto physical cores. Memory overcommit is riskier; guest pages must map to host pages, so ballooning, page sharing or swapping may be needed.

CPU ratio = (VMs × vCPUs per VM) ÷ host cores; memory ratio = (VMs × guest RAM per VM) ÷ host RAM

ratio > 1 means oversubscribed; ratio ≤ 1 means the host can meet the committed capacity, ignoring hypervisor overhead.

Containers are lighter. All containers on a host share one kernel. Linux namespaces isolate process IDs, network and mount views; control groups (cgroups) limit CPU and memory. A container starts in milliseconds and uses little memory because it does not boot a guest OS. The trade-off is weaker isolation: a kernel bug can affect every container.

Virtualization is not emulation. Emulation interprets each guest instruction in software for a different instruction set and is much slower. Virtualization runs most guest instructions directly on the CPU.

Computing environments

A computing environment is the hardware, OS, network and users that a program sees. The same kernel code can serve very different environments.

Traditional computing is one user on one machine: a desktop or laptop. Mobile computing adds touch input, ARM processors, battery limits and sensors; mobile OSes sandbox apps and restrict background work.

Client-server computing has a client send a request and a server reply; the web is the common example. Peer-to-peer nodes act as both clients and servers. Cloud computing rents compute, storage and network over the internet; a provider runs many VMs and containers on shared hardware.

Real-time systems must finish work before a deadline. A hard real-time miss can cause failure; a soft real-time miss only degrades quality. A distributed system is many independent computers that appear as one; it needs a network, clocks and failure handling. Distributed synchronization and file systems are in Unit 6.

An open-source OS ships source code under a licence that allows study, change and redistribution. Linux is the standard example. Open source helps debugging and teaching; support depends on the community and vendor.

Worked example

Question. A cloud host has 8 cores and 32 GB RAM. It runs 8 VMs, each with 2 vCPUs and 4 GB RAM. Is the host oversubscribed in CPU or memory? Explain using virtualization.

  1. Total vCPUs = 8 VMs × 2 vCPUs per VM = 16 vCPUs.
  2. CPU ratio = 16 vCPUs ÷ 8 host cores = 2.0. A ratio above 1 means CPU oversubscription; the hypervisor time-slices 16 vCPUs on 8 cores.
  3. Total guest RAM = 8 VMs × 4 GB = 32 GB.
  4. Memory ratio = 32 GB ÷ 32 GB = 1.0. The host is fully committed but not oversubscribed; ratio 1.0 means guest RAM equals host RAM, before hypervisor overhead.
  5. If all VMs touch all pages, the host has no spare frame. Any hypervisor overhead would force swapping or ballooning, so real deployments keep some headroom.

Answer. CPU is oversubscribed by a factor of 2.0; memory is exactly committed at 32 GB and is not oversubscribed.

Exam traps

  • Virtualization is not emulation. Emulation interprets instructions for a different instruction set; virtualization runs most same-ISA instructions directly.
  • Type 1 runs on bare hardware; type 2 runs on a host OS. Swapping these names loses marks.
  • Container = shared host kernel, no guest kernel.
  • CPU overcommit is common and usually safe; memory overcommit can cause host swapping and unpredictable latency. Ratio > 1 means oversubscribed, not broken.
  • A bitmap uses one bit per item, not one byte. 1 byte = 8 bits, so multiply bytes by 8 to get bitmap capacity.

Takeaways

  1. The OS does two jobs at once: it manages resources fairly and safely, and it hides hardware behind simple abstractions like process, file and address space.
  2. A computer system is a CPU, memory and device controllers joined by buses; interrupts and DMA make device handling efficient and give the OS control.
  3. Operating systems grew from batch to multiprogramming to time-sharing, and then split into real-time, mobile, distributed and cloud forms.
  4. Dual mode plus a timer is the basic safety net: user code cannot run privileged instructions, and it cannot keep the CPU forever.
  5. OS services split into those that help the user (interface, program execution, I/O, files, communication, error detection) and those that keep the system efficient (resource allocation, accounting, protection).
  6. A system call is a deliberate trap into the kernel; the standard families are process control, file management, device management, information maintenance, communication and protection.
  7. Kernel structure is a trade-off: a monolithic kernel is fast but large, a microkernel is small and reliable but pays IPC cost, and layers trade performance for clean design.
  8. Building turns source into a kernel image; booting moves firmware to bootloader to kernel to the first user process, and policy/mechanism separation keeps design flexible.
  9. Kernels lean on classic data structures — arrays, lists, queues, trees, hash tables, bitmaps — and the computing environment (traditional, mobile, cloud, container, real-time, distributed) decides what the OS must optimise.

Remember and understand

Understand Explain the two roles of an operating system — resource manager and abstraction layer — using a single example of a program reading a file from disk. 13 marks

Names the resources: CPU time, main memory, disk blocks, device access; Shows the abstraction: open/read/write on a named file, not sectors and tracks; Shows management: the OS schedules the disk request, checks permissions, updates buffers; States that both roles run together: abstraction is what the program sees, resource management is what the OS does underneath.

Understand Describe computer-system organization: CPU, memory, device controllers and buses. Explain how an interrupt lets a device get the CPU's attention. 13 marks

Remember Explain operating-system operations: dual-mode operation, privileged instructions and the use of a timer. Why are all three needed together? 13 marks

Mode bit: 0 kernel, 1 user; privileged instructions only in kernel mode; Examples of privileged instructions: set timer, load page-table base, disable interrupts, halt; System call switches to kernel mode; return switches back; Timer decrements and interrupts, so the OS regains the CPU even if user code loops forever; Names the cases that break without them: user code disabling interrupts, overwriting kernel memory, monopolising the CPU.

Understand List the services an operating system provides and classify them as user-facing services and system-efficiency services. 13 marks

Apply

Apply A user program running in user mode executes a read() call on a file. Trace, step by step, everything that happens from the instruction to the return of data, naming the hardware and OS components involved. 13 marks

Library wrapper places the system-call number and arguments; executes a trap instruction; CPU switches to kernel mode, saves the program counter and registers, indexes the system-call table; Kernel validates the arguments and the file descriptor, checks permissions; Kernel checks its buffer cache; if missing, issues a disk request and blocks the process, scheduling another; Interrupt from the disk completes the transfer; process is made ready; Data is copied to the user buffer, the process returns to user mode with the byte count.

Apply Compare monolithic and microkernel structures by placing the scheduler, file system and a graphics driver either in kernel mode or in user mode. Give the performance and reliability consequences of each placement. 13 marks

Monolithic: all three in kernel mode, direct function calls, fast, but one bug can crash the whole system; Microkernel: scheduler and basic IPC in kernel; file system and driver as user servers, reached by message passing; Reliability gain: a crashed driver can be restarted; smaller trusted code base; Cost: two context switches and message copies per request, so slower; Names hybrid designs (some code in kernel, some outside) and when each choice suits: embedded, real-time, general purpose.

Apply Explain the separation of policy from mechanism in OS design. Show how a scheduling policy or a login policy can be changed without rewriting the mechanism. 13 marks

Mechanism: the code that does the work, e.g. the context switch or the list of ready processes; Policy: the decision rule, e.g. priority values, or which users may log in; Example: the kernel provides priorities as a mechanism; a system administrator or loadable module sets the policy; Benefit: the same kernel serves many workloads and sites; fewer privileged-code changes; Mentions table-driven parameters and loadable kernel modules.

Analyze and evaluate

Evaluate "A microkernel is more reliable but slower than a monolithic kernel." Evaluate this claim, using the cost of inter-process communication and the effect of a faulty device driver. 13 marks

States the mechanism of the cost: trap, message copy, context switch, reply; Quantifies qualitatively: several switches per request versus one function call; fine for control operations, costly for high-rate I/O; Reliability argument: driver crash isolated, restartable, smaller privileged code; Counter-argument: the kernel still needs correct IPC and memory management, so bugs move rather than vanish; IPC paths become critical code; Concludes with conditions: microkernel wins where availability matters, monolithic where throughput per cycle matters.

Analyze A buggy user program tries to write into a kernel address and then runs an infinite loop. Explain every hardware and OS mechanism that should stop it, and what happens if each one is missing. 13 marks

Mode bit prevents privileged instructions; without it the program could disable interrupts or load a page table; Address translation and page-table protection bits stop the write and raise a trap; without it kernel memory is corruptible; The trap switches to kernel mode and the OS terminates the process; The timer interrupts the infinite loop and returns control to the scheduler; without it the machine hangs; Protection checks system-call arguments so the program cannot ask the kernel to write on its behalf; States that all mechanisms together, not any one alone, give protection.

Evaluate Compare batch, time-sharing and real-time operating systems. Which one suits a railway reservation server and which suits an engine-control unit, and what scheduling goal dominates in each case? 13 marks

Batch: jobs queued, no interaction, goal is throughput and low idle time; Time-sharing: many interactive users, goal is fast response and fairness; Real-time: goal is meeting deadlines, hard versus soft; predictability beats average speed; Reservation server: time-sharing, response time and fairness across many users; Engine control: real-time, worst-case latency must be bounded; a late answer is a wrong answer; Notes that general-purpose systems can be tuned but cannot guarantee hard deadlines.

Analyze System calls cost time because the CPU changes mode and saves state. Discuss why designers still insist on a controlled entry into the kernel instead of letting programs touch hardware directly, and how the cost can be reduced. 13 marks

Direct hardware access by any program allows corruption of other processes and of the kernel, and defeats accounting and protection; Controlled entry lets the kernel validate arguments, check permissions and keep a single point of policy; Cost components: mode switch, register save and restore, argument copy, cache effects; Reductions: faster trap instructions, batching, avoiding needless copies with shared memory, vsyscall/vDSO for read-only data like time, fewer but larger calls; Trade-off: too much in user space loses enforcement; too much in kernel loses speed.

Glossary

API
A programming interface, such as the POSIX calls, through which a program requests services, often wrapping system calls.
Bus
A shared set of wires carrying addresses, data and control signals between CPU, memory and controllers.
Container
An isolated group of processes sharing the host kernel, packaged with their own file-system view.
Device controller
Hardware that operates a device and exposes registers and buffers to the CPU over a bus.
Device driver
Kernel code that knows how to program one particular device controller.
Distributed system
A collection of independent computers that appears to its users as one coherent system.
Exception
A CPU-detected error or event, such as a page fault or divide by zero, that transfers control to a handler.
Firmware (BIOS/UEFI)
Programs stored in non-volatile memory that test the hardware and locate a bootloader at power-on.
Hypervisor
Software that presents virtual hardware on which one or more guest operating systems run.
Inter-process communication
Mechanisms such as pipes and shared memory that let processes exchange data.
Kernel
The part of the operating system that always runs in privileged mode and controls the hardware.
Kernel mode
The privileged CPU mode in which the kernel executes all instructions and touches all memory.
Layered structure
An OS design in which each layer uses only the services of the layer below it.
Linker and loader
Tools that combine object files into an executable and place it, with its libraries, into memory to run.
Loadable kernel module
Code that can be added to or removed from a running kernel, commonly used for device drivers.
Mode bit
A hardware bit that records whether the CPU is currently in kernel mode or user mode.
Polling
Repeatedly reading a device status register to see if it needs attention, instead of waiting for an interrupt.
Process
A program in execution, with its own address space, registers and OS state.
Real-time system
A system whose correctness depends on meeting deadlines as well as producing right answers.
Shell
A program that reads user commands and runs them as system programs or system calls.
System call interface
The fixed set of kernel entry points, called by number, that user programs and libraries use.
Throughput
The amount of work completed per unit time, such as processes finished per second.
Trap
A deliberate software interrupt used by a program to enter the kernel, as in a system call.
User mode
A restricted CPU mode in which application code runs and privileged instructions are refused.
