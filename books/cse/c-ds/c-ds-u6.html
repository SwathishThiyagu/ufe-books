6.1 Linear search and binary search

Searching is finding the position of a key (the value you are looking for) inside a collection, or reporting that it is not there. Linear search looks at the elements one by one and works on any array. Binary search looks at the middle, throws away the half that cannot contain the key, and repeats; it needs a sorted array but finds a key among a million elements in about twenty looks. Almost every sort in this unit exists so that binary search becomes possible.

You need: arrays and indexing (Unit 2), and Big-O notation with best, worst and average cases (Unit 1).

Linear (sequential) search

Start at index 0, compare the key with each element, stop at the first match. If the end of the array is reached, the key is absent. Nothing about the order of the data is assumed, so it works on an unsorted array, a linked list, or a file being read from disk.

int linear_search(int a[], int n, int key) {      /* C */
    for (int i = 0; i < n; i++)
        if (a[i] == key) return i;                /* found at i */
    return -1;                                    /* not found */
}

Cost is counted in comparisons. Best case: the key sits at index 0, one comparison, O(1). Worst case: the key is last or absent, n comparisons, O(n). Average case for a key that is present and equally likely to be anywhere: (1 + 2 + … + n)/n = (n + 1)/2 comparisons, still O(n). A small trick, the sentinel search, copies the key into a[n] so the loop needs no bounds test, but the growth rate stays O(n).

Binary search

On a sorted array, one comparison with the middle element answers a stronger question: not "is this the key?" but "which half holds the key?". Keep two indices, low and high, for the part of the array still in play.

  1. Set low = 0 and high = n − 1.
  2. While low ≤ high: compute mid = low + (high − low)/2 (integer division).
  3. If a[mid] equals the key, return mid.
  4. If a[mid] is smaller than the key, the key can only be to the right: set low = mid + 1.
  5. Otherwise the key can only be to the left: set high = mid − 1.
  6. If the loop ends (low has crossed high), the key is absent: return −1.
int binary_search(int a[], int n, int key) {      /* C, iterative */
    int low = 0, high = n - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;         /* avoids overflow of low+high */
        if (a[mid] == key) return mid;
        else if (a[mid] < key) low = mid + 1;
        else high = mid - 1;
    }
    return -1;
}

Every iteration halves the number of candidates: n, n/2, n/4, … , 1. After k halvings only one element is left, so n/2ᵏ = 1 and k = log₂n. The worst case is ⌊log₂n⌋ + 1 comparisons, O(log n); the best case is one comparison when the key sits at the first mid. For n = 1,000,000 that is 20 comparisons where linear search may need 1,000,000. The recursive version has the same cost and the recurrence T(n) = T(n/2) + 1, which solves to O(log n) (Unit 1, recurrences). Nothing is free: the array must already be sorted, and sorting costs at least n log n comparisons (chapter 6.6), so binary search pays off when the same array is searched many times, as in a dictionary or a railway timetable.

Exam traps

  • Binary search on an unsorted array gives a wrong answer, not a slow one. If a question gives unsorted data, sort it first and say so, or use linear search.
  • mid = (low + high)/2 overflows a 32-bit int when low + high exceeds about 2.1 × 10⁹. Write mid = low + (high − low)/2; examiners like this as a two-mark "find the bug" question.
  • The loop condition is low ≤ high, not low < high. With "<", a key sitting in the last single-element range is reported missing.
  • Average case of linear search is (n + 1)/2 for a successful search but n for an unsuccessful one; do not quote n/2 for both.
  • Binary search complexity is O(log n) for the search alone. If the question's data arrives unsorted, the total cost includes sorting, O(n log n).

6.2 Bubble, selection and insertion sort

Sorting puts records in order by a key so that searching, merging and reporting become cheap. The three simple sorts each run n − 1 passes over the array and cost O(n²) in the worst case, but they move data differently: bubble sort swaps neighbours, selection sort picks the minimum and swaps it into place, insertion sort slides each new element into an already sorted prefix. Examiners ask you to hand-trace them pass by pass and to count comparisons and swaps; many syllabi set exactly that as a tutorial.

You need: arrays (Unit 2) and the idea of counting comparisons from chapter 6.1.

Bubble sort: swap neighbours that are out of order

One pass compares a[0] with a[1], a[1] with a[2], … , a[n−2] with a[n−1], swapping any pair where the left is larger. After the pass the largest element has "bubbled" to the end, so the next pass can stop one place earlier. Pass p (counting from 1) makes n − p comparisons; total comparisons = (n−1) + (n−2) + … + 1 = n(n−1)/2, which is O(n²). Swaps range from 0 (already sorted) to n(n−1)/2 (reverse sorted). A swapped flag ends the sort early when a pass makes no swap, so a sorted input costs one pass, O(n).

void bubble_sort(int a[], int n) {                 /* C */
    for (int pass = 1; pass < n; pass++) {
        int swapped = 0;
        for (int j = 0; j < n - pass; j++)
            if (a[j] > a[j+1]) { int t = a[j]; a[j] = a[j+1]; a[j+1] = t; swapped = 1; }
        if (!swapped) break;                        /* already sorted */
    }
}

Selection sort: find the minimum, put it in place

Pass i (from 0) scans a[i..n−1] for the index of the smallest element and swaps it with a[i]. The sorted prefix grows by one each pass. Comparisons are always n(n−1)/2 whatever the input, so best, average and worst are all O(n²); but there are at most n − 1 swaps, the fewest of the three. That matters when a write is far costlier than a read, for example on flash memory. Selection sort is not stable: swapping a[i] with a far-away minimum can jump over an equal key and change the order of equal records.

Insertion sort: slide each element into the sorted prefix

Treat a[0] as a sorted list of one. For i = 1 to n − 1, take key = a[i], shift every larger element of a[0..i−1] one place right, and drop the key into the gap. This is how most people sort playing cards in hand. The number of comparisons equals the number of shifts plus about one per element, so it is adaptive: on a sorted array each key needs one comparison and no shift, O(n); on a reverse-sorted array, i shifts for key i, n(n−1)/2 in total, O(n²). Average is about n²/4 shifts. It is stable (equal keys are never jumped over) and it is the fastest of the three in practice, which is why library sorts switch to insertion sort for ranges of fewer than about 16 elements.

void insertion_sort(int a[], int n) {              /* C */
    for (int i = 1; i < n; i++) {
        int key = a[i], j = i - 1;
        while (j >= 0 && a[j] > key) { a[j+1] = a[j]; j--; }   /* shift right */
        a[j+1] = key;
    }
}

Exam traps

  • "Bubble sort is O(n²) in every case" is wrong once the swapped flag is used: best case becomes O(n). Selection sort is the one that is Θ(n²) always.
  • Counting: pass p of bubble sort makes n − p comparisons, not n − 1. Students who write n − 1 for every pass get 16 instead of 10 for n = 5.
  • Stability: bubble and insertion are stable; plain selection sort is not. If asked for a stable sort with few writes, say insertion sort, not selection.
  • In insertion sort the elements are shifted, not swapped; a shift is one assignment, a swap is three. Count what the question asks for.
  • Selection sort "swaps with itself" when the minimum is already at a[i]; most answer schemes count that as no swap. State your convention.

6.3 Merge sort and quick sort

Both sorts use divide and conquer: split the array, sort the parts recursively, combine. Merge sort does the trivial split (cut in the middle) and the real work in the combine step (merging two sorted runs). Quick sort does the real work in the split (partitioning around a pivot so that the combine step is nothing). Both run in O(n log n) on average, which is as good as any comparison sort can be (chapter 6.6), and both are asked as "trace with a divide-and-conquer diagram".

You need: recursion and solving recurrences (Unit 1), and the simple sorts of chapter 6.2 for comparison.

Merge sort

  1. If the range has one element, it is sorted: return.
  2. Find mid = (low + high)/2; sort a[low..mid] and a[mid+1..high] recursively.
  3. Merge: walk two pointers i and j along the two sorted halves, copy the smaller of a[i] and a[j] into a temporary array, advance that pointer; when one half is exhausted, copy the rest of the other; copy the temporary array back.

Merging two runs whose lengths add to n takes at most n − 1 comparisons and exactly n copies. The recursion has ⌈log₂n⌉ levels, and each level merges n elements in total, so T(n) = 2T(n/2) + cn, which gives Θ(n log n) in the best, average and worst case. The price is O(n) extra space for the temporary array, and the merge is stable because when a[i] equals a[j] the left one is copied first. Merge sort is the natural sort for linked lists (no extra array needed, just pointer rewiring) and for data on disk (chapter 6.6).

void merge(int a[], int lo, int mid, int hi, int tmp[]) {       /* C */
    int i = lo, j = mid + 1, k = lo;
    while (i <= mid && j <= hi) tmp[k++] = (a[i] <= a[j]) ? a[i++] : a[j++];
    while (i <= mid) tmp[k++] = a[i++];
    while (j <= hi)  tmp[k++] = a[j++];
    for (k = lo; k <= hi; k++) a[k] = tmp[k];
}
void merge_sort(int a[], int lo, int hi, int tmp[]) {
    if (lo >= hi) return;
    int mid = lo + (hi - lo) / 2;
    merge_sort(a, lo, mid, tmp); merge_sort(a, mid + 1, hi, tmp);
    merge(a, lo, mid, hi, tmp);
}

Quick sort

Choose a pivot element. Partition the array so that everything ≤ pivot is to its left and everything > pivot to its right; the pivot is now in its final sorted position. Sort the two sides recursively; nothing needs combining. The partition below is Lomuto's, the one in most Indian textbooks and the easiest to trace; the pivot is the last element.

  1. pivot = a[high]; i = low − 1 (i marks the end of the "≤ pivot" zone).
  2. For j from low to high − 1: if a[j] ≤ pivot, increment i and swap a[i] with a[j].
  3. Swap a[i+1] with a[high]. The pivot now sits at p = i + 1; return p.
  4. Recursively quick-sort a[low..p−1] and a[p+1..high].

Hoare's original partition (many exam papers use it) keeps the pivot at the first position and moves two indices inward, swapping out-of-place pairs, until they cross. Either way a partition of n elements costs about n comparisons (exactly n − 1 for Lomuto's) and no extra array.

If the pivot splits the range evenly every time, T(n) = 2T(n/2) + n, Θ(n log n). If the pivot is always the smallest or largest, one side is empty: T(n) = T(n − 1) + n, which sums to n(n+1)/2, Θ(n²). That happens with a last-element pivot on data that is already sorted. The average over random inputs is about 1.39 n log₂n comparisons, still Θ(n log n), and the constant is small because partition touches memory sequentially; that is why quick sort is usually the fastest in-memory sort. Choosing the pivot as the median of a[low], a[mid], a[high], or at random, makes the Θ(n²) case practically impossible. Quick sort is not stable, and uses O(log n) stack space on average, O(n) at worst.

Exam traps

  • Quick sort worst case is Θ(n²), not Θ(n log n). The examiner's favourite question: "when does it happen?" Answer: pivot always extreme, e.g. first or last element on sorted or reverse-sorted input.
  • Merge sort is Θ(n log n) in every case; it is the one to name when the question says "guaranteed".
  • In Lomuto's partition the pivot ends at i + 1, not at i; forgetting the final swap is the usual trace error.
  • Merge sort needs O(n) extra space for arrays, but O(1) extra for linked lists. Quick sort is in place apart from the recursion stack.
  • Do not say "quick sort is stable". It is not; merge sort is.

6.4 Heap sort

Heap sort turns the array itself into a max-heap (a complete binary tree stored in the array where every parent is at least as large as its children), then repeatedly swaps the root, which is the maximum, to the end and shrinks the heap by one. It is the only simple sort that is O(n log n) in the worst case and in place, which is why it is the fallback inside introsort. The whole algorithm is two ideas you already have: the array-as-tree index rule and the sift-down (heapify) operation.

You need: binary heaps and the array representation of a complete binary tree (Unit 4, Binary heaps and priority queues). This chapter only recalls the index rule.

The array is the tree

With 0-based indices, the children of node i are 2i + 1 and 2i + 2, and its parent is ⌊(i − 1)/2⌋. Leaves are the indices from ⌊n/2⌋ to n − 1; they are already one-node heaps. The max-heap property: a[i] ≥ a[2i+1] and a[i] ≥ a[2i+2] wherever those children exist. Nothing is said about left versus right child, so a heap is not a search tree.

Heapify (sift down) and build-heap

  1. heapify(i, n): let largest = i; if the left child 2i+1 < n and a[2i+1] > a[largest], largest = 2i+1; same test for the right child 2i+2.
  2. If largest ≠ i, swap a[i] with a[largest] and heapify(largest, n): the displaced element keeps sinking until both children are smaller or it reaches a leaf.
  3. build-heap: for i from ⌊n/2⌋ − 1 down to 0, call heapify(i, n). Working bottom-up guarantees that when node i is fixed, both its subtrees are already heaps.

heapify costs O(height of i). Summing over all nodes, most of which sit near the bottom with tiny height, gives build-heap a total of O(n), not O(n log n): there are at most n/2ʰ⁺¹ nodes of height h, and Σ h/2ʰ converges to 2.

The sort

  1. build-heap on a[0..n−1].
  2. For end = n − 1 down to 1: swap a[0] (the maximum) with a[end]; then heapify(0, end) so that a[0..end−1] is a heap again.
  3. Each swap fixes one more element at the right end; after n − 1 rounds the array is sorted ascending.
void heapify(int a[], int n, int i) {                   /* C, sift down */
    int l = 2*i + 1, r = 2*i + 2, big = i;
    if (l < n && a[l] > a[big]) big = l;
    if (r < n && a[r] > a[big]) big = r;
    if (big != i) { int t = a[i]; a[i] = a[big]; a[big] = t; heapify(a, n, big); }
}
void heap_sort(int a[], int n) {
    for (int i = n/2 - 1; i >= 0; i--) heapify(a, n, i);          /* build-heap: O(n) */
    for (int end = n - 1; end > 0; end--) {
        int t = a[0]; a[0] = a[end]; a[end] = t;                     /* max goes to the end */
        heapify(a, end, 0);                                          /* O(log n) */
    }
}

Cost: O(n) to build, then n − 1 heapify calls on a heap of shrinking size, each O(log n): O(n log n) in the best, average and worst case. Extra space O(1) (the recursion in heapify can be written as a loop). Heap sort is not stable, and in practice it runs slower than quick sort because the parent-child jumps across the array are unfriendly to caches. To sort descending, build a min-heap instead.

6.5 Shell sort and radix sort

Two sorts that break the pattern of the previous chapters. Shell sort is insertion sort run on elements a fixed gap apart, with the gap shrinking to 1: far-apart exchanges remove many inversions cheaply, so the final insertion sort has little left to do. Radix sort does not compare keys at all; it distributes them into buckets digit by digit, from the least significant digit, and so beats the n log n barrier of chapter 6.6 for keys with a fixed number of digits.

You need: insertion sort and the idea of a shift (chapter 6.2); stability (chapter 6.2) matters for radix sort.

Shell sort: insertion sort with a shrinking gap

Donald Shell published the method in 1959. Pick a gap sequence ending in 1, for example h = n/2, n/4, … , 1. For each gap h, do an insertion sort on each of the h interleaved sublists a[i], a[i+h], a[i+2h], … . An array where every such sublist is sorted is called h-sorted. The key fact: an array that is h-sorted stays h-sorted after being k-sorted for a smaller k, so earlier passes are never undone. The last pass, h = 1, is ordinary insertion sort, but on data that is nearly in order, where insertion sort is close to O(n).

void shell_sort(int a[], int n) {                      /* C, Shell's gaps n/2, n/4, ... */
    for (int h = n / 2; h > 0; h /= 2)
        for (int i = h; i < n; i++) {                   /* insertion sort with stride h */
            int key = a[i], j = i;
            while (j >= h && a[j - h] > key) { a[j] = a[j - h]; j -= h; }
            a[j] = key;
        }
}

The cost depends on the gap sequence, and no exact formula exists for most sequences. With Shell's own gaps n/2, n/4, … the worst case is Θ(n²) (for example when n is a power of two and the even and odd positions never mix until h = 1). Hibbard's gaps 2ᵏ − 1 (1, 3, 7, 15, …) and Knuth's (3ᵏ − 1)/2 (1, 4, 13, 40, …) give a worst case of Θ(n3/2); sequences found by experiment, such as Ciura's 1, 4, 10, 23, 57, 132, 301, 701, run fastest in practice. Shell sort is in place, uses O(1) extra space, is not stable (elements jump over each other across gaps), and for a few thousand elements it is competitive with quick sort while being far simpler.

Radix sort: sort by digits, least significant first

  1. Let d be the number of digits of the longest key (pad shorter keys with leading zeros) and b the base (10 for decimal digits, 256 for bytes).
  2. For digit position p = 1 (units) to d: distribute the keys into b buckets by digit p, keeping the order within each bucket (a stable distribution), then collect the buckets from 0 to b − 1 back into the array.
  3. After pass d the array is sorted, because the last pass sorted by the most significant digit and stability kept earlier digits in order for ties.

Each pass is a stable counting sort or bucket distribution of n items into b buckets, O(n + b). For d passes the total is O(d · (n + b)). When d is a constant (32-bit integers are 4 bytes, so d = 4 with b = 256), this is linear in n. Extra space O(n + b). It is stable. Its weaknesses: it needs keys with digits (integers, fixed-length strings, dates), the constant is not small, and for long keys d log b exceeds log₂n and a comparison sort wins. The MSD variant works from the most significant digit and recurses into buckets, like sorting a pile of letters by pin code then by name. Some syllabi also list address calculation sort: a one-pass cousin in which a hash-like function sends each key straight to an approximate position (say, floor(k/10) for keys in 0..99), with small sorted lists absorbing collisions; it is bucket sort by another name and runs O(n) when keys are spread evenly.

  • Shell sort is not stable; radix sort is stable. Students swap these.

6.6 Lower bound for sorting and external sorting

Can a sort that only compares keys beat n log n? No, and the decision-tree argument proves it in four lines. What if the data does not fit in memory? Then disk transfers are the cost, and external merge sort is the answer. A few syllabi name lower bound theory, or internal versus external sorting, as topics; elsewhere this chapter is background for chapter 6.3.

You need: merge sort (chapter 6.3), logarithms, and the height of a binary tree (Unit 4).

The decision-tree lower bound

A comparison sort learns about its input only by asking "is a[i] < a[j]?". Draw every possible run on n keys as a tree: each internal node is a comparison, its children the two outcomes, each leaf an output permutation. This is the decision tree; the comparisons made on an input equal the depth of its leaf.

  1. Each of the n! orderings of n distinct keys needs its own leaf, or two inputs would get the same output and one would be wrong: at least n! leaves.
  2. A binary tree of height h has at most 2ʰ leaves, so 2ʰ ≥ n! and h ≥ log₂(n!).
  3. By Stirling's approximation, log₂(n!) ≥ n log₂n − n log₂e ≈ n log₂n − 1.44n.
  4. So every comparison sort needs Ω(n log n) comparisons in the worst case; merge sort and heap sort meet this and are optimal up to a constant.

The average case is also Ω(n log n). Radix sort escapes because it reads digits instead of comparing, so no decision tree describes it.

External sorting

When a file of N records exceeds memory M, data moves in blocks of B records and the cost that matters is block transfers. External merge sort:

  1. Run formation: read M records, sort them in memory, write them as a sorted run; ⌈N/M⌉ runs after one pass.
  2. k-way merge: one block buffer per input run plus one for output, so k = M/B − 1 runs merge at once (a min-heap of the k heads picks the smallest). Each pass divides the number of runs by k and moves the whole file once.
  3. Passes = 1 + ⌈log_k(N/M)⌉; I/O = 2 × file size × passes.

Two named refinements: replacement selection forms runs of about 2M through an in-memory heap; polyphase merge spreads runs unevenly over files so no pass is wasted copying.

Worked example

Question (a). Minimum worst-case comparisons for any comparison sort when n = 5 and n = 10?

Solution. n = 5: 5! = 120, log₂120 = 6.91, so at least 7 comparisons. n = 10: 10! = 3,628,800, log₂(3,628,800) = 21.79, so at least 22. Merge sort on 10 elements uses at most 10 × 4 − 2⁴ + 1 = 25; bubble sort 45.

Question (b). A 1,000 MB file is sorted with 100 MB of memory and 10 MB blocks. Passes and data transferred? What changes with 110 MB?

Solution. Runs: ⌈1000/100⌉ = 10 runs of 100 MB after one pass. Buffers: 100/10 = 10, so k = 9. Merge passes: ⌈log₉10⌉ = 2 (nine runs into one, then that run with the tenth). Total passes 3; I/O = 3 × 1,000 MB read + 3 × 1,000 MB written = 6,000 MB. With 110 MB: k = 10, one merge pass: 2 passes, 4,000 MB.

Exam traps

  • The bound is on the worst case of comparison sorts; radix sort and a lucky sorted input are not counter-examples.
  • log₂(n!) is about n log₂n − 1.44n, not n log₂n; for small n compute n! and take the log.
  • One buffer is reserved for output: k = M/B − 1, not M/B.
  • Count I/O as reads plus writes; every pass moves the whole file twice.

6.7 Hashing: hash tables and hash functions

Searching so far has cost O(n) or O(log n) because the key's position had to be discovered by comparing. Hashing computes the position instead: a hash function turns the key into an index of an array called the hash table, so insert, search and delete take O(1) on average. The price is that two keys can land on the same index (a collision, chapter 6.8), and that the table must be kept from filling up (the load factor and rehashing). Hash tables are the dictionary behind compilers' symbol tables, Python's dict, and the lookup of a UPI ID to a bank account.

You need: arrays (Unit 2); the dictionary ADT (Unit 1); modular arithmetic.

From direct addressing to hashing

If keys are small integers 0..m−1, store the record for key k at a[k]: direct addressing, O(1) with no search. Real keys are roll numbers, PAN numbers, words, with a universe U far larger than the number of keys n you actually hold. A hash table keeps an array T[0..m−1] of m slots (also called buckets) with m close to n, and a hash function h: U → {0, 1, …, m−1} that says where key k lives: T[h(k)]. Search computes h(k) and looks in one slot. The load factor α = n/m is the average number of keys per slot and governs every cost formula in the next chapter.

A good hash function is (1) deterministic: the same key always gives the same index; (2) fast: O(1) arithmetic on the key; (3) uniform: it spreads the expected keys evenly over the m slots, so that clustering of real keys (consecutive roll numbers, words sharing a prefix) does not pile them into a few slots.

Hash functions for integer keys

  • Division method: h(k) = k mod m. Choose m a prime not close to a power of 2 or 10; with m = 2ᵖ the hash is just the low p bits of k, and keys that differ only in higher bits collide. Fastest and the usual exam choice.
  • Multiplication method: h(k) = ⌊m · (kA mod 1)⌋, where 0 < A < 1 and kA mod 1 is the fractional part of kA. The value of m does not matter, so m = 2ᵖ is fine. Knuth suggests A = (√5 − 1)/2 ≈ 0.6180339887 (the golden ratio conjugate), which spreads consecutive keys well.
  • Mid-square: square the key and take the middle digits (or bits): 72² = 5184, middle digits 18, then 18 mod m. The middle of the square depends on every digit of the key.
  • Folding: split the key into pieces and add them: 9876543210 → 987 + 654 + 321 + 0 = 1962, then mod m. Used for long numeric keys like Aadhaar or phone numbers.

String keys become integers first. The common choice is a polynomial hash: for a string s₀s₁…sL−1 with character codes ci, h = (c₀·bL−1 + c₁·bL−2 + … + cL−1) mod m with a small base such as b = 31, computed left to right as h = (h·b + ci) mod m so no large number ever forms. Simply adding the codes is a poor function: "act", "cat" and "tac" would all collide.

Load factor and rehashing

As keys are inserted, α rises and every operation slows: chains get longer, probes get longer. Implementations fix a threshold (0.75 is common with chaining, 0.5 with open addressing) and when α crosses it they rehash: allocate a new table about twice as large (the next prime above 2m for the division method), and insert every existing key again with the new hash function, because h(k) = k mod m changes when m changes. One rehash costs O(n), but it happens after about n insertions, so the average (amortized) cost per insertion stays O(1). Applications: symbol tables in compilers (identifier → type and address), dictionaries and sets in every language's library, caches (URL → page), database indexes for equality lookups, deduplication, and the HashMap behind an Android app's state.

Beyond the syllabus

Not for the exam. Modern hash functions for tables (MurmurHash3, xxHash, SipHash, wyhash) mix every bit of the key in a few CPU cycles, and SipHash is used by Python, Rust and Perl because an attacker who can predict a weak hash can send keys that all collide and turn an O(1) table into an O(n) denial-of-service. Cryptographic hashes (SHA-256, used in UPI transaction signing and blockchains) are a different tool: collision resistance matters, speed does not. Universal and perfect hashing give provable guarantees; cuckoo and Robin Hood hashing change how collisions are handled. Search for "SipHash hash flooding", "universal hashing" and "Swiss table".

6.8 Collision resolution: separate chaining and open addressing

A collision is two keys with the same hash value, and with any hash function and more keys than slots it is a certainty. There are two families of cures. Separate chaining lets each slot hold a linked list of all keys that hash there. Open addressing keeps every key inside the table array and, on a collision, probes other slots in a fixed sequence (linear, quadratic or double hashing) until an empty one turns up. Exams ask you to insert a list of keys under each scheme, draw the table, and quote the expected number of probes as a function of the load factor α.

You need: hash functions and load factor (chapter 6.7); singly linked lists (Unit 2).

Separate chaining

T[i] is the head of a linked list of all keys with h(k) = i. Insert: compute i, add the node at the head of the list, O(1). Search: walk the list at T[i]. With a uniform hash function, each list has α = n/m keys on average, so an unsuccessful search examines about α nodes and a successful search about 1 + α/2 (the key is on average halfway along its list). α may exceed 1; performance degrades gently, and deletion is just a list deletion. Costs: one pointer per key plus the array, and poor cache behaviour because the nodes are scattered in memory. This is what Java's HashMap does (with the chains turning into balanced trees when they grow past 8).

Open addressing

All keys live in T itself, so α ≤ 1 and m must exceed n. On a collision the table is probed at positions h₀(k), h₁(k), h₂(k), … until an empty slot is found (insert) or the key or an empty slot is found (search).

  1. Linear probing: hᵢ(k) = (h(k) + i) mod m. Try the next slot, then the next, wrapping around. Simple and cache-friendly, but runs of occupied slots grow and merge: primary clustering. Any key hashing into a cluster must walk to its end, and the cluster grows further.
  2. Quadratic probing: hᵢ(k) = (h(k) + i²) mod m. Probes jump 1, 4, 9, … slots ahead, breaking up primary clusters. Keys with the same h(k) still follow the same path (secondary clustering). With m prime and α ≤ 0.5, the first m/2 probes are all distinct, so an insertion always succeeds; beyond that it may fail even with empty slots.
  3. Double hashing: hᵢ(k) = (h₁(k) + i · h₂(k)) mod m with a second function such as h₂(k) = R − (k mod R), R a prime smaller than m. h₂(k) is never 0 and, with m prime, the probe sequence visits every slot. Different keys get different step sizes, so no clustering of either kind; this is the closest practical scheme to ideal uniform hashing.

Deletion cannot simply empty a slot: a later search for a key that probed past it would stop early and miss. Mark the slot deleted (a tombstone): search passes through it, insert may reuse it. Tombstones accumulate and count towards α, so tables are periodically rehashed.

6.9 String pattern matching: KMP, Boyer-Moore and tries

Pattern matching finds every place where a pattern P of length m occurs in a text T of length n: Ctrl+F, grep, a virus scanner, a DNA search. The naive method slides P along T and compares at every shift, O(nm) in the worst case. Knuth-Morris-Pratt (KMP) never re-reads a text character, O(n + m). Boyer-Moore compares from the right end of the pattern and often skips whole chunks of text, sublinear in practice. A trie stores a whole dictionary of words as a tree of characters so that any word is found in time proportional to its length. Several syllabi list this chapter; others leave it to a later algorithms course.

You need: arrays and strings (Unit 2); trees (Unit 4) for the trie.

Knuth-Morris-Pratt (1977)

When the naive method mismatches after matching j characters, it shifts by one and forgets everything. KMP keeps what it learned: the j matched characters are P[0..j−1], and the next useful shift is determined by P alone. Precompute the failure function (also called the LPS or prefix table): lps[i] = length of the longest proper prefix of P[0..i] that is also a suffix of P[0..i]. On a mismatch with j characters matched, continue matching with j = lps[j−1]; the text index never moves back.

  1. Build lps: lps[0] = 0, len = 0. For i = 1 to m − 1: while len > 0 and P[i] ≠ P[len], set len = lps[len − 1]; if P[i] = P[len], len = len + 1; lps[i] = len. O(m).
  2. Search: i = 0 (text), j = 0 (pattern). While i < n: if T[i] = P[j], advance both; if j reaches m, report a match at i − m and set j = lps[j − 1]. On a mismatch, if j > 0 set j = lps[j − 1], else advance i. O(n).

Each step either advances i or decreases j, and j can only decrease as many times as it increased, so the search makes at most 2n comparisons: Θ(n + m) in total, with O(m) extra space.

Boyer-Moore

Align P with T, but compare from the right end of P leftwards. On a mismatch at pattern index j with text character c, the bad character rule slides P right so that the rightmost occurrence of c in P lines up under the text position: shift = max(1, j − last[c]), where last[c] is the index of the last occurrence of c in P (−1 if absent). If c is not in P at all, the whole pattern jumps past it. The full algorithm adds the good suffix rule (reuse the matched suffix) and takes the larger of the two shifts. With both rules the worst case is O(n + m) for a pattern that does not occur; with the bad character rule alone it can degrade to O(nm) (text "aaaa…", pattern "baaa"). The best case is O(n/m): on English text with a 10-letter pattern most alignments cost one comparison and skip ten characters, which is why grep and text editors use Boyer-Moore variants.

Tries

A trie (from retrieval) is a tree in which each edge carries one character and each node represents the prefix spelled by the path from the root. Words end at nodes marked as terminal. Insert and search walk one level per character: O(L) for a word of length L, independent of how many words are stored. All words with a given prefix sit in one subtree, which gives autocomplete for free. The cost is space: a node with an array of 26 child pointers wastes most of them, so compact variants (ternary search tries, radix or Patricia trees with compressed edges) are used for large dictionaries, IP routing tables and T9-style keyboards.

Exam traps

  • lps[i] is the longest proper prefix that is also a suffix: never the whole string, so lps[0] = 0 always.

Takeaways

  1. Binary search costs ⌊log₂n⌋ + 1 comparisons but only on a sorted array; sorting is the price paid once so that every later search is cheap.
  2. The three simple sorts are all O(n²), but insertion sort is O(n) on nearly sorted data, selection sort makes the fewest swaps, and bubble sort with a flag stops early.
  3. Merge sort guarantees Θ(n log n) with O(n) space; quick sort averages Θ(n log n) in place but hits Θ(n²) with a bad pivot on sorted input.
  4. Heap sort is Θ(n log n) in place: build-heap is O(n), then n − 1 extractions of O(log n).
  5. Shell sort's cost depends on the gap sequence; radix sort is O(d(n + b)) because it reads digits instead of comparing.
  6. No comparison sort beats Ω(n log n): n! leaves need a decision tree of height log₂(n!).
  7. When data exceeds memory, sort runs of size M and k-way merge them; passes = 1 + ⌈log_k(N/M)⌉.
  8. A hash function (k mod m with prime m, or ⌊m(kA mod 1)⌋) gives O(1) average lookup; keep α = n/m below the threshold by rehashing.
  9. Collisions are resolved by chaining (lists, α may exceed 1) or open addressing (linear, quadratic, double hashing; α < 1; tombstones on delete); probe counts grow with 1/(1 − α).
  10. KMP matches in Θ(n + m) using the failure table; Boyer-Moore skips text with the bad character rule; a trie finds a word in O(L).

Outline: runs = 4096/256 = 16; buffers = 256/4 = 64, k = 63; ⌈log₆₃16⌉ = 1 merge pass; 2 passes; I/O = 2 × 2 × 4 GB = 16 GB; mention replacement selection halving the runs.

12. Build the KMP failure table for P = AABAAB and find all occurrences in T = AABAAAABAABAAB, listing every fallback. (10 marks)

Outline: lps = [0, 1, 0, 1, 2, 3]; the first five text characters match (j = 5), T[5] = A ≠ B → j = lps[4] = 2; A ≠ B again → j = lps[1] = 1; A = A → j = 2; T[6] = A ≠ B → j = 1; then matching proceeds to a full match ending at index 10 (start index 5), j = lps[5] = 3, and a second match at start index 8; 17 comparisons for n = 14, within the 2n bound; the text pointer never moved back.

13. For each situation choose a sort from this unit and justify with complexity and memory: (a) 50 exam marks on a microcontroller with 2 KB RAM, (b) 10 lakh Aadhaar-linked records that must stay in original order for equal keys, (c) 1 crore 32-bit integers, (d) a 20 GB log file on a laptop. (12 marks, spans chapters 6.2 to 6.6)

Outline: (a) insertion or selection sort, O(1) space, n tiny; (b) merge sort for stability at n log n, or Timsort-like; (c) LSD radix sort with 4 byte-passes, O(4(n + 256)), or quick sort if memory is tight; (d) external merge sort with runs of memory size and a k-way merge; justify each with the formulas.

14. "A hash table is always faster than a balanced BST." Evaluate this claim with respect to average and worst case, ordered operations, memory and the choice of hash function. (10 marks, spans chapters 6.7, 6.8 and Unit 4)

Outline: hash O(1) average vs BST O(log n); hash worst O(n) with bad function or adversarial keys vs AVL/red-black guaranteed O(log n); range queries, min/max, in-order listing need the BST; memory and rehashing pauses; conclusion: faster for exact lookup with a good hash and bounded α, not "always".

15. Compare linear probing, quadratic probing and double hashing at α = 0.5 and α = 0.9 using the expected-probe formulas, and recommend a rehash threshold for a system that must answer in a bounded time. (10 marks)

Outline: compute ½(1 + 1/(1−α)²): 2.5 and 50.5 for linear; 1/(1−α): 2 and 10 for double hashing; clustering explanation; quadratic may fail above 0.5 unless m is prime; recommend rehash at about 0.5 to 0.7 and double hashing or linear probing in one cache line.

16. A search feature must support exact match, prefix autocomplete and "find this substring in a document". Match each need to binary search, hashing, a trie, KMP or Boyer-Moore and justify the costs. (10 marks, spans chapters 6.1, 6.7 and 6.9)

Outline: exact match → hash table O(1) (or binary search O(log n) when memory matters); prefix → trie O(L) or binary search on a sorted array for the first match; substring in a document → KMP Θ(n + m) guaranteed, Boyer-Moore faster on natural text; explain why a hash cannot do prefixes and why a trie cannot do substrings without a suffix structure.

Glossary

Adaptive sort
A sort that runs faster on inputs that are already partly ordered, such as insertion sort.
Bad character rule
Boyer-Moore's shift: align the mismatched text character with its last occurrence in the pattern.
Binary search
Search on a sorted array that halves the range with every comparison; O(log n).
Border
A proper prefix of a string that is also its suffix; the KMP failure table stores the longest border of each prefix.
Build-heap
Turning an array into a heap by sifting down from the last non-leaf to the root; O(n).
Bucket
A slot of a hash table, or one of the b groups in a radix-sort pass.
Collision
Two different keys hashing to the same slot.
Comparison sort
A sort that learns the order of keys only by comparing pairs; bounded below by Ω(n log n).
Decision tree
Binary tree of all comparison sequences an algorithm can make; its height is the worst-case count.
Division method
h(k) = k mod m with prime m.
Double hashing
Open addressing with probe step h₂(k), different for different keys.
External sort
A sort for data larger than memory, measured in block transfers; external merge sort is the standard.
Failure function (lps)
KMP's table of longest borders, used to decide where to resume after a mismatch.
Gap sequence
The decreasing list of strides used by Shell sort, ending in 1.
Heapify (sift down)
Restore the heap property at a node by swapping it downward with its larger child.
In-place sort
A sort that uses O(1) extra memory beyond the array (recursion stack aside).
Inversion
A pair of elements in the wrong order; insertion sort does one shift per inversion.
Linear probing
Open addressing that tries slots h, h+1, h+2, … mod m.
Load factor
α = n/m, stored keys per slot.
Lomuto / Hoare partition
Two ways to split an array around a pivot in quick sort; Lomuto uses a last-element pivot and one scanning index.
Multiplication method
h(k) = ⌊m (kA mod 1)⌋ with 0 < A < 1.
Open addressing
Collision resolution that keeps all keys inside the table and probes for free slots.
Pivot
The element quick sort partitions around; ends in its final position.
Primary clustering
Growing runs of occupied slots under linear probing.
Rehashing
Moving every key to a larger table with a new hash function when α gets high.
Run
A sorted block of records written to disk in the first phase of external sorting.
Separate chaining
Collision resolution with a linked list per slot.
Stable sort
A sort that keeps equal keys in their original relative order.
Tombstone
A "deleted" marker in open addressing that searches pass over and inserts may reuse.
Trie
A tree with one character per edge; stores a set of strings with O(L) lookup.
