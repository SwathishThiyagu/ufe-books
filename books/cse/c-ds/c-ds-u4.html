4.1 Tree terminology and properties; general trees

A tree is a set of nodes joined by edges so that one node is the root and every other node hangs below exactly one parent. There is exactly one path from the root to any node, so a tree has no cycles. Trees exist because so much real data is a hierarchy: the folders on your phone, the sections of a syllabus, the reporting chain in a company, the structure of an HTML page. A general tree lets a node have any number of children; the rest of this unit restricts that to two.

The words you must know

Examiners test vocabulary in two-mark questions and use it without explanation in the long ones, so learn these against the tree on the left of Figure 4.1.1.

  • Root: the top node, the only node with no parent (A).
  • Parent, child, siblings: B is the parent of E and F; E and F are its children and are siblings of each other. B, C and D are siblings.
  • Leaf (external node): a node with no children (E, F, G, H, I). A node with at least one child is an internal node (A, B, C, D).
  • Degree of a node: the number of its children. A has degree 3, C has degree 1, every leaf has degree 0. The degree of the tree is the largest node degree, here 3.
  • Path: the sequence of nodes you walk along edges from one node down to another. The path from A to F is A → B → F; its length is 2 edges.
  • Depth (level) of a node: the number of edges from the root to it. Depth of A is 0, of B is 1, of F is 2. Nodes at the same depth form a level.
  • Height of a node: the longest downward path from it to a leaf, in edges. A leaf has height 0. The height of the tree is the height of the root: 2 here.
  • Ancestor and descendant: every node on the path from the root to X (excluding X) is an ancestor of X; X is their descendant. The ancestors of F are B and A.
  • Subtree: any node together with all its descendants. The subtree rooted at D is {D, H, I}.
  • Forest: a set of zero or more disjoint trees; removing the root of a tree leaves a forest of its subtrees.

Some syllabi list this chapter as "Tree ADT": the abstract data type (Unit 1) whose operations are root(), parent(x), children(x), isLeaf(x), size() and height(); the representations below say how they are implemented.

Properties worth proving

  1. A tree with n nodes has exactly n − 1 edges. Every node except the root has exactly one edge going up to its parent, and the root has none, so counting edges is counting non-root nodes. The examiner's favourite "prove that" question.
  2. Between any two nodes there is exactly one simple path. Two different paths could be joined into a cycle, and a tree has no cycles.
  3. Node count from degrees. If the tree has nᵢ nodes of degree i, then n = 1 + Σ i·nᵢ, because each node of degree i contributes i edges and there are n − 1 edges in all. This answers "a tree has 4 nodes of degree 3 and 2 of degree 2; how many leaves?"

Representing a general tree

The number of children is unknown in advance, so a node cannot simply have "a left and a right" pointer. Three representations are standard.

  • Array of k child pointers (k = degree of the tree). Simple, but 1000 nodes of degree 10 hold 10 000 pointers for 999 edges.
  • Linked list of children (Unit 2): no waste, but reaching the fifth child takes five steps.
  • Left-child, right-sibling (LC-RS): each node keeps exactly two pointers, firstChild and nextSibling, so the general tree becomes a binary tree, which is why the rest of the unit can concentrate on binary trees. The right side of Figure 4.1.1 shows the same tree in this form.
struct TNode {               /* C: left-child, right-sibling node */
    int data;
    struct TNode *firstChild;
    struct TNode *nextSibling;
};

To list the children of X you follow X->firstChild once and then nextSibling repeatedly until NULL. For B in the figure that gives E, then F, then NULL.

Worked example

Question. For the general tree in Figure 4.1.1 (root A; children of A are B, C, D; children of B are E, F; child of C is G; children of D are H, I) find: (a) the degree of each internal node and of the tree, (b) the height of the tree and the depth of G, (c) the number of edges, (d) the leaves, (e) the ancestors of F and the siblings of C. Then (f): a different tree has 10 internal nodes, each of degree exactly 3; how many nodes and how many leaves does it have?

Solution.

  1. (a) Count children: degree(A) = 3 (B, C, D), degree(B) = 2, degree(C) = 1, degree(D) = 2. The degree of the tree is the maximum, 3.
  2. (b) Longest root-to-leaf path is A → B → E (or any other leaf), 2 edges, so height = 2. Depth of G: path A → C → G has 2 edges, so depth(G) = 2.
  3. (c) n = 9 nodes, so edges = n − 1 = 8. Check by adding degrees: 3 + 2 + 1 + 2 = 8. ✓
  4. (d) Leaves (degree 0): E, F, G, H, I: five leaves.
  5. (e) Ancestors of F: walk up: parent B, then A. Siblings of C: the other children of A, namely B and D.
  6. (f) Use n = 1 + Σ i·nᵢ. The internal nodes contribute 3 × 10 = 30 edges; leaves contribute none. So n = 1 + 30 = 31 nodes. Leaves = n − internal = 31 − 10 = 21. Cross-check: edges = 31 − 1 = 30. ✓

Exam traps

  • Height in edges or in nodes? Weiss and most Indian papers count edges (a single node has height 0, an empty tree −1). Some books (Horowitz-Sahni) count levels, so a single node has height 1. State your convention in the first line of the answer and the examiner cannot deduct.
  • Level 0 or level 1? Same issue. If the question says "root is at level 1", every formula with 2ⁱ shifts by one.
  • Depth vs height. Depth is measured from the root down to the node; height from the node down to the deepest leaf. The root has depth 0 and maximum height.
  • Degree of a node vs degree of the tree. "Degree of the tree" is the largest node degree, not the sum.
  • "How many edges?" Always n − 1, whatever the shape. Students sometimes add one for the root.

4.2 Binary trees: properties and array/linked representation

A binary tree is a tree in which every node has at most two children, and the two are distinguished as the left child and the right child. That small restriction gives clean formulas (how many nodes fit in a given height, how many leaves a tree must have) and two simple ways to store the tree: in an array by position, or in linked nodes with two pointers. Every search tree and heap in this unit is a binary tree, so this chapter is the foundation of the rest.

You need: the terms of 4.1, and arrays and pointers from Unit 2.

Kinds of binary trees

A binary tree is either empty, or a root with a left subtree and a right subtree, each of which is a binary tree. "Empty" is a legal binary tree, with height −1 by the edge convention. The named shapes are:

  • Strict (full) binary tree: every node has 0 or 2 children, never exactly 1. Some books say "full", others "strictly binary"; the exam usually defines its term.
  • Perfect binary tree: all internal nodes have two children and all leaves are at the same depth; a perfect tree of height h has 2ʰ⁺¹ − 1 nodes.
  • Complete binary tree: every level except possibly the last is full, and the last level is filled from left to right with no gaps. This is the shape of a heap (4.7), because it packs into an array without holes.
  • Skewed (degenerate) tree: every node has one child, so the tree is really a linked list; the worst case for a search tree (4.5).

Some syllabi list this as "Binary Tree ADT", with operations create, isEmpty, leftChild(x), rightChild(x), parent(x), insert, delete and the traversals of 4.3.

Five properties, with their one-line proofs

  1. Level i holds at most 2ⁱ nodes (root at level 0): each node has at most two children, so each level at most doubles the previous one.
  2. A tree of height h has at most 2ʰ⁺¹ − 1 nodes. Add the levels: 1 + 2 + 4 + … + 2ʰ = 2ʰ⁺¹ − 1, a geometric series.
  3. n nodes need height at least ⌈log₂(n + 1)⌉ − 1. Turn property 2 around: n ≤ 2ʰ⁺¹ − 1 gives h + 1 ≥ log₂(n + 1). For n = 100: log₂ 101 ≈ 6.66, ceiling 7, so h ≥ 6.
  4. Leaves = nodes with two children + 1, written n₀ = n₂ + 1. Let n₁ be the nodes with one child. Count edges two ways: n − 1 (one per non-root node) and n₁ + 2n₂ (one per child pointer in use). With n = n₀ + n₁ + n₂, the equation n₀ + n₁ + n₂ − 1 = n₁ + 2n₂ gives n₀ = n₂ + 1. The examiner's favourite proof in the unit.
  5. A complete binary tree with n nodes has height ⌊log₂ n⌋, which is why heap operations cost O(log n).

Array representation

Number the nodes level by level, left to right, starting at 1 for the root, and store node number i in A[i]. The positions of the family are then arithmetic, not pointers:

left child of i  = 2i
right child of i = 2i + 1
parent of i      = ⌊i / 2⌋          (1-based)

left = 2i + 1,  right = 2i + 2,  parent = ⌊(i − 1) / 2⌋   (0-based, as in C)

Syllabi call this the "array representation" or "storage representation using matrices". It is perfect for complete trees: no pointers, no holes, and the parent of any node is one division away. It is wasteful for anything else: a right-skewed tree with k nodes puts its k-th node at index 2ᵏ − 1, so 10 nodes need 1023 slots, of which 1013 are empty. Missing nodes are marked with a sentinel (−1, 0, or a flag array).

Linked representation

Each node is a structure with the data and two pointers; some syllabi call this the "pointer representation". It uses 2n pointers for n nodes, and since there are only n − 1 edges, n + 1 of them are always NULL, a fact threaded binary trees exploit. The C declaration and a helper that allocates a node:

struct Node {
    int data;
    struct Node *left, *right;
};

struct Node *newNode(int v) {              /* C */
    struct Node *p = malloc(sizeof(struct Node));
    p->data = v; p->left = p->right = NULL;
    return p;
}
/* building the tree of Figure 4.2.1 */
struct Node *root = newNode(10);
root->left = newNode(20);  root->right = newNode(30);
root->left->left = newNode(40); root->left->right = newNode(50);
root->right->right = newNode(60);

Converting between the two forms is a common tutorial exercise: from the array, node i's children are at 2i and 2i + 1 if filled; from the linked tree, a level-order walk (4.3) assigns the indices.

Worked example

Question. A binary tree is stored in a 1-based array as A = [10, 20, 30, 40, 50, –, 60] where "–" marks an empty slot. (a) Draw the tree. (b) Is it complete? Is it strict? (c) Find n₀, n₁, n₂ and verify n₀ = n₂ + 1. (d) What is its height, and what is the minimum possible height for a binary tree with the same number of nodes? (e) How large an array would a right-skewed tree with the same 6 nodes need?

Solution.

  1. (a) Index 1 is the root, 10. Its children are at 2 and 3: 20 and 30. Children of 20 (i = 2) are at 4 and 5: 40 and 50. Children of 30 (i = 3) are at 6 and 7: slot 6 is empty, slot 7 is 60, so 30 has only a right child, 60. That is the tree of Figure 4.2.1.
  2. (b) Not complete: the last level has a gap (slot 6 empty while slot 7 is used). Not strict either, because 30 has exactly one child.
  3. (c) Two children: 10 and 20, so n₂ = 2. One child: 30, so n₁ = 1. Leaves: 40, 50, 60, so n₀ = 3. Check: n₂ + 1 = 3 = n₀. ✓ Total 6 nodes, 5 edges = n₁ + 2n₂ = 1 + 4. ✓
  4. (d) The deepest nodes (40, 50, 60) are 2 edges from the root, so height = 2. Minimum height for n = 6: ⌈log₂(6 + 1)⌉ − 1 = ⌈2.81⌉ − 1 = 3 − 1 = 2. This tree already has the minimum height.
  5. (e) Right-skewed: node k sits at index 2ᵏ − 1, so the 6th node is at 2⁶ − 1 = 63. The array needs 63 slots for 6 values: 57 wasted.

Second question. A strict binary tree has 41 nodes. How many leaves? Since n₁ = 0, n = n₀ + n₂ = (n₂ + 1) + n₂ = 2n₂ + 1, so 41 = 2n₂ + 1, n₂ = 20 and n₀ = 21.

Exam traps

  • Full, complete, perfect. The names move between books. Define the one you use in your first sentence; a "full" tree in one book is "perfect" in another.
  • Off-by-one in the array formulas. 2i and 2i + 1 are for a 1-based array; in a C array starting at 0 the children are at 2i + 1 and 2i + 2. Mixing them is the commonest slip in heap questions too.
  • 2ʰ⁺¹ − 1 or 2ʰ − 1? With height in edges and root at level 0, a tree of height h has h + 1 levels and at most 2ʰ⁺¹ − 1 nodes. If the paper counts levels (root at level 1), the maximum is 2ʰ − 1. Check which the question uses.
  • n₀ = n₂ + 1 holds for every binary tree, not only strict ones; n₁ simply cancels in the proof.

Beyond the syllabus

Not for the exam. The array layout returns in modern systems because it is cache-friendly: a heap, a segment tree, a Fenwick tree and the "Eytzinger layout" for fast binary search all put a complete tree into a flat array so that a parent and its children sit near each other in memory. Threaded binary trees reuse the n + 1 NULL pointers to point to the inorder successor so that traversal needs no stack. Search "Eytzinger layout" and "succinct trees".

4.3 Tree traversals: inorder, preorder and postorder

A traversal visits every node of a tree exactly once. A list has only one sensible order; a binary tree has three natural depth-first orders, named by when the root is visited relative to its subtrees: preorder (root first), inorder (root in the middle) and postorder (root last), plus the breadth-first level order. Traversals are how you print a tree, copy it, free it, evaluate an expression tree, and produce sorted output from a search tree. Tutorials ask you to trace all three by hand for a given diagram, and most papers do the same in a 4- or 8-mark question.

You need: recursion (Unit 1), the linked node of 4.2, and the queue ADT (Unit 3) for level order.

The three recursive orders

Each traversal is the same three-line recursion with the "visit" moved. L means traverse the left subtree, R the right subtree, N means visit (print) the node:

  • Preorder (N L R): visit the node, then its left subtree, then its right subtree. Used to copy a tree, to print a directory with its sub-directories, and to produce the prefix form of an expression.
  • Inorder (L N R): left subtree, node, right subtree. On a binary search tree this gives the keys in ascending order (4.5); on an expression tree it gives infix.
  • Postorder (L R N): left, right, then node. Used to delete a tree (children before parent), to compute sizes and heights bottom-up, and to produce postfix.
void preorder(struct Node *t) {            /* C */
    if (t == NULL) return;
    printf("%c ", t->data);
    preorder(t->left);  preorder(t->right);
}
void inorder(struct Node *t) {
    if (t == NULL) return;
    inorder(t->left);   printf("%c ", t->data);   inorder(t->right);
}
void postorder(struct Node *t) {
    if (t == NULL) return;
    postorder(t->left); postorder(t->right);  printf("%c ", t->data);
}

For the tree of Figure 4.3.1 the three calls print A B D E C F, D B E A C F and D E B F C A. Each visits n nodes and makes 2n + 1 calls (one per node plus one per NULL pointer), so the time is O(n); the recursion stack is as deep as the tree, O(h), which is O(n) for a skewed tree and O(log n) for a balanced one.

A hand method that never fails

Draw a dashed line that starts at the root, hugs the tree and walks around its outside, down the left side first and back up the right. Every node is passed three times: on the way down its left (preorder), when you cross underneath it from left to right (inorder), and when you leave it going up (postorder). Write the letter on the first pass for preorder, the second for inorder, the third for postorder. A leaf is passed three times in a row, which is why leaves keep the same relative order in all three lists. A quicker check for inorder: project every node straight down onto a line and read left to right.

Level order, with a queue

Level order visits nodes top to bottom, left to right: A B C D E F in the figure. It is not recursive; it uses the queue of Unit 3. Enqueue the root; while the queue is not empty, dequeue a node, print it, and enqueue its left then right child if they exist. Each node enters and leaves the queue once, so the time is O(n) and the queue holds at most one level. This is also the walk that assigns array indices to a linked tree (4.2).

Rebuilding a tree from two traversals

One traversal alone does not fix a tree (many shapes share a preorder). Preorder plus inorder does, and so does postorder plus inorder; preorder plus postorder does not, because a node with a single child could have it on either side. The reconstruction is the examiner's favourite 8-mark question:

  1. The first symbol of preorder (last of postorder) is the root.
  2. Find the root in inorder. Everything to its left is the left subtree's inorder; everything to its right is the right subtree's inorder.
  3. The next |left| symbols of preorder are the left subtree's preorder; the rest are the right subtree's.
  4. Recurse on each side until the pieces are single nodes or empty.

Question 2. A binary tree has preorder F B A D C E G I H and inorder A B C D E F G H I. Draw the tree and give its postorder.

  1. Root = first of preorder = F. In inorder, F is at position 6: left part A B C D E (5 nodes), right part G H I (3 nodes).
  2. Left subtree: preorder = next 5 symbols B A D C E, inorder A B C D E. Root B; inorder left of B is A, right is C D E. Preorder of the right part: D C E, inorder C D E → root D with left child C and right child E. So B has left child A and right child D, and D has children C and E.
  3. Right subtree: preorder G I H, inorder G H I. Root G; nothing to its left in inorder, so no left child; right part has inorder H I and preorder I H → root I with left child H.
  4. Tree: F( B( A, D(C, E) ), G( –, I(H, –) ) ). Postorder (left, right, node): A C E D B H I G F.

Check: the inorder of the drawn tree is A B C D E F G H I, the alphabet, so this is also a binary search tree (4.5).

Exam traps

  • A missing child shifts the order. When a node has only a right child, inorder visits the node before that child; students often write the child first. Mark empty children with a dash when you draw the tree.
  • Preorder + postorder is not enough to rebuild a tree; inorder must be one of the two. A favourite true/false.
  • Level order is not "preorder without recursion". Preorder with a stack visits the left subtree completely before any node on the right; level order visits one level at a time.
  • Counting calls. A recursive traversal of n nodes makes 2n + 1 calls, not n: every NULL pointer gets a call too.
  • Which order sorts a BST? Inorder, and only inorder. Preorder of a BST is what you need to rebuild it.

Beyond the syllabus

Not for the exam. Compilers walk the syntax tree of your program in postorder to generate code (children's values must exist before the parent's operation). 4.4 Expression trees

An expression tree is a binary tree that stores an arithmetic expression: every leaf is an operand (a number or a variable) and every internal node is an operator whose two subtrees are its operands. The tree removes the need for parentheses and precedence rules, because the structure itself says what is computed first. Compilers, calculators and spreadsheet engines build one from your input, and the three traversals of 4.3 read it back as prefix, infix or postfix. Syllabi list it as "expression manipulation" or "construction and evaluation".

You need: traversals (4.3) and the postfix notation and stack of Unit 3 (Infix, prefix and postfix conversion).

What the tree looks like

For the expression (a + b) × (c − d) / e, the last operation performed is the division, so "/" is the root. Its left operand is the whole product (a + b) × (c − d), a subtree rooted at "×"; its right operand is the single leaf e. Figure 4.4.1 draws it. Reading the tree with the three traversals gives:

  • Preorder: / × + a b − c d e: the prefix (Polish) form.
  • Inorder: a + b × c − d / e: the infix form, but without the parentheses. To get a correct infix string, print "(" before entering an internal node's left subtree and ")" after its right subtree: ((a + b) × (c − d)) / e.
  • Postorder: a b + c d − × e /: the postfix (reverse Polish) form, the one a stack machine evaluates.

So an expression tree is the single structure that unifies the three notations of Unit 3: convert between any two by building the tree from one and traversing it in the other order.

Building the tree from postfix

Postfix is the easiest input because there are no precedence decisions left. Use a stack whose elements are pointers to subtrees:

  1. Read the postfix string left to right, one symbol at a time.
  2. If the symbol is an operand, make a one-node tree for it and push the pointer.
  3. If the symbol is an operator, pop two pointers: the first popped is the right operand, the second is the left operand. Make a new node for the operator with those two subtrees and push it.
  4. At the end exactly one pointer remains on the stack: the root of the expression tree.

Each symbol is pushed and popped at most once, so building takes O(n) for n symbols. Building from infix means converting to postfix first (the shunting-yard method of Unit 3), or using two stacks, one for operands and one for operators. Building from prefix is the mirror image: read right to left and make the first popped node the left child.

struct Node *buildFromPostfix(char s[]) {          /* C; operands are single letters */
    struct Node *stack[100]; int top = -1;
    for (int i = 0; s[i]; i++) {
        if (s[i] == ' ') continue;
        struct Node *p = newNode(s[i]);
        if (isalnum(s[i])) { stack[++top] = p; }
        else { p->right = stack[top--]; p->left = stack[top--]; stack[++top] = p; }
    }
    return stack[top];
}

Evaluating the tree

Evaluation is a postorder traversal that returns a value instead of printing: a leaf returns its value, an operator node evaluates its left subtree, then its right subtree, then applies the operator.

int eval(struct Node *t) {                          /* C */
    if (t->left == NULL && t->right == NULL) return value(t->data);
    int l = eval(t->left), r = eval(t->right);
    switch (t->data) {
        case '+': return l + r;   case '-': return l - r;
        case '*': return l * r;   case '/': return l / r;
    }
    return 0;
}

The order matters for the non-commutative operators: left operand minus right operand, not the reverse. That is why step 3 of the construction assigns the first popped subtree to the right side.

Exam traps

  • Left and right swapped. On an operator, the first pop is the right operand. Getting this wrong flips every subtraction and division: c − d becomes d − c.
  • Inorder is not infix. Plain inorder drops the parentheses, so a + b × c − d is wrong for the tree in the figure. Add "(" and ")" around each internal node's output, or at least around subtrees of lower precedence.
  • Building directly from infix. Do not try to read "(a + b) × c" symbol by symbol into a tree in the exam; convert to postfix first (Unit 3) and then build. Say that you are doing so.
  • Operands at internal nodes. Every internal node must be an operator with exactly two children, and every operand must be a leaf. A tree breaking this is not an expression tree.
  • Unary minus. Rare in exams, but if it appears, it is an operator node with one child; mention that the algorithm must be adjusted.

4.5 Binary search trees: search, insertion and deletion

A binary search tree (BST) is a binary tree with one ordering rule: for every node, all keys in its left subtree are smaller than the node's key and all keys in its right subtree are larger. The rule turns a search into a walk from the root, going left or right at each node, so that a search, an insertion or a deletion costs one comparison per level: O(h) for a tree of height h. When the tree is bushy, h ≈ log₂ n and a million keys need about 20 comparisons; when it is skewed, h = n − 1 and the BST is no better than a list. That gap is why the balanced trees of 4.6 and 4.8 exist.

You need: binary trees (4.2) and inorder traversal (4.3).

The property and what it gives for free

Keys are assumed distinct (duplicates are either rejected or sent consistently to one side). Because of the ordering rule, an inorder traversal of a BST prints the keys in ascending order; this is the quickest way to check a tree someone hands you. The smallest key is the leftmost node (follow left pointers until NULL), the largest is the rightmost. The inorder successor of a node with a right subtree is the minimum of that right subtree; the inorder predecessor is the maximum of the left subtree. Deletion uses these.

Search

  1. Start at the root. If the tree is empty, the key is absent.
  2. Compare the key with the node. Equal: found. Smaller: go to the left child. Larger: go to the right child.
  3. Repeat until found or until the pointer becomes NULL (absent).
struct Node *search(struct Node *t, int key) {      /* C, iterative */
    while (t != NULL && t->data != key)
        t = (key < t->data) ? t->left : t->right;
    return t;                                        /* NULL if absent */
}

Insertion

Search for the key; it will not be found, and the NULL pointer where the search stops is exactly where the new node belongs. A new key is therefore always inserted as a leaf, and the shape of the tree depends entirely on the order of insertion: the keys 10, 20, 30, 40 inserted in that order give a right-skewed chain of height 3, while 20, 10, 30, 40 give height 2.

struct Node *insert(struct Node *t, int key) {       /* C, recursive; returns the new subtree root */
    if (t == NULL) return newNode(key);
    if (key < t->data)      t->left  = insert(t->left, key);
    else if (key > t->data) t->right = insert(t->right, key);
    return t;                                         /* duplicate: ignored */
}

Deletion: three cases

First search for the node. Then:

  1. Leaf: set the parent's pointer to NULL and free the node.
  2. One child: make the parent point to that child (splice the node out), then free it.
  3. Two children: find the inorder successor (minimum of the right subtree), copy its key into the node, and delete the successor from the right subtree. The successor has no left child, so that second deletion is case 1 or 2, never case 3 again. Using the inorder predecessor (maximum of the left subtree) is equally correct; say which one you use.
struct Node *deleteKey(struct Node *t, int key) {     /* C */
    if (t == NULL) return NULL;
    if (key < t->data)      t->left  = deleteKey(t->left, key);
    else if (key > t->data) t->right = deleteKey(t->right, key);
    else {                                            /* found */
        if (t->left == NULL)  { struct Node *r = t->right; free(t); return r; }
        if (t->right == NULL) { struct Node *l = t->left;  free(t); return l; }
        struct Node *s = t->right;                    /* two children: successor */
        while (s->left) s = s->left;
        t->data = s->data;
        t->right = deleteKey(t->right, s->data);
    }
    return t;
}

Performance analysis

Every operation follows one root-to-leaf path, so each costs O(h). Best case (a complete tree): h = ⌊log₂ n⌋, so O(log n). Worst case (sorted input, a skewed tree): h = n − 1, so O(n). Average over random insertion orders, the height is about 1.39 log₂ n, still O(log n). Some syllabi list this as "performance analysis"; the one-line answer is "O(h), which is O(log n) on average and O(n) in the worst case, and the AVL tree of 4.6 guarantees O(log n)". "Symbol table construction" is the classic application: a compiler stores each identifier and its attributes in a BST keyed by name.

Worked example

Question. Insert the keys 50, 30, 70, 20, 40, 60, 80, 35, 45 in that order into an empty BST. (a) Draw the final tree and state its height. (b) How many comparisons does a search for 45 make? For 65? (c) Delete 30 and draw the tree. (d) Then delete 50 and draw the tree.

Solution.

  1. (a) 50 becomes the root. 30 < 50: left child of 50. 70 > 50: right child. 20 < 50, < 30: left of 30. 40 < 50, > 30: right of 30. 60 > 50, < 70: left of 70. 80 > 50, > 70: right of 70. 35 < 50, > 30, < 40: left of 40. 45 < 50, > 30, > 40: right of 40. The result is the left tree of Figure 4.5.1. Height = 3 (path 50 → 30 → 40 → 35).
  2. (b) Search 45: compare with 50 (go left), 30 (go right), 40 (go right), 45 (found): 4 comparisons. Search 65: 50 (right), 70 (left), 60 (right), then NULL: 3 comparisons and the answer "absent".
  3. (c) Delete 30: it has two children (20 and 40). Successor = minimum of the right subtree rooted at 40 = 35. Copy 35 into the node and delete the leaf 35. Tree: 50( 35(20, 40(–, 45)), 70(60, 80) ). Inorder 20 35 40 45 50 60 70 80: still sorted.
  4. (d) Delete 50 (the root, two children). Successor = minimum of the right subtree = 60 (70, then left to 60). Copy 60 into the root and delete the old 60, a leaf. Tree: 60( 35(20, 40(–, 45)), 70(–, 80) ). Inorder 20 35 40 45 60 70 80. Height is still 3.

Contrast. Inserting the same nine keys in sorted order (20, 30, 35, 40, 45, 50, 60, 70, 80) gives a right-skewed chain of height 8, and a search for 80 then takes 9 comparisons instead of 3.

Exam traps

  • "Left child smaller" is not enough. Every key in the whole left subtree must be smaller than the node, not just the immediate child. A tree can satisfy the child rule and still fail: root 50, left child 30, and 30's right child 55 is invalid.
  • Two-child deletion: copy the key, then delete the successor. Students draw the successor moved up but forget to remove its old node, leaving a duplicate.
  • Successor or predecessor? Both are correct and give different trees. If the question does not say, use the inorder successor and write the word.
  • Complexity is O(h), not O(log n). Only a balanced tree makes h logarithmic; sorted input makes a BST degenerate to O(n).
  • Insertion order decides the shape. "Draw the BST for these keys" always means insert in the order given.

4.6 AVL trees: balance factor and rotations

An AVL tree is a binary search tree that repairs itself: after every insertion or deletion it checks that, at every node, the heights of the left and right subtrees differ by at most 1, and if not it rearranges three nodes with a rotation. The reward is a guaranteed height of about 1.44 log₂ n, so search, insert and delete are O(log n) even for sorted input, which would turn a plain BST (4.5) into a list. Named after Adelson-Velsky and Landis (1962), it is the first balanced tree in every syllabus; syllabi name the four rotations LL, RR, LR and RL, and papers ask for both insertion and deletion.

You need: BST insertion (4.5) and height (4.1).

Balance factor

The balance factor of a node is BF = height(left subtree) − height(right subtree), with the height of an empty subtree taken as −1. A tree is AVL when every node has BF ∈ {−1, 0, +1}. BF = +1 means left-heavy, −1 right-heavy, 0 equal. Some books define BF as right − left; the numbers flip sign but the rotations are the same, so state your convention on the first line. Each node stores its height (or its BF) so that the check costs O(1) after each update.

How much does the condition buy? The fewest nodes an AVL tree of height h can have is N(h) = N(h − 1) + N(h − 2) + 1 with N(0) = 1, N(1) = 2, giving 4, 7, 12, 20, 33, 54, … This grows like the Fibonacci numbers, so the height is at most about 1.44 log₂(n + 2): an AVL tree with 20 nodes has height at most 5, and one with a million nodes at most about 28, against 999 999 for a worst-case BST.

The four cases and their rotations

After a BST insertion, walk back up the path to the root updating heights. The first node whose BF becomes +2 or −2 is the pivot; call it k. The new node lies in one of four places relative to k, and each has one fix:

CaseWhere the insertion wentBF of pivot, BF of its childFix
LLleft subtree of the left child+2, +1single right rotation at the pivot
RRright subtree of the right child−2, −1single left rotation at the pivot
LRright subtree of the left child+2, −1left rotation at the left child, then right rotation at the pivot
RLleft subtree of the right child−2, +1right rotation at the right child, then left rotation at the pivot

A single rotation (Figure 4.6.1) lifts the heavy child to the pivot's place and hands the child's inner subtree across to the pivot; the inorder sequence is unchanged, which is why the result is still a BST. A double rotation (Figure 4.6.2) is two single rotations; the grandchild ends up on top with the two others as its children. After the fix the subtree has the height it had before the insertion, so no ancestor needs attention: one rotation (single or double) per insertion.

struct Node *rotateRight(struct Node *k2) {   /* C: LL fix; k1 = left child of k2 */
    struct Node *k1 = k2->left;
    k2->left = k1->right;                      /* inner subtree T2 crosses over */
    k1->right = k2;
    k2->h = 1 + max(h(k2->left), h(k2->right));
    k1->h = 1 + max(h(k1->left), h(k1->right));
    return k1;                                 /* new root of this subtree */
}
/* rotateLeft is the mirror image; LR = rotateLeft(k->left) then rotateRight(k);
   RL = rotateRight(k->right) then rotateLeft(k). */

Insertion and deletion procedure

  1. Insert the key as in a BST (new leaf, BF 0).
  2. Walk back up the insertion path. At each node recompute the height and the BF.
  3. At the first node with |BF| = 2, identify the case from the table (look at the sign of the pivot's BF, then the sign of the heavy child's BF) and apply the rotation.
  4. Stop; the tree is AVL again.

Deletion is a BST deletion followed by the same walk upward, but the case is read from the taller child of the pivot (if its BF is 0, treat it as a single-rotation case), and a rotation can shorten the subtree, so the check must continue to the root: up to O(log n) rotations.

Worked example

Question. Insert 10, 20, 30, 40, 50, 25 in that order into an empty AVL tree, showing every rotation. Give the final preorder.

Exam traps

  • Naming the case by the pivot, not by the new node. LR means "left child, then right subtree of that child" as seen from the pivot; read the two signs (+2 then −1) and the case is fixed.
  • Rotating at the wrong node. The pivot is the lowest node with |BF| = 2, the first one you meet walking up from the new leaf, not the root.
  • Dropping the inner subtree. In a right rotation, k1's right subtree (T2) must become k2's left subtree. Forgetting it loses keys; check with inorder.
  • Sign convention. If the paper defines BF as right − left, LL is −2/−1. Write your convention and be consistent.
  • Deletion is not insertion. After a deletion you may need more than one rotation; after an insertion never more than one.

4.7 Binary heaps and priority queues

A priority queue hands out items not in arrival order but by priority: the patient in the worst condition, the process with the earliest deadline, the IRCTC booking with tatkal status. The binary heap is the structure that makes both operations, insert and remove-the-smallest, cost O(log n). It is a complete binary tree (4.2) with one rule, parent ≤ children, stored in a plain array with no pointers at all. Heaps are the engine of heap sort (Unit 6), of Dijkstra's and Prim's algorithms (Unit 5), and of every operating-system scheduler. Every syllabus lists the heap, some as "priority queues and their representation".

You need: complete binary trees and the array formulas of 4.2; the queue ADT of Unit 3 for contrast.

The priority queue ADT and its implementations

Operations: insert(x), deleteMin() (or deleteMax; the two heaps are mirror images), findMin(), isEmpty(). Compare the obvious implementations for n items:

The heap wins because it gives up what a priority queue never needs: a full ordering. It only promises that the minimum is at the root.

The two properties of a binary heap

  • Structure property: the tree is complete, so with 1-based indexing the children of i are at 2i and 2i + 1 and the parent of i is at ⌊i/2⌋; the n items fill A[1..n] exactly and the height is ⌊log₂ n⌋.
  • Heap-order property (min-heap): every node's key is ≤ its children's keys. Nothing is said about left versus right, which is why a heap is not a search tree and an inorder walk of a heap means nothing.

In a max-heap the inequality is reversed and the root is the largest key. A heap of n keys has ⌊n/2⌋ internal nodes, at indices 1..⌊n/2⌋, and the rest are leaves: this fact drives the build procedure below.

Insert: percolate up

  1. Place the new key in the next free slot, A[n + 1], so the tree stays complete.
  2. While the key is smaller than its parent A[⌊i/2⌋], swap them (or, faster, slide the parent down into the hole and move the hole up).
  3. Stop when the parent is smaller or the hole reaches the root. At most ⌊log₂ n⌋ swaps.

DeleteMin: percolate down

  1. Save A[1], the minimum; it is the answer.
  2. Move the last key A[n] into the root slot and reduce n by 1, keeping the tree complete.
  3. While the key is larger than the smaller of its two children, swap it with that smaller child. Choosing the smaller child is what keeps the parent ≤ both children.
  4. Stop when both children are larger or the key reaches a leaf. At most ⌊log₂ n⌋ swaps.
void deleteMin(int A[], int *n) {                 /* C, 1-based array, min-heap */
    int last = A[(*n)--], i = 1, child;
    for (; 2 * i <= *n; i = child) {
        child = 2 * i;
        if (child < *n && A[child + 1] < A[child]) child++;   /* the smaller child */
        if (last > A[child]) A[i] = A[child]; else break;
    }
    A[i] = last;
}

Building a heap from n keys in O(n)

Inserting the keys one by one costs O(n log n). The Floyd build is faster: put all n keys in the array in any order, then for i = ⌊n/2⌋ down to 1 percolate A[i] down. Leaves are already heaps, and each internal node is fixed after its children are. The cost is Σ (nodes at height h) × h ≤ n Σ h/2ʰ⁺¹ < 2n swaps, so O(n), a favourite "show that" question.

Exam traps

  • Swapping with the wrong child. In percolate down, compare with the smaller child (larger in a max-heap). Swapping with the left child by habit breaks the heap.
  • Forgetting to move the last element. DeleteMin must fill the root with A[n], not with the smaller child, or the tree stops being complete.
  • A heap is not a BST. Inorder of a heap is not sorted, and "search for key 33" in a heap is O(n).
  • Build-heap is O(n), not O(n log n). The examiner wants the Σ h/2ʰ argument, or at least the sentence "most nodes are near the bottom and move only a little".
  • Index base. With a 0-based array the children are 2i + 1 and 2i + 2; mixing bases is the commonest error in dry runs.

4.8 Red-black trees and splay trees

Two more self-adjusting search trees, each with a different bargain. A red-black tree colours every node red or black and uses the colours, instead of exact heights, to keep the longest root-to-leaf path at most twice the shortest: height ≤ 2 log₂(n + 1), every operation O(log n) worst case, with fewer rotations than AVL. A splay tree keeps no balance information at all; it moves every accessed node to the root with rotations, so any sequence of m operations costs O(m log n) in total even though one operation can cost O(n). Red-black trees sit inside C++ std::map, Java TreeMap and the Linux kernel; splay trees appear in caches. About half the syllabi list this chapter.

You need: BST operations (4.5) and the rotations of 4.6.

Red-black tree: the five rules

  1. Every node is red or black.
  2. The root is black.
  3. Every NULL pointer counts as a black leaf.
  4. A red node has no red child (no two reds in a row on any path).
  5. Every path from a node down to its NULL leaves passes the same number of black nodes, its black-height.

Rules 4 and 5 together bound the height: a path can at most alternate red and black, so it has at most twice the black nodes of the shortest path. A tree with black-height b has at least 2ᵇ − 1 nodes, so b ≤ log₂(n + 1) and the height is at most 2 log₂(n + 1). For a million keys that is about 40 levels, against 28 for AVL and 999 999 for a skewed BST. Deletion also stays O(log n) and needs at most three rotations; insertion needs at most two.

Red-black insertion

  1. Insert as in a BST and colour the new node red (so rule 5 cannot break; only rule 4 can).
  2. If the new node is the root, colour it black. Done.
  3. If the parent is black, nothing is broken. Done.
  4. Parent is red. Look at the uncle (the parent's sibling). If the uncle is red: recolour parent and uncle black and the grandparent red, then repeat from step 2 with the grandparent as the "new node".
  5. Uncle black (or NULL): rotate. If the new node is an outer grandchild (LL or RR as in 4.6) do a single rotation at the grandparent; if it is an inner grandchild (LR or RL) do the double rotation. Then colour the node now on top black and its two children red. Done.

Recolouring can climb to the root, but it costs O(1) per level; rotations happen at most once per insertion. Deletion has more cases (the "double black" problem) and most exam papers ask for insertion and the properties; learn deletion from your prescribed book if your syllabus lists it.

Splay trees: move what you touch to the top

A splay tree is a BST with one extra habit: after every search, insert or delete, the node that was accessed (or the last node on the search path, if the key was absent) is splayed, rotated up until it is the root. Going up, three situations repeat (x is the node, p its parent, g its grandparent):

  • Zig: p is the root. One rotation at p. Used only as the last step.
  • Zig-zig: x and p are both left children (or both right). Rotate at g first, then at p: two rotations in the same direction (Figure 4.8.2). This is the step that makes the whole path halve in depth, and it is what distinguishes splaying from naive "rotate to root".
  • Zig-zag: x is a left child and p a right child, or the reverse. Rotate at p, then at g, exactly the double rotation of 4.6.

Splay trees store no heights or colours, so each node is just a key and two pointers. A single operation can take O(n) (think of a chain), but Sleator and Tarjan (1985) proved that any sequence of m operations on n nodes takes O(m log n): the amortised cost is O(log n). Keys accessed often sit near the root, so splay trees make natural caches. Deletion: splay the key to the root, remove it, splay the maximum of the left subtree to its root and attach the right subtree to it.

Worked example

Question 1. Insert 10, 20, 30, 15, 25 in that order into an empty red-black tree, naming each case. State the black-height of the result.

  1. 10: root, coloured black.
  2. 20: red right child of 10. Parent black: done.
  3. 30: red right child of 20. Parent 20 red; uncle is 10's left child, NULL, so black. Outer (RR) case: left rotation at 10. 20 becomes root, coloured black; 10 and 30 red. (Figure 4.8.1, left.)
  4. 15: 15 < 20, > 10: red right child of 10. Parent 10 red, uncle 30 red: recolour 10 and 30 black, 20 red; 20 is the root, so back to black. (Figure 4.8.1, right.)
  5. 25: 25 > 20, < 30: red left child of 30. Parent 30 is black: done.
  6. Final tree: 20 black; 10 black with red right child 15; 30 black with red left child 25. Every path to a NULL passes 2 black nodes, so the black-height is 2; the height is 2 with 5 nodes, and no path is more than twice any other.

Question 2. In the splay tree 50( 30( 20(10, 25), 40 ), 60 ), the key 20 is searched. Draw the tree after splaying.

  1. x = 20, p = 30, g = 50. Both x and p are left children: zig-zig.
  2. Rotate right at g = 50: 30 rises; 50 becomes its right child and takes 30's old right subtree 40 as its left child. Tree: 30( 20(10, 25), 50(40, 60) ).
  3. Rotate right at p = 30: 20 rises; 30 becomes its right child and takes 25 as its left child. Tree: 20( 10, 30( 25, 50(40, 60) ) ).
  4. 20 is now the root, so a repeat search for 20 costs one comparison; 10 moved from depth 3 to depth 1, and 50 went from depth 0 to depth 2. Inorder is still 10 20 25 30 40 50 60.

Exam traps

  • New nodes are red. Inserting black would break rule 5 immediately. The only node that is forced black is the root.
  • Uncle, not sibling. The case split looks at the parent's sibling. Students often look at the new node's sibling, which is always NULL.
  • Recolouring may continue upward; a rotation ends the repair. After a recolouring, re-examine the grandparent as if it were the new node.
  • Splay is not "rotate to root". Rotating x up one step at a time (all zigs) gives the wrong tree and loses the amortised bound; zig-zig rotates at the grandparent first.
  • Amortised is not average. O(log n) amortised means the total over any sequence is bounded, in the worst case; a single splay can still cost O(n).

4.9 B-trees and multi-way search trees

When the data lives on a disk or SSD, what costs time is not a comparison but a block read: fetching 4 KB takes as long as thousands of comparisons in memory, and a binary tree with a million keys needs about 20 block reads per search. A multi-way search tree puts many keys and many children in one node, so one block read moves you down one level of a very flat tree; a B-tree is the balanced version, with every leaf at the same depth and every node at least half full, so a million keys need three or four reads. Bayer and McCreight introduced B-trees in 1970, and database indexes and file systems use a B-tree or its B+ variant. Some syllabi list "multi-way search trees"; others list the 2-4 tree, the B-tree of order 4.

You need: BST search (4.5) and the idea of balance from 4.6.

m-way search trees

An m-way search tree is a tree in which each node holds up to m − 1 keys in sorted order, k₁ < k₂ < … < kⱼ, and up to m children c₀ … cⱼ, with every key in child cᵢ lying between kᵢ and kᵢ₊₁. A BST is the case m = 2. Searching is a BST search with a scan inside each node: find the first key ≥ x, stop if equal, otherwise follow the child just before it. Without further rules an m-way tree can be as unbalanced as a BST, so search is O(h) with no bound on h.

B-tree of order m

A B-tree (Knuth's definition, order m = maximum number of children) is an m-way search tree in which:

  1. every node has at most m children, so at most m − 1 keys;
  2. every internal node except the root has at least ⌈m/2⌉ children, so at least ⌈m/2⌉ − 1 keys: nodes are at least half full;
  3. the root has at least two children unless it is a leaf;
  4. all leaves are at the same level;
  5. a node with j children holds exactly j − 1 keys.

CLRS uses a minimum degree t instead: every non-root node has between t − 1 and 2t − 1 keys, a B-tree of order 2t. Either way the height is bounded: with n keys, h ≤ log_t((n + 1)/2). For t = 51 (50 to 101 keys per node, about one 4 KB block) and n = 1 000 000, log₅₁(500 000.5) ≈ 3.3, so at most three levels below the root: four block reads per search. A 2-3 tree is a B-tree of order 3; a 2-3-4 tree is order 4 (the "2-4 trees" of some syllabi) and is the red-black tree of 4.8 in disguise, each 3- or 4-node spread into a black node with red children.

Insertion: fill, then split

  1. Search for the key; it belongs in a leaf. Insert it there in sorted order.
  2. If the leaf now has m keys (one too many), split it: the median key moves up into the parent, the keys below the median stay as the left node and the keys above become a new right node.
  3. If the parent now overflows, split it the same way, and so on up. If the root splits, the median becomes a new root with two children: this is the only way a B-tree grows in height, and it grows at the top, which is why all leaves stay at one level.

Each insertion costs O(h) block reads plus O(m) work per node, O(log n) overall; splits are rare (a node splits only after m − ⌈m/2⌉ further insertions).

Deletion: borrow or merge

Delete from a leaf; a key in an internal node is first replaced by its inorder predecessor or successor, which is then deleted from its leaf. If the leaf then has fewer than ⌈m/2⌉ − 1 keys (underflow): if a neighbouring sibling has a spare key, borrow through the parent (the parent key comes down, the sibling's end key goes up); otherwise merge with the sibling, pulling the separating parent key down, and check the parent in turn. If the root loses its last key its single child becomes the new root and the height shrinks by one.

B+ trees

Databases (MySQL InnoDB, PostgreSQL, SQLite) use the B+ tree: all records sit in the leaves, internal nodes hold only copies of keys to guide the search, and the leaves are linked left to right. A range query such as "all bookings between 1 and 31 October" finds the first leaf and walks the linked leaves without climbing back up; internal nodes holding keys only fit more children per block, making the tree flatter still.

Exam traps

  • "Order" means different things. Knuth's order m is the maximum number of children; CLRS's minimum degree t gives maximum 2t children. State the maximum keys per node in your first line and stick to it.
  • Split on m keys, not m − 1. A node of order m may hold m − 1 keys; it splits only when a further insertion makes m. Splitting too early is the commonest mistake.
  • The median goes up, not a copy. In a B-tree the median leaves the node; in a B+ tree a copy stays in the leaf.
  • Leaves at the same level is a rule, not a result. Leaves at different depths mean the insertion was done wrongly.
  • Minimum keys for the root is 1; the half-full rule applies to non-root nodes.

Takeaways

  1. A tree with n nodes has n − 1 edges; height is counted in edges with a leaf at 0, and you must say so.
  2. Binary tree facts come from one count: level i has at most 2ⁱ nodes, and n₀ = n₂ + 1 because edges can be counted two ways.
  3. Store a complete binary tree in an array (children 2i, 2i + 1); store anything else with two pointers per node.
  4. The three traversals differ only in when the node is visited; inorder sorts a BST, postorder evaluates an expression tree, and inorder plus one other order rebuilds the tree.
  5. BST operations cost O(h): O(log n) when bushy, O(n) when the input was sorted.
  6. AVL repairs with one rotation per insertion, chosen by two signs: LL and RR single, LR and RL double; the grandchild rises in a double rotation.
  7. A heap is a complete tree with parent ≤ children: findMin O(1), insert and deleteMin O(log n), build O(n); it is not a search tree.
  8. Red-black trees allow height up to 2 log₂(n + 1) in exchange for fewer rotations; splay trees need no balance data and are O(log n) amortised.
  9. A B-tree keeps every node at least half full and every leaf at one level; it grows only by splitting the root, and the median moves up on each split.
  10. Whenever you draw a search tree in an exam, check it by writing its inorder sequence: it must be sorted.

Compare the array and linked representations of a binary tree with respect to space, access to parent and children, and suitability for complete and skewed trees. Write the C declarations for both. (8 marks)

Outline: array uses index formulas (2i, 2i + 1, ⌊i/2⌋), O(1) parent access, no pointers, but a skewed tree of k nodes needs 2ᵏ − 1 slots; linked uses 2n pointers of which n + 1 are NULL, no waste for any shape, parent needs a third pointer. Declarations: int A[MAX] with a flag array, and struct Node { int data; struct Node *left, *right; }.

Explain the priority queue ADT, compare three ways of implementing it, and describe the two properties of a binary heap. Why is a heap not a search tree? (8 marks)

Outline: operations insert, deleteMin, findMin; unsorted list O(1)/O(n), sorted list O(n)/O(1), heap O(log n)/O(log n) with findMin O(1); structure property (complete, array), order property (parent ≤ children); siblings unordered so inorder means nothing and search is O(n).

State the properties of a red-black tree and of a B-tree of order m. Give the height bound of each and say where each is used. (8 marks)

Outline: the five red-black rules, height ≤ 2 log₂(n + 1), used in C++ std::map and the Linux kernel; B-tree rules (≤ m children, ≥ ⌈m/2⌉ for non-root, leaves at one level, j − 1 keys for j children), height ≤ log_t((n + 1)/2), used by database indexes and file systems because one node is one disk block.

Apply

Construct the binary tree whose preorder is G B Q A C K F P D E R H and whose inorder is Q B K C F A G P E D H R. Give its postorder and its height. (10 marks)

Outline: root G; inorder splits into {Q B K C F A} and {P E D H R}. Left: preorder B Q A C K F → B with left Q and right A; A's inorder part K C F with preorder C K F → C with children K and F. Right: preorder P D E R H, inorder P E D H R → P with no left child and right D; D has left E and right R; R has left H. Postorder: Q K F C A B E H R D P G. Height 4 (G → P → D → R → H).

Construct the expression tree for the postfix expression a b c * + d e / − and write its prefix and infix forms; evaluate it for a = 2, b = 3, c = 4, d = 10, e = 5. (8 marks)

Outline: stack trace builds −( +(a, *(b, c)), /(d, e) ). Prefix: − + a * b c / d e. Infix: (a + (b × c)) − (d / e). Value: 2 + 12 = 14; 10 / 5 = 2; 14 − 2 = 12.

Insert 45, 15, 79, 90, 10, 55, 12, 20, 50 into an empty BST. Then delete 15, then 45, drawing the tree after each deletion and stating the case used. Give the final inorder. (12 marks)

Outline: tree 45( 15(10(–, 12), 20), 79(55(50, –), 90) ). Delete 15 (two children): successor 20, tree 45( 20(10(–, 12), –), 79(55(50, –), 90) ). Delete 45 (two children): successor 50 (79 → 55 → 50), root becomes 50 and the old 50 leaf is removed: 50( 20(10(–, 12), –), 79(55, 90) ). Inorder 10 12 20 50 55 79 90.

Insert 21, 26, 30, 9, 4, 14, 28, 18, 15, 10, 2, 3, 7 into an empty AVL tree, naming every rotation (LL, RR, LR, RL) as it occurs. (16 marks)

Outline, rotation by rotation (nine in all): 30 → RR at 21: 26(21, 30). 9: fine. 4 → LL at 21: 26( 9(4, 21), 30 ). 14 → BF(26) = +2 via 9's right subtree: LR at 26: 21( 9(4, 14), 26(–, 30) ). 28 → RL at 26: 21( 9(4, 14), 28(26, 30) ). 18: fine, right of 14. 15 → RL at 14: 15(14, 18) under 9. 10 → RL at 9: 14( 9(4, 10), 15(–, 18) ) under 21. 2 → LL at 21: root becomes 14( 9(4(2, –), 10), 21( 15(–, 18), 28(26, 30) ) ). 3 → LR at 4: 3(2, 4). 7 → LR at 9: 4( 3(2, –), 9(7, 10) ). Final preorder 14 4 3 2 9 7 10 21 15 18 28 26 30, height 3. Examiners award marks per correctly named rotation and per intermediate tree, so draw every step.

Show the array after each step while building a min-heap by inserting 23, 17, 14, 6, 13, 10, 1 one by one, then after two successive deleteMin operations. (10 marks)

Outline: [23]; [17, 23]; [14, 23, 17]; [6, 14, 17, 23]; [6, 13, 17, 23, 14]; [6, 13, 10, 23, 14, 17]; [1, 13, 6, 23, 14, 17, 10]. deleteMin returns 1: move 10 to root, percolate: [6, 13, 10, 23, 14, 17]. deleteMin returns 6: move 17 to root: [10, 13, 17, 23, 14].

Insert the keys 1 to 10 in order into an empty red-black tree, naming the case (recolour or rotation) at every step. (12 marks)

Outline: 1 black; 2 red; 3: uncle NULL → RR rotation at 1 → 2 black with red 1, 3; 4: uncle 1 red → recolour, 1 and 3 black, root stays black; 5: uncle NULL → rotation at 3 → 4 black with 3, 5 red; 6: uncle 3 red → recolour, 4 red, 3 and 5 black; 7: rotation at 5 → 6 black with 5, 7 red; 8: uncle 5 red → recolour 5, 7 black and 6 red, which now clashes with its red parent 4 whose uncle 1 is black → RR rotation at 2: root becomes 4 black with red children 2 and 6; 9: rotation at 7 → 8 black with 7, 9 red; 10: uncle 7 red → recolour 7, 9 black, 8 red; 8's parent 6 is red with uncle 2 red → recolour 2, 6 black, 4 red → root → black. Final: 4( 2(1, 3), 6(5, 8(7, 9(–, 10))) ) with 8 and 10 red, all others black; black-height 3.

Insert 20, 40, 10, 30, 15, 35, 7, 26 into an empty B-tree of order 4 (maximum 3 keys per node), showing each split. Then delete 40. (10 marks)

Outline (taking the second of four keys as the median; the third is also accepted if used consistently): [20 40] → [10 20 40] → 30 overflows: median 20 up, root [20] with [10] and [30 40]; 15 → [10 15]; 35 → [30 35 40]; 7 → [7 10 15]; 26 → [26 30 35 40] overflows, median 30 up: root [20 30], children [7 10 15], [26], [35 40]. Delete 40 from leaf [35 40]: [35], no underflow (minimum 1 key for order 4).

Analyze and evaluate

Keys arrive in sorted order. Compare the resulting BST, AVL tree and red-black tree after n insertions in height, number of rotations and search cost, and recommend one for a phone-book application that is read far more often than written. (10 marks)

Outline: BST becomes a chain of height n − 1, search O(n); AVL height ≤ 1.44 log₂ n with about one rotation per insertion; red-black height ≤ 2 log₂(n + 1) with at most two rotations per insertion but many recolourings. Read-heavy favours the shallower AVL; write-heavy favours red-black. Mention that a B-tree would be the answer if the book lives on disk.

Explain why building a heap bottom-up is O(n) while n insertions are O(n log n). Then explain why heap sort, which uses this heap, is still O(n log n). (Spans 4.7 and Unit 6.) (10 marks)

Outline: bottom-up, a node at height h does at most h swaps and there are at most ⌈n/2ʰ⁺¹⌉ such nodes, so the total is n Σ h/2ʰ⁺¹ < 2n; insertion lets each key climb up to log n levels. Heap sort then performs n deleteMin operations each O(log n), which dominates.

A compiler needs a symbol table and a scheduler needs a ready queue of processes ordered by priority. Choose a structure from this unit for each, justify with the operations each application performs, and state the cost of each operation. (Spans 4.5, 4.7, 4.8.) (12 marks)

Outline: symbol table does search, insert and sometimes ordered listing; a balanced search tree (AVL or red-black, O(log n) each, inorder gives sorted output) or a hash table from Unit 6 for pure lookups. Ready queue does insert and extract-highest-priority; a binary heap gives O(log n) for both and O(1) peek, and a BST would waste effort maintaining a full order. Mention decreaseKey for priority changes.

Evaluate the claim "a splay tree is always worse than an AVL tree because a single operation can take O(n) time". (8 marks)

Outline: true that one splay can be O(n) on a chain, but the amortised bound O(log n) per operation over any sequence matches AVL in total cost; splay trees need no height or colour fields, use simpler code, and move frequently accessed keys near the root, giving better than O(log n) on skewed access patterns (caches). Worse when a strict per-operation guarantee is needed, e.g. real-time systems.

Glossary

Ancestor
Any node on the path from the root to a node, excluding the node itself.
AVL tree
A BST in which every node's balance factor is −1, 0 or +1, restored by rotations.
Balance factor
height(left subtree) − height(right subtree) of a node.
B-tree
A balanced multi-way search tree with all leaves at one level and every non-root node at least half full.
B+ tree
A B-tree variant with all records in linked leaves and only guide keys in internal nodes.
Binary heap
A complete binary tree in which each parent is ≤ (min-heap) or ≥ (max-heap) its children, stored in an array.
Binary search tree
A binary tree in which every node's left subtree holds smaller keys and right subtree larger keys.
Black-height
The number of black nodes on any path from a node down to a NULL leaf in a red-black tree.
Complete binary tree
All levels full except possibly the last, which is filled from the left.
Degree
Of a node, its number of children; of a tree, the largest node degree.
Depth
The number of edges from the root to a node; the root has depth 0.
Expression tree
A binary tree with operators at internal nodes and operands at leaves.
Height
The longest downward path from a node to a leaf, in edges; a leaf has height 0 and an empty tree −1.
Inorder successor
The next larger key; for a node with a right subtree, the minimum of that subtree.
Leaf
A node with no children.
Left-child right-sibling
A representation of a general tree as a binary tree with pointers to the first child and the next sibling.
Level order
Traversal top to bottom and left to right within each level, using a queue.
m-way search tree
A tree whose nodes hold up to m − 1 sorted keys and up to m children.
Percolate
Moving a key up (after insert) or down (after deleteMin) in a heap until heap order holds.
Perfect binary tree
All internal nodes have two children and all leaves are at the same depth.
Priority queue
An ADT with insert and delete-the-minimum (or maximum) operations.
Red-black tree
A BST with red and black nodes, no red-red parent-child pair and equal black counts on all paths.
Rotation
A local restructuring of two nodes and three subtrees that keeps the inorder sequence and changes heights.
Skewed tree
A binary tree in which every node has at most one child; height n − 1.
Splay
To move an accessed node to the root using zig, zig-zig and zig-zag rotation steps.
Split
In a B-tree, dividing an overfull node into two and sending its median key to the parent.
Strict binary tree
Every node has either zero or two children.
Traversal
A systematic visit of every node once: preorder, inorder, postorder or level order.
