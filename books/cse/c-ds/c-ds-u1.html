1.1 What a data structure is; linear vs non-linear

A data structure is a way of arranging data in memory together with the operations that use that arrangement. The arrangement is the whole point: the same 60 marks stored in an array, a linked list or a tree are the same data, but finding the 40th mark costs one address calculation in the array, 40 pointer hops in the list and about six comparisons in a balanced tree. Choosing a structure is choosing which operations will be cheap. SRM lists this chapter as "Classification of Data Structures: Primitive and Non-Primitive, Linear and Non-Linear"; IIT Bombay, NIT Surathkal and Manipal call it "Introduction to data structures".

Data, information and data types

Data is a raw value: 72, 'A', 3.14, "Chennai". Information is data with a meaning attached: 72 is a mark out of 100, 'A' is a grade. A program never stores a bare value; it stores a value of a data type, and a data type is a set of allowed values plus the operations allowed on them. In C, int is the whole numbers that fit in 4 bytes with +, −, ×, ÷ and comparisons; char is one byte holding a character code; float and double approximate real numbers; a pointer holds an address.

These built-in types are the primitive data types. Everything built out of them is non-primitive: an array (many values of one type side by side), a structure or record (values of different types under one name), a string, a file, and every structure in this book. Primitive/non-primitive is the first classification examiners ask for; linear/non-linear is the second, and it applies only to the non-primitive side.

What a data structure is

Formally, a data structure is a collection of data values, the relationships among them, and the operations that can be applied to them. In practice it has two halves: a storage structure (how the values sit in memory: one block, scattered nodes joined by pointers, a table of slots) and a set of operations (insert, delete, search, traverse, sort) whose cost depends on that storage. An array keeps its elements in one contiguous block, so element i is at address base + i × size and is reached in one step; but inserting at the front means shifting every element right. A linked list scatters its nodes and joins them with pointers, so inserting at the front is one pointer change, but reaching element i means walking i pointers.

So the design question is always the same: which operations does this problem do most, and which structure makes those cheap? A railway reservation system searches by PNR millions of times a day; an editor's undo history only adds and removes at one end; a road map must answer "what is next to this junction?". Each gets a different structure. Unit 1 gives the language to ask the question; Units 2 to 6 give the structures that answer it.

Linear and non-linear structures

A structure is linear when its elements form a single sequence: every element has at most one predecessor and at most one successor, so the whole structure can be traversed in one pass, first to last, without ever choosing a direction. Arrays, linked lists, stacks and queues are linear. A stack and a queue are linear with restricted access (one end only, or in at one end and out at the other), which is why Unit 3 treats them as ADTs built on arrays or lists.

A structure is non-linear when an element can be related to many others. A tree is a hierarchy: one root, and every other node has one parent and any number of children, like folders inside folders. A graph is a network: any node may be joined to any other, like cities joined by roads, cycles allowed. Traversing a non-linear structure forces a choice at each step (which child first? which neighbour next?), so Unit 4 teaches tree traversals and Unit 5 teaches breadth-first and depth-first search.

Three other classifications cut across this line: contiguous vs linked storage (array vs linked list; a tree can be stored either way), static vs dynamic size (fixed at compile time vs grown at run time, chapter 1.3) and homogeneous vs heterogeneous contents (an array holds one type, a record holds several).

Exam traps

  • "Linear" does not mean "stored in one block". A linked list is linear (one next element) but its nodes are scattered; an array is both linear and contiguous. Keep linear/non-linear (the shape of the relationships) separate from contiguous/linked (the storage).
  • A stack and a queue are linear, however they are drawn. They restrict where you may insert and delete; they do not change the one-after-another shape.
  • A skewed tree in which every node has one child looks like a list but is still a tree (non-linear): the relationship is parent-to-children, not previous-to-next.
  • Examiners' favourite: "Define data structure. Classify data structures with examples." Give the definition (data + relationships + operations), then the tree of Figure 1.1.1 with two examples per leaf.

Beyond the syllabus

Not for the exam. In practice you rarely write these structures from scratch: C++ gives you std::vector and std::map, Java the Collections framework, Python list, dict and set; the skill is knowing which one your workload needs. Performance work goes one level further: a CPU fetches memory in cache lines of 64 bytes, so a contiguous array is often faster than a linked list even where the list "should" win, and game and database engineers design layouts around this ("data-oriented design"). Functional languages add persistent structures that keep every old version after an update. Search for "cache-friendly data structures" and "persistent data structures".

1.2 Abstract data types (ADTs)

An abstract data type is a data type described by what its operations do, not by how its values are stored. A List ADT promises get, insert, remove and size with stated effects; whether the list lives in an array or in linked nodes is an implementation decision that the user of the list never sees. The idea exists so that the "what" can be fixed, taught and tested once, while the "how" is swapped freely for speed or memory. Most syllabi list this as "Abstract Data Types (ADTs)"; IIT Delhi's wording is "introduction to ADTs and linear ADTs, for example sets, lists, vectors and sequences", and SRM's tutorial asks you to "design simple ADTs", which is the worked example below.

You need: the definition of a data type and the linear/non-linear classification from chapter 1.1.

Specification, not implementation

Every data type is two things: a set of values and a set of operations. An abstract data type writes down only the part a user can observe: the operations, their inputs and outputs, and the rules that connect them. It says nothing about memory. The built-in int is already an ADT in this sense: you use +, −, × and comparisons and never think about the two's-complement bits underneath. The ADT idea applies the same discipline to the structures you build yourself.

A good specification has four parts. The domain: what the values are (a sequence of integers; a set of strings). The operations with their signatures: name, arguments, result type. The preconditions: what must be true before an operation may be called (get(i) needs 0 ≤ i < size). The postconditions: what is true afterwards (after insert(i, x), size has grown by one and get(i) returns x). Think of a UPI app: pay(to, amount) has a precondition (enough balance) and a postcondition (both balances changed); you never see the bank's tables. That boundary, interface on one side and implementation on the other, is what the word "abstract" means here.

One interface, many implementations

The payoff of an ADT is that the same client code runs on different implementations. Client code written against the List ADT calls insert(0, x); it does not know that an array implementation shifts n elements to make room while a linked implementation changes one pointer. If the array version turns out too slow for a workload full of front insertions, the implementation is replaced and the client does not change by a character. Standard libraries work this way: Java's List is an interface with ArrayList and LinkedList behind it. Chapter 1.9 shows the mechanism in code: a class packages an ADT's operations with a hidden representation.

Choosing the implementation is an analysis question, which is why chapters 1.5 to 1.8 follow. The ADT fixes the meaning; the data structure fixes the cost.

Exam traps

  • ADT versus data structure: the ADT is the specification (operations and their meaning); the data structure is a concrete implementation (array, linked nodes). "A linked list is an ADT" is wrong; "List is an ADT, a linked list implements it" is right.
  • "Abstract" does not mean vague. A specification must state every operation's inputs, outputs and preconditions; an answer that lists only operation names gets half marks.
  • What happens when a precondition is broken (get(7) on a list of 3) is the implementation's business, usually an error; an ADT answer should state the precondition, not invent a return value like −1.
  • An ADT is not the same as an "abstract class" in C++ or Java. The language feature is one way to express an interface; the ADT is the mathematical idea and exists in C too, where it is a header file plus functions.
  • Examiners' favourite: "Define ADT. Specify the List (or Stack) ADT and give two implementations with their trade-offs." Use the four-part template, then the cost comparison of (c).

Analyze A team writes a Queue ADT but lets client code read the internal array index "front" directly "for speed". Analyse what is lost. 4 marks

The interface boundary is broken: clients now depend on the representation (an array with a front index), so the queue can no longer be reimplemented as a linked structure or a circular buffer without rewriting every client. Bugs can also corrupt the queue's invariants, since clients can move "front" outside the operations that keep it consistent. Any speed gain is usually illusory, as a front() operation costs the same single read. Lost: substitutability, invariants, testability; the fix is to expose front() in the interface.

Beyond the syllabus

Not for the exam. In industry the ADT idea appears as interfaces (Java, Go), abstract base classes and Protocols (Python), traits (Rust) and concepts (C++20), and tests written against the interface are what let teams replace an implementation safely. Formal methods go further: Z, Alloy and TLA+ write preconditions and postconditions precisely enough for a tool to check them, and "design by contract" checks them at run time. Do not confuse ADTs with the "algebraic data types" of Haskell and Rust, which build types from sums and products. Search for "design by contract" and "TLA+ specification".

1.3 Static and dynamic memory allocation

Every data structure needs memory, and there are two moments at which a program can ask for it. Static allocation decides the size while the program is being compiled: int marks[60]; reserves 240 bytes before a single student has registered. Dynamic allocation asks while the program is running: malloc(n * sizeof(int)) reserves exactly n integers after n is known, and free gives them back. Static is simpler and faster; dynamic is the only way to build structures whose size is not known in advance, which is every linked list, tree and graph of this course. SRM pairs this with ADTs ("Static and Dynamic Memory Allocation"), Manipal lists "Memory allocation functions", and NIT Surathkal reaches it through its introduction to data structures.

Where a running C program keeps its data

The memory of a running program is divided into segments (Figure 1.3.1). The text segment holds the compiled instructions. The data segment holds global and static variables, whose sizes the compiler knows. The stack holds each function's parameters, local variables and return address in a frame that is pushed when the function is called and popped when it returns. The heap is the pool from which run-time requests are served, between the data segment and the stack, growing towards the stack while the stack grows towards it.

Static allocation covers everything whose size is fixed at compile time: globals, static variables and ordinary local variables including fixed-size arrays. The compiler computes every address or stack offset; nothing has to be requested, and locals disappear automatically when their function returns. The price is rigidity: int marks[1000] holds 1000 marks even when a class has 60 (3760 bytes wasted) and cannot hold 1001.

Dynamic allocation takes memory from the heap during execution, in any amount, and keeps it until the program releases it, regardless of which function asked. That lifetime rule is what linked structures need: a node created inside insert() must survive after insert() returns.

All four are declared in <stdlib.h> and work in bytes, so sizes are always written with sizeof.

Worked example

Question. Write a C program that reads the number of students n, allocates exactly enough memory for their marks, reads the marks, then grows the array to hold two late admissions, prints the total, and releases the memory. Show the memory sizes at each stage for n = 5 and the output for marks 72, 65, 88, 91, 54 and late marks 60, 70. Compare with a static array int marks[100].

Solution. In C:

#include <stdio.h>
#include <stdlib.h>
int main(void) {
    int n, i, total = 0;
    scanf("%d", &n);                               /* n = 5 */
    int *marks = malloc(n * sizeof(int));           /* 5 * 4 = 20 bytes */
    if (marks == NULL) { printf("no memory\n"); return 1; }
    for (i = 0; i < n; i++) scanf("%d", &marks[i]);
    int *bigger = realloc(marks, (n + 2) * sizeof(int));   /* 7 * 4 = 28 bytes */
    if (bigger == NULL) { free(marks); return 1; }
    marks = bigger;                                 /* the block may have moved */
    scanf("%d %d", &marks[n], &marks[n + 1]);
    n = n + 2;
    for (i = 0; i < n; i++) total += marks[i];
    printf("students %d total %d\n", n, total);
    free(marks);                                    /* 28 bytes back to the heap */
    marks = NULL;
    return 0;
}

Exam traps

  • Three different "statics": static allocation (compile-time sizing), the C keyword static (a variable that keeps its value between calls, stored in the data segment) and a "static data structure" (an array that cannot grow). State which one the question means.
  • malloc does not zero the memory; calloc does. Printing a freshly malloc'd array as if it held zeros is a classic lost mark.
  • Writing p = realloc(p, bigger) loses the original block if realloc returns NULL; store the result in a second pointer first, as in the example.
  • Memory leak (allocated, never freed) and dangling pointer (freed, still used) are different bugs. After free(p) set p = NULL so the second cannot happen silently.
  • Examiners' favourite: "Compare static and dynamic memory allocation" expects the table above (when, where, growth, release, speed, failure), not a description of malloc alone.

1.4 Algorithms: characteristics and development

An algorithm is a finite list of unambiguous steps that turns an input into the required output. The definition is what separates a method you can analyse from a program you merely hope works. Only SRM ("Characteristics of algorithms") and NIT Trichy ("Development of Algorithms") list this chapter; elsewhere it is assumed. Learn the five properties and the development steps; the rest of the unit measures what they produce.

The five characteristics

Knuth's definition gives an algorithm five properties, and examiners ask for all five by name. Input: zero or more quantities supplied before it starts. Output: at least one quantity produced, related to the input. Definiteness: every step is precise and unambiguous ("divide a by b" is not definite unless b ≠ 0 is settled). Finiteness: it stops after a finite number of steps for every valid input. Effectiveness: every step is basic enough to be carried out exactly, by hand if needed, in finite time. A program that may loop forever is not an algorithm; a recipe saying "add salt to taste" fails definiteness.

Developing an algorithm

  1. Understand the problem and write its specification: what is given, what is wanted, what cases are valid (gcd of two positive integers).
  2. Choose a strategy: brute force, divide and conquer, greedy, dynamic programming, or a known result (Euclid: gcd(a, b) = gcd(b, a mod b)).
  3. Express it in pseudocode or a flowchart, language-independent but definite.
  4. Trace it by hand on small inputs, including edge cases (b = 0, a = b).
  5. Prove or argue correctness and termination: why each loop ends and what is true when it does.
  6. Analyse time and space (chapters 1.5 to 1.8), then implement, test and refine.

  • Pseudocode and flowcharts are notations for an algorithm, not algorithms themselves; a question asking for "characteristics" wants the five properties, not a flowchart.

1.5 Time and space complexity

The complexity of an algorithm is its cost written as a function of the size of its input: time complexity T(n) counts the basic steps it performs, space complexity S(n) counts the memory it needs, both for an input of size n. We count steps, not seconds, because seconds depend on the machine, the compiler and what else is running, while the step count depends only on the algorithm. This chapter teaches the counting; chapter 1.6 teaches the notation for writing the result. Christ lists it as "Space and time complexity of an algorithm", NIT Calicut as "Time and space complexity analysis", SRM under "Algorithm Basics".

You need: what an algorithm is (chapter 1.4) and the stack/heap picture of chapter 1.3 for space.

Steps, not seconds: the model

Analysis assumes a simple machine, the RAM model: one processor, memory cells reached in one step, and every basic operation (an assignment, an arithmetic operation, a comparison, an array access, a pointer dereference) costing one unit of time. Under this model the running time of an algorithm on a given input is the number of basic operations it executes, and the time complexity T(n) is that number as a function of the input size n. What "size" means depends on the problem: the number of elements for an array or list, the number of nodes and edges for a graph, the number of digits or bits for a numeric algorithm. Say which you mean.

Two programs that both take "about a second" today may differ enormously at ten times the input, and only the function T(n) predicts that. The same program measured on a laptop and on a phone gives two times but one T(n).

Counting time: the step-count table

The reliable way to find T(n) is to tabulate the program: for each statement, the steps per execution (s/e), the number of times it is executed (frequency), and their product. Three rules do most of the work.

  1. A simple statement (assignment, arithmetic, return) costs 1 step each time it runs.
  2. A loop header for (i = 0; i < n; i++) is evaluated n + 1 times (n tests that pass and the final one that fails); its body runs n times. A loop from i to n − 1 runs n − i times.
  3. Statements in sequence add; nested loops multiply, so a loop body inside two n-loops runs n × n = n² times.

Sum the last column to get T(n) as a polynomial; the leading term decides the growth and is what chapter 1.6 keeps.

Counting space

The space complexity of a program has a fixed part and a variable part: S(P) = c + SP(instance). The fixed part c covers the code, constants and simple variables, and does not depend on the input. The variable part depends on the instance: arrays sized by n, nodes allocated during the run, and the stack frames of recursive calls (one frame per active call, chapter 1.8). Most answers quote the auxiliary space, the extra memory beyond the input itself: a loop that sums an array uses O(1) auxiliary space however long the array is; a recursive version uses n frames. State whether you are counting the input or only the extra space.

Why the growth rate is what matters

At n = 1000, log₂ n ≈ 10, n log₂ n ≈ 10,000, n² = 10⁶, n³ = 10⁹ and 2ⁿ ≈ 10³⁰¹. On a machine doing 10⁹ steps a second, an n² algorithm finishes in a millisecond, an n³ one in a second, and a 2ⁿ one not before the universe ends. Figure 1.5.1 plots the common functions for small n; the ordering they settle into, 1 < log n < n < n log n < n² < n³ < 2ⁿ, is what every later chapter means by "faster" and "slower".

1.6 Asymptotic notations: Big-O, Omega and Theta

Chapter 1.5 produced counts such as T(n) = 2n² + 2n + 3. Asymptotic notation throws away what stops mattering as n grows, the constant 2 and the terms 2n + 3, and keeps the shape, n². Big-O says a function grows no faster than a given rate, Omega (Ω) says at least as fast, Theta (Θ) says at the same rate. Each is a precise statement with constants you can exhibit, and examiners ask you to exhibit them. SRM lists "Big-O, Big-Ω, Big-Θ", Christ "Types of asymptotic notations and orders of growth", IIT Delhi "asymptotic analysis", NIT Trichy "Notations and analysis".

You need: the step counts of chapter 1.5.

The three definitions

Let f(n) be the cost of an algorithm and g(n) a simple reference function (n, n², log n). All three notations compare f with a constant multiple of g for all large n: n₀ is the point from which the comparison must hold, and c (or c₁, c₂) is the multiple.

  • Big-O (upper bound). f(n) = O(g(n)) if there exist constants c > 0 and n₀ ≥ 1 such that f(n) ≤ c·g(n) for every n ≥ n₀. Read: f grows no faster than g.
  • Big-Omega (lower bound). f(n) = Ω(g(n)) if there exist c > 0 and n₀ such that f(n) ≥ c·g(n) for every n ≥ n₀. Read: f grows at least as fast as g.
  • Big-Theta (tight bound). f(n) = Θ(g(n)) if there exist c₁, c₂ > 0 and n₀ such that c₁·g(n) ≤ f(n) ≤ c₂·g(n) for every n ≥ n₀. Equivalently f = O(g) and f = Ω(g) together. Read: f grows at the same rate as g.

Two strict versions exist: little-o, f = o(g), means f/g → 0 (f is eventually smaller than c·g for every c, however small), and little-omega is its mirror. They appear in some syllabi (Christ's "types of asymptotic notations") and rarely in exams beyond their definitions.

Rules that make the notation quick

  1. Drop constant factors: 5n² = Θ(n²), and 3 = Θ(1).
  2. Keep only the fastest-growing term: 2n² + 2n + 3 = Θ(n²); n log n + n = Θ(n log n).
  3. Sequence adds, so the larger term wins: O(n) followed by O(n²) is O(n²). Nesting multiplies: an O(log n) search inside an O(n) loop is O(n log n).
  4. The base of a logarithm does not matter inside the notation, since loga n = logb n / logb a, a constant factor.
  5. Any polynomial is eventually smaller than any exponential (n¹⁰⁰ = O(1.01ⁿ)) and any power of log n is smaller than any positive power of n (log² n = O(√n)).

The growth classes in increasing order, with the names examiners expect: constant Θ(1), logarithmic Θ(log n), linear Θ(n), linearithmic Θ(n log n), quadratic Θ(n²), cubic Θ(n³), exponential Θ(2ⁿ), factorial Θ(n!).

Reading a bound correctly

O(g) is a set of functions, and "f = O(g)" means f belongs to it; the equals sign is one-way. Because it is only an upper bound, a true statement can be loose: linear search is O(n), and also O(n²), and also O(2ⁿ). Analysts therefore prefer Θ when they know the exact rate and reserve O for "no worse than". The notation says nothing about inputs: "worst case" and "best case" are about which input is given (chapter 1.7); O, Ω and Θ are about how a function grows. Each case has its own Θ: linear search is Θ(1) in the best case and Θ(n) in the worst.

Worked example

Question. (a) Show that f(n) = 2n² + 5n + 3 is Θ(n²) by finding constants c₁, c₂ and n₀. (b) Arrange in increasing order of growth: 100, log₂ n, √n, n, n log₂ n, n², 2ⁿ, n!, and justify with values at n = 16. (c) Is 2ⁿ⁺¹ = O(2ⁿ)? Is 2²ⁿ = O(2ⁿ)?

Solution. (a) Lower bound: 2n² ≤ 2n² + 5n + 3 for every n ≥ 0, since 5n + 3 ≥ 0; so c₁ = 2 works from n₀ = 1. Upper bound: we want 2n² + 5n + 3 ≤ 3n², i.e. n² − 5n − 3 ≥ 0. The roots of n² − 5n − 3 are (5 ± √37)/2, the positive one ≈ 5.54, so the inequality holds for n ≥ 6. Check: n = 6 gives 72 + 30 + 3 = 105 ≤ 108 ✓; n = 5 gives 78 > 75 ✗. Therefore with c₁ = 2, c₂ = 3, n₀ = 6: 2n² ≤ f(n) ≤ 3n² for all n ≥ 6, and f(n) = Θ(n²). (A quicker, equally valid choice: c₂ = 10, n₀ = 1, because 2n² + 5n + 3 ≤ 2n² + 5n² + 3n² = 10n² for n ≥ 1. Constants are not unique; any pair that works earns the marks.)

(b) At n = 16: log₂ 16 = 4; √16 = 4; n = 16; n log₂ n = 64; 100; n² = 256; 2ⁿ = 65,536; 16! ≈ 2.09 × 10¹³. Order by growth: 100 < log₂ n < √n < n < n log₂ n < n² < 2ⁿ < n!. Two notes: the constant 100 is largest at n = 16 but is Θ(1) and is overtaken by every other function (by n at n = 101); and log₂ n ties √n at n = 16 but loses from then on (n = 64: 6 against 8), by rule 5.

(c) 2ⁿ⁺¹ = 2 · 2ⁿ ≤ c · 2ⁿ with c = 2, so yes, 2ⁿ⁺¹ = O(2ⁿ) (in fact Θ). 2²ⁿ = 4ⁿ, and 4ⁿ / 2ⁿ = 2ⁿ grows without bound, so no constant c satisfies 4ⁿ ≤ c · 2ⁿ for all large n: 2²ⁿ ≠ O(2ⁿ).

Exam traps

  • Big-O is not "worst case" and Ω is not "best case". The cases are about inputs; the notations are about growth. Say "worst-case time is Θ(n²)" rather than "the Big-O is the worst case".
  • An O bound may be loose. "Bubble sort is O(n³)" is true and earns nothing; give the tight class, Θ(n²), or the smallest O you can prove.
  • When proving a bound, state c and n₀ and verify the inequality at n₀; a proof that only says "ignore lower terms" is a rule, not a proof.
  • O(1) means bounded by a constant, not "one step": an operation that always takes 50 steps is O(1).
  • n² and 2ⁿ are not neighbours: n² is polynomial (quadratic), 2ⁿ is exponential, and 2ⁿ /n² → ∞. Similarly log n is far below √n, and n log n is far below n².

1.7 Best, worst and average case analysis

Fix the input size n. Different inputs of that size can still cost very different amounts: searching a list of 1000 names for the first name takes one comparison, for a name that is not there takes 1000. The best case is the cheapest input of size n, the worst case the dearest, and the average case the expected cost over all inputs of size n under some assumed probability distribution. Each case is a function of n in its own right and gets its own Θ. Anna Univ, SRM, NIT Trichy, NIT Surathkal and Christ all list the three by name; Christ adds "algorithm efficiency", which is the reason to compute them.

You need: step counting from chapter 1.5 and the notations of chapter 1.6.

Three measures for one input size

Write T(I) for the number of steps on a particular input I, and let I range over all inputs of size n.

  • Worst case W(n) = max of T(I) over all I of size n. It is a guarantee: no input of size n costs more. It is the standard measure, quoted when nothing else is said, because guarantees are what systems need and because it is usually the easiest to compute.
  • Best case B(n) = min of T(I). Rarely useful on its own (an algorithm cannot be chosen for its luckiest input), but it exposes the structure of the algorithm and is a favourite short question.
  • Average case A(n) = Σ P(I) · T(I), the expected cost when input I occurs with probability P(I). It needs an assumption about the distribution, most often "every arrangement equally likely" or "the key is equally likely to be at any position", and the assumption must be stated with the answer.

Some algorithms have no spread at all. Finding the maximum of n numbers compares every element with the running maximum, n − 1 comparisons for every input; best, worst and average coincide. Others spread widely: insertion sort does n − 1 comparisons on sorted input and n(n − 1)/2 on reversed input, and binary search finds a key in 1 comparison when it sits in the middle and ⌊log₂ n⌋ + 1 when it does not (Unit 6 derives these).

Linear search: the derivation examiners want

Linear search compares the key with a[0], a[1], … until it matches or the array ends. Count comparisons for an array of n elements.

  1. Best case: the key is a[0]. One comparison: B(n) = 1, so Θ(1).
  2. Worst case: the key is a[n − 1] or absent. Every element is compared: W(n) = n, so Θ(n).
  3. Average case, successful search, key equally likely at each of the n positions: position i (counting from 1) costs i comparisons with probability 1/n, so A(n) = (1 + 2 + … + n)/n = n(n + 1)/(2n) = (n + 1)/2, which is Θ(n).
  4. Average case allowing failure: if the key is present with probability p (and absent with probability 1 − p, costing n), A(n) = p · (n + 1)/2 + (1 − p) · n.

Note the result of step 3: the average is about half the worst case, but half of a linear function is still linear, so the average-case class is the same as the worst-case class. That is common; the cases differ in class only when the algorithm's structure changes with the input, as in insertion sort (Θ(n) best, Θ(n²) worst) or quicksort (Θ(n log n) average, Θ(n²) worst).

Cases and notations are different axes

A case picks an input; a notation bounds a function. So every combination is meaningful: the worst case of linear search is Θ(n), which also makes it O(n) and Ω(n); its best case is Θ(1). The sloppy sentence "linear search is O(n) in the worst case and Ω(1) in the best" is true but weak, because Ω(1) says almost nothing; give Θ for each case when you can. The word amortised is a fourth, different measure (average over a sequence of operations on one structure, with no probability involved) and is not the average case.

Worked example

Question. The array a = [12, 7, 30, 25, 9, 48] is searched linearly. (a) Give the number of comparisons in the best case, the worst case and the average case (successful search, each position equally likely), and the Θ class of each. (b) If a search succeeds with probability 0.5, what is the average number of comparisons? (c) For the same array, how many comparisons does "find the maximum" make in its best and worst case?

Solution. (a) n = 6. Best case: key = 12, found at a[0]: 1 comparison, Θ(1). Worst case: key = 48 at a[5], or any absent key such as 50: 6 comparisons, Θ(n). Average case, successful: positions 1 to 6 cost 1 to 6 comparisons, each with probability 1/6, so A = (1 + 2 + 3 + 4 + 5 + 6)/6 = 21/6 = 3.5, which equals (n + 1)/2 = 7/2 ✓ and is Θ(n).

(b) With p = 0.5: A = p · (n + 1)/2 + (1 − p) · n = 0.5 × 3.5 + 0.5 × 6 = 1.75 + 3 = 4.75 comparisons. The possibility of failure pulls the average towards the worst case.

(c) Find-maximum compares a[1] … a[5] with the current maximum in turn: 5 comparisons for this array and for every other array of six elements. Best = worst = average = n − 1 = 5, Θ(n) in all cases; no input is lucky or unlucky.

Exam traps

  • Best case is not "small n". All three cases are for the same n; they differ in which input of that size is given.
  • Writing the average of linear search as n/2 is sloppy; the exact value is (n + 1)/2, and examiners who ask for it want the derivation Σ i/n.
  • An average needs a stated distribution. "Average case" without "each position equally likely" (or "each permutation equally likely") is incomplete.
  • The worst case of a search includes the unsuccessful search; forgetting it is the commonest slip in the "key absent" variant.
  • Examiners' favourite: "Derive the best, worst and average case of linear search" or the same for insertion sort or binary search (Unit 6). Lay out the four steps above every time.

1.8 Recursion and analysis of recursive algorithms

A recursive function solves a problem by calling itself on a smaller instance of the same problem, until an instance is small enough to answer directly. It exists because many structures are defined that way (a list is an item followed by a list; a tree is a root with subtrees) and the code that follows the definition is short and obviously right. Its cost cannot be read off a step-count table, because the table would contain the function itself; instead you write a recurrence relation and solve it. Manipal and SRM list "Recursion"; Christ lists "Analysis of non-recursive and recursive algorithms", which is the second half of this chapter.

You need: the stack frames of chapter 1.3 and the notations of chapter 1.6.

Anatomy of a recursive function

Every correct recursive function has two parts. The base case answers the smallest instances without recursion (0! = 1; an empty list has length 0). The recursive case reduces the problem to one or more strictly smaller instances and combines their answers (n! = n × (n − 1)!). The reduction must move towards a base case on every path, or the calls never end.

At run time each call gets its own stack frame holding its parameters, locals and return address (chapter 1.3). Calling fact(4) stacks frames for fact(4), fact(3), fact(2), fact(1), fact(0); only when fact(0) returns do the frames unwind, each multiplying the value it receives (Figure 1.8.1). The number of frames alive at once is the recursion depth, and it is the space cost of recursion. A missing base case means the depth grows until the stack segment is exhausted: a stack overflow.

Textbooks classify recursion by shape: direct (f calls f) versus indirect (f calls g, g calls f); linear (one recursive call per activation: factorial) versus binary or tree recursion (two or more: Fibonacci, merge sort); and tail recursion, where the recursive call is the last action (Euclid's gcd), which a compiler can turn into a loop. Any recursion can be rewritten as iteration with an explicit stack (Unit 3), saving frame overhead; recursion stays the natural form for trees and divide-and-conquer.

Recurrence relations: reading the cost off the code

A recurrence expresses T(n), the cost for size n, in terms of T at smaller sizes plus the work done in the current call. Write it in two lines from the code: the base case cost, and for the recursive case (number of calls) × T(their size) + (local work). Then solve it by back-substitution: unroll the recurrence a few times, spot the pattern after k steps, choose k so that the argument reaches the base case, and add everything up. Recurrence: the base case does one comparison and one return, T(0) = 2; the recursive case does a comparison, a multiplication and a return around one smaller call, T(n) = T(n − 1) + 3 for n ≥ 1. Back-substitution: T(n) = T(n − 1) + 3 = T(n − 2) + 6 = … = T(n − k) + 3k; with k = n, T(n) = T(0) + 3n = 3n + 2, so T(n) = Θ(n). An iterative loop does the same 3n + 2 work in Θ(1) space, the price recursion pays here.

Worked example 2

Question. Moving n discs in the Tower of Hanoi takes T(n) = 2T(n − 1) + 1 moves with T(1) = 1. Solve the recurrence and evaluate it for n = 3, n = 10 and n = 64.

Solution. Unroll: T(n) = 2T(n − 1) + 1 = 2[2T(n − 2) + 1] + 1 = 4T(n − 2) + 2 + 1 = 8T(n − 3) + 4 + 2 + 1. After k steps, T(n) = 2ᵏ T(n − k) + (2ᵏ − 1). Choose k = n − 1 to reach T(1): T(n) = 2ⁿ⁻¹ · 1 + 2ⁿ⁻¹ − 1 = 2ⁿ − 1, so T(n) = Θ(2ⁿ). Check against the recurrence: 2(2ⁿ⁻¹ − 1) + 1 = 2ⁿ − 1 ✓. Values: n = 3 gives 2³ − 1 = 7 moves; n = 10 gives 1023; n = 64 gives 2⁶⁴ − 1 ≈ 1.8 × 10¹⁹, which at one move per second is about 5.8 × 10¹¹ years. Each extra disc doubles the work: the signature of an exponential recurrence, and the reason the table above separates 2T(n − 1) from 2T(n/2).

Exam traps

  • No base case, or a base case that some inputs skip (fact(−1) never reaches n == 0), gives infinite recursion and a stack overflow, not a wrong answer.
  • T(n) = 2T(n/2) + n is Θ(n log n), not Θ(n²): two calls on half the input are very different from one call on n − 1. Keep halving (log n levels) separate from decrementing (n levels).
  • Time and space differ: binary search's recursion is Θ(log n) in both, merge sort is Θ(n log n) time but only Θ(log n) stack depth. Depth, not total calls, gives the space.
  • Naive Fibonacci is not "O(n) because there are n numbers": the call tree has about φⁿ nodes. Memoisation (Beyond) fixes it.
  • Examiners' favourite: "Write the recurrence for this recursive function and solve it" expects the two-line recurrence read off the code, the unrolling with k, the value of k that hits the base case, and the final Θ.

Analyze A student rewrites the recursive factorial as a loop and reports it "ten times faster". Does the recurrence predict that? What changed? 4 marks

What changed is the constant: each recursive call pushes a frame, saves registers and returns, several instructions beyond the one multiplication, and the loop avoids all of that in Θ(1) space. The speed-up is a constant factor, plausibly large for so tiny a body, and would stay about the same at every n rather than grow.

1.9 Implementing ADTs with classes and objects

A class is the programming-language tool that turns an ADT specification into code: its attributes hold the representation, its methods are the ADT's operations, and the language lets you hide the first behind the second. An object is one instance of the class, with its own state. Chapter 1.2 drew the wall between interface and implementation; this chapter shows how a class builds that wall, how inheritance lets one class extend another, and what the copying of objects does to an ADT's hidden data. Anna Univ lists this as "ADTs and classes, introduction to OOP, Classes in Python, Inheritance, Namespaces, Shallow and Deep Copying"; NIT Surathkal as "Objects and Classes" with the object-oriented pillars; IIT Delhi as "Object oriented programming". The code is Python; C++ and Java differ in syntax, not in idea.

You need: the ADT specification of chapter 1.2.

From specification to class

Take the Set ADT of chapter 1.2: add(x), remove(x), contains(x), size(). A Python class implements it in three moves. The constructor __init__ creates the representation when an object is made, here an empty list stored in the attribute self._items. Each ADT operation becomes a method, a function inside the class whose first parameter self is the object being operated on. The representation is hidden: the leading underscore in _items tells users not to touch it (C++ and Java enforce this with private), so the only way in is through the methods. A user writes s = IntSet(), s.add(5), s.contains(5) and never learns that a list is inside.

Because the representation is hidden, it can change. The same class could keep a sorted list (faster contains by binary search, Unit 6) or a hash table (Unit 6) without any user noticing, which is the ADT promise of chapter 1.2 made concrete.

The four pillars, seen from an ADT

  • Encapsulation: data and the operations on it live in one unit, the class, and the data is reachable only through the operations. It keeps the ADT's invariants true (no duplicates in a set) because no outside code can break them.
  • Abstraction: users see the interface (method names, arguments, results, preconditions), not the representation. It is the ADT specification itself.
  • Inheritance: a new class is defined as an extension of an existing one, keeping its methods and adding or overriding some. class CountingIntSet(IntSet) below adds a counter and overrides add, calling the parent's version with super().add(x).
  • Polymorphism: the same operation name works on objects of different classes, each in its own way. Client code written for an IntSet runs unchanged on a CountingIntSet, and a sorted or hashed implementation could be substituted the same way.

NIT Surathkal's list adds the benefits that follow: modularity (each class is a separate unit), reusability (the class is used in many programs), maintainability (a fix inside the class fixes every user) and scalability (new classes extend old ones without rewriting them).

Namespaces and copying

Python resolves a name such as s.add through a chain of namespaces: first the object's own (instance attributes created in __init__, such as _items), then the class's (methods, and any class attributes shared by all instances), then the base classes'. Two objects of one class therefore have separate _items lists but share one add method. A class attribute that is a mutable object is shared by every instance, a classic bug.

Copying an object copies its namespace, and here the hidden representation matters. A shallow copy (copy.copy(s)) makes a new object whose attributes refer to the same inner objects, so the copy and the original share one _items list and an add to either shows in both. A deep copy (copy.deepcopy(s)) copies the inner objects recursively, giving two independent sets. The worked example shows both. Assignment, t = s, copies nothing at all: both names refer to one object.

Worked example

Question. Implement the IntSet ADT as a Python class with a hidden list, then a subclass CountingIntSet that counts how many add calls were made. Trace: s = CountingIntSet(); s.add(5); s.add(3); s.add(5); s.contains(3); s.size(); s.adds; s.remove(3). Then show the difference between a shallow and a deep copy of s.

import copy

class IntSet:
    def __init__(self):
        self._items = []                 # hidden representation

    def add(self, x):
        if x not in self._items:         # keep the no-duplicates invariant
            self._items.append(x)

    def remove(self, x):
        self._items.remove(x)            # precondition: x is present

    def contains(self, x):
        return x in self._items

    def size(self):
        return len(self._items)

class CountingIntSet(IntSet):
    def __init__(self):
        super().__init__()
        self.adds = 0

    def add(self, x):                    # overrides, then reuses the parent
        self.adds += 1
        super().add(x)

Exam traps

  • A class is not an ADT; it is one implementation of it. The ADT is the specification (chapter 1.2); the class is code with a chosen representation.
  • Forgetting self as the first parameter, or calling add(x) instead of self.add(x) inside the class, is the commonest Python error in answers.
  • A class attribute (defined in the class body) is shared by all objects; an instance attribute (set through self in __init__) belongs to one object. Writing items = [] in the class body makes every set share one list.
  • Assignment, shallow copy and deep copy are three different things: t = s gives one object with two names; copy.copy gives a new object sharing inner data; copy.deepcopy gives a fully independent object.
  • Examiners' favourite: "Implement the X ADT as a class and demonstrate inheritance" expects the constructor, the hidden representation, every operation as a method, a subclass that overrides one method with super(), and a short trace.

7. (a) Prove that 3n² + 2n + 1 = Θ(n²), exhibiting constants. (b) Show that n log₂ n = O(n²) but n log₂ n ≠ Ω(n²). (c) Arrange 50, log n, n, n log n, n², 2ⁿ, n! in increasing order of growth with values at n = 10. (12 marks)

(a) Lower: 3n² ≤ 3n² + 2n + 1 for n ≥ 0, c₁ = 3. Upper: 3n² + 2n + 1 ≤ 3n² + 2n² + n² = 6n² for n ≥ 1, c₂ = 6, n₀ = 1. (b) n log n ≤ n · n = n² for n ≥ 1, so O(n²) with c = 1; for Ω we would need n log n ≥ c n², i.e. log n ≥ c n, false for large n since log n / n → 0. 8. Derive the best, worst and average number of comparisons of linear search on n elements, stating assumptions. Evaluate for n = 10, then for n = 10 when 30% of searches are for absent keys. (10 marks)

9. Write a recursive function to compute the sum of the first n natural numbers. Trace it for n = 4, write its recurrence, solve by back-substitution, and give the time and space complexity. Then solve T(n) = 2T(n/2) + n with T(1) = 1 for n = 8. (12 marks)

sum(n) = 0 if n = 0 else n + sum(n − 1). Trace: sum(4) = 4 + sum(3) = 4 + 3 + 2 + 1 + 0 = 10, with 5 frames at the deepest point. Recurrence T(n) = T(n − 1) + c, T(0) = c′; unroll to T(n) = nc + c′ = Θ(n); space Θ(n) from n + 1 frames. Second recurrence: T(8) = 2T(4) + 8 = 2(2T(2) + 4) + 8 = 4T(2) + 16 = 4(2T(1) + 2) + 16 = 8 + 8 + 16 = 32; in general n log₂ n + n = Θ(n log n).

10. Implement a Stack of integers as a Python class with push, pop, top, is_empty and size, hiding the representation. Derive a subclass that refuses to grow beyond a capacity given to its constructor. Trace push 4, push 9, push 2 on a capacity of 2, then pop. (12 marks)

Class with self._items = []; push appends; pop requires non-empty (precondition) and returns the last item; top reads it; size uses len. 12. A phone-contacts app must look up a name very frequently, add a contact occasionally, and list all contacts in alphabetical order on demand. Choose a data structure class, specify the ADT the app needs, propose two implementations and compare their operation costs with Big-O. (16 marks; spans chapters 1.1, 1.2, 1.5, 1.6)

Operations: search(name) dominant, insert(name, number) occasional, listSorted(). ADT: a Map from name to number with those three operations and preconditions (search on absent name returns not-found). Implementation A: sorted array; search by binary search O(log n), insert O(n) shifts, listing O(n). Implementation B: unsorted linked list; search O(n), insert O(1) at front, listing needs a sort O(n log n). Since search dominates, A wins; mention that Unit 4's search trees and Unit 6's hashing improve insert while keeping search fast. Marks for naming linear vs non-linear choices, the ADT spec, the cost table and the justified recommendation.

13. Compare recursive and iterative solutions of the factorial (or array-sum) problem on time, space and clarity. Support each claim with a step count or recurrence, and state when you would still choose recursion. (12 marks; spans chapters 1.5 and 1.8)

Iterative: step-count table gives T(n) = 2n + 3 or similar, auxiliary space Θ(1). Recursive: recurrence T(n) = T(n − 1) + c → Θ(n), same class; space Θ(n) from n + 1 frames, plus call overhead as a constant factor. Clarity: recursion mirrors the mathematical definition. Choose recursion when the data is recursive (trees, divide and conquer) or depth is small; choose iteration for deep linear recursion (stack overflow risk, Python's depth limit).

14. "An O(n²) algorithm is always slower than an O(n log n) algorithm." Evaluate this statement using the definitions of the notations, the role of constants and n₀, and best/worst/average cases, with a numeric example. (12 marks; spans chapters 1.6 and 1.7)

Three objections: O is an upper bound, so the O(n²) algorithm may really be Θ(n); constants and n₀ matter for small n (100 n log n exceeds n² until n ≈ 1000); and the bounds may refer to different cases (insertion sort is Θ(n) on nearly sorted input while a Θ(n log n) sort stays Θ(n log n)). Statement holds only for tight bounds, large n and the same case. Marks for citing definitions, a numeric crossover and a case-based counterexample.

15. A student stores a linked list's nodes in a static array of 10,000 node structures "to avoid malloc". Evaluate the design against dynamic allocation on memory use, flexibility, speed and failure behaviour, for lists of 50 and of 12,000 nodes. (10 marks; spans chapters 1.1 and 1.3)

Memory: the static pool reserves 10,000 nodes always (for 50 nodes almost all wasted); dynamic allocates exactly what is used. Flexibility: 12,000 nodes cannot fit the static pool at all, dynamic grows until the heap is exhausted. Speed: the static pool avoids allocator calls and may be faster and more cache-friendly, which is why real systems use pools for fixed workloads. Failure: static pool fails silently when full unless checked; malloc returns NULL. Verdict: a pool is a legitimate technique when the maximum is known; as a way to "avoid malloc" for unknown sizes it fails.

Glossary

Data structure
An organisation of data in memory together with the relationships among the values and the operations applied to them.
Primitive data type
A type built into the language (int, float, char, double, pointer) from which other structures are built.
Linear structure
A structure whose elements form one sequence, each with at most one predecessor and one successor.
Non-linear structure
A structure in which an element may be related to many others, as in a tree or a graph.
Abstract data type (ADT)
A data type specified by its values and the behaviour of its operations, independent of any implementation.
Precondition
What must be true before an operation may be called; postcondition: what is true after it.
Static allocation
Memory whose size is fixed at compile time, placed in the data segment or on the stack.
Dynamic allocation
Memory requested at run time from the heap, held until explicitly released.
Heap
The region of memory from which malloc, calloc and realloc serve requests.
Stack frame
The block pushed on the call stack for one function call: parameters, locals, return address.
Memory leak
Dynamically allocated memory that is never freed and can no longer be reached.
Dangling pointer
A pointer that still holds the address of a block that has been freed.
Algorithm
A finite sequence of unambiguous, effective steps that produces an output from an input.
Definiteness, finiteness, effectiveness
Three of the five properties of an algorithm: every step precisely specified; termination after finitely many steps for every valid input; every step basic enough to be carried out exactly in finite time.
Time complexity
The number of basic steps an algorithm performs, as a function T(n) of the input size.
Space complexity
The memory an algorithm needs, S(P) = c + SP(instance); auxiliary space excludes the input.
Step count
The method of tabulating steps per execution and frequency for each statement to obtain T(n).
RAM model
The abstract machine of analysis: one processor, constant-time memory access, unit-cost basic operations.
Big-O
f = O(g) when f(n) ≤ c·g(n) for all n ≥ n₀: an upper bound on growth.
Big-Omega (Ω)
f = Ω(g) when f(n) ≥ c·g(n) for all n ≥ n₀: a lower bound on growth.
Big-Theta (Θ)
f = Θ(g) when c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀: the same rate of growth.
Worst case
The maximum cost over all inputs of a given size; the best case is the minimum.
Average case
The expected cost over inputs of a given size under a stated probability distribution.
Recursion
A function defined in terms of itself on smaller instances, with a base case that stops it.
Recurrence relation
An equation giving T(n) in terms of T at smaller sizes plus the work of the current call; solved by back-substitution (unrolling until the base case, then summing).
Class and object
A class packages attributes and methods; an object is one instance of a class with its own state.
Encapsulation
Keeping data and the operations on it in one unit, with the data reachable only through the operations.
Inheritance
Defining a new class as an extension of an existing one, reusing and overriding its methods.
Polymorphism
The same operation name behaving according to the class of the object it is applied to.
Shallow copy
A new object whose attributes refer to the same inner objects as the original; a deep copy copies them recursively.
