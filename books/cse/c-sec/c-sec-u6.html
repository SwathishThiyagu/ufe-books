6.1 Firewalls: types and configurations

A firewall is a policy enforcement point. It sits between two networks and forwards only traffic that matches an ordered rule table. Each rule states a condition and an action, allow or deny. The first matching rule wins, and a final default-deny rule protects the rest. Firewalls exist because a network cannot trust every packet that arrives from the Internet or leaves for it. You meet them at home routers, in cloud security groups and in front of a company DMZ. This chapter covers rule tables, firewall types and common layouts.

You need: Unit 1 network attacks and port scanning, and Unit 5 VPN basics.

Rule tables and default deny

A firewall inspects each packet or connection at a boundary. The boundary can be between the Internet and a company LAN, between two internal subnets, or between a cloud network and the public Internet. The firewall applies a rule table in order. A rule has a match part and an action. The match part can name source address, destination address, protocol, source port and destination port. The action is allow or deny, often written accept or drop.

Order matters. The firewall compares a packet with rule 1, then rule 2, and stops at the first match. A broad allow placed above a specific deny hides the deny. Put specific rules first and a final default-deny rule last. Default deny means the firewall blocks anything not explicitly allowed. Default allow is unsafe because new services and mistakes pass without review.

  • Ingress filtering checks packets entering a network. Egress filtering checks packets leaving it.
  • Logging records time, source, destination, port, action and rule number. Logs support audit and incident response.
  • NAT translates private addresses to public addresses. It reduces direct exposure but is not a policy. Keep default deny after translation.
  • A stateless firewall needs rules for both directions. A stateful firewall records allowed connections and admits their replies.

Firewall types

A packet-filtering firewall, also called a screening router when it runs on a router, checks each packet against the rule table. It is fast and simple. It keeps no memory of earlier packets, so it needs a reverse rule for reply traffic. It cannot see application data inside a packet.

A stateful inspection firewall keeps a connection table. For a TCP connection, the table stores source, destination, ports and sequence state. When the server replies, the reply matches the table entry and is allowed without a separate reverse rule. The table has limits, so it can be exhausted by too many half-open connections.

An application-level proxy terminates the client connection and opens a second connection to the server. It can inspect HTTP, SMTP or DNS content and enforce user-level policy. It costs memory and CPU, and each proxied service needs support. A proxy hides internal hosts because the server sees the proxy address.

A next-generation firewall adds application identification, user identity and threat feeds to stateful filtering. Unified threat management combines a firewall with antivirus, intrusion prevention and web filtering. Only a few universities teach these details; keep the core idea: more inspection at the same policy point. IDS and IPS detail is in 6.2.

Configurations

The layout decides where inspection happens. A dual-homed host has two network interfaces and forwarding disabled. It can act as a proxy between the Internet and the LAN. A screened host puts a firewall on a router and a bastion host behind it. A screened subnet places public servers in a separate network called a DMZ.

  • Screening router: packet filtering on the border router. Cheap, but one device carries all policy.
  • Dual-homed host: one host with two interfaces, no IP forwarding, proxy services. A single failure point.
  • Screened host: border router filters traffic, then a bastion host applies stronger checks.
  • Screened subnet: firewall allows web and mail into a DMZ, and allows VPN and web into the internal LAN. The internal LAN is not directly reachable from the Internet.

In a screened subnet, the DMZ holds servers that need public access, such as a web server on TCP 443 and a mail server on TCP 25. The firewall allows those ports to the DMZ and allows only selected traffic, such as VPN and TCP 443, to the internal LAN. A DMZ limits damage: if a public server is compromised, the attacker still faces the firewall before the internal LAN. Security policy work is in 6.7.

Worked example

Question. A stateless firewall has rules in order: 1 allow TCP from 10.0.0.0/24 to 192.168.1.10 port 443; 2 deny TCP any to 192.168.1.10 port 23; 3 allow TCP any to 192.168.1.10 port 80; 4 deny all. State the decision for packets: (a) 10.0.0.5:50000 to 192.168.1.10:443, (b) 8.8.8.8:40000 to 192.168.1.10:23, (c) 10.0.0.5:50001 to 192.168.1.10:22.

  1. Packet (a): destination port is 443. Rule 1 allows TCP from 10.0.0.0/24; 10.0.0.5 is inside that prefix. The first match is rule 1, action allow.
  2. Packet (b): rule 1 fails because 8.8.8.8 is not in 10.0.0.0/24 and the destination port is 23, not 443. Rule 2 denies TCP to port 23; the first match is rule 2, action deny.
  3. Packet (c): rule 1 fails because the destination port is 22, not 443. Rule 2 fails because the destination port is 22, not 23. Rule 3 fails because the destination port is 22, not 80.
  4. No allow rule matches packet (c). The firewall reaches rule 4, deny all. The first match is rule 4, action deny.
  5. The deciding rule numbers are 1, 2 and 4 for packets (a), (b) and (c).

Answer. Packet (a) is allowed by rule 1, packet (b) is denied by rule 2, and packet (c) is denied by rule 4.

Exam traps

  • Default allow is unsafe: an unlisted service passes. Use a final default-deny rule.
  • First match wins, so a broad allow above a specific deny hides the deny. Put specific rules first.
  • A stateful firewall keeps a connection table and admits replies to allowed connections. A stateless firewall needs a separate reverse rule.
  • NAT changes addresses and ports; it is not a firewall and does not replace default deny.
  • An application proxy terminates the client connection; a packet filter forwards packets. They inspect at different layers.

6.2 Intrusion detection and prevention systems

A firewall follows rules you wrote in advance. An intrusion detection system (IDS) watches traffic or a host and raises an alert when it sees something suspicious. An intrusion prevention system (IPS) sits in the path of the traffic and can also drop the packet. Detection covers what a rule list cannot hold in advance: a new port scan, a strange login pattern, a known attack signature crossing an allowed port. Banks, cloud providers and campus networks run these sensors next to their firewalls, and analysts read the alerts on a console.

You need: 6.1 Firewalls for where a sensor sits in the network, and Unit 1 for the attacks and malware that the sensor is trying to detect.

Detect passively, prevent inline

An intrusion detection system is passive. It receives a copy of the traffic, from a switch SPAN port, a network tap, or an agent reading logs on a host, and it never sits in the path. If the IDS fails, traffic keeps flowing. When it sees something suspicious it writes an alert to a console, and maybe sends a syslog message or an email. The attack itself still reaches the target; a person or a script must respond.

An intrusion prevention system is inline. Traffic enters one interface and leaves another, so the device can drop a packet, reset a TCP connection, or block a source address for ten minutes. That power has a price. Every packet waits for the check, and one wrong block stops real work, such as a payment at a busy hour. Many products ship both modes and call the whole box an IDPS.

  • Host-based IDS (HIDS): an agent on one machine. It hashes important files, reads the system log, and watches processes and system calls. It sees traffic after the host decrypts it, but only for that host.
  • Network-based IDS (NIDS): a sensor on a link. It watches packets for many hosts at once. Traffic inside TLS stays unreadable without the keys (see Unit 5, SSL/TLS).

Placement follows the firewall logic of 6.1. Put a sensor outside the firewall to see attacks arriving from the internet, one in the DMZ beside the public servers, and one at the internal core to catch a laptop that is already infected.

How the engine decides: signature, anomaly, protocol state

A signature detector keeps a list of rules, each describing a pattern seen in earlier attacks. The engine compares every packet with the rules, and a match produces an alert. It is fast, cheap and explains itself, because the alert names the rule. It cannot catch an attack whose pattern is not in the list, which is the zero-day case.

An anomaly detector first learns a baseline of normal behaviour: packets per second on each port, usual login times, CPU use, DNS query sizes. It then scores each observation against that baseline and alerts when the score crosses a threshold. It can catch a new attack, and it also flags every legitimate change: a new application, a festival sale, a software update.

A stateful protocol detector parses the protocol instead of matching bytes. It checks that a TCP connection starts with SYN, that an HTTP request line has a method, a path and a version, and that the body length promised in a header matches what arrives. A request that breaks the grammar raises an alert even with no known attack pattern.

Rules are written in a small language. Fields differ between products; the shape is the same.

alert tcp any any -> 10.0.0.0/8 22 (
  msg:"repeated SSH logins";
  content:"SSH-";
  threshold:5 in 60s;
  sid:1001;
)

Here alert is the action, tcp is the protocol, any any is the source address and port, 10.0.0.0/8 22 is the destination network and port, msg is the text a human reads, threshold limits how often the rule may fire, and sid is the rule number.

Placement, tuning and the cost of wrong alerts

A NIDS interface runs in promiscuous mode: the network card hands every frame it sees on the segment to the sensor, not only frames addressed to the sensor's own MAC address. On a switched network a plain port sees only broadcast traffic, so the sensor needs a SPAN (mirror) port or a tap. A busy mirror can lose packets while copying them, so the sensor must report how many it dropped.

TP is attack packets alerted, FN is attack packets missed, FP is normal packets alerted, TN is normal packets not alerted. The first two rates are measured over the two real classes; precision is measured over the alerts. Multiply by 100 for a percentage.

The base rate decides how useful an alert is. When attacks are a tiny share of traffic, even a 3% false positive rate produces more false alerts than true ones, so precision falls while the detection rate still looks fine. Analysts tune with suppression rules, thresholds and whitelists, and they review the console every day, because an unread console is the same as no IDS.

One unusual sensor watches routing, not payload. It collects BGP announcements from peers and flags an anomaly, such as an autonomous system announcing a prefix it does not own, which is a hijack attempt. Full BGP security is outside this unit; only the detection idea matters here.

Worked example

Question. A signature-based NIDS watches a link for one hour and sees 1000 packets. 20 of them belong to a real attack. The system raises 48 alerts: 18 on attack packets and 30 on normal packets. Compute the detection rate, the false positive rate and the precision, and comment on the precision.

  1. Attack packets = 20. Normal packets = 1000 − 20 = 980.
  2. True positives TP = 18. False negatives FN = 20 − 18 = 2.
  3. False positives FP = 30. True negatives TN = 980 − 30 = 950.
  4. Check the alerts: TP + FP = 18 + 30 = 48, which matches the 48 alerts reported.
  5. Detection rate = TP ÷ (TP + FN) = 18 ÷ 20 = 0.90, that is 90%.
  6. False positive rate = FP ÷ (FP + TN) = 30 ÷ 980 = 0.03061, that is 3.06%.
  7. Precision = TP ÷ (TP + FP) = 18 ÷ 48 = 0.375, that is 37.5%.
  8. Comment: attack packets are only 2% of the traffic, so 30 false alerts outweigh the 18 true ones. Nearly two alerts in three are wrong, and each one costs an analyst time.

Answer. Detection rate 90%, false positive rate 3.06%, precision 37.5%; with attacks at 2% of traffic, most alerts are false.

Worked example 2

Question. Second example: in one minute a sensor sees 5000 packets, of which 10 are attack packets. It raises an alert on 8 attack packets and on 40 normal packets. Find the detection rate, the false positive rate and the precision.

  1. Normal packets = 5000 − 10 = 4990.
  2. TP = 8, FN = 10 − 8 = 2, FP = 40, TN = 4990 − 40 = 4950.
  3. Detection rate = 8 ÷ 10 = 0.80, that is 80%.
  4. False positive rate = 40 ÷ 4990 = 0.008016, that is 0.80%.
  5. Precision = 8 ÷ (8 + 40) = 8 ÷ 48 = 0.1667, that is 16.67%.

Answer. Detection rate 80%, false positive rate 0.80%, precision 16.67%.

Exam traps

  • An IDS copies traffic and only alerts; it cannot drop a packet. Only an inline IPS can block, and that is also why an IPS can break legitimate traffic.
  • Detection rate is not accuracy. Use TP ÷ (TP + FN), the share of real attacks caught, not TP ÷ total packets.
  • The false positive rate divides by the normal packets (FP + TN), not by all 1000 packets and not by the number of alerts.
  • A high detection rate with poor precision can still be useless when attacks are rare. Examiners like the line: 3% of 980 beats 90% of 20.
  • Signature detection misses zero-day attacks, anomaly detection catches them but flags legitimate new traffic, and a NIDS cannot read payload inside TLS.

6.3 Honeypots and honeynets

A honeypot is a decoy computer or service with no legitimate users. Its only purpose is to attract, record and study attacks. Because honest users never connect to it, any connection is suspicious and worth an alert. A honeynet is a small network of honeypots, often on one subnet, watched by an IDS. Security teams use honeypots for early warning, to collect attacker tools and to learn new scan patterns. Researchers use them to measure attacks. They are not production servers, so they must be isolated and handled with care.

You need: firewall rules and IDS monitoring; see Unit 1, Foundations for attacks and port scanning.

What a honeypot is and why it works

A honeypot is a decoy system whose only job is to be attacked. It has no real users and no real data. A connection to its address is therefore suspicious by definition. That is the core idea: the honeypot gives you a very low false-positive signal. A port scan, a login attempt or a worm probe that reaches it is recorded, not served. A production honeypot sits in an organisation to raise early alerts. A research honeypot collects samples, command sequences and attacker behaviour. Some syllabi call these deception systems.

Interaction level decides how much the attacker can do. A low-interaction honeypot emulates a few services, such as a fake SSH or HTTP banner, and logs the attempt. It is cheap, safe and easy to rebuild, but it sees only what it emulates. A high-interaction honeypot runs a real operating system and real applications. It records more, including post-exploitation steps, but it gives the attacker a real machine to use. That raises the escape and outbound-attack risk. Only a few universities teach high-interaction honeynets in detail; the design rule is the same: contain first, record second.

Decoy services are the listening parts: a fake telnet port, a web page that looks like a router login, a file share. They must look plausible but must not contain real credentials or real customer data. Logging is the product. Send logs to a remote collector so an attacker cannot delete them. Use timestamps and record source IP, port, time and payload hash.

Building a simple honeynet

A simple honeynet has four parts: a firewall, a switch, one or more decoys and an IDS sensor. The firewall owns the unused addresses. It redirects traffic for those addresses into the honeynet; the decoys never advertise themselves on the trusted LAN. The switch keeps the decoys on a separate VLAN. The IDS watches a mirror port, so it sees all honeynet traffic without sitting inline.

  1. Choose an unused block, for example 10.0.0.0/28.
  2. Put the honeynet behind its own firewall interface and switch VLAN.
  3. Add a redirect rule from each unused public or private address to a decoy address.
  4. Attach an IDS sensor to a mirror port and send logs to a remote collector.
  5. Limit outbound traffic from the honeynet; allow only what the research plan permits.

Containment is the part examiners look for. A high-interaction decoy is a real machine, so an attacker who escapes a virtual machine can reach the local network. Keep the honeynet off the trusted zone. Use a separate VLAN, host firewall rules, snapshots and a rebuild procedure. Data control matters too: capture only what you need, hash malware instead of running it, set a retention period and remove real secrets. A honeypot that is allowed to send unlimited outbound traffic can be used to attack others, which turns your sensor into a liability.

Law, ethics and operation

A honeypot is a monitored trap, so law and ethics matter. Record only what policy allows. Do not place real user credentials, real payment data or real private files on a decoy. Do not attack back. If the honeypot captures traffic from third parties, follow your organisation's data-retention and privacy rules. Legal duties differ by country; entrapment is mainly a law-enforcement concern, while a private honeypot usually faces privacy, data-protection and liability questions.

Operate it like a sensor, not a server. Patch the host outside the decoy, keep management on a separate network, and review alerts. An IDS alert from a honeypot is high value because the address should have no legitimate traffic. Still, a misconfigured client or an internet-wide scan can hit it, so confirm before you call it a targeted attack. If the honeypot is compromised, rebuild from a known image and keep the logs. A honeynet is useful only while it stays contained and believable.

Worked example

Question. A research honeynet is assigned the block 10.0.0.0/28. The network address is 10.0.0.0 and the broadcast address is 10.0.0.15. Reserve 10.0.0.1 for the gateway and 10.0.0.2 for the IDS sensor. (a) How many addresses does the block contain? (b) How many usable host addresses? (c) How many addresses remain for honeypots?   3. Usable hosts = 16 − 2 = 14, because network and broadcast are not hosts. The usable range is 10.0.0.1 to 10.0.0.14.

Exam traps

  • A honeypot sees only traffic sent to it. Silence does not prove the network is safe; it only proves nothing hit that decoy.
  • Low interaction is not a weaker firewall. It is a recorder with limited emulation; it may miss post-exploitation steps.
  • When you size a subnet, subtract the network and broadcast first, then subtract reserved addresses. For /28: 16 total, 14 usable, 12 after two reservations.
  • Do not put a honeypot inside the trusted zone. A real-OS decoy can be escaped or used as a pivot.
  • Any connection to a honeypot is suspicious, not automatically a targeted attack. Scans and misconfigured clients also arrive.

6.4 Program security: buffer overflow and malicious code

Program security studies flaws inside a running program. A memory-safety bug lets input change memory the programmer did not intend to change. The classic case is a stack buffer overflow in C. A separate class is malicious code: a virus, worm, trojan, logic bomb or backdoor that runs because someone placed it there. Both matter because a firewall can allow port 443 and still pass an attack that exploits a bug in the web server. The bug comes first, then the controls that make exploitation harder.

You need: Unit 1 malware basics and the C memory layout: text, data, heap and stack; for OS enforcement see Chapter 6.5.

Memory layout and unsafe C calls

When a C program runs, its address space is divided into regions. Text holds machine instructions. Data holds global and static variables. Heap holds memory from malloc and free. Stack holds function call frames: arguments, local variables, saved frame pointer EBP and return address EIP on 32-bit x86. The stack grows down on most systems, but textbook diagrams often draw low addresses on the left.

Many C library functions do not know the size of the destination. gets reads a line into a buffer with no limit. strcpy copies until the source null byte. sprintf formats into a buffer with no limit. strcat appends with no limit. If input is longer than the buffer, the extra bytes go to whatever follows in memory. That is a buffer overflow. A buffer overflow is usually a non-malicious program error, but an attacker turns it into an attack.

Safe replacements take a size: fgets(buf, sizeof buf, stdin), strncpy or snprintf. They still need care: strncpy may leave no null terminator, and snprintf returns the length that would have been written, not the length stored. The bug is not the function name; it is missing a bound.

Stack overflow, off-by-one and other memory bugs

A stack overflow writes past a local array and reaches the saved frame pointer and return address. On return, the CPU loads EIP from the overwritten slot and jumps to the attacker's chosen address. If the address points into the same buffer, the attacker can run injected machine code. Modern systems often block that with non-executable memory, so attackers reuse existing code instead. Return-oriented programming (ROP) chains short instruction sequences called gadgets that already exist in libraries. Only a few universities teach ROP and control-flow integrity in detail; the exam idea is that code reuse bypasses the need to inject code.

An off-by-one writes one byte too many. With strcpy, the null terminator is that extra byte. A one-byte overflow can change the low byte of the saved EBP, which can shift later references. An integer overflow makes a size calculation wrap: if len is unsigned 16-bit and len + 1 is 65536, it becomes 0, so a check passes and a copy still overflows. A heap overflow corrupts heap metadata or adjacent objects; exploitation is allocator-specific. A format-string bug happens when user input is passed as the format: printf(input). The %n conversion writes the number of bytes printed so far to a pointer taken from the argument list. The fix is printf("%s", input).

Malicious code classes

Malicious code is code with an unwanted effect. A virus attaches to a host file or boot sector and spreads when the host runs. A worm spreads by itself over a network, often by exploiting a service; it does not need a user to open a file. A trojan looks useful but carries a hidden payload; it does not self-replicate. A logic bomb waits for a condition, such as a date or a missing employee record, then acts. A backdoor is a hidden way in, left by an attacker or sometimes by a vendor for support. Spyware, ransomware and rootkits are further labels; a rootkit hides the attacker's presence.

Program security and malicious code meet at the exploit. A worm can use a buffer overflow to enter a host and then install a backdoor. A trojan can be the delivery step for a remote-access tool. Controls differ: memory-safety controls reduce the chance that a worm's exploit succeeds; antivirus and application allow-lists reduce the chance that a trojan runs. Neither control replaces the other.

Controls against program threats

Compile with warnings and bounds-checked libraries where available. Use fgets, snprintf and explicit length checks. Static analysis reads source or bytecode without running it and flags unsafe calls and missing checks. Dynamic analysis runs the program with test inputs and tools such as fuzzers and sanitizers; AddressSanitizer catches many out-of-bounds accesses during testing. These find bugs but cannot prove absence.

Stack canaries place a random value between the buffer and the saved return address. A function checks the canary before returning; a linear overflow that overwrites EIP also changes the canary. NX or DEP marks the stack and heap non-executable, so injected code cannot run. ASLR randomises base addresses of the stack, heap and libraries, so an attacker cannot hard-code a jump target. ASLR is probabilistic and does not fix the bug; a leak of one address can defeat it. Control-flow integrity checks that indirect jumps and returns go to valid targets; it is stronger but needs compiler and hardware support. None of these controls is a substitute for fixing the unsafe copy.

6.5 Operating system security: UNIX and Windows

Operating system security is the set of checks that decide which process may read, write or execute which file or setting. UNIX and Windows both attach an identity to a running process and permissions to an object; the kernel compares them on every access. This matters on servers, laptops, Android phones and Windows desktops. One wrong permission, such as a world-writable system file or a setuid root program, can turn a normal user into an administrator. This chapter covers UNIX modes and Windows ACLs, then hardening and analysis.

You need: memory protections from 6.4 and user authentication from Unit 5.

UNIX identity and the rwx mode

UNIX gives each user a numeric user identifier (UID) and at least one group identifier (GID). /etc/passwd maps names to UIDs; /etc/shadow stores password hashes readable only by root. A process has a real UID (who started it) and an effective UID (what the kernel checks). UID 0 is root, the superuser.

Each file has an owner, a group and three permission triads: owner, group, other. Each triad has read (r), write (w) and execute (x). The kernel scores a triad as 4 for read, 2 for write and 1 for execute, then adds them. So rwx is 7, r-x is 5, r-- is 4, --- is 0. A mode is three octal digits: 750 means owner rwx, group r-x, other ---. On a directory, x means search (enter) and r means list names.

mode = 4r + 2w + 1x

r, w, x are 1 if that triad has read, write or execute, else 0; apply this to owner, group and other.

Commands: chmod 750 file, chown alice file, chgrp auditors file. New files start from 666 minus umask; with umask 022 a file becomes 644 and a directory 755.

setuid, setgid, sticky bit and PATH attacks

Three extra bits sit above the nine permission bits: setuid (4), setgid (2) and sticky (1). They form a fourth octal digit on the left. Mode 4755 means setuid plus 755; the owner execute slot shows s: rwsr-xr-x.

setuid on an executable changes the process's effective UID to the file owner for the run. The real UID stays the same. A setuid root program runs with root power. setgid does this for the effective GID; on a directory it makes new files inherit the directory group. The sticky bit on /tmp lets only the file owner, directory owner or root delete a file.

setuid is a privilege-escalation target. A root program that reads a user-named file or calls a shell without dropping privilege can be abused. A PATH attack works like this: root runs a script that calls ls by name; the attacker puts a malicious ls in an early PATH directory. setuid is ignored on filesystems mounted nosuid, on scripts on many systems, and when execute permission is missing.

UNIX security analysis: find setuid files with find / -perm -4000, add -o -perm -2000 for setgid; check world-writable files and directories; check /etc/shadow permissions; review cron and startup scripts. Root can override mode bits, but not a read-only mount, an LSM policy or a container boundary.

Windows: SIDs, tokens and ACLs

Windows uses a security identifier (SID) for every user and group. At logon the system builds an access token: the user SID, group SIDs and privileges. Every process runs with a token. A process cannot upgrade its own token without a privileged service.

Each securable object has a security descriptor: owner SID, a discretionary access control list (DACL) and a system access control list (SACL). A DACL holds access control entries (ACEs). An ACE names a SID, an access mask (read, write, execute) and allow or deny. The SACL holds audit ACEs.

On access, the kernel compares the token with the DACL. It walks ACEs; a deny ACE usually wins over an allow ACE for the same right. If no ACE allows the right, the request is denied. The decision can be written to the Security log. This is the same subject-object check as 6.6, with Windows names.

Integrity levels add a second gate: low, medium, high, system. A low-integrity browser tab cannot write a medium file even if the DACL allows it. User Account Control (UAC) keeps an administrator at medium until consent, then gives a high-integrity token. Services run as LocalSystem, LocalService or NetworkService; give each the least privilege. Registry keys carry ACLs too, so a weak service key is as dangerous as a weak file.

Hardening, auditing and security kernels

Hardening reduces what an attacker can use. Run users and services with least privilege. Remove unused services and shares. Set a restrictive umask. Patch the OS and applications on a schedule: one local privilege-escalation bug defeats password policy. Audit logon, privilege use and object access, and send logs off the host. Logs must be time-synchronised or they are hard to correlate. Audit belongs with policy and risk in 6.7.

A security kernel is the small hardware and software part that mediates every access. A reference monitor must be complete (every access checked), isolated (tamperproof) and verifiable (small enough to review). Commercial systems were not built this way. Retrofitting adds hooks: Linux uses Linux Security Modules (LSM) for SELinux and AppArmor; Windows uses integrity levels, UAC and service hardening. Only a few universities teach security kernels and retrofitting in depth; know the three properties and one real example.

6.6 Access control models and policies

Access control answers one question for every request: may this subject perform this operation on this object? A subject is a user or process. An object is a file, folder, device or record. An operation is read, write, execute or delete. The answer comes from a model, such as an access matrix, and a policy enforced by the operating system or an application. It exists so data and services reach only the right people. Banks use it for accounts, hospitals for records, and Linux and Windows for files.

You need: 6.5 Operating system security: UNIX and Windows for users, processes and file permissions.

Access matrix, ACLs and capabilities

An access matrix is a table. Rows are subjects: users or processes that request access. Columns are objects: files, folders, devices or records. Each cell lists the rights, also called operations, that the subject holds on the object. Common rights are r for read, w for write, x for execute and - for none. In the figure, Bob has rw on f2 and Carol has rwx on f3. The matrix is a model; real systems store it in one of two ways.

An access control list (ACL) stores one column per object. The ACL for f2 is: Alice r, Bob rw, Carol r. A capability stores one row per subject. Bob's capability list is: f1 r, f2 rw, f3 x. An ACL is checked when a subject opens an object. A capability is presented by the subject when it requests an object.

Linux file ACLs use setfacl to add entries and getfacl to test them. setfacl -m u:alice:rw f1 gives Alice read and write on f1. getfacl f1 prints the ACL. setfacl -m d:u:bob:r dir1 sets a default ACL for new files in dir1.

DAC, MAC, Bell-LaPadula and Biba

In discretionary access control (DAC), the owner of an object decides who gets access. UNIX permissions are DAC. In mandatory access control (MAC), the system decides using labels. Every subject gets a clearance level and every object gets a classification level. A label is a security level such as public, secret or top secret. The user cannot change the label.

Bell-LaPadula protects confidentiality with two rules. No read up: a subject cannot read an object with a higher classification than its clearance. No write down: a subject cannot write to an object with a lower classification. The second rule stops a secret being copied into a public file.

Biba protects integrity and reverses the directions. No read down: a subject cannot read an object with lower integrity, so low-quality data does not contaminate a high-integrity process. No write up: a subject cannot write to an object with higher integrity. Read the names carefully: Bell-LaPadula is about secrecy, Biba is about trustworthiness.

RBAC and ABAC

Role-based access control (RBAC) gives permissions to roles, not directly to users. A role is a job function such as cashier, auditor or nurse. Users are assigned to roles. A session is a login in which a user activates some roles. Permissions are operations on objects. RBAC scales because a new cashier gets the cashier role, not twenty separate file rights.

Separation of duties (SoD) stops one person from completing a sensitive task alone. Static SoD says a user cannot hold two conflicting roles, such as buyer and payment approver. Dynamic SoD says the same user cannot activate both roles in one session.

Attribute-based access control (ABAC) decides from attributes. A subject attribute is department or clearance. A resource attribute is owner or classification. An action attribute is read or approve. An environment attribute is time or network. A policy might allow read when subject.department equals resource.department and time is before 18:00. ABAC is flexible but needs clean attribute data.

Enforcement, least privilege and biometrics

A policy is a rule. Enforcement is the check made on every request. A policy decision point (PDP) computes allow or deny. A policy enforcement point (PEP) blocks or passes the request. A reference monitor is the abstract guard that checks every access, cannot be bypassed, and is small enough to verify.

Least privilege gives a subject only the rights needed for its task, for the shortest time. Privilege creep is the slow growth of rights when people change jobs and old rights are not removed. Review rights on a schedule and remove unused entries.

FAR = FA ÷ N_impostor, FRR = FR ÷ N_genuine

FAR is the false acceptance rate; FA is the number of impostor attempts accepted; N_impostor is the total impostor attempts; FRR is the false rejection rate; FR is the number of genuine attempts rejected; N_genuine is the total genuine attempts.

Biometric access control uses a fingerprint, face or iris. It is taught in only a few courses. FAR measures how often a wrong person is accepted. FRR measures how often the right person is rejected. A strict threshold lowers FAR and raises FRR.

6.7 Security policies, risk management and audit

A security policy turns business rules into enforceable controls. Risk management decides which controls are worth their cost. A bank, a hospital or a UPI payment app cannot protect everything equally, so it ranks assets, threats and weaknesses, then chooses avoid, reduce, transfer or accept. Audit and monitoring produce evidence that the controls work. This chapter links policy hierarchy, risk scores, legal duties and audit practice into one management loop. It uses a simple annual loss calculation to show why a control may be rejected even when it improves security.

You need: access control policy and Unit 1 threats and vulnerabilities.

Policy, standard, procedure, guideline

A security policy is a management statement of intent. It says what must be protected and what behaviour is allowed. A standard is a mandatory, measurable rule that supports a policy, such as “all customer passwords must be stored using a salted one-way function”. A procedure is the ordered steps staff follow to meet a standard. A guideline is recommended advice; it is not mandatory. The hierarchy matters because auditors test standards and procedures, not slogans.

Policies fail when they are vague. “Protect data” cannot be enforced. “Remote access must use multi-factor authentication” can be enforced and audited. For example, access control policy names subjects, objects, operations and the model used for decisions.

Write the policy first, then the standards that make it testable. Add procedures for routine work: onboarding, key rotation, incident escalation. Keep guidelines short so people read them. Review all four levels after a major change, such as a new UPI service or a data-sharing contract.

Risk elements and treatment

Risk management starts with an asset: anything of value, such as a database, a laptop or a customer list. A threat is a possible cause of harm, such as a phishing gang or a power cut. A vulnerability is a weakness that a threat can exploit, such as an unpatched server. Likelihood is the chance that the threat exploits the weakness in a period. Impact is the loss if it happens. Risk combines both; it is not the same as threat or vulnerability alone.

risk score = likelihood × impact

likelihood and impact are integers from 1 to 5; the risk score ranges from 1 to 25.

Treatment has four choices: avoid the activity, reduce the risk with controls, transfer it (for example insurance), or accept it with management sign-off. A control costs money and staff time, so compare its yearly saving with its yearly cost. If the saving is smaller, the simple business case rejects the control.

SLE = asset value × exposure factor

SLE is single loss expectancy in rupees; exposure factor is the fraction of asset value lost in one event.

ALE = SLE × annualised rate of occurrence

ALE is annualised loss expectancy in rupees per year; annualised rate of occurrence is events per year.

Programme, law and audit

A risk register lists each risk with owner, score, treatment, cost and review date. It is the working memory of the programme. Security programme drivers include legal duty, contracts with customers, business continuity and past incidents. A regulator or a large client can require evidence, so the programme must produce records, not just controls.

ISO 27001 defines requirements for an information security management system (ISMS). ISO 27005 gives risk management guidance. Laws are narrower: FISMA 2002 covers US federal agencies; GLBA covers US financial institutions; HIPAA covers US health information. These laws require safeguards and evidence, but compliance alone does not prove security.

Audit checks whether controls exist and operate. Logging records events; monitoring watches them; compliance evidence includes tickets, approvals, logs and test reports. A vulnerability assessment finds weaknesses; a penetration test safely attempts exploitation. Cloud shared responsibility shifts some controls to the provider, as covered in cloud security services.

Worked example

Question. An asset is worth ₹10,00,000. A threat exploits a vulnerability with exposure factor 25% and annualised rate of occurrence 0.2 per year. (a) Compute single loss expectancy.   1. Asset value AV = ₹10,00,000.
  2. Exposure factor EF = 25% = 0.25.
  3. SLE = AV × EF = 10,00,000 × 0.25 = ₹2,50,000.
  4. Annualised rate of occurrence ARO = 0.2 events per year.
  5. ALE = SLE × ARO = 2,50,000 × 0.2 = ₹50,000 per year.

  9. The saving is less than the cost, so the control is not cost-effective by this simple measure.

Exam traps

  • Risk is not the same as a threat or a vulnerability. A threat is what may cause harm; a vulnerability is the weakness; risk combines likelihood and impact.
  • Compliance with a law or standard does not by itself make a system secure. It proves required paperwork and controls were checked, not that every attack fails.
  • ALE uses the annualised rate of occurrence, not the exposure factor. SLE uses asset value and exposure factor.
  • Policy and standard are not interchangeable. A policy states intent; a standard gives a mandatory measurable rule that supports it.

6.8 Cloud security services

Cloud security services are the controls a cloud provider supplies and the controls a customer must still apply. The idea is simple: the provider secures the platform, while the customer secures its own configuration, data and identities. It exists because cloud systems are multi-tenant: many customers share hardware, so isolation and clear duties are essential. You meet it in a SaaS CRM, an IaaS virtual machine, or a PaaS application platform. The same question repeats: who owns this control, the provider or the customer?

You need: access control models from 6.6, risk assessment from 6.7, and TLS basics from Unit 5.

Service models and shared responsibility

Cloud providers offer three service models. Infrastructure as a service (IaaS) gives virtual machines, storage and networks; the customer manages the operating system and everything above it. Platform as a service (PaaS) gives a runtime and managed services; the customer manages the application and data. Software as a service (SaaS) gives a finished application; the customer manages users, configuration and data.

The provider always owns the physical data centre, hardware and hypervisor. In PaaS and SaaS the provider also owns the operating system and runtime. The customer owns data classification, identities, role assignment and, in IaaS, operating system patches. The figure shows the SaaS split as a stack: the provider holds the bottom layers, from the facility up to the application, and the customer holds the top layers, data, keys and identities. The hypervisor is the provider's isolation boundary between tenants. A SaaS customer can still own the key policy when customer-managed keys are offered. This is why moving to cloud does not transfer all responsibility.

Identity, network and encryption controls

Identity and access management (IAM) is the set of users, groups, roles and policies in a cloud account. The customer grants each identity the least privilege it needs. Multi-factor authentication (MFA) adds a second proof beyond a password. A security group is a virtual firewall attached to a resource. It holds allow rules matched on port, protocol and source; anything not allowed is dropped by default. Rule order does not matter here, because all rules are evaluated together. Ordered, priority-based rules with explicit denies appear in network ACLs and in host firewall rule lists, as in 6.1.

A web application firewall (WAF) inspects HTTP requests and blocks common web attacks, complementing the TLS protection described in Unit 5. Encryption in transit uses TLS between client and service. Encryption at rest uses a block cipher such as AES from Unit 3, with keys held in a key management service (KMS). In envelope encryption, a data key encrypts the data and a master key encrypts the data key. A customer-managed key (CMK) means the customer writes the key policy that decides who may decrypt. The provider supplies the KMS and backup service, but the customer must test restores and watch audit logs. The provider runs the logging and monitoring service. The customer must enable logging, set retention, and write the alerts it actually needs.

Isolation, monitoring and incident response

Multi-tenancy means many customers share hardware. The provider isolates tenants with the hypervisor, virtual networks and storage controls. A hypervisor bug can therefore threaten more than one tenant; the provider patches it. The customer must still patch its own application and, in IaaS, its operating system.

Logging and monitoring turn activity into evidence: audit logs record API calls, flow logs record network traffic, and alerts flag unusual access. Backup protects availability, but a backup is useful only after a restore test. Recovery objectives are RPO (recovery point objective, the maximum acceptable data loss in time) and RTO (recovery time objective, the maximum acceptable downtime). Incident response is split by contract: the provider handles a platform incident, while the customer handles a compromised account or bad role policy, and the provider notifies the customer within an agreed time. Compliance is also shared: the provider holds audit reports for its data centre, and the customer must prove its own configuration and data handling. Encryption at rest does not protect data in use. A public storage bucket is usually a customer configuration error, not a provider break-in.

6.9 AI in security: anomaly detection, adversarial attacks

AI-based security tools learn patterns from data instead of only matching known signatures. An anomaly detector builds a model of normal behaviour and gives each event a score; a threshold turns that score into an alert. This finds attacks that no signature covers, so it is used in intrusion detection, malware classification and cloud monitoring. The same learning creates a new weakness: an attacker who understands the model can craft input that scores below the threshold, or poison the data used to train it. This chapter covers both the detector and its attacker.

You need: 6.2 IDS, 6.4 malware and 6.8 cloud telemetry.

Learning normal, scoring the rest

A detector turns each event into a feature vector: a fixed list of numbers. For a network flow the features might be bytes per second, packets per second, distinct destination ports and hour of the day. For a login they might be hour, country, device and failed attempts. Good features matter more than the choice of algorithm.

In supervised learning every training record carries a label, normal or attack, and the model learns the boundary. In unsupervised learning the model sees mostly normal records and learns their shape; a new record is scored by its distance from that shape. Semi-supervised training uses normal data plus a small labelled attack set, which is the common case in practice.

  1. Collect a baseline over a full weekly cycle, so a Monday peak is not treated as an attack.
  2. Clean the data and extract the features.
  3. Split into a training set and a separate validation set.
  4. Train on the training set only, and never report the training score as performance.
  5. Pick the threshold on the validation set, deploy, and retrain when behaviour drifts.
alert if score ≥ t; TPR = TP ÷ (TP + FN); FPR = FP ÷ (FP + TN)

score is the model output from 0 to 1; t is the threshold; TP and FN count attacks flagged and missed; FP and TN count normal events flagged and passed; TPR is the true positive rate (recall) and FPR the false positive rate.

Lowering t catches more attacks and raises false positives. Each false positive costs analyst minutes, and a flood of them causes alert fatigue, so real attacks get ignored. Raising t is quiet but gives an attacker room to score just under the line. The threshold is a decision about how many wrong alerts a team can absorb.

Accuracy misleads here. If 1 flow in 1000 is an attack, always answering normal scores 99.9% accuracy and detects nothing. Judge a detector by TPR, FPR and precision.

Where it is used

Anomaly detection fits wherever routine behaviour is plentiful and labels are scarce.

  • Intrusion detection: a flow-based model watches for traffic unlike the baseline and runs beside signature rules (6.2). A host-based model looks at process trees and file access.
  • Malware analysis: features come from the file (imports, section entropy, strings) or from a sandbox run (API calls, network destinations) (6.4).
  • Threat intelligence: models cluster reports and rank alerts. Only a few universities teach NLP for this, so keep it brief.
  • Cloud and identity: user and entity behaviour analytics score logins by device, time, location and data volume, so a stolen password shows up as odd behaviour (6.8).

The model complements signatures rather than replacing them. A signature catches a known tool cheaply and exactly. An anomaly model catches variants, at the price of more false alarms. Run both and show the analyst the evidence from each.

Adversarial machine learning

Adversarial machine learning studies how an attacker manipulates a model or its inputs. The aim is not to break cryptography; it is to move a score across a threshold the attacker cannot see.

  • Evasion: the attacker crafts input at test time that the model calls normal. A spam filter is beaten by adding innocent words; the attack score falls from 0.80 to 0.60 and the message passes.
  • Perturbation: a small deliberate change to the input. Malware appends unused bytes, renames an import or packs a section. The file looks harmless and its hash changes.
  • Poisoning: the attacker edits the training data, for example by feeding tainted samples through a public threat feed, to raise false positives or plant a backdoor.
  • Model extraction: the attacker queries a prediction API many times and fits a copy, then searches for evasive inputs offline.

Perturbations often transfer between models, so a copy or a rough substitute is enough. One changed feature can cross the line, which is why the worked example below matters more than it looks.

Defences and human review

No defence makes a model safe, but each of these raises the attacker's cost.

  • Adversarial training: add perturbed attack samples to the training set so the model learns them. It helps, it costs compute, and it does not cover tomorrow's perturbation.
  • Robust features: prefer what the attacker cannot easily change, such as section entropy, import table structure or a call sequence, over file names and string constants.
  • Human review: a person checks borderline scores and approves any blocking action.
  • Layering: keep signatures, allowlists and anomaly scores side by side (6.2).
  • Monitoring: watch the score distribution. A sudden jump in false positives suggests drift or poisoning.

Against model extraction, rate-limit prediction queries, log them, and keep high-value models offline. Budget for misses and rehearse the review step; a detector that nobody trusts is worse than none.

Worked example

Question. An anomaly detector gives scores from 0 to 1 with threshold 0.70. Normal scores: 0.10, 0.20, 0.35, 0.55. Attack scores: 0.65, 0.80, 0.90, 0.95. (a) Which scores are flagged? (b) Compute TPR and FPR at 0.70. (c) If the 0.80 attack is perturbed to 0.60, what is the new TPR?

  1. Flag if score ≥ 0.70. Attack scores: 0.65 is below 0.70 and missed; 0.80, 0.90 and 0.95 are flagged. So TP = 3 and FN = 1.
  2. Normal scores: 0.10, 0.20, 0.35, 0.55 are all below 0.70, so FP = 0 and TN = 4.
  3. TPR = TP ÷ (TP + FN) = 3 ÷ 4 = 0.75, that is 75% of attacks caught.
  4. FPR = FP ÷ (FP + TN) = 0 ÷ 4 = 0.00, that is no normal event flagged.
  5. Perturbed attack set: 0.65, 0.60, 0.90, 0.95. Flagged: 0.90 and 0.95 only, so TP = 2 and FN = 2.
  6. New TPR = 2 ÷ 4 = 0.50. FPR stays 0 ÷ 4 = 0.00 because no normal score changed.

Answer. (a) 0.80, 0.90 and 0.95 are flagged. (b) TPR = 0.75 (75%) and FPR = 0.00 (0%). (c) After the perturbation to 0.60, TPR falls to 0.50 (50%) at the same threshold.

Exam traps

  • High accuracy on imbalanced data proves nothing. Compare against the always-normal baseline and report TPR and FPR.
  • An anomaly is not an attack. A new software rollout or a festival sale can look anomalous, so an alert needs a human or a second signal.
  • TPR and FPR are not complements. FPR is measured on normal samples; 1 − TPR is the miss rate, which is a different number.
  • A threshold test is ≥ or >, so state which. Changing it shifts every metric, so compare two detectors only at the same threshold.
  • A perturbed sample can look harmless and have a new hash. 'No known signature' does not mean safe.

Takeaways

  1. A firewall is only as good as its rule order and its default policy; the first matching rule wins, so put specific rules above general ones.
  2. An IDS watches and alerts; an IPS sits inline and blocks, which also means a false positive can cut real traffic.
  3. A honeypot has no legitimate users, so any traffic reaching it is suspicious by definition and cheap to investigate.
  4. Memory-safety bugs such as buffer overflows are prevented by safer code, compiler checks and runtime defences such as ASLR and non-executable stacks.
  5. UNIX and Windows both separate authentication (who you are) from authorization (what you may touch), and check permissions on every object access.
  6. Access control models (matrix, ACL, capability, MAC, RBAC) are different ways to store and enforce the same question: may this subject do this operation on this object?
  7. Risk management decides which control is worth its cost; a control that costs more than the loss it prevents is a bad control.
  8. In cloud, almost every breach reported is a customer-side misconfiguration or stolen credential, not a broken hypervisor.
  9. Machine learning helps security mainly by ranking and triage, and it fails when attackers poison training data or craft evasive inputs.
  10. Every automated detector needs human review and a tuned threshold, because false positives cost analyst time and false negatives cost incidents.

Glossary

Access control matrix
A subject-by-object table whose cells list permitted operations, the abstract basis of most access control models.
Access token
A Windows object carrying a process's user SID, group SIDs and privileges, used in every access check.
Adversarial example
An input altered by a small perturbation so a trained model misclassifies it while humans see nothing odd.
ASLR
Address space layout randomization; it loads code, stack and libraries at unpredictable addresses so a fixed jump target fails.
Audit log
A tamper-resistant record of security-relevant events used to detect, investigate and prove compliance.
Buffer overflow
A memory-safety bug where data is written beyond a buffer's bounds, corrupting adjacent memory.
Data poisoning
Corrupting the training data of a model so it learns wrong behaviour or a hidden backdoor.
Default deny
The policy that traffic is blocked unless a rule explicitly allows it.
DMZ
A screened subnet holding public-facing servers, separated from the internal LAN by a firewall.
False positive
An alert raised on legitimate activity; it wastes analyst time and, in an IPS, can block real work.
Firewall
A device or software that enforces an ordered rule set on traffic crossing between two networks.
Honeynet
A controlled network of honeypots with capture and containment, used to study attack campaigns.
Honeypot
A decoy system with no legitimate users, deployed to attract and record attacks.
IDS
Intrusion detection system; a passive sensor that inspects traffic or host activity and raises alerts.
IPS
Intrusion prevention system; an inline sensor that can also drop or reset malicious traffic.
Least privilege
The principle that each subject gets only the rights needed for its task, for only as long as needed.
Malware
Software written to harm or misuse a system, including viruses, worms, trojans, rootkits and ransomware.
RBAC
Role-based access control; permissions attach to roles and users attach to roles.
Residual risk
The risk left after controls are applied, formally accepted by the asset owner.
Risk
The chance and size of loss from a threat exploiting a vulnerability; scored as likelihood × impact, where likelihood depends on the threat and the vulnerability.
Rule order (first match wins)
A firewall checks rules from the top and acts on the first rule that matches, so order changes meaning.
setuid
A UNIX mode bit causing a program to run with the file owner's user ID rather than the caller's.
Shared responsibility model
The cloud split in which the provider secures the platform and the customer secures configuration, data and identities.
Stack canary
A random guard value checked on function return; if it changed, an overflow occurred and the program aborts.
Stateful inspection
Firewall filtering that tracks each connection so replies to allowed sessions pass without new rules.
