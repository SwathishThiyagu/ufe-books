4.1 Public-key cryptosystems and trapdoor one-way functions

Public-key cryptography lets two strangers communicate securely without first sharing a secret key. It replaces the shared key with a pair: a public key anyone may see and a private key kept secret. The system rests on one mathematical idea, a trapdoor one-way function. Computing the function forward is cheap; reversing it is practically impossible unless you hold the trapdoor. This pattern carries session keys in HTTPS, signs software updates, and protects UPI transactions. The arithmetic differs across schemes, but the logic is the same.

You need modular arithmetic, exponents and Euler's theorem from Unit 2, plus symmetric ciphers and session keys from Unit 3; the RSA arithmetic itself waits in 4.2.

One-way and trapdoor functions

A one-way function is a function f from a domain X to a range Y with two properties. First, for any x in X, f(x) is easy to compute. Second, given a random y in Y, finding any x with f(x) = y is infeasible. Easy means a normal computer can do it in a reasonable time. Infeasible means no known method does it in practice, not that no method exists forever. The function itself is public; its hardness is the protection.

f: X → Y is one-way if f(x) is easy for all x ∈ X, but finding x from y = f(x) is infeasible.

X is the input set; Y is the output set; x is the input; y is the output; ∈ means 'is in'.

A trapdoor one-way function adds one secret. It is still infeasible to invert f without extra information. With a secret trapdoor t, the inverse f⁻¹(y) becomes easy. The name comes from a physical trapdoor: the door is locked from outside, but the owner has a hidden opening. When f is also a bijection, meaning every y has exactly one x, some syllabi call it a trapdoor permutation.

Five requirements of a public-key system

A public-key cryptosystem must meet five standard requirements.

  • Generating a key pair is cheap.
  • Encrypting with the public key is cheap.
  • Decrypting with the private key is cheap.
  • Deriving the private key from the public key is infeasible.
  • Either key can be used first for one direction: public key for encryption, private key for decryption; or private key for signing, public key for verification.

The first direction gives confidentiality. Anyone can encrypt to Alice with her public key; only Alice has the private key to decrypt. The second direction gives authentication. If Alice encrypts with her private key, anyone can decrypt with her public key, so the result is not secret; it proves the holder of Alice's private key produced it. Digital signatures use this direction on a hash; see 4.8.

Symmetric ciphers need one shared key per pair. For n users that is n(n−1)/2 keys. Public-key systems need one pair per user, so n pairs. For 12 employees, symmetric needs 12×11/2 = 66 keys; public key needs 12 pairs. Symmetric ciphers are much faster. AES-128 uses a 128-bit key; RSA-2048 uses a 2048-bit modulus. RSA is used for short values such as keys, not for bulk data.

Hybrid encryption and the family of schemes

Public-key operations are slow, so real systems use hybrid encryption. The sender makes a random session key, encrypts it with the receiver's public key, and encrypts the data with a symmetric cipher under that session key. The public key carries the key; AES or another symmetric cipher carries the data. TLS works this way; see Unit 5.

RSA, ElGamal, Rabin and elliptic-curve schemes all fit the same pattern. Each defines its own trapdoor one-way function. RSA hides a message in modular exponentiation; ElGamal hides it in a Diffie–Hellman-style shared value; elliptic-curve schemes use point multiplication. The details are in 4.2, 4.3, 4.4. Some syllabi call this asymmetric key cryptography. Public-key encryption never replaces symmetric ciphers; it distributes and manages keys. Trusting a public key is a separate problem, handled in 4.5.

Worked example

Question. A firm has 12 employees. (a) How many symmetric keys are needed for every pair to talk privately? (b) How many public-key pairs? (c) For n = 55 and f(x) = x³ mod 55, compute f(9). Given 55 = 5×11, φ(55) = 40 and e = 3, find d with 3d ≡ 1 mod 40 and compute 14^d mod 55.

  1. Symmetric keys for n people = n(n−1)/2 = 12×11/2 = 66 keys.
  2. Public-key system: each person has one pair; 12 public + 12 private = 12 pairs, not 66.
  3. f(9) = 9³ mod 55 = 729 mod 55. 55×13 = 715, remainder 14. So f(9) = 14.
  4. φ(55) = (5−1)(11−1) = 4×10 = 40.
  5. Need d = 3⁻¹ mod 40. 3×27 = 81 = 2×40 + 1, so d = 27.
  6. 14²⁷ mod 55 by repeated squares: 14² = 196 ≡ 31; 14⁴ ≡ 31² = 961 ≡ 26; 14⁸ ≡ 26² = 676 ≡ 16; 14¹⁶ ≡ 16² = 256 ≡ 36. Since 27 = 16+8+2+1: 36×16 = 576 ≡ 26; 26×31 = 806 ≡ 36; 36×14 = 504 ≡ 9. So 14²⁷ mod 55 = 9.

Answer. Symmetric keys = 66, public-key pairs = 12, f(9) = 14, φ(55) = 40, d = 27, and 14²⁷ mod 55 = 9.

Exam traps

  • The public key is not secret. Keeping it secret defeats the purpose; the private key is the secret.
  • Encrypting with the private key does not give confidentiality. Anyone with the public key can reverse it; it gives authentication, as in a digital signature.
  • Public-key cryptography does not replace symmetric ciphers. It carries a session key; the symmetric cipher carries the data.
  • A one-way function has no trapdoor by definition, so it cannot decrypt anything. Only a trapdoor one-way function has a fast inverse with secret information.
  • Not every trapdoor one-way function is a trapdoor permutation. A permutation must be a bijection, so every output has exactly one input.

4.2 RSA cryptosystem

RSA is the public-key cipher you can run with paper and pencil. The sender raises the message to a public power modulo a large number n; the owner brings it back with a private exponent. It works because n is the product of two secret primes, and only the owner knows them. RSA protects TLS sessions, encrypted email, software updates and bank APIs, and its second job, signing, sits inside every certificate your phone checks.

You need: 4.1 for the trapdoor idea, and Unit 2 for Euler's theorem, the extended Euclidean algorithm and the Chinese remainder theorem.

Key generation, step by step

RSA uses one public pair and one private number. The public pair (e, n) locks a message; the private number d unlocks it. Key generation builds all three from two secret primes.

  1. Pick two large random primes p and q, each about half the target key size, and keep both secret.
  2. Compute n = p×q. This is the modulus, and its bit length is the key size.
  3. Compute φ(n) = (p−1)(q−1), the count of numbers from 1 to n−1 that are coprime to n. Keep it secret.
  4. Choose the public exponent e with 1 < e < φ(n) and gcd(e, φ(n)) = 1. The usual value is 65537 = 2¹⁶ + 1: prime, only two 1-bits, so exponentiation is fast.
  5. Compute d = e⁻¹ mod φ(n) with the extended Euclidean algorithm. This d is the private exponent.
  6. Publish (e, n). Erase p, q and φ(n), or keep p and q safely for faster decryption by the Chinese remainder theorem.

e·d ≡ 1 (mod φ(n))

e is the public exponent, d is the private exponent, and φ(n) = (p−1)(q−1) is Euler's totient of the modulus n. This congruence is the one working rule of the whole scheme.

c = mᵉ mod n

m is the message written as an integer with 0 ≤ m < n, e and n are the public key, and c is the ciphertext integer.

m = c^d mod n

d is the private exponent; the owner raises the ciphertext to d modulo n and gets the message back.

Practice replaces φ(n) by the smaller Carmichael value λ(n) = lcm(p−1, q−1). Any d with e·d ≡ 1 (mod λ(n)) also decrypts: λ(n) is a multiple of both p−1 and q−1, so e·d − 1 is a multiple of p−1 and of q−1; Fermat's little theorem then gives m^(e·d) ≡ m modulo p and modulo q, hence modulo n. Using λ(n) only enlarges the set of valid d compared with φ(n).

Why decryption gives back the message

Euler's theorem says m^φ(n) ≡ 1 (mod n) whenever gcd(m, n) = 1. Key generation gave e·d = 1 + k·φ(n) for some whole number k.

c^d ≡ m^(e·d) = m·(m^φ(n))^k ≡ m·1ᵏ ≡ m (mod n)

c = mᵉ, so raising to d multiplies the exponent by d; the bracketed factor collapses to 1 by Euler's theorem.

So decryption costs one exponentiation and no searching. Now the leftover case gcd(m, n) ≠ 1. Then m is a multiple of p or of q, but not both, since m < n. Modulo p we get m ≡ 0, hence m^(e·d) ≡ 0 ≡ m. Modulo q Euler's theorem applies as usual. The Chinese remainder theorem glues the two answers into one value below n, so correctness holds for every m with 0 ≤ m < n.

The size limit is real: m must be smaller than n. Long data is never encrypted directly. RSA encrypts a short random key, and that key drives AES for the bulk data, as Unit 5 shows.

Security, sizes and real attacks

An attacker holds n, e and c and wants m. The best known attacks need the factorisation of n, and recovering d from (e, n) is provably as hard as factoring; no attack on RSA itself is known that beats factoring n. So RSA stands or falls with the difficulty of factoring n.

Current sizes: 2048 bits for new keys, 3072 bits for keys that must last for decades. A 2048-bit modulus is far beyond any published factorisation; the record sits near 250 decimal digits, about 829 bits.

  • Common modulus: two users share n with different e, and one message sent to both can be recovered without factoring.
  • Small e with small m: if mᵉ is below n, then c = mᵉ over ordinary integers, and an e-th root returns m.
  • Low private exponent: Wiener's attack recovers d when d is smaller than roughly n^(1/4), so d must be large.
  • Timing: decryption time follows the bits of d, so implementations use constant-time exponentiation (no data-dependent branches) and random blinding of the ciphertext to break the link between timing and d.
  • Chosen ciphertext: textbook RSA is multiplicative, so c₁·c₂ mod n decrypts to m₁·m₂ mod n, and an attacker can turn a decryption service into an oracle. Randomised padding such as OAEP blocks this.

Multiplicativity in one line: E(m₁)·E(m₂) = m₁ᵉ·m₂ᵉ = (m₁m₂)ᵉ = E(m₁m₂) mod n. The same m also always gives the same c. Textbook RSA is therefore malleable and deterministic, and no real system uses it bare.

Worked example

Question. Let p = 5, q = 11, e = 3 and m = 9. Build the RSA key pair, encrypt m, and verify the decryption with the Chinese remainder theorem.

  1. n = p×q = 5×11 = 55. The modulus is 6 bits long, so this is a toy key.
  2. φ(n) = (p−1)(q−1) = 4×10 = 40.
  3. gcd(3, 40) = 1, so e = 3 is a valid public exponent.
  4. Find d: 3×27 = 81 = 2×40 + 1, so 3×27 ≡ 1 (mod 40) and d = 27. Here λ(n) = lcm(4, 10) = 20, so d = 7 works as well as 27; the example keeps 27 because it was computed mod φ(n).
  5. Public key (e, n) = (3, 55); private key d = 27.
  6. Encrypt: c = 9³ mod 55 = 729 mod 55. Since 55×13 = 715, c = 729 − 715 = 14.
  7. Decrypt by CRT. Mod 5: 14 ≡ 4, the order of 4 is 2, and 27 is odd, so 4²⁷ ≡ 4. Mod 11: 14 ≡ 3, the order of 3 is 5 because 3⁵ = 243 = 22×11 + 1, and 27 ≡ 2 (mod 5), so 3²⁷ ≡ 3² ≡ 9.
  8. Combine: the value below 55 that is 4 mod 5 and 9 mod 11 is 9, and indeed 9 mod 5 = 4 and 9 mod 11 = 9.

Answer. The public key is (3, 55) and the private exponent is 27; the message m = 9 encrypts to c = 14 and decrypts back to m = 9.

Exam traps

  • Writing φ(n) = pq − 1. It is (p−1)(q−1): with p = 5, q = 11 the answer is 40, not 54.
  • Encrypting a message m ≥ n. Everything is mod n, so m = 60 with n = 55 quietly becomes 5 and the plaintext is lost. Split or pad so that m < n.
  • Believing d is unique. Every d ≡ e⁻¹ mod λ(n) decrypts; key files store the smallest positive one.
  • Calling textbook RSA secure. It is deterministic and multiplicative, so real systems add OAEP padding before the exponentiation.
  • Swapping the exponents. Encrypting with d instead of e is a signature, not encryption; see 4.8.

4.3 Diffie-Hellman key exchange

Alice and Bob have never met, yet they can agree on one secret number over a public network. Diffie-Hellman does this without ever sending the secret. Each side picks a private exponent, sends a public value derived from it, and mixes its own secret into the other side's public value. Both land on the same number. An eavesdropper sees the public values but cannot pull out the exponents, because that means solving a discrete logarithm. TLS handshakes, SSH and secure messengers use this to set up session keys.

You need: 4.1 for the one-way idea, and Unit 2 for modular exponentiation, generators and the group mod p.

The problem and the public parameters

Alice and Bob want to talk privately, and symmetric ciphers need a shared key. Sending that key over the wire gives it to any eavesdropper. Diffie-Hellman agrees on one number without ever transmitting it.

Two public parameters are fixed first. p is a large prime. g is a generator (primitive root) of the multiplicative group mod p: its powers g¹, g², …, g^(p−1) mod p run through every value from 1 to p−1 exactly once. Both p and g are public.

Security rests on the discrete logarithm problem: given p, g and the value gᵃ mod p, find the exponent a. Raising g to a power is cheap. Undoing it is not. For a 2048-bit p no known method finds a in useful time.

  1. Alice and Bob agree on public p and g.
  2. Alice picks a secret exponent a, computes A = gᵃ mod p, and sends A.
  3. Bob picks a secret exponent b, computes B = gᵇ mod p, and sends B.
  4. Alice computes K = Bᵃ mod p.
  5. Bob computes K = Aᵇ mod p. Both hold the same K.

K ≡ Bᵃ ≡ (gᵇ)ᵃ ≡ g^(ab) ≡ (gᵃ)ᵇ ≡ Aᵇ (mod p)

p is the public prime; g is the public generator; a and b are the private exponents, never sent; A and B are the public values; K is the shared secret.

Choosing p and the generator safely

p − 1 should have a large prime factor. Otherwise the Pohlig-Hellman method breaks the discrete log into small pieces and solves each one. A safe prime has the form p = 2q + 1 with q also prime.

With a safe prime, work in the subgroup of order q. A different symbol is used here: pick h in the range 2 to p−2 and set g_q = h² mod p. This g_q has order q, not p−1, and it is not a primitive root of the full group. Every element of this subgroup except 1 then has prime order q. This blocks the small-subgroup attack: an attacker who sends a value of small order, such as p−1, learns a modulo that small order from Alice's reply. Repeating with many small orders can expose a.

Check that a received value lies in the range 2 to p−2. Reject 0, 1 and p−1. Use p of at least 2048 bits, or 3072 bits for long-lived secrets. Elliptic-curve Diffie-Hellman (ECDH) is the same protocol over an elliptic-curve group, where a 256-bit curve gives comparable security.

Shared secret, KDF and authentication

K is a group element, not a uniform string of random bytes, so its bit pattern is biased. Both sides pass K through a key derivation function such as HKDF, with a context label, to get session keys. Never use K raw as a cipher key.

Plain Diffie-Hellman does not authenticate anyone. An active attacker, Mallory, runs one exchange with Alice while pretending to be Bob, and another with Bob while pretending to be Alice, then relays messages. Alice and Bob each hold a key, but each key is shared with Mallory. This is the man-in-the-middle attack (Unit 1).

The fix is authentication of the exchange. Each side signs the public values with a long-term signing key, or holds a certificate proving who owns the other public value (4.5). The station-to-station protocol adds signatures plus a key-confirmation step. TLS 1.3 does the same with ECDHE and certificates (Unit 5).

Worked example

Question. Alice and Bob use Diffie-Hellman with public parameters p = 23 and g = 5. Alice picks a = 6 and Bob picks b = 15. Compute the public values A and B, and show that both sides reach the same shared value K.

  1. Alice: A = 5⁶ mod 23. Use 5² = 25 ≡ 2 and 5⁴ ≡ 2² = 4. Then 5⁶ ≡ 4 × 2 = 8. So A = 8.
  2. Bob: B = 5¹⁵ mod 23. Use 5² ≡ 2, 5⁴ ≡ 4, 5⁸ ≡ 16. Then 5¹⁵ = 5⁸ × 5⁴ × 5² × 5 ≡ 16 × 4 × 2 × 5 = 640, and 640 − 23 × 27 = 640 − 621 = 19. So B = 19.
  3. Alice computes K = 19⁶ mod 23. Write 19 ≡ −4. Then (−4)² = 16, (−4)⁴ ≡ 16² = 256 ≡ 3, and (−4)⁶ = 3 × 16 = 48 ≡ 2.
  4. Bob computes K = 8¹⁵ mod 23. Use 8² = 64 ≡ 18, 8⁴ ≡ 18² = 324 ≡ 2, 8⁸ ≡ 2² = 4. Then 8¹⁵ = 8⁸ × 8⁴ × 8² × 8 ≡ 4 × 2 × 18 × 8 = 1152, and 1152 − 23 × 50 = 2.
  5. Both hold K = 2. An eavesdropper sees p = 23, g = 5, A = 8 and B = 19. Recovering a means solving 5ᵃ ≡ 8 mod 23, a short search here but infeasible when p has hundreds of digits.

Answer. A = 8, B = 19, and both sides compute the same shared value K = 2.

Exam traps

  • Saying Diffie-Hellman encrypts a message. It agrees a secret; a symmetric cipher then encrypts.
  • Saying plain Diffie-Hellman authenticates the parties. It does not; an active attacker can run two exchanges and sit in the middle.
  • Thinking a and b travel on the network. They never do. Only A and B are sent, and both are public.
  • Using K directly as the session key. Raw K is a biased group element; pass it through a KDF first.
  • Treating p = 23 as secure. Toy parameters fall to a short search; real p is thousands of bits.

4.4 ElGamal cryptosystem

ElGamal encryption turns the Diffie–Hellman exchange into a way to send a message. The receiver publishes y = g^x mod p and keeps x. The sender picks a fresh random k and sends two numbers: g^k mod p, and the message multiplied by y^k mod p. Only the holder of x can rebuild that mask and divide it out. Email tools such as GnuPG use it to protect short values, mostly the symmetric key that then encrypts the actual file. Taher ElGamal published the scheme in 1985.

You need: 4.3 for the Diffie–Hellman mask, 4.1 for the one-way idea, and Unit 2 for modular inverses and fast exponentiation.

Key generation: two numbers public, one secret

Diffie–Hellman lets two parties build a shared number g^(xy) mod p without ever sending it. ElGamal asks the next question: what if you want to send an actual message to someone whose public value you already have, with no back-and-forth? The answer is to let the sender play the second party, using a throwaway secret k.

A generator g modulo p is a number whose powers g¹, g², …, g^(p−1) mod p pass through every value 1 to p−1 exactly once.

  1. Choose a large prime p and a generator g of the numbers 1 to p−1 modulo p. Both are public and shared by everyone.
  2. Choose the private key x, a random integer with 1 ≤ x ≤ p−2. Keep it secret.
  3. Compute y = g^x mod p. This is the public key.
  4. Publish (p, g, y). Anyone who wants to write to you uses these three numbers.

y = g^x mod p

p is the prime modulus; g is the generator; x is the private key, an integer from 1 to p−2; y is the public key.

The public key hides x behind a discrete logarithm. Anyone holding p, g and y would need to find x with g^x ≡ y, and no fast method is known for a large p. That is the same hard problem that protects the Diffie–Hellman exchange.

Encryption and decryption

The message is first encoded as an integer m with 1 ≤ m ≤ p−1. Text is cut into blocks small enough for that, and each block is encrypted on its own.

  1. Sender: pick a fresh random k with 1 ≤ k ≤ p−2.
  2. Compute C1 = g^k mod p, a one-time public value.
  3. Compute the mask s = y^k mod p.
  4. Compute C2 = m × s mod p.
  5. Send the pair (C1, C2).

C1 = g^k mod p, C2 = m × y^k mod p

k is the sender's random secret for this message; m is the message as an integer; y is the receiver's public key; (C1, C2) is the ciphertext, two numbers modulo p.

  1. Receiver: compute s = C1^x mod p with the private key x.
  2. Find s⁻¹ mod p, the inverse of s modulo p, using the extended Euclidean algorithm (Unit 2).
  3. Recover m = C2 × s⁻¹ mod p.

m = C2 × (C1^x)⁻¹ mod p

C1 and C2 are the ciphertext numbers; x is the private key; the power minus one means the modular inverse.

Two lines prove it correct. Raising C1 to x gives (g^k)^x = g^(kx), and the sender's mask y^k equals (g^x)^k = g^(xk). The two masks are the same number, so multiplying C2 by its inverse leaves exactly m.

The random k: fresh, secret, never reused

  • Fresh: a new random k for every message, from a good random source.
  • Secret: k sits inside C1 = g^k, and recovering it from C1 is again a discrete logarithm.
  • Reuse breaks everything. If one k encrypts m₁ and m₂, both ciphertexts share C1 and the same mask s, so C2₁/C2₂ ≡ m₁/m₂ mod p. The attacker learns the ratio; if one message is guessable, a known header or a yes/no answer, the other falls out at once.
  • A leaked k also breaks its message: from k anyone computes s = y^k and then m = C2 × s⁻¹.

The ciphertext holds two numbers modulo p, so it is twice the size of the message, and encryption costs two exponentiations against RSA's one. That is why ElGamal encrypts keys and short values, never bulk data: a hybrid scheme encrypts a session key with ElGamal and the file with AES (Unit 5).

The scheme is multiplicative. If (C1, C2) hides m and (C1′, C2′) hides m′, then (C1C1′ mod p, C2C2′ mod p) decrypts to m × m′ mod p. Useful as a property, dangerous in practice: an attacker can alter a ciphertext predictably without the key, a chosen-ciphertext attack. Padding the message, or wrapping ElGamal in a hybrid construction with an integrity check, blocks this.

ElGamal, RSA and the signature scheme

Against RSA, the difference is randomness. Encrypting m twice with two different k values gives two unrelated ciphertexts, so an eavesdropper cannot tell the same message was sent twice. RSA without padding is deterministic and leaks exactly that. Raw ElGamal needs no padding to hide the message, though it needs padding or a hybrid wrapper to stop the tampering above. Its price is speed and size.

ElGamal also published a signature scheme in the same paper, and it is a different construction: it signs a hash of the message using a per-signature random value. Do not mix the two. That family, including DSA, is in 4.8 Digital signatures and RSA signatures.

Worked example

Question. An ElGamal system uses the domain parameters p = 23 and g = 5. The receiver's private key is x = 6. (a) Compute the public key y. (b) Encrypt the message m = 7 with the random value k = 15. (c) Decrypt the ciphertext and show that m returns.

  1. y = 5⁶ mod 23. Square and multiply: 5² = 25 ≡ 2, 5⁴ ≡ 2² = 4, so 5⁶ = 5⁴ × 5² ≡ 4 × 2 = 8. Public key y = 8; private key x = 6.
  2. C1 = 5¹⁵ mod 23. Write 15 = 8 + 4 + 2 + 1, so 5¹⁵ = 5⁸ × 5⁴ × 5² × 5. Powers: 5² ≡ 2, 5⁴ ≡ 4, 5⁸ ≡ 16. Product = 16 × 4 × 2 × 5 = 640 ≡ 640 − 621 = 19, since 23 × 27 = 621. C1 = 19.
  3. Sender's mask: 8¹⁵ mod 23. Powers of 8: 8² = 64 ≡ 18, 8⁴ ≡ 18² = 324 ≡ 2 (23 × 14 = 322), 8⁸ ≡ 2² = 4. Product = 4 × 2 × 18 × 8 = 1152 ≡ 1152 − 1150 = 2, since 23 × 50 = 1150. Mask s = 2.
  4. C2 = m × s mod 23 = 7 × 2 = 14. The ciphertext is (C1, C2) = (19, 14).
  5. Decrypt: C1^x = 19⁶ mod 23. Use 19 ≡ −4: (−4)² = 16, (−4)⁴ = 256 ≡ 3 (23 × 11 = 253), so (−4)⁶ = 3 × 16 = 48 ≡ 2. The mask is 2, the same number the sender used.
  6. Inverse: 2 × 12 = 24 ≡ 1 mod 23, so 2⁻¹ = 12.
  7. m = C2 × s⁻¹ = 14 × 12 = 168 ≡ 168 − 161 = 7, since 23 × 7 = 161. The original message returns.

Answer. The public key is y = 8, the ciphertext is (C1, C2) = (19, 14), and decryption gives back m = 7.

Exam traps

  • Decrypting with C2 alone. The mask must be rebuilt from C1: m = C2 × (C1^x)⁻¹, never C2 × y⁻¹ or C2 × x⁻¹.
  • Reusing k. Two messages under the same k give the same C1 and leak m₁/m₂ mod p; with one guessable message the other is exposed.
  • Calling C2 the ciphertext. The ciphertext is the pair, and C1 must be sent and stored with C2.
  • Mixing the two ElGamal schemes. Encryption and signature are different constructions; a signature question answered with C1 and C2 scores zero.
  • Forgetting the range. m must be encoded as an integer with 1 ≤ m ≤ p−1; longer blocks are split, and m = 0 encrypts to 0 and hides nothing.

4.5 Key management, key distribution and digital certificates

A public key alone proves nothing. Anyone can post a key and claim it is the bank's. Key management makes public keys trustworthy: how keys are handed out, how a name is bound to a key, and how that binding is withdrawn. The digital certificate is the main tool. Every HTTPS padlock and signed app update depends on it. This chapter is about trust, not arithmetic.

You need Chapter 4.1 and Chapter 4.8 for key pairs and signatures.

Four ways to hand out a public key

Bob needs Alice's real public key to encrypt to her or check her signature. Four methods exist.

1. Public announcement. Alice posts her key on a web page. Anyone can read it. The failure is forgery: an attacker posts a key under Alice's name, and Bob cannot tell which is real.

2. Public directory. A trusted directory stores name, key and timestamp. Reading is open; writing needs a login. The directory is one point of trust. If broken into, every key it gives out is wrong.

3. Key authority. A known authority with a publicised public key answers lookups with a signed reply. It must be online for every lookup, so it is a bottleneck and a single point of failure.

4. Certificates. The authority signs a record once, at registration. That record can be copied and cached. Each holder checks the signature offline using the authority's public key, already installed. The authority is needed at issue time, not use time. Certificates won for this reason.

What a certificate holds, and how a browser checks a chain

A certificate is a signed data structure. The common standard is X.509. The signature covers every field, so changing any field breaks the certificate.

  • Version and serial number — format edition, and a number unique within one issuer, used for revocation.
  • Issuer — the certificate authority (CA) that signed this certificate.
  • Subject — the owner of the key, such as the domain bank.example.
  • Validity — not-before and not-after dates. Outside that window the certificate is not trusted.
  • Subject public key — the public key and its algorithm.
  • Extensions — extra rules, including permitted DNS host names and whether the certificate may sign other certificates.
  • CA signature — the issuer's digital signature over the fields above.

A certificate carries a public key and is signed with the CA's private key. It never contains a private key and never encrypts anything by itself.

CAs form a tree. A root CA signs intermediate CAs; intermediates sign website certificates. A browser ships with a trust store: root public keys it already believes. To check a server certificate, the browser builds a chain up to a stored root, verifying one signature per link. It checks that the typed host appears in the subjectAltName (DNS names) extension; the Subject common name alone is not sufficient. It also checks today's date against the validity window. The root certificate is self-signed, which is safe only because the trust store, not the network, supplied it.

A once-valid certificate can stop being trusted by expiry or revocation. Expiry is automatic. Revocation is a CA decision that a key is compromised or a company closed. A certificate revocation list (CRL) is a signed list of revoked serial numbers that a client downloads. Online Certificate Status Protocol (OCSP) asks the CA about one serial number. Short-lived certificates limit the damage window. Pinning makes an app remember the key or CA it expects and refuse a different certificate for that host; it does not protect against theft of the original certificate and key.

PKI compared with a key distribution centre, and where session keys fit

A certificate system is a public key infrastructure, or PKI: CAs, certificates, trust stores, revocation services and policies. The alternative is a key distribution centre (KDC), as in Kerberos. Every user shares a long-term secret key with the centre, and the centre issues short-term keys when two users want to talk.

verify: se mod n = h

s is the signature on the certificate, e and n are the CA's public values, and h is the hash of the certificate fields, computed by the verifier; a match means the CA signed exactly these fields. See Chapter 4.8.

PKI gives non-repudiation: a signature checked against a certified public key can be shown to a third party, because only the signer holds the private key. A KDC cannot give that, because the centre knows every session key and could have forged the traffic. But a KDC is online and central, so it can revoke access at once and enforce policy at login. A PKI is offline and spread out, so revocation lags.

Both designs separate two key types. A long-term key lasts months or years and signs and authenticates, never encrypts bulk data. A session key is fresh for one conversation, used briefly and thrown away. The long-term key signs the handshake; the session key encrypts traffic. Leaking a session key costs one conversation; leaking a long-term key costs everything.

Not every trust model uses CAs. In a web of trust, users sign each other's keys and trust grows by paths of signatures, as PGP does. It scales without a central authority but asks each user to judge others, which most people will not do.

Worked example

Question. A browser gets an intermediate CA certificate and a bank certificate from bank.example. Root trust store: e = 3, n = 55. Intermediate: s = 4, h = 9; its public key is e = 3, n = 33. Bank: s = 5, h = 26. Forged bank.example certificate: s = 7, h = 21. Verify the chain and say what the browser does with each certificate.

  1. Step 1, check intermediate against root. 4³ mod 55 = 64 mod 55 = 9. Equals h = 9, so the root signed this intermediate. Browser accepts intermediate key (e = 3, n = 33).
  2. Step 2, check bank against intermediate. 5³ mod 33 = 125 mod 33 = 26. Equals h = 26, so the intermediate signed the bank certificate. Chain runs bank → intermediate → root.
  3. Step 3, check name and dates. The typed host must appear in the bank certificate's subjectAltName (DNS names), and today must lie between the not-before and not-after dates. Both hold, so the browser proceeds.
  4. Step 4, check forged certificate. 7³ mod 55 = 343 mod 55 = 13. Verifier h = 21, and 13 ≠ 21, so the signature fails under the root key.
  5. Step 5, decision. The forged certificate is rejected, a warning is shown, and no traffic is sent to it.

Answer. Intermediate verifies with 4³ mod 55 = 9 = h, bank verifies with 5³ mod 33 = 26 = h, forged fails because 7³ mod 55 = 13, not h = 21.

Exam traps

  • A certificate holds a public key and the CA's signature, never a private key. It does not encrypt data; a session key does.
  • CA signature binds a name to a key; site owner's signature binds a message to its author.
  • Verification computes se mod n and compares to h, not he mod n compared to s. Swapping roles makes correct certificates fail.
  • Expiry and revocation are the two ways a genuine certificate stops being trusted. Checking only the signature is incomplete.
  • In a KDC system the centre knows session keys, so it cannot give non-repudiation.

4.6 Cryptographic hash functions and SHA

A cryptographic hash takes a message of any length and returns a short fixed-length string called the digest. The same message always gives the same digest, but the digest cannot be turned back into the message, and nobody can find two messages that share a digest. Software downloads, Git commits, payment logs and TLS certificates all lean on this fingerprint. This chapter defines the hash, gives its three security properties, explains the birthday bound and the construction used inside SHA-1 and SHA-256, and lists where hashes are used.

You need: the one-way idea from 4.1, block-by-block processing from Unit 3, and basic probability for the birthday bound.

A hash squeezes any message into n bits

A cryptographic hash function is a map H: {0,1}* → {0,1}ⁿ. The star means the input can be any bit string, of any length. The n means the output always has the same fixed length. We write H(m) = h, where m is the message, H is the hash function, and h is the digest — also called the hash value or the fingerprint.

Three properties define a cryptographic hash:

  • Preimage resistance: given h, finding any m with H(m) = h takes about 2ⁿ hashes. This is what makes the hash one-way.
  • Second preimage resistance: given one message m, finding a different m′ with H(m′) = H(m) also takes about 2ⁿ hashes. This protects a message you already hold.
  • Collision resistance: finding any two different messages with the same digest takes about 2^(n/2) hashes, not 2ⁿ. The next section shows why.

The properties form a chain: collision resistance implies second preimage resistance, and second preimage resistance implies preimage resistance. Collision resistance is the strongest requirement and the one attackers try first. A usable hash must also be fast, and must avalanche: changing one input bit should change about half of the output bits, so a near-miss message gives a completely different digest.

The birthday bound halves the security

Suppose a room has 23 people. The chance that two of them share a birthday is above one half, which surprises people because 23 is far below 365. The reason is that we compare pairs, and 23 people form 253 pairs. A hash behaves the same way. To hit a chosen digest you need about 2ⁿ hashes, but you only need about 2^(n/2) hashes before two of your own digests match each other.

P(collision) ≈ 1 − e^(−k²/2^(n+1))

k is the number of hashes computed, n is the digest length in bits, and P is the chance that at least two of the k digests are equal. Setting P = 0.5 gives k ≈ 2^(n/2).

So a 256-bit digest gives only 128 bits of collision security, and a 128-bit digest gives 64 bits. A fast GPU computes billions of hashes per second. That makes 2^64 a real risk for a well-funded attacker, while 2^128 stays out of reach. Short digests are one reason MD5 and SHA-1 failed; the other is that their compression functions were also found to be weak.

Merkle–Damgård: pad, split, compress

A hash must accept any length, but the internal mixing function works on fixed sizes. The Merkle–Damgård construction bridges the two.

  1. Pad the message: append a 1 bit, then zeros, then the original message length as a fixed-size number, so the total becomes an exact multiple of the block size (512 bits for SHA-256).
  2. Split the padded message into blocks B₁, B₂, …, B_k.
  3. Start from a fixed chaining value h₀, called the initialisation vector (IV). SHA-256 uses eight fixed 32-bit words.
  4. For i = 1 to k compute hᵢ = f(hᵢ₋₁, Bᵢ). The compression function f takes the previous chaining value plus one block, and returns a new chaining value of the same size.
  5. The digest is the final chaining value h_k: 256 bits for SHA-256, which is 64 hex characters.

The gain is reuse. The function f only ever sees 512 + 256 bits, so the same code hashes a two-line email or a 2 GB video. If f is collision resistant and the padding is unambiguous, H is collision resistant too. MD5, SHA-1 and SHA-2 all use this design. SHA-3 uses a different one, the sponge: the message is absorbed into a wide state of b bits (rate r plus capacity c), and the digest is squeezed out at the end. There is no chaining value to restart, which matters for the flaw in the next section.

  • Password storage: keep salt and H(salt ‖ password), never the password itself. Salting defeats precomputed tables (see Unit 5).
  • Hash-then-sign: a signature over a long message is really a signature over its digest (4.8).
  • MAC building: a keyed hash authenticates a message (4.7).
  • Hash tables and deduplication: the digest indexes a bucket, or names a file so identical files are stored once.
  • Proof of work: a miner repeatedly hashes a block header with a changing nonce until the digest falls below a target.

One weakness follows directly from the design. In Merkle–Damgård the digest is the last chaining value, so anyone who knows H(m) and the length of m can continue the compression from that value and compute H(m ‖ pad ‖ X) for any suffix X, without knowing m. This breaks the naive MAC H(secret ‖ message). HMAC, in 4.7, is built to avoid exactly this.

Worked example

Question. A toy iterated hash uses 4-bit values: h₀ = 2 and hᵢ = (hᵢ₋₁ + Bᵢ) mod 16, where Bᵢ is the i-th message block, a number from 0 to 15. (a) Compute the digest of the blocks 3, 7, 5. (b) Recompute for the blocks 3, 7, 6. (c) Find a different three-block message with the same digest as part (a). (d) For a real 256-bit hash, state the brute-force cost of a preimage attack and of a collision attack.

  1. State the toy hash: h₀ = 2, and each block adds to the running value modulo 16.
  2. Block 3: h₁ = (2 + 3) mod 16 = 5.
  3. Block 7: h₂ = (5 + 7) mod 16 = 12.
  4. Block 5: h₃ = (12 + 5) mod 16 = 17 mod 16 = 1. Digest = 1.
  5. Part (b), last block changed to 6: h₁ = 5, h₂ = 12, h₃ = (12 + 6) mod 16 = 18 mod 16 = 2. Digest = 2. One changed block changed the digest.
  6. Part (c), try blocks 4, 6, 5: h₁ = (2 + 4) mod 16 = 6; h₂ = (6 + 6) mod 16 = 12; h₃ = (12 + 5) mod 16 = 17 mod 16 = 1. Same digest 1, so the messages (3, 7, 5) and (4, 6, 5) collide.
  7. Part (d): a preimage attack needs about 2^256 hashes for n = 256. A collision attack needs about 2^(256/2) = 2^128 hashes, by the birthday bound.
  8. Comment: the toy only adds, so collisions are trivial to build. A real compression function mixes and shifts, but the birthday bound still applies.

Answer. Digests are 1 for blocks 3, 7, 5 and 2 for blocks 3, 7, 6; the message 4, 6, 5 also hashes to 1; and for a 256-bit hash a preimage costs about 2^256 hashes while a collision costs about 2^128.

  • Hashing is not encryption. There is no key and no inverse operation; calling it encryption loses marks.
  • Collision resistance costs about 2^(n/2) operations because of the birthday attack, not 2ⁿ. Many answers lose marks here.
  • Read the question carefully: breaking a preimage, a second preimage and a collision are three different attacks on three different properties.
  • A salt is stored openly with the hash and is not a secret key. Its job is to make precomputed tables useless.
  • H(secret ‖ message) is not a safe MAC for Merkle–Damgård hashes, because of length extension. Use HMAC.

4.7 Message authentication codes and HMAC

A MAC is a short tag computed over a message with a shared secret key. It answers two questions at once: did this message come from someone holding the key, and was it changed in transit? Nothing is encrypted, so a MAC protects integrity, not secrecy. TLS, IPsec and the traffic between bank servers and the UPI switch carry a MAC on every record. This chapter defines the MAC, contrasts it with a plain hash and a signature, works through HMAC, and places it next to encryption.

You need 4.6 for hash properties and the Merkle–Damgård structure, and Unit 3 for CBC mode, block ciphers and CCA security.

What a MAC is and what it gives

A message authentication code (MAC) is a short tag T computed over a message M with a secret key K that both sides share in advance. The sender sends M and T together. The receiver recomputes the tag from the received message with the same key and compares. Equal tags mean the message came from a key holder and arrived unchanged.

T = MAC(K, M)    Verify(K, M, T) → accept or reject

K is the shared secret key; M is the message, of any length; T is the tag, a fixed n bits. Both sides run the same key, so a MAC is a symmetric-key tool.

Every bit of M affects T, so one flipped bit changes the tag almost always. The MAC hides nothing: M travels in the clear, or is encrypted separately.

  • Message authentication: only a key holder can produce a valid tag.
  • Integrity: any change to M or to T is caught.
  • Replay protection only if M carries a nonce or sequence number that the receiver checks; the tag alone says nothing about freshness.
  • No confidentiality: M is readable.
  • No non-repudiation: the receiver holds K too, so neither side can prove to a third party who sent it.

A plain hash (4.6) has no key, so anyone recomputes it and an attacker changes message and digest together. A digital signature (4.8) uses the sender's private key, needs no shared secret, gives non-repudiation, and is far slower.

CBC-MAC and the length-extension trap

CBC-MAC reuses a block cipher from Unit 3. Encrypt the message in CBC mode with IV = 0 and key K; the last ciphertext block is the tag.

C₁ = E_K(M₁), Cᵢ = E_K(Mᵢ ⊕ Cᵢ₋₁), T = Cₗ

M₁ … Mₗ are the message blocks, b bits each; E_K is AES or DES under key K; l is the block count; T is the one-block tag.

Requirement: every message must have the same fixed length. Otherwise, given the tag T = E_K(M₁) of a one-block message M₁, an attacker forges the tag of the two-block message M₁ ‖ (M₁ ⊕ T), because its tag is E_K((M₁ ⊕ T) ⊕ T) = E_K(M₁) = T. CMAC repairs this by deriving two subkeys from K and using one of them on the last block.

The shortcut T = H(K ‖ M) is unsafe with any Merkle–Damgård hash such as SHA-256. The digest is the final chaining value, and the next block is absorbed as if the chain continued. An attacker who sees M and T knows the internal state, appends blocks X without knowing K, and predicts the new tag; the receiver accepts M ‖ pad ‖ X. This is length extension.

HMAC hides that inner state.

HMAC in full

HMAC hashes twice, with the key under two different pads.

tag = H( (K ⊕ opad) ‖ H( (K ⊕ ipad) ‖ M ) )

K is the shared key, zero-padded to the hash block size b (64 bytes for SHA-256, 128 for SHA-512); ipad is the byte 0x36 repeated b times; opad is 0x5C repeated b times; ⊕ is XOR; ‖ is concatenation; H is SHA-256 here; the tag is n = 256 bits.

  1. If K is longer than b bytes, replace it by H(K), 32 bytes for SHA-256. Zero-pad it on the right to exactly b bytes.
  2. Inner key = K ⊕ ipad. Inner digest = H(inner key ‖ M), n bits.
  3. Outer key = K ⊕ opad.
  4. tag = H(outer key ‖ inner digest).
  5. Truncate to t bits if the protocol wants a shorter tag.

The attacker never sees the inner digest, because the outer step hashes it again, so the chain cannot be continued. The two pads make the inner and outer keys different.

Key length: at least n bits (256 for SHA-256) from a random source; longer keys are hashed down. Truncation: keep at least half of n as a rule of thumb; NIST permits shorter truncations, down to 32 bits, with security about 2^t, and real protocols use tags of 80 or 96 bits. Quote the t the protocol specifies. Verification runs in constant time: XOR the received and computed tags, OR the byte differences into one accumulator, and test once at the end. A loop that stops at the first mismatch leaks, through timing, how many leading bytes were right.

Where the MAC goes next to encryption

Unit 3 closed with CCA security: an attacker who asks for decryptions and watches which ciphertexts are rejected can break naive CBC. A MAC shuts that door, because a modified ciphertext fails verification before any decryption happens.

  • Encrypt-and-MAC: encrypt the plaintext, and separately compute the tag over the plaintext; ciphertext and tag travel side by side, the tag in the clear (as in SSH). A tag over plaintext sent openly can leak information about the plaintext, so avoid it.
  • MAC-then-encrypt: encrypt plaintext ‖ tag together. Used in older TLS; the receiver must decrypt before checking, which led to padding-oracle attacks.
  • Encrypt-then-MAC: encrypt, then tag the ciphertext and the header. The receiver checks the tag first and drops bad data without decrypting. Preferred.

Authenticated encryption with associated data (AEAD) modes do both jobs in one pass. AES-GCM and ChaCha20-Poly1305 produce ciphertext and tag together, and the tag also covers header bytes sent in the clear.

Worked example

Question. A toy hash adds message blocks modulo 16, starting from h₀ = 0: hᵢ = (hᵢ₋₁ + Xᵢ) mod 16. The 4-bit stand-ins are key K = 5, ipad = 6, opad = 12, and the message blocks are 7 and 4. (a) Compute the HMAC tag. (b) Compute the naive tag H(K ‖ M). (c) Say in one line why the naive value cannot be trusted.

  1. Inner key: K ⊕ ipad = 5 ⊕ 6 = 3, since 0101 ⊕ 0110 = 0011.
  2. Inner digest: h runs 0 + 3 = 3, then 3 + 7 = 10, then 10 + 4 = 14. Inner digest = 14.
  3. Outer key: K ⊕ opad = 5 ⊕ 12 = 9, since 0101 ⊕ 1100 = 1001.
  4. Outer digest: h runs 0 + 9 = 9, then 9 + 14 = 23; 23 mod 16 = 7. Tag = 7.
  5. (b) Naive: h runs 0 + 5 = 5, 5 + 7 = 12, 12 + 4 = 16; 16 mod 16 = 0. Naive tag = 0.
  6. (c) An attacker who sees M = 7, 4 and tag 0 knows the running state, so it appends any block X and predicts the new tag (0 + X) mod 16; the receiver accepts the longer message. The key is only a prefix of the data, not a hidden state, which is exactly what length extension exploits.

Answer. The HMAC tag is 7 and the naive H(K ‖ M) tag is 0; the naive form is forgeable by length extension.

Exam traps

  • A MAC does not encrypt. If confidentiality is also wanted, pair it with encryption; a tag over plaintext leaves the plaintext readable.
  • Both sides hold the MAC key, so a MAC gives no non-repudiation. Only a signature with the sender's private key does.
  • Never present T = H(K ‖ M) as a valid MAC: with a Merkle–Damgård hash it falls to length extension. Show the appended-block attack.
  • HMAC is H(outer ‖ H(inner ‖ M)): inner layer first, key XORed with the pad, not concatenated with it. Reversing the layers or dropping the XOR loses the marks.
  • Encrypt-then-MAC means the tag covers the ciphertext. Tagging the plaintext is a different scheme and breaks the CCA argument.

4.8 Digital signatures and RSA signatures

A digital signature proves who sent a message and that the message was not changed. The signer hashes the message and applies a private key to the hash; anyone can check the result with the public key. Only the private-key holder can produce a valid signature, so the receiver gets authentication, integrity and non-repudiation. Signatures are used in software updates, signed documents, bank messages and certificates. A signature does not hide the message: it proves origin and integrity, not secrecy.

You need: RSA exponents from <a href='#rsa-cryptosystem'>Chapter 4.2, hash properties from <a href='#cryptographic-hash-functions-and-sha'>Chapter 4.6, and public-key trust from <a href='#key-management-key-distribution-and-digital-certificates'>Chapter 4.5.

What a signature must give

A digital signature is a value attached to a message that lets any verifier check who signed and whether the message changed. It must give message authentication: the verifier learns that the signer holds the private key. It must give integrity: any change to M changes H(M), so the check fails. It must give non-repudiation: after signing, the owner cannot deny it, because only the owner has d. It must be unforgeable even when the attacker can ask for signatures on chosen messages; this is existential unforgeability under chosen-message attack (EUF-CMA). An existential forgery produces at least one new message together with a valid signature for it; the attacker does not choose that message. A universal forgery produces a valid signature for any message the attacker chooses. A signature does not hide the message. Anyone can read M; secrecy needs encryption. Used in software updates, signed PDFs, bank messages and certificates.

Hash then sign with RSA

The recipe is hash then sign. First compute h = H(M), a short digest. Then apply the signer's private key to h. With RSA the signature is s = hd mod n. Here M is the message, H is a hash function, h is the digest as an integer, d is the private exponent, n is the RSA modulus, and s is the signature, an integer with 0 ≤ s < n. e is the public exponent. The signer sends (M, s). The verifier recomputes h′ = H(M) and accepts if h′ = se mod n. This works because (hd)e = hde = h mod n for valid RSA keys, from <a href='#rsa-cryptosystem'>Chapter 4.2.

s = h<sup>d</sup> mod n,   check h′ = s<sup>e</sup> mod n

M is the message; h = H(M) is its hash as an integer; d is the private exponent; e is the public exponent; n is the RSA modulus; s is the signature; h′ is the verifier's recomputed hash.

Why hash first? RSA signs only numbers smaller than n. A long message is not a number below n. Hashing reduces any message to one fixed-size integer below n. Hashing also binds every bit of M into h; a one-bit change gives a different digest with high probability, as in <a href='#cryptographic-hash-functions-and-sha'>Chapter 4.6. In practice h is not signed raw. The hash is encoded with padding: PKCS#1 v1.5 uses a fixed byte pattern and a hash identifier, and PSS uses random salt and masks. Then s = Pad(H(M))d mod n. The verifier removes the padding after se mod n and compares the hash. Padding is required for security.

Padding blocks textbook forgery

Textbook RSA is multiplicative. If s1 = h1d mod n and s2 = h2d mod n, then (s1s2)e = h1h2 mod n. So s1s2 mod n is a valid signature on h1h2 mod n. An attacker who can ask for signatures on chosen messages can multiply two answers and forge a third. The attacker can also pick any s, compute h = se mod n, and obtain a valid pair (h, s) for a random h. Padding stops both: a padded hash has a fixed structure, and the product of two padded values is not a valid padded hash. A secure scheme must resist existential forgery under chosen-message attack. RSA signatures use PKCS#1 v1.5 or PSS for this reason. Never sign a raw hash with textbook RSA.

Other schemes and uses

Other signature schemes use different hard problems. DSA signs a hash with a random secret k. It sets r = (gk mod p) mod q and s = k−1(h + x r) mod q; verification computes w = s−1 mod q, u1 = h w mod q, u2 = r w mod q, and checks ((gu1 yu2) mod p) mod q = r. ECDSA is the elliptic-curve version and gives the same security with shorter keys. ElGamal over prime p with generator g and public y = gx mod p sets r = gk mod p and s = (h − x r) k−1 mod (p − 1), and verifies gh = yr rs mod p. k is chosen with 1 ≤ k ≤ p − 2 and gcd(k, p − 1) = 1, so that k−1 mod (p − 1) exists. These schemes need a hash; reusing k leaks the private key.

Applications: a blind signature lets a user get a signature without the signer seeing the message, used in some digital cash designs. Timestamping signs a hash plus a time, proving a document existed then. Code signing signs software binaries so the operating system can check the publisher. A signature still does not hide M. For confidentiality, encrypt separately. Trust in the public key comes from certificates, covered in <a href='#key-management-key-distribution-and-digital-certificates'>Chapter 4.5.

Worked example

Question. RSA signature with p = 5, q = 11, e = 3, d = 27. The message hash is h = 9. (a) Find the signature s = hd mod 55 and verify it. (b) Using the valid pairs (h1, s1) = (9, 4) and (h2, s2) = (4, 49), forge a valid pair for a new hash without using d.

  1. n = 5 × 11 = 55. φ(n) = 4 × 10 = 40. Check e d = 3 × 27 = 81 ≡ 1 mod 40, so the keys are valid.
  2. 27 = 16 + 8 + 2 + 1. Powers mod 55: 9² = 81 ≡ 26; 9⁴ ≡ 26² = 676 ≡ 16; 9⁸ ≡ 16² = 256 ≡ 36; 9¹⁶ ≡ 36² = 1296 ≡ 31. Multiply: 31 × 36 = 1116 ≡ 16; 16 × 26 = 416 ≡ 31; 31 × 9 = 279 ≡ 4. So s = 4.
  3. Verify: 4³ = 64 ≡ 9 mod 55, equal to h = 9. Accept.
  4. Second pair: 49 ≡ −6; (−6)³ = −216; −216 + 4 × 55 = 4, so (4, 49) is valid.
  5. Forge: h3 = 9 × 4 mod 55 = 36. s3 = 4 × 49 = 196 ≡ 31 mod 55.
  6. Check: 31³ = 29791; 55 × 541 = 29755; remainder 36 = h3. So (36, 31) is valid without d.

Answer. The signature is s = 4 and it verifies to 9; the forged pair is (36, 31) and 31³ mod 55 = 36.

Exam traps

  • A signature gives authentication, integrity and non-repudiation, not confidentiality. Do not say it hides the message.
  • Hash before signing. Raw textbook RSA is multiplicative and forgeable.
  • Padding (PKCS#1 v1.5 or PSS) is mandatory; s = hd mod n alone is not a secure signature scheme.
  • Signing with the private key is not encryption with the private key. That phrase only fits textbook RSA and misleads.
  • A valid signature does not prove identity unless the public key is trusted through a certificate.

4.9 Zero-knowledge proofs and protocols

A zero-knowledge proof lets one party, the prover, convince another, the verifier, that a statement is true without handing over the evidence. The verifier learns only one bit: the statement is true. This is useful when the evidence is a secret, such as a password, a private key, or a colouring of a graph. The idea appears in privacy-preserving login, anonymous credentials and blockchain systems, where you must prove you are allowed to act without revealing why.

You need one-way functions from Chapter 4.1 and hash commitments from Chapter 4.6; a little probability for the soundness error.

The three properties

A zero-knowledge proof is an interactive protocol between a prover P and a verifier V. P knows a secret witness w for a public statement x. The statement might be “this graph has a 3-colouring” and w is the colouring. The protocol must satisfy three properties.

Completeness: if the statement is true and P follows the protocol, V accepts with probability 1, or very close to 1. An honest prover always convinces an honest verifier.

Soundness: if the statement is false, no cheating prover can make V accept, except with a small probability called the soundness error. For one round of the 3-colouring protocol the error is at most 1 − 1/|E|, where |E| is the number of edges in the graph. Repeating r independent rounds drives the error to at most (1 − 1/|E|)^r.

Zero knowledge: V learns nothing beyond the truth of x. Formally, there is a simulator S that, using only x and V’s randomness, can produce a transcript that looks exactly like a real run with P. If such a simulator exists, the transcript carries no secret information.

Honest-verifier zero knowledge is the weaker version most courses state: the simulator works only when V follows the protocol and does not deviate. It does not protect against a verifier who chooses challenges maliciously.

A full protocol: 3-colouring

Take a graph G = (V, E). The public statement is: G has a 3-colouring. The secret witness is a colouring c: V → {1, 2, 3} in which the two ends of every edge have different colours. A commitment is a hash H(colour || r) with a random nonce r; it hides the colour and binds the prover to it.

  1. The prover picks a random permutation π of {1, 2, 3}. For each vertex v it computes the hidden colour π(c(v)), picks a fresh nonce r_v, and sends com_v = H(π(c(v)) || r_v) to the verifier.
  2. The verifier picks one edge (u, v) uniformly from E and sends it as the challenge.
  3. The prover opens only the two commitments for u and v: it sends π(c(u)), r_u, π(c(v)), r_v.
  4. The verifier recomputes the two hashes, checks they match the commitments, and accepts the round when the two opened colours differ.
  5. Both sides repeat r independent rounds. The prover must reshuffle and recommit every round.

P(pass one round) ≤ 1 − 1/|E|

|E| is the number of edges; the verifier picks one edge uniformly and at least one edge is monochromatic.

P(pass r rounds) ≤ (1 − 1/|E|)^r

r is the number of independent rounds; each round uses a fresh permutation and fresh commitments.

Why it leaks nothing: each round opens one edge under a fresh random permutation. The verifier sees two different colours, which is exactly what any valid edge looks like; it never sees the original colour labels or the unopened vertices. Commitments are hiding, so unopened colours stay secret, and binding stops the prover from changing a colour after seeing the challenge.

Non-interactive proofs and uses

The Fiat–Shamir transform removes the live verifier. The prover computes the challenge itself as e = H(statement || all commitments), where H is a cryptographic hash. The prover then sends the commitments and responses. Anyone can recompute e and check the proof. This makes the proof non-interactive; security is argued in the random-oracle model, where H behaves like a random function.

The 3-colouring protocol is one example. Graph isomorphism proves that two graphs are the same up to renaming vertices without revealing the mapping. Schnorr’s protocol proves knowledge of a discrete logarithm without revealing the exponent. Both use the same commit–challenge–respond pattern.

  • Password-free login: prove you hold a private key or password-derived secret without sending it.
  • Blockchain privacy: prove a transaction is valid without revealing sender, receiver or amount.
  • Cloud correctness: prove a remote server computed the promised result without sending all the data.
  • Anonymous credentials: prove you are over 18 or hold a valid permit without showing the full document.

Worked example

Question. A triangle graph has vertices A, B, C and edges AB, BC, CA. The prover claims it has a 3-colouring. (a) Show an honest prover using colours 1, 2, 3 on A, B, C passes one round. (b) A cheating prover has only colours 1 and 2. Find its pass probability for one round. (c) Find the probability it passes 10 independent rounds. (d) State the general soundness bound for a graph with |E| edges and r rounds.

  1. Label the triangle vertices A, B, C. The edges are AB, BC, CA, so |E| = 3.
  2. Honest colouring: A = 1, B = 2, C = 3. Edge AB has colours 1 and 2, BC has 2 and 3, CA has 3 and 1. All three edges have different endpoint colours.
  3. A random permutation of {1, 2, 3} keeps all endpoint colours different, so the honest prover passes every round with probability 1.
  4. Cheating prover with only colours 1 and 2: by the pigeonhole principle, two of the three vertices get the same colour. Those two vertices form exactly one edge. That edge is monochromatic.
  5. The other two edges have different colours. The verifier picks one of the 3 edges uniformly. The prover passes only if the verifier picks one of the two good edges, so P(pass) = 2/3 = 0.6667.
  6. In 10 independent rounds the prover must pass each round. P(pass all 10) = (2/3)^10 = 1024/59049 = 0.01734.
  7. General bound: for |E| = m edges and r rounds, P(pass all) ≤ (1 − 1/m)^r; substituting m = 3, r = 10 gives (2/3)^10.

Answer. The cheating prover passes one round with probability 0.6667 and ten independent rounds with probability 0.01734, so the soundness error is under 2 percent.

Exam traps

  • Do not say zero knowledge means the verifier learns nothing at all; the verifier does learn that the statement is true.
  • Do not swap soundness and completeness. Completeness is about an honest prover passing; soundness is about a cheating prover failing.
  • Do not forget that the prover must reshuffle and recommit every round. Reusing one commitment lets the verifier collect many opened edges and rebuild the colouring.
  • For the triangle with only two colours, exactly one of the three edges is monochromatic. The pass probability is 2/3, not 1/3 and not 1/2.

Message authentication code (MAC)A short tag computed over a message with a shared secret key; the receiver recomputes it to check both the source and the integrity of the message.4.7
Digital signatureThe sender's private-key operation on the hash of a message; anyone can verify with the public key, but only the key holder could have produced it, giving non-repudiation.4.8
Hash-then-signSigning H(M) instead of M itself; it is faster, works for any message length, and stops the multiplicative forgery that plain RSA signing allows.4.8
Zero-knowledge proofA protocol in which the prover convinces the verifier that a statement is true while leaking nothing beyond its truth.4.9
Completeness, soundness, zero-knowledgeThe three required properties: an honest prover always convinces, a cheating prover cannot convince except with small probability, and the transcript reveals nothing about the secret.4.9

Takeaways

  1. Public-key cryptography replaces a shared secret with a pair of keys, and it works only because some functions are easy one way and hard the other way.
  2. RSA hides the message inside modular exponentiation, and the trapdoor is the factorisation of n into its two primes.
  3. Diffie–Hellman lets two strangers build the same secret number over an open channel, but it authenticates nobody, so a man in the middle can defeat it unless signatures or certificates are added.
  4. ElGamal is Diffie–Hellman turned into encryption: each message gets a fresh random exponent and the ciphertext travels as a pair.
  5. A public key means nothing until a certificate binds it to a name, which is why CAs and X.509 certificate fields matter in real systems.
  6. A cryptographic hash compresses any input to a fixed digest and must resist preimages, second preimages and collisions.
  7. A MAC proves integrity and origin between two parties who already share a key; it cannot settle a dispute in court.
  8. A digital signature is the private-key operation on a hash, so it gives integrity, authentication and non-repudiation in one step.
  9. Zero-knowledge proofs let you prove you know a secret without showing it, and repeating rounds drives the cheating probability as low as you like.

Exam question bank

Long answers here usually ask you to state a scheme's hard problem, write the algorithm step by step, prove that decryption or verification works, and then name the attack that the scheme blocks or fails to block.

Remember and understand

Understand Define a one-way function and a trapdoor one-way function. Explain why public-key encryption needs the trapdoor property, and give two candidate functions used in practice. 13 marks

Definition of one-way function with the easy/hard directions stated; Trapdoor as extra secret information that makes inversion easy; Why a plain one-way function gives only key exchange or signatures, not encryption; Examples: integer factorisation (RSA) and discrete logarithm (Diffie–Hellman, ElGamal); Note that hardness is believed, not proved.

Understand Explain RSA key generation, encryption and decryption. Why must p and q be kept secret, and why must φ(n) never be published? 13 marks

Choose large primes p and q, compute n = p × q and φ(n) = (p − 1)(q − 1); Choose e with gcd(e, φ(n)) = 1, compute d with e × d ≡ 1 (mod φ(n)); Public key (e, n), private key (d, n); Encryption C = M^e mod n; decryption M = C^d mod n by Euler's theorem; Knowing φ(n) or the factorisation gives d at once, so both stay secret.

Understand Describe the Diffie–Hellman key exchange with a diagram. State the hard problem it rests on and the attack it does not prevent. 13 marks

Public parameters: large prime p and generator g; Alice picks secret a, sends A = g^a mod p; Bob picks secret b, sends B = g^b mod p; Shared secret K = B^a = A^b = g^(ab) mod p; Security rests on the discrete logarithm problem; No authentication, so a man-in-the-middle can run two separate exchanges.

Understand List the fields of an X.509 digital certificate and explain how a CA signature lets a stranger trust a public key. 13 marks

Version, serial number, issuer, validity, subject, subject public key, extensions, signature algorithm, signature value; CA hashes the body and signs the hash with its private key; Verifier obtains the CA public key out of band and checks the signature; Chain of trust up to a root CA; Revocation and expiry handled by validity dates and CRL/OCSP.

Understand Define a cryptographic hash function and explain preimage resistance, second preimage resistance and collision resistance with the birthday bound. 13 marks

Fixed-length digest from arbitrary-length input, plus efficiency and avalanche behaviour; Preimage: given h, find M with H(M) = h — about 2^n work; Second preimage: given M₁, find M₂ with the same digest; Collision: find any pair — about 2^(n/2) work by the birthday paradox; Consequence: a 256-bit hash gives only 128-bit collision security.

Understand Compare a message authentication code with a digital signature on the basis of keys used, services provided and non-repudiation. 13 marks

MAC uses one shared secret key; signature uses a private/public pair; Both give integrity and message origin authentication; Only a signature gives non-repudiation, because the verifier could not have made a MAC; MAC is symmetric and fast; signature is asymmetric and slower; Practical use: MAC inside TLS records, signature on certificates and software updates.

Apply

Apply Take p = 11, q = 17, so n = 187 and φ(n) = 160. With e = 7, find d, then encrypt the block M = 88 and show that decryption returns 88. 13 marks

d = 23 because 7 × 23 = 161 ≡ 1 (mod 160); C = 88^7 mod 187, computed by repeated squaring (88² → 77, 88⁴ → 132); C = 11; M = 11^23 mod 187 = 88; Check by confirming that e × d ≡ 1 (mod φ(n)) made the exponents cancel.

Apply In a Diffie–Hellman exchange take p = 23 and g = 5, with Alice's secret a = 6 and Bob's secret b = 15. Compute both public values and the shared secret, and show both routes give the same answer. 8 marks

A = 5^6 mod 23 = 8; B = 5^15 mod 23 = 19; K = B^a mod 23 = 19^6 mod 23 = 2; Check K = A^b mod 23 = 8^15 mod 23 = 2; Remark that a real p is hundreds of bits long.

Apply Write the ElGamal encryption and decryption steps and prove that decryption returns the plaintext. Then show what goes wrong if the sender reuses k for two messages. 13 marks

Public key (p, g, y = g^x mod p), private key x; Choose random k, compute C₁ = g^k mod p and C₂ = m × y^k mod p; Decrypt: s = C₁^x mod p, then m = C₂ × s⁻¹ mod p; Proof: C₂ × (g^(kx))⁻¹ = m × g^(xk) × g^(−xk) = m; Reusing k gives the same C₁ and the ratio C₂/C₂′ equals m/m′, so the plaintext leaks.

Apply Describe how an RSA digital signature is produced and verified on a long message, and why the message is hashed first. 13 marks

Sender computes h = H(M), then signature S = h^d mod n; Receiver computes h′ = H(M) and checks whether S^e mod n equals h′; Hashing makes signing fast and independent of message length; Hashing blocks the multiplicative forgery on raw RSA: S₁ × S₂ signs M₁ × M₂; Mention padding schemes and per-message hashing in practice.

Analyze and evaluate

Analyze Explain how a man-in-the-middle attack defeats a plain Diffie–Hellman exchange, and show how certificates or signed public keys stop it. Mention a replay attack as well. 13 marks

Attacker intercepts A and B, sends its own values to each side; Two shared secrets created, attacker decrypts and re-encrypts traffic; Root cause: the exchange authenticates nobody; Fix: sign the public values, or fetch them from a certificate issued by a trusted CA; Replay defence: fresh nonces or timestamps in the signed data.

Evaluate Textbook RSA is deterministic and multiplicatively homomorphic. Explain both weaknesses and evaluate the countermeasures used in practice. 13 marks

Deterministic: same plaintext always gives the same ciphertext, so guesses can be tested; Small-message and small-exponent attacks when M^e < n; Multiplicative: E(M₁) × E(M₂) = E(M₁ × M₂), enabling chosen-ciphertext forgery; Countermeasure: randomised padding such as OAEP, giving different ciphertexts each time; Goal is IND-CCA2 security; raw RSA has none.

Analyze Explain a zero-knowledge proof using the graph-colouring or Ali Baba cave example. State completeness, soundness and zero-knowledge, and show how repetition reduces cheating probability. 13 marks

Prover holds a secret witness, here a valid 3-colouring; Each round: prover commits to a random permutation of colours, verifier picks one edge, prover opens only those two vertices; Cheating succeeds with probability 1/2 per round, so t rounds give 2^−t; Completeness: honest prover always passes; soundness: a wrong colouring is caught; Zero-knowledge: each transcript can be simulated without the witness; Fiat–Shamir replaces the verifier with a hash to make it non-interactive.

Evaluate A company must let staff log in to a web portal and prove data came from its servers. Compare symmetric key distribution, public-key encryption, MACs and certificates, and recommend a full design. 16 marks

Symmetric keys scale as n(n − 1)/2 pairs; public keys need only a directory; Public-key encryption is slow, so use it to carry a session key, then symmetric ciphers for data; MAC or HMAC for per-record integrity between parties sharing the session key; Signatures and certificates for server identity and non-repudiation; Hashing for password storage and integrity checks; Recommendation: TLS-style handshake — certificates for authentication, Diffie–Hellman or RSA for the shared secret, AEAD or HMAC for records.

Glossary

Avalanche effect
The property that flipping one input bit changes roughly half the output bits.
Certificate Authority
A trusted body that signs certificates and whose public key verifiers already hold.
Ciphertext
The scrambled output of an encryption algorithm, unreadable without the key.
Collision
Two different inputs that produce exactly the same hash digest.
Digest
The fixed-length output of a hash function, also called the hash value or fingerprint.
Digital certificate
A signed data structure binding a subject's identity to that subject's public key.
Digital signature
A value derived from a message and a private key that anyone can verify with the matching public key.
Discrete logarithm
The exponent x solving gˣ ≡ h (mod p), believed hard to find for large primes.
Hash function
A function mapping an input of any length to a fixed-length digest, fast to compute and hard to invert.
HMAC
A standard keyed-hash MAC built from any hash function using inner and outer padded keys.
Key exchange
A protocol by which two parties who share no prior secret end up with a common key.
Man-in-the-middle attack
An attack where the adversary relays and alters traffic between two parties who believe they talk directly.
Message authentication code
A keyed tag over a message that proves integrity and origin to anyone holding the shared key.
Modulus
The number n in arithmetic modulo n, meaning all results are taken as remainders after division by n.
Non-repudiation
The property that the signer of a message cannot later deny having signed it; only signatures give this.
OAEP
Optimal Asymmetric Encryption Padding, a randomised padding for RSA that gives chosen-ciphertext security.
Padding
Extra bits or bytes added to a message before hashing or encryption to reach a block size or to add randomness.
Plaintext
The original readable message before encryption or after decryption.
Primitive root
A number g whose powers generate every nonzero residue modulo a prime p.
Public-key cryptography
Encryption or signature scheme in which each user holds a public key that anyone may use and a private key that only the user holds.
Replay attack
Resending a previously valid message or token to get it accepted a second time; countered with nonces or timestamps.
Totient φ(n)
The count of numbers from 1 to n that share no factor with n; φ(pq) = (p − 1)(q − 1) for distinct primes p and q.
Trapdoor one-way function
A function easy to compute forwards, hard to invert, but easy to invert for anyone who knows a secret trapdoor value.
X.509
The widely used standard format for public-key certificates and their fields.
Zero-knowledge proof
A protocol proving a statement true while revealing nothing beyond the truth of the statement.
