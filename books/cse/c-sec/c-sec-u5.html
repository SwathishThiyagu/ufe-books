5.1 User authentication: passwords, challenge-response, multi-factor

Authentication proves that a person or a device is who it claims to be. The system checks something you know (a password), something you have (a phone or token), or something you are (a fingerprint). Passwords alone are weak: people reuse them and servers leak them, so servers store salted slow hashes and demand a fresh random challenge at every login. Multi-factor authentication combines two or more kinds of proof. Bank apps, UPI payments and office VPNs all use these checks.

You need hash functions and MACs (Unit 4, Public Key Cryptography and Hashing), plus replay and phishing attacks (Unit 1, Foundations).

Entity authentication and the three factors

Entity authentication proves that a live party is who it claims to be, right now, in this session. Message authentication proves that one specific message came from the claimed sender and was not altered; MACs and digital signatures do that job (Unit 4). A login screen performs entity authentication; every request after login should carry message authentication.

Proof comes from one of three categories, called factors. Knowledge: something you know, such as a password or PIN. Possession: something you hold, such as a phone or smart card. Inherence: something you are, such as a fingerprint. Two secrets from the same category still count as one factor.

Some syllabi call this topic user authentication; the names cover the same material.

Storing passwords: salt and slow hashes

A server never stores plaintext passwords: one leaked database exposes every account, and reuse spreads the damage. A fast hash such as SHA-256 is not enough either, because the attacker hashes a wordlist once or uses precomputed tables.

A salt is a random value generated per user and stored in plain view beside the hash. The server keeps (salt, H(salt ‖ password)), where H is a hash function and ‖ means concatenation. Two users with the same password get different hashes, so precomputation fails and the attacker must guess separately for each account.

  1. Generate a random 16-byte salt for this user at registration.
  2. Compute h = H(salt ‖ password) with a slow password hash.
  3. Store the user id, salt, h and algorithm parameters.
  4. At login, read the salt, recompute h' from the typed password, compare in constant time.
  5. On failure, return the same error whether the user exists or not.

Three slow hashes dominate: bcrypt, PBKDF2 and Argon2, each with a tunable work factor. In bcrypt the cost is a power of two, so cost 12 means 2¹² = 4096 rounds of key setup. PBKDF2 takes an iteration count, often several hundred thousand. Argon2 takes memory, iterations and parallelism; being memory-hard it hurts GPU farms. Tune so one login costs about 0.1 to 0.5 s, and raise the parameters as hardware improves.

Online guessing hits the server and is stopped by rate limits, exponential backoff and CAPTCHA. Lockout after five failures works, but a permanent lock lets anyone deny service to a user, so lock for a fixed time. Offline guessing happens after a leak and is limited only by hash cost and password length.

Challenge-response: the fresh nonce

If the client sends the stored password hash to log in, that hash is a password equivalent: an attacker who records one login can replay it. A challenge-response exchange removes this. The server sends a fresh random number and the client's answer depends on it.

Answer = H(password ‖ R)

H is a hash function such as SHA-256, password is the shared secret, R is the server's random nonce, at least 128 bits, and ‖ means concatenation. The answer differs at every login because R differs.

  1. The client sends the login name and a request id, so two logins never share a nonce.
  2. The server picks R from a cryptographic random generator and ties it to that session.
  3. The client computes H(password ‖ R) and sends the answer.
  4. The server recomputes the expected answer, compares, then discards R.

Replay fails on freshness. Suppose R = 913. An attacker holds H(password ‖ 512) from an earlier session and sends it; the server computes H(password ‖ 913), sees a mismatch and rejects. With a MAC the answer is MAC_K(R), where K is a key derived from the password.

The server needs the password in usable form to verify such an answer, so this exchange normally runs inside TLS (see 5.4). PAKE protocols such as SPAKE2 and OPAQUE avoid that need; FIDO2 keys sign the challenge with a private key instead.

Multi-factor: OTP, TOTP and hardware tokens

An OTP (one-time password) is valid once and expires in minutes. Sent by SMS it is weak, because SIM swap and network interception exist, but it is still better than a password alone. An app-based TOTP avoids the SMS channel entirely.

T = ⌊t / 30⌋,  code = Truncate(HMAC(K, T)) mod 10⁶

t is Unix time in seconds, 30 is the time step in seconds, T is the step counter, K is the shared seed, HMAC uses SHA-1 or SHA-256, and truncation keeps 31 bits so the six-digit code is the remainder modulo 10⁶.

The server accepts the current step and usually one step either side for clock drift, and refuses a code already accepted in that window. The code space is only 10⁶, about 2²⁰, so rate-limiting the verification endpoint matters as much as the number of digits.

Hardware tokens and passkeys (FIDO2, WebAuthn) keep a private key inside the device and sign the server's challenge. The key never leaves the device and the signature is bound to the site's origin, so a phishing copy of the page gains nothing. Only a few syllabi go into those internals.

2FA means exactly two factors from different categories; MFA means two or more. Password plus OTP is 2FA. Password plus a security question is one factor asked twice. Step-up authentication adds a factor when risk rises: browse with a password, but demand an OTP to add a payee or move a large amount.

Worked example

Question. A server uses the toy hash H(s) = (sum of ASCII codes of s) mod 1000, chosen only so you can compute it by hand, and the user's password is "kite". Today's nonce is R = 913. (a) Compute the client's answer H(password ‖ R). (b) An attacker recorded the answer for an earlier nonce R = 512. Does the server accept it? Give both hash values.

  1. ASCII codes of "kite": 107, 105, 116, 101; sum = 429.
  2. ASCII codes of "913": 57, 49, 51; sum = 157.
  3. H("kite913") = (429 + 157) mod 1000 = 586. The client sends 586.
  4. ASCII codes of "512": 53, 49, 50; sum = 152.
  5. H("kite512") = (429 + 152) mod 1000 = 581. This is the recorded answer.
  6. The server expects 586 but receives 581, so the comparison fails and the login is rejected.

Worked example 2

Question. A TOTP app uses a 30 s time step. At Unix time t = 1799 s, which step counter T does the client use?

  1. Divide the time by the step: 1799 / 30 = 59.97.
  2. Take the floor: T = ⌊59.97⌋ = 59.
  3. The next step starts at t = 60 × 30 = 1800 s, so at 1799 s the counter is still 59.

Answer. The client uses step counter T = 59.

Exam traps

  • Sending H(password) with no fresh challenge makes the hash a password equivalent; a recorded answer logs in again.
  • Password plus OTP is 2FA; password plus security question is one factor counted twice. Two passwords are never two factors.
  • A salt is public and does not slow a targeted guess. It stops precomputation; the slow hash parameters do the slowing.
  • A six-digit OTP has only 10⁶ values, about 20 bits. Without rate limiting the endpoint falls to brute force in minutes.
  • A permanent lockout is a denial-of-service gift to an attacker. Use short temporary locks with backoff, and compare secrets in constant time.

5.2 Kerberos authentication

Kerberos is a network authentication protocol built around one trusted server, the Key Distribution Center (KDC). A user proves identity once, and the KDC hands out time-limited encrypted tickets. Each ticket is a small blob that a service can decrypt and trust without calling the KDC or asking for a password, so passwords never travel on the wire. It is used where many users share many servers inside one organisation: campus logins, Active Directory domains, NFS file shares, Hadoop clusters. This chapter follows Kerberos V5, the version still in use.

You need: 5.1 for challenge–response and freshness, and Unit 3 symmetric encryption for block ciphers and key distribution.

Principals, realms and the KDC

Kerberos starts with a counting problem. If M users must talk to N servers with shared secret keys, every pair needs its own key, so roughly M × N keys must be created and stored. Kerberos adds one trusted third party, the Key Distribution Center (KDC). Each user shares one long-term key with the KDC, and each server shares one long-term key with the KDC. That is M + N keys instead.

keys = M + N

M is the number of user principals, each sharing one long-term key with the KDC; N is the number of service principals, each sharing one long-term key with the KDC.

A principal is any named entity Kerberos authenticates. A user principal looks like alice@CSE.AC.IN. A service principal looks like nfs/host1.cse.ac.in@CSE.AC.IN, with an optional instance after the slash. A realm is the set of principals run by one KDC, written in uppercase, for example CSE.AC.IN. A ticket issued in another realm needs cross-realm trust, which is advanced material.

The long-term key comes from the user's password through a string-to-key function, or from a keytab file for a service. The KDC keeps a copy of every principal's long-term key. A session key is a fresh random symmetric key for one client–server conversation, alive only as long as its ticket.

The KDC runs two logical services, both on port 88. The Authentication Server (AS) issues the Ticket Granting Ticket (TGT). The Ticket Granting Server (TGS) issues service tickets.

Three exchanges: AS, TGS, AP

The client talks to the KDC twice and to the server once. Each exchange uses a different key, and each reply is mostly a blob the client cannot read.

  1. AS-REQ (client → AS): client name, the TGS name, a nonce (a random number used once). When the KDC requires pre-authentication (common policy, not a core V5 requirement), the first request is refused with KDC_ERR_PREAUTH_REQUIRED and the client resends with a pre-authenticator: the current timestamp encrypted under its long-term key.
  2. AS-REP (AS → client): two parts. Part one is encrypted under the client's long-term key and carries the session key K(c,tgs), the TGT lifetime and the nonce. Part two is the TGT itself, encrypted under the TGS's long-term key, holding the client name, K(c,tgs) and the ticket lifetime.
  3. The client decrypts part one with its password-derived key, recovers K(c,tgs), and stores the TGT unread.
  4. TGS-REQ (client → TGS): the TGT, the wanted service name, a nonce, and an authenticator — client name plus current timestamp, encrypted under K(c,tgs).
  5. TGS-REP (TGS → client): the TGS decrypts the TGT with its own key, recovers K(c,tgs), decrypts the authenticator, and checks the timestamp and its replay cache. It replies with a service ticket encrypted under the server's long-term key and holding K(c,s), plus K(c,s) encrypted under K(c,tgs).
  6. AP-REQ (client → server): the service ticket plus a fresh authenticator encrypted under K(c,s).
  7. AP-REP (server → client): the server decrypts the ticket with its own key, gets K(c,s), decrypts the authenticator, and checks timestamp and replay cache. An optional reply carries the authenticator timestamp plus one, encrypted under K(c,s).

The AP-REP gives mutual authentication: only the real server can read K(c,s) and return the incremented timestamp. The ticket is reusable until it expires; the authenticator is made fresh for every request.

Timestamps, clock skew and the opaque TGT

Kerberos uses time instead of a challenge nonce between client and server. A server accepts an authenticator when |t_client − t_server| ≤ skew, where t_client is the timestamp inside the authenticator, t_server is the server's clock at arrival, and skew is the allowed difference, 5 minutes by default. Outside the window the server returns a clock skew too great error.

Replay is the risk. An attacker who copies an AP-REQ can resend it inside the window. Servers keep a replay cache of authenticators seen within the window and drop duplicates. The window also bounds how long that cache must be kept.

The client cannot read its TGT because it is encrypted under the TGS's long-term key, which only the KDC knows. The client carries it as an opaque token. This is deliberate: the ticket is self-protecting, so the TGS trusts its contents without a database lookup, and the client cannot change the session key or stretch the lifetime. The client holds K(c,tgs) separately in the readable AS-REP part.

Pre-authentication guards the AS exchange. Without it, anyone could send an AS-REQ naming alice, receive a blob encrypted under alice's key, and guess passwords offline. In V5 pre-authentication is an extensible framework, not a core requirement: many KDCs first answer an AS-REQ without a pre-authenticator with KDC_ERR_PREAUTH_REQUIRED, and only the resent request carries the encrypted timestamp. A wrong password fails at once and the attempt can be logged.

Worked example

Question. The file server's clock reads 10:00. The realm's clock skew limit is 5 minutes. (a) The client sends an authenticator stamped 10:04 by its own clock. Is it accepted? (b) A later request carries 10:06. Is it accepted? (c) What is the latest client timestamp the server would still accept?

  1. Convert all times to minutes after midnight. Server: 10 × 60 + 0 = 600 min. First client timestamp: 10 × 60 + 4 = 604 min. Second client timestamp: 10 × 60 + 6 = 606 min.
  2. Case (a): |t_client − t_server| = |604 − 600| = 4 min.
  3. Compare with the limit: 4 min ≤ 5 min, so the authenticator is accepted.
  4. Case (b): |606 − 600| = 6 min.
  5. 6 min > 5 min, so the server rejects it with a clock skew error.
  6. Case (c): the largest accepted timestamp satisfies t_client − t_server ≤ 5 min, so t_client ≤ 600 + 5 = 605 min = 10:05.

Answer. (a) Accepted, the difference is 4 minutes, within the 5-minute limit. (b) Rejected, the difference is 6 minutes. (c) The latest accepted client timestamp is 10:05.

Exam traps

  • The client never reads its own TGT: it is encrypted under the TGS's long-term key. Only the AS-REP part under the client's key is readable.
  • A ticket is not an authenticator. The ticket is reusable and encrypted under the target's long-term key; the authenticator is fresh per request and encrypted under the session key.
  • The timestamp check is loose in both directions and uses ≤, not <. A timestamp exactly 5 minutes away from the server clock is still accepted.
  • Ticket lifetime and clock skew are different numbers. Skew is about unsynchronised clocks; lifetime is about how long the ticket stays valid.
  • Pre-authentication is not the same as mutual authentication. Pre-auth protects the AS exchange from offline password guessing; the AP-REP proves the server knows the session key.

The real bounds: already-issued tickets expire; short lifetimes limit abuse. The attacker must stay hidden or re-forge after expiry. Recovery works by rotating keys — the krbtgt key and every principal's key — which invalidates everything the attacker minted. Detection and hardening are the practical controls.

5.3 IP security (IPsec)

IPsec is a set of protocols that protects IP packets at the network layer. It authenticates the sender and can encrypt the payload, so routers and links between two sites cannot read or alter traffic. Each protected flow uses a security association: a one-way agreement holding keys, algorithms and counters. IPsec is common in site-to-site VPNs, remote-access VPNs and host-to-host links. Because it works below TCP and UDP, applications need no change. Some syllabi call it IPSec.

You need: block ciphers and modes (see Unit 3), MAC and HMAC (see Unit 4), and MITM and replay attacks (see Unit 1).

AH, ESP and the two modes

IPsec has two protecting protocols. Authentication Header (AH) adds a MAC over the IP header and payload. It proves integrity and data origin, but it does not encrypt. Encapsulating Security Payload (ESP) can encrypt the payload and can also authenticate it. ESP is the usual choice when confidentiality is needed.

Transport mode keeps the original IP header and protects the upper-layer payload. Host-to-host IPsec often uses transport mode. Tunnel mode puts the whole original packet inside a new packet with a new outer IP header. Gateway-to-gateway VPNs use tunnel mode. In tunnel mode a router sees only the gateway addresses; the inner addresses are hidden.

  • AH: integrity and origin authentication only; no confidentiality.
  • ESP: confidentiality and/or integrity; usually integrity is also enabled.
  • Transport: original IP header stays visible; payload is protected.
  • Tunnel: new outer IP header; original packet is protected.

ESP in tunnel mode has fields in a fixed order: outer IP header, ESP header, encrypted inner packet, ESP trailer and ESP authentication data. The ESP header carries the security parameter index (SPI), a 32-bit value that names the security association, and a sequence number. The receiver uses the SPI to find the right security association.

Security association and anti-replay

A security association (SA) is a one-way agreement between two endpoints. One SA protects traffic from A to B; a second SA protects B to A. An SA is identified by three values: the SPI, the destination IP address, and the protocol (AH or ESP). The receiver looks up the SA by SPI and destination address.

Each SA stores the algorithms, keys, lifetime and sequence counter. The sender starts the sequence number at 1 and increments it for every packet sent under that SA. The number is 32-bit. The receiver keeps a sliding anti-replay window, often 64 packets wide. A packet whose sequence number is inside the window and already seen is dropped. A packet older than the window is also dropped. This stops an attacker from replaying a captured packet.

SA = (SPI, destination IP, protocol)

SPI is the 32-bit name from the packet header; destination IP is the receiving endpoint; protocol is AH or ESP.

The Security Policy Database (SPD) decides what to do with a packet. An SPD entry matches selectors such as source IP, destination IP, protocol and port. The action is protect, bypass or discard. If the action is protect, the SPD points to an SA in the Security Association Database (SAD). The SAD holds the live SA parameters.

Common ESP algorithms are AES in CBC or GCM mode for encryption, and HMAC-SHA-256 or AES-GCM for integrity. AH commonly uses HMAC-SHA-256. The exact set is chosen by policy and negotiated by IKE.

IKE and policy

Internet Key Exchange (IKE) creates and maintains SAs. It authenticates peers, negotiates algorithms and derives fresh keys. IKEv1 uses two phases. Phase 1 builds an IKE SA for control traffic. Phase 2 builds IPsec SAs for user traffic. Main mode and aggressive mode are phase-1 variants. IKEv2 uses fewer exchanges and supports MOBIKE, an extension for a peer that changes address. Network address translation (NAT) traversal and mobility details are advanced; only a few universities teach them.

The SPD is checked before IKE runs. A packet that needs protection but has no SA triggers IKE. After IKE finishes, the SAD has the SA and packets flow. When the SA lifetime expires, IKE rekeys. This keeps long-lived VPNs secure.

IPsec protects IP packets, not routing protocols. Routing security such as the Border Gateway Protocol (BGP) is a separate topic; BGPsec is not IPsec. IPsec also does not replace TLS for web applications. TLS works inside the application connection; IPsec works below it. A company can use both.

Worked example

Question. Host A at 10.1.1.5 sends TCP port 443 traffic to host B at 10.2.2.7. Two gateways use ESP tunnel mode with outer addresses 203.0.113.2 and 198.51.100.9. Which addresses does a router on the Internet see? Which addresses are hidden?

  1. The gateways build an ESP tunnel SA between 203.0.113.2 and 198.51.100.9.
  2. The original packet is 10.1.1.5 → 10.2.2.7 with TCP port 443. It becomes the inner packet.
  3. ESP encrypts the inner packet and adds an ESP header, trailer and authentication data.
  4. A new outer IP header is added: source 203.0.113.2, destination 198.51.100.9.
  5. A router on the Internet reads only the outer header. It sees 203.0.113.2 → 198.51.100.9.
  6. The inner 10.1.1.5 → 10.2.2.7 and port 443 are inside the encrypted payload, so they are hidden.

Answer. The router sees 203.0.113.2 → 198.51.100.9; 10.1.1.5 → 10.2.2.7 and TCP port 443 are hidden.

Exam traps

  • AH authenticates but does not encrypt; ESP can encrypt. A question that asks for confidentiality alone rules out AH.
  • Transport mode keeps the original IP header; tunnel mode adds a new outer IP header.
  • An SA is one-way. Two hosts need two SAs for two-way traffic.
  • The SPI selects the SA; the sequence number stops replay. Do not mix them.
  • IPsec is not TLS and does not secure BGP. BGPsec and TLS are separate.

Not for the exam. IPsec appears in cloud VPN gateways, SD-WAN and mobile backhaul. IKEv2 with MOBIKE lets a phone keep a VPN while its IP address changes. NAT traversal wraps ESP in UDP port 4500. Post-quantum IPsec is an active research area.

5.4 SSL/TLS, HTTPS and SSH

TLS and SSH protect data sent over an unsafe network. Both first run a handshake that authenticates the server or host and agrees on fresh symmetric keys. Then a record or transport layer encrypts and integrity-protects every message with those keys, using fast ciphers such as AES. TLS secures HTTPS, banking and UPI web pages. SSH secures remote login and file copy on servers. The channel protects bytes in transit; it does not prove that the web application itself is free of bugs.

You need: Unit 4 certificates and digital signatures, Unit 3 symmetric ciphers, and 5.1 authentication.

TLS record and handshake

TLS (Transport Layer Security; SSL is the older name; some syllabi call it transport-level security) runs above TCP and below the application. The handshake sets up keys. The record protocol protects each block of application data. A TLS record carries a content type, a version, a length, and a payload of at most 214 bytes (16,384 bytes). In TLS 1.2 the sender computes a MAC over a sequence number, type, version, length and payload, then encrypts payload and MAC. The sequence number stops record replay and reordering. Modern suites use AEAD (authenticated encryption with associated data), such as AES-GCM, which encrypts and authenticates in one operation.

The TLS 1.2 handshake in the figure uses RSA key exchange. The client sends ClientHello with a random C = 0x11, a list of cipher suites and extensions. The server replies ServerHello with a random S = 0x22, the chosen cipher suite, and its certificate. The client validates the certificate, makes a 48-byte pre-master secret PMS, encrypts it with the server's RSA public key, and sends it. Both sides compute the master secret. They derive a key block. Both sides send Finished: verify_data = PRF(master_secret, "client finished" or "server finished", Hash(handshake messages)), sent encrypted under the new record keys. The client sends ChangeCipherSpec and Finished first, then the server replies with ChangeCipherSpec and Finished, and then application data follows.

master_secret = PRF(PMS, "master secret", C ‖ S); key_block = PRF(master_secret, "key expansion", S ‖ C)

PRF is the TLS pseudo-random function; PMS is the 48-byte pre-master secret; C and S are the client and server randoms; ‖ means concatenation. The master secret is always 48 bytes. The key_block length depends on the chosen cipher suite; for example, TLS_RSA_WITH_AES_128_CBC_SHA needs 104 bytes (2 × 20-byte MAC keys, 2 × 16-byte AES keys, 2 × 16-byte IVs).

Certificates, TLS versions and HTTPS

Certificate validation is the core of TLS server authentication. The client checks that the chain ends at a trusted root, that the leaf names the host contacted, that dates are valid, and that key usage allows server authentication. It may check revocation by CRL (certificate revocation list) or OCSP (online certificate status protocol). A valid signature for another hostname is not enough.

A cipher suite names key exchange, authentication, bulk cipher, and MAC or AEAD. For example, TLS_RSA_WITH_AES_128_CBC_SHA in TLS 1.2 means RSA key transport, RSA certificate, AES-128-CBC, and HMAC-SHA1. A full TLS 1.3 handshake uses ephemeral (EC)DHE for forward secrecy; resumption can also run PSK-only or PSK with (EC)DHE. RSA key transport and CBC are removed. TLS 1.3 uses AEAD ciphers such as AES-GCM or ChaCha20-Poly1305, and encrypts most of the handshake. A full TLS 1.3 handshake takes one round trip (1-RTT). Ephemeral DH gives forward secrecy: stealing the server's long-term private key later does not decrypt past sessions.

HTTPS is HTTP inside TLS, normally on TCP port 443. It protects passwords, cookies and page content in transit. It does not stop SQL injection, cross-site scripting (XSS) or broken access control; those are web application flaws, covered in 5.9.

Session resumption avoids a full handshake. TLS 1.2 uses session IDs or tickets. TLS 1.3 uses pre-shared keys (PSK) from a previous session. Resumption saves CPU and latency, but ticket keys must be protected; a stolen ticket key can let an attacker resume sessions. TLS 1.3 0-RTT early data can be replayed; only some syllabi cover it.

SSH transport and user login

SSH is a remote-login and file-transfer protocol, usually on TCP port 22. It has three layers. The transport layer runs a version exchange, a key exchange (often Diffie-Hellman), and server authentication with a host key. It then encrypts and MACs every packet; each binary packet has length, padding length, payload, random padding and a MAC. The user authentication layer proves the human or account. The connection layer multiplexes many channels over one SSH connection: a shell, an SFTP file transfer, or a forwarded port.

The host key is the server's public key. The client stores it in known_hosts. On first contact the client may trust the key without proof (trust on first use); this is weak against a man-in-the-middle. A changed host key should raise an alarm. The host key authenticates the server; it does not log in the user.

SSH user authentication has two common forms. Password login sends the password inside the encrypted transport, so it is not plaintext on the wire, but the server still sees it. Public-key login is stronger: the client proves possession of a private key by signing a session-specific challenge, and the server checks the matching public key in authorized_keys. Keyboard-interactive authentication can carry one-time passwords or OTP. After authentication, the connection layer opens channels with their own flow control. SSH protects interactive sessions and file copies. It is not a full VPN by itself, though port forwarding can tunnel traffic; see 5.8.

Worked example

Question. In TLS 1.2 RSA key exchange, the client random is C = 0x11 and the server random is S = 0x22. The client sends a 48-byte pre-master secret PMS encrypted under the server's RSA public key. (a) What does the server decrypt? (b) What is the master secret length?

  1. ClientHello carries the client random C = 0x11.
  2. ServerHello carries the server random S = 0x22 and the server certificate.
  3. The client encrypts PMS with the server's RSA public key; PMS is 48 bytes.
  4. The server decrypts with its RSA private key and recovers PMS, which is 48 bytes.
  5. Both sides compute master_secret = PRF(PMS, "master secret", C ‖ S). TLS fixes the master secret at 48 bytes.

Answer. The server decrypts a 48-byte pre-master secret; the master secret is 48 bytes.

Exam traps

  • TLS gives channel confidentiality, integrity and server authentication. It does not give non-repudiation; a signature is needed for that.
  • The SSH host key authenticates the server only. The user still needs password, public-key or keyboard-interactive authentication.
  • Do not say TLS 1.3 uses RSA key transport. TLS 1.3 removed RSA key exchange and CBC; it uses ephemeral DH/ECDH and AEAD.
  • A certificate with a valid signature but the wrong hostname must fail validation. Always check the name and chain.
  • HTTPS does not fix application bugs such as SQL injection or XSS; those sit above TLS, see 5.9.

5.5 Email security: PGP and S/MIME

Email was built for machines that trusted each other. SMTP carries every message in plaintext and lets any sender type any From address, so a mail that looks like it came from your bank may come from a stranger. Message-level security fixes this: the sender signs the message with a private key and encrypts it with the recipient's public key, so the text stays private even on the mail servers in between. PGP does this between individuals; S/MIME does it inside organisations using X.509 certificates.

You need: Unit 4 for RSA, hashes, digital signatures and certificates, and Unit 3 for symmetric ciphers and block cipher modes.

What goes wrong with plain email

SMTP, the protocol that moves mail between servers, has no way to check who really sent a message. The From: line is text the sender types. Nothing in the protocol ties it to the machine that opened the connection.

  • Spoofing: the sender address is forged.
  • Phishing: a spoofed mail with a link to a fake login page (see Unit 1, social engineering).
  • Spam: bulk unsolicited mail sent through open relays.
  • Eavesdropping: copies of the message sit on relays and in backups.
  • Modification: a gateway or relay edits the body.
  • Replay: the same signed message is delivered again later.

Replay deserves care. A correctly signed note saying "pay ₹500" is still valid next month. PGP puts a creation time inside the signature and clients warn about old dates; applications also keep a message ID and reject duplicates.

TLS between mail servers protects one hop only (see 5.4). The message is decrypted at each server and stored in plaintext, so TLS does not give end-to-end privacy. Email security therefore works on the message itself, adding a signature and an encryption layer that only the two endpoints can remove.

Two families do this. PGP is peer-to-peer and needs no authority. S/MIME is certificate-based and fits corporate mail.

PGP: key rings and sign-then-encrypt

PGP (Pretty Good Privacy) is peer-to-peer: two users secure mail without a server or authority between them. Each user holds a public-key pair for signing and for encryption (RSA for both, or DSA for signing with ElGamal for encryption), plus a set of supported symmetric ciphers (AES, CAST, IDEA) and hashes (SHA-256 and others). Each message names the cipher and hash it used in its header, so the receiver knows which to apply. A user also keeps two key rings. The public key ring holds other people's public keys. The private key ring holds the user's own private keys, each encrypted under a passphrase. Every key carries a short key ID so a message can say which key it used.

PGP replaces the CA hierarchy with a web of trust. Alice checks Bob's key fingerprint face to face and signs his public key with her own private key. Anyone who trusts Alice then treats Bob's key as partly trustworthy. Trust levels and introducers decide how far that carries. The question is "who vouches for this key", not "which CA issued it".

  1. Hash the message; sign the hash with Alice's private key.
  2. Join the signature to the message.
  3. Compress the pair. This shortens the ciphertext and removes repetition.
  4. Pick a random session key Ks, for example 0x7A.
  5. Encrypt the compressed data under Ks with a symmetric cipher. Symmetric work is fast for a long message.
  6. Encrypt Ks with Bob's public key and attach it.
  7. Encode the whole thing in radix-64.

Radix-64 (base64) turns every 3 bytes into 4 printable characters, so the output is about 33% longer, plus a CRC line. Old mail systems could not carry raw binary, so this armour keeps the message inside plain ASCII.

S/MIME and the DNS sender checks

MIME already lets one message carry several parts: text, images, attachments. S/MIME wraps a part in CMS (Cryptographic Message Syntax, the successor of PKCS#7) and labels it. A message marked multipart/signed carries the readable text plus a signature; application/pkcs7-mime carries enveloped, encrypted data. Keys come from X.509 certificates issued by CAs, and the mail address appears in the certificate, so S/MIME trusts a hierarchy rather than a web.

DNS gives a second, cheaper defence against forgery. SPF publishes the IP addresses allowed to send for a domain in a TXT record, and the receiver compares them with the connecting IP. The record belongs to the envelope-sender domain, the one in MAIL FROM / Return-Path, not the From: header the reader sees. DKIM has the domain sign chosen headers and a body hash; the public key sits in DNS, so the receiver can verify it. DMARC adds alignment: the envelope-sender domain or the DKIM signing domain must match the From: header domain, and the published policy (none, quarantine, reject) applies when neither aligned check passes, along with reports back to the owner. These check a domain, not a person, and give no encryption. DNS security itself is in 5.6.

Worked example

Question. Alice sends Bob a PGP message. She signs the text "Pay ₹500" with her private key, compresses it, generates session key Ks = 0x7A, encrypts the compressed data under Ks, and encrypts Ks with Bob's public key. (a) What is Ks in decimal? (b) How many separate key operations does Bob perform while reading and checking the message, and which key does each use?

Python program.

ks = int("7A", 16)
print(ks)
print(3)
  1. Ks = 0x7A = 7 × 16 + 10 = 122. The one-byte value is only so the arithmetic fits on one line. A real PGP session key is 128 or 256 bits, for example a random AES-256 key.
  2. Alice's side: hash the text, sign the hash with Alice's private key, compress, encrypt under Ks = 122, wrap 122 with Bob's public key (n_B, e_B).
  3. Bob operation 1: RSA-decrypt the wrapped key with Bob's private key d_B. He recovers Ks = 122.
  4. Bob operation 2: symmetric-decrypt the body under Ks = 122. He recovers the compressed signed text.
  5. Bob operation 3: decompress, then verify the signature with Alice's public key. Accept or reject.
  6. Count the operations: Bob's private key, the session key Ks, and Alice's public key. That is 3.

122

Answer. Ks = 122 in decimal, and Bob performs 3 key operations: his private key to recover Ks, Ks to decrypt the body, and Alice's public key to verify the signature.

Exam traps

  • Sign-then-encrypt and encrypt-then-sign are not the same. PGP signs first, so the signature is hidden inside the ciphertext and only Bob sees it. Encrypt-then-sign leaves the signature outside, readable by anyone, but then it covers the ciphertext, not the plaintext.
  • The PGP web of trust is not a CA hierarchy. Signing someone's key means "I checked this key", not "an authority certified this identity", and there is no root certificate anywhere.
  • PGP and S/MIME leave the outer From, To, Date and routing headers in clear, because the mail servers need them to deliver the message; the Subject leaks only if the client does not hide it. S/MIME enveloped data (application/pkcs7-mime with smime-type=enveloped-data) and PGP/MIME (multipart/encrypted) can carry the whole MIME entity, Subject included, inside the encryption, and many clients do hide it. Others still copy the Subject to the outer header in clear. Write "headers leak; the Subject leaks only if the client does not hide it", never "the Subject is never protected".
  • SPF, DKIM and DMARC authenticate the sending domain, not the human. A phished mailbox at a correctly configured domain passes all three, and none of them encrypts anything.

Beyond the syllabus

Not for the exam. 5.6 DNS security and DNSSEC

DNS is the Internet's name-to-record lookup service: a resolver asks the root, then a top-level domain, then an authoritative server, and caches the answer for a time-to-live (TTL). Early DNS has no authentication, so an attacker who spoofs a reply can poison a cache. DNSSEC adds digital signatures to DNS records. A validating resolver checks that each answer came from the named zone and was not changed. Banks, governments and public resolvers use DNSSEC to make name lookup trustworthy.

You need: Unit 4 digital signatures and hashes; Unit 1 spoofing and cache attacks.

DNS resolution and cache poisoning

A stub resolver on your phone asks a recursive resolver, often run by your ISP or a public service. The recursive resolver walks the DNS tree. It asks a root server for .in, asks the .in server for bank.in, and asks bank.in's authoritative server for www.bank.in. Each answer carries a TTL in seconds; the resolver may cache it until the TTL reaches zero. Caching cuts delay and load, but a cached wrong answer is served to many users.

DNS mostly uses UDP port 53. A reply has a 16-bit transaction ID and a source port, but an off-path attacker can guess both and race the real server. An on-path attacker can read the query and spoof a reply. A fake A record for bank.in can send users to an attacker's server. This is cache poisoning or DNS spoofing. DNSSEC does not stop the race. It makes a forged answer detectable, because a forged answer cannot carry a valid signature for the zone.

DNSSEC records and the chain of trust

DNSSEC signs resource record sets (RRsets), not single records. An RRset is all records of one name and type. The zone owner creates a public/private key pair. The private key signs the RRset. The public key is published in a DNSKEY record. The signature is published in an RRSIG record. The RRSIG identifies the signer, the key tag, the inception time and the expiration time. A validator checks the signature over the canonical RRset. The signature proves origin and integrity; it does not encrypt the RRset.

Trust starts at a trust anchor: the root zone's public key, configured in the validating resolver. The root publishes a DS record for .in. That DS is a hash of .in's DNSKEY. The .in zone publishes a DS for bank.in; bank.in publishes its DNSKEY; bank.in signs the www A record with its private key. A validator builds a chain: root DNSKEY → DS for .in → DNSKEY for .in → DS for bank.in → DNSKEY for bank.in → RRSIG on www A. If any link fails, the answer is bogus.

A signing resolver or authoritative server holds private keys and adds signatures. A validating resolver holds only public trust anchors and checks signatures; it does not sign. A non-validating resolver just caches. NSEC and NSEC3 records are themselves signed, so the zone can prove that a name does not exist. An attacker cannot invent a not-found answer, because it would need a valid signature from the zone. NSEC3 hashes names and is an advanced option.

What DNSSEC protects and what it does not

DNSSEC gives data integrity and origin authentication for DNS answers. A validating resolver accepts a signed answer only if the chain is valid and the RRSIG is inside its validity time. For a signed zone, the resolver rejects an unsigned or altered answer as bogus. For a zone with no DS in its parent, the answer is marked insecure and accepted, because nothing in the chain says that zone is signed. This stops cache poisoning from redirecting bank.in to 6.6.6.6. It also stops an attacker from replaying an old signed answer after the RRSIG expires, because the expiration time is part of the signed data.

DNSSEC does not give confidentiality. Queries and answers still travel in plaintext unless a separate protocol such as DNS over HTTPS (DoH) or DNS over TLS (DoT) wraps them. DNSSEC does not hide which names you look up; an observer still sees the query. It does not protect the web server after the lookup: a valid A record can point to a server with a weak TLS setup. It also does not sign every operational detail; it signs RRsets in signed zones. For a bank, DNSSEC plus HTTPS is stronger than either alone.

Worked example

Question. At time t = 0 s, a validating resolver receives two replies for www.bank.in. Reply A: A 203.0.113.7 with a valid RRSIG and TTL = 300 s. Reply B: A 6.6.6.6 with no RRSIG. The resolver caches only validated answers. (a) Which reply is accepted? (b) At t = 240 s, how many seconds remain before the accepted cached answer expires? (c) What happens at t = 300 s?

  1. Validate Reply A: the RRSIG on the A RRset checks under the bank.in DNSKEY, and the DS from .in links that DNSKEY to the root chain. Accept 203.0.113.7.
  2. Validate Reply B: it has no RRSIG, so it has no chain to the root. Mark 6.6.6.6 as bogus and discard it.
  3. TTL = 300 s. At t = 240 s, elapsed time = 240 s. Remaining time = 300 - 240 = 60 s. The cache time is min(TTL, RRSIG expiration time minus now). Here the RRSIG is valid for long enough, so the TTL of 300 s decides.
  4. At t = 300 s, remaining time = 300 - 300 = 0 s. The cache entry expires, so the resolver queries again and validates a fresh answer.

Answer. Accept 203.0.113.7; at t = 240 s, 60 s remain; at t = 300 s the cache entry expires and the resolver re-queries.

Exam traps

  • DNSSEC gives integrity and origin authentication, not confidentiality. It does not encrypt queries or answers.
  • An RRSIG on a DNS A record is not a TLS certificate. It signs DNS data, not the web server's HTTPS key.
  • The DS record lives in the parent zone and the DNSKEY lives in the child zone. Swapping them breaks the chain.
  • A correctly signed but expired RRSIG is bogus. The validator checks the expiration time, not only the signature math.
  • NSEC proves non-existence but can allow zone walking; NSEC3 hashes names. NSEC3 details are advanced for most syllabi.

5.7 Wireless network security

Wireless LANs broadcast frames through open air. Anyone in range can listen, inject, or pretend to be an access point. Wireless security exists to turn that open medium into an authenticated link with fresh per-session keys. It is used on home Wi-Fi, office WLANs, campus networks and public hotspots. The core job is two-part: authenticate the station and the access point, then derive a key that changes every session. The topics are 802.11 threats, WEP, WPA, WPA2 and WPA3, and the WPA2 four-way handshake that binds nonces, MAC addresses and a master key into a pairwise key.

You need: Unit 3 RC4 and block ciphers, Unit 4 PRF and keys, and 5.8 for EAP.

Threats on an open medium

An access point (AP) is the radio that bridges Wi-Fi to the wired network. The SSID is the network name. The BSSID is the AP's MAC address. In an open network there is no encryption, so every frame is readable by anyone with a radio in range. An attacker can capture traffic, inject frames, or send deauthentication frames to force clients to reconnect.

  • Rogue AP: an unauthorised AP plugged into the company LAN; it bypasses perimeter rules.
  • Evil twin: a fake AP that copies a real SSID, so a phone joins it and sends traffic through the attacker.
  • MAC filtering: the AP allows only listed MAC addresses; the list is not secret and MAC addresses are easy to spoof, so it is housekeeping, not security.
  • Hidden SSID: turning off the name does not stop probes; clients reveal the name when they connect.

The fix is mutual authentication and per-session keys. Confidentiality alone is not enough: without AP authentication, a client can be tricked into joining an attacker's radio.

From WEP to WPA3

WEP (Wired Equivalent Privacy) uses RC4 with a 24-bit IV and a CRC-32 integrity check. The IV is too short and repeats; repeating an IV with the same key repeats the RC4 keystream. An attacker who collects enough frames can recover the key or decrypt traffic. WEP is broken and must not be used.

WPA with TKIP kept RC4 but added per-packet key mixing, a 48-bit IV and a MIC. It fixed WEP's immediate flaws but remains RC4-based and deprecated. WPA2 uses CCMP: AES-128 in CCM mode with 128-bit keys. CCMP gives confidentiality, integrity and replay protection, and it is the long-standing default for 802.11.

WPA3-Personal replaces the pre-shared-key handshake with SAE (Simultaneous Authentication of Equals). SAE is a password-authenticated key exchange. It gives forward secrecy and resists offline dictionary attacks on a captured handshake. Some syllabi call this wireless security; SAE details are advanced and only a few universities teach them.

WPA2 four-way handshake and key types

WPA2 has two modes. Personal mode uses a pre-shared key (PSK), one passphrase for the whole network. Enterprise mode uses 802.1X with EAP to a RADIUS server, so each user has credentials and each session gets its own PMK. EAP details are in 5.8.

PTK = PRF(PMK, ANonce, SNonce, AP MAC, Client MAC)

PTK is the pairwise transient key that protects one client-AP session; PMK is the pairwise master key from the PSK or from 802.1X; ANonce and SNonce are random numbers from the AP and the client; AP MAC and Client MAC bind the key to the two radios; PRF is the pseudorandom function from Unit 4.

  1. AP sends ANonce, a random number, to the client.
  2. Client picks SNonce, derives the PTK, and sends SNonce with a MIC.
  3. AP derives the same PTK, checks the MIC, and sends the GTK with a MIC.
  4. Client installs the PTK and GTK, then sends an ACK.

Message 1 is not MIC-protected in WPA2. The MIC in message 2 proves the client knows the PMK; the MIC in message 3 proves the AP knows it. A fresh SNonce stops a replay of message 1 from fixing the PTK.

The PTK protects unicast traffic between client and AP. The GTK is a group key for broadcast and multicast. The MIC is a message integrity code made with the PTK; it proves the sender holds the same key. Nonces are public; secrecy comes from the PMK.

Worked example

Question. In a WPA2-Personal network, the AP sends ANonce = 0xA1 and the client replies with SNonce = 0xB2. Both sides compute PTK = PRF(PMK, ANonce, SNonce, AP MAC, Client MAC). A recorded first message is replayed with ANonce = 0xA1. Explain why the client's new PTK is not the old PTK. Give the decimal values of both nonces.

  1. Read ANonce = 0xA1. Convert hex to decimal: 0xA1 = 10×16 + 1 = 161.
  2. Read SNonce = 0xB2. Convert hex to decimal: 0xB2 = 11×16 + 2 = 178.
  3. The first PTK uses inputs (PMK, 161, 178, AP MAC, Client MAC).
  4. On replay, the AP repeats ANonce = 161. The client generates a fresh SNonce, so the pair is no longer (161, 178).
  5. A new SNonce changes the PRF input, so the PTK changes. An old MIC computed under the old PTK no longer matches and is rejected.

Answer. The nonces are 161 and 178; a replayed ANonce does not fix SNonce, so the client's fresh SNonce makes a new PTK and old MICs fail.

Exam traps

  • WEP is broken: 24-bit IV reuse leaks the RC4 keystream. Do not describe WEP as weak-but-usable.
  • Hiding the SSID and MAC filtering are not security. MAC addresses are sent in clear and can be spoofed.
  • WPA2-Personal uses a PSK, not per-user login. Per-user login is WPA2-Enterprise with 802.1X/EAP.
  • TKIP is not AES. WPA2 uses CCMP/AES; WPA with TKIP is deprecated.
  • Nonces are public. A replayed ANonce does not fix the PTK because the client chooses a fresh SNonce; old MICs then fail.

5.8 Network access control, EAP and VPNs

Network access control (NAC) decides whether a device may join a network and what it may reach. It exists because a wall socket or Wi-Fi signal is not proof of trust: any laptop can plug in. IEEE 802.1X carries authentication before the switch forwards ordinary traffic. EAP is the flexible authentication conversation; RADIUS carries it to a central server. A VPN (virtual private network) extends a private network over the Internet using authentication and a tunnel. Offices use NAC at the edge; remote workers use VPNs daily.

You need: 802.1X in wireless networks, IPsec, TLS, and certificates from Unit 4.

802.1X roles, EAPOL and RADIUS

802.1X is port-based access control. It has three roles. The supplicant is software on the client that proves identity. The authenticator is the switch or access point that controls the port. The authentication server is a RADIUS server (Remote Authentication Dial-In User Service) that checks credentials and policy. The switch does not store every user password; it relays.

An Ethernet switch port starts unauthorized. In this state it forwards only EAPOL frames. EAPOL means EAP over LAN; EAP is the Extensible Authentication Protocol, a framework for request and response messages, not one fixed method. Normal IP packets are dropped.

  1. Link comes up; the supplicant sends EAPOL-Start.
  2. The switch sends EAP-Request/Identity.
  3. The supplicant replies with an identity, for example alice.
  4. The switch puts the EAP message inside a RADIUS Access-Request to the server.
  5. Server and supplicant run an EAP method; the switch passes messages between them.
  6. The server sends Access-Accept or Access-Reject. Accept may include Tunnel-Private-Group-ID, a RADIUS attribute carrying a VLAN identifier. A VLAN is a virtual LAN, an isolated Layer 2 broadcast domain.
  7. The switch moves the port to authorized and places it in that VLAN. Access-Reject leaves it unauthorized.

EAP methods, NAC and posture

EAP methods differ in how they protect credentials. EAP-TLS uses certificates on both supplicant and server; it gives mutual authentication and needs client-certificate management. PEAP (Protected EAP) uses a server certificate only; a TLS tunnel protects an inner authentication, often a password method. EAP-TTLS (Tunneled TLS) is similar and can carry legacy inner methods. EAP alone has no encryption; PEAP and EAP-TTLS wrap the inner exchange in TLS, while EAP-TLS uses TLS with certificates on both sides. See TLS.

NAC is the policy layer around 802.1X. It asks not only who you are but whether the device is healthy. A posture check inspects OS patch level, antivirus status, disk encryption, or mandatory software. A failed check can put the device in a quarantine VLAN with only a remediation server. After remediation, the device can reauthenticate. RADIUS Change of Authorization can move a live session.

Posture assessment details are advanced; only a few universities teach them. The exam level is: identity plus device state plus VLAN decision.

VPNs: remote access, site-to-site and tunneling

A VPN builds a protected tunnel over the Internet. It gives confidentiality, integrity and authentication for traffic between endpoints.

  • Remote access VPN: one user device connects to a VPN gateway. Used for work from home. Often TLS-based or IPsec.
  • Site-to-site VPN: two gateways, for example a Chennai office and a Mumbai office, connect networks. End hosts do not run VPN software.
  • IPsec VPN: network-layer protection for all IP traffic in the tunnel; see IPsec. Good for site-to-site.
  • SSL/TLS VPN: uses TLS; often browser-based access to a few apps, or a client tunnel. The name says SSL, but modern versions use TLS.

Split tunneling decides routing. With split tunneling, only traffic for private subnets goes through the tunnel; Internet traffic goes direct. It saves gateway bandwidth, but the device is on two networks at once, so malware can bridge between them. Full tunneling sends all traffic through the gateway, giving central filtering.

MFA (multi-factor authentication) combines factors; see user authentication. A VPN should require MFA before it creates the tunnel, because a stolen password alone must not open the office network.

Worked example

Question. User alice connects to switch port Fa0/10. Before authentication the port is unauthorized. RADIUS returns Access-Accept with Tunnel-Private-Group-ID = 20. What changes? State the VLAN and the number of normal-traffic VLANs allowed on that port before authentication.

  1. Before authentication, port Fa0/10 is unauthorized. It accepts EAPOL frames only; normal data frames are dropped.
  2. Alice's supplicant sends EAPOL-Start. The switch asks for identity. Alice sends alice.
  3. The switch sends RADIUS Access-Request to the server. The server authenticates alice and returns Access-Accept with Tunnel-Private-Group-ID = 20.
  4. The switch reads the attribute value 20. It marks the port authorized and assigns VLAN 20.
  5. Normal traffic from alice now enters VLAN 20. Before step 4, normal traffic used 0 VLANs on that port.

Answer. The port becomes authorized and carries VLAN 20 traffic; before authentication, normal traffic on that port belongs to zero VLANs because only EAPOL is allowed.

Exam traps

  • The switch is the authenticator, not the authentication server. The RADIUS server makes the accept or reject decision.
  • EAP alone has no encryption. PEAP and EAP-TTLS protect the inner method with TLS; EAP-TLS uses certificates on both sides.
  • An unauthorized 802.1X port is not dead: it still passes EAPOL frames. Saying the port is down loses marks.
  • IPsec VPN works at the network layer; an SSL/TLS VPN uses TLS. A browser-based SSL VPN does not protect every IP packet by itself.
  • Split tunneling is a routing choice, not an encryption method. It can reduce load but widens the device's exposure.

5.9 Web security and OWASP vulnerabilities

Web security protects the browser-server conversation: logins, cookies, form posts, file uploads and API calls. The browser is untrusted, so every request can be edited, replayed or forged. OWASP collects the most common failure patterns so testers and developers can look for them in a known order. The same flaws appear in a college portal, a UPI merchant page or an IRCTC booking flow. The rule is simple: treat all input as hostile and enforce every check on the server.

You need: Chapter 5.4 for HTTPS and TLS; Chapter 5.1 for password storage; and Unit 1 for phishing and network attacks.

HTTP, cookies and the browser boundary

HTTP is stateless: each request stands alone. A cookie is a small name-value pair the server sets with Set-Cookie; the browser sends it back on later requests to the same site. A session cookie holds a random session ID, for example 32 random bytes, and the server keeps the real login state under that ID. If an attacker steals the cookie, the attacker becomes the user; this is session hijacking. Mark cookies HttpOnly (JavaScript cannot read them), Secure (sent only over HTTPS) and SameSite (not sent on cross-site requests by default).

HTTPS (TLS, Chapter 5.4) encrypts the channel and authenticates the server with a certificate. It stops a coffee-shop Wi-Fi sniffer from reading the session cookie. It does not stop SQL injection or XSS, because those attacks run inside the allowed channel.

The same-origin policy is a browser rule: a page from https://a.example can read responses only from the same scheme, host and port. It limits one site from reading another site's data with the user's cookies. It is not server-side access control; the server must still check every request. CORS relaxes the rule for chosen origins, and a loose CORS policy is a common finding.

The OWASP Top 10 in one pass

The OWASP Top 10 is an awareness list of common web failure classes, not a complete test plan. Learn the idea behind each name.

  • Broken access control: a user reaches data or actions outside their role.
  • Cryptographic failures: secrets or personal data stored without encryption, or hashed badly.
  • Injection: untrusted input changes a query or command.
  • Insecure design: the flaw is in the workflow, not a missing patch.
  • Security misconfiguration: default passwords, open cloud buckets, verbose errors.
  • Vulnerable and outdated components: old libraries with known CVEs.
  • Identification and authentication failures: weak passwords, broken session handling.
  • Software and data integrity failures: unsigned updates, untrusted build artifacts.
  • Security logging and monitoring failures: attacks happen but no alert fires.
  • Server-side request forgery (SSRF): the server is tricked into fetching an internal URL.

SQL injection, XSS, CSRF, IDOR and file upload

Five flaws cover most exam questions.

  • SQL injection joins input into a query. The login example below shows the mechanism. Defence: parameterized queries, not escaping.
  • Cross-site scripting (XSS) runs attacker JavaScript in the victim's browser. Stored XSS sits in a comment field; reflected XSS comes back in a link; DOM XSS is written by client-side code. Defence: context-aware output encoding.
  • Cross-site request forgery (CSRF) makes the victim's browser send a state-changing request to a site where the victim is logged in. The browser attaches cookies automatically. Defence: a random CSRF token checked on the server, plus SameSite cookies.
  • Insecure direct object reference (IDOR) changes an object ID such as /invoice?id=101 to 102. Defence: the server checks that the logged-in user owns the object, not just that the user is logged in.
  • File upload flaws let an attacker upload .php or .jsp, or use a double extension, and run it. Defence: server-side type check, a short allow-list, rename files, store outside the web root, and scan.

Defences that hold

Use defences at the right layer, and do not rely on one control.

  • Parameterized queries bind input as data, so quotes cannot change the query structure.
  • Output encoding is context-aware: HTML body, attribute, JavaScript and URL need different encodings.
  • CSRF tokens are random per session, placed in a hidden field, and checked on every state-changing request.
  • Secure cookies use HttpOnly, Secure and SameSite.
  • Content-Security-Policy (CSP) is a response header that restricts scripts to allowed origins; it reduces XSS damage but is not a cure.

stmt = db.prepare("SELECT * FROM users WHERE user = ? AND pass_hash = ?")
stmt.execute(username, hash)

Worked example

Question. A login query is SELECT * FROM users WHERE user='$u' AND pass='$p'. The users table has 3 rows. The attacker sets u = ' OR '1'='1' -- and p = x. Write the resulting query, state how many rows the query returns, and explain why login succeeds.

  1. Start query: SELECT * FROM users WHERE user='$u' AND pass='$p'.
  2. Substitute u = ' OR '1'='1' -- and p = x.
  3. Resulting query: SELECT * FROM users WHERE user='' OR '1'='1' -- ' AND pass='x'.
  4. The condition user='' is false, but OR '1'='1' is true for every row.
  5. The marker -- starts a SQL comment, so ' AND pass='x' is ignored; the password check is gone.
  6. The users table has 3 rows, and every row matches the true OR condition, so the query returns 3 rows.
  7. The login code reads the first row and grants access, so 1 login is accepted.

Answer. The injected query returns 3 rows, and the login code accepts 1 login as the first user row.

Exam traps

  • Escaping input is not enough; parameterized queries separate code from data.
  • XSS needs context-aware output encoding; HTML-escaping everywhere can corrupt data and still miss JavaScript contexts.
  • CSRF tokens must be unpredictable and tied to the session; SameSite cookies alone do not cover every browser or flow.
  • IDOR is an access-control bug, not an injection bug; hiding the ID in the page is not a fix.
  • HTTPS protects the channel, not the application; SQL injection and XSS still work over HTTPS.

Takeaways

  1. Authentication proves an identity using a secret, a device or a body trait; a fresh challenge is what stops a recorded answer from being replayed.
  2. Kerberos never sends a password over the network: it issues short-lived symmetric tickets from a trusted KDC, so compromise has an expiry date.
  3. IPsec moves protection down to the network layer, so every packet gets authentication and, with ESP, encryption under a named security association.
  4. TLS and SSH both do handshake-then-record: asymmetric work authenticates and agrees a key, symmetric keys then protect the bulk data cheaply.
  5. SMTP has no built-in sender proof, so mail security signs at the message level (PGP, S/MIME) and adds domain-level checks (SPF, DKIM, DMARC).
  6. DNSSEC gives integrity and authenticity of DNS answers, not confidentiality or availability, and it depends on a signed chain from the root zone down.
  7. Wireless is an open medium, so the real job is mutual authentication plus a fresh per-session key, never a static shared key reused forever.
  8. 802.1X decides whether a device may join at all, while a VPN extends a private network securely over the public Internet.
  9. Most web breaches come from ordinary coding faults: injection, broken access control, session theft and misconfiguration, not from broken ciphers.

Analyze WEP has been broken while WPA2 stands up to the same attacks. Explain, using the 4-way handshake, what design differences matter and what remains weak in WPA2. 13 marks

WEP: static shared key, 24-bit IV, RC4, weak integrity check; IV reuse leaks keystream; WPA2: per-session pairwise key from the 4-way handshake, AES-CCMP with proper integrity; Handshake proves both sides hold the pairwise master key without revealing it; nonces stop replay; Remaining weaknesses: offline dictionary attack on the passphrase from a captured handshake, KRACK-class implementation flaws, no protection of management frames until 802.11w; Conclusion: key freshness and a real integrity check are the design wins.

Evaluate A company allows split tunnelling on its VPN. Evaluate the security trade-off and state the policy controls you would add. 13 marks

Split tunnelling sends only corporate traffic through the tunnel; other traffic goes direct; Benefit: less bandwidth and latency at the gateway, better user experience; Risk: the client sits on two networks, so it can bridge malware or expose the corporate side; Controls: endpoint posture checks, host firewall, always-on VPN for sensitive roles, DNS handling to avoid leaks; Monitoring and logging of tunnel use; data loss prevention on the endpoint.

Evaluate Pick two OWASP-class vulnerabilities, such as injection and broken access control. Explain how each is exploited and rank the defences by how much they actually help. 13 marks

Injection arises when untrusted input is concatenated into a query or command, so data becomes code; Defence ranking: parameterised queries first, then input validation as a secondary layer, then least privilege on the database account, then WAF as a last net; Broken access control: a request for another user's object ID is served because the check is missing on the server; Defence: server-side authorisation on every request, deny by default, unguessable identifiers are not a control; Common ground: never trust the client, centralise the check, test with automated scans and manual review.

Analyze Explain how a network access control (NAC) system combines 802.1X, posture checks and VLAN assignment, and analyse what an attacker on the inside can still do. 12 marks

802.1X authenticates the device or user before the port carries traffic; Posture check: patch level, antivirus, disk encryption before full access; Result is a role or VLAN: full, limited or quarantine; Insider attacker with valid credentials still passes; lateral movement needs segmentation and monitoring; MAC authentication bypass and MAB spoofing are weak spots; mention IDS and anomaly detection.

Glossary

Authentication server
The RADIUS server that checks credentials and returns accept or reject with keying material.
Authenticator (802.1X)
The switch or access point that blocks the port until the authentication server answers.
Authenticator (Kerberos)
A client-name and timestamp block encrypted under the session key, proving the presenter is live.
Buffer overflow
Writing past the end of a buffer, which can overwrite a return address and redirect execution.
CMS
Cryptographic Message Syntax, the standard structure that S/MIME uses for signed and encrypted messages.
CSRF
Cross-site request forgery: a hostile page makes the victim's browser send an authenticated request.
EAP-TLS
An EAP method where both client and server authenticate with certificates inside the TLS handshake.
Evil twin
A rogue wireless access point using a legitimate network's name to capture traffic or credentials.
Key ID
A short fingerprint fragment that names a public or private key without transmitting the whole key.
NAC
Network access control: the policy system that decides whether a device may join and at what level.
Nonce
A value used once, so that a fresh run of a protocol cannot be answered with a recorded old reply.
PEAP
A protected EAP method that builds a TLS tunnel with a server certificate and then runs an inner method inside it.
Phishing
A message or site that impersonates a trusted party to make the user hand over credentials or data.
Private key ring
The local store of a user's own key pairs in PGP, protected by a passphrase.
Replay attack
An attacker resends a captured valid message hoping the receiver acts on it again.
Salt
A random value stored with a hashed password so identical passwords hash differently and precomputed tables fail.
Session key
A short-lived symmetric key used for one connection and then discarded.
Spam
Unsolicited bulk mail, often the delivery vehicle for phishing and malware.
Split tunnelling
A VPN setting where only selected traffic goes through the tunnel and the rest goes direct to the Internet.
Spoofing
Forging a sender address, name or identity so a message appears to come from someone else.
Supplicant
The device that asks to join the network in 802.1X.
Ticket
In Kerberos, a block encrypted under a server's secret key that carries the client name and a session key.
VPN
A virtual private network: an authenticated, encrypted tunnel carrying private traffic over a public network.
Zone (DNS)
A portion of the DNS namespace managed together, with its own keys when DNSSEC is used.
