5.1 Cloud computing for IoT and sensor clouds

Cloud computing for IoT is a shared, elastic pool of computing, storage and services reached over a network. It exists because tiny sensor nodes cannot store years of readings or run heavy analytics. A sensor cloud goes further: many physical sensors appear as virtual sensors that applications can query. You meet it in smart meters, fleet tracking and city air-quality dashboards.

You need Unit 1 logical design and communication models, Unit 2 sensor nodes and Unit 3 MQTT publish-subscribe basics.

Cloud characteristics

Cloud computing is a model for giving computing, storage and software as a service over a network. For IoT it solves a size problem: a sensor node may have kilobytes of RAM, while a city has years of readings. The cloud also adds servers when traffic rises and removes them when it falls.

  • On-demand self-service: a team requests a virtual machine or database through a portal and gets it without a human operator.
  • Broad network access: services are reached over standard networks, from phones, gateways or laptops.
  • Resource pooling: many customers share a pool of servers; the provider assigns and reassigns capacity.
  • Rapid elasticity: capacity grows or shrinks quickly with demand, often automatically.
  • Measured service: usage is metered, so you pay for what you consume.

A Chennai apartment using water meters shows the need. Two hundred meters send small readings. A cloud broker receives them, keeps months of history and runs billing. At the month end, billing jobs need more CPU; elasticity adds it. For the rest of the month, the system shrinks. Measured service turns this into a variable cost instead of a large server purchase.

Virtual machines and containers

Virtualization lets one physical computer run several isolated systems. The physical machine is the host. A hypervisor is software that creates and runs guest virtual machines (VMs). Each guest VM has its own virtual CPU, memory, disk and operating system. A VM image is a packaged disk and configuration from which a new VM starts. Provisioning creates the VM from an image. Templates repeat common settings. Snapshots save a point-in-time state before an upgrade. Monitoring watches CPU, memory, disk and network; scaling adds or removes instances.

Containers package an application with its libraries but share the host operating system kernel. A container image is the packaged filesystem and settings. A running container is an instance of that image. Namespaces isolate what a process can see, such as its process list and network. Control groups, or cgroups, limit and account for CPU, memory and I/O. Docker is a common packaging and runtime tool.

The difference matters for IoT. A VM is heavier: each guest carries a full OS. It gives strong isolation between different OS families. A container is lighter and starts faster, but it must match the host kernel family. A Linux container needs a Linux host kernel; it is not a small VM. Use VMs for hostile multi-tenant separation, containers for many small services.

Service models, deployment, IoT platforms and sensor clouds

Cloud services come in three standard models. IaaS (Infrastructure as a Service) gives virtual machines, storage and networks; you manage the operating system and runtime. PaaS (Platform as a Service) gives a runtime, database and scaling; you deploy code and the provider manages servers. SaaS (Software as a Service) gives a finished application, such as a dashboard, used through a browser.

Deployment models describe who shares the cloud. A public cloud is owned by a provider and open to many customers. A private cloud is used by one organisation, with self-service and pooling. A hybrid cloud joins public and private resources under common management. A community cloud is shared by organisations with a common concern, such as hospitals.

An IoT platform is a PaaS-like service for devices. Typical IoT cloud services are a device registry, a message broker, rules, time-series storage, alerts and dashboards. In a cloud IoT architecture, devices connect through gateways to the broker; streams go to storage and analytics; applications read results. Identity and device management give each device a credential, keys, permissions and a revocation path. This is not user login; a stolen meter credential must be disabled without affecting other meters.

A sensor cloud exposes physical sensors as virtual sensors. The broker ingests readings, keeps metadata and offers an API. A billing application asks a virtual sensor for a meter's history; it does not address the physical node. The figure shows this path.

Worked example

Question. An apartment water-meter cloud serves 200 meters. Each meter sends one 64-byte reading every 30 minutes. Find readings per day, raw data per day in bytes and MB, and raw data stored for 90 days in bytes and MB. Use 1 MB = 10⁶ bytes.

  1. Readings per meter per day: 24 hours = 24 × 60 = 1,440 minutes; 1,440 ÷ 30 = 48 readings.
  2. All meters: 200 × 48 = 9,600 readings/day.
  3. Raw bytes per day: 9,600 × 64 = 614,400 bytes/day.
  4. In MB: 614,400 ÷ 1,000,000 = 0.6144 MB/day.
  5. For 90 days bytes: 614,400 × 90 = 55,296,000 bytes.
  6. In MB: 55,296,000 ÷ 1,000,000 = 55.296 MB.

Answer. The cloud handles 9,600 readings/day, 614,400 bytes/day = 0.6144 MB/day, and 55,296,000 bytes = 55.296 MB in 90 days.

Exam traps

  • A container is not a small VM; it shares the host kernel and needs the same OS family.
  • A sensor cloud is not just cloud storage; it exposes and manages virtual sensors.
  • Elasticity is not free unlimited capacity; measured service bills the resources you use.
  • Private cloud is not merely an on-premises server; self-service, pooling and automation are part of the definition.
  • Device identity is not user login; revoking one device must not break others.

5.2 IoT cloud platforms: AWS IoT, Azure IoT Hub

A device that sends data to a cloud IoT platform gets four things without its owner building a server: a verified identity, a standard endpoint that speaks MQTT or AMQP over TLS, a stored copy of its last known state, and a rule engine that forwards each message to a database, a function or an alert. AWS IoT Core and Azure IoT Hub are the two most used examples. The same pattern — register, connect, publish, route, store — appears in every IoT product, from a farm's moisture sensors to a fleet of delivery bikes.

You need: Chapter 5.1 for cloud models and elastic resources, and MQTT publish-subscribe from Unit 3.

Six services that replace your own servers

A farm with 500 soil-moisture devices needs four capabilities at once: proof that each device is genuine, an endpoint that can hold hundreds of open connections, a store for the readings, and a way to alert when a value crosses a limit. Built by hand this means an authentication server, a broker, a database and a script runner — each patched, scaled and paid for separately. A cloud IoT platform sells all of them as one managed service.

  • Device registry: one record per device holding its ID, credentials, model and enabled or disabled flag.
  • Secure endpoint: MQTT over TLS, AMQP 1.0 or HTTPS; the platform terminates TLS and authenticates the device.
  • Device shadow or twin: a JSON document holding the last reported and last desired state of the device.
  • Rules engine: filters messages by topic, payload or a query, and forwards the matches to other services.
  • Routing targets: object storage, NoSQL tables, message queues, serverless functions, alerting services.
  • Monitoring and device management: connection counts, error and throttling metrics, plus remote jobs and firmware updates.

Pricing follows usage: messages in and out, device-minutes connected, and operations such as shadow updates. Publishing every 10 seconds where the physics needs 10 minutes is the most common way to overspend.

Identity, shadows and twins

The device registry is the authority. Registering a device creates a record with a unique device ID, its credentials and metadata such as model and location. Disabling the record stops connections at once, which is exactly what you want when a sensor is stolen.

AWS IoT Core issues an X.509 client certificate and key pair. The private key never leaves the device, and the device connects on port 8883 using mutual TLS — both sides present certificates. A policy attached to the certificate is a JSON document naming the topics the device may publish and subscribe to, so a hacked sensor can write to its own topic and nowhere else.

Azure IoT Hub uses a SAS token by default. A SAS (shared access signature) is a string carrying the hub's resource URI, an expiry time and a signature computed with the device's symmetric key. The device sends it in the connection string at each connect and simply builds a new one when it expires; X.509 is also supported. A SAS token is easy to compute on a small microcontroller, while a certificate needs a trusted clock and more memory.

A device shadow (AWS) or device twin (Azure) is a JSON document the platform stores for each device. Its desired section holds what the cloud wants, its reported section holds what the device last said, and the difference is the delta. A pump is offline during a Chennai power cut; you write desired state pump = off. On reconnect the device asks for the delta, sees the change and applies it. An app reads the same document to show last known state without waking the device.

Rules, routing and monitoring

A message arriving at the endpoint does nothing useful until it is routed. The rules engine matches on topic, payload or a query, then invokes actions in order. AWS uses a SQL-like statement, for example SELECT * FROM 'farm/+/moisture' WHERE moisture < 20. Azure uses message routing with a query string such as $body.moisture < 20. Both send matching messages to storage, queues and functions and drop the rest.

M_day = N × (1440 ÷ T)    and    B_day = M_day × b

M_day is messages per day; N is the number of devices; T is the publish interval in minutes; 1440 is the minutes in a day; B_day is bytes per day; b is bytes per message.

Monitoring closes the loop. Both platforms export metrics — connected devices, messages used against quota, throttled requests, errors by type — and these are the numbers worth alarming on.

Worked example

Question. A farm runs 500 soil-moisture devices. Each device publishes one 200-byte message every 10 minutes. Find (a) messages per day for the whole farm, (b) data volume per day in MB using 1 MB = 10⁶ bytes, (c) the peak message rate in messages per second if all 500 devices publish inside one 60-second window, and (d) the average rate for comparison.

  1. Publishes per device per day = 1440 minutes ÷ 10 minutes = 144 messages.
  2. Messages per day = 500 devices × 144 = 72,000 messages/day.
  3. Bytes per day = 72,000 × 200 bytes = 14,400,000 bytes/day.
  4. In MB = 14,400,000 ÷ 10⁶ = 14.4 MB/day.
  5. Peak rate = 500 messages ÷ 60 s = 8.33 messages/s.
  6. Average rate = 72,000 ÷ 86,400 s = 0.83 messages/s, so the peak is about ten times the average — size buffers for the peak, not the average.

Answer. The farm sends 72,000 messages per day, 14.4 MB per day, with a peak burst of 8.33 messages/s against an average of 0.83 messages/s.

Exam traps

  • AWS IoT Core and Azure IoT Hub are not just brokers. Exams ask separately for the device registry, the shadow or twin, and the rules engine.
  • Device shadow belongs to AWS, device twin to Azure. Swapping the names loses the mark even when the description is right.
  • MB here is 10⁶ bytes. If a question says MiB or 2²⁰, the answer changes: 14,400,000 bytes is 13.73 MiB, not 14.4 MiB.
  • Average rate and peak rate are different numbers. Use the publishing interval for daily volume and the burst window for peak.
  • A SAS token expires. A device with a wrong clock builds a token that looks already expired, and the hub refuses the connection.

Analyze A device's certificate expired at midnight. The platform refuses its connection, yet the rules engine shows no errors and the dashboard simply stops updating. Explain the failure point and where the fix belongs. 6 marks

The TLS handshake fails before any MQTT packet is sent, so no message ever reaches a topic and the rules engine has nothing to reject. The dashboard sees stale data rather than an error. The fix belongs in device management and provisioning: renew the certificate, and automate renewal before expiry so no human has to visit the device.

5.3 Data analytics and big data for IoT

IoT analytics turns a flood of sensor readings into summaries, alerts and models. A vibration sensor may send 2,000 samples every second, far too much for a person to read. Analytics filters and aggregates at the edge, stores recent values for live dashboards, keeps raw data for later batch training, and raises an alert when a motor starts to fail. It exists because bandwidth, storage and human attention are limited. It is used in factories, smart grids, vehicle fleets and city water systems.

You need: Unit 2 sensor sampling; Chapter 5.2 platform routing; basic DBMS.

Streams, batches and the four Vs

IoT data arrives as a stream: an ordered flow of readings, each with a time stamp. Stream processing handles each reading as it arrives and answers in seconds. Batch processing stores readings first and processes them later in large groups. A motor monitor uses both: a stream job raises a high-vibration alert now, while a nightly batch job retrains a failure model on a month of history.

Four properties describe the load. Volume is the total amount, for example 28.8 MB per hour from one vibration sensor. Velocity is the arrival rate, here 2,000 samples per second. Variety is the mix of types: numbers, status codes, images and logs. Veracity is how far the data can be trusted, since a loose wire can send zeros that look valid.

Edge pre-processing cuts the stream before it reaches the cloud. Filtering drops known-bad values. Windowing groups readings by time, such as 1-minute tumbling windows that do not overlap. Aggregation replaces a window with one summary: average, minimum, maximum or count.

x̄ = (Σ<sub>i=1</sub><sup>n</sup> x<sub>i</sub>) ÷ n

x̄ is the window average; xi are the sample values inside the window; n is the number of samples in the window.

  1. Open a window of fixed length, such as 60 s.
  2. Apply a filter, for example keep only values from 0 to 50 mm/s.
  3. Compute one aggregate for the window.
  4. Send the aggregate and its time stamp to the cloud.

Storing and processing the data

A time-series store is a database built for timestamped values. It indexes by time and by sensor id, so a query for the last hour of one motor is fast. Many designs keep two layers. A hot store holds recent values for dashboards and usually keeps days or weeks. A raw store keeps every sample, or a compressed form, for audits and model training.

Big data tools split work across machines. Hadoop HDFS stores large files in blocks spread over many disks, with copies for fault tolerance. MapReduce is a batch model: a map step transforms records, then a reduce step combines them by key. Spark runs batch and stream jobs and keeps working data in memory, which helps iterative training. A Kafka-style log ingests many device streams in order and lets several consumers read the same data. NoSQL stores, such as key-value or document databases, hold device metadata and flexible JSON records.

Dashboards, alerts and predictive maintenance

Visualization turns tables into decisions. A line plot shows a trend over time. A gauge shows the current value against a safe range. A heat map shows many sensors at once. A dashboard combines these views with a time range selector. The dashboard reads the hot store, so it must show data freshness, such as 'last update 12 s ago'.

An alert is a rule or model that fires when action is needed. A simple threshold alert fires when vibration exceeds 45 mm/s for 3 minutes. A smarter alert compares the current window with a learned baseline. Alerts must avoid fatigue: too many false alarms and operators ignore them.

In Industry 4.0, predictive maintenance uses vibration, temperature and current sensors on motors and pumps. A model learns normal behaviour and estimates remaining useful life. Maintenance is scheduled before failure, not after a breakdown. A simple sensor node does three jobs: sense, process a window locally, and send a summary with its device id.

Worked example

Question. A vibration sensor samples 2,000 times per second, 4 bytes per sample. Find raw data per hour. If the edge keeps only a one-minute average (one value per minute) for the dashboard, find the reduction factor in stored values per hour.

  1. Samples per hour = 2,000 samples/s × 3,600 s/h = 7,200,000 samples/h.
  2. Raw bytes per hour = 7,200,000 samples/h × 4 bytes/sample = 28,800,000 bytes/h.
  3. Use 1 MB = 1,000,000 bytes: raw data = 28,800,000 ÷ 1,000,000 = 28.8 MB/h.
  4. Dashboard values per hour = 60 min/h × 1 value/min = 60 values/h.
  5. Reduction factor = 7,200,000 raw samples/h ÷ 60 dashboard values/h = 120,000.

Answer. Raw data is 7,200,000 samples/h, 28,800,000 bytes/h or 28.8 MB/h; the dashboard stores 60 values/h, a reduction factor of 120,000 times.

Exam traps

  • Sampling rate is samples per second, not bytes per second. Multiply by bytes per sample before quoting MB.
  • A one-minute average stores 60 values per hour, not 60 samples per second. Do not multiply by 60 again.
  • Stream processing answers in seconds; batch processing runs later on stored data. A dashboard fed by a daily batch is not live.
  • Variety and veracity are different: variety is different data types, veracity is trustworthiness.
  • A dashboard is a view, not the database. Closing the dashboard does not delete the raw store.

Federated learning trains models across gateways without sending every raw sample to the cloud. 5.4 IoT security and privacy

IoT security keeps three things safe: who a device is, what it may do, and the data it sends or stores. Privacy decides how much personal data is collected and how long it is kept. A smart lock, a factory sensor and a smart meter all face the same questions. This chapter covers the security goals, device identity, protected channels, access control, privacy rules and the attacks that break them.

You need: device identity and brokers from Chapter 5.2, protocol basics from Unit 3, and basic cryptography ideas.

Security goals: what must stay true

A security goal is a property an attacker must not break. Six goals cover almost every IoT requirement.

GoalQuestion it answers
ConfidentialityWho may read this data?
IntegrityHas the data changed?
AvailabilityIs the service up when needed?
AuthenticationWho are you?
AuthorizationWhat may you do?
Non-repudiationCan you deny sending this?

Confidentiality uses encryption. Integrity uses a MAC (message authentication code) or a digital signature. Availability keeps the broker and gateway working through floods and power cuts; a shop with a backup gateway keeps reporting when the mains fails. Authentication proves identity with a key or certificate. Authorization is a separate decision taken after authentication, usually by a policy. Non-repudiation means a signed log can prove a command came from a device, so the sender cannot deny it.

The broker checks in this order:

  1. Authenticate the client, using a certificate or a token.
  2. Authorize the topic: may this client publish to home/lock/state?
  3. Check the message MAC or signature for integrity.
  4. Write an audit log entry, which supports non-repudiation.

Device identity and protected channels

Every device needs an identity that is hard to copy. A public-key certificate binds a device ID to a public key. The matching private key stays in the device, ideally inside a secure element or TPM (trusted platform module). Secure boot verifies a signature over the firmware before it runs. The hardware root of trust is the small immutable code and key storage that secure boot trusts first. If an attacker reflashes the firmware, secure boot fails and the device refuses to start.

  1. The manufacturer writes a unique certificate and private key into the device.
  2. On power-up, secure boot verifies the firmware signature.
  3. The device opens TLS for TCP (MQTT on port 8883) or DTLS for UDP (CoAP).
  4. Both sides exchange certificates and derive session keys.
  5. The broker applies topic permissions; payloads travel encrypted.

Network segmentation puts devices on their own VLAN (virtual LAN) or subnet behind a gateway that allows only needed traffic. A compromised smart bulb then cannot reach the billing server. MQTT over TLS protects data in transit. At rest, encrypt the database and limit key access to the cloud service account.

When certificates are short-lived, the device renews them from a CA at run time using its existing identity; the figure shows this renewal.

Access control, privacy and common attacks

Access control applies least privilege: each device or user gets only the permissions needed for its job. Roles group permissions, for example viewer, operator and admin. Tokens carry an expiry time, so a stolen token stops working soon. Short-lived tokens, from minutes to hours, limit the damage.

Privacy covers personal data. Data minimisation collects only what the service needs: a parking app needs the slot, not the driver's name. Consent records what the user agreed to and when. Retention deletes data after a fixed period. Anonymisation removes identifiers, so a dataset cannot be tied to a person. Pseudonymisation replaces names with tokens and is reversible with a key, so it is weaker.

Worked example

Question. A smart-lock fleet has 10,000 devices. Each active device certificate is 1 KB and rotates every 90 days. Find (a) the active certificate storage in MB, using 1 MB = 1000 KB, and (b) the number of certificates issued per year, using 365 days.

  1. Each device holds one active certificate of 1 KB.
  2. Active storage = 10,000 × 1 KB = 10,000 KB.
  3. Convert to MB: 10,000 ÷ 1000 = 10 MB.
  4. Rotations per device per year = 365 ÷ 90 = 4.0556.
  5. Certificates per year = 10,000 × 4.0556 = 40,555.6.
  6. Round up to whole certificates: 40,556.

Answer. Active storage is 10 MB; about 40,556 certificates are issued per year.

Exam traps

  • Encryption is not full security. Authentication, authorization and integrity are separate controls, and an examiner will ask for each by name.
  • Count only active certificates for storage. Revoked certificates sit in a revocation list (CRL) or are checked through OCSP, and expired certificates are rejected by their validity dates; neither counts as active storage.
  • A 90-day rotation gives about 4.06 certificates per device per year, not one. Multiply devices by rotations.
  • State the unit convention: this chapter uses 1 MB = 1000 KB. Using 1024 KB changes the answer.
  • Replay is not stopped by encryption alone. TLS protects each session separately, but it does not stop an attacker who holds valid credentials, or the plaintext payload, from publishing the same command again in a fresh session. The broker sees a correctly protected message and cannot tell it is old.

Analyze An attacker with valid credentials, for example a compromised device, records a valid 'unlock' MQTT message and resends it an hour later. TLS is in use. Explain why TLS does not stop this and give two controls that do. 5 marks

TLS protects each session separately, but it does not stop an attacker who holds valid credentials, or the plaintext payload, from publishing the same command again in a fresh session. The broker sees a correctly protected message and cannot tell it is old. Controls: a nonce or timestamp in the payload, checked by the broker; and a message ID rejected on a second arrival. If the credentials were a stolen token, short token expiry also shrinks the window.

Apply A smart meter sends 1-minute readings. Give one data-minimisation change and one retention rule that improve privacy without breaking billing. 4 marks

Send 15-minute totals for billing and keep 1-minute readings only for a 24-hour diagnostic window, then delete them. Keep the 15-minute billing records for 90 days and keep only monthly totals after that. Fewer detailed records reduce what a breach exposes.

5.5 Web of Things and IoT middleware

The Web of Things (WoT) gives every device capability a web address and a machine-readable description, so apps can use a sensor or motor like a web resource. A Thing Description (TD) lists properties, actions, events, protocol bindings and security. A servient is the software that serves or consumes TDs and translates web requests to CoAP, MQTT or HTTP. IoT middleware does the same hiding job more broadly: discovery, naming, protocol translation, caching and security mediation. You meet this in smart-home gateways, factory dashboards and city sensor portals, where many devices must look simple to many apps.

You need: Unit 3 MQTT, CoAP and service discovery, and Chapter 5.2 on cloud platform APIs.

WoT building blocks and the resource model

WoT turns a device capability into a web resource. A temperature sensor may expose /sensors/room1/temperature as a property. A fan may expose /actuators/fan1 as an action. A property is state that can be read and often written. An action is an operation the Thing performs when invoked. An event is a notification, such as an alarm.

The TD is JSON. It gives the Thing an id and title, then lists properties, actions, events, forms and security. A form is a machine-readable link. It states the protocol and URL or topic that reach one capability. The TD is metadata, not the live reading. The reading is the value returned when the resource is read.

The servient can act as client, server or both. A gateway servient runs on a stronger node and exposes many small devices on their behalf. A device servient runs on the device itself, which may be a constrained node.

A protocol binding maps a WoT operation to a concrete protocol. Read property may become an HTTP GET, a CoAP GET, or an MQTT request-reply exchange. The binding lets an app use JSON over HTTP while the device uses CoAP over UDP or MQTT. The resource model stays the same: property, action, event.

IoT middleware functions

IoT middleware is software between applications and devices. It hides hardware and protocol differences. A middleware layer can run at the edge gateway or in the cloud.

  • Discovery finds devices and services. It can use mDNS, DNS-SD or UPnP (discovery in Unit 3).
  • Naming gives each device and resource a stable name, so an app asks for room1.temperature, not a MAC address.
  • Protocol translation converts MQTT, CoAP, HTTP or a fieldbus format into one API.
  • Data aggregation combines readings: average temperature, sum of energy, count of active alarms.
  • Caching keeps the last value and the TD. An app can read without waking a sleeping device.
  • Event filtering forwards only useful changes, such as a temperature above a threshold, and drops repeated values.
  • Security mediation authenticates apps and devices, enforces access rules and terminates TLS or DTLS.

A constrained device has small RAM, a slow CPU and limited energy. Full HTTP over TCP is heavy for it. Many constrained devices use CoAP over UDP, often with 6LoWPAN. A web-enabled constrained device may run a small CoAP server and a compact TD. A gateway servient can translate for devices that cannot run web software. See Chapter 5.4 for the security rules.

WoT compared with direct MQTT

Direct MQTT has an app connect to a broker and subscribe to a topic, for example factory/line1/temp. The app must know topic names, payload format and quality-of-service rules. This is simple when both ends are fixed and owned by one team.

WoT adds a description layer. The app fetches a TD and calls a resource. The servient still publishes or subscribes through MQTT. WoT is an abstraction layer over MQTT, CoAP or HTTP, not a replacement.

Benefits are discovery, one API style and self-description. Costs are TD fetch and parse time, an extra servient hop and more metadata. Use direct MQTT for tight control loops with known devices. Use WoT when many apps and devices must interoperate.

A gateway with 20 sensors and 1.2 KB per TD stores 24.0 KB of raw descriptions. A 40% compression leaves 60%, or 14.4 KB. TD size matters on constrained links. Some syllabi treat WoT as a short middleware topic; only a few cover it deeply.

Worked example

Question. A gateway exposes 20 sensors as WoT Things. Each Thing Description is 1.2 KB. Compression reduces the stored description size by 40%. Find the total stored size for all descriptions after compression.

  1. Number of Things n = 20. Size per TD s = 1.2 KB.
  2. Raw total = n × s = 20 × 1.2 KB = 24.0 KB.
  3. A 40% reduction leaves 100% − 40% = 60% = 0.60 of the raw size.
  4. Compressed total = 24.0 KB × 0.60 = 14.4 KB.

Answer. The compressed descriptions occupy 14.4 KB; the raw size is 24.0 KB.

Exam traps

  • WoT replaces MQTT or CoAP. It does not; protocol bindings use them.
  • A Thing Description is live sensor data. It is metadata that says how to reach data.
  • A 40% reduction means multiply by 0.4. It leaves 60%, so multiply by 0.6.
  • Middleware is only a broker. It also discovers, names, translates, aggregates, caches, filters and mediates security.
  • Every constrained device must run a full servient. Many use a gateway servient.

5.6 Software defined networking for IoT

Software defined networking (SDN) takes the decisions about where packets should go out of the network devices and puts them in one program called the controller. The devices only forward. IoT sites need this because they have many cheap gateways that cannot run full routing software, and because a site manager wants to change paths and policies for all of them from one place. SDN is used in campus and data-centre networks, in telecom backhaul, and now in sensor gateways and fog nodes.

You need: Unit 3 network layer basics (packets, addressing, routing), Chapter 5.1 for the cloud side, and Chapter 5.5 for where middleware sits.

Control plane, data plane, and why to split them

In an ordinary router two jobs sit in the same box. The control plane works out where packets should go: it runs routing protocols, builds a map of the network, and picks paths. The data plane does the fast, simple part: it looks at each arriving packet and sends it out of a port.

SDN separates them. The control plane moves to one program, the SDN controller, which sees the whole network as a graph. The forwarding devices keep only the data plane. They hold no routing intelligence; they hold a table of rules handed to them.

  • Application plane: programs that state intent, for example "alerts from the wards must reach the cloud even when the video feed is busy".
  • Control plane: the controller, which turns that intent into rules.
  • Data plane: the gateways, which only match and forward.

Two interfaces join the planes. The northbound API sits between the application plane and the controller, usually a REST API, and it is what a programmer writes against. The southbound API sits between the controller and the devices; OpenFlow is the best-known one. The controller speaks southbound to every gateway and northbound to every application.

Why bother for IoT? A site may have hundreds of cheap gateways that cannot run routing protocols. One controller with a global view programs them all, and the whole site's behaviour changes by editing one program.

Flow tables: match, then act

A flow is a set of packets that share some header values: same source, same destination, same application. A gateway's flow table has one row per flow, and each row has four parts.

  • Match: header fields to compare, such as ingress port, source and destination MAC address, EtherType, VLAN id, IP address, and TCP or UDP port.
  • Priority: which row wins when several rows match.
  • Counters: packets and bytes seen, used for accounting.
  • Actions: forward out a port, drop, rewrite a header field, flood, or send the packet to the controller.

Lookup is match-then-act. A packet arrives; the gateway finds the highest-priority row whose match fields all fit the packet; it runs that row's actions. Nothing else is decided locally.

A new flow has no row at first. A table-miss entry at priority zero matches everything and sends such packets to the controller. The controller decides, installs a rule, and the packet is forwarded. The first packet takes the slow path; every later packet of that flow matches in the table. Known traffic can also be given static rules in advance.

M = R × s

M is the rule memory in bytes; R is the number of installed flow rules; s is the storage per rule in bytes, tens of bytes on a small gateway. This memory, not the payload, is the real cost on constrained devices.

What SDN gives IoT, and what it costs

  • Central policy: one place states which sensors may reach which cloud service and blocks the rest. Network rules and security rules live together (see Chapter 5.4).
  • Traffic engineering: when one gateway is congested, the controller moves some flows to its neighbours; the example below computes this.
  • Slicing: shared gateways and backhaul are cut into isolated virtual networks, one for hospital devices and one for building fans, each with its own rules and bandwidth. A slice behaves like a private network on shared wires.
  • Fast reroute: when a link or gateway dies, the controller installs an alternate path in milliseconds, where classical routing needs seconds to converge.
  • Cheaper devices: a gateway needs only a flow table, not a full routing stack. A Raspberry Pi (Unit 4) running Open vSwitch makes a lab for a few thousand rupees.

The limits are equally examinable. Controller scaling is one: a single controller handling thousands of gateways and flow setups per second becomes the bottleneck, so large sites use a hierarchy of controllers. A single controller is a single point of failure; if it dies, no new flow can be set up, though installed rules keep forwarding, which is why controllers are replicated. Latency matters when the controller sits in the cloud, because the first packet of a flow pays a round trip; placing the controller at a fog node reduces it. Finally, 6LoWPAN frames (Unit 3) are tiny, so a full OpenFlow header does not fit, and lightweight southbound protocols are used.

In IoT, SDN usually lives in sensor gateways, fog nodes and the backhaul between site and cloud, not on the battery-powered sensor itself.

Worked example

Question. A site has 200 sensor flows spread over 5 equal gateways. Static routing sends 40 flows to each gateway. The SDN controller moves 30% of the flows of one congested gateway to the other four, equally. Find the final number of flows on each gateway and verify the total.

  1. Initial flows per gateway = 200 ÷ 5 = 40 flows.
  2. Flows moved out of the congested gateway = 0.30 × 40 = 12 flows.
  3. Congested gateway after the move = 40 − 12 = 28 flows.
  4. Flows added to each of the other four gateways = 12 ÷ 4 = 3 flows.
  5. Each other gateway = 40 + 3 = 43 flows.
  6. Check the total = 28 + 4 × 43 = 28 + 172 = 200 flows, which matches the original count.

Answer. The congested gateway ends with 28 flows and each of the other four gateways ends with 43 flows, totalling 200 flows.

Exam traps

  • Mixing up the planes: the controller decides and the gateway forwards. The controller never carries sensor payload.
  • Treating the SDN controller as the cloud application. The application states policy through the northbound API; the controller converts that policy into flow rules.
  • Counting flow rules as data. Rules are instructions about handling packets; adding rule bytes to payload throughput is wrong.
  • Swapping northbound and southbound. Northbound faces applications (often REST); southbound faces devices (OpenFlow).
  • Forgetting the table-miss entry. The favourite question is how the first packet of a new flow is handled: it goes to the controller, which installs a rule, and later packets match in the table.

5.7 Resource management: clustering, agents, data synchronization

Large IoT deployments cannot let every sensor talk to the cloud. Resource management groups nearby nodes into clusters, gives each cluster a head, and runs software agents that filter and decide locally. Gateways and cloud copies of data are synchronized so they agree. Clustering cuts gateway messages and saves radio energy. Agents reduce response time and upstream traffic. Synchronization keeps replicated state usable after disconnections. Only a few universities teach this topic. It appears in smart-city, agriculture and industrial monitoring.

You need: 5.2 for cloud routing, Unit 2 for WSN basics, and Unit 3 for network layer.

Clustering and agents

Clustering groups sensor nodes into sets, and each set elects one cluster head (CH). Ordinary nodes send readings to the CH; the CH aggregates and forwards one message to the gateway. The gateway sees C streams instead of N streams, where N is the node count. This cuts backhaul messages and lets nodes use short radio hops, which saves energy. Cluster size is a trade-off. A large cluster means fewer CHs and fewer gateway messages, but the CH spends more energy and may become a bottleneck. A small cluster spreads load but brings back gateway traffic. CH election uses residual battery, link quality, and rotation. A simple rule scores each node and the highest score becomes CH for one round. Then rotate. M_gw = C × (T/Δt). M_gw is gateway messages in T seconds; C is the number of clusters; Δt is the cluster head's reporting interval in seconds (the node-to-CH interval is separate). This counts CH reports only. An agent is software that acts for a node or a user without waiting for the cloud. A stationary agent runs on a node, gateway, or CH; a mobile agent moves code and state between devices. Agents do local filtering: the CH agent sends an alert when temperature crosses 45 °C instead of streaming every sample. Agents can aggregate, cache, and negotiate with neighbouring agents to share a radio channel or reduce duplicate alarms. This lowers latency and upstream bytes. Agents differ from SDN controllers (see 5.6): an SDN controller centralizes path control, while agents keep local autonomy. An agent must be authenticated before it changes settings.

Data synchronization and eventual consistency

Replication keeps copies of a record at the gateway and in the cloud. Synchronization is the process that makes copies agree. A version vector is a list of counters, one per replica. Replica A's vector dominates B if every counter in A is at least the matching counter in B and at least one is greater. If neither dominates, the updates are concurrent and a conflict exists. Resolution can be last-writer-wins with a synchronized clock, or an application rule such as higher-priority alarm wins. Eventual consistency means that if updates stop, all replicas converge; it does not mean a read is instantly fresh. Sync frequency controls the trade-off: syncing every 60 s gives fresh data and more messages; syncing on reconnect saves bandwidth but risks stale reads. Steps: 1. Exchange version vectors. 2. Detect domination or conflict. 3. Apply or merge. 4. Store the new vector.

Worked example

Question. A field has 30 sensor nodes in 3 clusters of 10. Directly, each node sends a 64-byte reading to the gateway every 60 s. With clustering, each node sends the same reading to its cluster head every 60 s, and each head sends one 128-byte aggregate to the gateway every 60 s. Compare gateway inbound bytes per day (1 day = 86,400 s).

  1. Step 1: Reports per node per day = 86,400 ÷ 60 = 1,440.
  2. Step 2: Direct gateway bytes/day = 30 × 1,440 × 64 = 2,764,800 bytes/day = 2.7648 MB/day (1 MB = 1,000,000 bytes).
  3. Step 3: Clustered gateway bytes/day = 3 × 1,440 × 128 = 552,960 bytes/day = 0.55296 MB/day.
  4. Step 4: Reduction = 2,764,800 ÷ 552,960 = 5.

Answer. Gateway inbound falls from 2,764,800 bytes/day (2.7648 MB/day) to 552,960 bytes/day (0.55296 MB/day), one-fifth of the original (an 80% cut, 5 times fewer bytes); node-to-CH traffic still exists.

Exam traps

  • Cluster-head traffic is not free: node-to-head and head-to-gateway bytes add up; say whether you compare gateway inbound or total radio bytes.
  • Eventual consistency is not instant consistency; a read right after a write can be stale.
  • A larger cluster lowers gateway messages but can drain the head; there is no single best size.
  • An agent making local decisions is not an SDN controller.
  • Version vectors detect concurrent updates; one version number cannot order updates from different replicas.

Apply A factory has 500 temperature sensors. Each sends one 200-byte reading every 10 seconds. Size the cloud side: messages per second, data per day, and choose a broker plus storage strategy for live alerts and one-year history. 13 marks

Messages per second = 500 / 10 = 50 messages/s; Bytes per second = 50 x 200 = 10,000 B/s = 10 kB/s; Per day = 10 kB/s x 86,400 s = 864,000 kB, about 864 MB/day; Per year about 315 GB before replication and indexing; Broker: MQTT with QoS level suited to alerting; one topic per machine or per sensor type; Hot path: stream processing with a 1-minute tumbling window for threshold alerts; Cold path: write raw to object storage or a time-series database, downsample older data; Add retention policy, compression and partitioning by device ID.

Apply You must provision and protect a fleet of 5,000 electricity smart meters that connect to a cloud platform. Describe the security steps from manufacturing to daily operation. 13 marks

Unique device identity per meter, certificate or key injected at manufacture; Register each device in the cloud registry, mark it as provisioned; Mutual authentication with TLS so a fake server cannot collect readings; Per-device policy: the meter may publish only to its own topic; RBAC for human users: installer, operator, auditor; Key rotation and revocation for stolen or retired meters; Firmware update signed and verified, staged rollout; Data at rest encrypted; billing data access logged; Fallback: quarantine a device that behaves abnormally.

Apply A campus has 2,000 sensor nodes sending readings to one gateway. Apply clustering to reduce traffic and compute the reduction if clusters of 20 nodes each send one aggregated message per round instead of every node sending one. 13 marks

Cluster head election by residual energy, distance and rotation; Members send to the head over short hops; the head aggregates and forwards; Number of clusters = 2000 / 20 = 100; Messages reaching the gateway per round fall from 2000 to 100, a 20x reduction; Energy saved on long-range radio at the members; Costs: aggregation delay, head energy drain, need for rotation; State that cluster heads forward summaries, so raw data is lost unless sampled.

Apply A building has legacy Modbus sensors. Show how you would expose them through the Web of Things so a web dashboard can read them without knowing Modbus. 10 marks

Gateway reads Modbus registers on a polling cycle; Map each register to a WoT property with a name, type and unit; Write a Thing Description listing properties, events and a protocol binding; Gateway offers HTTP or MQTT binding with JSON payloads; Dashboard uses the description to build its view automatically; Security: authenticate the dashboard, allow read-only access; State the mapping table as the single place to change when a sensor is added.

Analyze and evaluate

Evaluate Compare AWS IoT and Azure IoT Hub on device identity, protocol support, rules and device state. Recommend one for a start-up with 300 devices and justify. 15 marks

Both: per-device identity, certificate based mutual TLS, MQTT and HTTPS support; AWS IoT Core: policies attached to certificates, rules engine with SQL-like statements, device shadow; Azure IoT Hub: per-device SAS tokens or certificates, routes and endpoints, device twin with desired and reported properties, built-in device management; Compare pricing units: connectivity plus messages versus tiered message allowance per day; Compare ecosystem lock-in, tooling maturity, regional availability; Recommendation must state a criterion such as cost at 300 devices, team skills, existing cloud use; Close with the migration risk of proprietary features.

Evaluate A home security product uploads continuous video and door-sensor logs to the cloud. Analyse the privacy risks and propose design changes using data minimization, retention limits and anonymization. 13 marks

Identify personal data: faces, voices, occupancy pattern, timestamps; Risks: pattern-of-life inference, unauthorized sharing, breach impact, over-retention; Minimization: record only on motion or door-open events, drop audio if not needed; On-device processing to send events and labels instead of raw video; Retention: keep short rolling window, delete after N days unless flagged; Anonymization: blur faces, generalize timestamps for analytics copies; Access control and audit logs for who watched what; Consent and a clear notice to household members and visitors; Trade-off: less data reduces both privacy risk and model quality.

Evaluate Evaluate whether software defined networking is justified for a city-wide IoT network. Discuss benefits, controller failure, latency and scalability. 13 marks

Benefits: central policy for thousands of devices, network slicing per application, fast reconfiguration; Traffic engineering for bursty sensor uploads; Controller placement: local controllers per zone, replicated for failure; Failure analysis: if the controller is down, switches keep last rules, so degrade gracefully not stop; Latency of control messages versus data path; keep data plane local; Scalability: flow table size, controller throughput, east-west consistency; Security: the controller is a high-value target, secure channel needed; Verdict: justified when policy changes are frequent and devices many, overkill for a small fixed deployment.

Evaluate In a sensor cloud, several tenants share physical sensors while gateways cache data locally. Analyse how multi-tenancy and data synchronization interact, and evaluate a suitable consistency choice. 15 marks

Multi-tenancy: one physical sensor serves several virtual sensors with different rates and privacy rules; Isolation must hold for data and for query load; Gateways cache during network loss, so copies diverge; Synchronization options: version vectors, timestamps, last-writer-wins, per-tenant logs; Last-writer-wins loses data when sensors emit different readings; per-reading append logs avoid loss; Strong consistency costs availability during a Chennai power cut or link loss; Eventual consistency fits sensor readings if the application tolerates a short delay; Evaluate: choose eventual consistency plus conflict-free append per tenant, reserving strong consistency for billing or alarms.

Glossary

Authentication
Proving that a device or user is who it claims to be.
Authorization
Deciding what an authenticated identity is allowed to do.
Batch processing
Computation over a stored, bounded collection of data, usually with high throughput and higher latency.
Cloud computing
Delivery of computing, storage and services over a network from a shared pool, provisioned on demand.
Cluster head
The node that collects, aggregates and forwards data for its cluster.
Clustering
Grouping nodes so a chosen head aggregates their data and reduces long-range traffic.
Container
A lightweight isolated package of an application and its libraries that shares the host operating system kernel.
Data lake
A store that keeps raw data in its native format until it is needed for analysis.
Data minimization
Collecting only the data actually needed for a stated purpose.
Data synchronization
The process of making copies of data on different nodes agree.
Device twin
A cloud copy of a device's reported and desired state, usable while the device is offline.
Digital twin
A model of a physical asset kept in step with its live data and used for simulation and prediction.
Elasticity
Automatic addition or removal of resources as demand changes.
Encryption at rest
Storing data in encrypted form so a stolen disk or backup does not reveal it.
Eventual consistency
A guarantee that replicas will converge to the same value if no new updates occur.
Flow table
A switch table of match fields and actions that tells the switch how to handle each packet.
IoT cloud platform
A managed service offering device identity, a message broker, rules, storage and device management for connected devices.
Message broker
A server that receives published messages and forwards them to subscribers, decoupling senders from receivers.
Middleware
Software between devices and applications that hides protocol and hardware differences.
Mobile agent
A program that moves between nodes and runs locally, carrying code instead of shipping raw data.
Multi-tenancy
One physical system serving several customers with logical isolation between their data and workloads.
QoS (MQTT)
A delivery guarantee level: at most once, at least once, or exactly once.
Rules engine
A service that evaluates conditions on incoming messages and triggers actions when they match.
Sensor cloud
A platform that virtualizes sensors from many owners so applications can request sensing as a service.
Software defined networking
A network architecture with a centralized controller that installs forwarding rules into switches.
Stream processing
Continuous computation on events as they arrive, with low latency.
Thing Description
A machine-readable document describing a device's properties, actions, events and protocol bindings.
Topic
A named string in a publish/subscribe system, such as home/room1/temperature, that subscribers match against.
Virtual machine
A software-defined computer with its own operating system running on shared physical hardware.
Virtual sensor
A logical sensor created on demand from one or more physical sensors with chosen location, rate and duration.
Web of Things
Exposing devices as described web resources reachable over standard web protocols.
Window
A finite grouping of stream events by time or count so that aggregates can be computed.
X.509 certificate
A signed digital document binding a public key to a device or server identity.
