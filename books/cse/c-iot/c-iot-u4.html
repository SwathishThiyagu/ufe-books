4.1 Arduino boards, IDE and ecosystem

An Arduino is a small open-source board built around a microcontroller. You write one program on a PC, send it down a USB cable, and the board runs that program again and again, reading and writing its pins. That is the whole idea: the PC is for writing only, the board does the work alone afterwards. Students use it for the first working version of an IoT device — a light that blinks, a pump that switches, a sensor value pushed to the cloud. This chapter covers the boards, the IDE, and the ecosystem around them.

You need: the microcontroller-versus-single-board-computer comparison from Unit 2, Sensors, Actuators and Embedded Hardware.

Boards: Uno, Nano and Mega

An Arduino board is a microcontroller plus a crystal, a voltage regulator, a USB-to-serial chip and rows of header pins on one printed circuit board. On the Uno the pins are labelled digital 0–13 and analog A0–A5. The Nano adds A6 and A7; the Mega has far more of both. Power pins are 5V, 3.3V, GND and Vin. A digital pin can be an output, where the board drives it to 5 V (HIGH) or 0 V (LOW), or an input, where the board reads whether it is high or low.

Uno, Nano and Mega are 5 V boards. The Uno and Mega have a barrel jack that takes 7–12 V, and an onboard regulator makes the 5 V. The Nano has no barrel jack: power it from USB, or feed 7–12 V into its Vin pin, which goes through its own small regulator. The Nano is an Uno squeezed onto a breadboard-sized board with the same chip; the Mega is wider because it carries more pins and more memory.

Choose by counting pins first. If the project needs four sensors, three relays and a display, add up the pins before buying. Flash holds the program; SRAM holds the variables while it runs. The Uno's 2 KB of SRAM is small — a few long text strings and you are out of room. You cannot add RAM the way you add a stick to a PC. Shrink the code (flash-resident strings, smaller variable types) first, and move to a bigger board only when that is not enough.

The IDE: write, verify, upload

The IDE is one program on the PC with three jobs: write, verify, upload.

  1. Write the sketch in the editor. The file ends in .ino and holds two functions: setup() runs once at power-on, loop() repeats forever.
  2. Pick the board under Tools → Board, and the serial port under Tools → Port.
  3. Verify (the tick button). This compiles the C++ into machine code for that exact chip and reports syntax errors before any hardware is touched.
  4. Upload (the arrow button). The board resets, a small bootloader already burned into flash listens on the USB serial line for a moment, receives the binary and writes it.
  5. Open the Serial Monitor to watch printed values: Serial.begin(9600) in setup, Serial.println() in loop.

Verify is not upload. Verify only compiles on the PC and nothing reaches the board. Upload fails if the wrong port is picked, or if another program is holding that serial port open.

The board package (Board Manager) adds support for chips the IDE does not ship with, such as ESP32 or ESP8266. Install it once and the board appears in the Tools menu. Names vary between syllabi — some call the program a sketch, some call the language Arduino C/C++. Both are fair: the file is .ino, the language is C++, and the board package supplies the matching C++ compiler — AVR-GCC for the Uno's ATmega328P, another toolchain for other families.

Libraries, shields and the ecosystem

A library is code someone else wrote and tested. Adding one inserts a #include line at the top of the sketch, and a servo, an SD card or a Wi-Fi module then takes about ten lines to drive. The IDE ships with a standard set — Servo, Wire for I²C, SPI, EEPROM — and the Library Manager supplies thousands more.

A shield is a board that plugs straight into the Arduino headers. Motor, Ethernet and GSM shields line up with the pins so no wiring is needed, and the shield's own library knows which pin does what. Shields can stack, but they fight over pins; check which pins each one claims before stacking two.

The design is open, so many companies sell Uno-compatible clones at lower prices. They use the same IDE; a few need a CH340 USB driver installed on the PC first. Some Arduinos — Due, Nano 33, MKR series — run at 3.3 V, so check the logic level before connecting a sensor. The Uno pin layout has become a de-facto standard, and most shields assume it even when the board is different.

Worked example

Question. An Arduino Uno runs at 5 V. An LED with forward voltage 2 V is connected from pin 9 to ground through a 1 kΩ resistor. (a) Find the current through the LED. (b) Find the power wasted in the resistor. (c) Write the sketch lines that blink the LED at 500 ms on and 500 ms off, and state the blink frequency.

  1. The pin is at HIGH (5 V) feeding the resistor, the LED and ground at 0 V. So 5 V is shared between resistor and LED.
  2. The LED holds about its forward voltage, V_f = 2 V. The resistor takes the rest: V_R = 5 V − 2 V = 3 V.
  3. Ohm's law gives the current: I = V_R ÷ R = 3 V ÷ 1000 Ω = 0.003 A = 3 mA. Here R = 1000 Ω is the resistance and I is the current in amperes.
  4. The usual working limit of an Arduino pin is about 20 mA, so the pin can source 3 mA directly.
  5. Power in the resistor: P = I² × R = (0.003 A)² × 1000 Ω = 0.009 W = 9 mW, so any quarter-watt resistor is safe.
  6. BLINK. In setup: pinMode(9, OUTPUT); In loop: digitalWrite(9, HIGH); delay(500); digitalWrite(9, LOW); delay(500);. Delays are in milliseconds, so one cycle takes 500 ms + 500 ms = 1000 ms and the frequency is 1 ÷ 1 s = 1 Hz.

Answer. The pin current is 3 mA, the resistor dissipates 9 mW, and the sketch blinks the LED at 1 Hz.

Exam traps

  • A 5 V output wired straight into a 3.3 V sensor input. Check the sensor's absolute maximum first; use a resistor divider or a level shifter.
  • Forgetting the series resistor. An LED without one pulls far more than the pin limit and both can die; always compute I = (V_s − V_f) ÷ R and keep it well under 20 mA.
  • Verify is not upload. Verify only compiles on the PC; nothing reaches the board until you upload.
  • Putting one-time setup code inside loop(). setup() runs once; loop() repeats without end, as fast as its own code allows — thousands of times a second for an empty loop, once a second if it contains delay(1000). So motor or display initialisation must sit in setup().
  • delay() takes milliseconds as a whole number. delay(500) is half a second, not 500 seconds and not 0.5 ms.

4.2 Arduino C programming: sketches, variables, digital I/O

An Arduino sketch is a C++ program with two required functions. setup() runs once at power-on; loop() repeats forever. Typed variables hold pin numbers and readings. pinMode() selects input or output. digitalWrite() drives a pin HIGH or LOW. digitalRead() samples a digital pin. delay() waits in milliseconds. if/else chooses a branch; Serial.print shows values in the IDE. Only a few universities teach this as a separate programming chapter. Makers use it for buttons, LEDs and relays, such as a doorbell LED that follows a switch.

You need: Chapter 4.1.

Sketch structure and typed variables

A sketch is a C++ program. The Arduino core supplies main(), which calls setup() once and then loop() forever. You do not write main(). setup() runs once after reset. loop() repeats forever. Every variable has a type. int stores a whole number, such as pin 13. On AVR boards such as the Uno, int is 16 bits, so it holds -32768 to 32767; use long or unsigned long for larger values. float stores a decimal, such as 2.5. boolean stores true or false. Use const int LED = 13; for a pin that never changes; const blocks accidental writes. Names are case-sensitive. End statements with a semicolon. Comments use // or /* */. Serial.begin(9600); starts serial output at 9600 bits per second. Serial.println(value); prints value and a newline in the Serial Monitor. That is the main debugging tool when no display is attached. A variable declared inside loop() is recreated each pass; a global keeps its value. Use meaningful names: buttonPin, ledPin. The board stores the sketch in flash; variables live in RAM. Choose the smallest type that fits.

Digital I/O functions and control flow

pinMode(pin, mode) sets a pin. mode is INPUT or OUTPUT. OUTPUT can source or sink limited current; use a series resistor for an LED. digitalWrite(pin, value) sets an output pin to HIGH (5 V on most Uno-class boards) or LOW (0 V). digitalRead(pin) returns HIGH or LOW from an input pin; it does not set the pin. delay(ms) blocks for ms milliseconds. if (condition) { } else { } chooses a branch. Use == to compare, not =. Example: read pin 2; if HIGH, set pin 13 HIGH; else LOW. With a pull-down resistor, a released button reads LOW; a pressed button connects 5 V and reads HIGH. The loop repeats this test, so the LED follows the button. delay() stops all other work. Call pinMode(pin, INPUT) or pinMode(pin, INPUT_PULLUP) to state the direction, and give the pin a defined level with a pull resistor. An unconnected input floats and gives random values. A short delay can debounce a noisy button. Check wiring before power.

Worked example

Question. A push button connects 5 V to Arduino pin 2. A 10 kΩ resistor pulls pin 2 to ground. An LED is on pin 13. Write setup() and loop() so the LED is on only while the button is pressed. Find the pull-down current when pressed.

C program.

const int BUTTON_PIN = 2;
const int LED_PIN = 13;

void setup() {
  pinMode(BUTTON_PIN, INPUT);
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  if (digitalRead(BUTTON_PIN) == HIGH)
    digitalWrite(LED_PIN, HIGH);
  else
    digitalWrite(LED_PIN, LOW);
}
  1. 1. Set directions in setup(): pinMode(2, INPUT); pinMode(13, OUTPUT).
  2. 2. In loop(), if digitalRead(2) == HIGH, digitalWrite(13, HIGH); else, digitalWrite(13, LOW).
  3. 3. Pressed: pin 2 is at 5 V. Pull-down current I = V ÷ R = 5 V ÷ 10 kΩ = 5 ÷ 10000 A = 0.0005 A = 0.5 mA.
  4. 4. Released: no 5 V path; the resistor holds pin 2 at 0 V; current is 0 mA.

Exam traps

  • digitalRead(pin) reads a pin; pinMode(pin, INPUT) sets its direction.
  • == compares; = assigns. if (x = HIGH) is wrong.
  • INPUT_PULLUP inverts logic: a button to ground reads LOW when pressed.
  • delay(1000) is 1000 ms = 1 s, not 1 ms.
  • A pin set OUTPUT must not be driven by an external voltage source.

4.3 Raspberry Pi board, interfaces and Linux

A Raspberry Pi is a small single-board computer. It runs Linux from a microSD card, so it has a file system, user accounts and a terminal, not just one repeating program. A 40-pin header exposes general-purpose input/output (GPIO) pins at 3.3 V logic. That mix makes the Pi useful when an IoT node must sense, decide, log data and serve a web page, while still driving simple LEDs, relays and sensors. This chapter looks at the board blocks, the Linux system that starts on power-up, and the serial interfaces UART, I2C, SPI and PWM.

You need: Unit 2 on single-board computers and <a href='#arduino-boards-ide-and-ecosystem'>Chapter 4.1 for the contrast with a microcontroller board; basic Linux helps.

Board blocks and the 3.3 V header

A Raspberry Pi board is built around a system on chip (SoC). The SoC contains the processor, graphics unit, memory controller and many peripherals on one integrated circuit. RAM (random-access memory) chips sit beside it and hold running programs; RAM loses its contents when power is removed. A microSD card holds the operating system and files, so it is non-volatile storage.

The board also has USB ports, an HDMI video output, and Ethernet or Wi-Fi for network access. The 40-pin GPIO header is the part an IoT circuit uses. GPIO means general-purpose input/output: pins that software can set high or low, or read as high or low.

Logic level is the voltage that represents 0 or 1. On the Raspberry Pi header, high is 3.3 V and low is 0 V. A pin is not 5 V tolerant. A 5 V signal connected directly to a GPIO pin can damage the SoC. Use a level shifter or a resistor divider when a sensor outputs 5 V. Some header pins also carry UART, I2C, SPI and PWM signals.

Linux boot, user account, terminal, apt and files

On power-up, the Raspberry Pi reads a bootloader from the microSD card. The bootloader loads the Linux kernel into RAM. The kernel is the core of the operating system; it talks to hardware and starts services. The kernel mounts the root file system from the microSD card. A login prompt then appears. Some syllabi call the standard system Raspberry Pi OS, formerly Raspbian.

A user account separates your files and permissions from system files. The terminal is a text interface: you type a command, press Enter, and read the output. Common file commands are ls to list a directory, cd to change directory, and nano to edit a text file. Your home directory is usually /home/username.

The package manager apt installs software. The command sudo apt update refreshes the package list; sudo runs the command as the superuser. The command sudo apt install package-name installs a package and its dependencies. Reboot after a kernel update. A Pi can also run a web server or an MQTT client, so it can act as a small network node, not only as a local controller.

Interfaces: UART, I2C, SPI and PWM

The header exposes several serial interfaces. UART means universal asynchronous receiver/transmitter. It uses two data wires, TX and RX, and no shared clock. Both ends must use the same baud rate, which is bits per second. UART is point-to-point.

I2C means inter-integrated circuit. It uses two wires, SDA for data and SCL for clock. Many devices share the bus, and each device has a 7-bit address. Pull-up resistors are needed on both lines. SPI means serial peripheral interface. It uses SCLK for clock, MOSI for master-out-slave-in, MISO for master-in-slave-out, and one chip-select (CS) line per device. SPI is faster than I2C but uses more pins.

PWM means pulse-width modulation. A pin switches fast between high and low. Duty cycle is the fraction of time the pin is high:

D = (ton ÷ T) × 100%

D is duty cycle in percent; ton is on time in seconds; T is period in seconds.

PWM sets LED brightness or motor speed. All these signals use 3.3 V logic on the Pi. A 5 V device needs a level shifter. Sensor wiring is in <a href='#interfacing-sensors-and-actuators-with-boards'>Chapter 4.5; Python control is in <a href='#programming-raspberry-pi-with-python'>Chapter 4.4.

Worked example

Question. A red LED with forward voltage 2.0 V is driven from a Raspberry Pi GPIO pin whose high level is 3.3 V. The design target is 5 mA. Find the exact series resistance, choose the nearest standard value, and find the actual current. State units.

  1. GPIO high voltage is 3.3 V, LED forward voltage is 2.0 V, target current is 5 mA = 0.005 A.
  2. Resistor voltage = 3.3 V − 2.0 V = 1.3 V.
  3. R = 1.3 V ÷ 0.005 A = 260 Ω.
  4. 260 Ω is not a standard value; the nearest standard value is 270 Ω.
  5. Actual current = 1.3 V ÷ 270 Ω = 0.00481 A = 4.81 mA.

Answer. The exact resistance is 260 Ω; use 270 Ω, giving an actual current of 4.81 mA.

Exam traps

  • Raspberry Pi GPIO is 3.3 V logic and not 5 V tolerant; a 5 V sensor output can damage the pin unless you use a level shifter or divider.
  • Do not confuse RAM with microSD: RAM is volatile working memory; the OS and files live on the microSD card.
  • UART has no shared clock and is point-to-point; I2C is an addressed bus with SDA and SCL; SPI uses chip-select lines.
  • Duty cycle and frequency are different: duty cycle sets the high-time fraction, frequency sets how many periods occur per second.
  • In the LED resistor calculation, convert mA to A before dividing; 5 mA is 0.005 A. The exact 260 Ω is not standard; 270 Ω gives 4.81 mA.

4.4 Programming Raspberry Pi with Python

Python is the usual language for Raspberry Pi control because it reads like plain English and has libraries for the GPIO header. A short script can set a pin high, wait, read a button, or fetch a number from an external chip. This chapter shows the Python pieces you need, the gpiozero calls for LEDs and buttons, and the SPI route to an analog sensor. The Pi has no analog input pins, so an external ADC such as the MCP3008 is part of the circuit, not an optional extra.

You need: the Raspberry Pi board, Linux and 3.3 V GPIO header from Chapter 4.3.

Python pieces you need

A variable is a name for a value. t = 20.0 stores a float in t. A list holds many values in order: temps = [20.0, 21.5, 19.8]. Indexing starts at 0, so temps[0] is 20.0. A for loop visits each item. An if chooses a branch when a condition is true. A function groups steps under a name and returns a result.

Use import to load a module. import time gives time.sleep; from gpiozero import LED brings one class into your file. Save a script as blink.py and run it with python3 blink.py. The program runs top to bottom, then exits unless it contains a loop.

Python program.

temps = [20.0, 21.5, 19.8]
total = 0.0
for t in temps:
    total = total + t
mean = total / len(temps)
print(f'mean = {mean:.2f} C')

Output

mean = 20.43 C

GPIO output and input with gpiozero

GPIO means general-purpose input/output. gpiozero names a pin by its Broadcom GPIO number. LED(17) means GPIO17, not physical pin 17. The library sets the pin as an output for you. led.on(), led.off() and led.toggle() change it. For input, Button(27) creates a button object on GPIO27. button.is_pressed is True while the button is held. button.when_pressed can call a function instead of polling.

The older RPi.GPIO library uses different names. You set a numbering mode once with GPIO.setmode(GPIO.BCM); then GPIO.setup(17, GPIO.OUT), GPIO.setup(27, GPIO.IN), GPIO.output(17, GPIO.HIGH), and GPIO.input(27) work on the same header. Do not mix BCM and board numbering in one program. time.sleep(0.05) pauses for 0.05 s and stops the CPU from spinning in a tight loop.

Pseudocode.

from gpiozero import LED, Button
from time import sleep
led = LED(17)
button = Button(27)
while True:
    if button.is_pressed:
        led.on()
    else:
        led.off()
    sleep(0.05)

Reading an analog sensor over SPI

The Pi's GPIO header is digital: a pin reads 0 or 1, roughly 0 V or 3.3 V. A sensor such as the LM35 gives a voltage that changes smoothly with temperature, so the Pi needs an external analog-to-digital converter (ADC). The MCP3008 is a 10-bit ADC with eight input channels and an SPI (Serial Peripheral Interface) connection. It returns an integer code from 0 to 1023.

Wire the LM35 output to channel 0 of the MCP3008. The Pi talks to the MCP3008 over SPI: four wires, clock, data in, data out and chip select. In Python, gpiozero provides MCP3008; create it as adc = MCP3008(channel=0) together with the SPI pins. Then adc.value gives the reading as a fraction of Vref (0 to 1), and adc.raw_value gives the integer code 0 to 1023. For another channel, create another MCP3008 object with a different channel number. The conversion is:

V<sub>in</sub> = (code ÷ 1023) × V<sub>ref</sub>

Vin is the ADC input voltage in volts; code is the raw 10-bit value, 0 to 1023; 1023 is 210 − 1, the full-scale code; Vref is the ADC reference voltage in volts, here 3.3 V.

For the LM35, the output is 10 mV per °C, that is 0.010 V/°C. So T = Vin ÷ 0.010 V/°C. A code of 62 with Vref = 3.3 V gives 0.200 V and 20.0 °C. The sequence diagram shows the same exchange. Keep the reference stable; a noisy 3.3 V rail adds error to every code. Sensor physics is in Chapter 4.5.

Worked example

Question. An LM35 sensor outputs 10 mV per °C. It feeds channel 0 of an MCP3008 10-bit ADC with reference 3.3 V. A Python script reads raw value 62. Find the ADC input voltage and the temperature. Then write a Python program that performs the conversion and prints both values.

Python program.

code = 62
vref = 3.3
full_scale = 1023
vin = code / full_scale * vref
sensitivity = 0.010
temperature = vin / sensitivity
print(f'V = {vin:.3f} V')
print(f'T = {temperature:.1f} C')
  1. LM35 sensitivity = 10 mV/°C = 0.010 V/°C; ADC full-scale code = 210 − 1 = 1023.
  2. ADC input voltage: Vin = (62 ÷ 1023) × 3.3 V = 0.200 V. Here 62 is the raw code, 1023 is full scale, and 3.3 V is Vref.
  3. Temperature: T = 0.200 V ÷ 0.010 V/°C = 20.0 °C.

4.5 Interfacing sensors and actuators with boards

A sensor turns a physical quantity — light, distance, temperature — into a voltage or digital pulse. A board reads it on a pin, compares it with a rule and switches an actuator: LED, buzzer, relay or motor. This chapter covers common IoT interface circuits — LED resistor, push button, voltage divider, ultrasonic ranger, temperature sensor — and drivers for 12 V lamps or motors. The pattern runs door alarms, water-level cutoffs, smart parking and cold-chain monitors.

You need pinMode, digitalWrite and digitalRead from Chapter 4.2, Raspberry Pi GPIO from Chapter 4.3, and the voltage divider idea.

Digital pins: LEDs and push buttons

Every board exposes digital pins. As output, a pin is 0 V (LOW) or logic voltage (HIGH): 5 V on most Arduinos, 3.3 V on a Raspberry Pi. As input, it reports whether voltage is above or below about half logic voltage. One bit drives an LED or reads a button.

An LED needs a series resistor: R = (Vsupply − Vf) ÷ I, where Vf is forward voltage (about 2 V red, 3.2 V blue), I is current in amperes. For 5 V, red LED and 10 mA: R=(5−2)÷0.01=300 Ω; use 330 Ω. Keep an Arduino pin at or below 20 mA; more needs a transistor.

A bare push button leaves the pin floating when open. Connect one side to the pin and the other to GND, then pinMode(pin, INPUT_PULLUP). The pin reads HIGH when open and LOW when pressed; forgetting inversion is a common bug. Contacts bounce for milliseconds, so ignore repeats for about 20 ms.

Analog sensors: light, temperature, humidity

An analog sensor returns a varying voltage; the ADC converts it to a number. Arduino Uno ADC is 10-bit against 5 V. There are 1024 steps (2¹⁰) across the reference, so one step is Vref ÷ 1024 ≈ 4.9 mV. The code formula V = reading × Vref ÷ 1023 maps largest reading 1023 to full scale; both appear because step count is 1024 but codes run 0–1023. reading is analogRead(), 0 to 1023. Raspberry Pi has no ADC, so it uses an external chip such as MCP3008 (see Chapter 4.4).

Vout = Vcc × R ÷ (R_LDR + R)

Vout is the midpoint voltage sent to the ADC pin; Vcc is the supply, 5 V; R_LDR is the LDR resistance in ohms; R is the fixed resistor in ohms.

An LDR (light-dependent resistor) drops resistance as light rises — roughly 1 MΩ dark and 1 kΩ bright. A pin reads voltage, not resistance, so use a divider: LDR from 5 V to midpoint, fixed R from midpoint to GND. With R = 10 kΩ, dark gives 5×10÷1010≈0.05 V; bright gives 5×10÷11≈4.55 V. Light level rises with voltage.

LM35 outputs 10 mV per °C and 0 V at 0 °C. T = Vout ÷ 0.01 V/°C; 0.303 V means 30.3 °C. At 4.9 mV per ADC step, one count is about 0.49 °C, so good to about half a degree.

DHT11 and DHT22 are digital: one wire carries a 40-bit burst of humidity and temperature, decoded by a library. DHT11: 0–50 °C to ±2 °C and 20–90 % RH to ±5 %. DHT22: −40 to 80 °C to ±0.5 °C and 0–100 % RH to ±2 %. Read DHT11 at most once a second and DHT22 once every two seconds, or they return errors.

Actuators: buzzer, relay, motor driver

A pin supplies only a few milliamperes; lamps, pumps and motors need more. An actuator sits behind a driver, and the pin drives the driver.

  • Buzzer: an active buzzer has its own oscillator, so digitalWrite(pin, HIGH) starts a fixed tone; a passive buzzer needs tone(pin, 2000) for 2 kHz. Small buzzers that draw under about 20 mA can be driven from a pin directly; anything that draws more (many buzzers draw 25–40 mA, and the Arduino per-pin recommended limit is 20 mA) needs a transistor driver, the same as a loud buzzer.
  • Relay: a 5 V coil closes contacts in a separate circuit — a 230 V lamp or a pump. A ready-made module contains the driver transistor and a flyback diode that absorbs the coil's inductive kick at switch-off. Contacts carry a rating such as 10 A at 250 V AC. Mains wiring is dangerous: keep it enclosed and switch off before touching.
  • DC motor: an H-bridge driver (L293D, L298N, TB6612) sits between the pin and the motor, with its own supply and a shared ground. Two pins set direction, and analogWrite() with PWM from 0 to 255 sets speed.

The control pattern is read, compare, act. One threshold makes a relay chatter near the boundary, so use two: on below 19 cm, off above 21 cm. The gap is hysteresis; it protects relay and load.

Crossing between 3.3 V and 5 V

Boards do not share logic voltage. Arduino Uno pins are 5 V. Raspberry Pi GPIO is 3.3 V and not 5 V tolerant: a 5 V signal can destroy it; a 3.3 V output may be too low for some 5 V modules to read HIGH.

Vout = Vin × R2 ÷ (R1 + R2)

Vin is the incoming signal voltage; R1 is the resistor from Vin to the midpoint; R2 is the resistor from midpoint to GND; Vout is the reduced voltage reaching the pin.

Three fixes: choose a 3.3 V sensor; use a resistive divider for one-way high-to-low; or use a bidirectional MOSFET level-shifter for two-way lines such as I²C. For 5 V with R1=1 kΩ and R2=2 kΩ, Vout=5×2÷3=3.33 V, safe for Pi. Power is a second gap: Pi 3.3 V pins give little current, so motors and relays take own supply with common ground.

4.6 Other boards: ESP8266, BeagleBone, pcDuino

An Arduino has no network and a Raspberry Pi cannot promise a pulse to the microsecond. Other boards fill the gaps. The ESP8266 puts a Wi-Fi radio and a small processor on one 3.3 V chip. The BeagleBone Black runs Linux and adds fast real-time co-processors. The pcDuino runs Linux on a board that accepts Arduino shields. This chapter compares all three on five checks: logic voltage, operating system, wireless, pin count and power.

You need: Chapter 4.1 for what an Arduino board is and Chapter 4.3 for Linux boards and 3.3 V GPIO.

ESP8266: Wi-Fi on one chip

The ESP8266 is one chip from Espressif: a 32-bit processor, some memory and a 2.4 GHz Wi-Fi radio. A bare module costs a few hundred rupees. The chip runs at 3.3 V and every pin is 3.3 V.

A bare module such as the ESP-01 is awkward: eight pins, no USB socket, and it needs a steady 3.3 V supply while the radio pulls a few hundred milliamps in a transmit burst. Some pins must sit at the right level at boot or the chip starts in the wrong mode.

The NodeMCU board wraps the chip with a USB-to-serial converter, a 3.3 V regulator, two buttons and breadboard headers. You program it from the Arduino IDE after installing the ESP8266 board package; setup() and loop() behave as on an Arduino (see Chapter 4.2).

The radio is why you choose it. The board joins a Wi-Fi network, receives an IP address and can publish a reading straight to a server. Between readings it enters deep sleep: processor and radio off, only a timer running, drawing about 20 µA. That is the chip figure. A stock NodeMCU still draws about a milliamp in sleep because its regulator and USB-to-serial chip keep working.

BeagleBone Black: Linux with fast I/O

The BeagleBone Black is a single-board computer in the same class as the Raspberry Pi (see Chapter 4.3). It boots Linux from 4 GB of on-board flash and has an Ethernet socket, a USB host port and a microSD slot.

Its difference is the header. Two rows of 46 pins give about 65 general-purpose input/output lines, plus analogue inputs, PWM outputs and I2C, SPI and UART buses. All are 3.3 V, and each pin sources only a few milliamps, so a relay or motor needs a driver.

The unusual part is the two PRUs, Programmable Real-time Units. Each is a small 32-bit core at 200 MHz with its own memory, outside the reach of the Linux scheduler. A PRU can hold a pin at an exact rate while Linux is busy with files and network traffic. That is what real-time I/O means here: the timing does not depend on the operating system.

Power comes from a 5 V barrel jack or USB, and the board draws a few hundred milliamps. That rules it out as a battery node and suits it to fixed installations driving many pins with exact timing.

pcDuino: Arduino headers, Linux inside

pcDuino is a family of boards built round one idea: run Linux and still accept the shields people already own. The headers are laid out and labelled like an Arduino Uno, so a shield plugs straight in with no wiring.

Inside is an ARM system-on-chip from Allwinner with around 1 GB of RAM, running a full Linux distribution. Control code is written in C or Python on Linux, not as an Arduino sketch. The header pins are wired to that system-on-chip.

Two cautions. The header shape promises mechanical fit, not electrical fit: the pins are 3.3 V and weak, so a 5 V shield can damage the board. And the pin numbers in the vendor library are the vendor's own, so Arduino pin 13 is not automatically the same physical pin.

The gain is one board instead of two: camera, network, storage and physical pins on one Linux machine, with no USB link between a Pi and an Arduino. Some syllabi also list the Cubieboard in this group, another Allwinner-based Linux board, but its GPIO comes out on pin headers rather than an Uno-layout shield socket.

Choosing between them: five checks

Five checks settle most choices. Work down the list and stop at the first board that passes all five.

  1. Logic voltage: match the sensors. A 5 V sensor on a 3.3 V board needs a divider or a level shifter (see Chapter 4.5).
  2. Operating system: no OS means one loop and no files; Linux means Python, files and a network stack, but timing jitter.
  3. Wireless: is Wi-Fi built in, or must you buy a module?
  4. Pins: count GPIO, analogue inputs and buses now, before the design grows.
  5. Power: a battery node wants microamps in sleep; a mains-fed board can draw hundreds of milliamps.

4.7 Designing a simple IoT system

A simple IoT system turns a physical goal into a short loop: a sensor measures, a board decides, an actuator acts, and the board reports. The loop must still work when Wi-Fi or the cloud is down. Home water tanks show the pattern: an ultrasonic sensor measures empty space from the top, the board subtracts that from tank height, a relay starts a pump at a low level, and an MQTT dashboard shows the level. The same four steps fit parking, crop moisture, cold-chain and energy meters.

You need: Chapters <a href='#interfacing-sensors-and-actuators-with-boards'>4.5 and <a href='#other-boards-esp8266-beaglebone-pcduino'>4.6, MQTT basics from Unit 3, and the cloud overview in Unit 5.

From goal to threshold

The design starts with one measurable goal, not a board. For a home tank, the goal is: keep water between 30 cm and 90 cm, and show the level on a phone. Write each limit with its unit and the exact operator. A start rule of ≤ 30 cm and a stop rule of ≥ 90 cm are different from a start rule of < 30 cm and a stop rule of > 90 cm: at exactly 30 cm the first starts the pump and the second does not.

Choose a board after the goal. A Wi-Fi ESP8266 is enough for one ultrasonic sensor, one relay and an MQTT publish; a Raspberry Pi is better if you also need a camera or local logging (<a href='#other-boards-esp8266-beaglebone-pcduino'>4.6). Mount the ultrasonic sensor at the tank top, facing down. It measures distance d to the water surface, not water depth. Define H as tank height in cm and d as that empty distance in cm. Then h = H − d, where h is water height in cm.

h = H − d V = h × A

h is water height in cm; H is tank height in cm; d is the distance from the top sensor to the water surface in cm; V is volume in cm³; A is base area in cm².

With base area A, volume V = h × A. Keep units consistent: 1 m² = 10 000 cm², and 1 L = 1000 cm³. Measure A from the inside of the tank. A square tank of side s has A = s²; a rectangular tank has A = length × breadth.

Local loop, radio and report

Write the local control loop first, with the radio off. Read the sensor every few seconds; convert echo time to distance; compute h; reject impossible readings; apply the rule; drive the relay, an electrically operated switch. The pump must run on the local rule even when Wi-Fi or the cloud is down.

  1. Sense: trigger the ultrasonic sensor and read the echo; store d in cm.
  2. Convert: h = H − d; if h < 0 or h > H, mark the reading invalid.
  3. Decide: start pump when h ≤ 30 cm; stop pump when h ≥ 90 cm.
  4. Act: switch the relay; keep the relay off while the reading is invalid.
  5. Report: publish h, d and relay state to an MQTT topic such as home/tank/level every 60 s.

Hysteresis means two thresholds, not one. A single rule at 30 cm would switch the relay on and off as the water surface ripples. The 30 cm start and 90 cm stop band prevents that chatter. The cloud side can use MQTT, a publish-subscribe protocol, or HTTP, the request-reply protocol of the web. MQTT publishes to a topic and a dashboard subscribes; HTTP posts to an endpoint and waits for a reply. MQTT suits small, frequent readings on one topic. HTTP suits occasional updates where the device posts to an endpoint and waits for the reply. The dashboard shows level in cm, litres and pump state.

Power and enclosure are part of the design. Use a regulated 5 V supply for the ESP8266; power the relay module from its specified supply. Use an opto-isolated relay board and keep the 230 V mains wiring in a closed box, wired by a qualified person. Add a watchdog timer, which reboots a stuck board. The safe fallback is simple: local control continues, the relay goes off on invalid sensor data, and readings wait in a small buffer for the next connection.

Test the boundary and the failure

Test with a ruler, not only with water. Hold the sensor at known distances and check h and V. Test d = H (empty tank), d = 0 (full tank), and d just above and below each threshold. The 30 cm boundary is the examiner’s favourite: with the rule ≤ 30 cm the pump starts at exactly 30 cm; with < 30 cm it does not. Write the operator you tested.

Failures to test: Wi-Fi off, cloud unreachable, sensor unplugged, board reboot, and power cut. After power returns, keep the pump off until a valid reading arrives. Do not expose the relay to the public internet; use a device password and an encrypted connection. Unit 5 covers cloud platforms and security design; here, keep secrets out of source code and give each device its own credentials. Log every threshold event with a timestamp; this turns a demo into a maintainable system.

Worked example

Question. A home water tank is 100 cm tall and has base area 1 m². An ultrasonic sensor at the top reads distance d = 70 cm to the water surface. Find the water height and the volume in litres. The pump starts at level ≤ 30 cm and stops at level ≥ 90 cm. State the pump action at d = 70 cm. Explain why the operator matters at the boundary.

  1. Tank height H = 100 cm; sensor distance d = 70 cm.
  2. Water height h = H − d = 100 cm − 70 cm = 30 cm.
  3. Base area A = 1 m² = 1 × 10 000 cm² = 10 000 cm².
  4. Volume V = h × A = 30 cm × 10 000 cm² = 300 000 cm³.
  5. Convert: V = 300 000 cm³ ÷ 1000 cm³/L = 300 L.
  6. Rule: start when h ≤ 30 cm. Here h = 30 cm, so the condition is true and the pump starts.
  7. The stop rule h ≥ 90 cm is false. If the start rule were h < 30 cm, the pump would not start at this exact reading, so the operator must match the design.

Exam traps

  • The sensor measures the air gap from the top, not the water depth. Subtract d from tank height H.
  • Do not convert m² to cm² by dividing; multiply by 10 000.
  • A single threshold makes the relay chatter; use hysteresis with separate start and stop levels.
  • At the boundary, ≤ and < give different actions; copy the design operator exactly.
  • The relay switches 230 V mains; keep low-voltage control and mains wiring isolated and enclosed.

Check yourself

Remember Name the four steps of the simple IoT loop in this chapter. 2 marks

Sense, decide, act, report. Convert (h = H − d) is a calculation inside the decide step, not a fifth step.

Understand Why does the pump use a 30 cm start and 90 cm stop instead of a single 30 cm threshold? 3 marks

Hysteresis prevents relay chatter and rapid pump cycling when the water surface ripples near the threshold.

Apply A tank is 120 cm tall with base area 0.8 m². The sensor reads d = 45 cm. Find h and V in litres. 4 marks

h = 120 − 45 = 75 cm. A = 0.8 × 10 000 = 8000 cm². V = 75 × 8000 = 600 000 cm³ = 600 L.

Analyze Wi-Fi fails for two hours. What should the ESP8266 do about the pump and about reporting? 4 marks

Keep local sense-decide-act running; keep the relay rule active. Buffer or drop readings and send the latest state when the link returns; do not stop the pump only because the cloud is unreachable.

Apply Tank height 100 cm, rule starts at ≤ 25 cm and stops at ≥ 85 cm. The sensor reads d = 75 cm. What is h and what does the pump do? 2 marks

h = 100 − 75 = 25 cm; 25 ≤ 25 is true, so the pump starts.

Understand Why publish every 60 s instead of on every loop pass? 3 marks

The dashboard does not need every sample; fewer messages save power and bandwidth and reduce cloud load. The local loop still runs fast.

Takeaways

  1. An Arduino is a microcontroller board: one sketch, no operating system, and pins you drive directly.
  2. Every Arduino sketch is just setup() run once and loop() run forever, so timing depends on how fast loop() finishes.
  3. The Raspberry Pi is a full computer — it boots Linux from a microSD card, which means files, networking and multiple programs, but no guaranteed microsecond timing.
  4. Raspberry Pi GPIO pins are 3.3 V only; a 5 V sensor output must be divided or level-shifted before it touches a pin.
  5. Python on the Pi turns hardware control into short readable code: import a library, create an object, then read or set it.
  6. A sensor converts a physical quantity into a voltage or a digital word; the board converts that into a decision, and the actuator makes the physical change.
  7. A Raspberry Pi cannot read an analog voltage without an external ADC; an Arduino can, on pins A0–A5.
  8. Choose ESP8266 when you need only Wi-Fi and a couple of pins, BeagleBone when you need Linux plus many fast I/O pins, and pcDuino when you need Linux plus Arduino shields.
  9. A simple IoT system is a loop of sense, decide, act and report, and the act step must still work when the network is down.

Exam question bank

Long answers in this unit are judged on board-level detail — pin voltages, resolution, library names, sample code — and on a clear justification of which board suits a stated application.

Remember and understand

Understand Compare an Arduino board with a Raspberry Pi under four headings: what program runs on it, presence of an operating system, GPIO logic voltage, and typical use in an IoT node. 10 marks

Arduino: microcontroller, one sketch in flash, setup() then loop(), no OS, 5 V logic on Uno, best for real-time sensing and control; Raspberry Pi: single-board computer, boots Linux from microSD, runs many processes, 3.3 V GPIO, best for gateway, camera, dashboard, cloud upload; Arduino handles microsecond timing and analog inputs; Pi does not guarantee timing and has no ADC; Consequence for design: Pi for compute and connectivity, Arduino for hard real-time or analog work, often used together.

Understand Explain the structure of an Arduino sketch. Show the roles of setup() and loop(), and write a sketch that blinks an LED on pin 13 once per second. 10 marks

Remember List the main hardware features of a Raspberry Pi board and explain what the 40-pin GPIO header provides. 8 marks

SoC with ARM CPU and GPU, RAM, microSD slot for the OS, USB ports, HDMI, Ethernet or Wi-Fi, power input; GPIO header: digital input/output pins at 3.3 V, plus 5 V, 3.3 V and ground pins, UART, I2C and SPI pins; Pins are 3.3 V; 5 V on a signal pin can damage the SoC; No analog input pins on the header; an external ADC is needed for analog sensors; Linux boots from microSD, so the same board can run Python scripts, a web server and an MQTT client.

Understand Describe the ESP8266 module: its hardware, how it connects to a network, and the two ways it is normally used in an IoT product. 8 marks

Apply Write a Python program for a Raspberry Pi that reads a push button on GPIO 2 and switches an LED on GPIO 17, using GPIO Zero. Explain each line. 12 marks

Apply An LM35 temperature sensor is connected to pin A0 of an Arduino Uno with a 5 V reference. Write the code and derive the temperature in degrees Celsius from the ADC value. 12 marks

LM35 gives 10 mV per degree Celsius, linear, no calibration; int raw = analogRead(A0) returns 0 to 1023 for 0 to 5 V; Voltage = raw × 5.0 ÷ 1024; temperature = voltage × 100; One line version: t = raw * 500.0 / 1024.0; Print with Serial.println(t); keep loop() slow with delay(1000); Mention resolution limit: 4.9 mV per step, about 0.49 °C.

Four pins: VCC 5 V, GND, Trig input, Echo output; Send a 10 microsecond HIGH pulse to Trig; Echo goes HIGH for the round-trip time; measure with pulseIn(); Distance = time × speed of sound ÷ 2 = time × 343 m/s ÷ 2, or time × 0.0343 ÷ 2 in centimetres with time in microseconds; Add a timeout to pulseIn so a missing echo does not hang the sketch; Range and accuracy limits, and effect of temperature on the speed of sound.

Apply For each of these three requirements, name the most suitable board and justify it: (a) a battery-run soil moisture node reporting over Wi-Fi, (b) a factory panel needing Linux plus ten fast digital inputs, (c) a lab project reusing an existing Arduino shield but needing a full desktop. 12 marks

(a) ESP8266: built-in Wi-Fi, low cost, low power, one ADC pin for the moisture probe, deep sleep between readings; Justify rejection of a Pi: higher power draw, boot time, overkill for one sensor; (b) BeagleBone Black: Linux plus two 46-pin headers, many pins, and real-time co-processors for fast I/O; Justify rejection of an Arduino: no OS, no file system, no networking stack without extra hardware; (c) pcDuino: Linux application processor with Arduino-style headers so the shield plugs in directly; State the trade-off principle: pins and timing on one side, OS and connectivity on the other.

Analyze and evaluate

Analyze Design a simple IoT system that monitors an overhead water tank, switches the pump off at full level, and alerts the owner on a phone. Cover sensing, decision, action and reporting, and say what happens when the internet link fails. 14 marks

Sense: level sensor (float switch or ultrasonic) read by the board at a fixed interval; Decide: a threshold rule — pump off when level is at full, on when below a low mark, with a dead band to stop chattering; Act: relay or contactor driving the pump; the relay must be rated for motor current; Report: MQTT publish of level and pump state to a broker; phone app or SMS alert; Fallback: when the broker is unreachable, the local rule still switches the pump; buffer readings and resend later; a fail-safe timer stops the pump after a maximum run time; Monitoring: log readings with timestamps, and raise an alert if the level stops changing while the pump runs.

Evaluate A 5 V sensor output is connected directly to a Raspberry Pi GPIO pin. Analyse the fault and evaluate two ways of fixing it, with the resistor values. 14 marks

The Pi pin is 3.3 V logic; a steady 5 V drives current into the protection diode and can destroy the SoC; Fix 1: resistive divider, Vout = Vin × R2 ÷ (R1 + R2); with R1 = 1 kΩ and R2 = 2 kΩ, 5 V gives about 3.3 V; Trade-offs: divider draws continuous current, slows edges, and adds resistor tolerance error; Fix 2: level shifter or a dedicated logic-level converter; bidirectional, faster, but costs more; A series resistor alone is not a fix; it limits current but the voltage is still too high; Check the same issue on Arduino side in reverse: a 3.3 V sensor into a 5 V Arduino usually reads HIGH correctly, but confirm the threshold.

Evaluate Compare two designs for a home automation controller: (a) an ESP8266 node per room with a cloud broker, (b) a Raspberry Pi running a local broker with ESP8266 nodes. Judge them on latency, cost, privacy and behaviour during a network or power failure. 16 marks

Latency: local broker answers in milliseconds; cloud adds round-trip delay; Cost: many ESP8266 nodes are cheap; a Pi adds cost but serves many nodes; Privacy: local broker keeps data in the house; cloud design sends usage patterns to a third party; Failure: with the cloud design a lost link means no control unless local fallback rules are flashed into the node; a local Pi keeps working over Wi-Fi but dies on a power cut unless on a UPS; Scalability and maintenance: cloud gives remote access and updates from anywhere; local gives control only inside the home network unless port-forwarding or a VPN is used; Recommended design: local broker with node-level fallback rules, cloud used only for remote access and long-term storage.

Glossary

Actuator
A device that converts an electrical command into physical action, such as a motor, relay, solenoid or buzzer.
Analog sensor
A sensor whose output is a continuously varying voltage proportional to the measured quantity.
Bootloader
A small program on the board that accepts a new sketch over USB and starts the stored program.
Breadboard
A reusable plastic board with connected holes for building circuits without soldering.
Broker
The server in a publish-subscribe system that receives messages on topics and forwards them to subscribers.
Compile
To translate source code into machine instructions for the target board before it can run.
Debounce
Ignoring the brief contact chatter of a mechanical switch, in hardware with a capacitor or in software with a short delay.
Deep sleep
A low-power mode where a module shuts most circuits off and wakes on a timer or event, used to extend battery life.
Digital sensor
A sensor that outputs a discrete value, either one bit or a coded word over a bus such as I2C.
Edge processing
Doing part of the decision on the local device instead of sending all raw data to the cloud.
Fail-safe
A design in which a loss of power, signal or network leaves the system in a safe state, such as the pump switching off.
Firmware
The program stored in a device's non-volatile memory that runs when it powers up.
GPIO
General-Purpose Input/Output; a digital pin whose direction and level the program controls.
I2C
A two-wire bus (clock and data) that lets one board talk to many addressed sensor chips.
Logic level
The voltage that represents digital 1 on a pin; 5 V on most Arduino boards and 3.3 V on a Raspberry Pi.
Microcontroller
A single chip containing a processor, memory and input/output peripherals, designed to run one fixed program repeatedly.
MQTT
A lightweight publish-subscribe messaging protocol where devices send topics to a broker and subscribers receive them.
Node
One device in an IoT system that senses, acts and communicates with the rest of the system.
Relay
An electrically operated switch that lets a low-voltage board control a high-voltage or high-current load.
Single-board computer
A complete computer on one printed circuit board with processor, memory, storage slot and input/output ports.
SPI
A four-wire synchronous serial bus used for fast links to displays, memory and some sensors.
Transistor driver
A transistor, often with a base resistor and a flyback diode, used between a board pin and a load that needs more current.
