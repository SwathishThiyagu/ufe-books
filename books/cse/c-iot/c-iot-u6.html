6.1 Home automation and smart homes

A smart home turns sensor events into rules that switch actuators and inform the owner. A PIR sensor notices motion, a door sensor notices an open door, a hub holds the rule, and a relay switches the lamp. The same event can travel to a cloud service so a phone app alerts you while you are at the office. People use this for lighting, fans, door and camera alerts, and to cut electricity bills. This chapter builds the whole path — sensor, hub, local rule, cloud rule, actuator — and then costs the energy it uses.

You need: Unit 2 on sensors and actuators, Unit 3 on MQTT publish-subscribe, Unit 4 on Raspberry Pi and GPIO interfacing, and Unit 5 on cloud platforms and IoT security.

Sensors, actuators and the home hub

A smart home is one building run as a small IoT system. It has the same four parts as any deployment: sensors that produce events, actuators that change the physical world, a hub that decides, and an app that shows the owner what happened.

A PIR (passive infrared) sensor detects the body heat of a moving person and gives a digital output: 1 for motion, 0 for none. A door sensor is a reed switch that closes when a magnet fixed to the door is beside it, so it reports open or closed. A temperature sensor reports room temperature in °C. A light sensor (an LDR or photodiode, often read through an ADC) reports illuminance in lux; the hub uses it to decide whether a room is dark enough to need the lamp.

  • Relay module: an electrically operated switch that turns a mains lamp or fan on and off.
  • Smart plug: a relay inside a plug body, controlled over Wi-Fi.
  • Siren or buzzer: the local alarm for a door or smoke event.
  • Smart lock: an actuator that opens the door after a rule passes.

The hub is an always-on small computer — a Raspberry Pi, or a dedicated ZigBee gateway — that joins the sensors and holds the rules. A rule is an if-then line: IF motion = 1 AND lux < 200 THEN relay ON for 5 minutes. Here lux is light level; the lamp is needed only when the room is dark.

  1. The sensor sends its value to the hub over Wi-Fi, ZigBee or a wired bus.
  2. The hub evaluates every rule that mentions that sensor.
  3. A rule that fires sends a command to an actuator.
  4. The hub logs the event and, if a cloud rule exists, publishes it.
  5. The actuator changes state and the app shows the new state.

Local rules and cloud rules

A rule can run on the hub (local rule) or on a cloud service (cloud rule). Local rules keep working when the internet link drops. Cloud rules exist so you can act from outside the home and keep history in one place.

A power cut is not the same as an internet outage. A hub and router on mains die with the supply, so local rules stop too. Put both on a small UPS or battery and the local rules survive; the cloud rules return only when the fibre or 4G link comes back.

Door and camera alerts use both paths. The hub sounds the siren immediately, and the cloud sends the phone notification with a short camera clip. Changing default passwords and keeping cameras on a separate network are covered in Unit 5.

A Raspberry Pi as a web-enabled home device

A Raspberry Pi is a constrained web-enabled device: it runs Linux, has GPIO pins, and can serve a small page to a phone on the same Wi-Fi. Reading a sensor and answering one HTTP request fit in a short program. On real hardware the first two lines read a GPIO pin and a light sensor through an ADC (see Unit 4). The version below uses fixed values so it runs anywhere.

Python program.

pir = 1                  # 1 = motion seen, 0 = no motion
lux = 120                # light level in lux
THRESHOLD = 200          # lamp is needed below this lux

lamp = "ON" if (pir == 1 and lux < THRESHOLD) else "OFF"
page = "<h1>Home hub</h1><p>motion " + str(pir) + "</p><p>lamp " + lamp + "</p>"

print("HTTP/1.1 200 OK")
print("Content-Type: text/html")
print()
print(page)

Output

HTTP/1.1 200 OK
Content-Type: text/html

<h1>Home hub</h1><p>motion 1</p><p>lamp ON</p>

The rule sits in one line of Python: motion and darkness together switch the lamp. When a home has twenty devices, the hub publishes events over MQTT instead of polling, and the packet format is in Unit 3.

Standby power and running cost

A large share of a smart home bill is always-on power. Bulbs run a few hours, but the hub and the cameras run all day — nearly half the energy in the example below — so they must be counted for 24 h.

E_day = (Σ Pᵢ × tᵢ) ÷ 1000

E_day is energy per day in kWh; Pᵢ is the power of device i in watts (W); tᵢ is the hours device i runs per day (h); dividing by 1000 converts watt-hours (Wh) to kilowatt-hours (kWh).

Cost = E_day × number of days × tariff, where the tariff is in rupees per kWh. Convert to kWh before multiplying by the tariff, never after.

Worked example

Question. A home has 10 smart bulbs rated 9 W used 5 h a day, one hub rated 3 W running all day, and 2 cameras rated 5 W running all day. Electricity costs ₹7.50 per kWh. Find the monthly energy use and cost for 30 days.

  1. One bulb: 9 W × 5 h = 45 Wh/day. Ten bulbs: 10 × 45 = 450 Wh/day.
  2. Hub: 3 W × 24 h = 72 Wh/day.
  3. One camera: 5 W × 24 h = 120 Wh/day. Two cameras: 240 Wh/day.
  4. Total per day: 450 + 72 + 240 = 762 Wh/day.
  5. Convert once: 762 ÷ 1000 = 0.762 kWh/day.
  6. For 30 days: 0.762 × 30 = 22.86 kWh.
  7. Cost: 22.86 kWh × ₹7.50/kWh = ₹171.45.

Answer. The home uses 22.86 kWh in 30 days and pays ₹171.45.

Exam traps

  • Standby power is not zero. The hub and cameras here use 312 of the 762 Wh/day, about 41 % of the bill, from two small devices running 24 h.
  • Unit slip: 762 Wh is 0.762 kWh, not 762 kWh. Divide by 1000 once, before multiplying by the tariff.
  • 'Local control survives a power cut' is true only if the hub and router sit on a UPS or battery. On mains they stop with the supply.
  • An internet outage and a power cut are different failures. A powered hub keeps local rules alive with no internet; cloud rules do not.
  • Watch the examiner's wording: a 5 W camera used 24 h is 120 Wh, but two cameras are 240 Wh, not 120 Wh.

Apply A door sensor rule sends a phone alert through the cloud. The home internet fails at the same moment. What should the hub do locally? 4 marks

The hub must still evaluate the door rule locally and sound the siren or buzzer, and store the event for upload later. The phone alert is retried when the link returns.

6.2 Smart cities and smart parking

A smart city puts many small sensing deployments under one city authority: traffic, street lights, waste bins, water lines and parking. Each deployment is small. The value comes from sharing one network, one cloud and one dashboard. Smart parking is the clearest complete example. A sensor in each bay reports whether a car is there, a low-power wide-area network carries that one piece of news, a cloud service keeps the slot map, and a driver app sells the slot and takes payment. This chapter follows that chain and shows how to pick the radio link for each part.

You need: Unit 3 on LPWAN, NB-IoT and MQTT, and Unit 5 on IoT cloud services.

What a smart city actually deploys

A smart city uses sensors, networks and data to run city services with fewer manual checks and less waste. It is not one system. It is a portfolio of small deployments under one authority, sharing a network and a cloud platform.

  • Mobility. Inductive loops and radar counters at junctions count vehicles; the count feeds signal timing. Bus position comes from a GPS unit on the bus. Number-plate cameras need a high data rate and are a separate, wired or 4G service.
  • Street lighting. A photocell and a motion sensor per pole dim the lamp when the road is empty. The saving appears on the electricity bill, which is why this is often the first project funded.
  • Waste. An ultrasonic sensor in each bin reports fill level, so trucks collect only the bins that are full.
  • Water. Flow and pressure sensors at valves find leaks and measure supply; see 6.5 for the water chain in detail.

The shared part matters in exams. One low-power wide-area network can carry parking, bins and meters together. One cloud platform holds the dashboards, billing and alarms. Adding a service then means adding devices and a message topic, not building a new network.

Smart parking: from slot sensor to payment

Sensing. An in-ground sensor is a magnetometer buried in the bay. A car changes the local magnetic field by a few microtesla, and the node reports occupied or free. It needs no wiring and lasts years on one battery, but the road must be opened to replace it. An overhead sensor, ultrasonic or camera on a pole, is easy to service but needs power and a cable.

Message. The sensor sends a state change, plus a heartbeat every 5 minutes, about 60 bytes. It is not a video and not a continuous stream.

Radio. NB-IoT fits this job. A 180 kHz carrier gives tens of kbit/s uplink, far more than 60 bytes needs. The link budget is roughly 20 dB better than GSM, so a sensor under a car in a basement still reaches the cell. Power saving mode and extended discontinuous reception let the modem sleep for minutes, with the network holding any message. The price is latency of seconds to tens of seconds.

Deployment. In a baseline deployment the operator adds an NB-IoT carrier to base stations it already owns, in-band or guard-band with LTE, or standalone in refarmed GSM spectrum, and upgrades the core for cellular IoT. The city buys SIMs and an access point name; it does not buy base stations. Because you cannot dig up 5000 sensors to test them, coverage and capacity are first simulated with system-level or ray-tracing tools, then checked with a pilot of a few hundred sensors.

Path. The sensor publishes to a topic such as parking/slot/17 with a retained payload, and the cloud subscribes over MQTT. The cloud updates the slot map and offers it to the driver app, which reserves, takes a UPI payment, and holds the slot for a short time. The barrier opens on the number plate or a QR code; its camera sits on 4G or Ethernet, never on NB-IoT.

One car park uses several links at once. Pick the slowest link that carries the required data rate, then check power and cost.

Worked example

Question. A car park has 200 slots. Each slot sensor sends one 60-byte message every 5 minutes. Find the average uplink bit rate and the data volume per day.

  1. Messages per slot per hour = 60 min ÷ 5 min = 12.
  2. Total messages per hour = 200 slots × 12 = 2400 messages/hour.
  3. Convert to per second: 2400 ÷ 3600 s = 0.6667 messages/s.
  4. Bits per message = 60 B × 8 bit/B = 480 bit.
  5. Average uplink rate = 0.6667 messages/s × 480 bit = 320 bit/s.
  6. Daily messages = 2400 messages/hour × 24 h = 57,600 messages.
  7. Daily volume = 57,600 × 60 B = 3,456,000 B = 3.456 MB.
  8. Check: 320 bit/s × 86,400 s ÷ 8 = 3,456,000 B, which agrees.

Answer. The average uplink rate is 320 bit/s, and the park sends 3.456 MB per day (about 0.6667 messages per second).

Exam traps

  • NB-IoT is for small, infrequent uplink. Do not put the barrier camera's live video on it; that camera needs 4G or Ethernet.
  • Convert messages per hour to messages per second by dividing by 3600 before finding a bit rate. Forgetting the 3600 gives an answer 3600 times too large.
  • Bytes and bits are different. A 60-byte message is 480 bits; state your unit at every step.
  • NB-IoT latency is seconds, so the barrier cannot wait for the cloud to open the gate. The gate controller decides locally and reports afterwards.
  • A smart city is not one giant sensor network. It is many deployments sharing a platform, and each has its own data rate and power budget.

Remember What physical quantity does an in-ground parking slot sensor measure? 2 marks

The local magnetic field. The metal mass of a car changes it by a few microtesla, which the magnetometer reads as occupied.

Understand Why is NB-IoT preferred over Wi-Fi for in-ground slot sensors? 3 marks

The sensor is buried, so it needs deep indoor and underground penetration, and the link budget of NB-IoT is about 20 dB better than GSM. It runs for years on one cell using power saving mode. It sends tiny payloads, which matches its tens of kbit/s uplink. No site cabling or access point is needed; the operator owns the network.

Apply A designer must connect a slot sensor, a barrier number-plate camera and a gate controller inside one car park. Choose a link for each and justify it in one line. 4 marks

Slot sensor: NB-IoT, because the rate needed is a few hundred bit/s and the device must last years on a battery. Camera: 4G or Ethernet, because live video needs megabits and mains power is available. Gate controller: wired or Wi-Fi, because opening the barrier needs millisecond response on site.

Understand What is the role of MQTT in the parking system? 3 marks

MQTT is the publish-subscribe message path. The sensor or its gateway publishes to a topic such as parking/slot/17 with a retained state, and the parking cloud subscribes. The two sides do not need to know each other's address, and the retained message gives a new subscriber the latest state immediately.

Analyze A vendor proposes sending one frame of video from every slot every 5 minutes over NB-IoT instead of a 60-byte status message. Analyse the proposal. 5 marks

A compressed frame is tens of kB, roughly a thousand times the 60-byte message, so the uplink rate and the daily volume rise by that factor and the data plan cost follows. NB-IoT uplink is tens of kbit/s, so each frame takes many seconds, and latency already runs to seconds. Radio-on time per message grows, so the multi-year battery life collapses and buried sensors must be dug up and replaced. The correct design is a cheap sensor on NB-IoT, with a camera on 4G doing local processing only where an image is genuinely needed.

Analyze Why are NB-IoT networks simulated before a city-wide parking rollout? 5 marks

You cannot install thousands of buried sensors to test coverage. Simulation with system-level or ray-tracing tools predicts path loss in basements and street canyons, estimates how many sensors one cell carries, and shows where repeaters or extra carriers are needed. It turns a rollout into a design problem, and a small pilot then confirms the prediction.

Remember Name three smart city services other than parking that use the same shared network. 2 marks

Any three of: street lighting control, waste-bin fill level, water flow and leak monitoring, vehicle counting at junctions, bus tracking, electricity metering.

Not for the exam. Real city platforms increasingly separate the device layer from the service layer, so a parking operator can rent connectivity and cloud from the city instead of building both. 6.3 Industrial IoT and Industry 4.0

Industrial IoT (IIoT) connects machines, sensors and business software so that production data drives control, maintenance and planning. It exists because a factory already produces the data: motor current, temperature, cycle counts, alarms. IIoT moves that data from a machine to a plant screen and to an order system. Industry 4.0 is the wider idea of cyber-physical production built on this flow. You meet it in automotive plants, food processing, textile mills and power stations. The plant metric is OEE, overall equipment effectiveness.

You need: Unit 2 sensors and sensor nodes; Unit 3 industrial protocols; Unit 5 data analytics.

The automation hierarchy

Industry 4.0 is cyber-physical production: computation and the physical process are linked so that data changes what the plant does. A plant is organised in levels. At Level 0, sensors measure the process and actuators act on it. A sensor converts a physical quantity, such as temperature or vibration, into a signal. An actuator converts a command into motion, heat or flow.

Level 1 is the PLC (programmable logic controller). It reads inputs and writes outputs in a fixed cycle, often every few milliseconds, and it owns real-time control. Example: stop a conveyor when a guard door opens. Level 2 is SCADA (supervisory control and data acquisition). It shows the plant, logs alarms and lets an operator change a setpoint. Level 3 is MES (manufacturing execution system): it turns an order into a production schedule, assigns batches and records which material went into which part. Level 4 is ERP (enterprise resource planning): orders, purchase, stock and finance.

Data moves up as summaries; targets move down. OPC-UA is an integration name for exchanging plant data; see Unit 3 for protocol details. A sensor node on a motor may sample vibration locally and send one feature per minute to the next level. Some syllabi call this industrial automation.

Industry 4.0 building blocks

Four building blocks appear in most Industry 4.0 designs. The closed-loop idea is in Chapter 6.4.

  • A digital twin is a software model of a machine or process, kept fed with live data. It lets an engineer test a schedule or estimate wear without stopping the line.
  • A smart factory uses connected assets, edge computing and analytics to adapt production.
  • Predictive maintenance uses condition data to estimate when a failure is likely and schedules service before it.
  • Big data and visualization store long histories from many machines and show OEE, energy per part and alarm frequency on dashboards.

Edge computing processes data near the machine. Cloud computing stores years of data and compares plants. A sensor node on a bearing may send raw vibration to an edge gateway. The gateway computes RMS (root mean square) vibration and sends one reading per minute to the cloud. Edge gives low latency and keeps the line running during a wide area network outage; cloud gives long storage and cross-plant models. Remote monitoring of a distant pump is Chapter 6.5.

Security is a lifecycle. Keep an inventory of devices, set a firmware update policy, and use role-based access control so an operator can change a setpoint but a contractor cannot. Unit 5 owns the mechanisms.

OEE: the plant metric

OEE (overall equipment effectiveness) is the plant metric for how much good production a scheduled machine delivers. Define the terms in minutes and parts.

Planned production time is the time the machine is scheduled to make parts. Downtime is scheduled time lost to breakdown, setup or no operator. Run time = planned production time − downtime. Total count is all parts made, including rejects. Good count is parts that meet quality. Ideal cycle time is the fastest stable time per part.

OEE = A × P × Q, where A = Run time ÷ Planned production time, P = (Ideal cycle time × Total count) ÷ Run time, Q = Good count ÷ Total count

A is availability; P is performance; Q is quality; OEE is overall equipment effectiveness. Run time = planned production time − downtime. Ideal cycle time is the fastest stable time per part. All three factors are dimensionless; multiply by 100 for percent.

A machine can be available for the whole shift and still have low OEE if it runs slowly or makes rejects. Performance uses total count. Quality then removes rejects. Convert ideal cycle time to the same unit as run time, usually minutes.

Worked example

Question. A machine is scheduled for 480 min. It is down for 48 min. It makes 800 parts; 760 are good. Ideal cycle time is 30 s per part. Find availability, performance, quality and OEE.

  1. Planned production time = 480 min; downtime = 48 min.
  2. Run time = 480 − 48 = 432 min.
  3. Availability A = 432 ÷ 480 = 0.900 = 90.0%.
  4. Ideal cycle time = 30 s = 30 ÷ 60 = 0.5 min per part.
  5. Performance P = (0.5 min/part × 800 parts) ÷ 432 min = 400 ÷ 432 = 0.9259 = 92.6%.
  6. Quality Q = 760 ÷ 800 = 0.950 = 95.0%.
  7. OEE = A × P × Q = 0.900 × 0.9259 × 0.950 = 0.7917 = 79.2%.

Exam traps

  • Performance uses total count, not good count; quality applies the good count. Mixing them double-counts rejects.
  • Convert ideal cycle time to the same unit as run time. 30 s is 0.5 min, not 30 min.
  • OEE is not the same as availability. A machine can be available for 100% of scheduled time and still have low OEE from slow cycles or rejects.
  • Downtime is subtracted from planned production time, not from 24 hours. Use the schedule you are measuring.
  • SCADA is supervision, not real-time control; the PLC closes the control loop. Do not credit SCADA with millisecond actuation.

6.4 Cyber-physical systems and their applications

A cyber-physical system (CPS) joins computation with a physical process in a closed feedback loop. Sensors measure the process, a controller computes a command, and actuators change the process. The physical result depends on timing: the sampling period, actuator delay and sensor error all enter the loop. CPS ideas appear in engine ignition, anti-lock brakes, adaptive cruise control, drones, mobile robots and camera dollies. This chapter shows the loop and the errors that matter. Some syllabi call these mechatronics and IoT case studies.

You need: Unit 2 sensors and actuators; Unit 4 interfacing; and Unit 3 industrial protocols for plant examples (see <a href='#industrial-iot-and-industry-4-0'>Industrial IoT).

The closed loop and its timing

A CPS repeats four actions: measure the physical state, compute a command, drive an actuator, and let the process change. The next measurement closes the loop. A car brake, a robot wheel and a drone rotor are all physical processes here. The controller is a computer, but the result is physical. Timing is part of correctness: a command that arrives late is a wrong command.

fs = 1 / Ts

fs is the sampling frequency in hertz (Hz); Ts is the sampling period in seconds (s).

Sensor error is measured value minus true value. Actuator delay is the time from the command to the physical effect. These are separate faults. Slow sampling misses a fast change; actuator delay makes the correction late; sensor error makes the correction wrong.

A CPS is not just a sensor on the internet. The controller must act inside the process time scale. If the plant is a brake, the loop time is milliseconds; if it is a water tank, it may be seconds.

Ignition, brakes and cruise control

Electronic ignition uses a crank-angle sensor to time the spark. The engine control unit samples crank position, computes ignition advance and fires the coil. At high engine speed the same angle arrives sooner, so the sampling period must shrink. Coil and injector delays shift the spark; crank-sensor error shifts it too, causing knock or a misfire.

ABS is a clear CPS. A tone ring with fixed teeth turns with each wheel. The sensor produces pulses; the controller computes wheel speed and wheel slip. It then commands brake-pressure valves. The sampling period must be short enough to catch a locking wheel, the valve delay limits how fast pressure can fall, and tooth or gap error adds speed error.

EBD uses the same ABS sensors to split braking force between axles. Adaptive cruise control measures the gap to the car ahead and commands throttle or brakes. In both, the loop is closed, so the values above set the physical result.

Robots, drones and camera dollies

A drone is a CPS with fast inner loops. An inertial measurement unit (IMU) measures rotation rate and acceleration. A controller compares the desired attitude with the measured attitude and sets motor speeds. Electronic speed controllers drive the motors and propellers. Only a few syllabi teach the drone control equations; know the blocks: estimate, compare, command, actuate, measure again. IMU sampling must be fast, motor and propeller delay must be small, and vibration causes sensor error.

An autonomous robot adds a vision system. A camera produces frames; vision code finds an obstacle or a lane; a planner sets wheel speeds. The camera sampling period is longer than the wheel-control period. The robot must handle that delay. Lighting changes and lens dirt are sensor errors; wheel slip and motor lag are actuator delays.

A robotic camera dolly is a small CPS used in video. An encoder measures wheel position; a controller drives the motor to follow a planned move. Smooth motion needs short sampling and low actuator delay. Encoder error or a late motor command makes the move jerky, and a jerky dolly blurs the shot.

Exam traps

  • Do not put km/h into v = ωr. Convert to m/s first: 60 km/h = 16.67 m/s.
  • The 48 teeth are per wheel revolution, not per second of travel. Multiply rev/s by 48, not speed by 48.
  • Sampling period Ts and sampling frequency fs are inverses. A 10 ms period is 100 Hz, not 10 Hz.
  • Sensor error is a wrong measurement. Actuator delay is a late action. One does not fix the other.
  • A CPS needs a closed loop. A sensor that only sends data to a dashboard is monitoring, not closed-loop control.

Remember Define sampling period and actuator delay in a CPS. 2 marks

Sampling period Ts is the time between two measurements in seconds. Actuator delay is the time from a command to its physical effect.

Understand Why can a CPS with correct code still give a wrong physical result? 3 marks

Code can be correct but late. Slow sampling misses a fast change, actuator delay makes a correction late, and sensor error makes a correction wrong. The closed loop turns these into physical error.

Apply A wheel has radius 0.25 m and a 36-tooth tone ring. The car moves at 36 km/h. Find the ABS pulse frequency. 4 marks

Analyze A drone is stable at low speed but oscillates at high speed. Use sampling and actuator delay to explain. 5 marks

At high speed the physical state changes faster. The same IMU sampling period and motor delay become a larger fraction of the loop time. The correction arrives late, so the controller overshoots and oscillates. A faster loop or lower delay is needed.

Understand Give one sensor error and one actuator delay in ABS. 3 marks

A dirty or damaged tone ring gives a wrong wheel-speed pulse: sensor error. A brake valve that takes time to release pressure is actuator delay.

Apply A camera dolly has a 1000-count-per-revolution encoder on a wheel of radius 0.05 m. It must move at 0.2 m/s. Find the encoder count rate. 5 marks

Wheel circumference = 2π × 0.05 = 0.3142 m. Wheel rev/s = 0.2 ÷ 0.3142 = 0.6366. Count rate = 0.6366 × 1000 = 636.6 counts/s.

Analyze Why is ABS a cyber-physical system and not just a sensor system? 4 marks

ABS measures wheel speed, computes slip and commands brake pressure in a loop. The actuator changes the wheel, and the next measurement depends on that change. The physical braking result depends on loop timing.

6.5 Remote monitoring, e-health and water management

Remote monitoring puts a sensor, a gateway and a cloud service between a distant process and the person who acts on it. The sensor measures, the gateway collects and forwards, the cloud stores and compares each reading against limits, and only a crossed limit becomes an alert on a phone or a dashboard. It exists because nobody can sit beside every tank and every patient. It is used for home health wearables, hospital-at-home kits, and municipal or campus water supply, where a pump house and a hundred tanks are watched from one screen.

You need: sensors from Unit 2, MQTT topics from Unit 3, a Raspberry Pi or ESP8266 gateway from Unit 4, a cloud dashboard from Unit 5, and the rule-and-actuator pattern of Chapter 6.1.

The chain from a distant process to a person

Remote monitoring has one job: keep a person informed about a process they cannot stand next to, and disturb them only when something must be done. Four parts do the work. The sensing point is a sensor plus a small board. The gateway holds the network link and a short buffer. The cloud stores readings, runs threshold rules and serves a dashboard. The human is the operator, the nurse or the engineer who acts.

R = f × n × b

R is the raw data rate in bit/s, f is samples per second, n is the number of channels, and b is bits per sample. A 3-axis accelerometer at 50 Hz with 16-bit samples gives R = 50 × 3 × 16 = 2400 bit/s.

T = C ÷ I_avg

T is battery life in hours, C is cell capacity in mAh, and I_avg is average current in mA. A node drawing 12 mA from a 2000 mAh cell lasts 2000 ÷ 12 ≈ 167 h, about 7 days.

  1. The sensor turns the physical quantity into an electrical signal; the board turns it into a number.
  2. The board stamps the reading with a time and keeps it in a small buffer.
  3. Every upload interval the gateway publishes the buffer over MQTT to a topic.
  4. The cloud stores the reading, evaluates the threshold rule, and refreshes the dashboard.
  5. If the rule fires, the cloud sends an alert and repeats it until someone acknowledges it.

The radio, not the sensor, decides the battery. A 100-byte packet is 800 bits; one per minute averages 800 ÷ 60 ≈ 13 bit/s, against 2400 bit/s for the raw stream. Send summaries and keep raw samples on the device.

The upload interval also sets how late an alarm can be. A reading every minute means a limit crossed at 10:02.10 is caught by 10:03 at the latest. Shorten the interval, or check the limit on the device, when minutes matter.

E-health: wearables, ECG, SpO2 and falls

A health wearable measures a few quantities and sends them, or features of them, through a phone to the cloud. SpO2 is the percentage of haemoglobin carrying oxygen, found from the ratio of red to infrared light absorbed through the finger; a healthy resting value at sea level is roughly 95-100%. The band reports a number, and only a clinician turns that number into a diagnosis.

An ECG lead is sampled at 250 samples per second with 12-bit samples, so 250 × 12 = 3000 bit/s. Bluetooth Low Energy carries that easily, but a radio left on flattens a small cell. So the band filters the signal and uploads features, or a ten-second strip when an event fires.

Fall detection uses the acceleration vector magnitude a = √(ax² + ay² + az²), where ax, ay and az are the three axis readings in m/s². At rest a ≈ 9.81 m/s². A fall shows a free-fall dip near 0, then a spike, then stillness. One rule: spike above 2.5 g, then 10 s without motion → ask the wearer to cancel within 30 s → if nobody cancels, escalate.

  • Level 1: the band vibrates.
  • Level 2: phone notification.
  • Level 3: SMS to a family contact.
  • Level 4: call to the clinician on duty.

Each level has a timeout, so silence pushes the alert one step up. This ladder is the part that makes remote monitoring safe: an alert that nobody sees is the same as no alert. A 200 mAh patch drawing 0.5 mA average lasts 200 ÷ 0.5 = 400 h, about 16 days.

Water management: tank level, pump control, leak detection

A centralized water management system puts many tanks, pumps and flow meters under one dashboard: a housing society, a campus, or a ward of a city. Each tank has a level sensor at the rim. An ultrasonic sensor measures the distance d from the sensor down to the water surface, so the water depth is h = H − d, where H is the tank's internal height. The level in percent is 100 × h ÷ H.

Pump control uses two thresholds, not one. Start the pump when the level falls to 20% and stop it at 90%. The gap is hysteresis: it stops the pump switching on and off every few seconds, a fault called short cycling that damages the motor.

Leak detection uses the minimum night flow. Between 2 am and 4 am genuine demand is small, so a clean zone reads close to zero. If a meter still shows more than 5 L/min on three nights, that zone has a leak. A second method compares volume in with volume billed: a gap above 10% over a week points to a leak somewhere in the zone.

The water-level control lab has a small tank, a level sensor, a relay, a pump and a Raspberry Pi. Log every reading to the cloud, watch the dashboard, pour water in by hand, and confirm the pump stops at 90%. This controller adds dead-band logic to a simple level reading:

Python program.

level = 35          # water level as percent of tank depth
low, high = 20, 90  # start below low, stop above high

if level <= low:
    print("pump ON")
elif level >= high:
    print("pump OFF")
else:
    print("hold")

hold

Worked example

Question. A rooftop tank is 2 m long, 1.5 m wide and 1.2 m deep. A 0.5 HP pump fills it at 20 L/min, and the tank is empty at 6:00 am. Find the tank volume in m³ and in litres, the fill time in minutes and hours, the pump's electrical input power in W and kW, the electrical energy used in kWh, and the cost at ₹7 per kWh.

  1. Volume V = length × width × depth = 2 m × 1.5 m × 1.2 m = 3.6 m³.
  2. 1 m³ is 1000 L, so capacity = 3.6 × 1000 = 3600 L.
  3. Fill time = capacity ÷ flow = 3600 L ÷ 20 L/min = 180 min.
  4. In hours: 180 ÷ 60 = 3 h.
  5. Electrical input power P = 0.5 HP × 746 W/HP = 373 W.
  6. In kW: 373 ÷ 1000 = 0.373 kW.
  7. Energy E = P × t = 0.373 kW × 3 h = 1.119 kWh.
  8. Cost = 1.119 kWh × ₹7/kWh = ₹7.833, that is ₹7.83.

Answer. The tank holds 3.6 m³ (3600 L), fills in 180 min (3 h), uses 1.119 kWh and costs ₹7.83.

Exam traps

  • 1 HP is 746 W, not 1000 W. Using 1000 W turns 373 W into 500 W and inflates the cost.
  • 1 m³ is 1000 L, not 100 L. The litre figure shifts by a factor of 10 and so does the fill time.
  • The worked example uses electrical input power. The hydraulic power the pump delivers to the water is a different, smaller number; mixing the two is the commonest slip.
  • A faster sampling rate does not make the alarm quicker if the threshold is checked only at upload. The check interval, not the sample rate, sets the delay.
  • Level percent is 100 × h ÷ H with h the water depth. Using the sensor-to-surface distance d instead of h inverts the reading, so a full tank shows 0%.

Understand Why does a tank controller use two level thresholds instead of one? 3 marks

Two thresholds give hysteresis. With a single threshold the pump starts and stops repeatedly around that level (short cycling), which wears the motor. Starting at 20% and stopping at 90% keeps each run long.

Analyze A cloud rule checks SpO2 only when a reading arrives, every 5 minutes. A patient's SpO2 falls at 10:02 and recovers at 10:04. What happens, and how do you fix it? 6 marks

The 10:05 reading is normal, so the rule never fires and the event is lost. Fix it by running the threshold on the device at the full sample rate and publishing an event the moment the limit is crossed, or by shortening the upload interval so a two-minute dip cannot fall between readings.

Analyze An ECG band streams 250 samples/s at 12 bits continuously over Bluetooth Low Energy. Explain why such bands usually send features or short strips instead. 5 marks

The raw rate is 3000 bit/s, which BLE carries fine, but a radio on continuously drains the small cell in days or less. The raw stream is also noisy and useless without filtering. So the band filters on the device, sends features or a ten-second strip on an event, and the battery lasts weeks.

Understand Why is leak detection done on night flow rather than on daytime flow? 3 marks

At night genuine demand is close to zero, so almost all measured flow is loss. In the daytime real use hides the leak, so a normal-looking reading can still contain a large loss.

6.6 Domain-specific IoT applications and case studies

The same four blocks — sensor, network, cloud and actuator — appear in a farm, shop, truck, substation and river. What changes is the constraint: a soil probe must run two years on one cell; a cold-chain box must alarm within minutes; a meter must bill a household. Domain-specific IoT fits sensor, radio, interval and power to that constraint. Judge a case study by how it meets the constraint and how it fails, not by sensor count.

You need: Prerequisites: sensors and actuators (Unit 2), protocol families with payload, range and duty-cycle limits (Unit 3), and cloud analytics with security as a deployment constraint (Unit 5). Protocol detail is not repeated.

Same blocks, different constraints

Every deployment has four blocks: a sensor that measures, a network that carries the reading, a cloud service that stores and compares, and an actuator or person who acts. The blocks do not change from farm to substation. The constraint that chooses each block does.

A soil probe may sit 2 km from the gateway and must run two years on one cell. A cold-chain box on a fish truck must alarm within 5 minutes of crossing 4 °C. A meter reports every 15 minutes for billing and outage detection. A fitness band must last a day and reach a phone within 10 m.

Read each case backwards. Interval and message size give the data rate; rate and range give the radio; radio and battery give the power budget.

R = (N × S × 8) ÷ T

R is the mean bit rate in bit/s; N is the number of messages in the period; S is the message size in bytes; 8 converts bytes to bits; T is the period in seconds.

Agriculture, retail and logistics

In agriculture a capacitive soil-moisture probe reports volumetric water content in percent. The node sends every 10 minutes through a field gateway to the cloud. If the value stays below the crop threshold for several readings, the cloud opens a valve. Need-based irrigation saves water and pump current. The same chain is described for water systems in remote monitoring and water management.

A portable wireless interactive sensor is a handheld unit with its own radio. It joins the field network on demand, shows the reading and can switch a valve from where the farmer stands. It covers patches with no fixed node.

In retail, a shelf weight mat or infrared beam detects a gap and creates a refill task. A chiller logger alarms above its limit. An RFID reader counts cartons at the stockroom door, and electronic shelf labels update prices from the same cloud.

Logistics repeats this at larger scale: GPS plus cellular modem in each truck, RFID scans at hubs, geofence alarms when a truck leaves its route, and a door sensor for unexpected opening. Parcel scans give the customer the same event the depot sees.

Energy, environment, wearables and vehicles

In energy, a smart meter reports every 15 minutes and sends a last-gasp message when supply is lost, so the utility learns of an outage before the first phone call. At peak load a load-control actuator sheds water heaters and air conditioners for 30 minutes, and the customer is credited for the energy not consumed (the shed kWh). This closed loop is covered in industrial IoT, applied to a grid instead of a plant.

Environment nodes use optical PM2.5, gas carbon-monoxide and ultrasonic water-level sensors. Calibration drift is the main failure: a cheap gas sensor walks away over months, so the node is co-located with a reference or swapped on schedule. Air-quality nodes are dense because pollution varies street by street, unlike a smart city parking bay whose state is local and simple.

Wearables measure optical heart rate, blood oxygen and steps. The band uses Bluetooth Low Energy to a phone, and the phone forwards to the cloud. Battery and skin contact limit it; consent is the deployment constraint. Vehicles combine GPS, OBD-II and an accelerometer for harsh braking. Live tracking needs 4G, a daily summary fits NB-IoT, and a truck that leaves terrestrial coverage needs satellite backhaul.

Judging a case study in seven questions

A case-study answer that lists sensors earns few marks. Run seven questions.

  1. State the problem and decision: irrigate, refill or shed load?
  2. List each sensor, what it measures, range and accuracy.
  3. Choose the network from range, payload and duty cycle.
  4. Compute data rate from message size and interval.
  5. Compute power budget: average current × time, compared with cell mAh.
  6. Estimate cost per node and per year in rupees, including SIM or gateway share.
  7. Name the most likely failure mode and how the system detects it.

Many sites over months produce more data than a person can read, so rules and dashboards matter. A dashboard compares 40 farms on one axis; an alarm fires only when a value crosses a limit. Big-data work stores raw series, computes summaries per site per day and ranks sites by water saved.

Security is a constraint. A node must authenticate before its reading is accepted. Meter aggregation must hide one household's daily curve while giving the utility the transformer total. A wearable needs informed consent and a delete path.

Worked example

Question. A farm deploys 500 soil-moisture sensor nodes. Each node sends one message of 80 bytes every 10 minutes. (a) How many messages does one node send per day? (b) How many messages does the farm send per day? (c) What is the daily data volume in bytes and in MB, taking 1 MB = 10⁶ bytes? (d) What mean bit rate does this need? (e) In EU868/IN865 at the common data rates the LoRaWAN application payload limit is 51 bytes; it depends on region and data rate. How many frames does one reading need, and how many frames per day does the farm send?

  1. One day is 24 × 60 = 1440 minutes. Messages per node per day = 1440 ÷ 10 = 144.
  2. Farm total per day = 500 nodes × 144 messages = 72,000 messages.
  3. Daily data = 72,000 × 80 bytes = 5,760,000 bytes. In MB: 5,760,000 ÷ 1,000,000 = 5.76 MB per day.
  4. Bits per day = 5,760,000 × 8 = 46,080,000 bit. One day = 86,400 s. Mean rate R = 46,080,000 ÷ 86,400 = 533.33 bit/s, about 0.53 kbit/s.
  5. In EU868/IN865 at the common data rates the maximum application payload is 51 bytes; it depends on region and data rate. Each 80-byte reading must be split: 80 ÷ 51 = 1.57, so ⌈1.57⌉ = 2 frames per reading.
  6. Frames per day = 2 × 72,000 = 144,000 frames.

Answer. 144 messages per node per day; 72,000 messages, 5,760,000 bytes (5.76 MB) and a mean rate of 533.33 bit/s for the farm; and 2 frames per reading, that is 144,000 frames per day, because at these settings 80 bytes exceeds the 51-byte payload limit.

Exam traps

  • Sizing a link from the number of sensors alone. Use message size × interval to get bit/s, then check range and duty cycle.
  • Reading a payload limit as a frame size. In EU868/IN865 at common data rates the 51-byte LoRaWAN limit is the application payload; headers and MAC commands sit outside it. Other regions and data rates allow larger payloads.
  • Mixing MB and MiB. 5,760,000 bytes is 5.76 MB in base 10 but about 5.49 MiB in base 2. State the base you used.
  • Treating a fitness band as a medical device. A band sampling at 1 sample/s is not an ECG at 250 samples/s; the rate and the power budget differ by orders of magnitude.
  • Describing a case study as a sensor list. Marks come from the constraint, the rate calculation and the named failure mode.

vibration, temperature and current sensors; edge feature extraction reduces data; cloud trend and threshold alarm; maintenance ticket in the plant system; baseline and false-alarm handling.

Apply Design an agriculture IoT case study with soil-moisture sensing, valve control and farmer alerts. State how you would judge whether it is a good deployment. 12 marks

soil-moisture nodes and valve controller; gateway and farmer SMS or app alert; schedule, manual override and dry-run protection; power, water pressure and connectivity constraints; judge by water saved, reliability and cost.

Analyze and evaluate

Analyze Analyze how sampling delay, network jitter and sensor error in a cyber-physical control loop change the physical result. Use a robot arm or drone example. 13 marks

sampling delay shifts the measured state; jitter makes control intervals uneven; actuator lag adds overshoot or oscillation; sensor error and calibration offset the result; mitigate with edge control, timestamps and watchdog.

Evaluate Evaluate a smart-city deployment that adds street lighting, waste-bin sensing and smart parking. Discuss shared network, power, privacy, maintenance and cost per service. 14 marks

each service has different message rate and power need; shared network can reduce cost but raises failure impact; cameras and payment create privacy duties; maintenance and interoperability decide uptime; judge by reliability and cost per service, not device count.

Evaluate Evaluate security and privacy risks in a remote e-health monitoring service. Propose safeguards across device, gateway, cloud and clinician alerting. 14 marks

health data is sensitive and needs consent; device theft and insecure gateway are entry points; use encryption, authentication and data minimisation; alarm acknowledgement and clinician escalation; audit logs and privacy rules.

Evaluate Compare an agriculture irrigation case study with a logistics cold-chain case study. Judge both by constraints such as power, connectivity, cost, environment and user action. 13 marks

agriculture constraints: power, water, rural link; cold chain constraints: temperature, motion, handover; compare sensors, network, cloud rule and user; compare failure modes and cost; judge by constraints and outcomes, not sensor list.

Glossary

Actuator
A device that converts a control signal into physical action, such as a relay, motor or valve.
Alarm threshold
A value limit that triggers an alert when a measurement crosses it.
Cold chain
A temperature-controlled supply chain monitored from production to retail.
Cyber-physical system
A system where computation controls a physical process through a closed loop of sensing and actuation.
Digital twin
A software model of a physical asset kept current by data and used for monitoring or prediction.
Edge computing
Processing data near the sensors or machine instead of sending everything to the cloud.
Feedback loop
A control cycle in which measured output changes the control action and therefore the output.
Gateway
A device that connects local sensors to a wider network and may run local rules.
IIoT
Industrial Internet of Things: connected industrial machines and systems that share data for control, maintenance and planning.
Industry 4.0
The use of connected data, automation and analytics to make production more flexible and responsive.
Jitter
Variation in delay between successive messages or samples.
Latency
The time taken for data or a control action to travel from source to destination.
LoRaWAN
An open LPWAN protocol that uses LoRa radio and can be deployed as a private network.
LPWAN
A low-power wide-area network designed for long-range, small, infrequent messages from battery devices.
MQTT
A lightweight publish–subscribe messaging protocol often used between IoT devices and cloud services.
NB-IoT
A narrowband cellular LPWAN standard used on licensed mobile-operator spectrum.
OPC UA
An industrial standard for secure, typed and interoperable data exchange between machines and systems.
Precision agriculture
Farming that uses local data to apply water, fertiliser or pesticide only where it is needed.
Remote monitoring
Sensing a distant process and sending data to a service that informs or alerts a person.
Rule engine
Software that evaluates condition–action rules and triggers actions when conditions are met.
Smart home
A home where sensors, rules and actuators automate lighting, security, comfort or energy use.
Smart meter
A utility meter that records consumption and sends readings or events to the operator.
Smart parking
A parking system that senses bay occupancy, guides drivers and often handles payment.
Telemetry
Measured data sent automatically from a remote site to a monitoring centre.
