3.1 Shared-memory programming with Pthreads and OpenMP

A shared-memory parallel program runs several threads inside one process. Threads read and write the same RAM, so splitting work is cheap: no data is copied and no messages are sent. The price is coordination: two threads updating one variable at the same moment can lose an update. Pthreads (POSIX threads) is the C library that creates, joins and locks threads. OpenMP uses compiler pragmas for the same job with less typing. Multicore laptops, phone chips and cloud servers all use these tools.

You need Unit 1 on shared-memory architecture and the speedup measure S = T₁/T_p, where T₁ is the one-thread time and T_p is the time on p threads (see Unit 1, Foundations).

Threads share one address space

A process is a running program with its own virtual memory. A thread is one execution path inside it. Threads of one process share code, global variables and heap; each thread has its own registers, program counter and stack. Passing data between threads costs nothing, but any thread can overwrite a variable another is reading.

Pthreads is the standard C interface for this. Four calls carry most programs: pthread_create(&tid, NULL, fn, arg) starts function fn with argument arg in a new thread and fills in tid; pthread_join(tid, NULL) waits for that thread to finish; pthread_mutex_lock(&m) and pthread_mutex_unlock(&m) bracket a critical section that only one thread may enter at a time.

A data race happens when two threads touch the same memory location at the same time, at least one writes, and no lock orders the accesses. The result then depends on timing. The statement total += a[i] is three machine steps: load total, add a[i], store total. Two threads can load the old value, both add, and both store, so one addition disappears.

C program.

#include <stdio.h>
#include <pthread.h>

int a[4] = {10, 20, 30, 40};
long total = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

void *add(void *arg) {
    int id = *(int *)arg;
    for (int i = 2 * id; i < 2 * id + 2; i++) {
        pthread_mutex_lock(&m);
        total += a[i];
        pthread_mutex_unlock(&m);
    }
    return NULL;
}

int main(void) {
    pthread_t t[2];
    int id[2] = {0, 1};
    for (int k = 0; k < 2; k++) pthread_create(&t[k], NULL, add, &id[k]);
    for (int k = 0; k < 2; k++) pthread_join(t[k], NULL);
    printf("total = %ld\n", total);
    return 0;
}

Output

total = 100

OpenMP: parallel for, reduction, critical, atomic, barrier

OpenMP (Open Multi-Processing) puts the same idea into compiler directives for C, C++ and Fortran. You mark a loop and the compiler writes the thread creation, private copies and joins. The model is fork-join: one master thread runs serially, reaches a parallel region, forks a team, and joins them at the end.

#pragma omp parallel for splits the iterations of the next for loop among the team. The default schedule is static: the range is cut into contiguous blocks, one per thread. Every variable that exists before the loop is shared unless you say otherwise. private(x) gives each thread an uninitialised copy of x; firstprivate(x) copies the current value in. In C and C++ the loop index of a parallel for is private automatically.

reduction(+:S) is the standard way to sum in parallel. Each thread adds into its own private copy of S, and at the join OpenMP combines the copies with +. Other operators are *, −, min, max, &, |, ^, && and ||. Use #pragma omp critical when a block of statements must run alone, #pragma omp atomic for a single simple update such as x += y, which is cheaper, and #pragma omp barrier when every thread must arrive before any continues.

Schedules, false sharing and correctness

schedule(static) costs nothing at run time and suits loops where every iteration does equal work, such as adding array elements. schedule(dynamic, c) hands out chunks of c iterations to whichever thread is free, so it balances uneven loops, for example a loop over image pixels where some pixels take an extra branch. It pays a small scheduling cost per chunk. guided sits between the two.

False sharing: two threads write different variables that happen to sit in the same 64-byte cache line. There is no data race and the answer is correct, yet the line bounces between cores on every write, so the parallel code can be slower than the serial one. Pad hot per-thread structures to a cache line, or use a reduction.

Two conditions decide whether a loop may be parallelised at all. The iterations must be independent: no iteration reads a value that another iteration writes, no iteration writes a value that another iteration reads, and no two iterations write the same location. Loop-carried dependences in either direction break the parallel for. Every shared update must go through reduction, critical or atomic. If both hold, the loop is correct on any number of threads. Without them, a shared update in a parallel loop is a data race that OpenMP never fixes for you.

Worked example

Question. Write an OpenMP C program that computes S = 1 + 2 + ... + 1,000,000 with 4 threads and a reduction clause. Give S and the partial sum of each thread under the default static schedule. Then explain why a shared variable total updated inside the loop without a critical section can print a wrong value.

C program.

#include <stdio.h>

int main(void) {
    long long S = 0;
    long long i;
    #pragma omp parallel for reduction(+:S) num_threads(4)
    for (i = 1; i <= 1000000; i++) {
        S += i;
    }
    printf("S = %lld\n", S);
    return 0;
}
  1. The loop has 1,000,000 iterations. The num_threads(4) clause fixes the team at 4 threads, and the runtime splits the iterations across them.
  2. The default schedule(static) cuts the loop into 4 contiguous blocks of 1,000,000 / 4 = 250,000 iterations. Thread 0 gets 1..250000, thread 1 gets 250001..500000, thread 2 gets 500001..750000, thread 3 gets 750001..1000000.
  3. Each thread keeps a private copy of S, starting at 0, and adds its own block into it.
  4. Block sums use n(n+1)/2 for a range. Thread 0: 250000 × 250001 / 2 = 31,250,125,000.
  5. Thread 1: 500000 × 500001 / 2 − 31,250,125,000 = 125,000,250,000 − 31,250,125,000 = 93,750,125,000.
  6. Thread 2: 750000 × 750001 / 2 − 125,000,250,000 = 281,250,375,000 − 125,000,250,000 = 156,250,125,000.
  7. Thread 3: 1,000,000 × 1,000,001 / 2 − 281,250,375,000 = 500,000,500,000 − 281,250,375,000 = 218,750,125,000.
  8. The join adds the four private copies: 31,250,125,000 + 93,750,125,000 + 156,250,125,000 + 218,750,125,000 = 500,000,500,000.
  9. Without the reduction, total += i is a load, an add and a store on one shared variable. Two threads can load the same old total and both store their own new value, so additions are lost. The printed total is then smaller than 500,000,500,000 and changes from run to run.

Exam traps

  • A shared variable updated in a parallel loop is not made atomic by the pragma. #pragma omp parallel for splits iterations; it does not lock the body. Missing reduction(+:S) gives a wrong, varying total.
  • private(x) gives an uninitialised copy, not the old value. Use firstprivate(x) to carry the value in, and remember the reduction result is written back to the shared variable only at the join.
  • The loop index of a parallel for is private automatically in C/C++, but any variable declared before the loop stays shared unless you name it in private or declare it inside the loop.
  • False sharing is not a data race. Nothing is logically wrong and the answer is correct, but the program is slow because one cache line is traded between cores.
  • Critical is correct but serialises; putting it inside a loop of a million iterations usually makes the program slower than the serial version. Atomic fits one simple statement only.

3.2 Distributed-memory programming with MPI

MPI is the Message Passing Interface: a library and standard for programs whose processes have separate memories. They cannot read each other’s variables. To cooperate, one process packs data into a message and sends it; another receives it. This is the natural model for a cluster, where each node has its own RAM, and for supercomputers used in weather, crash simulation and train scheduling. This chapter shows the six calls that carry most MPI programs: init, rank, size, send, receive and finalize, then the collectives that replace many hand-written messages.

You need: Unit 1’s distributed-memory model and the message-passing basics in Unit 4; compare with shared-memory programming, where threads share variables.

Separate memories, one communicator

Every MPI program starts with MPI_Init(&argc, &argv) and ends with MPI_Finalize(). Between them the process may call MPI. A communicator is a named group of processes allowed to talk. The default, MPI_COMM_WORLD, contains all processes started by mpirun -np P. P is the number of processes.

Inside a communicator each process has a rank: an integer from 0 to P−1. MPI_Comm_rank(comm, &rank) writes the caller’s rank into rank. MPI_Comm_size(comm, &size) writes the number of processes into size. Rank is an identity, not a priority; rank 0 is usually the root that reads input and prints output.

Each process runs the same program, called SPMD: single program, multiple data. It uses if (rank == 0) ... else ... to take different paths. Variables are private. If rank 0 sets x = 5, rank 1’s x is unchanged unless a message carries the value. This is the key break from Pthreads and OpenMP, where a shared variable is visible to all threads.

Point-to-point: send, receive, tag and deadlock

A point-to-point message has a sender and a receiver. The basic calls are MPI_Send(buf, count, datatype, dest, tag, comm) and MPI_Recv(buf, count, datatype, source, tag, comm, &status). buf is the address of the data; count is how many items; datatype is e.g. MPI_INT or MPI_DOUBLE; dest and source are ranks; tag is an integer label; comm is the communicator. MPI_Recv also needs a status object that records the actual source and tag.

Tags let one process send different kinds of message to the same receiver. A receive with tag 7 will not take a message with tag 8. Source can be MPI_ANY_SOURCE and tag MPI_ANY_TAG, but then read the real values from status.

Both calls are blocking in the usual sense. MPI_Send returns when the send buffer can be reused; for a small message it may copy into an internal buffer and return at once, for a large message it may wait until the matching receive starts. MPI_Recv returns only after the message has arrived and been copied into buf. So a blocking send is not a promise that the receiver has finished using the data.

Deadlock is the common failure. If rank 0 calls MPI_Send to rank 1 and then MPI_Recv from rank 1, while rank 1 calls MPI_Send to rank 0 and then MPI_Recv from rank 0, each send may wait for the other’s receive. No process proceeds. Safe orders: make one side send first and the other receive first, or use non-blocking calls, or MPI_Sendrecv which does both in one call.

Collectives and the root-worker pattern

A collective is one call made by every process in a communicator. The library does the many point-to-point messages for you. All ranks must pass matching arguments for that collective: same root for rooted collectives such as Bcast, Scatter, Gather and Reduce, same count and datatype, and same op for Reduce. Otherwise the program may hang. If one rank skips a collective, the others wait forever.

Root-worker pattern: rank 0 is root. It reads the whole array, scatters chunks, workers compute local results, reduce returns combined result to root, root prints. Worked example

Question. Two MPI processes, ranks 0 and 1, sum A = [1,2,3,4,5,6,7,8] with MPI_Scatter and MPI_Reduce using MPI_SUM. Give the four elements and local sum of each rank, and the final sum at rank 0. Write the key MPI calls.

#include <mpi.h>
#include <stdio.h>

int main(int argc, char **argv) {
    int rank, size, i;
    int A[8] = {1,2,3,4,5,6,7,8};
    int local[4], sum = 0, total = 0;
    int sums[2];

    MPI_Init(&argc, &argv);
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    MPI_Comm_size(MPI_COMM_WORLD, &size);

    MPI_Scatter(A, 4, MPI_INT, local, 4, MPI_INT, 0, MPI_COMM_WORLD);
    for (i = 0; i < 4; i++) sum += local[i];
    MPI_Reduce(&sum, &total, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);
    MPI_Gather(&sum, 1, MPI_INT, sums, 1, MPI_INT, 0, MPI_COMM_WORLD);

    if (rank == 0)
        printf("local sums: %d %d\ntotal: %d\n", sums[0], sums[1], total);

    MPI_Finalize();
    return 0;
}
  1. P = 2 processes and n = 8 integers, so each rank gets count = 8 ÷ 2 = 4 elements.
  2. Rank 0 receives indices 0 to 3: values [1,2,3,4]. Local sum = 1+2+3+4 = 10.
  3. Rank 1 receives indices 4 to 7: values [5,6,7,8]. Local sum = 5+6+7+8 = 26.
  4. MPI_Reduce with MPI_SUM sends both local sums to root rank 0. Root computes 10 + 26 = 36.
  5. For printing, MPI_Gather collects [10,26] at rank 0; the final total is already 36.

Exam traps

  • Processes do not share variables. A global array in the program text is a private copy in each process; only messages or collectives move values.
  • A blocking MPI_Send is not a guarantee of delivery to the receiver's buffer; it only says the send buffer can be reused. Two sends before two receives can deadlock.
  • Ranks start at 0, so P processes have ranks 0 to P−1. Off-by-one errors in root or dest are common.
  • Collectives must be called by all ranks in the communicator, with matching arguments for that collective: same root for rooted collectives, same count and datatype, and same op for Reduce. One missing call hangs the job.
  • MPI_Scatter splits the array; it does not give every rank the whole array. That is MPI_Bcast.

3.3 GPU architecture and the CUDA programming model

A GPU is a many-core device built for data parallelism. It trades the few large cores of a CPU for many small lanes that run the same instruction across data. CUDA is NVIDIA's programming model for this device. Threads are grouped into warps, warps into blocks, and blocks into a grid. This structure lets one launch cover a large array. You meet it in matrix multiplication, image filters and neural-network training, where the same operation repeats over thousands of pixels or weights.

You need: Unit 1 SIMD and data parallelism, and the thread idea from 3.1.

CPU cores and GPU streaming multiprocessors

A CPU core is built to run one instruction stream fast. It has a large cache, branch prediction and out-of-order logic. A server CPU may have 8 to 64 such cores. A GPU uses a different balance. It has many streaming multiprocessors (SMs). Each SM holds many simple CUDA cores, a warp scheduler and registers. One SM can keep hundreds of threads alive. The GPU hides memory latency by switching to another warp while one waits. That is why a GPU is weak on a long serial loop but strong on an array operation.

CUDA calls its execution model SIMT: single instruction, multiple threads. In one warp, the hardware issues one instruction to all active threads at the same time. Each thread still has its own registers and its own threadIdx. This differs from pure SIMD, where one instruction works on a vector of data lanes; SIMT keeps a thread view for the programmer.

A warp is the hardware scheduling unit. In current CUDA a warp has 32 threads. A block is a group of threads that can share shared memory and synchronise. A grid is all blocks from one kernel launch. The figure shows a grid of 2 blocks with 4 threads each.

Host, device and thread indexing

A CUDA program has a host (CPU) and a device (GPU). The host allocates data, copies it, launches a kernel and copies the result back. The device runs the kernel. A kernel is a C or C++ function marked __global__; the host calls it with launch syntax kernel<<<gridDim, blockDim>>>(args). The first number is the blocks in the grid; the second is the threads per block. For example add<<<2, 4>>>(A, B, C) starts 2 blocks of 4 threads, so 8 threads total. Inside the kernel, built-in variables give position: blockIdx.x, blockDim.x and threadIdx.x.

tid = blockIdx.x × blockDim.x + threadIdx.x

tid is the global thread index in the grid; blockIdx.x is the block number along x, from 0; blockDim.x is the number of threads in one block along x; threadIdx.x is the thread number inside its block, from 0.

With one dimension, every thread gets a unique global index. A guard such as if (tid < N) { ... } protects a partly filled last block, where N is the number of elements in the array. The host can query device limits with cudaGetDeviceProperties(&prop, 0). Read prop.name for the GPU model, prop.multiProcessorCount for the number of SMs and prop.maxThreadsPerBlock for the largest legal block. The full kernel file layout is in 3.4.

SIMT execution and warp divergence

All threads in a warp start together. They execute the same instruction. When a branch condition is equal for all 32 threads, the warp takes one path and no lane idles. When threads disagree, the warp is divergent. Hardware runs the taken path with some threads active, then the other path with the rest active. The two paths serialise; the cost is the sum, not the maximum. A loop whose trip count depends on threadIdx.x can also diverge. Code with if (tid % 2 == 0) makes half a warp idle on each side. This is the main trap: a GPU thread is not an independent CPU thread.

Divergence is not an error; it is a cost. For data-parallel code, keep branch conditions uniform across a warp, for example branch on blockIdx.x. Warps in a block can be held at a barrier, and memory scope matters; see 3.5 and 3.6.

Worked example

Question. A CUDA kernel launches 2 blocks of 4 threads. Write the global thread index formula and list the 8 indices. For A[5]=11 and B[5]=3, state which thread computes C[5] and give C[5].

C program.

#include <stdio.h>
int main(void) {
    int A[8] = {0,0,0,0,0,11,0,0};
    int B[8] = {0,0,0,0,0,3,0,0};
    int C[8] = {0};
    int blocks = 2;
    int threads = 4;
    for (int b = 0; b < blocks; b++) {
        for (int t = 0; t < threads; t++) {
            int tid = b * threads + t;
            C[tid] = A[tid] + B[tid];
            printf("block %d thread %d tid %d C=%d\n", b, t, tid, C[tid]);
        }
    }
    printf("C[5]=%d\n", C[5]);
    return 0;
}
  1. Read the launch: gridDim.x = 2 blocks and blockDim.x = 4 threads per block. Total threads = 2 × 4 = 8.
  2. Write the one-dimensional index: tid = blockIdx.x × blockDim.x + threadIdx.x = blockIdx.x × 4 + threadIdx.x.
  3. Block 0 has threadIdx.x = 0,1,2,3, so tid = 0,1,2,3. Block 1 has threadIdx.x = 0,1,2,3, so tid = 4,5,6,7.
  4. Target C[5] uses tid = 5. blockIdx.x = floor(5 ÷ 4) = 1. threadIdx.x = 5 mod 4 = 1. So block 1, thread 1 computes it.
  5. C[5] = A[5] + B[5] = 11 + 3 = 14.

Exam traps

  • A CUDA thread is not a CPU thread. Threads in a warp run the same instruction in lockstep; divergence makes both sides run one after the other.
  • Do not mix block index and thread index. threadIdx.x restarts at 0 in every block; only blockIdx.x*blockDim.x + threadIdx.x is global.
  • A block of 4 threads is not a warp of 4. A warp is 32 threads; a small block is part of one warp, and several small blocks may share an SM.
  • A branch that is uniform across a warp costs nothing extra. A branch on threadIdx.x % 2 inside a warp serialises the two paths.
  • More threads do not always mean more speed; launch overhead, occupancy and memory access pattern set the real limit.

3.4 CUDA program structure: kernels, grids, blocks, threads

A CUDA program has two parts: host code that runs on the CPU and kernels that run on the GPU. A kernel is a function launched over a grid of blocks, and each block holds a fixed number of threads. Every thread computes its own global index from built-in variables, then works on one array element. This structure lets one launch cover thousands of independent data items. It is used in image filters, matrix multiplication, neural-network training and any loop whose iterations do not depend on each other.

You need: the GPU execution model from Chapter 3.3.

Host code and device kernels

A CUDA source file mixes two kinds of code. Host code runs on the CPU. Device code runs on the GPU. A function marked __global__ is a kernel: the host launches it, and many GPU threads run the same body. A function marked __device__ is called only from GPU code. A function marked __host__ is ordinary CPU code, which is the default. Kernels must return void.

The launch syntax is kernel<<<grid, block>>>(arguments). The first slot gives grid dimensions, the second gives block dimensions. For a 1D launch of 2 blocks with 4 threads each, write add<<<2, 4>>>(dA, dB, dC). The host first allocates device arrays and copies input data. Then it launches the kernel. Then it copies the result back. The memory copies are covered in Chapter 3.6.

nvcc, the NVIDIA CUDA compiler, compiles the file. It splits host code for the CPU compiler and device code for the GPU. A typical command is nvcc add.cu -o add. The host code cannot read a device pointer directly; device memory is a separate address space. The pointer arguments passed to a kernel must point to device memory. The kernel itself does not allocate global arrays; the host does that before launch.

Grid, block and thread indices

CUDA gives each thread four built-in variables. gridDim.x is the number of blocks in the grid along x. blockDim.x is the number of threads in one block along x. blockIdx.x is the block number, from 0 to gridDim.x − 1. threadIdx.x is the thread number inside its block, from 0 to blockDim.x − 1. The fields .x, .y and .z allow 1D, 2D or 3D layouts.

i = blockIdx.x × blockDim.x + threadIdx.x

i is the global array index; blockIdx.x is the block number; blockDim.x is the number of threads per block; threadIdx.x is the thread number inside its block.

With blockDim.x = 4, block 0 gives i = 0,1,2,3 and block 1 gives i = 4,5,6,7. Every thread gets a different i, so threads do not collide. For 2D data such as an image of width W, use column = blockIdx.x × blockDim.x + threadIdx.x and row = blockIdx.y × blockDim.y + threadIdx.y. The flat index is i = row × W + column. This row-major order matches a C array stored row by row. A launch of dim3 grid(2,3) and dim3 block(16,16) therefore has 2 × 3 = 6 blocks and 16 × 16 = 256 threads per block.

Bounds checks and two common patterns

A launch often rounds the block count up. If N = 10 and blockDim.x = 4, you need ceil(10/4) = 3 blocks, which gives 12 threads. Threads with i = 10 and i = 11 have no array element. Guard every access with if (i < N) { ... }. Without this check, the extra threads read or write past the array. The write may corrupt another variable, or the read may return garbage.

The map pattern gives each thread one output element: C[i] = A[i] + B[i]. The kernel body is short, and the grid supplies all parallelism. A grid-stride loop handles arrays larger than one launch: for (int i = blockIdx.x*blockDim.x + threadIdx.x; i < N; i += blockDim.x*gridDim.x) { ... }. Each thread processes several elements with the same index formula.

The reduce pattern combines many values into one. A simple version has each thread load one element, then threads in a block combine partial results. The final result may need one more pass over per-block partials. Shared memory makes the in-block part faster; that memory space is described in Chapter 3.5. Bounds checks remain necessary in both patterns whenever N is not an exact multiple of the block size.

3.5 GPU memory hierarchy: global, shared and constant memory

A CUDA kernel sees several memory spaces. A register belongs to one thread. Shared memory belongs to one block. Global and constant memory belong to the whole grid. They differ in speed, size and who can access them. The hierarchy exists because fast memory is small and close to the arithmetic units, while large memory is slow and off-chip. Every serious GPU kernel uses it: matrix multiplication tiles a matrix in shared memory, and an ML kernel keeps filter weights in constant memory so every thread reads the same value cheaply.

You need: Chapter 3.3 for warps and blocks, and Chapter 3.4 for grid and block dimensions.

Scope: who can see a variable

A CUDA memory space has a scope and a location. Scope is which threads can see a variable. Location is on-chip or off-chip. On-chip memory is fast and small; off-chip memory is slow and large. Registers are per-thread. Shared memory is per-block. Global and constant memory are per-grid.

  • Registers: per-thread, on-chip, fastest. The compiler places scalar variables here. A thread cannot read another thread's register.
  • Local memory: per-thread, but physically in global memory. It holds spills and large private arrays. It is cached.
  • Shared memory: per-block, on-chip, programmer-managed. Declare it with __shared__. Each block gets its own copy.
  • Global memory: per-grid, off-chip DRAM, largest. All threads can read and write it.
  • Constant memory: per-grid, read-only from device code, cached. Declare it with __constant__. The host writes it before launch.

A CUDA programmer chooses a space for each array, not just a data type.

Shared memory and __syncthreads

Shared memory is a scratchpad inside a block. A declaration such as __shared__ float tile[16][16]; is visible to every thread in the block. Block 0 and block 1 each get a separate tile.

  1. Each thread loads one or more elements from global memory into the shared tile.
  2. Call __syncthreads() so every load is visible.
  3. Threads read the tile, compute, and write results.
  4. Call __syncthreads() again before reusing the tile.

__syncthreads() is a block-wide barrier. Every thread in the block must reach it; no thread passes until all have arrived. It does not synchronise different blocks.

Shared memory uses banks, typically 32 banks of 4 bytes. A warp of 32 threads can service one 4-byte word per bank per cycle. If two threads in a warp request different words in the same bank, the hardware serialises them: a bank conflict. A stride of 32 floats maps every thread to bank 0, a 32-way conflict. Padding a row to 17 floats changes the stride and removes the conflict.

bank = (byte_address ÷ 4) mod 32

bank is the shared-memory bank number; byte_address is the address of the 4-byte word in bytes; 32 is the number of banks on typical NVIDIA GPUs.

Tiling reused data and constant-memory broadcast

Tiling is the main use of shared memory. If a block reads the same global value many times, load it once into shared memory, synchronise, then reuse it. In matrix multiplication, each block loads one tile of A and one tile of B, so arithmetic reads on-chip shared memory instead of slow global memory.

In a convolution kernel, a block may need the same filter values for every output pixel. Put the filter in constant memory. Constant memory is small, read-only and cached. When all threads of a warp read the same constant address, the hardware broadcasts one value. That matches filter weights: one weight, many threads.

Declare constant memory outside the kernel: __constant__ float filter[256];. The host copies values with cudaMemcpyToSymbol before launch. If threads read different addresses, the constant cache serialises them. Large tables with random per-thread indices belong in global memory.

Choose by reuse and access pattern: shared for per-block reuse, constant for grid-wide read-only broadcast, global for large read-write data. Host-device copy costs are covered in Chapter 3.6.

3.6 Host-device memory transfers and data locality

In CUDA, the CPU host and the GPU device have separate memories. Every array the kernel needs must cross the bus, and every result must come back. Those copies cost time, often more than the kernel itself. Real speed therefore comes from moving data once, keeping it on the device across iterations, and arranging device accesses so neighbouring threads read neighbouring addresses. cudaMalloc, cudaMemcpy and cudaFree set the pattern; pinned memory and streams hide copy time; coalescing, tiling and arithmetic intensity decide whether the GPU is fed or starved.

You need: Chapter 3.4 for the host/kernel split and Chapter 3.5 for global and shared memory.

Allocate, copy, free

The host uses malloc; the device uses cudaMalloc. A device pointer is an address in GPU memory, and host code must not dereference it. Allocate with cudaMalloc(&d_a, N * sizeof(float)); d_a is a float*, N is the number of elements, and sizeof(float) is 4 bytes on standard CUDA platforms.

Copy with cudaMemcpy(d_a, h_a, bytes, cudaMemcpyHostToDevice) and copy back with cudaMemcpy(h_a, d_a, bytes, cudaMemcpyDeviceToHost). Release with cudaFree(d_a). Plain cudaMemcpy is synchronous: the host call returns after the copy finishes.

Tcopy = B ÷ BWbus

Tcopy is copy time in seconds; B is bytes moved; BWbus is effective bus bandwidth in bytes per second. Multiply by 1000 for milliseconds.

A 4 MB copy at 10 GB/s takes 4×106 ÷ 10×109 = 0.0004 s = 0.4 ms. That is larger than many small kernels. A chain of small synchronous copies also leaves the GPU idle while the host waits.

  1. Allocate host memory and fill it.
  2. Allocate device memory with cudaMalloc.
  3. Copy inputs host-to-device (H2D).
  4. Launch the kernel.
  5. Copy results device-to-host (D2H).
  6. Free device memory with cudaFree.

Pinned memory and streams

Ordinary malloc memory is pageable. The driver may copy through a hidden staging buffer, so cudaMemcpyAsync cannot safely overlap it. Pinned memory is locked in physical RAM. Allocate with cudaHostAlloc(&h_a, bytes, cudaHostAllocDefault) or cudaMallocHost; free with cudaFreeHost. Pinned memory gives faster copies but takes RAM the OS cannot page out.

A stream is an ordered queue of device work. Operations in one stream run in issue order: H2D, kernel, D2H. Different streams can overlap if the GPU has copy engines. Split the array into chunks and use several streams to pipeline the copy of chunk k+1 with the kernel of chunk k.

Asynchronous calls return at once. Use cudaMemcpyAsync(d_a, h_a, bytes, cudaMemcpyHostToDevice, stream) and cudaDeviceSynchronize() before reading results or stopping a timer. Overlap helps only when there is enough independent work; a single small kernel still waits for its input.

Coalescing, tiling and arithmetic intensity

Global memory is fastest when a warp's 32 threads touch one contiguous block. If thread t reads a[base + t], the hardware combines the 32 loads into a few 128-byte transactions. If threads read with stride 32, each load lands in a different segment and bandwidth is wasted. In CUDA the index blockIdx.x * blockDim.x + threadIdx.x gives coalesced access for a one-dimensional array.

Tiling, also called blocking, copies a small tile into shared memory, synchronises, then reuses it. In matrix multiplication C = A × B, each block loads one tile of A and one of B, and each element is used blockDim times from shared memory instead of global memory. This is spatial locality: neighbours are used together. It is also temporal locality: the same value is reused.

Arithmetic intensity I = F ÷ B, where F is floating-point operations and B is bytes moved between global memory and the processor, or between host and device. Low I means memory-bound: adding cores does not help. High I means compute-bound. Copies outside the kernel count in B, so a kernel that does ten operations per float has I = 10 ÷ 4 = 2.5 FLOP/byte, while a tiled matrix multiply that reuses a tile reaches far more.

For repeated ML training, keep weights, gradients and the dataset on the device. Copy one minibatch H2D, run many kernels, and copy only final weights or metrics D2H. Copying the model every layer turns a compute problem into a bus problem.

3.7 OpenCL device architecture and programming

OpenCL is a portable framework for running one program on CPUs, GPUs, and other accelerators. A host program finds available devices, prepares a kernel, and launches it over an NDRange. The NDRange is divided into work-groups, and each work-group contains work-items. Each work-item runs the same kernel on its own data. Phones, laptops, and FPGA boards use OpenCL when the same code must use whichever device is present.

You need Chapters 3.3 to 3.6: GPU SIMT execution, CUDA grids and blocks, the memory hierarchy, and host-device transfers.

Platform, NDRange and work-groups

OpenCL has a platform model and an execution model. The host is the CPU program that controls everything. An OpenCL device is a processor that runs kernels: a GPU, a CPU, or an accelerator. A platform is the vendor runtime that exposes devices. A device contains compute units; each compute unit contains processing elements that execute work-items.

A kernel is a function written in OpenCL C and compiled for the device. The host launches it over an NDRange, a one-, two-, or three-dimensional index space. The global size is the total number of work-items. The NDRange is cut into work-groups; the local size is the number of work-items in one work-group.

A work-item is one parallel instance of the kernel. Each work-item has a global id in the NDRange and a local id inside its work-group. A work-group is a set of work-items that can share local memory and synchronise at a barrier. In the usual one-dimensional case, global size must be a multiple of local size: global size 8 and local size 4 give 2 work-groups, each with 4 work-items.

global id = group id × local size + local id

For a one-dimensional NDRange, group id = global id ÷ local size (integer division) and local id = global id mod local size. Local size is the number of work-items per work-group.

Memory spaces and host steps

OpenCL defines four memory spaces. Global memory is visible to all work-items and is read/write; the host allocates it and copies data in and out. Constant memory is read-only for kernels and cached for repeated reads. Local memory is shared by the work-items of one work-group and is faster than global memory. Private memory belongs to one work-item, like registers and a private stack. A local array is not shared across work-groups.

The host follows a fixed sequence. First query platforms and choose a device. Second create a context, which holds devices and memory objects, and a command queue, which orders work for one device. Third create a program from kernel source and build it for the device. Fourth create buffers, copy inputs, enqueue the kernel with global and local sizes, wait, and read the output buffer. Enqueue is asynchronous, so the host must wait on an event or call finish before reading results. This transfer cost is the same issue as in Chapter 3.6.

Reading ids and comparing with CUDA

Inside a kernel, get_global_id(0) returns the global id, get_local_id(0) returns the id inside the group, and get_group_id(0) returns the group number. Use the global id for array indexing and the local id for a local-memory slot. Mixing them makes two work-items write the same local slot or read the wrong global element.

OpenCL terms map closely to CUDA: a work-item is a thread, a work-group is a block, and an NDRange is a grid. The global id matches a global thread index; the local id matches threadIdx. Local memory matches shared memory. The same kernel can therefore be built for a GPU, a CPU, or an FPGA, while CUDA targets NVIDIA devices. Portability has a cost: the runtime build step and device queries add host code, and performance still depends on memory access patterns.

Worked example

Question. A one-dimensional OpenCL NDRange has global size 8 and local size 4. (a) State the number of work-groups. (b) State the global id of the last work-item. (c) For A = [1,2,3,4,5,6,7,8] and B = [10,10,10,10,10,10,10,10], the kernel computes C[i] = A[i] + B[i] using zero-based global id i. Compute C[6].

C program.

#include <stdio.h>
int main(void) {
    int N = 8, L = 4;
    int A[8] = {1,2,3,4,5,6,7,8};
    int B[8] = {10,10,10,10,10,10,10,10};
    int C[8];
    int g, lid, i;
    for (g = 0; g < N / L; g++) {
        for (lid = 0; lid < L; lid++) {
            i = g * L + lid;
            C[i] = A[i] + B[i];
        }
    }
    printf("work-groups = %d\n", N / L);
    printf("last global id = %d\n", N - 1);
    printf("C[6] = %d\n", C[6]);
    return 0;
}
  1. Global size N = 8 work-items. Local size L = 4 work-items per group.
  2. Number of work-groups = N ÷ L = 8 ÷ 4 = 2 work-groups.
  3. Global ids run from 0 to N − 1 = 7, so the last global id is 7.
  4. Work-item i reads A[i] and B[i]. For i = 6: A[6] = 7 and B[6] = 10.
  5. C[6] = A[6] + B[6] = 7 + 10 = 17.

Exam traps

  • Do not use get_local_id(0) as the array index. For a one-dimensional NDRange, global id = group id × local size + local id = get_global_id(0).
  • Global size is the number of work-items, not the number of work-groups. Divide by local size to get the group count.
  • In the simple one-dimensional launch, local size must divide global size. Global size 10 and local size 4 do not give 2.5 groups; that launch is invalid under the simple rule.
  • OpenCL kernels are compiled by the runtime for the device. Host C code cannot call a kernel like an ordinary function.
  • Local memory is per work-group, not per device; another work-group cannot see it.

Takeaways

  1. Threads share memory, so OpenMP is easy to add but shared updates still need synchronization.
  2. MPI processes do not share memory; every cooperation is an explicit send or receive.
  3. A GPU executes many threads in warps, so branching and memory access patterns decide speed.
  4. A CUDA kernel launch fixes grid and block dimensions, and those dimensions map each thread to data.
  5. Shared memory is per block and fast; global memory is large but slow; constant memory is read-only and cached.
  6. Host-device copies are often the largest cost, so move data once and reuse it on the device.
  7. Coalesced, reused data turns GPU bandwidth into useful work.
  8. OpenCL expresses the same device ideas with NDRanges, work-groups and local memory.
  9. Choose OpenMP for one node, MPI across nodes, and GPUs for regular data-parallel work.

Glossary

Barrier
A barrier is a synchronization point where threads wait until all members of a group arrive.
Coalesced access
Coalesced access is a memory pattern where adjacent threads access adjacent addresses in one transaction.
Collective operation
A collective operation is an MPI call in which all ranks of a communicator participate.
Communicator
A communicator is an MPI group of processes plus a context for their messages.
Constant memory
Constant memory is read-only device memory that is cached and useful for values read by many threads.
Distributed memory
Distributed memory is a model in which each process has its own address space and cannot directly read another process's variables.
Global memory
Global memory is large device memory accessible by all threads in a grid and by host transfers.
GPU
A GPU is a many-core processor designed to run thousands of threads for data-parallel work.
Grid
A grid is the complete set of thread blocks created by one kernel launch.
Kernel
A kernel is a function written for device execution and launched over many GPU threads.
Local memory
Local memory is per-thread device memory used when registers are insufficient or indexing is dynamic.
Message passing
Message passing is cooperation by explicit send and receive operations between processes.
MPI
MPI is a standard message-passing interface for programs running as multiple processes.
Mutual exclusion
Mutual exclusion ensures that only one thread at a time executes a critical section.
NDRange
An NDRange is the OpenCL index space that defines the global and local dimensions of work-items.
OpenMP
OpenMP is a compiler-directive API for shared-memory parallel programming with threads.
Pthreads
Pthreads is a POSIX thread library for creating and synchronizing threads in one process.
Race condition
A race condition is a timing-dependent error caused by unsynchronized access to shared data.
Rank
A rank is the integer identifier of a process inside an MPI communicator.
Shared memory
Shared memory is a programming model in which threads of one process read and write the same variables.
Shared memory (CUDA)
CUDA shared memory is fast on-chip memory private to one thread block.
SIMT
SIMT is a GPU execution model where one instruction is issued for many threads at once.
Thread
A thread is an execution path inside a process that shares the process address space with other threads.
Thread block
A thread block is a group of GPU threads that can share block-level memory and synchronize.
Warp
A warp is a group of GPU threads scheduled and executed together, 32 threads in NVIDIA GPUs.
Work-group
A work-group is a set of OpenCL work-items that can share local memory and synchronize.
