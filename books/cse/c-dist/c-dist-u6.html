6.1 Naming and distributed file systems

A name is a handle people use; an address is where the thing sits. Naming resolves the first into the second, step by step. A distributed file system uses naming so a file on a remote server opens like a local path, then decides where to cache bytes and when a write becomes visible. NFS, AFS and HDFS all make this trade.

You need Unit 4 for remote procedure call and message cost, and Unit 5 for consistency models.

From names to addresses, flat and structured

A name is a string such as notes.txt. An identifier names at most one entity, such as an inode number. An address is where the entity is reached, such as server S plus a file handle. Resolution maps a name to an address. A flat name has no structure, so the system needs a search rule.

  • Broadcast asks every server; message cost grows with server count.
  • Forwarding pointer stays at the old address; long chains add lookups.
  • Home-based naming keeps one home address; the home becomes a hotspot.
  • DHT hashes the name to a key and stores the key on the node that owns it.

owner(k) = first node clockwise from h(k)

k is the key from the name; h(k) is its position on a 2^m ring of m bits; owner(k) is the node that stores k. Consistent hashing moves few keys when a node joins or leaves.

A structured name is a path such as /home/ravi/notes.txt. The name space is a labelled graph: directories are internal nodes, files are leaves, edges carry component names. Resolution walks one component at a time; each component returns the next node. An absolute name starts at the root; a relative name starts at the current directory.

A mount point is a local directory where a remote export is spliced in. /home/ravi/remote can represent server S's /export/ravi. The closure is the set of nodes visited. A hard link is another name for the same identifier; a soft link stores a path and breaks if the target moves.

Distributed file systems: caching and freshness

A distributed file system has two access models. In the remote access model, each read or write goes to the server and the client keeps no local copy. In the upload/download model, the client downloads the whole file, works locally, and uploads it changed.

Caching can hold a whole file or fixed-size blocks. The cache can sit on the client disk, in client memory, or in server memory. Client disk survives a crash but is slower; client memory is faster but lost on reboot; server memory helps repeated reads.

Sharing semantics decide when a write becomes visible.

  • Unix semantics: a read after a write sees the write immediately, even from another client.
  • Session semantics: changes become visible when the file is closed.
  • Immutable files: a file never changes; a new version gets a new name.
  • Transaction semantics: reads and writes appear atomic, as in a database transaction.

NFS v3 uses a stateless server: it keeps no per-client open or lock state, and every operation is idempotent, so a retry after a lost reply is safe. NFS resolves one path component per RPC and caches a file handle per component. AFS caches whole files on client disks and validates them on open. HDFS stores fixed-size blocks and keeps block locations in a single NameNode.

Worked example

Question. A client opens /home/ravi/remote/notes.txt. The directory /home/ravi/remote is a mount point for the export /export/ravi on server S. (a) List the lookups and say which go to S. (b) How many round trips to S are needed on the first open, and on the second open of the same file if the client caches the file handles of remote and notes.txt?

  1. 1. Resolve /, home, ravi locally: 3 local lookups.
  2. 2. remote is a mount point for S:/export/ravi; use its cached handle or one RPC if absent.
  3. 3. Ask S for notes.txt inside /export/ravi: 1 RPC to S, which returns its file handle.
  4. 4. First open: 1 round trip to S.
  5. 5. Second open with both handles cached and the file unchanged: 0 round trips to S.
  6. 6. Closure = {/, home, ravi, S:/export/ravi, S:/export/ravi/notes.txt}; size 5.

Answer. First open: 1 round trip to S; second open: 0 round trips; closure size: 5.

Exam traps

  • A mount point is a local directory, not the remote root. The remote root here is /export/ravi.
  • NFS v3 keeps no per-client state; a retry must repeat safely, so operations are idempotent.
  • Whole-file caching fetches the full file; block caching fetches only needed blocks. Do not mix them.
  • Unix semantics makes a write visible immediately; session semantics waits for close.
  • A hard link names the same identifier; a soft link stores a path.

6.2 Distributed query processing and optimization

A distributed query is one SQL statement whose tables sit at different sites. The optimiser rewrites it into relational algebra, replaces each table by its fragments, and chooses the join order and the site where each step runs. The winning plan is not the one with the least CPU work; it is the one that pushes the fewest bytes over the slowest link. The rule: move the query to the data, not the data to the query.

You need relational algebra and SQL (selection σ, projection π, join ⋈) from your database course, plus message cost and latency from Unit 4, Distributed System Models and Logical Time.

Decomposition and data localization

SQL states which rows you want, not how to build them. The optimiser rewrites it as relational algebra over σ (select), π (project), × (product) and ⋈ (join). It normalises WHERE into conjunctive form, an AND of small conditions, so each can be moved and tested alone, then deletes always-true conditions and branches that can never yield a row.

  1. Rewrite the SQL into relational algebra.
  2. Normalise predicates into an AND of small conditions.
  3. Simplify by deleting always-true and always-false parts.
  4. Replace each global relation by the union of its fragments — data localization.
  5. Apply reduction rules that cut joins and unions which cannot contribute rows.

A horizontal fragment holds a subset of rows, for example customers split by state. A vertical fragment holds a subset of columns and must carry the primary key so a full row can be rebuilt. A mixed fragment is both.

  • If two horizontally fragmented relations are joined on the fragment attribute under the same predicate, only matching fragment pairs can produce rows; the rest are removed.
  • A union of all fragments of one relation collapses back to the relation.
  • If a query touches only the columns of one vertical fragment, the join that would rebuild the other columns is dropped.

Costing a plan: CPU, disk, network

Every candidate plan gets a number, a weighted sum of CPU, disk and network terms.

C = c_cpu × cpu_ops + c_io × pages + c_msg × messages + c_byte × bytes

c_cpu is cost per instruction and cpu_ops the instruction count; c_io is cost per disk page and pages the pages read; c_msg is cost per message and messages the number sent; c_byte is cost per byte and bytes the total bytes sent.

CPU and disk are local and paid once per site. Communication is paid on every hop and grows with data volume. On a wide-area link one byte can cost thousands of times a local disk byte, so a plan that rereads a page ten times can beat a plan that ships it once. For one message, elapsed time is latency plus bytes divided by bandwidth; latency dominates small messages, bandwidth large transfers.

Join strategies across sites

With R at site A and S at site B, four standard arrangements exist.

  • Ship the whole relation: send all of R to B and join there. Cheapest when R is small.
  • Ship the fragment: project only the needed columns of R at A before sending.
  • Semi-join: B sends π_sid(S) to A; A keeps only matching tuples of R and ships the reduced R′ to B, where the join runs. Pays off when the join filters out most of R.
  • Bloom join: B sends a bit-array hash filter of its keys instead of the key list. No false negatives, so no match is lost; a few false positives slip through and are removed by the final join.

Predicate push-down belongs to the same family: any selection that mentions only R is applied at A before shipping. Shrink, filter and project where the data sits, and send upstream only what the next step needs. The best plan moves the fewest bytes, not runs the fewest instructions.

Searching for the cheapest plan

Optimisation is a search. Each plan is a tree whose leaves are fragments and whose internal nodes are operations. The optimiser enumerates trees, for example all join orders up to a size bound, and scores each with the cost function above. The space grows exponentially with the number of joins, so systems prune with heuristics such as left-deep trees and greedy join ordering.

A static plan is fixed before execution from statistics. A dynamic or adaptive plan re-optimises while running: if the first result is smaller than estimated, the next join switches to a semi-join. Adaptive plans cost bookkeeping but save bytes when statistics are stale.

Group-by parallelises easily. Each site computes SUM, COUNT, MIN or MAX on its fragment and ships one partial per group; a coordinator combines them. AVG does not split, so it is rewritten as SUM divided by COUNT. MapReduce and Spark SQL run this same decomposition, localisation and cost-based search at larger scale; scaling is in 6.6.

Worked example

Question. Relation R sits at site A with 100,000 tuples of 100 bytes. Relation S sits at site B with 500 tuples of 60 bytes. The query R ⋈ S on sid produces 10,000 tuples of 160 bytes, and the result must be delivered at B. The link carries 125 KB/s, with 1 KB = 1000 bytes and 1 MB = 10⁶ bytes. Compare three plans: (a) ship R to B and join there; (b) ship S to A, join at A, send the result to B; (c) semi-join — send π_sid(S) to A, ship the reduced R′ to B, join with S at B. For each, give bytes moved and elapsed time.

  1. R = 100,000 × 100 B = 10,000,000 B = 10 MB.
  2. S = 500 × 60 B = 30,000 B = 30 KB.
  3. Result = 10,000 × 160 B = 1,600,000 B = 1.6 MB.
  4. Link = 125 KB/s = 125,000 B/s.
  5. Plan (a): 10,000,000 B ÷ 125,000 = 80 s.
  6. Plan (b): S to A = 30,000 B = 0.24 s; result to B = 1,600,000 B = 12.8 s. Total 1,630,000 B, 13.04 s.
  7. Plan (c): π_sid(S) = 500 × 4 B = 2,000 B = 0.016 s. R′ = 10,000 × 100 B = 1,000,000 B = 1 MB = 8.0 s. Total 1,002,000 B, 8.016 s.
  8. Selectivity = 10,000 ÷ 100,000 = 10%, so 90% of R never crosses the link.

Answer. Plan (c), the semi-join, moves 1,002,000 bytes and takes 8.016 s, against 10,000,000 bytes and 80 s for plan (a) and 1,630,000 bytes and 13.04 s for plan (b).

Exam traps

  • Costing CPU and disk carefully and forgetting communication, usually the largest term.
  • Using a semi-join when the join is not selective: if 90% of R matches, you ship the key list on top of nearly all of R.
  • Dropping the cost of delivering the final result, which changes the ranking in plan (b).
  • Mixing MB and Mb, or binary and decimal units. Fix the convention before dividing.
  • Believing a Bloom join can lose a match. It has only false positives, no false negatives.

Remember What is a semi-join between R at A and S at B? 2 marks

Understand Why does communication usually dominate a distributed plan's cost? 3 marks

CPU and disk are paid once, locally, at hardware speed. A link byte costs far more, is paid on every hop, and grows with data volume. Small messages also pay a fixed latency per step.

Apply R at A has 40,000 tuples of 200 bytes. S at B has 1,000 tuples; its sid is 8 bytes. The result has 2,000 tuples of 300 bytes and stays at B. The link is 100 KB/s. Find the bytes moved and time for (a) shipping R to B and (b) a semi-join on sid. 4 marks

(a) 40,000 × 200 = 8,000,000 B = 8 MB; 8,000,000 ÷ 100,000 = 80 s. (b) π_sid(S) = 1,000 × 8 = 8,000 B = 0.08 s; R′ = 2,000 × 200 = 400,000 B = 4 s. Total 408,000 B, 4.08 s. The semi-join is about 20 times faster.

Apply Customers are horizontally fragmented by state, and a query joins Customers and Orders on cust_id with the predicate state = 'TN' on both relations. Which fragment pairs must be joined? 3 marks

Only the TN fragment of Customers with the TN fragment of Orders. All other state pairs can produce no row under the predicate, so the reduction rule deletes them from the fragment tree.

Analyze A Bloom join is chosen over a semi-join for a join on a 32-byte text key with 200,000 keys at B. Explain the trade-off and what happens to false positives. 4 marks

Sending 200,000 keys of 32 bytes is 6.4 MB; a bit-array filter of a few hundred kilobytes conveys the same membership information. The filter has no false negatives, so no match is lost at A. False positives let a few non-matching tuples of R through; they travel to B and are removed by the final join, costing a little extra bandwidth.

Analyze A plan is estimated to ship 1 MB, but at run time only 20 KB arrives. What does an adaptive optimiser do, and why is a static plan worse here? 4 marks

The adaptive optimiser reads the actual cardinality, sees the intermediate result is far smaller than estimated, and switches the next step to a nested-loop or broadcast plan instead of the pre-computed hash join, saving a data reshuffle. The static plan trusts stale statistics and ships more bytes than needed.

Understand Why must AVG be rewritten as SUM divided by COUNT before a parallel group-by? 3 marks

An average of averages is wrong unless the group sizes are equal. SUM and COUNT each split into partials that combine by addition, so each site sends one SUM and one COUNT per group and the coordinator divides the totals.

Beyond the syllabus

Not for the exam. Real engines split this work: Apache Calcite does the algebra rewrite, Trino and Presto plan across connectors, and Spark's Catalyst optimiser applies the same rules before code generation. Research has moved toward learned and adaptive optimisers that correct cardinality estimates from actual run-time rows, because bad estimates, not bad search, cause most slow distributed plans. The ideas in this chapter reappear whenever data is too big to move, which is the normal case in cloud warehouses.

6.3 Distributed transactions and concurrency control

A distributed transaction must finish at every site or at none. That all-or-nothing rule is atomicity, and it is hard when sites crash and messages are lost. Two-phase commit (2PC) gives one coordinator the power to decide and makes every participant wait for that decision. Three-phase commit (3PC) adds a pre-commit step to avoid blocking under site failures, though it still blocks under network partitions. Underneath, each site still needs concurrency control so concurrent transactions do not corrupt shared data. Banks, ticket booking and order systems use these ideas when one purchase touches several databases.

You need: Unit 4 for logical clocks that stamp transactions, and Unit 5 for deadlock detection and consensus; 6.2 shows why a site can be busy with a long report.

One transaction, many sites

A transaction is a unit of work that must satisfy ACID: atomicity (all or nothing), consistency (moves one valid state to another), isolation (concurrent transactions do not see each other's partial work), and durability (a committed result survives a crash). A distributed transaction runs at several sites. A flat transaction has no internal structure; a nested transaction is a tree of subtransactions. A parent may commit only after all children have completed. A child abort does not automatically abort the parent, but the child's effects are undone. One site acts as coordinator: it starts the protocol and keeps the decision. Every other site that holds data is a participant. Each participant keeps either a private workspace or an undo log. In a workspace model, new values stay private and are not written to the database until the decision arrives. In an undo-log model, the participant writes new values locally but does not make them visible or commit them, and it logs old values so it can roll back. If the transaction aborts, the participant discards the workspace or applies the undo log. If it commits, it makes the changes visible. These mechanisms are why a site can still say no after doing work.

Two-phase commit

Two-phase commit (2PC) has two phases. In the prepare phase the coordinator sends a prepare message to every participant. Each participant does the work, writes a prepare record and its undo data to stable storage, and votes. A yes vote is a promise: this site can commit if told. A no vote means it cannot. The participant then waits; it may not change its vote. In the decision phase the coordinator collects votes. If every vote is yes, it appends COMMIT to its log and forces the log to disk before sending commit. If any vote is no, or a timeout occurs, it may send abort without forcing an abort record; writing ABORT is optional and only for cleanup. Only the COMMIT decision must be forced before the commit message leaves. After a crash the coordinator reads its log and knows the decision; a missing commit record means abort. It then sends commit or abort to all participants. Each participant applies or undoes its work, releases locks, and sends an ack. If the coordinator dies after a yes vote but before the decision is logged, participants that voted yes hold locks and block. That is 2PC's blocking problem. Presumed abort reduces log writes: if the coordinator has no commit record on recovery, it presumes abort. A participant that voted yes and has a prepare record must still wait or query the coordinator; it must not abort just because it has no local commit record. Presumed commit is the mirror choice and needs more careful recovery.

M = 4n

M is the total number of messages in a 2PC run with n participants when every participant votes yes and every participant acknowledges; n is the number of participants.

Three-phase commit and distributed concurrency control

Three-phase commit (3PC) adds a pre-commit phase between prepare and commit. After all sites vote yes, the coordinator writes pre-commit and tells them. A site that has pre-committed knows every site can commit. If the coordinator now fails, the sites can finish without waiting forever. 3PC is non-blocking for site failures. It still blocks under a network partition: one group may have pre-committed while the other has not, and neither can safely decide alone. Consensus under partition is the subject of Unit 5. Concurrency control still runs at each site. Strict two-phase locking (2PL) means a transaction acquires locks before reading or writing and holds every lock until commit or abort. At each site this gives a strict local schedule; with 2PC's single commit point, the global schedule is conflict serializable and no cascading aborts occur. Timestamp ordering gives each transaction a unique timestamp from a logical clock (Unit 4). Each data item stores the largest read and write timestamps; an operation that arrives too late is rejected and the transaction restarts. This guarantees serializability in timestamp order. Optimistic validation lets transactions run freely, then checks at commit that no concurrent transaction wrote a value they read; a failed check aborts and retries. Distributed deadlock detection and consensus are covered in Unit 5; here the key point is that atomic commit sits on top of local concurrency control, not instead of it.

Worked example

Question. A transfer T debits ₹5,000 at site A, credits ₹5,000 at site B, and writes an audit row at site C. Site C's participant finds the audit table locked by a long report and votes no. (a) Write the message sequence with the coordinator's log write in the right place. (b) Count the messages. (c) Say what each site does after the decision.

  1. Coordinator sends prepare to A, B, C.
  2. A debits ₹5,000 in its private workspace, writes a prepare record, and votes yes. B credits ₹5,000 in its private workspace, writes a prepare record, and votes yes. C cannot get the audit lock and votes no.
  3. Coordinator receives yes, yes, no. It need not force an abort record; it may write ABORT for cleanup, but a missing commit record already means abort.
  4. Coordinator sends abort to A, B, C.
  5. A discards the debit, B discards the credit, C discards nothing; all release locks and send ack.
  6. Messages: 3 prepare + 3 votes + 3 abort + 3 ack = 12. Net money movement = 5000 − 5000 = ₹0.

Answer. Only a COMMIT decision must be forced before the commit message; an abort needs no forced record. The run costs 12 messages, and the net movement is ₹0.

Exam traps

  • Writing COMMIT to the coordinator log after sending it. The log write must come first, or recovery cannot know the decision.
  • Saying 3PC never blocks. It avoids waiting on a dead coordinator in some failure cases, but a network partition can still split the sites.
  • Treating a yes vote as a commit. A yes vote only promises to commit if the coordinator says so; the participant must wait.
  • Forgetting that a participant's undo log must be forced before the yes vote. Otherwise it cannot roll back after a crash.
  • Treating presumed abort as a rule for any participant. Presumed abort is a coordinator recovery rule for a missing commit record; a prepared participant still waits or queries the coordinator.

Analyze Why is 3PC still blocking under a network partition? 4 marks

The partition can leave one group pre-committed and another group not. Neither group can know the other group's votes, so neither can safely commit or abort alone.

If the coordinator has no commit record on recovery, it presumes abort. A prepared participant still waits or queries the coordinator; it does not abort just because it lacks a local commit record. This saves an abort log write.

Apply A transaction reads x at site A and writes y at site B under strict 2PL. When can it release the lock on x? 4 marks

Only after the global commit or abort. Strict 2PL holds all locks until the transaction finishes, so it cannot release x early.

Analyze Why is atomic commit needed if each site already runs strict 2PL? 5 marks

Strict 2PL gives a serial order at each site. Without atomic commit, one site could commit while another aborts, so the global result would be partial. 2PC gives one commit point for all sites.

Beyond the syllabus

Not for the exam. Real systems often keep 2PC inside one database or message broker and avoid it across microservices, because a blocked coordinator holds locks. Some large systems place a consensus layer below the commit decision so a partition cannot split the decision. Search for 'presumed abort', 'three-phase commit', and 'distributed serializability'.

6.4 Cloud computing: service and deployment models

Cloud computing rents computing as a metered utility. A provider owns the machines and the network, and you buy capacity by the hour or by the request. The service model you choose fixes where your responsibility stops: the provider manages the layers below that line. The deployment model fixes who shares the hardware and who owns it. Together they explain most cloud bills, most cloud outages and most cloud lock-in. A Pune startup, a bank and a government office can all use the same provider under different models.

You need: Unit 4 for the characteristics and design challenges of distributed systems, and 6.1 for why remote storage must look local.

What counts as cloud: five tests

Cloud computing is a model for on-demand network access to a shared pool of computing resources — servers, storage, networks, applications — that can be provisioned and released quickly with little management effort. The provider owns the hardware; you rent capacity. Five tests separate a cloud from a plain data centre.

  • On-demand self-service: you create a VM or a database from a portal or API without asking a person.
  • Broad network access: services are reachable over the network from phones, laptops and office systems.
  • Resource pooling: many customers share a pool of machines, and the provider assigns and reassigns capacity.
  • Rapid elasticity: capacity grows or shrinks with demand, often in minutes.
  • Measured service: the provider meters use — hours, requests, gigabytes — and bills against the meter.

A data centre you own is not automatically a private cloud. It must pass these tests too.

Service models: who manages the stack

The service model sets the line between your work and the provider's work. The same application can be built at three levels.

IaaS (infrastructure as a service): you rent virtual machines, storage and networks. You install and patch the operating system, the runtime and the application. Amazon EC2 and Azure Virtual Machines are examples.

PaaS (platform as a service): the provider runs the servers and the operating system. You deploy code and data; the provider patches the runtime and scales the workers. Google App Engine and Heroku are examples.

SaaS (software as a service): the provider runs everything. You open a browser and use the application. Gmail and Salesforce are examples.

Two newer labels split the same stack differently. Serverless, or function as a service, runs a function per event and bills per invocation and execution time; you do not manage a server. Database as a service gives you a managed database with backups and patching done for you.

The line is not fixed. A managed Kubernetes service is closer to PaaS than to raw IaaS. In every case, ask who patches the OS and who owns the data.

Deployment models, drivers and risks

The deployment model says who owns the hardware and who shares it.

  • Public cloud: a provider owns the hardware and many customers share it. Tenants are isolated by software.
  • Private cloud: one organisation uses the cloud, on its own hardware or hosted. It still needs self-service, pooling and metering.
  • Community cloud: several organisations with a shared concern — a group of banks, a set of hospitals — share a cloud.
  • Hybrid cloud: two or more models are joined so data and applications can move between them.

Cloud turns capital cost into operating cost. A team avoids buying servers and pays monthly. Provisioning takes minutes, not weeks. A service can reach users in many regions, and capacity can stretch for exam-week peaks, then shrink.

The risks are real. Vendor lock-in grows when you use proprietary APIs. Data security and privacy remain your duty even when the provider secures the hardware. Compliance and data residency may require data to stay in a country. Downtime, latency, network dependence and surprise bills follow from renting someone else's machines.

AWS, Microsoft Azure and Google Cloud are the largest public platforms; Oracle Cloud and IBM Cloud also serve enterprises. India's MeghRaj is a government cloud initiative for public departments.

Worked example

Question. A startup in Pune runs an exam-practice app. Option 1 is IaaS: one VM of 2 vCPU and 4 GB at ₹2.5 per hour, running 24×7. Option 2 is PaaS: ₹1,500 base per month plus ₹0.9 per 1,000 requests, with 3 million requests per month. Use 730 hours in a month. Compare the monthly bills.

  1. IaaS hours in a month = 730 hours.
  2. IaaS bill = 730 hours × ₹2.5 per hour = ₹1,825 per month.
  3. PaaS request blocks = 3,000,000 requests ÷ 1,000 requests per block = 3,000 blocks.
  4. PaaS request charge = 3,000 blocks × ₹0.9 per block = ₹2,700.
  5. PaaS bill = ₹1,500 base + ₹2,700 = ₹4,200 per month.
  6. IaaS is cheaper in money by ₹2,375 per month, but the team must patch the OS and runtime itself.

Answer. IaaS costs ₹1,825 per month and PaaS costs ₹4,200 per month; IaaS is cheaper by ₹2,375, but PaaS includes OS patching.

Exam traps

  • Calling any owned data centre a private cloud. A private cloud still needs self-service, resource pooling, elasticity and measured service; without them it is just virtualised servers.
  • Mixing PaaS with SaaS. PaaS gives you a runtime to deploy your own code; SaaS gives you a finished application that you only use.
  • Assuming IaaS is always cheaper. The VM bill is lower, but OS patching, backups and staff time are now your cost.
  • Ignoring data residency. A public cloud region outside your country may break a compliance rule even when the technology works.

6.5 Virtualization for cloud computing

Virtualization makes one physical computer look like several. A hypervisor, or virtual machine monitor, runs guest operating systems side by side, each with virtual CPU, memory, disk and network. The point is to use idle hardware, isolate tenants, snapshot a machine state as a file, clone it, and move it to another host. Cloud infrastructure-as-a-service depends on this: when you rent a 4 GB server for an hour, you usually get a virtual machine, not a physical one. Containers are a lighter cousin that share one kernel.

You need: Unit 1 for machine organisation, and 6.4 for the cloud service models that sit on these VMs.

Hypervisor, guest and host

The hypervisor is the software that owns the real hardware and hands each virtual machine (VM) a slice. The operating system inside a VM is the guest. The guest has a virtual CPU, virtual memory and virtual devices, and its kernel believes it is running on real hardware. The machine underneath is the host.

Why virtualize: consolidation packs ten lightly loaded servers onto one host; isolation keeps one tenant's crash or break-in away from another; snapshots and cloning turn a machine state into a file you can copy; migration moves a running VM to another host for repair or load balance. The guest OS is usually unmodified, so it runs its normal drivers on virtual devices.

Type 1 hypervisor runs bare metal: hardware, hypervisor, guest OS, app. Type 2 is hosted: hardware, host OS, hypervisor, guest OS, app. Type 2 is convenient on a laptop but pays host-OS scheduling and driver overhead. A type 2 hypervisor still needs the host OS; it is not bare metal.

CPU, memory and I/O virtualization

The guest kernel executes privileged instructions: loading page tables, masking interrupts, halting the CPU. On native hardware these run in the highest privilege ring. Under a hypervisor the guest runs with less privilege, so a privileged instruction traps to the hypervisor, which emulates the effect and resumes the guest. Early x86 did not trap cleanly, so full virtualization used binary translation: the hypervisor scans guest code and replaces awkward instructions with safe calls. Paravirtualization instead modifies the guest kernel to issue hypercalls, explicit calls to the hypervisor; it is fast but needs a modified guest. Hardware help (Intel VT-x, AMD-V) adds a root mode for the hypervisor and a non-root mode for guests, so privileged instructions cause a clean VM exit.

Memory has two mappings: guest virtual to guest physical, and guest physical to machine physical. Shadow page tables make the hypervisor build one combined guest-virtual-to-machine-physical table and trap guest page-table writes; that is costly. Nested page tables (EPT on Intel, NPT on AMD) let hardware walk both tables, removing most traps. For I/O, emulated disks and network cards are slow; virtio uses shared memory rings and paravirtual drivers so guest and host batch requests, giving near-native disk and network throughput.

Containers, images and live migration

Containers do not virtualize hardware. All containers share the host kernel. Linux namespaces give each container its own process IDs, network, mounts and hostname; cgroups cap CPU, memory and I/O. A container starts in milliseconds because no guest OS boots, and many containers fit on one host. Isolation is weaker: a kernel bug or a privileged container can affect the host. A VM carries its own kernel, so it isolates better and can run a different OS.

A VM image is the disk plus configuration; a template is a read-only image you clone. Cloud providers launch many instances from one image. Containers use layered images instead.

Live migration by pre-copy: copy all memory pages to the target while the source keeps running. The guest dirties pages during the copy, so copy the dirty set in rounds. Convergence needs dirty rate d less than link bandwidth B; if d ≥ B the copy never catches up. When the remaining dirty set is at or below a threshold, stop the guest, copy the last pages, resume on the target. Downtime is the last copy plus setup.

When virtualization is bad: CPU-bound code with many privileged operations pays VM exits; latency-sensitive trading, GPU passthrough, nested virtualization and huge VMs with high dirty rates can be worse than bare metal or containers. Dense stateless services often run better in containers, but with weaker isolation.

Worked example

Question. A 4 GB VM (4096 MB of memory) runs on host H1 and dirties memory at 40 MB/s. The migration link carries 100 MB/s. Pre-copy stops when the dirty set left is below 64 MB. Find the number of pre-copy rounds, total bytes copied, total time, and downtime.

  1. Round 1 copies 4096 MB; time = 4096 ÷ 100 = 40.96 s; new dirty = 40 × 40.96 = 1638.4 MB.
  2. Round 2 copies 1638.4 MB; time = 16.384 s; new dirty = 655.36 MB.
  3. Round 3 copies 655.36 MB; time = 6.5536 s; new dirty = 262.144 MB.
  4. Round 4 copies 262.144 MB; time = 2.62144 s; new dirty = 104.8576 MB.
  5. Round 5 copies 104.8576 MB; time = 1.048576 s; new dirty = 41.94304 MB, which is below 64 MB, so pre-copy ends.
  6. Final stop-and-copy copies 41.94304 MB; downtime = 41.94304 ÷ 100 = 0.4194304 s.
  7. Total bytes = 4096 + 1638.4 + 655.36 + 262.144 + 104.8576 + 41.94304 = 6798.70464 MB.
  8. Total time = 40.96 + 16.384 + 6.5536 + 2.62144 + 1.048576 + 0.4194304 = 67.9870464 s.

6.6 Scalability and elasticity in the cloud

Scalability is the headroom a design leaves for growth. Elasticity is renting that headroom automatically for the minutes you need it and returning it after. A shop that keeps 18 servers all month pays for idle machines; an elastic shop runs one server at night and eighteen during a four-hour rush. Cloud systems use this to survive cricket-final spikes and local power cuts without over-buying. The same ideas choose load balancers, replica counts and auto-scaling rules.

You need: 6.4 for service models, Unit 1 for speedup and load balancing, and Unit 5 for replication consistency models.

Growing up or growing out

Vertical scaling replaces a machine with a bigger one: more cores, more RAM, a faster disk. It needs no program change, but it stops at the largest machine a provider sells and often costs more per unit of work. Horizontal scaling adds more machines and spreads work across them. It has no single-machine ceiling, but the program must run as several copies.

The limit on horizontal scaling is the serial part. If a fraction s of the work cannot be split, N workers give the speedup below. S(N) is speedup over one worker, s is the serial fraction from 0 to 1, and N is the number of workers. As N grows, S(N) tends to 1/s; with s=0.2 the ceiling is 5×, or 500 requests per second (req/s) if one server does 100.

S(N) = 1 / (s + (1 − s)/N)

S(N) is speedup, s is the serial fraction (0 ≤ s ≤ 1), and N is the number of servers.

A tier that keeps no user data in its own memory is stateless and scales out by adding copies behind a load balancer. A tier that keeps session state, uploaded files or a shopping cart in local memory is stateful; adding a copy splits users across machines that do not know each other. Move session state to a shared store or a signed cookie before scaling out.

Load balancing, copies and shards

Put a load balancer in front of identical servers. Round robin gives request 1 to server 1, request 2 to server 2, and so on; it assumes equal request cost. Weighted round robin gives a stronger server more turns. Least connections picks the server with the fewest open requests, which suits long-lived connections. IP hash uses hash(client IP) mod N and pins a client to one server; it breaks when N changes. Consistent hashing places servers and keys on a ring, so adding one server moves only its share of keys, not all keys. That gives cache affinity without rehashing everything.

Health checks probe each server; a failed probe removes it from the pool. Sticky sessions keep one user on one server, but they make failures and scaling harder. Prefer a shared session store.

Replication keeps copies for read scale and failure. In primary-replica, writes go to the primary and reads to replicas. A multi-primary setup accepts writes at more than one node, but conflict reconciliation becomes the hard part. With N replicas, a write must reach W replicas and a read contacts R replicas. If R+W>N, the read set and write set overlap, so the read sees the latest write. For N=3, W=2, R=2: 4>3. Read replicas scale reads, not writes.

Sharding splits data by key, for example a user-ID range, so each shard is small. Cross-shard queries and transactions become the cost; see 6.3.

Elasticity, signals and cost

Elasticity is automatic scaling: a controller watches a metric, compares it with a threshold, and changes the server count. CPU utilisation is common. Queue length and requests per second are better when work arrives in bursts. A cool-down waits after a scaling action so the metric settles; without it the controller adds servers, sees CPU fall, removes them, and thrashes.

Reactive auto-scaling responds to current load. Scheduled scaling adds servers before a known peak, such as 8 p.m. match time. Predictive scaling learns the daily pattern and acts earlier. All three need a maximum and minimum count, because a runaway rule can create a large bill.

Monitoring uses three streams: metrics are numbers over time, logs are events, traces follow one request across services. An SLI is a measured indicator, for example successful requests ÷ total requests. An SLO is the target for that SLI. An SLA is the contract with penalties. Availability of 99.9% leaves 0.1% downtime; in a 30-day month of 720 h that is 0.001×720×60 = 43.2 minutes. Over-provisioning buys safety with idle hours; the worked example prices it.

Worked example

Question. An app must serve 2,000 requests per second at peak. Each request needs 50 ms of CPU on one core, and a server has 8 cores. You size servers to run at 70% utilisation. The app needs 1 server off peak and full capacity for 4 hours a day, 30 days a month, at ₹6 per server-hour. (a) How many servers at peak? (b) What does elastic scaling cost per month? (c) What would 18 fixed servers cost, and how much does elasticity save?

  1. One core serves 1 ÷ 0.050 s = 20 requests per second (req/s).
  2. One 8-core server serves 8 × 20 = 160 req/s.
  3. At 70% utilisation, usable capacity is 0.70 × 160 = 112 req/s.
  4. Peak servers = ceil(2000 ÷ 112) = ceil(17.86) = 18.
  5. Peak hours = 4 h/day × 30 days = 120 h. Total hours = 30 × 24 = 720 h. Off-peak = 720 − 120 = 600 h.
  6. Elastic cost = 600 h × 1 server × ₹6 + 120 h × 18 servers × ₹6 = ₹3,600 + ₹12,960 = ₹16,560.
  7. Fixed 18 servers = 720 h × 18 × ₹6 = ₹77,760. Saving = ₹77,760 − ₹16,560 = ₹61,200.

Answer. Peak needs 18 servers; elastic cost is ₹16,560 per month; 18 fixed servers cost ₹77,760, so elasticity saves ₹61,200.

6.7 Grid computing

Grid computing pools computers owned by different organisations into one virtual supercomputer. Each site keeps its own machines and policy; shared standard protocols let a user reach them as one system. The set of users allowed to share is a virtual organisation (VO). A grid is not a cluster, which one owner controls, and not a cloud, which is rented on demand. Grids suit large batch jobs needing many CPU-hours (one CPU busy for one hour).

You need Chapter 6.4 for the cloud comparison and Unit 4 for distributed-system design challenges.

What a grid is

A grid is coordinated resource sharing without central control. It covers CPUs, storage, instruments and software. Each provider keeps its own administrative domain, so no single owner holds every machine or every login. The VO groups users and sites that agree to share for one project; middleware maps a VO identity to local accounts. A grid is loosely coupled and heterogeneous.

The unit of work is a job: a program plus input and a resource request. Grids usually run batch jobs.

Layers, brokers and trust

The grid architecture has five layers. The fabric layer is the machines, storage and networks at each site. The connectivity layer handles authentication and secure transfer. The resource layer enforces each site's policy for its own resources. The collective layer spans sites: brokers, allocation and directories. The application layer holds user jobs.

The connectivity and resource layers form a narrow neck, like an hourglass. Every job crosses that neck, so standard protocols let many applications use many fabrics. A resource broker accepts a job and does matchmaking: it compares CPU count, memory, disk, software and deadline with free capacity, then asks one or more sites. The broker owns no machines.

A data grid moves large files to the site where computation will run. File transfer tools schedule and restart transfers. Security uses X.509 certificates; delegation lets a job act for its user at a remote site for a limited time. National and international research grids exist as examples.

Worked example

Question. A grid has three sites. Site A offers 40 free CPUs for 8 hours. Site B offers 100 free CPUs for 4 hours. Site C offers 20 free CPUs for 12 hours. A job needs 800 CPU-hours and must finish within 12 hours. (a) Find total free capacity in CPU-hours. (b) Give a schedule and its finish time.

  1. Capacity A = 40 × 8 = 320 CPU-hours.
  2. Capacity B = 100 × 4 = 400 CPU-hours.
  3. Capacity C = 20 × 12 = 240 CPU-hours.
  4. Total = 320 + 400 + 240 = 960 CPU-hours; 800 fits.
  5. Run all 160 CPUs for 4 h: 160 × 4 = 640 CPU-hours; B leaves.
  6. Remaining = 800 − 640 = 160 CPU-hours.
  7. A and C give 60 CPUs; phase 2 = 160 ÷ 60 = 2.67 h.
  8. Finish = 4 + 2.67 = 6.67 h, inside 12 h.

  • Forgetting CPU-hours: 40 CPUs for 8 hours is 320 CPU-hours, not 40 or 8.
  • Assuming the broker owns capacity: it only requests capacity from site managers.

6.8 Web data management and web-based systems

A web system is a distributed data system whose clients are browsers. It keeps data close to the reader by caching and replicating it, and cheap to find by indexing it. HTTP carries requests for named resources; caches answer most of them without touching the origin server. This chapter explains how the web stores, finds and serves data at scale, why a cached copy can be stale, and how systems use validation, sharding, replication and retries to stay correct enough. Search engines, UPI dashboards, IRCTC pages and social feeds use these mechanisms.

You need: 6.1 for caching and sharing semantics, 6.6 for replication and load balancing, and Unit 5, Consistency models and replication, for consistency models.

HTTP resources, stateless requests and sessions

HTTP is a request-response protocol. A client asks for a resource named by a URL; the server returns a representation, usually HTML or JSON. The protocol is stateless: between requests the server need not remember the client. Methods carry meaning. GET reads a resource, PUT replaces it, DELETE removes it, and POST asks the server to process data or create a subordinate resource.

GET and PUT are idempotent. Repeating the same request leaves the server state as one request would; POST is not idempotent, so a retried payment can charge twice. Statelessness does not forbid sessions. A cookie is a small name-value pair that the server sets and the browser returns on later requests. The cookie often holds only a session id; session data sits in a shared store.

REST is a design style: expose resources, use uniform methods, keep requests self-contained, and exchange representations such as JSON. It is the default for public web APIs.

Freshness, validation and edge caches

Caching stores a response closer to the user. Freshness is set by Cache-Control: max-age=N. For N seconds a cache may reuse the copy without asking the origin. That is fast, but it is not a consistency guarantee: the origin may already have changed the page.

After max-age expires, the cache validates. The origin's first response carried an ETag, an opaque version string such as v7. The cache sends If-None-Match: v7. A match returns 304 Not Modified with no page body; the stored copy is reused. A mismatch returns 200 OK with a new body and new ETag.

A purge removes a cached object early. Push purge names the URL or tag; time-to-live is the fallback. The hit ratio decides cost.

H = h ÷ (h + m)

H is the hit ratio, h is requests served by the cache, and m is requests sent to the origin; H is between 0 and 1.

A CDN puts edge servers near users. DNS returns a nearby edge address; an origin shield funnels misses through one cache to protect the origin.

Web-scale data: indexes, shards and stores

A search index is an inverted index: for each term t it stores a postings list of document ids and positions. A query intersects postings lists, then ranks documents. A simple score is tf × idf, where tf is term frequency in a document and idf = log₂(N ÷ df), N is number of documents and df is number containing the term.

Web data is sharded and replicated. Sharding splits a key space across servers so each holds a slice; replication keeps copies for read scale and failure. A shard key that concentrates hot keys creates a hotspot.

Key-value stores map a key to an opaque value. Document stores keep JSON-like documents and index selected fields. Both belong to NoSQL, a family that relaxes relational schemas. CAP says a distributed store facing a network partition must choose consistency or availability. BASE means basically available, soft state, eventual consistency; ACID means atomic, consistent, isolated, durable transactions.

Faults, services and safety on the web

Web services expose data to other programs. SOAP is an XML messaging standard with a WSDL contract; REST with JSON is now common because it maps to HTTP methods and caches well.

Fault tolerance uses redundancy, timeouts and retries. Retry only idempotent requests, or give each POST a unique idempotency key so the server can discard a duplicate. A circuit breaker opens after repeated failures and fails fast until a probe succeeds.

HTTPS is HTTP over TLS. TLS encrypts the channel and authenticates the server certificate; it does not authorise the user. Authentication proves who you are; authorisation decides what you may do. Injection attacks occur when untrusted input becomes code: SQL injection in a query string, script injection when a page includes unescaped user content.

Social systems store a social graph and build feeds. A feed is often assembled from many replicas, so a new post may appear after a short delay; eventual consistency is accepted. See 6.3 for strict transactions.

Worked example

Question. A page is 300 KB. Edge caches serve 92% of requests; the rest reach the origin. Traffic is 1,000,000 requests per day. Edge round trip is 20 ms, origin round trip is 120 ms, and transfer rate is 2 MB/s. Use 1 MB = 1000 KB. (a) How many bytes leave the origin per day? (b) What is the average latency per request, and how much does the cache save versus no cache?

  1. Transfer time = 300 KB ÷ 2 MB/s = 300 KB ÷ 2000 KB/s = 0.15 s = 150 ms.
  2. Miss rate = 1 − 0.92 = 0.08. Misses = 0.08 × 1,000,000 = 80,000 requests/day.
  3. Origin bytes = 80,000 × 300 KB = 24,000,000 KB = 24,000 MB = 24 GB/day.
  4. Hit latency = 20 ms + 150 ms = 170 ms.
  5. Miss latency = 120 ms + 150 ms = 270 ms.
  6. Average = 0.92×170 + 0.08×270 = 156.4 + 21.6 = 178 ms.
  7. Saving = 270 − 178 = 92 ms per request.

Answer. (a) 24 GB leave the origin per day; (b) average latency is 178 ms, and the cache saves 92 ms per request compared with 270 ms with no cache.

Exam traps

  • max-age does not keep a copy consistent with the origin; it only permits reuse for N seconds.
  • A 304 response has no page body; the client uses its stored copy.
  • GET and PUT are idempotent, but GET is also safe (read-only); POST retry can duplicate a charge.
  • Hit ratio counts requests, not bytes; a small hot object can raise request hit ratio without saving much bandwidth.
  • CAP is a trade-off during a partition, not a permanent choice of any two from three.

Analyze What does a CDN DNS redirect achieve, and what is origin shielding? 3 marks

DNS returns a nearby edge IP so users fetch from a low-latency cache. Origin shielding sends all edge misses through one cache layer, reducing origin load and thundering herd.

Beyond the syllabus

Not for the exam. Modern web systems push cache and code to the edge, run WebAssembly functions near users, and use HTTP/3 over QUIC to cut connection setup. Feeds and collaborative documents use conflict-free replicated data types (CRDTs) so replicas merge without a central lock. Search next for edge computing, CRDT, HTTP/3, and OpenTelemetry tracing.

Takeaways

  1. A distributed file system hides the network by resolving names to locations and by choosing, per file, whether to cache and how to keep cached copies fresh.
  2. Hard links point to a file identifier and survive renaming; soft links point to a name and break when the target moves.
  3. The remote access model is always fresh but slow; the caching model is fast but needs a consistency rule for stale copies.
  4. A distributed query is fragmented and pushed to the sites holding the data, and the winning plan is the one that ships the fewest bytes.
  5. Semijoins beat full shipping when the join column is small and few rows match.
  6. Two-phase commit gives all-or-nothing across sites at the cost of blocking while the coordinator's decision is unknown.
  7. The cloud service model fixes the split of responsibility: IaaS leaves you the OS, PaaS leaves you the code, SaaS leaves you only the data.
  8. A hypervisor turns a server into a file, which is what makes snapshots, cloning, consolidation and live migration possible.
  9. Scalability is a property of the design; elasticity is an operating policy that buys capacity for minutes and returns it.
  10. A grid federates machines owned by different organisations under shared protocols while each site keeps its own policy.
  11. Web systems trade freshness for latency: caches, replicas and indexes are why stale reads are a design decision, not a bug.

Understand Explain how a name is resolved to an address in a distributed file system, using a path such as /home/me/notes.txt as the running example. Distinguish absolute from relative names and name from address. 13 marks

Understand Compare the remote access model with the caching model of a distributed file system. How does each model decide where a client's data lives? Discuss the cache consistency problem and one protocol to solve it. 13 marks

Remote access model: file stays on server, every operation is an RPC, always fresh, high latency; Caching model: copy brought to client, reads local, faster, needs invalidation or write-through; Client-initiated versus server-initiated consistency; Lease or callback invalidation, or time-based staleness bound; Open-file sharing semantics: UNIX versus session semantics; Choose a model for a read-heavy intranet file share and justify.

Understand Describe the two-phase commit protocol. Give the messages, the states each participant passes through, and what happens when a participant or the coordinator fails. 13 marks

Phase 1: coordinator sends prepare; participant votes yes (and writes to log) or no; Phase 2: coordinator logs the decision and sends commit or abort to all; Participant states: initial, ready, committed, aborted; Failure of a participant before voting: coordinator aborts; Failure after voting yes: participant blocks until the decision is known; Coordinator failure: participants may block; presumed abort versus presumed commit; Termination and recovery protocol with the coordinator's log.

Understand Explain how a hypervisor virtualises a CPU. Cover privileged instructions, traps, VM exit, binary translation or paravirtualisation, and hardware-assisted virtualisation. 13 marks

Apply Relation R has 1,000,000 rows and S has 10,000 rows, stored at different sites. R.a = S.a, and the join column is 8 bytes while a full row is 200 bytes. Analyze and evaluate

Analyze A distributed transactions workload runs across four sites on a cloud with occasional virtual machine restarts. Analyse how two-phase commit, replication and live migration interact when the coordinator's host is migrated during phase 2, and state what guarantee survives. 16 marks

Coordinator's log must be durable on shared storage before it broadcasts a decision; Live migration preserves the VM's state, so the broadcast continues after the switch; If the coordinator genuinely crashes, participants block after a yes vote; Three-phase commit or a replicated coordinator removes the single point of blocking; Replication of the log converts one coordinator into a quorum; Atomicity survives; liveness may not, and the answer must say which is which.

Evaluate A start-up with three developers must deploy a new application with unpredictable load. Evaluate the choice between IaaS, PaaS and SaaS for their situation, and state how virtualisation underneath supports your choice. 16 marks

Define the responsibility boundary of each model; IaaS: full control, most operational work, needs an administrator; PaaS: the provider patches the runtime and the OS, the team ships code; SaaS: least work, least control, fits only if the application is standard; Small team and unpredictable load favour PaaS plus managed database; Virtualisation gives the provider cheap isolation, snapshots and migration, which is why small units of compute can be rented; Cost model: pay for usage, but beware network egress and idle managed services; State the exit path so the team is not locked in.

Analyze Compare a grid and a cloud for a research group that must run a week-long simulation over data held by five partner institutes. Cover ownership, trust, scheduling, fault tolerance and elasticity. 14 marks

Grid: machines owned by each institute, shared protocols, each site keeps its own policy and identity; Cloud: provider owns the hardware, the customer rents and trusts the provider; Scheduling: grid brokers across administrative domains, with local queues; a cloud allocates instances directly; Fault tolerance: grid jobs checkpoint and restart, since nodes are donated and may vanish; the cloud offers the same via migration and restart; Elasticity: cloud can add a thousand cores for an hour, the grid cannot; Data: in a grid, data usually stays where its owner put it, so move the job to the data; Choose the grid where governance requires the data and machines to stay with the institutes.

Evaluate Cloud monitoring shows a service that scales out correctly but leaks a stale cache entry for exactly the value that drives autoscaling. Evaluate the risk to availability and propose safeguards. 14 marks

Describe the feedback loop: metric, scaling decision, action, re-measure; A stale metric can trigger scale-in while load is high, causing overload; Use a windowed aggregate, not the latest sample; require consecutive breaches; Keep a hard minimum instance count as a floor; Health checks and load balancer removal before termination; Cross-check with an independent signal such as request rate; Alert on the feedback loop itself, not only on the metric.

Evaluate You must choose between replication of data and live migration of virtual machines to survive a host failure. Evaluate both for a 100 GB database that must stay available, and say where each is the better tool. 16 marks

Replication: keep a second up-to-date copy at another host, failover in seconds, application-level consistency rules needed; Migration: moves a running VM, does not protect against host failure by itself; Migration is for maintenance and packing, replication is for fault tolerance; Cost of 100 GB: full copy over the network versus continuous log shipping; Synchronous versus asynchronous replication and the latency it adds; Recovery objectives: recovery time and recovery point; Combine: replicate for availability, migrate for planned maintenance.

Glossary

Address
The location information a system really uses to reach an object, such as a server plus a local file identifier.
Auto-scaling
A control loop that adds or removes instances to keep a chosen metric inside its thresholds.
Blocks
The fixed-size units a file server transfers; a file's size and access pattern decide how many block transfers a read costs.
cgroups
A Linux kernel feature that limits and accounts the CPU, memory and I/O a group of processes may use, forming the basis of containers.
Content delivery network
A set of caches placed close to users that serve copies of static content and shorten the network path.
Grid middleware
The software layer that handles authentication across sites, job submission, data movement and resource discovery in a grid.
Hybrid cloud
Two clouds of different kinds joined by enough portability that workloads and data can move between them.
Hypercall
A deliberate call from a paravirtualised guest into the hypervisor, cheaper than a trap and emulate round.
Identifier
An internal, location-independent handle for a file or object; a name is resolved to it, and the identifier never needs to change.
Load balancer
A component that spreads incoming requests over a set of instances and stops sending to unhealthy ones.
Multitenancy
One running instance serves many customers whose data is kept apart by software, sharing the cost of the hardware.
Namespaces
A Linux kernel feature that gives a process its own view of process IDs, network, mounts and hostname, so it cannot see other tenants.
PaaS
Platform as a Service: the provider runs the OS and runtime; the customer supplies code and data.
Paravirtualisation
Virtualisation where the guest is modified to make hypercalls instead of executing trapped privileged instructions.
Private cloud
Cloud technology operated for one organisation, on its own or rented hardware, with self-service and metering inside it.
Relative name
A name interpreted from the client's current directory rather than from the global root.
Serializability
The correctness rule that the outcome of interleaved transactions equals some serial order of them.
Shadow page tables
Software-maintained tables that map guest virtual addresses straight to host physical addresses, kept in step with the guest's own tables.
Snapshot
A point-in-time copy of a virtual machine's disk and memory state, used as a restore point or as a base for clones.
Soft link
A directory entry holding a text path to another file; resolution restarts at that path, so the link breaks if the target moves.
Stale read
A read that returns an older value than the latest committed write, because it was served from a cache or a replica.
Three-phase commit
An atomic commit protocol that adds a pre-commit phase so participants are not blocked by a single coordinator failure, at more message rounds.
Type-1 hypervisor
A hypervisor running directly on the hardware, with guest operating systems above it.
Virtual organisation
A set of people and sites from different organisations who share resources under agreed rules for the life of a project.
