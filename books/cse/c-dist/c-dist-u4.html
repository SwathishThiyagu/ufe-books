4.1 Characteristics and design challenges of distributed systems

A distributed system is a set of independent computers that cooperate through a network and appear to a user as one system. The computers do not share memory. Each has its own CPU, memory and clock. They exchange data only by messages. This arrangement gives resource sharing, fault tolerance and growth, but it creates design problems: naming, clock synchronisation, partial failure, security and global state. You meet it in UPI payments, IRCTC booking and cloud services, where many machines must act like one.

You need: Unit 1 on shared-memory and distributed-memory architectures, and on speedup and efficiency.

Definition and core characteristics

A distributed system has multiple independent computers. Each computer has its own processor and memory. No variable is shared between machines. A process on one machine can read another machine's data only by sending a message and receiving a reply. The machines run concurrently. Events on different machines can happen at any time relative to each other, and there is no single global clock to order them. This is why logical clocks appear in 4.6.

Other characteristics follow from that separation. Heterogeneity means the machines and networks may differ in hardware, operating system and protocol. Resource sharing means users can use printers, files, databases or compute cycles on other machines. Openness means published interfaces let new components join. Scalability means the system can grow in users, nodes or data without a redesign. Transparency means the system hides its distribution from the user. Middleware is the software layer between the application and the network that builds these transparencies.

Transparency, and distributed versus parallel

Transparency is not one property. Each type hides a different fact, and each needs protocol support. The table states the common types, what each hides, and one example.

Distributed systems are often compared with parallel systems. A parallel system is tightly coupled. Its processors usually share memory and a clock, and its goal is speed on one job. A distributed system is loosely coupled. It has no shared memory and no global clock, and its goals include resource sharing, fault tolerance and growth. A parallel program on 8 cores can use one clock; a distributed program on 8 machines must use messages, as in 4.2, and must handle independent failures. The worked example shows the cost difference.

Architectural models and design challenges

Three common architectural models are client-server, peer-to-peer and three-tier. In client-server, clients request services and a server supplies them. In peer-to-peer, each node can act as both client and server. In three-tier, a presentation tier, a logic tier and a data tier are separated. Some syllabi also list older models: the minicomputer model, where users log in to a few powerful machines; the workstation model, where workstations share file and print services; and the processor-pool model, where a pool of processors is allocated on demand.

  • Naming: a name must map to a location and survive movement or replication.
  • Scalability: adding nodes must not make coordination or lookup collapse.
  • Fault tolerance: a node can fail while others continue; the system must detect, mask or recover.
  • Security: messages cross shared networks, so authentication, confidentiality and access control are needed.
  • Clock synchronisation: crystal clocks drift, so timestamps need bounds; see 4.5.
  • Global state: no machine sees the whole computation, so snapshots need care; see 4.8.

Many early designs failed because they assumed a network is reliable, has zero delay, is secure, and has one administrator. A real network drops packets, delays them, can be attacked, and spans organisations with different policies. Every protocol must be written for loss, delay, attack and multiple owners.

Worked example

Question. One task needs 100 s of CPU work on one machine. It is split over 8 machines on a LAN. The whole job exchanges 5000 messages in total, and each message round trip costs 2 ms. Compute the per-machine compute time, network overhead, total time, speedup and efficiency. Compare with an ideal 8-core shared-memory machine.

  1. Per-machine compute time = 100 s ÷ 8 = 12.5 s.
  2. Network overhead = 5000 × 2 ms = 10 000 ms = 10 s. Use total messages, not messages per machine; per-machine counting would multiply the overhead by 8.
  3. Total time = 12.5 s + 10 s = 22.5 s.
  4. Speedup = 100 s ÷ 22.5 s = 4.44.
  5. Efficiency = 4.44 ÷ 8 = 0.556 = 55.6 percent.
  6. The ideal shared-memory 8-core machine has no message overhead: time = 12.5 s, speedup = 8, efficiency = 100 percent. Real memory contention lowers this.

Answer. The distributed split takes 22.5 s, gives speedup 4.44 and efficiency 55.6 percent; the ideal shared-memory split takes 12.5 s.

Exam traps

  • Writing only 'many computers working together'. Marks come from consequences: no shared memory, no global clock, independent failures, and the transparencies built to hide them.
  • Treating parallel and distributed as synonyms. Parallel is tightly coupled with shared memory and a common clock, built for speed; distributed is loosely coupled with messages and independent failures, built for resource sharing and fault tolerance.
  • Swapping migration and relocation transparency. Migration means a resource has moved; relocation means it moves while you are using it.
  • Using 'each machine sends 5000 messages' as 5000 messages in total. If 8 machines each send 5000 one at a time, overhead is 8 × 10 s = 80 s, not 10 s; if they send in parallel, the wall time stays near 10 s. Read whether the count is total or per machine.
  • Assuming a network is reliable, zero-delay, secure and has one administrator. Real networks drop, delay, can be attacked and cross owners.

4.2 Message passing versus shared memory; communication primitives

Processes on different machines cannot read each other's variables. They exchange data as explicit messages. A message-passing system gives each process two primitives: send and receive. Buffering, blocking, reliability and order are all properties of those two calls. Shared-memory threads instead use ordinary reads and writes in one address space. The same send and receive primitives sit under sockets, MPI, remote procedure calls and microservices. This chapter compares the two models and classifies the primitives, so you can judge cost and spot bugs before writing code.

You need: Chapter 4.1 for why there is no shared memory.

Shared memory and message passing

Shared memory means several threads run in one address space. One thread writes a variable and another reads it with a normal load or store. Pthreads and OpenMP use this model. The hardware must keep caches coherent, and the language must define a memory consistency model; see Unit 3 for those details. One machine can scale this way to a few sockets, but not across a network.

Message passing means each process has its own address space. A process cannot read the other's variables. It calls send with a destination and a message. The receiver calls receive, which gives a message and usually the sender's identity. The kernel or network card copies the bytes from the sender's buffer into a kernel buffer, then into the receiver's buffer. The channel is the logical link between them.

The design reduces to how send and receive behave: when they return, what they copy, what happens if no message is waiting, and what order messages keep. Interprocess communication (IPC) is the general name for this exchange.

Shared memory costs a load or store but no copy; message passing costs a kernel copy and a system call per message, and that copy is the price of running across machines.

How send and receive behave

A blocking send returns only when the sender may safely reuse its buffer. A blocking receive returns only when it has a message. A non-blocking send or receive returns at once; the call reports completion or gives a handle to test later.

A synchronous send, also called rendezvous, waits until a matching receive has started or taken the message. An asynchronous send copies the message into a buffer and returns. Buffering is storage between sender and receiver. With an unbounded buffer, a sender never waits for space. Real buffers are finite, so an asynchronous send can still block when the buffer is full.

Direct communication names the partner process. Indirect communication uses a mailbox or port: the sender names the mailbox, and the receiver reads from it. A reliable primitive reports loss or retries. An unreliable one may drop messages. A channel may preserve FIFO order or not; group ordering is in Chapter 4.9.

Send and receive block independently. Four combinations exist: blocking send with blocking receive; blocking send with non-blocking receive; non-blocking send with blocking receive; and non-blocking send with non-blocking receive. All four are legal; each side picks its own primitive. A non-blocking send needs a buffer to hold the message until the receiver asks for it. Real systems provide that buffer, so non-blocking send with blocking receive is common. Only a system with no buffering at all can lose the message.

Cost model and buffering

Measure a message by startup latency L and bandwidth B. L is the fixed cost per message: system call, kernel copy, network stack and interrupt. B is the sustained rate in bytes per second. The transfer time for m bytes is m / B. The total is

T = L + m / B

T is total time in seconds; L is startup latency in seconds; m is message size in bytes; B is bandwidth in bytes per second.

Startup dominates small messages. Sending many small messages pays L many times, so batch items into one large message when the application allows it. Bandwidth sets the floor for large messages.

Buffering hides delay. The sender copies into a kernel buffer, so the receiver can run later. The unbounded-buffer assumption lets a model ignore send blocking. Real systems bound the buffer; when it fills, send blocks or fails. A blocking receive with no matching message waits forever unless it uses a timeout.

Use the model to choose message size. If L is 50 µs and B is 125 MB/s, one 1 MB message costs about 8.05 ms; one thousand 1 KB messages cost about 58 ms. The worked example does the arithmetic.

Worked example

Question. A link has bandwidth 1 Gbps and startup latency 50 µs. Send a 1 MB message as one message, then as 1000 messages of 1 KB. Use 1 MB = 1,000,000 bytes and 1 KB = 1000 bytes. Find the transfer time, total time, and slowdown ratio.

  1. Convert bandwidth: 1 Gbps = 1×10⁹ bits/s. Divide by 8: B = 125×10⁶ bytes/s = 125 MB/s.
  2. One 1 MB message: m = 1,000,000 bytes. Transfer time = m / B = 1,000,000 / 125,000,000 = 0.008 s = 8.0 ms.
  3. Startup latency L = 50 µs = 0.05 ms. Total time = 8.0 + 0.05 = 8.05 ms.
  4. One small message: m = 1000 bytes. Transfer time = 1000 / 125,000,000 = 8×10⁻⁶ s = 8 µs. Each total = 50 + 8 = 58 µs.
  5. For 1000 small messages: total = 1000 × 58 µs = 58,000 µs = 58.0 ms.
  6. Slowdown ratio = 58.0 ms / 8.05 ms ≈ 7.2.

Answer. One 1 MB message takes 8.0 ms of transfer plus 0.05 ms startup, total 8.05 ms. The 1000 small messages take 58.0 ms. Slowdown ratio = 58.0 ms / 8.05 ms ≈ 7.2, so the small messages are about 7.2 times slower.

Exam traps

  • Asynchronous send does not mean the message arrives immediately. It means the sender does not wait; delivery delay is unchanged.
  • Non-blocking send with blocking receive is legal and common when a buffer exists to hold the message until the receiver asks. Only a system with no buffer at all can lose the message, because the send returns before the receive asks and the bytes have nowhere to wait.
  • Bandwidth units: 1 Gbps = 125 MB/s, not 1000 MB/s. Divide bits per second by 8 to get bytes per second.
  • Startup latency is charged per message, not per byte. Sending 1000 small messages pays the startup cost 1000 times.
  • Cache coherence is a shared-memory issue. It is not a message-passing primitive and does not order messages on a channel.

4.3 Interprocess communication and remote procedure call

Interprocess communication (IPC) is how processes exchange data when they do not share memory. The processes may be on the same machine (pipes, shared memory) or on different machines (sockets). Remote procedure call (RPC) builds on IPC across machines: it hides the send and receive behind a function call, so a client calls a procedure that runs on a server. RPC is used in web services, microservices, distributed databases and file systems.

You need Chapter 4.2 for send and receive primitives.

IPC forms and the RPC path

A process cannot read another machine's memory. It must use an interprocess communication (IPC) mechanism that moves bytes or messages. Four standard forms are:

  • Socket: an endpoint named by an IP address and a port; two processes exchange a byte stream or datagrams.
  • Pipe: a one-way byte stream between processes, usually related processes on one machine.
  • Message queue: a kernel-held queue of discrete messages; sender and receiver need not run at the same time.
  • Shared-memory segment: one memory region mapped into two processes on the same machine; fastest, but needs separate synchronisation.

RPC builds request and reply on top of IPC. The client writes an ordinary call; a local stub turns it into messages, and a server stub turns messages back into a call.

  1. The client calls the client stub. The call looks like a local procedure, with the same name and arguments.
  2. The client stub marshals the arguments. Marshalling packs values into an agreed byte format; a pointer value is not valid on another machine, so arguments cross by value.
  3. The transport sends the request message to the server host and port.
  4. The server stub unmarshals the arguments and calls the real server procedure.
  5. The server procedure computes and returns its result to the server stub.
  6. The server stub marshals the result into a reply message.
  7. The client stub receives the reply, unmarshals the result, and returns it to the client.

Binding is how the client finds the server: a name or directory service maps a service name to a host and port. The request carries a procedure identifier so the server stub knows which procedure to call.

Call semantics and differences from a local call

A lost reply leaves the client unsure whether the server ran the procedure. Three call semantics describe the promise:

  • At-most-once: the client sends one request and never retries; the procedure may not run if the request is lost.
  • At-least-once: the client retries until a reply arrives; the procedure can run more than once.
  • Exactly-once: the client sees one execution; the server must detect duplicate requests, usually with request IDs and stored replies.

Exactly-once is hard because the server and client can fail independently. If the server crashes after computing but before replying, the client cannot tell that from a lost reply. An idempotent operation can be repeated safely — for example, reading a record — but a non-idempotent operation such as debiting ₹500 must not be repeated blindly.

RPC differs from a local call in four ways: latency is milliseconds not nanoseconds; partial failure is normal; there is no shared address space; and parameters pass by value only, so pointers and object references cannot cross.

Worked example

Question. A program makes 10,000 calls. A local call costs 0.1 µs. The same calls as RPC over a LAN cost 2 ms per round trip. Find the local loop time, the remote loop time, and the slowdown ratio.

  1. Local time = 10,000 × 0.1 µs = 1,000 µs.
  2. Convert to ms: 1,000 µs ÷ 1,000 = 1 ms.
  3. Remote time = 10,000 × 2 ms = 20,000 ms.
  4. Convert to s: 20,000 ms ÷ 1,000 = 20 s.
  5. Slowdown = 20 s ÷ 1 ms = 20,000 ms ÷ 1 ms = 20,000.

Answer. The remote loop takes 20 s, which is 20,000 times the 1 ms local loop.

Exam traps

  • RPC is not a local call: pointer arguments cannot cross the network; pass data by value.
  • Exactly-once is not free: it needs duplicate detection at the server; a simple timeout and retry gives at-least-once.
  • A lost reply is not the same as a failed procedure; the server may have run it.
  • At-most-once may not run at all; at-least-once may run twice.

4.4 Model of distributed computations; synchronous vs asynchronous

A distributed computation is a set of processes, each running its own sequence of events. Events are internal steps, sends and receives. The only link between processes is messages. The model says what we may assume about timing, message delay and failures. Those assumptions decide whether a timeout is a proof or a guess. The same code can be correct on one model and wrong on another. This chapter sets out the synchronous and asynchronous models and the round-based programs that sit between them.

You need: Chapter 4.1 for what a distributed system is, and Chapter 4.2 for send and receive.

Processes, events and an execution

A process is a program running on one computer. Its local history is the sequence of events it performs. An event is one of three things: an internal step (a local computation), a send of a message, or a receive of a message. A send and its matching receive are two events, one in each process. They are linked by the message, not by a shared clock.

An execution (also called a run) is one complete set of events of all processes plus the messages between them. The events of one process are totally ordered: that process does them one after another. Events of different processes are not automatically ordered. If no message chain connects two events, either order is possible. So an execution is a partial order, not a single sequence. This is why two machines can disagree about which of two events happened first; Chapter 4.6 turns this into logical clocks.

A state-based view treats each process as a state machine. It has a state s and a transition function δ: on an event e it moves to s′ = δ(s, e). A send adds a message to a channel; a receive removes one. The global state is the vector of local states plus the messages in transit. Snapshot algorithms in Chapter 4.8 capture such a global state without stopping the system.

A failure model says what can go wrong. The common ones are crash (a process stops and stays stopped), fail-stop (a crash that other processes can detect), omission (a process fails to send or receive some messages), and Byzantine (a process may behave arbitrarily, including lying). This chapter only names them; Unit 5 develops them.

Synchronous model: bounds you can trust

In the synchronous model every process takes a known maximum time to execute one step, and every message takes a known maximum time Δ to reach its destination. Δ is a time bound in seconds or milliseconds. The model does not require the clocks of the machines to show the same time. It requires only that the delay is bounded.

With these bounds an execution can be organised in rounds. In each round every process sends its messages, then receives the messages sent in that round, then does local work. A slow process cannot fall behind forever: its step time is bounded. A late message cannot arrive after the round ends: its delay is bounded by Δ. A timeout can therefore be set safely. If a reply does not arrive within the bound, the sender knows that something has failed, not merely that the network is slow.

T_max = n × w + (n − 1) × Δ

T_max is the worst-case finish time of a chain; n is the number of processes; w is the maximum work time per process; Δ is the maximum message delay.

This makes the synchronous model easy to reason about. It is used in real-time control, in some hardware buses, and as a teaching model for parallel algorithms. The cost is that the bounds must be true. On the public Internet a router queue can grow without a small fixed limit, so the model often fails. A semi-synchronous model keeps one bound, often on local step time, and drops the other, often on message delay. It is a common middle ground.

Asynchronous model and round-based programs

Control of a distributed computation means deciding when each process may proceed; the model sets what that control may assume. In the asynchronous model there is no upper bound on message delay and no bound on the time a process takes between steps. A message may take one millisecond or twenty seconds; both are legal. There is no shared clock that can be used to compare events across processes. No timeout can be trusted: a missing reply may mean a crashed process or a very slow one. The consequence is strong. Some problems cannot be solved at all in this model without extra assumptions. Detecting whether a process has crashed is one example; consensus is another. Unit 5 takes up those problems.

Programs still need structure. One common structure is asynchronous execution with synchronous communication. The program is written as rounds: in round r each process sends to a fixed set of neighbours and receives one message from each. The network is asynchronous, but a synchroniser delays the start of round r + 1 until all messages of round r have been delivered. The program then behaves as if it were synchronous, because the logical order of rounds is preserved. This is the basis of synchronisers and of many parallel libraries.

The same idea is called synchronous program order on an asynchronous system. The program's logical order is fixed by sends and receives; real time is not bounded. A receive waits for the matching message, and the code after it runs only when that message has arrived. The order of statements is preserved even when the actual delay is unknown. This is the order that logical clocks in Chapter 4.6 and vector clocks in Chapter 4.7 describe.

Worked example

Question. Four processes P1, P2, P3 and P4 form a chain. Each does 5 ms of local work and then sends one message to the next process. In a synchronous system every message delay is at most 20 ms. (a) Find the maximum time for the chain to finish. (b) Is a 100 ms timeout safe? (c) What changes in the asynchronous model?

  1. Work intervals: 4 processes × 5 ms = 20 ms of local work in total.
  2. Message hops: P1→P2, P2→P3 and P3→P4, so 3 hops. Maximum delay = 3 × 20 ms = 60 ms.
  3. Worst-case finish time = 20 ms + 60 ms = 80 ms.
  4. Timeout slack = 100 ms − 80 ms = 20 ms. Since 20 ms ≥ 0, the timeout is safe in the synchronous model.
  5. In the asynchronous model no delay bound exists. One message may legally take 20 s, so the same 100 ms timeout is a guess, not a guarantee.

Answer. The chain finishes within 80 ms, so a 100 ms timeout is safe with 20 ms of slack in the synchronous model; in the asynchronous model it is only a guess.

Exam traps

  • Asynchronous message passing does not mean non-blocking send. It means no bound on delay. A blocking receive can exist in an asynchronous system.
  • A synchronous model does not require identical physical clocks. It requires bounded step time and bounded message delay.
  • In an asynchronous system a timeout is not evidence of a crash. A slow process and a crashed process look the same.
  • An execution is a partial order. Do not draw it as one global time line unless you add a total-order assumption.
  • Synchronous communication (blocking send and receive) is not the synchronous model. A program can use blocking sends on an asynchronous network.

4.5 Physical clock synchronization and NTP

Every computer carries its own quartz clock. The crystal runs at a slightly different rate from every other crystal, so two machines that start together slowly separate. This difference makes a timestamp from another machine unsafe as a real-time order. Clock synchronisation keeps each machine within a known bound of a reference such as UTC. NTP is the standard Internet service that does this. It matters for logs, banking timestamps, distributed databases, and any protocol that compares times across machines.

You need: Chapter 4.4 for the system model and what a timing assumption means.

Drift, skew and Cristian's bound

Each physical clock is a counter driven by a crystal oscillator. Its reading is not true time; it is an estimate. Clock skew is the instantaneous difference between two clocks. Drift is the rate at which that difference grows, measured in parts per million (ppm). A drift of 1 ppm changes a reading by 1 microsecond per second. Skew is a position; drift is a speed.

Synchronisation is external if every clock is kept near a real reference such as UTC. It is internal if the clocks are kept near each other, even when the group is slightly away from UTC.

Cristian's algorithm uses a time server. The client sends a request and the server replies with its time. The client measures the round-trip time RTT and sets its clock to the server time plus RTT/2. The error is at most RTT/2: the reply cannot take less than zero time or more than the whole RTT. This is a bound, not an exact correction.

NTP hierarchy and Berkeley

NTP (Network Time Protocol) arranges servers in strata. Stratum 0 is not a server: it is a reference clock such as a GPS receiver. A primary server at stratum 1 is attached to that reference. Secondary servers at stratum 2 and below take time from a higher level. A client queries several servers, discards outliers, and combines the rest.

The exchange records four timestamps: T1, client sends; T2, server receives; T3, server replies; T4, client receives. The estimates are

θ = [(T2 − T1) + (T3 − T4)] / 2

θ is the estimated offset: server clock minus client clock. Positive θ means the client is behind.

δ = (T4 − T1) − (T3 − T2)

δ is the round-trip delay after removing the server's processing time T3 − T2.

The true offset lies within θ ± δ/2; the midpoint is exact only when the two one-way delays are equal.

The Berkeley algorithm is for a local group. A coordinator polls each node, computes offsets, averages them after dropping an outlier, and tells each node how much to adjust. No external reference is needed. On a LAN, NTP is accurate to milliseconds; across the Internet, the bound is worse because paths are asymmetric. Where no such bound is acceptable, use logical clocks (Chapter 4.6).

Worked example

Question. An NTP exchange gives T1 = 1000 ms, T2 = 1100 ms, T3 = 1105 ms, T4 = 1120 ms. Find θ, δ, and the offset error bound. Which way must the client clock move?

  1. θ = [(T2 − T1) + (T3 − T4)] / 2.
  2. T2 − T1 = 1100 − 1000 = 100 ms.
  3. T3 − T4 = 1105 − 1120 = −15 ms.
  4. θ = (100 − 15) / 2 = 85 / 2 = 42.5 ms.
  5. θ is positive: server ahead, client 42.5 ms behind, move forward.
  6. δ = (T4 − T1) − (T3 − T2) = 120 − 5 = 115 ms.
  7. Error bound = ±δ/2 = ±57.5 ms; true offset in 42.5 ± 57.5 ms.

Answer. Client moves forward by 42.5 ms; δ = 115 ms; offset error bound ±57.5 ms.

Exam traps

  • Halving the full round trip and calling it the offset. It is only a bound unless server processing is zero and the two one-way delays are equal.
  • Forgetting to subtract server processing time T3 − T2 from the delay.
  • Wrong sign: θ positive means the client is behind, not ahead.
  • Treating Cristian's correction as exact; it is exact only when the two one-way delays are equal.

4.6 Logical clocks: happened-before and scalar time

Lamport timestamps solve a narrow but vital problem: giving a consistent order to events spread over machines whose physical clocks disagree. Each process keeps one integer. It increments the integer for every event, and on receiving a message it jumps above the sender's timestamp. This scalar clock respects the happened-before relation: if event a can have influenced event b, then a's timestamp is smaller. It cannot detect concurrency, because smaller timestamps do not prove influence. The idea is used in distributed mutual exclusion, logging, debugging and any protocol that needs a cheap global order without synchronised clocks.

You need: Chapter 4.4 for events and the asynchronous model, and Chapter 4.5 for why physical clocks cannot order events across machines.

Happened-before: the only order we can trust

Physical clocks on separate machines drift, and NTP leaves a bounded error. So real timestamps cannot decide which of two events came first. Lamport asked a smaller question: could event a have influenced event b? He wrote a → b for "a happened before b". The relation has three rules.

  • If a and b are events in the same process, and a occurs before b in program order, then a → b.
  • If a is the send of message m and b is the receive of the same m, then a → b.
  • The relation is transitive: if a → b and b → c, then a → c.

If neither a → b nor b → a, events a and b are concurrent. Concurrent does not mean simultaneous. It means no chain of program order and messages connects them, so one cannot have caused the other. This partial order is the causality we can defend without synchronised clocks.

Lamport's scalar clock rules

Each process Pi keeps one integer Ci, its scalar logical clock. The starting value is arbitrary; usually it is 0. Three rules update it and stamp events.

  1. Before every event in Pi, set Ci = Ci + 1. The event's timestamp is the new value.
  2. If the event is a send of message m, put the timestamp Ci inside m.
  3. On receiving message m with timestamp t, set Ci = max(Ci, t) + 1. The receive event gets this new value.

a → b ⇒ C(a) < C(b)

a and b are events; C(e) is the Lamport timestamp of event e; → is happened-before. This is the clock condition.

The condition holds by induction over the three rules. Inside one process, each event adds at least 1, so order is preserved. For a send and its receive, the sender stamps t, and the receiver sets C = max(local, t) + 1, which is strictly greater than t. Transitivity follows because < is transitive. The converse is false: C(a) < C(b) does not prove a → b. That gap is the whole limitation of scalar time.

Total order and its limit

Lamport timestamps give every event a pair (C(e), i), where C(e) is the timestamp and i is the process id. Sorting these pairs lexicographically gives one total order that every process can compute. If two events have equal timestamps, the process id breaks the tie. This is useful when a system needs all sites to agree on one order, as in Lamport's distributed mutual exclusion algorithm (see Unit 5).

The total order is consistent with causality, but it adds order between concurrent events. Two concurrent events get some order only because the tie-break rule is arbitrary. For causality exactly, use Chapter 4.7 and vector clocks. If storing one counter per process is too heavy, direct dependency clocks keep counters only for processes a site directly depends on; they reduce state but still do not make the converse true.

Worked example

Question. Three processes P1, P2 and P3 run in an asynchronous system. All scalar clocks start at 0. P1 has internal event a, then sends message m1 to P2. Answer. The eight timestamps in event order are a = 1, send m1 = 2, c = 1, receive m1 = 3, send m2 = 4, f = 1, g = 2, receive m2 = 5. Exam traps

  • C(a) < C(b) does not mean a → b. The clock condition runs one way only; a smaller timestamp can belong to a concurrent event.
  • Equal timestamps on different processes do not order events. If a → b then C(a) < C(b), so equal values rule out causality; the events are concurrent.
  • On receive, do not do C = C + 1 and ignore the message timestamp. The rule is C = max(C, t) + 1, so the receive is later than the send.
  • The timestamp of a send is taken after the increment for that send event, not before. A common slip is to attach the old value.
  • Program order applies only inside one process. Event 3 in P1 and event 3 in P2 are not ordered by the number 3 alone.

4.7 Vector clocks and causality

Scalar clocks give one number per event. They order events that are causally related, but they cannot tell whether two events are unrelated. A vector clock keeps one counter for every process. Comparing two vectors then gives three answers: earlier, later, or concurrent. This is the standard tool for detecting causality in distributed systems, from debugging traces to replicated databases. This chapter gives the vector-clock rules, proves the comparison theorem, and states the cost: n integers per message for n processes.

You need Chapter 4.6 for happened-before and scalar clocks.

Vector clock rules

A vector clock assigns a vector V(e) to each event e. For n processes, the vector has n entries, one per process. Entry i counts the events of process Pi that are in the causal history of e. All entries start at 0.

  1. At every local event, Pi increments its own entry V[i] by 1. This includes sends, receives and internal events.
  2. On a send, the message carries the sender's current vector. This is the vector after the send event has incremented the sender's entry.
  3. On a receive of a message with vector W, Pi first sets V[j] = max(V[j], W[j]) for every j. Then it increments V[i] by 1 for the receive event.
  4. Compare two events a and b component by component. V(a) ≤ V(b) means every entry of V(a) is less than or equal to the same entry of V(b).

V(a) < V(b) iff V(a) ≤ V(b) and V(a) ≠ V(b)

V(a) and V(b) are vector timestamps of events a and b; V(a) ≤ V(b) means every entry of V(a) is less than or equal to the same entry of V(b). If neither V(a) ≤ V(b) nor V(b) ≤ V(a), the events are concurrent.

Why the comparison is exact

The central theorem is: for any two events a and b, a → b if and only if V(a) < V(b). Here a → b means a happened before b in the sense of Chapter 4.6.

First direction. If a → b, prove V(a) < V(b) by induction on the length of the causal chain from a to b. For one step on the same process, the later event has a larger own entry and equal other entries. For one message step, the receiver takes the component-wise maximum, so every entry is at least the sender's entry; the receive increment makes its own entry strict. Induction adds the steps.

Second direction. If V(a) < V(b), let a be the k-th event of process Pj. Then V(a)[j] = k. The inequality gives V(b)[j] ≥ k. By the invariant below, V(b)[j] counts how many events of Pj are in the causal history of b. Since events on one process are ordered, that history contains a. So a → b.

The invariant: after every event e, V(e)[i] equals the number of events of Pi in the causal history of e. The two update rules preserve it: a local event adds itself, and a receive adds the sender's known history before adding itself.

Cost: each message carries n integers for n processes. The overhead grows with group size, so vector clocks suit groups where exact causality matters more than bandwidth. The same counters appear as version vectors in replicated data; see Unit 6.

Checks and use

To check any proposed clock algorithm, verify two things. First, the local rule must make the own entry increase at every event. Second, the receive rule must take the component-wise maximum and then increment. Then prove the theorem by induction on the length of the causal chain, as above.

Vector comparison is not arithmetic. Never compare by the sum of entries or by a single entry. The vectors (2,0,0) and (0,0,1) have sums 2 and 1, but neither is ≤ the other, so the events are concurrent.

Causal message delivery uses exactly this test; see Chapter 4.9. Replicated stores use the same idea under the name version vectors to decide whether two versions are ordered or concurrent; see Unit 6. Some syllabi call happened-before potential causality. The vector is the same relation, made computable.

4.8 Global state and consistent snapshots

A global state is the local state of every process together with every message in transit on the channels. A snapshot is consistent when, for every message, it contains the send and the receive or neither. Chandy and Lamport record such a snapshot without stopping the system by sending markers over FIFO channels. The result may not match any single real instant. Snapshot algorithms support checkpointing, termination detection and deadlock detection.

You need: FIFO channels and the asynchronous model from Chapter 4.2 and Chapter 4.4, and causal knowledge from Chapter 4.7.

Local states, channels and cuts

A distributed computation runs on n processes P1, P2, ..., Pn. Each process has a local state: the values of its variables and its program counter at a point in its run. A run is the actual sequence of events at all processes. Processes communicate only by messages over directed channels; an asynchronous model means no bound on message delay.

A channel state is the set of messages sent on that channel but not yet received. A global state is every local state plus every channel state. A cut is a frontier that chooses a prefix of events at each process. The cut is consistent if, for every message, a receive inside the cut implies the matching send is also inside the cut. Equivalently, the snapshot must contain both send and receive or neither.

If a receive is inside the cut and its send is outside, the snapshot shows a message arriving from nowhere. That is an inconsistent cut. If the send is inside and the receive is outside, the message is in transit. The cut is still consistent. But when you add up the totals, the channel state must include that message, or the total is short.

S = Σ L(Pi) + Σ C(c)

S is the snapshot total for an additive quantity such as money; L(Pi) is the local state of process i; C(c) is the state of channel c, meaning messages sent but not received in the cut.

Chandy–Lamport marker algorithm

Assumptions: n processes, directed FIFO channels, no failures, asynchronous timing. FIFO means a marker cannot overtake an earlier application message on the same channel. Only the initiator starts; every process records exactly once.

  1. The initiator records its own local state, then sends a marker on every outgoing channel.
  2. A process that receives its first marker records its own local state and marks that incoming channel empty. It forwards a marker on every outgoing channel.
  3. For every incoming channel, an application message that arrives after the first marker but before the marker on that same channel is appended to that channel's state, not to the process's state.
  4. When a marker arrives on any other incoming channel, the process stops recording that channel; its state is whatever arrived on it after the process recorded its own state and before this marker, and it is empty if nothing arrived.
  5. A message that arrives before the first marker is already reflected in the receiver's local state.
  6. The snapshot is complete when every process has recorded its state and every channel has been marked. The initiator's incoming channels are marked when their markers arrive.

The snapshot is consistent because each channel's marker closes the channel state at a known point. It need not correspond to one instant in real time: processes record at different real times, and the channel states stitch the pieces into one consistent cut.

The snapshot supports checkpointing, termination detection, deadlock detection and evaluation of stable predicates. A stable predicate stays true once true, such as deadlock or termination; an unstable predicate, such as 'A has ₹70', may become false again. For non-FIFO channels the same marker rule fails; extra bookkeeping is needed.

Worked example

Question. Account A holds ₹100 and account B holds ₹100, so the starting total is ₹200. A transfers ₹30 to B by one message. Snapshot S1: A records ₹70 after sending, B records ₹100 before receiving, and the channel A→B holds the ₹30 message. Snapshot S2: A records ₹100 before sending, B records ₹130 after receiving, and the channel is empty. Compute both totals and say which snapshot is consistent.

  1. Starting total = ₹100 + ₹100 = ₹200.
  2. S1: A's local state = ₹70; B's local state = ₹100; channel A→B state = ₹30.
  3. S1 total = 70 + 100 + 30 = ₹200. The send is inside the cut and the receive is outside, so the ₹30 message is correctly held in the channel. S1 is consistent.
  4. S2: A's local state = ₹100; B's local state = ₹130; channel state = ₹0.
  5. S2 total = 100 + 130 + 0 = ₹230. The receive is inside the cut but the send is outside, so S2 is inconsistent.
  6. Money invented by S2 = ₹230 − ₹200 = ₹30.

Answer. S1 totals ₹200 and is consistent; S2 totals ₹230, invents ₹30, and is inconsistent.

Exam traps

  • Believing a snapshot must be instantaneous or must stop the system. Chandy–Lamport records a consistent cut while processes keep running.
  • Forgetting channel states. A message sent inside the cut but not yet received must appear in the channel state, or the total is short.
  • Putting a message that arrives after the process's first marker but before the marker on its own channel into the receiving process's local state. That message belongs to that channel's state until that channel's marker arrives.
  • Assuming the same marker rule works for non-FIFO channels. FIFO prevents a marker from overtaking an earlier message; non-FIFO needs extra bookkeeping.
  • Confusing a consistent snapshot with the real system state at one real time. The local states may be recorded at different real times.

4.9 Message ordering and group communication

A group is a set of processes that act as one recipient. Group communication sends one message to all members. The network can deliver copies in different orders at different members. If a member acts on a message too early, replicas can diverge. Message ordering gives delivery promises: FIFO, causal and total. Replicated services, chat rooms, stock tickers and cluster control planes use these promises.

You need vector clocks from Chapter 4.7 and consistent snapshots from Chapter 4.8.

Groups and the delivery problem

A group is a named set of processes. The list of current members is the membership. A multicast is one send that creates a copy for every member. Ordinary multicast is best effort: some members may get a copy, others may not. Atomic multicast is stronger: either every current member delivers the message or no member does. A delivery is the moment the message is handed to the application; a receive may only place it in a buffer. This difference is the whole game. A member can receive early and still wait. Ordering rules say when waiting ends. Group communication appears in replicated databases, cluster managers, chat rooms and market-data feeds. Membership change, when a process joins, leaves or is suspected dead, is a hard problem because old and new members must agree on which messages belong to which view. Real systems spend much code there.

Ordering paradigms

Unordered means no promise. FIFO means: for each sender, messages are delivered in send order. If P1 sends m1 then m3, every member delivers m1 before m3. FIFO says nothing about m1 from P1 and m2 from P2; different members may interleave them differently. Causal order adds cross-sender order that follows happened-before. If send(m1) → send(m2), every member delivers m1 before m2. Concurrent messages may still be ordered differently at different members. Total order is a separate axis: every member delivers all messages in one same sequence. Total order does not require that sequence to respect happened-before. A sequencer can put a causally later message first. Causal plus total is the strongest practical service in this unit: one sequence that also respects causality. It is what replicated services need. Ordinary multicast is not atomic; atomic multicast is the all-or-none delivery promise.

Implementing causal and total order

Implement causal order with vector timestamps. Each process keeps Vdel[j] = highest sequence number it has delivered from process j. A message m from sender s carries Vmsg, where Vmsg[j] is the number of messages from j that causally precede m, including m itself for j = s. This is the same vector clock idea as Chapter 4.7. A member delivers m only when two tests pass.

V<sub>msg</sub>[s] = V<sub>del</sub>[s] + 1 and V<sub>msg</sub>[j] ≤ V<sub>del</sub>[j] for every j ≠ s

Vmsg is the message's vector timestamp; Vdel is the receiver's vector of highest delivered sequence numbers; s is the sender's index. The first test is FIFO; the second is causal. If either test fails, buffer m and try again after the next delivery. On delivery, set Vdel[j] = max(Vdel[j], Vmsg[j]) for all j.

Total order has two common implementations. In a sequencer, one process numbers every message 1, 2, 3, ...; members deliver in increasing number. If the sequencer is a bottleneck or failure point, members run an agreement round to choose the next number; that round is consensus, left to Unit 5. Total order alone can reorder causal messages, so real systems combine causal plus total. Atomic multicast needs the all-or-none property; replicated services use it (see Unit 6).

Worked example

Question. P3 starts with Vdel = (0,0,0). It receives m2 from P2 with Vmsg = (1,1,0) before m1 from P1 with Vmsg = (1,0,0). Using causal delivery, decide what P3 buffers and delivers. Give the delivery order and final Vdel. Then a sequencer stamps m1 = 1 and m2 = 2. Give the total-order delivery sequence.

  1. For m2, sender s = P2, so s = 2. FIFO check: Vmsg[2] = 1 and Vdel[2] + 1 = 0 + 1 = 1, so the FIFO test passes.
  2. Causal check for m2: for P1, Vmsg[1] = 1 and Vdel[1] = 0. 1 ≤ 0 is false. Buffer m2. Vdel stays (0,0,0).
  3. For m1, s = P1. FIFO: Vmsg[1] = 1 equals Vdel[1] + 1 = 1. Causal for P2: Vmsg[2] = 0 ≤ Vdel[2] = 0. Deliver m1. Vdel becomes (1,0,0).
  4. Re-check m2: FIFO 1 = 0 + 1; causal for P1: 1 ≤ 1. Deliver m2. Vdel becomes (1,1,0).
  5. Causal delivery order at P3: m1 then m2. Total-order stamps are 1 for m1 and 2 for m2, so total order is also m1 then m2.

Answer. P3 buffers m2, delivers m1, then delivers m2; final Vdel = (1,1,0), and the total-order sequence is m1, m2 with stamps 1, 2.

Exam traps

  • FIFO does not give causal order across senders: FIFO says nothing about m1 from P1 and m2 from P2.
  • Total order does not imply causal order; a sequencer can place a causally later message first.
  • Causal order does not fix one global sequence; two concurrent messages can be delivered in different orders at different members.
  • Receive is not deliver; a received message may wait in a buffer until its ordering tests pass.

Understand Why can FIFO order alone let two replicas diverge? 3 marks

FIFO orders messages from each sender, but not between different senders. One replica may deliver m1 then m2 while another delivers m2 then m1 if the sends are concurrent.

FIFO: 1 = 0 + 1. Causal: for P1, 1 ≤ 1. Yes. Deliver m2, Vdel = (1,1,0).

Analyze A total-order service stamps m2 = 1 and m1 = 2, even though send(m1) → send(m2). Is this allowed? What property is missing? 5 marks

Yes, total order alone only requires one common sequence. It does not require causal order, so the sequence can violate happened-before. The missing property is causal order; causal plus total would forbid it.

Remember What does FIFO order guarantee for one sender? 2 marks

If a sender sends m1 before m2, every member delivers m1 before m2.

Understand Why does the causal algorithm buffer a message instead of dropping it? 3 marks

The message is valid but not yet deliverable; an earlier causal message is missing. Buffering preserves it until the missing message is delivered.

Analyze What does causal plus total order add over causal order alone? 4 marks

Causal order gives happened-before delivery. Total order adds one common sequence for all members. Together every member delivers in the same causal sequence.

Beyond the syllabus

Not for the exam. Industry group communication appears in cluster membership services, replicated logs and publish-subscribe buses. Raft and Paxos are usually described as consensus on a log, but the log gives a total order of commands to replicas. Kafka gives FIFO order within a partition, not total order across partitions. Search for virtual synchrony, sequencer total order, atomic multicast and view change if you meet a real group service.

Takeaways

  1. A distributed system trades the simplicity of shared memory for independence and scale, so every design problem reduces to coping with no global clock, no shared memory and partial failure.
  2. Processes without common memory can only exchange explicit messages, and the design lives in the exact rules for send, receive, buffering and blocking.
  3. Remote procedure call hides the message behind a local-looking stub, and its real difficulties are marshalling, failure detection and repeated execution.
  4. The asynchronous model assumes no bound on delay, so algorithms must be correct under any interleaving; the synchronous model buys simplicity by assuming known time bounds.
  5. Physical clocks drift, so NTP keeps them within a stated bound of UTC by comparing with servers at a known stratum and adjusting rate as well as offset.
  6. Lamport's happened-before relation is the correct notion of causal order; a scalar counter respects it but cannot detect concurrency.
  7. A vector clock is exactly equivalent to happened-before, so it can tell apart causal order from concurrent events at the cost of n counters per timestamp.
  8. A snapshot taken by recording local states independently may be inconsistent; the Chandy-Lamport marker algorithm on FIFO channels gives a consistent one without stopping anything.
  9. Group communication strengthens ordering step by step: FIFO keeps a single sender's order, causal adds happens-before, total forces one common order and also solves mutual exclusion.
  10. Mutual exclusion, leader election and termination detection all reduce to ordering events or agreeing on a common global state.

Exam question bank

Long answers are expected to prove properties, not just describe them: state the system model, give the algorithm, prove the safety property (mutual exclusion, consistency of the snapshot, causal delivery), then argue complexity in number of messages and time delay.

Remember and understand

Understand Define a distributed system and explain the design challenges that arise from having no shared memory, no global clock and only partial failure. Give one Indian application example for each challenge. 12 marks

Definition: independent computers cooperating to appear as one system; Heterogeneity: different hardware, operating systems and languages must interoperate; No global clock: each node has its own crystal, so ordering needs logical clocks or NTP bounds; No shared memory: communication is by messages only, so latency and loss must be handled; Partial failure: a node or link dies while others continue; a node cannot tell a slow node from a dead one; Concurrency, transparency, scalability and security follow from these; Examples: IRCTC booking spread over servers, UPI switch talking to many bank hosts.

Understand Compare message passing with shared memory communication. Explain blocking and non-blocking send and the design consequences of each. 10 marks

Shared memory needs a common address space; message passing needs only a channel; Message passing has explicit copies, so marshalling and data representation matter; Blocking send: sender waits for buffer space or for the receiver, giving flow control but risking deadlock; Non-blocking send with buffering returns immediately, needs unbounded or bounded buffers and a policy for overflow; Receive may be blocking or non-blocking too; message addressing by name, mailbox or port; Trade-offs: performance, copying cost, simplicity of reasoning.

Understand Describe remote procedure call step by step. Explain marshalling, stubs, the client-server binding, and the failure semantics of RPC. 12 marks

Client calls a local stub with the same signature as the remote procedure; Stub marshals arguments into a message, sends it, and blocks on the reply; Server stub unmarshals, calls the real procedure, marshals the result, sends it back; Client stub unmarshals the result and returns it to the caller; Binding: how the client learns the server address and port; Failures: lost request, lost reply, server crash; may-execute, at-least-once, at-most-once semantics; Idempotent operations make retries safe; at-most-once needs duplicate filtering with call identifiers.

Remember Define the happened-before relation and state the scalar logical clock rules. Prove that a → b implies C(a) < C(b), and show with an example that the converse fails. 10 marks

Relation defined by program order, message send-receive pairs, and transitivity; IR1: C increments between two events of the same process; IR2: on receive the clock is set to max(local, message timestamp) + 1; Proof by induction along the chain of the relation; Counterexample: two concurrent events can still have unequal scalar timestamps, so concurrency is not detectable.

Apply

Apply Three processes p1, p2 and p3 execute with six messages. Given the event trace, compute the scalar and vector timestamps of every event, and list all pairs of concurrent events. 13 marks

Apply C = max(C, received) + 1 at each event for scalar clocks; Apply V[j] = max over the two vectors, then increment own entry, for vector clocks; Message carries the sender's timestamp at the send event; Compare vectors: V(a) ≤ V(b) and V(a) ≠ V(b) gives a → b; Concurrency when neither vector dominates the other; Correct step-by-step table of timestamps.

Apply Explain the Chandy-Lamport snapshot algorithm for FIFO channels. Trace it on a three-process system and show why the recorded state is consistent. 13 marks

Any process may start by recording its state and sending a marker on every outgoing channel; A process records its state at the first marker it receives and marks that channel empty; Markers on other incoming channels are forwarded after the state is recorded; A channel's state is the sequence of application messages received after the state was recorded and before the marker on that channel; FIFO guarantees no application message can overtake the marker; Proof: for every message either both send and receive are inside the snapshot or neither; Termination: each process records once and each channel contributes finitely.

Apply Describe how NTP synchronises a client to UTC. Explain offset and round-trip delay computation, strata, and how the client decides which servers to trust. 12 marks

Client sends a request stamped with its local time, server replies with its own receive and transmit times; Offset θ = ((T2 − T1) + (T3 − T4)) / 2, delay δ = (T4 − T1) − (T3 − T2); Assumes roughly symmetric path delay; the error is bounded by δ/2; Stratum 0 is the reference clock, stratum 1 servers attach directly, higher strata sync from lower; Selection and clustering algorithms filter falsetickers; the client keeps a set of survivors; Clock is disciplined by slewing (adjusting rate) for small errors and stepping for large ones.

Apply Design a causal-order multicast for a group of n processes. State the algorithm, and prove that it delivers messages in an order consistent with happened-before. 13 marks

Each process keeps a vector clock and a delivery queue; Sender increments its own entry and attaches the vector to the message; A message is deliverable when it is next in the sender's sequence and all other entries in its vector are already delivered; Hold undeliverable messages in a queue and re-check on each delivery; Safety: any causally earlier message has a smaller vector entry and is therefore delivered first; Liveness: the message that is next in the required order eventually becomes deliverable; Cost: n counters per message and per process.

Analyze and evaluate

Analyze Compare scalar clocks and vector clocks for detecting causality. Prove both directions of the vector clock theorem and state the cost of each scheme. 13 marks

Scalar: a → b implies C(a) < C(b); the converse is false, so concurrency is invisible; Vector: V(a) < V(b) if and only if a → b; Forward proof by induction over the happened-before chain; Backward proof by contradiction, using the fact that a counter can only grow when its own process takes a step; Concurrency test: neither vector dominates the other; Cost: scalar needs O(1) space and O(1) per message, vector needs O(n) both; Optimisation: direct dependency clocks, and skipping entries for processes that never communicate.

Analyze Compare FIFO, causal and total order broadcast. For each, give an application where the weaker order is enough and one where it is not. 12 marks

FIFO: messages from the same sender are delivered in send order; different senders may be reordered; Causal: delivery respects happened-before; needed for a reply to arrive after its question; Total: all members deliver in one common order; needed when replicas must agree, e.g. a shared account balance; Total order plus FIFO gives causal order, but causal does not give total; Total order broadcast is equivalent to consensus in the asynchronous crash model; Applications: chat, replicated state machine, distributed lock service.

Evaluate Distributed mutual exclusion can be built on Lamport timestamps, on a token, or on quorums. Compare them on message complexity, delay, and tolerance to failure, and state what each assumes. 14 marks

Timestamp algorithm: request with timestamp, all grant, release; 2(n−1) messages per entry, needs total order on requests; Token ring: 0 messages when idle, 1 to n−1 to pass the token, delay grows with ring size, a lost token stalls the system; Quorum: ask a majority, needs 2 out of 3 or majority sets; tolerates node failure but more messages than a token; Assumptions: FIFO channels, known membership, no byzantine faults; Fairness: timestamp order is fair, token passing may be unfair; Failure handling: election of a new token holder, or lease-based timeouts.

Evaluate Explain why a set of independently recorded local states may be inconsistent, and state the exact condition a consistent global state must satisfy. Show how the Chandy-Lamport algorithm satisfies it under FIFO channels. 13 marks

Local state recording at arbitrary times can record a receive without its send; Consistency condition: for each message, sent is in the snapshot if and only if received is; In-transit messages form part of the global state and must be recorded; Markers cannot overtake application messages on FIFO channels, so a channel's recorded sequence ends exactly at the marker; State the theorem and sketch the proof in both directions; Note the limitation: channel must be FIFO; non-FIFO needs extra bookkeeping.

Analyze A client retries a money-transfer RPC after a timeout and the balance is debited twice. Analyse the cause using RPC failure semantics and propose a fix. 12 marks

Timeout does not mean the call failed; the server may have executed it; At-least-once semantics with retries gives duplicate execution; Non-idempotent operation: a transfer cannot be repeated safely; Fix: unique request identifier per call and a duplicate filter at the server; Fix: at-most-once protocol with cached replies, or a transaction with commit and abort; Idempotency by design: use a transfer id and make the server reject repeated ids.

Glossary

Binding
The step in which a client learns the network address and port of the server that offers a required interface.
Causal order
Delivery order that never places an effect before its cause, i.e. respects the happened-before relation between messages.
Channel
A directed path by which messages travel from one process to another; it may reorder or delay messages unless declared FIFO.
Configuration
For each process, its sequence of events plus, for each message, the send and receive events that pair together.
Cristian's algorithm
A client asks a time server for its time and adds half the measured round-trip delay to estimate the correct time.
Global predicate
A property of the whole distributed computation that depends on all local states, such as deadlock or termination.
Group communication
A service that sends one message to many receivers with a stated ordering and membership guarantee.
Idempotent operation
An operation that gives the same result and the same effect when executed more than once.
Lamport's condition
The requirement a → b implies C(a) < C(b), which any correct logical clock must satisfy.
Leader election
Choosing one process among a group to act as coordinator, agreeing on the choice and handling failures.
Marker
A control message used by the snapshot algorithm to separate messages already received from messages still in transit.
Marshalling
Encoding arguments and results into a flat byte format so they can be transmitted and decoded on another machine.
Membership
The set of processes currently considered part of a group, with agreement on its view among the participants.
Message buffer
Storage at the sender, receiver or channel that holds messages until they are consumed.
Openness
The property that interfaces are published so components from different vendors can be added and combined.
Physical clock
A counter driven by a quartz oscillator that approximates real time and is read as a timestamp.
Process
A single sequential thread of control in a distributed computation; its events form a total order.
Scalability
The ability of the system to keep working well as the number of users, nodes or messages grows.
Slew
Correcting a clock gradually by running it slightly faster or slower, instead of jumping it, to avoid time going backwards.
Socket
An endpoint of a communication channel, identified by an address and a port, over which messages are sent and received.
Strong consistency of clocks
The stronger condition that C(a) < C(b) if and only if a → b, achievable only with vector or equivalent clocks.
Termination detection
Deciding that no process is active and no message is still travelling, so the whole computation has finished.
Transparency
The property that distribution is hidden from users and programmers, in access, location, migration, replication, concurrency and failure.
UTC
Coordinated Universal Time, the reference time scale to which network clocks are synchronised.
Virtual synchrony
A guarantee that membership changes and messages delivered in the same view are seen in the same order by all members.
