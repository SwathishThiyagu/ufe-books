5.1 Distributed mutual exclusion: Lamport and Ricart-Agrawala

One printer, one bank account, or one record in a replicated database can be touched by only one process at a time. Distributed mutual exclusion gives that guarantee when processes share no memory and talk only by messages. Each process asks with a timestamp. Lamport's algorithm uses REQUEST, REPLY and RELEASE; Ricart–Agrawala removes RELEASE: it replies at once to an older request (or whenever it is not requesting), and holds back the reply to a newer request until it leaves the critical section. The same idea guards cluster locks and replicated storage, where a double entry corrupts data.

You need: message passing and Lamport logical clocks from Unit 4, especially the happened-before order that makes timestamps comparable.

The model and what must hold

Take N processes, P1 to PN. They talk only by messages over FIFO channels: messages from one sender to one receiver arrive in the order sent. There is no shared memory and no central lock server. Each process has a critical section (CS), code that must run alone, such as updating a balance. Outside the CS a process is idle or doing local work.

A request carries a timestamp: a Lamport clock value plus the process id as tie-breaker. The pair (10, P2) is smaller than (10, P3), so all processes get one total order. Three properties are required.

  • Mutual exclusion (safety): at most one process is in the CS at any time.
  • No starvation (liveness): every process that asks eventually enters, if it stays up.
  • Timestamp order (fairness): a request with a smaller timestamp enters before a request with a larger one.

Both algorithms keep a local queue of requests ordered by timestamp. They differ in how many messages they spend to learn that the queue head is safe.

Lamport's algorithm

Each process keeps a queue Q of REQUEST messages, ordered by timestamp. Process Pi does these steps to enter the CS.

  1. Send REQUEST(ts, i) to all other N−1 processes and put a copy in its own Q.
  2. When a REQUEST(ts, j) arrives, put it in Q and send REPLY(j) at once. The reply only says 'I have recorded your request'.
  3. Enter the CS when Pi's own request is at the head of its Q and it has REPLY from every other process.
  4. On leaving, send RELEASE(i) to all others and remove its own request from Q.
  5. When RELEASE(j) arrives, remove j's request from Q.

C_Lamport = 3(N − 1)

C_Lamport is the total number of messages exchanged for one CS entry; N is the number of processes.

Why it works: if Pi and Pj both believe they may enter, each has all replies. The one with the smaller timestamp has its request ahead in the other's queue, because the other replied only after recording it. So the later request cannot be at the head. RELEASE is needed to remove stale requests; without it the queue never clears.

Ricart–Agrawala

Ricart–Agrawala uses two message types, REQUEST and REPLY, and no RELEASE. A process wanting the CS sends REQUEST(ts, i) to all N−1 others and waits for N−1 replies. The reply rule is:

  • If Pi is not requesting the CS, it sends REPLY at once.
  • If Pi is requesting with timestamp T_own, compare (T, j) with (T_own, i). If T_own is larger, Pi's own request is later, so send REPLY at once.
  • If T_own is smaller, Pi's own request is earlier, so defer the REPLY and store j in a deferred set.
  • On leaving the CS, Pi sends REPLY to every process in the deferred set and clears it.

A process enters when it has N−1 replies. No RELEASE is needed: the deferred replies sent on exit are the release signal.

C_Ricart = 2(N − 1)

C_Ricart is the total number of messages exchanged for one CS entry; N is the number of processes.

Correctness: the smaller timestamp gets an immediate reply from the larger, while the larger defers. Only the smallest outstanding request can collect all replies. Equal timestamps are broken by process id.

Failure: if one process crashes after receiving a REQUEST, every requester that needs its REPLY waits forever. RA has no timeout. A real system adds a failure detector, group membership, or a lease; see process resilience. Some syllabi call both algorithms timestamp-based or non-token mutual exclusion, and put quorum-based sets in the same lecture. Token schemes avoid this by passing one object; see token-based mutual exclusion.

Worked example

Question. Three processes P1, P2 and P3 use Ricart–Agrawala. P1 requests the CS with timestamp 10, P2 with timestamp 8, and P3 with timestamp 12. All three send their requests before any reply is sent. List every message, state who enters first, second and third, and count the messages for the three entries.

  1. N = 3, so N−1 = 2 replies are needed per entry.
  2. Requests: P1 sends REQUEST(10) to P2 and P3. P2 sends REQUEST(8) to P1 and P3. P3 sends REQUEST(12) to P1 and P2. That is 6 REQUEST messages.
  3. P1 receives P2's 8. P1's own 10 is larger, so P1 sends REPLY to P2.
  4. P3 receives P2's 8. P3's own 12 is larger, so P3 sends REPLY to P2. P2 has 2 replies and enters first. P2 defers P1's 10 and P3's 12 because its own 8 is smaller.
  5. P3 receives P1's 10. P3's own 12 is larger, so P3 sends REPLY to P1. P1 has one reply from P3 and defers P3's 12 because its own 10 is smaller.
  6. P2 exits: it sends REPLY to P1 and P3. P1 now has 2 replies and enters second.
  7. P1 exits: it sends REPLY to P3. P3 now has 2 replies and enters third.
  8. Counts: 6 REQUEST plus 6 REPLY = 12 messages. Per entry 2(N−1) = 4; for 3 entries 3 × 4 = 12.

Answer. P2 enters first, P1 second, P3 third; 6 REQUEST and 6 REPLY messages, 12 in total, which is 2(N−1) = 4 per entry.

Exam traps

  • Do not swap the counts: Lamport needs 3(N−1) messages per entry, Ricart–Agrawala needs 2(N−1). For N = 3 that is 6 versus 4.
  • In Ricart–Agrawala a process that is not requesting must reply immediately; withholding the reply turns the algorithm into deadlock.
  • In Ricart–Agrawala defer only when your own timestamp is smaller. A larger own timestamp means reply now. Equal timestamps compare process id.
  • Lamport still needs RELEASE; without it earlier requests stay in queues and can block later entries.
  • Both algorithms assume processes do not crash. One crash can stop all requesters in RA because a REPLY never comes; this is a failure problem, not a mutual-exclusion bug.

Analyze A process in Ricart–Agrawala crashes after receiving a REQUEST. What happens to a requester, and what fix is needed? 5 marks

The requester waits forever for the missing REPLY. RA alone has no failure detection; add a timeout, failure detector, group membership, or lease.

Analyze Why is timestamp order more than safety in these algorithms? 4 marks

Safety alone allows a later request to overtake an earlier one and starve it. Timestamp order makes the queue head predictable and gives bounded waiting when no process fails.

Understand What does a REPLY mean in Lamport's algorithm and in Ricart–Agrawala? 3 marks

In Lamport it means 'I have recorded your request'. In RA it means 'I do not object; you may go ahead'.

They build locks from leases, failure detectors and consensus services, because a crashed holder must lose the lock after a timeout. Ricart–Agrawala is still the clean mental model for permission-based locks. Search 'distributed lock service', 'lease-based mutual exclusion', 'Maekawa quorum', and 'failure detector' next.

5.2 Token-based mutual exclusion: Suzuki-Kasami algorithm

One token travels between processes; holding it is the right to enter the critical section. The token carries the waiting list, so no process needs to know who is queued elsewhere. Some syllabi call this the broadcast algorithm. It fits small clusters, such as one process writing an end-of-day settlement file while others wait. With N processes all busy, one entry costs N messages: N − 1 REQUEST broadcasts plus one token transfer. Ricart–Agrawala costs 2(N − 1) per entry. Idle cost is 0.

You need 5.1 for REQUEST and REPLY, and Unit 4 for sequence numbers.

The token and its arrays

Every process keeps RN[1..N]; RN[i] is the largest request number seen from i. The token carries Q, a queue of waiting ids, and LN[1..N]; LN[i] is the latest request number of i already granted. RN is not in the token.

  1. Process i sets sn = RN[i] + 1.
  2. Broadcast REQUEST(i, sn) to the other N − 1 processes.
  3. Every receiver sets RN[i] = max(RN[i], sn).

Only the process granted a request writes its own LN entry, at entry to the critical section.

Entering and passing on

On REQUEST(j, sn) while holding the token: set RN[j] = max(RN[j], sn). If not inside the critical section and RN[j] = LN[j] + 1, send the token to j now; otherwise append j to Q.

  1. Holder i: if RN[i] = LN[i] + 1, set LN[i] = RN[i], enter, work, leave.
  2. After leaving, pop head j of Q and send the token to j; if Q is empty, keep the token.
  3. If no own request is pending and Q is nonempty, send the token to the head of Q.

C = (N − 1) + 1 = N, and C_RA = 2(N − 1)

C is messages per entry when all N processes request continuously: N − 1 REQUESTs plus 1 token transfer. C_RA is the same figure for Ricart–Agrawala. Idle cost is 0 messages.

Why sequence numbers matter

After a crash duplicates the token, mutual exclusion can break two ways: two processes hold copies and enter together, and the same process may be granted twice, because a stale copy has an out-of-date LN that still passes the entry test. Keep the copy with the larger LN; destroy the other, for example by a token sequence number. See 5.3.

Worked example

Question. P1–P4 share one token. P1 holds it, Q is empty, RN = LN = [0,0,0,0]. P2, P4, P3 request with sn = 1; REQUESTs reach P1 in order P2, P4, P3. P4 reaches P2 while P2 is inside, and P3 reaches P4 while P4 is inside. Give Q, entry order, LN, messages.

  1. Each requester sets sn = 1.
  2. 3 requests × 3 receivers = 9 messages; RN = [0,1,1,1].
  3. P1 gets P2 first: not inside, RN[2] = 1 = LN[2] + 1, so sends the token to P2. Q is empty.
  4. P2 enters, LN[2] = 1. P4's request arrives inside, so Q = [4]. On exit P2 sends to P4, Q empty.
  5. P4 enters, LN[4] = 1. P3's request arrives inside, so Q = [3]. On exit P4 sends to P3, Q empty.
  6. P3 enters, LN[3] = 1. Q empty, so P3 keeps the token. LN = [0,1,1,1].
  7. Messages: 9 + 3 token transfers = 12 = N per entry.

Answer. Entry order P2, P4, P3; LN = [0,1,1,1]; 12 messages, N = 4 per entry.

Exam traps

  • i sets LN[i] = RN[i] when taking the token, before entering the critical section. Only the granted process writes its own LN entry.
  • The entry test is RN[i] = LN[i] + 1, not RN[i] ≥ LN[i] or RN[i] = LN[i].
  • Use RN[i] = max(RN[i], sn), not RN[i] = sn. A delayed smaller value must not overwrite a larger one.
  • LN records granted requests; RN records requests seen. Examiners ask for both arrays.
  • A stale second token lets two processes pass their entry tests at the same time.

Understand Why does the token carry Q instead of every process keeping its own queue of waiters? 3 marks

Only the holder decides who is next, so one copy is enough. Otherwise each process must merge N partial queues, and order depends on message arrival at every site.

Apply N = 6 processes all request continuously. Give the messages per entry here and for Ricart–Agrawala. 4 marks

Here: (6 − 1) + 1 = 6 messages. Ricart–Agrawala: 2(6 − 1) = 10 messages. Saving is 4 messages per entry.

Apply RN = [0,2,1,0], LN = [0,1,1,0] and process 2 holds the token. May it enter, and what changes? 4 marks

RN[2] = 2 = LN[2] + 1, so yes. It sets LN[2] = 2, then sends the token to the head of Q if Q is nonempty. Process 3 cannot enter: RN[3] = LN[3] = 1.

Analyze A REQUEST(i, 5) arrives at a site where RN[i] is already 7. What happens and why is it safe? 5 marks

max keeps RN[i] = 7, so the delayed REQUEST(i, 5) changes no state and is ignored. It is safe because the entry test always works from the highest request number seen, so an older number can neither create an extra entry nor push LN[i] backwards; grants only move LN[i] forward, one request number at a time.

Analyze After a crash two tokens exist. What can go wrong, and what limits the damage? 5 marks

Two holders can pass their tests and enter together, so mutual exclusion is lost. The same process can also be granted twice from a stale copy, because its LN is behind. Nothing inside the token limits the damage on its own; one of the two tokens must be detected and removed before either is used again.

Beyond the syllabus

Not for the exam. Raymond's tree-based algorithm sends the token along a path to the requester, cutting messages. Self-stabilizing token circulation is studied for wireless and ad hoc networks. Some cluster lock managers still use a single token holder, though most now prefer lease-based locks.

5.3 Deadlock detection in distributed systems

This chapter is about finding a cycle of processes that wait on each other when no single computer can see the whole picture. In a distributed system each site keeps only its local wait-for information, so a detector sends a small probe from site to site along waiting edges. When a probe returns to the process that started it, the waiting is circular and no process in the cycle can proceed. The idea is used in distributed databases, cluster job schedulers and message-based middleware that must break deadlocks without stopping the whole system.

You need: message passing and global state from Unit 4, and the request and reply traffic of 5.1.

The global wait-for graph and four deadlock models

A distributed system has sites S1, S2, ..., SN. Each site runs processes and a resource manager, which records local waits. In the simple model a site runs one process; real sites run many, and the same bookkeeping applies per process. An edge Pi → Pj means process Pi is blocked waiting for a resource that process Pj holds. The wait-for graph (WFG) has a vertex for each process and a directed edge for each wait. A deadlock is a directed cycle in the WFG. No site sees the whole WFG, because edges cross site boundaries.

WFG = (P, E), E = { (Pi, Pj) : Pi is blocked and Pj holds a resource Pi needs }

P is the set of processes; E is the set of wait-for edges; Pi and Pj are processes.

ModelWait conditionExample
ANDPi proceeds only after every requested resource is granted.A transaction needs two locks before commit.
ORPi proceeds when any one requested resource is granted.A worker waits for any one replica to answer.
AND-ORSome requests are all-or-nothing, others any-one.A query needs all shards, but a quorum reply is enough for a read.
CommunicationProcesses wait for messages, not for held resources.A server waits for a reply from a client that is itself waiting for a message from another server.

Chandy–Misra–Haas edge chasing

The Chandy–Misra–Haas algorithm detects cycles in the AND model without collecting the global WFG. A detector at process Pk sends a probe with three fields. The first field names a process Pi that is waiting; the second names the process Pj it waits for; the third names the initiator Pk that started the probe.

probe(i, j, k): Pi is blocked on Pj, and Pk started this probe

i is the waiting process; j is the process it waits for; k is the initiator that began detection.

Note the field order. Many textbooks write probe(initiator, sender, receiver); here the order is (waiting process, waited-on process, initiator). Read the fields as defined, not by position alone.

  1. Pk starts detection when it becomes blocked. It sends probe(k, q, k) to the site of every process q that holds a resource Pk needs.
  2. A site receiving probe(i, j, k) checks whether Pj is blocked. If Pj is not blocked, the probe dies; it reached a process that can run.
  3. If Pj is blocked, the site forwards probe(j, r, k) to the site of every process r on which Pj waits. This follows every outgoing edge of Pj in the AND model.
  4. If a forwarded probe reaches the initiator Pk, Pk receives probe(i, k, k): the second field is Pk and the third field equals the initiator.
  5. Pk declares a deadlock involving itself. The returned probe names only the last sender and the initiator; listing every member of the cycle needs a variant where the probe carries the path it has travelled.

In the OR model a blocked process needs only one requested resource, so its wait is a disjunction. The detector forwards the probe along one outgoing edge, not all. A single round can therefore miss a cycle that is reached through another edge; repeated rounds with different choices are needed.

A message delay creates a phantom deadlock: the WFG changes while probes travel, and a returning probe may close a cycle that has already broken. Detectors use timeouts, sequence numbers or repeated passes to discard stale reports.

Cost, centralized and hierarchical detection

A probe is one message, so message cost is also O(N·E) per round. The bound is loose because most probes die at unblocked processes. In the OR model the per-round cost falls, but detection may need several rounds.

probes per detection round = O(N × E)

N is the number of processes; E is the number of wait-for edges in the global WFG; O gives the upper-bound growth rate.

  • Centralized detection: one site gathers local WFG fragments and searches for cycles. It is exact if reports are consistent, but adds a bottleneck and a single point of failure.
  • Hierarchical detection: sites form clusters. Each cluster detects internal cycles; cluster leaders exchange summaries and search for cycles that cross clusters.
  • Breaking a detected cycle is a separate policy; recovery and agreement under failures appear in 5.4.

Worked example

Question. Three sites run Chandy–Misra–Haas under the AND model. P1 on site S1 is blocked waiting for P2 on S2; P2 is blocked waiting for P3 on S3; P3 is blocked waiting for P1. P1 starts detection. Write every probe and state how the algorithm decides.

  1. P1 is the initiator, so the probe it starts carries third field P1. P1 waits for P2, so S1 sends probe(P1, P2, P1) to S2. This is probe number 1.
  2. S2 receives probe(P1, P2, P1). P2 is blocked, and P2 waits for P3, so S2 forwards probe(P2, P3, P1) to S3. This is probe number 2.
  3. S3 receives probe(P2, P3, P1). P3 is blocked, and P3 waits for P1, so S3 forwards probe(P3, P1, P1) back to S1. This is probe number 3.
  4. S1 sees probe(P3, P1, P1). The second field is P1, and the third field is also P1. The probe has returned to its initiator, so the cycle P1 → P2 → P3 → P1 is closed.
  5. P1 declares a deadlock. The detection used one probe per edge of the cycle, so the total is 3 probes.

Answer. P1 sends probe(P1, P2, P1), S2 forwards probe(P2, P3, P1), S3 returns probe(P3, P1, P1), and P1 declares a deadlock after 3 probes.

Exam traps

  • A probe that merely reaches a blocked process proves nothing. Only a probe whose second field is the initiator, that is probe(i, Pk, Pk), proves a cycle.
  • Under the OR model a process forwards along a single edge, so one detection round may miss a real deadlock.
  • Message delay can produce a phantom deadlock: the reported cycle may have broken before the probe returns.
  • Wait-for edge direction matters: Pi → Pj means Pi waits and Pj holds. Reversing the arrow gives the wrong cycle.
  • O(N·E) is a per-round upper bound on probes, not a total for the whole run; N is processes and E is wait-for edges.

Not for the exam. Real systems rarely run one detector per process; cluster managers and databases combine edge chasing with timeouts, priority inheritance and victim selection. Cloud job schedulers and distributed lock services use similar wait-for graphs to find stuck tasks. 5.4 Consensus and agreement under failures

Consensus is the problem of making a group of processes agree on one value even when some processes crash or lie. Each process starts with a proposed value. Every correct process must eventually decide the same value, and that value must come from one of the proposals. Replicated databases, leader election in cloud systems, and payment ledgers all need this agreement. The number of failures a system can survive depends on two choices: the failure type (crash or Byzantine) and the timing model (synchronous or asynchronous).

You need Unit 4 on synchronous versus asynchronous systems and message ordering, and the group communication ideas in Chapter 5.6.

The agreement problem and its conditions

A distributed system has N processes. A process is correct if it follows its algorithm and does not fail during the run. A faulty process may stop (crash failure) or behave arbitrarily, including sending false values (Byzantine failure). Consensus starts when each process proposes a value. A decision is final: once a process decides, it does not change its mind. The chapter uses value 1 for attack and 0 for retreat in the general example.

  • Termination: every correct process eventually decides a value.
  • Agreement: no two correct processes decide different values.
  • Validity (also called integrity): the decided value was proposed by some process.

Timing matters. In a synchronous model every message has a known bounded delay and every process runs at a known bounded speed. In an asynchronous model no bound on message delay or process speed is known. These models decide which algorithms are possible. A crash failure is easier than a Byzantine failure, and a synchronous system is easier than an asynchronous one.

Crash failures: majority voting in f+1 rounds

Let f be the maximum number of processes that may crash. The system can tolerate f crashes when N ≥ 2f+1, so a strict majority of processes are correct. For example, with f = 1, N = 3 is enough; two correct processes outvote one silent process.

N ≥ 2f + 1

N is the total number of processes; f is the maximum number of crash failures; a majority is more than N/2 processes.

  1. Each process starts with its own proposed value.
  2. For f+1 rounds, every process sends the set of values it knows to every other process.
  3. After each round, a process keeps the value that appears in a majority of the values it has received.
  4. After f+1 rounds, every correct process decides that majority value.

Why f+1 rounds? A value needs to survive f silent processes. After f+1 exchanges, every correct process has heard the same majority of values. If fewer than f+1 rounds are used, a crashed process can hide a value from some correct process and break agreement. See Chapter 5.6 for process groups and retries.

Byzantine failures and the 3f+1 bound

A Byzantine process can send different values to different peers, stay silent, or lie about what it received. Let f now be the maximum number of Byzantine processes, including a faulty commander. The oral-messages algorithm needs N ≥ 3f+1, that is f ≤ (N−1)/3. With f = 1, at least four generals are needed. Three is not enough because one traitor can split the two loyal lieutenants.

N ≥ 3f + 1

N is total processes; f is maximum Byzantine faults; for f = 1, N must be at least 4.

  1. The commander sends its value to every lieutenant.
  2. Each lieutenant forwards the value it received to every other lieutenant.
  3. Each loyal lieutenant takes a majority over the value from the commander and the values forwarded by the other lieutenants.
  4. The algorithm uses f+1 rounds; each round lowers the number of traitors by one.

The figure shows f = 1 with four generals. L3 is the traitor. It tells L1 and L2 that the commander said 0. L1 still receives 1 from C, 1 from L2, and 0 from L3, so its majority is 1. L2 receives 1 from C, 1 from L1, and 0 from L3, so its majority is also 1. Agreement holds because two loyal values outvote one lie. With N = 3 and f = 1 the same vote has only two values, 1 and 0, and no majority.

FLP and practical protocols

The FLP result (Fischer, Lynch, Paterson) says no deterministic algorithm can solve consensus in a purely asynchronous system if even one process may crash. The algorithm can be safe, but it cannot guarantee termination in every run. Practical systems therefore use synchrony, randomisation, or failure detectors to make progress.

  • Paxos: proposers send values to acceptors; a value is chosen when a majority of acceptors accept the same proposal. It keeps safety under crashes and asynchronous delays, but may stall.
  • Raft: a leader is elected by a majority, and it replicates a log to followers. It is designed to be easier to understand than Paxos.
  • Two-phase commit (2PC): a coordinator asks all participants to prepare, then sends commit or abort. It can block if the coordinator crashes after some participants prepare.
  • Three-phase commit (3PC): adds a pre-commit phase to reduce blocking, but it still needs timing assumptions to be safe.
  • Failure detector: a local module that suspects which processes have crashed; an eventually perfect detector is enough for some consensus algorithms.

Use the right model before choosing a protocol. Synchronous crash-tolerant systems can use majority voting. Asynchronous systems need Paxos, Raft, or a randomised algorithm. Byzantine systems need 3f+1 replicas, as used in some blockchains and safety-critical control.

Worked example

Question. Four generals are C, L1, L2, L3. The maximum number of Byzantine generals is f = 1, and L3 is the traitor. C orders attack, value 1. L3 tells L1 and L2 that C said 0. Run the oral-messages algorithm for f = 1. State N, the minimum N required by 3f+1, the number of values each loyal lieutenant collects, the majority threshold, and the decision of L1 and L2.

  1. N = 4 and f = 1. The minimum is 3f+1 = 3(1)+1 = 4, so N = 4 is exactly enough.
  2. Round 1: C sends 1 to L1, L2 and L3. L3 is faulty; it will lie in round 2.
  3. Round 2: L1 forwards 'C said 1' to L2 and L3. L2 forwards 'C said 1' to L1 and L3. L3 forwards 'C said 0' to L1 and L2.
  4. L1 collects: from C 1, from L2 1, from L3 0. That is 3 values. Majority threshold = floor(3/2)+1 = 2. Count of 1 is 2, count of 0 is 1, so L1 decides 1.
  5. L2 collects: from C 1, from L1 1, from L3 0. Same counts. L2 decides 1.
  6. Agreement holds: both loyal lieutenants decide 1, which was C's proposed value. With N = 3, each loyal lieutenant would collect only 2 values, 1 and 0, and no strict majority would exist.

Answer. N = 4, f = 1, minimum N = 3f+1 = 4, each loyal lieutenant collects 3 values, majority threshold 2, and both L1 and L2 decide 1 (attack).

Exam traps

  • Using N ≥ 2f+1 for Byzantine faults. That bound is only for crash faults; Byzantine faults need N ≥ 3f+1, that is f ≤ (N−1)/3.
  • Thinking FLP forbids every consensus algorithm. FLP applies only to deterministic asynchronous systems with even one crash failure; synchronous systems can always agree, and randomised algorithms agree with probability 1.
  • Swapping validity and agreement. Validity says the decided value was proposed; agreement says no two correct processes decide differently.
  • Counting the Byzantine commander as extra. The value f includes every faulty process, commander or lieutenant.
  • Forgetting that f+1 rounds are message exchanges, not seconds. The round count is a correctness requirement.

5.5 Checkpointing and rollback recovery

A crash loses whatever was only in memory. Checkpointing copies a process's state to stable storage at chosen moments; recovery loads a saved state and replays from there. In a distributed system the copies must fit together: no process may receive a message that the recovered run never sent. This chapter gives that rule, shows how independent checkpointing breaks it through the domino effect, and covers the two cures: coordinated checkpoints and message logging.

You need Unit 4's global state and consistent snapshots, and the failure models of 5.4.

Local checkpoints and the recovery line

A local checkpoint C(i,k) is the k-th saved copy of process i's state: variables, program counter and open files, written to stable storage. Stable storage survives a crash, such as a disk or two disks in different rooms. After a crash the process loads C(i,k) and continues; work done after that point is lost.

One checkpoint is not enough. A global state here is one local checkpoint chosen from each process. It is consistent when no message is shown as received inside the chosen set but not yet sent inside it. Such a message is an orphan: in the recovered run it arrives with no sender.

The mirror case is a lost message: the sender's checkpoint is after the send, the receiver's before the receive. Replay re-sends it, costing time but breaking nothing.

C = {C(1,a₁), C(2,a₂), …, C(n,aₙ)} is consistent ⇔ for every message m: receive(m) ∈ C(i,aᵢ) ⟹ send(m) ∈ C(j,aⱼ)

C(i,aᵢ) is the checkpoint chosen for process i; receive(m) ∈ C(i,aᵢ) means the receive of m happened before that checkpoint was taken; send(m) ∈ C(j,aⱼ) is the same for the send on process j; n is the number of processes.

A consistent set is a recovery line. Restart from it and everything after is a legal execution: every delivered message has a sender. Finding the latest recovery line after a failure is the job of rollback recovery.

Independent checkpointing and the domino effect

The simplest scheme lets each process checkpoint whenever it likes, with no coordination: independent, or uncoordinated, checkpointing. It adds no messages and no pause; its weakness shows at recovery time.

The rollback rule: if process j's checkpoint contains the receive of a message m, and m was sent by process i after the checkpoint i has chosen, the recovered run has the receive but not the send. j's checkpoint holds an orphan and is invalid, so j rolls back to a checkpoint taken before it received m. That rollback can itself invalidate a checkpoint of a third process, and the chain continues.

The cascade can reach the first checkpoint of every process and throw away hours of work: the domino effect. In the worst case a coordination-free scheme needs as many checkpoints per process as there are processes, to keep some consistent set available.

Old checkpoints cost disk. A checkpoint that can never belong to a recovery line should be deleted; deciding which are useless is garbage collection. The worked example runs one full domino chain.

Coordinated checkpointing

Coordinated (synchronous) checkpointing makes the processes agree on when to checkpoint, so every set taken is consistent. There is no domino effect, one recovery line exists, and older checkpoints can be deleted at once.

  1. A coordinator sends CHECKPOINT REQUEST to all processes; each stops sending application messages.
  2. Each takes a tentative checkpoint, writes it to stable storage, and replies.
  3. When all replies arrive the coordinator broadcasts COMMIT; each makes its checkpoint permanent and resumes.
  4. If a process fails during the round, the coordinator aborts and all discard their tentative checkpoints.

The price is blocking: the system freezes while checkpoints are written, and one slow disk slows everyone. Non-blocking protocols number checkpoints in rounds, so the round-r checkpoint of any process is consistent with the round-r checkpoints of the rest; they must still handle a failure in mid-round.

Communication-induced checkpointing sends no extra control messages: each application message carries a few piggybacked numbers about its sender's checkpoints, and the receiver takes a forced checkpoint when delivery would otherwise make its latest checkpoint inconsistent. Quasi-synchronous protocols are one family within this class.

Log-based rollback recovery

Logging solves the problem from the other side: instead of rolling processes back, replay the messages. Each process is piecewise deterministic: every nondeterministic event it meets is the reception of a message, and between two such events its execution is deterministic. A saved state plus the received messages in logged order therefore rebuilds the state exactly.

Pessimistic logging writes every message to a stable log before delivery, and acknowledges it to the sender only after that. After a crash the process reloads its last checkpoint and replays its log. No other process rolls back; this is independent recovery. The cost is one stable write per message, which can dominate latency.

Optimistic logging writes the message later, in the background. Normal operation stays fast, but a crash may find messages delivered and not yet logged. The recovering process must ask others for copies, and they may have to roll back to find them. Orphan detection and log garbage collection are the hard parts.

Both styles depend on stable storage and garbage collection. Once a new recovery line is committed, older checkpoints and log records for applied messages can be deleted; keeping them fills the disk. Reliable logging groups are covered in 5.6.

Worked example

Question. P1 checkpoints at t = 1 and 7; P2 at 2 and 8; P3 at 3 and 11 (seconds). Messages: m1 from P1 at 4 to P2 at 5; m2 from P2 at 6 to P3 at 9; m3 from P3 at 5 to P1 at 6; m4 from P1 at 7.2 to P2 at 7.6. P1 crashes at t = 13 and restarts from its latest checkpoint. Find the recovery line, count rollbacks, and find the work lost.

  1. P1 restarts from C1,1 at 7. A message P1 sent after 7 and recorded before another process's checkpoint is now an orphan.
  2. m4 sent at 7.2, received by P2 at 7.6 before C2,1 at 8: C2,1 holds the receive but P1 holds no send. C2,1 is invalid; P2 rolls back to C2,0 at 2. Rollbacks: 1.
  3. m2 sent by P2 at 6, received by P3 at 9 before C3,1 at 11. C3,1 invalid; P3 rolls back to C3,0 at 3. Rollbacks: 2.
  4. m3 sent by P3 at 5, received by P1 at 6 before C1,1 at 7. C1,1 invalid; P1 rolls back to C1,0 at 1. Rollbacks: 3.
  5. Check {C1,0 at 1, C2,0 at 2, C3,0 at 3}: every send (4, 5, 6, 7.2) is after its sender's checkpoint, every receive (5, 6, 7.6, 9) after its receiver's. No receive without a send, so the set is consistent.
  6. Lost work from 13 s: P1 13 − 1 = 12 s, P2 13 − 2 = 11 s, P3 13 − 3 = 10 s. Total 33 s.

Answer. Recovery line C1,0, C2,0, C3,0 at 1, 2, 3 s; 3 rollbacks; 33 s lost.

Exam traps

  • Independent checkpointing causes the domino effect; coordination or logging removes it. The reverse scores zero.
  • Orphan: the receiver's checkpoint has the receive, the sender's not the send. A lost message is the opposite and costs only a retransmission.
  • The recovery line is the latest consistent set, not every process's latest checkpoint.
  • Checkpointing saves state; logging saves messages. Removing the domino effect accepts coordinated checkpoints or logging.
  • A checkpoint costs a stable write; in blocking two-phase checkpointing the system waits for it.

5.6 Process resilience and reliable communication

A process group is a set of processes that act as one service. Replication puts the same state on several members, so one crash need not stop the service. Reliable communication adds sequence numbers, acknowledgements and duplicate suppression, so a lost reply or repeated request does not corrupt state. Together they keep a wallet or bank balance correct over an unreliable network.

You need: 5.4 for agreement, and the ordering chapter for RPC, group communication and message ordering.

Process groups and replication

A process group is a named set of processes that act as one service. In a flat group members are equal. In a hierarchical group one coordinator sends work to members. A closed group admits only members; an open group also admits outside clients.

Replication puts the same state on several members. In primary-backup replication, one primary executes each request and sends the update to backups. It replies after enough backups acknowledge, so a crash does not lose an acknowledged update. If the primary crashes, survivors agree on one new primary before a backup takes over.

State machine replication is stricter. Every replica runs the same deterministic operations in the same order. Order matters when operations do not commute. Example: start at ₹1000, debit ₹700 and ₹500; if ₹700 is applied first, ₹500 is rejected at ₹300 left, final ₹300; if ₹500 is applied first, ₹700 is rejected, final ₹500. Different orders, different balances. Plain arithmetic debits do commute. Agreement on order, and on membership, is the consensus problem of 5.4; serving reads is the consistency question of 5.7.

Survivors must agree on membership. A majority quorum is:

q = ⌊n/2⌋ + 1

q is the smallest number of members that must agree to form a majority (the quorum size); n is the group size; for n = 3, q = 2.

Reliable communication and RPC semantics

An unreliable network can lose a message, deliver it twice, or reorder two messages. A sequence number is a counter in each message; the receiver uses it to order messages and spot repeats.

Acknowledgement with timeout and retransmission gives at-least-once delivery: the sender repeats until an ack arrives, so the request arrives, but may arrive more than once. The receiver keeps a duplicate-suppression table of request ids already applied. On a repeat it returns the stored reply and does not apply the operation again. Exactly-once at the server means at-least-once delivery plus this table; the network itself cannot promise it.

An idempotent operation can be repeated with the same effect, such as setting balance to ₹1500. A debit is not idempotent. Give each debit a unique request id, such as 77.

At-most-once RPC sends once, never retries, and can lose the request without telling the client.

Ordering has three useful levels, covered in the ordering chapter. FIFO keeps each sender's messages in send order. Causal order also respects happened-before. Total order makes every receiver see the same sequence, which state machine replication needs.

Worked example

Question. Three wallet replicas hold ₹2000. A client debits ₹500 with request id 77. The reply is lost; the client retries twice, so the server sees id 77 three times. Find the balance and duplicate table with suppression, then without it. How many replicas still form a majority after one crash?

  1. B0 = ₹2000; debit a = ₹500; arrivals m = 3.
  2. With suppression, first arrival applies one debit: B = 2000 − 500 = ₹1500. Table {77: reply}; next two are repeats; applied = 1.
  3. Without suppression, all 3 apply: debited = 3 × 500 = ₹1500; B = 2000 − 1500 = ₹500; applied = 3.
  4. n = 3; q = ⌊3/2⌋ + 1 = 2. One crash leaves 2, still a majority.

Answer. With suppression the balance is ₹1500 after one debit; without it ₹500 after three debits; 2 of 3 replicas remain a majority.

Exam traps

  • Exactly-once delivery is impossible on an unreliable network; at the server it means at-least-once plus duplicate suppression.
  • At-most-once RPC can lose the request silently.
  • The duplicate table must survive failover, or a retry on the new primary applies the debit twice.
  • Three replicas need 2 for a majority, not 3; two primaries cause split brain.

5.7 Consistency models and replication

Replication keeps the same data on several machines. It buys availability, low latency, read throughput and fault tolerance, and it charges one awkward question: when a client reads, which copy answers? A consistency model is the contract that settles this — it names the values a read may return, given the writes that came before. A bank balance shown in a UPI app must behave like one number; a cricket score or a social feed can lag a second and nobody minds. Choosing the model is choosing that trade.

You need: 5.6 for replicated process groups and safe message retries, and Unit 4 for happened-before and causal ordering.

Why replicate, and what the contract says

A replica is a copy of a data item kept on a second machine. It gives four gains: availability (a dead replica is covered by its peers), latency (a copy sits near the user), read throughput (reads spread over N replicas) and fault tolerance (a lost disk is not a lost record). The cost is a coordination question.

A model is defined over a history: read and write operations on data items, each issued by a process and ordered by that process's program order, plus, in real-time models, by wall-clock time. Strong models allow few answers and cost messages or waiting; weak models allow many answers and answer fast from a local copy.

  • Data-centric model: a rule for the whole store, saying in which order clients see writes.
  • Client-centric model: a rule for one client session, saying what that client may see.
  • Update protocol: the mechanism that carries a write to replicas — primary-based or quorum-based.

An IRCTC seat count on the payment page must be linearizable: two people must not both pay for the last seat. A live cricket score on a phone can be eventual.

Data-centric models, strongest to weakest

Order the models by how much reordering each one permits. Every step down removes an ordering constraint, so more reads can be served from a nearby replica.

ModelGuarantee
StrictRead returns the latest write, even while the write is in progress.
LinearizableOne global order, consistent with real time.
SequentialOne global order; each process's own order kept; real time ignored.
CausalOrder respects happened-before only; concurrent writes may appear in different orders.
FIFOWrites from one process stay in order; writes from different processes are unordered.
WeakData is consistent only after a synchronisation point.
ReleaseWrites before a release are seen by any read after the matching acquire.
EventualIf writes stop, all replicas converge to the same value.

Linearizability is what engineers mean by strong: each operation looks instantaneous at some point between its start and its end, and the order agrees with real time. Sequential consistency keeps a single global order but drops real time, so process P can read an old value after a write has finished, provided every process sees that same order. Causal consistency keeps only happened-before, so two concurrent writes may be seen in different orders at different replicas. Release consistency splits access into acquire and release phases and is what a lock-protected shared variable needs. Eventual consistency is the weakest useful promise: once writes stop, replicas agree.

Client-centric guarantees and update protocols

A mobile client wants guarantees about itself, not about the world. Three are standard.

  • Read-your-writes: after a process writes x, its own later reads of x see that value or newer.
  • Monotonic reads: successive reads by one process never go back to an older version.
  • Writes-follow-reads: a write issued after reading x is applied to at least that version of x.

These are packaged as session guarantees. A load balancer that sends each request to an arbitrary replica breaks all three; pinning a session to one replica or carrying a version token keeps them.

Primary-based protocols use one replica as the primary. In remote-write the client sends every write to the primary, which forwards it to the others; reads may be local. In local-write the primary moves to the writing client, so the write costs one hop, but the system must track where the primary is.

Replicated-write has no primary. Each item carries a version number; a client writes to W replicas and reads from R replicas.

R + W > N

N is the number of replicas; W is how many replicas must acknowledge a write; R is how many a read must contact. If R + W > N, every read quorum overlaps every write quorum, so at least one reply carries the latest version.

The client keeps the reply with the highest version and sends it back to any replica that answered with an older one; this is read repair. Version numbers give a total order per item. Vector clocks are needed only when writes are concurrent and must be compared, not merely ordered (Unit 4).

Worked example

Question. Three replicas R1, R2, R3 hold x = 7 at version 4. N = 3, W = 2. A client writes x = 10 and the write reaches only R1 and R2. (a) A read uses R = 2 and contacts R2 and R3. What is returned and what happens next? (b) A second read uses R = 1 and hits R3 only. What is returned? (c) Justify both with R + W > N.

  1. After the write, R1 holds (version 5, x = 10) and R2 holds (version 5, x = 10); R3 still holds (version 4, x = 7).
  2. Part (a): read quorum R = 2 contacts R2, which replies (v5, 10), and R3, which replies (v4, 7).
  3. Check the rule: R + W = 2 + 2 = 4, and N = 3, so 4 > 3 holds and the read quorum must overlap the write quorum.
  4. The client keeps the highest version, 5, and returns x = 10.
  5. Read repair: the client sends (v5, 10) to R3, so R3 becomes (v5, 10).
  6. Part (b): R + W = 1 + 2 = 3, which is not greater than N = 3, so a one-replica read need not touch the write quorum.
  7. R3 replies (v4, 7); that version is the only one seen, so the client returns x = 7, one version stale.

Answer. With R = 2 the client returns x = 10 and repairs R3 to version 5; with R = 1 hitting only R3 it returns the stale x = 7, because 2 + 2 = 4 > 3 holds but 1 + 2 = 3 does not.

Exam traps

  • Claiming R + W = N gives strong consistency. The rule is strict: R + W > N. Equality lets a read quorum miss the write quorum, as 1 + 2 = 3 with three replicas shows.
  • Calling sequential consistency stronger than linearizability. Linearizability adds real-time order; sequential consistency keeps only each process's own order.
  • Treating eventual consistency as no consistency. It still promises per-item ordering and convergence once writes stop; what it drops is the bound on how long staleness lasts.
  • Mixing client-centric and data-centric guarantees. Read-your-writes is a promise to one session, not a global order for the store.
  • Using a single version number where vector clocks are needed. A counter orders writes but cannot tell whether two writes were concurrent.

Analyze Why is eventual consistency acceptable for a cricket score but not for a bank balance? 5 marks

A cricket score is read-only for viewers and a one-second lag changes nothing important, so cheap local reads win. A bank balance drives debits and credits; a stale read lets the same money be spent twice, so the read must see the latest write. That needs linearizability, which costs coordination and higher latency.

Analyze Why does remote-write make read-your-writes easy but local-write harder? 4 marks

With remote-write the primary is fixed, so a client that reads from the primary always sees its own write. With local-write the primary moves to the writer, so a later read must be directed to the current primary; if the client reads elsewhere it can miss its own write.

  2. Timestamp algorithms spend 2(n-1) messages per entry and have a synchronization delay of one message time; Ricart-Agrawala removes the release message but still pays 2(n-1).
  3. A token costs only 0 to n messages per entry but adds a wait of up to n message times when the token is elsewhere.
  4. Deadlock detection in a distributed system can only chase cycles by passing probes; no site sees the whole wait-for graph.
  5. Consensus is solvable only inside the limits set by the failure type (crash or Byzantine) and the timing model (synchronous or asynchronous).
  6. A checkpoint set is usable only if it is globally consistent; otherwise recovery rolls back past consistent states.
  7. Replication, reliable message delivery and consensus together turn unreliable processes and links into a service that keeps answering.
  8. A consistency model is a trade: stricter models are easier to program against but cost more communication and latency.

Exam question bank

Examiners ask for comparisons backed by numbers: timestamp against token mutual exclusion, AND against OR deadlock models, and one consistency model against another, each supported by a worked trace and a message-complexity count.

Remember and understand

Understand Describe Lamport's distributed mutual exclusion algorithm. Explain the three message types and prove that two processes can never be in the critical section together. 13 marks

State the queue of (timestamp, id) requests; REQUEST broadcast, REPLY unicast, RELEASE broadcast; Ordering rule: smaller timestamp wins, ties by process id; Proof uses total order of timestamps plus one REPLY held back per process; Message count 3(n-1) per entry.

Understand Explain the Suzuki-Kasami token-based mutual exclusion algorithm. Give the data structures used at each process and the steps followed when the token arrives. 13 marks

Token holds Q and LN array; each site keeps RN; Requesting site increments RN[i] and broadcasts; Holder compares RN to LN and appends to Q; On release the holder updates LN and passes the token to the queue head; Message cost 0 to n per entry, delay up to n.

Understand What are the AND and OR models of distributed deadlock? Explain the Chandy-Misra-Haas probe algorithm for each model. 13 marks

AND model: process needs all requested resources; OR model: process needs any one; Probe carries (initiator, sender, receiver); Probe follows wait-for edges and returns to initiator to signal a cycle; Number of messages grows with edges, not with processes.

Understand Define the consensus problem. Explain why the failure type and the timing model decide how many failures a system can survive. 13 marks

Agreement, validity, termination; Crash against Byzantine failures; Synchronous against asynchronous timing; Crash failures need 2f+1; Byzantine need 3f+1; FLP blocks guaranteed termination in asynchronous systems.

Understand Explain checkpointing and rollback recovery. What is a globally consistent checkpoint set and what causes the domino effect? 8 marks

One local checkpoint per process; Consistency condition on in-transit messages; Recovery line and the domino effect; Coordinated checkpointing as a cure.

Apply

Apply Three processes P1, P2, P3 have Lamport clocks 4, 4 and 2. P1 and P3 request the critical section at the same clock value from their own view. Trace Lamport's algorithm and state the order of entry. 13 marks

Form request tuples and sort by (timestamp, id); Show queue contents at each stage; Show which replies are deferred; State the entry order and the release broadcasts.

Apply Trace one full round of the Suzuki-Kasami algorithm for four processes when the token is held by P1 and P3 and P4 send requests with sequence numbers 2 and 5. 13 marks

Initial RN and LN values; Queue update on each request; Holder comparison of RN against LN; Token transfer order and final Q and LN; Message count for this round.

Apply A distributed system has the waits P1 to P2, P2 to P3, P3 to P1, and P4 to P2. Run the Chandy-Misra-Haas OR-model probe algorithm from P1 and from P4 and state the result in each case. 13 marks

List the probes generated at each step; Show the probe that returns to its initiator; P1 reports a deadlock, P4 does not; Explain the difference between a cycle and a knot.

Apply Compare Lamport's algorithm, Ricart-Agrawala and Suzuki-Kasami on messages per critical section entry, synchronization delay and throughput under heavy load. Show the cost figures for n = 5. 16 marks

3(n-1) against 2(n-1) against 0 to n messages; Delay of one message time against up to n; Throughput under heavy load; Numerical table for n = 5; Which algorithm suits low load and which suits high load.

Analyze and evaluate

Analyze Explain the Byzantine generals problem. Show why n ≥ 3f + 1 is needed with oral messages and how signed messages relax the bound. 13 marks

Statement of the problem and the traitor count; Oral message algorithm OM(m) and its recursion; Bound 3f+1 with an f = 1 counterexample for n = 3; Signed messages allow n ≥ f + 2; Link to replicated services.

Evaluate Compare coordinated checkpointing with message logging for rollback recovery. Which one avoids the domino effect and at what cost? 13 marks

Consistency requirement in each scheme; Coordinated checkpointing blocks or uses extra messages; Message logging keeps a volatile log and allows independent recovery; Domino effect ruled out by coordination and by logging; Cost in storage, blocking and recovery time.

Evaluate Describe the consistency models from strict to eventual and explain which one a bank balance read in a UPI-style payment app needs. 16 marks

Strict, sequential, causal, eventual; Read-your-writes and monotonic reads; Quorum rule R + W > N; Balance check needs strong or linearizable read; Cost in latency and availability.

Evaluate Explain how process groups, reliable message delivery and consensus work together to keep a replicated service alive when a process and some messages are lost. 13 marks

Flat and hierarchical groups; At-least-once and exactly-once delivery, retries and duplicate suppression; Agreement on the order of updates; Leader election after a crash; Failure masking seen by the client.

Glossary

Byzantine failure
A process continues to run but sends wrong or conflicting information.
Chandy-Lamport snapshot
A distributed global state recorded by sending markers along channels so that no site needs to stop the computation.
Checkpoint
A saved local state of one process from which it can restart.
Deadlock
A set of processes each waiting for a resource held by another, so none can proceed.
Eventual consistency
Replicas may differ for a while, but if updates stop, all replicas converge to the same value.
Fail-stop failure
A process stops and stays silent; other processes can detect the silence.
Knot
A set of processes in a wait-for graph from which every path leads back into the set, so all of them are deadlocked.
Lamport timestamp
A pair (clock value, process id) that gives a total order over all events in the system.
Leader election
Choosing one process from a group to act on its behalf, and choosing another when it fails.
Linearizability
Each operation appears to take effect at a single instant between its call and its return, consistent with real time.
Liveness property
A property saying something good eventually happens, such as every request eventually being granted.
Logical clock
A counter that only tracks the order of events, not real time, so that if a happens before b then the clock of a is smaller.
Message logging
Recording received messages so that a failed process can replay them instead of rolling everyone back.
Mutual exclusion
The guarantee that at most one process at a time executes the code that touches a shared resource.
Phantom deadlock
A false deadlock report produced by state that was true at different times at different sites.
Probe
A control message that follows wait-for edges to look for a cycle that returns to its starting site.
Quorum
A minimum number of replicas that must participate so that any two quorums overlap.
Recovery line
The most recent consistent set of checkpoints, one per process, used to restart the system.
Reliable multicast
Delivery of a message to every member of a group, with retries and duplicate suppression, despite losses.
Replica
A copy of the same data or service placed on another machine for availability and speed.
Request queue
The ordered list of pending requests kept inside the token in a token-based algorithm.
Safety property
A property saying nothing bad happens, such as two processes never being in the critical section together.
Synchronization delay
The time between one process leaving the critical section and the next process entering it.
Token passing
Circulating one permission message around the processes; only its holder may enter the critical section.
