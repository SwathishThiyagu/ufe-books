5.1 Sending SMS and e-mail from apps

An app can send a short message without owning a radio stack. On Android, SmsManager hands text to the phone's SMS service; e-mail goes through an intent to a mail app. This keeps account setup, retries and carrier billing outside your code. Apps use it for OTP alerts, delivery updates, support replies, UPI receipts and sharing invoices. Some syllabi call it SMS messaging and sending e-mail.

You need: Unit 2 intents and built-in apps, and Unit 1 SMS as a mobile service.

SMS through SmsManager

SmsManager is the Android class that talks to the telephony service. Declare the SEND_SMS permission in the manifest and request SEND_SMS at runtime on Android 6.0 and later. Without it, the call throws SecurityException.

A single 7-bit GSM SMS carries 160 characters. A long message is concatenated: each part carries a user data header of 6 bytes, and after 7-bit packing that header takes 7 of the 160 characters, leaving 153 characters of payload per part (160 − 7 = 153). Use divideMessage(text), which returns a list of strings already split at safe boundaries. Do not cut at 160 yourself.

  1. Call SmsManager sms = SmsManager.getDefault(). On API 31 and later use context.getSystemService(SmsManager.class), which also supports per-SIM managers; getDefault() is deprecated from Android 12 (API 31).
  2. Call ArrayList<String> parts = sms.divideMessage(body).
  3. Build a sent PendingIntent and a delivered PendingIntent for each part.
  4. For each part call sms.sendTextMessage(phone, null, part, sentPI, deliveredPI).
  5. Check the result code in the sent receiver; handle RESULT_ERROR_GENERIC_FAILURE and RESULT_ERROR_RADIO_OFF.

The sent intent fires when the part leaves the phone for the carrier. The delivered intent fires when the recipient's phone acknowledges it. Billing is per part, so a 320-character message is three chargeable SMS. Keep the destination in E.164 form, for example +919876543210.

E-mail with intents

Your app does not log in to an SMTP server. It asks a mail app to compose. For an e-mail-only action use Intent.ACTION_SENDTO with a mailto: URI. For general sharing use Intent.ACTION_SEND with type text/plain and wrap it in Intent.createChooser.

For ACTION_SENDTO put the address in the URI, for example Uri.parse("mailto:someone@example.com"); EXTRA_EMAIL is not reliable there and some mail apps ignore it. EXTRA_EMAIL is used when you attach recipients to ACTION_SEND or ACTION_SEND_MULTIPLE. Other fields go in extras: EXTRA_SUBJECT, EXTRA_TEXT for body, and EXTRA_STREAM for an attachment. An attachment must be a content:// URI, not file://; add FLAG_GRANT_READ_URI_PERMISSION so the mail app can read it.

The chooser shows every app that can handle the intent. With createChooser the chooser itself shows its own message when no app matches. The try/catch for ActivityNotFoundException is needed when you start ACTION_SENDTO, or any implicit intent, directly without a chooser. The user still taps Send inside the mail app, so your app never sees the final message.

E-mail needs a configured account and internet; SMS needs carrier signal and balance. Test on a real phone: emulators often lack a SIM and a mail account.

Worked example

Question. An Android app sends a 320-character SMS in 7-bit GSM encoding. A single SMS carries 160 characters. Each part of a concatenated SMS carries 153 characters because the 6-byte user data header takes 7 characters of the 160. How many SMS parts are sent? At ₹0.20 per part, what is the cost?

  1. Payload per concatenated part = 153 characters.
  2. Number of parts n = ⌈320 ÷ 153⌉ = ⌈2.09⌉ = 3.
  3. Cost = 3 parts × ₹0.20 per part = ₹0.60.

Answer. 3 SMS parts are sent; the cost is ₹0.60.

Exam traps

  • Using 160 characters per part for a long SMS; the 6-byte concatenation header takes 7 characters, leaving 153 characters per part in 7-bit GSM.
  • Treating the sent PendingIntent as proof of delivery; sent means handed to the carrier, delivered means the recipient phone acknowledged.
  • Forgetting the runtime SEND_SMS permission and getting SecurityException.
  • Using ACTION_SEND when only e-mail apps should answer; ACTION_SENDTO with a mailto: URI restricts the chooser to e-mail.
  • Passing a file:// attachment; use a content:// URI with FLAG_GRANT_READ_URI_PERMISSION.

5.2 Displaying maps in apps

A map screen does not draw roads or labels. The app tells a map SDK where to look; the SDK fetches square tiles over HTTPS and paints them. The app adds its own shops, riders or customers as markers. Building tiles, projection and zoom yourself takes months, so apps reuse the SDK. Ride-hailing, food delivery and station finders work this way.

You need Unit 2 fragments, Unit 3 basic views, and the manifest idea from Unit 2.

Fragment, view and the API key

  • MapFragment or SupportMapFragment owns the map lifecycle; reach the map in onMapReady.
  • MapView is a plain View; forward onResume, onPause and onDestroy to it or the map leaks.
  • API key: created in the cloud console, restricted to package name and signing SHA-1, pasted into AndroidManifest.xml as a meta-data entry named com.google.android.geo.API_KEY.

A missing or wrong key raises no error. The map shows a grey grid. setMapType picks MAP_TYPE_NORMAL, SATELLITE, HYBRID or TERRAIN.

Camera and markers

LatLng(latitude, longitude) holds a point in degrees: latitude runs −90 to +90, longitude −180 to +180.

lat_center = (lat_max + lat_min) ÷ 2,  lat_span = lat_max − lat_min

lat_max and lat_min are the largest and smallest marker latitudes in degrees; longitude uses the same formulas. Build a LatLngBounds with new LatLngBounds.Builder().include(new LatLng(lat_min, lon_min)).include(new LatLng(lat_max, lon_max)).build(); south-west corner is (lat_min, lon_min), north-east corner is (lat_max, lon_max).

  • newLatLng(point) recentres the map.
  • newLatLngZoom(point, zoom) recentres and zooms: 0 is the whole world, 21 a single building.
  • newLatLngBounds(bounds, padding) fits every marker with a screen margin in pixels.

moveCamera jumps instantly; animateCamera glides. A marker is MarkerOptions().position(p).title("Shop").snippet("Open till 9"); tapping it opens the info window.

Wiring the map into an activity

  1. Add the play-services-maps dependency and the INTERNET permission.
  2. Create the API key and restrict it to the package and SHA-1.
  3. Declare a <meta-data> element with android:name="com.google.android.geo.API_KEY" and android:value="YOUR_KEY" inside the <application> element of AndroidManifest.xml.
  4. Put a SupportMapFragment in the layout XML with an id.
  5. The activity implements OnMapReadyCallback; in onCreate get the fragment by id with getSupportFragmentManager().findFragmentById(R.id.map) and call getMapAsync(this) on it.
  6. In onMapReady set the map type, add markers, then move the camera.
  7. For MapView, forward onResume, onPause, onDestroy and onLowMemory.

Markers are not kept by the saved view state. After a rotation add them again, or the screen returns empty.

Worked example

Question. A map screen must show three markers at (12.0, 77.0), (12.1, 77.2) and (11.9, 77.1). Find the camera centre and the latitude and longitude spans so all three fit.

  1. Smallest latitude = 11.9°, largest = 12.1°.
  2. Latitude centre = (12.1 + 11.9) ÷ 2 = 12.0°.
  3. Smallest longitude = 77.0°, largest = 77.2°.
  4. Longitude centre = (77.2 + 77.0) ÷ 2 = 77.1°.
  5. Latitude span = 12.1 − 11.9 = 0.2°; longitude span = 77.2 − 77.0 = 0.2°.

Answer. Move the camera to LatLng(12.0, 77.1) and choose a zoom that covers a 0.2° span in both directions, i.e. about 22 km north to south.

Exam traps

  • Swapping the arguments. LatLng takes latitude first; new LatLng(77.0, 12.0) moves a shop near Bengaluru (12.0° N, 77.0° E) into the Arctic, and the map still draws, so the bug survives testing.
  • Calling getMap() in onCreate gives null. Use getMapAsync and add markers in onMapReady.
  • A wrong or missing API key shows a grey grid, not an error. Check the meta-data name and that Maps SDK for Android is enabled.
  • A MapView that never forwards onPause, onResume and onDestroy leaks the map and can crash on return.
  • Zoom is a scale factor: each step doubles the scale, it is not a span in degrees, and it may be fractional. Use CameraUpdateFactory.newLatLngBounds to fit a degree span instead of guessing a zoom number.

5.3 Location data and location-based services

Location data is the phone's estimate of where it is: latitude, longitude and an accuracy radius. Location-based services (LBS) turn that stream of fixes into an answer — what is near me, did the user enter my zone, where is my rider, which offer fits this shop. Ride-hailing, food delivery and geofenced alerts all run on it. This chapter shows how Android gives an app location, and how the app uses it.

You need: activities and the permission model from Unit 2, plus the tracking idea from Unit 1 (see Unit 1, Handover, location tracking and mobility management).

Fine versus coarse, and the providers

Android guards location because it reveals where a person lives and works. ACCESS_FINE_LOCATION gives accuracy to a few metres; ACCESS_COARSE_LOCATION gives about a kilometre. Coarse suits weather or city-level offers; ask for fine only when a map pin or a 100 m geofence needs it. The manifest declaration alone is not enough on modern Android: the app must also request the permission at runtime and handle a refusal.

Below the permission sits a provider, the actual source of fixes.

  • GPS: satellites, accurate to metres outdoors, slow first fix, fails indoors, heavy on battery.
  • Network: Wi-Fi and cell-tower lookup, fast, works indoors, accuracy tens to hundreds of metres.
  • Passive: fixes other apps already requested, free, arrives unpredictably.

LocationManager is in the platform; you name the provider yourself. FusedLocationProviderClient, from Google Play services, merges GPS, Wi-Fi and sensors into one better fix. Both return a Location: latitude and longitude in degrees, accuracy in metres, and a time stamp.

Requesting and stopping updates

getLastKnownLocation(provider) returns the last cached fix — possibly null, possibly minutes old — without waking any radio. Show it as a stand-in, then request live updates.

requestLocationUpdates(provider, minTime, minDistance, listener)

minTime is the minimum gap between fixes in milliseconds; minDistance is the minimum movement in metres before a new fix is delivered; listener is the LocationListener that receives each Location.

Both numbers are filters, not a schedule: the system may deliver later, never earlier. Stop with removeUpdates(listener) in onPause() and register again in onResume(); a paused activity that keeps GPS alive only drains the battery. The fused client uses requestLocationUpdates(request, callback, Looper) and removeLocationUpdates(callback), with the interval and displacement held in a LocationRequest.

Test every fix with getAccuracy(); 900 m is a city, not a doorstep. Throw away stale fixes by comparing getTime() with the current clock.

Geocoding, proximity alerts and LBS

Geocoding maps an address to latitude and longitude; reverse geocoding maps coordinates to a street address. Geocoder returns lists and is slow, so call it off the main thread. addProximityAlert(latitude, longitude, radius, expiration, pendingIntent) fires an Intent when the device enters or leaves a circle of radius metres, and the Play services geofencing API does the same for many zones with less battery.

Typical services: nearby search for an ATM, tracking a delivery rider, a school-zone alert, a mall coupon when you walk in. To draw the fix on a map, see Chapter 5.2.

Worked example

Question. A delivery app requests location updates every 20 s with a minimum distance of 100 m. A rider moves at 18 km/h. What is the maximum number of updates per minute, and how far does the rider move between two time ticks?

  1. Speed in metres per second: 18 km/h = 18000 m ÷ 3600 s = 5 m/s.
  2. Distance moved in one 20 s tick: 5 m/s × 20 s = 100 m.
  3. 100 m is not less than the 100 m filter, so the distance filter is met at every tick; the time filter alone decides.
  4. Updates per minute: 60 s ÷ 20 s = 3.

Answer. At most 3 updates per minute, with the rider moving exactly 100 m between ticks.

Exam traps

  • Manifest permission alone is not enough on modern Android; ask for fine or coarse location at runtime and handle a denial.
  • minTime is in milliseconds: 20 s must be written 20000, not 20.
  • minTime and minDistance are lower bounds. The system can deliver later, never earlier.
  • getLastKnownLocation can return null or a stale fix; it never wakes the GPS.
  • A user may grant only coarse even when you asked for fine; check the accuracy you actually received.

Beyond the syllabus

Not for the exam. Indoors, GPS fails and Wi-Fi round-trip time plus Bluetooth beacons take over. Surveying uses RTK correction for centimetre fixes. Search for "Android location permissions", "FusedLocationProviderClient" and "geofencing API" next.

5.4 Mobile security issues

Mobile security is the set of threats and the controls that answer them, grouped by where the attacker sits: in your app's code and data, on the network between phone and server, or in the handset itself. Every app you build carries a wallet's worth of risk, because it holds user data, talks to a server and sits in a pocket. The controls are unglamorous — least privilege, encrypted storage, TLS, a screen lock, a remote wipe — and together they decide how much a lost phone or a curious user actually costs.

You need the file and preference storage of Chapter 4.2 and the wireless risks of Unit 1, Wireless LANs.

Three layers of risk

Group mobile threats by where the attacker stands. The app layer is your code and the data it stores. The network layer is traffic between the phone and your server. The device layer is the physical handset and the person holding it.

  • App layer: a repackaged APK carrying malware, a permission the feature never uses, a secret printed to the log, a private file written to shared storage, data leaking through an implicit intent.
  • Network layer: plain HTTP, a fake free Wi-Fi hotspot that copies traffic (an evil twin, see Unit 1, Wireless LANs), a TLS setting that trusts every certificate.
  • Device layer: a lost phone with no screen lock, a shoulder surfer reading a notification, an automatic backup that copies private files to a laptop.

A useful habit is the attacker's view: what does the attacker gain, and what does it cost them? A stolen unlocked phone costs nothing to read. The same phone behind a 6-digit PIN with remote wipe costs time, and the data may be erased before it is read.

OWASP publishes a Mobile Top 10, a list of common mobile weakness categories. Treat it as a review checklist. The entries change between editions, so read the current list rather than memorising an old one.

Least privilege and the app sandbox

Android gives each installed app its own Linux user id. Its internal files are readable only by that user id. This is the app sandbox. It stops one app reading another's files, and it is the reason internal storage is the default home for private data.

The sandbox says nothing about what the app itself may do. That is the permission system. Each dangerous capability — camera, contacts, location, microphone — is a permission declared in the manifest. From Android 6.0 (API 23) the dangerous ones are granted at runtime, one prompt at a time.

  1. Declare the permission in AndroidManifest.xml.
  2. Before using the feature, check the current grant with ContextCompat.checkSelfPermission.
  3. If it is not granted, call requestPermissions, showing a one-line reason first.
  4. Handle onRequestPermissionsResult: on grant, do the work; on refusal, hide or disable the feature.
  5. Re-check at every use. The user can revoke the permission from Settings at any time.

Least privilege means asking only for what the feature needs. An app that picks one photo can use the system photo picker and request no storage permission at all. Fewer permissions means less damage if the app is later compromised, and fewer users abandoning the install.

Data at rest and data in transit

Data at rest means stored bytes: files, SQLite rows, SharedPreferences. Internal storage is private but not encrypted by your app. Sensitive values — access tokens, card references, health notes — should be encrypted before they are written.

The Android Keystore holds keys, not data. You generate a key inside it, and the key material never leaves the keystore; you receive a Cipher object that uses it. On many devices the key sits in dedicated hardware, so an image of the flash memory cannot be decrypted on another machine.

Bad places for a secret: hardcoded in the source, printed with Log.d, or written to world-readable external storage. An APK can be unzipped and its strings read.

Data in transit means bytes on the wire. Use HTTPS, which is HTTP inside TLS. TLS gives encryption, integrity, and a check that the server certificate chains to a trusted authority.

Two common mistakes. A custom TrustManager that accepts all certificates turns TLS into decoration. And HTTPS says nothing about stored data: both the server and the phone hold plaintext at the ends of the connection.

Certificate pinning fixes the acceptable certificate or public key inside the app. It defeats an attacker holding a rogue authority certificate, at the cost of a forced app update whenever you rotate the key.

Protecting the device itself

The device layer holds the cheapest controls. A screen lock — PIN, pattern, password or fingerprint — turns a stolen phone from an open book into a locked box.

N = 10^d

N is the number of possible numeric PINs and d is the number of digits; each digit is 0-9.

Length beats cleverness. A 4-digit PIN has 10⁴ = 10,000 combinations; a 6-digit PIN has 10⁶ = 1,000,000, a hundred times more. A lockout delay after a few wrong tries matters more than either.

Remote wipe lets the owner erase the handset over the network, through Find My Device or an enterprise MDM (mobile device management) server. It works only while the phone is online; a thief who stays on airplane mode keeps the data.

Other device-level controls: auto-lock after about 30 s, hide notification content on the lock screen, exclude sensitive files from auto backup using android:allowBackup and backup rules, and set android:usesCleartextTraffic="false" so a bug cannot silently fall back to HTTP.

Worked example

Question. A wallet app uses a 4-digit PIN. How many PINs are possible? At 10 guesses per second with no lockout, how long does trying all of them take? If the app locks for 30 s after every 5 wrong guesses, what is the approximate total time to try all 10,000 PINs?

  1. Each digit runs 0-9, four places, so the number of PINs is N = 10⁴ = 10,000.
  2. No lockout: 10,000 guesses ÷ 10 guesses per second = 1,000 s.
  3. 1,000 s is 16 min 40 s (16 × 60 = 960 s, plus 40 s).
  4. With lockout: 10,000 ÷ 5 = 2,000 groups of five wrong guesses.
  5. Lock time = 2,000 × 30 s = 60,000 s. The 30 s wait is not guessing time, so guessing time stays 1,000 s.
  6. Total = 60,000 s + 1,000 s = 61,000 s.
  7. In hours: 61,000 ÷ 3,600 = 16.94 h.

Answer. 10,000 PINs; 1,000 s (16 min 40 s) with no lockout; about 61,000 s ≈ 16.94 h with the 30 s lockout.

Exam traps

  • HTTPS protects data on the wire only. Local files and SharedPreferences on the phone still need encryption or a keystore key.
  • A permission written in the manifest is not a permission granted. Runtime grants can be revoked, so check before every use.
  • The app sandbox protects one app's files from other apps on a healthy device; it does not protect against a rooted phone or a backup that copies the files out.
  • Full-device encryption protects data when the phone is off or locked, not while it is unlocked with the app running.
  • Pinning and 'trust all certificates' look like TLS settings but do opposite jobs; the examiner often asks which one is the vulnerability.

5.5 Preparing apps for publishing and deploying APKs

A debug build is not shippable: it uses a throwaway key, lets a debugger attach, and is not shrunk. Publishing makes a release build: a versioned, signed, optimised package that a store or phone accepts. The signing key is created once and kept for the app's life. versionCode must rise on every upload; versionName labels each release.

You need the Android project and SDK tools from Unit 2, and Unit 4 data storage. Chapter 5.4 covers attacks on keys and credentials.

Build types and the two version numbers

Gradle builds every Android app in a build type. Debug is for your emulator or phone: the SDK signs it with a per-machine debug key, a debugger can attach, and nothing is shrunk. Release is for users: signed with your key, not debuggable, code and resources shrunk. Same source, different output.

Both builds read two version values from defaultConfig in build.gradle.

FieldTypeSeen byRule
versionCodepositive integerAndroid and the storemust strictly increase on every upload
versionNametext, for example 1.2.4users and store listingno ordering rule, free form

versionCode is the update counter. A phone compares it with the store listing; the store keeps the highest accepted code for the package and refuses anything not greater.

versionName is a label. Teams use major.minor.patch: major for a redesign, minor for features, patch for fixes. 1.2.3 to 1.2.4 is a patch release.

targetSdkVersion also gates publishing: stores require a recent target and stop accepting old API levels.

Signing with a release keystore

An APK is a zip of code and resources. Signing adds a certificate block over the file. The signature ties the APK to the holder of the private key; it is how Android recognises an update to the same app and detects later byte changes. Android verifies it before installing.

Identity is package name plus signing certificate. An installed app updates only from an APK with the same package name and certificate. A different certificate gives INSTALL_FAILED_UPDATE_INCOMPATIBLE on a phone and a rejection on a store.

The certificate lives in a keystore: a file, usually .jks, holding private keys under aliases, protected by a store password and key password. Create it once with keytool — keytool -genkeypair -v -keystore release.jks -alias appkey -keyalg RSA -keysize 2048 -validity 10000 — then keep two backups, one offline.

Point the release build at the keystore, and keep passwords out of version control.

android {
  signingConfigs {
    release {
      storeFile file("release.jks")
      keyAlias "appkey"
      storePassword System.getenv("KS_PASS")
      keyPassword System.getenv("KEY_PASS")
    }
  }
  buildTypes {
    release {
      signingConfig signingConfigs.release
      minifyEnabled true
      shrinkResources true
    }
  }
}

With Play App Signing, Google holds the app signing key and you sign uploads with an upload key. A lost upload key can be reset; a lost app signing key on an app not enrolled cannot.

Shrinking the build and testing the release

minifyEnabled true runs R8: it deletes unreachable code, renames classes and members to short names, and with shrinkResources true deletes unused resources. The package shrinks, which helps metered data, and renaming hinders reverse engineering.

Renaming breaks text-name lookups: reflection, JSON model filling, JNI entry points, XML-inflated views. Protect those classes with keep rules in proguard-rules.pro.

Then test the release build, not the debug one.

  1. Build: ./gradlew assembleRelease writes app-release.apk; ./gradlew bundleRelease writes app-release.aab.
  2. Install the signed APK on a phone and run sign-in, payment, and any API key tied to a certificate (maps, see 5.2). Register both debug and release SHA-1 fingerprints in the console and test both builds: a key for one fingerprint fails in the other build.
  3. Confirm logs are off, no test server address is compiled in, and crash reports arrive.

Deploying the APK

Two artifacts come from a release build. The APK installs on one device. The AAB is a publishing format: Play splits it into per-device APKs, so each phone downloads only what it needs.

Route A, a store. Create the app, fill listing, content rating and data safety form, upload the AAB, and roll out. Later uploads need a higher versionCode; the store refuses an accepted code.

Route B, direct install, called sideloading.

  1. Copy the signed APK to the phone by USB, download link or messaging app.
  2. Allow installs from that source (Settings, then Install unknown apps).
  3. Tap the file and install.
  4. Check the version under Settings, then Apps.

Businesses ship this way to staff phones, warehouses and kiosks; some stores accept plain APKs.

Update rules, both routes: same package name, same certificate, higher versionCode. Change one and you install a different app, not an update.

Worked example

Question. An app has versionCode 7 and versionName 1.2.3. You publish one patch update that fixes two bugs and adds nothing new. What are the new versionCode and versionName? Why can versionCode 7 not be uploaded again?

Python program.

version_code = 7
major, minor, patch = 1, 2, 3
new_code = version_code + 1
new_patch = patch + 1
print(new_code)
print(new_patch)
  1. versionCode is the machine counter and must rise on every upload: 7 + 1 = 8.
  2. versionName is the display label. A patch keeps major 1 and minor 2 and raises patch 3 to 4, so 1.2.4.
  3. The store already holds 7 for this package. An upload with 7 is not greater, so it is rejected as a duplicate; a phone on 7 sees no update.
  4. Change: versionCode 7 → 8, versionName 1.2.3 → 1.2.4.

Output

8
4

Answer. versionCode 8 and versionName 1.2.4; 7 cannot be reused because a versionCode must be strictly greater than every code already accepted for the package.

Exam traps

  • Reusing or lowering versionCode. A store compares numbers, so 7 after 7, or 6 after 7, is rejected and no device updates.
  • Confusing versionName with versionCode. Writing 1.2.5 while versionCode stays 7 updates nobody; only versionCode is compared.
  • Losing the upload keystore, alias or password. You then cannot sign an update for the same identity; back the file up offline and record the alias.
  • Publishing a debug build. The debug key is per machine and not your release identity, so later release-signed updates will not install over it.
  • Testing only the debug build. Shrinking (R8 renaming or deleting reflectively used classes) fails only in release. A certificate-restricted API key works only in builds signed with that certificate: keys registered with the debug SHA-1 fail in release, and release-SHA-1 keys fail in debug. Register both fingerprints and test both builds.

Check yourself

Remember Define versionCode and versionName. 2 marks

versionCode is a positive integer used by Android and the store as an update counter; users never see it. versionName is a display string such as 1.2.4 with no ordering rule.

Remember What is a keystore? 2 marks

A .jks file holding private keys under aliases, protected by a store password and key password. The release build is signed with one key from it.

Understand Why must every update of an app be signed with the same certificate? 3 marks

Android identifies an installed app by package name plus signing certificate. An update signed with another key fails the signature check, so existing users cannot be updated.

Understand What does R8 do when minifyEnabled is true? 3 marks

It removes unreachable code, renames classes and members to short names, and with shrinkResources true removes unused resources. The package shrinks; keep rules protect names reached only by reflection.

Apply An app has versionCode 41 and versionName 2.7.0. You ship a release that adds one feature and fixes two bugs. Give the new values. 4 marks

Apply Which file do you upload to Play, and which do you send to a warehouse phone that installs by hand? 4 marks

The AAB goes to Play, which splits it into per-device APKs. The signed APK goes to the warehouse phone for direct install.

Analyze An app works in debug but crashes only in the release build, right after shrinking is switched on. Explain and fix. 5 marks

Beyond the syllabus

Not for the exam. Play has required AAB for new apps since 2021, and Play App Signing is the default, so upload key and app signing key are separate things to protect. Teams automate: a CI job reads keystore passwords from encrypted secrets, builds, signs, runs release tests, and publishes. Releases often use staged rollout to a small share, so a bad build can be halted. Search for Play App Signing, R8 keep rules, staged rollout and Gradle Play Publisher next.

5.6 M-commerce on mobile devices

M-commerce is buying and selling through a mobile device: an app, a mobile web page or a USSD menu. It exists because the phone is always with the buyer, so a shop can reach her at the moment of need. The money does not move in one jump. It passes along a chain of four parties, and each one may take a fee. That fee decides what the seller actually keeps.

You need: Chapter 5.1 for app-to-service messaging, Chapter 5.4 for transport security, and the mobile network basics of Unit 1.

The four parties in the chain

A mobile payment is a message, not cash. The customer taps Pay; the merchant app creates an order; the payment gateway forwards an authorisation request to the bank; the bank approves or declines; the answer returns along the same path. The figure traces a ₹1,200 payment.

  • Customer: holds the funding instrument (card, bank account, wallet balance) and authenticates.
  • Merchant: the seller's app or site; it creates the order and shows the receipt.
  • Payment gateway: a switch that routes messages between merchant and bank, and applies the merchant's fee.
  • Bank or PSP: the customer's bank, the card issuer, or a payment service provider that holds the money.

Pros: wide reach, one-tap repeat orders, location-linked offers. Cons: small screen for typing, a dropped network mid-payment, and fraud that arrives with the convenience.

Payment methods and their fees

Four instruments cover most Indian m-commerce. Published rates change; check the current schedule.

  • Card: card number or a saved token; the merchant pays a percentage plus a fixed amount per transaction.
  • Wallet: a prepaid balance held by a wallet issuer; the merchant pays the issuer a fee.
  • UPI: a bank-to-bank push from a UPI app; merchant fees are zero for many small merchants today.
  • Carrier billing: the amount is added to the phone bill; convenient for small sums, but the fee is the highest.
InstrumentTypical merchant fee
Card1.5%–3% + ₹2–₹5
Wallet0%–2%
UPI0% for many merchants
Carrier billingoften above 5%

Settlement, fees and security

Settlement is the step where the gateway and bank move the money into the merchant's account, usually one or two working days after the sale (T+1 or T+2). Until settlement, the sale is only an authorisation.

net = G − (r × G + f)

net is what the merchant receives in rupees; G is the gross order value in rupees; r is the fee rate as a decimal (0.02 for 2%); f is the fixed fee per transaction in rupees.

  • Run the payment in the gateway's page or SDK; never store the full card number.
  • Tokenise: the gateway returns a token that stands for the card.
  • Verify the payment on your server, not only in the app.
  • Send an idempotency key so a retry does not charge twice.
  • Refunds and chargebacks can reverse a settled sale weeks later.

Worked example

Question. A merchant sells an item for ₹1,200. A card gateway charges 2% plus ₹3 per transaction. A UPI transfer charges 0%. What does the merchant receive after each payment? For 500 card orders, what is the total gateway fee?

  1. Card fee = 0.02 × ₹1,200 + ₹3 = ₹24 + ₹3 = ₹27.
  2. Card net = ₹1,200 − ₹27 = ₹1,173.
  3. UPI fee = ₹0, so UPI net = ₹1,200 − ₹0 = ₹1,200.
  4. For 500 card orders, total fee = 500 × ₹27 = ₹13,500.

Answer. The merchant receives ₹1,173 on the card sale and ₹1,200 on UPI; 500 card orders cost ₹13,500 in gateway fees.

Exam traps

  • Comparing gross order value with net revenue: subtract the gateway fee first.
  • Writing 2% as 2 in a formula; use 0.02.
  • Charging the fixed fee per item instead of per transaction.
  • Confusing the customer's bank charge with the merchant's gateway fee.
  • Treating an authorisation as settlement; funds arrive at T+1 or T+2.

Check yourself

Remember Name the four parties in a mobile payment chain. 2 marks

Customer, merchant, payment gateway, bank or PSP.

Understand The customer pays ₹1,200 in full, yet the merchant receives less. Why? 3 marks

The gateway deducts its fee from the sale before settlement, so net = gross − fee.

Apply An ₹800 order uses a card gateway at 2.5% plus ₹2. Find the fee and the merchant's net. 4 marks

Fee = 0.025 × 800 + 2 = 20 + 2 = ₹22; net = 800 − 22 = ₹778.

Analyze A seller moves all card orders to UPI because the fee shows 0%. Give one risk in this decision. 4 marks

It depends on one rail: rules and fees can change, some customers lack UPI, and an outage stops all sales.

Remember What is settlement? 2 marks

The movement of funds into the merchant's account after authorisation, usually at T+1 or T+2.

Understand Why should the merchant app never store the full card number? 3 marks

A breach would expose card data and widen compliance scope; a gateway token replaces the number.

Beyond the syllabus

Not for the exam. Real gateways expose server-side payment APIs, webhooks for status, and reconciliation reports; production apps never trust the client's success screen. Researchers work on offline UPI over USSD and on privacy-preserving payment tokens. Search next for 'payment gateway webhooks', 'PCI-DSS SAQ A' and 'UPI merchant MDR'.

Takeaways

  1. An app should hand an SMS or e-mail to the phone's own app with an implicit intent unless the business case truly needs silent, server-side sending.
  2. A map screen is just a view that draws server-supplied tiles plus your markers, and every marker is a latitude–longitude pair you already hold.
  3. Location data is a trade-off between accuracy and battery, so pick a provider and an update interval that match the job.
  4. Geofencing moves the work from your app to the platform: you register a fence and wait for ENTER, DWELL or EXIT callbacks.
  5. Mobile security has layers — device, network, app — and every layer needs its own control: permission system, TLS with pinning, app sandbox and Keystore.
  6. Least privilege is the cheapest security control: every permission you do not request is a permission that cannot be abused.
  7. Publishing is a fixed sequence: version, shrink, sign with the release keystore, align, test the release build, then upload or distribute.
  8. In m-commerce the app is only one link in a chain of customer, merchant, gateway and bank, and the gateway fee decides net revenue.

Glossary

ACTION_SEND
Intent action that shares content of a given MIME type, letting the user pick any app that can accept it.
ACTION_SENDTO
Intent action that means 'send a message to this URI', used with smsto:, mailto: or tel: URIs and handled by another app.
Android Keystore
A system service that holds cryptographic keys in protected storage and performs operations without exposing key material.
App sandbox
The isolation boundary where each app gets its own Linux user ID and private storage, limiting damage if it is compromised.
Application ID
The unique package name that identifies the app on a device and in a store, and the identity that signing protects.
Camera position
The latitude, longitude, zoom and tilt that define what a map view is currently showing.
Certificate pinning
Restricting which server certificate or public key the client will trust, defeating man-in-the-middle attacks with forged certificates.
Dangerous permission
A permission class in Android that gives access to private user data or device control and therefore needs explicit user consent.
Data at rest
Data stored on the device or server, protected by encryption and access control.
Data in transit
Data travelling across a network, protected by TLS and optionally certificate pinning.
Fused location provider
A location API that merges GPS, Wi-Fi and sensor signals to give better accuracy at lower battery cost than any single provider.
Least privilege
Giving an app or a user the smallest set of rights needed for the current task, and no more.
Location provider
A source of position fixes such as GPS, network or passive, each with its own accuracy, speed and power profile.
Manifest
The AndroidManifest.xml file that declares the app's package, components, permissions and hardware features.
Merchant discount rate
The percentage fee a merchant pays on each card or wallet transaction, covering gateway, network and bank charges.
Mobile Top 10
OWASP's ranked list of the most common mobile app security risks, used as a checklist during design and testing.
ProGuard / R8
Tools that shrink, optimise and obfuscate class names in a release build, reducing APK size and raising the effort to reverse engineer.
Remote wipe
A command from a management server that erases device or work-profile data after loss, theft or employee exit.
Runtime permission
A permission the app must request from the user while running, because it protects a dangerous resource such as location or SMS.
sms_body
The intent extra key that carries the pre-filled text of an SMS when the SMS composer is opened.
SmsManager
Android class that sends and divides long SMS messages directly over the phone radio, requiring the SEND_SMS permission.
Tile server
The map provider's service that returns map tile images for a zoom level and tile coordinate.
UPI
India's Unified Payments Interface, which lets a mobile app send a payment request to a bank account through a virtual payment address.
versionCode
An integer in the manifest that must increase with every store release; the platform uses it to decide which build is newer.
versionName
The user-visible version string such as 2.4.1 shown in the store listing and the app's About screen.
zipalign
A build step that aligns uncompressed resources on 4-byte boundaries so Android can memory-map them efficiently.
