2.1 Mobile operating systems: Android, iOS, Windows Phone

Every phone runs an operating system: the layer that owns the hardware and lends it to apps. It decides which app gets the CPU, which is killed when memory runs short, which may read your contacts, and which may be installed at all. That last power makes the OS a shopkeeper as well as a manager. Pick Android, iOS or the retired Windows Phone and you also pick a language, a build tool and a store. This chapter compares the three, with Android in the most detail, because the rest of this unit builds on it.

You need Unit 1 for what a cellular network and a data connection do; nothing else.

What a mobile OS actually does

A mobile operating system (OS) is the software layer between the phone's hardware and the apps on the screen. When you hold the power button, the OS starts, checks the hardware and shows the home screen. From then on it hands out CPU time, memory, storage and radio access to every app that asks.

Four jobs define a phone OS.

  • Process and memory management. Each app runs as one or more processes, and the OS gives each process a private memory area. A phone has little RAM, so when a new app needs memory the OS quietly kills a background app and restarts it later from saved state.
  • Power management. The battery is the hard limit. The OS sleeps the CPU when nothing needs it, slows the clock under light load, and freezes background apps so they cannot drain the battery.
  • Sandboxing and permissions. Each app is boxed in. Android gives every app its own Linux user id (uid), so the file system itself blocks it from other apps' files. iOS uses its own sandbox for the same purpose. Anything outside the box — camera, contacts, location, microphone — needs a permission the user grants at run time.
  • Install, update and payment. The OS decides what code may be installed and who must have signed it. On Android and iOS that means an app store; on Windows Phone it meant the Microsoft Store.

This is why the OS choice is a business decision, not a detail. It fixes your language, your tools and how you get paid.

Android, iOS and Windows Phone side by side

Android sits on the Linux kernel, but it is not a Linux distribution in the Ubuntu sense: a retail phone has no shell package manager, and the framework you touch is Google's code. Above the kernel lie a hardware abstraction layer, native C and C++ libraries, the Android Runtime (ART) that executes an app's DEX bytecode, and the Java API framework. Apps are written in Java or Kotlin; Kotlin is Google's preferred language now. The core is open source as the Android Open Source Project, and most retail phones add Google Play services — Maps, push messaging, the Play Store — under licence.

iOS runs on Darwin, Apple's Unix core, whose kernel XNU is built from Mach and BSD code; iOS is closed source and ships only on Apple hardware. Apps use Swift, or the older Objective-C, and are built in Xcode. Xcode runs only on macOS, so an iOS build needs a Mac. Ordinary installs go through the App Store; TestFlight betas and enterprise builds are the managed exceptions.

Windows Phone used C# and XAML on the .NET stack, built in Visual Studio, with a tile-based interface called Metro or Modern UI. Microsoft stopped developing it, so treat it as history, next to BlackBerry's QNX-based system. Some syllabi group these under 'commercial mobile operating systems'.

From source code to a paid download

The path from source code to a download is the same shape on every platform.

  1. Write the code in the platform language.
  2. Declare what the app needs: Android lists permissions in AndroidManifest.xml; iOS states usage reasons in its Info.plist.
  3. Build and sign. Gradle produces a signed APK or AAB with your key; Xcode signs with your certificate and provisioning profile.
  4. Distribute. The store reviews the build and publishes it.
  5. Bill. The store charges the buyer, keeps its commission and remits the rest to you.

That last step is where m-commerce enters. An in-app purchase is charged to the user's stored card through the store's billing, and the developer is paid monthly. Selling physical goods may use an outside gateway such as UPI instead, which is why checkout rules differ between app categories. See Unit 5 for the publishing and checkout flow.

Worked example

Question. A small team must ship the same to-do app on Android, iOS and Windows Phone. For each platform, state the main language, the build tool, the store, and the one extra requirement. Then state how many of the three platforms the app actually ships on.

  1. Android: language Java or Kotlin; build tool Android Studio with Gradle; store Google Play; extra requirement none — any Windows, macOS or Linux PC will build it.
  2. iOS: language Swift or Objective-C; build tool Xcode; store the App Store; extra requirement a Mac running macOS, because Xcode runs nowhere else.
  3. Windows Phone: language C# with XAML for the interface; build tool Visual Studio; store the Microsoft Store; extra requirement none, but the platform is no longer developed, so there are no new devices and no new users to win.
  4. Count the platforms that are still living: Android and iOS are developed, Windows Phone is retired. Living platforms = 3 − 1 = 2.
  5. So the to-do app is written twice, in Java/Kotlin and in Swift, and the third build is dropped.

Answer. Two of the three platforms ship: Android in Java or Kotlin built with Gradle for Google Play, and iOS in Swift built in Xcode on a Mac for the App Store; Windows Phone (C#, XAML, Visual Studio) is retired.

Exam traps

  • Writing that Android is a Linux distribution in the Ubuntu sense. Only the kernel is Linux; the framework, ART and Play services above it are Google's.
  • Quoting a platform version without its API level. Android 13 is API level 33, and the API level is what decides whether a call compiles.
  • Mixing up ART and Dalvik. Dalvik was the older Android runtime; ART replaced it and is what executes app bytecode today.
  • Mixing up Windows Phone with Windows Mobile. They are separate products, and Windows Mobile is the older one.
  • Claiming Xcode runs on Windows. It does not, so any iOS build and signing job needs a Mac.

2.2 Android platform, SDK and development tools

Android is not one program but a fixed stack of layers, from a Linux kernel at the bottom to the dialer and contacts apps at the top. Your own app sits just above the Java API framework. The SDK, the software development kit, is the set of tools that compiles your code and installs it against one chosen version of that stack. Every Android project starts here: pick a platform version, build an APK, push it to a phone or an emulator. This chapter opens the stack, then opens the toolbox.

You need: Chapter 2.1 for what an operating-system layer is and why apps are sandboxed.

The stack, from the kernel up

The Android platform is a stack of six layers. Each layer talks only to the layer directly below it. That single rule keeps a camera bug away from the power driver.

Linux kernel, at the bottom. It carries the device drivers for touchscreen, Wi-Fi, camera and audio, and it does process isolation: every app runs as its own Linux user id, so one app cannot read another app's memory. It also handles power management and kills processes when memory runs low.

HAL, the hardware abstraction layer, sits on the kernel. It is a set of standard C interfaces for camera, audio, sensors and Bluetooth. A phone maker writes one HAL module per chip, and the layer above calls the same function names on every phone. This is why one Android release ships on hardware from many vendors.

Native libraries and the Android runtime share the next layer. The libraries are C and C++ code: SQLite for databases, OpenGL ES for drawing, the WebView engine for web content, which is Chromium-based on modern Android (it used WebKit before Android 4.4), media codecs, and Bionic, Android's own C library. The runtime is ART, the Android Runtime. Your Java or Kotlin source becomes DEX bytecode, a register-based format built for small memory, and ART executes it. ART replaced Dalvik from Android 5.0, compiling ahead of time at install. From Android 7.0 it also compiles just in time while the app runs, and later ahead-of-time compiles follow the recorded hot paths.

Java API framework. These are the classes you write against: Activity for one screen, View for a widget, ContentProvider for shared data, NotificationManager, PackageManager. Chapter 2.4 and Unit 3 use them; here you only need to know they form a thin layer over everything below.

System apps at the top: dialer, contacts, messages, settings, launcher. They are ordinary apps on the same framework API, which is why you can install a replacement launcher.

The SDK: what is inside the box

The SDK is not one program. It is a folder of tools, libraries and platform files that the SDK Manager downloads into versioned subfolders. Android Studio is an editor and debugger standing in front of it. Without the SDK, Studio opens your files but cannot build.

  • Platforms: one folder per API level, for example platforms/android-34. Inside is android.jar, the compiled framework classes your code is checked against.
  • Build-tools: versioned programs that run during a build. AAPT2 compiles XML resources and generates the R class; d8 converts Java bytecode into DEX.
  • Platform-tools: adb, the Android Debug Bridge, plus fastboot. adb install puts an APK on a phone, adb logcat prints the log, adb shell gives a shell on the device.
  • Emulator and system images: a complete Android image per API level. An AVD, Android Virtual Device, is a named setup of image, screen size and RAM that the emulator boots.
  • Command-line tools: sdkmanager and avdmanager, for build servers where nobody clicks a mouse.

Gradle is the build system. The Android Gradle Plugin adds tasks such as assembleDebug, which writes app-debug.apk. Logcat is one shared log stream carrying lines from every app and from the framework. Lint reads your source and resources for likely bugs before you run anything.

API level and the three numbers

An API level is the integer that names a platform version. Android 5.0 is API 21, Android 7.0 is API 24, Android 8.0 is API 26, Android 14 is API 34. Code and documentation use the integer because the marketing name changes every year.

android {
    compileSdk 34
    defaultConfig {
        minSdk 24
        targetSdk 34
    }
}

compileSdk is the platform folder used at build time. It fixes which framework classes and methods type-check: a class added in API 35 fails to compile under compileSdk 34.

minSdk is the lowest API level allowed to install the APK. The package manager reads it from the manifest and refuses anything lower.

targetSdk is the level you tested against and whose behaviour changes you accept. Android keeps old behaviour switched on for apps with a lower targetSdk, a compatibility mode. Raising targetSdk turns those switches off: background execution limits from API 26, stricter background location rules later.

minSdk and targetSdk are written in the module's build.gradle, and Gradle copies them into the manifest as minSdkVersion and targetSdkVersion. compileSdk is build-time only and is never put in the manifest.

Worked example

Question. A module's build.gradle sets compileSdk 34, minSdk 24 and targetSdk 34. A tester's phone reports API level 21. Explain what each of the three numbers means for this build, and state exactly what the tester sees when the APK is installed.

  1. compileSdk 34: the build compiles against platforms/android-34/android.jar. Any call into the Android 14 framework type-checks; a call to a class added in API 35 stops the build with a cannot-find-symbol error.
  2. minSdk 24: Gradle writes minSdkVersion 24 into the APK manifest. At install time the package manager compares the phone's API level with 24.
  3. The phone reports 21. Since 21 < 24, installation is refused with INSTALL_FAILED_OLDER_SDK, and on Google Play the listing is filtered out, so the app does not appear in search on that phone.
  4. The shortfall is 24 − 21 = 3 API levels.
  5. targetSdk 34: on a phone at API 34 or higher the app runs with Android 14 behaviour, because the compatibility switches kept for older targets stay off.
  6. To support the tester, drop minSdk to 21. compileSdk stays at 34, and each call to a method added after API 21 must be wrapped in a guard using that method's own API level, for example if (Build.VERSION.SDK_INT >= 26) for a method added in API 26. Without the guard the app compiles and then throws NoSuchMethodError on the API 21 phone.

Answer. compileSdk 34 fixes the compile-time framework and targetSdk 34 opts the app into Android 14 behaviour, while minSdk 24 blocks the API 21 tester, who is 3 API levels short and sees INSTALL_FAILED_OLDER_SDK plus no Play Store listing.

Exam traps

  • Swapping compileSdk and targetSdk. compileSdk is build-time only; targetSdk is a run-time behaviour opt-in, and reversing them is the examiner's favourite mistake.
  • Thinking Android Studio is the SDK. Studio is the editor; the SDK is the platforms, build-tools and platform-tools folders it drives.
  • Lowering minSdk as if it were free. Each call to a newer API then needs a Build.VERSION.SDK_INT guard, or the app crashes with NoSuchMethodError on old phones.
  • Reading API level as the Android version number. API 21 is Android 5.0, not Android 21.
  • Placing ART above the native libraries. ART is the runtime that executes DEX and sits beside them, not on top of them.

2.3 Creating a first Android app and its anatomy

An Android project is a small, fixed set of files. You edit XML for text and layout, Java for behaviour, and a manifest for app identity. The build turns each XML file and string into an integer constant in a generated class called R. Java then uses R.layout.activity_main or R.string.greeting, not file names. This separates design from code and catches missing resources at build time. Every Android app uses it.

You need: Chapter 2.2 for the SDK and API level.

Files you touch first

A new project called HelloApp has one app module. The module folder holds four things you touch first. manifests/AndroidManifest.xml names the app and its first activity. java/.../MainActivity.java is the screen's Java class. res/layout/activity_main.xml is the view tree. res/values/strings.xml holds text. build.gradle holds module settings: SDK levels, dependencies and app ID. The top-level build.gradle is separate; the module one decides how this app is built. In the New Project wizard choose Java as the language (and Groovy DSL if offered), so the module file is build.gradle and the activity is MainActivity.java. Kotlin projects follow the same anatomy, with .kt files and build.gradle.kts.

AndroidManifest.xml is not optional. For the first screen it needs an activity with the MAIN action and LAUNCHER category. Without that pair, the app installs but no icon opens it. MainActivity.java extends AppCompatActivity, which itself extends Activity, and overrides onCreate in both cases. setContentView(R.layout.activity_main) makes Android inflate the XML view tree. Add findViewById(R.id.text1) only when Java must change a view at run time. The package name, here com.example.hello, gives R its full name.

AAPT2 and the R class

During a build, Gradle runs AAPT2, the Android asset packaging tool. AAPT2 compiles each resource file. It gives every layout, string, drawable and view ID an integer constant. It writes these constants into R.java, generated in the app's package, for example com.example.hello.R. You never type or edit R.java. It contains nested classes: R.layout, R.id, R.string.

R.layout.activity_main is an int, not a file path. R.id.button1 is an int, not a button. R.string.greeting is an int, not text. At run time the framework uses the int to look up the compiled resource in the APK. In XML, @+id/button1 creates an ID; @id/button1 refers to an existing one; @string/greeting refers to a string resource. A bad @string name leaves no constant, so Java shows a red R. That is a resource error, not a missing import.

Run on an emulator

Start an emulator from Device Manager. Press Run. Gradle builds a debug APK, installs it, and sends a launch intent naming the launcher activity. Android creates MainActivity, calls onCreate, and setContentView inflates res/layout/activity_main.xml. The TextView reads @string/greeting and shows Hello, Chennai. Log.d("HelloApp", "onCreate") writes to Logcat. Open Logcat and filter by tag HelloApp or package com.example.hello. If the app stops, the top line is usually the exception.

Use a real phone the same way after enabling USB debugging. The build must finish before install starts; a failed build leaves the old APK running, which looks like an ignored edit. Check the Run window for BUILD SUCCESSFUL. Clear Logcat before a fresh run; old lines mislead. A crash on launch usually points to the manifest (activity not declared, wrong theme) or to findViewById returning null because the id is missing from the inflated layout. A missing layout file stops the build instead.

Worked example

Question. A new project is HelloApp, package com.example.hello, one empty activity. You must show Hello, Chennai. (a) Name the two files you edit and the exact change in each. (b) State how many files are edited. (c) State the manifest condition for the app to open.

  1. res/values/strings.xml: add a string resource named greeting with value Hello, Chennai. AAPT2 will make R.string.greeting.
  2. res/layout/activity_main.xml: add a TextView with id text1 and text set to @string/greeting. This creates R.id.text1 and uses R.string.greeting.
  3. MainActivity.java: leave it unchanged. The template already calls setContentView(R.layout.activity_main), which inflates activity_main, so the TextView appears with the greeting. findViewById(R.id.text1) is needed only to change the text at run time.
  4. Manifest: not edited here, but its activity needs MAIN and LAUNCHER, or no icon opens the app.

Answer. Two files are edited: strings.xml and activity_main.xml. MainActivity.java is untouched; its existing setContentView(R.layout.activity_main) inflates the layout, and the TextView takes its text from @string/greeting. The manifest must declare the launcher activity with MAIN and LAUNCHER.

Exam traps

  • Editing XML and expecting the running app to change without a rebuild. Resources are compiled into R and the APK.
  • No import of R is needed, because R sits in the app's own package com.example.hello. The harmful one is import android.R. A red R almost always means a resource error somewhere, not a missing import.
  • Confusing @+id/button1 (creates an ID) with @id/button1 (refers to one).
  • Missing MAIN and LAUNCHER: the app installs but no launcher icon opens it.
  • Calling findViewById before setContentView returns null.

2.4 Activities and the activity life cycle

An activity is one screen of an Android app: a login form, a list of trains, a single ticket. The user jumps between screens and rotates the phone, and Android must free memory, save battery and let other apps come forward. So the system creates and destroys activity objects itself and calls a fixed order of methods, the life cycle, as the screen becomes visible, gets covered and disappears. Knowing that order tells you where to build the screen, where to start and stop the camera, and where to save a half-typed form.

You need Chapter 2.3 for the Activity class, the manifest entry and setContentView, and Chapter 2.1 for why Android must reclaim memory from apps it cannot see.

One screen, one activity

An activity is one screen with one job. Each screen is a Java class that extends Activity (or AppCompatActivity) and calls setContentView to attach an XML layout.

Android cannot start a class it does not know about, so every activity is declared in AndroidManifest.xml:

<activity android:name=".MainActivity" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

The MAIN action with the LAUNCHER category marks the screen the app icon opens. Other activities are listed with only android:name. A class missing from the manifest throws ActivityNotFoundException when you try to open it. Chapter 2.5 shows how one activity names another.

While the object lives, Android tracks four states: created (object exists, not visible), started (visible, not in front), resumed (visible, in front, receives touches) and destroyed (object gone). A stopped activity is back in the created state. Visible and foreground are not the same: onStart makes the screen visible, onResume puts it in front. A dialog-style activity on top leaves your activity visible but paused — you can see it, you cannot touch it.

Activities the user opens sit on a back stack inside a task. Pressing Back pops the top activity and returns to the one below.

The seven callbacks

Android calls these methods, called callbacks, in a fixed order. Override only the ones you need, and always call super first.

  1. onCreate(Bundle savedInstanceState) — runs once per instance. Attach the layout, create objects, wire listeners. Keep it fast.
  2. onStart() — the activity becomes visible.
  3. onResume() — the activity is in front and has focus. Start the camera preview, sensor listeners, animations.
  4. onPause() — the activity loses the foreground, because another screen is coming forward or the user pressed Home. Stop animations and release the camera. Be quick: the next activity's onResume waits for your onPause to return.
  5. onStop() — the activity is no longer visible. Release heavy things such as a database cursor or a GPS listener.
  6. onDestroy() — the instance is about to go: rotation, Back, or the system finishing it.
  7. onRestart() — a stopped activity is coming back; it runs before onStart.

To read the order on a real phone, put Log.d("LC", "onCreate") at the top of each override and filter Logcat by the tag LC. The messages appear in the order the callbacks ran, with a timestamp on each line.

Rotation: destroy and recreate

When the phone rotates, Android by default throws the activity away and builds a new one, because the new orientation may need a different layout file (Unit 3, screen components and layouts). For a rotation while the activity is resumed the order is onPause, onStop, onDestroy, then onCreate, onStart, onResume on the fresh object. Fields are not copied: an int counter holding 7 comes back as 0.

Carry small state in a Bundle, a key-value store of ints, strings and small objects. onSaveInstanceState(Bundle outState) runs before the activity can be destroyed: after onStop from Android 9 (API 28), before onStop on older versions. onCreate receives the same Bundle as savedInstanceState, which is null on a fresh launch.

Pseudocode.

onSaveInstanceState(Bundle out):
    super.onSaveInstanceState(out)
    out.putInt("count", count)

onCreate(Bundle saved):
    super.onCreate(saved)
    setContentView(R.layout.activity_main)
    if saved != null:
        count = saved.getInt("count", 0)

A Bundle suits a few hundred bytes. Five thousand rows belong in a file or SQLite (Unit 4). And onDestroy is not guaranteed: when RAM runs low the system may kill the whole process after onStop without calling onDestroy, so save what matters in onPause or onSaveInstanceState.

Worked example

Question. An activity logs every callback with Log.d("LC", name). Write the exact log lines in order, and the number of lines, for each action: (a) launch the app from the app drawer, (b) press Home, (c) reopen the app from the recents list, (d) press Back. Then (e) rotate the phone while the activity is resumed. Also state what an int field holding count = 7 shows after that rotation.

  1. (a) Launch: the instance is created, becomes visible, comes to the front. Lines: onCreate, onStart, onResume. That is 3 lines.
  2. (b) Home: the activity is fully hidden behind the launcher. Lines: onPause, onStop. That is 2 lines. A paused-only step would need something that is still visible, such as a dialog.
  3. (c) Recents: a stopped activity returns through onRestart before it is started again. Lines: onRestart, onStart, onResume. That is 3 lines.
  4. (d) Back: the activity leaves the back stack for good. Lines: onPause, onStop, onDestroy. That is 3 lines.
  5. (e) Rotation while resumed: the old instance is destroyed and a new one is created. Lines: onPause, onStop, onDestroy, then onCreate, onStart, onResume. That is 6 lines.
  6. Total lines logged: 3 + 2 + 3 + 3 + 6 = 17.
  7. The field count is an ordinary int inside the destroyed object, so the new object starts with count = 0. Saving it with out.putInt("count", count) in onSaveInstanceState and reading it back from savedInstanceState in onCreate brings back 7.

Answer. The orders are (a) onCreate, onStart, onResume; (b) onPause, onStop; (c) onRestart, onStart, onResume; (d) onPause, onStop, onDestroy; (e) onPause, onStop, onDestroy, onCreate, onStart, onResume — 17 log lines in all, and the counter reads 0 unless it was saved in a Bundle.

Exam traps

  • Saying onPause means the activity is destroyed. It is still alive, and it may still be visible under a dialog; only onStop says it is hidden.
  • Assuming onDestroy always runs. When the system is short of memory it can kill the process after onStop without any callback, so onDestroy is not a safe place to save data.
  • Thinking rotation calls onRestart. It does not: the instance is new, so onCreate runs, not onRestart.
  • Expecting onSaveInstanceState to run when the user presses Back. It does not, because that activity is finishing and its state will never be restored.
  • Mixing up visible and foreground. onStart gives visibility, onResume gives the foreground; a started-but-not-resumed activity is visible but gets no touches.

2.5 Intents: linking activities and calling built-in apps

An intent is a message object. It can name one target activity, or name an action for Android to match. It exists so screens and apps can ask for work without hard-coding each other. A restaurant screen can open the dialer, a browser, or a share sheet with the same mechanism. Used in calls, maps, sharing and picking a contact.

You need Chapter 2.4 for what an activity is and how it is declared.

Intent as a message

An intent is an Intent object. It carries a request from one component to another. The system routes an implicit intent; the caller does not choose the process.

Key fields: component names one exact class; action is a verb such as ACTION_VIEW; data is a Uri such as tel:9876543210; extras is a Bundle of key-value pairs; category and type filter matches.

An explicit intent sets component and opens a known screen. An implicit intent sets action, data and often type. Android compares it with intent filters in other apps' manifests. A filter lists accepted actions, categories and data patterns.

If no filter matches, startActivity throws ActivityNotFoundException. The figure follows both buttons from the intent, through the match, to the launch.

Use explicit intents for your own screens; use implicit intents for another app's work. The caller never sees the target's class name in an implicit intent.

Built-in actions and safe launch

Use new Intent(this, DetailActivity.class) for your own screen. For another app, set an action.

  • ACTION_DIAL opens the dialer with a number; no permission.
  • ACTION_CALL places a call; needs CALL_PHONE.
  • ACTION_VIEW opens a Uri such as https, geo or tel.
  • ACTION_SEND shares typed content; set the MIME type.
  • ACTION_SENDTO sends to a Uri such as mailto: or smsto:.
  • ACTION_PICK asks another app to return a chosen item.

ACTION_DIAL fills the dialer and needs no permission. ACTION_CALL places the call and needs CALL_PHONE.

Common extras keys: EXTRA_TEXT, EXTRA_SUBJECT, EXTRA_EMAIL. Before starting, check intent.resolveActivity(getPackageManager()) != null, or query PackageManager. startActivityForResult is deprecated; use the Activity Result API.

For sharing, createChooser(share, "Send via") shows the app list. Without it Android may use a default, and may throw if no app matches. A chooser is itself an implicit intent wrapper.

Worked example

Question. A restaurant screen has two buttons. Call should open the dialer with 9876543210 filled in. Share should send the text Table for 4 to whichever app the user picks. Write both intents and name the checks.

  1. Call intent: action Intent.ACTION_DIAL, data Uri.parse("tel:9876543210"). This fills the dialer. It needs no permission; the user presses call.
  2. Do not use ACTION_CALL: it places the call directly and needs CALL_PHONE.
  3. Share intent: new Intent(Intent.ACTION_SEND); setType("text/plain"); putExtra(Intent.EXTRA_TEXT, "Table for 4").
  4. Wrap it: startActivity(Intent.createChooser(share, "Send via")). The chooser lists apps and avoids a silent default.
  5. Guard the start. From targetSdk 30, package visibility makes resolveActivity return null unless the manifest declares a <queries> entry for the intent, so Share would silently do nothing. Declare <queries> and check share.resolveActivity(getPackageManager()) != null, or start it inside a try-catch for ActivityNotFoundException.

Answer. Call uses ACTION_DIAL with tel:9876543210; Share uses ACTION_SEND, type text/plain, extra Table for 4, inside createChooser.

Exam traps

  • Starting an implicit intent without a resolveActivity or PackageManager check causes ActivityNotFoundException.
  • Using ACTION_CALL where ACTION_DIAL is enough: direct call and missing CALL_PHONE permission.
  • Forgetting setType on ACTION_SEND: many share apps will not match.
  • Putting a Uri in extras when it belongs in data: intent-filter matching fails.
  • Sending an explicit intent to another app's private activity: SecurityException.

2.6 Fragments and specialized fragments

A fragment is a reusable piece of a screen that lives inside an activity and has its own life cycle. One list-and-detail code base can fill a phone screen or half a tablet screen without being written twice. The activity owns the window; the fragment draws inside a container view the activity provides. Fragments carry most visible content of a modern Android app: lists, settings, dialogs. Their data goes in through an arguments Bundle and comes out through the host activity, and the FragmentManager adds, replaces and removes them.

You need: Chapter 2.4 for the activity life cycle and Chapter 2.3 for layouts and the R class.

Why fragments exist

A phone is narrow, so a list and the details of one item usually need two screens. A tablet can show both at once. Writing the logic twice wastes effort and the copies drift apart.

A fragment has its own layout XML and Java class and draws inside a container view owned by an activity. The same ListFragment can fill a whole phone screen or the left half of a tablet screen. The activity stays in charge of the window; the fragment is a guest.

The activity layout holds at least one container, usually a FrameLayout such as R.id.list_container. The fragment never chooses its position; the activity's XML does. Android picks the layout by qualifier: res/layout holds the phone layout with one container, res/layout-sw600dp holds one with two containers, list_container and detail_container, used when the smallest width is at least 600 dp.

A dp (density-independent pixel) is a screen-size unit that does not change with pixel density; 1 dp is about 1/160 inch. A typical phone is about 360 dp wide, a tablet 900 dp or more. Code calls findViewById(R.id.detail_container): on the phone it returns null, on the tablet it returns the second container.

The fragment life cycle

The host activity drives the fragment. Android calls these methods in this order: onAttach(Context), onCreate(Bundle), onCreateView(LayoutInflater, ViewGroup, Bundle), onViewCreated(View, Bundle), onStart(), onResume(), onPause(), onStop(), onDestroyView(), onDestroy(), onDetach().

The list splits into two halves. From onCreate to onDestroy the fragment object exists. From onCreateView to onDestroyView it has a view on screen. onCreateView must return the root View, usually by calling inflater.inflate(R.layout.fragment_list, container, false); onDestroyView throws that view away. A fragment parked on the back stack keeps its object and loses its view.

The callbacks are tied to the host but never equal to it. A fragment cannot resume before its activity resumes, and when the activity stops, its fragments are stopped in the same pass right after the activity's own onStop() runs. getActivity() returns the host activity, and null once onDetach has run.

Rotation destroys and recreates the activity. The FragmentManager recreates its fragments and restores their saved state, so do not keep important data in plain fields; put it in the arguments Bundle.

FragmentManager and FragmentTransaction

Every activity has a FragmentManager. Call getSupportFragmentManager() in the activity, or getParentFragmentManager() inside a fragment. The manager keeps the list of fragments attached to each container and restores them after a configuration change.

A transaction is a group of changes applied together. Begin it with beginTransaction(), which returns a FragmentTransaction.

  • add(containerId, fragment, tag): puts a new fragment into that container.
  • replace(containerId, fragment): removes everything in that container, then adds the new fragment.
  • remove(fragment): takes one fragment out of its container.
  • addToBackStack(name): records the transaction so Back undoes it.
  • commit(): sends work to the main thread and returns immediately.

Without addToBackStack, Back closes the whole activity instead of returning to the previous fragment. Calling commit() after onSaveInstanceState throws IllegalStateException; check isStateSaved() first, and avoid commitAllowingStateLoss() unless losing the change is safe.

Data goes in through setArguments(bundle) before the transaction, read with getArguments(); never pass data through a constructor, because the system recreates the fragment with no arguments. Data comes out through the host activity: declare an interface, let the activity implement it, call it from the fragment. Newer code uses the Fragment Result API: setFragmentResult("itemKey", bundle) on the sender and setFragmentResultListener("itemKey", this, listener) on the receiver. Never hold a direct reference to another fragment.

Specialized fragments

Three ready-made fragment types cover common screens. Each is still a fragment: same life cycle, same FragmentManager, same arguments Bundle.

  • ListFragment: its view is a ListView; call setListAdapter(adapter) and override onListItemClick. Good for short lists; newer code puts a RecyclerView inside an ordinary fragment (see Unit 3).
  • DialogFragment: shows a dialog window. Override onCreateDialog(Bundle) to build an AlertDialog, or onCreateView for a custom layout. It survives rotation because the FragmentManager recreates it; close it with dismiss().
  • PreferenceFragmentCompat: builds a settings screen from an XML preference file. It needs the AndroidX preference library and writes choices through the preference system (see Unit 4).

A DialogFragment can hand a result back through the Fragment Result API, which is why raw AlertDialog objects are avoided: a raw dialog is lost on rotation and the activity has no safe handle on it.

Worked example

Question. A master-detail app lists 3 items. The phone is 360 dp wide and the tablet is 900 dp wide. State which layout folder each device uses, how many fragment containers each layout has, and trace what happens when the user taps item 2 on each device. Give the back-stack size after the tap.

  1. The qualifier sw600dp matches when the device's smallest width is at least 600 dp. Phone: 360 dp < 600 dp, so res/layout/activity_main.xml is used. Tablet: 900 dp ≥ 600 dp, so res/layout-sw600dp/activity_main.xml is used.
  2. The phone layout holds one FrameLayout, list_container; the tablet layout holds two, list_container and detail_container. Container counts are 1 and 2.
  3. The activity adds a ListFragment of 3 items into R.id.list_container: getSupportFragmentManager().beginTransaction().add(R.id.list_container, new ListFragment()).commit().
  4. findViewById(R.id.detail_container) returns null on the phone, so no detail fragment is added: 1 fragment on screen, back stack = 0. On the tablet it returns the second container, so the activity adds a DetailFragment with arguments item = 1. Fragments = 2, back stack = 0.
  5. Phone tap item 2: the ListFragment calls the host's onItemSelected(2). The host builds a DetailFragment with arguments item = 2 and runs replace(R.id.list_container, detail), addToBackStack(null), commit(). The list view dies but its fragment object stays on the back stack, so back-stack size = 1.
  6. Tablet tap item 2: the host replaces whatever sits in detail_container with a new DetailFragment with arguments item = 2, no addToBackStack. The list stays visible at left; back-stack size = 0.

Answer. The sw600dp threshold is 600 dp: the 360 dp phone uses 1 container and ends with 1 back-stack entry after the tap, while the 900 dp tablet uses 2 containers and ends with 0 back-stack entries.

Exam traps

  • Calling getActivity() after onDetach, or getView() after onDestroyView. The fragment object may still exist on the back stack with no host and no view.
  • Calling commit() after onSaveInstanceState and crashing with IllegalStateException. Check isStateSaved() first.
  • Treating the fragment and activity life cycles as identical. A fragment on the back stack can run onDestroyView while the activity is fully resumed; the view dies, the object does not.
  • Passing data through a constructor. On rotation the system recreates the fragment with the no-argument constructor, so the field is empty; use setArguments and getArguments.
  • Calling another fragment's method directly. After rotation the saved reference points at a dead fragment object no longer attached to any window.

Beyond the syllabus

Not for the exam. In production Android, most apps follow a single-activity design: one activity hosts many fragments, and the Jetpack Navigation component owns the FragmentManager transactions and the back stack. Fragments keep gaining features such as the Fragment Result API and view life-cycle-aware data collection. Takeaways

  1. A mobile OS does four jobs that matter most to app developers: sandboxing, permissions, process and memory control, and power management.
  2. Android, iOS and Windows Phone differed mainly in how open the platform was, how apps were distributed, and how strictly apps were sandboxed.
  3. The Android platform is a stack of layers; the SDK lets you write code against one chosen API level of that stack.
  4. An Android project is a small fixed set of files, and R is the generated bridge from Java code to XML resources.
  5. An activity is one screen, and Android moves it through a fixed callback order as it becomes visible, gets covered and is destroyed.
  6. Save your state in onSaveInstanceState and restore it in onCreate, because Android may recreate or kill your activity at any time.
  7. An explicit intent names the activity to open; an implicit intent names an action and lets the system pick a handler.
  8. A fragment lets one activity show different layouts for phone and tablet, and FragmentManager transactions add, replace and remove it.

The stack of activities or fragment transactions that the Back button pops.
Context
The handle an app uses to reach its resources, package information and system services.
DialogFragment
A fragment that shows a floating dialog window instead of a full screen.
Doze
A power-saving mode that delays background network and CPU work when the phone is idle and still.
Extras
Key-value data carried inside an intent's Bundle to the receiving component.
FragmentManager
The object that adds, replaces, removes and tracks fragments inside an activity.
Garbage collection
Automatic freeing of memory that no longer has a live reference, done by the runtime.
Gradle
The build tool that compiles code, merges resources and produces the APK or app bundle.
Intent filter
A manifest entry that declares which actions, data types and categories a component can handle.
Low-memory killer
The Android component that closes low-priority background processes when RAM is short.
Manifest
The XML file that declares an app's components, permissions and required SDK levels.
minSdkVersion
The lowest API level on which the app will install and run.
onCreate
The first activity callback, where you inflate the layout and set up state.
onPause
The callback when the activity loses focus but may still be partly visible.
onSaveInstanceState
The callback where an activity stores small pieces of state in a Bundle before it may be killed.
PendingIntent
A wrapped intent that another app may fire later on your app's behalf, used in notifications and alarms.
Resource ID
An integer generated into R that names one layout, string, drawable or view.
Sandbox
An isolated area of storage and memory that only one app's user ID can read or write.
Sideloading
Installing an app from a file or non-official store instead of the main store.
targetSdkVersion
The API level the app was tested against, which turns on that version's behaviour changes.
