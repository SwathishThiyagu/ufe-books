3.1 Screen components and layouts

An Android screen is not one drawing but a tree of small parts. Each part is a View: a button, a line of text, an image. A special View called a ViewGroup holds other views and decides where they sit. The activity window has one root ViewGroup, and every widget on the screen hangs below it. This tree is why Android screens are easy to change: move one branch, and only that part changes. You write the tree in XML, the activity inflates it in onCreate, and the user sees the result.

You need: Unit 2, activities and the activity life cycle, because a layout is inflated inside onCreate.

Views, view groups and the screen tree

A View occupies a rectangle on the screen and draws itself. It also receives touch events. A ViewGroup is a View with children. The group measures each child, places it, and passes touches down. Because a ViewGroup is itself a View, groups can nest: a vertical LinearLayout can hold a horizontal LinearLayout, which holds three buttons. The activity window holds exactly one root ViewGroup. Everything else is a descendant. This parent-child relation is the screen tree.

Every view shares a set of XML attributes. The id gives the view a name you can find from Java: android:id='@+id/saveButton'. The + means create the id if it does not exist. Width and height take match_parent (fill the parent), wrap_content (just big enough for the content) or a fixed size in dp. Padding is space inside the view, between its border and its content. Margin is space outside, between this view and its neighbours. Background sets a colour or drawable. Visibility is visible, invisible (hidden but still takes space) or gone (hidden and takes no space). enabled='false' blocks clicks and often greys the view.

Layouts place the children

A layout is a ViewGroup with a placement rule. LinearLayout puts children in one line, set by android:orientation to horizontal or vertical. Extra space can be shared by android:layout_weight. If three buttons in a horizontal row have weights 1, 2 and 3, the free space is cut into 1+2+3=6 parts and shared in that ratio. For weights to work cleanly, set the child's layout_width to 0dp in a horizontal layout (or layout_height to 0dp in a vertical one). Then the child does not first ask for its content width; the weight decides the whole width. weightSum sets the total by hand when you want a weight to mean a fraction of a fixed total.

Other layouts answer other questions. RelativeLayout places a child relative to the parent or to a sibling: layout_alignParentRight='true', layout_below='@id/title', layout_toRightOf='@id/icon'. FrameLayout stacks children in order; the last child is drawn on top, so it suits a badge over an image. TableLayout makes rows, and stretchColumns names columns that share leftover width. ConstraintLayout ties each child to the parent or to siblings with constraints, such as start to parent start and end to parent end; a child with both horizontal constraints and width 0dp spreads between them. GridLayout uses row and column indexes. Some syllabi call this 'designing by declaration' and call layouts 'screen containers'.

dp, sp and resource files

Sizes on Android are not pixels. A dp is a density-independent pixel: 1 dp is 1 pixel on a 160 dpi baseline screen and grows on denser screens so the physical size stays about the same. The conversion is:

px = dp × dpi ÷ 160

px is device pixels; dp is the density-independent size; dpi is the screen density in dots per inch.

Text uses sp, a scale-independent pixel. It is like dp but also follows the user's font-size setting. Use dp for margins, padding and view sizes; use sp for text. A button height of 48 dp and a text size of 16 sp are typical Android choices.

Do not hard-code repeated strings, sizes and colours in the layout. Put them in res/values/strings.xml, dimens.xml and colors.xml, then refer to them as @string/app_name, @dimen/margin_small and @color/brand_blue. This keeps one change in one place and helps translation. The layout itself lives in res/layout/. When the activity calls setContentView(R.layout.main), Android inflates the XML into the view tree. State kept across rotation is a separate problem; see <a href='#handling-display-orientation-changes'>3.2.

Worked example

Question. A horizontal LinearLayout is match_parent wide on a screen 360 dp wide. It holds three buttons, each with layout_width = 0dp and layout_weight = 1, 2 and 3. Find each button's width in dp, and in pixels on a 480 dpi screen. Show the check that the widths add to the row width.

  1. Total weight = 1 + 2 + 3 = 6.
  2. One weight unit = 360 dp ÷ 6 = 60 dp.
  3. Button A = 1 × 60 = 60 dp; Button B = 2 × 60 = 120 dp; Button C = 3 × 60 = 180 dp.
  4. Check: 60 + 120 + 180 = 360 dp, which is the full row.
  5. Density = 480 ÷ 160 = 3.
  6. In pixels: A = 60 × 3 = 180 px; B = 120 × 3 = 360 px; C = 180 × 3 = 540 px.

Answer. Button A is 60 dp (180 px), B is 120 dp (360 px), C is 180 dp (540 px), and the three widths add to 360 dp.

Exam traps

  • gravity centres a layout's own children, while layout_gravity places that view inside its parent. Swapping them is the most common layout bug.
  • Weights share space cleanly only when the child's width is 0dp in a horizontal layout. With match_parent the child already asks for the whole row, so the arithmetic gives surprising widths.
  • Margin is outside a view; padding is inside. A margin pushes neighbours away; padding moves the content within the border.
  • Use dp for sizes and sp for text. Text set in dp ignores the user's font-size setting, and a fixed px value breaks across screens.
  • invisible keeps the view's space; gone removes the space as well. Use gone when a hidden row should not leave a gap.

3.2 Handling display orientation changes

Rotate a phone and Android destroys the activity and builds a new one on a new layout. Rotation is a configuration change; the system answers it like a fresh launch, so values held only in Java fields die with the old object. This chapter shows the Bundle that carries state across, the view ids that save themselves, and the -land resource folders that give a real landscape design. Only a few universities teach this in full.

You need the activity life cycle from Unit 2 and the view tree from 3.1 Screen components and layouts, because rotation inflates a second layout tree.

Rotation rebuilds the activity

Portrait on a 1080 × 1920 phone, landscape on 1920 × 1080. The resource qualifier changed, so Android treats this as a configuration change, like a language switch or a keyboard plug-in.

The response is drastic: onPause → onStop → onDestroy on the old activity, then onCreate → onStart → onResume on a new one. Two Activity objects exist in that sequence, never one. Every field — a counter, a list, a socket — belonged to the old object and is gone; the new object starts from its field initialisers.

Only one thing crosses the gap: a Bundle Android hands to onCreate, after onSaveInstanceState fills it.

Saving and restoring state

onSaveInstanceState(Bundle outState) runs before the activity is destroyed for a configuration change. Write small key-value pairs: outState.putInt("count", count).

Read them in onCreate(Bundle savedInstanceState). On first launch that Bundle is null, so test for null. onRestoreInstanceState(Bundle) runs after onStart, when the view tree exists.

Views with an android:id save their own state, but what each saves differs. EditText saves typed text, CheckBox its tick, ScrollView its scroll position. A plain TextView saves its text only if android:freezesText="true" is set. A view with no id saves nothing.

The Bundle is not storage. Keep a record id there, not a hundred rows; reload rows from your database (Unit 4).

Alternative resources and the escape hatch

Alternative resources carry the design. res/layout-land/activity_main.xml is a second layout used only in landscape: same file name, different folder picked by qualifier. res/values-land/ holds landscape dimensions or strings; res/values-sw600dp/ matches any screen at least 600 dp wide, such as a tablet. With no landscape layout Android reuses the portrait one and stretches it.

The escape hatch is android:configChanges="orientation|screenSize" in the manifest. Rotation then does not destroy the activity: onConfigurationChanged(Configuration) runs on the same object and fields survive. List both values; screenSize is needed by modern Android. Use it only for a surface you redraw yourself, such as a video player or drawing canvas. It never inflates a landscape layout.

To keep objects across rotation without that trick, use a retained fragment or a ViewModel; both hand the same instance to the new activity.

Worked example

Question. An activity keeps an int field count and a TextView shows "Taps: 7" after seven taps. The phone rotates. What does the label show (a) with no saving code, (b) with onSaveInstanceState putting count in the Bundle and onCreate reading it back, (c) with android:configChanges="orientation|screenSize" declared?

  1. Before rotation the field holds count = 7 and the label reads "Taps: 7".
  2. Rotation changes the orientation qualifier, so Android destroys the old activity and creates a new one.
  3. (a) No saving code: the new object's count is 0, so the label reads "Taps: 0".
  4. (b) count = 7 goes into the Bundle; the new onCreate reads 7, so the label reads "Taps: 7".
  5. (c) configChanges is declared: the activity is not destroyed, count still holds 7, label reads "Taps: 7".

Answer. (a) Taps: 0, (b) Taps: 7, (c) Taps: 7 — only the Bundle copy or the configChanges declaration carries the 7 across.

Exam traps

  • onSaveInstanceState is not called when the user presses Back or when you call finish(). It is for transient screen state only.
  • android:configChanges hides the problem but gives you no landscape layout, so the portrait design stays stretched.
  • Forgetting the null check on savedInstanceState crashes on the first launch.
  • onRestoreInstanceState runs after onStart, not before onCreate.
  • The Bundle is passed through the system: large bitmaps or long lists cause a TransactionTooLargeException. It is not a database.

3.3 Action bar and menus

The action bar is the strip at the top of an activity. It shows the app icon, a title, a few action buttons and a three-dot overflow list. Those buttons are not hard-coded: they come from a menu XML file that the activity inflates, then handles by item id. This keeps commands in one resource and lets Android decide what fits. Modern apps often use a Toolbar set as the support action bar, but the menu API and item ids stay the same.

You need: 3.1, because the action bar sits above the activity's content layout.

The strip above the content

An activity owns a rectangular strip at the top called the action bar. Some syllabi call the same idea the app bar. It normally contains the app icon, the activity title, action buttons that run common commands, and an overflow button drawn as three vertical dots. The overflow button opens a small list for commands that do not fit or that are rare.

Commands are declared in a menu resource, usually res/menu/main.xml. The root element is menu. Each command is an item element with android:id, android:title, android:icon and app:showAsAction. android:orderInCategory sets ordering. A group element can share visibility or checkable settings, and a nested menu element creates a submenu. The activity inflates this file at runtime; the bar is a view of the menu, not a hand-built row of buttons.

Modern code often places a Toolbar in the layout and passes it to setSupportActionBar(toolbar). The old framework action bar is then replaced by that Toolbar, but the menu callbacks and item ids do not change. The content layout sits below the bar, as described in 3.1.

Inflating a menu and handling clicks

onCreateOptionsMenu(Menu menu) is called when the activity first needs the options menu. Call getMenuInflater().inflate(R.menu.main, menu), then return true. Returning false suppresses the menu.

onPrepareOptionsMenu(Menu menu) runs before the menu is shown each time. Use it to enable or disable an item, hide it, or change its title. Rotation destroys and recreates the activity, as covered in 3.2, so the menu is inflated again and prepared again.

onOptionsItemSelected(MenuItem item) receives the click. Read item.getItemId(), compare with R.id.search and other ids, run the command, and return true. Returning false makes the system fall through, so the item looks dead. The Up arrow arrives here with id android.R.id.home. Up moves up the app's screen hierarchy; the system Back button pops the back stack. They are not the same action.

showAsAction controls placement. There are three placement values. always asks for a bar slot. ifRoom takes a slot only when one is free. never keeps the item in overflow. withText is not a placement value; it is a flag joined with a pipe, for example app:showAsAction="ifRoom|withText". It shows the title beside the icon when the item is shown on the bar. Combine withText with always or ifRoom. Items marked ifRoom are placed in declaration order until the slots run out. On a Toolbar write app:showAsAction with the app namespace; the android: form is ignored.

Context menus and popup menus

A context menu belongs to one view, not to the whole screen. Call registerForContextMenu(view) for that view. A long press then calls onCreateContextMenu(ContextMenu menu, View v, ContextMenu.ContextMenuInfo info). Inflate the menu there and call super first. The click arrives in onContextItemSelected(MenuItem item); handle the id and return true.

Use a context menu for actions on one row or one image, such as Rename or Delete on a list item. The menu should be short. A long list belongs in a dialog or a new screen.

A PopupMenu is a floating list anchored to a view. Create it with new PopupMenu(this, anchorView), inflate its menu, set setOnMenuItemClickListener, then call show(). It is local to that anchor and does not use onCreateOptionsMenu or onOptionsItemSelected. Use it for a small choice beside a button, such as Sort by date or Sort by name.

Choose by scope: options menu for screen-wide frequent commands, context menu for one item, popup menu for a local choice. All three use the same menu XML format and item ids.

Worked example

Question. A Toolbar has room for 3 action slots. Its menu XML has five items: Search with showAsAction=always; Share, Edit and Delete with showAsAction=ifRoom; Settings with showAsAction=never. Which items appear on the bar, and how many go to overflow?

  1. Start with 3 free slots, an empty bar and an empty overflow list.
  2. Search is always, so it takes slot 1. The bar is Search. Free slots are now 2.
  3. Share is ifRoom, so it takes slot 2. The bar is Search, Share. Free slots are now 1.
  4. Edit is ifRoom, so it takes slot 3. The bar is Search, Share, Edit. Free slots are now 0.
  5. Delete is ifRoom, but no free slot remains, so it goes to overflow. Overflow is Delete.
  6. Settings is never, so it goes to overflow. Overflow is Delete, Settings.

Answer. The bar shows 3 items, Search, Share and Edit; overflow holds 2 items, Delete and Settings.

Exam traps

  • showAsAction is a custom attribute on a Toolbar, so write app:showAsAction and declare the app namespace. android:showAsAction is ignored and every item drops into overflow.
  • Returning false from onOptionsItemSelected lets the event fall through. The click appears to do nothing; return true after handling your id.
  • Up is not Back. android.R.id.home should move up the app's screen hierarchy; the system Back button pops the back stack.
  • In onCreateContextMenu call super first, then inflate the menu with getMenuInflater().inflate(R.menu.x, menu). An empty long-press menu is caused by not inflating the menu; the default super call does nothing, so a missing super alone does not empty it.
  • A PopupMenu uses setOnMenuItemClickListener, not onOptionsItemSelected. Mixing them leaves the popup click unhandled.

3.4 Basic views: buttons, text, picker and list views

A screen is built from small views, and each basic view has its own input model. A TextView only shows text. An EditText lets the user type. A CheckBox lets the user pick many things; a RadioGroup lets them pick exactly one. Picker views — Spinner, DatePicker, TimePicker, NumberPicker — make the user choose from a fixed set. List views show many rows, and they never store the data themselves: an adapter hands out row views one at a time, only for the rows on screen. This chapter covers those views and the adapter idea behind every list.

You need: 3.1 Screen components and layouts for views and ViewGroups, and Unit 2 for activities and the onCreate method, because listeners are wired up there.

Text, edit fields and buttons

A TextView displays text and the user cannot edit it. android:textSize="16sp" sets the size in scale-independent pixels: sp follows the user's system font setting, dp does not, so text should use sp. android:textColor="#FF1A237E" is an ARGB colour. android:maxLines="2" with android:ellipsize="end" stops a long string at two lines and ends it with "...".

An EditText is a TextView the user can type into. android:hint shows grey stand-in text while the field is empty; the hint is not a value, and getText().toString() returns an empty string, not the hint. android:inputType chooses which keyboard appears. It does not validate anything: you still read the text and check it yourself.

A Button is a TextView that is clickable by default. Set android:text and attach setOnClickListener. An ImageButton shows a drawable from android:src instead of text, so give it android:contentDescription, otherwise a screen reader announces nothing useful.

Choice views: one or many

A CheckBox has two states and is independent: several check boxes on one screen can be ticked at the same time. Read it with isChecked(), which returns true or false.

A RadioButton also has two states, but it must sit inside a RadioGroup. The group is the part that enforces the rule: ticking one button clears the others in that group. Two RadioGroups on one screen are separate; one button in each can be on. Read the choice with radioGroup.getCheckedRadioButtonId(), which returns the resource id of the ticked button, or -1 when nothing is ticked.

Switch and ToggleButton are on/off controls with the same isChecked() reading. A ToggleButton shows android:textOn and android:textOff; a Switch shows a sliding thumb.

AutoCompleteTextView is an EditText with a drop-down of suggestions from an adapter. setThreshold(1) opens the list after one typed character. The user may still type anything; the list only helps.

Picker views

A Spinner is a one-line drop-down. Fill it statically with android:entries="@array/plans" from a string array, or in code with spinner.setAdapter(new ArrayAdapter<>(this, android.R.layout.simple_spinner_item, plans)). Listen with setOnItemSelectedListener; the callback is onItemSelected(AdapterView<?> parent, View view, int position, long id).

  • Android calls onItemSelected once while laying the spinner out, with position 0, before the user touches it.
  • getSelectedItemPosition() returns the index, getSelectedItem() returns the object at that index.
  • setSelection(3) changes the choice but does not call the listener.

A DatePicker is set with init(year, month, day, listener). The month is 0-based: month 2 means March. getMonth() returns 0 to 11 and getDayOfMonth() returns 1 to 31. A TimePicker gives getHour() (0 to 23 in 24-hour mode, set by setIs24HourView(true)) and getMinute() (0 to 59). A NumberPicker is a wheel of numbers: set setMinValue, setMaxValue, setValue, and read getValue().

List views and the adapter

A ListView shows a scrolling column of rows and stores no data of its own. The data lives in your list; an adapter is the bridge that turns list entries into row views on demand. The same pattern runs every list-style view in Android.

  1. You keep the data in an ordinary list, for example String[] items.
  2. You wrap it: new ArrayAdapter<>(this, android.R.layout.simple_list_item_1, items).
  3. The built-in row layout simple_list_item_1 is one TextView with id android.R.id.text1.
  4. listView.setAdapter(adapter) asks the adapter how many rows exist and calls its getView for each row that becomes visible.

A tap arrives at setOnItemClickListener as onItemClick(AdapterView<?> parent, View view, int position, long id). Here parent is the ListView, view is the row that was tapped, position is the row's index inside the adapter, and id is the row id the adapter reports (for an ArrayAdapter it equals position). getItemAtPosition(position) asks the adapter for the object at that index.

Only the rows on screen exist as views. When a row scrolls off, Android keeps its view and passes it back as convertView to getView(int position, View convertView, ViewGroup parent). Reuse it when it is not null and inflate only when it is null. A small ViewHolder object can cache the child lookups. After changing the backing list, call notifyDataSetChanged(), or the screen keeps the old rows.

Worked example

Question. A ListView is bound by an ArrayAdapter to five items shown with simple_list_item_1: Fig, Plum, Pear, Kiwi, Lime. The user taps the third row. Give the arguments of onItemClick and say what getItemAtPosition(2) returns. Then the same five entries fill a Spinner whose default selection is index 0; after setSelection(3), what do getSelectedItemPosition() and getSelectedItem() return?

Java program.

public class AdapterDemo {
    static String[] items = {"Fig", "Plum", "Pear", "Kiwi", "Lime"};

    static String getItemAtPosition(int position) {
        return items[position];
    }

    public static void main(String[] args) {
        int position = 2;
        System.out.println("position = " + position);
        System.out.println("getItemAtPosition(2) = " + getItemAtPosition(position));

        int selected = 0;
        selected = 3;
        System.out.println("getSelectedItemPosition() = " + selected);
        System.out.println("getSelectedItem() = " + items[selected]);
    }
}
  1. Adapter indices start at 0: Fig = 0, Plum = 1, Pear = 2, Kiwi = 3, Lime = 4.
  2. The third row is index 2, so the callback is onItemClick(parent, view, position, id) with position = 2.
  3. parent is the ListView object, view is the tapped row View, and id is the row id reported by the adapter, which for an ArrayAdapter equals 2.
  4. getItemAtPosition(2) asks the adapter for the object at index 2, which is the string "Pear".
  5. The Spinner starts at index 0, giving "Fig". setSelection(3) moves the choice to index 3, which is "Kiwi".
  6. So getSelectedItemPosition() returns 3 and getSelectedItem() returns "Kiwi".

Exam traps

  • position is the index inside the adapter, so it shifts the moment a header or footer view is added; id is the row id the adapter reports. Treating id as the index taps the wrong row.
  • Changing the backing list does not redraw the ListView. Without notifyDataSetChanged() the screen keeps the old rows, a favourite one-mark question.
  • DatePicker months are 0-based: getMonth() returns 0 for January, so the displayed month is getMonth() + 1.
  • A Spinner fires onItemSelected once during layout with position 0, and setSelection() does not fire it. Code that opens a network call inside the listener runs on screen load even if the user never touches the spinner.
  • android:inputType only changes the keyboard; it is not validation. A numberPassword field still returns whatever characters the user pastes.

3.5 Image views and additional views

Text and buttons cover only part of a screen. Android adds a second family of views for pictures, progress and scrolling. ImageView and ImageButton draw bitmaps; WebView draws a web page; ProgressBar, SeekBar and RatingBar show and collect a value along a range; ScrollView, HorizontalScrollView and GridView move content that is bigger than the screen. Each of these has one rule that decides how its content is measured and scaled, and marks are lost when that rule is confused. Only a few universities teach this group in detail.

You need the basic views and the adapter idea from 3.4, and the view tree from 3.1.

ImageView and its scaleType

An ImageView shows a drawable, usually a PNG or WebP file in res/drawable. Two XML attributes look alike but do different jobs. android:src is the image content, and it obeys scaleType. android:background paints the view's own background behind everything, and it is always stretched to the view bounds, ignoring scaleType.

scaleType decides how the source bitmap is fitted into the view box (view width W, view height H, bitmap width w, bitmap height h):

  • fitCenter: scale = min(W/w, H/h); the whole image fits, blank space is left over.
  • centerCrop: scale = max(W/w, H/h); the box is filled, the extra image is cropped.
  • fitXY: image is stretched to W × H, aspect ratio is not kept.
  • center: no scaling, image centred, cropped if larger than the box.
  • centerInside: scale down to fit, never enlarge, then centre.
  • matrix: you supply the scale and translation yourself.

android:adjustViewBounds="true" lets the view resize itself to the image's aspect ratio when one side is wrap_content. ImageView is used for product thumbnails, profile photos and map pins drawn over a layout.

ImageButton, GridView and WebView

ImageButton is an ImageView you can tap. It has android:src for the picture and no text. Use it for a search glass or a camera icon.

GridView lays children in a scrolling two-dimensional grid. It holds no data itself; like ListView it asks an adapter for each cell. Extend BaseAdapter and override getCount, getItem, getItemId and getView. getView receives a recycled convertView; set every field inside it on every call. Set android:numColumns to fix the number of columns.

  1. Write the cell layout XML with one ImageView and one TextView.
  2. Subclass BaseAdapter; return data.size() from getCount.
  3. In getView, inflate the cell when convertView is null, otherwise reuse it.
  4. Fill the ImageView and TextView from the data at the given position, then return the view.
  5. Call gridView.setAdapter(myAdapter).

WebView renders HTML inside your app. Call webView.loadUrl("https://example.com"). For network pages add <uses-permission android:name="android.permission.INTERNET"/> to the manifest, otherwise the page fails with a blank screen.

Feedback views and scrolling views

ProgressBar shows work in progress. In determinate mode, with style="?android:attr/progressBarStyleHorizontal", call setProgress(n) where n runs from 0 to the maximum. Without that style it is indeterminate: a spinning circle with no value, correct when you cannot estimate the remaining time.

SeekBar is a slider. Attach a SeekBar.OnSeekBarChangeListener, which has three callbacks: onProgressChanged(seekBar, progress, fromUser), onStartTrackingTouch and onStopTrackingTouch. RatingBar shows stars: setNumStars(5), setRating(3.5f), and setStepSize(0.5f) for half stars.

ScrollView scrolls vertically and HorizontalScrollView scrolls sideways. Each holds exactly one child, so put a LinearLayout inside it and add the rest to that layout. A GridView scrolls by itself and must never sit inside a ScrollView. VideoView plays a video file in one line of code; playback itself belongs to another unit.

Worked example

Question. An ImageView is 400 px wide and 300 px high. The source bitmap is 200 px wide and 600 px high. Find the drawn size of the bitmap and the amount cropped or left blank for scaleType fitCenter, and then for centerCrop.

  1. fitCenter uses scale = min(W/w, H/h) = min(400/200, 300/600) = min(2, 0.5) = 0.5.
  2. Drawn width = w × 0.5 = 200 × 0.5 = 100 px; drawn height = h × 0.5 = 600 × 0.5 = 300 px.
  3. The image fits the height exactly, so no height is lost. The blank width is 400 − 100 = 300 px, split as 300/2 = 150 px on the left and 150 px on the right.
  4. centerCrop uses scale = max(W/w, H/h) = max(2, 0.5) = 2.
  5. Drawn width = 200 × 2 = 400 px; drawn height = 600 × 2 = 1200 px.
  6. The width fills the box exactly. The height is cropped from 1200 px to 300 px, so 1200 − 300 = 900 px is lost, 900/2 = 450 px from the top and 450 px from the bottom.

Answer. fitCenter draws the bitmap at 100 × 300 px with 150 px blank on each side; centerCrop draws it at 400 × 1200 px and crops 450 px from the top and 450 px from the bottom.

Worked example 2

Question. A 600 × 400 px ImageView holds a 300 × 300 px bitmap. Find the drawn size for fitCenter and for centerCrop.

  1. W/w = 600/300 = 2; H/h = 400/300 = 1.333.
  2. fitCenter: scale = min(2, 1.333) = 1.333, drawn 400 × 400 px, blank height 400 − 400 = 0, blank width 600 − 400 = 200 px, 100 px each side.
  3. centerCrop: scale = max(2, 1.333) = 2, drawn 600 × 600 px, crop height 600 − 400 = 200 px, 100 px from the top and 100 px from the bottom.

Answer. fitCenter draws 400 × 400 px with 100 px blank on each side; centerCrop draws 600 × 600 px and crops 100 px top and bottom.

Exam traps

  • fitXY stretches the bitmap to the view box and drops the aspect ratio, so faces look fat; it is the answer examiners expect to be marked wrong.
  • scaleType acts on src only. A background drawable is stretched to the view bounds and ignores scaleType completely.
  • fitCenter and centerInside differ when the bitmap is smaller than the view: centerInside never enlarges, fitCenter does.
  • A ScrollView with two direct children crashes at inflation; wrap them in one layout.
  • GridView needs an adapter and recycles row views, so getView must set every field on every call or old images reappear.

It scales width and height independently to the view box, so the aspect ratio of the bitmap changes.

android.permission.INTERNET, declared in the manifest.

Beyond the syllabus

Not for the exam. In production Android, plain ImageView is usually replaced by image-loading libraries that download, cache and downscale bitmaps off the main thread, because a full-size photo in an ImageView causes jank and out-of-memory crashes. WebView grows into a full app shell with JavaScript bridges and custom clients. Progress and rating views feed design systems that fix colours and sizes once. 3.6 Creating UI programmatically and handling UI events

Every XML layout is a tree of views, and most view attributes map to a setter: android:text → setText, android:visibility → setVisibility. Attributes that start with layout_ do not; they belong to the parent's LayoutParams, so you set them with new LinearLayout.LayoutParams(...) or by calling setLayoutParams. Java can build the same tree with new TextView(this), setText and addView, which helps when rows are dynamic, such as one row per UPI transaction. A touch becomes a callback through one fixed path: dispatchTouchEvent → onTouchEvent → performClick → your onClick. Only a few universities teach programmatic UI; it is worth knowing because it makes sizes, weights and listeners explicit.

You need 3.1 for LayoutParams and weights, and 3.4 for listeners on buttons and lists.

Building a screen in Java

Create the root, create each child, set its properties, attach LayoutParams, add the child, then pass the root to setContentView. Sizes are pixels unless you convert. The display density is getResources().getDisplayMetrics().density; at density 3, 1 dp is 3 px.

  1. LinearLayout root = new LinearLayout(this); root.setOrientation(LinearLayout.HORIZONTAL);
  2. TextView t = new TextView(this); t.setText("Balance"); t.setTextSize(16); t.setPadding(16, 8, 16, 8);
  3. t.setId(100 + i); t.setLayoutParams(new LinearLayout.LayoutParams(0, LinearLayout.LayoutParams.WRAP_CONTENT, 1f));
  4. root.addView(t); then setContentView(root);

px = dp × density

px is the pixel value passed to setPadding; dp is the design size; density is getResources().getDisplayMetrics().density, for example 3 on a high-density phone.

setTextSize(16) uses sp by default. setPadding takes px. A view made in code has no LayoutParams until you set them. With addView(view) and no params, the parent uses its default LayoutParams: wrap_content × wrap_content when the LinearLayout is horizontal, match_parent × wrap_content when it is vertical. Weight can only be set through explicit LinearLayout.LayoutParams, so it silently does nothing here.

Listening for UI events

A click can be wired in three ways. In XML, android:onClick="onButtonClick" needs a public void onButtonClick(View v) method in the activity. In Java, use an anonymous class: b.setOnClickListener(new View.OnClickListener(){ public void onClick(View v){ ... } });. Or let the activity implement View.OnClickListener and call b.setOnClickListener(this).

  • A tap reaches dispatchTouchEvent first, which sends the event down the view tree.
  • The view's onTouchEvent returns true to consume the touch, then performClick runs, then your onClick.
  • If onTouchEvent returns false, the view does not consume the touch, so the parent may handle it and your click may not fire.
  • Text fields notify through a TextWatcher; afterTextChanged(Editable s) runs after each change.
  • Log.d("TAG", "clicked") confirms that a listener fired; v.getId() tells you which view.

Worked example

Question. A horizontal LinearLayout on a 360 dp screen will hold three buttons. Each button has layout width 0 and weight 1. Button i gets id 100 + i, and all three share one OnClickListener. The user taps the second button. What is each button's width, and what does the listener receive? Use density 3.

Java program.

public class ButtonWeights {
  public static void main(String[] args) {
    int screenDp = 360;
    int n = 3;
    int density = 3;
    int eachDp = screenDp / n;
    int eachPx = eachDp * density;
    int tappedId = 100 + 1;
    int index = tappedId - 100;
    System.out.println(eachDp);
    System.out.println(eachPx);
    System.out.println(tappedId);
    System.out.println(index);
  }
}
  1. This snippet only computes the widths and the tapped id; the LinearLayout, Button, LayoutParams and listener calls are shown in Section 1.
  2. Root width = 360 dp. There are 3 equal weights, so each weight unit gets 360 ÷ 3 = 120 dp.
  3. Each button width = 120 dp because width 0 plus weight 1 gives all space by weight.
  4. Convert to pixels: px = dp × density = 120 × 3 = 360 px per button.
  5. Tapped button is the second, so i = 1 and its id = 100 + 1 = 101.
  6. The listener receives v, the tapped View. v.getId() returns 101.
  7. The index is v.getId() − 100 = 101 − 100 = 1.

Answer. Each button is 120 dp (360 px) wide, and the listener receives the second button's View, whose id is 101 and index is 1.

Exam traps

  • A view created in code has no LayoutParams until you set them; addView(view) with no params uses the parent's default LayoutParams (wrap_content × wrap_content in a horizontal LinearLayout, match_parent × wrap_content in a vertical one), and weights silently do nothing.
  • The XML onClick method must be public, return void and take exactly one View argument, or the app crashes on the first tap.
  • setPadding takes pixels, not dp; convert with density first or spacing looks too small.
  • onTouchEvent returning false means the view does not consume the touch, so performClick and your onClick may not run.
  • setTextSize(16) means 16 sp, not 16 dp; do not treat text size and padding units as the same.

Takeaways

  1. An Android screen is a tree of View objects, and every View that has children is a ViewGroup whose job is measuring and placing them.
  2. XML layouts and Java-built layouts produce the same tree; XML is only a declaration that LayoutInflater turns into objects.
  3. Rotation destroys and recreates the activity, so any value the user typed must live in a ViewModel or be saved in onSaveInstanceState.
  4. The action bar and its overflow list come from a menu XML file, and each click is routed back to your code by the item id.
  5. A list view holds no data; the adapter builds row views on demand and recycles old rows to keep memory flat.
  6. Each specialised view (ImageView, ProgressBar, ScrollView) has one measurement rule that decides whether it looks right.
  7. A touch becomes a callback in one fixed order: dispatchTouchEvent, onTouchEvent, performClick, then your onClick.
  8. Understanding this order explains why a clickable child can steal a touch from its parent.
  9. Using dp for sizes, sp for text and a correct scaleType or layout_weight stops the same layout from breaking on a different phone.

Glossary

Activity
A single screen with a user interface, managed by the Android framework through lifecycle callbacks.
Adapter
An object that supplies row Views to a list-style view, one per data item, on demand.
Bundle
A key-value container that carries small saved state between activity instances.
Configuration
The current set of device properties such as orientation, screen size, locale and density that Android matches to resource folders.
Density-independent pixel (dp)
A size unit equal to 1/160 inch, so layouts keep the same physical size on every screen density.
Drawable
Any graphic resource (bitmap, shape, selector) that a view can draw as its background or content.
Event dispatch
The path by which a MotionEvent travels from the activity down the view tree to the view that consumes it.
Indeterminate progress
A progress indicator that spins without a known total, used when the duration cannot be computed.
Inflate
To read a layout or menu XML file and build the matching objects in memory.
Layout weight
A LinearLayout attribute that shares leftover space among children in proportion to the weight values.
LayoutInflater
The framework service, obtained by getLayoutInflater(), that converts layout XML into View objects.
MeasureSpec
A packed integer carrying a parent's size mode and size value that is passed to a child during measurement.
Menu resource
An XML file in res/menu describing menu items, their ids, titles and action-bar behaviour.
OnClickListener
An interface with one method, onClick(View), called when a clickable view completes a click.
onSaveInstanceState
The activity callback used to write UI state into a Bundle before the activity may be destroyed.
Overflow menu
The list of menu items that did not fit as action buttons, opened from the three-dot icon.
performClick
The View method that fires the registered OnClickListener and plays the click sound.
Picker
A wheel-style input widget such as DatePicker, TimePicker or NumberPicker.
Resource qualifier
A folder suffix such as -land or -sw600dp that tells Android which version of a resource to load for the current configuration.
Scale-independent pixel (sp)
A text size unit equal to one dp scaled by the user's chosen font size.
scaleType
An ImageView property that decides whether the bitmap is stretched, cropped or letterboxed inside the view.
View
The base class for any on-screen element that draws and can receive touch events.
ViewGroup
A View that contains and positions other Views; all layouts are ViewGroups.
ViewHolder
A small holder object that caches child view references inside a recycled row so findViewById is not repeated.
