4.1 Saving and loading user preferences

A game remembers your best score after you close it. SharedPreferences is the Android class behind that small memory: a private key-value store for a few settings. Each setting is a key, a String name, and a value of a simple type. Android saves the pairs as one XML file inside your app's private folder. You use it for flags, scores, the last selected tab and small choices, not for lists or photos.

You need: Unit 2 for activities and the activity life cycle, because the right moment to save is onPause or onStop.

A tiny private key-value store

A key-value store keeps pairs: a key names a value. In SharedPreferences the key is a String, and the value is a String, int, boolean, long or float. Android writes the pairs into one XML file under your app's private data folder. With normal permissions, other apps cannot read that file.

Use preferences for sound on/off, best score, last selected tab, or a user's language choice. Do not use them for lists, images or logs; those belong to file storage or SQLite.

CallWhat it gives
getSharedPreferences("settings", MODE_PRIVATE)A named file, settings.xml, shared by the whole app
getPreferences(MODE_PRIVATE)A file tied to one Activity, useful for one screen only
PreferenceManager.getDefaultSharedPreferences(context)The default file for the whole app

MODE_PRIVATE means only your app can read the file. The older modes MODE_WORLD_READABLE and MODE_WORLD_WRITEABLE are deprecated and insecure. Preferences are not encrypted, so never store a password or a bank token in plain preferences.

Writing and reading values

To write, get an Editor from the preferences object, call typed put methods, then save. To read, call a typed get method with the same key and a default value.

  1. Get the file: SharedPreferences prefs = getSharedPreferences("settings", MODE_PRIVATE);
  2. Get an editor: SharedPreferences.Editor editor = prefs.edit();
  3. Put values: editor.putInt("best_score", 4200); editor.putBoolean("sound_on", false);
  4. Save with editor.apply(); or editor.commit();
  5. Read back: int score = prefs.getInt("best_score", 0); and boolean sound = prefs.getBoolean("sound_on", true);

apply() saves in the background and returns nothing. commit() saves immediately and returns true or false. Use apply() on the UI thread. Remove one key with remove("key"); remove all keys with clear().

The default is returned only when the key is missing. If you wrote an int and read it with getString, you get a ClassCastException, not the default. A listener, OnSharedPreferenceChangeListener, runs when a key changes; register it where you need live updates and unregister it when the screen goes away.

When to save and what to expect

Save in onPause() or onStop(), not only in onCreate(). Android may kill your process after it leaves the screen. Read saved values early, in onCreate() or onStart(), so the screen opens with the old choice.

Preferences suit a few dozen small values. For a thousand scores, use a database; for an image, use a file. Showing the loaded value on screen is data binding to views.

On disk the file lives at /data/data/<package>/shared_prefs/settings.xml. It is a simple XML file; the next section shows its contents for the game example.

Worked example

Question. A game settings screen saves a best score of 4200 under the key best_score and a mute flag of false under the key sound_on, into the file settings.xml. Write the code to save both values and the code to read them back after the app restarts. State what the XML file contains.

  1. Open the named file: SharedPreferences prefs = getSharedPreferences("settings", MODE_PRIVATE);. The file path is /data/data/<package>/shared_prefs/settings.xml.
  2. Get an editor: SharedPreferences.Editor editor = prefs.edit();
  3. Put the int: editor.putInt("best_score", 4200);
  4. Put the boolean: editor.putBoolean("sound_on", false);
  5. Save without blocking the UI: editor.apply();. If the question demands an immediate true or false result, use commit().
  6. After restart, read with the same keys: int score = prefs.getInt("best_score", 0); gives 4200, and boolean sound = prefs.getBoolean("sound_on", true); gives false.
  7. The XML file holds <int name="best_score" value="4200" /> and <boolean name="sound_on" value="false" />.

Answer. The code saves 4200 under best_score and false under sound_on, reads them back as 4200 and false, and settings.xml stores the int 4200 and the boolean false.

Exam traps

  • apply() saves in the background and returns nothing; commit() saves immediately and returns true or false. Writing commit() when the question says 'without blocking the UI' loses marks.
  • Reading an int key with getString throws a ClassCastException. The type is fixed at write time, so the default is not used for a type mismatch.
  • getPreferences(MODE_PRIVATE) is tied to one Activity. For a setting shared by the whole app, use getSharedPreferences(name, MODE_PRIVATE) or PreferenceManager.getDefaultSharedPreferences.
  • MODE_WORLD_READABLE and MODE_WORLD_WRITEABLE are deprecated and unsafe. Preferences are also not encrypted, so storing a password there is a security mistake.
  • Saving only in onCreate() misses changes made during the screen's life. Save in onPause() or onStop(), before Android can kill the process.

4.2 File storage: internal storage and SD card

A file is a named block of bytes on storage. Android gives your app two file homes. Internal storage is private, small, and always present. External storage is shared, larger, and may be removed. openFileOutput and openFileInput read and write files inside the app's files/ folder; getFilesDir() and getCacheDir() return the File objects for files/ and cache/. Apps use files for logs, downloaded images, exports, and caches. Only a few universities teach the mode flags and scoped-storage rules at this depth.

You need: Context and the package name from Unit 2, and the private key-value idea from Chapter 4.1.

Internal storage: private and always present

Internal storage lives under /data/data/<pkg>/ on the device. This area is private to the app. getFilesDir() returns files/. getCacheDir() returns cache/, which Android may clear when space is low. getDir(name, mode) creates or opens a named subfolder.

For simple files call openFileOutput(name, mode); it returns a FileOutputStream. openFileInput(name) returns a FileInputStream. MODE_PRIVATE keeps the file readable only by your app and is the safe default. MODE_APPEND adds to the end instead of replacing. MODE_WORLD_READABLE and MODE_WORLD_WRITABLE are deprecated; do not use them in new code.

Internal files need no permission and are always available, even when no SD card is present. They are deleted on uninstall, and the cache can be cleared earlier. A file the user must see in a file manager is a poor fit. Do long writes off the main thread; a slow write blocks the UI.

Writing and reading a text file

Open the file, wrap the byte stream in a character stream, write lines, close. try-with-resources closes the stream even if an exception occurs.

  1. Pick the file name and mode: MODE_PRIVATE or MODE_APPEND.
  2. Call openFileOutput(name, mode) to get a byte stream.
  3. Wrap it in OutputStreamWriter and BufferedWriter to write text.
  4. Write each line, then close the stream. Use try-with-resources.
  5. To read, wrap openFileInput(name) in an InputStreamReader, then in a BufferedReader, and call readLine() until it returns null.

OutputStreamWriter uses the device default charset, which is UTF-8 on Android. Pass StandardCharsets.UTF_8 explicitly so the bytes are fixed and other tools can read the file. A small log fits in memory. A 5 MB log should stream in chunks, not build one giant String.

External storage: check, permission, scope

External storage may be a removable SD card or emulated shared storage. Before any write, compare Environment.getExternalStorageState() with Environment.MEDIA_MOUNTED. If it is not mounted, skip the write; the file will not appear.

getExternalFilesDir(type) returns your app's external folder, usually Android/data/<pkg>/files/. Pass null for the root or a type such as Environment.DIRECTORY_PICTURES. It returns null if external storage is not currently available; test for null before creating files in it. This folder is removed on uninstall and is the right place for a 5 MB log.

Shared public folders are different. Older apps asked for READ_EXTERNAL_STORAGE and WRITE_EXTERNAL_STORAGE. From Android 10 (API 29), scoped storage limits direct access to public folders. For shared media use MediaStore; for user-picked documents use the Storage Access Framework. Share files through a content provider, not a guessed path (Chapter 4.5).

Worked example

Question. An app writes a 3-line log at 32 bytes per line and a 40 KB thumbnail. (a) Which folder for each? (b) Total bytes? (c) What happens on uninstall? (d) Where can a 5 MB log go, after what check?

  1. Log: 3 × 32 = 96 bytes; path getFilesDir()/log.txt because it is private and small.
  2. Thumbnail: 40 × 1024 = 40,960 bytes; path getCacheDir() because it can be regenerated.
  3. Total: 96 + 40,960 = 41,056 bytes. Both paths are under /data/data/<pkg>/; uninstall deletes both, and cache may be cleared earlier.
  4. For 5 MB: getExternalFilesDir(null); first check Environment.getExternalStorageState() equals MEDIA_MOUNTED.

Answer. The log goes to getFilesDir(), the thumbnail to getCacheDir(), total 41,056 bytes; both are deleted on uninstall; a 5 MB log can use getExternalFilesDir(null) after the MEDIA_MOUNTED check.

Exam traps

  • Writing external storage without checking state. When storage is not mounted, getExternalFilesDir() returns null, so building a File or stream from it throws NullPointerException, and a path on unmounted storage fails with FileNotFoundException. Check Environment.getExternalStorageState() equals MEDIA_MOUNTED and check the returned folder for null before writing.
  • Saying internal files survive uninstall. Both filesDir and cacheDir are deleted; cache may be cleared sooner.
  • Using MODE_WORLD_READABLE in new code. It is deprecated; share with a content provider.
  • Doing a 5 MB write on the main thread. The UI freezes; use a background thread and close streams with try-with-resources.

4.3 SQLite databases in Android

An app often needs a table, not a single value: a list of students, monthly expenses, cricket scores. SQLite is a small relational database engine built into Android. A whole database is one private file inside your app, and you talk to it in ordinary SQL. SQLiteOpenHelper creates that file on first use, upgrades it when you change the tables, and hands you an SQLiteDatabase to run insert, update, delete and query against. Nothing outside your app sees the data unless you publish it through a content provider.

You need: activities and the life cycle from Unit 2, plus the idea of private, app-only storage from Chapter 4.1 and Chapter 4.2.

The helper that owns the database file

A SQLite database is one file, usually under /data/data/<your.package>/databases/. No other app can read it. The file survives restarts and is deleted when the user uninstalls.

Tables must be created once, not on every launch. SQLiteOpenHelper does this with a version number stored inside the file. You subclass it and call super(context, name, factory, version). name is the file name, say "college.db". factory is null in practice. version is your schema version, starting at 1 and going up whenever the table definitions change.

  1. getWritableDatabase() opens college.db read-write, creating the file if it is missing.
  2. If the file is new, onCreate(db) runs once. Create your tables there.
  3. If the file exists and its stored version is lower, onUpgrade(db, oldVersion, newVersion) runs.
  4. If the versions match, neither method runs; you just get the open database.
  5. getReadableDatabase() returns the same read-write object unless the disk is full or locked, when it falls back to read-only.

The version number is the whole trick. Bump it and onUpgrade fires on every phone holding an older file. Add a column without bumping it and old installs keep the old table, then crash on the missing column. Inside onUpgrade you run ALTER TABLE, or copy the rows into a new table and drop the old one.

Writing rows: execSQL, ContentValues and ?

execSQL() runs statements that return nothing: CREATE TABLE, ALTER TABLE, DROP TABLE. Your onCreate body looks like this:

SQL program.

CREATE TABLE students(
  _id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  marks INTEGER
);

The first column is named _id on purpose. List adapters look for a column with exactly that name; without it the list stays empty even when the cursor holds rows. AUTOINCREMENT makes SQLite fill 1, 2, 3 for you.

For row data, use the helper methods instead of pasting values into SQL strings.

  • insert("students", null, values) returns the new _id, or -1 on failure. ContentValues is a column-to-value map: values.put("name", "Asha"); values.put("marks", 88);
  • update("students", values, "marks > ?", new String[]{"60"}) returns how many rows changed.
  • delete("students", "_id = ?", new String[]{"2"}) returns how many rows went away.

Each ? is filled from the String array, left to right, and quoted safely. Never join the value into the WHERE clause with +. A name like O'Brien breaks the quotes, and text typed by a user becomes a free SQL injection.

Reading with a Cursor

query() takes seven arguments: table, columns, selection, selectionArgs, groupBy, having, orderBy. Pass null wherever you have nothing to say. It returns a Cursor, a pointer that starts just before the first row.

Cursor c = db.query("students", null, "marks > ?", new String[]{"60"}, null, null, "marks DESC"); Then getCount() gives the row count, moveToFirst() jumps to the first row and returns false if the set is empty, moveToNext() advances one row. getColumnIndex("name") gives the column position once; getString(i) and getInt(i) read the value at the current row.

Call close() on the cursor in a finally block. An open cursor holds a file handle and a window of rows in memory; leaked cursors eventually exhaust the database.

rawQuery(sql, selectionArgs) runs any SQL, including joins that query() cannot express, and its arguments still go through ?: db.rawQuery("SELECT s.name, m.marks FROM students s JOIN marks m ON s._id = m.student_id WHERE m.marks > ?", new String[]{"60"}).

Transactions: all or nothing

By default each insert is its own transaction, flushed to disk on its own. A thousand inserts take seconds. Wrap them:

  1. Call db.beginTransaction().
  2. Do all the inserts or updates.
  3. Call db.setTransactionSuccessful().
  4. Call db.endTransaction() in a finally block.

setTransactionSuccessful() is the commit flag. If it is not called before endTransaction(), everything since beginTransaction() rolls back. That gives you all-or-nothing when two tables must agree, for example a student row and its marks row.

Worked example

Question. Create a table students(_id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT, marks INTEGER). Insert Asha with 88, Ravi with 72 and Meera with 95. Then run SELECT _id, name, marks FROM students WHERE marks > 60 ORDER BY marks DESC. Give the SQL, the equivalent Android query() call, and the exact rows returned in order.

Python program.

import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE students(_id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT, marks INTEGER)")
con.executemany("INSERT INTO students(name, marks) VALUES(?, ?)", [("Asha", 88), ("Ravi", 72), ("Meera", 95)])
cur = con.execute("SELECT _id, name, marks FROM students WHERE marks > 60 ORDER BY marks DESC")
for _id, name, marks in cur.fetchall():
    print(_id, name, marks)
print("count =", con.execute("SELECT COUNT(*) FROM students WHERE marks > 60").fetchone()[0])
con.close()
  1. CREATE TABLE students(_id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT, marks INTEGER); the three inserts get _id 1 (Asha, 88), 2 (Ravi, 72), 3 (Meera, 95).
  2. The filter marks > 60 keeps all three rows: 88, 72 and 95 are above 60.
  3. ORDER BY marks DESC sorts 95, 88, 72, so the order is Meera, Asha, Ravi.
  4. Raw SQL: rawQuery("SELECT _id, name, marks FROM students WHERE marks > 60 ORDER BY marks DESC", null).
  5. The same through the helper: query("students", null, "marks > ?", new String[]{"60"}, null, null, "marks DESC").
  6. The cursor returns 3 rows: (3, Meera, 95), (1, Asha, 88), (2, Ravi, 72), so getCount() is 3.

Exam traps

  • Forgetting to bump the version. onUpgrade runs only when the number passed to the helper is higher than the stored one, so a new column never reaches old installs and they crash on 'no such column'.
  • Building WHERE clauses with + instead of ? and selectionArgs. Quoting breaks on names like O'Brien, and text from a user becomes SQL injection.
  • Not calling close() on the Cursor. Each open cursor holds a file handle and a row window; enough of them and the database fails.
  • Calling endTransaction() without setTransactionSuccessful() and then wondering why nothing was saved. Without the flag the whole block rolls back.
  • Assuming getReadableDatabase() always returns a separate read-only object. Usually it hands back the same read-write database.

4.4 Content providers: using and creating your own

A content provider publishes an app's data behind a content:// URI. Other apps, and your own, read that data through ContentResolver, not by opening your database file. The provider owns the SQLite database and decides what each URI means. Android's contacts, media and call-log apps work this way. The same pattern lets two of your apps share a marks table safely. Reading a built-in provider takes a few lines. Creating one is advanced; only a few universities teach it. This chapter shows both, with URI anatomy, UriMatcher, a contract class and manifest permissions.

You need Chapter 4.3 for SQLite, and Unit 2 for the manifest and implicit intents.

Reading through ContentResolver

Every provider has an authority, a unique string such as com.example.marks. The URI content://com.example.marks/students/2 has three parts. content:// is the scheme. com.example.marks is the authority. /students/2 is the path; 2 is the _id of one row. The authority must be unique on the phone, so start it with your package name.

Call getContentResolver().query(uri, projection, selection, selectionArgs, sortOrder). It returns a Cursor, a pointer to result rows. projection lists columns; null means all. selection is a WHERE clause with ? stand-ins; selectionArgs fills them. sortOrder is ORDER BY; null means none. Read rows with while (cursor.moveToNext()). Close the cursor. A CursorAdapter can bind a Cursor to a ListView.

  • Built-in example: ContactsContract.Contacts.CONTENT_URI.
  • The provider runs the SQL; the caller only sees a Cursor.
  • Never open another app's database file directly.
  • An empty result still returns a Cursor, with zero rows.
  • For a single row, the final path segment is the _id.

Creating a provider

Write a contract class. It holds constants: AUTHORITY = "com.example.marks", TABLE = "students", COL_ID = "_id", COL_NAME = "name", COL_MARKS = "marks", and CONTENT_URI = Uri.parse("content://" + AUTHORITY + "/" + TABLE).

  1. Extend ContentProvider. Implement onCreate, query, getType, insert, delete and update.
  2. In onCreate, create the SQLiteOpenHelper database. Return true. Do not open it in query().
  3. Build a UriMatcher. addURI(AUTHORITY, TABLE, 1) matches all rows. addURI(AUTHORITY, TABLE + "/#", 2) matches one row; # means a number. match(uri) returns 1, 2 or NO_MATCH.
  4. query(): switch on match(uri). Code 1 runs db.query(TABLE, projection, selection, selectionArgs, null, null, sortOrder). Code 2 adds "_id = ?" and the last path segment. Return the Cursor.
  5. insert(): db.insert(TABLE, null, values); return ContentUris.withAppendedId(CONTENT_URI, newId).
  6. delete() and update(): use the same switch. For one row add "_id = ?". Return the changed row count.
  7. getType(): vnd.android.cursor.dir/com.example.marks.students for many rows; vnd.android.cursor.item/com.example.marks.students for one row.

Manifest, permissions and MIME types

Declare the provider in AndroidManifest.xml inside the application element. Use android:name=".MarksProvider", android:authorities="com.example.marks", android:exported="true", android:readPermission="com.example.marks.READ" and android:writePermission="com.example.marks.WRITE".

android:name is the provider class; the leading dot means the app package. android:authorities is the unique authority; it must equal AUTHORITY. android:exported="true" lets other apps call it, subject to permissions. exported="false" hides it. The authority in code and manifest must match exactly. Define custom permissions with a permission element. Forget the provider element and the system never registers the provider. Use readPermission for query and writePermission for insert, update, delete.

  • MIME types: vnd.android.cursor.dir means many rows; vnd.android.cursor.item means one row.
  • A CursorAdapter reads the Cursor and binds rows to a ListView.
  • Your own app can call an exported=false provider through ContentResolver.
  • The manifest entry is read at install time; a missing entry means no provider.
  • Custom permissions appear in the manifest as permission elements.

Worked example

Question. Your provider has authority com.example.marks and serves the students table. Trace getContentResolver().query(Uri.parse("content://com.example.marks/students/2"), null, null, null, null). What does the caller receive?

  1. UriMatcher has addURI("com.example.marks", "students", 1) and addURI("com.example.marks", "students/#", 2).
  2. Path students/2 has two segments; # matches 2; match returns code 2.
  3. Code 2 runs db.query("students", null, "_id = ?", new String[]{"2"}, null, null, null).
  4. SQLite returns one row: _id = 2, name = Ravi, marks = 72.
  5. getType returns vnd.android.cursor.item/com.example.marks.students.

Answer. The caller receives a Cursor with 1 row: _id 2, Ravi, 72 marks; match code 2 and the item MIME type.

Exam traps

  • Authority in code and manifest differ; every URI returns NO_MATCH.
  • exported="false" hides the provider from other apps; a missing provider element means no registration.
  • Opening the database in query() instead of onCreate() repeats work and can leak resources.
  • Calling another app's database file directly; use ContentResolver instead.
  • Forgetting to close the Cursor, or returning a Cursor without _id for a CursorAdapter.

4.5 Sharing data between apps

An app shares data by sending a content:// URI in an intent with a temporary read grant. It does not copy files into a public folder or reveal a private path. The receiver asks Android for bytes through ContentResolver. This is how a report app sends a PDF to a viewer, a photo app sends an image to chat, and a receipt is attached to email. The grant is narrow: one URI, read only, for one activity. Only a few universities teach this advanced topic.

You need Chapter 4.4 for content URIs and resolvers, and Unit 2 for implicit intents.

Share with an intent, not a folder

An implicit intent names an action, not a target class. ACTION_SEND shares one item; ACTION_SEND_MULTIPLE shares many. Call setType("application/pdf") so Android lists apps that accept that MIME type. Text goes in Intent.EXTRA_TEXT. A file goes in Intent.EXTRA_STREAM as a content:// URI, never as a File. For many files, put an ArrayList<Uri> in the same extra. A wrong MIME type can hide the right receiver. Set the MIME type with setType() so Android can match receivers; putExtra() later does not change it. Do not call setData() after setType(), because setData() clears the type (and setType() clears the data).

Intent.createChooser(send, "Share report") opens the system share sheet; the string is its heading. The chooser does not copy the file. The selected app receives the same extras and URI. The receiver calls getContentResolver().openInputStream(uri). This design exists because each app has a private data folder; guessing another app's path is unsafe and often impossible. It also lets Android apply a temporary grant instead of a broad folder permission. The URI points to the provider, not to a raw directory.

Publish your file with FileProvider

Your app must turn a private File into a shareable URI. Use FileProvider, an AndroidX subclass of ContentProvider. Add a <provider> tag. Set android:name="androidx.core.content.FileProvider", android:authorities="com.example.reportapp.fileprovider", android:exported="false", and android:grantUriPermissions="true". Inside the <provider> tag add <meta-data android:name="android.support.FILE_PROVIDER_PATHS" android:resource="@xml/file_paths" />. This line connects the provider to file_paths.xml; without it getUriForFile throws IllegalArgumentException ("Failed to find configured root that contains ..."). The authority is a name you invent; it must match the string in code. exported="false" stops other apps from browsing the provider. grantUriPermissions="true" lets an intent give a temporary pass to one URI.

Add res/xml/file_paths.xml. It maps a public name to a private folder: <paths><files-path name="reports" path="reports/" /></paths>. Here reports/ is inside getFilesDir(). Then call Uri uri = FileProvider.getUriForFile(this, "com.example.reportapp.fileprovider", file);. If file is .../files/reports/report.pdf, the URI is content://com.example.reportapp.fileprovider/reports/report.pdf. The real path stays hidden. A file:// URI is refused from Android 7 (API 24): sharing it throws FileUriExposedException.

Give one temporary read grant

A content URI alone is not access. Add send.addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION). This flag travels with the intent and lets the chosen receiver read that URI. Without it, the receiver's openInputStream call fails with SecurityException.

The grant lasts while the receiving activity is alive. It covers only the URI in the intent. It does not let the receiver list the reports folder, read other files, or write. If you share many files, add the flag once to the ACTION_SEND_MULTIPLE intent; each URI in EXTRA_STREAM gets the grant. The receiver opens the stream, copies or displays it, and closes it. The sender keeps ownership of the file. A mail app may attach a copy; a viewer may only display it. Do not promise permanent access in an answer. A grant is not a password and not a file permission on disk.

Worked example

Question. A report app has report.pdf of 1.5 MB in .../files/reports/. Its authority is com.example.reportapp.fileprovider. Write the sharing code for any PDF viewer. State what the viewer may do.

  1. Confirm the <provider> tag contains <meta-data android:name="android.support.FILE_PROVIDER_PATHS" android:resource="@xml/file_paths" />, which connects the provider to file_paths.xml. Then confirm the folder is declared there: <files-path name="reports" path="reports/" />.
  2. Build the File object for report.pdf. Its size is 1.5 MB = 1572864 bytes.
  3. Call Uri uri = FileProvider.getUriForFile(this, "com.example.reportapp.fileprovider", file);. The result is content://com.example.reportapp.fileprovider/reports/report.pdf.
  4. Build the intent: Intent send = new Intent(Intent.ACTION_SEND); send.setType("application/pdf"); send.putExtra(Intent.EXTRA_STREAM, uri); send.addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION);.
  5. Start the chooser: startActivity(Intent.createChooser(send, "Share report"));.
  6. The viewer may call openInputStream(uri) and read exactly 1572864 bytes of that one file. It cannot list the reports folder or write. The grant ends with the receiving activity.

Answer. The viewer gets a temporary read grant to one content URI for report.pdf of 1.5 MB (1572864 bytes); it cannot browse the folder or write.

Exam traps

  • Passing a file:// URI (for example Uri.fromFile(file)) in EXTRA_STREAM, or as the intent data, throws FileUriExposedException on Android 7 (API 24) and later. Always pass the content:// URI from FileProvider instead.
  • Leaving out FLAG_GRANT_READ_URI_PERMISSION gives the receiver SecurityException.
  • A grant is temporary and per URI; it is not permanent folder access.
  • The manifest authority and the getUriForFile authority must match exactly.
  • Forgetting setType, or using the wrong MIME type, can leave the chooser empty.

4.6 Data binding to views

A layout with a TextView and a value in code usually needs one line of glue: textView.setText(user.name). Data binding removes that glue. You declare in the XML which object feeds which view, and Android writes the setText calls for you. Change the object and the view redraws. It is used in forms, score screens and dashboards where many views follow one object. Only a few universities teach this topic; most stop at findViewById.

You need: layouts, TextView and event handling from Unit 3, and the data you bind from Chapter 4.1 or Chapter 4.3.

Turning it on: layout, variable, generated class

View binding generates a class that holds only the view references, so you can skip findViewById. Data binding uses a generated class too, and also evaluates expressions written in the XML. Both are built from the layout file. Switch data binding on inside the android block of the module-level build.gradle, then sync:

android {
    buildFeatures {
        dataBinding true
    }
}

Rename the root of activity_main.xml to <layout>. Inside it a <data> block declares the variables, and the old root view follows. The file name decides the class name: activity_main.xml gives ActivityMainBinding.

<layout>
  <data>
    <variable name="user" type="com.example.app.User"/>
  </data>
  <LinearLayout ... >
    <TextView android:text="@{user.name}" ... />
  </LinearLayout>
</layout>
  1. ActivityMainBinding binding = ActivityMainBinding.inflate(getLayoutInflater());
  2. setContentView(binding.getRoot()); the root view, not the binding object.
  3. binding.setUser(user); one setter is generated per <variable>.

Expressions and observable data

@{user.name} is read once, at the moment setUser runs. A plain int or String field never redraws the screen, because the binding has no way to know it changed.

  • ObservableField<String> name: name.set("Asha") notifies every view that reads it.
  • ObservableInt score: score.set(95) notifies; score.get() reads the value.
  • BaseObservable: mark the getter @Bindable, then call notifyPropertyChanged(BR.score) after a change. BR is the generated id class.

Two-way binding writes back: android:text="@={user.name}" copies what the user types in an EditText into the object. The expression must be assignable and the types must match. Make the field observable (ObservableField, LiveData, or BaseObservable with @Bindable) as well, otherwise a change made in code will not update the EditText. With LiveData, call binding.setLifecycleOwner(this) so the binding follows the activity lifecycle instead of leaking.

Worked example

Question. A User object has name "Asha" and an ObservableInt score holding 88. The layout shows them with @{user.name} and @{String.valueOf(user.score)}. Show the layout root, the binding code in onCreate, and what appears on screen after score.set(95). (6 marks)

  1. Root of activity_main.xml: <layout>, containing <data><variable name="user" type="com.example.app.User"/></data>, then a LinearLayout with two TextViews.
  2. First TextView: android:text="@{user.name}". Second TextView: android:text="@{String.valueOf(user.score)}", because an ObservableInt must be turned into text.
  3. onCreate: ActivityMainBinding binding = ActivityMainBinding.inflate(getLayoutInflater()); setContentView(binding.getRoot()); binding.setUser(user);
  4. First screen: Asha in the first TextView, 88 in the second.
  5. The user taps +7: user.score.set(88 + 7) = 95. ObservableInt tells the binding, which rebinds the second TextView.
  6. Second screen: Asha and 95. The first TextView is untouched, and there is no findViewById and no setText anywhere.

Answer. The screen shows Asha and 88, then Asha and 95 after the tap; only the score TextView is redrawn.

Exam traps

  • Using a plain public int for score and expecting a redraw. A plain field is read once at setUser; only ObservableField, ObservableInt or notifyPropertyChanged triggers a rebind.
  • Forgetting the <layout> root. No Binding class is generated, the build fails, and the error points at generated code or R, not at your XML.
  • Writing setContentView(binding) instead of setContentView(binding.getRoot()); the root view must be passed.
  • Using @= with a non-observable field: typing still writes into the object, but a change made in code will not appear in the EditText. A mismatched or non-assignable expression fails the build.
  • Believing data binding saves data. It only displays values; saving is Chapter 4.1 or 4.3.

Takeaways

  1. SharedPreferences holds a few key-value settings in one private XML file; it is not a place for lists of records or large data.
  2. Internal storage is private and always present, external storage is shared and may be unmounted, so check availability before writing.
  3. SQLiteOpenHelper keeps the create and upgrade logic in one class, so every part of the app opens the same database the same way.
  4. A Cursor is a window over the result rows; read the column indexes once and close the Cursor when the work is done.
  5. A content provider hides your tables behind a content:// URI, so other apps never touch your files directly.
  6. ContentResolver is the client half of the same contract: your own app should also read provider data through it.
  7. Share data by sending a content:// URI with a temporary grant flag, never by giving out a raw file path.
  8. Data binding removes the findViewById and setText glue; change the model and the bound views update on their own.
