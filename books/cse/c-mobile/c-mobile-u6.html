6.1 Swift basics: constants, variables and data types

Swift stores every value in a constant or a variable, and the stored type decides which operations are legal. A constant is bound once; a variable can change. The compiler checks types before the app runs, so a wrong mix such as Int times Double stops the build. You use this in every iOS screen: a fare, a name, a switch setting. Some syllabi call these first lessons 'SDK lessons' or 'documentation'. This chapter stays short and moves to real code.

You need Unit 2, which compares iOS with the other mobile platforms; 6.2 comes next for operators and control flow.

Constants and variables

Use let for a constant: you assign it once and cannot assign again. Use var for a variable when the value must change. A name starts with a letter or underscore, then letters, digits or underscores; Swift is case-sensitive, so km and Km differ. Choose a type once and keep it.

Type inference: let rate = 9.0 infers Double because 9.0 has a decimal point; var km = 8 infers Int. Explicit annotation states the type: let baseFare: Double = 20.0. Use annotation when the inferred type is not the one you need or when a public value must be clear.

Core types: Int for whole numbers, Double and Float for real numbers (Double is the default and has more precision), Bool for true or false, String for text, Character for one character, and tuples for a fixed group such as (code: Int, message: String).

Constants protect values that must not drift, such as a tax rate; variables hold values that change, such as a trip distance. The type is part of the name's contract. See 6.3 for structures and classes that group such values.

Types, safety and optionals

Swift is type-safe and never converts silently. km * rate with Int and Double is a compile error, not a warning. Write Double(km) * rate. Converting text to Int returns an Optional because the text may not be a number: Int("8") gives Optional(8), and Int("eight") gives nil. An Optional is a box that may hold a value or may hold nil.

Unwrap before use. if let n = Int("8") { ... } runs only when the box has a value. The nil-coalescing operator gives a fallback: let n = Int("eight") ?? 0 stores 0. The forced unwrap ! crashes if the box is nil, so use it only after a check.

print writes to the console. String interpolation puts a value inside text: print("Total: \(total) rupees"). The backslash-parentheses form inserts the value; it is not a format string. These tools show values while you debug, and they feed labels later. Operators and loops are in 6.2.

Worked example

Question. A city cab charges a fixed ₹20 booking fee plus ₹9.0 per kilometre. Write the Swift for a trip of 8 km and give the total.

  1. The fixed booking fee is 20.0 rupees, stored as a Double: let baseFare: Double = 20.0.
  2. Store the rate: let rate = 9.0; inference makes it Double, rupees per km.
  3. Store the distance: let km = 8; inference makes it Int, km. The distance is fixed for this trip, so a constant fits.
  4. Convert the Int to Double: Double(km) = 8.0.
  5. Distance cost = 8.0 × 9.0 = 72.0 rupees.
  6. Total = 20.0 + 72.0 = 92.0 rupees.
  7. Without conversion, km * rate is a compile error; Int("8") is Optional(8) and Int("eight") is nil.

Answer. The total fare is 92.0 rupees.

Exam traps

  • Multiplying an Int by a Double and expecting automatic conversion; Swift rejects it at compile time.
  • Treating Int("8") as a plain Int; it is an Optional that must be unwrapped.
  • Assuming let only means 'constant expression'; it means the name is bound once and cannot be reassigned.
  • Forcing an unwrap with ! on a nil Optional; the app crashes instead of returning a fallback.
  • Confusing Float and Double; Double is the default and the usual choice for coordinates and measurements.
  • Storing money in Double; use Decimal or store paise as Int, because Double cannot represent values like 0.10 exactly.

6.2 Swift operators, control flow, strings and functions

A program stores values, then acts on them. Operators combine values, control flow decides which statement runs next, strings hold text, and functions name a block so it can be called with different inputs. These four tools turn the constants, types and optionals of the previous chapter into behaviour. Every screen later — a fare label, a login check, a row count — is written with them. Treat this as working vocabulary for the rest of the unit.

You need: Chapter 6.1 — the constants, types and optionals being operated on.

Operators and ranges

Arithmetic is + - * / %. On two Int values, / throws away the remainder: 7 / 2 gives 3. The % operator gives the integer remainder: 7 % 2 gives 1, and the sign follows the left operand, so -7 % 2 gives -1. Write one operand as a Double to keep the fraction: 7.0 / 2.0 gives 3.5.

Comparison operators == != < > <= >= produce a Bool. The single = is assignment, not comparison. The logical operators are && (and), || (or) and ! (not). Swift short-circuits: in a && b, b is skipped when a is false.

A range is written a...b (closed, includes b) or a..<b (half-open, stops before b). 1...5 holds five values, 1..<5 holds four. For an array of count n, loop over 0..<n.

The nil-coalescing operator a ?? b gives a when a is not nil, otherwise b. The ternary condition ? x : y picks x when the condition is true, else y.

Branching and looping

if / else if / else runs the first block whose condition is true. guard is the early exit: guard km > 0 else { return "invalid" } leaves the function unless the condition holds, which keeps the main path flat.

switch compares one value against cases. Swift does not fall through — the first match runs and the switch ends. Cases may be ranges and may carry a where clause.

let km = 12.0
var rate = 0.0
switch km {
case 0...10: rate = 9.0
case 11...: rate = 11.5
default: rate = 11.5
}
print(rate)

Output

11.5

A switch must cover every possible value, which is why the default stays.

Loops: for i in 1...5 { } walks a range or a collection; while condition { } tests before each pass; repeat { } while condition runs the body once before testing.

Strings and functions

Strings join with + and interpolate with \(...): "Short trip: ₹\(fare)". The properties count and isEmpty, and the methods hasPrefix / hasSuffix, inspect text without changing it. A literal wrapped in triple quotes keeps its line breaks.

func fareLabel(km: Double) -> String declares a function: km is the parameter name, Double its type, String the return type. In func f(label name: Type), label is the argument label typed at the call site and name is the parameter name used inside the body. With one word, as in fareLabel(km: Double), that word is both. Write _ in the label position to drop the label.

A parameter may have a default value. inout lets a function change the caller's variable and is called with &: swap(&a, &b). A function may return a tuple such as (label: String, fare: Double).

A closure is a function you pass around as a value; the table view callbacks in 6.6 are closures.

Worked example

Question. A cab app charges a ₹20 base plus ₹9.0 per km for trips up to 10 km, and ₹11.5 per km beyond that. Write fareLabel(km: Double) -> String and trace it for 8 km and 12 km.

    let rate = km <= 10 ? 9.0 : 11.5
    let fare = 20 + km * rate
    let kind = km <= 10 ? "Short" : "Long"
    return "\(kind) trip: ₹\(fare)"
}
print(fareLabel(km: 8))
print(fareLabel(km: 12))
  1. Call 1, km = 8: 8 ≤ 10 is true, rate = ₹9.0. fare = 20 + 8 × 9.0 = 92.0; label "Short trip: ₹92.0".
  2. Call 2, km = 12: 12 ≤ 10 is false, rate = ₹11.5. fare = 20 + 12 × 11.5 = 158.0; label "Long trip: ₹158.0".

Exam traps

  • C-style fallthrough: Swift stops at the first match unless fallthrough is written.
  • Mixing 0...3 (includes 3) with 0..<3 (stops before 3). Looping 0...array.count reads one past the end and crashes.
  • Integer division: 7 / 2 is 3, not 3.5. At least one operand must be Double.
  • Argument label versus parameter name: the label is typed at the call site, and _ removes it.
  • guard's else must leave the scope with return, break, continue or throw, or the code does not compile.

6.3 Swift structures, classes and inheritance

A struct is a value type: assigning it makes a second copy. A class is a reference type: two variables can point at one shared object. Inheritance lets a subclass reuse a superclass and override its methods. Swift uses structs for small model data such as a Trip, and classes for shared state and for UIKit views. The copy-versus-share rule decides most exam marks, and the override rule decides the rest.

You need: Chapter 6.2 — functions become methods and parameters become initializers.

Structs: value types that copy

A struct groups stored properties. struct Trip { var km: Int } gives an automatic memberwise initializer, so Trip(km: 8) is valid without writing an init. The initializer is memberwise: it takes one argument per stored property in declaration order. Assigning a struct copies it. Let a = Trip(km: 8) and var b = a; then set b.km = 12. a.km is still 8 and b.km is 12: two separate copies, not one shared box.

A method that changes a stored property must be marked mutating; without it the compiler stops you. A computed property calculates its value on each read and stores nothing. A didSet observer runs after a stored property changes. String, Array and Dictionary are structs, so they behave as value types when you assign or pass them. For structs that contain arrays or strings, Swift shares the underlying storage until a write; the visible rule is still value semantics.

Classes: shared objects and inheritance

A class is a reference type. Two variables can point at the same object. class Ride { func fare(km: Int) -> Double { return 20 + Double(km) * 9.0 } } is a base class. class Cab: Ride { override func fare(km: Int) -> Double { return super.fare(km: km) + 15 } } is a subclass. override is required; super.fare calls the parent version. For 8 km, Ride gives 20 + 8 × 9.0 = ₹92 and Cab gives ₹92 + ₹15 = ₹107.

Use === to test whether two class variables point at the same object; == is for value equality. A subclass initializer sets its own stored properties first, then calls super.init. final stops further overriding. deinit runs when the last reference goes away. Polymorphism means a Ride variable can hold a Cab, and the call uses Cab's override.

Choose a struct for small model data that is copied, such as Trip. Choose a class for shared state and for anything UIKit must subclass; see Chapter 6.5.

Exam traps

  • Do not expect var b = a on a struct to share changes back to a; each variable owns a copy.
  • A subclass method that replaces a superclass method needs override; without it Swift reports a compile error.
  • A subclass initializer must call super.init after setting its own properties; forgetting it is a compile error, unless the superclass's only designated initializer is a no-argument init(), which Swift then calls for you.
  • Use === for class identity, not ==. == asks value equality and may not exist for a class.
  • A struct method that assigns to a stored property must be mutating.

6.4 Building, running and debugging an iOS app

An iOS app moves from source text to a compiled bundle, an installed copy, a running process, and a paused process under the debugger. Xcode organises this work with a project, target, scheme, bundle identifier, Info.plist and asset catalogue. You edit, build, install, run and debug. Build errors appear before installation; crashes appear only when a line executes. The debugger lets you stop at a breakpoint, inspect variables with LLDB, walk the view hierarchy, and read Apple's documentation with Option-click. Exams often test the order of steps and the meaning of a crash message.

You need: Chapter 6.3, because there must be a class or struct worth running.

The Xcode project and what a build does

An Xcode project is the folder that holds source files, settings and resources. A target is one product built from that project, usually the app. A target also lists the files and build settings used for that product. A scheme names the targets to build, the build configuration for each action, and the executable/launch settings; the run destination is chosen separately in the toolbar. The bundle identifier is the app's unique reverse-domain name, such as com.example.fares. Info.plist stores app metadata and permission text. The asset catalogue stores images and colours. The daily loop is edit, build, install, run, debug.

A build compiles every Swift file and links the results with frameworks into an .app bundle. A compile error stops the build. A warning does not stop it. A runtime crash happens only after install, when a line executes. The figure shows this order, then the crash.

Run, pause and inspect

Choose the simulator for fast testing on the Mac, or a connected device for real camera, sensors and performance. Press Run; Xcode builds, installs, launches and attaches the debugger. A breakpoint is a line marker that pauses execution there. The debug area shows variables and the call stack. Step over runs the current line and stops on the next; step into enters a called function. Simulator builds are faster; device builds need code signing.

The LLDB console accepts commands. po fares prints an object or value. A runtime crash opens the same debug area at the crashing line. The view hierarchy debugger shows every view's frame and order, useful when a control is invisible or misplaced. Option-click any type or method in the editor to open Apple's documentation. The loop is edit, build, install, run, debug, then fix and rebuild. Use breakpoints sparingly; each pause lets you inspect, not guess.

From crash message to fix

Read a crash message in two parts. The first line names the error, such as Fatal error: Index out of range. The stack trace lists the functions active at the crash, with your code usually near the top. A breakpoint set on the suspect line pauses before the bad access, so you can inspect values. Compile errors and runtime crashes need different fixes. A compile error means the compiler rejected the text; the app never installed. A runtime crash means the binary ran and a condition failed. Warnings may hint at the cause but do not stop the build.

The worked example separates the two. For an index crash, check the array count and the range operator. Use the half-open range, or loop over the elements directly. The debugger shows the count and the elements, so check both before editing. Fix the smallest line, rebuild, and rerun the same path. Do not change unrelated code during a debug session.

Worked example

Question. An iOS app stores let fares = [92, 158, 65] and prints each fare with for i in 0...fares.count { print(fares[i]) }. The app is built, installed and run. Explain what the debugger shows when the loop crashes, give the valid index range, the first bad index, and the smallest code fix. State whether this is a build error or a runtime crash.

  1. The array has 3 elements: 92, 158 and 65.
  2. The valid indices are 0, 1 and 2. The last valid index is 2.
  3. The closed range 0...fares.count includes 3, so the loop reaches fares[3].
  4. The debugger pauses on that line with Fatal error: Index out of range.
  5. po fares prints [92, 158, 65], confirming the count is 3.

Exam traps

  • Calling a red runtime crash a compile error: build errors stop before install; index crashes happen only when the line runs.
  • Using a closed range over an array count, which visits one index past the end.
  • Thinking the simulator and a device behave identically; sensors and performance differ.
  • Confusing step over with step into; step into enters a function.

6.5 UIKit and Interface Builder basics

UIKit is Apple's framework of on-screen objects for iOS: views that draw and respond to touch, and view controllers that own one screen each. Interface Builder is the editor that builds a storyboard file, a saved set of screens wired to your Swift code. The wiring happens through outlets (references to views) and actions (methods a control calls). Almost every existing iOS app uses this stack, so reading a storyboard and a view controller together is a core skill.

You need: Chapter 6.4 — the project must build and run before a screen can appear, and Chapter 6.3 for subclassing.

The UIKit layer: views and one controller per screen

UIKit supplies the objects that appear on an iOS screen. At the root of the tree sits UIResponder, the class that can receive touches and other events. UIView is a UIResponder that covers a rectangle and draws inside it; every label, button and text field is a UIView. UIControl is a UIView that also sends an action when the user interacts, and UIButton is a UIControl that sends its action on a tap. UILabel shows read-only text; UITextField takes typed text.

A UIViewController is not a view. It is a UIResponder that owns exactly one screen's worth of views through its view property, and it holds the code for that screen. You subclass it, one subclass per screen. The subclass adds outlets and actions; it does not do the drawing itself.

Many courses now teach SwiftUI beside or instead of storyboards.

A storyboard is data, loaded at run time

The storyboard file is data, not code. It is an XML document listing scenes, one scene per view controller, each holding an archived copy of its views and their properties. At run time UIKit unarchives a scene into real objects, allocates your view controller subclass and sets its view.

  • Object library: the list of available views you drag onto a scene.
  • Attributes inspector: sets a selected object's text, font, colour or stand-in, with no Swift at all.
  • Assistant editor: opens the Swift file beside the canvas so you can Control-drag from a view into code.

Every connection is stored in the storyboard as a name. Rename the outlet later, or change the action's signature, and the stored name stops matching; the app then crashes while running, not while compiling.

Outlets, actions and the life cycle

Control-dragging from a view into code creates one of two things.

Pseudocode.

@IBOutlet weak var fareLabel: UILabel!

@IBAction func showFare(_ sender: UIButton) {
    let fare = 20 + 8 * 9.0
    fareLabel.text = String(format: "₹%.2f", fare)
}

An outlet is a reference to a view. @IBOutlet marks it for the storyboard. weak is correct because the view hierarchy already owns the view, so a strong outlet would add a second owner. The type is implicitly unwrapped (the !) because the outlet is nil while the controller is being created and is filled in when the scene loads. An action is a method a control calls; @IBAction exposes it to Interface Builder, and sender is the control that fired it, useful when several buttons share one action.

  1. viewDidLoad — runs once, first point where outlets are guaranteed connected; one-time setup goes here.
  2. viewWillAppear — runs before the screen is shown; repeated refresh work goes here.
  3. viewDidAppear — the screen is visible.
  4. viewWillDisappear — the screen is about to go away; stop timers here.
  5. viewDidDisappear — the screen is gone.

Worked example

Question. A taxi app screen shows a label reading ₹0 and a button labelled Show fare. Tapping the button for an 8 km trip must show the city fare: a ₹20 base plus ₹9.0 per km. Write the outlet, the action and the placement of the code, and state the fare shown.

  1. Fare = base + distance × rate = ₹20 + 8 km × ₹9.0 per km = ₹20 + ₹72 = ₹92.00.
  2. Declare the outlet: @IBOutlet weak var fareLabel: UILabel! — weak because the view hierarchy owns the label, implicitly unwrapped because it is nil until the scene loads.
  3. Declare the action: @IBAction func showFare(_ sender: UIButton) — sender is the button that fired.
  4. Inside the action work out the fare and write it: let fare = 20 + 8 * 9.0, then fareLabel.text = String(format: "₹%.2f", fare), which shows ₹92.00.
  5. Use the outlet only after the scene has loaded: before viewDidLoad it is still nil, so any use in an initializer or an early property observer crashes.

Answer. The label shows ₹92.00, written by fareLabel.text = String(format: "₹%.2f", fare) when the button is tapped.

Exam traps

  • Using an outlet from an initializer or a property observer that fires before loading — it is still nil and the app crashes.
  • Editing an @IBAction signature after connecting it; the storyboard still names the old one and the app crashes at run time, not compile time.
  • Believing the storyboard contains code or creates your class: it only archives objects and names connections.
  • Declaring an outlet strong instead of weak, which gives the view a second owner.
  • Confusing viewDidLoad (once, setup) with viewWillAppear (every time the screen is shown, refresh).

6.6 Displaying data and controls in action

A screen that shows a list never copies its data into the view. The view asks a data source how many rows exist, and asks again for each row just before that row appears. Controls run the other way: a switch, slider or text field fires an event and your code reacts to it. This asking and reacting pair is how nearly every iOS screen works — a fare list, a route picker, a profile photo, a share menu. This chapter builds that loop with UITableView, UIPickerView, UIImageView, UIMenu and control events.

You need: functions and closures from 6.2, and outlets and actions from 6.5.

A table view asks for rows on demand

UITableView shows a scrolling list and stores no data of its own. It holds two connections to your view controller: dataSource and delegate. Both are protocols, meaning a list of methods a class promises to implement. The data source answers "how many rows" and "what goes in this row". The delegate answers "the user did something".

Two data source methods are required. tableView(_:numberOfRowsInSection:) returns an Int, the row count for the section number passed in. tableView(_:cellForRowAt:) returns one configured UITableViewCell. IndexPath carries two Int fields, section and row, both counting from 0. Row 1 is the second row, not the first.

  1. The table view calls numberOfRowsInSection once per section to learn the counts.
  2. It calls cellForRowAt only for rows near the visible area, not for all rows.
  3. Inside that method, call dequeueReusableCell(withIdentifier:for:) to take a recycled cell from the reuse pool.
  4. Fill the cell's labels from the model array, using indexPath.row as the index.
  5. Return the cell; the table places it on screen.
  6. When the array changes, call tableView.reloadData() so the table asks again.

Reuse is why the identifier matters. A cell scrolled off the bottom returns to the pool, and a cell scrolled into view is pulled out of it. The identifier string in code must equal the prototype cell's Identifier in the storyboard. If they differ, the app stops with the message "unable to dequeue a cell with identifier".

didSelectRowAt fires on a tap. Read indexPath.row, look up the model, and pass that one value onward. For a custom layout, subclass UITableViewCell, connect its label outlets, and cast the dequeued cell: let cell = tableView.dequeueReusableCell(withIdentifier: "FareCell", for: indexPath) as! FareCell.

Pickers, images and menus

UIPickerView is a spinning wheel. It has components (columns) numbered from 0, and each component has rows. The data source returns numberOfComponents and pickerView(_:numberOfRowsInComponent:). The delegate returns pickerView(_:titleForRow:forComponent:) and receives didSelectRow. That is the same ask-don't-push pattern as the table.

UIImage is the in-memory bitmap; UIImageView draws it. Put image files in the asset catalogue (Assets.xcassets) so Xcode supplies the right scale. Load with UIImage(named: "chennai"), with no file extension. contentMode decides how the image fits its frame: .scaleAspectFit keeps the ratio and leaves empty space, .scaleAspectFill keeps the ratio and crops, .scaleToFill stretches and distorts.

UIMenu and UIAction build a pop-up menu without a storyboard. An action has a title, an optional image, and a handler closure (see 6.2). Group actions in a UIMenu, then attach it: button.menu = menu and button.showsMenuAsPrimaryAction = true, or barButtonItem.menu = menu. Some syllabi call this using menus with views.

Control events and supporting views

Controls report change through events. In Interface Builder you drag from the control to your code and choose the event. In code you call addTarget(_:action:for:). The handler usually takes the sender, for example @IBAction func fareChanged(_ sender: UISlider) { label.text = String(sender.value) }.

  • UISwitch fires .valueChanged; read its isOn Bool.
  • UISlider fires .valueChanged; read value as a Float, bounded by minimumValue and maximumValue.
  • UISegmentedControl fires .valueChanged; read selectedSegmentIndex, an Int counting from 0.
  • UITextField fires .editingChanged on every keystroke and .editingDidEnd when editing stops; read text, a String?.

Three supporting views appear on most screens. UIScrollView scrolls content larger than the screen. UIStackView arranges children in a row or a column and is the usual way to build a form (see 6.7). UIActivityIndicatorView is a spinner: call startAnimating() before slow work and stopAnimating() after. For a message, build a UIAlertController, add a UIAlertAction, then present(_:animated:completion:).

The rule holds everywhere: the view asks the model for data at the moment it needs it. Data never pushes itself into a view. You change the array, then call reloadData() or set the label, and the view redraws.

Worked example

Question. A cab app charges a base fare of ₹20 plus distance × rate per km. The city rate is ₹9.0 per km; the outstation rate is ₹11.5 per km. Three trips are booked in a one-section table: 8 km city, 12 km outstation, 5 km city. (i) Compute each fare. (ii) What does numberOfRowsInSection return? (iii) What does the cell at indexPath.row = 1 display? (iv) The user taps that row — what value must the next screen receive?

  1. Fare 0 = 20 + 8 × 9.0 = 20 + 72 = ₹92.
  2. Fare 1 = 20 + 12 × 11.5 = 20 + 138 = ₹158.
  3. Fare 2 = 20 + 5 × 9.0 = 20 + 45 = ₹65.
  4. The model array is [92, 158, 65]. It has 3 elements, and the table has one section, so numberOfRowsInSection returns 3.
  5. The table calls cellForRowAt for indexPath.row = 1. The index picks the second element, so the cell shows ₹158.
  6. didSelectRowAt records indexPath.section = 0 and indexPath.row = 1, reads fares[1] = 158, and passes 158 to the next screen, not the whole array.

Answer. The fares are ₹92, ₹158 and ₹65; the table has 3 rows; row 1 shows ₹158; the tap passes the single value 158 onward.

Worked example 2

Question. Second short check: a slider has minimumValue 0 and maximumValue 100 and sits at 37.5. The handler is label.text = String(sender.value). What does the label show, and how do you print it to one decimal place?

  2. String(37.5) gives the shortest exact description, so the label shows 37.5.

Exam traps

  • Using indexPath.section where indexPath.row belongs. With one section, section is always 0, so every row shows fares[0]; index the model array with indexPath.row.
  • The reuse identifier in code not matching the prototype cell in the storyboard. The app stops with "unable to dequeue a cell with identifier".
  • Re-sorting or filtering the model array inside cellForRowAt, so row numbers no longer match the data. Sort once, outside the method.
  • Returning a recycled cell without resetting every label, so an old row's text flashes in a new row. Always overwrite all labels.
  • A storyboard action or outlet still connected to a method or property you renamed or deleted. The app crashes on unrecognized selector when the control fires. Delete the old connection and reconnect it.

6.7 Auto Layout and stack views

Auto Layout turns every view's position and size into linear equations called constraints. Instead of a fixed frame, you state rules — this button sits 16 points from the leading edge, that label is centred — and the system solves them for whatever screen it meets. The same rules survive rotation, a bigger phone, or split screen. Stack views bundle the common cases into one object with an axis, alignment and distribution. Every iOS screen relies on this, from a UPI confirmation to an IRCTC train list.

You need Chapter 6.5 for views and view controllers, and Chapter 6.6 for the controls being constrained.

Constraints are equations

Most constraints are linear equations over a view's frame; a constraint may also be an inequality such as height ≥ 44, which the solver satisfies rather than solves exactly. The attributes are leading, trailing, top, bottom, width, height, centerX and centerY. Leading is the side writing starts from — left in English, right in Arabic — so leading-based layouts mirror themselves.

item1.attr = m × item2.attr + c

item1 and item2 are views, usually a child and its superview; attr is one of the eight attributes; m is the multiplier (default 1); c is the constant in points. Pinning a button 16 points in from the leading edge is button.leading = safeArea.leading + 16.

The safe area is the part of the screen not covered by the notch, status bar or home indicator. Pin to view.safeAreaLayoutGuide, not to view, or the top row slides under the sensor housing.

A label or button also carries an intrinsic content size — the size its text and font ask for. Two priorities arbitrate when space is short. Content hugging (default 250) resists growing; a higher value keeps the view small. Compression resistance (default 750) resists shrinking; a higher value refuses to squash. Priority 1000 is UILayoutPriority.required — the strongest wish, and you cannot soften it by lowering it. If required rules conflict, the system still breaks one at runtime and logs the conflict, so the fix is to remove or rewrite it.

An ambiguous layout has more than one solution and shows as orange or dashed lines. Fix it by adding a rule — pin both leading and trailing, or give an explicit width or height — because the system needs one more equation to reach a single solution. An unsatisfiable layout has contradictory rules; fix it by deleting or lowering the priority of a conflicting rule. The runtime also breaks one and logs it.

Stack views and fillEqually arithmetic

A UIStackView arranges its arrangedSubviews in a row or column and writes the constraints itself.

  • axis — horizontal or vertical.
  • alignment — placement on the other axis: .fill stretches children across it; also .center, .leading, .trailing.
  • distribution — .fill (the arranged subviews stretch to fill the axis; the child with the lowest content hugging priority, default 250, takes the slack, and the one with the lowest compression resistance shrinks when space is short), .fillEqually (every child equal), .equalSpacing (children keep intrinsic size, gaps equalise).
  • spacing — a constant number of points between neighbours.

Nest a horizontal stack inside a vertical stack to build a form without a dozen hand-written constraints. Setting isHidden = true on an arranged subview removes it from the layout; alpha = 0 does not.

A fixed frame such as CGRect(x: 0, y: 0, width: 100, height: 40) is in points and never updates. After rotation, or on a 320-point phone instead of a 430-point one, it is simply wrong. Constraints re-solve on every size change.

w = (W − L − R − s(n − 1)) ÷ n

W is the container width in points, L and R the leading and trailing margins, s the spacing, n the number of arranged subviews, and w the width of each.

With n = 3, s = 8, L = R = 16 on W = 360: 360 − 32 = 328 content, minus 16 of gaps = 312, so w = 104 points.

Worked example

Question. A horizontal stack view holds three buttons, spacing 8 points, pinned 16 points from the leading and trailing safe-area edges, distribution fillEqually. Find each button's width on a 360-point-wide screen and on a 320-point-wide screen.

  1. On 360 points: 360 − 16 − 16 = 328 points of content width.
  2. Two gaps of 8 give 16 points.
  3. 328 − 16 = 312; 312 ÷ 3 = 104 points per button.
  4. On 320 points: 320 − 32 = 288; 288 − 16 = 272; 272 ÷ 3 ≈ 90.67 points per button.

Answer. Each button is 104 points on a 360-point screen and about 90.67 points on a 320-point screen.

Exam traps

  • Pinning to view instead of view.safeAreaLayoutGuide: on a notched iPhone the top row slides under the sensor housing.
  • Giving a label both a fixed width and a trailing pin: the layout turns unsatisfiable. Delete one rule; do not shrink the font.
  • Swapping priorities: hugging 250 resists growing, compression resistance 750 resists shrinking.
  • Expecting .equalSpacing to equalise widths; it equalises gaps.
  • Dividing the full screen width by n and forgetting margins and gaps.

6.8 Segues and navigation controllers

A navigation controller owns a stack of view controllers. The bottom is the root; new screens are pushed on top. A segue is a storyboard-declared move from one screen to another. It pushes inside a navigation controller, or presents modally, and carries data through prepare(for:sender:). This gives the back button, titles and a predictable return path. Most UIKit apps use this for list and detail screens.

You need: a source screen with data and a destination screen to fill from Chapter 6.5 and Chapter 6.6.

The navigation stack

UINavigationController is a container view controller. It shows one child at a time and remembers a stack. The first screen is the root view controller. The root stays loaded at the bottom. Push a new view controller to slide it on top. Pop removes the top controller and reveals the one below. The navigation bar shows the current title and a back button. Set title for short text. Set navigationItem.largeTitleDisplayMode on each screen, and navigationController?.navigationBar.prefersLargeTitles once for the whole stack. The back button is created for you and labelled with the previous screen's title.

Use pushViewController(_:animated:) and popViewController(animated:) in code. Storyboards create the same pushes through a show segue.

Segues: show, modal and unwind

A segue is a storyboard connection from a control or cell to a destination scene. A show segue pushes only when the source is inside a UINavigationController. Outside one, UIKit falls back to modal presentation: the destination appears without a back button or navigation bar. To get a push, embed the source in a UINavigationController. Present Modally also shows the destination over the current screen, with no back button; add a Close button that calls dismiss(animated:). An unwind segue goes backwards to an existing screen by calling an @IBAction method that takes a UIStoryboardSegue.

  1. Give the segue an identifier, for example showDetail.
  2. Call performSegue(withIdentifier: "showDetail", sender: self), or let the cell tap trigger it.
  3. Override prepare(for:sender:). Read sender or tableView.indexPathForSelectedRow in the source controller.
  4. Cast segue.destination as? DetailViewController; if nil, return.
  5. Set destination properties, for example detail.fare = 158.

On a push, the destination runs viewDidLoad once, then viewWillAppear and viewDidAppear. When you pop back, the source's viewWillAppear fires again. Its viewDidLoad does not run again. Use viewWillAppear to refresh values that may change while Detail is open.

Pseudocode.

override func prepare(for segue: UIStoryboardSegue, sender: Any?) {
    guard segue.identifier == "showDetail" else { return }
    guard let row = tableView.indexPathForSelectedRow?.row else { return }
    guard let detail = segue.destination as? DetailViewController else { return }
    detail.fare = fares[row]
}

Output

Result: row 1 sets detail.fare to 158 before Detail appears; prepare returns no value.

Tab bar controllers and safe data passing

A UITabBarController switches between whole view controllers or whole navigation stacks. Each tab keeps its own stack and root. Tapping a tab selects a child; it does not push. Apps use this for Home, Bookings and Account. Some syllabi list tab bar controllers and the view controller life cycle with this chapter.

For a storyboard segue, prepare(for:sender:) is the correct place to hand data over. For a code-driven push, create the destination, set its properties, then call pushViewController(_:animated:). An initializer or closure is also valid. prepare(for:sender:) runs before the destination appears, so outlets may not be connected yet. Read tableView.indexPathForSelectedRow in the source controller inside prepare, because the source owns the table view. The row stays selected after you return unless you call tableView.deselectRow(at:animated:) yourself. Use as? and a guard. A wrong identifier or class then does nothing instead of crashing. Force-casting with as! is the usual crash in exams.

Worked example

  2. Read the selected row: fare = fares[1] = ₹158.
  3. In prepare(for:sender:), cast destination as? DetailViewController and set detail.fare = 158.
  4. Before the push the stack has 1 controller, [Fare List]. After the push it has 2, [Fare List, Detail].

Exam traps

  • Reading tableView.indexPathForSelectedRow in the destination: the destination has no access to the source table view. Read it in the source inside prepare(for:sender:). The row stays selected after you return unless you deselect it.
  • Force-casting segue.destination as! DetailViewController with a wrong identifier or class crashes. Use as? and return on nil.
  • Using a show segue outside a navigation controller: UIKit falls back to modal presentation. The screen appears but has no back button or navigation bar. Embed the source in a UINavigationController for a push.
  • Confusing viewDidLoad with viewWillAppear: when you pop back, viewWillAppear runs again, viewDidLoad does not.

embed list screen in navigation controller; segue from cell or button; prepare(for:sender:) runs before push; destination view controller receives model; back button pops the stack.

model array owned by list view controller; table view data source supplies count and cells; selection triggers segue; prepare passes selected model to detail; detail outlets show data; navigation controller pops on back.

Glossary

Array
An ordered collection that stores values of one type at integer indices.
Closure
A block of code that can be passed and called later, like a function without a name.
Compression resistance
A constraint priority that resists a view shrinking below its intrinsic size.
Content hugging
A constraint priority that resists a view growing larger than its intrinsic size.
Data source
The object that supplies a table view's row count and cells.
Delegate
An object that receives callbacks, such as selection or layout events, from another object.
Dictionary
An unordered collection that maps unique keys to values.
Initializer
A special method that prepares a new instance by setting its stored properties.
Intrinsic content size
The natural size a view wants based on its content, such as a label's text.
Navigation stack
The ordered list of view controllers a navigation controller manages, with the last one on screen.
Optional binding
An if let or guard let construct that unwraps an optional only when it contains a value.
Property
A value or computed value stored on or provided by a type or instance.
Reference cycle
A situation where two class instances strongly refer to each other and neither is freed.
Reuse identifier
A string that lets a table view recycle a cell of the correct prototype.
Safe area
The part of a screen not covered by status bars, home indicators or other system UI.
Scene
One screen's worth of views and a view controller inside a storyboard.
String interpolation
Writing \(expression) inside a string literal to insert that expression's text.
Subclass
A class that inherits from another class and can add or override behaviour.
Superclass
The class from which a subclass inherits properties and methods.
Table view cell
A reusable view that draws one row of a table view.
Type annotation
Writing a colon and a type after a name to state the type explicitly.
Type inference
The compiler's ability to deduce a value's type from its initial value without an explicit annotation.
Unwind segue
A segue that returns from a scene to an earlier view controller in the storyboard.
UserDefaults
A small key-value store for user preferences that persists across launches.
