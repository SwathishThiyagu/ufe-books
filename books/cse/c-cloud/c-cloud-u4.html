4.1 Cloud storage: organization of data

Cloud storage does not keep a user file as one piece on one disk. It puts the file in a namespace, cuts it into chunks, records where each chunk lives in metadata, and places copies on many machines. That layout decides durability when a disk dies, latency when a reader asks for bytes, and the monthly bill. Photo services, backups, logs, VM disks and databases all use it, but they choose different storage shapes and different copy schemes. This chapter shows the shapes and the layout.

You need: storage devices, usage monitors and SLAs from Unit 2, and storage virtualization from Unit 3; the chunk-server design appears in 4.2.

Three storage shapes

Cloud offers three storage shapes. Block storage gives a raw volume: a sequence of fixed-size blocks with no file system inside it. The VM attaches the volume and formats it. Use it for boot disks, databases and workloads needing low latency and random writes. File storage gives a shared directory tree. Many VMs mount the same directory and use paths and file locks. Use it for home directories, shared application files and build caches. Object storage gives a flat namespace called a bucket. Each item has a key and a value, reached over HTTP. Use it for photos, videos, backups, logs and static sites. Some syllabi call object storage blob storage, and call chunks blocks or extents. The three shapes differ in access method and in who manages the file system.

ShapeAccessTypical use
Blockraw blocks, attached to VMdatabase, boot disk
Fileshared path treehome dirs, shared apps
ObjectHTTP key in bucketphotos, backups, logs

How one object is laid out

Organization starts with a namespace. The bucket is a flat namespace: the key img1.jpg is unique inside it. A prefix such as 2025/ looks like a folder but is only part of the key. The store then splits the object into fixed-size chunks, for example 64 MB each. A metadata service records the object name, size, chunk list and the servers that hold each chunk. The metadata is small compared with data but must be highly available. Each chunk is copied to r servers. The replication factor r is the number of full copies kept; r=3 means three full copies. On a read, the client asks metadata, then fetches chunks from a replica. A caching tier in front of the store keeps hot objects close to users. Data locality means running the compute near the chunk: a photo resizer should run in the same region as the bucket. The data type also matters. Block and file storage suit structured records with a schema; object storage suits semi-structured files such as JSON and logs; key-value stores suit simple lookups by key. Erasure coding replaces full copies with k data fragments and m parity fragments. Any k of the k+m fragments rebuild the chunk. RS(6,3) uses 6 data and 3 parity fragments, so 9 fragments in total.

raw disk = S × r

S is the logical data size in GB; r is the replication factor, the number of full copies kept.

storage factor = (k + m) ÷ k

k is the number of data fragments; m is the number of parity fragments; k + m is the total fragments per chunk.

Durability, latency and the bill

Replication is simple and fast. A read can come from any copy, and a rebuild is a copy from a live replica. Its cost is disk. Erasure coding is cheaper in disk but needs more CPU and network to encode, decode and rebuild. Small random reads can be slower because a read may need several fragments. A repair also needs k surviving fragments and network traffic, so the saving is paid for in work. The bill follows raw disk, requests and egress, not logical bytes. Reporting 600 GB of user data as 600 GB of disk is wrong when r=3; the provider buys 1800 GB. Metadata, snapshots and indexes add more. Durability is not three times one copy. Three copies on the same rack still fail together, so providers place replicas on different racks or zones and repair lost copies automatically. Latency comes from distance and round trips: metadata lookup, chunk fetch, cache miss. A local cache cuts the last two. For a photo service, the hot set is small; caching it changes both latency and egress cost.

Worked example

Question. A photo service stores 600 GB of images. With a replication factor of 3, how much raw disk is needed, and what does it cost per month at ₹1.5 per GB-month? With erasure coding RS(6,3) instead, how much?

  1. Logical data S = 600 GB.
  2. Replication factor r = 3, so raw disk = S × r = 600 GB × 3 = 1800 GB.
  3. Price p = ₹1.5 per GB-month, so replication cost = 1800 GB × ₹1.5 = ₹2700 per month.
  4. RS(6,3) has k = 6 data fragments and m = 3 parity fragments, total n = 9. Storage factor = n ÷ k = 9 ÷ 6 = 1.5.
  5. Raw disk = S × 1.5 = 600 GB × 1.5 = 900 GB.
  6. Erasure-coding cost = 900 GB × ₹1.5 = ₹1350 per month.
  7. Saving = ₹2700 − ₹1350 = ₹1350 per month.

Answer. Replication needs 1800 GB and costs ₹2700 per month; RS(6,3) needs 900 GB and costs ₹1350 per month, saving ₹1350 per month.

Exam traps

  • Logical size is not the disk bill. With replication factor r, raw disk is S × r; metadata, snapshots and indexes add more.
  • Replication factor 3 means three copies, not three times the durability of one copy. Durability depends on independent failure domains and timely repair.
  • Block storage (a raw volume for a VM) is not the same as a chunk or block inside an object store. The first is a product; the second is an internal piece.
  • Erasure coding is not free storage. It saves disk but spends CPU, network and repair time, and can hurt small random reads.
  • A bucket is flat. Prefixes look like folders but are part of the key, so renaming a prefix is not a cheap directory rename.

4.2 Distributed file systems: GFS and HDFS

GFS and HDFS keep one metadata master and many chunk servers. The master stores file names, directories and a map from each file to its chunks; the chunk servers store the bytes. Every chunk is copied three times by default. This design exists because cheap commodity disks fail often, and replication turns a disk failure into a routine event. The single master keeps placement simple. Large blocks give high sequential read throughput for batch jobs, log stores and cloud data lakes.

You need 4.1 for chunks, metadata and replication.

GFS: master, chunks and the write lease

GFS splits each file into fixed-size chunks, 64 MB by default. A single master holds the namespace (directories and file names) and the chunk map (which chunk servers hold each chunk). The chunk servers hold the bytes. Each chunk has three replicas by default, so one disk failure does not lose data. The master is small and does not stream file data.

On a write, the client asks the master to create a file. The master records the file and returns. When the client is ready to write a chunk, the master grants a lease on that chunk to one replica, called the primary, for a fixed time. The master also returns the replica locations for that chunk. The lease gives the primary the right to order writes. The client pushes data along a pipeline: primary, then second replica, then third. Each server stores the bytes and sends an acknowledgement back. The primary sends the final ack to the client. All replicas apply writes in the same order, so the chunk stays consistent. For a read, the client asks the master for chunk locations, then reads directly from a chunk server.

HDFS: NameNode, DataNodes, racks and HA

HDFS copies the same idea with new names. The NameNode holds the namespace and the block map. DataNodes store blocks. The default block size is 128 MB; many older clusters use 64 MB. Replication is 3. Rack-aware placement keeps at least one replica on a different rack, so a rack switch or power failure does not remove all copies.

Read path: a client asks the NameNode where a block lives. The NameNode returns DataNode addresses. The client reads the block directly from a DataNode, usually the nearest one. File data does not pass through the NameNode, so one metadata server can support many readers.

DataNodes send block reports to the NameNode. hdfs fsck checks missing and under-replicated blocks. For high availability, an active NameNode and a standby NameNode share an edit journal. The standby reads the journal and can take over. The Secondary NameNode is not a standby: it only merges the edit log into the fsimage checkpoint.

Files are write-once. You can append at the end, but you do not update bytes at random offsets. This fits batch jobs that write large files once and read them many times.

Small files and the metadata count

Small files are expensive. The NameNode keeps one metadata entry per file and one entry per block, not per replica. A 1 MB file still uses one block entry, even if the block size is 128 MB. One million 1 MB files therefore create about two million entries, while the data is only 1 TB. NameNode memory becomes the limit before disk does.

Replication uses DataNode disk, not NameNode entries. If a file has B blocks and replication R, the cluster stores B × R block copies, but the NameNode records B block entries plus one file entry. Use the block size given in the question. GFS at 64 MB and HDFS at 128 MB give different counts for the same file. Failure recovery after a disk loss is covered in 4.6.

blocks = ⌈S ÷ B⌉; replicas = blocks × R; metadata entries = blocks + 1

S is file size in MB; B is block size in MB; R is replication factor; ⌈⌉ rounds up. The +1 is the file entry, not one per replica.

Worked example

Question. A 1024 MB file is written to HDFS with block size 128 MB and replication factor 3. Find the number of blocks, block replicas, and NameNode metadata entries (block entries plus the file entry). Then repeat for GFS with 64 MB chunks.

  1. HDFS blocks = 1024 ÷ 128 = 8 blocks.
  2. HDFS block replicas = 8 × 3 = 24 copies on DataNodes.
  3. NameNode entries = 8 block entries + 1 file entry = 9 entries. It does not store 24 entries.
  4. GFS chunks = 1024 ÷ 64 = 16 chunks.
  5. GFS replicas = 16 × 3 = 48 chunk copies.
  6. GFS metadata entries = 16 chunk entries + 1 file entry = 17 entries.

Answer. HDFS: 8 blocks, 24 block replicas and 9 NameNode entries. GFS: 16 chunks, 48 chunk replicas and 17 metadata entries (16 chunk entries + 1 file entry).

Exam traps

  • The Secondary NameNode is not a backup or standby; it only checkpoints the edit log into the fsimage.
  • Do not mix the block sizes: GFS uses 64 MB chunks, HDFS defaults to 128 MB, and older HDFS clusters often use 64 MB.
  • NameNode entries are per block, not per replica, so 8 blocks with replication 3 give 8 block entries, not 24.
  • File data goes from the client to a DataNode, not through the NameNode; the NameNode only gives locations.
  • Write-once and append-only do not mean random updates; random writes are a poor fit for GFS and HDFS.

4.3 BigTable and cloud databases

BigTable is a sparse, distributed, sorted map: most cells are empty, rows sit in key order, and data is spread over thousands of machines. A cell is addressed by row key, column key and timestamp. It exists because a web index is too large for one relational database and needs range scans. The NoSQL cloud databases in this unit generalise the trade: they drop joins and fixed schemas to scale out. They run search indexes, click logs, user profiles and time-series data. Some syllabi call this unit 'key-value and semi-structured data storage'.

You need: 4.1 for chunks and metadata, and 4.2 for the replicated file system under BigTable.

Rows, families, qualifiers and versions

BigTable stores an untyped byte string in every cell. A cell is addressed by a row key (a string), a column key, and a timestamp (a 64-bit integer). The column key is written family:qualifier. The row key is the only index. Rows are sorted lexicographically, so keys with the same prefix sit together and a range scan reads them in one pass.

Column families are created before data is written. A family is the unit of storage, compression and access control; its columns are stored together. Inside a family, qualifiers can appear freely, so contents:html and anchor:cnnsi.com need no schema change. A missing cell takes no space; that is what sparse means.

Each cell may hold several versions. Every write gets a timestamp; a read at time T returns the newest version with timestamp at or before T. Old versions are removed by garbage collection rules set per family.

value = map[row][family:qualifier][timestamp]

row is the row key string; family:qualifier is the column key; timestamp is the 64-bit version number; value is an uninterpreted byte string.

Tablets, METADATA and the write path

BigTable splits a table by row-key range into tablets. A tablet is the unit of distribution. One tablet server owns each tablet; as data grows a tablet splits, and as servers fail tablets move.

A three-level METADATA tree finds tablets. The root tablet never splits. It lists metadata tablets; each metadata tablet lists user tablets and their ranges. A lock service called Chubby holds the root tablet location and detects failure. Clients cache the path, so most reads go straight to the owning server.

A write is durable before it is visible. Steps:

  1. Client sends the write to the tablet server for that row range.
  2. Server appends the write to a commit log on disk.
  3. Server inserts the write into the memtable, a sorted in-memory map.
  4. A full memtable is frozen and written to disk as an immutable SSTable.
  5. Compaction merges SSTables and removes old versions only when the family's garbage-collection rules allow, for example beyond a version count or an age limit.

An SSTable is an immutable sorted file of key-value pairs. A read merges the memtable and SSTables and returns the newest visible version; bloom filters skip files that cannot hold the key. Replication and recovery targets are in 4.6.

The NoSQL family and consistency choices

BigTable is one point in the NoSQL family. NoSQL means 'not only SQL': keep a simple data model and scale by partitioning and replication instead of joins. Common types:

TypeExampleData model
Key-valueDynamoDBA key maps to one opaque value; the value may be a document.
Wide-columnCassandraRows with named columns grouped into families; sparse and sorted by row key.
DocumentMongoDBA JSON-like document per key; fields can differ between documents.
GraphNeo4jNodes and edges; traversal follows relationships.

These stores hold semi-structured data: each record carries its own field names, so the schema is flexible. The cost is no planned join across records; the application must model each query into the key.

Consistency is a design choice. Strong consistency returns the latest committed write. Eventual consistency lets replicas converge later, so a read may return an older value. During a network partition a system may choose availability over consistency; that is the CAP trade. A shopping cart may prefer availability; a bank ledger may prefer strong consistency.

Row-key design decides performance

Rows are sorted by key, so the row key is the physical layout. A good key turns the common query into a short range scan; a bad key makes every write hit one tablet.

A crawler stores www.cnn.com as com.cnn.www. If keys kept hostnames unreversed, pages from different cnn.com subdomains such as www, sports and money would sort apart. Reversing the domain components puts all cnn.com hosts under the prefix com.cnn. A range scan then reads those rows contiguously; a large site spans several adjacent tablets.

Monotonic keys create a hotspot. If the key is an always-increasing timestamp, every new write goes to the last tablet while other servers idle. Add a hash prefix or reverse the timestamp to spread writes. Choose the key before the database; no index fixes a bad key.

This is why cloud databases suit large logs, click streams, sensor readings and user profiles. Each query is answered from a key range, not a join. You gain scale and predictable range scans; you give up ad-hoc joins and a rigid schema.

Worked example

Question. A crawler stores pages under reversed domain names. Row key com.cnn.www has column family contents with three versions at timestamps t3, t5 and t6, and two anchor columns: anchor:cnnsi.com at t3 and anchor:my.look.ca at t6. (a) Which contents value does a read at time t5.5 return? (b) Why reverse the domain? Give the version count and anchor-column count.

  1. Contents versions sorted: t3, t5, t6.
  2. Candidate versions with timestamp ≤ t5.5: t3 and t5; t6 is excluded because 6 > 5.5.
  3. Newest candidate: t5. BigTable returns that contents value.
  4. Contents version count = 3; anchor-column count = 2 (anchor:cnnsi.com, anchor:my.look.ca).
  5. Reversing www.cnn.com to com.cnn.www makes all cnn.com rows share the prefix com.cnn, so they sit together in sorted order and a range scan reads them contiguously.

Answer. The read returns the contents version stamped t5; the row has 3 contents versions and 2 anchor columns.

Exam traps

  • Treating BigTable as relational: it has no joins, no foreign keys and no cheap full scan; row-key design is the query plan.
  • Using increasing timestamps as row keys; every write lands on the last tablet and creates a hotspot.
  • Confusing a column family with a qualifier; families are schema and storage units, qualifiers are free names inside a family.
  • Reading a timestamp as a clock display; it is a version number, and a read returns the newest version at or before its time.
  • Mixing strong and eventual consistency; eventual reads may return an older value after a write.

4.4 Resource provisioning and allocation

Resource provisioning decides how much capacity a provider makes available; resource allocation decides which host and which slot actually serves each request. Both are judged by two numbers: utilisation, the share of installed capacity doing useful work, and the SLA, the promise made to the tenant. Give too much capacity and money burns; give too little and the promise breaks. Every provider runs this loop, from a UPI app on a Friday evening to a Chennai startup's batch job at 2 a.m., and simulators use hosts, VMs and MIPS ratings to study it.

You need: virtual machines and live migration from Unit 3, hypervisors; SLAs and automated scaling from Unit 2, elastic and on-demand computing.

The two decisions, kept apart

Provisioning answers how much. Allocation answers where. Provisioning runs on a slow clock: a monthly capacity plan, an autoscaling rule firing in minutes. Allocation runs fast: a scheduler places a VM or container in seconds, and live migration may move it later.

Admission control sits before both. It checks the request against the tenant's quota and the SLA — say 2 vCPU and 8 GB for a new web tier — and accepts, queues or rejects. A provider that accepts work it cannot place has already broken its SLA.

Four resources must fit at once: vCPU (a virtual processor core), RAM in GB, disk IOPS (input/output operations per second) and network bandwidth in Mbit/s. A host with free CPU but a saturated disk fits nothing more. Allocation is therefore a vector test, not one number.

host accepts request  ⇔  for every resource r:  used_r + need_r ≤ capacity_r

used_r is the capacity already promised on that host for resource r; need_r is what the new VM asks for; capacity_r is the host's total for that resource. If any r fails, the host is rejected.

How much: static, dynamic and headroom

Static provisioning reserves a fixed slice — a rack, a committed 100 Mbit/s line. Easy to bill, wasteful when idle. Dynamic (elastic) provisioning adds and removes capacity with demand: a ticket site before a final, a retail app on a sale day. It needs a monitor, a scaling rule (add a VM when mean CPU over 5 minutes passes 70 percent) and a cooldown so it does not oscillate.

Over-provisioning buys safety and wastes money. Under-provisioning saves money and breaks the SLA through throttling, long queues or out-of-memory kills. Both are read off utilisation:

U = (busy capacity ÷ installed capacity) × 100%   and   A = (promised capacity ÷ installed capacity) × 100%

U is utilisation in percent; busy capacity is what is actually doing work. A is the allocation ratio in percent; promised capacity is what tenants were given. installed capacity is what the provider bought and powered. The worked example and quizzes below report A, the allocation ratio, because busy load is not given.

Keep headroom. The hypervisor needs CPU and RAM of its own, so planning often holds back 10 to 20 percent of vCPU. A second reserve stops a host thrashing: if RAM is sold to 100 percent, the hypervisor swaps and every VM on that host slows down. Never plan to 100 percent.

In simulators a host is rated in MIPS, millions of instructions per second. That is an instruction rate, not a clock speed in MHz. Each VM or cloudlet asks for a share of the host's MIPS, and the simulator checks that the shares sum to no more than the rating.

Which host: allocation as bin packing

Placement is bin packing. Hosts are bins, VMs are items, and item sizes have several dimensions. Bin packing is NP-hard, so real schedulers use fast heuristics.

  1. Sort pending VMs largest first (first-fit decreasing).
  2. Walk the host list in order.
  3. Place the VM on the first host where every resource fits.
  4. If no host fits, open a new host or queue the request.

Best-fit picks the host with the least free space left after placing, which packs tightly and reduces the number of hosts used, but it leaves small leftover gaps that a later large VM cannot use. First-fit is faster and leaves larger free regions on the later hosts. Worst-fit spreads load, useful when VMs are bursty and share a network link.

Rules override the packing. Affinity keeps two VMs together, such as a web tier and its cache, to cut latency. Anti-affinity keeps them apart, such as two replicas of a database, so one host failure cannot take both.

Live migration rebalances without downtime: copy a running VM's memory pages to another host, then switch over. Use it on hot hosts, to drain a host before maintenance, and after a scale-out. It spends network bandwidth, so it is not free.

Worked example

Question. A host has 16 vCPU and 64 GB RAM. The provider keeps 20 percent of the vCPU for the hypervisor and does not oversubscribe RAM. Each VM requests 2 vCPU and 8 GB RAM. (a) How many VMs fit on one host? (b) How many hosts are needed for 10 VMs? (c) What is the CPU utilisation (allocation ratio) of that cluster? (d) How many vCPU sit idle, and why?

  1. Usable vCPU = 16 × (1 − 0.20) = 12.8 vCPU.
  2. CPU limit = floor(12.8 ÷ 2) = 6 VMs.
  3. RAM limit = floor(64 ÷ 8) = 8 VMs.
  4. The smaller limit wins: min(6, 8) = 6 VMs per host.
  5. Hosts for 10 VMs = ceil(10 ÷ 6) = 2 hosts.
  6. Allocated vCPU = 10 × 2 = 20 vCPU.
  7. Installed vCPU = 2 × 16 = 32 vCPU.
  8. Utilisation = (20 ÷ 32) × 100 = 62.5 percent.
  9. Idle vCPU = 32 − 20 = 12 vCPU: 6.4 vCPU held as hypervisor reserve (2 × 3.2), 0.8 vCPU stranded on the first host because 12.8 − 12 = 0.8 is too small for one more 2-vCPU VM, and 4.8 vCPU simply unused on the second host because only 4 of its 6 slots are filled.

4.5 Scheduling: policies and mechanisms

A cloud scheduler is built in two layers. The mechanism is the machinery: a queue, an admission test, a timer and a dispatcher that starts work. The policy is the rule that picks the next item from the queue. Keeping them apart lets a provider change from first-come-first-served to a fairness rule without rebuilding the platform. The same split appears when tasks run on a VM, when VMs are placed on hosts, and when user requests enter a data centre. This chapter covers the mechanisms, the common policies, the timing measures used to compare them, and how CloudSim models the parts.

You need: Chapter 4.4 for placement and resource units.

Mechanism, policy and the timing measures

A scheduler has two separable parts. The mechanism holds and moves work: a ready queue, an admission check, a timer and a dispatcher. The policy chooses the next item from the queue. A provider can swap the policy without rebuilding the queue. The same split appears for tasks on a VM, VMs on hosts, and requests entering a data centre.

Three times describe a job. Arrival time is when it becomes ready. Start time is when it first gets the resource. Finish time is when it completes.

wait = start − arrival

start is the time the job first gets the resource and arrival is when it enters the system; this holds when the job runs without preemption.

completion = finish − arrival

finish is the time the job ends; completion time is also called turnaround time.

makespan = last finish − first arrival

last finish is the end of the final job in the set and first arrival is the earliest arrival in that set.

On one machine, a policy can lower average waiting time but cannot reduce makespan when all jobs must run and the machine never idles. Short jobs moved earlier only change who waits.

Policies and when to use them

A policy is chosen for the workload, not for fashion.

  • First-come-first-served runs in arrival order. A long job at the front makes later jobs wait: the convoy effect.
  • Shortest-job-first runs the smallest run time first. It minimises average wait on one machine when all jobs are ready, but needs estimates and can starve long jobs. Shortest remaining time is its preemptive form.
  • Priority runs the highest priority first; aging raises a waiting job so it eventually runs.
  • Round robin gives each job a fixed time slice, called a quantum, so no job waits long: it suits interactive work. Weighted round robin gives each tenant slices in proportion to its weight, so a tenant with double the weight gets double the time.
  • Backfilling lets small jobs fill gaps while a large job keeps its reservation; batch clusters use it to raise utilisation without missing the reservation.
  • Fair share gives each tenant or queue an equal share of the schedulable resource pool (for example memory slots), and unused share is handed to others. Dominant resource fairness (DRF) generalises this to many resource types: it computes each tenant's dominant share and picks the tenant with the smallest one; it fits clusters where tenants need different resources.
  • Earliest deadline first runs the nearest deadline. If no order meets all deadlines, admission control must reject or delay work.
  • Cost-aware scheduling picks the cheapest VM or slot that still meets the deadline; spot capacity is cheaper but can be taken back.

Levels, preemption and CloudSim

Scheduling happens at three levels: user requests to a data centre, VMs to hosts (4.4), and application tasks to a VM.

Preemption stops a running job and returns it to the queue. It needs checkpointing for a process or live migration for a VM. Both cost time and bandwidth; live migration moves memory over the network (Unit 3). A model that ignores this cost reports a schedule that is too good.

A centralized scheduler keeps one queue and one cluster view; it is simple but a bottleneck and a single failure point. A decentralized scheduler lets hosts schedule locally and share load by offers or work stealing; it scales but needs conflict handling.

In CloudSim, a cloudlet has a length in million instructions (MI). A VM has a speed in million instructions per second (MIPS), so run time = length ÷ MIPS. A broker submits cloudlets, applies a policy and receives results from a data centre.

Worked example

Question. Three cloudlets arrive at time 0 on one VM rated 1000 MIPS. P1 needs 3000 MI, P2 needs 600 MI and P3 needs 1200 MI. Compare FCFS with SJF by average waiting time and state the makespan.

  1. Run time = length ÷ MIPS. P1 = 3000 ÷ 1000 = 3 s; P2 = 600 ÷ 1000 = 0.6 s; P3 = 1200 ÷ 1000 = 1.2 s.
  2. FCFS order P1, P2, P3. P1 starts 0, finishes 3 s; P2 starts 3 s, finishes 3.6 s; P3 starts 3.6 s, finishes 4.8 s.
  3. Waiting time = start − arrival and all arrivals are 0, so waits are 0 s, 3 s and 3.6 s. Average = (0 + 3 + 3.6) ÷ 3 = 6.6 ÷ 3 = 2.2 s.
  4. SJF order is shortest first: P2, P3, P1. Starts are 0, 0.6 and 1.8 s; finishes are 0.6, 1.8 and 4.8 s.
  5. SJF waits are 0 s, 0.6 s and 1.8 s; average = (0 + 0.6 + 1.8) ÷ 3 = 2.4 ÷ 3 = 0.8 s.
  6. Makespan = last finish − first arrival = 4.8 − 0 = 4.8 s in both. SJF lowers average wait by 1.4 s but does not change the span.

Answer. FCFS average wait is 2.2 s; SJF average wait is 0.8 s; makespan is 4.8 s for both.

Exam traps

  • Waiting time is not completion time: wait = start − arrival, completion = finish − arrival. In the FCFS lane of the example P1 completes at 3 s but waits 0 s; under SJF it waits 1.8 s.
  • Makespan is last finish − first arrival. On one machine a policy can lower average wait but cannot shrink makespan when all jobs must run.
  • SJF uses total run time; shortest remaining time uses remaining time and can preempt. They differ when arrivals are staggered.
  • Preemption is not free; include checkpoint or live-migration time and bandwidth in the schedule.

4.6 Fault tolerance, replication and business continuity

Fault tolerance is the property that a cloud service keeps working when parts of it break. A cloud never asks whether a server will fail; it assumes failure, detects it with a heartbeat, and moves the work to a replica. Every provider turns that into a promise: a recovery time objective (how long until service returns) and a recovery point objective (how much data may be lost). UPI switches, ticketing sites and payment gateways are built this way, and the promise is what the customer actually buys.

You need: 4.1 for chunks and metadata, 4.2 for replica placement, and 4.3 for quorum reads and writes.

Faults and four kinds of redundancy

Only a few universities teach this chapter in depth. A fault is a defect; a failure is the visible loss of service. Cloud design assumes every disk, server, switch and zone will fail, so it never asks whether, only when.

  • Crash: the node stops silently.
  • Omission: a message is dropped or a step skipped.
  • Timing: the answer arrives too late.
  • Byzantine: the node answers wrongly, sometimes on purpose.

Redundancy is the cure. Hardware redundancy adds a second server. Software redundancy adds a second process or a retry. Time redundancy repeats the operation. Information redundancy adds check bits or extra copies of the data. A second replica on separate hardware buys hardware and information redundancy at once, which is why clouds lean on it.

Detection is the other half. A heartbeat is a small periodic message; the monitor declares a node dead after k missed beats. Large k means slow detection, small k means false alarms.

Replication models and their consistency cost

Primary-backup. One replica, the primary, takes all writes and holds a lease, a time-bounded permission to be primary. It forwards each write to the backups. When the heartbeat stops, the monitor waits for the lease to expire, then promotes a backup. The lease stops two nodes from both believing they are primary.

Quorum. With N replicas a write must reach W of them and a read must contact R. The rule below makes every read set overlap every write set, so a read sees the latest write. With N = 3, W = 3 and R = 1 reads are cheap and writes are slow.

W + R > N

N is the number of replicas; W is the number of replicas that must acknowledge a write; R is the number of replicas a read must contact.

Chain replication. The head takes the write and passes it along a chain; the tail answers reads. Writes stay ordered and reads are cheap, but a mid-chain failure stalls the pipeline.

Multi-master. Every replica accepts writes and merges later: highest availability, weakest consistency. Good for carts and counters, not for balances.

Business continuity: RTO, RPO, backups and drills

Business continuity is fault tolerance written as a customer promise, fixed by two numbers. RTO (recovery time objective) is the longest acceptable time to restore service. RPO (recovery point objective) is the acceptable data loss, measured in time.

Backup types. Full copies everything. Incremental copies changes since the last backup of any kind. Differential copies changes since the last full. Restoring an incremental chain needs the last full plus every increment.

Sites. A hot site runs in parallel and takes over in minutes. A warm site is provisioned but needs current data loaded. A cold site is floor space and contracts; recovery takes days. A runbook is the written recovery procedure; a drill is its rehearsal. An untested runbook is a guess.

Allowed downtime per month = (1 − A) × 43,200 minutes

A is availability as a fraction (99.9% → 0.999); 43,200 = 30 × 24 × 60, the minutes in a 30-day month.

Worked example

Question. A service promises 99.9% availability with RPO 15 minutes and RTO 1 hour. A 30-day month has 30 × 24 × 60 minutes. (a) How much downtime per month does 99.9% allow, and how much does 99.99% allow? (b) Is an hourly snapshot enough for the RPO? (c) What does the 1-hour RTO demand?

  1. Minutes in the month = 30 × 24 × 60 = 43,200 minutes.
  2. 99.9% availability leaves 1 − 0.999 = 0.001 of the month unavailable.
  3. Allowed downtime = 0.001 × 43,200 = 43.2 minutes per month.
  4. For 99.99%: 0.0001 × 43,200 = 4.32 minutes per month.
  5. An hourly snapshot loses up to 60 minutes of data, more than the 15-minute RPO, so snapshot or ship the transaction log every 15 minutes or less.
  6. The 1-hour RTO is a separate requirement: the runbook must restore service within 60 minutes.

Answer. 99.9% allows 43.2 minutes of downtime per month (4.32 minutes at 99.99%), and hourly snapshots break the 15-minute RPO, so snapshots must run at least every 15 minutes.

Exam traps

  • Swapping RTO and RPO: RTO is time to restore service, RPO is data lost measured in time.
  • Calling three replicas a backup. A bad write or a delete reaches every replica instantly; only a point-in-time copy survives human error or corruption.
  • Adding replicas inside one rack or zone: they share a failure domain, so availability does not rise.
  • Breaking the quorum rule: W + R must be greater than N, or a read may miss the latest write.
  • Reading 99.9% as 0.1 minute per month. It is 0.1% of 43,200 minutes = 43.2 minutes.

4.7 Energy-efficient and green cloud computing

A cloud data centre spends most of its electricity on servers that are switched on but mostly idle. The binding cost is power, not CPU seconds, so providers consolidate work, switch idle hosts off and place VMs where power is used best. Power is measured in watts, energy in kilowatt-hours, and PUE compares total facility power with IT power. Only a few universities teach this as a separate chapter.

You need host utilisation and consolidation from Chapter 4.4 and placement and migration decisions from Chapter 4.5.

The idle floor and PUE

A server draws power even at zero load. A common model is:

P = P_idle + (P_max − P_idle) × u

P is power in watts (W); P_idle is power at zero load; P_max is power at full load; u is utilisation, 0 ≤ u ≤ 1 (fraction of capacity used).

With P_idle = 200 W and P_max = 400 W, a server at u = 0.3 draws 200 + 200 × 0.3 = 260 W. That is more than half its peak, so idle servers waste most of the power. Energy is power over time: E = P × t, in kilowatt-hours (kWh), with P in kW and t in hours.

PUE = total facility power ÷ IT power

PUE (power usage effectiveness) is dimensionless; cooling, fans, UPS losses and lighting make it above 1. PUE = 1.5 means 1 kW of IT needs 1.5 kW at the meter.

Techniques: consolidate, sleep, slow down, site

  • Consolidation with live migration. Pack VMs onto fewer hosts, move the rest with live migration, then switch empty hosts off. This removes the idle floor.
  • DVFS and low-power states. Dynamic voltage and frequency scaling lowers CPU voltage and clock when load falls; sleep states cut whole hosts.
  • Power-aware placement. A scheduler that knows each host's power curve chooses the host that adds least watts for the same SLA, not the one with most free RAM.
  • Renewable-aware scheduling. Delay flexible batch jobs to hours when solar or wind supply is high, if the SLA allows.
  • Free cooling and climate siting. Cold climates, outside-air cooling and efficient cooling design lower PUE.

Metrics and the reverse effect

Use energy per transaction, energy per VM-hour and carbon per kWh (gCO₂/kWh). A low PUE and high utilisation give a low energy per VM-hour. The same ideas work in reverse: a badly chosen placement, a heavy replication factor, or keeping replicas on hot idle hosts raises the power bill. See Chapter 4.6 for replication trade-offs.

Worked example

Question. A data centre has 100 servers, each P_idle = 200 W and P_max = 400 W, at 30 percent average utilisation. Cooling gives PUE = 1.5 and power costs ₹8 per kWh. Find monthly energy and cost, then the same after consolidation onto 40 servers at 75 percent. Use 730 hours per month.

  1. 1. Per server: P = 200 + 200 × 0.30 = 260 W.
  2. 2. IT power = 100 × 260 W = 26,000 W = 26 kW.
  3. 3. Monthly IT energy = 26 kW × 730 h = 18,980 kWh.
  4. 4. Facility energy = 18,980 × 1.5 = 28,470 kWh; cost = 28,470 × ₹8 = ₹2,27,760.
  5. 5. After: P = 200 + 200 × 0.75 = 350 W; IT power = 40 × 350 W = 14,000 W = 14 kW.
  6. 6. Energy = 14 × 730 = 10,220 kWh; facility = 10,220 × 1.5 = 15,330 kWh; cost = 15,330 × ₹8 = ₹1,22,640.
  7. 7. Saving = (28,470 − 15,330) ÷ 28,470 × 100 = 46.15 percent.

Answer. Monthly facility energy falls from 28,470 kWh to 15,330 kWh and cost from ₹2,27,760 to ₹1,22,640, a 46.15 percent cut for the same work.

Exam traps

  • Applying PUE in the wrong direction: multiply IT energy by PUE to get facility energy, never divide.
  • Mixing power (kW, an instant) with energy (kWh, over time); the bill is in kWh, so a missing 730 hours is a factor-of-730 error.
  • Using u = 30 instead of 0.30 in the power model, which gives 6,200 W instead of 260 W.
  • Treating power as proportional to load: a 30 percent loaded server draws 260 W here, not 120 W, because the idle floor never disappears.

4.8 Market-oriented clouds, cost models and billing

A market-oriented cloud treats capacity as a priced good. Providers publish prices, users state a budget and deadline, brokers bid or reserve, and a scheduler matches the job to a VM under a service level agreement (SLA). The bill is metered usage multiplied by the price at the provider’s billing granularity. This idea appears in spot markets, reserved instances and enterprise chargeback, where an engineering team must see what its cloud use actually costs.

You need: Unit 1 for cloud economics and roles; Unit 2 for SLAs and usage monitors; 4.4 for capacity and 4.5 for allocation.

The market-oriented reference model

The market-oriented cloud computing (MOCC) reference model makes price and negotiation parts of the system, not a number added after the job runs. It names six core parts: consumer, broker, provider, virtual machine (VM), service level agreement (SLA), and pricing policy. Some versions add an auctioneer or market directory that records offers and matches bids.

  1. Consumer: has a job, a budget, a deadline and a quality target.
  2. Broker: turns the job into requirements, chooses a pricing scheme, negotiates the SLA, and can compare providers.
  3. Provider: owns capacity, sets the pricing policy, and admits the allocation.
  4. VM: is the metered unit; a usage monitor records VM-hours, GB-months and egress.
  5. SLA: states availability, response time, and the credit paid if the provider misses it.
  6. Pricing policy: is the rule that turns capacity and demand into a price: fixed, time-varying, auction, or priority.

Optional in some versions: a market directory or auctioneer that publishes offers, receives bids, and clears the trade.

A pricing policy is the rule that turns capacity and demand into a price: fixed, time-varying, auction, or priority. The broker is the part that makes the cloud a market; without it the user simply accepts a posted rate.

Pricing schemes

A pricing scheme sets what a unit costs and when the provider may take it back. Names vary, but a common seven-way market list is below.

  • Posted price: a catalogue rate per VM-hour or GB-month; the user cannot negotiate.
  • On-demand: a posted price billed only while the resource runs; no commitment.
  • Reserved or subscription: a one- to three-year commitment for a lower rate; capacity is held for the buyer.
  • Spot: spare capacity sold at a dynamic price; cheap, but the provider can reclaim it with short notice.
  • Auction: users bid and the highest bid wins at a clearing price; suits batch work.
  • Bidding and bargaining: the broker negotiates price, deadline and availability together, not one list price.
  • Differentiated or priority: the user pays more for a higher service class, such as guaranteed latency.

Reserved is a commitment, spot is a gamble on spare capacity, and priority is a service class. Mixing these names is a common exam error.

The cost model and the bill

Monthly bill = Σ (compute VM-hours × price per VM-hour) + Σ (storage GB-month × price per GB-month) + Σ (egress GB × price per GB) + licence fees + support fee

VM-hours are running virtual machines multiplied by hours; GB-month is one gigabyte stored for one month; egress is data leaving the provider’s network; licence and support are fixed or per-user charges.

Billing granularity is the smallest unit the provider charges. It may be per second, per minute, per hour, or an hour with a minimum charge. A VM that is running but idle still costs money: 5 percent CPU use does not reduce a VM-hour bill. Total cost of ownership (TCO) compares the cloud bill with an owned data centre: servers, power, cooling, staff, real estate and network. Inside a company, showback reports each team’s cost without charging it; chargeback actually moves money from the team’s budget. If measured availability falls below the SLA, the contract turns the shortfall into a service credit, usually a percentage of the monthly fee.

Worked example

Question. A team runs 2 VMs continuously for a 730-hour month, stores 200 GB and sends 50 GB out of the cloud. On-demand VMs cost ₹6 per VM-hour, reserved VMs cost ₹4 per VM-hour, spot costs ₹2.1 per VM-hour, storage is ₹2 per GB-month and egress is ₹5 per GB.   1. On-demand compute = 2 × 6 × 730 = ₹8,760.
  2. Reserved compute = 2 × 4 × 730 = ₹5,840.
  3. Spot compute = 2 × 2.1 × 730 = ₹3,066.
  4. Storage = 200 × 2 = ₹400.
  5. Egress = 50 × 5 = ₹250.
  6. On-demand total = 8,760 + 400 + 250 = ₹9,410.
  7. Reserved total = 5,840 + 400 + 250 = ₹6,490.
  8. Saving = 9,410 − 6,490 = ₹2,920, which is 2,920 ÷ 9,410 × 100 = 31.03 percent.
  9. Spot total, if all compute were spot, = 3,066 + 400 + 250 = ₹3,716, but spot VMs can be reclaimed.

Answer. On-demand costs ₹9,410; reserved costs ₹6,490, a saving of ₹2,920 or 31.03 percent; spot compute alone is ₹3,066 and all-spot total would be ₹3,716.

Exam traps

  • Quoting a per-hour price as the monthly cost: multiply by hours and by VM count, then add storage and egress.
  • Forgetting data-transfer-out (egress) and storage; these lines often decide the bill.
  • Ignoring minimum billing granularity: a 20-second job billed as one hour is charged 180 times its real duration.
  • Treating reserved and spot as the same discount: reserved is a commitment, spot can be reclaimed.
  • Using list price for TCO without support, licences, idle running VMs and staff.

4.9 Federated clouds and intercloud

A federated cloud lets separate providers lend and borrow capacity under a contract and one common interface. The user signs in once; a broker splits one job across two or three clouds and presents the result as a single service. This is how a video site survives a cricket final, how a batch job finds cheaper machines in another region, and how a small provider earns money from capacity it would otherwise leave switched on and idle.

You need: 4.8 for pricing and brokers, and Unit 2 for SLAs and web-service interfaces.

Four terms that look alike

Multi-cloud means one user picks several providers independently: separate accounts, separate bills, a copy of the data in each. Nothing is agreed between the providers themselves. Hybrid cloud is one organisation's private cloud plus a public cloud, run together, often to burst peak load. Federation is different: two or more independent providers sign a contract, expose the same interface, and share resources, while each keeps its own users and its own ownership. The user then sees one large virtual provider. Intercloud is the wider picture, many clouds and the federations between them, trading capacity across the internet.

The exam test is one question: who signed the agreement? If nobody signed, it is multi-cloud, not federation.

The lifecycle and the stack

A federation runs as a repeating six-step lifecycle, driven by a broker, which is software that acts for the user across providers.

  1. Discovery: every provider publishes machine-readable offers, giving VM sizes, price, location and SLA.
  2. Matchmaking: the broker filters offers against the job's requirements, for example 300 VMs, 4 hours, delay at most 150 ms, data stays in India.
  3. Authorisation and trust: providers verify each other and the user's delegated rights, and the SLA is signed. Identity is federated so the user logs in once (see Unit 6).
  4. Allocation: the partner creates the VMs and returns their addresses to the broker.
  5. Operation: the broker monitors the partner against its SLA and moves work if the partner slips (see 4.6).
  6. Termination and accounting: VMs are destroyed, usage is metered, and the two providers settle between themselves.

The same idea as a stack, bottom to top: physical servers, storage and network inside each provider; the provider interface, the IaaS API that creates and deletes VMs; the cross-provider layer of transport, identity and the signed SLA; the broker doing discovery, matchmaking and monitoring; and finally the user application, which sees one endpoint.

C_total = Σ (u_i × p_i) + D × e

u_i is the units (VM-hours) taken from provider i; p_i is that provider's price in rupees per VM-hour; the sum runs over every provider in the federation; D is the data in GB that leaves a provider; e is the egress charge in rupees per GB.

Architectures and open problems

A centralised broker sees every offer, so matchmaking and pricing are easy, but it is a single point of failure and gives one company a view of everyone's prices. Peer-to-peer federation has providers negotiating directly with no middleman: more resilient, harder to discover and to trust. A third-party broker is the common commercial form, a content-delivery network that rents capacity from several providers and shows the user one name, one DNS entry, one API, so the user never learns which cloud served a request.

  • Trust: competitors must expose capacity to each other; the SLA and the audit trail are the only protection.
  • Data location and law: data sent to a partner in another country falls under that country's law, and many rules require data to stay inside the country.
  • Interoperability: APIs differ, so the broker must translate between them, and every new provider is new code.
  • Cross-provider transfer cost: egress is billed by the sending provider, so cheap compute can be eaten by the data move.

Edge and fog computing are the small end of the same idea: small nearby clouds that federate with one big cloud (see Unit 1).

Worked example

Question. A video site runs 100 VMs of its own in cloud A. For the four hours of a cricket final it expects peak demand of 300 VMs. Partner cloud B offers VMs at ₹5 per VM-hour with delay close to A. Partner cloud C offers ₹4.5 per VM-hour but adds 200 ms to every request. The site allows at most 150 ms of added delay for interactive traffic. (a) How many VMs must it rent? (b) What does each partner cost for the four hours? (c) Which partner does the broker choose, and how much does the site save or lose by that choice?

  1. Peak demand is 300 VMs and 100 are already owned, so rented VMs = 300 − 100 = 200 VMs.
  2. Cost from B = 200 VMs × ₹5 per VM-hour × 4 h = ₹4,000.
  3. Cost from C = 200 VMs × ₹4.5 per VM-hour × 4 h = ₹3,600.
  4. Price difference = ₹4,000 − ₹3,600 = ₹400, so C is 400 ÷ 4,000 = 10% cheaper on raw price.
  5. Delay check: C adds 200 ms, the allowed added delay is 150 ms, so C fails the interactive requirement. B adds about 0 ms and passes.
  6. Decision: interactive traffic goes to B at ₹4,000. If some work is batch and delay-tolerant, the broker can split that part to C and keep the money.

Answer. Rent 200 VMs; B costs ₹4,000 and C costs ₹3,600 for the four hours, but C's extra 200 ms breaks the 150 ms delay budget, so the broker places the interactive job on B at ₹4,000 and may move only delay-tolerant work to C.

Exam traps

  • Calling any use of two providers a federation. Multi-cloud is independent use with no sharing agreement; federation needs a contract, a common interface and trust.
  • Forgetting egress. Cross-provider traffic is billed by the sending provider, so the D × e term can cancel the cheaper partner's advantage.
  • Assuming the lowest price wins. The broker places a VM only after the matchmaking filter, and latency, data location or SLA can remove the cheapest offer.
  • Confusing federation with hybrid. Hybrid is one organisation mixing private and public; federation is between independent organisations.
  • Believing federation needs one central broker. Peer-to-peer federation exists, and it trades a single point of failure for harder discovery and accounting.

Understand Why does the broker matchmake before it allocates? 3 marks

Discovery can return hundreds of offers, and requirements such as price, latency, location and SLA rules remove most of them. Allocating first would mean paying for VMs that already break the SLA, and moving a running job later costs both money and time.

Understand Explain how a cheap partner can become expensive once data moves. 4 marks

The total cost is Σ(u_i × p_i) + D × e. A partner that charges less per VM-hour still charges for data leaving it, and egress is billed per GB. A job that repeatedly ships large datasets pays D × e many times, which can exceed the compute saving.

Apply Use the worked example. If partner C's added delay fell to 100 ms, which partner would the broker choose and how much would the site save over the other? 4 marks

The added delay of 100 ms is inside the 150 ms budget, so C passes matchmaking. C costs 200 × 4.5 × 4 = ₹3,600 against B at ₹4,000, a saving of ₹400, which is 10% of the B price.

Apply A batch job needs 500 VMs for 3 h. The own cloud supplies 150 VMs. A partner sells VM-hours at ₹6. Find the rental cost and the total cost if own VMs are counted at ₹4 per VM-hour. 5 marks

Rented VMs = 500 − 150 = 350. Partner cost = 350 × 6 × 3 = ₹6,300. Own cost = 150 × 4 × 3 = ₹1,800. Total = 6,300 + 1,800 = ₹8,100.

Analyze Compare a centralised broker with peer-to-peer federation: give one advantage and one risk of each. 6 marks

Centralised broker: advantage is global matchmaking and one view of all prices, so placement is near-optimal; risk is a single point of failure and market power, since one party sees every competitor's price. Peer-to-peer: advantage is resilience with no middleman and no shared price book; risk is slower discovery, weaker trust and harder accounting when many pairs settle separately.

Takeaways

  1. Splitting a file into chunks with metadata is what lets a cloud place it on thousands of cheap disks, and that split is what fixes durability, latency and cost.
  2. GFS and HDFS both keep one master holding only metadata and many workers holding three replicas of every chunk, so a dead disk is repaired from a surviving copy.
  3. BigTable is a sorted sparse map indexed by row key, column and timestamp; its order makes range scans cheap and its sparsity means empty cells cost nothing.
  4. Provisioning sizes the pool of capacity, allocation hands each request to a host or VM, and the score of both is the gap between utilisation and the SLA.
  5. Splitting a scheduler into mechanism and policy lets a provider trade fairness for throughput by changing a rule, not by rebuilding the queue and dispatcher.
  6. Fault tolerance is designed, not hoped for: assume failure, detect it, move work to a replica, and state the recovery time and data-loss window.
  7. Idle servers still draw most of their peak power, so consolidation with live migration and DVFS attack the power bill that dominates data-centre cost.
  8. A cloud is a market: published prices, bids from users and brokers, a scheduler matching demand to supply, and a bill that is metered usage times unit price.
  9. Federation lets one job use two providers' capacity through agreed interfaces; multi-cloud means using several providers without any such agreement, and hybrid means mixing private and public.

Exam question bank

Long answers in this unit are rewarded for showing the design trade-off — why the architecture is shaped that way, what it costs, and where it breaks — rather than for listing component names.

Remember and understand

Understand Compare block, file and object storage on the unit of access, the protocol used, typical latency and cost per GB, and give one cloud workload that fits each. 8 marks

Block: raw fixed-size blocks over iSCSI or a virtual disk attach; lowest latency; used for databases and boot volumes; File: named files in folders over NFS or SMB; shared access with locking; used for home directories and general shared content; Object: flat key-value namespace over HTTP, metadata travels with each object; highest throughput per object but no in-place edits; used for backups, images, logs; Rule of thumb: latency and control fall from block to file to object; scale and cost per GB rise in the other direction; State that no single type wins; the access pattern decides.

Understand Explain the GFS/HDFS architecture and trace one file write and one file read through it. 13 marks

One master holds namespace and chunk map in RAM; many chunk servers hold chunks on local disk, typically 64 MB each; Client asks the master for chunk locations; master replies with a list of servers ordered by network distance; Write: client is given a lease holder, data flows along a pipeline of replicas, and success is acknowledged only when all replicas have the chunk; Read: client contacts the nearest replica directly; the master is not in the data path, so throughput scales with the number of servers; Every chunk has three copies on different racks; heartbeats let the master detect a dead server and re-replicate; Why this shape: commodity disks fail often, so software replication is cheaper than expensive hardware; large sequential reads dominate the workload.

Understand Describe BigTable as a data model. Explain row key, column family, timestamp and sparsity, and why rows are kept in sorted order. 13 marks

Model is a map: (row key, column, timestamp) → byte string; nothing else is assumed about the value; Rows are sorted lexicographically by row key and split into tablets that migrate between servers; Column families are created up front and stored and compressed together; new columns inside a family need no schema change; Timestamps keep several versions of a cell; garbage collection keeps the last n or the last t seconds; Sparsity: absent cells take no space, so a very wide table is normal; Sorted order makes range scans by key prefix cheap — the design reason for reversing the domain in row keys so that related items sit together.

Understand Distinguish resource provisioning from resource allocation. Define MIPS and show how MIPS is used to decide whether a host can hold one more VM. 8 marks

Provisioning: deciding total capacity and making it available ahead of time (hosts, VMs, storage, network); Allocation: at request time, choosing which host or VM serves this request; MIPS = million instructions per second; a host has total MIPS and total RAM, and each VM asks for a share; Feasibility test: sum of allocated MIPS ≤ host MIPS and sum of allocated RAM ≤ host RAM, plus bandwidth and storage checks; Oversized provisioning wastes money; undersized provisioning overruns the SLA; the aim is minimum slack consistent with the SLA.

Understand Define scheduling policy and scheduling mechanism, and show how a provider changes one without rebuilding the other. 8 marks

Mechanism: run queue, timer interrupt, context switch, dispatcher — the part that actually moves work onto a CPU or VM; Policy: the rule that selects the next ready item — FIFO, round robin, shortest job first, priority, cost-aware; Same mechanism can run any policy: the queue and dispatcher are unchanged, only the pick function is replaced; Example: switching from round robin to shortest-job-first raises throughput but can starve long jobs; the mechanism is untouched; In CloudSim, the broker and the VM scheduler hold the mechanism and the allocation policy is the pluggable part.

Apply

Apply A 640 MB file is stored with 64 MB chunks and replication factor 3. Compute how many chunks exist in the namespace, how much raw disk is used, and what the system does when one chunk server dies. 10 marks

Chunks in namespace = 640 ÷ 64 = 10; Raw disk = 10 × 64 MB × 3 = 1920 MB, i.e. 1.875 GB for a 640 MB file; Loss of one server loses at most one replica of some chunks; the master sees missing heartbeats and schedules re-replication; Re-replication copies from a surviving replica to a new server until the factor is 3 again; reads continue throughout; Note the overhead ratio 3:1, and that a smaller chunk size would raise the metadata burden on the NameNode.

Apply A service has 10 identical hosts, each carrying 8 VMs of 1000 MIPS. Demand over 24 hours is given in a table. Show how consolidation with live migration reduces the number of powered hosts, and check the SLA after consolidation. 13 marks

Compute total MIPS demanded in each interval and divide by host capacity to get the minimum host count; Compare with the always-on 10-host baseline: the difference is the idle capacity that consolidation removes; Live migration moves a VM with a short pause; it costs network bandwidth and a little CPU on both ends, so migrate during a trough; Check SLA: after consolidation no host should exceed a safe utilisation ceiling, because queueing delay grows sharply near 100 percent; Compute power saved as (hosts removed) × idle power, then add the saving from DVFS on the surviving hosts; State the risk: too aggressive consolidation leaves no headroom for a sudden spike; keep a reserve.

Apply Three providers publish prices and a broker has a job with a deadline. Describe how the broker chooses a provider and how the final bill is computed. 13 marks

List each provider's unit price (per VM-hour or per million instructions), startup delay and transfer cost; Filter providers that can meet the deadline and the SLA; among the rest, rank by total cost; Total cost = compute units × unit price + storage GB-month + data transfer out + any minimum charge; Billing granularity matters: per-second billing and per-hour rounding can differ by a large factor for short jobs; Add the broker's own fee; state who bears the risk if the job overruns the deadline; Mention spot or bid-based pricing: cheaper, but the instance can be withdrawn, so it suits tolerant batch work only.

Apply Design fault tolerance for a service that promises RTO of 15 minutes and RPO of 5 minutes. State the replication, detection and failover steps. 13 marks

RTO = 15 min: longest allowed downtime; RPO = 5 min: most data that may be lost, measured in time; Replication: three copies across racks, plus asynchronous cross-region copy every few minutes to bound RPO; Detection: heartbeats and health checks at a stated interval; a slow detector inflates RTO, a fast one risks false failover; Failover: health check fails → traffic switched by DNS or load balancer to the standby → standby promoted, writes resume; Data: replay the write-ahead log or transaction log; async replication means the last few minutes may need replay, which is exactly the RPO; Test the whole path on a schedule: an untested failover is a guess. Record the measured RTO and RPO afterwards.

Apply A batch job must run in two different clouds owned by different providers. Explain what a third-party broker does, step by step, from submission to billing. 10 marks

User submits the job and constraints to the broker, not to either provider; Broker translates the job into each provider's API through the agreed federation interface; Broker splits the work, places parts according to price, capacity and data location, and moves input data or reads it where it already sits; Broker monitors progress, restarts failed parts on the other cloud, and enforces the SLA; Broker returns one consolidated bill and one status view; the user never opens two accounts; Trust and data-protection terms are agreed between providers in advance, which is what separates federation from ad-hoc multi-cloud.

Analyze and evaluate

Analyze Analyse why GFS and HDFS use a single metadata master. What breaks first as the cluster grows, and what are the mitigations? 13 marks

Single master keeps the namespace consistent without distributed locking and keeps lookups in RAM, so latency is tiny; It removes the master from the data path, so read throughput scales with the number of chunk servers, not with master size; Bottleneck is master RAM: roughly a few hundred bytes per file and per chunk, so billions of small files exhaust it; Second bottleneck is the write path: every new chunk needs a master decision, so creation rate, not bandwidth, saturates; Mitigations: larger chunk size, fewer small files by packing, a read-only shadow master, and federation of namespaces; Newer designs split the namespace across many masters with a table layer; note that they give up the simple single-lock model; Judgement: the design is right for a few large files read sequentially, wrong for a social-media photo store, where object storage wins.

Evaluate Evaluate the trade-off between energy saving and SLA compliance in a green data centre. Use PUE, idle power and DVFS in your answer, and recommend a policy. 13 marks

PUE = total facility power ÷ IT equipment power; a PUE of 1.2 means 20 percent overhead. Lower is better and free cooling is the main lever; Idle servers draw a large fraction of peak power, so many lightly loaded hosts waste far more than one busy host; Consolidation plus live migration raises utilisation and cuts the number of powered hosts, but leaves less headroom for spikes; DVFS cuts power roughly with the cube of voltage; it helps only when the workload is not memory-latency bound; Renewable-aware scheduling shifts deferrable batch work to hours when the grid is clean; interactive work cannot be shifted; Recommendation: consolidate to a safe ceiling, keep a small reserve, use migration only in troughs, and put deferrable jobs where and when energy is cheapest and cleanest; State the metric that decides: energy per completed request at a stated SLA percentile, not energy alone.

Evaluate A team must store 10 million files of about 100 KB each. Evaluate HDFS, object storage and BigTable for this workload and justify a choice. 13 marks

HDFS: one metadata entry per file and per chunk in NameNode RAM; 10 million small files is a memory problem, and a 64 MB block wastes space on a 100 KB file; HDFS read path is built for long sequential reads; many tiny reads mean one master lookup per file — latency dominated by metadata; Object storage: flat namespace, per-object metadata held by the store, scales to billions of keys, HTTP access, no in-place edits; BigTable or a key-value store: good when the file is looked up by key and you want ordered scans by key prefix, and when values are small; Decision rule: size of the object, need for in-place update, need for range scans by key, cost per GB and per request; Recommendation for a photo or document store: object storage with a database index; keep HDFS for large sequential analytical files.

Evaluate "Federation, hybrid cloud and multi-cloud are not the same thing." Analyse the differences in interfaces, billing, trust and failure handling, and say when federation is worth the cost. 13 marks

Multi-cloud: one user, several providers, no agreement between them; the user integrates everything and bills separately; Hybrid: private infrastructure plus one public provider, joined by a secure link and a common management layer; Federation: providers publish agreed interfaces and lend capacity; a broker can place one job across two clouds; Interfaces: federation needs a common API, identity and data-movement standard; multi-cloud needs only per-provider SDKs; Billing: federation can produce one bill through a broker; multi-cloud produces as many bills as providers; Trust: federation requires agreed data-protection and jurisdiction terms before any job runs; multi-cloud leaves this to the user; Failure handling: in federation the broker can restart a failed part elsewhere; without it the user's own orchestrator must; Worth it when peak demand exceeds one provider's capacity or when price differences are large and the job is portable; not worth it for a single short-lived workload.

Glossary

Allocation
Choosing the host or VM that will actually serve a given request or task.
Broker
The component that accepts a user's request, chooses resources under a policy and submits tasks to them.
Chunk
A fixed-size slice of a file that a distributed file system stores, replicates and checksums as one unit.
Cloudlet
In CloudSim, one task with a length in million instructions and a file size, placed in a VM.
Column family
A named set of BigTable columns stored and compressed together, created when the table is created.

The guarantee about what a reader sees after a write; strong consistency makes replicas agree before replying.
DataNode
An HDFS worker process that stores chunks on local disk and serves reads and writes.
Dispatcher
The mechanism component that performs the context switch and puts the chosen item on the processor.
DVFS
Dynamic voltage and frequency scaling, lowering clock speed and voltage when load falls to cut power.
Fault tolerance
The property that the service keeps meeting its promise when a component fails, using detection, redundancy and recovery.
Heartbeat
A periodic short message from a worker to the master saying it is alive; missed heartbeats trigger re-replication.
Hypervisor
The layer that runs virtual machines and divides physical CPU, memory and I/O among them.
Intercloud
The idea of a fabric of interconnected clouds that can exchange capacity and move workloads between each other.
Live migration
Moving a running VM to another host with a pause short enough that users do not notice.
MIPS
Million instructions per second, the capacity unit CloudSim uses for hosts, VMs and tasks.
NameNode
The HDFS master process that holds the file namespace and chunk locations in memory.
Namespace
The tree of file and directory names plus their attributes, kept by the master separately from the data itself.
Provisioning
Making capacity available ahead of demand, in hosts, VMs, storage and network.
PUE
Power usage effectiveness: total facility power divided by IT equipment power; 1.0 is perfect.
Replication factor
The number of copies kept of each chunk, three by default in GFS and HDFS.
RPO
Recovery point objective, the largest amount of data, measured as time, that may be lost in a failure.
RTO
Recovery time objective, the longest allowed downtime after a failure.
Sparse table
A table in which missing cells take no storage, so very wide tables are practical.
Spot instance
Capacity sold at a discount that the provider may reclaim at short notice, suited to tolerant batch work.
Tablet
A contiguous sorted range of BigTable rows that is the unit of distribution and migration.

A software-defined computer with its own vCPUs, RAM and disk, running on a shared physical host.
