2.1 Networks, ISPs and data centre technologies

A cloud region is a set of data centres in one geographic area. Each data centre is a building full of racks, switches, power and cooling. A user reaches it through a chain: phone to local ISP, then transit or peering, then an internet exchange, then long fibre into the region. That physical path sets latency, the time a signal takes, and availability, whether the path and the building stay up. Bandwidth, the bits per second, is a different number. This chapter follows one request into a Mumbai region and then inside to a server rack.

You need Unit 1 for cloud regions and deployment models, and Chapter 2.5 for how traffic is spread once it reaches a region.

From the phone to the region

The user's phone joins an access network. The last mile is the final link from a street cabinet or radio tower to the user; it can be fibre, coax or mobile radio. The local ISP (internet service provider) owns that access network and sells the connection.

ISPs form a hierarchy. A tier 3 ISP is close to users and buys transit from larger providers. A tier 2 ISP covers a region or country and buys some transit. A tier 1 ISP owns a backbone that reaches many countries and usually buys no transit; it swaps traffic with other tier 1 ISPs. Transit is paid carriage: a customer pays a provider to carry its packets to the rest of the internet. Peering is a direct exchange between two networks, often without payment because both gain.

An internet exchange point (IXP) is a building or switch fabric where many ISPs meet to peer. It shortens paths: two networks at the same IXP exchange traffic without crossing a distant transit provider.

Latency is the time for a signal to cross the path, in milliseconds (ms). Bandwidth is capacity, in bits per second. A 1 Gbps link and a 10 Mbps link on the same fibre have the same travel time. Round-trip time (RTT) is the time to go there and back.

Inside the data centre

Some syllabi call this the public cloud infrastructure layer. A data centre is a building engineered for continuous operation. Servers sit in racks, metal frames roughly 2 m tall. Each rack has a top-of-rack (ToR) switch. Servers connect to the ToR by short copper or fibre links. ToR switches connect upward to aggregation switches, and aggregation switches connect to core switches. The core connects the building to long-haul fibre and to other data centres.

Power enters through transformers, switchgear, uninterruptible power supplies (UPS) and power distribution units (PDUs). A UPS carries the load for minutes until generators start. Cooling removes heat because servers turn almost all electrical energy into heat. PUE (power usage effectiveness) is total facility power divided by IT power. IT power is the power drawn by servers, storage and network gear. Total facility power adds cooling, losses and lighting. A PUE of 1.4 means every 1 W of IT needs 1.4 W at the building meter. Lower is better.

PUE = P_total ÷ P_IT

PUE is power usage effectiveness (no unit); P_total is total facility power in W or MW; P_IT is power drawn by IT equipment in the same unit.

Redundancy is described against N, the capacity needed. N+1 has one spare unit, such as one extra UPS or chiller. 2N has two full independent sets, so one set can fail or be maintained while the other carries all load. 2N costs more and uses more space.

A region is a geographic area with one or more data centres. An availability zone (AZ) is an isolated data centre or group of data centres inside a region, with independent power, cooling and network. A region with three AZs can lose one AZ and keep serving. Replicas are placed across AZs; Chapter 2.5 covers the failover.

What sets delay and availability

Distance sets latency, not bandwidth alone. Light in glass travels at about 2×10⁸ m/s, two-thirds of its speed in vacuum. Route length is longer than map distance, so a measured RTT is a better guide than kilometres. A Chennai user talking to a Mumbai region often sees tens of milliseconds, while a farther region adds more.

Bandwidth matters for bulk transfer. A 1 MB page is 8 megabits. At 100 Mbps it takes 80 ms just to serialise, while fibre travel over 1,200 km is 6 ms one way. Both appear in the user's wait.

Availability comes from redundant paths and redundant building systems. One ISP is one failure. A cloud provider peers at IXPs and buys transit from several providers, so one backbone failure does not isolate a region. Inside, N+1 or 2N power and multiple AZs support the availability figure.

Worked example

Question. A Chennai user talks to a Mumbai region 1,200 km away over fibre at 2×10⁸ m/s. The access network adds 5 ms, ISP hops add 2 ms, and data centre switching adds 0.5 ms. Find the one-way delay and the round-trip time. The data centre draws 1.5 MW for IT equipment at PUE 1.4 and pays ₹8 per kWh. Find its monthly energy cost for 730 hours.

  1. Fibre time = 1,200,000 m ÷ 2×10⁸ m/s = 0.006 s = 6 ms.
  2. One-way delay = 6 ms + 5 ms + 2 ms + 0.5 ms = 13.5 ms.
  3. RTT = 2 × 13.5 ms = 27 ms.
  4. IT power = 1.5 MW. Total facility power = 1.5 MW × 1.4 = 2.1 MW.
  5. Monthly energy = 2.1 MW × 730 h = 1,533 MWh = 1,533,000 kWh.
  6. Monthly cost = 1,533,000 kWh × ₹8/kWh = ₹1,22,64,000, about ₹1.23 crore.

Answer. The one-way delay is 13.5 ms, the RTT is 27 ms, the facility draws 2.1 MW, monthly energy is 1,533 MWh (1,533,000 kWh), and the monthly energy cost is ₹1,22,64,000, about ₹1.23 crore.

Exam traps

  • Bandwidth is not latency: a fat link can still be far away. A 1 Gbps link does not shorten the 6 ms fibre hop.
  • PUE is total facility power ÷ IT power. Inverting it gives 0.71 for PUE 1.4, which is wrong.
  • Use one-way distance for one-way delay and double it for RTT. Do not double the distance and also double the time.
  • An IXP is a meeting point, not an ISP. A tier 1 ISP is not the same as a top-of-rack switch.
  • N+1 is one spare unit; 2N is a full duplicate. They are not the same cost or floor space.

2.2 Web technologies and multitenant technologies

Cloud software is a web application before it is anything else. A user types a name, DNS turns it into an address, and an HTTP request carries the user's identity to a server. Multitenancy is how one running stack serves many customers without giving each its own machine. The application keeps tenants apart in rows, schemas, databases, caches and network rules. The path runs from browser to tenant rows; the isolation models and the failures that leak data across tenants follow.

You need: Chapter 2.1 for the client-to-data-centre path, and Unit 1 for SaaS and the cloud reference model.

DNS, HTTP and the stateless web

DNS (Domain Name System) is the phone book of the web. The browser asks a resolver for api.shop.in and receives an A record: the IPv4 address of the host. The record carries a TTL (time to live), for example 60 seconds, so resolvers cache the address for that long. A short TTL helps a provider move traffic after a failure; a long TTL reduces lookup load.

The browser opens a TCP connection and runs a TLS (Transport Layer Security) handshake: ClientHello, ServerHello with the server certificate, key exchange and Finished. Only then does it send HTTP (HyperText Transfer Protocol) over the encrypted channel. A request has a method, a path, headers and an optional body, for example GET /orders HTTP/1.1 with a Host header and a Cookie header. A response has a status code, headers and a body, for example 200 OK, Content-Type: application/json, then JSON such as [{"id":7,"amount":499}]. HTML (HyperText Markup Language) is the same response shape for a page.

HTTP is stateless: the server keeps no memory of an earlier request. Sessions add memory. After login the server sets a cookie, for example sid=abc123. The browser sends that cookie on every later request, and the server maps sid to a user and a tenant. The cookie is a key, so it must be random and protected; HttpOnly and Secure flags stop script access and plain-HTTP leakage.

A web server such as nginx terminates TLS and serves static files. An application server runs business code, calls databases and builds JSON. Chapter 2.3 covers the REST style used by most cloud APIs; Chapter 2.5 covers the load balancer in front.

Multitenancy models and isolation

Multitenancy means one running instance of software, and often one database server, serves many tenants. A tenant is a customer organisation: a company using a CRM (customer relationship management) system, a subscriber on a media stream, a clan in an online game. Sharing saves cost. The provider must still keep every tenant's data separate.

  • Shared database, shared schema: every row has a tenant_id column. A read is SELECT ... WHERE tenant_id = 42. This is the cheapest model and the easiest to leak: one forgotten predicate returns another tenant's rows.
  • Shared database, separate schemas: tenant 42 owns schema t42. Queries name the schema, so a missing predicate is less likely to cross tenants. Migrations must run once per schema.
  • Separate databases: each tenant gets its own database. This gives the strongest separation and the highest cost; regulated data or very large tenants often justify it.

Caches follow the same rule. A key must contain the tenant, for example order:42:7, never order:7. A shared cache also produces noisy-neighbour effects: one tenant's heavy query, cache-miss storm or bulk import slows every other tenant on the same database. Per-tenant rate limits, queues and resource quotas reduce that effect.

A logical network perimeter is the tenant's boundary drawn in software: firewall rules, virtual network segments or policy that lets tenant 42's application reach only tenant 42's database. It is not a separate physical LAN. Some syllabi call this boundary a logical network perimeter. CRM, social feeds, streaming and gaming all use these patterns.

One request from browser to tenant rows

Figure 1 follows a request. The browser looks up api.shop.in and gets an A record with TTL 60. It sends GET /orders with cookie sid. The web server passes sid to the application, which maps it to tenant 42. The application sends SELECT ... WHERE tenant_id = 42 to the tenant database. Two rows come back; the application writes JSON; the web server returns 200 OK.

The index decides the cost. With no index and no tenant filter, the engine scans every row. With an index on (tenant_id, id), it seeks to tenant 42 and reads only that tenant's range. The worked example puts numbers on this difference. The tenant key is checked in the data path, not only at login. A missing tenant predicate in any query, background job or cache key breaks the model. The figure's order matters: identity first, tenant second, data last.

Worked example

Question. A SaaS order table holds 1,000,000 rows shared by 500 tenants. (a) How many rows does a query scan with no tenant filter? (b) With an index on (tenant_id, id), roughly how many rows does one tenant query scan on average? (c) What is the reduction factor?

  1. Total rows N = 1,000,000. Number of tenants T = 500.
  2. (a) No tenant filter means a full table scan: 1,000,000 rows.
  3. (b) Average rows per tenant = N ÷ T = 1,000,000 ÷ 500 = 2,000 rows.
  4. (c) Reduction = N ÷ rows per tenant = 1,000,000 ÷ 2,000 = 500.

Answer. (a) 1,000,000 rows, (b) 2,000 rows on average, (c) 500 times fewer rows.

Exam traps

  • Multitenancy does not mean one machine per customer. One stack serves many tenants; separation is logical, in rows, schemas, caches and network policy.
  • A missing tenant_id in a WHERE clause or in a cache key leaks another tenant's data. The filter and the key are security controls, not performance extras.
  • HTTP is stateless; cookies and sessions store state. A server that appears to remember you is reading a cookie, a token or a server-side session store.
  • A logical network perimeter is policy and routing in software, not a separate physical LAN or a dedicated VLAN for every tenant.
  • DNS TTL is not a request timeout. TTL is how long a resolver may cache an address; a timeout is how long a client waits for a response.

Tenant 43 asking for order 7 can hit tenant 42's cached order, so the cache returns another tenant's data. The fix is to put tenant_id in the key: order:42:7. Test cross-tenant cache hits.

Understand Name the three multitenancy data models and give one cost of each. 4 marks

Beyond the syllabus

Not for the exam. Industry is moving tenant isolation from ad-hoc WHERE clauses to row-level security, policy engines and per-tenant encryption keys. Search for PostgreSQL row-level security, OpenPolicy Agent, and cell-based architecture. Newer curricula discuss tenant units and shuffle sharding to limit blast radius. The same ideas appear in Kubernetes namespaces and service meshes, where policy replaces a physical perimeter.

2.3 Service-oriented architecture, web services and REST

A service-oriented architecture (SOA) builds an application from services. A service is a self-contained program that publishes a contract: named operations, inputs and outputs. Clients call the contract and do not depend on the provider's language or database. SOA exists to reuse business functions and to change one part without breaking others. REST is a lighter style that exposes resources over HTTP; most cloud APIs use it. You meet both in payment APIs, IRCTC booking flows, UPI integrations and cloud storage APIs.

You need: Chapter 2.2 for HTTP verbs, status codes and statelessness.

SOA: contracts, registry and coupling

A service is a self-contained unit of software with a published contract. The contract lists operations, inputs, outputs and faults. A client calls the contract; it never calls the provider's database or internal code.

  • Loose coupling: a client knows only the contract, so a provider can be replaced without editing the client.
  • Abstraction: the contract hides language, database and server details.
  • Reuse: one service, such as a GST calculator, serves many applications.
  • Autonomy: a service owns its data and release cycle.
  • Statelessness: each request carries the information needed, so the service does not rely on an earlier call. Retries and scaling become simpler.
  • Discoverability: a service registry lists available services so consumers can find them.

Classic SOA uses SOAP, an XML message protocol. A WSDL file describes the operations and message shapes; UDDI is a registry standard for publishing and finding services. An enterprise service bus (ESB) sits between providers and consumers and adds routing, message transformation and protocol bridging.

Orchestration uses one coordinator that calls services in a fixed order and handles errors. Choreography has no central controller: each service reacts to events and publishes new events. Orchestration is easier to trace; choreography couples services less.

REST: resources over HTTP

REST is an architectural style, not a protocol. A resource is a thing, such as a payment or a customer. A URI names it, for example /payments/42. A representation is the bytes sent, usually JSON. The client changes a resource by sending a representation to its URI.

  • Client-server: the user interface and data storage evolve separately.
  • Stateless: every request contains all needed context; the server keeps no client session between calls.
  • Cacheable: responses say whether they may be reused, which cuts repeated work.
  • Uniform interface: resources are named by URIs and manipulated through representations with standard methods.
  • Layered system: a client cannot tell whether it talks to the origin server or to a proxy.
  • Code on demand (optional): the server may send executable code, such as JavaScript.

HTTP verbs give the action: GET reads, POST creates, PUT replaces, PATCH partly updates, DELETE removes. Status codes report the result: 200 OK, 201 Created, 400 Bad Request, 404 Not Found, 409 Conflict, 500 Internal Server Error. See Chapter 2.2 for the HTTP basics.

An operation is idempotent if repeating it gives the same effect as one call. GET, PUT and DELETE are idempotent; POST is not, because each POST may create a new record. A safe method does not change the resource; GET is safe. JSON is the common representation because it is compact and easy to parse.

SOAP has built-in standards for security and transactions, but messages are verbose. REST is smaller and uses HTTP caches and proxies well. REST does not force JSON; XML or another representation is allowed.

Microservices are a descendant of SOA: small services, each deployed alone, often with REST/JSON and its own database. They avoid a central ESB and use simple calls or events. Containers make them easy to pack; see Unit 3, Virtualization and Containers.

Choose SOAP when a partner already publishes WSDL and needs WS-Security. Choose REST when you build a public cloud API, a mobile app back end or an internal service that benefits from HTTP caching. The choice is about contract and tooling, not about which is newer.

Worked example

Question. A payment API charges ₹500 per successful POST /payments. A client sends one request; the response is lost. It retries twice with the same Idempotency-Key, so three attempts reach the server. (a) What is debited if the server ignores the key? (b) What if it honours the key and stores the first response? (c) How many replays are returned? (d) The key is kept for 24 hours. A fourth attempt with the same key arrives at 25 hours. What is the maximum total debited then?

  1. Number of attempts = 1 first try + 2 retries = 3.
  2. Without the key, each POST creates a payment: 3 × ₹500 = ₹1,500.
  3. With the key, the server debits once: 1 × ₹500 = ₹500. The other 3 − 1 = 2 attempts are replays of the stored response.
  4. The key lives for 24 hours. The fourth attempt arrives at 25 hours, and 25 > 24, so the key has expired.
  5. The expired key cannot be matched. The server treats the fourth attempt as new: ₹500 + ₹500 = ₹1,000 maximum total.

Answer. Without the key the customer is debited ₹1,500; with the key the first three attempts debit ₹500 and return 2 replays; after the 24-hour key expires, the 25-hour retry can raise the total to ₹1,000.

Exam traps

  • REST is an architectural style, not a protocol; it does not require XML. JSON is common but optional.
  • PUT and DELETE are idempotent; POST is not, so retries need an idempotency key. GET is safe and idempotent.
  • Statelessness means no client session state on the server between requests. The server may still store resources and idempotency records.
  • Orchestration has a central coordinator; choreography has none. An ESB is a messaging backbone, not the same thing as SOA.
  • 404 means the resource is absent; 400 means the request is malformed; 409 means a conflict, such as a duplicate key with a different body.

2.4 Elastic and on-demand computing; automated scaling

Elastic computing adds or removes running capacity as demand changes. On-demand computing means a user can ask for a resource when needed and stop paying when it is released. Together they let a cloud group follow traffic instead of buying for the worst hour. The control loop measures load, compares it with a target, and changes the number of servers inside a minimum and maximum. You meet this in web apps, batch queues and video streaming, where load rises at known times and falls later.

You need chapter 2.1 for data centre capacity, and Unit 4 for provisioning and scheduling policies.

Elasticity, scalability and direction

Scalability is the ability of a system to grow and still work. Elasticity is automatic, demand-driven scaling inside limits. A system can be scalable but not elastic: you can add servers by hand, but nothing reacts to a traffic spike at 9 p.m. Elasticity is the control that uses scalability.

Vertical scaling changes the size of one machine. Scaling up gives a server more CPU, memory or disk; scaling down removes them. This is simple and keeps one address, but it hits a hardware ceiling and often needs a restart. Horizontal scaling changes the number of machines. Scaling out adds servers; scaling in removes them. It needs a load balancer, so see chapter 2.5.

  • On-demand capacity is started for a short period and billed by time used, such as a server-hour. A server-hour is one server running for one hour.
  • Reserved capacity is booked for a long period. It is cheaper per hour but paid even when idle.
  • An elastic group is a set of identical servers managed as one unit, with minimum and maximum size.

N = ceil(L ÷ C)

N is the number of servers (a whole number); L is peak load in requests per second (RPS); C is safe capacity per server in RPS; ceil rounds a value up to the nearest whole number; a value that is already whole stays the same, so 12 stays 12.

The auto-scaling control loop

An auto-scaler is a control loop. It collects metrics, checks a rule or target, changes capacity, waits, then repeats. Metrics are measured numbers such as CPU utilisation (per cent), queue length (jobs waiting) and requests per second (RPS).

  1. Collect metrics from each server and from the group.
  2. Compare the metric with the target, for example 60% CPU.
  3. If load is above target and size is below maximum, scale out. If load is below target and size is above minimum, scale in.
  4. Enforce a cooldown, such as 300 s, before the next change. This is the wait after a scaling action.
  5. Take a server from a warm pool when possible. A warm pool holds stopped servers that can start quickly.
  6. Run a health check before sending traffic. A health check tests whether a server answers.

Minimum and maximum limits cap the group. The minimum keeps spare capacity for failures; the maximum protects cost and downstream systems. Some syllabi call the rule engine an automated scaling listener.

  • Target tracking keeps a metric near a set value, such as 60% CPU.
  • Step scaling adds a larger step when the breach is large.
  • Scheduled scaling changes capacity at a known time, such as a ticket sale.
  • Predictive scaling learns a daily pattern and adds capacity before the rise.

Metrics, policies and failure modes

Choose a metric that moves before users suffer. CPU is easy but lags on I/O-bound work. Queue length shows backlog directly. Requests per second shows arrival rate. Pair it with latency: high latency with high CPU and high RPS means scale out; high latency with low CPU and low RPS means the bottleneck is outside the group (a slow database or downstream service), so adding servers will not help.

Flapping, or thrashing, is rapid scale out and scale in. A cooldown of 300 s after each change stops it. Average CPU can hide one hot instance. Use per-instance CPU metrics to find it; a health check only tells you whether a server responds, not whether it is overloaded. A warm pool reduces boot delay but you still pay for the storage and resources kept ready for the stopped servers.

Scale in slowly. Remove one server at a time and watch latency. If a server is unhealthy, replace it before you count it as spare. Keep logs of every scaling action: time, metric value, old size, new size and reason. Reserved capacity is not elasticity: it is a fixed booking. On-demand capacity follows the peak only when the loop has a correct target and limits.

Worked example

Question. A web app peaks at 600 requests per second for 4 hours. Each server handles 100 requests per second at full load. The target is 60% utilisation, so each server is kept at 60 requests per second. The group keeps a minimum of 2 servers. A server-hour costs ₹9. Assume off-peak load stays below 2 × 60 = 120 requests per second, so the minimum of 2 servers is enough outside the peak. Compare the elastic cost with running 10 servers for the full 24 hours.

  1. Capacity per server at target = 100 × 0.60 = 60 requests per second.
  2. Required servers at peak = 600 ÷ 60 = 10 servers.
  3. Minimum = 2 servers, so extra servers = 10 − 2 = 8 servers.
  4. Base cost for 2 servers for 24 h = 2 × 24 h × ₹9 = ₹432.
  5. Extra cost for 8 servers for 4 h = 8 × 4 h × ₹9 = ₹288.
  6. Elastic total = ₹432 + ₹288 = ₹720.
  7. Fixed cost for 10 servers for 24 h = 10 × 24 h × ₹9 = ₹2,160.
  8. Saving = ₹2,160 − ₹720 = ₹1,440.

Answer. The elastic group needs 10 servers at peak and costs ₹720, against ₹2,160 for 10 servers all day, so the saving is ₹1,440.

2.5 Load balancing, resource replication and high availability

A load balancer is a front door that sends each request to a healthy server. Replication keeps extra copies of data and servers, so one failure does not stop service. Together they give high availability: the service stays reachable for a promised share of time. You meet this in every UPI payment, IRCTC ticket search and video stream: many servers behind one address, and databases with copies in another rack or zone.

You need: Chapter 2.4 for adding instances and Chapter 2.1 for regions and zones.

Load balancing: spreading requests

A load balancer sits between clients and a pool of servers. It accepts one public address and forwards each request to a chosen server. The pool can grow or shrink without clients changing their code. A health check is a small probe, such as GET /health every 5 seconds; a server that fails the probe is removed from the pool until it recovers.

Algorithms use different rules. Define request as one client call. Round robin sends requests in order: 1→Server 1, 2→Server 2, 3→Server 3, then repeats. Weighted round robin gives more turns to stronger servers: weights 3,1,1 send three requests to Server 1 for every one to each of the other two. Least connections sends the next request to the server with the fewest open connections. Least response time uses the fastest recent response. IP hash computes hash(client IP) mod N and sends that client to the same server, where N is the number of servers.

Layer 4 balancing looks only at IP and TCP/UDP ports. It is fast and does not read HTTP. Layer 7 balancing reads HTTP method, path and cookies; it can send /images to an image server and /pay to a payment server. Sticky sessions keep one user on one server by cookie. A shared session store, such as Redis, is better for failover because any server can read the session.

Replication: keeping copies in step

Replication stores the same data on more than one node. A primary-replica setup sends writes to one primary database and copies them to replicas. Read replicas serve read queries; writes still go to the primary. This raises read capacity and keeps a copy for failover.

Synchronous replication waits for the replica to confirm before the write is acknowledged. If the primary dies, the replica has the latest write, but each write costs a network round trip. Asynchronous replication acknowledges at the primary and copies later. It is faster, but a crash can lose the last few writes. Replication lag is the delay between a write on the primary and its arrival at a replica. A read from a lagging replica may miss a just-written value.

Quorum replication needs agreement from a majority. Let N be the number of replicas, W the writes that must confirm, and R the reads that must confirm. If R + W > N, a read set and the latest write set overlap, so the read sees the write. Example: N=3, W=2, R=2 gives 4>3. Quorum tolerates one failed node.

High availability and failover

High availability (HA) means the service is reachable for a large share of time, usually written as a percentage. Availability A is uptime divided by total time. Downtime is 1−A times total time. In series, all parts must work: A_series = A₁ × A₂ × … × Aₖ, where A_i is the availability of part i and k is the number of parts. In parallel, the service works if at least one copy works: A_parallel = 1−∏(1−A_i), where the product covers all parallel copies. For two copies each at 0.99, A_parallel = 1−0.01×0.01 = 0.9999.

Active-passive has one working node and one standby. A failover system detects failure, promotes the standby and moves the address. Active-active has both nodes serving traffic; losing one reduces capacity but not service. Redundancy is the extra copy itself. Failover takes time; recovery time objective (RTO) is the maximum acceptable downtime, and recovery point objective (RPO) is the maximum acceptable data loss. Chapter 2.6 treats SLA targets.

Worked example

Question. Three web servers each have availability 0.99 and sit behind one load balancer with availability 0.999. The servers fail independently, and the service works if the load balancer works and at least one server works. Find the server-group availability, the service availability, and the yearly downtime in 8,760 hours.

  1. For one server, failure probability is 1 − 0.99 = 0.01.
  2. All three fail independently with probability 0.01³ = 0.000001.
  3. At least one server works with probability 1 − 0.000001 = 0.999999. This is the parallel group availability.
  4. The load balancer is in series with the group: A_service = 0.999 × 0.999999 = 0.998999001.
  5. Downtime = (1 − 0.998999001) × 8,760 hours = 0.001000999 × 8,760 = 8.76875124 hours per year, about 8.77 hours.

Answer. Server-group availability is 0.999999, service availability is 0.998999001 (about 99.90%), and downtime is 8.76875124 hours per year (about 8.77 hours); the load balancer is now the bottleneck.

Exam traps

  • Available parts in series multiply; a 99.9% load balancer can cap the whole service below the servers' 99.9999% group.
  • A parallel group is 1 minus the product of failure probabilities, not the sum of availabilities or failure probabilities.
  • Synchronous replication lowers data loss but adds write latency; asynchronous replication can lose recent writes and creates replication lag.
  • Health checks remove a failed server from new traffic; they do not repair it or move its in-memory session unless a shared session store exists.
  • Active-passive failover is not zero downtime; RTO is the allowed recovery time, RPO the allowed data loss.

2.6 Service level agreements: SLAs and SLOs

A service level agreement (SLA) is the written promise a cloud provider makes to a customer. A service level objective (SLO) is the stricter target the provider or team aims for inside that promise. A service level indicator (SLI) is the number actually measured, such as uptime or latency. The gap between SLO and SLA is the warning space: before contract credits are due, the team sees the error budget run out and slows risky releases. This chapter shows how the three fit together, how nines become minutes, and how series services multiply their promises.

You need: availability and replication in Chapter 2.5 and service models in Unit 1.

SLI, SLO and SLA are three different things

A service level indicator (SLI) is the number a system measures. For uptime, the SLI is uptime minutes ÷ total minutes in the window. For an API, it may be successful requests ÷ valid requests. The window is part of the definition: 99.95% over one month is not the same as 99.95% over one day.

A service level objective (SLO) is the target for that SLI. Example: 99.95% of valid API requests succeed in a 30-day window, checked by one-minute probes. An SLO is internal. It guides releases and alerts.

A service level agreement (SLA) is the contract. It names the parties, the service, the metric, the measurement window, exclusions, support, and the credits or penalties if the promise is missed. The SLA is what a customer can claim against; the SLO is the stricter operating target that leaves room before that claim.

A good SLA is measurable by both sides. 'Fast support' is not an SLA. '95% of severity-1 tickets get a human response within 30 minutes, measured monthly' is testable. Exclusions usually cover scheduled maintenance, customer misconfiguration and force majeure.

Nines, allowed downtime and error budgets

Availability is written as a fraction A or a percentage. 99.9% is A = 0.999. The missing fraction 1 − A is the allowed unavailability. Each extra nine makes the allowed failure ten times smaller: 99% is two nines, 99.9% is three nines.

D = T × (1 − A)

D is the allowed downtime in minutes; T is the measurement window in minutes; A is the promised availability as a fraction, so 99.9% is A = 0.999.

For a repairable service, A = MTBF ÷ (MTBF + MTTR), where MTBF is mean time between failures and MTTR is mean time to repair. Cloud SLAs usually measure with probes, not MTBF, but the arithmetic of allowed downtime is the same.

Budget = T × (1 − SLO)

Budget is the allowed failure time in minutes; T is the window in minutes; SLO is the objective as a fraction, so 99.95% is 0.9995.

The error budget is the allowed failure inside the SLO. If the SLO is 99.95%, the budget is 0.05% of the window. When the budget is spent, the team freezes risky changes or adds reliability work. If the SLO is looser than the SLA, the budget is larger than the contract allows, so it gives no early warning before credits are due.

A<sub>total</sub> = A<sub>1</sub> × A<sub>2</sub> × ... × A<sub>n</sub>

Atotal is the availability of the whole chain; A1 to An are the availabilities of services in series, each as a fraction.

For services in series, a request must pass every part, so availabilities multiply. Two 99.9% parts give 0.999 × 0.999 = 0.998001, about 99.8%, not 99.9%. Parallel replicas with failover work differently; see Chapter 2.5. Composite SLA is the product, not the minimum.

Recovery promises, monitoring and reports

Two recovery numbers appear in many SLAs. Recovery time objective (RTO) is the maximum acceptable time to restore service after a failure. Recovery point objective (RPO) is the maximum acceptable data loss, measured in time. RTO 15 minutes and RPO 5 minutes means the service must be back within 15 minutes and may lose at most the last 5 minutes of data. RTO is about downtime; RPO is about data.

Monitoring makes the SLA auditable. Synthetic probes call the service every minute from outside; real-user monitoring records actual request success and latency; logs and incident records explain gaps. The monthly report should show the SLI, the SLO status, the error budget spent, incidents and any excluded time.

Credits are not automatic in most contracts. The customer usually files a claim inside a stated period, and the provider checks the measurement and exclusions. See Unit 4 for billing and cost models and Unit 6 for security clauses and audits. Do not quote one provider's percentage as a universal rule.

2.7 Virtual servers, storage devices and usage monitors

A virtual server is a guest machine on a shared host. Cloud storage is sold as block volumes, object buckets and file shares. A usage monitor samples these resources at fixed intervals and turns the samples into a bill. Together they are the metered units of cloud computing: the customer rents capacity, not a machine. Only a few universities teach this chapter. It explains where a cloud bill comes from, and why a stopped machine can still cost money.

You need: chapter 2.1 for the data centre holding these servers, and chapter 2.4 for why their count changes.

The virtual server as a billed guest

A virtual server, also called a virtual machine or instance, is a guest that borrows CPU, memory and disk from a physical host. The hypervisor enforces the split; Unit 3 covers how. For billing you need three numbers: vCPU count, RAM in GB, and disk in GB. A vCPU is one virtual core, a share of a physical core, not a whole chip. Rates are per unit per hour, such as ₹6 per vCPU-hour, so cost grows with size and with running time. A running instance is charged for its lifetime, usually rounded up to the minute or the hour.

A stopped instance is billed differently. CPU and RAM charges stop, but the disk image keeps billing, because those bytes still sit on the provider's storage.

Storage devices at the billing level

  • Block volume: a raw disk attached to one server, billed per GB-month. A 200 GB volume costs the same empty or full.
  • Object bucket: files reached over HTTP, billed per GB-month plus a charge per request and per GB moved out.
  • File share: a network folder that many servers mount together, billed per GB-month.

GB-month is storage summed over time: 200 GB held for half a month is 100 GB-month. Unit 4 covers how these stores are built.

The usage monitor

A usage monitor, which some syllabi call a metering service, samples each resource at a fixed interval, say every 5 minutes, and writes a record: resource id, timestamp, quantity, unit. Samples per hour = 60 ÷ interval, so a 5-minute interval gives 12 samples an hour.

An aggregator adds samples into hourly or daily totals, because billing works on totals, not on raw samples. Tags are key-value labels such as team=finance that ride on every record. Tags make chargeback possible: each team is billed for what it tagged. Quotas are caps checked against the same live meter, not against the invoice.

cost = Σ quantityᵢ × priceᵢ

quantityᵢ is the aggregated amount in its billing unit (vCPU-hour, GB-month); priceᵢ is the rate in ₹ per unit; the sum runs over all metered resources.

Worked example

Question. A virtual server has 4 vCPU, 16 GB RAM and a 200 GB block volume. It runs for 10 hours and the usage monitor samples every 5 minutes. Rates: ₹6 per vCPU-hour, ₹1.5 per GB-hour of RAM, ₹0.8 per GB-month of disk, with 730 hours in a month. Find the sample count and the total cost.

  1. Samples: 10 h × 60 min ÷ 5 min = 120 samples.
  2. CPU: 4 vCPU × 10 h = 40 vCPU-hours; 40 × ₹6 = ₹240.
  3. RAM: 16 GB × 10 h = 160 GB-hours; 160 × ₹1.5 = ₹240.
  4. Disk: 200 GB × (10 ÷ 730) month = 2.7397 GB-month; 2.7397 × ₹0.8 = ₹2.19.
  5. Total: 240 + 240 + 2.19 = ₹482.19.

Answer. The monitor records 120 samples, and the 10-hour run bills ₹482.19.

Exam traps

  • A stopped VM still bills its disk. Only CPU and RAM charges stop.
  • GB-month is not GB per month. Divide hours held by 730 before you price disk.
  • Host-level meters hide tenants. Without tags you cannot charge back.
  • Rounding changes totals: an hourly rounded meter bills a 61-minute run as 2 hours.

Phone to Wi-Fi or mobile network to local ISP; ISP to regional ISP or backbone; exchange point (IXP) where networks meet; Provider edge router, then load balancer, then server inside the region; Each hop adds delay; distance sets a minimum latency; Any single hop or ISP failure breaks the path, so multi-region and CDN help.

Remember Explain the roles of a load balancer, resource replication and a failover system in a highly available cloud service. 12 marks

Load balancer spreads requests and removes unhealthy backends; Health check: periodic probe, N failures mark a backend out; Replication keeps an identical copy of service or data; Failover switches traffic or promotes a standby copy; Together they remove single points of failure; state must be shared or replicated.

Understand Distinguish between an SLA and an SLO. Give an example of each for a payment API and explain why the SLO is kept stricter. 10 marks

SLA: contract, customer-facing, credit or penalty; SLO: internal target, engineering-facing; Example: SLA 99.9% with service credits, SLO 99.95%; Headroom absorbs measurement noise, maintenance and short incidents; Error budget: the gap between SLO and SLA is the allowed failure.

Remember List the resources a cloud usage monitor typically meters for a virtual server and for block storage, and state the usual billing units. 8 marks

Compute: vCPU-hours or instance-hours, GB-hours of memory; Storage: GB-months of provisioned or used disk; Network: GB out, number of requests; Snapshots and public IP addresses billed separately; Meter records feed the billing system per tenant per period.

Apply

Apply An auto-scaling policy is: if average CPU stays above 65% for 3 minutes, add 2 instances, up to a maximum of 10, with a 5-minute cooldown. Starting from 4 instances, trace the steps for a traffic surge and for the later fall in traffic. 12 marks

Metric window: 3 minutes above 65% triggers one scale-out action; Add 2 instances: 4 to 6; cooldown blocks further actions for 5 minutes; Repeat until 10; the maximum limit caps cost; Scale-in uses a lower threshold so it does not flap; Warm-up time means new instances do not help instantly; state the risk of scaling on a lagging metric.

Apply Design a small REST API for a railway ticket-booking service. Name the resources, the methods and status codes, and explain why the design is stateless. 12 marks

Resources: /trains, /trains/{id}, /bookings, /bookings/{id}; GET to read, POST to create a booking, DELETE to cancel; Status codes: 200, 201, 404, 409 for seat conflict, 400 for bad input; No client session on the server; a token carries identity on every call; Idempotency for retries; versioning of the API.

Apply A service promises 99.9% availability in its SLA and runs to an internal SLO of 99.95%. Calculate the allowed downtime per 30-day month for both, and state the size of the internal error budget. 10 marks

30 days = 720 hours = 43200 minutes; 99.9% allows 0.1% of 43200 = 43.2 minutes; 99.95% allows 0.05% = 21.6 minutes; Error budget for the team = 21.6 minutes; gap to the contract = 21.6 minutes; Discuss that planned maintenance is usually excluded from the SLA count.

Apply Four identical web servers sit behind a load balancer. Describe, step by step, what happens when server 3 stops responding, and what the user sees at each stage. 12 marks

Health check fails after the configured number of attempts; Load balancer removes server 3 from the pool; no new requests go to it; In-flight requests on server 3 fail or time out; retry to a healthy node; Remaining three servers carry the load; capacity check against peak; Server 3 replaced by auto-scaling; it rejoins after passing health checks.

Apply A SaaS product serves 200 small firms. Compare a shared table with a tenant ID column against one schema per tenant for isolation, cost and upgrade effort. 12 marks

Shared table: cheapest, one schema to migrate, needs every query filtered by tenant ID; One schema per tenant: stronger isolation, easier export and delete, many schemas to migrate; Per-tenant database is costlier but suits regulated customers; Noisy neighbour still possible on shared hardware; quotas and rate limits; Migration and reporting complexity named for each option.

Analyze and evaluate

Evaluate A team wants to move an existing SOAP/WSDL service estate to REST APIs. Evaluate the change: what is gained, what is lost, and what should not be migrated. 14 marks

SOA strengths: formal contract, transactions, WS-Security, tooling for typed clients; REST gains: simpler HTTP tooling, caching, mobile and browser friendly, smaller payloads; Losses: formal contract discovery, some reliability and security standards; Criteria for decision: public API versus internal, transaction needs, existing client base; Migration path: wrap old services behind a gateway, move read paths first.

Analyze "Elasticity automatically saves money." Analyse this claim using scaling limits, cooldowns, warm-up time and billing granularity. 13 marks

Elasticity matches capacity to demand, but only between min and max; Cooldown and warm-up cause over-provisioning during fast surges; Billing is often per hour or per second; idle minimum instances still cost; Scaling the wrong metric (CPU for an IO-bound service) misfires; Evaluation: elasticity saves only with correct metrics, right limits and workload that actually varies.

Evaluate A service claims 99.99% availability but depends on one region, one database and one ISP. Evaluate the claim and propose the architecture changes needed to support it. 14 marks

99.99% allows about 4.3 minutes of downtime in 30 days; Single region and single database are single points of failure; Dependency chain: ISP path, provider edge, load balancer, DB; Proposals: replicas across zones, standby in a second region, DNS failover, health checks; Cost and consistency trade-offs; realistic target versus marketing claim.

Analyze Discuss the threats that appear when many tenants share one virtual server pool, and how hypervisors, network isolation and usage monitors reduce them. 13 marks

Tenant isolation at hypervisor level; escape and side-channel risks; Network separation: virtual networks, security groups, per-tenant VLANs; Storage isolation: separate volumes and encryption keys per tenant; Usage monitors detect abnormal consumption and abuse; Residual risk: shared CPU cache, misconfiguration exposing buckets or schemas.

Glossary

Auto-scaling policy
A rule that maps a metric, threshold, window and action into automatic capacity change, bounded by minimum and maximum.
Availability
The fraction of time a service is usable, commonly quoted in nines such as 99.9%.
Availability zone
An isolated data-centre group inside a region, with its own power and network, so a failure in one zone does not take down another.
DNS
The Domain Name System, which resolves a name to an IP address using cached records with a time to live.
Elasticity
Automatic adjustment of capacity to match measured demand within set limits.
Failover
Moving traffic or the active role to a healthy copy after a failure.
Health check
A periodic probe that decides whether a backend should keep receiving traffic.
Horizontal scaling
Adding or removing whole instances rather than making one machine bigger.
HTTP
The request-response protocol of the web, in which a method and URL produce a status code and a body.
Hypervisor
The layer that creates, schedules and isolates virtual machines on a physical host.
ISP
An Internet Service Provider, the company that connects a customer's network to the rest of the Internet.
IXP
An Internet Exchange Point, a shared site where networks exchange traffic directly instead of through a backbone provider.
Latency
The time a request takes to travel to a server and back, measured in milliseconds.
Load balancer
A component that distributes incoming requests across a set of backend servers.
Metering
Recording resource consumption per tenant in measured units so that billing can be calculated.
Multitenancy
Running one copy of software for many customers, keeping each customer's data logically separate.
Region
A geographic area in which a cloud provider runs one or more data centres, chosen for proximity to users or for legal reasons.
Replication
Keeping identical copies of a service or data set so a lost copy can be replaced.
REST
A stateless, resource-oriented style of using HTTP that most cloud APIs follow.
Service contract
The published interface of a service: operations, message formats, endpoint and rules.
SLA
A contract stating the promised service level, how it is measured, and the remedy if it is missed.
SLO
An internal target, stricter than the SLA, used by the team to run the service.
SOA
Service-Oriented Architecture, a style in which loosely coupled services communicate through published contracts.
Statelessness
A property where each request carries all the information needed to process it, so the server keeps no session between calls.
Tenant
One customer or organisation in a multitenant system, identified by a tenant ID attached to its records and requests.
Virtual machine
A software-defined computer with virtual CPU, memory and disk, running on a hypervisor.
