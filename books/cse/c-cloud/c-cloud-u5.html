5.1 Parallel and distributed programming models for the cloud

A cloud program cuts one job into parts that run at the same time on rented machines. The choice of programming model decides how those parts talk and how they fail: shared-memory threads share variables, message-passing processes send packets, data-parallel workers run one function on many slices. Pick the wrong one and you lose either speed or correctness. The same three models sit under a UPI settlement batch, an IRCTC seat-availability search and a startup's log analysis on rented virtual machines.

You need: Unit 1's parallel versus distributed computing, and Unit 2's web services and REST.

Decomposition, granularity and the cost of talking

Decomposition is the first decision: how to cut the job into tasks. Task decomposition gives different work to different tasks. Data decomposition gives the same work to different slices of the data. Splitting 8,000,000 numbers into four slices of 2,000,000 each is data decomposition.

Granularity is the amount of work inside one task. Coarse tasks need little coordination but leave workers idle when the split is uneven. Fine tasks balance better and pay more overhead per unit of work.

Communication is never free. Every message costs latency (the time to start a transfer) plus transfer time. Two threads in one process pass data in nanoseconds. Two virtual machines in one data centre pay tens of microseconds per message.

Synchronization makes tasks wait for each other. A barrier waits for all workers to arrive. A lock lets one thread enter a critical section at a time.

Load balance sets the finish time, because the run ends when the slowest worker ends. Partial failure is the cloud's speciality: a rented machine can vanish mid-task. A distributed program must detect the lost worker and re-run its slice. Threads inside one process die together, so they cannot recover alone.

Four families of parallel models

Shared-memory threads. All threads live in one process and read the same variables. Coordination is fast and the code is simple, but there is only one address space, so the model scales to the cores of one machine and no further. A race condition appears when two threads write the same variable without a lock.

Message passing. Each process has private memory and processes exchange explicit messages; MPI is the classic library. No variable can be read by accident, so the model scales across virtual machines and data centres. The price is writing send and receive calls and designing for messages that never arrive.

Data parallelism. One function is applied to many slices at once and the framework spreads the slices. It suits uniform work such as scoring a million loan applications, and it is the base of MapReduce.

Master-worker. One master hands tasks to idle workers and collects results. Load balancing and retries are natural; the master is the single point of failure.

Concurrency, threads and the speedup limit

Concurrency means several activities are in progress at once. Parallelism means several instructions run at the same instant on different cores or machines. One core can be concurrent (tasks interleaved) but never parallel, so a thread program on a single-core VM is no faster than a plain loop.

S(p) = T(1) ÷ T(p)

S(p) is the speedup with p workers; T(1) is the time with one worker; T(p) is the time with p workers. Efficiency is E = S(p) ÷ p.

S(p) = 1 ÷ (s + (1 − s) ÷ p)

Amdahl's law: s is the serial fraction of the work (0 ≤ s ≤ 1) and p is the number of workers. As p grows, S approaches 1 ÷ s. With s = 0.2 and p = 4, S = 1 ÷ (0.2 + 0.2) = 2.5, not 4.

Coordination is the second ceiling. Thread creation, locks and the final merge all sit outside the parallel part, so they add directly to the finish time.

Multithreading with Aneka threads

Aneka is a middleware platform that runs .NET applications on a cloud of physical or virtual machines. It offers three programming models: Threads, Tasks and MapReduce. Tasks belong to 5.2 and MapReduce to 5.3; here the subject is Threads.

Aneka Threads keeps the familiar thread style. You create a thread object, give it a method to run, and call Start(). The runtime may run that thread on another machine in the Aneka cloud instead of inside your own process. You write thread code that looks local; the platform handles placement, node failure and collection of results.

The cost model changes, because a thread call can become a network call. Tiny thread bodies waste more time in travel than in work, so group the work into coarser threads. Memory is no longer shared either: a remote thread body must receive its input and return its result explicitly.

Worked example

Question. A program adds 8,000,000 numbers. The sequential version takes 160 ms. The parallel version uses four worker threads, each adding 2,000,000 numbers. Creating the four threads costs 5 ms in total and merging the four partial sums costs 5 ms. Find (a) the ideal speedup, (b) the actual speedup and (c) the efficiency. A Python version of the split is below; give its output.

part = [0] * P

  3. Overhead: thread creation 5 ms + merge 5 ms = 10 ms, all of it outside the parallel phase.

  5. Ideal speedup, ignoring overhead: 160 ms ÷ 40 ms = 4×.
  6. Actual speedup: 160 ms ÷ 50 ms = 3.2×.

Exam traps

  • Threads share one address space. They do not by themselves spread a job across virtual machines, so a four-thread program on one VM is still one machine.
  • Concurrency is not parallelism. Ten tasks interleaved on one core finish no sooner than the same ten tasks run one after another.
  • Ideal speedup uses 160 ÷ 40 = 4×; the honest figure adds the 10 ms of coordination and gives 160 ÷ 50 = 3.2×. The examiner looks for which one you reported.
  • Amdahl's law is an upper bound, not a measurement. Load imbalance and coordination can push the real speedup below it.
  • Very fine granularity raises speedup on paper and lowers it in practice, because every task pays latency before it does any work.

5.2 High-throughput and task-based computing

High-throughput computing (HTC) pushes many independent tasks through a pool of workers and counts work finished per hour. A team resizing a lakh of photos overnight cares only about the completed total. Each task is short, needs no other task, and can run on any free worker. The platform keeps every worker busy; an idle worker is lost throughput.

You need Chapter 5.1 for parallel and distributed programming models, especially master-worker.

HTC versus HPC, and the numbers that matter

High-performance computing (HPC) makes one tightly coupled job finish fast, so latency is the target. HTC runs many independent tasks and counts finished work per unit time, so throughput is the target. A bag-of-tasks application is N tasks with no dependencies and no messages: rendering frames, resizing photos, sweeping parameters.

T = N × (t + o) ÷ W

N tasks; t minutes per task on a worker; o minutes of scheduling overhead the worker pays per task; W workers; T makespan in minutes. This holds when N divides evenly by W; otherwise round tasks per worker up.

throughput = N ÷ T

N tasks; T makespan in minutes; throughput in tasks per minute.

Task models and the dependency DAG

A task is the unit of work: input files, one program, output files. In the task-based model the programmer writes the task only; the platform picks a worker, moves files, retries failures, collects results.

When task v needs task u's output, draw edge u → v. All edges form a directed acyclic graph (DAG). Independent tasks are a DAG with no edges. The makespan cannot be shorter than the longest path, the critical path.

Master-worker scheduling fits both. One master holds a queue of ready tasks; each worker takes one, runs it, reports back. If a worker dies the master re-issues that task, so tasks must be safe to repeat. Tasks are kept small, and each worker holds only a small batch at a time, so one slow task delays very little work and the other workers stay busy.

Aneka task-based programming

Aneka is a .NET platform for running .NET and Java applications on a private or public cloud. You describe each task, submit the set to an AnekaApplication, and Aneka's master places tasks on worker nodes. Only a few universities teach this in depth.

  1. Write a task class overriding Execute; read inputs from the task's file data.
  2. Create AnekaApplication with the task type and a config file naming the master.
  3. Add tasks; call AddDependency when one task needs another's output.
  4. Submit and wait; Aneka stages inputs out and results back.
  5. Read results from task objects or output files.

Because the programmer never names a worker, Aneka can grow the pool or move a task after failure without code changes.

Exam traps

  • HTC maximises tasks per minute; HPC maximises speed of one job. Latency questions belong to HPC.
  • Overhead is per task per worker. Total overhead 600 × 0.5 = 300 min of worker-time is only 25 min on each of 12 workers; do not subtract 300 from makespan.
  • Adding workers stops helping when a shared resource becomes the bottleneck: the master that hands out tasks, the shared file store, or the network. Each worker's own ceiling is 1 ÷ (t + o) tasks per minute, and total throughput is W ÷ (t + o) only until some shared stage saturates. The formula T = N × (t + o) ÷ W has no shared-stage term, so it is optimistic.
  • A DAG is not a bag of tasks. With dependencies the makespan cannot fall below the critical path, however many workers you add.
  • Keep units straight: makespan in minutes, throughput in tasks per minute; 2.67 tasks/min is 160 tasks/hour.

5.3 MapReduce programming model

MapReduce is a programming model for data-intensive work on many machines. A map function reads each input record and emits key-value pairs. The system groups all values for the same key in a shuffle, then a reduce function combines each group into a result. The model hides message passing, data movement and machine failures behind two functions. It is used for word counts, log analysis, inverted indexes for search and page-rank style link analysis. Hadoop MapReduce is a widely used implementation.

You need: Chapter 5.1 for parallel models, and Unit 4 for the distributed file system that stores input splits.

Map and reduce functions

A MapReduce job reads input splits. An input split is a chunk of input that one map task can read on its own. The programmer writes two functions, map and reduce. The framework schedules tasks, moves intermediate data and retries failures. Optional functions are a combiner, which pre-combines map output, and a partitioner, which chooses a reducer for each key.

map(k1, v1) → list(k2, v2); reduce(k2, list(v2)) → list(v3)

k1 is the input key, often a byte offset or line number; v1 is the input value, often one line; k2 is the intermediate key; v2 is an intermediate value; v3 is an output value.

  1. Map: read one split and emit (k2, v2) pairs.
  2. Shuffle: group pairs by k2 and sort each group.
  3. Reduce: combine the values for each k2 and write v3.

Map output is intermediate whenever the job has reducers; only reduce output is final. If the job has zero reducers, the map output is the job output.

Shuffle, combiner and partitioner

The shuffle moves map output to reducers and sorts it by key. For one key, a reducer sees a list of all values. In word count, map emits (cat,1) for each cat. With a per-line combiner, shuffle groups cat → [2,1]. The reducer adds 2+1 to get 3.

A combiner is optional. It runs on the map side before the shuffle. It is safe only when its operation is associative and commutative: grouping and order do not change the result. Sum and maximum are safe; a naive average is not, unless you carry both a sum and a count.

The partitioner maps a key to one reducer, usually hash(key) mod R, where R is the number of reducers. All values for a key must reach the same reducer. This rule keeps the reduce result correct, but one hot key can send all its values to one reducer. Adding reducers does not split that key's values. Salting adds a random prefix to hot keys, then a second job combines the partial results.

Fault tolerance and uses

MapReduce tolerates machine failure by re-execution. If a map task fails, the framework reruns it on another machine from the same input split. If a reduce task fails, it reruns using intermediate data that is still available. A slow task may get a speculative copy; the first copy to finish is kept. The programmer writes no recovery code.

Word count is the standard example. Information retrieval builds an inverted index: map emits (term, document id) after parsing each document; reduce collects the postings for each term. Page ranking uses repeated jobs: one job sends link contributions from each page, another sums them per page and applies the damping formula. Hadoop MapReduce is an implementation that runs on a cluster. For iterative page-rank rounds, in-memory frameworks often do better; see Chapter 5.4.

Exam traps

  • Map output is intermediate whenever the job has reducers. The final answer comes only after reduce, so a combiner cannot be treated as the job output.

5.4 Apache Spark and other frameworks

Apache Spark is a cluster computing engine that keeps working data in memory between steps. It stores data as immutable, partitioned collections called RDDs (Resilient Distributed Datasets). A program describes transformations, and Spark records a lineage graph until an action asks for a result. On failure, it rebuilds only lost partitions from that lineage. Spark suits iterative machine learning, log analysis and near-real-time streams. Only a few universities teach this in depth; many stop at MapReduce.

You need: Chapter 5.3 for map, shuffle and reduce, and the distributed storage ideas of Unit 4.

RDDs, laziness and lineage

An RDD is an immutable, partitioned collection spread over executor processes (workers). Every transformation creates a new RDD; actions return a value or write output. Partitions are slices processed by tasks. Transformations (map, flatMap, filter, reduceByKey) only build the plan; no job runs until an action such as collect, count or saveAsTextFile. This is lazy evaluation: no job runs until an action. The driver program (the process running main()) then schedules stages, cutting the lineage DAG (directed acyclic graph) at shuffles. A shuffle moves all pairs with the same key to one partition; reduceByKey needs it, map does not.

Lineage is the record of transformations. If a partition is lost, Spark recomputes it from its parents instead of reading a replica. Long lineage slows recovery, so checkpointing writes an RDD to reliable storage and truncates the graph. cache() uses executor memory; persist() can use memory, disk or both. Both are lazy. For memory-only storage, partitions that do not fit are evicted and recomputed; MEMORY_AND_DISK spills to disk instead.

DataFrames, streams and graphs

DataFrames add named columns and a schema to RDDs. Spark SQL's Catalyst optimizer rewrites queries, so DataFrames usually beat raw RDDs on structured data.

Spark Streaming cuts a live stream into micro-batches at a fixed interval, such as 1 second. Each batch is an RDD; a DStream (discretized stream) is the sequence. Latency is seconds, not milliseconds.

GraphX runs graph algorithms on Spark: vertices and edges are RDDs, and vertex programs exchange messages. GraphLab is a separate distributed graph framework with update functions over vertices and edges; it allows asynchronous execution.

MapReduce writes map output (intermediate data) to local disk before the reduce phase within a job, then follows a fixed map-shuffle-reduce plan. Spark keeps cached data in memory, plans a general DAG, and reuses RDDs across iterations. MapReduce stays simple for one-pass batch jobs; Spark wins on iterative and streaming work.

Exam traps

  • Transformations are lazy; no Spark job runs until an action such as collect() or count().
  • collect() moves every result to driver memory and can crash it; use take() or save output to storage.
  • cache() uses executor memory; persist() can use memory, disk or both. Both are lazy. For memory-only storage, partitions that do not fit are evicted and recomputed; MEMORY_AND_DISK spills to disk instead.
  • reduceByKey aggregates before the shuffle; groupByKey shuffles every value. For sums and counts, reduceByKey is cheaper.
  • Long lineage slows recovery because more parent stages must be rerun; caching does not shorten lineage, checkpointing does.

5.5 Amazon Web Services: compute, storage and communication

Amazon Web Services (AWS) sells cloud computing as separate building blocks you rent one at a time. EC2 gives you virtual machines, EBS gives each machine a disk, S3 stores files as objects, a VPC gives your machines a private network with subnets and firewalls, and SQS or SNS carries messages between parts of your system. You assemble these pieces into an application instead of buying a server. Most Indian startups, banks and government portals run at least part of their stack this way, paying by the hour or by the gigabyte.

You need: Unit 1 service models (IaaS, PaaS) and Unit 2 load balancing and high availability; see 5.1 for how the parts communicate.

EC2: a virtual machine you rent

EC2 (Elastic Compute Cloud) rents you a virtual machine, called an instance. A hypervisor on AWS hardware boots it from an image, so you get a fresh Linux or Windows machine in about a minute (Unit 3 covers the hypervisor layer). You pay for the time it runs.

An AMI (Amazon Machine Image) is the template: an operating system, some preinstalled software, and disk snapshots. Ten instances launched from one AMI are identical. An instance type names the hardware size, for example t3.micro or m5.large. The letter is the family — t for burstable general purpose, m for balanced, c for compute-heavy, r for memory-heavy — and the size after the dot sets vCPUs and RAM.

  1. Pick an AMI, for example Amazon Linux.
  2. Pick an instance type and a subnet.
  3. Choose or create a key pair; the private key file is your SSH login.
  4. Attach a security group that allows SSH on port 22 from your own address only.
  5. Set the root EBS volume size and launch.
  6. Connect with: ssh -i key.pem ec2-user@<public-ip>.

An instance moves through pending, running, stopped and terminated. A stopped instance keeps its disk and loses its public IP; a terminated one is gone. Tag every instance with Name, Owner and Environment, or a bill listing forty instances becomes unreadable.

EBS and S3: two kinds of storage

EBS (Elastic Block Store) is a virtual hard disk. You attach a volume to one instance in the same Availability Zone, format it with a filesystem, and read and write fixed-size blocks. The operating system cannot tell it from a local disk. The volume outlives the instance.

S3 (Simple Storage Service) stores objects. An object is a byte sequence plus metadata, kept in a bucket under a key such as photos/chennai-2024/IMG_0412.jpg. Bucket names are globally unique. You PUT and GET whole objects over HTTPS; there is no seek and no partial write. S3 copies each object across devices and zones for very high durability.

Rule of thumb: anything a program opens as a file lives on EBS; anything a user uploads or downloads lives in S3.

VPC, subnets and security groups

A VPC (Virtual Private Cloud) is your own network inside AWS. You choose its address range in CIDR form, for example 10.0.0.0/16, which holds 2¹⁶ = 65,536 addresses. Nothing outside reaches in unless you allow it.

A subnet is a slice of that range pinned to one Availability Zone. A /24 subnet such as 10.0.1.0/24 has 2⁸ = 256 addresses; AWS reserves 5 in every subnet, so 251 are usable by instances.

A route table decides where packets from a subnet go. A subnet is public only when its route table sends 0.0.0.0/0 to an internet gateway and the instance has a public IP. A private subnet has no such route; it reaches the internet, if at all, through a NAT gateway.

A security group is a stateful firewall on an instance. You write allow rules only: port, protocol, source. Replies to allowed traffic return automatically — that is what stateful means. A network ACL is the stateless filter at the subnet edge. An Application Load Balancer sits in front of the web instances, ends TLS on port 443, and health-checks each target.

SQS, SNS and CloudWatch

SQS (Simple Queue Service) is a durable message queue. A producer sends a message; a worker polls, processes, and deletes it. While a worker holds a message it is invisible to others for the visibility timeout; if the worker dies, the message reappears. Delivery is at-least-once, so make processing idempotent.

SNS (Simple Notification Service) is publish/subscribe. You publish to a topic and every subscriber gets a copy — an email, an SMS, an SQS queue, a function. Use SQS when one worker should take each job, SNS when many listeners should hear each event.

CloudWatch collects metrics such as CPUUtilization, keeps logs, and fires alarms. An alarm can add instances to an Auto Scaling group or publish to an SNS topic. Auto Scaling holds a group at a target count and replaces unhealthy instances; a launch template says which AMI and instance type the new ones get.

Worked example

Question. A web application needs 2 web servers, 1 database server, 100 GB of user images and a job queue. Design it on AWS using VPC 10.0.0.0/16, public subnet 10.0.1.0/24 and private subnet 10.0.2.0/24. State the usable addresses per subnet, where each resource sits, and which traffic flows are allowed.

  1. 10.0.0.0/16 gives 2^(32−16) = 65,536 addresses. Each /24 gives 2^(32−24) = 256 addresses.
  2. AWS reserves 5 addresses per subnet, so 256 − 5 = 251 usable in each subnet, 502 across both.
  3. Public subnet 10.0.1.0/24 holds the 2 web EC2 instances and the Application Load Balancer. Its route table sends 0.0.0.0/0 to the internet gateway.
  4. Private subnet 10.0.2.0/24 holds the 1 database EC2 instance. Its route table has only the local route, so no direct internet path.
  5. The 100 GB of images goes to 1 S3 bucket and the jobs go to 1 SQS queue. Both are regional services outside the VPC, reached over their HTTPS endpoints.
  6. web-sg: inbound 443 from 0.0.0.0/0, inbound 22 from the admin address. db-sg: inbound 3306 with source = web-sg (a group reference, not a CIDR block).
  7. Total EC2 instances = 3. Flows allowed: user → 443 → load balancer → web; web → 3306 → database. A direct internet → 3306 → database attempt matches no rule and is dropped.

Answer. 251 usable addresses in each subnet (502 in total), 3 EC2 instances (2 web in 10.0.1.0/24, 1 database in 10.0.2.0/24), a 100 GB S3 bucket and one SQS queue, with port 443 open from the internet to the web group and port 3306 open only from the web group to the database group.

Exam traps

  • A security group is not a subnet. It is a stateful firewall on an instance's network interface; the subnet-level filter is the network ACL, which is stateless.
  • S3 is object storage. You cannot mount it as a block disk and run a database on it; a filesystem needs EBS, whole objects are PUT and GET.
  • A subnet is public because of its route table, not its name. Without a 0.0.0.0/0 route to an internet gateway it stays private even if an instance has a public IP.
  • An EBS volume lives in one Availability Zone and cannot attach to an instance in another zone. Snapshot it, then create the volume from the snapshot in the new zone.
  • Stopping is not terminating. A stopped instance keeps its EBS volume and data; a terminated instance deletes the root volume by default.

5.6 Google App Engine and Google Cloud Platform

Google App Engine is a managed platform as a service (PaaS): you upload code, and Google runs it, scales it and patches the servers underneath. Google Cloud Platform (GCP) is the wider family around it — virtual machines, disks, object storage, messaging and monitoring, all held inside a project. App Engine suits a web app that must absorb sudden traffic without a capacity plan; Compute Engine suits software that needs a whole machine. This chapter covers both and ends by comparing App Engine with AWS EC2.

You need: Chapter 5.5 for the modular AWS picture, and Unit 2 (elastic and on-demand computing, automated scaling) for the scaling idea.

App Engine: a PaaS that runs your code

App Engine runs your source code on Google's machines. You never see the operating system, the load balancer or the patch schedule. You pick a runtime, write handlers that answer HTTP requests, and deploy; App Engine creates instances, adds them when traffic rises and removes them when traffic falls.

There are two environments, and the exam expects you to tell them apart.

  • Standard: code runs in a sandbox with fixed runtimes (Java, Python, Go, PHP, Node.js). It starts in milliseconds, scales to zero instances when idle, cannot write to local disk (use Cloud Storage instead), and has per-request time limits.
  • Flexible: your app is packaged as a container and runs inside a Compute Engine VM. Any runtime, native libraries, background threads and SSH are allowed. Start-up is slower and at least one instance stays running, so it never reaches zero.

Both scale automatically. You set a target CPU utilization, a maximum instance count and, if you wish, a maximum number of concurrent requests per instance. The scheduler compares measured CPU with the target and adds or removes instances.

N = ⌈ R × c ÷ (60 × u) ⌉

N is the number of instances needed; R is the request rate in requests per minute; c is the CPU time of one request in CPU-seconds; u is the target utilization as a fraction (0.5 means 50%); 60 is the CPU-seconds per minute one instance supplies at 100% utilization.

The request path is short. A client sends HTTPS to the App Engine front end, which terminates TLS, routes by service and version, load-balances, and forwards to one or more instances. Anything slow is pushed to Pub/Sub instead of being done inside the request.

Projects, Compute Engine and VPC firewall rules

Every GCP resource lives inside a project. A project holds the resources, the billing account and the list of enabled APIs; you enable the Compute Engine API before creating a machine. Projects sit in folders, and folders sit in an organization, so one policy can cover many projects. Identity and access control at these levels is in Unit 6, Identity and access management.

  1. Choose a region and zone; the zone decides which data centre holds the machine (for example asia-south1-a for Mumbai).
  2. Choose a machine type, which fixes vCPUs and memory (e2-small gives 2 vCPUs and 2 GB of RAM).
  3. Choose a boot image: a public image such as Debian or Ubuntu, or a custom image you built earlier from a disk. An image is a read-only template; a snapshot is a copy of one disk.
  4. Attach the instance to a VPC network and give it a network tag such as web.
  5. Open the ports it needs with a firewall rule, then connect over SSH.

Firewall rules belong to the VPC network, not to the instance. Each rule states a direction (ingress or egress), an action (allow or deny), a source or destination range in CIDR form, a protocol and port, and a target. The target is a network tag or a service account, so a rule whose target tag is web applies only to instances carrying that tag. GCP denies incoming traffic and allows outgoing traffic by default, so a fresh web server answers nothing until you add an allow rule for tcp:80 and tcp:443.

Cloud Storage, Pub/Sub and Cloud Monitoring

Cloud Storage keeps objects in buckets. A bucket name is globally unique and an object is named by a key such as photos/2024/chennai.jpg. Objects are immutable: to change one you upload a replacement. Pick a storage class — Standard, Nearline, Coldline or Archive — by how often you read the data; colder classes cost less to store and more to read. Buckets hold static files, backups, and the uploads an App Engine standard instance cannot keep on local disk.

Pub/Sub is the messaging service. A publisher sends a message to a topic; each subscription on that topic gets a copy; a subscriber pulls messages or receives them pushed to an endpoint. Delivery is at-least-once, so the subscriber must tolerate a duplicate. Use it to move slow work — sending email, rendering a PDF, calling a payment gateway — off the request path, so the user waits 30 ms instead of 3 s.

Cloud Monitoring collects metrics such as instance CPU, request latency and instance count, draws dashboards and fires alerting policies when a metric crosses a threshold. Uptime checks probe your URL from several regions. Logs go to Cloud Logging, where you filter by severity and set log-based alerts.

App Engine PaaS against EC2 IaaS

EC2 gives you a virtual machine; you install OS updates, the runtime and an Auto Scaling group. App Engine gives you a runtime; Google does that work. The trade is control for convenience.

Worked example

Question. An App Engine standard service receives 900 requests per minute. Each request needs 30 ms of CPU time. The operator sets the target CPU utilization to 50%. One instance supplies 60 CPU-seconds per minute at 100% utilization. (a) How much CPU time per minute does the traffic need? (b) How much does one instance supply at the target? (c) How many instances are required? (d) Repeat (c) if traffic doubles to 1,800 requests per minute.

  1. Convert one request's CPU time to seconds: c = 30 ms = 0.030 CPU-s.
  2. Demand at 900 requests/min: 900 × 0.030 = 27 CPU-s/min.
  3. Capacity of one instance at the 50% target: 60 × 0.50 = 30 CPU-s/min.
  4. Instances needed: N = ⌈27 ÷ 30⌉ = ⌈0.9⌉ = 1 instance.
  5. At 1,800 requests/min: 1,800 × 0.030 = 54 CPU-s/min of demand.
  6. N = ⌈54 ÷ 30⌉ = ⌈1.8⌉ = 2 instances.
  7. Check the trap: dividing by the 100% figure 60 would give ⌈27 ÷ 60⌉ = 1 and ⌈54 ÷ 60⌉ = 1, which under-provisions the doubled load.

Answer. One instance carries 900 requests/min at a 50% CPU target; 1,800 requests/min needs 2 instances.

Exam traps

  • Standard App Engine is a sandbox, not a raw VM: no SSH, no root, no local disk writes. Flexible runs your container inside a Compute Engine VM — do not write 'App Engine gives you a VM' without saying which environment.
  • Size instances at the target utilization, not at 100%. Using 60 CPU-s/min with a 50% target halves your answer and under-provisions.
  • Take the ceiling, not the round: 1.8 instances means 2 instances, because a fractional instance cannot serve traffic.
  • Cloud Storage objects are replaced whole, never edited in place, and the bucket name is globally unique across all of GCP — a name taken by someone else cannot be reused.
  • A VPC firewall rule with a target tag applies only to instances carrying that tag, and ingress is denied by default; exam questions love an instance that 'has a web server' but no allow rule.

5.7 Microsoft Azure

Microsoft Azure is a public cloud from Microsoft. Its central idea is grouping: a subscription holds resource groups, and a resource group holds related resources. A virtual network connects the virtual machines inside it, and reaches a database through a private endpoint when you configure one. Blob storage normally sits outside the virtual network: clients reach it over its public endpoint unless you add a private endpoint. Network security group rules decide which traffic may enter each subnet. Azure is used for lift-and-shift Windows and Linux servers, managed web apps, SQL databases and blob storage. This chapter shows how the pieces fit and how a small web-and-database system is deployed.

You need Chapter 5.5 and Chapter 5.6 for the comparison, and Unit 3 for virtual machines.

Subscriptions and resource groups

An Azure subscription is the billing and quota boundary. Every resource belongs to one subscription, and the bill and most quotas are counted there. One subscription can hold many resource groups.

A resource group is a logical container for resources with a shared lifecycle. It is not a region. The group stores metadata; the virtual machines inside may run in different Azure regions. Deleting the group deletes every resource in it, so keep production and test in separate groups. An Azure Resource Manager template treats the group as one deployment unit: it creates or updates all described resources together.

Tags are name-value pairs such as cost centre = hostel. They help billing reports, not access control; role-based access control handles that (see Unit 6).

Virtual networks, subnets and NSG rules

A virtual network (VNet) is a private IP address space in one region. You divide it into subnets, which are ranges of addresses. Resources in one subnet reach each other by default.

Azure reserves five addresses in every subnet: the first four and the last. In 10.0.1.0/24, usable addresses run from 10.0.1.4 to 10.0.1.254, giving 256 − 5 = 251 usable addresses.

A network security group (NSG) is a set of rules attached to a subnet or network interface. Each rule has a priority from 100 to 4096, a source, destination, port, protocol and allow or deny action. Azure checks from the lowest priority number upward and stops at the first match. A deny at priority 100 beats an allow at priority 200. Rules are stateful: reply traffic for an allowed connection passes automatically.

Default rules allow traffic inside the VNet and from the Azure load balancer, and deny inbound internet traffic. For a web tier, add an allow rule for TCP 443 from Internet to the web subnet. For the database tier, allow TCP 1433 only from 10.0.1.0/24. Then the web VMs face the internet and the database does not.

Compute, storage and databases

Azure Virtual Machines are IaaS compute. You choose a size (vCPU count, memory, local disk), an image and disks. An image is a template: a marketplace image such as Ubuntu or Windows Server, or a custom image. A generalized image has machine-specific data removed; a specialized image keeps it. Managed disks serve as OS and data disks.

Availability sets group VMs into fault domains (separate power and network) and update domains (separate maintenance batches). Availability zones are separate physical data centres in one region; a zone-redundant service survives one zone failing. Use zones for new designs, sets where zones are unavailable.

Azure Storage offers four services: Blob, Files, Queue and Table. Blob stores objects in containers: block blobs for files, page blobs for virtual hard disks, append blobs for logs. Blob access tiers are hot, cool, cold and archive; colder tiers cost less to store and more to read. Files gives SMB or NFS shares. Queue carries messages between components. Table stores key-value rows. Disk gives managed block disks to VMs. Blob is not a file system: you read and write whole objects through the REST API or SDK, not by mounting it as a drive.

Azure SQL Database is a managed relational database; Microsoft runs patching and backups. SQL Server on a VM is IaaS: you manage the operating system and engine.

Deployment path and comparison

  1. Create resource group rg-web-prod in Central India.
  2. Create VNet 10.0.0.0/16 with web subnet 10.0.1.0/24 and DB subnet 10.0.2.0/24.
  3. Create NSGs: allow TCP 443 from Internet to web; allow TCP 1433 from 10.0.1.0/24 to DB.
  4. Create two web VMs from an image in an availability set or zones, attached to the web subnet. Or deploy an App Service web app, which is PaaS and needs no VM patching.
  5. Create Azure SQL Database and a 100 GB Blob container.
  6. Enable Azure Monitor: metrics, activity log, diagnostic settings to a Log Analytics workspace, alert rules. Azure Automation runbooks can start or stop VMs on a schedule.

AWS uses VPC, security groups, EC2, S3, RDS and CloudWatch. Azure uses VNet, NSGs, VMs, Blob, Azure SQL and Monitor. Google Cloud uses a global VPC, firewall rules, Compute Engine, Cloud Storage, Cloud SQL and Cloud Monitoring. Names differ; the pattern of network, compute, storage, database and monitoring is the same.

Worked example

Question. A resource group holds a VNet 10.0.0.0/16, web subnet 10.0.1.0/24 with 2 web VMs, DB subnet 10.0.2.0/24 with Azure SQL Database, a 100 GB Blob container, and one NSG on each subnet. Exam traps

  • A resource group is logical, not a region. Its resources may sit in different regions; deleting the group deletes all of them.
  • NSG rules are ordered by priority, lowest number first, and stop at the first match. A later allow rule cannot override an earlier deny.
  • Blob storage is object storage, not a mountable file system, and it sits outside the VNet by default. Use Azure Files for an SMB share and managed disks for VM disks.
  • An availability set is inside one data centre; an availability zone is a separate data centre in the same region. They solve different failure sizes.
  • Azure SQL Database is PaaS: Microsoft patches it. SQL Server on a VM is IaaS: you patch the guest operating system and database.

5.8 Open-source platforms: Eucalyptus, OpenStack, OpenNebula

An open-source IaaS platform turns a rack of physical servers and their hypervisors into a private cloud. It gives users a web dashboard, an API, virtual machine images, networks and storage volumes, without a public-cloud bill. Eucalyptus copies the Amazon EC2 and S3 APIs, OpenStack splits the work across named services, and OpenNebula uses a small front end with hypervisor drivers. Indian campuses and companies use these platforms when data must stay on site or when a public cloud is too costly for steady workloads.

You need: service models from Unit 2 and hypervisors from Unit 3, plus the AWS building blocks in 5.5.

OpenStack: services that form one cloud

OpenStack is not one program. It is a collection of services that share an identity system and a message queue. Keystone authenticates users and issues tokens; every other service checks a token before acting. Nova manages virtual machines: it receives a request, picks a host, and asks the hypervisor to start the VM. Neutron supplies virtual networks, subnets, routers and security groups. Cinder gives block volumes that attach to one VM like a disk. Swift is an object store for files reached by HTTP, not a mounted disk. Glance stores VM images, and Horizon is the web dashboard.

Packages come from Linux distributions or deployment tools. A small install needs a database, a message queue, Keystone endpoints, and then the chosen services. You register images, define networks, create flavors, and launch instances.

usable vCPU = (H − r) × C

H is the number of physical hosts; r is the number of hosts reserved for control-plane services; C is vCPU per host.

usable RAM = (H − r) × M

M is RAM per host in GB.

VMs = min(⌊usable vCPU ÷ vCPU per VM⌋, ⌊usable RAM ÷ RAM per VM⌋)

⌊⌋ rounds down to a whole VM; min takes the smaller of the two limits.

Eucalyptus: an AWS-compatible private cloud

Eucalyptus is an open-source private cloud that exposes Amazon-compatible APIs. A Cloud Controller (CLC) is the entry point and makes scheduling decisions. Walrus provides S3-compatible object storage. The Storage Controller (SC) manages EBS-like block volumes. A Cluster Controller (CC) manages a group of nodes and their network. A Node Controller (NC) runs on each physical host and controls the hypervisor, usually KVM or Xen. An optional VMware Broker connects to vSphere.

Because the API matches EC2 and S3, existing AWS tools and code can point at a Eucalyptus cloud by changing the endpoint URL. The match is at the API level; behaviour, supported features and limits can differ. Test before migrating.

  1. Install CLC, Walrus, SC and CC on management hosts.
  2. Install NC on every physical node.
  3. Configure network ranges and register nodes and images.
  4. Create user credentials and test EC2 and S3 calls.

OpenNebula, CloudStack and choosing a platform

OpenNebula uses a front end: a host with the oned daemon and a database. Sunstone is its web interface; the CLI and XML-RPC API do the same work. Drivers connect the front end to hypervisors such as KVM, Xen and VMware, to storage datastores, and to virtual networks. A host runs a small node package; the front end schedules VMs onto hosts. Images and templates define what to start.

Apache CloudStack is another open-source IaaS platform. It groups hosts into clusters and pods, offers a management UI and an API, and supports KVM, XenServer and VMware. It suits teams that want a simpler install and a single management server.

All four platforms need the same first decisions: hypervisor, network ranges, image storage, and user authentication. A test install can run on one host with nested virtualization; production spreads control-plane services over at least three hosts. Reserve control-plane capacity, because those hosts still consume CPU and RAM.

Worked example

Question. A private cloud has 8 hosts. Each host has 32 vCPU and 128 GB RAM. Reserve 1 host for the control plane. Each VM needs 4 vCPU and 8 GB RAM. At 1:1 CPU overcommit, how many VMs fit? At 2:1 CPU overcommit? RAM is not overcommitted.

  1. Usable hosts = 8 − 1 = 7 hosts.
  2. Usable vCPU = 7 × 32 = 224 vCPU.
  3. Usable RAM = 7 × 128 = 896 GB.
  4. At 1:1, CPU allows ⌊224 ÷ 4⌋ = 56 VMs. RAM allows ⌊896 ÷ 8⌋ = 112 VMs. The smaller limit is 56 VMs; CPU is the bottleneck.
  5. At 2:1, virtual CPU capacity = 224 × 2 = 448 vCPU, so CPU allows ⌊448 ÷ 4⌋ = 112 VMs. RAM still allows 112 VMs. The smaller limit is 112 VMs.

Answer. At 1:1 the cloud fits 56 VMs; at 2:1 it fits 112 VMs.

Exam traps

  • Reserve control-plane hosts before dividing capacity; forgetting them overestimates VMs.
  • 2:1 CPU overcommit doubles virtual CPU capacity, not RAM; RAM overcommit can swap or crash.
  • Eucalyptus or OpenStack API compatibility with AWS does not guarantee feature parity; test.
  • OpenNebula's front end is not the hypervisor; drivers and node packages do the work.

5.9 Cloud simulation with CloudSim

CloudSim is an open-source Java simulator that runs a whole cloud inside one laptop: data centres, hosts, virtual machines, a broker and tasks called cloudlets. Comparing scheduling policies on rented hardware is slow, costly and never repeats exactly; a simulation gives the same answer every run. Researchers use it to test VM placement, cloudlet ordering, energy models and SLA rules before touching a real provider. This chapter builds one VM, runs five cloudlets shortest-job-first, and checks every number by hand.

You need the scheduling vocabulary from Unit 4 (policies, mechanisms, waiting and turnaround time). Chapter 5.8 helps for what a real data centre looks like; no provider account is needed here.

The pieces CloudSim models

CloudSim is a discrete-event simulator written in Java. A clock jumps from one scheduled event to the next instead of ticking in real time, so a 31-second schedule finishes in milliseconds. Nothing is virtualised for real: no hypervisor, no network packet, no disk.

Six entities describe the model.

  • CloudSim: the engine. Holds the event queue, the clock and every entity.
  • Datacenter: the building. Owns the hosts and a VM allocation policy.
  • Host: one physical server. Has processing elements (PEs, that is cores), RAM in MB, bandwidth in Mbps and storage in MB.
  • VM: a slice of a host. Declares MIPS, number of PEs, image size, RAM and bandwidth.
  • DatacenterBroker: your agent. Submits VMs and cloudlets, then hands the results back.
  • Cloudlet: one task. Carries a length in MI, plus a file size and an output size in MB.

Two policies drive everything. VmAllocationPolicy decides which host receives a VM. CloudletScheduler decides the order cloudlets run inside one VM; the built-in ones are TimeShared and SpaceShared. Shortest job first (SJF) is not built in, so you sort the cloudlet list yourself before submitting.

Units matter. MI means million instructions, the size of a task. MIPS means million instructions per second, the speed of one PE. Divide one by the other to get seconds.

t = L ÷ P

t is the run time in seconds; L is the cloudlet length in MI; P is the VM speed in MIPS. A 2000 MI cloudlet on a 1000 MIPS VM needs 2000 ÷ 1000 = 2 s.

Installing it and running a built-in example

  1. Install a JDK (version 8 or newer) and confirm it with javac -version.
  2. Download the CloudSim release zip; keep the core jar and the examples folder together. The jar file name carries the version number, not just cloudsim.jar.
  3. Compile your own class with the jar on the classpath: javac -cp cloudsim.jar MySim.java.
  4. Run a shipped demo first. The example classes are not inside the core jar, so both jars go on the classpath: java -cp cloudsim-x.y.jar:cloudsim-examples-x.y.jar:. org.cloudbus.cloudsim.examples.CloudSimExample1, replacing x.y with the release version. On Windows use ';' instead of ':' between classpath entries.
  5. In your class, create CloudSim, one Datacenter with hosts, one DatacenterBroker, a VM list and a cloudlet list. Call broker.submitVmList(...), broker.submitCloudletList(...), then CloudSim.startSimulation().
  6. After the run, read broker.getCloudletReceivedList(). Each Cloudlet reports getExecStartTime() and getExecFinishTime() in seconds.

Every finished cloudlet prints one line with the same seven columns. The two you need for waiting and turnaround are Start Time and Finish Time.

Running SJF on one VM

CloudletSchedulerSpaceShared runs one cloudlet at a time on the VM and queues the rest in submission order. To get SJF, sort the cloudlet list by length before submitting. With one VM and one PE, that sort is the whole policy.

On a dedicated VM each cloudlet runs alone at full VM speed. The order changes waiting time but never the makespan: the last cloudlet finishes at total length divided by speed, whatever the order.

makespan = Σ Lᵢ ÷ P

Σ Lᵢ is the sum of all cloudlet lengths in MI and P is the VM speed in MIPS; the result is in seconds.

Three numbers describe each cloudlet. Completion time C is when its run ends. Waiting time W = C − its own run time, because every cloudlet arrives at t = 0 here. Turnaround time is C − arrival, which equals C in this case. Mean waiting is ΣW ÷ n and mean turnaround is ΣC ÷ n.

SJF gives the lowest mean waiting on one machine when all jobs are available at the start. Its price is that lengths must be known in advance, and a long cloudlet can starve while short ones keep arriving; real brokers add ageing to prevent that. On the same five cloudlets first-come-first-served gives mean waiting 14.6 s against 8.6 s for SJF, with the same 31 s makespan.

Worked example

Question. A private cloud has one host carrying one VM of 1000 MIPS. A broker submits five cloudlets at time 0, one PE each, in this order: C1 = 10000 MI, C2 = 5000 MI, C3 = 8000 MI, C4 = 2000 MI, C5 = 6000 MI. The VM uses space-shared scheduling. Sort the cloudlets shortest job first and give each run time, completion time and waiting time, then the mean waiting time, the mean turnaround time and the makespan.

  1. Run time t = L ÷ P with P = 1000 MIPS: C1 = 10 s, C2 = 5 s, C3 = 8 s, C4 = 2 s, C5 = 6 s.
  2. SJF order by length: C4 (2000 MI), C2 (5000), C5 (6000), C3 (8000), C1 (10000).
  3. Run times in that order: 2, 5, 6, 8, 10 s.
  4. Completion times, adding each run to the previous finish: 2, 7, 13, 21, 31 s.
  5. Waiting W = C − own run time: 0, 2, 7, 13, 21 s. Sum 43 s, so mean waiting = 43 ÷ 5 = 8.6 s.
  6. Turnaround equals completion here, since every cloudlet arrives at 0: 2, 7, 13, 21, 31 s. Sum 74 s, so mean turnaround = 74 ÷ 5 = 14.8 s.
  7. Makespan 31 s, which also equals the total length 31000 MI ÷ 1000 MIPS.

Answer. SJF runs C4, C2, C5, C3, C1 in that order; mean waiting time 8.6 s, mean turnaround time 14.8 s, makespan 31 s.

Exam traps

  • Cloudlet length is in MI, not seconds. An 8000 MI cloudlet on a 2000 MIPS VM takes 4 s; writing 8000 s loses every mark.
  • MIPS is per PE. A VM with 2 PEs at 500 MIPS does not run a one-PE cloudlet at 1000 MIPS.
  • SJF needs lengths known in advance and can starve a long cloudlet; FCFS and round robin never starve but give higher mean waiting.
  • CloudSim is a simulator with no hypervisor and no packets. It compares policies; it cannot benchmark a real application's speed.
  • A cloudlet's file size and output size are data in MB, not work. On one VM they add nothing to the run time, which comes only from length ÷ MIPS.

Analyze FCFS on the five cloudlets of the worked example gives mean waiting 14.6 s; SJF gives 8.6 s, yet both end at 31 s. Explain both facts. 5 marks

Every cloudlet runs alone at full VM speed, so the total work and hence the makespan depend only on the sum of lengths, not the order. Waiting time does depend on order: SJF puts short jobs first, so four jobs wait less and only the long one waits long, cutting the mean from 14.6 s to 8.6 s.

Analyze A student runs the same CloudSim program twice and gets identical output, then runs the same policy on a rented VM and gets different times. Why? 4 marks

CloudSim is deterministic: the event order is fixed by the program, with no other tenant load, no network delay and no hardware variation. A rented VM shares physical hardware, cache and network with other tenants, so its measured time changes run to run.

Takeaways

  1. A cloud program runs faster or slower mainly because of the parallel model chosen, so match the model to how the work communicates.
  2. High-throughput computing optimises finished tasks per hour across a pool, which is a different goal from making one job finish fast.
  3. MapReduce hides all the hard parts of a distributed job — splitting, shuffling, retrying, failing over — behind two functions you write.
  4. Spark's in-memory RDDs plus lineage-based recovery make iterative algorithms such as PageRank far cheaper than repeated MapReduce jobs.
  5. AWS, Google Cloud and Azure all sell the same four primitives — compute, storage, network, messaging — with different names and different defaults.
  6. Open-source IaaS platforms such as OpenStack turn your own racks into a private cloud with the same API shape as a public one.
  7. CloudSim lets you compare scheduling policies on a laptop before spending money on real virtual machines.

Glossary

Action
A Spark operation such as count or save that triggers actual computation of the pending transformations.
Autoscaling
Adding or removing instances automatically when a metric such as CPU load crosses a threshold.
Availability zone
A separate physical site inside a cloud region, with independent power and network, used for replication.
Barrier
A synchronisation point where every participating thread or process must arrive before any may continue.
Block storage
Storage presented as a raw disk that one machine mounts and formats, such as EBS or a Cinder volume.
CloudSim
A Java simulation library that models data centres, hosts, VMs, brokers and cloudlets for policy experiments.
Combiner
A local partial reduce run on the same machine as the map, used to shrink the data sent to the shuffle.
Directed acyclic graph (DAG)
The graph of stages Spark builds from a chain of transformations; it has no cycles, so a lost stage can be rebuilt.
Distributed computing
Running a job across several networked machines that share only the network, not memory.
Embarrassingly parallel
Work that splits into independent parts with no communication between them, so it scales almost linearly.
Object storage
Storage where each item is a whole object reached by a key inside a bucket, with no directory tree and no in-place edits.
Parallel computing
Running one job on many processors at the same time so it finishes sooner.
Partitioner
The function that decides which reducer or partition receives a given key after the shuffle.
Race condition
A bug where the result depends on the unpredictable order in which concurrent threads touch shared data.
Scheduler
The component that decides which task runs on which worker and at what time.
Speculative execution
Launching a duplicate copy of a slow task and taking whichever copy finishes first.
Straggler
A task that runs far slower than its peers and holds up the whole job.
Tenant
One customer of a shared cloud whose resources and data must stay isolated from other customers.
Thread
A single sequence of instructions inside a process that shares memory with the other threads of that process.
Transformation
A Spark operation such as map or filter that defines a new RDD lazily without computing it.
Virtual machine image
A stored template of an operating system and preinstalled software from which new virtual machines are booted.
Virtual private cloud
A logically isolated network inside a public cloud where you choose subnets, routes and firewalls.
Worker pool
A fixed set of processes or machines that repeatedly take tasks from a queue and run them.
