3.1 Virtualization: characteristics, pros and cons

A virtual machine is a computer built in software. Virtualization is the layer that lets many such computers run on one physical server at the same time. Software called the hypervisor creates and runs the VMs, hands out virtual CPUs, memory, disks and network cards, and keeps the guests apart. A bare-metal (Type 1) hypervisor sits directly on the hardware and owns it; a hosted (Type 2) hypervisor runs as a program on top of a normal host OS. Virtualization exists because most servers use a small fraction of their capacity, so one server per application wastes money, power and rack space. Cloud providers use it to rent IaaS instances; enterprises use it to consolidate, test and recover.

You need: Unit 1 on service models, because a VM is the unit that IaaS rents out.

One physical machine, many guests

Start with one server. It has a fixed number of CPU cores, a fixed amount of RAM, some disks and a network card. Without virtualization, one operating system owns all of it and every application runs inside that one OS. If two applications need different OS versions, or if one crashes the kernel, you buy a second server.

Virtualization adds a software layer between the hardware and the operating systems. This layer is the hypervisor, also called the virtual machine monitor (VMM). The hypervisor creates virtual machines (VMs). A VM is a complete computer in software: it has a virtual CPU (vCPU), virtual RAM, a virtual disk and a virtual network card. A normal guest operating system and its applications run inside it.

A bare-metal hypervisor owns the real hardware and decides which vCPU runs on which physical core and when, which physical memory pages hold which guest's data, and which guest's disk request reaches the controller. A hosted hypervisor runs as a program on a normal host OS and asks that OS for the same resources. Either way the guest does not see this. It believes it has a private machine. The physical server is the host. Its resources are shared among the guests. That sharing is the point: one host carries the load of many underused servers. Hypervisor designs differ; see 3.3.

Four characteristics of a virtualized environment

Textbooks describe a virtualized environment by four properties.

Partitioning. The host's resources are divided into separate slices, one per VM. Each VM is configured with a stated number of vCPUs and a stated amount of RAM. Slices can differ in size and can change later.

Isolation. Each VM runs as if alone. A crash, a reboot or a runaway process in one VM does not stop the others. Isolation also separates security domains: code inside VM A cannot normally read VM B's memory. The strength of that separation is the strength of the hypervisor, so see Unit 6 on VM security.

Encapsulation. A VM's configuration and disks live in a small set of files: a configuration file and one or more disk images, plus a memory snapshot if one is taken. Those files can be copied, backed up or moved. When a running VM is migrated, its memory pages are transferred separately over the network to the new host.

Hardware independence. The guest sees standard virtual hardware, not the exact model of the physical board. An image built on one vendor's host boots on another host with the same CPU architecture.

Two formulas describe the sharing:

Allocated vCPU = Σ vCPU<sub>i</sub> for i = 1 to n

vCPUi is the number of virtual CPUs configured for VM i; n is the number of VMs on the host; the sum is a limit, not reserved cores.

Consolidation ratio = number of VMs ÷ number of hosts

a ratio of 20:1 means twenty VMs per host on average.

Pros and cons

Pros.

  • Consolidation: ten old servers, each using a small fraction of its own much larger capacity, become ten VMs on one powerful host, with less power, cooling, rack space and cabling.
  • Higher utilisation: the same hardware does more work.
  • Elasticity: a new VM is a file copy plus a boot, often under a minute; a template can be cloned to add capacity and deleted later.
  • Legacy support: an old application that needs an old OS runs in a VM on new hardware.
  • Encapsulation in practice: snapshots, backup and live migration of a running VM become file operations.
  • Tenant isolation, which is what makes public IaaS possible.

Cons.

  • Overhead: the hypervisor uses CPU and memory, and I/O passes through an extra layer. A few percent loss is normal; I/O-heavy workloads lose more.
  • Complexity: a new layer to configure, patch and monitor, and new skills to hire.
  • Licence cost: each guest OS and some per-core software must be licensed, so part of the hardware saving goes to licences.
  • Security surface: the hypervisor is a target. A bug that lets code escape a VM, called a VM escape, exposes every guest on the host.
  • Not universal: workloads that need hard real-time guarantees, special add-in cards or a specific GPU may virtualize poorly.

Allocated is a limit, not a reservation

When the hypervisor gives a VM 2 vCPU, it does not lock two physical cores for that VM. It records a limit and schedules the VM's vCPUs onto whatever cores are free. RAM is handled similarly, though it is reclaimed less freely; see 3.5 for ballooning and address translation.

So the sum of allocated vCPU can exceed the number of physical cores. This is overcommit, and it is normal. It works because most VMs are idle most of the time. It fails when many VMs peak together: the host runs short of CPU, every guest slows down, and one busy neighbour spoils the others.

The worked example puts numbers on a host of this kind.

Worked example

Question. A physical host has 16 CPU cores and 64 GB of RAM. It runs 5 virtual machines. Each VM is configured with 2 vCPU and 8 GB of RAM. (a) Find the total allocated vCPU and RAM. (b) Find the remaining unallocated vCPU and RAM. (c) Each VM averages 20% of its vCPU. Find the physical cores' worth of CPU used on average and the percentage of the host's cores.

  1. Allocated vCPU = 5 VMs × 2 vCPU per VM = 10 vCPU.
  2. Allocated RAM = 5 VMs × 8 GB per VM = 40 GB.
  3. Allocated vCPU limit = 10 vCPU out of a hosting capacity of 16 cores, so the unused vCPU allowance is 16 − 10 = 6 vCPU (assuming one vCPU per core here).
  4. Unallocated RAM = 64 GB − 40 GB = 24 GB.
  5. Average CPU per VM = 20% of 2 vCPU = 0.20 × 2 = 0.4 vCPU.
  6. Total average CPU = 5 × 0.4 = 2.0 vCPU. With perfect packing this is about 2 physical cores of work.
  7. Fraction of the host = 2.0 ÷ 16 = 0.125 = 12.5%.

Answer. The host allocates 10 vCPU and 40 GB, leaving 6 vCPU and 24 GB unallocated; the VMs average 2.0 cores of work, which is 12.5% of the host's 16 cores.

Exam traps

  • Allocated vCPU is a limit, not a reserved core. Write 'configured with 2 vCPU', not 'owns 2 cores'.
  • Isolation is not absolute security. A hypervisor bug can allow a VM escape, so the hypervisor must be patched like any OS.
  • Overcommit is deliberate, not an arithmetic error. It fails only when many guests peak together, the noisy-neighbour effect.
  • A snapshot is not a backup when it sits on the same storage as the VM. Copy it to separate storage.
  • Hardware independence is about virtual hardware of the same architecture. An x86 image does not boot on an ARM host without emulation.

3.2 Taxonomy and implementation levels of virtualization

Virtualization is classified by the implementation level: the place where the software layer sits between a program and the resources it uses. The layer may be inside one application, in a library, in the operating system, or directly on the hardware. This taxonomy exists because each level trades portability, isolation, and overhead differently. A phone user sees it through app runtimes and containers; a data centre sees it through hypervisors.

You need: 3.1, where virtualization inserts a software layer that shares one physical machine among isolated virtual machines.

Why the level matters

Every virtual system has an interface. Below the interface, resources are real or already virtual. Above it, a program believes it owns a machine. The implementation level names that interface. Put the layer just above the hardware and you can run whole operating systems. Put it inside one process and you can run bytecode on any host. The classification tells you what is shared and what is emulated.

Two other views appear in exams. A resource-based view asks what is virtualized: CPU, memory, storage, or network. A transparency-based view asks how much the guest knows about the layer. These are useful tags, not separate rungs on the same ladder. Some syllabi call the whole idea the taxonomy of virtualization techniques, or types of virtualization.

The levels are application, library, operating-system, and hardware. The order runs from a layer close to one program to a layer close to the hardware. The hardware branch later splits by guest cooperation into full and para virtualization, covered in 3.4. The operating-system branch leads to containers in 3.7.

Four implementation levels

Each level answers a different need.

  • Application-level. A virtual machine runs as an ordinary process on the host operating system. It executes portable bytecode, which is code for a virtual processor. The Java Virtual Machine (JVM) runs Java bytecode; the Common Language Runtime (CLR) runs .NET code. No guest operating system boots, and no hypervisor is involved. The benefit is portability: the same bytecode runs on any host with a compatible runtime.
  • Library-level. The layer replaces or translates calls to a library or application programming interface (API). WINE lets many Windows programs run on Linux by implementing Windows library calls with Linux calls. The program still runs on the host operating system. Only programs that use the translated calls work, so coverage is partial.
  • Operating-system level. One host kernel is shared by many isolated user-space instances. Containers use namespaces (which make resources look private to a process group) and cgroups (which cap resource use); details are in 3.7. Each container looks like a small server, but it has no kernel of its own. Startup is fast and overhead is low because the kernel is not duplicated.
  • Hardware level. A hypervisor, also called a virtual machine monitor, sits between the physical hardware and one or more guest operating systems. It exports virtual hardware: virtual CPUs, memory, disks, and network cards. The guest OS boots on that virtual hardware. The hypervisor is covered in 3.3. Hardware level splits into full and para by how much the guest cooperates, not by a new level.

A system can mix levels. A container can run a JVM; a hypervisor can host a VM that runs Docker.

Reading a system by its level

Use four questions in order. The first match gives the level.

  1. Ask whether a guest operating system boots on virtual hardware. If yes, the level is hardware-level.
  2. Ask whether one host kernel runs several isolated user-space environments, each looking like a separate server, with no kernel image of its own (namespaces and cgroups). If yes, the level is OS-level.
  3. Ask whether a runtime executes portable code as an ordinary process. If yes, the level is application-level.
  4. Ask whether library or API calls are translated for a foreign program. If yes, the level is library-level.

A JVM or a WINE program is an ordinary host process; it shares the kernel but is not an isolated user-space environment, so it does not match the OS-level test.

The order matters. A container running a Java service is OS-level for the container and application-level for the JVM inside it. Name the layer you are asked about, not every layer present. Level is also separate from transparency. Full and para are choices inside hardware-level virtualization: full hides the hypervisor from an unmodified guest; para expects a modified guest to make hypercalls, which are calls into the hypervisor. Both are hardware-level because both run a guest OS on virtual hardware.

Worked example

Question. A cloud team runs four workloads. Workload X: Xen with an unmodified guest operating system. Workload D: Docker containers on one Linux host. Workload J: a Java program on the JVM. Workload W: a Windows program under WINE on Linux. Classify each workload by implementation level. For the Xen workload, state which split inside hardware-level virtualization applies.

  1. Xen: the hypervisor sits between the hardware and the guest OS and exports virtual hardware. The guest OS boots on that virtual hardware, so the level is hardware-level. The guest is unmodified, so the transparency choice is full virtualization; see 3.4.
  2. Docker: containers share the host Linux kernel and isolate processes with namespaces and cgroups. No guest OS boots, so the level is OS-level; see 3.7.
  3. JVM: the Java Virtual Machine runs as an ordinary process on the host OS and executes Java bytecode. The level is application-level.
  4. WINE: WINE translates Windows library calls into Linux calls for a program running on the host OS. The level is library-level.

Answer. Xen is hardware-level (full virtualization); Docker is OS-level; the JVM is application-level; WINE is library-level.

Exam traps

  • Level is not the same as full or para. Full and para are transparency choices inside hardware-level virtualization.
  • Application-level virtual machines such as the JVM are not hypervisor virtual machines. They run as processes and do not boot a guest OS.
  • Library-level virtualization translates calls; it does not virtualize hardware. WINE is not a hypervisor.
  • OS-level virtualization shares the host kernel. A container has no guest kernel, so calling it a full virtual machine is wrong.
  • A mixed system has several levels. State which layer the question asks about; a container running a JVM is both OS-level and application-level depending on the boundary.

3.3 Hypervisors and virtual machine monitors

A hypervisor, also called a virtual machine monitor, is the software layer that creates and runs virtual machines on one physical host. It exists to share CPU, memory and devices among isolated guests while keeping each guest inside its own virtual hardware. Cloud providers use it to sell small VMs from large servers; a laptop user runs it to test another operating system. Examples include Xen, ESXi and Hyper-V on servers, and VirtualBox and Workstation on desktops. This chapter explains the two placements, the control domain, CPU rings, vCPU scheduling and device emulation.

You need: 3.2, which places the hypervisor among implementation levels.

Role and two placements

A hypervisor is software that creates and runs virtual machines. The same idea has another name: virtual machine monitor, or VMM. It sits between the physical hardware and the guest operating systems. It gives each guest a virtual CPU, virtual memory and virtual devices. It also keeps guests apart: one guest cannot read another guest's memory through normal instructions.

Why does it exist? A physical server is often too large for one small job. The hypervisor turns one server into many smaller machines. A cloud provider can then rent a 2 vCPU VM to one customer and a 16 vCPU VM to another. On a laptop, a developer can run Linux inside Windows without rebooting.

There are two standard placements. A Type 1 hypervisor runs directly on the hardware; it is also called bare-metal. Xen, VMware ESXi and Microsoft Hyper-V are Type 1. A Type 2 hypervisor runs as an application on a host operating system; it is also called hosted. Oracle VirtualBox and VMware Workstation are Type 2. The figure shows both. The difference matters: Type 1 has no general-purpose host OS between it and the hardware, so it controls devices and scheduling directly. Type 2 borrows the host OS for drivers and file systems, which is convenient on a laptop but adds a layer of delay.

Control domain, rings and vCPU scheduling

In Xen, the first VM, called domain 0 or Dom0, is privileged. It runs a driver VM that talks to real devices and offers services to other guests. Other guests are unprivileged domains, sometimes called domU. The hypervisor is still the lowest layer; Dom0 is a helper, not the hypervisor itself. Hyper-V uses a parent partition in a similar role. Some designs call this a service VM or control domain.

x86 processors have privilege rings 0 to 3. Ring 0 is most privileged; ring 3 is least. In a plain OS, the kernel runs in ring 0 and applications in ring 3. A hypervisor needs ring 0 for itself. A guest kernel cannot run in ring 0, or it could control the machine. Hardware-assisted virtualization solves this with two modes: a root mode for the hypervisor and a non-root mode for guests. The guest kernel still believes it is in ring 0, but the CPU exits to the hypervisor on sensitive instructions. Older or para-virtual designs put the guest kernel in ring 1 and trap sensitive calls; see 3.4.

Each guest sees one or more virtual CPUs, or vCPUs. The hypervisor's scheduler maps runnable vCPUs onto physical CPU cores. It gives each vCPU a time slice, saves its registers, and switches to another vCPU. If a host has 8 cores and the guests have 12 vCPUs in total, the hypervisor can overcommit: at most 8 vCPUs run at one instant. Overcommit raises utilisation but makes latency less predictable. Details of CPU virtualisation are in 3.5.

Device emulation

A guest cannot touch a real disk or network card directly unless the hypervisor allows it. Device emulation is the default: when the guest writes to a virtual device register, the hypervisor traps the access, performs the operation on a real device, and returns the result. This works with unmodified guests and lets many VMs share one card. The cost is CPU time per I/O operation. A second option is passthrough: the hypervisor gives one VM direct control of a device, often through an IOMMU, a unit that translates device addresses. Passthrough is fast but the device is no longer shared. A third option is a split driver: a front-end driver in the guest talks to a back-end driver in the control domain; Xen uses this model. The choice affects throughput, isolation and how many VMs can use the device. For the storage and network layers above this mechanism, see 3.6.

Worked example

Question. A laptop has 16 GB of RAM. The host OS uses 4 GB and a Type 2 hypervisor uses 1 GB. A virtual machine is configured with 12 GB of guest RAM. (a) Find the free RAM before the VM starts. (b) Find the shortfall if the VM tries to use its full 12 GB. (c) Can the VM get all 12 GB without overcommit or ballooning?

  1. Total physical RAM = 16 GB.
  2. RAM left after the host OS = 16 − 4 = 12 GB.
  3. RAM left after the hypervisor = 12 − 1 = 11 GB. This is the free RAM before the VM starts.
  4. The VM asks for 12 GB. Shortfall = 12 − 11 = 1 GB.
  5. Without overcommit or ballooning, the hypervisor cannot promise the missing 1 GB, so the VM cannot get its full 12 GB.

Answer. Free RAM before the VM is 11 GB; the VM is short by 1 GB, so it cannot get its full 12 GB without overcommit or ballooning.

Exam traps

  • A Type 1 hypervisor runs directly on hardware; a Type 2 hypervisor needs a host OS underneath. Do not draw Type 2 as bare-metal.
  • The hypervisor is not the guest operating system. Each VM carries its own guest OS image and its own kernel.
  • A control domain such as Xen Dom0 is a privileged VM that helps with I/O and management; it is not the hypervisor itself.
  • A vCPU is a virtual CPU, not a physical core. More vCPUs than cores is overcommit; it does not create extra hardware.
  • Device emulation costs CPU time per I/O. Passthrough is faster but takes the device away from other VMs.

3.4 Full virtualization and para-virtualization

A hypervisor must run a guest operating system that was written for real hardware. Full virtualization hides the hypervisor completely: the guest runs unmodified, and every privileged instruction it executes is trapped and emulated. Para-virtualization takes the opposite deal — the guest OS is edited to call the hypervisor directly through hypercalls, which is faster but needs a modified guest. Both techniques let one physical machine host many isolated virtual machines. The choice between them decides how much compatibility you trade away for speed.

You need: 3.3 for what a hypervisor does, and 3.2 for where this choice sits in the taxonomy.

Full virtualization: the guest never knows

Full virtualization runs a guest OS that has not been changed in any way. The guest believes it owns a real machine. Its kernel executes privileged instructions, writes control registers and programs devices exactly as it would on bare metal. The hypervisor, or VMM (3.3), hides itself and keeps the illusion alive.

The difficulty is a class of instructions called sensitive instructions. A sensitive instruction is one whose result depends on the privilege state or the configuration of the machine — reading the interrupt flag, reloading the page-table base register, halting the CPU. The guest runs in a lower privilege ring, so the CPU will not let it perform these actions directly. The VMM must catch each one and apply its effect to the virtual CPU instead.

  1. Trap and emulate. The VMM runs the guest in a lower privilege ring. When the guest executes a privileged instruction the CPU raises a trap, control jumps to the VMM, and the VMM decodes the instruction and updates the virtual machine state.
  2. Return to the guest at the instruction after the trapped one, so the guest never notices the interruption.
  3. Use binary translation for instructions that do not trap cleanly. The VMM copies a block of guest code, scans it before running it, and replaces risky instructions with safe calls into the VMM. Translated blocks are cached and reused.

Why translation is needed at all: on some older x86 designs a handful of privileged instructions failed silently instead of trapping, so a pure trap-and-emulate design could not see them. Translation catches them before they execute.

sensitive ⊆ privileged

sensitive is the set of instruction types whose behaviour depends on the privilege state of the machine; privileged is the set of instruction types the CPU allows only in the highest privilege ring. This is the Popek and Goldberg condition: if every sensitive instruction is also privileged, the machine can be virtualized with traps alone and the guest needs no change.

Para-virtualization: the guest cooperates

Para-virtualization edits the guest OS source code. Instead of executing a privileged instruction and waiting to be trapped, the guest asks the hypervisor to do the work. That deliberate request is a hypercall.

A hypercall is a software call from a para-virtualized guest kernel into the hypervisor. It carries a call number and arguments in agreed registers, like a system call but aimed at the VMM instead of at the OS kernel. The hypervisor publishes the interface: a list of hypercall numbers and their argument conventions. Some syllabi spell the term paravirtualization.

  1. The guest kernel places the hypercall number in one fixed register and the arguments in others.
  2. It executes the hypercall instruction that the interface defines.
  3. The CPU switches to the hypervisor's privilege ring. The VMM reads the number and dispatches to the matching handler.
  4. The handler performs the operation on the virtual machine's state, for example updating a shadow page table or masking an interrupt.
  5. Control returns to the guest with a result code in a register.

The gain is small per call and large in total. A trap costs a ring switch plus the VMM's instruction decode. A hypercall costs a ring switch plus a table lookup, with no decode and no guesswork. Batch many operations into one hypercall and the saving grows further. The cost is portability: the guest kernel must be recompiled against the new interface, and that same binary will not boot on bare metal.

Exam traps

  • Full virtualization does not run the guest in the highest privilege ring. The guest runs below the hypervisor; that is exactly why its privileged instructions trap.
  • Para-virtualization does not remove the hypervisor. It removes the trap, not the VMM — the guest still calls into it for every sensitive operation.
  • Sensitive and privileged are not synonyms. An instruction is privileged if the CPU blocks it in a lower ring; it is sensitive if its result depends on machine state. The Popek and Goldberg condition is that sensitive is a subset of privileged, not the other way round.
  • Percentage saving is divided by the full-virtualization time, not the para-virtualization time. Here 800 ÷ 2,000 = 40%, not 800 ÷ 1,200 = 67%.
  • Binary translation is not cross-architecture emulation. It rewrites the same instruction set into safe calls; running ARM code on x86 is a different technique.

3.5 Virtualization of CPU, memory and I/O devices

One physical server runs many virtual machines because a hypervisor can fake the three things every operating system needs: a processor, memory and devices. It gives each VM virtual CPUs that the host scheduler time-slices, a memory map that hides the real machine frames, and device interfaces that either emulate hardware or pass it through. This is the machinery behind every IaaS instance you rent, every VM on a developer laptop, and the isolation that keeps one tenant's crash away from another.

You need: 3.3 for what a hypervisor is, and 3.4 for full versus para-virtualized guests.

CPU virtualization: vCPUs, traps and hardware assist

A guest OS runs its own scheduler and thinks it owns a physical processor. The hypervisor gives it a vCPU: a virtual processor with its own registers, program counter, flags and interrupt state. Every vCPU is a thread on the host, queued and time-sliced by the host scheduler. Two vCPUs on one core take turns, and the guest sees this only as slower time.

Privileged instructions are the difficulty. A guest kernel changing page tables or masking interrupts must not affect the host. Trap and emulate handles this: hardware runs the guest in a restricted mode, the instruction faults into the hypervisor, the hypervisor performs the effect in software, and the guest resumes. Each trap costs microseconds, so frequent traps hurt.

Some x86 instructions are sensitive but do not fault, so early hypervisors rewrote guest kernel code on the fly, called binary translation (3.4). Intel VT-x and AMD-V add a root and a non-root mode: the guest runs in non-root mode at ring 0, and only a fixed list of events causes a VM exit to the hypervisor; a VM entry resumes the guest. Exits become rarer and cheaper, so CPU virtualization runs near native speed.

Para-virtualized guests avoid many traps by calling the hypervisor directly with hypercalls.

Scheduling matters when vCPUs outnumber cores. A host with 16 cores may run four VMs of 8 vCPUs each: 32 vCPUs share 16 cores, which is oversubscription. Busy guests then wait, and a guest can read the lost time as steal time. For SMP guests, the hypervisor may co-schedule sibling vCPUs together so they do not spin waiting for each other.

Memory virtualization: two levels of translation

Guest memory has two layers. The guest's own page table maps guest virtual (GV) to guest physical (GP). The hypervisor's table maps GP to machine (M), the real RAM frames. The MMU needs one GV→M translation per access.

Shadow page tables do this by merging: the hypervisor builds a single GV→M table and points the MMU at it. Guest writes to its page tables are write-protected, so each update traps and the shadow table is rebuilt. That is accurate but costly for workloads that touch page tables often.

EPT (Intel Extended Page Tables) and NPT (AMD Nested Page Tables) instead keep two tables and let hardware walk both: the MMU walks the guest table, and for each GP entry it walks the EPT table. A TLB miss needs a walk of the guest table plus an EPT walk for each level of it, so several memory accesses, but no traps. TLB entries are tagged with a virtual-processor or address-space identifier (VPID on Intel, ASID on AMD), so switching vCPUs or VMs need not flush the TLB.

MA = (MFN × page_size) + offset

MA is the machine address in real RAM; MFN is the machine frame number holding that page; page_size is 4 KB = 0x1000 on x86; offset is the byte position inside the page, from 0 to 0xFFF.

Hosts are usually overcommitted: 64 GB of RAM may back VMs configured for 96 GB. Three reclaim paths exist. A balloon driver inside the guest allocates pages, pins them and returns them to the hypervisor, so the guest's own allocator sees less RAM. Page sharing merges identical pages and copies on write. Host swapping pushes guest pages to disk, which is slow. Ballooning is cooperative and needs a driver in the guest; the hypervisor cannot know which guest pages are free.

I/O virtualization: emulation, virtio and passthrough

In emulation the guest touches a device register at a fixed address, the access traps, and the hypervisor imitates a well-known device such as an Intel e1000 NIC or an IDE disk. Any unmodified guest works, but every I/O is a VM exit, so packet rates stay low.

Virtio is para-virtualized I/O. A guest driver and a host backend share a ring of descriptors in guest memory. The guest places a buffer and kicks a doorbell register; the host reads the buffer directly from guest memory. One exit per batch replaces one exit per packet, which is why virtio-net and virtio-blk are the default in most clouds.

Direct assignment (passthrough) gives a whole device to one VM. An IOMMU (Intel VT-d or AMD-Vi) translates the device's DMA addresses, so the device can reach only that guest's memory. Speed is near native, but the device cannot be shared.

SR-IOV adds sharing without losing speed. A PCIe device exposes one physical function (PF) for control and many virtual functions (VF), each with its own configuration space and queues. Each VF is passed to a different VM, so sixteen VMs can share one 10 GbE port at near-native speed.

Storage and network virtualization as concepts are covered in 3.6.

Worked example

Question. A guest uses 4 KB pages. Guest virtual page 5 maps to guest physical page 20, and the hypervisor maps guest physical page 20 to machine page 80. Find the machine address that corresponds to guest virtual address offset 0x2F0 inside that page. Give the guest virtual, guest physical and machine addresses.

  1. Page size = 4 KB = 0x1000 bytes, so the low 12 bits of an address are the offset. Offset = 0x2F0, which is less than 0x1000.
  2. Guest virtual address = GV page × page_size + offset = 5 × 0x1000 + 0x2F0 = 0x5000 + 0x2F0 = 0x52F0.
  3. Guest physical address = GP page × page_size + offset = 20 × 0x1000 + 0x2F0 = 0x14000 + 0x2F0 = 0x142F0.
  4. Machine address = machine page × page_size + offset = 80 × 0x1000 + 0x2F0 = 0x50000 + 0x2F0 = 0x502F0.
  5. The same three values in decimal: 21232, 82672 and 328432. The offset 0x2F0 is unchanged by both translations.

Answer. The machine address is 0x502F0, that is 328432 in decimal, reached through guest physical address 0x142F0.

Exam traps

  • A vCPU is a scheduled thread, not a dedicated core. Four VMs with 8 vCPUs each on a 16-core host do not deliver 32 cores of throughput; they share 16.
  • Trap and emulate means the instruction faults into the hypervisor. VT-x and AMD-V make exits rarer and cheaper, but they do not remove them; do not write that hardware assist eliminates traps.
  • Shadow page tables keep one merged GV→M table and trap on guest page-table writes. EPT and NPT keep two tables and walk both in hardware. Swapping these descriptions is the commonest mark-loser.
  • Passthrough without an IOMMU lets a device DMA into any memory. Always name the IOMMU (Intel VT-d, AMD-Vi) when you explain direct assignment.
  • Ballooning is cooperative and needs a driver inside the guest; page sharing by deduplication and host swapping are different reclaim paths.

3.6 Storage and network virtualization

Storage virtualization hides many physical disks behind logical volumes. Network virtualization hides physical links behind virtual NICs and switches. Both let a hypervisor give each VM a clean, isolated device while sharing hardware. A VM sees a disk that may span arrays, or a network card that may share one uplink with dozens of neighbours. Cloud providers use these layers to sell storage and bandwidth in slices, to snapshot and migrate VMs, and to keep tenants apart. The same ideas support a Chennai firm renting IaaS capacity without buying a disk per server.

You need: 3.5 for device virtualization and 3.1 for isolation.

Storage virtualization: disks into pools

Physical disks differ in size, speed and failure rate. A storage pool hides that variety. The pool groups disks and lets an administrator carve logical volumes from one free-capacity number. A LUN (logical unit number) is the identifier of a logical disk presented to a host. The hypervisor gives each VM a virtual disk; that virtual disk is a file or volume inside the pool. The VM sees a normal block device and does not know which physical disks hold its blocks.

RAID 5 is common inside a pool. It stripes blocks across disks and stores parity. A hot spare lowers usable capacity.

Usable RAID 5 U = (n − 1) × d; P = Σ v<sub>i</sub>; overprovision = P ÷ U

n is number of equal disks; d is TB per disk; vi are thin volume sizes in TB; P is total provisioned logical TB; U is usable pool TB.

Thin provisioning sells logical size before physical blocks exist. A thin volume of 1.5 TB is created at once, but blocks are allocated on first write. Total logical P is the sum of all volume sizes. A ratio above 1 means promises exceed physical space; writes fail when the pool fills. Snapshots record a point-in-time view, usually by copy-on-write: old blocks are kept when new writes arrive. A snapshot protects against a bad update, not against loss of the whole pool.

Network virtualization: vNICs and overlays

Network virtualization gives each VM its own vNIC (virtual network interface card). The vNIC has a MAC address and driver inside the guest, but it is software. Frames leave the vNIC and enter a virtual switch (vSwitch), a layer-2 switch running in the hypervisor or host. The vSwitch forwards frames between vNICs and out through a physical NIC. It can apply policy: VLAN tag, bandwidth cap, or security rule. Traffic between two VMs on the same vSwitch can stay on the host and never touch the physical NIC.

VLAN (virtual LAN) adds a 12-bit tag to Ethernet frames and keeps groups in separate broadcast domains. It isolates traffic; it does not encrypt it. VXLAN wraps Ethernet frames inside UDP/IP and uses a 24-bit VNI (VXLAN network identifier). That carries layer-2 networks over a routed layer-3 data-centre fabric, beyond the 4094 usable VLAN IDs.

SDN (software-defined networking) separates the control plane from the data plane. The control plane decides paths; the data plane forwards packets. A controller programs flow rules into vSwitches and physical switches. The physical link becomes a shared resource; virtual links are policy. If twenty VMs each have a 1 Gb/s cap and share one 10 Gb/s uplink, demand is 20 Gb/s and contention is 20 ÷ 10 = 2:1. A cap does not reserve bandwidth.

What the VM actually sees

The VM never sees the physical path. Its disk driver writes to a virtual disk. The hypervisor maps that disk to a volume in the storage pool. The pool maps blocks to physical disks and applies RAID. Its network driver sends frames to a vNIC. The vNIC is attached to a vSwitch port. The vSwitch maps the port to a VLAN or VXLAN segment and chooses an uplink physical NIC. This chain is why live migration works: if both hosts can reach the same storage pool and the same virtual network, the VM's disk and MAC address move with it. Worked example

Question. A storage pool has 6 disks of 2 TB each in RAID 5. Twelve VMs each receive a thin volume of 1.5 TB. Average real use is 40% of provisioned logical capacity. Twenty VMs each have a 1 Gb/s vNIC cap and share one 10 Gb/s uplink. Find usable pool capacity, total provisioned capacity, overprovision ratio, real data, spare usable capacity, network demand and contention ratio.

  1. Usable RAID 5 capacity = (6 − 1) × 2 TB = 5 × 2 TB = 10 TB.
  2. Total provisioned capacity = 12 × 1.5 TB = 18 TB.
  3. Overprovision ratio = 18 TB ÷ 10 TB = 1.8.
  4. Real data at 40% use = 0.40 × 18 TB = 7.2 TB.
  5. Spare usable capacity = 10 TB − 7.2 TB = 2.8 TB, so the data fits.
  6. Network demand = 20 × 1 Gb/s = 20 Gb/s.
  7. Contention ratio = 20 Gb/s ÷ 10 Gb/s = 2, written 2:1.

Answer. Usable capacity is 10 TB, provisioned capacity is 18 TB, overprovision ratio is 1.8, real data is 7.2 TB with 2.8 TB spare; network demand is 20 Gb/s on a 10 Gb/s uplink, contention 2:1.

Exam traps

  • Thin provisioning does not guarantee space. An overprovision ratio above 1 can fail when the pool fills.
  • A VLAN isolates broadcast domains but does not encrypt frames; it is not a confidentiality control.
  • RAID 5 usable capacity is (n − 1) × d, not n × d. Parity consumes one disk's worth.
  • A snapshot is a point-in-time view in the same pool, not an independent backup; pool loss loses both.
  • A vNIC bandwidth cap limits a VM but does not reserve uplink bandwidth; the sum of caps can exceed the physical link.

3.7 Virtual machines and Docker containers

A virtual machine (VM) runs a full guest operating system on a hypervisor, so each VM carries its own kernel and drivers. A Docker container packs an application with its libraries but shares the host Linux kernel, using namespaces to hide processes and cgroups to cap CPU and memory. The VM gives a strong boundary and slow start; the container gives a small image and fast start with a weaker boundary. A UPI payment service can run many container copies on one host; a legacy banking application that needs its own kernel stays in a VM.

You need: the virtualization idea from 3.1 and the hypervisor role from 3.3.

The VM path: guest OS and hypervisor

A virtual machine (VM) is a software computer created by a hypervisor, the layer that owns the physical CPU, memory and devices. The hypervisor gives each VM virtual CPUs, a memory range, virtual disks and virtual network cards. The VM then boots its own guest operating system (guest OS): a full kernel, drivers and system services. The application sits above that guest OS. A Type 1 hypervisor sits directly on hardware; a Type 2 hypervisor runs as a program on a host OS, as in the figure.

This design gives strong isolation. Two VMs share hardware but not a kernel. A crash or kernel bug inside one guest OS does not directly reach another guest OS. The price is size and time. A VM image carries the guest OS, so it is often several GB before the application is added. Booting the guest OS takes seconds to minutes.

VM image = guest OS + app (+ any data baked into the image)

guest OS is the installed guest operating system size; app is the application and its libraries; any data baked into the image is stored data included in the image. All terms are in GB. Live application data usually lives on separate volumes and is not counted here.

Use a VM when the tenant needs a different kernel, a licensed operating system, or a hard boundary between customers. The hypervisor's own work is covered in 3.3.

The Docker path: shared kernel, namespaces, cgroups

Docker is a container platform; its engine starts containers from images. A container is one or more processes on the host, packed with their libraries and files, but it does not boot a guest OS. It uses the host kernel. The engine prepares a root filesystem from an image, then starts the process inside isolated views.

Two Linux kernel features do the work. Namespaces isolate what a process can see: the process ID namespace gives its own PID 1, the mount namespace gives its own filesystem tree, the network namespace gives its own interfaces, and the UTS, IPC and user namespaces isolate hostname, inter-process communication and user IDs. Cgroups, or control groups, limit and account for resources: CPU shares, memory ceilings, block I/O and process counts. A namespace is not a quota; a cgroup is not a hiding mechanism.

Images are built in layers. A base layer may hold a 100 MB Linux userland; an application layer adds 500 MB. Layers are read-only and shared. When a container writes, copy-on-write makes a private writable layer that stores only the changed data — whole files with overlay-style drivers, single blocks with block-level drivers — instead of the full image. Ten containers from one image therefore share the read-only layers instead of copying them ten times.

Some syllabi call this topic Docker containers, namespaces and cgroups. The limit is the shared kernel: a kernel vulnerability can cross containers, and a Linux container cannot run a Windows kernel. Unit 6 covers container security.

Choosing between the two

Use containers for stateless web servers, microservices, CI/CD build jobs and batch workers that need fast start and dense packing. Use VMs for legacy applications, different operating systems, untrusted tenants and workloads that need a separate kernel. Many clouds run containers inside VMs: the VM gives the tenant boundary, and containers give fast packing inside it. Running many containers across hosts needs orchestration; see Unit 5, Cloud Programming and Platforms.

Worked example

Question. A team must host 10 copies of an application. A VM design gives each copy a 2 GB guest OS and a 500 MB application. A Docker design uses one shared 100 MB base image and a 500 MB application layer per container. Compare total image storage for 10 instances, and find the saving in GB and as a percentage.

  2. VM storage per instance = 2 GB guest OS + 0.5 GB app = 2.5 GB.
  3. VM storage for 10 instances = 10 × 2.5 GB = 25 GB.
  4. Assume each copy has its own distinct application layer (for example, a different build), so only the 100 MB base is shared.
  5. Container shared base = 0.1 GB, counted once.
  6. Container app layers = 10 × 0.5 GB = 5 GB.
  7. Container storage for 10 instances = 0.1 GB + 5 GB = 5.1 GB.
  8. If all ten ran the identical image, the 500 MB app layer would also be shared and the total would be 0.1 GB + 0.5 GB = 0.6 GB.
  9. Saving = 25 GB − 5.1 GB = 19.9 GB.
  10. Percentage saving = (19.9 GB ÷ 25 GB) × 100 = 79.6%.

Exam traps

  • Containers share the host kernel. They are not lightweight VMs and do not give the same isolation boundary.
  • A VM image includes a guest OS, so it is much larger than a container app layer. Do not compare only the application size.
  • Namespaces isolate visibility, while cgroups limit resources. A namespace is not a CPU or memory quota.
  • Docker image layers are read-only and shared; the writable layer is per container and uses copy-on-write. The base is not copied ten times.
  • Watch units: 500 MB is 0.5 GB, and a shared base is counted once, not once per container.

The claim is false. Containers share the host kernel, so a kernel vulnerability can cross container boundaries. VMs have separate guest kernels. Containers are suitable for trusted workloads; stronger separation needs VMs, microVMs or extra sandboxing.

Understand What do namespaces do, and what do cgroups do? 3 marks

Namespaces isolate what a process can see, such as process IDs, mounts and network interfaces. Cgroups limit and account for resources such as CPU, memory and block I/O.

Apply Ten VMs each use a 3 GB guest OS and a 1 GB app. Ten containers use one 0.2 GB shared base; assume each container has its own distinct 1 GB application layer (for example, a different build). Find the saving in GB. What would the saving be if all ten ran the identical image? 4 marks

VM total = 10 × (3 + 1) = 40 GB. Container total = 0.2 + 10 × 1 = 10.2 GB. Saving = 40 − 10.2 = 29.8 GB. If all ten ran the identical image, the 1 GB app layer would also be shared: total = 0.2 + 1 = 1.2 GB, so saving = 40 − 1.2 = 38.8 GB.

Analyze Why does copy-on-write make many containers from one image cheap? 4 marks

Image layers are read-only and shared. Each container gets a small writable layer, and copy-on-write stores only the changed data — whole files with overlay-style drivers, single blocks with block-level drivers — instead of the full image. The full base is not copied per container, so disk use grows with changes, not with the whole image.

Beyond the syllabus

Not for the exam. Docker split into containerd and runc; the OCI image and runtime standards let other engines use the same images. Kata Containers and Firecracker microVMs put each container in a small VM to recover a stronger boundary. gVisor intercepts system calls in user space to reduce kernel exposure. WebAssembly runtimes now offer another sandbox for small functions. Search for OCI image spec, runc, Kata Containers, Firecracker and gVisor.

3.8 Virtual clusters and virtualized data centres

A virtual cluster is a logical group of virtual machines that is managed as one unit even though its VMs may sit on different physical hosts. A virtual data centre goes further: it gives a tenant a private view of pooled compute, storage and network drawn from a shared physical data centre. Both exist because physical hardware boundaries are too rigid and too large for one customer. Cloud providers use them to sell a slice of a building; private clouds use them to divide one building among departments.

You need: 3.1 for what a virtual machine is, 3.3 for the hypervisor layer, and 3.6 for pooled storage and network.

A virtual cluster is a logical cluster

A physical cluster is a set of hosts joined to shared storage and a network, managed as one pool: if a host dies, cluster software restarts its virtual machines elsewhere. A virtual cluster is the same idea one level up. It is a named group of virtual machines, taken from one or more hosts, managed together under one set of policies.

The group shares four things: a name and folder, a resource pool, a virtual network segment, and policies. The usual policies are high availability, which restarts a VM on a surviving host, and automated load balancing, which moves VMs when one host runs hot.

A resource pool is a container of CPU and RAM carved out of a parent host or cluster. It has three settings. A reservation is the guaranteed minimum, in MHz or GB, that the pool always gets. A limit is the maximum it may use. Shares are relative weights used only when the parent is contended: a pool with twice the shares of its sibling gets twice the contested capacity.

Virtual clusters exist because software expects several nodes. A Hadoop test cluster, a set of Kubernetes workers or a three-tier web application each wants N machines. Ten VMs on three hosts give the application its ten nodes without ten machines, and any node can be rebuilt from a template in minutes.

Remember what is logical here. Cluster membership says nothing about where the VMs sit. All ten VMs may share one physical host, and then one hardware failure takes the whole cluster down.

The virtual data centre: pooled resources and tenant isolation

A virtual data centre (VDC) is a tenant's private logical view of a data centre. It bundles a compute pool, a storage pool, a network pool, policies, quotas and a template catalogue, separated from every other tenant's VDC. The provider still owns the building, the hosts and the switches.

Build a VDC from pieces already covered: hosts grouped into clusters for compute, datastores built from LUNs or NFS exports for storage, overlay networks or VLAN segments for networking. Add role-based access so tenant A's administrator sees only tenant A's objects.

Isolation comes in layers. The hypervisor keeps the vCPUs and memory of different VMs apart. The network overlay keeps packets apart even when two VMs share one physical NIC. Storage zoning and LUN masking keep disks apart. No single layer is enough on its own.

A tenant is often sold more vCPU than the provider owns. That is oversubscription, and it is normal, because most VMs idle. A VDC described as 20 hosts of 16 vCPU may be placed on far fewer physical cores than 320.

Placement, migration, oversubscription and blast radius

Placement is the choice of host for each VM. Two rules shape it. An affinity rule keeps VMs together, for example a web server and its cache, to cut network delay. An anti-affinity rule keeps them apart, for example the two nodes of a database pair, so one host failure cannot take both.

Migration moves a running VM to another host. Live migration pauses the VM for milliseconds by copying memory pages while it runs; the mechanics belong to Unit 4. Providers use it for hardware maintenance, for balancing load across a cluster, and for emptying hosts at night to save power.

R = Σ vCPU ÷ Σ cores    U = requested capacity ÷ total capacity × 100%

R is the oversubscription ratio: the sum of all vCPU counts given to VMs divided by the total physical cores they can run on. R = 1 means no oversubscription; R = 4 means four virtual cores per real core. U is utilisation as a percentage, with capacity in cores, GB or MHz.

Admission control is the gatekeeper. When a tenant asks for a new VDC or an extra host, the manager adds the request to what is already committed, checks the reservations and limits of every pool, and refuses if a guarantee would break. It compares against committed capacity, not against the free memory of that second.

Blast radius is the set of things one failure destroys. Anti-affinity rules and separate clusters shrink it; a virtual cluster does not. A VDC narrows the tenant's blast radius from the physical site, but shared switches, shared storage arrays and shared power still remain.

Worked example

Question. A physical data centre has 50 hosts. Each host has 24 cores and 256 GB of RAM. A tenant asks for a virtual data centre of 20 hosts, each with 16 vCPU and 64 GB of RAM. (a) Find the physical and the requested totals. (b) Find the percentage of physical CPU and of physical RAM the request uses. (c) Should admission control accept the request, and what is the CPU oversubscription ratio?

  1. Physical cores = 50 hosts × 24 cores per host = 1,200 cores.
  2. Physical RAM = 50 hosts × 256 GB per host = 12,800 GB.
  3. Requested vCPU = 20 hosts × 16 vCPU per host = 320 vCPU.
  4. Requested RAM = 20 hosts × 64 GB per host = 1,280 GB.
  5. CPU use U = 320 ÷ 1,200 = 0.2667, that is 26.7%.
  6. RAM use U = 1,280 ÷ 12,800 = 0.10, that is 10.0%.
  7. Both values are well under 100%, so admission control accepts. CPU oversubscription ratio R = 320 ÷ 1,200 = 0.27, below 1, so the tenant is not oversubscribed on CPU.

Answer. The request fits: 320 vCPU is 26.7% of 1,200 cores and 1,280 GB is 10.0% of 12,800 GB, so the virtual data centre is admitted with no CPU oversubscription.

Exam traps

  • A virtual cluster is a logical grouping; it does not guarantee separate physical hosts or separate failure domains.
  • An oversubscription ratio above 1 is normal, not an error. Reservations and limits still bind, so check them before you conclude a request fits.
  • A virtual data centre is not a physical building. The tenant sees a private set of pools, but the provider owns every host.
  • Percentages are taken against the whole data centre total, not against one host. Dividing 320 by 24 cores is a classic slip.
  • Admission control compares the request against committed capacity minus reservations, not against the free memory at that instant.

3.9 Examples: Xen, VMware and Microsoft Hyper-V

Xen, VMware ESXi and Microsoft Hyper-V are Type 1 hypervisors. Each runs directly on the physical host and shares it among virtual machines. They differ in how they manage devices. Xen uses a privileged control domain called Dom0. VMware ESXi uses its own VMkernel. Hyper-V uses a privileged parent or root partition. These management domains are not ordinary guest workloads. The examples show real control-domain designs, not just product names. Use them to answer exam questions on hypervisor architecture and on the path a device request takes.

You need 3.3 for the hypervisor role and 3.4 for full and para-virtualization, including hypercalls.

Xen: Dom0, DomU, PV and HVM

Xen puts a small hypervisor directly on the hardware. The hypervisor schedules vCPUs, controls memory and delivers interrupts, but it does not hold full disk and network drivers. That work sits in a special virtual machine.

Dom0 is the first domain and the privileged control domain. It runs a full OS, device drivers and the toolstack that creates, starts and stops guests. DomU is an unprivileged guest domain. A DomU cannot read Dom0 memory or another DomU memory; the hypervisor enforces that boundary.

Xen guests run in two modes. A paravirtualized (PV) guest has a modified OS and uses hypercalls for privileged operations. An HVM (hardware virtual machine) guest is unmodified and uses hardware virtualization from Intel VT-x or AMD-V; QEMU, a device emulator in Dom0, emulates some devices for it. PV drivers can be added to an HVM guest to speed up disk and network I/O.

Device path in Xen: a DomU writes to a shared memory ring, a Dom0 backend driver reads it, and the Dom0 driver talks to the physical device. Dom0 is therefore both a control domain and often a driver domain. It consumes host CPU and RAM like any VM, but its privilege is much higher.

VMware ESXi: the VMkernel

VMware ESXi is a Type 1 hypervisor that runs on bare metal. Its core is the VMkernel. The VMkernel schedules vCPUs, manages memory, runs the storage stack, runs the network stack and loads physical device drivers. ESXi has no general-purpose service console; management comes from outside.

vSphere is the management suite around ESXi. vCenter Server is the central manager for many ESXi hosts. A vSphere Client or API talks to vCenter or to a single host. vSphere is not the hypervisor; ESXi is. This is a common exam confusion.

Device path in ESXi: a guest writes to a virtual NIC or virtual disk. The VMkernel receives that request, applies its virtual switch or storage rules, and calls the physical driver. The guest never programs the physical device directly. Isolation is enforced by the VMkernel, which keeps each VM's memory and virtual devices separate.

ESXi stores VM files on VMFS, a clustered file system, or on NFS. Live migration of a running VM is vMotion. These are management and storage features, not the definition of a Type 1 hypervisor.

Microsoft Hyper-V and the comparison

Microsoft Hyper-V is a Type 1 hypervisor, but it is installed with a Windows parent partition. The hypervisor runs beneath that partition. The parent partition, also called the root partition in newer documentation, runs Windows and the virtualization stack. It owns most physical devices and creates child partitions.

A child partition holds a guest OS. It has no direct hardware access. Hyper-V provides synthetic devices through VMBus, an in-memory channel between parent and child. The parent has a virtual service provider (VSP); the child has a virtual service client (VSC). A request goes child VSC → VMBus → parent VSP → parent driver → hardware. Emulated devices exist for boot, but they are slower.

Hyper-V is called a microkernel design because the hypervisor is small and drivers stay in the parent. Isolation is still enforced by the hypervisor: child partitions cannot access each other's memory or the parent's memory. The parent is privileged, not an ordinary guest.

Exam traps

  • Dom0 in Xen and the parent partition in Hyper-V are privileged management domains. They are not ordinary guest workloads, and their CPU and RAM count in host allocation.
  • ESXi is the Type 1 hypervisor. vSphere and vCenter Server are management products. Do not call vSphere the hypervisor in an exam answer.
  • Xen HVM does not mean no PV drivers. An HVM guest can use PV drivers for faster disk and network I/O; QEMU is mainly for emulated devices and boot.
  • VMBus is an in-memory communication channel, not a physical bus. A child partition reaches hardware through a parent VSP and a parent driver.
  • All three isolate guest memory, but they place drivers differently: Dom0, VMkernel, or parent partition. The placement changes the device path, not the need for isolation.

Takeaways

  1. Virtualization puts a software layer between hardware and operating systems so one machine behaves as many isolated machines.
  2. The hypervisor is the piece that partitions, schedules and isolates, and it can sit at hardware, OS, library or application level.
  3. Full virtualization runs an unmodified guest using trap-and-emulate or binary translation; para-virtualization runs a modified guest that makes hypercalls.
  4. CPU, memory and I/O each need their own virtualization trick: vCPU scheduling, two-level address translation, and shared or assigned devices.
  5. Hardware assists such as EPT, NPT and IOMMU remove most of the cost of trapping, which is why virtualization became cheap and common.
  6. Storage virtualization hides many disks behind one logical pool; network virtualization hides physical links behind logical ones.
  7. A VM carries a full guest OS and boots in minutes; a container shares the host kernel and starts in under a second.
  8. Containers are just processes held apart by namespaces and held in check by cgroups, which is why they are lighter but less isolated than VMs.
  9. A virtual cluster or virtual data centre is a tenant's logical view built out of VMs, virtual disks and virtual networks on shared hardware.
  10. Xen, VMware ESXi and Hyper-V all differ in where the control logic lives, but all three are Type 1 hypervisors running guests directly on the metal.
