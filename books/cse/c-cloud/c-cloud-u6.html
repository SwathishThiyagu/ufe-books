6.1 Cloud security threats, risks and attack vectors

Cloud security is a shared job. The provider protects the physical platform, the hypervisor and the network fabric. The customer protects identities, permissions, configurations, data and every exposed interface. An attacker needs one weak link: a reused password, a leaked API key, or a bucket policy set to public. This chapter defines threat, vulnerability, risk and attack vector. It maps common cloud attacks to the identity, network and storage layers. It uses the shared responsibility model to show why a provider control and a customer control must meet. You will use this map to review a cloud account or answer an exam question about a breach.

You need Unit 1's NIST cloud definition and service models, and Unit 2's web APIs and network basics.

Threat, vulnerability, risk and attack vector

Four words are often mixed. A threat is a possible cause of harm: a criminal, a worm, a careless employee. A vulnerability is a weakness that the threat can use: a weak password policy, an unpatched server, a bucket open to the internet. A risk is the chance and size of loss when a threat uses a vulnerability against an asset. An attack vector is the path or method used to reach the asset: a phishing email, a public API endpoint, a stolen key. Risk has two parts: likelihood and impact. In cloud work, the asset may be a bucket, a database, a VM or an identity. Exposure factor (EF) is the fraction of asset value lost in one incident. Single loss expectancy (SLE) is asset value × EF. Annual loss expectancy (ALE) is SLE × incidents per year. These numbers turn a vague fear into a budget question. If a bucket holds records worth ₹50,00,000 and one breach destroys 40% of that value, SLE is ₹20,00,000. Two incidents a year give ALE ₹40,00,000. The cloud attack surface is every interface a user, service or attacker can reach: consoles, APIs, SSH ports, bucket endpoints, IAM roles and third-party integrations. Each exposed interface must be authenticated, authorised, patched and monitored. The next section groups attacks by the layer they hit.

SLE = AV × EF; ALE = SLE × λ

AV is asset value in rupees; EF is exposure factor, a fraction from 0 to 1; SLE is single loss expectancy in rupees; λ (lambda) is incidents per year; ALE is annual loss expectancy in rupees per year.

Common attack vectors by layer

Credential theft hits the identity layer. Phishing, password reuse, leaked keys in code repositories and over-permissive roles let an attacker act as a valid user. MFA helps, but a stolen session token can bypass a password prompt. Short-lived credentials, least privilege and key rotation reduce this; see IAM and authentication. Misconfigured storage hits the storage layer. A bucket or blob container set to public read needs no exploit. Scanners find it. Missing logging is a second fault, so nobody sees the reads. Bucket policy, encryption and access logs are customer controls. Insecure APIs hit the network and application layer. A cloud is API-driven: every console click becomes a call. Missing input checks, weak tokens, exposed admin endpoints and no rate limit create paths. An API gateway with authentication, schema validation and throttling reduces this. DDoS hits availability. A flood of requests exhausts bandwidth, connection tables or application workers. Providers offer scrubbing and autoscaling, but a badly designed autoscale rule can raise cost. Co-residency hits isolation: two tenants share hardware, and a hypervisor or side-channel flaw may leak data. Providers patch hypervisors; customers patch guest OS and images. See VM security and secure isolation. Insider abuse comes from a provider or customer employee with legitimate access. Separation of duties, audit logs and least privilege limit it. Supply chain attacks enter through a compromised library, image, SaaS tool or provider, so you inherit their weakness. Signed images, software bills of materials and vendor review help. Map each vector to one layer for exam answers: identity for stolen keys, storage for public buckets, network for DDoS and APIs, isolation for co-residency, people and process for insider and supply chain.

Shared responsibility and the STRIDE checklist

The shared responsibility model splits controls. The provider is responsible for security of the cloud: physical sites, hardware, hypervisor, managed service code and the provider network. The customer is responsible for security in the cloud: identities, permissions, bucket policies, guest OS patches, data classification and application code. The split moves with the service model. In IaaS the customer patches the OS. In PaaS the provider patches the runtime, but the customer still protects code, secrets and data. In SaaS the provider runs the application, but the customer still manages users, sharing settings and data. The model is not a shield. A provider can pass every audit and a customer bucket can still be public. A customer can enable MFA and a provider API can still have a flaw. The meeting point is the interface: IAM policy, network rule, encryption key, API token. Test both sides there. STRIDE is a checklist, not a proof. It names six threat types: spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege. Use it to ask one question per component: can an attacker pretend, alter, deny, read, block or escalate? It does not rank risk or find every cloud path. Pair it with the attack-path view and monitoring and incident response.

Worked example

Question. A bucket policy grants read access to any authenticated user and holds 10,000 customer records. A stolen key provides that authenticated access. Asset value is ₹50,00,000, exposure factor is 0.4, and two such incidents happen a year. Find the single loss expectancy (SLE) and annual loss expectancy (ALE).

  1. Asset value AV = ₹50,00,000.
  2. Exposure factor EF = 0.4, so one incident loses 40% of asset value.
  3. SLE = AV × EF = ₹50,00,000 × 0.4 = ₹20,00,000.
  4. Incident frequency λ = 2 incidents per year.
  5. ALE = SLE × λ = ₹20,00,000 × 2 = ₹40,00,000 per year.

Answer. SLE is ₹20,00,000 and ALE is ₹40,00,000 per year.

Exam traps

  • A threat is not a risk. A threat is a possible cause of harm; risk combines likelihood and impact.
  • A vulnerability is not an attack. A public bucket is a weakness; a scanner reading it is the attack.
  • The provider secures physical hosts, but the customer still owns bucket policy, IAM and data classification.
  • A public bucket is usually a customer configuration error, not a provider platform breach.
  • DDoS damages availability, not confidentiality. Do not label it a data breach unless data was also read.

6.2 Security services: confidentiality, integrity, authentication, non-repudiation

A security service is a guarantee a system gives about its data and users. Cloud systems usually name four: confidentiality, integrity, authentication and non-repudiation. Many texts add availability, the A of the CIA triad, as a fifth. Each answers a different question, needs a different mechanism, and fails differently in the cloud. Every UPI payment and API call rests on separating these five.

You need Chapter 6.1 for the threat model, and Unit 1 for the provider–customer split of responsibility.

Four goals, four different questions

Confidentiality: only authorised parties can read data. It answers: who may see this? Integrity: changes are detected, accidental or malicious. It answers: has this been modified? Authentication: a party proves its identity. It answers: who are you? Non-repudiation: a party cannot later deny an action. It answers: can you deny this?

One tool can serve two goals, which is where exams and breaches go wrong. Encryption gives confidentiality. A keyed hash gives integrity and sender authentication. Only a digital signature or append-only log gives non-repudiation. Availability means the service is reachable when needed; an outage is an attack outcome.

Confidentiality and integrity in practice

Encryption turns plaintext into ciphertext using a key. Without the key, ciphertext is unreadable. It promises nothing else: an attacker who cannot read a message can still modify it. Encryption alone never gives integrity. Ciphers and key custody are in Chapter 6.3.

A hash compresses any message into a fixed-length digest: h = H(m). The receiver recomputes H(m) and compares. A plain hash fails over a network: an attacker changes the message, recomputes the hash, and sends the new pair. Integrity needs a secret.

A MAC keys the hash with a shared key. A digital signature uses the sender's private key; anyone verifies with the public key. AEAD, such as AES-GCM, encrypts and appends an authentication tag in one pass: confidentiality and integrity together.

HMAC(K, m) = H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ m))

H is a hash such as SHA-256, K is the shared secret, m is the message, ‖ means concatenation, and opad and ipad are fixed padding constants; the output is the MAC the receiver recomputes.

Cloud integrity checks appear as S3 ETags, multipart checksums, and TLS record tags. A common fault: storing object and checksum in the same bucket under the same write permission, so an attacker can rewrite both.

Authentication, authorization and non-repudiation

Authentication uses factors: something you know, have, or are. Two factors from two categories is MFA. Authorization decides what an authenticated principal may do; IAM is Chapter 6.5, MFA and SSO are Chapter 6.6.

Non-repudiation is strictest. A MAC cannot give it: both sides hold the key, so either could produce it. A digital signature can: only the private-key holder signs, anyone verifies, and it binds to the exact message. A tamper-evident audit log — append-only or WORM storage, separate account, synchronised timestamps — preserves the record.

Use the deny question. A customer says I never made that transfer. Encryption hides content but names no person. A MAC fails because the bank could compute it. Only a signature with the customer's private key, or a log the bank cannot silently edit, proves otherwise. Payment systems sign; audit trails live in object-locked storage (Chapter 6.9).

Exam traps

  • Saying encryption gives integrity. An attacker who cannot read a message can still flip bits in it. Only a hash, MAC, signature or AEAD tag detects that.
  • Saying a hash authenticates the sender. A plain hash is public arithmetic; anyone can change the message and recompute it. Keying it (HMAC) or signing it adds authentication.
  • Confusing authentication with authorization. Login proves who you are; IAM decides what you may touch. A user can log in correctly and still be denied a bucket.
  • Claiming a MAC gives non-repudiation. Both sides hold the same symmetric key, so either could have produced it; only a digital signature separates the parties.
  • Forgetting availability. The CIA triad has an A, and an outage from DDoS or a single-region design is a security failure, not just an operations problem.

6.3 Encryption and key management in the cloud

Encryption turns readable data into ciphertext that only a key holder can reverse. In the cloud the cipher is the easy part; the hard part is where the keys live and who may use them. A provider that stores your ciphertext and your key in the same place has protected nothing. This chapter covers the ciphers used in practice, the key hierarchy of root keys, key encryption keys and data encryption keys, the lifecycle operations of rotation, revocation, escrow and bring-your-own-key, and the certificates that carry public keys.

You need: 6.2 for confidentiality and integrity, and Unit 2 for TLS and web services.

Two ciphers, two jobs

A symmetric cipher uses one key for both encryption and decryption. AES is the standard choice: it works on 128-bit blocks and takes a key of 128, 192 or 256 bits. In AES-256-GCM the same key encrypts the data and produces a 16-byte authentication tag, so any edit to the ciphertext makes decryption fail. That gives confidentiality and integrity in one mechanism, the goal set out in 6.2. A server CPU with AES instructions moves several gigabytes per second.

An asymmetric cipher uses a key pair. RSA-2048 and elliptic-curve keys such as P-256 are common. Data encrypted with the public key opens only with the private key; a signature made with the private key is checked by anyone holding the public key. Asymmetric operations cost far more per byte, so they carry only small items: key transport, key agreement and signatures.

TLS joins the two. The handshake uses asymmetric keys, or the ECDHE key-agreement exchange, to fix a shared secret. Both sides derive session keys from it, then application data flows under AES-GCM or ChaCha20-Poly1305. That protects data in transit. Data at rest never travels, so it is protected by AES directly, under a key from the hierarchy below.

Envelope encryption and the key hierarchy

A hardware security module (HSM) is a tamper-resistant device that generates and holds keys and does crypto inside its own boundary; a key marked non-exportable can never leave it. An HSM is slow and costly per operation, so multi-megabyte objects cannot pass through it. Envelope encryption layers the keys instead.

  1. The key management service (KMS) generates a data encryption key (DEK), for example 256 bits for AES-256-GCM.
  2. The storage node encrypts the object with that DEK and writes ciphertext plus the 16-byte tag; the plaintext DEK lives only in memory.
  3. The KMS wraps (encrypts) the DEK with a key encryption key (KEK) using AES key wrap or AES-GCM; the wrapped DEK goes into the object's metadata.
  4. A reader sends the wrapped DEK back to the KMS, receives the plaintext DEK over TLS, decrypts the object and wipes the DEK.
  5. The KEK is itself wrapped by a root key held inside the HSM and never exported.

The KMS now sees 60-byte blobs instead of gigabytes, so one tenant KEK wraps a thousand DEKs cheaply. Rotation follows the same lines: a new KEK means rewrapping the DEKs, a new DEK means re-encrypting the object.

Key lifecycle: rotation, revocation, escrow and custody

Rotation replaces a key with a fresh one on a schedule or after an incident. Rotating a DEK re-encrypts the object, a full pass over the data. Rotating a KEK only unwraps and rewraps each DEK, kilobytes of work. Rotation caps how much data one key protects and shortens the life of a leaked key.

Revocation disables a key, so the KMS refuses to unwrap with it. Revoke a KEK without first rewrapping its DEKs and every object beneath it becomes unreadable until the old KEK is re-enabled. Revocation alone is reversible, so it is not crypto-shredding. Crypto-shredding is the destruction of the key: if the key is destroyed and no copy exists anywhere, the objects stay unreadable forever. Destroying one key wipes out petabytes. Retention rules in 6.4 use crypto-shredding deliberately.

Escrow keeps a copy of a key with a third party or offline, so data survives a lost HSM or a departed administrator. Custody is where the key material physically sits. In BYOK (bring your own key) you generate the key and import it into the provider's KMS, stored inside the provider's HSM. In HYOK (hold your own key) the key stays in your own HSM and the provider calls out for every unwrap, so it never enters the provider at all. Who may call the key is an access-control question, see 6.5.

Certificates and chains of trust

A public key alone proves nothing about who owns it. A certificate is a signed statement binding a public key to an identity: subject name, public key, issuer, serial number, validity dates, and the issuer's signature over all of it. The common format is X.509.

Certificates form a chain. The server presents its leaf certificate; the leaf is signed by an intermediate CA; the intermediate is signed by a root CA; the root certificate is pre-installed in the client's trust store. The client walks the chain, checks each signature, checks that the name matches the host it dialled, checks the dates, and checks revocation through a CRL or an OCSP responder. A cloud load balancer terminates TLS for you, so the chain configured on that balancer is part of your security surface.

Worked example

Question. A tenant bucket holds 1,000 objects of 4 MB each. Every object has its own 256-bit AES-GCM data encryption key (DEK). All 1,000 DEKs are wrapped by one tenant KEK, and a stored wrapped DEK occupies 60 bytes. The tenant rotates the KEK. Find (a) how many objects must be re-encrypted, (b) how many bytes of wrapped DEKs are rewritten, (c) how many bytes of object data a full DEK rotation would rewrite, and (d) the factor by which KEK rotation reduces the work.

  1. KEK rotation rewraps DEKs only and never touches stored ciphertext. Objects re-encrypted = 0.
  2. Wrapped DEK bytes rewritten = 1,000 × 60 bytes = 60,000 bytes = 60 kB.
  3. Object data under a full DEK rotation = 1,000 × 4,000,000 bytes = 4,000,000,000 bytes = 4 GB (taking 1 MB = 10⁶ bytes).
  4. Work ratio = 4,000,000,000 ÷ 60,000 = 66,666.67, so about 66,667 times less work.

Answer. Zero objects are re-encrypted, 60,000 bytes (60 kB) of wrapped DEKs are rewritten, against 4,000,000,000 bytes (4 GB) for a full data re-encryption — roughly 66,667 times less work.

Exam traps

  • A key stored beside the ciphertext — same bucket, same database row, same config file — protects nothing. The attacker who takes the data takes the key with it.
  • Rotating a KEK rewraps DEKs and does not re-encrypt data; rotating a DEK does re-encrypt the object. Exam questions swap these two on purpose.
  • Encryption alone gives confidentiality, not integrity. AES-CBC without a MAC can be edited and still decrypt; use AES-GCM or encrypt-then-MAC.
  • Revoking a KEK before rewrapping its DEKs makes every object under it unreadable until the old KEK is re-enabled, and rotating that key does not help because the new KEK never wrapped those DEKs. Only destroying the key with no copy left is crypto-shredding, and that loss is permanent.
  • Tokenization replaces a value with a surrogate that has no mathematical relation to it; it is not encryption and is handled in 6.4.

Beyond the syllabus

Not for the exam. In industry the hierarchy is standardised: KMIP is the protocol many KMS products speak, and an external key store lets a provider call into a customer HSM at unwrap time. Post-quantum key encapsulation, standardised by NIST in 2024, is being added to TLS handshakes because a recorded session can be broken later by a quantum computer. Crypto-agility, designing so a cipher or key size can be swapped without redesign, is the practical skill to search next, along with 'KMIP', 'external key store' and 'confidential computing'.

6.4 Data security, data protection and data retention

Data security protects data through its lifecycle: classify it, control who can read it, encrypt or mask it where needed, keep it only as long as a policy allows, then delete or archive it safely. Data protection is the legal and policy duty to safeguard personal data and honour the data subject's rights, such as consent, purpose limitation and erasure. Data security is the set of technical and organisational controls that carry out that duty. Data retention is one rule inside that duty: it decides lifetime. Cloud storage makes copies cheap and fast, so deletion must reach backups, snapshots and replicas too. Use this when you design log retention, customer records, card data or tenant storage.

You need: Unit 4 cloud storage, replication and backups, and 6.3 encryption and key management.

Classify data, then reduce exposure

Data classification labels data by sensitivity so controls can follow the label. Four common classes are public, internal, confidential and restricted. A public price list needs little control; a restricted customer record needs strict access and audit. Classification is the first step because you cannot protect every byte the same way without wasting money or slowing work.

  • Data loss prevention (DLP) inspects content and blocks or logs the movement of sensitive data, for example a card number leaving a web form.
  • Tokenization replaces a value with a token and keeps the real value in a separate vault. A payment service can store a token instead of a card number.
  • Redaction removes or masks fields before sharing data with test teams or reports.
  • Obfuscation replaces sensitive fields with realistic but false values while keeping the format, so tests still run.

Encryption is covered in 6.3, but the idea here is selective use. Encrypt restricted data at rest and in transit, tokenize values that must never sit in an application store, and redact before copying production data to a test environment. Access control decides who may read the data after these controls; that is 6.5 IAM.

Retention policy, legal hold and the log timeline

A retention policy states, for each data class, how long the data must exist, where it lives, who approves deletion and how it is deleted. Retention is a business and legal rule, not just the storage lifetime. A legal hold is a directive that suspends deletion for an investigation or dispute, even after the normal retention period ends.

R = Vd × Da + (Vd × Dr) ÷ C

R is the total stored volume at the end of the archive period, in GB (active copies plus compressed archive copies); Vd is the daily data volume in GB per day; Da is active days; Dr is archive days; C is the compression ratio. Deletion, backups and tenant separation

Deleting the live copy is not deletion if backups, snapshots or replicas still hold the data. A backup lifetime is the recovery window; it can differ from the retention period. A backup may outlive retention, so the deletion job must also expire backups and snapshots. Secure disposal of physical media and crypto-shredding, which destroys the key so ciphertext cannot be read, close the last copies.

  1. Freeze new writes for the data set and open a deletion ticket.
  2. Find every copy: live store, snapshots, backups, replicas, caches and search indexes.
  3. Check legal holds; if a hold applies, stop.
  4. Delete or crypto-shred each copy; verify by sampling.
  5. Expire keys and media, then log the result for audit in 6.9.

Tenant data separation keeps one customer's data away from another in a shared cloud service. Use per-tenant encryption keys, separate partition keys or table prefixes, and IAM conditions that limit each request to one tenant. These controls must hold for backups and archives too, because a copy that ignores tenant labels leaks data even when the live store is correct.

6.5 Identity and access management (IAM)

Identity and access management (IAM) is the cloud control plane that answers one question for every request: may this principal perform this action on this resource under these conditions? It exists because a network boundary cannot protect a shared, API-driven cloud; every call must be checked. IAM is used when an analyst opens a finance dashboard, a service account reads a queue, or a partner account assumes a role across accounts. It ties identities, policies and conditions into an auditable decision: allow or deny.

You need: 6.2 authentication for who a principal is, and Unit 1 roles and boundaries for what a cloud account owns.

Identities, principals and policies

An IAM system has four parts: identities, resources, actions and policies. An identity is a principal that can make a request. A user is a long-lived identity for a person. A group is a collection of users that shares permissions. A role is a set of permissions that a principal assumes for a limited time; it is not a person. A service account is an identity for a workload, such as a billing job that reads a queue. A resource is the object being accessed, for example a finance table. An action is the operation, for example read. A policy is a rule that binds effect, principal, action, resource and condition. The effect is Allow or Deny; a condition can require a source IP range, a time window or an MFA result. RBAC assigns permissions to roles and roles to users or groups. It is simple and matches job functions, but it can be coarse. ABAC writes policies over attributes of the principal, resource and request context. It is finer and more complex. Least privilege grants only the actions, resources and time needed for the task. Separation of duties ensures no single identity can both request and approve a sensitive action, such as a payment.

Evaluating a request

Every request carries a principal, an action, a resource and context such as source IP and session details. The IAM engine collects every policy that matches the request. It applies three rules. First, the default is deny: if no policy allows the request, the answer is Deny. Second, an explicit Deny beats every Allow. Third, the request is allowed only if at least one Allow matches and no Deny matches.

Decision = Allow if (∃ Allow) ∧ (¬∃ Deny); otherwise Deny

∃ Allow means at least one matching Allow statement; ¬∃ Deny means no matching Deny statement; ∧ means both conditions must hold.

Conditions narrow an Allow: the principal may read only when MFA is present (see 6.6) and the source IP is inside 10.0.0.0/8. The figure shows this gate sequence. The engine checks the MFA result, then the IP range, then the role permission; one failed gate gives Deny. A policy that says Allow read on finance data is not enough if its condition fails. This is why IAM reviews test both the policy text and the request context.

Temporary trust and privilege escalation

Long-lived access keys are a risk. IAM therefore issues temporary credentials: a trusted principal asks the identity service for a short-lived token, and the token carries the permissions of a role. Cross-account trust uses this mechanism. Account A creates a role and a trust policy that names a principal in account B. A user or service in B calls the role-assumption API, receives temporary credentials, and acts in A with only the role's permissions. Two policies matter: the trust policy decides who may assume the role, and the permissions policy decides what the role may do. Privilege escalation is the path from limited access to greater access. Typical paths are changing a policy that protects the identity, creating a new role with more power, passing a powerful role to a compute service, or assuming a role that trusts the identity. Controls include permissions boundaries, deny statements on policy changes, separation of duties for role creation, and regular review of trust policies. End-to-end access control checks every hop: user to API, service to service, and service to data.

  • A role is a set of permissions assumed for a time, not a user. Do not treat a role name as a person's account.
  • Default deny means a missing policy is not permission. If no Allow matches, the request is denied.
  • 10.0.0.0/8 covers 10.0.0.0 to 10.255.255.255 only. 192.168.x.x is private but not in that range, so it fails the condition.

6.6 Authentication: multi-factor, single sign-on, identity federation

Authentication proves a principal is who it claims. Cloud users open many apps, so they face many logins. Multi-factor authentication (MFA) adds a second proof beyond a password. Single sign-on (SSO) lets one login open many apps. Identity federation lets a trusted identity provider (IdP) vouch for the user to each service provider (SP). Used in Google Workspace, Microsoft 365, AWS IAM Identity Center and campus logins.

You need 6.5 IAM and Unit 2 web services.

MFA: knowledge, possession, inherence

MFA combines proofs from different categories. Knowledge is something you know: a password or PIN. Possession is something you have: a phone, smart card or hardware key. Inherence is something you are: a fingerprint or face. Two passwords are not MFA; they are one factor twice.

A time-based one-time password (TOTP) is a possession factor. The server and token share a secret key K. The counter T advances every 30 seconds. The token computes a 6-digit code from K and T. The server recomputes it and accepts a small clock-skew window.

T = floor((t − T₀) ÷ 30); code = HOTP(K, T)

t is Unix time in seconds; T₀ is the start epoch; K is the shared secret; HOTP is the HMAC-based one-time password truncated to 6 digits.

A push factor sends a notification to a registered app; the user taps approve. Push is easy but enables MFA fatigue: repeated prompts until someone taps by mistake. FIDO uses public-key cryptography. The private key stays on the device; the server stores the public key. The device signs a challenge that includes the website origin, so a phishing site cannot replay it.

SSO, federation, SAML and OIDC

Single sign-on (SSO) is one authentication event for many applications. After login, the IdP gives the browser a session cookie or the app a token. Each app trusts that session instead of asking for a password again.

Federation is the trust agreement behind SSO. The identity provider (IdP) authenticates the user and issues a signed statement. The service provider (SP) is the app. The SP checks the IdP's signature, the audience and the expiry, then creates a local session.

SAML is an XML-based federation protocol used by enterprise apps. The IdP sends a signed SAML assertion in the browser flow. OpenID Connect (OIDC) is a newer identity layer on OAuth 2.0. OAuth 2.0 handles authorization: access tokens for APIs. OIDC adds an ID token, a JSON Web Token (JWT), with claims such as sub (subject), iss (issuer), aud (audience) and exp (expiry). Claims are statements about the user.

The trust has risks. A stolen session cookie or bearer token lets an attacker act as the user until expiry. A misconfigured SP may accept a token meant for another app. The IdP is a single point of failure and a high-value target: compromise it and every trusting app is exposed.

Worked example

Question. A user opens 3 SaaS apps that trust one IdP. The IdP requires a password plus a 6-digit TOTP. The SSO session lasts 8 hours. The workday is 8 hours. How many TOTP entries are needed in the workday, and how many signed assertions does the IdP send?

  1. Apps trusting the IdP = 3.
  2. Sessions per workday = workday ÷ SSO session lifetime = 8 h ÷ 8 h = 1.
  3. TOTP entries = sessions × 1 TOTP per login = 1 × 1 = 1.
  4. Signed assertions = apps × sessions = 3 × 1 = 3.

Answer. The user makes 1 OTP entry in the workday, and the IdP issues 3 signed assertions.

Exam traps

  • SSO is not MFA. SSO reduces repeated logins; MFA strengthens the one login. A system can have SSO with only a password.
  • OAuth 2.0 is for authorization, not authentication. OpenID Connect adds the ID token that authenticates the user. Using an OAuth access token as proof of identity is a common exam error.
  • Federation trust is transitive risk: if the IdP is compromised, every SP trusting it accepts the attacker. A wrong audience or redirect URI lets a token be replayed to another app.
  • A 6-digit TOTP is one factor. It becomes MFA only when paired with a different factor such as a password. The code is valid for a short time step, usually 30 seconds, with clock skew.
  • A SAML assertion is signed, not encrypted by default. A stolen bearer assertion can be replayed until it expires.

6.7 Virtual machine security and secure isolation

Virtual machine security keeps one tenant's VM from reading, changing, or reaching another tenant's VM on shared hardware. The hypervisor draws the first boundary, but images, management APIs, snapshots, and live migration cross it. Isolation is therefore designed: hardened images, least privilege, patched guests and hypervisors, segmented virtual networks, and protected migration. Cloud providers use it in IaaS and private cloud, where many customers share physical hosts. The goal is not only a strong hypervisor but tested separation of every path between tenants.

You need Unit 3 on hypervisors and virtual machines and 6.1 on cloud threats.

Where VM isolation is built

A type-1 hypervisor runs directly on the physical host and gives each virtual machine (VM) virtual CPU, memory, disk, and network interface. The guest operating system inside the VM believes it owns a real machine. The hypervisor traps privileged instructions and keeps each VM's memory ranges apart. A virtual NIC (vNIC) connects a VM to a virtual switch. The switch forwards frames to other VMs on the same host or to the physical network. The management plane is the control API that creates VMs, attaches disks, takes snapshots, and starts live migration. It is powerful, so it needs strong authentication and role-based least privilege.

Secure isolation is built in layers:

  • Physical host: firmware, baseboard management controller (BMC), and boot chain must be patched and restricted.
  • Hypervisor: patch the virtual machine monitor (VMM) and virtual switch; remove unused virtual hardware.
  • Management plane: separate admin roles, use multi-factor authentication, log every API call.
  • Guest and image: harden the guest OS, patch it, disable unused services, and keep secrets out of the image.

One weak layer can expose all VMs on the host, so control each layer separately.

How isolation fails

An attacker who controls one VM tries to cross the boundary. A VM escape is an exploit that breaks out of the guest and runs code in the hypervisor or host. It is rare but severe: one escape can reach every VM on the host. Co-residency is sharing one physical host with another tenant. Co-residency alone is normal in cloud; cache-timing and other side channels can still leak small amounts of data if the hypervisor and CPU mitigations are weak.

Other paths cross the boundary by design. A snapshot copies disk state and sometimes memory; it can contain passwords, session tokens, keys, and personal data. A clone copies the VM identity, including host keys, local accounts, and agent tokens. Live migration sends memory pages over a network; without encryption and mutual authentication, an attacker can read or alter them. Templates and images can carry default accounts or old packages.

Network isolation is separate from VM isolation. Two VMs on one host can still reach each other through the virtual switch unless policy denies it. Inter-tenant segmentation places tenant A on 10.1.0.0/24 and tenant B on 10.2.0.0/24, then applies a default-deny rule between the segments. Microsegmentation adds rules per VM or per workload, for example allow only TCP 443 from A-web to A-db. The hypervisor isolates memory; the network policy isolates reachability. You need both.

Designing and testing secure isolation

Secure isolation strategies combine hardening, least privilege, segmentation, and evidence. Use this order:

  1. Harden the golden image: remove default accounts, disable unused services, install current patches, and add a monitoring agent.
  2. Patch in two tracks: guest OS patches by the customer, hypervisor and firmware patches by the provider. Track both in a register.
  3. Apply least privilege to the management plane: create VM, snapshot, and migrate are separate permissions.
  4. Segment traffic: default deny between tenants; allow only named flows; log denied packets.
  5. Protect copies: encrypt snapshots, restrict who can restore them, rotate secrets after cloning, and expire old images.
  6. Protect migration: use encrypted channels, mutual authentication, and a dedicated migration network.
  7. Test: run escape and policy tests, review audit logs, and verify that a VM cannot reach another tenant's segment.

Virtualization strategy matters. Prefer current hypervisor versions with CPU mitigations enabled. Do not mix tenants of different trust levels on one host when policy forbids it. Containers add another isolation boundary: they share the host kernel, so a kernel bug can cross containers more easily than a hypervisor boundary. Use containers for speed, VMs for stronger separation, and combine them when needed.

6.8 Security design patterns: cloud bursting, secure interfaces

A design pattern is a reusable arrangement of components that stops a known problem from coming back. Cloud bursting is one: a private cloud carries the steady load and, at a peak, the overflow goes to a public cloud. Secure interfaces are the other: every call that crosses a trust boundary passes an API gateway that checks identity, encrypts traffic, validates input and limits rate. Together they keep identity, data and traffic controlled while a workload crosses trust domains. Ticketing sites use this on match day; banks on salary day.

You need: 6.3 encryption, 6.5 IAM, 6.6 federation, and elasticity from Unit 2.

Cloud bursting: trigger, broker, tunnel

Bursting keeps the steady load in a private cloud and sends only the overflow to a public cloud for as long as the peak lasts. The trigger is a threshold on a measurable signal: requests per second, queue depth, or CPU. A private cloud built for 100 req/s starts bursting when the five-minute average passes 100 and stops at 80, so it does not switch on and off at the boundary. Only a few universities teach this pattern.

burst requests = (peak rate − base rate) × burst duration

peak rate is requests per second at the top of the peak; base rate is what the private cloud serves; burst duration is in seconds.

  1. Set the trigger with hysteresis: start at 100 req/s, stop at 80 req/s.
  2. Route the decision through the burst broker. It is the only component allowed to create public-cloud resources, it holds the credentials, and it checks policy: tenant, region, spend cap.
  3. Keep one identity. The private identity provider issues short-lived tokens that the public cloud accepts, so no long-term keys are copied across.
  4. Carry traffic in a secure tunnel: IPsec or TLS between the two clouds, and the public side accepts connections only from that tunnel.
  5. Encrypt data before it leaves, with a key the customer holds. Better still, send code to the data, not data to the code.
  6. Write egress rules as an allow-list: the public side may call only named endpoints; everything else is denied.
  7. Drain on exit: stop new work, finish running work, wipe instance storage, revoke tokens, log the burst.

Secure interfaces: gateway, mTLS, scopes

An interface is secure when the caller is authenticated, authorised for exactly that action, and cannot overload or corrupt the backend.

  • API gateway: one entry point. It terminates TLS, authenticates the caller, applies quota, validates and routes. Backends stay private.
  • Mutual TLS: client and server both show certificates. Plain TLS proves the server only; mTLS proves both ends, which is what service-to-service calls need.
  • OAuth scopes: the token carries scopes such as read:orders. The scope limits what the token can do, so ask for the narrowest one.
  • Input validation: check type, length, range and encoding on the server, before the request reaches the backend.
  • Rate limits: per key, per IP, per tenant; answer 429 when exceeded. This caps credential stuffing and surprise bills.

An API key shipped inside a mobile app is not a secure interface. Anyone can extract it, and TLS protects the bytes in transit but decides nothing about who may do what.

Worked example

Question. A private cloud is sized for 100 requests/s. A cricket final pushes peak load to 150 requests/s for 2 hours. The broker bursts the overflow to a public cloud at ₹0.001 per request. How many requests go to the public cloud, and what does the burst cost?

  1. Overflow rate = 150 − 100 = 50 requests/s.
  2. Duration = 2 h × 3,600 s/h = 7,200 s.
  3. Burst requests = 50 requests/s × 7,200 s = 360,000 requests.
  4. Cost = 360,000 × ₹0.001 = ₹360.

Answer. 360,000 requests go to the public cloud, costing ₹360.

Exam traps

  • Bursting without federated identity and encrypted data copies tenant data into a second trust domain, where the first cloud's controls do not reach.
  • An API key inside a mobile app is not a secure interface; it is a password printed on the box.
  • TLS protects data in transit. It does not authorise: a valid certificate says nothing about permission.
  • A broker holding permanent admin keys in the public cloud turns one compromise into two. Use short-lived tokens.
  • Without hysteresis the workload flaps across the boundary and cost doubles.

6.9 Monitoring, auditing and incident response

Monitoring gives evidence: logs, metrics and traces record what happened. Auditing proves a control worked by comparing that evidence with policy. Incident response uses both to limit damage in a repeatable loop: detect, contain, eradicate, recover, then learn. Every cloud deployment needs this loop. A UPI payment gateway in Chennai watches failed transactions, a booking site watches a ticket-release spike, and a regulator asks for the audit trail months later. The same evidence supports an SLA claim and a forensic investigation.

You need: 6.1 threats, 6.2 non-repudiation and 6.5 IAM.

Logs, metrics and traces

Monitoring rests on three signals. A log is a timestamped record of one event: who called an API, which login failed, which firewall rule dropped a packet. A metric is a number sampled over time: CPU percent, requests per second, error count. A trace follows one request across services and shows where the time went. The three answer what happened, how much, and where.

Cloud providers keep audit trails. An audit trail records control-plane actions: create a bucket, change an IAM role, delete a key. Each entry has a principal, an action, a resource, a time and a result. For non-repudiation the trail must be append-only and read-restricted; see 6.2. The provider logs its control plane. The customer logs the guest OS, the application, data-plane access and the identity provider. Collect both.

An audit picks one control, for example only admins can delete buckets. It tests the control against the audit trail for a chosen period, samples entries, and records pass or fail with the evidence used. The record names the control, the period, the sample and the result.

Every log line carries a timestamp. Clocks drift, so all sources sync to one time service (NTP). Without sync, two events minutes apart can appear reversed, and an attacker can hide a sequence. Set retention before you need it: a 7-day window cannot prove a breach that began a month ago. Logs also hold personal data, so redact and restrict them under your retention policy (see 6.4).

Alerting and SIEM

A SIEM (security information and event management) system collects logs from many sources, normalises them, correlates rules, and raises alerts. Example rule: five failed logins from one IP in one minute, then a success. Correlation across sources is the point. A single log line is weak evidence.

Two clocks matter. MTTD (mean time to detect) is the average delay from incident start to alert. MTTR (mean time to recover) is the average delay from incident start to restored service. The two measure different things: MTTD stops at the alert, MTTR runs to restored service. A fast alert alone does not shorten repair, but because MTTR is counted from incident start, faster detection usually does cut downtime.

MTTD = (1/N) Σᵢ (t_alert,i − t_start,i); MTTR = (1/N) Σᵢ (t_recover,i − t_start,i)

N is the number of incidents; t_alert,i is the alert time for incident i; t_start,i is its start time; t_recover,i is its restored-service time; all times use the same unit, usually minutes.

An alert triggers a runbook: a short, tested procedure that says who to call, what to capture and what to disable. Automation can quarantine a VM or revoke a token. Keep a human approval for destructive steps. False positives waste time, so tune rules against a baseline of normal behaviour.

Incident response phases

Incident response follows six phases. Some syllabi use six phases (prepare, detect, contain, eradicate, recover, learn); the NIST guide groups the same steps into four, with containment, eradication and recovery as one phase. Prepare: roles, contacts, runbooks, backups. Detect: alert triage and scope. Contain: isolate the instance, disable the credential, block the IP. Eradicate: patch, rebuild, rotate keys. Recover: restore service and verify integrity. Learn: write the post-incident review and fix the gap.

Preserve evidence before you destroy it. Volatile evidence (memory, running processes, network connections) disappears on reboot. Take a disk snapshot, compute a cryptographic hash, and record who handled it and when. That record is the chain of custody. Do not delete the instance to 'clean up' before the snapshot is verified.

Provider and customer duties split. The provider investigates its platform and supplies audit logs. The customer investigates its own identities, configurations and data. SLA reports come after the fact: uptime, response time and notification time. A provider can meet 99.9% monthly uptime measured across all regions, or over a year, and still have a 3-hour outage in your region. Read the SLA's measurement point and period before you accept the dashboard number.

Worked example

Question. An incident starts at 09:00. An alert fires at 09:10, the incident is contained at 09:30, and service is recovered at 12:00. Use the response timeline in the figure (detect 0–10 min, contain 10–30 min, eradicate 30–90 min, recover 90–180 min). Find detection time, time to containment, containment phase duration and total downtime in minutes and hours.

  1. Detection time = alert time − incident start = 09:10 − 09:00 = 10 min.
  2. Time to containment = contained time − incident start = 09:30 − 09:00 = 30 min. Containment phase duration from the figure = 30 min − 10 min = 20 min.
  3. Total downtime = recovered time − incident start = 12:00 − 09:00 = 3 h = 180 min.
  4. Eradication window from the figure = 90 min − 30 min = 60 min; recovery window = 180 min − 90 min = 90 min.

Answer. Detection = 10 min, time to containment = 30 min, downtime = 180 min = 3 h; containment phase lasts 20 min, eradication takes 60 min and recovery 90 min.

Exam traps

  • Unsynchronised clocks make log correlation unreliable: two events can appear in the wrong order, so an attack sequence looks innocent.
  • MTTD is not MTTR. MTTD measures start-to-alert delay; MTTR measures start-to-recovery delay. Containment is not recovery.
  • Provider audit logs cover the control plane. Guest OS logs, application logs and data-plane access are the customer's responsibility.
  • Rebooting a compromised VM or deleting the instance destroys volatile evidence; snapshot and hash first, then eradicate.
  • Short log retention defeats auditing. A breach discovered after the retention window leaves no usable trail.

Takeaways

  1. Cloud security is shared: the provider hardens the platform, while the customer owns identity, configuration and data.
  2. A threat needs a vulnerability and a path; closing any one of the three removes the risk.
  3. Confidentiality, integrity, authentication and non-repudiation each need a different mechanism, and each fails differently in the cloud.
  4. Encryption is only as strong as the key hierarchy and who holds the root key.
  5. Data protection follows the data lifecycle: classify, control access, encrypt or redact, retain, then delete or archive safely.
  6. IAM is the main control plane in the cloud; least privilege and short-lived credentials cut most attack paths.
  7. MFA strengthens one login, SSO reduces repeated logins, and federation moves the trust decision to one identity provider.
  8. Hypervisor isolation is necessary but not sufficient; shared hardware, images and migration paths need their own controls.
  9. Monitoring gives evidence, auditing proves control, and incident response is a repeatable loop: prepare, detect, contain, eradicate, recover, learn.
  10. Cloud bursting and secure interfaces keep identity, data and traffic controlled when a workload crosses a trust boundary.
