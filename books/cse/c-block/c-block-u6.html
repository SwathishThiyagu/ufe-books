6.1 Hyperledger frameworks and the Fabric model

Hyperledger is an open-source family of permissioned blockchain frameworks. It exists because enterprises need shared ledgers with known members, not anonymous miners. Hyperledger Fabric is the best known: a channel runs on peers, orderers and cryptographic identities, and a transaction commits only when an endorsement policy is met. Banks, exporters and insurers use this model when they must agree on records without exposing them to the public internet.

You need Unit 1's private and consortium blockchain types and Unit 3's transaction life cycle, plus 6.2 for the contract side.

The Hyperledger family

Hyperledger is not one blockchain. It is an umbrella project hosted by the Linux Foundation. Common frameworks include Fabric for general enterprise ledgers, Sawtooth for modular transaction families, Indy for decentralized identity, Besu for Ethereum-compatible enterprise chains, and Iroha for small trusted networks. Each has a different design goal, so the names are not synonyms.

Two tools sit around the frameworks. Explorer reads a ledger and shows blocks and transactions. Caliper measures throughput and latency, so a team can compare a chaincode change with a baseline.

The building blocks are the same ideas under different names. Some syllabi call them components.

  • Ledger: the append-only block history plus the current world state.
  • Membership: who may join and what each identity may do.
  • Consensus: how nodes agree on order. Fabric uses Raft for ordering. Earlier releases offered a Kafka-based ordering service for production networks and a single-node Solo orderer for development and testing only; both are now deprecated. Names only here; proofs are in Unit 3.
  • Chaincode: the smart contract that reads and writes state. See 6.2.
  • Events: notifications that let an outside application react after a commit.

Fabric's permissioned model

Fabric assumes members are known. An organisation is a company or authority with its own membership service provider (MSP). The MSP turns certificates into roles: a peer identity, an admin identity, a client identity. A user cannot simply invent a key and write; the channel checks the MSP.

A peer hosts a copy of the ledger and runs chaincode. A peer can be an endorser, a committer, or both. An orderer receives endorsed transactions, puts them in a block, and delivers the block to peers. The orderer does not run chaincode and does not execute business logic. That is the commonest exam confusion.

A channel is a private subnet of the same Fabric network. Only organisations joined to the channel see its ledger. Two firms can share a channel for invoices while a regulator joins a separate audit channel. Channels give privacy by separation, not by encryption of one global ledger.

Private data goes further. A chaincode can keep a data collection off-chain and write only a hash to the channel ledger. Members of the collection see the raw value; other channel members see the hash and can later verify that the value was not changed.

Endorsement, ordering, commit

  1. A client sends a proposal to the peers named by the endorsement policy.
  2. Each peer simulates chaincode against its copy of state, signs a read-write set, and returns an endorsement.
  3. The client collects endorsements and sends them to the orderer.
  4. The orderer orders transactions into a block; it does not validate business rules.
  5. Committer peers check signatures, the endorsement policy, and read-set versions. A version change means another transaction already wrote that key. The earlier transaction stays valid; the transaction now being validated is marked invalid and is not applied to world state.
  6. Valid transactions update world state and append to the ledger; events fire.

An endorsement policy is a rule over MSP identities, for example "1 of Org A AND 1 of Org B". Extra signatures are allowed but not required. A transaction can be endorsed and still fail commit if its read-set version is stale.

This split keeps ordering simple and keeps execution with the members who own the data. It is why Fabric is called an execute-order-validate architecture, unlike the order-execute design of public chains. See 6.8 for the throughput cost of this trade.

Worked example

Question. Org A has peers A1 and A2. Org B has peers B1 and B2. One orderer serves the channel. The endorsement policy is "1 of Org A AND 1 of Org B". A proposal is endorsed by A1, A2 and B1. (a) How many distinct organisations endorsed? (b) How many endorsements came from Org A? (c) Does the set satisfy the policy?

  1. List the endorsers: A1, A2, B1.
  2. Map each peer to its organisation: A1 → Org A, A2 → Org A, B1 → Org B.
  3. Distinct organisations = {Org A, Org B}, so the count is 2.
  4. Endorsements from Org A = A1 and A2, so the count is 2.
  5. Policy needs at least one from Org A and at least one from Org B. Org A is present and Org B is present, so the policy is satisfied.
  6. The extra Org A signature (A2) is allowed; the policy does not forbid extra endorsements.

Answer. Two distinct organisations endorsed, Org A supplied two endorsements, and the AND policy is satisfied; the extra A2 signature is allowed.

Exam traps

  • Calling the orderer a miner. A Fabric orderer orders transactions into blocks; it does not execute chaincode or mine.
  • Treating a channel as an organisation. One organisation can join many channels, and one channel can serve several organisations.
  • Confusing endorsement with commit. A transaction can collect valid endorsements and still be invalidated at commit by a read-set version mismatch.
  • Treating an MSP identity as a website login. The MSP is a certificate-backed membership record checked by the channel.
  • Assuming private data is fully hidden by the hash. The hash proves integrity; only collection members receive the raw value.

6.2 Chaincode: smart contracts in Hyperledger

Chaincode is the smart contract of Hyperledger Fabric. It is a program, written in Go, Java or Node.js, that runs in a container on a peer and reads or writes channel state through a shim API. Banks and consortia use chaincode for transfers, trade documents and claims where each organisation must endorse a change before the ledger accepts it.

You need: Chapter 6.1 for peers, orderers and channels, and Unit 5 for the general smart-contract idea.

Chaincode as a program

Chaincode is application logic that owns a namespace on a channel. A namespace is a key prefix such as car; a key CAR1 becomes carCAR1, so two chaincodes do not collide.

Every chaincode runs inside a container started by the peer. The container talks to the peer through the shim API: GetState, PutState, DelState and GetStateByRange. A read-write set is the list of keys read and values to write. The API is the only door to the ledger.

Execution must be deterministic. The same proposal on two endorsing peers must produce the same read-write set, so code must not use random numbers, wall-clock time, external HTTP calls or local files. Pass such data as arguments.

Solidity contracts run on every Ethereum node under the EVM and pay gas. Fabric chaincode runs only on endorsing peers chosen by policy, uses permissioned identities, and has no gas; the cost is that the endorsement policy fixes who must run it. See Unit 5 for Solidity.

Lifecycle, endorsement and commit

  1. Package chaincode with its metadata.
  2. Install it on each endorsing peer.
  3. Approve the definition for each organisation.
  4. Commit the definition to the channel.
  5. Invoke sends a transaction proposal; query calls a read-only function.

An endorsement policy names the organisations or peers that must sign the simulated result. A policy AND(OrgA.peer, OrgB.peer) needs both. A proposal goes to those peers; each runs the chaincode against its local state and returns a read-write set plus signature. The client sends the set to the orderer. The orderer cuts a block. Each committing peer checks the signatures, the policy and that the read-set versions are unchanged, then writes the write-set. If another transaction changed a key first, the read-set check fails and the transaction is invalid; it stays on the ledger but is not applied.

A private data collection keeps the value with authorised peers and puts only a hash on the shared ledger; other organisations see the hash, not the value.

A write to carCAR1 does not touch loanCAR1, because the namespace prefix is part of the key.

Exam traps

  • Execution changes the ledger immediately: it does not; only ordering and commit apply the write-set.
  • Endorsement is ordering or consensus: endorsement is simulation plus signature; the orderer only orders.
  • A query needs a block: queries read committed state and skip ordering.
  • AND and OR policies are read carelessly: AND needs every named peer, OR needs at least one.
  • Solidity gas and EVM rules apply to chaincode: they do not; Fabric has no gas in this sense.

6.3 Blockchain in finance and insurance

Banks, exporters, insurers and hospitals each keep their own copy of the same fact: a payment, a bill of lading, a claim. When the copies disagree, someone spends days reconciling them. A shared blockchain ledger gives these parties one tamper-evident record that each of them can check without trusting a single owner. Finance uses it for cross-border payments, trade finance, KYC and settlement of tokenised assets. Insurance uses it for policies, claims and reinsurance. This chapter shows the pattern, and where the pattern stops: a ledger enforces data and rules, not the truth of the outside world.

You need: chaincode from 6.2 and digital signatures from Unit 2, because every entry on a finance ledger is signed by the party that wrote it.

One record instead of many books

An exporter in Surat ships fabric to a buyer in Hamburg. The payment passes through the exporter's bank, a correspondent bank and the buyer's bank. Each bank books its own entry, applies its own charges and settles on its own timetable. The money does move; the slow part is agreeing on what happened.

A shared ledger removes the argument. Each bank runs a node on the same permissioned network (see 6.1). A payment is one signed entry that every node sees in the same order. Reconciliation, which means comparing two sets of books, becomes a read of one set of books.

Know-your-customer (KYC) follows the same logic. Today a customer submits the same documents to every bank. On a shared KYC ledger, one bank verifies the documents, stores the files off-chain, and writes an attestation on-chain: a signed statement plus a cryptographic hash of the file. Another bank reads the statement and the hash, checks the signature, and skips the repeat check. Personal data never reaches the ledger; only the hash and the claim do.

The pattern repeats everywhere in this chapter: private data off-chain, hash and signature on-chain, business rules inside a smart contract.

Trade finance, letters of credit and tokenised assets

Trade finance runs on paper. In a letter of credit (LC) the importer's bank promises to pay the exporter's bank once documents prove the goods were shipped. The invoice, bill of lading and insurance certificate travel by courier, and one mismatch lets the bank refuse payment.

  1. The importer's bank writes the LC terms into chaincode: amount, goods, latest shipment date, required documents.
  2. The exporter ships, stores each document off-chain, and puts its hash and its signature on-chain.
  3. Chaincode compares the submitted hashes with the required list and the dates with the terms.
  4. If every condition holds, chaincode releases payment to the exporter's bank in the same transaction.
  5. If any condition fails, chaincode writes a rejection naming the failed condition into the audit log.

Because the check is code, both sides can test the rules before a single container is loaded. Disputes that remain are about facts the ledger cannot see, such as whether the goods were really loaded, not about arithmetic.

A bond can be issued as a token: a ledger entry naming the issuer, face value, coupon and maturity date, with the legal claim held in an off-chain register. Settlement becomes delivery-versus-payment (DvP): one transaction moves the token from seller to buyer and the money from buyer to seller, or neither leg moves. On paper the two legs settle hours or days apart, and that gap is counterparty risk.

Tokenised does not mean the asset changed. The token is a pointer plus a rule set; the law still decides who owns the bond. Amounts and counterparties are commercially sensitive, so finance networks split them into channels that only named members can read (see 6.8).

Insurance: policy, claim and payout

A policy on a shared ledger is a record of terms: who is covered, the sum insured, the deductible, the exclusions and the validity dates. Insurer, insured and hospital all read the same version.

A claim arrives from outside the ledger: a hospital bill, a discharge summary, a repair estimate. Ledger nodes cannot observe these events. They accept a signed statement from a trusted party, or from an oracle, which is a service that feeds signed external data on-chain.

payout = max(0, min(claim, sum insured) − deductible)

payout is what the insurer pays, in rupees; claim is the amount claimed, in rupees; sum insured is the policy's maximum total payment, in rupees; deductible is the part of each claim the insured bears, in rupees; max(0, ...) stops a negative payout.

  • The policy must be active on the claim date.
  • The claim hash must not appear in the paid-claims set, which blocks double payment.
  • The claim must carry the signature of an authorised submitter.

Parametric insurance replaces loss assessment with a measured trigger. A crop policy might pay when rainfall recorded at a named station falls below 50 mm in a month. The oracle posts the reading, chaincode compares it with the threshold, and payment follows. No surveyor and no delay, but there is basis risk: the station's reading may not match the farmer's actual loss.

Reinsurance uses the same ledger across companies. A treaty says the reinsurer takes 30% of every claim, so chaincode splits each payout at source and the reinsurer sees the claim and its share at the same moment as the primary insurer.

Worked example

Question. A health policy lives on a shared ledger with sum insured ₹5,00,000, a deductible of ₹10,000 per claim, and status active. A hospital submits a claim of ₹1,20,000 with document hash H. (a) Compute the payout. (b) Compute the sum insured left after this payout. (c) The hospital resubmits the identical claim with the same hash H. What does the chaincode do, and why?

  1. Read the policy: status active, sum insured ₹5,00,000, deductible ₹10,000.
  2. Check status: active, so the check passes.
  3. Check the claim against the cap: ₹1,20,000 ≤ ₹5,00,000, so min(claim, sum insured) = ₹1,20,000.
  4. Check the hash: H is not in the paid-claims set, so this claim is new.
  5. Apply the formula: payout = ₹1,20,000 − ₹10,000 = ₹1,10,000.
  6. Deduct from the cap: remaining sum insured = ₹5,00,000 − ₹1,10,000 = ₹3,90,000.
  7. Resubmission: chaincode finds H already in the paid-claims set and rejects the claim, so the second payout is ₹0.

Answer. The first claim pays ₹1,10,000 and leaves ₹3,90,000 of sum insured; the resubmitted claim pays ₹0 because its hash is already recorded.

Worked example 2

Question. A second policy has sum insured ₹2,00,000 and a deductible of ₹5,000. A claim of ₹1,80,000 arrives with a new hash. Compute the payout.

  1. Policy active: check passes.
  2. Cap check: min(₹1,80,000, ₹2,00,000) = ₹1,80,000.
  3. Hash check: new hash, so the claim is accepted as new.
  4. payout = ₹1,80,000 − ₹5,000 = ₹1,75,000.

Answer. The payout is ₹1,75,000.

Exam traps

  • Subtracting the deductible before capping by the sum insured, or subtracting it twice: the order is min(claim, sum insured) − deductible, floored at 0.
  • Believing the ledger proves a hospital bill is genuine. It proves the bill was signed by the submitter and has not changed, so a lying oracle still produces a valid-looking payout.
  • Treating tokenised as legally transferred: the token points to an off-chain register and the law still decides ownership.
  • Assuming everyone on the network can see every entry. On a permissioned network, channels limit visibility, as in 6.1.
  • Skipping the double-payment check. Without the stored claim hash, the same bill can be paid many times.

Confidential amounts are shifting toward zero-knowledge proofs so that a channel is not the only privacy tool. Useful search terms: CBDC pilot, delivery-versus-payment distributed ledger, parametric insurance oracle, electronic transferable records.

6.4 Blockchain in supply chain and logistics

A supply chain ledger records each custody and quantity change as one hash-linked event: farm, transporter, warehouse, retailer. Each event stores the hash of the event before it, so a later edit breaks the chain and shows where the record changed. The ledger does not weigh goods or read thermometers. It proves the record you see now is the record written at handover. Exporters, food and pharma distributors, and e-commerce logistics teams use it for provenance, customs paperwork and fast recalls.

You need Chapter 6.1 for peers and channels, Chapter 6.2 for chaincode, and Unit 2 for hash pointers.

Custody events and batch identity

Goods move through hands: farm, transporter, warehouse, retailer. Each handover is a custody change. Provenance is the origin and full history of a batch. Chain of custody is who held the goods, when, and for how long. The blockchain keeps one shared, tamper-evident record for parties who do not trust each other's databases.

The unit is the batch ID or lot ID — the quantity produced or packed together, such as 100 kg of mangoes from one farm on one day. Every carton carries that ID, and every event carries it. Without a batch ID the ledger is only a diary.

event = H(batch_id ‖ actor ‖ action ‖ qty ‖ time ‖ doc_hash ‖ prev_hash)

H is SHA-256; ‖ means concatenation; actor is the party's identity; action is dispatch, receive or store; qty is the quantity in kg or pieces; time is the timestamp; doc_hash is the hash of the attached paperwork; prev_hash is the hash of the previous event for the same batch. Changing any field changes H and breaks every later link.

A past event sits inside the hash of every later event, and later events are held by other organisations. If the transporter edits 98 kg to 100 kg, the warehouse's prev_hash no longer matches, so the gap is visible.

On-chain hash, off-chain document

Invoices, bills of lading, certificates and temperature logs are large and often confidential. Keep the file off-chain in the ERP or an object store, and put its SHA-256 hash into the event. The hash is a fingerprint; changing the file changes the hash.

  1. Fetch the file from the ERP or document store.
  2. Compute its SHA-256 hash.
  3. Read doc_hash from the ledger event for that batch.
  4. Compare the values: equal means the file is the one recorded at handover; different means it was edited after recording, so reject it and audit.

Cold chain: vaccines, milk, fish and some medicines must stay inside a temperature band. A sensor reading every few minutes is too many records. Batch the readings and store a Merkle root, or store min, max, count and any excursion. Chaincode rule example: above 8 °C for more than 30 minutes flags the batch.

The ledger proves readings were recorded as written. It does not prove the sensor was honest or calibrated; that needs device identity and calibration records — see Chapter 6.5.

Handovers, recalls and payment on delivery

Loss at one handover = dispatched quantity − received quantity. Positive means goods were lost, spoiled or stolen on that leg. Negative usually means a recording error, not a gain. Total loss is first quantity minus last, but events show which leg to audit.

Recalls become fast. For a contaminated lot, walk backwards on the batch ID to the farm and date; walk forwards to every shipment carrying that lot. All parties read the same hash-linked events, so they reach the same answer.

Payment on delivery uses chaincode from Chapter 6.2. The contract holds: when the retailer's receive event for batch B001 commits, release the agreed amount minus a penalty per kg lost beyond tolerance. This escrow removes argument about whether delivery happened.

  • The ERP stays the system of record for inventory and accounting; an adapter writes selected events to the ledger.
  • Some syllabi call this supply chain insight from enterprise resource planning: the ledger adds cross-company proof to the ERP's internal numbers.
  • Never mirror whole ERP tables on-chain. Write only the events another company needs to verify.
  • Keep the ERP row ID in the event so an auditor can join the records.

Worked example

Question. Batch B001 of mangoes leaves the farm with 100 kg. The transporter records 98 kg, the warehouse records 98 kg, and the retailer records 95 kg. (a) Compute the loss at each handover and the total recorded loss. (b) Compute the loss as a percentage of the quantity dispatched by the farm. (c) State which handovers an auditor should investigate.

  1. q0 = 100 kg farm dispatch, q1 = 98 kg transporter, q2 = 98 kg warehouse, q3 = 95 kg retailer.
  2. Leg 1: 100 − 98 = 2 kg. Leg 2: 98 − 98 = 0 kg. Leg 3: 98 − 95 = 3 kg.
  3. Total = 2 + 0 + 3 = 5 kg = 100 − 95.
  4. Percentage loss = (5 kg ÷ 100 kg) × 100 = 5.0 %.
  5. Audit Leg 1 and Leg 3; Leg 2 matches.

Answer. Losses are 2 kg, 0 kg and 3 kg per leg, total 5 kg or 5.0 % of the 100 kg dispatched; audit the farm-to-transporter and warehouse-to-retailer handovers.

Worked example 2

Question. A sensor records milk temperature every 10 minutes for a 4-hour trip, giving 24 readings. The chaincode stores only the Merkle root of the 24 hashes on-chain and keeps the readings in cold storage. An auditor is shown the readings file later. State the check the auditor performs and what a mismatch means.

  1. Recompute the SHA-256 hash of each of the 24 readings.
  2. Rebuild the Merkle tree from the 24 leaf hashes and take the root.
  3. Compare the computed root with the Merkle root stored in the ledger event for that batch.
  4. If the roots match, the file is exactly the set of readings recorded during the trip.
  5. If they differ, at least one reading was added, removed or edited after the event was committed; reject the file and audit the batch.

Answer. The auditor rebuilds the Merkle root of the 24 readings and compares it with the on-chain root; equality proves the readings are unchanged, and a mismatch proves the file was altered after recording.

Exam traps

  • Believing a blockchain weighs the goods. The weight is typed in by a party; the ledger only proves the record was not changed afterwards.
  • Confusing provenance with quality. A ledger shows origin and history, not that the mangoes are safe or sweet.
  • Storing full invoices and temperature logs on-chain 'for safety'. That is expensive and leaks confidential data to every peer; store the hash.
  • Dropping the batch ID. Events not tied to a lot cannot support a recall, however tamper-evident they are.
  • Treating a negative loss as a gain without checking for a unit slip (kg versus pieces) or a recording error.

6.5 Blockchain in healthcare, agriculture, IoT and smart cities

Hospitals, farms, sensor fleets and city offices all face the same problem: several parties keep separate databases, and each can quietly edit its own copy. The shared pattern is simple. A device or an organisation signs each piece of data. A small fingerprint of that data goes on a permissioned ledger. Applications then read one verifiable history. Health systems use it for records and consent, agriculture for crop provenance and payments, IoT for device identity and firmware logs, cities for parking, waste, energy and land records. The ledger stores fingerprints, not the raw data.

You need: Unit 2, Merkle trees and hash pointers, plus Chapter 6.2 on chaincode and endorsement.

Health: records, consent and clinical trials

A patient's history sits in many places: a hospital system, a lab, a pharmacy, an insurer. Each keeps its own database and each can edit it. A permissioned ledger fixes one narrow thing: who wrote which record, and when.

The ledger stores a hash of each record, not the record. A hash is a fixed-length fingerprint; changing the record changes the hash. The hospital keeps the full file off-chain.

Consent becomes a ledger entry. The patient signs a transaction saying: doctor X may read record hash H until 31 March. Chaincode checks the consent entry before releasing the file. Withdrawing consent writes a new entry, so the old grant stays in history — exactly what an audit needs.

Clinical trials use the same trick on documents. The protocol and each database lock (the frozen dataset at the end of a trial) are hashed and time-stamped when fixed, so a later change to a primary endpoint shows up as a broken link.

Off-chain data and on-chain Merkle roots

One vaccine fridge sends 6 readings per hour, so 144 per day. Thousands of fridges writing every reading would fill the ledger with numbers nobody reads again. So the gateway batches them.

  1. The fridge reads the temperature and its device id, and the device signs the reading with its own private key; the gateway verifies that signature against the registered public key, then batches the signed readings.
  2. It hashes each signed reading: hᵢ = SHA-256(reading).
  3. It pairs the hashes and hashes again, level by level, until one root remains.
  4. It sends one transaction: device id, date, root, and the number of readings in the batch.
  5. To prove one reading, the app sends that reading plus its sibling hashes along the path; the verifier recomputes the root and compares it with the on-chain value.

proof length ≈ ⌈log₂ n⌉ sibling hashes

n is the number of readings in one batch; ⌈ ⌉ rounds up, because the tree is padded to a power of two.

Raw readings stay in the hospital database: they are large, private, and a blockchain cannot delete a mistake.

Agriculture: provenance and payments

Crop provenance is a chain of custody. Each step — farm, warehouse, mandi, packer, retailer — appends an event with quantity, date and a hash of its paperwork. The packet carries a QR code. A buyer scans it, sees the whole path, and knows that no event was inserted later.

Payments use chaincode escrow. The buyer's money is held by the contract and released when both sides sign the warehouse receipt. The farmer reads the condition in code instead of trusting a middleman's promise.

Field sensors add data: soil moisture, rainfall, a drone photo. These are hashed and batched like fridge readings. A crop-insurance payout can then follow a rainfall reading that farmer and insurer both verify, the same logic as the claims in Chapter 6.3.

IoT identity and smart cities

A device needs an identity before its data means anything. Each device gets a key pair; its public key is registered against a manufacturer and an approved firmware hash. A gateway rejects readings signed by an unknown key, or by a device whose firmware hash is not on the list. Firmware updates are logged as transactions, so an owner can prove which version a meter ran on a given date.

  • Parking: the sensor records the spot as free, the ledger records the release and the payment, so the driver cannot dispute a signed record.
  • Waste: bins report fill level, collection trips are logged, and the contractor is paid per verified trip.
  • Smart grid: smart meters send signed readings; a neighbourhood micro-grid trades surplus solar units, and the ledger settles who sent what.
  • E-governance: land records and licences are stored as hashes, so the citizen holds a copy that any office can check.

Worked example

Question. A vaccine fridge sends one temperature reading every 10 minutes. (a) How many readings does it produce in a day? (b) The gateway writes one Merkle root per day. How many sibling hashes does a proof for one reading need at most? (c) Three readings are above 8 °C. What percentage of the day's readings is that, to two decimals?

  1. Readings per hour = 60 ÷ 10 = 6.
  2. Readings per day = 6 × 24 = 144.
  3. Find the smallest k with 2^k ≥ 144: 2⁷ = 128 is too small, 2⁸ = 256 is enough, so k = 8.
  4. Proof length = ⌈log₂ 144⌉ = 8 sibling hashes; each level of the tree adds one hash.
  5. Percentage = (3 ÷ 144) × 100 = 2.0833... = 2.08 %.
  6. Storage: all 144 readings stay in the hospital database; the chain gets one 32-byte root.

Answer. (a) 144 readings per day, (b) at most 8 sibling hashes, (c) 2.08 % of the readings are above 8 °C.

Exam traps

  • Putting raw IoT readings on-chain. Keep the raw readings in the hospital database and put only a hash or a Merkle root on the ledger, so the ledger stays small.
  • Believing the ledger proves the reading was correct. It proves the reading was not changed after it was written, not that the sensor was calibrated.
  • Mixing up the root and the proof. The root is one hash on the ledger; the proof is the short list of sibling hashes.
  • Using n instead of ⌈log₂ n⌉ for proof length. For 144 readings the proof is 8 hashes, not 144.
  • Expecting consent to be erased. Revocation is a new entry; the old grant stays visible in history.

6.6 Blockchain in the metaverse

The metaverse is a set of immersive digital experiences, not one app. It runs on a seven-layer value chain from Experience down to Infrastructure. Blockchains supply ownership, identity and payments for virtual assets such as NFTs, virtual land and wallets. Games, social worlds and virtual property markets use this.

You need Unit 5 tokens and smart contracts, and Chapter 6.2 chaincode.

Immersive experience and the seven-layer value chain

The metaverse is a persistent, shared, immersive digital space. Immersive experience means VR headsets and AR overlays put the user inside a scene; phones and browsers give lighter access. The idea grew from text worlds and 2D games into 3D social worlds, with no single launch date.

Its value chain has seven layers. Experience: games and social worlds. Discovery: stores, ads and search. Creator economy: tools and assets. Spatial computing: 3D engines, AR and VR. Decentralization: blockchain and NFTs. Human interface: phones and headsets. Infrastructure: cloud and 5G. Each layer depends on the ones below; the top is user-facing, the bottom technical.

Blockchain is only the decentralization layer. A virtual concert needs Experience, Spatial computing and Infrastructure as much as it needs tokens. A game may use a centralized server and still issue land as NFTs. No layer alone makes a metaverse.

NFTs, virtual land, wallets and identity

An NFT is a token with a unique ID on a ledger. It proves who controls an asset, not where the file sits. Virtual land is an NFT whose metadata points to a plot in a 3D world. The 3D scene stays off-chain because graphics are large; the ledger stores ownership and sale history.

Wallets hold private keys; the wallet address is the public identity. Payments use ether or platform tokens. A marketplace lists land, takes a fee, and calls a smart contract; the sale moves the NFT and records the transfer. Chaincode or an EVM contract can enforce escrow and royalties.

Identity can be a wallet, a decentralized identifier (DID), or a platform login. Wallet control is self-custody; platform login is delegated. Payments settle on-chain, while chat, voice and 3D rendering stay on servers. That split is why the metaverse is not 'all blockchain'.

NFT metadata usually includes a URL or content hash; if the link dies, the token survives but the asset may not.

6.7 Emerging platforms: Ripple, Quorum, Tendermint, Kadena

Ripple, Quorum, Tendermint, Kadena and Rootstock answer five needs: fast payment settlement, private smart contracts, immediate BFT finality, parallel-chain scalability and Bitcoin compatibility. Each is a design choice. Ripple settles cross-border payments, Quorum hides enterprise transactions, Tendermint commits in one BFT round of prevote and precommit, Kadena braids proof-of-work chains, and Rootstock brings Ethereum contracts to Bitcoin.

You need Unit 3 consensus and Unit 5 EVM and smart contracts; see 6.8 for the limits these designs face.

Ripple and Quorum: settlement and privacy

Ripple is a payment network; the XRP Ledger is its public ledger. Validators agree using a trusted list, often called the unique node list. There is no mining race. A payment can settle in seconds, and the ledger carries XRP or issued balances such as dollars or rupees. Banks use this model for cross-border settlement, where correspondent banking is slow and costly. Settlement happens on the ledger itself, not in a smart contract; the ledger records balances and payments.

Quorum is permissioned Ethereum for enterprises. It keeps the EVM and Solidity, so Ethereum contracts move across. Known nodes are admitted by a consortium. Private transactions send the payload only to selected nodes; other nodes see that a private transaction happened, not its contents. Consensus can be Raft for crash faults or IBFT/QBFT for Byzantine faults. A bank consortium shares one state without exposing every trade to every member. This is useful for trade finance.

Tendermint BFT and Kadena Chainweb

Tendermint is Byzantine fault tolerant consensus. Validators take turns proposing a block, then prevote and precommit. A block commits when more than two-thirds of voting power signs the same precommit. Finality is immediate: after commit it does not roll back under the fault assumption. Each Cosmos chain runs Tendermint-style consensus, and the IBC protocol links these chains.

For n validators with equal voting power, a block needs more than two-thirds of voting power. In votes, quorum = floor(2n/3) + 1. This equals 2f + 1 only when n = 3f + 1, where f = floor((n − 1) / 3) is the maximum number of faulty validators the network can tolerate. With n = 7, f = floor(6 / 3) = 2, and quorum = floor(14 / 3) + 1 = 4 + 1 = 5. Five matching votes commit; four do not. Bitcoin's longest-chain rule is probabilistic; a Tendermint commit is a fixed decision.

Kadena uses Chainweb, a braid of parallel proof-of-work chains. Each chain mines its own blocks and includes headers from peer chains, so work on one chain strengthens others. More chains raise throughput. Pact is Kadena's smart-contract language, built for readable contracts and formal checks. The trade is complexity: users must track many chains and cross-chain proofs.

Rootstock and a comparison

Rootstock is a Bitcoin sidechain with an EVM. It is merge-mined with Bitcoin, so miners reuse hash power. A peg backs RBTC with BTC. A user moves BTC in, runs Solidity contracts, and moves value back through the peg. Bitcoin holders gain smart contracts without changing Bitcoin's base rules. The peg is run by a federation, so trust is not identical to Bitcoin's.

6.8 Scalability, privacy and other challenges

A blockchain that is secure and spread across many nodes is slow. A fast one usually asks you to trust fewer parties. Throughput, latency, storage, privacy and decentralisation pull against each other, and every design picks a point on that trade-off. This chapter measures the limits — transactions per second, bytes added per day — and surveys the standard fixes: bigger blocks, sharding, rollups, payment channels, private data and zero-knowledge proofs. It then covers regulation, energy, interoperability and quantum risk.

You need: Chapter 6.1 for channels and peers, plus consensus from Unit 3 and the limitations listed in Unit 4.

The trilemma, measured in numbers

The scalability trilemma says a chain can hold only two of three at once: decentralisation (many independent validators), security (high cost to attack), and scalability (high transactions per second at low fees). It is a design trade-off, not a law of physics, but it explains why a public chain running on thousands of ordinary machines cannot match a payment network's throughput.

TPS = T ÷ Δt

TPS is committed transactions per second; T is the number of transactions in one block; Δt is the block interval in seconds.

Storage is the second limit. Every full node keeps every block forever, so the ledger grows by T × s bytes every Δt seconds, where s is the average bytes per transaction record. High TPS without pruning or checkpointing pushes ordinary nodes off the network, which quietly cuts decentralisation.

  • Bigger blocks raise T but take longer to propagate, so forks and stale blocks become more likely (see Unit 3, forks).
  • A shorter Δt raises TPS the same way, at the same risk.
  • Throughput is not latency: finality time can stay slow even when TPS is high.

Layer 1, layer 2 and permissioned shortcuts

A layer-1 change edits the base protocol. Sharding splits the state and the validator set into k shards, each processing its own transactions, for roughly k times the throughput; cross-shard transactions then need extra messaging rounds and lose cheap atomicity.

A layer-2 change moves work off the chain but keeps its security. A rollup runs transactions off-chain and posts compressed data plus a proof back: an optimistic rollup assumes correctness and allows a challenge window, a ZK rollup posts a validity proof. A payment channel locks funds once on-chain, swaps many signed updates off-chain, and settles once. Side chains run their own consensus, so they are cheaper but borrow little security from layer 1.

Permissioned platforms get privacy from topology instead. In Fabric a channel limits who sees a transaction, and a private data collection puts a hash on-chain and the payload in a side database that only endorsed parties can read through chaincode.

Privacy, law, energy and long-term risk

  • Zero-knowledge proofs show a statement is true — 'this transfer is valid' — without revealing amounts, addresses or the witness. zk-SNARKs are small but usually need a trusted setup; zk-STARKs avoid it using hashes alone, with larger proofs.
  • KYC and AML rules push licensed businesses towards identified, permissioned ledgers. Data-protection law gives people a right to correction or erasure, which an append-only ledger cannot honour, so personal data stays off-chain and only a hash goes on.
  • Proof of Work pays for security in electricity; Proof of Stake pays in bonded capital and uses far less energy per transaction (see Unit 3, Proof of Stake).
  • Bridges lock an asset on one chain and mint a wrapped copy on another; the bridge, not either chain, holds the funds, which is why bridge failures have been the largest single loss point in practice.
  • Shor's algorithm would break ECDSA signatures on a large quantum computer. Hash-linked data survives better, and post-quantum signature schemes are the migration path.

Worked example

Question. A chain makes blocks every 12 s. Each block holds 1,000 transactions, and each transaction record is 500 bytes. Find the throughput in tx/s, the number of blocks per day, and the ledger growth per day in GB (use 1 GB = 10⁹ bytes).

  1. Read the data: block interval Δt = 12 s, transactions per block T = 1,000, average record size s = 500 bytes, seconds per day = 86,400.
  2. Throughput: TPS = T ÷ Δt = 1,000 ÷ 12 = 83.33 tx/s.
  3. Blocks per day = 86,400 ÷ 12 = 7,200 blocks.
  4. Bytes per day = blocks per day × T × s = 7,200 × 1,000 × 500 = 3,600,000,000 bytes.
  5. Convert: 3,600,000,000 ÷ 1,000,000,000 = 3.6 GB per day.

Answer. Throughput is 83.33 tx/s, the chain adds 7,200 blocks per day, and the ledger grows by 3.6 GB per day.

Exam traps

  • Quoting TPS without Δt: 1,000 transactions per block means nothing until you divide by the block interval.
  • Confusing throughput with latency: a chain can commit many transactions per second and still take minutes to reach finality.
  • Unit slip: 3.6 × 10⁹ bytes is 3.6 GB, not 3.6 MB and not 36 GB. Keep the 10⁹ divisor explicit.
  • Treating rollups and side chains as the same thing: a rollup posts proofs or data to layer 1, a side chain runs its own consensus.
  • Assuming zero-knowledge means anonymous: the proof hides the witness, but the transaction, its timing and its fee are still visible.

The bridge contract or validator set custodies locked funds on one chain while minting a representation on the other, so it becomes a single high-value target; a bug or a key compromise drains the pool without breaking either chain.

6.9 Enterprise blockchain and blockchain with AI

Enterprise blockchains are shared ledgers run by a known group. They add permissioning, identity and integration to the ledger. Permissioning means only approved organisations join. Identity means each user signs with a certificate. Integration means the ledger talks to ERP, payment and AI systems. AI adds prediction and model audit on top of trusted data. Banks use this for trade finance, manufacturers for supplier records, and auditors for model checks.

You need: chaincode, scalability limits and IoT data patterns.

Enterprise permissioning and consortium networks

A consortium network is a blockchain owned by several firms, not one firm and not the public. Members know each other. A membership service issues a certificate to every user and node. A channel is a private subnet; only channel members see its transactions. This is permissioning: read and write rights are explicit. It suits trade finance, insurance claims and supplier records where privacy and legal identity matter (see finance).

Blockchain as a Service (BaaS) is cloud hosting for such networks. A provider runs peers, orderers, certificates and chaincode lifecycle. The enterprise pays a monthly fee and connects its ERP through APIs. ERP integration posts a hash of an invoice or purchase order to the ledger. The full document stays in the ERP database. BaaS lowers setup cost, but the provider becomes an operational dependency. Legal contracts still sit outside.

Oracles, off-chain data and AI

An oracle is a service that writes outside facts to the chain. It signs the data, so readers know which oracle supplied it. On-chain data is small and shared: hashes, amounts, status flags. Off-chain data is the raw document, image or sensor stream. Keep private data off-chain and store a pointer plus hash.

  1. Enterprise hashes an input record and logs the input hash.
  2. The AI service reads approved off-chain data.
  3. The AI service stores a model hash on the chain.
  4. The enterprise requests a prediction and receives a score plus hash.
  5. An auditor checks the model hash and the input hash.

AI is used for fraud detection, demand forecasting and credit scoring. The ledger does not make a model truthful; it makes the model version and inputs auditable. This is model provenance. A chaincode can release payment only when the prediction cites an approved model hash. The raw training set never goes on-chain.

Model provenance, federated learning and audit

Model provenance is the record of which model, which data version and which settings produced a prediction. Store a model hash, a data-version hash and a prediction log. An auditor reruns the model hash and checks the log. Federated learning trains a shared model across firms without moving raw data. Each firm sends model updates; the ledger records update hashes and training rounds. This gives audit trails with data minimisation.

A model card can list training data, accuracy and owner; its hash goes on-chain. That gives reproducible checks. The pattern is: raw data off-chain, hashes on-chain, AI off-chain, audit on-chain. Governance decides who approves models and oracles. If an oracle lies, the hash is valid but the fact is false; trust the oracle process. Store hashes and pointers, never full models or private training data, on-chain.

Worked example

Question. An enterprise logs 1,000 AI predictions per day. Each log stores a 32-byte input hash and a 32-byte model hash. Find the storage per day in bytes and kB, and the storage for 30 days in kB and MB. Use 1 kB = 1000 B and 1 MB = 1000 kB.

  1. Each log stores H_in = 32 B and H_model = 32 B, so one log uses 32 B + 32 B = 64 B.
  2. For N = 1,000 predictions/day: storage/day = N × (H_in + H_model) = 1,000 × 64 B = 64,000 B.
  3. Convert to kB: 64,000 B ÷ 1,000 B/kB = 64 kB.
  4. For 30 days: 64 kB/day × 30 days = 1,920 kB.
  5. Convert to MB: 1,920 kB ÷ 1,000 kB/MB = 1.92 MB.

Answer. The 30-day hash log needs 1.92 MB; raw inputs and models stay off-chain.

Exam traps

  • Storing full training data or model weights on-chain; store a 32-byte hash and an off-chain pointer.
  • A hash proves integrity, not that the oracle's fact is true.
  • A consortium chain is not a public chain with a login screen; membership and endorsement are enforced.
  • BaaS is managed hosting; it does not remove governance or key management.
  • Use 1 kB = 1000 B as in the example; 1 KiB = 1024 B changes the answer.

Takeaways

  1. Hyperledger is a family of permissioned frameworks; Fabric is the most used member and organises work into channels of peers, orderers and identified members.
  2. A Fabric transaction commits only after the endorsement policy is met, so the policy, not the code alone, decides what the ledger accepts.
  3. Chaincode is ordinary program code in a container; it is the only way application logic reads and writes channel state.
  4. Finance and insurance gain from one shared tamper-evident record of payments, trade documents and claims among parties who do not fully trust each other.
  5. Supply chain ledgers work because every custody change is a hash-linked event, so a later edit breaks the chain and exposes the gap.
  6. Healthcare, agriculture, IoT and smart cities reuse one pattern: signed data written by devices or organisations, read back as verifiable history.
  7. The metaverse is a seven-layer value chain; blockchains supply ownership, identity and payments for virtual assets, not the immersive experience itself.
  8. Ripple, Quorum, Tendermint, Kadena and Rootstock answer different questions about settlement, privacy, BFT finality, scalability and Bitcoin compatibility.
  9. Every blockchain trades throughput, latency, storage, privacy and decentralisation against each other; no design removes all limits.
  10. Enterprise blockchains add permissioning, identity and integration; AI adds prediction and model audit on top of the trusted data they hold.

Glossary

Byzantine fault tolerance
The ability of a network to agree correctly even when some nodes fail or act maliciously.
Chaincode
A program deployed on a Fabric channel that implements the business rules and updates state.
Channel
A private sub-network inside a Fabric network with its own ledger and its own set of member organisations.
Endorsement policy
A rule stating which organisations must sign a transaction before the peers will commit it.
Event
A message emitted by chaincode or the peer when something happens, used to notify outside systems.
Finality
The point after which a committed transaction cannot be reversed by the protocol.
Hyperledger Fabric
An open-source permissioned blockchain framework built from modular components such as peers, orderers and chaincode.
Invoke
A chaincode call that proposes a state change, as opposed to a query that only reads.
Latency
The time between submitting a transaction and seeing it finally committed.
Lot ID
An identifier for a batch of goods that ties physical packages to their ledger records.
Membership Service Provider
The Fabric component that issues and checks identity certificates and maps them to organisations.
Metaverse
A set of persistent, immersive digital experiences reached through various devices and platforms.
Oracle
A service that supplies outside data, such as prices or sensor readings, to a smart contract.
Orderer
A Fabric node that collects endorsed transactions, orders them into blocks and distributes the blocks.
Peer
A Fabric node that stores the channel ledger, runs chaincode and endorses or validates transactions.
Permissioned blockchain
A ledger where only identified organisations may read or write, with membership controlled by certificates.
Private data collection
A Fabric feature that shares values only with named organisations and puts a hash of them on the channel ledger.
Provenance
The recorded history of an item's origin and movement, verifiable from hash-linked entries.
Read-write set
The record of keys read and values written during chaincode simulation, checked again at commit time.
Settlement
The final transfer of value between parties that discharges the underlying obligation.
Sidechain
A separate chain linked to a parent chain, letting assets move between them under defined rules.
Throughput
The number of transactions a network commits per second.
World state
A key-value database holding the current value of each ledger key, updated by committed transactions.
Zero-knowledge proof
A cryptographic proof that a statement holds, without revealing the underlying data.
