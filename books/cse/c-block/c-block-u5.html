5.1 Ethereum network and ecosystem components

Ethereum is a public blockchain that keeps a shared record of accounts, not a list of coins. Thousands of computers called nodes run client software, check every transaction, and agree on one world state: a table of accounts holding balances, code and storage. Around the network sits an ecosystem — wallets that hold keys, block explorers that show history, testnets for free practice, and applications that use it. This chapter maps the network, account model and ecosystem, then points forward to ether, the EVM and contracts.

You need: blockchain networks and nodes (Unit 1, Blockchain networks and nodes) and peer-to-peer networking (Unit 3, Peer-to-peer networking: architecture and network discovery).

The network and its nodes

Ethereum is public and permissionless. There is no application form or approving administrator. Any computer running the right software can join, download the chain, verify it, and pass on new transactions.

A node is such a computer. The program it runs is a client. After proof of stake, a node normally runs two clients: an execution client that keeps account state and runs contract code, and a consensus client that follows the fork-choice rule for new blocks. Both are needed for full validation.

Nodes find each other peer-to-peer. No central server is involved. A node keeps a list of peers and exchanges new transactions, new blocks, and requests for state it does not hold. Many nodes repeat the same checks, so one lying node is ignored.

Node typeStoresTypical use
Full nodeRecent state, all blocksDefault; validates and serves peers
Archive nodeEvery past state as wellExplorers, analytics, history queries
Light nodeBlock headers onlyPhones and low-power devices

A full node answers 'what is this balance now'. An archive node also answers 'what was this balance at block 15,000,000'. A light node asks a full node for the value plus a Merkle proof, and checks that the proof hashes up to the state root inside a header it already holds. Running your own full node is the strongest way to stop trusting someone else's server.

Accounts and the world state

Ethereum stores accounts, not coins. That is the main structural difference from Bitcoin, which tracks unspent outputs. An account is a record with four fields:

  • nonce — the number of transactions this account has sent (for a contract account, the number of contracts it has created).
  • balance — ether held, counted in wei; 1 ETH = 10¹⁸ wei.
  • codeHash — the hash of the account's code; for an externally owned account it is the Keccak-256 hash of empty code (the same fixed value for every EOA).
  • storageRoot — the root hash of the account's own storage.

There are two account types. An externally owned account (EOA) is controlled by a private key and carries no code. A contract account carries code and is controlled by that code. Making a wallet creates an EOA; deploying a contract creates a contract account.

The world state is the whole table of address → account. Every full node that has validated the chain holds the same table; light nodes keep only headers and fetch values with proofs. Each block header carries a 32-byte state root, a fingerprint of the entire table (see Unit 2, Merkle trees). Two nodes that disagree on any balance get different roots, so disagreement is visible immediately.

new balance = balance − value − gasUsed × effectiveGasPrice

balance is the sender's balance in wei before the transaction; value is the wei sent to the recipient; gasUsed is the gas actually consumed; effectiveGasPrice is the price of one gas unit in wei, equal to base fee + priority fee. The product gasUsed × effectiveGasPrice is the fee. The whole fee leaves the sender and never reaches the recipient: the base fee is burned, and only the priority fee goes to the block producer.

The nonce orders one account's transactions and blocks replay: a signed transaction with nonce 7 is valid once only, because afterwards the account's nonce is 8. Transaction fields are covered in 5.2.

The ecosystem around the network

The core chain is small. The ecosystem is the software people actually touch:

  • Wallet — holds private keys, signs transactions, displays balances it reads from a node.
  • Block explorer — a search engine over the chain; look up an address, a transaction hash or a block number.
  • dApp — a web front end that reaches contracts through a wallet and a node.
  • Token — a contract keeping its own table of holder amounts; see 5.2.
  • Testnet — a separate chain with free ether for practice; see 5.6.
  • Developer tools — compilers, libraries and frameworks that build and deploy contracts; see 5.7.

Here is the full path of one request:

  1. The user asks the wallet to send 0.3 ETH to a contract.
  2. The wallet builds a transaction, shows the fee, and the user signs it with the private key.
  3. The wallet sends the signed transaction to one node.
  4. That node checks the signature, nonce and balance, then gossips the transaction to peers.
  5. A block producer includes it; every node executes it and updates world state; the wallet refreshes by querying again.

A wallet is neither a chain nor a node. It is a key holder plus a viewer. If its node is stale, the wallet shows a stale number; the chain's state did not move. The node and world state decide balances and nonces, never the wallet.

Worked example

Question. A wallet shows 2 ETH for an account whose nonce is 7. The user sends 0.3 ETH to a contract account and pays a gas fee of 0.001 ETH. The contract already holds 0 ETH and does nothing else during the call. Find the user's balance, the contract's balance and the user's nonce after the transaction is included in a block.

  1. Start: user balance = 2 ETH, user nonce = 7, contract balance = 0 ETH.
  2. Value moved: 0.3 ETH leaves the user's balance and enters the contract's balance.
  3. Fee paid: gasUsed × effectiveGasPrice = 0.001 ETH leaves the user's balance; the base fee is burned and the priority fee goes to the block producer, not the contract.
  4. User balance = 2 − 0.3 − 0.001 = 1.699 ETH.
  5. Contract balance = 0 + 0.3 = 0.3 ETH.
  6. Nonce counts the transaction once: 7 + 1 = 8.

Answer. User balance = 1.699 ETH, contract balance = 0.3 ETH, user nonce = 8.

Exam traps

  • Treating the wallet as the blockchain. The wallet holds keys and displays a view; the node and world state hold the truth.
  • Mixing up node and client. The client is the software; the node is the computer running it. Exam answers that say 'a client is a machine' lose marks.
  • Adding the gas fee to the receiving contract. Only the value reaches the contract; the whole fee leaves the sender, with the base fee burned and only the priority fee going to the block producer.
  • Forgetting the nonce goes up by exactly one per included transaction, even if the call fails during execution.
  • Assuming a light node keeps the full state. It keeps headers and checks proofs; the state lives on full and archive nodes.

5.2 Ether, tokens, transactions and messages

Ether is the money Ethereum runs on. Fees and value transfers are counted in wei, an integer. A transaction is a signed instruction from an account that owns a private key: it moves value, pays gas and changes shared state. A message is an internal call made by code during execution, with no signature and no pool entry. Tokens are contract records, not coins. This chapter keeps ether, transactions and messages apart, because examiners test that confusion and every wallet depends on it.

You need: 5.1 for accounts and nodes, the transaction life cycle from Unit 3, and digital signatures from Unit 4.

Ether, units and two account types

Ether (ETH) is Ethereum's native currency. It pays for computation and moves between accounts. The network stores no decimals; it stores whole numbers of wei. 1 ETH = 10¹⁸ wei. Gas prices are quoted in gwei: 1 gwei = 10⁹ wei, so 1 ETH = 10⁹ gwei. Contract code holds wei as an integer, never as a floating-point number.

Ethereum has two account types. Both have a 20-byte address and both can hold ether.

  • Externally owned account (EOA): derived from a public key and controlled by the matching private key. It has a balance and a nonce, and no code. Only an EOA can start a transaction.
  • Contract account: created by a transaction or by another contract. It has code and storage. It cannot act on its own; it runs only when a transaction or a message calls it.

The nonce is a counter kept per account. For an EOA it is the number of transactions that account has sent: a transaction with nonce 7 is rejected until nonce 6 is on chain, which fixes ordering and stops anyone re-broadcasting a signed transaction to move the same funds twice. For a contract account it counts the contracts created.

A transaction: fields and life cycle

A transaction is a signed instruction from an EOA. Its fields are:

  • nonce — the sender's next count
  • to — recipient address; empty when the transaction creates a contract
  • value — ether sent, in wei
  • data — input bytes for a contract call, or the bytecode when creating one
  • gasLimit — the maximum gas the sender allows this transaction to burn
  • gas price — legacy transactions give one gasPrice in wei per gas; newer type-2 transactions give maxFeePerGas and maxPriorityFeePerGas instead
  • v, r, s — the ECDSA signature over all the above fields and the chain id

A plain transfer to an EOA consumes exactly 21,000 gas and runs no code. Intrinsic gas for any transaction is 21,000 for the base, plus 32,000 more when creating a contract, plus 16 gas per non-zero calldata byte and 4 gas per zero byte. On top of that come the opcodes actually executed (5.3). The fee is not the same thing as the value.

fee = gasUsed × gasPrice

gasUsed is the gas actually consumed (in gas); gasPrice is the price of one gas in wei per gas; fee is in wei. gasLimit is a cap, not a charge.

  1. The wallet fills the fields, hashes them, signs the hash with the sender's private key and produces a raw transaction.
  2. It broadcasts the raw bytes to a node.
  3. The node checks the signature, the chain id, that the nonce is the next one, that the balance covers value + gasLimit × gasPrice, and that gasLimit is at least 21,000.
  4. The transaction waits in the pool; a block producer orders candidates by fee per gas.
  5. The EVM executes it, charging gas per opcode. Unused gas returns to the sender.
  6. The node returns a receipt; the wallet reports confirmation as later blocks pile on top.

Messages, receipts and logs

A message is a call made by code while the EVM is already executing. CALL, STATICCALL and DELEGATECALL each send a message to another address, but the callee sees different things:

  • CALL: the sender is the calling contract's address and the value is whatever is passed, which may be zero. The callee uses its own storage.
  • STATICCALL: the value is always zero and state writes are forbidden.
  • DELEGATECALL: the target's code runs in the caller's storage, and the callee sees the original msg.sender and msg.value of the parent frame — not the calling contract's own address or its own value.

The message also carries a data payload and a gas allowance. It is not a transaction: it has no signature and no nonce of its own, it never enters the pool, and it cannot exist without the transaction that started it. If a message reverts or runs out of gas, that frame's state changes and its ether transfer are undone; the caller receives a success flag and decides whether to continue or revert as well.

After execution the node stores a receipt: status 1 for success or 0 for reverted, the gas used, the cumulative gas in the block, a bloom filter for quick log search, and the logs.

Logs, also called events, are the cheap output channel. Each log has the emitting contract's address, up to four topics — topic 0 is usually the hash of the event signature — and a data blob. Contracts cannot read logs; logs exist for wallets, indexers and block explorers. Emitting a log costs far less gas than writing the same data to storage.

Tokens, and the two chains ETH and ETC

A token is not a currency on its own chain; it is a number inside one contract's storage. ERC-20 defines a mapping from address to balance, a totalSupply, a decimals field, the functions transfer, approve and transferFrom, the view function balanceOf(address), a nested allowance mapping (owner to spender to amount), and the events Transfer and Approval. Wallets call balanceOf to display a balance. approve sets one entry in the allowance mapping; transferFrom spends from it.

Token amounts are integers in the token's smallest unit. With decimals = 6, a stored balance of 2,500,000 means 2.5 tokens. Sending tokens is a transaction to the token contract whose data names transfer and the recipient, and its gas is paid in ether — so an account holding tokens but no ether cannot move them.

Non-fungible tokens follow ERC-721: each tokenId has exactly one owner, so every unit is distinct rather than a line in a shared balance.

In 2016 the DAO contract (5.8) was drained. Most participants accepted a hard fork that rewrote the affected state, and that chain is ETH. Nodes that rejected the fork kept the original history and became ETC. Blocks before the fork are shared, and the same private key controls the same address on both chains, so replay is prevented only by putting the chain id in the signature.

Worked example

Question. A sender transfers 0.1 ETH to a friend. The transaction consumes 21,000 gas and the gas price is 20 gwei. Find the fee in wei and in ETH, and the total ether debited from the sender.

  1. gasUsed = 21,000 gas. gasPrice = 20 gwei = 20 × 10⁹ wei = 2 × 10¹⁰ wei per gas.
  2. fee = gasUsed × gasPrice = 21,000 × 2 × 10¹⁰ wei = 4.2 × 10¹⁴ wei.
  3. Convert to ETH: 4.2 × 10¹⁴ ÷ 10¹⁸ = 0.00042 ETH. Check in gwei: 21,000 × 20 gwei = 420,000 gwei, and 420,000 ÷ 10⁹ = 0.00042 ETH.
  4. value = 0.1 ETH is separate from the fee.
  5. Total debit = value + fee = 0.1 + 0.00042 = 0.10042 ETH.

Answer. The fee is 4.2 × 10¹⁴ wei = 0.00042 ETH, and the sender is debited 0.10042 ETH in total.

Exam traps

  • The fee is gasUsed × gasPrice, never the value sent. They are added, not confused.
  • Unit slip: 20 gwei is 20 × 10⁹ wei. Multiply by 10⁹ before multiplying by gas, or the answer is off by a billion.
  • gasLimit is a cap: ether reserved is gasLimit × gasPrice, ether spent is gasUsed × gasPrice, and the difference is refunded.
  • A message is not a transaction: no signature, no nonce, no pool entry. Only an EOA starts a transaction.
  • Token balances carry their own decimals: a stored 2,500,000 with decimals = 6 is 2.5 tokens.

Not for the exam. Most networks now use EIP-1559 pricing: each block has a base fee that is burned and a priority tip for the block producer, so estimation uses maxFeePerGas and maxPriorityFeePerGas instead of one gasPrice. 5.3 Ethereum Virtual Machine (EVM)

The Ethereum Virtual Machine (EVM) is the part of every Ethereum node that runs contract bytecode. It is a stack machine with 256-bit words, so the same bytecode gives the same result on every node. It is gas-metered: each opcode has a price, and execution stops when gas runs out. The EVM changes account state only through state changes that a block finally commits. Wallets, tokens, DeFi and NFTs all run on it.

You need: transaction execution in 5.2 and block structure from Unit 1.

A deterministic stack machine

The EVM is a virtual machine: software inside each Ethereum node that executes bytecode. Bytecode is a sequence of bytes; each opcode is one byte, sometimes followed by immediate data. A contract account stores code. A transaction or message calls that code. Every full node runs the same bytecode with the same input and gets the same result. This determinism lets nodes agree on state without trusting one executor. Some syllabi call this the EVM execution model.

The EVM is a stack machine, not a register machine. It has one last-in-first-out stack of 256-bit words. A 256-bit word is 32 bytes. Arithmetic is modulo 2²⁵⁶: values wrap on overflow. The stack holds at most 1024 items. Opcodes push, pop or combine stack items. For example PUSH1 0x02 pushes the one-byte value 2; ADD pops two items, adds them, and pushes the sum. High-level code from 5.5 compiles to this. Deployment and ABI are covered in 5.7.

Memory, storage and calldata

The EVM has three data areas beyond the stack. Memory is a flat byte array, created fresh for each call frame. It is volatile: it disappears when the frame ends. Reading or writing memory costs gas, and memory expands in 32-byte words when touched, so large arrays cost more. Calldata is the read-only input bytes attached to a call. It is cheap to read and cannot be changed by the running code.

Storage is persistent contract state: a key-value map from 256-bit keys to 256-bit values. SSTORE writes storage; SLOAD reads it. Storage survives between transactions and is part of account state committed in a block. Storage writes are far more expensive than memory writes because every node must keep the data. MSTORE writes a 256-bit word to memory. A common mistake is to treat memory as permanent; it is not. State that must survive must go to storage or be emitted in logs and stored off-chain.

Gas and call frames

Gas is the unit of execution work. Every opcode has a gas cost. A transaction sets a gas limit; if execution uses all gas, it stops with out-of-gas and its state changes are rolled back. Unused gas is returned to the sender, subject to the fee rules. Gas accounting makes infinite loops impossible: a loop must pay each iteration. Gas costs can change between protocol upgrades, so bytecode that assumes a fixed total may fail after an upgrade.

A CALL creates a new call frame with its own stack, memory and calldata. The caller can pass value in wei (see 5.2) and a gas limit. If the callee reverts, the CALL returns 0 and the callee's state changes are undone, but the caller can continue. REVERT stops execution, undoes the frame's state changes, returns remaining gas and can return error data. An invalid opcode consumes all gas in the frame. Logs are written by LOG opcodes; they appear in transaction receipts and are not readable by contracts during execution.

What a block commits

The EVM itself does not decide consensus. It executes during block processing. After execution, the node has a new state root: a cryptographic commitment to all account balances, nonces, code and storage. The block header carries that root. If two nodes execute the same transactions on the same parent state, they must reach the same root. A revert leaves the state as if the failing internal call had not happened, apart from gas paid to the miner or validator. This is why contract code must check inputs and use REVERT deliberately.

Worked example

Question. A contract's bytecode begins 60 02 60 03 01. Opcode 60 is PUSH1: read the next byte and push it. Opcode 01 is ADD: pop two values, add them, and push the sum. PUSH1 costs 3 gas and ADD costs 3 gas. Give the stack after each instruction, top first, and the total gas used.

  1. Start: stack is empty and gas used is 0.
  2. Execute 60 02: PUSH1 0x02 pushes 2. Stack top first is [2]. Gas used = 3.
  3. Execute 60 03: PUSH1 0x03 pushes 3. Stack top first is [3, 2]. Gas used = 3 + 3 = 6.
  4. Execute 01: ADD pops 3 and 2, pushes 3 + 2 = 5. Stack top first is [5]. Gas used = 6 + 3 = 9.

Answer. After ADD the stack is [5] top first, and the total gas used is 9 gas.

Exam traps

  • The EVM is a stack machine, not a register machine. ADD pops two values and pushes one result; it does not leave the operands in place.
  • EVM words are 256-bit, and arithmetic wraps modulo 2²⁵⁶. Do not treat values as ordinary Python integers in overflow questions.
  • Memory is temporary and expands during a call, so memory gas grows. Storage is persistent account state and costs much more to write.
  • REVERT undoes the frame's state changes and returns unused gas; an invalid opcode consumes all gas in that frame. Out-of-gas also fails and rolls back.
  • Logs go to receipts, not to contract storage. A contract cannot read a log from an earlier transaction as if it were state.

5.4 Smart contracts: concept and development

A smart contract is code that lives on the blockchain at its own address, together with the data it keeps. Send it a transaction and it runs, on every node, with the same result everywhere. It exists so that an agreement can be enforced by published rules instead of a trusted middleman: the money moves when the condition is met, and no party can quietly change the condition. Escrow, subscription micropayments, token sales and decentralized lotteries all run this way.

You need: 5.3 EVM execution and the simple contract ideas from Unit 4, Bitcoin scripts.

Code plus state at an address

A smart contract is a program stored on the blockchain together with the data it owns. It sits at its own address, like an account number. Anyone can send a transaction to that address. The code then runs on every node, and every honest node computes the same result.

The point is to remove the middleman. A buyer and a seller who do not trust each other can lock money in a contract that pays out only when its published rule is met. The bytecode at an address cannot be edited, so a new version of the rules needs a new address, and both sides can read the code before they join. The one deliberate exception is a proxy pattern, where a fixed address forwards to logic that can be replaced (see Beyond).

Ethereum has two account types. An externally owned account (EOA) is controlled by a private key and belongs to a person or an off-chain program. A contract account holds code and storage and has no private key. It cannot sign anything; it acts only when an EOA, or another contract, calls it. See 5.2.

  • Code is fixed. The bytecode at an address cannot be edited; a new version needs a new address.
  • State is public. Anyone can read a contract's storage.
  • Execution is deterministic. Same input and same starting state give the same output on every node.
  • Execution is metered. Every operation costs gas, so a loop that never ends cannot hang the network.

From rules to a running contract

  1. Write the rules as functions and variables in a contract language. Solidity is the common one; details are in 5.5.
  2. Compile. The compiler produces EVM bytecode for the chain and an ABI, a JSON list of function names and argument types that tools use to call them.
  3. Test on a local chain or testnet. Every path, including the refund path, is exercised before real money is at risk (5.6).
  4. Deploy with a transaction that has no recipient and carries the bytecode. Deployment happens once and costs gas in proportion to the bytecode length.
  5. Interact. Users send transactions that may change storage, or make free calls that only read.
contract_address = keccak256(rlp(sender, nonce))[12:]

sender is the deploying EOA's address; nonce is that EOA's transaction count; keccak256 is Ethereum's hash function; [12:] keeps the last 20 bytes, which is the address.

The address depends on the sender and its nonce, so the same developer can deploy the same bytecode twice and get two different contracts.

Calls, events and outside data

There are two ways to talk to a contract. A transaction is signed, costs gas, is mined into a block and may change storage. A call is a free local read: the node runs the code against the current state and throws the result away. Reading a balance is a call; sending ether is a transaction.

A contract reports what happened through events. An event writes a log in the transaction receipt. The contract cannot read its own past logs, but wallets and indexers watch them to show messages such as Payment released.

Determinism has a price. Every node must get the same answer, so a contract cannot read a real clock, a random number or a website. If it could, two nodes would disagree and the chain would split. The block timestamp is available, but the block producer can nudge it by a few seconds.

Outside data enters through an oracle: a separate service that fetches a price or a score and writes it into a contract in a transaction. The contract then reads the stored value. The oracle is a trust point, and a bad feed gives a wrong contract result.

Escrow, micropayments, decentralized lotteries

Escrow. The buyer deposits ether; the contract releases it to the seller if the buyer confirms within a fixed time. If the buyer does not confirm, the buyer calls a refund function after the deadline, and only then does the contract send the deposit back. The worked example below uses 1 ETH and 7 days.

Micropayments. A viewer deposits a small amount into a payment channel and signs a voucher for each second of video watched. The channel settles once, on exit, so thousands of tiny payments cost one transaction fee instead of thousands.

Decentralized lottery. Players pay an entry fee to the contract, which stores the list of players. When the round closes, the contract picks a winner and pays the pot. A plain block hash is a weak random source, because the block producer can bias it, so real designs use commit-reveal or an external verifiable random function.

Worked example

Question. A buyer deposits 1 ETH into an escrow contract. The contract releases the 1 ETH to the seller if the buyer calls confirm within 7 days; if the buyer does not confirm, the buyer can claim a refund after 7 days. The buyer confirms on day 3. Ignoring gas, find the amount paid to the seller and the contract balance after the release.

  1. Deposit received: the contract balance becomes 1 ETH, and the buyer's address is recorded as the payer.
  2. Deadline check: confirm_day = 3 days and deadline = 7 days, so 3 ≤ 7. The condition is true.
  3. Payout to the seller = deposit = 1 ETH. The contract sends this with an internal message, so no extra transaction is needed from the buyer beyond the confirm call.
  4. Refund to the buyer = deposit − payout = 1 − 1 = 0 ETH, because the confirm path ran and the refund path is now closed.
  5. Contract balance after the release = 1 − 1 − 0 = 0 ETH. The storage still exists at the address, but it holds no ether.
  6. Seller receipt = payout = 1 ETH. Gas is ignored, so the seller gets the full amount.
  7. Note the ordering: the contract must zero its own record of the deposit before sending ether, or a re-entrant call could drain it twice.

Answer. The contract pays 1 ETH to the seller, the seller receives 1 ETH, and the contract balance is 0 ETH.

Exam traps

  • 'Smart' does not mean intelligent. A smart contract is deterministic code; it does not think, negotiate or read the news.
  • A contract cannot start itself, keep a timer, or fetch a web price. It runs only when a transaction reaches it, and outside data must come through an oracle.
  • Deploying is a transaction and costs gas. A call to a view function costs the caller no gas, because no state change is persisted and nothing is written to a block; the receiving node still does the work of running the code.
  • A contract account has no private key, so it can never sign a transaction. Every transaction on Ethereum begins at an EOA.
  • In escrow questions, do not add the payout to the balance. After releasing 1 ETH the contract holds 0 ETH; the seller receives the deposit, not the deposit twice.

5.5 Solidity programming language

Solidity is a statically typed language for writing smart contracts on Ethereum. A compiler turns a .sol file into EVM bytecode. The language exists so a developer can name state, functions, events and access rules in one contract. It is used for tokens, wallets, DeFi pools, NFT marketplaces and DAO voting. This chapter reads a small contract line by line: pragma, state, mapping, functions, visibility, modifiers, events, errors, payable, inheritance and storage versus memory. Some syllabi call this the Solidity language or smart contract programming.

You need: 5.3 EVM for bytecode and gas, and 5.4 contract lifecycle for what a contract account is.

Pragma, contract and state

Every Solidity file starts with a version pragma. pragma solidity ^0.8.0; means compile with a 0.8.x compiler, not 0.7.x. Compiler versions differ, so the pragma pins the rules the file expects. A contract is a type: it holds state variables and functions at one address.

pragma solidity ^0.8.0;
contract SimpleBank {
    mapping(address => uint) public balances;
}

contract declares the type. mapping(address => uint) is a hash table from an account address to an unsigned integer. address is a 20-byte Ethereum account identifier. uint means uint256, a non-negative integer from 0 to 2²⁵⁶−1. balances is a state variable: it lives in contract storage on every node. public makes Solidity generate a getter function called balances(address); it does not make the variable callable as balances(). An unknown key returns 0, because every storage slot starts at zero. That zero default is useful and dangerous: it looks like a real balance of zero, never an error.

Functions, visibility, payable and modifiers

A function declares inputs, visibility, mutability and output.

function deposit() public payable {
    balances[msg.sender] += msg.value;
    emit Paid(msg.sender, msg.value);
}

function starts the definition. deposit is the name. public means callable from outside and inside the contract. payable allows ether with the call. msg.sender is the caller address. msg.value is the wei sent; 1 ETH = 10¹⁸ wei. += adds to the stored balance. emit Paid(...) writes a log.

Visibility: public callable anywhere; external only from outside; internal only this contract and children; private only this contract. view promises no state change; pure promises no state read or change.

A modifier wraps a function with a check. modifier positive(uint x) { require(x > 0, "zero"); _; } The underscore _ is where the function body runs. require(condition, message) reverts the whole call if false. Modern code can use error ZeroAmount(); then revert ZeroAmount();; a custom error is cheaper than a string.

An event is a log declaration: event Paid(address indexed who, uint amount); indexed makes a searchable topic. Events are not readable by contracts; they are for off-chain tools.

Storage, memory and inheritance

storage is permanent state on chain. memory is temporary data for one call. A local variable of a reference type, such as a string or array, must say where it lives. string memory name = "Asha"; is copied for the call. Assigning a storage pointer to a memory variable copies; assigning storage to storage shares. Value types like uint and address are copied by default.

Inheritance lets a contract reuse code: contract Savings is SimpleBank { ... } Savings gets the state and functions of SimpleBank. A child can override a function marked virtual by marking its own override. Constructor code runs once at deployment. address payable is an address that can receive ether with transfer or send; plain address cannot. In 0.8.x, arithmetic overflow reverts by default, so x + y on uint is checked.

Worked example

Question. A contract SimpleBank has mapping(address => uint) balances. Alice deposits 0.5 ETH, Bob deposits 0.2 ETH, and Alice withdraws 0.1 ETH. Give Alice balance, Bob balance and total contract balance.

pragma solidity ^0.8.0;
contract SimpleBank {
    mapping(address => uint) public balances;
    event Paid(address indexed who, uint amount);
    function deposit() public payable {
        balances[msg.sender] += msg.value;
        emit Paid(msg.sender, msg.value);
    }
    function withdraw(uint amount) public {
        require(balances[msg.sender] >= amount, "low balance");
        balances[msg.sender] -= amount;
        payable(msg.sender).transfer(amount);
        emit Paid(msg.sender, amount);
    }
}
  1. Start: Alice = 0 ETH, Bob = 0 ETH, contract total = 0 ETH.
  2. Alice deposits 0.5 ETH: Alice = 0.5 ETH, Bob = 0 ETH, contract total = 0.5 ETH.
  3. Bob deposits 0.2 ETH: Alice = 0.5 ETH, Bob = 0.2 ETH, contract total = 0.7 ETH.
  4. Alice withdraws 0.1 ETH: Alice = 0.5 − 0.1 = 0.4 ETH, Bob stays 0.2 ETH, contract total = 0.4 + 0.2 = 0.6 ETH.

Exam traps

  • A mapping returns 0 for an unknown key; it does not revert. A zero balance and a missing key look the same.
  • address and address payable are not the same; only address payable can be the target of transfer.

5.6 Ethereum development environment and test networks

Ethereum development needs a safe chain to compile, deploy and test contracts before real ether is at risk. A development environment is the editor, compiler, EVM and connection tools you use. A test network is a public chain with valueless ether. A private net is your own chain with your own genesis. These tools catch bugs, check gas and rehearse deployment before mainnet.

You need: contract lifecycle in 5.4, Solidity in 5.5, and mining and consensus in Unit 3.

Development environments and test networks

A development environment is all the software used to write, compile, deploy, call and debug a contract. Remix IDE runs in a browser. It has an editor, a Solidity compiler, a deploy panel and a debugger. It can run a JavaScript VM in the browser, so a contract deploys in seconds without a node. It can also connect to an injected wallet or to a node RPC URL.

  • Local blockchain tools such as Ganache, Hardhat Network and Anvil start a chain on your laptop. They mine on demand and give funded test accounts.
  • Use local tools for automated tests and quick resets. Use a public testnet when other people or services must reach your contract.

A testnet is a public Ethereum network with ether that has no market value. Sepolia is a common testnet. Testnet names and endpoints change, so never trust an old tutorial. A faucet is a service that sends a small amount of test ether to your address. It may require a sign-in or a proof of work. Test ether lets you pay gas without risking rupees.

Testnets share Ethereum rules but not mainnet state. A contract address on Sepolia is not the same contract on mainnet. The address can look the same, but the state and balance belong to that chain. The chain ID inside transactions keeps signatures from being replayed on another chain. See 5.2 for transaction fields.

Setting up a private net

Some syllabi call this Ethereum development environment, test networks and setting up a private net. A private net is a chain you control. It has its own genesis block, its own chain ID and its own accounts.

  1. Write a genesis file. It sets config.chainId to 1337, gasLimit to 30,000,000, and an alloc entry that gives account A, whose key you hold, 100 ETH. The chain ID is used in transaction signatures. The alloc gives starting balances before block 1.
  2. Initialize the data directory: geth init genesis.json --datadir ./mynet. This writes the genesis block into that directory. A different genesis file creates a different chain.
  3. Start the node with the same data directory and a network ID, for example --networkid 1337. The network ID groups peers; the chain ID from genesis signs transactions. Turn on HTTP RPC only on 127.0.0.1 for local work. Turn on mining if your client version supports it; on some local dev chains blocks are produced on demand.
  4. Create account B with geth account new or import a key. Unlock account A locally so it can sign a transaction. Never unlock a mainnet account on a public RPC.
  5. Send 1 ETH from A to B with gas limit 21,000 and gas price 1 gwei. The transaction enters the pending pool.
  6. Mine block 1. The transaction is included, A pays 1 ETH plus the fee, and B receives 1 ETH. Query both balances to confirm.

Reading the numbers

A transfer of ether between two externally owned accounts costs 21,000 gas. Gas is the unit of work; gas price is ether per gas. The fee is:

fee = gas used × gas price

fee is in ETH; gas used is in gas units; gas price is in ETH per gas. 1 gwei = 0.000000001 ETH.

The block gas limit is the maximum gas all transactions in a block may use. It does not set your fee. A gas limit on a transaction is a cap; unused gas is refunded. The miner receives the fee. In the worked example, block rewards are ignored because they do not change A or B.

A pending transaction has no balance change. A wrong chain ID or a different genesis gives a different network, not a connection to mainnet. Test ether is only for testing and has no market value. See Unit 3, Proof of Work and mining, for why a block must be mined.

Worked example

Question. A private net genesis sets chainId 1337 and block gas limit 30,000,000. Account A starts with 100 ETH in genesis. A sends 1 ETH to B using 21,000 gas at 1 gwei. Ignoring block rewards, find A and B balances after mining.

  1. Gas used = 21,000 gas. Gas price = 1 gwei = 0.000000001 ETH per gas.
  2. Transaction fee = 21,000 × 0.000000001 ETH = 0.000021 ETH. This is 21,000 gwei.
  3. A starts with 100 ETH. A sends 1 ETH to B and pays 0.000021 ETH fee: 100 − 1 − 0.000021 = 98.999979 ETH.
  4. B receives the transfer only. B = 0 + 1 = 1 ETH. The fee goes to the miner, not to B.
  5. The block gas limit 30,000,000 is above 21,000, so the transaction fits. It does not change the fee. Ignoring block rewards, final balances are A = 98.999979 ETH and B = 1 ETH.

Answer. After block 1 is mined, A has 98.999979 ETH and B has 1 ETH.

Exam traps

  • Test ether has no market value. If a site sells test ether, treat it as a warning. Faucets give small amounts for testing only.
  • A wrong chain ID or genesis file creates a different network. It does not connect to mainnet. The same address on two chains has separate balances and state.
  • Do not confuse gas limit with fee. A 21,000 gas transfer at 1 gwei costs 0.000021 ETH. A block gas limit of 30,000,000 is only a block cap.
  • A pending transaction is not a balance change. If mining is off, the transfer stays pending and balances do not move.
  • Testnet names, RPC URLs and faucets change. Check the chain ID before sending a transaction; an old tutorial may point to a dead or different network.

5.7 Web3, contract deployment and development frameworks

A DApp is a web page or mobile app that talks to a contract on Ethereum. The page cannot reach the chain by itself: a Web3 library turns a JavaScript function call into a JSON-RPC request, a wallet adds the signature, and a node runs the result on the EVM. Deployment follows the same path with one extra step — a transaction whose data is the contract's bytecode, which the network stores at a fresh address. Teams therefore use a development framework to compile, test and deploy the contract, and then to wire its address and ABI into the front end.

You need: 5.2 for transactions and gas, 5.5 for Solidity functions, and 5.6 for local chains and testnets.

JSON-RPC, providers and signers

An Ethereum node exposes its functions over JSON-RPC. Every request is a small JSON object with four fields: jsonrpc (the protocol version, normally "2.0"), method (the function to run), params (an array of arguments) and id (a tag echoed back in the reply). To read a balance the client sends method eth_getBalance with the address and the block tag "latest". Plain HTTP suits one-off requests. WebSocket suits subscriptions, where the node pushes new blocks and event logs to the client as they appear.

A Web3 library writes and parses these messages so the programmer never handles raw JSON. Web3.js and ethers.js are the two JavaScript libraries in wide use. Both take a contract object, encode the call, send it to the node and decode the reply into ordinary JavaScript values. Python and Java have similar libraries.

Two objects do the work. A provider knows a node's URL and transports requests; it is read-only. A signer holds a private key and can produce a signed transaction. ethers.js keeps them separate on purpose, so that code which only reads state can run with no key at all.

In a browser the signer is usually a wallet extension such as MetaMask, which injects a provider object at window.ethereum. The page asks the wallet to sign; the key never leaves the wallet. This is why a private key pasted into front-end JavaScript is a serious bug — anyone who opens the page can read it.

ABI, bytecode and the deployment transaction

The Solidity compiler emits two things a DApp needs. Bytecode is the hexadecimal EVM code that lives on chain. The ABI (Application Binary Interface) is a JSON list describing each public function: its name, argument types, return types, and whether it is view, pure or payable. The ABI is a calling convention, not code. It plays the role a function prototype plays in C — it tells the caller how to pack arguments and unpack results.

To call a function, the library hashes the signature text, for example transfer(address,uint256), with keccak-256 and keeps the first four bytes. That is the selector. Calldata is the selector, then each argument padded to a 32-byte word. Without the right ABI the library cannot build this calldata, so an address alone is not enough to use a contract.

Deployment is a transaction with an empty to field. The data field holds the bytecode, with any constructor arguments appended. The EVM runs that init code, which returns the runtime code, and the node stores the runtime code at a new address. The address is the last 20 bytes of the keccak-256 hash of the RLP encoding of the deployer's address and its nonce, so each deployment from the same account lands at a different address.

A read uses eth_call: one node runs the function against current state, returns the value at once, needs no signature, and spends no gas. A write is a full transaction: signed, gossiped, mined, and paid for in gas. It returns only a transaction hash, not a value. You read the outcome later from the receipt and its event logs.

Frameworks and DApp front-end architecture

A development framework automates the loop of compile, test, deploy. Hardhat is JavaScript and TypeScript based; it starts a local chain inside the same process, gives Solidity a console.log, and loads plugins for testing and verification. Truffle is the older tool: it uses numbered migration scripts and usually pairs with the Ganache local chain. Foundry, written in Rust, is a newer option. All three produce a build artifact per contract that bundles the ABI and bytecode, plus the address after deployment.

  1. Write the contract in a .sol file and compile it; the artifact holds ABI and bytecode.
  2. Write tests that deploy to a local chain and assert on return values and events.
  3. Write a deploy script that sends the deployment transaction and records the new address.
  4. Point the front end at the node URL and load the artifact with address and ABI.
  5. The user connects a wallet; reads go through the provider, writes through the wallet's signer.

The front end has three jobs. It shows contract state by calling view functions through a provider. It sends changes by asking the wallet to sign a transaction, then waits for the receipt and updates the screen from pending to confirmed. It listens for contract events so the display stays current without a manual refresh. The figure traces one click through these layers.

Worked example

Question. A team deploys a contract with a deployment transaction that uses 1,500,000 gas at a gas price of 20 gwei. The deployer account starts with 5 ETH and the transaction sends 0 ETH of value. Find the deployment fee in ETH and the balance left in the account.

  1. Gas used = 1,500,000 gas. Gas price = 20 gwei.
  2. Convert the price: 1 gwei = 10⁹ wei, so 20 gwei = 20 × 10⁹ = 2 × 10¹⁰ wei per gas.
  3. Fee in wei = gas used × gas price = 1,500,000 × 2 × 10¹⁰ = 3 × 10¹⁶ wei.
  4. Convert to ether: 1 ETH = 10¹⁸ wei, so fee = 3 × 10¹⁶ ÷ 10¹⁸ = 0.03 ETH.
  5. The transaction sends 0 ETH of value, so only the fee leaves the account: balance = 5 − 0.03 = 4.97 ETH.

Answer. The deployment fee is 0.03 ETH, and the deployer is left with 4.97 ETH.

Worked example 2

Question. A read call to a view function is made with eth_call and costs nothing. A second operation writes to storage using 45,000 gas at 40 gwei. What does the write cost in ETH, and what does the caller receive back from the node immediately?

  1. Fee in gwei = 45,000 × 40 = 1,800,000 gwei.
  2. Convert: 1,800,000 gwei ÷ 10⁹ gwei per ETH = 0.0018 ETH.
  3. A write is a transaction, so the node returns a transaction hash at once, not the function's return value.
  4. The return value and events appear only in the receipt after the transaction is mined.

Answer. The write costs 0.0018 ETH, and the caller immediately receives only a transaction hash.

Exam traps

  • An address alone cannot be called. You need the address and the matching ABI; the wrong ABI builds wrong calldata and the call fails or returns garbage.
  • eth_call is not a transaction. It changes nothing, spends no gas, needs no signature, and returns the value directly. A state-changing send returns a hash and must be waited on.
  • The ABI is not the bytecode and gives no security. It is only a description of the interface; anyone can write an ABI for any address.
  • The deployment address depends on the deployer address and its nonce, not on the bytecode alone, so the same bytecode deployed twice gives two different addresses.
  • Unit slip: gas price is quoted in gwei (10⁹ wei) but balances are in ether (10¹⁸ wei). Multiply gas by the price in wei first, then divide by 10¹⁸.

Indexing layers such as The Graph store event logs so a DApp can query history without scanning every block. 5.8 DAO, GHOST protocol and side chains

A DAO is an organisation whose rules, treasury and decisions live in smart contracts and token votes, with no board in the middle. GHOST is a fork-choice rule that follows the heaviest block subtree instead of the longest chain, so stale blocks still count. A side chain is a separate blockchain joined to a main chain by a bridge. Only a few universities teach this chapter; the ideas appear in DeFi governance, Ethereum's uncle blocks and scaling side chains.

You need: Unit 3 forks and consensus, and 5.1 Ethereum network.

DAO: rules and votes in code

A DAO (decentralised autonomous organisation) is a group whose membership, treasury and rules sit in smart contracts. Governance tokens give voting rights. Anyone may submit a proposal: a call to a contract function with arguments. A vote needs a quorum and a majority, and a timelock delays execution so members can leave before a change lands.

The DAO, launched in 2016, held a large ether treasury. Its split function sent ether to the caller before setting that caller's balance to zero. An attacker re-entered split through a fallback function and repeated the withdrawal inside one transaction. This is reentrancy: an external call made before the state update. The chain was hard forked to return the funds, splitting Ethereum and Ethereum Classic.

Other contract attacks: integer overflow, missing access control on admin functions, front-running of trades, and price-oracle manipulation. Defences are the checks-effects-interactions order, reentrancy guards, audited libraries and a pause switch.

GHOST and uncle blocks

GHOST (Greedy Heaviest Observed SubTree) is a fork-choice rule. Short block times create many blocks at one height; longest-chain throws all but one away. GHOST follows the branch whose subtree holds the most blocks, so stale work still counts.

weight(b) = 1 + Σ weight(c)

weight(b) is the number of blocks in b's subtree including b itself; c ranges over the direct children of b; Σ is their sum.

  1. Start at the root block.
  2. Compute weights bottom-up: a leaf has weight 1.
  3. Move to the child with the larger weight.
  4. Repeat until a leaf; that path is the main chain.

Ethereum uses a GHOST-based rule, so orphaned blocks become uncles: a later block names them and they earn a partial reward, which protects miners against network latency.

Side chains and bridges

A side chain is a separate blockchain with its own consensus and validators, joined to a main chain by a bridge. In a two-way peg, users lock coins in a main-chain contract, the bridge mints the same amount on the side chain, and burning on exit unlocks the original.

The side chain does not inherit mainnet security. Its validators can reorg or halt it, and the bridge contract holding the locked coins becomes the target. Federated bridges rely on a multisig of known signers; trustless bridges verify the other chain's headers. Both add attack surface. Rollups differ: they post data or proofs back to the main chain.

Worked example

Question. Blocks form this tree: A is the root. A has children B and U1. B has children C and U2. C has child D. A block's weight is 1 plus the weights of its children. Under GHOST, which child of A and which child of B lie on the main chain? Give every weight.

  1. D is a leaf: weight(D) = 1.
  2. C has one child: weight(C) = 1 + 1 = 2.
  3. U2 is a leaf: weight(U2) = 1.
  4. B has children C and U2: weight(B) = 1 + 2 + 1 = 4.
  5. U1 is a leaf: weight(U1) = 1.
  6. Children of A: B = 4, U1 = 1, so A moves to B.
  7. Children of B: C = 2, U2 = 1, so B moves to C.
  8. C has only D, so the main chain is A-B-C-D.

Answer. A follows B (4 against 1), B follows C (2 against 1); the main chain is A-B-C-D, with U1 and U2 as uncles.

Exam traps

  • GHOST is not longest-chain: it compares subtree weights, not heights.
  • Weight includes the block itself; forgetting the +1 gives 3 instead of 4 for B.
  • Uncles are not on the main chain and earn a partial reward, not a full one.
  • A side chain does not inherit mainnet security; the bridge contract and its signers add risk.
  • Reentrancy is an ordering bug (external call before the balance update), not a compiler fault.

Takeaways

  1. Ethereum is an account-based blockchain: state is a mapping from addresses to balances, code and storage, and nodes agree on that state block by block.
  2. Ether is the native coin; tokens are just numbers kept inside a contract, so holding a token never means holding ether.
  3. A transaction is signed outside the chain and changes state once; a message is a nested call made while that transaction executes.
  4. The EVM is a deterministic, gas-metered stack machine, which is why every node reaches the same state after running the same bytecode.
  5. Gas turns computation into a price, so an infinite loop costs money instead of freezing the network.
  6. A smart contract cannot act by itself: it only runs when a transaction or another contract calls it.
  7. Solidity compiles to bytecode and an ABI, and the ABI is what lets a DApp talk to the deployed code.
  8. Testnets and private nets exist so bugs are paid for with worthless coins, not real rupees.
  9. GHOST and side chains are both answers to scaling: one changes how forks are chosen, the other moves work to a separate chain with its own security.
  10. A DAO replaces managers with contracts and voting, so a bug in the voting rule is a bug in the organization.

Analyze and evaluate

Analyze Compare GHOST with the longest-chain rule and explain why GHOST suits Ethereum's block times. 13 marks

Longest chain: picks the chain with most blocks, ignores side branches; Ghost: picks the subtree with the greatest total work, counting stale blocks; Short block times create many near-simultaneous blocks and frequent forks; Without GHOST, stale blocks waste work and unfairly cut rewards; GHOST keeps security in the heaviest subtree and credits stale blocks; Trade-off: more bookkeeping, different confirmation intuition.

Evaluate Explain how a DAO works on Ethereum and evaluate its main risks. 14 marks

Membership and voting power held as tokens; Proposals submitted, debated and voted on chain; Treasury held by the contract and released only on a passed proposal; Execution automatic, so rules must be precise; Risks: code bugs, low turnout, vote buying, flash-loan voting, majority capture; Mitigations: timelocks, quorum, audit, upgrade or exit mechanisms.

Evaluate Assess side chains as a scaling answer for Ethereum: what they gain and what they give up. 12 marks

Gain: higher throughput, lower fees, own consensus tuned for the use case; Bridge mechanism moves assets in and out; Give up: mainnet security does not extend to the side chain; Bridge becomes a large target; validator set may be small; Withdrawal delays and fraud or validity proofs add complexity; Reasonable for experiments and games, weaker for high-value settlement.

Analyze Compare Bitcoin and Ethereum in data model, execution, currency and consensus, and say what each design favours. 16 marks

Bitcoin: UTXO set, script with limited operations, 21 million cap, proof of work; Ethereum: accounts with balance, code and storage, Turing-complete EVM, no fixed cap but fee burn; Transactions: Bitcoin inputs and outputs; Ethereum nonce, to, value, data, gas fields; Contracts: Bitcoin script is a spending condition; Ethereum contracts hold state and call each other; Consensus: both began with proof of work; Ethereum moved to proof of stake; Design aim: Bitcoin favours simple, auditable value transfer; Ethereum favours general computation.

Glossary

ABI
A JSON description of a contract's functions and arguments, used to encode calls and decode results.
Account nonce
A counter on an externally owned account that increases with each outgoing transaction and blocks replay.
Client
Software such as a full node implementation that stores the chain, validates blocks and answers RPC requests.
DAO
An organization whose membership, treasury and decisions are governed by contracts and token voting.
ERC-20
A widely used token interface standard with functions like transfer, balanceOf and approve.
Ethereum
A public, permissionless, account-based blockchain whose nodes run the EVM and agree on one shared state.
Event
A log entry a contract writes during execution; it is stored in transaction receipts and read by off-chain tools.
EVM bytecode
The binary instruction sequence the EVM executes for a contract.
Faucet
A service that sends small amounts of test ether to a testnet address.
Function selector
The first 4 bytes of the Keccak-256 hash of a function signature, used to identify the function in call data.
Gas limit
The maximum gas a sender allows a transaction to consume.
Gas price
The amount of ether offered per unit of gas, which sets the fee when multiplied by gas used.
Genesis block
The first block of a chain, defined by a configuration file for private networks.
GHOST
A fork-choice rule that follows the subtree containing the most total work, counting stale blocks.
JSON-RPC
The request format a wallet or DApp uses to talk to an Ethereum node over HTTP or WebSocket.
Memory
A contract's temporary byte array, cleared after each external call.
Modifier
A Solidity guard attached to a function that runs a check before or after the function body.
Revert
An EVM operation that undoes state changes in the current call and returns the unused gas.
Side chain
An independent chain connected to a main chain by a bridge, with its own consensus and security.
Signer
The object that holds a private key or asks a wallet to sign a transaction before it is sent.
Stale block
A valid block that is not on the chosen chain and earns no full reward.
Storage
A contract's permanent key-value store on chain, where every slot is 32 bytes.
Testnet
A public Ethereum network that uses worthless coins so contracts can be tested safely.
Wei
The smallest unit of ether; 1 ether = 10¹⁸ wei.
