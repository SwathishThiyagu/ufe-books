1.1 History, evolution and growth of blockchain

Blockchain is a shared ledger that many parties keep in step without a single owner. It exists because digital cash kept failing at one problem: a file can be copied, so one coin could be spent twice. The 2008 Bitcoin design solved that, and the ledger idea inside it outgrew the currency. Today the same idea sits behind cross-border payments, supply-chain records, land registries and smart contracts. This chapter traces how it got here: pre-Bitcoin digital cash, the 2008 whitepaper, the 2009 genesis block, Ethereum in 2015, and enterprise ledgers after that.

You need: no earlier chapter; a rough idea of a database helps, and hashing is covered later (see Unit 2, Cryptographic hash functions and SHA-256).

Digital cash before Bitcoin

Money stored as bits can be copied perfectly and free. A paper note cannot be in two places at once; a file can. If a buyer sends the same digital coin to two sellers, both see a payment that looks valid. This is double spending, and every digital-cash design before 2008 had to answer it.

Most answers used a central party. In the 1980s David Chaum's ecash hid buyer identity behind blind signatures, but a bank still cleared each coin to stop reuse. Later proposals such as b-money, bit gold and hashcash (proof of work used to price email) supplied pieces of a system, not a whole one.

A working system needed two things at once:

  • No central issuer, so no single party can freeze or inflate the money.
  • One agreed history, so every participant accepts the same order of transactions.

The second is the hard part, and it is a consensus problem; see Unit 3, Consensus mechanisms and their types. The building blocks were already known: hash functions and hash pointers (Unit 2, Linking blocks with hash pointers), Merkle trees, and digital signatures. Nobody had assembled them into a ledger that a stranger could verify. That assembly is what 2008 delivered.

The 2008 whitepaper and the 2009 genesis block

In October 2008 a short paper titled Bitcoin: A Peer-to-Peer Electronic Cash System appeared online. Its author is credited as Satoshi Nakamoto, a pseudonym; the real identity has never been confirmed. The claim was narrow and strong: payments between strangers, with no trusted third party, over a peer-to-peer network.

The method in outline: transactions are broadcast to the network, nodes gather them into a block, each block carries the hash of the block before it, producing a block costs computational work, and nodes follow the chain that has the most work behind it. Tampering with an old block breaks every link after it.

On 3 January 2009 the network produced its first block, the genesis block (block 0). It has no parent, so its previous-hash field is set to zero. It carried a 50 BTC coinbase reward. The first transfer to another person followed within days, and the ledger has run without an administrator since. That continuity is the real achievement of the genesis block.

Blockchain, defined separately: an ordered, append-only list of blocks, each block carrying the hash of its predecessor, copied across many nodes that accept a new block only if it obeys shared rules. Bitcoin is not the same thing. Bitcoin is a currency, a network and a protocol; blockchain is the ledger structure and update rule inside it. Think of blockchain as the notebook and Bitcoin as one account book written in it. Many blockchains now exist that hold no money at all (see 1.5).

Growth in three waves: 1.0, 2.0, 3.0

Growth is usually told as three loose waves. The 1.0, 2.0 and 3.0 numbering comes from industry writing, not a standards body; some syllabi call this the growth of blockchain technology.

Blockchain 1.0, currency. From 2009 Bitcoin showed the ledger worked at public scale. Altcoins copied the code with small changes: Namecoin for names, Litecoin for faster blocks (Unit 4, Alternative coins).

Blockchain 2.0, contracts. The Ethereum network launched in 2015, from a design proposed in 2013 by Vitalik Buterin and co-founders. It adds a virtual machine, so the ledger can run small programs. A smart contract is code stored on the chain that executes when its conditions are met, like a vending machine built in software (Unit 5, Smart contracts: concept and development). Ethereum also made issuing tokens a few lines of code.

Blockchain 3.0, wider use. Organisations that do not fully trust each other, but do know each other's identity, built consortium chains: a fixed set of validators rather than open membership. Hyperledger Fabric and Corda target trade finance, supply chain and insurance (Unit 6, Enterprise blockchain).

Two visible signs of growth:

  • Scaling debates: bigger blocks versus layers above the chain. Disagreement produced hard forks such as Bitcoin Cash in 2017 (Unit 3, Forks).
  • Consortium and private chains: proof that the ledger idea was separated from a traded currency.

Both point to the same shift: blockchain outgrew digital cash and became a general way to keep a shared record.

Exam traps

  • Writing 'Bitcoin and blockchain are the same'. Bitcoin is one currency and network; blockchain is the ledger structure and rules it uses.
  • Dating the start of Bitcoin to October 2008. That is the whitepaper; the genesis block is dated 3 January 2009, and the network went live on 9 January 2009.
  • Starting blockchain history at Ethereum in 2015, which skips roughly seven years of working Bitcoin history.
  • Treating a hard fork such as Bitcoin Cash as a software bug. It is a rule disagreement about block size that split the chain.
  • Assuming the 1.0, 2.0, 3.0 labels are official standards. They are informal industry labels for currency, contracts and wider enterprise use.

1.2 Distributed systems, distributed databases and distributed ledgers

A distributed system is a set of computers that work together and appear as one service. A distributed database stores data across those computers. A distributed ledger is a replicated, append-only database whose updates are validated by shared rules, not only by one administrator. Banks, UPI switches and supply-chain platforms use these ideas. This chapter separates three terms students often merge: distributed system, distributed database and distributed ledger.

You need: Chapter 1.1 for Bitcoin as an example of a distributed ledger.

Distributed systems and distributed databases

A distributed system has multiple nodes, each a computer or process, connected by a network. The nodes share work so the system can scale, survive a node failure and serve users in different places. A distributed database is a database whose data is stored on more than one node, but managed as one database.

Four ideas appear in every distributed database. Replication keeps copies of the same data on several nodes. Fragmentation splits tables or rows across nodes. Transparency hides that split from the user, who writes ordinary queries. Concurrency control orders simultaneous transactions so they do not corrupt shared data.

The CAP trade-off says a distributed data store cannot always give all three of consistency (every read sees the latest write), availability (every request gets a response) and partition tolerance (the system works when the network splits). During a partition, a system usually chooses consistency or availability. A bank balance system often chooses consistency; a social feed often chooses availability.

  • Administrator trust: a database administrator can change rules, balances or logs.
  • Conflict resolution: two sites may accept contradictory updates during a partition.
  • Reconciliation: after the partition, the system must decide which update wins.
  • Query needs: joins, indexes and SQL are strengths, but they assume a trusted coordinator.

Ledgers, distributed ledgers and blockchain

A ledger is an ordered record of transactions. In double-entry bookkeeping, every transaction has a debit entry and a credit entry, and total debits must equal total credits. That equality catches many errors. A bank's core ledger is a database plus business rules: a withdrawal must not make a balance negative.

A distributed ledger is a replicated, append-only record. Append-only means old entries are not silently edited; a correction is a new entry. Replicated means many participants hold a copy. Shared validation means participants apply the same rules before accepting an entry. Cryptographic linking means changing an old entry changes later links; Unit 2 covers the hash functions that make this work.

Distributed ledger technology (DLT) is the broader family. A blockchain is one DLT design that groups entries into blocks and links each block to the previous one. Not every DLT uses blocks. Replication alone does not make a distributed database a blockchain; shared validation and append-only hash-linked blocks are extra.

Two Generals and Byzantine Generals

The Two Generals problem models agreement over an unreliable link. Two armies must attack at the same time, but messengers may be captured. A general sends a time; the other agrees; the acknowledgment may be lost. No finite exchange of messages makes both generals certain that both will attack. The lesson is that acknowledgment does not create common knowledge.

The Byzantine Generals problem models agreement when some participants may send conflicting messages. Some generals may be traitors who tell one group attack and another retreat. The loyal generals need one plan despite faulty or malicious nodes. A crash fault is a node that stops silently. A Byzantine fault is a node that behaves arbitrarily: it may lie, delay or send different answers to different peers.

Ordinary distributed databases are built mainly for crash faults: replicate data, detect a dead node and recover. A distributed ledger that faces untrusted participants must also handle Byzantine faults. It needs enough independent validators and shared rules so a bad node cannot rewrite history alone. Consensus algorithms for this belong to Unit 3.

Worked example

Question. A bank runs a distributed database with 4 sites. A customer's balance of ₹10,000 is replicated at all 4 sites. Two withdrawals of ₹8,000 each are accepted locally at site 1 and site 2 at the same time, to be reconciled later. Explain why an overdraft can appear, and how a distributed ledger with shared validation avoids it.

  1. Initial balance B = ₹10,000 at each of the 4 sites.
  2. Site 1 accepts withdrawal W1 = ₹8,000 because its local copy shows ₹10,000 ≥ ₹8,000. Local balance becomes ₹2,000.
  3. Site 2 accepts withdrawal W2 = ₹8,000 because its local copy also shows ₹10,000 ≥ ₹8,000. Local balance becomes ₹2,000.
  4. After reconciliation, apply both withdrawals to the replicated balance: ₹10,000 − ₹8,000 − ₹8,000 = −₹6,000. The account is overdrawn by ₹6,000.
  5. With a distributed ledger, shared validation orders the two withdrawals. First W1 is checked against ₹10,000 and accepted; new balance is ₹2,000.
  6. Next W2 is checked against ₹2,000. Since ₹2,000 < ₹8,000, W2 is rejected. Final balance is ₹2,000.

Answer. The naive replicated database ends at −₹6,000, an overdraft of ₹6,000; shared validation accepts only one withdrawal and leaves ₹2,000.

Exam traps

  • Do not say a distributed database is automatically a blockchain. Replication copies data; shared validation and append-only hash-linked blocks are additional design choices.
  • Do not use DLT and blockchain as synonyms. DLT is the broader family; a blockchain is one DLT design that uses blocks.
  • In CAP, partition tolerance is not optional in a real network. The real choice during a partition is usually consistency versus availability.
  • Crash fault and Byzantine fault are different. A crashed node stops; a Byzantine node may keep running and lie.
  • Double-entry bookkeeping is not the same as two copies of a database. It is a rule that every transaction has matching debit and credit entries.

1.3 Decentralization and the need for blockchain

Decentralization means moving control of a system from one authority to many participants. It exists because a single owner can fail, censor, or charge rent. Blockchain is one route: it replicates data, shares validation, and records rules in code. It is not the only route and not always the right one. You meet the idea in UPI-style payment switches, branch banking, supply chains, and decentralized applications. The useful distinctions are centralization, decentralization, and distribution. The useful questions are who writes, who validates, and who can change the rules.

You need: Chapter 1.2 for replicated databases and shared ledgers.

Centralized, decentralized, distributed

A centralized system has one node or office that controls writes and validation. Other nodes may hold read-only copies. A decentralized system has many participants sharing control; no single participant can change the accepted state alone. A distributed system spreads computation or storage across many machines.

Distribution is about where processing sits. Decentralization is about who controls writes and validation. A bank with one core server and 6 read-only branch databases is centralized and distributed. A service on 100 cloud machines run by one company is still centralized if that company alone writes and validates.

Partial decentralization shares some control but keeps a central owner for membership, identity, or upgrades. Full decentralization has no central operator. Most real systems are partial. The figure shows the firm from the worked example before and after it takes this route.

Why decentralize, and what it costs

  • Single point of failure: one server or one administrator can fail or be attacked.
  • Censorship: a central owner can block a transaction, account, or application.
  • Trust: users need not trust one record keeper if many independent validators check the same ledger.
  • Cost: disintermediation removes a middle party and its fees.
  • Transparency: shared records can be audited by participants.
  • Coordination: many validators must agree; this takes messages and time.
  • Speed: shared validation is slower than one database write.
  • Governance: who changes the rules? Forks and votes are hard.
  • Legal clarity: responsibility is split across participants.

Decentralization is a trade, not a free upgrade. Use it when the failure, censorship, or trust cost of a central owner is higher than the coordination cost. A branch network may decentralize validation but keep central membership control. In a metaverse, shared asset records can let a user carry items between worlds; in payments, shared validation can reduce one switch's control.

Methods and routes to decentralization

  • Disintermediation: remove the middle party; buyer and seller deal directly.
  • Open participation: anyone may read, write, or validate under published rules.
  • Replicated data: every node keeps a copy of the ledger.
  • Shared validation: nodes agree on each write before it is accepted.
  • Token incentives: participants are paid or fined to follow the rules.

Some syllabi call these by other names; the mechanism is what matters. A common route has five steps: replicate the data across branches, open read access, open write access with signed transactions, add shared validation by consensus, then move rules into smart contracts. See Unit 3 for consensus and Unit 5 for smart contracts.

Smart contracts can hold escrow until delivery, send micropayments per use, or run a decentralized lottery without a central cashier. A DAO is a destination: an organization run by code and token votes, with no central boss. Decentralized applications (dApps) on Ethereum are another destination.

Blockchain alone does not give full ecosystem decentralization. If one company controls all validators, identity, and upgrades, the system is centralized in control even if it is distributed in storage. In practice, the decentralized web shares storage, identity, and naming; many projects still rely on central gateways.

Worked example

Question. A firm has 1 head-office server and 6 branch databases. The head office alone can write; branches hold read-only copies. Later all 6 branches and the head office validate writes on a shared ledger. (a) What fraction of the 7 sites can write before and after? (b) How many ledger copies exist after? (c) Is the first system centralized, decentralized, or distributed? (d) Which route did the firm take, and what may remain centralized?

  1. Count sites: 1 head office + 6 branches = 7 sites.
  2. Before, writers = 1 (head office). Write share = 1/7 = 0.142857... ≈ 0.143, or 14.3%.
  3. Before, all 7 sites hold copies, but only 1 writes. That is distributed storage with centralized control.
  4. After, writers and validators = 7. Validation share = 7/7 = 1.0, or 100%.
  5. Ledger copies after = 7.
  6. Route: replicate to 7 sites, open writes to branches, add shared validation. Smart contracts and a DAO may come later.
  7. Still centralized: head office may control membership, identity, or upgrade rules.

Answer. Before, 1/7 ≈ 0.143 (14.3%) of sites could write; after, 7/7 = 1.0 (100%) validate, with 7 copies. The first system is centralized but distributed; the route is replication plus shared validation, and membership or governance may remain central.

Exam traps

  • "Many machines means decentralized" is wrong. Distribution is not control; one owner can run 100 machines and still be centralized.
  • "Distributed and decentralized are synonyms" is wrong. A distributed database can have one administrator who controls all writes.
  • "Blockchain always gives full decentralization" is wrong. The validator set, identity system, and upgrade rules can stay central.
  • "Decentralization has no cost" is wrong. Coordination, speed, governance, and legal clarity all become harder.
  • "A DAO has no rules" is wrong. A DAO has rules in code and token voting; it has no central boss, not no governance.

1.4 Features, potential and myths of blockchain

Blockchain features are real but conditional. Tamper-evidence, transparency, auditability, availability, pseudonymity, programmability and disintermediation each solve a problem, and each brings a cost: collusion risk, lost privacy, lower throughput, fees, key loss or oracle trust. This chapter pairs every claimed benefit with its limit, maps the main application areas, and tests common myths. Use it to judge a claim the way an engineer judges a quote: what is promised, what is the price, and what would make the promise fail?

You need: Chapter 1.3 on decentralization and the ledger view in Chapter 1.2.

Features with a price

A feature is a property of the design, not a guarantee for every use. Read each line as a pair: what the blockchain gives, and what it asks in return.

  • Tamper-evidence: each block stores a short fingerprint (hash) of the previous block, so changing an old transaction changes all later hashes. Limit: if colluding validators control more than 50% of power, they can rewrite recent history. Evidence is not proof against a majority.
  • Transparency: every participant can read the ledger and verify rules. Limit: salaries, prices and customer names become visible; privacy needs encryption, private channels or zero-knowledge proofs.
  • Auditability: the append-only history lets an auditor replay every entry. Limit: a false entry is audited as faithfully as a true one; auditability does not clean the input.
  • Availability and throughput: many replicas keep the ledger online through node failures. Limit: every node repeats validation, so public chains often process few transactions per second and peak demand raises fees.
  • Pseudonymity: a user acts through keys and addresses, not a name. Limit: addresses are public and linkable; one KYC exchange or delivery address can expose the full history. See Unit 2, cryptography.
  • Programmability: smart contracts run business rules on-chain. Limit: a bug is public and may be irreversible, and code is not automatically law. See Unit 5, Ethereum and smart contracts.
  • Disintermediation: a shared ledger can replace a reconciling middleman. Limit: outside facts still enter through an oracle, and governance of the ledger remains a human problem.

Potential: a map, not a promise

Potential means where the feature fits, not where it is already proved. Use this map to place an application, then ask who writes, who validates and who pays. See Unit 6 for details.

  • Payments: cross-border remittance and merchant settlement can shorten reconciliation between banks. A Chennai exporter still needs regulated on-ramps and off-ramps; the ledger settles the record, not the rupees in a bank account.
  • Records: land titles, degrees and insurance claims can share one append-only register. The registrar must still verify the first entry; a blockchain cannot decide who owns a plot.
  • Supply chains: drug, coffee or auto-parts batches can carry a shared trail from factory to shop. Sensors and warehouse staff feed the trail, so bad data remains bad.
  • Identity: a person can hold verifiable credentials and disclose only what is needed. Key loss and recovery become the hard part; a lost private key is not a lost password.
  • Voting: a voting ledger can give a public audit trail and one-vote tokens. It must also protect ballot secrecy and resist coercion at home; a public chain alone does neither.

Myths and tests

A myth takes a conditional property and drops the condition. Test each claim with three questions: who can break it, what does the user reveal, and what does it cost?

  • Unhackable. Breaking SHA-256 is not the usual attack; capturing consensus is. A pool with 45% is below the line, but pools with 45% and 25% together hold 70%. A rewrite becomes possible when colluding hash power is above 50%; no chain is unhackable, only expensive to attack.
  • Anonymous. Public addresses are pseudonyms. Chain analysis groups addresses; an exchange record can attach a name.
  • Always cheaper or faster. Public chains charge per transaction and repeat work on many nodes. A ₹40 fee on a small payment is expensive; a permissioned chain may be faster but trusts fewer validators. Compare fees, energy, throughput and integration.
  • Trustless. No third party is not zero trust. Trust moves to miners or validators, wallet software, stablecoin issuers and oracles. The better word is trust-minimized.
  • On-chain data and code are always true or legal. The chain proves data was written and not changed, not that it matches reality. A forged invoice remains forged on-chain, and a court decides whether a contract is valid.

colluding share = s₁ + s₂ + ... + sₖ

s₁ to sₖ are the hash-power shares of the colluding pools; k is their count. A rewrite risk exists when the colluding share is greater than 50%.

Worked example

Question. A startup claims its public blockchain is unhackable, anonymous and free. It has five mining pools with hash shares 45%, 25%, 15%, 10% and 5%. All transaction addresses are public. The average fee is ₹40 per transaction. Test each claim and state which fail.

  1. Unhackable, single pool: the largest share is 45%. Since 45% < 50%, one pool alone cannot control consensus.
  2. Unhackable, collusion: sort the shares as 45%, 25%, 15%, 10%, 5%. The top two pools hold 45 + 25 = 70%. Since 70% > 50%, two pools can collude to exceed a majority; the absolute claim fails.
  3. Anonymous: all addresses are public, so every transfer is visible. If one address is linked to a name through KYC or delivery data, its history is exposed; the claim fails and the system is only pseudonymous.
  4. Free: the fee is ₹40 per transaction. For 100 transactions the cost is 100 × ₹40 = ₹4,000, so the claim fails.
  5. Result: all three claims fail as stated, even though the chain has real tamper-evidence and availability.

Answer. All three claims fail: the top two pools reach 70% collusion, addresses are public, and 100 transactions cost ₹4,000 at ₹40 each.

Exam traps

  • Tamper-evident is not tamper-proof; 51% collusion can rewrite recent history, not the entire chain.
  • Pseudonymous is not anonymous; public addresses are linkable and can be tied to names by exchanges.
  • Trustless is shorthand for trust-minimized; oracles, wallets and validators still carry trust.
  • On-chain data is verifiable as written, not true; a forged invoice stays forged, and a court decides legality.
  • Always cheaper or faster is not a feature; compare fees, energy, throughput and integration.

1.5 Types of blockchain: public, private and consortium

A blockchain can be public, private or consortium. The label comes from three permissions: who may read the ledger, who may write a transaction, and who may validate a block. This matters because a chain for Bitcoin payments and a chain for three banks share data differently. Public chains let anyone join; private chains are open only to one organisation; consortium chains share control among a known group. Banks, land registries, supply chains and enterprise pilots use these labels to state trust and access rules before choosing a platform.

You need: Chapter 1.4 on features and Chapter 1.3 on decentralization.

Read, write and validate

A blockchain type is mainly a permission rule, not a product name. Three questions decide it. Read permission: who may see the ledger and its history? Write permission: who may submit a transaction? Validate permission: who may check transactions and append a block? The set of nodes allowed to append is the validator set.

A public blockchain is open on all three. Anyone may read, submit a transaction and join the validator set. It is permissionless because no gatekeeper approves entry. Bitcoin is the standard example: anyone can run a node, and miners compete to append blocks.

A private blockchain is controlled by one organisation. Read access may be open or limited. Write and validate access are given only to approved nodes. It is permissioned: membership is by invitation or approval. A company with 12 offices may let all 12 validate, but the company still sets the rule.

A consortium blockchain, also called a federated blockchain, is shared by several organisations. No single member owns the rule alone. A known group, such as 3 banks, approves members and validates blocks. It is permissioned. Some systems mix public read with private write; treat that as a hybrid mix, not a fourth basic permission rule.

How the three types compare

Trust differs. A public chain trusts open rules and costly consensus. A private chain trusts the owning organisation. A consortium trusts shared membership rules. Speed and cost differ too: public proof-of-work chains are slow and energy-heavy; permissioned chains with known validators can confirm faster and cheaper, but only inside that group.

Privacy follows read permission. A public ledger exposes transactions to all readers. Permissioned chains may restrict readers to approved members, but a private chain can also allow public read while keeping write and validation closed; the type label alone does not fix read access. Governance also changes: public changes need broad node or miner agreement; private changes follow one organisation; consortium changes need the group's rule. Hyperledger Fabric is a permissioned platform used for private or consortium networks; its details belong to Unit 6.

Choosing a type without mistaking private for closed

Permissioned does not mean centralized by default. A private or consortium chain can run many nodes, copy the ledger and validate by rule. What is controlled is membership: an administrator or a group approves who joins. Centralisation would mean one node can rewrite history alone. A well-built permissioned chain still checks blocks against shared rules and signatures.

  1. List who must read the ledger. If unknown outsiders must read, check whether public read is acceptable.
  2. List who may write. Separate customers who only view records from staff who submit updates.
  3. List who validates. One organisation points to private; several organisations point to consortium; an open set points to public.
  4. Check governance: who adds or removes validators, and whose signature changes the rule?
  5. Check legal privacy needs. Personal records may need restricted read even if validation is shared.

Some syllabi use public, private and consortium as the three types. In practice, the deciding question is who validates. A chain with 13 validating offices under one registrar is private. A chain with 3 validating banks under a shared rule is consortium.

Worked example

Question. A land registry has 1 registrar and 12 sub-registrar offices. Citizens may read records but not write them. The registrar and all 12 offices can validate updates.   3. Count the trade-finance validators: 3 banks.

  • Assuming public is always better. Public gives open access but often costs more and runs slower; private gives control but trusts the admin more.
  • Saying permissioned means centralized. Many nodes can validate; only membership is controlled.
  • Confusing a consortium with a public chain that has many users. A consortium is a closed set of organisations with shared governance.
  • Treating read and write permission as one. Citizens may read a land ledger but not write to it.

1.6 Blockchain architecture and structure of a block

A blockchain stores history as blocks in a line. Each block has a header and a body. The header carries a pointer to the previous block, so blocks form an append-only chain. The body carries transactions. A block is created by a miner, checked by nodes, then added. This structure is used in Bitcoin, Ethereum and enterprise ledgers to make history easy to verify and hard to rewrite. This chapter shows the layers, the fields of a block, and why one edited transaction breaks later blocks.

You need: Chapter 2 on distributed ledgers and Chapter 5 on chain types.

The four architecture layers

Think of blockchain as four layers stacked. The application layer is what users touch: wallets, supply-chain forms, token dashboards. It creates transactions and reads confirmed state. The consensus layer decides which candidate block becomes next. It holds rules such as proof of work or voting, and the reward rules. The network layer moves transactions and blocks between peers. It uses peer-to-peer links, gossip and block propagation. The data layer is the ledger itself: blocks, headers, transactions, hash pointers and state. The data layer is the part this chapter opens. The layers are logical, not separate machines; one node runs all four. A wallet may run only the application layer and ask a node for data. Some syllabi call this overview and structure of a block.

Inside one block: header and body

A block is two parts. The header is metadata. The body is the transaction count and the transaction list. Header fields are:

  • version: the protocol rules the block follows.
  • previous block hash: the hash of the parent header, used as a pointer.
  • Merkle root: one hash that summarises every transaction in the body.
  • timestamp: the miner's claimed creation time, within protocol limits.
  • difficulty or target: the mining hardness, or the target value the header hash must beat.
  • nonce: a counter the miner changes to get a header hash below the target.

Hn = Hash(headern)

Hn is the hash of block n; headern contains the previous block hash Hn-1, the Merkle root, the timestamp, the target and the nonce; Hash is the chain's hash function, such as SHA-256 in Bitcoin.

The block hash is not Hash(transactions). It is Hash(header). The Merkle root is how the transactions enter the header. Unit 2 builds the Merkle tree. A candidate block is a block a miner has assembled but not yet accepted; it may still lack a valid nonce. The genesis block is block 0. It has no parent. Block height is the number of blocks before a block; the genesis block has height 0.

Hash pointers, height and tampering

Each block stores the hash of the block before it. That value is a hash pointer: it points to the parent and also checks the parent's contents. Block 20 has previous hash 0000a1. Block 21 is mined with the hash of Block 20 as its previous hash. If Tx 2 inside Block 20 is edited, the body changes. The Merkle root must change from 7c2e to a new value. The header of Block 20 changes, so its hash changes. Block 21 still stores the old hash of Block 20, so its previous-hash field is now wrong. Block 21's header hash changes too, and every later block is affected.

For the chain to accept the edit, a miner must re-mine Block 20: find a new nonce so Hash(header) meets the target. Then re-mine Block 21 and all later blocks with the new previous hashes. Honest nodes reject the edited chain unless it wins under the consensus rule. In proof of work that usually means more total work than the honest chain. Appending a new block is cheap; rewriting old history is expensive. See Unit 3 for forks and consensus.

Worked example

Question. Block 20 has previous hash 0000a1, Merkle root 7c2e, nonce 18, and 3 transactions. Block 21 is mined with the hash of Block 20 as its previous hash. Tx 2 in Block 20 is edited. Which fields of Block 20 and Block 21 change, and what must happen for the chain to accept the edit?

  1. Block 20 header: previous hash 0000a1, Merkle root 7c2e, nonce 18, timestamp and version. Body: Tx 1, Tx 2, Tx 3.
  2. Edit Tx 2. The body of Block 20 changes. The transaction count stays 3. The Merkle root must change from 7c2e to a new value, for example 7d5f.
  3. Hash of Block 20 = Hash(header). The header now has the new Merkle root, so the old hash of Block 20 is invalid. A new nonce must be found by mining.
  4. Block 21 stores the old hash of Block 20 as its previous hash. That field must change to the new hash of Block 20. Block 21's header then changes, so Block 21 must be re-mined with a new nonce.
  5. Every later block stores the old hash of its parent, so all later blocks must be re-mined too. The edited chain is accepted only if it wins under the consensus rule, for example by having more total work in proof of work.

Answer. Block 20 changes in Tx 2, Merkle root, nonce after re-mining, and block hash. Block 21 and all later blocks change in previous hash, nonce after re-mining, and block hash. The chain accepts the edit only if the edited chain is re-mined from Block 20 onward and wins under the consensus rule.

Exam traps

  • Saying the block hash is the hash of the transactions only. It is Hash(header), and the Merkle root carries the transactions into the header.
  • Calling block height the number of transactions. Height is the count of blocks before this block; the genesis block has height 0.
  • Thinking the previous block hash is stored in the body. It is a header field.
  • Mixing the Merkle root with the block hash. The root summarises transactions; the block hash covers the whole header.
  • Assuming an edited old block can be accepted after changing only one field. Every later block stores the old hash, so later headers must be rebuilt.

1.7 Blockchain networks and nodes

A blockchain network is a peer-to-peer overlay: nodes run the same protocol and connect directly to chosen peers, not through one central server. Each node stores and validates according to its role, and together they relay transactions and blocks. This design exists so no single owner can silently rewrite the ledger. You meet it in public chains such as Bitcoin, in consortium ledgers, and in test networks used before deployment. This chapter separates the roles—full, pruned, mining, light, wallet and seed—and shows how one transaction travels through a small network.

You need: Chapter 1.6 on blocks and Chapter 1.2 on distributed systems.

The network as a peer-to-peer overlay

A blockchain network is not a new cable or router. It is an overlay: a logical graph of nodes that use the Internet to open direct connections to other nodes. Two nodes are peers when they speak the same protocol messages and can exchange transactions and blocks. The physical path may cross many Internet service providers; the overlay hides that path.

Each node keeps a list of peers. It may accept inbound connections, make outbound connections, or both. In a public chain, anyone with the software and enough disk and bandwidth can join. In a private or consortium chain, an administrator controls admission; the peer-to-peer links still move data, but membership is restricted (see Chapter 1.5).

The network is defined by shared rules: message formats, block validity, and the genesis block. A node that follows different rules is on a different network, even if it uses the same software; test networks therefore use a separate genesis block and chain identifier. A simple model is a graph. Vertices are nodes; edges are live peer connections. A node does not need a link to every other node. It needs enough links for messages to reach the rest of the graph by relaying.

Node roles: storage and validation

A node is one running program with an identity (often a public key or network address) and a local copy of whatever data its role requires. The role decides three things: what it stores, what it checks, and what it serves to others.

A light node trusts full nodes for data availability but checks that headers form the most-work chain and that a transaction is inside a block through a Merkle branch (see Unit 2). A wallet is not automatically a node; many phone wallets are light clients or use a remote full node.

Propagation, mempool and network shape

Transaction propagation uses gossip. A wallet signs a transaction and sends it to one full node it trusts or operates. That node checks the signature, the format, and obvious double-spend rules against its current state. If the transaction is valid and pays enough fee, the node puts it in its mempool and sends it to its peers. Each peer repeats the check and the forward. Gossip is robust but not instant; duplicates are dropped by transaction ID.

A mempool is a local pool of unconfirmed transactions. There is no single global mempool. Two nodes may hold different sets because of timing, fee policy and connection patterns. Miners choose from their own mempool when building a candidate block. (The full transaction life cycle is in Unit 3.)

Block propagation follows the same shape. A miner sends a new block to its peers. Each full node validates the header, the proof of work or validator signature, and every transaction, then forwards the block. Light nodes receive headers and ask for proofs when needed. Propagation delay matters: a block that spreads slowly gives competing miners more time to find a rival block at the same height.

Network size and topology affect decentralization, but count alone is not enough. A thousand nodes run by one cloud account are not a thousand independent validators. Decentralization needs independent operators, diverse software and geography, and enough full nodes to serve data. More connections speed gossip but add bandwidth cost.

A test network is a separate blockchain with its own genesis block and worthless coins. Developers use it to test code and upgrades before mainnet. Testnet tokens have no money value; they exist to pay test fees.

Apply Five partner banks want one shared record of inter-bank settlements, with each bank validating updates but customer data hidden from outsiders. Recommend a chain type and justify the choice. 13 marks

Identify permissioned consortium chain; Read access restricted, write allowed to member banks, validator set fixed by governance; Why not public: privacy, throughput, regulatory accountability; Why not private: no single bank should control the ledger; Governance rules for adding or removing members.

Apply A block contains four transactions with hashes T1 to T4. Describe step by step how the Merkle root is built and why it is useful. 10 marks

Hash each transaction to get leaf nodes; Pair T1,T2 and hash; pair T3,T4 and hash; Hash the two results to get the root; If the count is odd, the last hash is paired with itself; Use: one field in the header commits to all transactions; Use: Merkle proofs let a light client check one transaction.

Apply Trace the life cycle of a transaction from a wallet to final inclusion in a block, naming the node roles involved. 13 marks

Wallet signs the transaction with the private key; Transaction broadcast to peer nodes; Nodes check signature, balance and format, then relay; Nodes hold it in a mempool; A block proposer picks transactions into a candidate block; Consensus accepts the block; other nodes validate and append it; Confirmations increase as later blocks are added.

Apply A state government wants land records on a blockchain. Describe how decentralization would be applied and which parts should stay centralized. 13 marks

Define decentralization: control spread across participants; Route 1: distribute the ledger across revenue offices and banks; Route 2: allow citizens to verify their own record with a proof; Keep identity verification and legal title centralized by law; Consensus rules and validator set defined by statute; Discuss disputes: chain records the entry, courts decide ownership.

Analyze and evaluate

Evaluate 'Blockchain removes the need for trust.' Examine this claim using the ideas of decentralization and blockchain myths. 14 marks

Blockchain replaces trust in one party with trust in rules, code and incentives; Trust shifts to: correct code, majority of validators, key custody; Myths: immutability is absolute, on-chain data is true, anonymity is guaranteed; Counter-examples: oracle data, exchange hacks, governance forks; Conclusion: trust is redistributed, not removed.

Analyze Explain double spending and the 51% attack, and evaluate why waiting for confirmations matters. 14 marks

Double spend: same coins sent to two receivers; Nodes order transactions; only the first valid one in the accepted chain counts; 51% attacker: majority of hashing power can reorder or reverse recent blocks; Depth of a block: rewriting k blocks requires redoing their work; Practical rule: more confirmations for larger value; Trade-off: waiting time versus security.

Evaluate For a supply-chain traceability project, compare a distributed database with a permissioned blockchain and recommend one. 14 marks

Criteria: who owns data, how many parties, trust level, throughput, privacy; Distributed database: fast, admin controlled, needs a trusted operator; Permissioned blockchain: shared validation, tamper-evident audit trail, slower; Volume and latency of supply-chain events; Recommendation with conditions, e.g. blockchain only if parties do not trust one operator.

Evaluate Evaluate the scaling and governance trade-offs between public and consortium blockchains as transaction volume grows. 14 marks

Public chain limits: block size, block interval, global propagation; Scaling responses: larger blocks, layer-2 channels, sharding; Consortium: fewer validators, faster finality, but weaker censorship resistance; Governance: open improvement proposals versus a signed member agreement; Trade-offs: throughput versus openness, privacy versus verifiability.

Analyze Explain how nodes in a peer-to-peer blockchain network reach agreement when some nodes are faulty, and relate this to the Byzantine Generals Problem. 13 marks

Peer-to-peer topology: no central server, gossip relay; Fault tolerance: honest majority assumption; Byzantine fault: node may lie, not just crash; Consensus rules and block choice under competing proposals; Why permissioned chains handle faults differently from public chains.

Glossary

Block
A container of transactions plus a header, added to the chain after consensus.
Block body
The list of transactions carried inside a block.
Block header
The summary fields of a block: previous hash, Merkle root, timestamp, target and nonce.
Block height
The position of a block counted from the genesis block, which is height 0.
Blockchain
A chain of blocks, each holding transactions and the hash of the block before it, copied across many nodes.
Byzantine fault
A failure where a node sends wrong or contradictory information instead of simply stopping.
Candidate block
A block a node has assembled but not yet accepted by the network.
Consensus
The process by which nodes agree on the next valid block and on the order of transactions.
Consortium
A group of organisations that jointly govern a shared permissioned ledger.
Decentralization
Distribution of control among many participants rather than one authority.
Distributed database
A database spread across machines but controlled by an administrator.
Distributed ledger
A ledger replicated across many nodes and updated under shared validation rules.
Double spending
Sending the same digital asset to two recipients; blocked by ordering and validation.
Fork
A split in the chain when two blocks at the same height are both accepted temporarily, or a permanent rule change.
Full node
A node that downloads and validates every block and keeps the complete ledger.
Genesis block
The first block of a chain, with no predecessor and height 0.
Hash pointer
A cryptographic hash of the previous block stored in the current block, which makes tampering detectable.
Merkle root
The single hash that commits to every transaction in a block.
Merkle tree
A binary tree of hashes over transactions, whose top hash is the Merkle root.
Node
A computer running blockchain software that stores, checks and relays blocks and transactions.
Peer-to-peer network
A network of machines that connect directly and exchange data without a server in the middle.
Permissioned
Restricted so that only approved participants may read, write or validate.
Permissionless
Open to anyone to join, read and validate without prior approval.
Smart contract
Program code stored on the chain that executes automatically when its conditions are satisfied.
