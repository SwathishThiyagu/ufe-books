3.1 Peer-to-peer networking: architecture and network discovery

A blockchain has no server in the middle. Every computer running the software is a peer, equal to the others, and peers find each other on their own. Together they form an overlay network: a logical mesh of TCP connections laid over the ordinary internet. This chapter covers the three architectures, the join-and-discover procedure, the gossip that spreads each new transaction, and the security measures that keep an open network usable. Bitcoin and Ethereum run on exactly this design.

You need: nodes and network structure from Unit 1 (Blockchain networks and nodes), and hash pointers from Unit 2 (Linking blocks with hash pointers).

Nodes, peers and three architectures

A node is any computer running the blockchain software. A peer is that node seen from the outside, as an equal partner rather than a servant. The pattern of connections among peers is the overlay network: a logical graph drawn on top of the physical internet. We draw the graph; the wires underneath are TCP connections.

Client-server. One central server holds the data and clients ask it. Cheap and fast, but the server is a single point of failure and a single point of control. A bank's account database behind UPI is close to this shape.

Pure peer-to-peer. Every node is both client and server. No node is privileged, and any node may leave without stopping the network. Gnutella in 2000 was the first large pure design.

Hybrid. A few nodes take extra jobs: supernodes relay more traffic, bootstrap servers only hand out addresses. Bitcoin is pure at run time but hybrid at start-up, because a brand-new node needs one first address from somewhere.

Short history. Napster (1999) kept a central index and moved only the files peer-to-peer. Gnutella removed the index and flooded queries. BitTorrent (2001) cut files into pieces and used a central tracker to find holders; later versions replaced the tracker with a DHT. Bitcoin (2009) was the first P2P network carrying money, so its peers must also agree on one order of transactions — see Consensus mechanisms and their types.

Joining the network and spreading data

  1. Read the seed list: a few IP addresses hardcoded in the source code, plus DNS seed hostnames. Resolving a DNS seed returns a batch of live peer addresses.
  2. Open a TCP connection to one or two of those addresses.
  3. Handshake: each side sends a version message (protocol version, services, timestamp, own address, best chain height); each replies verack. Both sides now know whom they are talking to.
  4. Ask for more addresses with getaddr. Peers reply with addr messages, each carrying several (IP, port, services, timestamp) entries. The node saves them in an address book and drops stale ones.
  5. Dial the new addresses, grow to a target number of connections, and repeat as peers come and go.
  6. Gossip: a new transaction is passed to every connected peer, and each of them passes it onward. Duplicate detection stops it being passed on again; designs that flood, such as Gnutella, also add a hop limit.

Structured lookup. In a distributed hash table (DHT), every node and every key hash into the same identifier space. Each node keeps a small set of contacts at every distance from itself — a few near neighbours and a few far ones. A lookup for key k jumps to a contact closer to k each hop, halving the remaining distance, so it needs about log₂ n hops for n nodes. Ethereum's discovery protocol uses a Kademlia-style DHT; Bitcoin uses the address-book gossip described above.

Unstructured, structured and hybrid overlays, and keeping the network safe

Unstructured overlay: no rule maps data to a particular node, so a message is flooded to neighbours with a hop limit called TTL (time-to-live), counted in hops. Gnutella works this way. The hop limit plus duplicate detection bound the work; the cost is that many peers receive the same message.

Bitcoin relays by announce-and-request. A node sends a small inventory hash (inv message) to its peers. A peer that does not already have the transaction replies with getdata, and the full transaction is then sent. Each node keeps a record of what it has already seen and stays silent about it afterwards. So peers exchange many small announcements rather than pushing the full transaction to everyone.

Structured overlay uses a DHT key, so a lookup goes almost straight to the right node. It is efficient and is used mainly for finding peers. Hybrid overlay, in this section's sense, uses a structured DHT for lookups and unstructured flooding for broadcast. Note that this is a different sense of 'hybrid' from Section 1, where it meant a few nodes carrying extra jobs.

  • Encrypted, authenticated transport: Ethereum's connection layer encrypts and authenticates every link, and Bitcoin offers an encrypted transport option, so a relay cannot read or quietly rewrite traffic.
  • Signatures: transactions and blocks are signed, so a relaying peer cannot alter them; the receiver validates before forwarding.
  • Peer scoring and banning: invalid data, a bad proof of work or a flood of messages earns a bad score, then a disconnect and a ban.
  • Connection diversity against an eclipse attack: many outgoing connections, address buckets split by IP range, and saved anchor peers, so one attacker cannot surround a node with its own peers.
  • Limits: maximum message size, hop count and message rate per peer, so one peer cannot exhaust memory or bandwidth.

Bitcoin and Ethereum are the standard examples. One line worth remembering: P2P crypto exchanges and P2P marketplaces are trading venues, not network topologies. A P2P exchange matches two users directly; an OTC exchange has a dealer quote a price; neither changes how nodes connect.

Worked example

Question. A blockchain network floods each new transaction with fan-out 3 (each peer forwards to 3 neighbours that have not yet seen it) and time-to-live 3 hops. Count the copies sent in each round, the total copies sent by all peers, and the total counting the originator's own copy.

  1. Round 0, hop 1: the originator sends 3 copies. Copies sent so far = 3.
  2. Round 1, hop 2: each of the 3 receivers forwards to 3 peers, so 3 × 3 = 9 copies. Running total = 3 + 9 = 12.
  3. Round 2, hop 3: each of the 9 receivers forwards to 3 peers, so 9 × 3 = 27 copies. Running total = 12 + 27 = 39.
  4. TTL is now 0, so the 27 receivers stop forwarding. Copies in the last round = 27.
  5. The originator's own copy is never sent to anyone, so copies that exist = 39 + 1 = 40.
  6. Duplicate detection applies: a peer that already holds the transaction does not forward it again, so the real count stays near 39 and does not explode.

Answer. All nodes together send 39 copies (the originator's 3 plus 9 plus 27), 27 of them in the last round; counting the original copy the originator still holds, 40 copies exist.

Exam traps

  • Calling a P2P crypto exchange or a P2P marketplace a P2P network. Those are trading venues; the topology is unchanged.
  • Assuming a connected peer is a trusted peer. Any node may connect and may lie; every message is validated locally.
  • Calling Bitcoin fully pure P2P without noting its hardcoded seeds and DNS seeds at start-up — it is hybrid only during bootstrap.
  • Confusing a bootstrap node (hands out addresses, then steps aside) with a supernode (relays data for others).
  • Forgetting that flooding needs both a TTL and duplicate detection, and then claiming every node receives every message without limit.

3.2 Transaction life cycle and the role of miners

A transaction is a signed instruction to move coins. It starts in a wallet, spreads by gossip to many nodes, waits in a pool of unconfirmed transactions, and enters a block only when a miner picks it. The miner is paid to choose and to order, and the network accepts the block only after every other node rechecks it. This life cycle explains why a crypto payment is quick to send but slow to become final, and why the fee you offer decides how long you wait. Exchange deposit credits and refund waits both follow this flow.

You need: what a block holds (Unit 1), hashing and digital signatures (Unit 2), and how nodes find each other and gossip, from 3.1.

A transaction is built, signed, then gossiped

A wallet does not hold coins. It holds keys and points to coins on the chain called unspent transaction outputs, or UTXOs. A UTXO is an amount locked to an address that no transaction has spent yet. To pay someone, the wallet builds a transaction with three parts: inputs (the UTXOs being spent), outputs (amount plus receiver address), and a fee. The inputs must add up to at least the outputs plus the fee.

The wallet then signs. It hashes the transaction data and signs that hash with the sender's private key. Any node can verify the signature with the sender's public key. The signature covers the amounts and the recipient, so changing even one satoshi breaks it.

  1. Check the signature against the public keys of the inputs.
  2. Check the spending conditions on each input are satisfied.
  3. Check each input exists on the chain and is still unspent.
  4. Check inputs ≥ outputs, so the fee is not negative.
  5. Check the same input is not already waiting in the mempool (double spend).

A transaction that passes all checks goes into the node's mempool, the pool of valid but unconfirmed transactions, and is passed to other peers. A transaction that fails is dropped; nobody sends a rejection message. Mempools are local, so two nodes may hold different sets at the same moment. That is normal and not a disagreement about history.

The fee is size times rate

fee = size (bytes) × fee rate (satoshi per byte)

fee is the total satoshi given to the miner; size is the transaction's size in bytes; fee rate is the price the sender offers for one byte of block space. 1 bitcoin = 100,000,000 satoshi.

A block has a size limit, so the scarce thing miners sell is space, not transactions. That is why the price is quoted per byte. A transaction with twice the size at the same rate pays twice the fee.

  • Miners rank by fee rate, not by total fee. A small transaction at 30 sat/byte beats a large one at 10 sat/byte.
  • When the mempool is crowded, senders bid the rate up; when it is empty, even the minimum rate gets in.
  • Fee is not deducted as a separate output. It is the gap between inputs and outputs, and the miner claims it.

From candidate block to confirmation

  1. Place the coinbase transaction first. It creates the block reward plus the fees of all included transactions.
  2. Fill the rest of the block from the mempool, highest fee rate first, until the size limit is reached.
  3. Write the previous block hash, the Merkle root of the transactions, a timestamp, the target and a nonce.
  4. Change the nonce until the block hash falls below the target. This is the Proof of Work of 3.4.
  5. Broadcast the finished block to peers.

Every other node now validates the whole block, not just the puzzle: correct proof of work, every transaction valid, no double spend inside the block or against the chain, correct coinbase amount. A valid block is added to the chain tip. An invalid one is rejected and the miner's whole reward is lost, which is why serious miners also run a full node.

Confirmations are counted in blocks. The block that holds your transaction gives one confirmation; each block mined on top adds one more. Six is a common convention for large amounts, not a rule of the protocol.

The coinbase output has maturity: in Bitcoin it can be spent only after 100 more blocks. Two miners may also find blocks at the same height. Nodes follow one, and the other becomes a stale or orphan block: its coinbase is worthless and its transactions go back to the mempool.

Miners order, full nodes check

  • Ordering: the miner decides which transactions go in and in what sequence.
  • Extension: the miner adds the next block and so lengthens the heaviest chain.
  • Issuance: the coinbase transaction creates new coins at a fixed schedule.
  • Collection: the miner takes the fee gap of every transaction it includes.

A full node that does not mine validates every transaction and block and keeps the rules. A miner that does not validate is blind: it can be handed an invalid chain and waste its hash power building on top of it. Miners supply ordering; full nodes supply the checking that makes the ordering trustworthy.

One flaw belongs here. A third party can alter a signature without invalidating the transaction, which changes its transaction id. This is transaction malleability, and SegWit fixes it (see Unit 4).

Worked example

Question. A mempool holds three transactions. T1 is 250 bytes with a fee of 5000 satoshi. T2 is 500 bytes with a fee of 15000 satoshi. T3 is 1000 bytes with a fee of 10000 satoshi. (a) Find the fee rate of each. (b) Give the order a profit-maximising miner puts them in a block. (c) Find the total size, total fee and average fee rate of that block.

  1. Fee rate = fee ÷ size, in satoshi per byte.
  2. T1: 5000 ÷ 250 = 20 sat/byte.
  3. T2: 15000 ÷ 500 = 30 sat/byte.
  4. T3: 10000 ÷ 1000 = 10 sat/byte.
  5. Rank by fee rate: T2 (30) first, then T1 (20), then T3 (10). Ordering by total fee instead would put T3 second and waste block space on 10 sat/byte.
  6. Total size = 250 + 500 + 1000 = 1750 bytes.
  7. Total fee = 5000 + 15000 + 10000 = 30000 satoshi.
  8. Block fee rate = 30000 ÷ 1750 ≈ 17.14 sat/byte.

Answer. Fee rates are 20, 30 and 10 sat/byte; the order is T2, T1, T3; the block is 1750 bytes carrying 30000 satoshi, about 17.14 sat/byte.

Exam traps

  • Treating the fee as a fixed amount. It is size × rate, so the same rate on a bigger transaction costs more.
  • Ranking by total fee instead of fee rate. The 15000 satoshi fee looks bigger, but per byte the small transaction may pay more.
  • Calling a transaction final after one block. Confirmations are blocks on top, and six is a convention, not a protocol rule.
  • Expecting a stale block to pay its miner. Its coinbase is invalid and its transactions return to the mempool.
  • Spending mining income at once. The coinbase output matures only after 100 further blocks in Bitcoin.

3.3 Consensus mechanisms and their types

A blockchain has no manager. Many equal computers must still agree on one order of blocks, even when some are slow, disconnected or dishonest. The rules that produce that agreement are the consensus mechanism. Consensus stops the same coin being spent twice, because every honest node decides which transaction came first. This chapter defines consensus, lists the properties it must have, counts how many faulty nodes a network can survive, and sorts the named mechanisms into families: proof-based, voting-based, round robin and hybrids.

You need Unit 1 for public, private and consortium chains, and 3.1 for how equal nodes reach each other without a server.

What consensus has to deliver

A consensus mechanism (some syllabi say consensus algorithm or consensus protocol) is the set of rules by which independent nodes agree on one ordered history of blocks. Each node keeps its own copy of the chain, and the mechanism makes every honest copy identical, link by link.

Three properties are checked in every correctness proof.

  • Agreement: no two honest nodes decide different blocks at the same height.
  • Validity: the decided block was really proposed and its transactions are valid; the protocol cannot invent a block.
  • Termination: every honest node eventually decides. Blockchain versions often weaken this to 'eventually, with very high probability'.

Two kinds of failure make this hard. A crash fault is a node that simply stops; silence is easy to catch with a timeout. A Byzantine fault is a node that keeps talking but lies, showing different blocks to different peers. A Byzantine node may also stay silent, so Byzantine fault tolerance covers crash faults but not the reverse.

Two obstacles sit on top: network delay, so messages arrive late and out of order, and message loss. The same problem appears outside blockchains, where Raft and Paxos order writes in a database cluster.

How many faulty nodes a network can survive

Let n be the number of nodes and f the number of faulty nodes the network must tolerate. Two bounds are standard.

crash faults: n ≥ 2f + 1;  Byzantine faults: n ≥ 3f + 1;  quorum = 2f + 1

n is the total number of nodes; f is the number of faulty nodes to be tolerated; quorum is the number of matching votes needed to decide a block in a Byzantine fault tolerant protocol. The first bound assumes nodes only stop; the second assumes some nodes may lie.

Why n ≥ 2f + 1 for crashes: with a majority quorum of f + 1 votes, any two quorums share at least one node, and a node that missed a round learns the latest decision from that shared node. With n = 5 and f = 2, the quorum is 3.

Why n ≥ 3f + 1 for Byzantine faults: the f liars can vote with either side of a split. With a quorum of 2f + 1, any two quorums overlap in at least f + 1 nodes. At most f of those are liars, so at least one honest node sees both sides and refuses to back two conflicting blocks.

The families of consensus

Proof-based mechanisms give the right to propose a block to whoever shows a scarce resource. Proof of Work uses hashing power, Proof of Stake uses locked coins, Proof of Elapsed Time uses a random wait enforced inside a trusted chip, and Proof of Authority uses the reputation of a short approved validator list.

Voting-based mechanisms ask known members to vote. PBFT needs a 2f + 1 quorum and tolerates liars. Raft and Paxos tolerate only crashes. Tendermint is Byzantine fault tolerant and decides once and for all. The Stellar consensus protocol uses quorum slices: each node names a small set of peers it trusts, and the slices must overlap.

Round robin gives each node a fixed turn: the leader rotates slot by slot, so ordering is cheap, but a silent leader stalls the round until a timeout. Many real systems are hybrids, mixing a proof to pick the proposer with a vote to confirm.

Permissionless networks cannot vote, because one person can create thousands of identities at no cost, a Sybil attack, and free identities would make voting free to capture. A scarce resource makes each identity costly, which is what Sybil resistance means. Permissioned networks already know their members (Unit 1), so voting there is safe, fast and cheap.

Finality differs by family. In probabilistic finality a block can still be replaced, and confidence grows as blocks pile on top. In deterministic finality the block is decided once and cannot be reverted without breaking the protocol rules.

The 51% attack

A Proof of Work chain is safe only while no single party controls most of the hashing power. An attacker with more than half the total hash rate can mine a private chain faster than the honest network on average, publish it later, and replace recent blocks. That enables double spending: pay a merchant, let the payment confirm, then release a longer chain in which the payment never happened. It does not let the attacker steal coins, because spending needs private keys, and it cannot cheaply rewrite very old blocks. The defence is economic: honest miners have more to lose.

Worked example

Question. A consortium blockchain runs a Byzantine fault tolerant voting consensus among n = 7 validators. (a) What is the largest number of faulty nodes f it can tolerate? (b) How many votes form the quorum? (c) To tolerate f = 3, what is the minimum n? (d) On a public Proof of Work chain with total hash rate 100 GH/s, an attacker controls 40 GH/s. What share does it hold, and can it outrun the honest chain?

  1. Byzantine bound: n ≥ 3f + 1.
  2. With n = 7: 7 ≥ 3f + 1, so 3f ≤ 6 and f ≤ 2. Largest tolerated f = 2.
  3. Quorum = 2f + 1 = 2 × 2 + 1 = 5 votes out of 7.
  4. For f = 3: n ≥ 3 × 3 + 1 = 10 nodes.
  5. Attacker share = 40 ÷ 100 × 100 = 40%.
  6. 40% < 50%, so it cannot outrun the honest chain for long.

Answer. f = 2, quorum 5 of 7 votes, minimum n = 10 for f = 3, and the attacker holds 40%, below half (50%), so it cannot outrun the honest chain.

Exam traps

  • Consensus is not the same as mining. Mining is only how Proof of Work reaches consensus; voting-based chains do not mine at all.
  • Proof of Stake still needs Sybil resistance: the locked stake is the cost that makes fake identities expensive.
  • Using n ≥ 2f + 1 for Byzantine faults, or a quorum of f + 1. Liars need n ≥ 3f + 1 and a quorum of 2f + 1.
  • Treating a Proof of Work block as final. It has probabilistic finality only; it becomes very costly, not impossible, to reverse.
  • Permissioned chains vote because membership is known, not because the members trust each other.

3.4 Proof of Work and mining

Proof of Work is the rule that makes a block expensive to produce. A miner searches for a nonce so that SHA-256 applied twice to the 80-byte header, read as a 256-bit number, falls below a target. Bitcoin double-hashes; some other chains hash once. Finding a winning hash takes many tries, checking it takes one. The target is retuned so blocks arrive steadily. Building blocks and hunting the winning hash is called mining.

You need: Unit 2 for SHA-256 and the block header, and 3.3 for where proof of work sits among the consensus types.

The puzzle in the block header

A miner fills a candidate block: transactions from the mempool, and a coinbase line that pays the miner's own address the block reward plus fees (see 3.2). Then it hashes only the block header, 80 bytes long, with six fields: version, previous block hash, Merkle root of the transactions, timestamp, target bits, and nonce.

The target bits field encodes the target T, a 256-bit number. Bitcoin accepts the block only if SHA-256(SHA-256(header)), read as an integer, is less than T. Single SHA-256 is used by some other chains, not by Bitcoin. A small T leaves very few winning outputs out of the 2²⁵⁶ possible hashes, so the puzzle is costly to solve and cheap to check.

p = T ÷ 2²⁵⁶ ≈ 16⁻ᶻ   and   expected tries = 1 ÷ p = 16ᶻ

p is the probability that one hash attempt wins; z is the number of leading zero hexadecimal digits the target demands; 16ᶻ is sixteen raised to the power z.

  1. Assemble the candidate block and its coinbase transaction.
  2. Compute the Merkle root of the transactions and write the header.
  3. Set nonce = 0.
  4. Hash the header with SHA-256 twice (SHA-256d) and compare the result, as an integer, with T.
  5. If the hash is below T, broadcast the block and collect the reward.
  6. Otherwise add 1 to the nonce and hash again.
  7. If the 32-bit nonce wraps around, change the timestamp or an extra nonce inside the coinbase and keep going.

Difficulty and the 2016-block adjustment

Difficulty D is a rescaled way of stating the target: D = T₁ ÷ T, where T₁ is the target of difficulty 1, the fixed value 0x00000000FFFF0000 followed by zeros, and T is the target in use. A higher difficulty means a smaller target and more expected hashes per block. Difficulty is not a hash rate; it says how hard the puzzle is, not how fast anyone runs.

Bitcoin aims at one block per 10 minutes. Every 2016 blocks (about two weeks) each node recomputes the difficulty from the time the window actually took.

D_new = D_old × (2016 × 10 min) ÷ actual time for the window

D_old and D_new are the difficulty before and after the retune; 2016 × 10 min = 20160 min = 14 days is the target duration; actual time is measured from the timestamps of the first and last block of the window.

If the window finished in 12 days, blocks came too fast, so difficulty rises by 14 ÷ 12. If it took 16 days, difficulty falls by 14 ÷ 16. Bitcoin limits one adjustment to a factor of 4 up or down, so a timestamp error cannot jump the difficulty wildly.

Hardware races and mining pools

  • CPU: the first miners used ordinary processors, a few million hashes per second.
  • GPU: graphics cards run thousands of simple lanes in parallel, giving a large jump.
  • FPGA: field-programmable chips wire the hash function directly and waste less power.
  • ASIC: application-specific chips do only SHA-256, nothing else, and dominate today.

As ASICs pushed the network hash rate up, a single machine almost never finds a block alone. Miners join a pool. The pool manager builds the candidate block, hands each member a different template, and counts shares: any hash that falls below the pool's easy share target. A share measures effort. If a share also falls below the network target, it is the block solution as well as a share, and the pool submits it and splits the reward.

Payment schemes differ. Pay-per-share pays a fixed amount for every valid share, so the miner has steady income and the pool carries the luck. Proportional schemes pay only when the pool finds a block, in proportion to shares. Pool hopping was an early exploit: miners joined a pool near the end of a round, when expected payout per share was high, and left at the reset. Score-based or pay-per-share accounting now blunts it.

Attacks, security and energy cost

The security claim is that rewriting history costs as much as writing it. An attacker with more than half the hash rate can mine a private chain faster than the honest network and publish it later, replacing recent blocks. That allows double spending: pay in a transaction on the public chain, then release a longer private chain without it. The same power can censor transactions. It cannot forge signatures, so it cannot spend coins that belong to someone else.

Selfish mining is a subtler strategy: a pool withholds blocks and releases them at chosen moments to waste rivals' work. Only the name is needed here.

The cost is real electricity. Energy use is roughly hash rate × joules per hash; ASICs lowered joules per hash, but the total climbed as hash rate grew. Mining also produces electronic waste when rigs are replaced. Chains that dislike this cost move to 3.5 or to fair-turn rules such as 3.6.

Worked example

Question. A target requires the first four hex digits of the 256-bit block hash to be zero. (a) Find the probability that one hash attempt succeeds and the expected number of tries. (b) A miner runs at 2 × 10¹¹ hashes per second; how long would it take on average if it owned the whole network's hash rate? (c) A difficulty window of 2016 blocks finishes in 12 days instead of the target 14 days. Find the new difficulty and the percentage change.

  1. One hex digit has 16 possible values, so the chance that a given digit is zero is 1/16. For z = 4 independent digits: p = (1/16)⁴ = 1/16⁴ = 1/65536 ≈ 1.526 × 10⁻⁵.
  2. Expected tries = 1 ÷ p = 65536 ≈ 6.55 × 10⁴ hashes.
  3. Time = tries ÷ hash rate = 65536 ÷ (2 × 10¹¹ hashes per second) = 3.2768 × 10⁻⁷ s.
  4. Target window duration = 2016 blocks × 10 min per block = 20160 min = 14 days. Actual duration = 12 days = 17280 min.
  5. New difficulty = old difficulty × (20160 ÷ 17280) = old difficulty × 1.1667.
  6. Percentage change = (1.1667 − 1) × 100% = 16.67%, a rise.

Answer. Expected tries = 65536 hashes at p ≈ 1.526 × 10⁻⁵, the run takes 3.2768 × 10⁻⁷ s at 2 × 10¹¹ hashes per second, and the difficulty rises by a factor of 1.1667, that is by about 16.67%.

Exam traps

  • Thinking more leading zeros make mining easier. More zeros means a smaller target, so fewer hashes win and mining is harder.
  • Confusing difficulty with hash rate. Difficulty fixes the puzzle; hash rate is how fast a machine tries. Rising hash rate forces difficulty upward at the next retune.
  • Comparing the hash as a string of zeros instead of as a 256-bit integer below a target. Two hashes with the same leading zeros can fall on opposite sides of T.
  • Using 2016 × 10 seconds instead of 2016 × 10 minutes for the window. The target window is 14 days, not about 5.6 hours.
  • Claiming a 51% attacker can steal coins. It can reorder and censor, and double spend its own coins, but it cannot forge signatures or spend other people's coins.

3.5 Proof of Stake

Proof of Stake is a consensus rule where validators lock the chain's own coin and are chosen to propose blocks in proportion to that locked amount. It exists because Proof of Work spends electricity to make block production costly. In PoS the cost is capital at risk: a validator's deposit can be destroyed if it cheats. Ethereum switched from PoW to PoS in 2022, and many newer chains use PoS or its delegated form.

You need: 3.3 for proof-based consensus and Sybil resistance, and Unit 2 for digital signatures.

Stake replaces watts

The scarce resource in Proof of Stake is the native coin, not electricity. A node that wants to validate sends a special transaction that locks a deposit called its stake. The locked coins stay in the protocol and cannot be spent while the validator is active. The set of validators and their stakes is public, so every node can compute the same selection odds.

P(i) = s_i ÷ S

P(i) is the chance validator i proposes the next block; s_i is its stake in coins; S = Σ s_j is the total staked coins over all active validators.

Selection can be stake-weighted, coin-age-based, or nearly random with equal chance. Stake-weighted selection is common: pick a random point in the total stake and see whose interval it falls in. Coin-age selection multiplies stake by time unspent to reward long holders, but it can encourage going offline and returning. Pure random selection treats every validator equally, which needs another rule to stop Sybil identities.

  1. Deposit the native coin into the staking contract and wait for activation.
  2. When selected, propose exactly one block at that height.
  3. Attest to other validators' blocks to support the chain.
  4. Earn rewards in proportion to stake and participation.
  5. If the validator signs two different blocks at the same height, slashing destroys part of the stake and removes it.

Slashing, nothing at stake, finality

The nothing-at-stake problem appears when signing many competing forks costs nothing. A validator could vote on every branch and collect rewards whichever wins. PoS answers with slashing: a validator that signs two different blocks at the same height, or two conflicting attestations, loses part of its stake, and the protocol removes it. The evidence is the two signed messages, so any node can prove the offence.

A checkpoint is a block that the protocol treats as final after enough validators attest. Finality means the block cannot be reverted without validators losing large deposits. Without checkpoints, PoS gives probabilistic settlement: more confirmations means lower reorg chance. With checkpoints, in Casper-style designs a checkpoint is first justified, then finalised one epoch later, so finality takes two epochs.

The long-range attack uses old validator keys to build a different history from an early point. A new node cannot tell which history is real by stake alone. Checkpoints and weak subjectivity solve this: a new node trusts a recent checkpoint from a known source, and old keys below the checkpoint cannot rewrite it.

Delegated PoS and trade-offs

In Delegated Proof of Stake, token holders vote for a small set of block producers. Those producers take turns making blocks; voters can remove them by re-voting.

  • Advantage: low energy use, because there is no hash race.
  • Advantage: cheap hardware, since a normal server or cloud VM can validate.
  • Advantage: faster finality, because checkpoints can finalize in seconds or a few slots.
  • Disadvantage: rich get richer, as rewards add to the largest stakes.
  • Disadvantage: cartel risk: a few large stakers, or a small producer set, can coordinate to control block production.
  • Disadvantage: security needs a large honest share of stake: above 50% an attacker can dominate block choice and censor, and finality rules usually need about two thirds of stake attesting.

Worked example

Question. Four validators A, B, C and D lock 500, 300, 150 and 50 tokens. Total stake is 1000 tokens. (a) Find each validator's chance of proposing the next block. (b) In 100 blocks, how many blocks should each propose on average? (c) Suppose this chain applies a 5% penalty without ejection (some PoS designs do this). B double-signs and pays the penalty. Find the penalty amount, B's new stake, B's new chance using the old total for comparison, and B's new chance after the destroyed tokens leave the total.

  1. Total stake S = 500 + 300 + 150 + 50 = 1000 tokens.
  2. P(A) = 500 ÷ 1000 = 0.50 = 50%; P(B) = 300 ÷ 1000 = 30%; P(C) = 150 ÷ 1000 = 15%; P(D) = 50 ÷ 1000 = 5%.
  3. Expected blocks in 100 = chance × 100: A gets 50, B gets 30, C gets 15, D gets 5 blocks.
  4. Penalty on B = 5% × 300 = 0.05 × 300 = 15 tokens. B's new stake = 300 − 15 = 285 tokens.
  5. Using the old total, B's chance = 285 ÷ 1000 = 0.285 = 28.5%. After the 15 destroyed tokens leave the total, new total = 1000 − 15 = 985 tokens. Final chance = 285 ÷ 985 = 0.28934 = 28.93%.

Answer. A, B, C and D have 50%, 30%, 15% and 5%; expected blocks are 50, 30, 15 and 5. B pays 15 tokens, falls to 285, shows 28.5% of the old total, and 28.93% after the total falls to 985 tokens.

Exam traps

  • PoS does not remove all attacks. A holder above 50% of stake can still reorganise or censor blocks.
  • Slashing is not a normal transaction fee. It destroys part of the stake and removes the validator.
  • Chance is stake ÷ total stake, not stake ÷ 100 or stake ÷ initial supply. The denominator changes when slashed coins are destroyed.
  • Nothing-at-stake is answered by slashing and checkpoints, not by faster hardware or more confirmations alone.
  • Probabilistic settlement and checkpoint finality are different. A block is final only when the protocol's checkpoint rule says so.

3.6 Proof of Elapsed Time and round robin consensus

Proof of Elapsed Time (PoET) and round robin consensus replace heavy hash computation with a fair turn rule. In PoET, every validator asks a trusted timer for a random wait; the shortest wait wins the right to propose a block, and a signed proof shows the wait was real. In round robin, the leader rotates in a fixed order, slot by slot. Both suit permissioned chains, where validators are known and a small group needs fast, cheap agreement. They are poor fits for open public chains unless paired with identity or another defence.

You need: 3.3 for permissioned versus permissionless consensus, and 3.5 for how stake-based turns work.

How Proof of Elapsed Time works

PoET uses a timer inside a trusted execution environment (TEE). A TEE is a protected part of a processor that runs code and keeps keys hidden from the normal operating system. Each validator runs the same timer code in its TEE and asks for a random wait W, measured in seconds. The validator with the smallest W sleeps until that time, then proposes a candidate block. It also produces a signed proof, called a wait certificate or receipt, that says: this TEE generated W, and the validator really waited W seconds. Other validators check the signature and the timer result before they accept the block. If two waits tie, a fixed rule breaks the tie.

The trust does not vanish. You trust the TEE design and the hardware maker. If the TEE is broken or its keys leak, a validator can fake a short wait or produce a false proof. A public chain also faces Sybil risk: one person can run many TEEs and ask for many waits. So PoET is mainly used in permissioned chains, where each validator is already known and admitted. The advantages are large: almost no electricity compared with Proof of Work (see <a href="#3.4">3.4), a fair spread of turns, and cheap hardware because no farm of miners is needed. The disadvantages are also clear: trust in the hardware maker, no safety if the hardware is broken, and weak protection for a public chain.

Round robin: a fixed order of leaders

Round robin is simpler. The validators are listed in a fixed order: v1, v2, ..., vN. Time is cut into equal slots of length T seconds. Slot n has one leader, and the leader is the only node allowed to propose a block in that slot. The other nodes check the block and vote or sign it. If enough honest nodes accept, the block is final. The leader order repeats after N slots. With N validators and slot 1 given to v1, the proposer of slot n is ((n − 1) mod N) + 1, and slot n starts at (n − 1) × T seconds.

proposer(n) = ((n − 1) mod N) + 1; start(n) = (n − 1) × T

proposer(n) is the validator number that leads slot n; n is the slot number starting at 1; N is the number of validators; T is the slot length in seconds; start(n) is the time in seconds at which slot n begins, measured from the start of slot 1, so slot 1 begins at 0 s; mod gives the remainder.

Round robin is simple, deterministic, fair, wastes no power, and gives fast finality on a small known network. Its weaknesses are just as direct. A faulty or offline leader stalls its slot. The next leader is predictable, so an attacker can target that node. Only one node proposes per turn, which limits throughput. Alone, round robin gives no Sybil resistance: a public chain with free identities can be flooded with fake validators. It only selects a leader; it is not a full Byzantine agreement rule. It must be paired with known identities and a vote or commit protocol. If a leader is dishonest, honest nodes must reject its block and skip the slot under a stated timeout rule.

Where each rule fits

Use PoET when you want an unpredictable leader among known validators and can trust a TEE. Use round robin when you want a predictable, auditable rotation and the network is small and permissioned. Neither gives public-chain security on its own. PoET buys unpredictability with hardware trust. Round robin buys simplicity with a fixed schedule. Both are cheap and fast, but both need identity control. In both, the block still needs validation: check signatures, transaction rules, and state. The turn rule only answers who may propose next. The vote rule answers whether the block is accepted. A common pattern is round robin for leader choice plus a Byzantine agreement step for commit; PoET can use the same commit step after its timer lottery. The consensus mechanism is the whole rule set, not just the leader picker.

Worked example

Question. Three validators draw PoET waits of 4 s, 2 s and 7 s. (a) Which validator proposes, and at what time? (b) A round-robin chain has 3 validators, slots of 5 s each, and slot 1 is given to validator A. Find the proposer and start time of slot 7.

  1. List the waits: A = 4 s, B = 2 s, C = 7 s.
  2. Smallest wait = min(4, 2, 7) = 2 s, so B wins at t = 2 s. B proposes; the others verify B's signed proof before accepting.
  3. Round robin: N = 3 validators, T = 5 s per slot, and n = 7.
  4. Compute n − 1 = 6.
  5. proposer = (6 mod 3) + 1 = 0 + 1 = 1, which is validator A.
  6. start = (7 − 1) × 5 = 6 × 5 = 30 s. Slot 7 runs from 30 s to 35 s.

Answer. B proposes at 2 s; validator A leads the seventh slot and it starts at 30 s.

Exam traps

  • PoET is not trustless. It trusts the timer code and the hardware maker; a broken TEE lets a validator fake a short wait or a false proof.
  • Round robin alone does not survive Byzantine nodes. It only picks the proposer; a separate vote or commit rule must reject bad blocks and skip a failed leader.
  • Round robin is not Sybil-resistant by itself. A public chain with free identities can create many validators; pair it with permissioned membership or another identity rule.
  • In PoET every validator draws a random wait and sleeps for it. The validator whose wait ends first (the smallest W) proposes; the others are still waiting and then verify its signed wait proof. There is no simultaneous race to propose, because the shortest wait always finishes first.
  • Do not call PoET energy-free. The timer uses little energy, but hardware, attestation and network costs remain.

3.7 Forks: soft forks and hard forks

A fork is a split in the block chain: two histories that share a parent but not the same future. Forks happen when software rules change, when a bug is fixed, when developers or miners disagree, and even in normal operation when two miners find a block at the same height. The label soft or hard depends on one test: do nodes running the old rules still accept blocks made under the new rules? That test decides whether the network stays on one chain or splits into two coins.

You need: 3.4 and 3.5 for the two ways blocks are produced, and Unit 1 for block structure and hash links.

What a fork is, and the ordinary temporary fork

A fork is any divergence in the block chain: two blocks or two chains with a shared parent. One cause is ordinary latency. Miner A and miner B may find a block at the same height, both with parent at height 100. Some nodes hear A first, some hear B. The next block, mined on one of them, makes the other a stale block: a valid block that is not in the best chain. Nodes then reorganise to the heavier chain. Reorg depth is the number of blocks removed from the best chain in that switch. This temporary fork is normal and does not change the rules. Rule-change forks are different: a software upgrade, a bug fix that changes validity, disagreement among developers or miners, or an emergency rollback. The fork type is decided by validity, not by who intends what.

Soft fork: tighter rules, old nodes still accept

A soft fork tightens the rules. A block valid under the new rules is also valid under the old rules, so old nodes accept it.

NewValid(B) ⇒ OldValid(B)

NewValid(B) means block B passes the new rules; OldValid(B) means B passes the old rules. The arrow means: if the left side is true, the right side must also be true.

Some old-valid blocks may fail the new rules; new nodes reject those. That is still backward compatible because the old software can follow the new chain. A soft fork needs a majority of hash power or stake to enforce the tighter rule. If only a minority runs it, old-rule miners can keep producing blocks that new nodes reject, and two tips can compete until one side wins. SegWit in Bitcoin in 2017 is the standard example: it changed how signature data is counted without making old nodes reject the new blocks. A soft fork can therefore split the chain for a while, but it does not require a permanent split.

Hard fork: incompatible rules, permanent split, and confirmation depth

A hard fork widens or changes the rules so that old and new nodes disagree on validity. There is a block B with NewValid(B) true and OldValid(B) false. Old nodes reject B, so they reject the new chain. If a large group keeps running the old rules and mining, the result is two chains with separate histories and separate coins. Bitcoin Cash in 2017 raised the block size and split from Bitcoin. Ethereum's 2016 hard fork reversed the DAO theft; the chain that rejected the change became Ethereum Classic. A hard fork is a rule change, not automatically two live coins: if every node and miner upgrades, the old chain stops. Confirmation depth protects against temporary forks. Waiting for k confirmations means the block holding the transaction has k−1 blocks built on top of it. The transaction survives only if the reorg depth is less than k. The chance that a shorter branch overtakes it falls as k grows. Reorg depth measures how many blocks were replaced. A stale block is one discarded block under the same rules, not a hard fork.

Worked example

Question. At height 100 the network splits. Miners on the new rules have 85% of total hash power; old-rule miners have 15%. Ignore difficulty changes and network latency. (a) When the new chain has mined 2016 blocks, what is its height? (b) What is the expected number of old-chain blocks in the same time, rounded to the nearest whole block? (c) What is the old-chain height?

  1. Both chains start at height 100.
  2. The new chain mines 2016 blocks, so its height is 100 + 2016 = 2116.
  3. The old-to-new block rate ratio is 0.15 ÷ 0.85 = 3/17 = 0.17647.
  4. Expected old-chain blocks = 2016 × 0.17647 = 355.76 blocks. A block count is an integer, so round to 356 blocks.
  5. This count assumes difficulty stays fixed, as the question states. In a real split each chain retargets its own difficulty; the old chain's difficulty falls with its hash power, its block rate rises, and the old-chain count in the same time would be larger than 356.

Answer. The new chain is at height 2116, the old chain is expected to have 355.76 blocks (356 whole blocks), so the old chain is at height 456.

Exam traps

  • Saying a soft fork can never split the chain: during activation a minority old-rule chain can compete, and a lasting split is possible if old miners keep mining blocks that new nodes reject.
  • Calling an ordinary stale block a hard fork: the stale block follows the same rules and is discarded only because another branch grew first.
  • Assuming a hard fork always creates two live coins: if every node and miner upgrades, the old chain stops and no second coin survives.
  • Reversing backward compatibility: a soft fork means old software accepts new blocks, not that new software accepts every old block.
  • Treating confirmations as a formality: each extra confirmation lowers the chance that a temporary fork reverses the transaction.

Old nodes accept new-rule blocks because the new rules are a subset of the old rules. The old software can follow the new chain even though it does not enforce the tighter rule.

Apply New-rule miners have 70% of hash power and old-rule miners have 30%. After the new chain mines 1000 blocks, what is the expected number of old-chain blocks? Round to the nearest block. 4 marks

Rate ratio = 0.30 ÷ 0.70 = 3/7 ≈ 0.42857. Expected old blocks = 1000 × 0.42857 = 428.57, so 429 blocks.

Apply A transaction has 3 confirmations. A reorg replaces 4 blocks from the tip. Is the transaction still in the best chain? 3 marks

No. With 3 confirmations the block holding the transaction is third from the tip. A 4-block reorg removes the first four blocks from the tip, and any reorg of depth 3 or more would also remove it, because reorg depth ≥ confirmations means the transaction block is replaced. The transaction must be re-mined or re-included.

Analyze Two miners find a block at height 101 with the same parent. The next block is mined on one of them. Is this a hard fork? 4 marks

No. Both blocks follow the same rules. This is a temporary fork caused by latency; the other block becomes a stale block and the network reorganises to one tip.

Analyze Why can a hard fork produce two coins, while a soft fork usually does not? 5 marks

In a hard fork old nodes reject new-rule blocks, so old-rule miners can keep a separate valid chain with its own history and coin. In a soft fork old nodes accept new-rule blocks, so the old tip loses unless a lasting group keeps mining blocks that new nodes reject.

Understand What does reorg depth measure? 2 marks

Reorg depth is the number of blocks removed from the best chain when a competing branch becomes the best chain.

Beyond the syllabus

Not for the exam. In practice forks are managed with activation signaling, replay protection and chain IDs; exchanges and wallets often pause deposits around upgrades. Newer research looks at fork choice, finality and social consensus, because code rules cannot settle which chain a community should value. Takeaways

  1. Blockchain nodes form a serverless peer-to-peer overlay and discover peers through seed nodes, known addresses, or gossip.
  2. Gossip spreads each transaction and block quickly, but nodes filter duplicates and validate before forwarding.
  3. A transaction moves from wallet to mempool to candidate block to mined block, and the miner earns fees and block reward for ordering.
  4. Consensus must keep agreement, validity, and termination even when nodes crash or behave dishonestly.
  5. Voting-based consensus gives fast finality in a known validator set; proof-based consensus works in open networks with Sybil resistance.
  6. Proof of Work secures history by cost: miners search a nonce for a hash below target, and difficulty adjusts to keep block time steady.
  7. Proof of Stake replaces hash power with locked stake; slashing makes attacks costly but can concentrate power among large holders.
  8. Proof of Elapsed Time and round robin suit permissioned chains where identities are known and energy cost matters.
  9. A soft fork tightens rules while old nodes still accept new blocks; a hard fork changes rules so old and new nodes reject each other.

Glossary

51% attack
An attack where one entity controls most mining power or stake and can reorder or censor blocks.
Byzantine fault
A fault in which a node may lie, omit messages, or send conflicting messages.
Candidate block
A block a miner or validator is assembling and trying to make acceptable to the network.
Consensus
The protocol rules and process that make independent nodes agree on one ordered history.
Crash fault
A fault in which a node stops working and sends no further messages.
Deterministic finality
A guarantee that a finalised block cannot be reversed by the protocol.
Difficulty
A measure of how low the Proof of Work target is, adjusted to keep block time steady.
Fork
A divergence in the blockchain, either temporary or permanent.
Gossip protocol
A spreading method where each node forwards new data to its neighbours.
Hard fork
A rule change that makes new blocks invalid to old nodes, often splitting the chain.
Mempool
A node's local pool of valid but unconfirmed transactions.
Miner
A node that selects transactions and performs Proof of Work to produce a block.
Network discovery
The process by which a node learns the addresses of peers and joins the overlay.
Nonce
A variable number a miner changes to search for a valid Proof of Work hash.
Peer-to-peer network
A network of equal nodes that exchange data directly without a central server.
Probabilistic finality
A finality model where reversal becomes less likely as more blocks are added.
Proof of Elapsed Time
A consensus method where nodes wait for a random timer and the first to finish proposes.
Proof of Stake
A consensus method where validators lock coins and propose blocks in proportion to stake.
Proof of Work
A consensus method where a block requires a hash below a target.
Round robin
A turn-taking rule where nodes propose blocks in a fixed order.
Slashing
A Proof of Stake penalty that destroys part of a validator's locked coins for misbehaviour.
Soft fork
A rule tightening that old nodes still accept as valid.
Stake
Coins locked by a validator as a bond in Proof of Stake.
Sybil attack
An attack where one entity creates many fake identities to gain influence.
Target
The threshold value that a Proof of Work block hash must be below.
Validator
A node that proposes or attests blocks under Proof of Stake.
