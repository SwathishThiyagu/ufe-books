2.1 Cryptographic primitives

Cryptographic primitives are small, standard tools that each answer one security question. A hash checks that data did not change. A cipher hides data. A message authentication code checks integrity with a shared key. A public-key operation proves who sent data. Blockchain uses them together: hashes link blocks, signatures authorize transfers, and ciphers protect wallets and network traffic. Read the four tools by the question each answers, not by the algorithm name.

You need: Unit 1, block structure and distributed ledger (Foundations of Blockchain), especially what a block header contains.

Security goals and the words for them

A sender starts with plaintext: the readable message. Encryption turns it into ciphertext, which looks random. A key is the secret value that controls the transformation. The adversary is anyone who tries to break the system. Assume the adversary knows the algorithm and can read all traffic. Security comes from the key, not from hiding the method.

  • Confidentiality: only allowed parties can read the plaintext.
  • Integrity: any change to the message is detected.
  • Authentication: the receiver knows who created the message.
  • Non-repudiation: the sender cannot later deny signing the message.

A shared secret gives authentication between the two holders: either could have made the message. Non-repudiation needs a private key that only one party holds. A cryptographic primitive is a well-defined operation with a stated security assumption. Do not ask a primitive to do a job outside that assumption.

The four primitives

Symmetric encryption uses one key for both encryption and decryption. A cryptographic hash takes any input and returns a fixed-size digest; it uses no key. A message authentication code (MAC) is a keyed check on a message. Public-key cryptography uses a pair: a private key and a public key. It can encrypt or sign. Chapters 2.5 and 2.6 give the mathematics.

Key length, randomness and encoding

Key length is measured in bits. Brute force tries keys until one works. For a random n-bit key, there are 2n possible keys. For example, a 128-bit key has 2128 ≈ 3.4 × 1038 possible keys. The expected search is half the keyspace.

expected trials ≈ 2n−1

n is the key length in bits; trials is the number of keys tried before success.

Each extra bit doubles the work. A 128-bit key and a 129-bit key differ by a factor of two in brute-force cost. Use a cryptographically secure random number generator for keys. A key made from a phone number, a name or the current time is guessable. A weak random source breaks every tool above it.

Keys, hashes and signatures are byte strings. Hex writes each byte as two characters from 0-9 and a-f. Base64 writes three bytes as four characters and is common in JSON and email. Base58 drops characters that look alike, such as 0, O, I and l; Bitcoin addresses use it. See 2.7. Encoding changes the display, not the security.

Worked example

Question. A system uses a 128-bit key. An attacker can test 10¹² keys per second. The expected brute-force search is half the keyspace. How long is that in years? Use 1 year = 3.15 × 10⁷ s.

  1. Number of possible keys = 2¹²⁸. Half the keyspace = 2¹²⁷ = 1.7014 × 10³⁸ keys.
  2. Time in seconds = keys ÷ rate = 1.7014 × 10³⁸ ÷ 10¹² = 1.7014 × 10²⁶ s.
  3. Time in years = seconds ÷ seconds per year = 1.7014 × 10²⁶ ÷ 3.15 × 10⁷ = 5.4013 × 10¹⁸ years.

Answer. The expected brute-force search is about 5.4013 × 10¹⁸ years.

Exam traps

  • A hash is not encryption. It has no key and cannot be reversed.
  • A MAC uses a shared key, so either holder can compute it; it cannot prove non-repudiation.
  • Key length is in bits. A 256-bit key is 32 bytes, not 256 bytes.
  • A public key encrypts or verifies a signature; a private key decrypts or signs. Reversing the roles breaks the scheme.
  • Base64 is an encoding, not encryption; it hides nothing.

2.2 Cryptographic hash functions and SHA-256

A cryptographic hash function takes any message, short or long, and produces a fixed-size fingerprint. SHA-256 gives 256 bits, printed as 64 hexadecimal characters. The fingerprint is easy to compute and very hard to reverse or to fake with a different message. Blockchains use it to name blocks, link them and commit to transactions. This chapter explains the security properties, the avalanche effect, the birthday bound, and the SHA-256 padding and compression steps.

You need: the four cryptographic tools and one-way ideas from Chapter 2.1.

Three security properties

Write H(M) = d. H is the hash function, M is any message in bits, and d is the 256-bit digest. A cryptographic hash has three separate promises.

  • Preimage resistance: given d, it is infeasible to find any M with H(M) = d.
  • Second-preimage resistance: given M, it is infeasible to find a different M′ with H(M′) = H(M).
  • Collision resistance: it is infeasible to find any two different messages M and M′ with the same digest. This is stronger than second-preimage resistance because the attacker may choose both messages.
  • Avalanche effect: flipping one input bit changes about half of the 256 output bits. A good hash gives no visible pattern.
  • Birthday bound: with 2²⁵⁶ possible digests, a collision appears after about √(2²⁵⁶) = 2¹²⁸ random trials. So SHA-256 gives about 128 bits of collision security, not 256.

H: {0,1}* → {0,1}²⁵⁶

H is the hash function; {0,1}* is any finite bit string; {0,1}²⁵⁶ is a 256-bit output.

SHA-256 padding and compression

SHA-256 first pads the message so its length is a multiple of 512 bits. The padding is not optional; it makes the compression step unambiguous.

  1. Let L be the message length in bits.
  2. Append one 1 bit.
  3. Append k zero bits, where k = (448 − (L + 1)) mod 512. The mod keeps the count valid for long messages.
  4. Append L as a 64-bit unsigned integer.
  5. The total length is now a multiple of 512 bits. Split it into 512-bit blocks, each 16 words of 32 bits.
  6. Start with eight 32-bit chaining words. For each block, expand 16 words to 64 words, run 64 rounds, and add the block result into the chaining value.
  7. Concatenate the final eight words: 256 bits, written as 64 hexadecimal characters.

k = (448 − (L + 1)) mod 512

L is the message length in bits; k is the number of zero bits appended after the single 1 bit.

The 64 rounds mix 32-bit words with Boolean functions, rotations and addition modulo 2³². You will rarely be asked for the full round schedule; know that the compression function exists and that it is repeated for every block. SHA-256 uses the Merkle–Damgård construction. SHA-3 uses Keccak. The output is always 256 bits: 64 hex characters such as 3a7bd3e2... .

Hashing in blockchain

Some syllabi call this hashing in blockchain. The hash is public and keyless: anyone can recompute it, so it is not encryption. Its job is to identify data and make tampering visible.

  • A hash pointer stores the previous block hash and the address of that block, so an edit breaks the chain from that point onward. See Chapter 2.3.
  • A Merkle root hashes transactions pairwise into one 32-byte value, so a block header commits to thousands of transactions. See Chapter 2.4.
  • Mining repeatedly hashes a block header with a changing nonce; the target decides the difficulty. See Unit 3, Proof of Work and mining.
  • An address is a short encoded hash of a public key, not the key itself. See Chapter 2.7.

Worked example

Question. A message is 448 bits long. SHA-256 appends one 1 bit, then k zero bits, then a 64-bit length. Find k and the total padded length. State how many 512-bit blocks result.

  1. The message length is L = 448 bits.
  2. After the single 1 bit, the length is L + 1 = 449 bits.
  3. We need 449 + k ≡ 448 (mod 512). So k ≡ −1 ≡ 511 (mod 512). Take k = 511 zero bits.
  4. Append the 64-bit length field. Total length = 448 + 1 + 511 + 64 = 1024 bits.
  5. 1024 ÷ 512 = 2, so the padded message is two 512-bit blocks.

Answer. k = 511 zero bits; total padded length = 1024 bits, which is two 512-bit blocks.

Exam traps

  • Forgetting the single 1 bit and computing k from L instead of L + 1.
  • Padding the whole message to 448 bits always, instead of making the length 448 modulo 512 before adding the 64-bit length field.
  • Confusing 256 bits with 256 bytes, or 64 hexadecimal characters with 64 bytes; 64 hex characters are 32 bytes.
  • Treating a hash as encryption. A hash has no key and is not meant to be reversed; encryption with a key is reversible.
  • Saying SHA-256 gives 256 bits of collision security. The birthday bound gives about 2¹²⁸ trials for a collision.

Second-preimage resistance fixes one message M and asks for a different message with the same hash. Collision resistance asks for any two different messages with the same hash, and the attacker can choose both.

About half of the 256 output bits should change because of the avalanche effect. In a blockchain, even a tiny edit to a block changes its hash, so hash pointers detect tampering.

Not for the exam. In industry, SHA-256 runs in hardware and is used far beyond blockchains, including TLS certificates and file integrity checks. Newer systems sometimes choose SHA-3, BLAKE3 or hash-based signatures for different trade-offs. Research looks at collision attacks, hardware side channels and post-quantum hash-based schemes. 2.3 Linking blocks with hash pointers

A hash pointer is an ordinary pointer with one addition: it also stores the cryptographic hash of the data it points to. In a blockchain each block's header holds a hash pointer to the block before it. That one field turns a loose list of blocks into a chain that cannot be edited quietly, because an edit changes a hash and the next block's pointer no longer matches. Bitcoin, Ethereum and every other chain rely on it, and the same trick appears in version-control history, audit logs and certificate transparency.

You need: 2.1 and 2.2 for hashing, and the block header from Unit 1, Blockchain architecture and structure of a block.

A pointer that carries a fingerprint

An ordinary pointer stores one thing: the address of the data it points to. Read through it and you get whatever is there now. The pointer itself never tells you whether the data changed since the pointer was made.

A hash pointer stores the cryptographic hash of the data it points to. In a block header the field is just the 32-byte hash of the parent block's header; the parent's address is implicit. To use it, fetch the parent block—found by its hash—hash its header yourself, and compare the two values. Equal means the parent is exactly what the pointer was built for. Different means someone edited it.

HP(i − 1) = H(header of block i − 1)

HP(i − 1) is the hash pointer kept inside block i, stored as the 32-byte prev field; H is the chain's header-hash function (Bitcoin uses SHA-256d, two SHA-256 applications, returning 32 bytes); header of block i − 1 means the full 80-byte header of the parent block. The parent is identified by this hash; any address is implicit and looked up, not stored.

The hash costs 32 bytes whether the pointed data is a ten-byte note or a four-megabyte block, because a 256-bit hash always outputs 32 bytes (see 2.2). That fixed size is what lets a long chain stay small.

The hash covers the pointed header completely. One flipped bit in the header changes H(header). A body edit changes the Merkle root, and updating the header then changes H(header). So the moment block i commits to that hash, block i − 1's header is frozen: any edit is detectable by anyone holding block i's header.

The standard name is hash pointer. In a block header the stored field is called the previous block hash, or prev. Use those terms; they are what exam answers expect.

  1. Start from the newest header you trust.
  2. Read its prev field. That value should equal the hash of the block before it.
  3. Fetch that earlier block, hash its header with the chain's header-hash function (SHA-256d for Bitcoin), and compare the two.
  4. If they match, step back one block and repeat.
  5. Stop at the genesis block. Reaching it with every link matching means the chain is intact.

Inside the block header

A block is a header plus a body. The body carries transactions; the header carries the links and the metadata. Bitcoin's header is exactly 80 bytes and has six fields.

FieldSizeWhat it holds

Merkle root32 bytesone hash committing to every transaction in the body

Only the header is hashed, using the chain's header-hash function (SHA-256d for Bitcoin). Two blocks with identical headers hash identically, so changing any one of the six fields changes the block's own hash, and therefore every prev field that points at it.

The genesis block is the first block of a chain. It has no parent, so there is no hash to store. Its prev field is set to 32 zero bytes, a value a real block hash will not produce in practice. Nodes read prev = 0 as 'root', which gives every node the same agreed starting point. Bitcoin's genesis header is hardcoded into every client.

The Merkle root is the second hash in the header. It is a single 32-byte value that commits to every transaction in the body, built as a Merkle tree (2.4). Difficulty bits and nonce belong to mining, covered in Unit 3, Proof of Work and mining.

Why the tamper travels forward

Suppose an attacker rewrites a transaction inside block i. The body changes, so the Merkle root inside block i's header changes, so H(header of block i) changes. Block i + 1 still stores the old value as its prev field. The check at that single link fails.

Repairing the link means writing the new hash into block i + 1's prev field. But prev is part of block i + 1's header, so H(header of block i + 1) changes too. Block i + 2 now fails. The damage walks forward one link at a time, up to the newest block.

Hiding one edit therefore costs a rehash of every later block. That part is cheap: a laptop computes millions of header hashes per second. The expensive part is that each rewritten header must also beat the difficulty target, while honest miners keep extending the chain. Hash pointers give tamper-evidence; mining gives tamper-resistance. Keep the two apart.

  • An edit breaks the chain from that block onward, not just the next link.
  • Block order is fixed: block i's hash depends on block i − 1, so blocks cannot be swapped.
  • Checking one Bitcoin link costs two SHA-256 calls (SHA-256d), so verification stays cheap as the chain grows.

Headers alone are enough to check the skeleton. A million 80-byte headers is about 80 MB, which fits on a phone. A wallet can download only headers and still confirm that a transaction it cares about sits under a header chain it trusts (see Unit 4, Bitcoin protocol).

Worked example

Question. Blocks 1, 2 and 3 have hashes 0001, 0002 and 0003. Block 1 stores prev = 0000 (the genesis hash), block 2 stores prev = 0001, and block 3 stores prev = 0002. An attacker rewrites a transaction in block 2, so H(block 2) becomes 0009, and recomputes nothing else. (a) How many stored prev fields now fail to match? (b) Which block's prev field is it, and what value must it hold after the fix?

  1. List the stored prev fields: block 1 → 0000, block 2 → 0001, block 3 → 0002.
  2. Hash of each parent after the attack: genesis = 0000, block 1 = 0001, block 2 = 0009, block 3 = 0003.
  3. Block 1: stored prev 0000 against H(genesis) = 0000. Match.
  4. Block 2: stored prev 0001 against H(block 1) = 0001. Match, because block 1 was not touched.
  5. Block 3: stored prev 0002 against H(block 2) = 0009. Mismatch. So exactly one prev field fails.
  6. Fix: set block 3's prev to 0009. That changes block 3's header, so H(block 3) moves away from 0003, and any block 4 holding prev = 0003 breaks next.

Answer. One stored prev field fails, block 3's; it must change from 0002 to 0009, and that change breaks the link to block 4.

Exam traps

  • Answering only that the next block breaks. The examiner wants the cascade: every block after the edit must be rehashed.
  • Confusing a block's own hash with its prev field. The header stores the parent's hash; the block's own hash is what the child stores.
  • Treating genesis prev = 0 as the hash of something. It is a fixed marker that every node reads as 'root'.
  • Swapping the Merkle root and the previous block hash in a header diagram. Both are 32 bytes; only one links blocks.
  • Saying the hash pointer stores a copy of the block. It stores a 32-byte fingerprint; the address is implicit and looked up, not stored.

2.4 Merkle trees

A Merkle tree takes many transaction hashes, pairs them, hashes each pair, and repeats until one hash remains: the Merkle root. A block header stores that one root, so 32 bytes stand for thousands of transactions. The tree also makes proof cheap: to show that one transaction is in the block, you send only the sibling hashes on its path to the root, about log₂ n hashes. Bitcoin uses this design; Ethereum uses a Merkle Patricia trie. The build, the proof and the common mistakes follow.

You need: Chapter 2.2 for the hash function H and collision resistance, and Chapter 2.3 for why a block header carries one root hash.

Building the tree

Start with n transactions T1 … Tn. Each transaction is hashed once: hi = H(Ti). These hashes are the leaves. A leaf is a node with no children. The tree is binary: each internal node has two children. An internal node stores the hash of its two child hashes joined in order: H(left || right). The two vertical bars || mean concatenation: write the left hash bytes, then the right hash bytes.

Pair leaves from left to right: h1 with h2, h3 with h4, and so on. Hash each pair to get the next level. Repeat on that level. Stop when one hash remains. That top hash is the Merkle root R. It is also called the root hash.

  1. Hash every transaction: hi = H(Ti). These are the leaves.
  2. Join neighbours in order: h12 = H(h1 || h2), h34 = H(h3 || h4), and so on.
  3. Repeat on the new level until one hash is left. That hash is R.
  4. If a level has an odd count, duplicate the last hash and pair it with itself. Bitcoin does this.
R = H( H(h<sub>1</sub> || h<sub>2</sub>) || H(h<sub>3</sub> || h<sub>4</sub>) )

H is the hash function (SHA-256 in Bitcoin); || joins two hashes in fixed left-to-right order; h1 = H(T1) and so on; R is the Merkle root, 32 bytes for SHA-256.

For four transactions the height is two hash steps above the leaves. A tree with n leaves has about log₂ n levels, because each level halves the node count.

Proof of inclusion

A Merkle path, also called a Merkle proof or inclusion proof, shows that one transaction is in the tree. The verifier already trusts the root R from the block header. The prover sends the transaction and the sibling hash at each level, from the leaf upward. The verifier hashes the transaction to get its leaf, joins it with the first sibling in the correct order, hashes, and repeats. If the final hash equals R, the transaction is included.

Order matters. At each step the verifier must know whether the running hash is the left child or the right child. A proof therefore carries a side bit, or the verifier knows the index of the transaction in the block. Swapping the two inputs gives a different hash and the check fails.

For n leaves the path has about log₂ n hashes; exactly, at most ceil(log₂ n). A block with 1,024 transactions needs at most 10 hashes, not 1,024. That is the reason the tree exists. Payment verification with such proofs is covered in Unit 4, Bitcoin and Cryptocurrencies.

Odd levels need care. If a level has an odd number of nodes, Bitcoin copies the last node and hashes it with itself: H(x || x). The copy is not stored as a new transaction; it is a rule for building the level. A proof for that last node includes x as its own sibling.

What the root commits to

The Merkle root is a commitment. Change one transaction, and its leaf hash changes. That changes every hash on the path to the root. The root changes. Because the block header holds the root and the header is itself hashed into the next block (see Chapter 2.3), an edit cannot hide.

The root does not prove that a transaction is valid, that it has a signature, or that it is not a double spend. It proves only that the transaction is in the set committed by that root. Validation is separate: signatures are in Chapter 2.6; the transaction life cycle is in Unit 3.

Bitcoin uses a binary Merkle tree over transaction IDs. Ethereum uses a different structure, a Merkle Patricia trie, for accounts and storage; the name is enough here. Some syllabi call this topic digital structures in blockchain. The main exam skill is to build the levels, recompute the path after one change, and state the size of a proof.

Worked example

Question. Four transactions T1, T2, T3 and T4 have hashes h1 = H(T1), h2 = H(T2), h3 = H(T3) and h4 = H(T4). (a) Write the Merkle root R. (b) Transaction T3 is replaced by T3′. Which stored hashes must be recomputed, and what is the new root?

  1. Pair the leaves in order: h12 = H(h1 || h2) and h34 = H(h3 || h4).
  2. Hash the two level-1 hashes in order: R = H(h12 || h34) = H( H(h1 || h2) || H(h3 || h4) ).
  3. For the change, compute the new leaf h3′ = H(T3′). h1, h2 and h4 do not change.
  4. Recompute the parent of h3′ and h4: h34′ = H(h3′ || h4). The other parent h12 = H(h1 || h2) does not change.
  5. Recompute the root: R′ = H(h12 || h34′). Only h3′, h34′ and R′ are new; h12 is reused.

Answer. R = H( H(h1 || h2) || H(h3 || h4) ); after T3 changes, recompute h3′, h34′ and R′, while h12 stays the same.

Exam traps

  • Reversing the pair: H(h2 || h1) is not H(h1 || h2). A proof must keep left and right.
  • Odd level: forget to duplicate the last hash, or duplicate a middle hash. Bitcoin duplicates only the last node at that level.
  • Mixing raw data and hashes: internal nodes hash two hashes, not two raw transactions.
  • Confusing the Merkle root with the block hash. The root covers transactions; the block hash covers the header.
  • Saying a proof needs all transactions or n hashes. It needs about log₂ n sibling hashes.

2.5 Public-key and elliptic curve cryptography

Public-key cryptography gives each user a pair of numbers: a private key kept secret and a public key shared openly. The public key is computed from the private key, but no practical method runs that calculation backwards. This one-way relation lets two strangers agree on a secret, or check who signed a message, without ever meeting. A blockchain uses it for ownership: your key pair is your account (see Chapter 2.7). Elliptic curve cryptography makes the pair short enough to live on a phone.

You need: Chapter 2.1 for where public-key operations sit among the four primitives, and modular arithmetic — the remainder after division — from school maths.

The key pair and the one-way relation

A public-key system gives you two numbers, not one. The private key is a secret random number, usually written k. The public key is a second number K, computed from k by a fixed rule. You may print K on a visiting card. Nobody can use K to recover k.

The rule is one-way: going from k to K takes microseconds, and going from K to k takes longer than the age of the universe. Formally, the system rests on a hard mathematical problem. In RSA the problem is integer factorisation: multiplying two large primes is cheap, splitting the product back into primes is not. In elliptic curve cryptography (ECC) the problem is the elliptic curve discrete logarithm: given a fixed starting point G and the result K = k·G, find the integer k.

That is the whole trick. Two strangers can agree on a shared secret, or verify that a message came from the holder of k, while exchanging only numbers that are safe to publish. Your UPI app does this every time it opens a secure connection to the bank: it checks a certificate carrying a public key, and the session key travels encrypted.

A longer key is not automatically a better key. Security comes from the hard problem, and different problems need different key lengths.

The curve and its arithmetic

An elliptic curve is the set of points (x, y) that satisfy the equation below, where a and b are constants and the curve has no repeated roots, which requires 4a³ + 27b² ≠ 0.

y² = x³ + a·x + b (mod p)

x and y are the point coordinates; a and b are curve constants fixed for all users; p is a large prime; mod p means every value is a whole number from 0 to p−1.

Because the arithmetic is modulo p, the curve is not a smooth line. Over a prime field the same equation produces a scattered cloud of integer points, as the figure shows for p = 17, and that scattering is what makes the discrete log hard.

The useful part is that points can be added. Draw a straight line through P and Q. It meets the curve at a third point. Reflect that point across the x-axis and you have P + Q. Addition is commutative and associative, and there is an identity element called the point at infinity, which plays the role of zero.

When P = Q the line becomes the tangent, and the slope is m = (3x₁² + a) / (2y₁) mod p. This is point doubling. For two distinct points the slope is m = (y₂ − y₁) / (x₂ − x₁) mod p; note that a appears only in the doubling formula.

x₃ = m² − x₁ − x₂, y₃ = m(x₁ − x₃) − y₁

m is the slope computed above; (x₁, y₁) and (x₂, y₂) are the two points being added; (x₃, y₃) is the result, all values taken mod p.

Repeated addition gives scalar multiplication: k·G means G added to itself k times, computed quickly by repeated doubling. The public key is K = k·G. Bitcoin and Ethereum use one named curve, secp256k1, with a = 0, b = 7, a 256-bit prime p = 2²⁵⁶ − 2³² − 977, and a fixed base point G.

Both RSA and ECC are believed secure, but ECC reaches the same strength with far shorter keys. The accepted comparison is below: a 256-bit ECC key gives roughly the security of a 3072-bit RSA key. Shorter keys mean less storage, less bandwidth and faster arithmetic — which matters on a low-end Android phone on a slow connection.

Worked example

Question. The curve y² = x³ + 2x + 2 is defined over the prime field F₁₇. The point P = (5, 1) lies on it. Using the point-doubling formulas, compute 2P.

  1. Read the constants: a = 2, b = 2, p = 17. The point is (x₁, y₁) = (5, 1), so 2y₁ = 2.
  2. Slope of the tangent: m = (3x₁² + a) / (2y₁) mod 17 = (3·25 + 2) / 2 = 77/2 mod 17.
  3. Replace division with multiplication by the modular inverse: 2⁻¹ mod 17 = 9, because 2 × 9 = 18 ≡ 1 (mod 17).
  4. Reduce the numerator: 77 mod 17 = 77 − 68 = 9.
  5. So m = 9 × 9 = 81 ≡ 81 − 68 = 13 (mod 17).
  6. x₃ = m² − 2x₁ = 169 − 10 = 159 ≡ 159 − 153 = 6 (mod 17).
  7. y₃ = m(x₁ − x₃) − y₁ = 13(5 − 6) − 1 = −13 − 1 = −14 ≡ 3 (mod 17).
  8. Check that the answer is on the curve: y₃² = 3² = 9, and x₃³ + 2x₃ + 2 = 216 + 12 + 2 = 230 ≡ 9 (mod 17). Both sides agree.

Answer. 2P = (6, 3) on y² = x³ + 2x + 2 over F₁₇, with slope m = 13.

Exam traps

  • Treating 'divide by 2y₁' as ordinary integer division. It means multiply by the modular inverse: 77/2 mod 17 is 77 × 9 = 693 ≡ 13, not 38 (integer division) and not 38.5.
  • Drawing the smooth real curve and reading points off it. In the crypto setting x and y are integers mod p, and the points look like a scatter of dots.
  • Calling the public key an 'encrypted private key'. The relation is scalar multiplication on the curve, and no decryption recovers k from K.
  • Swapping the hard problems: RSA rests on integer factorisation, ECC on the elliptic curve discrete logarithm. Writing the wrong one loses the marks.
  • Mixing up constants: secp256k1 has a = 0 and b = 7, while the practice curve y² = x³ + 2x + 2 has a = 2 and b = 2. The constant a also appears in the doubling slope but not in the slope for two distinct points.

2.6 Digital signatures and ECDSA

A digital signature is a short value that proves the holder of a private key approved a particular message. Anyone with the matching public key can check it, but nobody can produce it without the private key. Blockchains need this because no bank or login server vouches for a payment: a Bitcoin transaction carries a signature, and every node checks it against the sender's public key. ECDSA, the Elliptic Curve Digital Signature Algorithm, is the scheme Bitcoin has used from its first block. This chapter shows how signing and verification work, and the one careless mistake that destroys the private key.

You need: Chapter 2.2 for the hash z, and Chapter 2.5 for curve order, base point and the step Q = dG.

Signing and verification

A digital signature is a value attached to a message that proves who approved the message and that it was not altered afterwards. A signing algorithm produces it from the message and a private key d. A verification algorithm checks it using the message and the matching public key Q.

  • Authenticity: only the holder of d can create a valid signature.
  • Integrity: change one bit of the message and verification fails.
  • Non-repudiation: the signer cannot later deny signing, because nobody else holds d.

Why not a MAC? A message authentication code also uses a secret, but signer and verifier share the same one, so the verifier could have forged the tag himself. In a blockchain thousands of strangers must verify, and none of them may hold the signer's secret. Public-key signatures give exactly that split.

In Bitcoin every transaction input carries a signature, and nodes check it before the transaction enters a block. The transaction format itself is in Unit 4.

ECDSA step by step

ECDSA turns the curve arithmetic of Chapter 2.5 into a signature scheme. Fix a curve, a base point G on it, and the order n of G: n is how many distinct multiples G, 2G, 3G, … exist before the pattern returns to the point at infinity. Bitcoin uses the curve secp256k1, whose n is a 256-bit prime.

Q = d·G

d is the private key, an integer in [1, n−1]; Q is the public key, a point on the curve; G is the base point; · means repeated point addition.

  1. Hash the message with SHA-256 and take the leftmost n bits of the digest as an integer z.
  2. Pick a fresh random nonce k in [1, n−1]. It is secret and used once.
  3. Compute the point R = k·G and set r = R.x mod n, where R.x is its x-coordinate. If r = 0, restart.
  4. Compute s = k⁻¹(z + r·d) mod n. If s = 0, restart.
  5. The signature is the pair (r, s), two 256-bit numbers.

s = k⁻¹(z + r·d) mod n

k⁻¹ is the modular inverse of the nonce, so k·k⁻¹ ≡ 1; z is the truncated hash; r is the x-coordinate of R = kG reduced mod n; d is the private key; n is the order of G.

  1. Reject unless 1 ≤ r ≤ n−1 and 1 ≤ s ≤ n−1.
  2. Compute u₁ = z·s⁻¹ mod n and u₂ = r·s⁻¹ mod n.
  3. Compute the point P = u₁·G + u₂·Q.
  4. Accept if P.x mod n = r; otherwise reject.

Why it works. Put Q = dG: then P = (z + r·d)·s⁻¹·G. Because s = k⁻¹(z + rd), we get s⁻¹(z + rd) = k, so P = kG = R and the x-coordinates agree. The verifier never learns k or d.

P = u₁G + u₂Q = (z + r·d)s⁻¹G = kG

P is the point the verifier computes; u₁ = z·s⁻¹ mod n; u₂ = r·s⁻¹ mod n; the last equality holds because of how s was formed.

Nonce reuse, malleability and encoding

Reusing k destroys the key. Let the same k sign two messages with hashes z₁ and z₂, giving s₁ = k⁻¹(z₁ + rd) and s₂ = k⁻¹(z₂ + rd). Subtracting gives s₁ − s₂ = k⁻¹(z₁ − z₂), hence k = (z₁ − z₂)(s₁ − s₂)⁻¹ mod n, and then d = (s₁k − z₁)r⁻¹ mod n. Both signatures are public, so anyone can finish the calculation. A famous console firmware failure came from exactly this. A wallet either draws k from a strong random source or derives it deterministically from the message and d, as RFC 6979 does.

Malleability. Replacing s by n − s gives a second signature that also verifies: the verifier then computes −P instead of P, and a curve point and its negation share an x-coordinate. So the signature is not unique. Bitcoin's standard rule keeps only the low-s form, s ≤ n/2, and rejects the twin, which would otherwise let someone change a transaction id without changing the payment.

Encoding. The pair (r, s) is serialised with DER, an ASN.1 format that writes each number as a variable-length signed integer. Different encoders can emit different bytes for the same (r, s), so Bitcoin demands strict DER in addition to low-s.

Schnorr signatures are a newer alternative over the same curve. They are linear, so several keys and signatures can be added into one, and they rest on a cleaner security assumption. Bitcoin adopted them later; see Unit 4. One limit of any signature: it proves authorship, not secrecy. The message itself stays readable.

Worked example

Question. A toy ECDSA setup uses a curve of order n = 11 and a base point G of order 11. A signer has private key d = 3, chooses the nonce k = 7, and signs a message whose truncated hash is z = 5. The x-coordinate of R = kG reduces to r = 4. Find the signature (r, s), then verify it with Q = dG and state which multiple of G the verifier computes.

  1. Find k⁻¹ mod 11: 7 × 8 = 56 = 5×11 + 1, so k⁻¹ = 8.
  2. Compute z + r·d = 5 + 4×3 = 17 ≡ 6 (mod 11).
  3. Compute s = 8 × 6 = 48 ≡ 4 (mod 11). The signature is (r, s) = (4, 4).
  4. Verify: s⁻¹ mod 11 = 4⁻¹ = 3, since 4 × 3 = 12 ≡ 1.
  5. Compute u₁ = z·s⁻¹ = 5 × 3 = 15 ≡ 4 (mod 11) and u₂ = r·s⁻¹ = 4 × 3 = 12 ≡ 1 (mod 11).
  6. The public key is Q = dG = 3G, so the verifier's point is u₁G + u₂Q = 4G + 1×3G = 7G.
  7. That point is R itself, because u₁ + u₂d = 4 + 3 = 7 = k. Its x-coordinate is 4, which equals r, so the signature is accepted.

Answer. The signature is (r, s) = (4, 4); the verifier computes 4G + 3G = 7G = R, whose x-coordinate 4 matches r, so verification succeeds.

Exam traps

  • Reusing k. Two signatures with the same k give k = (z₁ − z₂)(s₁ − s₂)⁻¹ mod n and then d = (s₁k − z₁)r⁻¹ mod n, so the private key leaks.
  • Confusing r with the hash z. r is R.x mod n for R = kG; z is the truncated message hash. An answer that mixes them still looks like a formula, which is how examiners catch it.
  • Forgetting malleability. Both (r, s) and (r, n − s) verify, so quote Bitcoin's low-s rule s ≤ n/2 as the fix.
  • Calling a signature encryption. The message is not hidden; only authenticity and integrity are proved.
  • Signing the raw message instead of the hash, or forgetting that z is cut to the leftmost n bits of the digest.

2.7 Digital keys, addresses and identity

A blockchain identity is a key pair. The private key is a 256-bit secret; the public key is computed from it by elliptic-curve scalar multiplication. The address is a short encoded hash of the public key, not the key itself. This design gives a compact destination for payments and hides the public key until it is spent. Whoever controls the private key can sign, so control of the key is the identity. Bitcoin and Ethereum use this path with different hash and encoding steps.

You need: hash functions from Chapter 2.2, key pairs from Chapter 2.5, and signatures from Chapter 2.6.

The private key is the identity

On secp256k1, a private key is a 256-bit integer k. The public key is the curve point P = k × G. Here G is the fixed generator point of the curve, and × means repeated point addition, not ordinary multiplication. P is 33 or 65 bytes depending on encoding. The step from k to P is easy; the reverse is the discrete logarithm problem, which is infeasible.

Signing uses k; verification uses P. A signature proves that the signer knows k without revealing it. This is the link between identity and cryptography: the key pair is the account.

Creating an identity needs no server. Pick random k; derive P; hash P to an address. The network stores no names and no registration record. Control of k is the identity: lose k, lose funds; leak k, anyone can spend. There is no password reset.

Bitcoin: public key to Base58Check address

A Bitcoin address is not the public key. The public key is hashed first, then wrapped with a version byte and a checksum.

  1. Take the public key bytes: 65 bytes as 04 || x || y, or 33 bytes as 02 or 03 || x.
  2. Compute h = RIPEMD160(SHA256(pubkey)). h is 20 bytes. This value is called HASH160.
  3. Prepend version byte 0x00 for mainnet P2PKH. The payload is 21 bytes.
  4. Compute checksum c = first 4 bytes of SHA256(SHA256(version || h)).
  5. Form 25 bytes = version || h || c.
  6. Encode with Base58Check. A mainnet P2PKH address starts with 1.

HASH160 = RIPEMD160(SHA256(pubkey))

pubkey is the public-key byte string; HASH160 is 20 bytes (160 bits).

address_bytes = version || hash160 || checksum

version is 1 byte, hash160 is 20 bytes, and checksum is 4 bytes; total 25 bytes before Base58 text encoding.

Compressed keys, WIF and Ethereum

The compressed public key stores x and a parity bit for y. Recover y from the curve equation, choosing the even or odd value from the prefix. The same elliptic-curve point therefore gives a different byte string from the uncompressed form, so the hash and address differ. Wallet software must use one encoding consistently.

WIF, Wallet Import Format, encodes a private key with a version byte and checksum in Base58Check. WIF is a secret, not an address. HD wallets use BIP32 to derive child keys from one seed and BIP39 to turn words into that seed.

Ethereum hashes the 64-byte uncompressed public key x || y without the 04 prefix. The address is the last 20 bytes of Keccak-256 of those 64 bytes.

eth_address = last 20 bytes of Keccak-256(x || y)

x and y are 32-byte coordinates; Keccak-256 gives 32 bytes, and the last 20 bytes are written as 0x plus 40 hex characters.

Keccak-256 is not SHA-256. A wallet holds your keys; an exchange holds keys for you.

Worked example

Question. A compressed public key is 33 bytes. HASH160 gives 20 bytes. The version byte is 0x00. The checksum is the first 4 bytes of SHA256(SHA256(version || hash160)). How many bytes are Base58Check-encoded before conversion to Base58 text?

  1. The compressed public key is 33 bytes = 1 prefix byte + 32 bytes of x. It is hashed first and is not part of the Base58Check payload.
  2. HASH160 is RIPEMD-160 applied to the SHA-256 hash of the key, so its output is 160 bits = 20 bytes.
  3. The version byte is 1 byte, value 0x00 for mainnet P2PKH.
  4. The checksum is 4 bytes.
  5. The Base58Check input is version || hash160 || checksum = 1 + 20 + 4 = 25 bytes.

Answer. 25 bytes are Base58Check-encoded before the bytes are written as Base58 text.

Exam traps

  • An address is not the public key. Bitcoin P2PKH hashes the public key; Ethereum keeps 20 bytes of a Keccak-256 hash.
  • Do not drop the checksum. Mainnet P2PKH Base58Check encodes 25 bytes: 1 version + 20 hash160 + 4 checksum.
  • Do not mix compressed and uncompressed encodings. The same curve point gives a different public-key byte string, so a different address.
  • WIF is an encoded private key, not an address. Anyone who sees it can spend.
  • Ethereum uses Keccak-256 on the 64-byte x || y public key and keeps the last 20 bytes. It does not hash the address and does not use SHA-256.

Takeaways

  1. Cryptography supplies four separate tools — hashing, symmetric encryption, MACs and public-key operations — and each one answers a different security question.
  2. A cryptographic hash is a one-way, collision-resistant fingerprint of fixed length; SHA-256 always outputs 256 bits = 32 bytes.
  3. A hash pointer makes a block self-checking: change any old block and every later hash pointer fails, so tampering is visible from that point onward.
  4. A Merkle tree lets a 32-byte root in the block header stand in for thousands of transactions, and a proof of membership costs only log₂ n hashes.
  5. Public-key cryptography uses a trapdoor: multiplying the generator point by the private key is fast, dividing back is infeasible.
  6. Elliptic curves give the same security as RSA with far shorter keys, which is why a 256-bit Bitcoin key is enough.
  7. ECDSA proves the holder of a private key approved a specific message hash; the signature is (r, s) and is checked using only the public key.
  8. A blockchain identity is just a key pair; the address is a shortened hash of the public key, not the key itself, which adds a layer of protection.
  9. Reusing the ECDSA nonce k leaks the private key, so k must be fresh and unpredictable for every signature.

Exam question bank

Long answers here are marked on precise definitions plus worked steps: state the property, show the formula, and trace tamper detection or signature verification block by block, with numbers.

Remember and understand

Understand Explain the four security goals of cryptography — confidentiality, integrity, authentication and non-repudiation — and name the cryptographic tool that delivers each one. 13 marks

Define each goal in one line; Confidentiality → symmetric or public-key encryption; Integrity → hash function, MAC, digital signature; Authentication → MAC with shared key, or signature with private key; Non-repudiation → digital signature only, because a shared key can be denied by either party; Give one blockchain use of each.

Understand List the properties a cryptographic hash function must satisfy and describe how SHA-256 processes a message to produce a 256-bit digest. 13 marks

Preimage resistance, second-preimage resistance, collision resistance, avalanche effect; Fixed output length 256 bits = 32 bytes regardless of input size; Padding to a multiple of 512 bits with the length appended; Message schedule and 64 rounds over eight 32-bit working variables; Final addition of the initial hash values gives the digest; State why collision resistance matters for proof of work.

Understand What is a hash pointer? Explain how hash pointers link blocks into a chain and how they make the chain tamper-evident. 10 marks

Definition: address of previous block + hash of its contents; Difference from an ordinary pointer; Block header field prev_block hash; Editing block i changes its hash, so the pointer in block i+1 no longer matches; All later blocks must be re-mined; state the work involved; Genesis block has no previous pointer.

Understand Describe the construction of a Merkle tree for n transactions and explain how a Merkle proof is verified using the block header. 13 marks

Leaf = H(transaction), pairs combined as H(left ‖ right); Odd node is duplicated or promoted upward; Levels halve each step until one root remains; Root stored in the 80-byte block header; Proof = sibling hashes along the path, log₂ n of them; Verifier recomputes upward and compares with the header root; Use for SPV clients that do not download full blocks.

Understand Explain public-key cryptography using elliptic curves: key generation, the role of the generator point, and why the private key cannot be computed from the public key. 13 marks

Private key d = random integer in [1, n−1]; Public key Q = d × G, G is the standard generator on secp256k1; Curve equation y² = x³ + 7 (mod p) with stated p and n; Point addition and point doubling rules, geometric meaning; Scalar multiplication by double-and-add; Discrete log problem: given Q and G, finding d is infeasible; Key sizes: 256-bit ECC roughly equals 3072-bit RSA.

Understand Distinguish between symmetric encryption, message authentication codes, hash functions and digital signatures. Which of these does a blockchain use, and for what? 10 marks

Shared-key vs two-key tools in a table; Hash function: no key, integrity only, used for block linking and PoW; MAC: shared key, integrity plus authentication between two parties; Digital signature: private key signs, anyone verifies, gives non-repudiation, used for transactions; Symmetric encryption is rarely used on-chain; keys and wallets may encrypt locally; State that a MAC cannot settle a dispute because both parties hold the key.

Apply

Apply A block contains 4096 transactions. How many hashes does a Merkle proof for one transaction contain, and how many hashes would a node need without a Merkle tree? Show the working. 8 marks

4096 = 2¹², so tree height is 12; Proof = 12 × 32 bytes = 384 bytes; Without a tree the verifier needs all 4096 hashes = 131 072 bytes; Compare the two and state the saving ratio; Mention that the root is still 32 bytes in the header.

Apply Starting from a 256-bit private key, list the steps to derive a Bitcoin address and give the approximate length of the final address. 13 marks

Private key d → public key Q = d × G (33-byte compressed or 65-byte uncompressed); SHA-256 of the public key; RIPEMD-160 of that result gives the 20-byte hash160; Prepend version byte (0x00 for mainnet); Double SHA-256, take the first 4 bytes as checksum; Append checksum and encode in Base58; Result is about 26–35 characters beginning with 1.

Apply A transaction hash is the third leaf in an 8-leaf Merkle tree. Given the three sibling hashes supplied in the proof, show step by step how a light client checks that this transaction is in the block. 10 marks

Concatenate leaf with its sibling in the correct left/right order; Hash to get the parent; Repeat with the next sibling at the next level; After three rounds one hash remains; Compare it byte for byte with merkle_root in the header; Equal → membership proven; different → reject; Note what happens if the order left/right is swapped.

Apply Describe how a sender signs a transaction hash with ECDSA and how a node verifies the signature using the public key. Include the roles of r, s, k and the message hash z. 13 marks

Choose random nonce k, compute point R = k × G, set r = R.x mod n; s = k⁻¹(z + r·d) mod n; Signature is (r, s), published with the transaction; Verifier computes w = s⁻¹ mod n, u₁ = z·w, u₂ = r·w; Point P = u₁·G + u₂·Q; check P.x mod n equals r; Any change to the message changes z and the check fails; Note: k must never repeat — reuse leaks d.

Analyze and evaluate

Analyze Compare a simple hash chain of blocks with a Merkle-tree block structure for tamper detection and for light-client verification. Which is better and why? 13 marks

Hash chain detects any edit with a single hash comparison per block; Merkle tree adds per-transaction membership proofs of size log₂ n; A full block download is O(n); a Merkle proof is O(log n); Header alone (80 bytes) plus proof lets an SPV client verify a payment; Hash chain alone gives no per-transaction proof without the whole block; Conclusion: hash pointers give chain integrity, Merkle trees give scalable inclusion proofs; Mention the cost: tree construction and storage of intermediate hashes.

Evaluate An attacker modifies one transaction inside block 100 of a chain whose latest block is 106. Trace what breaks and evaluate how deep the attack must go to succeed. 13 marks

Transaction hash changes → Merkle root changes; Block 100 header hash changes; prev_block hash inside block 101 no longer matches; Every block from 101 to 106 must be recomputed; New proof of work needed for each of those blocks; Attacker must out-mine the honest network, and other nodes reject the longest-chain rule if outrun; Conclusion: cost grows with confirmation depth; six confirmations is a common practice.

Evaluate Bitcoin addresses are 20-byte hashes of the public key rather than the public key itself. Evaluate the security and size reasons for this choice. 10 marks

Size: 20 bytes vs 33/65 bytes in every output, saves block space; Extra hash layer means the public key is not revealed until spending; Attackers must break hash preimage and elliptic-curve discrete log; Hash160 also shortens and standardises identity; Risk: sending to a mistyped address, mitigated by Base58Check checksum; No identity is embedded — an address is pseudonymous, not anonymous.

Analyze Explain why ECDSA fails completely if the same nonce k is used for two different messages, and derive the private key in that case. 13 marks

Two signatures share r because r = (k × G).x mod n; s₁ = k⁻¹(z₁ + r·d), s₂ = k⁻¹(z₂ + r·d) mod n; Subtract: s₁ − s₂ = k⁻¹(z₁ − z₂) mod n; So k = (z₁ − z₂)(s₁ − s₂)⁻¹ mod n; Then d = (s₁·k − z₁)·r⁻¹ mod n; Conclude: the private key is exposed publicly and funds are lost; Rule: k must be random or derived deterministically (RFC 6979).

Glossary

Avalanche effect
A small change in input causing a large, unpredictable change in output bits.
Base58Check
An encoding that uses 58 safe characters and appends a 4-byte double-SHA-256 checksum so typos are caught.
Birthday attack
A search that finds a hash collision in about 2^(n/2) tries instead of 2^n.
Block header
The 80-byte summary of a block holding version, previous block hash, Merkle root, time, bits and nonce.
Checksum
A short derived value stored with data so that accidental errors can be detected on read.
Ciphertext
The unreadable output produced after encrypting plaintext.
Collision
Two different inputs x and y that produce the same hash H(x) = H(y).
Cryptography
The science of writing messages so that only the intended reader can read or verify them.
Digest
The fixed-size output of a hash function, also called the hash value.
Digital signature
A value attached to a message that proves the signer holds the private key and that the message is unchanged.
Discrete logarithm problem
The hard problem of recovering d from Q = d × G on an elliptic curve.
Elliptic curve
A curve of the form y² = x³ + ax + b over a finite field, on which a group of points is defined.
Generator point (G)
The fixed base point on the curve from which every public key is computed as d × G.
Genesis block
The first block of a chain, which has no previous block pointer.
Hash function
A function that maps an input of any size to an output of fixed size.
Hash pointer
A pointer that gives both the location of some data and the hash of that data, so the data can be checked.
Key
A secret or public value that controls an encryption, hash-based or signature operation.
Merkle tree
A binary tree of hashes that reduces many data items to a single root hash.
Plaintext
The original readable message before any cryptographic operation.
Public-key cryptography
A scheme with a public key for verifying or encrypting and a private key for signing or decrypting.
secp256k1
The specific elliptic curve Bitcoin uses, with equation y² = x³ + 7 over a 256-bit prime field.
SHA-256
The SHA-2 member that always produces a 256-bit (32-byte) digest; used twice in Bitcoin's block hashing.
Signature nonce (k)
The one-time random number used inside ECDSA; it must never repeat for two different messages.
SPV (simplified payment verification)
A light-client method that checks a transaction using block headers and Merkle proofs instead of full blocks.
Tamper-evident
A structure in which any change is detectable, even if the change cannot be prevented.
Wallet import format (WIF)
A Base58Check encoding of a single private key, used to move keys between wallets.
