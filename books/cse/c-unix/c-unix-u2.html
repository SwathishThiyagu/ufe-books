2.1 Linux file system structure and file types

Linux stores everything in one tree. The tree hangs from a single directory, /, called the root directory. Directories, ordinary files, devices and sockets all sit in that tree. There is no C: drive. One set of commands, one set of permissions and one way of naming things then work everywhere. When you run ls in your home directory, install a package, or read a log in /var/log after a service fails, you walk the same tree. This chapter maps the tree, explains paths, and names the seven file types that every directory entry belongs to.

You need: Unit 1, the kernel and user space split, and the basic command line (pwd, cd, ls).

One tree, fixed top-level directories

Every mounted disk joins the same tree. A USB stick does not become a new drive letter; it appears as a directory such as /media/ravi/stick. The top level is fixed by convention so that scripts and users find the same things on every machine.

  • /bin: user commands such as ls and cp.
  • /sbin: system administration commands, used at boot and by root.
  • /boot: the kernel image and boot loader files.
  • /dev: device files, one per disk, terminal and so on.
  • /etc: configuration files, almost always plain text.
  • /home: one directory per user, such as /home/ravi.
  • /lib: shared libraries and kernel modules.
  • /media and /mnt: mount points for removable disks and for temporary mounts.
  • /opt: add-on software installed outside the normal command packages.
  • /proc: kernel and process information, generated on demand.
  • /root: the home directory of the root user, not the root directory.
  • /srv: data served by this machine, such as web pages.
  • /tmp: temporary files; any user may write here.
  • /usr: programs, libraries and documentation; /usr/bin holds most commands on modern systems.
  • /var: files that change size, such as logs in /var/log, print spool and package caches.

Some syllabi call this layout the Filesystem Hierarchy Standard (FHS). Fixing the names matters: a shell script written on one machine still finds /etc/passwd and /var/log on the next.

Paths: absolute, relative, and how the kernel walks one

An absolute path starts at / and is complete, like /home/ravi/notes.txt. A relative path starts at the current working directory, which pwd prints. If you stand in /home/ravi, then notes.txt, lab/notes.txt and ../ravi are all relative paths.

  1. Start at / for an absolute path, or at the process's current directory for a relative one.
  2. Split the path at each / character into components.
  3. Look up the next component by name inside the current directory. This lookup needs execute (x) permission on that directory.
  4. A component of . means the directory itself; .. means its parent directory.
  5. If the component is a symbolic link, replace it with the link's target and continue. A counter stops after too many links, which kills loops.
  6. Open the final component. The kernel returns that file's inode number, and the path name is no longer used.

The kernel caps one path name passed to a system call at PATH_MAX, 4096 bytes including the terminating null byte, so about 4095 usable bytes. Deeper nesting is fine as long as the path string stays under the cap.

Seven file types

Every entry is one of seven types. The first character of an ls -l line gives the type; the next nine characters are permissions (see 2.4).

CharTypeExample
-regular filenotes.txt, a binary, a photo
ddirectory/home, lab
lsymbolic linklatest -> notes.txt
ccharacter device/dev/tty1, /dev/null
bblock device/dev/sda
pnamed pipe (FIFO)made by mkfifo, read by two processes
ssocketused for local inter-process talk

A directory entry maps a name to an inode number. The inode stores the type, owner, permissions, size, timestamps and the addresses of the data blocks; the name is not inside the inode. That is why two names can share one file, and the link count becomes 2 (see 2.3).

/proc and /sys are virtual file systems. They use no disk blocks. /proc/1234 describes the process with PID 1234, /proc/meminfo reports memory, and /sys/class/net lists network devices. Reading such a file runs kernel code and builds the text at that moment.

Worked example

Question. A listing of /home/ravi shows four lines: -rw-r--r-- 1 ravi students 2148 Jan 5 10:20 notes.txt drwxr-xr-x 2 ravi students 4096 Jan 5 09:00 lab lrwxrwxrwx 1 ravi students 9 Jan 4 18:02 latest -> notes.txt crw--w---- 1 root tty 4, 1 Jan 5 08:00 tty1 (a) Give the file type of each line. (b) Explain why the link counts are 1, 2, 1 and 1. (c) Say what 2148 counts. (d) Standing in /home/ravi/lab, give the absolute path reached by ../latest and the type of the final file after the link is followed.

  1. Line 1 begins with -, so notes.txt is a regular file. Line 2 begins with d, so lab is a directory. Line 3 begins with l, so latest is a symbolic link. Line 4 begins with c, so tty1 is a character device.
  2. notes.txt has one name, so its link count is 1.
  3. lab shows link count 2, so it has no subdirectories: the two links are the . entry inside lab and the name lab in /home/ravi. Each subdirectory would add one more.
  4. latest is a symbolic link with one name, so its link count is 1.
  5. tty1 has one name, so its link count is 1.
  6. 2148 is the size of notes.txt in bytes, that is 2148 bytes.
  7. The 9 on the link line is the length in bytes of the target string notes.txt, which has 9 characters.
  8. On the device line, 4 and 1 are the major and minor numbers, not a byte count. Major 4 selects the terminal driver; minor 1 selects one terminal.
  9. Start at /home/ravi/lab. The component .. moves to /home/ravi. Then latest is a symbolic link whose target is notes.txt; resolved against the link's own directory /home/ravi, it becomes /home/ravi/notes.txt.
  10. The final file /home/ravi/notes.txt has three name components, home, ravi and notes.txt. It is the regular file from line 1.

Answer. Types: regular, directory, symbolic link, character device. Link counts: 1, 2, 1, 1. Size 2148 bytes. The path is /home/ravi/notes.txt, the regular file from line 1, with three components.

Exam traps

  • The first character of an ls -l line is the file type, not a permission. A leading d or l does not mean 'no permission'.
  • On a device line the pair 4, 1 is major,minor. Students often read it as a size or as a date.
  • /root is the home directory of the root user. The root directory is / alone.
  • A symbolic link's size is the length of its target string, not the size of the target file, and its link count is 1.
  • /proc files often show size 0 yet return text when read, because they are generated on demand.

2.2 Listing and viewing files: ls, cat, more, less

ls lists what exists; cat, more and less show what is inside. Every Linux user runs these commands daily to find a file, check a config, read a log, or print a page. The shell and these tools split one job: ls works on names in a directory, while the viewers work on bytes inside one file. Some syllabi call this 'listing files' and 'displaying files'. The skill is choosing the right viewer for the file size, so a 5 MiB (5,242,880 bytes) log does not flood your terminal.

You need: the one-tree view and file types from Chapter 2.1.

ls: names in a directory

An entry is one name in a directory. ls prints entries. With no argument it lists the current directory. With a path it lists that path. A plain file name prints itself.

Options change the output. -l gives a long listing. -a includes hidden names, and also the two special entries . (current directory) and .. (parent directory). -h prints sizes as K, M, G using powers of 1024. -R lists subdirectories too. -t sorts by modification time, newest first; -r reverses the order. -i prints the inode number. -d lists the directory itself, not its contents. -F adds a slash to directories and a star to executables.

A long listing has seven fields: type and permissions, hard links, owner, group, size in bytes, date and time, name. The first character is - for a regular file, d for a directory, l for a link. The next nine characters are permissions, covered in Chapter 2.4.

The shell expands wildcards before ls runs. Typing ls *.c makes Bash replace *.c with the matching names. ls never sees the star. If nothing matches, Bash passes the pattern unchanged by default. That is why an error about a missing file named *.c can appear.

cat: the whole file at once

cat is short for concatenate. cat notes.txt copies every byte of the file to standard output. Standard output is the terminal by default. cat has no pager, so it never pauses. For a small file this is perfect: you see all lines, then your prompt returns.

cat -n notes.txt adds line numbers. cat -A notes.txt shows non-printing characters: tabs appear as ^I and line ends as $. This helps find trailing spaces. cat -s notes.txt squeezes many blank lines into one. Options combine: cat -ns notes.txt numbers lines and squeezes blanks.

On a 5 MiB log, cat big.log floods the terminal. Thousands of lines scroll past. You cannot scroll back reliably in a plain terminal, and the shell waits while it writes. Use less for large files. Relatives: tac reverses line order, head shows the first lines, and tail shows the last lines.

more, less and printing

more and less are pagers. A pager shows one screen and waits for a key. more notes.txt moves mostly forward. Space shows the next screen. b may go back one screen in some versions. q quits.

less big.log is the stronger pager. Space moves forward, b moves back, G jumps to the last line, and g goes to the first. Type /ERROR and press Enter to search forward. Type ?ERROR and press Enter to search backward. Press n for the next match and N for the previous match. q quits.

less does not load the whole file into memory. It reads what it needs as you move. That is why it opens a huge log quickly. more is smaller but weaker; on a few systems more is a link to less, but on most distributions more is a separate, simpler program with fewer keys.

To print, lpr notes.txt sends the file to the default printer. lpq shows the print queue. Printing is different from viewing: the file leaves your terminal and waits in a queue.

Worked example

Question. /home/ravi/lab holds notes.txt (2148 bytes), big.log (5,242,880 bytes), the hidden file .profile, and one subdirectory reports that holds two files. (a) Write the command that lists every entry, hidden ones included, with sizes in human units. How many lines does it print? (b) Write the command that lists the entry reports itself, not its contents. (c) Show notes.txt with line numbers. (d) Page through big.log, jump to the last line, then search backwards for ERROR. (e) What size does ls -lh print for big.log?

  1. (a) Use ls -lah. -a includes .profile, . and ..; -l gives long form; -h uses human sizes. Entries: ., .., .profile, big.log, notes.txt, reports = 6 entries. GNU ls also prints one total line, so GNU ls shows 7 lines; ls versions without a total line show 6.
  2. (b) ls -ld reports. -d stops ls from opening the directory. Output is one line starting with d.
  3. (c) cat -n notes.txt. It prints each line with a line number.
  4. (d) less big.log. Press G to go to the last line. Type ?ERROR and press Enter to search backwards. Press n for the next match in the same direction. Press q to quit.
  5. (e) ls -lh big.log. 5,242,880 ÷ 1024 = 5120 KiB. 5120 ÷ 1024 = 5 MiB. The size field prints 5.0M.

Answer. notes.txt is 2148 bytes; big.log is 5,242,880 bytes, shown as 5.0M; GNU ls -lah prints 7 lines (6 entries plus a total line), ls versions without a total line print 6, and reports holds 2 files.

Exam traps

  • ls -l on a directory prints the directory's contents, never the directory's own details; use -d for the entry itself.
  • -h divides by 1024, so 5,242,880 bytes prints as 5.0M, not 5.2M.
  • -a includes . and ..; -A includes hidden names but leaves out those two entries.
  • The shell expands *.c before ls runs. ls receives names, not the pattern.
  • cat -A changes only what you see on screen; it does not change the file.

2.3 File and directory operations: cp, mv, rm, ln, find

Every file you see is a name in a directory. The name points to an inode, a numbered record that holds the file's metadata and data locations. cp, mv, rm and ln change names or inodes, so knowing which one changes decides what survives. find searches the tree by inode properties such as type, size, time and permission. These commands run daily on servers and phones: copying a project, moving a download, deleting logs, linking a config, finding old files.

You need: Chapter 2.1 for the single tree and file types, and Chapter 2.2 for ls -l and viewing files.

Names, inodes and directories

A directory is a file whose data is a table of entries. Each entry is a name plus an inode number. The inode is a numbered record that holds the file type, permissions, owner, size, times, link count and data block pointers; the name is not in the inode. A file system is one mounted tree with its own set of inode numbers. The link count is the number of directory entries that point to an inode. Removing one name lowers the count; the data blocks are freed only when the count reaches 0.

  • mkdir -p /home/ravi/work/logs creates any missing parent directories and does not fail if the path already exists.
  • rmdir work/logs removes an empty directory only.
  • cd work changes the current directory of the shell; pwd prints the absolute path of that directory.
  • touch notes.txt creates an empty file if it does not exist, or updates its access and modification times if it does.

Copy, move and remove

cp notes.txt backup.txt reads the source inode and writes a new inode with copied data. The two files are independent after the copy. cp -r dir1 dir2 copies a directory tree. cp -p preserves mode, ownership where permitted, and timestamps. cp -i asks before overwriting. cp -u copies only when the source is newer than the destination or the destination is missing. cp -d copies a symbolic link as a link, not as the file it points to.

mv old new inside one file system changes a directory entry: the inode number and data stay the same. Across file systems, mv must copy the data to a new inode and then remove the old name, so the inode number changes. If the destination is a directory, the file keeps its name inside that directory. Use mv -i before an overwrite you did not plan.

rm notes.txt removes one directory entry and lowers the inode link count by 1. The data survives while any other name points to that inode. rm -r dir removes a directory and its contents. rm -i asks for each file; rm -f never prompts and ignores missing names. rm -rf is fast and has no undo and no recycle bin; a wrong space or wildcard can delete a tree. Check the target with ls or find ... -print first.

Hard links, symbolic links and find

ln notes.txt hard.txt makes a hard link: a second directory entry for the same inode. The link count rises by 1. Both names read and write the same data, and the data remains until the count reaches 0. A hard link cannot cross a file system because the directory entry stores an inode number, and inode numbers are local to one file system. Most systems also forbid hard links to directories, to keep the tree acyclic.

ln -s notes.txt soft.txt makes a symbolic link. ln -s creates a new inode of type link; its data is the text of the target path. The target's link count does not change. If the target is removed, the link remains and is dangling: cat soft.txt gives “No such file or directory”. A relative target is resolved from the directory that holds the link. A symbolic link may cross file systems and may point to a directory.

find /home/ravi -type f -size +1M -mtime -7 -print searches the tree. -name '*.log' matches a name, -type f picks regular files, -size +1M is larger than 1 MB, -mtime -7 is modified in the last 7 days, -perm 644 matches permission bits, -exec cmd {} \; runs a command on each match, and -delete removes matches. Test with -print before -delete. To archive before deleting, tar -cvf backup.tar dir/ stores names and data in one file.

Worked example

Question. /home/ravi and /home/ravi/work are on the same file system. notes.txt in /home/ravi has inode 1042 and 300 bytes. Step 1: ln notes.txt hard.txt. Step 2: ln -s notes.txt soft.txt. Step 3: rm notes.txt. (a) Give the link count of inode 1042 after each step. (b) What does cat hard.txt print after step 3, and why? (c) What does cat soft.txt print after step 3? (d) Write a find command that lists regular files under /home/ravi larger than 1 MB and modified in the last 7 days. (e) Then run mv hard.txt work/. Does the inode number change?

  1. Before step 1, notes.txt is one directory entry for inode 1042, so the link count is 1.
  2. After step 1, hard.txt is a second entry for inode 1042. The link count becomes 1 + 1 = 2.
  3. Step 2 creates soft.txt as a symbolic link on a new inode, 2011. Its stored data is the path text notes.txt. Inode 1042 is not linked again, so its link count stays 2.
  4. Step 3 removes the entry notes.txt and lowers the link count of inode 1042 by 1: 2 - 1 = 1. hard.txt still points to inode 1042.
  5. (a) The link counts after steps 1, 2 and 3 are 2, 2 and 1.
  6. (b) cat hard.txt prints the 300 bytes of file data. hard.txt is still a name for inode 1042, and the data is freed only at link count 0.
  7. (c) cat soft.txt fails with “No such file or directory”. The link stores the text notes.txt, and that name no longer exists, so the link is dangling.
  8. (d) find /home/ravi -type f -size +1M -mtime -7 -print lists regular files larger than 1 MB modified in the last 7 days.
  9. (e) mv hard.txt work/ stays inside one file system, so it only changes the directory entry. The inode number stays 1042 and the link count stays 1.

Answer. The link counts after steps 1, 2 and 3 are 2, 2 and 1; hard.txt still prints the data, soft.txt is dangling, and the same-file-system mv leaves the inode number unchanged.

Exam traps

  • rm does not always free data; it removes one name. Data remains if another hard link exists, so check the link count.
  • rm -rf has no undo and no recycle bin; a space in the wrong place removes a different tree. Test with ls or find -print first.
  • A symbolic link can be dangling and still exist; a hard link cannot cross a file system because inode numbers are local to one file system.
  • mv across file systems copies and deletes, so the inode changes; mv inside one file system only renames the entry, so the inode stays.
  • find -delete acts as soon as it matches; -print is not just decoration. Run the same find with -print first.

2.4 File permissions and chmod

Every file and directory on a Linux machine carries a permission mode, and that mode is written as ten characters in a long listing or as three or four octal digits on a command line. The mode answers one question: what may the owner, the group and everyone else do with this entry? It exists because Linux is multi-user, so one login must not silently rewrite another person's files. You use it every time you run chmod, every time umask decides the mode of a new file, and every time you wonder why a script will not run or a shared folder in /tmp is safe.

You need: the long listing from chapter 2.2 and some test files and directories from chapter 2.3.

Ten characters, three triads

In a long listing the first field is ten characters. Character 1 is the file type: - regular file, d directory, l symbolic link (see chapter 2.1). The other nine are three triads: owner (also called user), group, other. Other means everyone else on the machine. Inside a triad the order is always r, w, x. A letter allows the action, a dash refuses it. So -rwxr-xr-- reads as owner rwx, group r-x, other r--.

What r, w and x mean depends on whether the entry is a file or a directory.

LetterOn a regular fileOn a directory
rread the contents (cat, less)list the names inside (ls)
wchange the contents (edit, append)create, delete, rename entries
xrun it as a programenter it and traverse it

On a directory, x is the right to traverse. To open /home/ravi/lab/report.txt the kernel walks /, /home, /home/ravi and lab, and each of those needs x for you. A directory with r but no x lists names, yet nothing inside can be opened. The x on a directory is not about running anything.

chmod in octal and in symbolic form

Each permission letter has a value: r = 4, w = 2, x = 1. Add the values inside one triad and you get a single octal digit 0 to 7. Three digits, one per triad, describe the whole mode.

chmod 754 notes.txt gives owner 4+2+1 = 7 (rwx), group 4+0+1 = 5 (r-x), other 4+0+0 = 4 (r--). The listing becomes -rwxr-xr--.

The symbolic form is chmod who op perms file. who is u (owner), g (group), o (other) or a (all three). op is + (add), - (remove) or = (set exactly). perms is any mix of r, w, x. Clauses are separated by commas.

  • chmod u+x,g+x,o-r notes.txt turns 644 into 750, the same as the octal command.
  • chmod go-w report.txt removes write from group and other.
  • chmod u=rwx,go=rx notes.txt sets 755 and clears anything not listed.
  • chmod -R 750 lab applies the mode to every entry below lab.

If you leave out who, the command is treated as a, but bits set in your umask are not touched, so chmod +x f can give 755 rather than 777.

umask decides the default mode

New entries do not start at 777. The kernel starts from a base mode: 666 for a regular file (x is left out so that touch never hands you a runnable program) and 777 for a directory (without x you could not enter it). The umask holds the bits to remove, so 666 & ~umask and 777 & ~umask give the mode that is actually created.

umask with no argument prints the current value; umask 027 sets a new one for this shell and its children. With umask 022 a new file is 666 & ~022 = 644 (-rw-r--r--) and a new directory is 777 & ~022 = 755 (drwxr-xr-x).

Digit-wise subtraction from the base gives the same answer whenever each umask digit's bits fit inside the base digit, but writing it as 666 & ~umask is always correct.

The three special bits

A fourth octal digit sits in front of the nine and carries three special bits. Only a few syllabi teach these in this unit, so know what each one does and how it looks.

  • SUID (4): the program runs with the file owner's user id. /usr/bin/passwd needs it so an ordinary user can write /etc/shadow. The owner x slot shows s, or S when x is off.
  • SGID (2): the same idea for the group id on a program. On a directory it makes new files inherit the directory's group, which is how shared project folders work.
  • Sticky (1): on a directory, only the file's owner, the directory's owner or root may delete or rename an entry. /tmp is drwxrwxrwt, so everyone may write there and nobody may delete your file. The last slot shows t when x is also on, and T when the sticky bit is set but x is off.

chmod 1777 /tmp sets the sticky bit with open permissions.

Worked example

Question. notes.txt shows -rw-r--r-- and is owned by ravi. (a) Give two commands, one octal and one symbolic, that change it to rwxr-x---. (b) With umask set to 022, what mode does touch a.txt give a new file, and what mode does mkdir d give a new directory? (c) A user with umask 022 wants new files to come out as 640 instead of 644. What must the umask be? (d) The directory lab is drwxr-x--- and the file lab/report.txt inside it is -rw-r--r--. priya is not ravi and is not in ravi's group. Can she read report.txt?

  1. (a) The current mode is 644. The target rwxr-x--- is 7, 5, 0, so the octal command is chmod 750 notes.txt.
  2. Symbolic: owner 6 to 7 needs +x, group 4 to 5 needs +x, other 4 to 0 needs -r. Command: chmod u+x,g+x,o-r notes.txt.
  3. (b) File base is 666, so 666 & ~022 = 644, that is -rw-r--r--. It has no x, because files never get x by default.
  4. Directory base is 777, so 777 & ~022 = 755, that is drwxr-xr-x.
  5. (c) Wanted 640 from base 666. Owner stays 6 (umask bit 0). Group 6 to 4 removes w, so umask digit 2. Other 6 to 0 removes r and w, so umask digit 4+2 = 6. The umask must be 026.
  6. (d) For priya, both entries are checked in the other triad. lab is drwxr-x---, so other has ---, with no x. Without x she cannot traverse lab, so opening lab/report.txt fails with Permission denied.
  7. The read bit on report.txt is never reached, because the kernel stops at the directory lookup.

Answer. (a) chmod 750 notes.txt or chmod u+x,g+x,o-r notes.txt; (b) new file 644, new directory 755; (c) umask 026; (d) no, she cannot read it because lab gives other no x.

Exam traps

  • Other bits on a file are useless if a parent directory gives other no x. The kernel cannot reach the file to check its mode, and open fails with Permission denied.
  • The base mode for a file is 666, not 777. Subtracting the umask from 777 for a file gives a wrong answer, usually one with a phantom x.
  • A directory with mode 644 is broken for everyone, the owner included: there is no x in any triad, so nobody can enter it or create files inside it. The owner can only list the names (r), because w on a directory is useless without x.
  • With symbolic chmod, leaving out who makes the change respect your umask, so chmod +x f is not the same as chmod a+x f.
  • SUID is the lower-case s in the owner x slot. The upper-case S means the setuid bit is set but x is off, so the program cannot run and the bit does nothing.

Check yourself

drwxr-x---

Remember Give the octal value of r, w and x, and the mode string produced by chmod 640. 2 marks

r = 4, w = 2, x = 1. chmod 640 gives -rw-r-----.

Understand Why does x on a directory control access to the files inside it, even when those files are world-readable? 3 marks

To open a file the kernel must resolve each path component in turn. Entering a directory component requires x on it. Without x the lookup stops there and the file's own mode is never examined, so open returns Permission denied.

Apply A file is -rw-r--r--. Give two different commands that make it -rw-r-----, one octal and one symbolic. 3 marks

chmod 640 file, or chmod o-r file. Both remove only the read bit from the other triad.

Apply A shell has umask 027. What mode does touch f create, and what mode does mkdir d create? Give both in octal. 3 marks

File: 666 & ~027 = 640 (-rw-r-----). Directory: 777 & ~027 = 750 (drwxr-x---).

Analyze /tmp is drwxrwxrwt. Explain what each part of that mode allows and why the last bit is needed. 4 marks

Everyone may list, create and traverse, so any program can use /tmp as scratch space. The t is the sticky bit: inside a directory with write and traverse for all, deletion is restricted to the owner of the file, the owner of the directory or root. Without it any user could delete another user's temporary file.

Analyze With umask 022, chmod +x script.sh gives 755 while chmod a+x script.sh gives 777 on a file that was 644. Explain the difference. 4 marks

When who is omitted, the change is treated as a but bits set in the umask are protected. umask 022 protects group w and other w, so those stay off and only x is added to all three triads, giving 755. Naming a explicitly ignores the umask and adds x to all three triads of 644, giving 777.

Beyond the syllabus

Not for the exam. Real systems rarely stop at nine bits; POSIX ACLs add per-user and per-group entries through setfacl and getfacl, and that is where chapter 2.5 leads. Modern desktops and servers also carry mandatory access control modules such as SELinux and AppArmor, which decide access from a policy rather than from the mode. Linux capabilities split root's power into named rights such as CAP_NET_BIND_SERVICE, so a program no longer needs to be setuid root. Containers reuse all of this: image layers store modes, and a careless chmod 777 in a Dockerfile is a common review comment. Search next for setfacl, getfacl, capabilities(7), and the find -perm option for auditing loose modes.

2.5 File ownership, users and groups

A Linux file carries two owners: one user and one group. The kernel stores them as numbers, a uid and a gid, and compares them with the numbers of the process asking for access. This matters on every shared machine: a lab server, a web root, a database directory. The rule is simple but strict. Root is checked first. Then the file's owner bits, then its group bits, then the other bits. The first match decides, and later triplets are never consulted. This chapter shows how those numbers are set and how to change them.

You need: the permission bits and chmod from Chapter 2.4.

Users are numbers, not names

Every file has two owners: one user and one group. The kernel stores numbers, not names. A user identifier (uid) is the number of one account. A group identifier (gid) is the number of one group. The superuser, root, has uid 0. Any account given uid 0 is also the superuser, so the kernel can test for root with one comparison of the number.

/etc/passwd lists local accounts with seven colon-separated fields. Field 1 is the login name, field 3 the uid, field 4 the primary gid, field 6 the home directory, field 7 the login shell. Field 2 is usually x because the password hash is in /etc/shadow. Field 5 is a description.

/etc/group lists groups. Field 1 is the group name, field 3 the gid, field 4 a comma-separated list of supplementary members. A user has exactly one primary group from /etc/passwd and may have many supplementary groups. A new file takes your primary group, unless the directory has the setgid bit; then it takes the directory's group. Lab sharing usually means making a group, adding people, and giving that group read or write permission. See Chapter 2.4 for the bits.

Changing the owner and the group

whoami prints your login name. id prints your uid, primary gid and all groups. groups prints group names only. Sample id output: uid=1001(ravi) gid=1001(ravi) groups=1001(ravi),1002(students). Read it as: uid 1001, primary group ravi with gid 1001, supplementary group students with gid 1002.

newgrp students starts a new shell whose primary group is students. It does not add you to the group; it chooses among groups you already have. Exit the shell to return.

chown changes the owner. chgrp changes the group. Only root can change the owner. The owner may change the group to a group the owner belongs to. Forms: chown user file, chgrp group file, chown user:group file. Add -R to recurse into a directory. Recurse with care: chown -R ravi /home/ravi/project changes every file and directory below project. A wrong path can change the whole system. Check with ls -l before and after.

The check stops at the first match

The kernel checks in a fixed order. First, if the process's effective uid is 0, read and write are allowed; execute still needs at least one execute bit. Second, if the effective uid equals the file's uid, only the owner triplet applies. Third, if the file's gid is in the process's group list, only the group triplet applies. Fourth, the other triplet applies. The first match decides; later triplets are never read. A user who owns a file never falls through to the group or other bits. If owner bits are r-- and group bits are rw-, the owner cannot write even when also in the file's group.

In the worked example, Priya is not the owner but is in students, so group bits decide. Arjun is neither owner nor in students, so other bits decide. Root is not decided by the owner bits; root skips the check.

Access control lists (ACLs) add per-user entries to the three triplets. Only a few syllabi teach this, so keep the idea: setfacl -m u:arjun:r report.txt grants read to arjun alone. getfacl report.txt shows the entries. The owner and group stay unchanged. Adding an entry recalculates the mask, shown in place of the group bits in ls -l. Here the mask is r--, so students keep read; if the mask were smaller, group access would shrink. A plus sign after the mode in ls -l marks a file with an ACL.

Worked example

Question. The file /home/ravi/project/report.txt is owned by ravi, group students, mode 640. The users are: ravi (uid 1001, primary group ravi, also in students), priya (uid 1002, groups priya and students), arjun (uid 1003, group arjun). (a) For priya and arjun, say read, write, execute allowed or denied, and which triplet decided it. (b) root runs cat report.txt. Allowed? Why? (c) Write the command, run by root, that changes the file's group to arjun. (d) After (c), who can read it: priya or arjun? What did the students get and lose? (e) Give a better way to let arjun read it without moving the group.

  1. Mode 640 in octal means owner 6 = rw-, group 4 = r--, other 0 = ---.
  2. Priya has uid 1002, which is not the owner uid 1001. Priya is in students, the file's group, so the group triplet r-- decides. Read allowed, write denied, execute denied.
  3. Arjun has uid 1003, not the owner, and is not in students. The other triplet --- decides. Read denied, write denied, execute denied.
  4. root has effective uid 0. The root rule allows the read before any triplet is read. cat succeeds, but not because of the owner bits.
  5. As root: chgrp arjun /home/ravi/project/report.txt. The owner ravi can not do this himself, because he is not a member of arjun.
  6. After the change the file's group is arjun and the mode is still 640. Priya is not in arjun, so other bits --- decide: read denied. Arjun is in arjun, so group bits r-- decide: read allowed. The students are no longer the file's group, so they lose the read access they had; they gain nothing.
  7. Better: setfacl -m u:arjun:r /home/ravi/project/report.txt. The group stays students, so priya and the other students keep read, and arjun gets read from the ACL entry. Adding the entry sets the ACL mask to r--, shown in place of the group bits; a smaller mask would shrink group access.

Answer. Priya read=1, write=0, execute=0 by the group triplet; Arjun read=0, write=0, execute=0 by the other triplet; root is allowed by the root rule; after chgrp arjun, Priya read=0, Arjun read=1, and another student read=0; keep the group and run setfacl -m u:arjun:r /home/ravi/project/report.txt.

Exam traps

  • Do not read the other bits for a user who is in the file's group. One user is matched by exactly one triplet.
  • Root bypasses file permission checks; it is not allowed by the owner bits. Root still needs an execute bit to run a program.
  • chgrp changes the group only. It does not change the owner, and it does not add users to the new group.
  • The owner of a file cannot give it away with chown; only root can change the uid.
  • A user's primary group and supplementary groups are different. id shows both, and newgrp changes only the primary group in a new shell.

Beyond the syllabus

Not for the exam. Production systems use POSIX ACLs, NFSv4 ACLs and container user namespaces, where a container's root is mapped to an ordinary host uid. The mapping is the security boundary: a file owned by uid 0 inside a container may be owned by uid 100000 on the host. Search for setfacl, getfacl, NFS uid mapping and user namespaces to go further.

Takeaways

  1. All of Linux is one tree under /, and devices, pipes and sockets sit in that tree as files, so the same open, read and write calls work on them.
  2. A name is not the file: the directory entry points to an inode, and the inode holds everything the kernel needs except the name.
  3. cat is for short files, less is for long files because it reads lazily and pages both ways, more is the older forward-only pager.
  4. cp creates new data, mv usually only rewrites a name, and rm deletes a name — which is why a hard link keeps data alive after the original name is gone.
  5. The ten characters of ls -l are one type character plus three triples; the same information fits in three octal digits.
  6. umask decides the mode of every new file and directory, so a wrong umask breaks group work silently.
  7. The kernel checks root first, then owner, then group, then other, and stops at the first match, so a group permission never rescues the owner.
  8. Root bypasses permission checks on ordinary files, which is convenient for repair and dangerous for accidents.

Glossary

absolute path
A path that starts at / and names a location from the root of the tree.
current working directory
The directory a process resolves relative paths against, printed by pwd and changed by cd.
dangling link
A symbolic link whose target path no longer exists.
device node
A file in /dev that represents a piece of hardware, block or character, identified by major and minor numbers.
effective uid
The user id the kernel actually uses for permission checks, normally the same as the real uid.
FIFO
A named pipe, a file type that carries a byte stream between processes and shows as p in ls -l.
hard link
A second directory entry for an existing inode, created with ln and confined to one filesystem.
inode number
The identifier of an inode inside one filesystem, shown by ls -i and used by tools such as find -inum.
link count
The number of directory entries that point at one inode; the data is freed when it falls to zero.
mode bits
The nine permission bits plus the special setuid, setgid and sticky bits stored in the inode.
pager
A program such as less or more that shows output one screen at a time and waits for a key press.
pseudo-filesystem
A filesystem with no disk storage that presents kernel data as files, such as /proc and /sys.
relative path
A path interpreted from the current working directory rather than from /.
root (superuser)
The account with uid 0, which bypasses ordinary permission checks.
setgid bit
On a program it runs with the file's group; on a directory it makes new files inherit that directory's group.
setuid bit
A mode bit that makes a program run with the file owner's effective uid, used by tools such as passwd.
socket file
A file type used as an endpoint for local interprocess communication, shown as s in ls -l.
standard output
The default stream, file descriptor 1, that a command writes to, usually the terminal.
sticky bit
On a shared directory it stops users from deleting files they do not own, as in /tmp.
supplementary groups
Extra groups a user belongs to beyond the primary group; all of them count in the group check.
symbolic link
A file whose data is a path to another file, created with ln -s, allowed across filesystems.
umask
The process attribute whose set bits are cleared from the default creation mode of new files and directories.
wildcard expansion
The shell's replacement of patterns such as *.c with matching names before the command runs.
