5.1 Kernel data structures: task structure and process table

Every process and every kernel thread in Linux is represented by one C structure, task_struct. The kernel cannot use the process's own memory to describe the process, so this record lives in kernel memory. Because thousands of tasks may exist, the kernel also keeps indexes: a doubly linked list of all tasks, a hash table keyed by PID (in classic kernels), and a parent-child tree. Together these are loosely called the process table. The same mechanism lets ps list processes, lets the scheduler pick the next task, and lets a parent collect a child's exit status.

You need: Unit 1 (kernel, shell and user space) and Unit 4 (viewing and controlling processes).

One record per task

Linux describes every schedulable entity with one C structure, task_struct. A user process, a thread and a kernel thread all have one. Some syllabi call this the process descriptor or the process control block (PCB). It lives in kernel memory, never in the process's own address space, because the kernel must be able to describe a process whose user memory is unmapped, swapped or damaged.

The structure is large: identity, state, memory pointers, open files, signal state, credentials, scheduling data and links to other tasks. It is allocated from a dedicated slab cache, so creating and destroying tasks reuses memory instead of calling the page allocator every time. The kernel stack is a separate small region used while the task executes a system call or interrupt in kernel mode.

The process table: list, hash and tree

Linux does not keep the process table as an array indexed by PID. It keeps three indexes over tasks: a global list of task_struct objects, a PID lookup of struct pid entries (a hash table in classic kernels; since Linux 4.15 an IDR radix tree), and a parent-child tree of task_struct objects.

  • Global task list: a circular doubly linked list through every task's tasks field. Walking it visits every process; ps and the OOM killer use this kind of sweep.
  • PID hash table (classic kernels, before 4.15): the numeric PID is hashed to a bucket chain of struct pid entries. A struct pid is a small kernel record that names one PID number for a task in a namespace and points to its task_struct. Lookup computes the bucket and walks that chain; average lookup is O(1). The real hash was hash_long, not a plain remainder; the examples here use PID mod B as the simple model. Since Linux 4.15 the PIDs live in an IDR radix tree instead.
  • Parent-child tree: children and sibling links let the kernel find a parent's children and a child's siblings. PID 1, init, is the ancestor of normal user-space processes; kernel threads have no user parent.

bucket = PID mod B

PID is the process id; B is the number of hash buckets; mod gives the remainder. In the example PID 1201 and B = 512 give bucket 177.

Where the structures live

task_struct comes from a slab cache. Slab keeps preallocated objects of one size, so a fork does not search for free pages. Small kernel pieces such as a path buffer use kmalloc, which returns physically contiguous memory. Large areas use vmalloc, which returns virtually contiguous memory that may be scattered in physical RAM.

None of this memory is swapped: the kernel has no user address space to fault back to and no disk backing for its own structures, so kernel pages stay resident. The kernel stack is also resident and small, often 8 KB or 16 KB. Deep recursion or a large local array in kernel code can overflow it.

Worked example

Question. A classic PID hash table, modelled as bucket = PID mod B, has 512 buckets. (a) Which bucket holds PID 1201? (b) The task in that bucket has state TASK_RUNNING, with mm and files pointers set. What changes when the process calls exit() and the parent has not yet waited?

  1. Write the bucket rule: bucket = PID mod B.
  2. Substitute PID = 1201 and B = 512: 1201 mod 512.
  3. 512 × 2 = 1024, and 1201 − 1024 = 177, so bucket = 177.
  4. (b) exit() changes state to TASK_ZOMBIE and stores the exit code.
  5. The kernel detaches mm and frees the address space, closes the files table, releases the fs, namespace, semaphore and shared-memory resources, but keeps task_struct, the PID slot, the exit status, the credentials and the signal state until the parent calls wait() and the task is finally released.

Answer. PID 1201 hashes to bucket 177; on exit without a wait, the task becomes TASK_ZOMBIE and keeps its task_struct, PID slot, exit status, credentials and signal state until reaped.

Exam traps

  • The process table is not an array indexed by PID. It is a global task list plus a PID lookup (a hash table in classic kernels, a radix tree since 4.15) plus a parent-child tree.
  • User data does not live on the kernel stack. The kernel stack holds kernel frames, saved registers and return addresses while the task runs in kernel mode.
  • TASK_RUNNING means runnable, not necessarily using a CPU. A runnable task may be waiting in the run queue.
  • Threads share a tgid but have different pids. A single-threaded process has tgid equal to pid.
  • A zombie has already freed its address space but still owns its task_struct and PID until the parent calls wait().

5.2 Kernel mechanisms: signals, interrupts and timers

An asynchronous event can arrive at any instruction. Hardware reports it to the kernel as an interrupt; a process receives it as a signal. A periodic timer tick gives the kernel a heartbeat for timekeeping, timeouts and scheduling. These three mechanisms let Linux react to devices, stop runaway programs, and keep time without busy-waiting. The path runs from a device IRQ or a kill command to the code that runs, and the boundary between kernel mode and user mode decides what that code may do.

You need: task_struct and process states from 5.1, and the shell's kill command from Unit 4.

Signals: asynchronous notices

A signal is a small integer sent to a process by the kernel or another process. It reports an event. Standard signals carry no data; a signal sent with sigqueue() (or a real-time signal) can carry a small value. Common signals: 1 SIGHUP (terminal closed), 2 SIGINT (Ctrl-C), 9 SIGKILL (forced kill), 15 SIGTERM (polite terminate). Each task_struct has a pending mask and a blocked mask. A blocked signal stays pending until the process unblocks it.

Default actions are: terminate, ignore, dump core, or stop. A process can install a handler with signal() or sigaction(). sigaction() is preferred because its behaviour is reliable and portable; old signal() semantics differ between systems. The handler is ordinary user code. It runs in user mode, on the process stack, not in kernel mode.

The kernel delivers a signal on the return path from kernel to user mode. It takes pending & ~blocked, clears that bit, and arranges the CPU to start the handler. If several are pending, Linux delivers the lowest-numbered signal first, so signal 9 is handled before signal 15. When the handler returns, a small trampoline calls sigreturn to restore the old context. SIGKILL (9) and SIGSTOP cannot be caught, blocked or ignored, so a runaway process can always be stopped. A blocked signal is not the same as an ignored one: ignored means discarded, blocked means held.

Interrupts and the system call gate

A hardware device raises an interrupt request on an IRQ line. The interrupt controller gives the CPU a vector number. The CPU reads that entry in the IDT, the interrupt descriptor table, and jumps to the handler. On x86 the common C entry is do_IRQ().

The top half runs immediately with interrupts disabled on that CPU. It must be short: acknowledge the device, copy urgent bytes, then schedule deferred work. Slow work runs in a bottom half. Softirqs are a few statically defined handlers and may run on several CPUs at once. Tasklets are built on softirqs, but a given tasklet runs on only one CPU at a time, so it never races with itself; it still cannot sleep. Workqueues run in kernel threads and may sleep. This split keeps interrupt latency low.

A system call enters the kernel through a controlled software interrupt. Old x86 uses int 0x80; modern x86-64 uses the syscall instruction. The call number indexes sys_call_table, an array of kernel function pointers, so user code cannot jump to an arbitrary kernel address. The return path from either an interrupt or a system call is where pending signals are noticed.

Timers, jiffies and boot time

HZ is the number of timer ticks per second chosen when the kernel is built, for example 250. Each tick increments jiffies, an unsigned long counter. jiffies is an integer count of ticks, not seconds: seconds = jiffies ÷ HZ. The tick drives timekeeping, timeouts, and scheduler decisions (see 5.8 for run queues).

Kernel code arms a timer with add_timer() and changes its expiry with mod_timer(). The timer wheel groups timers by expiry so the tick can find due ones quickly. High-resolution timers, hrtimers, provide finer expiry where hardware allows. CLOCK_REALTIME is wall-clock time and can jump when NTP or an administrator changes it. CLOCK_MONOTONIC never goes backwards, so it is used for measuring intervals.

At boot the kernel reads the real-time clock once to set CLOCK_REALTIME, then uses the tick and hrtimers to maintain time. The boot path: firmware, bootloader, start_kernel (which sets up traps and timers), then init. A timer interrupt is handled like other interrupts; its bottom half runs expired timers and wakes tasks.

Worked example

Question. A kernel is built with HZ = 250. (a) How many jiffies are in 1 s and in 20 ms? (b) A 32-bit jiffies counter starts at 0 at HZ = 250. After how many seconds and days does it wrap? (c) A process blocks SIGINT, calls raise(SIGINT), then unblocks SIGINT. When does the handler run?

  1. HZ = 250 ticks per second, so 1 s = 250 jiffies.
  2. 20 ms = 0.020 s; 0.020 × 250 = 5 jiffies.
  3. The counter range is 0 to 2³² − 1, so it wraps after 2³² = 4,294,967,296 ticks.
  4. Time = 4,294,967,296 ÷ 250 = 17,179,869.184 s.
  5. Days = 17,179,869.184 ÷ 86,400 = 198.841... ≈ 198.84 days.
  6. SIGINT remains pending while blocked; raise() marks it pending. After unblocking, the kernel delivers it on the return to user mode, so the handler runs then.

Answer. (a) 250 jiffies in 1 s and 5 jiffies in 20 ms; (b) 17,179,869.184 s, about 198.84 days; (c) after SIGINT is unblocked, on the return to user mode.

Exam traps

  • A signal handler runs in user mode. It cannot call kernel-only functions or assume kernel privileges.
  • SIGKILL and SIGSTOP cannot be caught, blocked or ignored; kill -9 is not a polite request.
  • Blocked is not ignored: a blocked signal waits, an ignored signal is discarded.
  • jiffies is an integer tick count, not seconds. Divide by HZ to get time.
  • The top half runs with interrupts disabled; softirqs and tasklets cannot sleep, but workqueues can.

5.3 Virtual address space and paging in Linux

A process never sees physical RAM. It works in virtual addresses, and the memory management unit (MMU) translates each one page by page into a physical frame. Linux does not build that translation eagerly. It records what the process asked for and fills in page tables only when a page is first touched, through a page fault. That is why malloc returns instantly, why two processes can share one library, and why one bad pointer kills only its own program with SIGSEGV.

You need: 5.1 for task_struct and mm_struct, and Unit 1 for the kernel/user split.

Pages, tables and the MMU

RAM is divided into frames of 4 KB. A process's memory is divided into pages of the same size. The MMU translates a virtual address to a physical address one page at a time. The offset inside the page is copied unchanged, because page and frame are both 4 KB and aligned.

On 32-bit x86 the address has 32 bits: 10 bits choose an entry in the page directory, 10 bits choose an entry in one page table, and 12 bits are the offset (2¹² = 4096). Two levels cover the 4 GB space.

x86-64 uses four levels — PGD (page global directory), PUD, PMD and PTE — each index 9 bits, plus 12 offset bits, giving 48-bit virtual addresses. The register CR3 holds the physical base of the PGD. A context switch loads the new process's CR3.

physical address = frame number × 4096 + offset

frame number is the page-table entry with its low 12 flag bits removed (PTE >> 12); on a 64-bit PTE, mask the address field (bits 12–51) before shifting: frame = (PTE & 0x000FFFFFFFFFF000) >> 12. 4096 is the page size in bytes; offset is the low 12 bits of the virtual address, 0 to 4095.

A page-table entry (PTE) is a 32-bit or 64-bit word. The low bits are flags: bit 0 present, bit 1 writable, bit 2 user-accessible. The remaining bits, shifted right by 12, give the frame number.

The TLB is a small cache of recent translations inside the CPU. When the kernel changes a PTE it must flush the stale entry: INVLPG for one page, or reloading CR3 for the whole set.

mm_struct, VMAs and demand paging

Every process has one mm_struct (some syllabi call it the address space or memory map). It points to the top-level page table, counts the pages, and keeps a list of vm_area_struct objects, each called a VMA. A VMA is one contiguous range, such as code, data, heap, stack or a mapped file, with a start, an end and permission bits.

Linux fills page tables lazily. A VMA only promises space. No frame is assigned until the page is touched.

  1. The CPU fails the translation and raises a page fault, pushing the faulting address into CR2.
  2. The kernel finds the VMA containing that address. No VMA, or a permission mismatch, means the access is invalid.
  3. Minor fault: the page is already in memory, in the page cache or an allocated frame. The kernel writes the PTE and returns; no disk I/O.
  4. Major fault: the page sits on disk or in swap. The process sleeps while the kernel reads it, then maps it.
  5. Invalid fault: the kernel delivers SIGSEGV to the process.

malloc and mmap return immediately because they only create or extend a VMA. The first read or write to each page faults, and only then does a frame appear. A loop writing one byte per 4 KB touches many frames; writing 4 KB contiguously touches one.

Copy-on-write, mmap, zones and reclaim

fork does not copy memory. Parent and child share frames, and both sets of PTEs are marked read-only. When either side writes, the handler sees a write to a shared page, copies the frame, points the writer's PTE at the new frame and marks that PTE writable; the other process keeps its read-only PTE pointing at the original frame (it stays read-only for as long as the frame is shared). This is copy-on-write (COW). A following exec discards the old mm_struct and builds a fresh one.

mmap adds a VMA without reading the file. File-backed pages arrive on fault from the page cache, and a shared mapping lets several processes see the same frames.

Physical memory is grouped into zones: DMA (low addresses for old devices that cannot address high RAM), NORMAL, and HIGHMEM (32-bit only, not permanently mapped by the kernel). The kernel also keeps a direct map, where physical RAM (all of it on 64-bit; everything except high memory on 32-bit) appears at a fixed virtual offset, so frame number to kernel virtual address is addition, not a page walk.

When free frames run low, page reclaim runs: kswapd drops clean file-backed pages and writes anonymous pages to swap. Slab allocation belongs to 5.4; file-page caching is in 5.6.

Worked example

Question. On a 32-bit x86 machine with 4 KB pages, a process reads virtual address 0x00403ABC. The page-directory entry at index 1 points to a page table, and entry 3 of that table holds 0x00012007. Find the directory index, the table index, the offset, the frame number and the physical address, and name the flag bits that are set.

  1. 4 KB pages need 12 offset bits, so 32 − 12 = 20 bits are left. On 32-bit x86 these split 10 + 10.
  2. Write the address in binary: 0x00403ABC = 0000 0000 0100 0000 0011 1010 1011 1100.
  3. Group as 10 | 10 | 12: 0000000001 = 1, 0000000011 = 3, 1010 1011 1100 = 0xABC = 2748.
  4. Directory index = 1, table index = 3, offset = 2748 bytes.
  5. The low 12 bits of 0x00012007 are flags. Shift right by 12: 0x00012007 >> 12 = 0x00012 = 18, the frame number.
  6. Physical address = 18 × 4096 + 2748 = 73728 + 2748 = 76476 = 0x12ABC.
  7. Flags = 0x007 = binary 111: bit 0 present = 1, bit 1 writable = 1, bit 2 user-accessible = 1.

Answer. Directory index 1, table index 3, offset 2748 bytes, frame number 18, physical address 76476 (0x12ABC); the PTE has present, writable and user bits set (flag value 7).

Exam traps

  • The offset is copied unchanged, not translated. Only the page number goes through the page tables.
  • malloc reserves virtual space, not frames. Frames arrive on first touch, so a successful malloc proves nothing about free RAM.
  • The PTE is not the physical address. Mask off the low 12 flag bits (or shift right by 12) before multiplying by 4096.
  • A page fault is normal, not an error. Only a fault with no matching VMA or a wrong permission becomes SIGSEGV.
  • After changing a PTE the TLB may still hold the old translation. Without INVLPG or a CR3 reload the CPU keeps using stale data.

5.4 Kernel synchronization, queues and semaphores

Two CPUs can run kernel code at the same instant, and an interrupt handler can cut in on either of them. If both touch the same variable, one update can vanish. Kernel synchronization is the set of tools that prevents this: atomic counters, spinlocks for short sections that never sleep, semaphores and mutexes when a waiter may sleep, and wait queues that park a task until an event happens. Drivers, /proc counters, network buffers and file-system caches all depend on them.

You need: 5.1 for task states and 5.2 for interrupt context.

Race conditions and the critical section

A race condition is a bug where the result depends on the order in which two CPUs, or a CPU and an interrupt handler, reach the same data. The lines of code that touch that shared data form the critical section. Only one execution path may be inside it at a time.

The classic case is count++. The compiler turns it into three machine steps: read count, add 1, write it back. Two CPUs can both read the old value before either writes, so one update is lost. Both CPUs start from count = 5 in the figure below.

count++  →  r1 = count;  r2 = r1 + 1;  count = r2

count is a shared int in kernel memory; r1 and r2 are per-CPU registers, so each CPU keeps its own copy of the intermediate values.

For a plain counter the kernel uses atomic_t, a type that may be changed only through atomic operations. atomic_read(&v) returns the value, atomic_set(&v, n) sets it, atomic_inc(&v) and atomic_dec(&v) add or remove one, and atomic_add(n, &v) adds n. Each compiles to one locked instruction, so no lock is needed. atomic64_t does the same for 64-bit values, and refcount_t guards reference counts against overflow.

Spinlocks: waiting without sleeping

A spinlock is a lock that a CPU waits for by looping, that is, spinning, until it becomes free. Declare spinlock_t l and initialise it with spin_lock_init(&l). spin_lock(&l) takes it and spin_unlock(&l) releases it. A CPU that finds the lock taken burns cycles until the holder finishes, so a spinlock protects a few instructions, never a long operation.

The holder must never sleep. Sleeping means calling schedule(), which can switch to another task that wants the same lock; the holder is then not running, so nobody releases it. So no copy_to_user, no kmalloc(GFP_KERNEL) and no wait_event inside a spinlock.

Interrupts need care. If a handler on the same CPU takes the lock that the interrupted process is holding, that CPU deadlocks with itself, because the handler will not let the process run again to unlock. The fix is spin_lock_irqsave(&l, flags), which disables interrupts on the local CPU and saves the old interrupt state in flags, an unsigned long. spin_unlock_irqrestore(&l, flags) restores that state.

On a single-CPU kernel with preemption enabled, spinlocks are still required, because preemption can switch tasks in the middle of a critical section.

Semaphores, mutexes and completions

A semaphore is an integer count plus a wait queue. down(&s) tries to decrement the count; if the count is already zero, the caller goes to sleep until someone calls up(&s). up(&s) increments the count and wakes one sleeper. sema_init(&s, n) sets the starting count. A count of 1 behaves like a lock; a count of n allows n holders at once.

Because down() may sleep, a semaphore suits process context and is forbidden in an interrupt handler. down_interruptible(&s) returns 0 on success and -EINTR if a signal wakes the task; drivers prefer it so that Ctrl-C works.

A mutex is a semaphore with extra rules: the count is 0 or 1, the structure records the owner, and only the owner may unlock. The calls are mutex_lock(&m) and mutex_unlock(&m). It may sleep, so it cannot be used in interrupt context or inside a spinlock.

A read-write semaphore lets many readers in together but writers alone: down_read/up_read and down_write/up_write. A completion is a one-shot signal: one task blocks in wait_for_completion(&c), another calls complete(&c), and the waiter runs.

Wait queues, kernel queues and deadlock

A wait queue is the kernel's general sleep-and-wake mechanism. Declare wait_queue_head_t wq and call init_waitqueue_head(&wq). The short form is wait_event_interruptible(wq, condition): it tests condition, and if that is false it adds the task to the queue and calls schedule(). The matching wake_up_interruptible(&wq) wakes the sleepers, which test the condition again and sleep again if it is still false.

  1. The task tests the condition; it is false.
  2. The task sets its own state to TASK_INTERRUPTIBLE and links itself into the wait queue.
  3. The task calls schedule(); the scheduler runs another task on that CPU.
  4. Another thread changes the data and calls wake_up_interruptible(&wq).
  5. The task becomes runnable, tests the condition again, finds it true and continues.

The retest loop matters because several sleepers may wake and only one may find the condition true. Deadlock is the other risk: task A holds lock 1 and wants lock 2 while task B holds lock 2 and wants lock 1, so both wait forever. The cure is a fixed lock order, always taking locks in the same sequence everywhere. Memory barriers such as smp_mb() and barrier() keep loads and stores in order when a lock alone is not enough.

kfifo is the kernel's byte queue: kfifo_alloc() creates it, kfifo_in() pushes bytes and kfifo_out() pops them, for one producer and one consumer.

Worked example

Question. count is a shared int holding 5. Two CPUs each execute count++ once. (a) Give an interleaving that leaves count = 6. (b) Both increments are now wrapped in spin_lock(&l) and spin_unlock(&l); what is the final value?

  1. Each count++ is three machine steps: read count into a register, add 1, write the register back.
  2. Case (a): CPU 0 reads 5 at step 0. CPU 1 reads 5 at step 2, before CPU 0 has written.
  3. CPU 0 writes 6 at step 7 and CPU 1 writes 6 at step 9, so the second write overwrites the first.
  4. Final value in case (a) is 6, but two increments should have given 7, so one update is lost.
  5. Case (b): CPU 0 takes the lock, reads 5, writes 6 and unlocks; CPU 1 spins until then.
  6. CPU 1 now reads 6, writes 7 and unlocks, so no update is lost.

Dry run

0read 5-5
2-read 55
7write 6-6
9-write 66

Answer. (a) count = 6, one update lost. (b) count = 7.

Exam traps

  • A semaphore may sleep, so it can never be used in an interrupt handler or while a spinlock is held.
  • A spinlock must not be held across copy_to_user, kmalloc(GFP_KERNEL) or any call that can sleep.
  • spin_lock_irqsave must be matched by spin_unlock_irqrestore with the same saved flags, not by plain spin_unlock, or interrupts stay disabled.
  • A semaphore with count 3 admits three holders at once; it is not a lock, and only a mutex has an owner who must be the one to unlock.

5.5 Inter-process communication: pipes, sockets and ptrace

Two processes cannot read each other's memory, so they meet inside the kernel. The kernel keeps a small set of objects that carry data between processes: the pipe, a one-way byte queue reached through two file descriptors; the socket, a two-way endpoint with an address, a domain and a type, working on one machine or across a network; and ptrace, which lets one process stop another and read or change its registers and memory. Shell pipelines, database servers, gdb and strace all rest on these three objects.

You need: file descriptors and files_struct from 5.1, wait queues and wakeups from 5.4, and the shell pipeline from Unit 3.

Pipes: a byte queue behind two file descriptors

A pipe is a kernel buffer with two ends. The call pipe(fd) fills an array of two ints: fd[0] reads, fd[1] writes. Both are ordinary file descriptors, so read, write and close work on them. The shell command ls | grep txt creates exactly this pair, with one descriptor in each child process. Inside the kernel the pipe is an inode on a private file system called pipefs, and the data sits in a ring of 16 pages attached to that inode.

capacity = 16 pages × 4096 bytes = 65536 bytes

16 is the number of pages in the default pipe ring, 4096 bytes is the page size, and 65536 bytes is the largest amount the pipe can hold. PIPE_BUF is 4096 bytes: the largest write the kernel guarantees is not interleaved with another writer's bytes.

A write copies bytes into free pages and sleeps on a wait queue when the ring is full; a read copies bytes out and wakes the writer. A read returns only what is available, up to the count asked, so one 4 KB write can come back as two reads. When every writer has closed fd[1], read returns 0, which is end of file. A write after every reader has closed raises SIGPIPE, whose default action kills the process. mkfifo("/tmp/f", 0600) creates a named pipe, a FIFO with a path, so programs that never shared a fork can open it by name.

Sockets and other kernel channels

A socket is not just a pipe with an address: a pipe is one-way, while a socket is a two-way endpoint with a domain (AF_UNIX, AF_INET) and a type (stream or datagram). socket(AF_UNIX, SOCK_STREAM, 0) creates a local byte stream; the server binds a path with bind, calls listen, and accept returns a new descriptor for each client. socketpair(AF_UNIX, SOCK_STREAM, 0, sv) makes two already-connected ends with no path at all. AF_INET with SOCK_STREAM gives TCP: the same read, write, send and recv calls, going through the VFS like any file, so one function can serve a socket and a disk file alike.

Each socket keeps a send buffer and a receive buffer in the kernel; a blocking write sleeps when the send buffer is full, exactly like a pipe. For many descriptors, select and poll report who is ready, while epoll keeps the interest set inside the kernel. Shared memory (mmap with MAP_SHARED, or the older shmget) maps one set of physical pages into two address spaces and copies nothing, but it needs a semaphore to order access. Message queues keep record boundaries where a pipe has none.

ptrace: one process controls another

ptrace is a debugging hook built into the kernel. The tracer calls ptrace(PTRACE_ATTACH, pid) and the tracee stops; the tracer then calls waitpid(pid, &status, 0) and sees that stop. From then on the tracee runs only when the tracer says so.

  1. PTRACE_ATTACH, then waitpid: the tracee is now stopped and ready to inspect.
  2. PTRACE_PEEKTEXT reads one word of the tracee's text at an address; PTRACE_POKETEXT writes one word, which is how a breakpoint byte 0xcc is planted.
  3. PTRACE_GETREGS fills a user_regs_struct with rip, rsp, rax and the other registers; PTRACE_SETREGS changes them.
  4. PTRACE_SINGLESTEP runs exactly one instruction and stops again; PTRACE_CONT resumes until a signal or breakpoint.
  5. PTRACE_DETACH lets the tracee go and ends the relation.

gdb uses these calls for breakpoints and stepping; strace uses PTRACE_SYSCALL to stop at every system call and print its number and arguments. Permission is controlled by /proc/sys/kernel/yama/ptrace_scope: 0 means any process of the same user may attach, 1 means only descendants (the default on many distributions), 2 means admin only, 3 means no attach at all. That is why gdb normally starts the program itself instead of attaching to a stranger's PID.

Worked example

Question. A pipe has capacity 65536 bytes and is empty. It was opened O_NONBLOCK on the write end. A writer calls write(fd, buf, 70000). A reader then reads 8192 bytes. The writer then calls write for the 4464 bytes still left in its own buffer. Give each return value and the number of bytes left in the pipe.

  1. Free space before the first write is 65536 bytes; the writer asks for 70000 bytes.
  2. A non-blocking write copies only what fits: min(70000, 65536) = 65536 bytes. The first write returns 65536. Bytes still in user space: 70000 − 65536 = 4464 bytes.
  3. The reader reads 8192 bytes and read returns 8192. The pipe now holds 65536 − 8192 = 57344 bytes.
  4. Free space is now 65536 − 57344 = 8192 bytes. The second write asks for 4464 bytes, which is less than 8192, so all of it fits and the write returns 4464.
  5. Bytes in the pipe afterwards: 57344 + 4464 = 61808 bytes.

Answer. The first write returns 65536, the read returns 8192 and leaves 57344 bytes, the second write returns 4464, and the pipe holds 61808 bytes.

Exam traps

  • A pipe has no message boundaries: 4 KB written may be read as 3 KB then 1 KB, and end of file is read returning 0, never −1.
  • Pipe capacity (65536 bytes) is not PIPE_BUF (4096 bytes). PIPE_BUF is the atomicity limit for one write, not the size of the buffer.
  • SIGPIPE is a signal, not an error code. You see EPIPE as errno only after SIGPIPE has been ignored or blocked.
  • Leaving the unused end of a pipe open in a forked child keeps a writer alive, so the reader waits forever instead of getting end of file.
  • PTRACE_PEEKTEXT on a running tracee fails with ESRCH: the tracee must first be attached and reaped with waitpid.

5.6 Linux file systems: inodes, proc and ext2

A read() call does not need to know whether bytes come from a hard disk or from kernel memory. The virtual file system (VFS) describes every open file with an inode plus an operation table, so ext2 on disk and /proc in memory use the same calls. This chapter follows one file descriptor down to its inode, opens an ext2 disk layout, counts what its block pointers can reach, and shows how /proc builds files at read time. These ideas explain ls -i, hard links, and why cat /proc/meminfo works with no disk file.

You need 5.1 for the file-descriptor table in task_struct, and Unit 2 for file types, ls -i, ln and permissions.

Four VFS objects

The virtual file system (VFS) is the kernel layer that gives every file one set of calls, whatever stores it. It keeps four objects. A superblock describes one mounted file system: block size, root inode and operation table. An inode describes one file: type, size, owner, times, link count, block map and file_operations. Some syllabi call the inode an index node. A dentry ties a name to an inode. A struct file is one open file description: offset, flags and a pointer to the dentry.

An open file descriptor is a small integer indexing the process's descriptor table in task_struct. The entry points to a struct file, which points to a dentry, which points to the inode. The inode's operation table is what turns read() into ext2 or proc code.

An inode number is unique inside one file system. ls -i shows it. A hard link is another name for the same inode; ln a b raises the link count to 2. Data is freed only when the link count falls to 0 and no process holds the file open. A symbolic link is a new inode whose data is a path; it can cross file systems and can dangle. An inode has no filename: names live in directory entries.

ext2 on disk

ext2 starts with a 1 KB boot block. The rest of the partition is split into block groups, so metadata sits near its data. Each group has a copy of the superblock, group descriptors, a block bitmap, an inode bitmap, an inode table and data blocks. The superblock records block size, inode count and free counts. The bitmaps hold one bit per block or inode. The inode table holds fixed-size records, usually 128 bytes.

An ext2 inode stores 15 block pointers: 12 direct, one single indirect, one double indirect and one triple indirect. A pointer is 4 bytes. With 1 KB blocks, one pointer block holds 1024 ÷ 4 = 256 entries. Direct pointers cover 12 × 1 KB = 12 KB. The single indirect pointer covers 256 × 1 KB = 256 KB. The double indirect pointer covers 256² × 1 KB = 64 MiB. The triple indirect pointer covers 256³ × 1 KB = 16 GiB. The worked example adds them.

Direct pointers keep small files fast: no extra block read. Large files pay one, two or three extra reads to reach a data block. ext2 has no journal, so a crash during a write can leave inconsistent metadata; ext3 added a journal.

/proc: files built at read time

/proc is a pseudo file system: it uses inodes and the VFS, but stores no file data on disk. When a process reads /proc/meminfo, the kernel's read handler formats current memory counters into text. /proc/PID/status gives one process's Name, State, Pid, PPid and VmRSS. /proc/cpuinfo describes CPUs. Most files are read-only views; a few are writable knobs.

Because values are made when read, two reads can differ, and ls -l often shows size 0. Deleting or creating a process changes /proc/PID entries immediately. /sys (sysfs) is a similar in-memory file system that shows devices, drivers and kernel objects as directories with one value per file.

The VFS makes /proc look ordinary: open, read and close work, and tools such as cat, ps, top and free need no special calls. The inode's operation table points to proc handlers instead of disk blocks. That is the same mechanism a device driver uses (see 5.7).

Worked example

Question. Ext2 uses 1 KB blocks and 4-byte block pointers. It has 12 direct, 1 single indirect, 1 double indirect and 1 triple indirect pointers. (a) What is the largest file size in KB and GiB? (b) Which data block in the pointer scheme reaches byte offset 300000, and what byte range does that block cover?

  1. One pointer block holds 1024 ÷ 4 = 256 pointers.
  2. Blocks reachable = 12 + 256 + 256² + 256³ = 12 + 256 + 65536 + 16777216 = 16843020 blocks.
  3. Each block is 1 KB, so largest size = 16843020 KB. In GiB: 16843020 ÷ 1024² = 16.06 GiB (17,247,252,480 bytes).
  4. Direct bytes = 12 × 1024 = 12288, offsets 0 to 12287.
  5. Single indirect bytes = 256 × 1024 = 262144, offsets 12288 to 274431.
  6. Double indirect starts at 274432. Offset 300000 is inside it.
  7. Offset inside double area = 300000 − 274432 = 25568 bytes. Block index = floor(25568 ÷ 1024) = 24.
  8. Since 24 < 256, the top-level double-indirect entry is 0 and the second-level entry is 24.
  9. Block 24 starts at 274432 + 24 × 1024 = 299008 and ends at 299008 + 1023 = 300031.

Answer. Largest file = 16,843,020 KB ≈ 16.06 GiB; offset 300000 lies in double-indirect data block index 24 (top-level entry 0, second-level 24), covering bytes 299008–300031.

  • A larger inode number does not mean a newer file; ext2 allocates inodes in its own order.
  • /proc files use no disk blocks. Their reported size is often 0 even when cat prints many lines.
  • Direct pointers cover 12 KB with 1 KB blocks, not 12 MB; unit slips are common.
  • An unlinked but open file keeps its data until the last close, even when link count is 0.

5.7 Device drivers: character and block devices

A device driver is kernel code that turns a hardware device into a file. It registers a major number for itself and minor numbers for each instance, then fills a table of function pointers. When a program calls read(), the kernel finds that table through the inode and calls the driver's own function, which copies bytes into the user buffer. Keyboards, serial ports and every disk in the machine are reached this way. The same pattern covers character drivers that move byte streams and block drivers that move disk sectors.

You need: 5.6 on inodes and file_operations, and 5.3 on user versus kernel addresses.

Device numbers: major and minor

Every device node carries two numbers. The major number selects the driver. The minor number selects one instance of the device that the driver handles. /dev/ttyS0 and /dev/ttyS1 share a major and differ in minor, because one driver serves both serial ports.

The kernel stores the pair in dev_t, an integer type. The classic encoding packs 8 bits of major and 8 bits of minor into 16 bits. Newer kernels allow 12 bits of major and 20 of minor. Do not hand-shift in real code: MKDEV(major, minor) builds a dev_t, and MAJOR(dev) and MINOR(dev) take it apart again.

dev = (major << 8) | minor

dev is the classic 16-bit dev_t; major is the driver number (0-255); minor is the instance number (0-255); << shifts the major 8 bits left and | merges the two fields. The modern encoding is 12 bits of major and 20 bits of minor.

The node is made by mknod /dev/mydrv c 240 3 — c for character, b for block, then major and minor — or automatically by udev when the driver registers. mknod creates only a name and a number. If no driver holds major 240, open() fails with ENODEV.

The character driver and its file_operations table

A character driver moves a byte stream: keyboard, serial port, /dev/null. There is no block size and no caching layer. The driver claims a major with register_chrdev() (older) or alloc_chrdev_region() plus cdev_add(), then fills a struct file_operations from <linux/fs.h> with function pointers: .open, .read, .write, .unlocked_ioctl, .release.

read has the signature ssize_t my_read(struct file *filp, char __user *buf, size_t count, loff_t *f_pos). Here count is how many bytes the user asked for, f_pos is the current offset, and buf is a user virtual address that may be unmapped or paged out.

The kernel must not touch buf directly. copy_to_user(buf, kbuf, n) copies n bytes from kernel memory kbuf to the user buffer and returns the number of bytes it could not copy, 0 on success. copy_from_user() does the reverse for write.

Return the number of bytes actually transferred (at most count); return 0 at end of file; return a negative error code such as -EFAULT, -EINVAL or -ENOMEM. Update *f_pos by the same number of bytes. Never return -1: the kernel wants the error code itself, and libc turns -EFAULT into a return of -1 with errno set to EFAULT.

The kernel has no libc. printk replaces printf, kmalloc/kfree replace malloc/free, and memcpy and memset are the kernel's own versions. A module that calls printf or malloc gets no symbol from the kernel and fails to load with an unresolved-symbol error. ioctl carries commands that are not plain bytes: baud rate, gain, reset.

Block drivers: gendisk, bio and the request queue

A block driver serves a disk. Data moves in fixed-size sectors of 512 bytes, and the kernel keeps recently used blocks in the page cache, so two reads of the same block reach the driver only once.

The driver describes the disk with struct gendisk: major, first_minor, minors (the number of minor numbers reserved for this disk, one for the disk plus one for each allowed partition), fops and queue. alloc_disk() and blk_mq_init_queue() set it up; add_disk() publishes it, and the /dev nodes appear.

I/O does not arrive as a byte count. The block layer hands over a struct bio — a list of page-sized segments covering one operation — after merging and sorting many bios into a request queue. The driver takes requests, programs the controller with DMA, and completes them later from an interrupt.

Layer order: VFS → page cache → block layer → request queue → driver → device. That complexity buys caching, merging, reordering, partitions and hotplug. brd, the RAM disk, is a small complete block driver worth reading.

Modules: loading, unloading and context

A driver usually ships as a loadable module: module_init() names its load function, module_exit() its unload function, and MODULE_LICENSE("GPL") declares the license.

Two contexts matter. A read() runs in process context and may sleep, so kmalloc(GFP_KERNEL), mutex_lock and copy_to_user are allowed. An interrupt handler is atomic: it cannot sleep, must use GFP_ATOMIC and spinlocks, and must never call copy_to_user. Queue the work and finish it later in process context.

Worked example

Question. A character driver named mydrv takes major 240 and minors 0 to 3. (a) What does mknod /dev/mydrv c 240 3 create? (b) Give its dev_t value in the classic 16-bit encoding. (c) A user calls read(fd, buf, 100) and the driver has 100 bytes ready. What does the driver return, and what does the system call return?

  1. (a) The letter c asks for a character device node. The two numbers after it are major 240 and minor 3: a node that reaches instance 3 of the driver holding major 240.
  2. (b) Classic encoding: dev = (major << 8) | minor = (240 << 8) | 3.
  3. 240 << 8 = 240 × 256 = 61440.
  4. 61440 | 3 = 61440 + 3 = 61443. So dev_t = 61443.
  5. (c) VFS takes the inode of the node, reads its major 240, finds mydrv's file_operations, and calls my_read with count = 100.
  6. my_read puts the 100 bytes in a kernel buffer and calls copy_to_user(buf, kbuf, 100). It copies all 100 bytes and returns 0 bytes left over.
  7. my_read therefore returns 100. The kernel passes that value straight back, so read() returns 100 to the user, with buf holding the 100 bytes.

Answer. (a) A character device node with major 240 and minor 3; (b) dev_t = 61443; (c) the driver returns 100 and the system call returns 100.

Exam traps

  • mknod makes a name and a number, not a driver. The node works only after some module registers that major; otherwise open() gives ENODEV.
  • Never dereference a user pointer in the kernel. copy_to_user and copy_from_user validate and page in the buffer; a plain memcpy to buf can panic the machine.
  • A driver returns a negative error code such as -EFAULT, not -1. libc converts it, so the user sees -1 with errno set while the kernel saw -14.
  • Major picks the driver, minor picks the instance. Swapping them in mknod gives a node that no driver answers.
  • copy_to_user may sleep, so it belongs in process context only — never inside an interrupt handler or while holding a spinlock.

5.8 Multiprocessing support in Linux

Linux symmetric multiprocessing (SMP) lets every CPU run kernel code and user tasks at the same time over one shared memory. That gives throughput, but shared data can be corrupted and some CPUs can sit idle. Linux therefore uses per-CPU data, spinlocks and atomic operations for safety, and one CFS run queue per CPU plus periodic load balancing for speed. Phones, servers and cloud machines all depend on it. Some syllabi say “multiprocessing” for multitasking; in this chapter it means SMP: many CPUs, one kernel.

You need: 5.4 for locking, 5.1 for task_struct, and 5.2 for IPIs and the timer tick.

CFS run queues and load balancing

Linux runs one CFS run queue per CPU. CFS means Completely Fair Scheduler. A run queue holds tasks that are ready to run on that CPU. Each task has a vruntime: the runtime it has received, scaled by its weight. A task with lower nice value has larger weight and its vruntime grows more slowly, so it is picked sooner. The queue is a red-black tree ordered by vruntime; the leftmost node is the next task. The scheduler picks that node, runs the task for a slice, then reinserts it. Because each CPU has its own tree, CPUs do not fight over one global list.

vruntime_new = vruntime_old + Δt × (w₀ ÷ w_task)

Δt is actual CPU time in ns; w_task is the task's weight from its nice value; w₀ is the weight at nice 0; a larger weight makes vruntime grow more slowly.

The periodic load balancer compares queue load. If one CPU has too many runnable tasks, it moves a task to a less loaded CPU. The move is a migration: the task is stopped on the old CPU, its task_struct is moved to the new run queue, and it resumes there. CPU affinity limits migration. sched_setaffinity() sets a CPU mask for a process, and taskset -c 0 make runs the program make only on CPU 0, because taskset -c 0 restricts the process it launches to CPU 0. Affinity helps cache locality, but pinning too much work to one CPU can starve it while other CPUs idle.

NUMA is an advanced extension: on some machines memory is closer to one CPU than another. Only a few syllabi teach NUMA placement; the basic exam picture is one flat memory shared by all CPUs.

Bringing CPUs up and per-CPU data

UP means uniprocessor: one CPU. SMP means symmetric multiprocessing: several identical CPUs share memory and run the same kernel. At boot one CPU, the boot CPU, starts first. It brings the other CPUs, called application processors (APs), online by sending an INIT IPI and then a STARTUP IPI (together INIT-SIPI). The STARTUP IPI gives a startup address; the AP enters the kernel there, initialises its local state, and joins the scheduler.

Per-CPU variables give each CPU its own copy of a value. The kernel accesses the current CPU's copy with this_cpu_inc() or get_cpu(). get_cpu() disables preemption and returns the CPU number; put_cpu() re-enables preemption. While preemption is off, the task cannot move to another CPU, so the copy it uses is its own. That copy is safe without a lock only from its own CPU. Another CPU or an interrupt handler can still change its own copy, so shared logical state still needs a lock. Per-CPU counters, caches and statistics use this pattern.

Shared data: spinlocks, atomics, barriers, IPIs

Shared kernel data needs protection because two CPUs can read and write it at the same time. A spinlock is a lock that busy-waits: the CPU repeats a test until the lock is free. The holder must finish quickly and must not sleep. Spinlocks are used in interrupt context and for short critical sections. An atomic operation, such as atomic_inc() on an atomic_t, reads, changes and writes a value as one indivisible step, so no lock is needed.

RCU (read-copy-update) lets readers walk a shared structure without locks while a writer publishes a new version and waits for existing readers to finish. Memory barriers stop the compiler or CPU from reordering memory accesses around a point; smp_mb() is a full barrier. An IPI, inter-processor interrupt, runs a function on another CPU. Linux uses IPIs for TLB shootdown, scheduler wakeups and synchronisation. The main exam trap: a spinlock is not a sleeping lock. If the critical section may sleep, use a mutex or semaphore from 5.4.

Worked example

Question. Eight equal-weight CPU-bound tasks start on a 4-CPU machine with no affinity. (a) What share of one CPU does each task get? (b) A programmer pins four of them to CPU 0 with taskset -c 0. What does each task get now?

  1. In (a), total capacity is 4 CPUs. Eight equal tasks share it. Each task gets 4 ÷ 8 = 0.5 CPU, that is 50% of one CPU.
  2. In (b), four pinned tasks share CPU 0. CPU 0 capacity is 1 CPU. Each pinned task gets 1 ÷ 4 = 0.25 CPU, that is 25% of one CPU.
  3. The other four tasks can run on CPUs 1, 2 and 3, total 3 CPUs. Each gets 3 ÷ 4 = 0.75 CPU, that is 75% of one CPU.
  4. The load balancer keeps CPUs 1–3 roughly balanced; affinity stops pinned tasks from moving to those CPUs.

Answer. With no affinity each task gets 0.5 CPU (50%); after pinning, each pinned task gets 0.25 CPU (25%) and each unpinned task gets 0.75 CPU (75%).

Exam traps

  • A single-threaded program does not run faster just because the machine has more CPUs; it has one instruction stream.
  • A per-CPU variable is safe without a lock only from its own CPU with preemption disabled. From another CPU it is just shared data.
  • A spinlock busy-waits and cannot be held across sleep; use a mutex or semaphore for code that may sleep.
  • CPU affinity is a restriction, not a promise of more speed; pinning all work to CPU 0 leaves other CPUs idle.
  • Some syllabi use “multiprocessing” for multitasking. In this unit it means symmetric multiprocessing: several CPUs sharing one kernel and memory.

Check yourself

Remember Define SMP and UP. What is the main hardware difference? 2 marks

UP has one CPU; SMP has several identical CPUs sharing memory and running one kernel.

Understand Why is a per-CPU variable safe without a lock only when accessed from its own CPU with preemption disabled? 3 marks

Each CPU has its own copy of the variable. With preemption disabled the task cannot migrate, so the copy it reads or writes is always the one belonging to the CPU it is running on. Without that, the task could be moved to another CPU between taking the CPU number and the access, and would then touch a different CPU's copy while that CPU is using it.

Apply Six equal CPU-bound tasks run on a 3-CPU machine with no affinity. Then three are pinned to CPU 0. (a) What share of one CPU does each get with no affinity? (b) What does each pinned and each unpinned task get after pinning? 4 marks

(a) 3 CPUs ÷ 6 tasks = 0.5 CPU each. (b) Pinned: 1 CPU ÷ 3 tasks = 0.33 CPU each. Unpinned: 2 CPUs ÷ 3 tasks = 0.67 CPU each.

Analyze Why does Linux use one run queue per CPU instead of one global run queue? 4 marks

A per-CPU run queue avoids a global lock and cache contention; each CPU schedules locally, and the load balancer moves tasks when queues differ.

Understand What is vruntime and how does nice value affect it? 3 marks

vruntime is scaled runtime; larger weight from lower nice makes it grow more slowly, so the task is picked more often.

Remember What is an IPI and name one use. 2 marks

An inter-processor interrupt runs a function on another CPU; it is used for TLB shootdown or scheduler wakeups.

Analyze A load balancer sees CPU 0 with eight runnable tasks and CPU 1 idle. What does it do, and what can stop it? 4 marks

It migrates a task from CPU 0 to CPU 1 if affinity and cache rules allow; CPU affinity or pinning can stop migration.

Takeaways

  1. Every running program is one task_struct, and the process table is the set of lists that finds it by PID or by parent.
  2. Interrupts travel from hardware to the kernel, signals travel from the kernel to a process; both arrive without warning.
  3. The timer tick keeps time, expires timeouts, and gives the scheduler its regular chance to switch tasks.
  4. A process only ever sees virtual addresses; Linux fills in the translation map lazily, page by page, as faults arrive.
  5. Kernel data is shared between CPUs and interrupt handlers, so each critical section needs a lock chosen to match that context.
  6. Pipes and sockets are kernel buffers reached through file descriptors, and ptrace is a kernel channel for one process to control another.
  7. The VFS inode and its operation tables make ext2 on disk and /proc in memory answer the same read() call.
  8. A device is a major number, a minor number and a file_operations table.
  9. Multiprocessor Linux buys correctness with locking and speed with per-CPU data plus a load balancer.

Exam question bank

Long answers here almost always ask you to trace one event — a kill, a page fault, a read() on a device — through the kernel structures it touches, so name each structure, the field used and the step in order.

Remember and understand

Remember Draw a task_struct and label the fields used for lookup: pid, state, parent and children links, mm and files. Explain how the process table finds a task by PID and how it lists that task's children. 10 marks

task_struct is the process descriptor, allocated in kernel memory; pid field plus the PID hash table gives O(1) lookup; parent and children/sibling links form the process tree; state field values: running, interruptible, stopped, zombie; mm holds the address space, files holds the open file table.

Understand Explain how a hardware interrupt reaches its handler: the inter-request line, the vector, saving the context and returning. Say why Linux splits handling into a top half and a bottom half, with one example of each. 13 marks

device raises IRQ, interrupt controller signals the CPU; CPU reads the vector and indexes the interrupt descriptor table; current context saved on the kernel stack, interrupts disabled on that CPU; top half runs quickly: acknowledge device, copy urgent data; bottom half (softirq, tasklet, workqueue) does the long work with interrupts on; return path restores context, possibly reschedules.

Remember Define a signal. List four common signals with their default actions, and describe how a pending signal is delivered and what happens after a handler returns. 10 marks

signal is an asynchronous notification, numbered 1 to 64; SIGTERM terminates, SIGKILL terminates and cannot be caught, SIGCHLD notifies parent, SIGSEGV core dumps; pending bit set on the task, blocked by the signal mask; delivered when the process returns from kernel to user mode; handler runs on the user stack, then sigreturn restores the old context; default action taken if no handler is installed.

Understand Explain address translation in Linux: virtual address, page, page frame, page table and TLB. Then give the steps of handling a page fault on a valid but not yet mapped page. 13 marks

virtual address splits into page number and offset; page table maps page number to frame number plus permission bits; TLB caches recent translations; fault traps to kernel, faulting address read from a control register; handler checks the VMA for the address; valid: read from disk or zero-fill a frame, install mapping, return and retry the instruction; invalid: send SIGSEGV.

Understand Compare spinlocks, kernel semaphores and wait queues. For each, state whether the holder may sleep and where the kernel uses it. 10 marks

spinlock busy-waits, non-preemptible section, holder must not sleep; used for short sections shared with interrupt handlers; semaphore counts, down() sleeps the caller, used for longer holds; mutex is a semaphore with count one and an owner; wait queue holds sleeping tasks until a condition becomes true; wake_up moves tasks to the run queue; rule: never sleep inside interrupt context.

Understand Describe byte-stream pipes: how one is created, the read and write ends, what read() returns at end-of-file, and why the pipe has a fixed capacity. 8 marks

pipe() returns two file descriptors; anonymous pipe exists only through these descriptors; writer blocks when the buffer is full, reader blocks when empty; read() returns 0 when all write ends are closed; SIGPIPE if the reader has gone; fixed capacity keeps memory bounded and gives natural flow control.

Apply

Apply A user program calls read() on the device file of a character driver. Trace the call from the system call entry to the copy of bytes into user memory. State where the major number, the minor number and the file_operations table are used. 13 marks

syscall entry, arguments checked, file descriptor looked up in the file table; file points to a dentry and inode; inode type says character device; major number selects the driver through the character device table; minor number is passed to the driver to pick the instance; VFS calls the read entry of the driver's file_operations; driver copies data with copy_to_user and returns the count; return value and errors handled at the syscall exit.

Apply Two CPUs increment the same kernel counter without protection and one update is lost. Show how the race happens, then remove it once with an atomic operation and once with a spinlock. Explain why a semaphore is the wrong choice when the code also runs in an interrupt handler. 13 marks

read-modify-write is not one instruction at the memory bus level; interleaving of load and store loses an update; atomic_t or atomic_inc uses a single locked instruction; spinlock gives mutual exclusion around a longer section; spin_lock_irqsave also disables local interrupts to avoid deadlock; a semaphore may sleep, and sleeping is illegal in interrupt context; keep the critical section short to limit contention.

Apply Trace the shell command kill -TERM <pid> from the kill system call to the target process running its handler. Cover PID lookup, the permission check, the pending bit, waking a sleeping task and delivery on return to user mode. 13 marks

kill() enters the kernel with a PID and a signal number; process table lookup by PID fails with ESRCH if absent; permission check: same user or a privileged process; signal bit set in the pending set of the target; if the target sleeps interruptibly it is woken; signal delivered at the next return to user mode; handler installed by the process runs, else the default action.

Apply A process touches a heap address it has never used before. Trace the event from the instruction to every possible outcome, including the case where the process is killed. 10 marks

MMU finds no valid translation and raises a page fault; faulting address and error code passed to the handler; kernel searches the VMAs of the task for the address; inside a VMA: allocate a zeroed frame, insert the mapping; page table updated, TLB flushed if needed; instruction restarted and now succeeds; outside every VMA: SIGSEGV delivered; under memory pressure: reclaim or OOM kill.

Analyze and evaluate

Analyze Analyse demand paging with lazy allocation in Linux. What does the kernel save, what does each fault cost, and how can overcommit end in the OOM killer? 13 marks

pages are mapped only when first touched; saves memory and start-up time for large sparse programs; each fault costs a trap, a frame allocation and often disk I/O; overcommit allows total virtual size to exceed RAM plus swap; reclaim, swap and page cache shrink under pressure; when reclaim fails the OOM killer picks a task; tuning knobs change how strict overcommit is.

Analyze Explain how a debugger uses ptrace to set a breakpoint and read a register of the program under test. Then analyse why ptrace is treated as a security-sensitive interface. 12 marks

tracer attaches with PTRACE_ATTACH or starts the child with PTRACE_TRACEME; tracee stops at each signal and syscall boundary; tracer writes a trap instruction over the target byte; SIGTRAP returns control to the tracer, original byte restored; PTRACE_PEEK/POKE read and write memory, GETREGS reads registers; a tracing process can read and change another process's memory; hence the same-user rule and restrictions on setuid programs.

Evaluate Compare the on-disk inode of ext2 with the in-memory inode of the VFS. Evaluate how the operation tables in the in-memory inode let /proc answer the same read() call as a file on disk. 13 marks

on-disk inode holds mode, owner, size, times, direct and indirect block pointers; no function pointers on disk, fixed layout; VFS inode built in memory when the file is first touched; inode_operations and file_operations hold function pointers; address space operations connect the page cache to the backing store; ext2 read goes through the block device; proc read builds text; uniform interface: the system call never knows which file system it hit.

Evaluate Linux once serialised kernel code with one global lock and now runs it on many CPUs at once. Evaluate the change: per-CPU data, spinlocks, cache behaviour on contended locks, and the job of the load balancer. 16 marks

global lock gave correctness but no scaling; per-CPU data removes sharing for counters and caches; spinlock protects genuinely shared state, cost rises with contention; cache line bouncing makes a hot lock expensive; lock ordering rules prevent deadlock; load balancer moves runnable tasks between CPUs; affinity and NUMA placement affect performance; trade-off: fine-grained locking is harder to get right.

Glossary

Atomic operation
An operation that completes as one indivisible step, so no other CPU sees a half-done result.
Bottom half
Deferred interrupt work done later, as a softirq, tasklet or workqueue, with interrupts enabled.
Character device
Device read and written as a stream of bytes, such as a terminal or serial port.
Critical section
Code that touches shared data and must run as if it were alone.
Demand paging
Loading a page into memory only when it is first touched, not when it is mapped.
Dentry
Directory entry object that links a file name to its inode and caches path lookups.
FIFO
Named pipe; a pipe that has a path in the file system so unrelated processes can open it.
HZ
Build-time constant giving timer ticks per second; jiffies counts those ticks.
IDT
Interrupt descriptor table; holds the handler entry point for each interrupt vector.
init
The first user process, always PID 1, which starts the rest of the system.
ioctl
System call that passes device-specific commands and arguments straight to a driver.
Load balancing
Scheduler activity that moves runnable tasks to idle CPUs to keep every CPU busy.
MMU
Memory management unit; hardware that translates virtual addresses to physical addresses using page tables.
Mutex
Sleeping lock with a single owner, used when the critical section may block.
Page
Fixed-size block of virtual memory, commonly 4 KiB on x86.
Page frame
Fixed-size block of physical memory that holds one page.
Page table
Per-process table that maps page numbers to frame numbers and holds permission bits.
Process descriptor
The task_struct in kernel memory that holds everything the kernel knows about one process.
Process table
The lists and hash tables that hold all process descriptors and allow lookup by PID or by parent.
Signal handler
User function that runs instead of a signal's default action when the process has installed one.
Superblock
In-memory object describing one mounted file system.
TLB
Translation lookaside buffer; a small cache of recent virtual-to-physical translations.
Top half
The interrupt handler that runs immediately with interrupts partly disabled and must be short.
Unix domain socket
Socket that stays inside one machine and is addressed by a file-system path.
Zombie
A finished process whose descriptor stays until its parent collects the exit status.
