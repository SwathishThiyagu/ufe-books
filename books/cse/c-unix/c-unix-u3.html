3.1 Shell basics: Bourne shell and Bash

The shell is the program that reads your command line and turns it into action. It is also a programming language: the same words can sit in a file and run as a script. The Bourne shell, sh, is the old portable standard; Bash is its widely used successor with extra features. You meet both in login sessions, build scripts and cron jobs. This chapter separates the two roles, shows how a script starts, and explains how a command is found and how success is reported.

You need Unit 1 command-line interface and basic commands, and Unit 2 file permissions and chmod.

Two jobs in one program

A shell does two jobs. As a command interpreter, it reads a line such as ls -l, expands variables and quotes, finds the program, and asks the kernel to run it. As a programming language, it runs a file of commands one after another, with variables, tests and loops. Interactive use is typing at a prompt; script use is non-interactive execution from a file. Both go through the same parser.

sh is the Bourne shell. Its path is usually /bin/sh. Bash is the Bourne Again SHell, usually /bin/bash. Bash accepts sh syntax and adds arrays, [[ ]] tests, brace expansion and more. A portable script limits itself to POSIX sh features. The POSIX standard defines the common shell language, so a script written for sh runs on many systems. Some syllabi call this shell basics or shell scripting fundamentals.

  • Interactive shell: prompt, history, job control.
  • Script shell: no prompt, reads a file, exits with a status.

Running a script and finding commands

The first line of a script is the shebang. It starts with #! and gives an absolute interpreter path, for example #!/bin/sh or #!/bin/bash. The kernel reads it when the file is executed directly with ./greet.sh. The file then needs execute permission. Running sh greet.sh does not use the shebang: you chose sh. Running bash greet.sh chooses Bash.

  1. Write the script and put the shebang on line 1.
  2. Make it executable: chmod +x greet.sh or chmod 755 greet.sh. 755 means rwxr-xr-x.
  3. Run it as ./greet.sh. The kernel uses the shebang.
  4. Or bypass the shebang: sh greet.sh or bash greet.sh.

A command name is first checked against shell builtins such as cd, echo and export. If it is not builtin, the shell searches the directories in PATH from left to right. PATH is a colon-separated list such as /usr/local/bin:/usr/bin:/bin. The first matching executable file runs. A builtin does not need a file.

After a command finishes, the shell stores its exit status in $?. 0 means success; any non-zero value means failure. if and while use this value, so scripts make decisions from exit status, not from printed text. See conditionals and loops.

Portable sh and Bash extras

Write for sh when a script must run on many machines, including small systems and containers. Use Bash when you need its extras and can require /bin/bash. The shebang should match the features you use. A script with #!/bin/sh but Bash-only syntax may fail when /bin/sh is a smaller shell.

  • Bash arrays: names=(Ravi Asha); echo ${names[1]} prints Asha.
  • Bash [[ ]]: [[ $name == A* ]] does pattern matching without word splitting.
  • Bash brace expansion: touch file{1..3}.txt creates three names.
  • POSIX sh: use [ ], case, for, while and quoted "$var".

Variables and quoting are in shell variables and operators. File redirection is in file input and output. Pipes are in pipes and filters.

Worked example

Question. A file greet.sh contains two lines. Line 1 is #!/bin/sh. Line 2 is echo "Hi $USER". Assume USER is asha. The file mode is 644. You run ./greet.sh. Then you run chmod 755 greet.sh and run ./greet.sh again. Finally you run bash greet.sh. State each outcome. Explain how bash greet.sh differs from ./greet.sh, and what sh greet.sh would do.

  1. Mode 644 is rw-r--r--. The owner can read and write but cannot execute. ./greet.sh asks the kernel to execute the file, so it fails with Permission denied.
  2. chmod 755 sets rwxr-xr-x. The owner can execute, group and others can read and execute.
  3. ./greet.sh now runs. The kernel reads #!/bin/sh and starts /bin/sh on the file. USER is asha, so line 2 prints Hi asha.
  4. bash greet.sh starts Bash explicitly on the file. Bash treats the shebang as a comment and runs the lines. The script uses no Bash-only syntax, so it also prints Hi asha.
  5. sh greet.sh starts sh explicitly; the shebang is again ignored. It prints Hi asha. The shebang matters only for direct execution.

Exam traps

  • The shebang must be the first line and must use an absolute path. A blank line or a space before #! makes it an ordinary comment.
  • Running ./script needs execute permission. Running sh script does not; it only needs read permission.
  • Running sh script ignores the shebang, so the interpreter is sh even if line 1 says bash.
  • $? is 0 for success. A command that prints an error can still return 0; a command that prints nothing can return 1.
  • Builtins like cd and echo are not found through PATH. A function or alias can also hide an external program.

3.2 Shell variables and operators

A shell variable is a name that holds a string. The shell uses variables to keep a path, a user name, a count or any text a script needs later. Quoting decides what happens when the shell reads a variable: it may expand to its value, stay as literal text, or split into several words. Every script uses this for configuration, counters and tests.

You need: Chapter 3.1 for how the shell reads a command line.

Storing and reading a value

A variable is a name that holds a string. The shell does not care whether the text looks like a number; COUNT=7 stores the character 7, not an integer. To assign, write NAME=Asha. There must be no spaces around the = sign. The shell reads NAME = Asha as a command called NAME with two arguments.

Read the value with $NAME or ${NAME}. The braces mark the end of the name, so ${NAME}file gives Ashafile while $NAMEfile looks for a variable called NAMEfile. Use braces whenever text follows the name.

export NAME passes the variable into child processes as an environment variable. Without export, a script started from this shell does not see NAME. readonly NAME locks the value; a later assignment fails. unset NAME removes it.

Two useful forms: ${VAR:-default} gives the value of VAR, or default when VAR is unset or empty. ${#VAR} gives the number of characters in the value. Arrays exist in Bash, but only a few universities teach them in a first shell course; treat them as advanced.

Quoting decides expansion

Quoting controls expansion. Single quotes keep every character literal: echo '$NAME' prints $NAME. Double quotes expand variables and command substitution, but keep the result as one word: echo "$NAME" prints the value. A backslash \ escapes the next character, so echo \$NAME prints $NAME, with the dollar sign as literal text.

Unquoted text is split into words on spaces, tabs and newlines, and patterns such as * are expanded. If NAME='Asha Rao', echo $NAME prints two words, while echo "$NAME" prints one. Quote variables in scripts unless you truly want splitting.

Command substitution runs a command and puts its standard output in place. Use $(command); the older backtick form `command` does the same and is harder to nest. For example, TODAY=$(date +%F) stores a date string.

Arithmetic expansion computes with integers: $((expression)). It supports +, -, *, / and %. Division truncates toward zero, so $((7/2)) is 3 and $((7%2)) is 1. A bare $COUNT+3 is just text: 7+3. Write $((COUNT+3)) to get 10.

Operators for tests

Conditional tests use operators. String tests compare text: [ "$A" = "$B" ] is true when equal, [ "$A" != "$B" ] when different. [ -z "$A" ] is true when the string is empty, and [ -n "$A" ] when it is not empty. Always quote the variable inside [ ].

Numeric tests compare integers: -eq equal, -ne not equal, -lt less than, -le less than or equal, -gt greater than, -ge greater than or equal. Write [ "$COUNT" -eq 7 ]. The string form = would compare the characters, so "05" = "5" is false while "05" -eq 5 is true.

File tests check the file system: -f path is true for a regular file, -d for a directory, -r readable, -w writable, -x executable. They are used with if, case and loops; Chapter 3.3 shows the control-flow syntax. Spaces around [ and ] and around each operator are required.

These operators are the vocabulary of decisions: compare a count, test a string, or check that a file exists before reading it.

3.3 Conditionals and loops in shell scripts

Shell scripts need to choose and repeat. The shell decides by exit status: every command returns a number to $?, where 0 means success and true, and any non-zero value means failure and false. If, case, while, until and for read that status and decide which commands run. This is how a script checks whether a file exists, validates user input, counts lines, or processes a list of servers. The rule is small but strict, and it explains most beginner mistakes with tests and loops.

You need: Chapter 3.2 Shell variables and operators for variables, quoting and expansion; Chapter 3.1 Shell basics helps with sh versus Bash.

Exit status and the if ladder

Every command, built-in or external, returns an exit status. The shell stores it in $?. Status 0 means success, and the shell treats it as true. Any non-zero value means failure, and the shell treats it as false. This is opposite to C, where 0 is false.

if runs a command and reads its status. If the status is 0, the then block runs. If not, the next elif test runs; else is the final fallback. The whole ladder ends with fi. Only the first true branch runs.

if test -f file; then cat file; elif test -d dir; then ls dir; else echo error; fi is one ladder. test -f file is true when file is a regular file. test -d dir is true when dir is a directory. Any command can sit after if, including grep -q or a script. The shell does not read text truth; it reads the command's exit status.

Tests, [[ ]] and case

test and its alias [ compare values and return an exit status. Spaces are required: [ -f file ] is a command; [-f file] is one word and fails. The closing ] is an argument to test. Bash also has [[ ... ]], a keyword with the same idea plus &&, || and pattern matching.

  • String: = equal, != not equal, -z empty, -n non-empty.
  • Numeric: -eq, -ne, -lt, -le, -gt, -ge.
  • File: -f regular file, -d directory, -r readable, -w writable, -x executable.
  • Quote variables: [ "$x" = yes ] works when x is empty; [ $x = yes ] becomes [ = yes ] and fails. Use -eq for numbers; [ 01 -eq 1 ] is true, while [ 01 = 1 ] is false because those are strings.

case matches one value against patterns and ends with esac. Each branch ends with ;;. Only the first matching branch runs: case $ans in y|Y) echo yes;; n|N) echo no;; *) echo other;; esac.

Loops, break and continue

while repeats while its command returns 0: while [ $i -lt 3 ]; do echo $i; i=$((i+1)); done. The counter starts before the loop and must change inside it, or the loop never ends. until is the mirror: it repeats while the command returns non-zero, and stops when the command returns 0.

for has two common forms. The word-list form visits each word: for n in 4 7 10 13; do ...; done. The C-style form uses arithmetic: for ((i=0; i<5; i++)); do ...; done. In the C-style header, i=0 runs once, i<5 is tested before each pass, and i++ runs after each pass.

To read a file line by line, use while IFS= read -r line; do ...; done < file. -r stops backslash processing, and < file sends the file to standard input. break leaves the innermost loop at once; continue skips to the next pass. Use them when a search succeeds or a bad record must be skipped.

  • Unquoted empty variable: [ $x = 1 ] becomes [ = 1 ] and fails. Write [ "$x" = 1 ].

3.4 Shell functions and command-line arguments

A function packs a set of commands under one name. You call it like a command and pass it values, called arguments. Inside the function those values appear as positional parameters: $1 is the first, $2 the second. A function runs in the same shell as the script, so it can change variables around it unless you declare them local. It returns only an exit status, a number from 0 to 255. Real output goes to stdout. This keeps scripts short and lets one piece of logic serve many calls, from checking a UPI transaction ID to printing a report header.

You need: Chapter 3.2 for variables and quoting, and Chapter 3.3 for exit status and loops.

Define once, call many times

Definition: name() { commands; }. A space before { is safe. The call is name arg1 arg2, without parentheses. The shell checks functions before external commands of the same name.

greet() {
  echo "Hello, $1"
}
greet Ravi

Output

Hello, Ravi

The call greet Ravi sets $1 to Ravi inside the body. No new shell process starts. The current shell runs the body and then continues after the call. That matters for variables.

local limits a variable to the function in Bash:

count=0
bump() {
  local n=1
  count=$(( count + n ))
}
bump
echo $count

Output

1

This prints 1. n disappears after the call; count stays changed. Without local, every variable is global to the shell. POSIX sh lacks local; use rare names or a subshell when portability matters.

Return status, not data

Every command ends with an exit status. 0 means success; non-zero means failure. A function uses return n to set its status. n must be 0 to 255. If n is larger, the shell stores n modulo 256. return ends the function at once.

return cannot carry a string or a large number. return 3 shows up only as $? after the call. To send data, write to stdout:

add() {
  echo $(( $1 + $2 ))
}
sum=$(add 7 8)
echo "$sum"

Output

15

The command substitution $(...) runs add, collects stdout and drops the final newline. sum gets 15. The status of the assignment is the status of add. Use stdout for the result and return for success or failure. For a test, run if add 2 3 > /dev/null; then ...; fi; the redirection hides stdout but the status still chooses the branch. Redirection is in Chapter 3.5.

Positional parameters and shift

Inside a script or function, $1 is the first argument, $2 the second, and so on. Write ${10} for the tenth. Plain $10 means ${1}0, the first argument followed by the digit 0. $# is the number of arguments. $0 is the script name; inside a function it does not become the function name.

$@ and $* both list all arguments. Quoting changes the result. "$@" keeps one word per argument, so an argument with spaces stays whole. "$*" joins all arguments into one word using the first character of IFS, usually a space. Use "$@":

show() {
  for a in "$@"; do
    echo "[$a]"
  done
}
show "ICICI Bank" 500

Output

[ICICI Bank]
[500]

Unquoted $@ splits on spaces. shift removes $1 and moves the rest down. Old $2 becomes $1, and $# drops by one. shift 2 removes two. Process a list with:

while [ $# -gt 0 ]; do
  echo "arg: $1"
  shift
done

[ $# -gt 0 ] is true while arguments remain. getopts parses options such as -a and -b value; only a few universities teach it.

3.5 File input and output in scripts

A running program has three open channels: one for input, one for normal results, one for error messages. The shell numbers them 0, 1 and 2 and can point any of them at a file instead of the terminal, before the program starts. That is what file input and output means in a script: the script still reads stdin and writes stdout, but the shell has already swapped the destination. Nightly backups, cron jobs and log-writing scripts all rest on this one idea.

You need: 3.1 Shell basics, 3.2 Shell variables and operators for quoting, 3.3 Conditionals and loops for while, and the Unit 2 notes on file permissions to know who may read the file.

Standard input, standard output, standard error

Every process starts with three open channels called file descriptors. A file descriptor is a small whole number the kernel uses to name an open file. Number 0 is standard input, or stdin: the stream that read and cat take text from. Number 1 is standard output, or stdout: where echo and printf write results. Number 2 is standard error, or stderr: where error messages go. By default all three are attached to your terminal.

Why keep output and errors apart? Stdout carries data, clean lines that a program or a person will use later. Stderr carries complaints about the run. If both shared one channel, a line like cannot open file would sit inside your clean result. Separating them lets you save data in one file and warnings in another.

Redirection is done by the shell, not by the program. The program never learns a file name; it just writes to fd 1. So ls > list.txt works for every command, including ones written decades before you were born.

Redirection: pointing a descriptor at a file

  • cmd > file sends fd 1 to file. The shell creates the file, or empties it if it already exists, before cmd runs.
  • cmd >> file appends instead of truncating.
  • cmd < file opens file as fd 0.
  • cmd 2> file moves only the error stream; stdout still reaches the terminal.
  • cmd &> file (Bash) sends both streams to the same file.
  • 2>&1 means point fd 2 at wherever fd 1 points right now. It is an instruction about order, not a file name.

Order decides the result. ./run.sh > out.txt 2>&1 puts everything in out.txt, because fd 1 moves first and fd 2 then copies it. ./run.sh 2>&1 > out.txt first points fd 2 at the terminal, then moves fd 1 to the file, so errors still appear on screen.

/dev/null is a device that discards whatever is written to it and returns end of file on read. find / -name "*.conf" 2> /dev/null hides permission errors while you keep the real matches.

Several redirections can sit on one command line. ./count.sh < data.txt > out.txt 2> err.txt gives the script a file as input, a file for results and a third file for errors, all at once.

Reading a file line by line

read takes one line from stdin and cuts it into fields using IFS, the internal field separator. IFS is an ordinary shell variable holding the characters treated as separators; by default these are space, tab and newline.

In read -r a b, the first field goes to a and the rest of the line goes to b. The -r means raw: a backslash stays a backslash instead of escaping the next character.

The standard loop is while IFS= read -r line; do ...; done < file. Writing IFS= sets IFS to empty for that one command, so leading and trailing spaces survive. The < file after done attaches the file to stdin for the whole loop, so the file is opened once and read forward.

Avoid for line in $(cat file). Command substitution splits on spaces, so a name like Ravi Kumar becomes two items, a blank line vanishes, and the whole file is loaded into memory first.

A here-document feeds lines to stdin without a file. cat <<EOF, the lines, then EOF on its own line. Variables expand inside it; quote the marker as <<'EOF' to keep text literal. It is handy for writing a config file or feeding SQL to a client.

tee copies a stream: cmd | tee log.txt shows the output and saves the same bytes in log.txt. At end of file read returns a non-zero status, which simply stops the while loop. That is normal, not a failure.

Worked example

Question. A script count.sh contains only the loop body while read -r a b; do echo $((a + b)); done. It is run as ./count.sh < data.txt > out.txt 2> err.txt. The file data.txt holds exactly three lines: "1 2", "3 4" and "5 6". State the contents of out.txt, the contents of err.txt and the exit status of the script.

#!/bin/sh
while read -r a b; do
    echo $((a + b))
done
  1. Before the script runs, the shell opens data.txt as fd 0, creates out.txt as fd 1 and creates err.txt as fd 2. No command in the script names a file.
  2. Pass 1: read takes the line "1 2" and splits it on the space, so a = 1 and b = 2. $((1 + 2)) = 3, and echo writes 3 plus a newline to fd 1, which is out.txt.
  3. Pass 2: a = 3, b = 4, so $((3 + 4)) = 7 goes to out.txt.
  4. Pass 3: a = 5, b = 6, so $((5 + 6)) = 11 goes to out.txt.
  5. Pass 4: read finds no characters left, returns a non-zero status, and the while loop ends. Nothing failed, so nothing is written to fd 2.
  6. The script's exit status is the status of its last command, the loop, which ended normally: 0.

Exam traps

  • > empties the target before the command starts, so sort marks.txt > marks.txt leaves an empty file. Write to a second file, then move it.
  • 2>&1 copies where fd 1 points at that moment. Putting it before > out.txt sends errors to the terminal, not to the file.
  • Without -r, read treats a backslash as an escape and silently drops it, so Windows-style paths change when read.
  • A failing read at end of file is how the loop stops. Do not test it as an error and do not print a message for it.
  • done < file opens the file once for the whole loop; writing read -r line < file inside the body reopens and restarts the file every pass, giving an endless loop.

3.6 Pipes and filters for data processing

The pipe operator | connects the standard output of one command to the standard input of the next. A filter reads stdin, transforms or selects data, and writes stdout. Chains of small filters turn raw text into answers without temporary files. System administrators use pipelines on log files; analysts use them on CSV exports of sales, UPI transactions or attendance. The same few filters can process a Chennai power-cut log or a cricket score table.

You need: Chapter 3.5 for stdin, stdout and stderr, and Chapter 3.1 for running commands.

How a pipe moves data

The vertical bar | is the pipe operator. It starts the command on its left and the command on its right as two processes. The left command's standard output, file descriptor 1, becomes the right command's standard input, file descriptor 0. Error messages on file descriptor 2 do not enter the pipe unless you redirect them first; see Chapter 3.5.

Write cmd1 | cmd2 | cmd3. Data flows left to right. No temporary file is created. Each stage is a separate process. For example, cut -d, -f1,3 sales.csv | grep '^Delhi' sends only fields 1 and 3 of each comma-separated line to grep, and grep keeps lines that start with Delhi.

A filter reads stdin, does one job, and writes stdout. cut selects fields. sort orders lines. head limits lines. Small filters are easy to test alone and easy to reorder. A pipeline is the whole chain; its result appears on the stdout of the last stage.

Filters and their options

cut selects columns. cut -d, -f1,3 uses comma as the delimiter given by -d and prints fields 1 and 3 given by -f. sort orders lines. sort -t, -k2 -n uses comma as field separator, sorts on key field 2 given by -k, and compares numbers because of -n. Without -n, sort uses dictionary order, so 100 comes before 20.

Exit status and process isolation

A pipeline's exit status is the exit status of its last command. In cut -d, -f1,3 sales.csv | grep '^Delhi' | head -2, suppose grep finds no Delhi line. head still succeeds with status 0, so the pipeline reports success. The failure in the middle is hidden. This is a common pipeline trap.

Bash provides PIPESTATUS, an array with the status of every stage, and set -o pipefail, which makes the pipeline return the rightmost non-zero status. Only a few universities teach these. Plain POSIX sh may not have them. For portable scripts, test the important filter separately or write its result to a file.

Each stage is a separate process. A variable changed inside a stage may not be visible in the parent shell. printf 'a\n' | read x; echo "$x" often prints an empty line in POSIX sh because read ran in a process that exited. Use command substitution, a here-document, or a shell that defines the behaviour when the value must survive.

Use pipelines for quick reports on logs, CSV dumps and system output. Test each filter on a small file, then join the stages. See Chapter 3.8 for stricter checking.

3.7 Text processing with grep, sed and awk

grep, sed and awk are three text filters that turn a file into a small answer. grep picks whole lines that match a pattern. sed changes each line as it flows past, for example replacing a space with a comma. awk splits each line into fields, tests them, and can count or add values. Together they form a pipeline: find the useful lines, tidy the format, then summarise numbers. System logs, marks lists, CSV exports and UPI settlement reports are common places where these commands save an hour of manual work.

You need: shell variables and quoting from Chapter 3.2 and pipes and filters from Chapter 3.6.

grep selects lines by regular expression

grep prints every line that contains a match for a pattern. The pattern is a regular expression, not a shell glob. In a regular expression, ^ means start of line, $ means end of line, . means any one character, and * means zero or more repeats of the previous item. A bracket list [aeiou] matches one vowel; [^0-9] matches one character that is not a digit. These forms work in basic grep. Extended regular expressions add + (one or more), ? (zero or one), | (either side) and () for grouping; ask for them with grep -E. The old command egrep means the same as grep -E. Useful options: -i ignores case, -v inverts the match, -n prints line numbers, -c prints only the count, and -l prints only file names. grep returns exit status 0 when it selected at least one line, 1 when it selected none, and 2 on an error. Scripts can test that status; see Chapter 3.3.

sed edits a stream line by line

sed reads input line by line and applies a command to each line. The common substitution is sed 's/old/new/'. Without g, it replaces only the first match on each line. With g, sed 's/ /,/g' replaces every space with a comma. An address limits where a command runs: a line number like 2d, a range like 2,4d, or a pattern like /^R/d deletes matching lines. d deletes a line. By default sed prints every line after editing. -n suppresses that automatic print, so sed -n '3p' prints only line 3. The p command prints the current line. -i edits the file in place; it overwrites the original. Test the command without -i first, or use -i.bak to keep a backup. In-place editing needs write permission on the directory containing the file, because sed -i writes a temporary file there and renames it over the original. A read-only file in a writable directory can still be edited this way; see Unit 2, Files, Directories and Permissions.

awk processes records and fields

awk treats input as records, normally lines, and splits each record into fields. $1 is the first field, $2 the second, and $NF the last field of the current record. NF is the number of fields in this record. NR is the record number from the start of input. The separator is whitespace by default; -F, makes comma the field separator. A program has the shape pattern { action }. The action runs only when the pattern is true. With no pattern, the action runs for every record. A numeric-looking field such as $2 is compared as a number in $2 >= 60; a non-numeric string follows text comparison. BEGIN { ... } runs before the first record, and END { ... } runs after the last. print writes fields separated by spaces; printf gives format control. For a total, use { sum += $2; n++ } END { print n, sum }. Here sum holds the running total, n the count, and $2 the second field of the current record. Arrays and user functions in awk are advanced; only a few universities teach them.

Worked example

3.8 Error handling and debugging scripts

Scripts fail: a file is missing, an argument is wrong, a command is absent. Error handling makes those failures visible and controlled. You check the exit status, stop when a defined step fails, print a message to standard error, and leave a trace of what ran. Debugging is the other half: turn on tracing, read the trace, fix the first wrong command. Every reliable shell script uses these habits. The tools are status codes, set options, and trap cleanup.

You need: exit status in Chapter 3.3, functions in Chapter 3.4, and stderr in Chapter 3.5.

Exit status: the shell's report card

Every command ends with an exit status, an integer from 0 to 255. 0 means success. Any non-zero value means failure. The shell stores the status of the last command in $?, read as dollar question. After grep root /etc/passwd, $? is 0 if a line matched and 1 if none matched.

Common codes: 0 success; 1 general error; 2 misuse of a shell builtin or wrong option; 126 found but cannot execute; 127 command not found; 128+n killed by signal n. For example, a script killed by signal 9 reports status 137, because 128+9=137.

Test a command directly with if. if cp "$1" /backup; then echo copied; else echo "copy failed" >&2; exit 1; fi. The if reads the command's status; no $? test is needed. If you must print $?, save it first: cp "$1" /backup; s=$?; echo "status $s" >&2. The next command overwrites $?.

Send error text to stderr with >&2. stdout may be redirected to a data file, so errors on stdout would be lost or mixed into data. stderr stays on the terminal or goes to a log file.

Fail fast with set -e, trace with set -x

Put options after the shebang. set -e exits the script when a command returns non-zero. set -u exits when an unset variable is used. set -x prints each command after expansion, prefixed by +, to stderr. set -o pipefail makes a pipeline fail if any command in it fails, not only the last one. A common first line is set -euxo pipefail.

set -e has limits. It is ignored for a command used as an if or while condition, in a && or || list except the last command, and after !. So if grep -q root /etc/passwd; then ...; fi still handles a failed grep. This is deliberate: those forms test failure. In a function, the rules are subtle; test functions directly.

The figure shows backup.sh with three cp commands. The first cp returns 0. The second cp, on missing.txt, returns 1. With set -e the shell exits with status 1; the third cp and echo done do not run. Without set -e the shell continues, copies c.txt, prints done, and exits 0. That final 0 hides the failed copy, which is why fail-fast matters.

For debugging, run bash -x script.sh without editing the file. Turn tracing off with set +x. Trace output goes to stderr, so it does not corrupt data on stdout.

trap: cleanup and error messages

trap runs a command when the shell receives a condition. trap 'rm -f "$tmp"' EXIT runs cleanup when the script exits, by normal end or by set -e. trap 'echo "failed at line $LINENO" >&2' ERR runs when a command fails (the same exceptions as set -e apply: if/while tests, all but the last command of && / ||, commands after !). It works with or without set -e. Use single quotes so $tmp and $LINENO expand when the trap runs.

A logging function keeps messages consistent. log(){ echo "$(date) $*" >> "$log"; }; die(){ echo "error: $*" >&2; exit 1; }. Call die "missing file $1" on a bad argument. die writes to stderr and exits the script with status 1. Never follow an error with exit 0; that reports success.

Save status before cleanup. cp "$1" /backup || { s=$?; log "copy failed: $s"; exit "$s"; }. The || list keeps set -e from exiting before the log line; a bare cmd; s=$? only works when set -e is off. The EXIT trap keeps the same status unless you call exit inside it. Log both the message and the status, so a reader can reproduce the failure.

Use set -e for scripts that must stop, and explicit if tests for steps you can recover from. Check the first failing command in the trace, not the last line.

It prints start, then exits after false with status 1. end is not printed.

Analyze Why does set -e; if grep -q x file; then echo yes; fi; echo after still print after when grep fails? 4 marks

set -e is ignored for the command used as the if condition. The if condition is false, the then branch is skipped, and echo after runs.

Analyze A script uses trap 'rm -f "$tmp"' EXIT, then cp "$1" "$tmp" fails under set -e. What runs, and what status should the script report? 5 marks

The EXIT trap runs rm -f on the temporary file. The script should report the non-zero status of the failed cp, not 0.

Beyond the syllabus

Not for the exam. In industry, shell scripts are the glue in CI/CD, backup jobs and container entrypoints. Teams lint them with ShellCheck, run them under bash -x, and start with set -euo pipefail. The same ideas appear in Python automation through subprocess return codes and logging, and in systemd services through exit status and restart policies. Search for ShellCheck, Bash pipefail, and trap ERR for deeper study.

Takeaways

  1. The shell is both a command interpreter and a programming language; sh gives portable syntax and Bash adds extensions.
  2. Shell variables store strings, and quoting decides expansion, literal text and word splitting.
  3. Exit status is the basis of shell decisions: 0 means true or success, non-zero means false or failure.
  4. if, case and loops choose which commands run and repeat work over lists or input.
  5. Functions group commands, receive positional parameters, return an exit status and send data through stdout.
  6. File descriptors 0, 1 and 2 plus redirection and here-documents connect scripts to files and logs.
  7. Pipes chain filters so stdout of one command becomes stdin of the next command.
  8. grep, sed and awk cover line selection, stream editing and field summaries; debugging uses status checks, set -e, set -x, trap and logs.

Exam question bank

Long answers are expected to combine syntax with working script fragments: quoting and variables, exit-status control flow, functions and arguments, redirection and pipes, grep/sed/awk pipelines, and defensive error handling.

Remember and understand

Understand Explain the shell as both a command interpreter and a programming language. Compare the Bourne shell (sh) and Bash in portability and features. 10 marks

Shell reads a command line, expands words, executes commands and starts programs; Shell language includes variables, control flow, functions and redirection; sh is the portable POSIX base with small standard syntax; Bash is its successor and adds arrays, [[ ]], brace expansion and process substitution; Scripts choose #!/bin/sh or #!/bin/bash according to needed features.

Understand Explain shell variables and quoting. Show how unquoted, single-quoted and double-quoted values differ for $name and word splitting. 12 marks

Assignment is name=value with no spaces around =; $name expands to the stored string; Unquoted expansion splits on IFS and can glob; Single quotes keep every character literal; Double quotes expand variables but stop splitting and globbing; Backslash escapes a single character.

Remember Define exit status. Explain how if and loops use exit status, and how case selects branches by pattern. 10 marks

Exit status 0 means success or true; 1–255 means failure or false; if command; then ... uses the status of a command list; while runs while its condition returns 0; until runs until it returns 0; case matches a word against patterns and runs the first match; $? holds the last command status.

Understand Explain shell functions and positional parameters. How does a function return an exit status and how does it send data to the caller? 12 marks

Function name() { commands; } runs in the current shell; $1, $2, $# and $@ work inside the function; return n sets the function exit status; exit ends the whole shell or script; Data returns through stdout and command substitution; local limits a variable to the function.

Understand Explain stdin, stdout and stderr with their file descriptors. Describe the redirection operators <, >, >>, 2>, 2>&1 and <<. 12 marks

stdin is fd 0, stdout is fd 1, stderr is fd 2; < reads input from a file; > truncates and writes stdout to a file; >> appends; 2> redirects stderr to a file; 2>&1 sends stderr to the current stdout destination; order matters; << word is a here-document.

Apply

Apply Write a shell script that reads a file line by line, skips empty lines, counts non-empty lines and prints the count. Use a loop and input redirection. 12 marks

while IFS= read -r line; do ... done < file; [ -n "$line" ] tests for a non-empty line; count=$((count+1)) increments the counter; printf prints the final count; Variables are quoted to avoid splitting.

Apply Write a shell script that creates a configuration file with a here-document and sends error messages to a log file while normal output stays on the terminal. 10 marks

cat > config <<'EOF' writes literal lines until EOF; Quoting the delimiter stops expansion; command 2>> error.log appends stderr to the log; stdout remains on the terminal by default; exec 2>>log can redirect errors for the rest of the script.

Apply Use a pipeline of grep, sed and awk to read a log file, keep lines containing ERROR, remove a timestamp prefix, and print the count of messages per user field. 12 marks

grep 'ERROR' log selects matching lines; sed removes the prefix with a substitution; awk '{count[$NF]++} END {for (u in count) print u, count[u]}' summarises fields; Pipes connect stdout to stdin at each stage; Patterns are quoted to protect special characters.

Apply Write a shell function that validates whether its first argument is a positive integer and returns 0 or 1. Call it for two values and print a message based on status. 10 marks

Function reads $1; case "$1" in ''|*[!0-9]*) return 1;; esac rejects non-digits; [ "$1" -gt 0 ] checks positivity; return 0 or return 1 sets status; if validate "$x"; then ... tests the status; The function sends no data except through stdout.

Apply Write a menu-driven script using while and case that offers count lines, show first lines and quit; put each action in a function. 12 marks

while true; do prints the menu and reads choice; read -r choice reads the input safely; case "$choice" in runs the selected branch; Functions implement each action; break leaves the loop on quit; A default branch prints a usage message.

Analyze and evaluate

Evaluate A script run by cron fails at night with no message. Explain how you would find and fix the failure using exit status checks, set -e, set -x, trap and logging. 14 marks

Reproduce the run and check $? after key commands; Add explicit tests and error messages; set -e stops on unchecked failures; note its exceptions; set -x prints a trace; redirect the trace to a log file; trap ERR or EXIT logs the failure point; Check cron environment: PATH, current directory and file permissions; Fix and retest the script.

Analyze Compare grep, sed and awk for selecting lines, editing text and summarising fields. Choose a tool for three data-cleaning tasks and justify each choice. 14 marks

grep selects lines by regular expression; sed edits each line of a stream, for example substitution or deletion; awk splits records into fields and supports arithmetic and END summaries; Pipelines combine the tools; Choice depends on task: selection, editing or field summary; Readability and speed guide the choice.

Analyze A pipeline processes filenames that contain spaces and sometimes fails to split fields correctly. Diagnose the quoting and IFS problems and show a corrected pipeline. 14 marks

Unquoted $file splits on IFS and can glob; Use while IFS= read -r line; do ... done with quoted "$line"; find -print0 with xargs -0 handles spaces safely; Avoid parsing ls output; Quote all variable expansions; Test with filenames containing spaces.

Glossary

argument
Word passed to a command after its name; inside scripts it is available as a positional parameter.
break
Loop control command that leaves the nearest enclosing loop.
comment
Text beginning with # that the shell ignores, except inside quotes or a here-document.
continue
Loop control command that skips to the next iteration of the nearest enclosing loop.
elif
Short for else if; tests another condition after a failed if branch.
environment variable
Variable exported to child processes; it appears in their environment.
exit
Shell builtin that ends the current shell or script with a status.
field separator
In awk, FS; the input character or regular expression that divides each record into fields $1, $2, ...
file descriptor
Integer handle for an open file or stream; 0, 1 and 2 are the standard descriptors.
for loop
Loop that assigns each word from a list to a variable and runs the body once per word.
globbing
Shell pathname expansion that replaces patterns containing *, ? or [ ] with matching filenames.
IFS
Internal Field Separator; characters used for word splitting and for read to divide fields.
local variable
Variable declared with local in a function; visible in that function and its called functions, not in the parent shell.
pipefail
Bash option set -o pipefail; a pipeline's status is the rightmost non-zero status, or zero if all succeed.
regular expression
Pattern language for matching text; used by grep, sed, awk and shell case patterns.
return
Shell builtin that ends a function and sets its exit status to the given number.
shebang
First line #!interpreter in a script; the kernel uses it to choose the interpreter.
stderr
Standard error, file descriptor 2; default destination for error messages.
stdin
Standard input, file descriptor 0; default source of input for commands.
stdout
Standard output, file descriptor 1; default destination for normal command output.
tee
Filter that copies stdin to stdout and to one or more files.
test command
Builtin [ or test that evaluates a condition and returns exit status 0 if true.
trap
Shell builtin that runs a command when the shell receives a signal or exits.
until loop
Loop that runs while its condition command returns non-zero; stops when it returns 0.
variable expansion
Replacing $name or ${name} by the variable's value.
word splitting
After expansion, unquoted results are split into words using characters in IFS.
