1.1 History and evolution of Unix and Linux

Unix and Linux are related by design, not by shared source code. Unix began in 1969 at Bell Labs as a small multiuser system. It was rewritten in C in 1973, which made it easier to move to new computers. Different groups then built BSD and System V, and POSIX later set a common interface. Linux is a free Unix-like kernel (the core program of an operating system) that Linus Torvalds started in 1991. With GNU tools, it became a complete system used on servers, Android phones, cloud machines and routers. The timeline and the design ideas that survived explain today's command line.

You need: no earlier chapter; this is the first chapter.

Unix at Bell Labs

Unix began at Bell Labs in 1969. The usual names are Ken Thompson and Dennis Ritchie. They wanted a small multiuser operating system for a spare DEC computer. Multiuser means many people can log in at once. Multitasking means many programs can run at once. The first version was written in assembly language, which ties code to one machine.

In 1973 the team rewrote Unix in C. C is a portable systems programming language. A C compiler can be built for many processors, so the same source can be rebuilt on a new computer. This rewrite helped Unix spread to universities and companies.

Two families became important: BSD from Berkeley and System V from AT&T. They shared ideas but differed in system calls and tools. A program written for one might not build on the other. POSIX addressed this by defining a standard set of interfaces. POSIX is not an operating system; it is a written standard. A program that uses only POSIX calls can be built on many Unix-like systems.

The kernel is the core program that manages memory, processes and devices. The shell is an ordinary user program that reads commands and asks the kernel to act. Their split is covered in Kernel, shell and user space.

Linux starts in 1991

Minix was a small Unix-like teaching system. It gave students source code to read, but it was not a full production kernel. Linus Torvalds, then a student in Finland, began a kernel for his own PC. In 1991 he announced the project; the first public version was small. He chose the GNU General Public License, or GPL. The GPL is a copyright licence that lets anyone run, study, change and redistribute the code, provided derived code keeps the same licence. This is one form of open source; see Open source software and its benefits.

Linux is the kernel, not the whole system. A usable system also needs libraries, compilers, a shell and commands. Much of that came from the GNU project, which had built free tools but lacked a working kernel. The combination is often called GNU/Linux. Linux 1.0 appeared in 1994. Later, distributions packaged the kernel with tools and an installer; see Linux distributions and installation. Features such as multi-user login and loadable modules are covered in Linux features.

Because the source was free, many people could fix bugs and port the kernel to new machines. That is why Linux reached servers, phones and embedded boards. Android, for example, uses a Linux kernel. The kernel is not Unix source code; it is an independent Unix-like kernel.

Design ideas that survived

Unix and Linux share a style of design. Small tools do one job well. A tool reads text, writes text, and exits. The shell connects tools with pipes, so the output of one becomes the input of the next. The shell is a program that reads commands and starts other programs. This is why text streams matter: a log file, a CSV file or a command output can all be processed by the same filters.

The phrase everything is a file is a shorthand. In Unix-like systems, many resources are reached through file operations: open, read, write, close. A device, a pipe or a network socket can be used through a file descriptor, which is a small integer that names an open file. This does not mean every object is a regular file on disk; it means the same interface is reused. Unit 2 covers files and permissions; Unit 3 covers pipes and filters.

Portable C is another pillar. The kernel and tools are mostly written in C. When C is available on a new CPU, much of the software can be rebuilt with few changes. The shell is also portable: a script written for a POSIX shell can run on many systems. The command line is that text loop; see Command-line interface and basic commands.

These ideas are not laws. They are conventions that make systems easy to combine. A small tool can be tested alone. A text stream can be inspected by eye. A file interface can be reused by many programs. That is the practical legacy of Unix, and Linux carries it forward.

Worked example

Question. Arrange these four events in time order and give the gap in years between the first and last: Linux 1.0 (1994), Unix work begins (1969), Linux kernel announced (1991), Unix rewritten in C (1973).

  1. Read each event with its year: Unix work begins = 1969; Unix rewritten in C = 1973; Linux kernel announced = 1991; Linux 1.0 = 1994.
  2. Sort by year in ascending order: 1969 Unix work begins, 1973 Unix rewritten in C, 1991 Linux kernel announced, 1994 Linux 1.0.
  3. First year = 1969. Last year = 1994.
  4. Gap = last year − first year = 1994 − 1969 = 25 years.

Answer. The order is Unix work begins (1969), Unix rewritten in C (1973), Linux kernel announced (1991), Linux 1.0 (1994); the gap is 25 years.

Exam traps

  • Linux is not a version of Unix source code; it is an independently written Unix-like kernel.
  • BSD and System V are Unix branches, not Linux distributions. A Linux distribution packages the Linux kernel with tools.
  • POSIX is an interface standard, not an operating system or a kernel.
  • The GPL is a software licence; it does not mean the code has no owner.
  • The key dates are 1969 for Unix work, 1973 for the C rewrite, 1991 for the Linux kernel announcement and 1994 for Linux 1.0; do not swap them.

1.2 Linux features: multi-user, multitasking, modularity

Linux features are properties that let one computer serve many people and many programs at the same time, and still change kernel code after boot. The three core features are multi-user access, multitasking and modularity. Multi-user means separate accounts and permissions. Multitasking means a preemptive scheduler shares CPU time among processes. Modularity means the kernel can load and unload code modules. These features make Linux common on shared lab servers and cloud machines, where one machine serves many users at once, and the same kernel sits inside every Android phone.

You need Chapter 1, History and evolution of Unix and Linux, and Kernel, shell and user space for the kernel and shell split.

Multi-user: separate accounts, not many terminals

Multi-user means one running Linux system keeps separate accounts for different people. Each account has a user name and a numeric user ID (UID). The system also records group IDs, which grant shared rights. During login, the system checks the password and starts a shell that carries that identity. From then on, every file open, read, write or execute is checked against the permissions of that account. Two users can run the same command and get different results because their files and rights differ. A person may open several terminal windows, but that is still one account. Multi-user is not just many terminals. The useful part is isolation: a student cannot edit another student's marks file unless permissions allow it. On a shared lab server, three students can log in and each gets a shell and a home directory. The kernel still has one set of hardware to protect.

  1. User enters a name and password at login.
  2. System checks the password and starts a shell with the user's UID and groups.
  3. Every file access from that shell is checked against permissions.

Multitasking: sharing one CPU core by turns

Multitasking means one system runs many processes over the same period. A process is a running program with its own memory and state. A CPU core can execute only one process at a time. The kernel's scheduler gives each ready process a short turn, called a time slice. When the slice ends, or when a higher-priority process becomes ready to run, the kernel preempts the running process and switches to another. Preemptive means the kernel can take the CPU back without the program's permission. This fast switching creates the illusion of simultaneous work. Ninety processes on two cores do not run truly together; at any instant at most two run. The scheduler rotates the rest. Multitasking is about time-sharing CPU time, not about having many CPUs. Multiprocessing is many cores; multitasking can exist on one core. The lab server case combines both features: multi-user lets the students log in, and multitasking lets ninety processes share two cores.

Modularity: a monolithic kernel with loadable modules

Modularity means the kernel is built from parts that can be added or removed while the system runs. Linux is monolithic: most core services run in kernel space, the privileged memory area. But Linux also supports loadable kernel modules (LKMs). A module is compiled kernel code, such as a device driver or file-system driver, that can be loaded with modprobe and removed with rmmod. The kernel calls the module's init function on load and its exit function on unload. This keeps the base kernel small while allowing new hardware support without a reboot. Modularity does not make Linux a microkernel. A microkernel moves services out of kernel space; Linux keeps them in the kernel and loads modules into the same privileged space. A layered design appears inside the kernel: system-call interface, virtual file system, device drivers and hardware. The module joins the kernel layer. Some syllabi call this set 'Design principles of Linux'.

Worked example

Question. A lab server has 4 logged-in students, 90 processes and 2 CPU cores. Each student has one login shell. Which Linux feature lets all 4 students work at once? Which feature lets the 90 processes share the 2 cores? Also compute the average number of processes per core.

  1. Separate accounts and permission checks let 4 students log in and work without seeing each other's private files. That feature is multi-user. The count is 4 users.
  2. A core runs one process at a time. The scheduler gives turns to 90 processes on 2 cores. That feature is multitasking. The count is 90 processes and 2 cores.
  3. Average processes per core = total processes ÷ cores = 90 ÷ 2 = 45 processes per core.
  4. Name both features: multi-user and multitasking.

Answer. Multi-user lets 4 students work at once, and multitasking lets 90 processes share 2 cores at an average of 45 processes per core.

Exam traps

  • Multi-user is about separate accounts and permissions, not many terminal windows. One account can open many terminals.
  • Multitasking is not multiprocessing. A single-core machine can multitask by time-sharing; many cores add parallel execution.
  • Modularity does not mean Linux is a microkernel. Linux is monolithic with loadable modules that run in kernel space.
  • Preemptive means the kernel can take the CPU back. Cooperative multitasking waits for the program to yield.
  • A kernel module is not a user program or an installed package. It is kernel code loaded into privileged memory.

1.3 Kernel, shell and user space

A Linux computer separates power. The kernel is the privileged core that owns the hardware: it schedules processes, manages memory, and talks to disks and network cards. Everything else, including the shell you type into, runs in user space with limited rights. The shell is an ordinary program: it reads a command line, starts other programs, and asks the kernel to act through system calls. This split is why one bad program rarely crashes the machine, and why a small shell can control a large system. You meet it every time you type a command.

You need Chapter 1.1 for Unix and Linux history and Chapter 1.2 for multi-user, multitasking and modular kernel ideas.

Kernel mode and user mode

The CPU has at least two privilege levels. In kernel mode, code can execute every instruction and touch every memory address. In user mode, code is restricted: it cannot directly read a disk or change page tables. The kernel runs in kernel mode. Your programs run in user mode. A mode bit in the CPU status register decides which level is active; a trap or interrupt switches the CPU into kernel mode.

The kernel is the part of the operating system that stays in memory. It schedules which process runs on the CPU, manages virtual memory and page tables, runs device drivers, and provides system calls. A system call is a controlled entry point from user mode to kernel mode. Examples are open, read(2), write, fork and execve. User code puts a system-call number and arguments in registers, then executes a trap instruction. The CPU switches to kernel mode, the kernel checks the request, does the work, and returns to user mode.

The layers are simple to draw. Hardware is at the bottom: CPU, RAM, disk and network card. The kernel sits above it in privileged mode. The system-call boundary is the gate between modes. User programs sit above that gate: the shell, utilities such as ls and vi, and applications such as a browser.

The shell is an ordinary user program

The shell is a command interpreter. It prints a prompt, reads a line from the terminal, parses it into words, performs expansions, and decides what to run. bash, zsh and sh are shells. None is part of the kernel. When you type ls, bash does not read the directory itself. It searches the directories listed in PATH, an environment variable, finds /bin/ls, starts it as a child process, and waits.

The shell resolves a command line in this order: alias, reserved word or keyword such as if and while, function, built-in, then an external file found in PATH. The common cases are four. A shell built-in runs inside the shell process, so it can change the shell's own state; cd and export are built-ins. An external command is a separate program file such as /bin/ls. An alias is a shell shortcut for another command line. A function is a named block of shell commands. For an external command, the shell calls fork to make a child and execve to load the program. fork and execve are system calls, so the kernel performs them, but the decision to call them is made by the shell in user mode.

Utilities are separate programs too: ls, cp, grep, vi and your browser all live in user space. They use the same system-call boundary. A new utility does not need a new kernel. A faulty editor usually dies without stopping the kernel. The shell plus utilities form the user-visible command line; the kernel remains the shared foundation underneath.

Why the boundary matters

The boundary gives protection and stability. A user process cannot write to another process's memory or to raw disk blocks unless the kernel allows it. The kernel checks every request: file permissions, memory addresses, device access. If a program divides by zero or dereferences a bad pointer, the CPU raises a fault; the kernel may kill that process, but other processes and the kernel keep running.

The cost is overhead. Each system call switches mode and copies small amounts of data. Programs batch reads and writes instead of asking the kernel for one byte at a time. The split also makes the shell replaceable: you can run bash, dash or zsh on the same kernel. A distribution packages a kernel with libraries, shells and utilities; see Chapter 1.5. The simple rule: the kernel is privileged and shared; the shell is unprivileged and yours.

Worked example

Question. A user types ls and presses Enter in bash. Trace the steps: shell parses the line; shell starts /bin/ls; ls makes system calls; the kernel returns directory bytes and ls prints. Which steps run in user mode and which in kernel mode? Name the two user processes.

  1. bash is in user mode. It calls read(2) on the terminal; the kernel's terminal driver runs in kernel mode, takes the bytes for the line ls, and returns them to bash. bash parses the line into one word, ls, expands no variables, and sees that ls is not a built-in. Still user mode.
  2. bash searches PATH, finds /bin/ls, and calls fork. The kernel runs in kernel mode to create a child process. fork returns 0 in the child and the child's process ID (PID) in bash. bash calls waitpid and sleeps.
  3. The child calls execve('/bin/ls', argv, envp). By convention argv[0] is the command name ls, the remaining entries are the arguments, and envp holds environment strings of the form NAME=value. The kernel runs in kernel mode, checks the file, replaces the child's memory image with the ls program, and returns to user mode at the entry point of ls. The process keeps the same PID.
  4. ls runs in user mode. It calls open and read(2) on the directory; each call traps to the kernel, where the file system and disk driver fetch directory bytes and return them. ls formats the names and calls write; the kernel sends the bytes to the terminal. ls exits; the kernel notifies bash; bash prints the next prompt.

Answer. bash and ls are the two user processes; parsing, formatting and printing happen in user mode, while fork, execve, open, read, write and process creation run in kernel mode.

Exam traps

  • The shell is not the kernel. bash is a user program; the kernel is the privileged core.
  • cd cannot be an external program. It changes the shell's own current directory, so it must be a built-in.
  • A utility, a shell built-in and a system call are different: ls is a utility, cd is a built-in, and getpid or write(2) is a system call; bash also has a built-in called read, which is not the read(2) system call.
  • fork and execve are not the same: fork copies a process; execve replaces its memory image.
  • User mode does not mean no kernel work: every file read crosses into kernel mode through a system call.

1.4 Open source software and its benefits

Open source software is software whose source code is published under a licence that lets people study it, change it and share changed copies. The idea exists because closed software hides the code, so only the vendor can fix or extend it. In practice open source runs phones, web servers, data-centre tools and the Linux systems in this course. This chapter explains source code, licences, the benefits and the real costs.

You need: Chapter 1.1 for Unix and Linux history and Chapter 1.3 for kernel, shell and user space.

Source code and the licence

Source code is the human-readable form of a program: the C, Python or shell statements that a programmer writes. A compiler or interpreter turns it into machine instructions, often called binaries. When you buy closed software, you usually get binaries only. Open source software ships the source code as well, under a licence.

A licence is the legal document that says what you may do with the software. Copyright gives the author control by default: others may not copy, modify or redistribute without permission. An open-source licence gives those permissions on stated conditions. A copyleft licence, such as the GNU General Public License (GPL), requires anyone who distributes a modified version to use the same licence and provide source. The change stays open. A permissive licence, such as MIT or BSD, allows modification and redistribution, including inside closed products, provided copyright notices are kept. So open source is not one rule; the licence decides the duties.

Benefits that matter

Open source lowers lock-in: you can change vendor or hire another team because the code is available. Auditability is the power to inspect what the program does. A bank, hospital or election office can read the code or pay an auditor to check it, instead of trusting a vendor's promise. The licence usually carries no per-seat fee, so cost does not grow with every extra user or lab PC. Local customization is possible: a college can add a local language menu, and a firm can patch a bug that matters only to its workflow. Community support means bug reports, patches and documentation come from many users; a widespread problem is often fixed once and shared. Long-term use improves because the source survives even if the original vendor stops selling the product. These benefits are why Linux runs most web servers, Android phones and many government systems.

Costs and fair comparison

The benefits are real, but open source is not zero cost. Support may be bought from a company or handled by your own staff. Training takes time because tools differ from the old system. Migration has a one-time cost: converting files, testing printers and changing scripts. Staff time is a running cost. A fair comparison adds these items:

Total cost = licence fees + support + training + migration + staff time

licence fees is what you pay for the legal right to use the software; support is paid help; training is user and admin learning; migration is the one-time move from the old system; staff time is ongoing internal effort.

Here licence fees may be ₹0 for an open-source product, but the other terms are not zero. A proprietary product also has training and migration costs, so compare like with like. The licence still exists: it gives permissions and imposes conditions, such as keeping notices or sharing changes. 'Free' in free software means freedom to study, run, change and share, not a price tag. Freeware is different: it is free of charge but may hide its source and forbid modification.

Worked example

Question. A college needs an operating system for 40 lab PCs. A proprietary licence costs ₹8,000 per PC. A Linux distribution has ₹0 licence cost but ₹60,000 total support. Compute the proprietary licence cost, the open-source total, and the saving against the proprietary licence alone.

  1. Proprietary licence per PC = ₹8,000.
  2. Number of PCs = 40.
  3. Proprietary licence cost = 40 × ₹8,000 = ₹3,20,000.
  4. Open-source licence cost = ₹0.
  5. Open-source total = ₹0 + ₹60,000 support = ₹60,000.
  6. Saving against the proprietary licence alone = ₹3,20,000 − ₹60,000 = ₹2,60,000.

Answer. The open-source route costs ₹60,000, so the saving against the proprietary licence alone is ₹2,60,000.

Exam traps

  • Open source does not mean zero cost. Support, training, migration and staff time still cost money.
  • Open source is not 'no licence'. It has a licence that grants rights and often imposes duties, such as keeping notices or sharing changes.
  • 'Free' in free software means freedom to study, run, change and share, not price. Freeware may cost nothing but can be closed.
  • Copyleft and permissive licences differ. GPL-style copyleft requires modified distributed versions to stay under the same licence; MIT and BSD allow closed products if notices are kept.
  • Publishing source is not enough. If the licence forbids modification or redistribution, the software is not open source in the usual sense.

1.5 Linux distributions and installation

A Linux distribution, or distro, is the Linux kernel packed with libraries, system tools, a shell, an installer and a package manager, so a computer becomes usable after one installation. The kernel alone cannot run your programs; it needs those parts plus a way to fetch more software. Distros exist because assembling all of it by hand is slow and easy to get wrong. You meet them when you format a laptop with Ubuntu, when a server runs RHEL, or when you boot a live USB to repair a machine that will not start.

You need: Chapter 1.3 for the kernel and shell split, and Chapter 1.4 for why the source code is shared.

What a distribution actually contains

The kernel is one file plus loadable modules. On its own it can start a processor and manage memory, but it gives you no way to type a command. A distribution adds the missing layers and a program that copies them onto your disk.

  • Kernel: the privileged core; it talks to hardware and schedules processes.
  • init: the first program the kernel starts, which then starts everything else, usually systemd.
  • Shell and core utilities: Bash plus hundreds of small commands such as ls, cp and grep.
  • Package manager: the tool that downloads, installs, updates and removes software in signed packages.
  • Desktop: optional; GNOME, KDE Plasma or a plain text console.
  • Installer: the menu-driven program that writes this set onto a disk or a virtual disk.

Only the kernel is common to every distro. Two distros can run the same kernel version and still feel different, because their installer, package manager and default tools differ.

A release is a frozen snapshot of all these parts, given a version number. A long-term-support (LTS) release keeps receiving security fixes for several years without jumping to new versions of the tools. Ubuntu publishes an LTS every two years and supports it for five years. This matters in a lab of 30 machines: you install once, and the same commands keep working for years.

The main distribution families

Distros are grouped by the package format they inherit, because that decides which software you can install with one command.

Debian is community-run and favours stability. Ubuntu is built on Debian and adds its own installer, hardware support and release schedule. Fedora is a fast-moving testing ground for RHEL, the commercial Red Hat distribution used on many company servers. Arch ships almost nothing by default and expects you to build the system yourself. SUSE is strong in European enterprise installations.

Package names are not interchangeable. A .deb package belongs to Debian-family systems, an .rpm package to Fedora and SUSE systems. The commands to install them are taught in Unit 4, Package management.

Where you install it

Before any files are copied, the installer asks where Linux should live. There are four common answers.

  1. Pick the language, keyboard layout and time zone.
  2. Choose the target disk or virtual disk. The installer shows a summary of what it will erase.
  3. Create a user account and a password. This user can become root later.
  4. Select the software set: desktop, server tools, development packages.
  5. Let the installer copy files, then reboot into the new system.

A dual-boot machine gives Linux the whole processor and memory when it runs, but only one operating system runs at a time. A virtual machine runs both at once and shares the hardware, so it is slower. In a college lab, one clean install followed by cloning the disk is faster than repeating the installer on every PC.

Worked example

Question. A lab has 30 identical PCs that must all run Ubuntu. One clean installation on a PC takes 25 minutes. After that first PC is ready, its disk can be cloned to another PC in 10 minutes per clone, and every one of the 30 PCs needs a finished disk. Compare the time for installing each PC separately with the time for installing once and cloning the rest. Give the saving in minutes and in hours.

  1. Separate installs: each of the 30 PCs takes 25 min. Time = 30 × 25 = 750 min.
  2. Convert to hours: 750 ÷ 60 = 12.5 h, that is 12 h 30 min.
  3. Install once, then clone: the first PC costs 25 min; the other 29 PCs cost 10 min each. Clone path = 25 + 29 × 10.
  4. 29 × 10 = 290 min, so the clone path = 25 + 290 = 315 min.
  5. Convert: 315 ÷ 60 = 5.25 h, that is 5 h 15 min.
  6. Saving = 750 − 315 = 435 min.
  7. Convert the saving: 435 ÷ 60 = 7.25 h, that is 7 h 15 min.

Answer. Install-one-then-clone takes 315 min (5 h 15 min) instead of 750 min (12 h 30 min), a saving of 435 min (7 h 15 min).

Worked example 2

Question. A single laptop is set up to dual boot Ubuntu and Windows. A student also runs Ubuntu inside a virtual machine on a lab PC that has Windows installed. State two differences between the two setups.

  1. In dual boot, only one operating system runs at a time; the boot menu chooses which one starts.
  2. In a virtual machine, Windows keeps running and Ubuntu runs as a guest process inside it, sharing processor and memory.
  3. Dual boot gives Ubuntu the full hardware; the virtual machine is slower because resources are shared.
  4. Dual boot changes the disk partitions; the virtual machine stores Ubuntu in a disk image file on the host.

Answer. Dual boot runs one OS at a time with full hardware and real partitions; a virtual machine runs both OSes together, sharing hardware, inside a disk image file.

Exam traps

  • A distribution is not just the kernel. Ubuntu and Fedora run the same Linux kernel but differ in installer, package manager and default tools.
  • Dual boot is not a virtual machine. Dual boot switches between operating systems at start-up; a virtual machine runs the guest while the host stays on.
  • A live USB is not an installed system. Changes made while running from the pen drive usually vanish on shutdown unless you ask for persistence.
  • Package managers are tied to families. Do not tell an examiner that dnf installs .deb packages or that apt belongs to Fedora.
  • LTS means long support, not the newest software. An LTS release deliberately holds older, tested versions of its tools.

1.6 Command-line interface and basic commands

The command line is a text loop. The shell prints a prompt, you type one line, the shell runs it, prints the result, and the prompt returns. The same line always does the same thing, and a line saved in a file can be run again tomorrow. That is why servers and cloud machines are run from a terminal: exact, scriptable, cheap over a slow ssh link. This chapter shows the loop, the shape of a command, and the commands for moving around directories and looking after files.

You need: the kernel/shell split from Chapter 1.3 and the idea of a login session from Chapter 1.5.

The prompt loop and the shape of a command

Open a terminal and the shell prints a prompt and waits. A typical prompt is ravi@laptop:~$ — user name, machine name, current directory, then a $ sign. A $ means an ordinary user; a # means root. You type a line and press Enter. The shell splits the line into words, finds the program named by the first word, runs it, shows its output, and prints the prompt again.

Every line has the same shape. The command is a program name and must come first. Options change how the command behaves; short options start with one hyphen (-l) and long options with two (--all). Arguments are the things the command acts on, usually file or directory names. Spaces separate the words. Case matters: ls works, LS does not. So ls -la /tmp means: run ls, with combined options -l and -a, on the directory /tmp.

command [options] [arguments]

command is the program name; options are flags such as -l or --all; arguments are file names, directory names or other words the command needs. Square brackets mean optional.

Words are exact and repeatable. The same line gives the same result, and a line can be stored in a file and replayed. It also survives a slow link, which is why remote servers are managed this way.

Moving around and listing: pwd, cd, mkdir, rmdir, ls

pwd prints the absolute path of the current directory, that is, the full path starting from the root /. cd changes that directory: cd notes enters a subdirectory, cd /home/ravi goes to an absolute path, cd .. goes to the parent, cd with no argument goes to your home directory, and cd - returns to the previous directory. mkdir notes creates a directory. mkdir -p a/b/c creates the whole chain and does not complain if part already exists. rmdir removes a directory only when it is empty.

ls lists the names in a directory. ls -a also shows names beginning with a dot, which are hidden by default, plus . (this directory) and .. (the parent). ls -l prints one long line per entry. Combine them as ls -la.

Viewing, printing and file operations

cat a.txt prints the whole file to the screen; it suits short files. more a.txt shows one screen and waits for the space bar. less a.txt does the same but scrolls both ways, and q quits. lpr a.txt sends the file to the printer queue, so printing from a terminal needs no application.

cp a.txt b.txt copies the contents into b.txt. Add -r to copy a whole directory. mv a.txt /tmp/work/ moves the file; mv a.txt c.txt renames it in place. rm a.txt deletes a file, and rm -r notes deletes a directory with everything inside it. ln a.txt hard makes a hard link, a second name for the same file; ln -s /home/ravi/a.txt shortcut makes a symbolic link, a small file that points at the target. find /home/ravi -name "*.txt" walks the tree and prints matching paths.

chmod changes permissions in one line: chmod u+x run.sh adds execute for the owner, and chmod 644 a.txt gives the owner read and write, everyone else read. Permission bits, owners and groups are covered properly in Unit 2.

The vi editor and getting help

vi a.txt opens a file and creates it on the first save. vi has modes. You start in command mode, where keys are commands, not text. Press i to enter insert mode and type your line. Press Esc to return to command mode. Then :w writes to disk, :q quits, :wq writes and quits, and :q! quits and throws the changes away.

  1. Type vi a.txt and press Enter.
  2. Press i, type the text, and press Enter for a new line.
  3. Press Esc to leave insert mode.
  4. Type :wq and press Enter to save and exit.
  5. To abandon the edit instead, type :q! and press Enter.

For help, man ls shows the manual page for ls; space pages forward and q quits. Manual pages are grouped in numbered sections: section 1 is user commands, section 5 is file formats, section 8 is administration commands, so man 5 passwd reads the file format rather than the command. man -k word searches the one-line descriptions. Most GNU commands also accept --help, a short summary that is faster when you need one option.

Worked example

Question. A user logs in and the shell starts in /home/ravi. These commands are typed in order: (1) mkdir notes, (2) cd notes, (3) pwd, (4) vi a.txt, where one line is typed and the file is saved and closed with :wq, (5) cp a.txt b.txt, (6) ls, (7) rm a.txt. Give (a) the output of pwd, (b) the output of ls, (c) the final working directory, and (d) the files left inside notes. (6 marks)

  1. mkdir notes creates an empty directory named notes inside /home/ravi. No output is printed.
  2. cd notes moves the shell's own working directory into that new directory, so the shell is now at /home/ravi/notes.
  3. pwd prints the absolute path of that directory: /home/ravi/notes.
  4. vi a.txt starts an editor session. The typed line is held in the editor's buffer; :wq writes it to a.txt and exits. notes now contains a.txt.
  5. cp a.txt b.txt reads a.txt and writes an identical b.txt, so notes contains two files: a.txt and b.txt.
  6. ls prints the two names in the current directory, in sorted order: a.txt and b.txt (shown in columns on a terminal, one per line when piped).
  7. rm a.txt unlinks a.txt. The directory now holds only b.txt and the shell stays where it is.

Answer. pwd prints /home/ravi/notes; ls prints a.txt and b.txt; the final working directory is /home/ravi/notes; only b.txt is left in notes.

Exam traps

  • rm does not use a trash folder. A deleted file is gone, and rm -r on the wrong directory can remove a whole tree with no undo.
  • rmdir refuses a directory that still has entries in it; the error is 'Directory not empty', not a permissions problem.
  • cd changes only the working directory of the shell process that runs it. A script that runs cd cannot move the terminal you launched it from, because the script is a child process with its own copy.
  • mv inside one file system just renames the entry and the file keeps its identity; cp makes a new file with a new identity. mv across file systems has to copy and then delete.
  • ls without -a hides every name beginning with a dot, so a 'missing' file may simply be hidden. Quote the pattern, as in find /home/ravi -name "*.txt", so the shell passes it unchanged to find. Unquoted, the shell may expand *.txt into matching file names in the current directory before find ever sees it.

The script runs as a child process. It gets its own copy of the working directory, so its cd affects only itself; the parent shell's directory is unchanged.

Analyze A student runs rmdir notes and gets 'Directory not empty'. Give two ways to finish the job and say which is riskier. 4 marks

Either delete the contents first (cd notes; rm the files; cd ..; rmdir notes), or run rm -r notes. The second is riskier: one typing slip removes the wrong tree with no undo, so check the path with pwd and ls first.

Esc returns to command mode; :wq writes the file and quits.

:wq saves the buffer to disk then exits, used when the edit is wanted. :q! exits without saving, used to throw away a bad edit. Plain :q refuses to exit if there are unsaved changes.

Takeaways

  1. Unix gave the model (files, processes, shell, small tools); Linux gave a free, open implementation of that model.
  2. Multi-user, multitasking and modularity are kernel-level promises, not extra features bolted on top.
  3. The kernel is the only privileged code; the shell is just another user-space program that asks the kernel for work.
  4. Open source lowers lock-in and spreads the cost of finding and fixing bugs across many users.
  5. A distribution is kernel plus libraries, tools, installer and package manager; the distro choice mostly decides your package manager and support model.
  6. Installation means answering four questions: where to install, how to boot it, which user accounts, and which packages.
  7. The command line is a loop: prompt, read, run, return; every basic command is a small program in that loop.

Glossary

Absolute path
A path starting at the root /, such as /home/ravi/notes.txt, valid from any directory.
Bootloader
The small program that loads the kernel into memory and hands control to it at startup.
Current working directory
The directory you are currently in, printed by pwd and used to resolve relative paths.
Desktop environment
The graphical layer (windows, panels, menus) that runs on top of the kernel and shell, e.g. GNOME or KDE.

A complete installable system made of the Linux kernel, libraries, utilities, installer and package manager.
GPL
The GNU General Public License, which requires modified versions of the code to stay under the same licence.
init
Process number 1, started by the kernel at boot, which brings up and supervises all other services.
Kernel
The privileged core of the system that controls memory, CPU time, devices and files.
Kernel module
A loadable piece of kernel code, often a device driver, added or removed without rebooting.
Linux
The free, open source kernel started by Linus Torvalds in 1991 and used in distributions such as Ubuntu and Fedora.
Live USB
A bootable USB stick that runs a full distribution in memory without installing it, useful for testing and repair.
Man page
The built-in reference page for a command, opened with man command or read with --help.
Multi-user
A property of the system that lets many people have accounts and work on one machine at once.
Multitasking
Running many processes apparently at the same time by switching the CPU between them.
Open source software
Software released with its source code under a licence that permits study, change and redistribution.
Package manager
A program such as apt, dnf, zypper or pacman that installs, upgrades and removes software and tracks dependencies.
Process
A running program together with its memory, registers and open files, identified by a PID.
Prompt
The shell's short ready signal, often user@host:dir$ , printed before it reads a command.
Relative path
A path interpreted from the current working directory, such as ../notes.txt.
Shell
A user-space program that reads commands from you and asks the kernel to execute them.
System call
A defined request from a user program to the kernel, such as read, write or fork.
Terminal
The window or device that connects you to a shell so you can type commands.
Unix
A multiuser, multitasking operating system built at Bell Labs from 1969 whose design Linux follows.

The restricted memory area where ordinary programs run and reach hardware only through system calls.
