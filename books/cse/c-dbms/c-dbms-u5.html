A bank transfer, a UPI payment or an IRCTC booking is several reads and writes that must happen together, while thousands of other users change the same tables. 5.1 Transaction concept and transaction states

A transaction is a unit of program execution that reads and possibly updates data items, and that the DBMS treats as one logical piece of work: either all of it takes effect or none of it does. Moving ₹500 from account A to account B is two updates, a debit and a credit, but to the bank it is one act. Transactions exist because two things go wrong in a shared database: the system can fail halfway, and many users change the same data at once.

You need: COMMIT and ROLLBACK in SQL (Unit 3, Transaction control: COMMIT, ROLLBACK and SAVEPOINT) and the idea that the DBMS works on copies of disk blocks held in main memory (Unit 6, Disk storage and RAID).

What a transaction does: read, write and the buffer

Theory describes a transaction by its reads and writes of data items (a row, a field or a block):

  • read(X) copies item X from the database into a local variable of the transaction, also called X.
  • write(X) copies the local variable X back into the database.

"The database" here means the buffer: the copy of the disk block held in main memory. A separate step, output(B), later copies block B from the buffer to the disk; the buffer manager decides when. So after write(A) the new balance may sit only in memory for some time. That gap is why recovery (Chapter 5.8) is needed. The transfer, written in this notation, is:

T1: read(A);
    A := A − 500;
    write(A);
    read(B);
    B := B + 500;
    write(B);
    commit

In SQL (PostgreSQL syntax; the SQL standard writes START TRANSACTION for BEGIN) the same transaction is:

BEGIN;
UPDATE account SET balance = balance - 500 WHERE acc_no = 'A';
UPDATE account SET balance = balance + 500 WHERE acc_no = 'B';
COMMIT;

The psql client prints BEGIN, UPDATE 1, UPDATE 1, COMMIT; "UPDATE 1" means one row changed.

The five transaction states

From start to end a transaction is always in one of five states (Figure 5.1.1).

  1. Active: the starting state. The transaction is executing its reads and writes.
  2. Partially committed: the last statement has executed. The changes may still be only in main-memory buffers, so a power cut can still stop it.
  3. Failed: normal execution cannot go on. Causes: a logical error (the balance check finds A has only ₹300), a system error (the DBMS chooses it as a deadlock victim, Chapter 5.6), or a crash before the commit record is safe on disk.
  4. Aborted: the transaction has been rolled back; every change it made has been undone and the database is as it was before the transaction started. The system then either restarts it as a new transaction (when the cause was outside its own logic, such as a deadlock or a hardware fault) or kills it (when the cause was in the transaction itself: bad input, a missing row, a failed check).
  5. Committed: the transaction finished and enough information, the commit record in the log, is on stable storage that its changes will survive any later crash.

A transaction that has committed or aborted is terminated. Elmasri and Navathe's diagram has no separate aborted state: committed and failed both lead to a final "terminated" state.

Two rules follow from the diagram. First, an observable external write, such as an ATM dispensing notes or an SMS saying "₹500 debited", must wait until the transaction is committed, because the DBMS can undo a database write but not cash in a customer's hand. Second, a committed transaction can never be aborted. To reverse it you run a new compensating transaction, such as a refund.

User transactions and system transactions

A user transaction is started by an application or a person: the transfer above, an IRCTC booking, a mark entry. A system transaction is started by the DBMS for its own work: splitting a full B+ tree page during an insert (Unit 6, B-trees and B+ trees), giving a table a new disk page, or updating the data dictionary. A system transaction changes how data is stored, not what it means, so it commits on its own. If a user transaction caused a page split and then rolls back, its row is removed but the split stays, and the tree is still correct.

Worked example

Question. Transaction T moves ₹2,000 from account A (₹10,000) to account B (₹5,000). The power fails at one of three moments: (a) after write(A), before read(B); (b) after write(B) has executed, before the commit record reaches the disk log; (c) just after the commit record reaches the log, before the buffer blocks holding A and B are written to disk. For each case give the state of T when the power fails, what the DBMS does on restart, and the final balances. (6 marks)

Exam traps

  • Partially committed is not committed. All statements have run, but a crash can still roll the transaction back.
  • write(X) is not output. write(X) changes the buffer in memory; the disk changes only when the block is output. Students who say "write(X) updates the disk" lose the recovery marks.
  • Abort and kill differ. Every failed transaction is aborted (rolled back); only then is it restarted or killed. A restarted transaction is a new transaction.
  • No abort after commit. Undoing a committed transfer needs a compensating transaction, not ROLLBACK.
  • The favourite question is "Draw the state diagram of a transaction and explain each state" (8 marks): draw all five states and label every arrow with its cause.

5.2 ACID properties

Every DBMS promises four things about each transaction: Atomicity, Consistency, Isolation and Durability, together called ACID. Atomicity and durability protect the data against failures; isolation protects it against other users running at the same time; consistency is the goal the other three serve. Theo Härder and Andreas Reuter coined the acronym in 1983, and it is now the checklist for judging any system that claims to be transactional.

You need: the transaction and its states (Chapter 5.1).

The four properties on one transfer

Take T1: move ₹3,000 from account A (₹20,000) to account B (₹12,000). Before and after, A + B = ₹32,000.

  1. Atomicity: all of the transaction happens, or none of it. If the power fails after write(A) but before write(B), the disk may hold A = ₹17,000 and B = ₹12,000, so ₹3,000 has vanished. The DBMS keeps the old value of every item it changes in a log (Chapter 5.8) and, on restart, undoes the half-done work. Enforced by: the recovery system.
  2. Consistency: a transaction that runs alone, from a consistent database, leaves the database consistent. "Consistent" means every rule holds: declared integrity constraints (primary keys, foreign keys, CHECK (balance >= 0), Unit 2) and unwritten business rules (a transfer does not change A + B). In the middle of T1 the database is briefly inconsistent; that is allowed, because no one else may see it. Enforced by: the application programmer, who must write a correct transaction, with the DBMS checking the declared constraints.
  3. Isolation: although transactions run at the same time, each behaves as if it ran alone. For any two transactions Ti and Tj, it appears to Ti that Tj either finished before Ti started or started after Ti finished. If T2 adds up A + B between T1's write(A) and write(B), it sees ₹17,000 + ₹12,000 = ₹29,000, a total that never existed. Enforced by: the concurrency-control system (Chapters 5.3 to 5.7).
  4. Durability: once a transaction commits, its changes survive any later failure. If the server loses power one second after the "₹3,000 sent" SMS, B must still read ₹15,000 after restart. The DBMS forces the log, with the new values, to stable storage before it reports the commit, and redoes the work from the log if the data blocks had not reached the disk. Enforced by: the recovery system.

Who is responsible for what

Exams ask which part of the DBMS ensures each property. Atomicity and durability belong to the recovery system, through the log (Chapters 5.8 and 5.9). Isolation belongs to the concurrency-control system, through locks, timestamps or validation (Chapters 5.4 and 5.5). Consistency belongs mostly to the programmer: the DBMS cannot know that a transfer should preserve A + B unless someone writes that rule. It enforces only the constraints declared in the schema, and it guarantees that a correct transaction stays correct under failures and concurrency, given A, I and D.

Stable storage is storage that never loses data. No single device is like that, so it is approximated by keeping copies on separate disks, as RAID does (Unit 6), or at separate sites. Durability is only as good as this approximation.

Worked example

Question. A = ₹20,000 and B = ₹12,000; T1 moves ₹3,000 from A to B. For each event, name the ACID property that has been broken, and give the balances a correct DBMS would show. (a) The server crashes after write(A); after restart the bank shows A = ₹17,000, B = ₹12,000. (b) While T1 runs, a report T2 prints the total of A and B as ₹29,000. (c) T1 was coded as B := B + 300 by mistake and has committed. (d) After the success SMS the data centre loses power; next morning B shows ₹12,000. (8 marks)

Solution.

  1. (a) Atomicity is broken: only half of T1 took effect, and A + B = ₹29,000. A correct DBMS undoes write(A) from the log: A = ₹20,000, B = ₹12,000.
  2. (b) Isolation is broken: T2 saw T1's half-done state. A correct DBMS makes T2 run as if before T1 (total ₹32,000) or after it (₹17,000 + ₹15,000 = ₹32,000). Either way it prints ₹32,000.
  3. (c) Consistency is broken: after commit, A = ₹17,000 and B = ₹12,300, so A + B = ₹29,300, not ₹32,000. The DBMS cannot catch this, because no declared constraint fails. The bank must run a compensating transaction that adds ₹2,700 to B, giving A = ₹17,000, B = ₹15,000.
  4. (d) Durability is broken: a committed change was lost. A correct DBMS redoes T1 from the log on restart: A = ₹17,000, B = ₹15,000.

Exam traps

  • Atomicity is about failures; isolation is about other users. A half-done transfer after a crash is an atomicity problem; a report that reads a half-done transfer is an isolation problem.
  • The DBMS does not guarantee consistency on its own. It checks declared constraints; the logic of a transaction is the programmer's job.
  • ACID's C is not CAP's C. In the CAP theorem of distributed systems, consistency means every copy of the data agrees; in ACID it means integrity rules hold.
  • Temporary inconsistency is allowed inside a transaction, as long as no other transaction sees it.
  • The favourite question is "Explain the ACID properties with an example" (8 marks): use one example, such as the transfer, for all four, and name who enforces each.

5.3 Schedules, serializability and recoverability

When transactions run at the same time, their reads and writes interleave. The order in which they actually run is a schedule. Some schedules give the same result as running the transactions one after another; these are serializable, and they are exactly the ones isolation allows. Some schedules also decide whether an abort can be cleaned up safely; these are recoverable. This chapter gives the tests examiners ask you to apply: the precedence graph for conflict serializability, the three conditions of view serializability, and the recoverable, cascadeless and strict classes.

You need: read(X) and write(X) (Chapter 5.1) and isolation (Chapter 5.2).

Why run transactions concurrently

Running one transaction at a time is always correct, but slow. While one transaction waits for the disk, another can use the CPU, so more transactions finish per second (throughput). A short UPI payment also need not wait behind a 10-second month-end report, so the average response time falls. The price is that interleaving can produce wrong answers, so the DBMS must allow only the safe interleavings.

Schedules and conflicts

Write r1(A) for "T1 reads A", w2(B) for "T2 writes B", c1 for "T1 commits" and a1 for "T1 aborts". A schedule lists the operations of several transactions in the order they run, keeping each transaction's own order. In a serial schedule each transaction runs completely before the next starts; n transactions have n! serial schedules. Two transactions with n1 and n2 operations can be interleaved in (n1 + n2)! ÷ (n1! × n2!) ways, so most schedules are not serial.

Two operations conflict when they belong to different transactions, touch the same item, and at least one is a write. So r–w, w–r and w–w pairs on one item conflict; r–r pairs never do, and operations on different items never do. Swapping two adjacent operations that do not conflict cannot change any result. Schedules that can be turned into each other by such swaps are conflict equivalent, and a schedule is conflict serializable when it is conflict equivalent to some serial schedule.

The precedence-graph test

  1. Draw one node per committed transaction.
  2. For every pair of conflicting operations where Ti's operation comes first, draw an edge Ti → Tj, labelled with the item.
  3. If the graph has a cycle, the schedule is not conflict serializable.
  4. If it has no cycle, it is. Any topological order of the graph (repeatedly take a node with no incoming edge) gives an equivalent serial schedule.

View serializability

Two schedules on the same transactions are view equivalent when, for every item Q: (1) the same transaction reads the initial value of Q; (2) whenever Ti reads a value of Q written by Tj in one schedule, it does so in the other; (3) the same transaction performs the final write of Q. A schedule is view serializable when it is view equivalent to a serial schedule. Every conflict-serializable schedule is view serializable. The extra view-serializable schedules all contain blind writes, writes of an item the transaction never read. Testing view serializability is NP-complete, so real systems enforce conflict serializability instead.

Recoverability

Serializability ignores aborts. Suppose T1 writes A, T2 reads that A, and then T1 aborts: T2 has used a value that never officially existed (a dirty read).

  • Recoverable: if Tj reads an item written by Ti, then Ti commits before Tj commits. w1(A), r2(A), c2, a1 is not recoverable: T2 committed a dirty value that can no longer be undone.
  • Cascadeless: Tj reads an item only after the transaction that wrote it has committed. w1(A), r2(A), c1, c2 is recoverable but not cascadeless: had T1 aborted, T2 would have had to roll back too, a cascading rollback.
  • Strict: no transaction reads or writes an item until the last transaction that wrote it has committed or aborted. w1(A), w2(A), c1, c2 is cascadeless (no reads) but not strict. Strict schedules make undo simple: restore the old value from the log.

Each class lies inside the one before: strict ⊂ cascadeless ⊂ recoverable.

Worked example 1: precedence graph

Question. Is S = r1(X), r2(Y), w1(X), r3(X), w2(Y), r1(Y), w3(X), w1(Y) conflict serializable? If so, give the equivalent serial schedule. (6 marks)

  1. Operations on X in order: r1, w1, r3, w3. Conflicting pairs: r1(X)–w3(X), w1(X)–r3(X), w1(X)–w3(X). All give the edge T1 → T3.
  2. Operations on Y in order: r2, w2, r1, w1. Conflicting pairs: r2(Y)–w1(Y), w2(Y)–r1(Y), w2(Y)–w1(Y). All give T2 → T1. (r2(Y) and r1(Y) do not conflict: both are reads.)
  3. Graph: T2 → T1 → T3 (Figure 5.3.1). No cycle, so S is conflict serializable.
  4. Topological order: T2 has no incoming edge, then T1, then T3. Equivalent serial schedule: r2(Y), w2(Y), r1(X), w1(X), r1(Y), w1(Y), r3(X), w3(X).

Worked example 2: view serializable but not conflict serializable

Question. S2 = r1(A), w2(A), c2, w1(A), c1, w3(A), c3. Is S2 conflict serializable, view serializable, recoverable? (6 marks)

  1. Conflicts on A: r1(A) before w2(A) gives T1 → T2; w2(A) before w1(A) gives T2 → T1. The cycle T1 → T2 → T1 means S2 is not conflict serializable.
  2. Try the serial schedule T1, T2, T3. Initial read of A: by T1 in both. No transaction reads a value written by another, in either. Final write of A: by T3 in both. All three conditions hold, so S2 is view serializable, equivalent to T1, T2, T3. The blind writes w2(A) and w3(A) make this possible: their values are overwritten without being read.
  3. No transaction reads a value written by another, so S2 is recoverable and cascadeless. Every write of A comes after the previous writer's commit (c2 before w1(A), c1 before w3(A)), so S2 is also strict.

Exam traps

  • Edges come from conflicts only. r1(Y) then r2(Y) gives no edge; neither do operations on different items.
  • Edge direction follows time: from the transaction whose operation comes first.
  • Not conflict serializable does not mean not serializable. Check view serializability when the schedule has blind writes.
  • Recoverable is about commit order, not about the order of reads and writes. Look at where ci falls relative to cj.
  • The lost update r1(A), r2(A), w1(A), w2(A) is the favourite non-serializable schedule: edges T1 → T2 and T2 → T1.

5.4 Lock-based protocols and two-phase locking

A lock is a mark the DBMS attaches to a data item to say which operations other transactions may perform on it right now. A lock-based protocol is a set of rules for when a transaction must lock and unlock items. The most important rule, two-phase locking (2PL), guarantees that every schedule it allows is conflict serializable (Chapter 5.3). Most commercial systems use a form of it.

You need: conflicts and the precedence graph (Chapter 5.3).

Shared and exclusive locks

A transaction asks the lock manager for one of two modes:

  • Shared lock, lock-S(Q): the holder may read Q but not write it. Many transactions can share it.
  • Exclusive lock, lock-X(Q): the holder may read and write Q. No one else may hold any lock on Q.

A request is granted only if it is compatible with every lock other transactions hold on Q; otherwise the transaction waits. The lock manager keeps a lock table, a hash table on item names in which each entry is a queue of granted and waiting requests. Requests are served in order of arrival, so a writer waiting for X is not passed by an endless stream of new readers; that would be starvation.

Locking alone does not give serializability. If T1 unlocks A straight after writing it and before locking B, another transaction can read the new A with the old B. Worked example part (a) shows the wrong total this produces. The fix is a rule about when unlocking may begin.

The two-phase locking protocol

Each transaction issues its lock and unlock requests in two phases:

  1. Growing phase: the transaction may obtain locks but may not release any.
  2. Shrinking phase: the transaction may release locks but may not obtain any new one.

The moment a transaction gets its last lock is its lock point. Result: every schedule obeying 2PL is conflict serializable, and ordering the transactions by lock point gives an equivalent serial schedule. The reason: an edge Ti → Tj means Tj got a conflicting lock only after Ti released its lock, so Ti's lock point comes first. A cycle would need a lock point earlier than itself, which is impossible.

Lock conversion refines this: a transaction may upgrade S to X only in the growing phase and downgrade X to S only in the shrinking phase. Upgrading lets a transaction read many rows under S and take X only on the one it decides to change.

Variants of 2PL and what basic 2PL does not solve

Basic 2PL leaves two problems. It can deadlock: T1 holds A and waits for B while T2 holds B and waits for A (Chapter 5.6). And it allows cascading rollback: a transaction in its shrinking phase may release X on A before committing, another reads A, and then the first aborts. The variants fix the second problem, and one fixes the first:

  • Strict 2PL: hold all exclusive locks until commit or abort. Schedules are strict, so there are no cascading rollbacks. The most widely used form.
  • Rigorous 2PL: hold all locks, shared and exclusive, until commit or abort. Transactions are then serialized in the order they commit.
  • Conservative (static) 2PL: lock every item the transaction will need before it starts, all at once. No deadlock is possible, but the transaction must know its items in advance and holds them longer.

It is conflict serializable and deadlock-free without being two-phase, though not always recoverable.

5.5 Timestamp-ordering protocols

Locking decides the serial order while transactions run, at their lock points. Timestamp ordering decides it in advance: each transaction gets a number, its timestamp, when it starts, and the DBMS makes the schedule equivalent to the serial schedule in timestamp order. Any operation that arrives "too late" for that order is refused and its transaction is rolled back. No transaction ever waits, so there are no deadlocks.

You need: conflict serializability (Chapter 5.3) and the cost of waiting under 2PL (Chapter 5.4).

Timestamps on transactions and on items

Each transaction Ti receives a unique timestamp TS(Ti) when it starts, from the system clock or from a counter that goes up by one per transaction. A smaller timestamp means an older transaction. Each data item Q carries two values:

  • W-TS(Q): the largest timestamp of any transaction that has successfully written Q.
  • R-TS(Q): the largest timestamp of any transaction that has successfully read Q.

Both start at 0. "Largest" matters: if T with TS 30 reads Q and then T with TS 20 reads it, R-TS(Q) stays 30.

The basic timestamp-ordering rules

  1. Ti issues read(Q). If TS(Ti) < W-TS(Q), a younger transaction has already overwritten the value Ti should see: reject the read and roll back Ti. Otherwise execute the read and set R-TS(Q) = max(R-TS(Q), TS(Ti)).
  2. Ti issues write(Q). If TS(Ti) < R-TS(Q), a younger transaction has already read the old value and would miss this write: reject and roll back Ti.
  3. Otherwise, if TS(Ti) < W-TS(Q), Ti is trying to write an obsolete value over a younger write: reject and roll back Ti.
  4. Otherwise execute the write and set W-TS(Q) = TS(Ti).

A rolled-back transaction restarts with a new, larger timestamp. Because every pair of conflicting operations runs in timestamp order, every precedence-graph edge goes from an older to a younger transaction, so no cycle is possible: the protocol guarantees conflict serializability. It is deadlock-free because nobody waits. A long transaction can, however, be rolled back again and again (starvation).

Thomas's write rule

Look again at rule 3. If TS(Ti) ≥ R-TS(Q) but TS(Ti) < W-TS(Q), no younger transaction has read Q, and a younger one has already written it. In the timestamp order, Ti's value would be overwritten before anyone read it. So the write is useless, and Thomas's write rule simply ignores it and lets Ti continue, instead of rolling Ti back. Schedules under this rule are view serializable but not always conflict serializable: the ignored write is a blind write (Chapter 5.3).

One gap remains. Basic timestamp ordering checks only timestamps, not commits, so Tj can read a value written by an older Ti that later aborts; the schedule may not be recoverable. Systems fix this by holding writes until commit, or by making readers wait for the writer to commit.

Validation-based (optimistic) protocol

When conflicts are rare, as in a read-mostly reporting system, checking every operation is wasted effort. The validation-based or optimistic protocol lets each transaction run in three phases: read (it reads items and writes only to private local copies), validation (the DBMS checks that applying the writes keeps the schedule serializable), and write (the local copies go to the database). It records Start(Ti), Validation(Ti) and Finish(Ti) and uses TS(Ti) = Validation(Ti). Tj passes validation if, for every Ti with TS(Ti) < TS(Tj), either Finish(Ti) < Start(Tj), or Start(Tj) < Finish(Ti) < Validation(Tj) and the items Ti wrote do not overlap the items Tj read. Otherwise Tj is rolled back; since it wrote nothing to the database, there is nothing to undo.

5.6 Deadlock handling in databases

A deadlock is a state in which every transaction in a set is waiting for a lock held by another transaction in the same set, so none can ever proceed. Locking protocols, including 2PL, make deadlocks possible: T1 holds A and asks for B while T2 holds B and asks for A. A DBMS handles them in one of two ways: prevention, so that a deadlock can never form, or detection and recovery, which lets one form, finds it and breaks it by rolling a transaction back.

You need: lock modes and 2PL (Chapter 5.4); transaction timestamps (Chapter 5.5).

Why deadlocks happen

Four conditions must all hold for a deadlock: mutual exclusion (an X lock has one holder), hold and wait (a transaction keeps its locks while asking for more), no preemption (a lock cannot be taken away) and circular wait (T1 waits for T2, which waits for T1, possibly through others). Every prevention scheme breaks one of them.

Deadlock prevention

  • Lock in a fixed order. Number all items and make every transaction lock them in increasing order, for example accounts by account number. A cycle of waits is then impossible (breaks circular wait).
  • Lock everything at once. Conservative 2PL (Chapter 5.4) takes all locks before the first operation (breaks hold and wait), at the cost of knowing them in advance and holding them longer.
  • Preempt by timestamp. Give each transaction its start timestamp; older means smaller. When Ti requests an item held by Tj:
    • Wait-die (non-preemptive): if Ti is older than Tj, Ti waits; otherwise Ti dies (is rolled back).
    • Wound-wait (preemptive): if Ti is older than Tj, Ti wounds Tj (Tj is rolled back and Ti takes the lock); otherwise Ti waits.
    In both, waits go in one direction only by age, so no cycle can form. A rolled-back transaction restarts with its original timestamp, so it grows relatively older and is never starved. Wait-die tends to roll back more often, since a young transaction may die several times asking for the same item.
  • Lock timeout. A transaction waits at most a fixed time, say 5 seconds, and is then rolled back. It is simple, but a timeout too short kills transactions that were merely slow, and one too long leaves deadlocks standing.

Detection with the wait-for graph

The wait-for graph has one node per active transaction and an edge Ti → Tj when Ti is waiting for an item that Tj holds. The edge is added when Ti's request is blocked and removed when it is granted. The system is deadlocked exactly when the graph has a cycle, and the transactions on the cycle are the deadlocked ones. The DBMS runs a cycle check periodically, or every time a transaction blocks; the more often deadlocks occur, the more often it should check.

Recovery from deadlock

  1. Choose a victim on the cycle, the one whose rollback costs least: how long it has run and how much work remains, how many items it has locked or changed, how many more it needs, and how many other transactions its rollback would affect.
  2. Roll it back: totally (abort and restart) or partially (only back to just before the lock request that closed the cycle, which needs more bookkeeping).
  3. Avoid starvation: if cost alone picks the same transaction every time, it never finishes. Count its rollbacks in the cost.

5.7 Isolation levels and multiple granularity locking

Full serializability makes transactions wait, so SQL lets a transaction choose a weaker isolation level and accept some anomalies for speed. And a transaction reading a whole table should not lock a million rows one by one: multiple granularity locking lets it take one table lock while others lock single rows.

The four SQL isolation levels

SQL defines the levels by three anomalies. A dirty read sees a value another transaction has not yet committed. A non-repeatable read reads one row twice and gets different committed values because another transaction updated it in between. In a phantom, a query re-run with the same WHERE condition finds new rows another transaction inserted.

Data items form a tree: database, then areas, then files (tables), then records. Locking a node implicitly locks everything below it. 5.8 Log-based recovery and write-ahead logging

The log is a sequential, append-only record of every change made to the database: which transaction changed which item, from what value to what value, and when each transaction started, committed or aborted. After a crash, the recovery system reads the log to undo the changes of transactions that had not committed (atomicity) and to redo the changes of those that had (durability). Write-ahead logging (WAL) is the rule that makes this possible: the log record of a change reaches stable storage before the change itself reaches the database on disk. Undo; redo; undo-redo logging".

You need: read, write and output (Chapter 5.1); atomicity and durability (Chapter 5.2).

Failures and storage

Three kinds of failure matter. A transaction failure stops one transaction: a logical error (bad input) or a system error (chosen as a deadlock victim). A system crash (power cut, operating-system or DBMS fault) wipes main memory but leaves the disks intact. A disk failure destroys data on a disk; it is repaired from a backup copy plus the log kept elsewhere. Storage is likewise volatile (main memory, lost in a crash), non-volatile (disk and SSD) or stable (never lost, approximated by keeping copies on separate devices). The log lives on stable storage.

Log records, undo and redo

  • <Ti start>: Ti has started.
  • <Ti, X, V1, V2>: Ti wrote item X, changing it from the old value V1 to the new value V2.
  • <Ti commit> and <Ti abort>: Ti has committed or aborted.

undo(Ti) scans Ti's update records backward, setting each item back to its old value; for each it writes a redo-only record <Ti, X, V1>, and at the end <Ti abort>. redo(Ti) scans them forward, setting each item to its new value. Both are idempotent: doing them twice has the same effect as once. That matters, because the system can crash again in the middle of recovery.

After a crash, scan the log. If it has <Ti start> and <Ti commit>, redo Ti. If it has <Ti start> but neither commit nor abort, undo Ti. (A transaction that had already aborted before the crash has its undo steps in the log as redo-only records, so replaying them forward finishes its rollback.)

Undo logging, redo logging and undo/redo logging

How much the log must hold depends on when changed blocks may reach the disk. Two buffer policies decide it. Steal lets the buffer manager write a block changed by an uncommitted transaction (so undo may be needed); no-steal forbids it. Force writes all of a transaction's blocks to disk at commit (so redo is never needed); no-force does not.

The write-ahead logging rules

  1. Ti enters the committed state only after <Ti commit> has been written to stable storage.
  2. Before <Ti commit> is written to stable storage, all other log records of Ti must be there.
  3. Before a block in main memory is written to the database on disk, every log record about data in that block must be on stable storage.

Log records first collect in a log buffer in memory and are forced to disk together, so one disk write can carry the commit records of many transactions (group commit).

  2. Check (b): T1's transfer survives (durability) though the disk may have held only old values; T2's withdrawal is gone (atomicity).
  3. Under redo logging (deferred modification), uncommitted values never reach the disk, so (a) needs no action and (b) needs only the redo of T1. The final values are the same.

Exam traps

  • Undo backward, redo forward. If T updates A twice, undoing forward would leave the middle value.
  • Redo every committed transaction, even if you think its blocks reached the disk. Recovery cannot tell, and redo is idempotent.
  • WAL means log before data, never data before log.
  • Deferred modification needs no old values; immediate modification needs them for undo.
  • The commit point is the commit record on stable storage, not the moment the data blocks reach the disk.

Commit only after the commit record is on stable storage; all of a transaction's log records reach stable storage before its commit record; all log records about a block reach stable storage before that block is written to the database.

Understand Why must undo and redo be idempotent? 2 marks

The system may crash during recovery and run recovery again; repeating an undo or redo must leave the same result as doing it once.

Redo T1: X = 80. Undo T2 backward: X = 80, then Y = 20. Final X = 80, Y = 20.

Apply A DBMS uses steal and no-force. Which of undo and redo does its recovery need? 2 marks

Both. Steal can put uncommitted data on disk (needs undo); no-force can leave committed data off disk (needs redo).

Analyze Compare undo logging and redo logging for a transaction that changes 10,000 blocks. 4 marks

Undo logging forces all 10,000 blocks to disk before commit, so commit is slow, but the buffer may write them early (steal). Redo logging commits after one log write, but must keep all 10,000 changed blocks in memory until commit (no-steal), which may not fit. Undo/redo logging avoids both limits.

SQLite offers a WAL mode in which readers keep working while a writer appends to the log. Some cloud databases send only the log to their storage layer and rebuild pages from it there. 5.9 Checkpoints, shadow paging and ARIES recovery

Log-based recovery (Chapter 5.8) works but, without help, scans the whole log. A checkpoint limits how far back recovery must look. Shadow paging is a different design that needs no undo or redo at all. ARIES is the recovery algorithm behind most commercial systems.

Checkpoints

A simple checkpoint pauses updates and (1) writes all log records in memory to stable storage, (2) writes all modified buffer blocks to disk, (3) writes the record <checkpoint L>, where L lists the transactions active at that moment. On recovery, find the last checkpoint record. Transactions that committed before it need nothing, since their blocks are on disk. Only transactions in L or started after the checkpoint matter: redo those with a commit record, undo those without.

Shadow paging

The database is a set of pages found through a page table. When a transaction starts, the table on disk becomes the shadow page table and is never changed; the transaction works with a current page table. The first write to a page copies it to a free page and points the current table at the copy. To commit: write the changed pages and the current table to disk, then overwrite the one db pointer at a fixed disk address so it points to the current table. That single write is the commit point. After a crash the pointer still names the shadow table, so no undo or redo is needed. The costs: copying and writing the page table, pages scattered over the disk, garbage collection of old pages, and poor support for concurrent transactions.

ARIES

ARIES (Mohan and others, IBM, 1992) uses undo/redo logging with steal and no-force. Each log record has a log sequence number (LSN); each page stores the LSN of the last update applied to it (PageLSN); a dirty page table gives, for each changed page not yet on disk, the first LSN that dirtied it (RecLSN). Undo writes compensation log records (CLRs), so undo work is never repeated after a second crash. Fuzzy checkpoints record the transaction and dirty page tables without stopping work. Recovery has three passes:

  1. Analysis, forward from the last checkpoint: rebuild both tables; transactions still active at the crash are the losers; RedoLSN = the smallest RecLSN.
  2. Redo, forward from RedoLSN: repeat history, losers included. Skip an update if its page is not in the dirty page table, its LSN < the page's RecLSN, or the page's PageLSN ≥ its LSN.
  3. Undo, backward: roll back the losers, writing CLRs.

Worked example

Question. For Figure 5.9.1 (checkpoint at 40 s with L = {T2, T4}, crash at 100 s), say what recovery does with each transaction. (5 marks)

  1. T1 ran 5–30 s and committed before the checkpoint: nothing.
  2. T2 (20–70 s, in L) and T3 (50–90 s, after the checkpoint) have commit records: redo both.
  3. T4 (from 30 s, in L) and T5 (from 60 s) have no commit record: undo both, backward. T4's undo reaches back to 30 s, before the checkpoint.

Exam traps

  • Transactions committed before the checkpoint are neither redone nor undone.
  • Shadow paging's commit point is the db pointer write, not the page writes.
  • ARIES redoes losers too, then undoes them.

Takeaways

  1. A transaction is all-or-nothing work. It is committed only when its commit record is on stable storage, not when its last statement runs.
  2. ACID: the recovery system gives atomicity and durability, concurrency control gives isolation, and the programmer with declared constraints gives consistency.
  3. A concurrent schedule is correct when it is serializable. Test conflict serializability with the precedence graph; check view serializability only when there are blind writes.
  4. Recoverability is about commit order: strict schedules ⊂ cascadeless ⊂ recoverable.
  5. Two-phase locking guarantees conflict serializability in lock-point order; strict 2PL also stops cascading rollback; neither stops deadlock.
  6. Timestamp ordering fixes the serial order at start, never waits and never deadlocks, but rolls back late operations; Thomas's rule drops obsolete writes; validation suits rare conflicts.
  7. Deadlocks are prevented by lock ordering, conservative 2PL, wait-die or wound-wait, or detected as cycles in the wait-for graph and broken by rolling back the cheapest victim.
  8. Weaker SQL isolation levels trade anomalies for speed; intention locks let table locks and row locks coexist.
  9. Write-ahead logging puts the log before the data. Recovery redoes committed work forward and undoes the rest backward; checkpoints shorten it, and ARIES does it with analysis, redo and undo passes.

Glossary

ACID
Atomicity, consistency, isolation, durability: the four guarantees a DBMS gives each transaction.
ARIES
A recovery algorithm using LSNs, a dirty page table and compensation log records, with analysis, redo and undo passes.
Cascading rollback
Rolling back one transaction forces rollback of others that read its uncommitted data.
Cascadeless schedule
A schedule in which every transaction reads only committed data.
Checkpoint
A log record <checkpoint L> written after flushing log and data, so recovery can start near it.
Compensating transaction
A new transaction that reverses the effect of a committed one, such as a refund.
Conflict
Two operations of different transactions on the same item, at least one of them a write.
Conflict serializable
Conflict equivalent to some serial schedule; its precedence graph has no cycle.
Deadlock
A set of transactions each waiting for a lock held by another in the set.
Dirty read
Reading a value written by a transaction that has not committed.
Intention lock
IS, IX or SIX lock on an ancestor node, announcing finer locks below it.
Isolation level
How much a transaction is protected from others: read uncommitted, read committed, repeatable read or serializable.
Lock point
The moment a two-phase transaction acquires its last lock.
Log
An append-only record of transaction starts, updates (old and new values), commits and aborts on stable storage.
Phantom
A row that appears when a query with the same condition is run again, inserted meanwhile by another transaction.
Precedence graph
A graph with an edge Ti → Tj for each conflict where Ti's operation comes first.
Recoverable schedule
One in which a transaction commits only after every transaction it read from has committed.
Schedule
The order in which the operations of concurrent transactions are executed.
Shadow paging
Recovery by keeping the old page table untouched and switching a single pointer to the new one at commit.
Stable storage
Storage assumed never to lose data, approximated by copies on independent devices.
Steal / force
Buffer policies: steal lets uncommitted changes reach disk; force writes all changes to disk at commit.
Strict schedule
No item is read or written until its last writer has committed or aborted.
Thomas's write rule
In timestamp ordering, ignore a write that is older than the item's last write but not older than its last read.
Timestamp
A unique number given to a transaction at start; smaller means older.
Two-phase locking (2PL)
Every transaction acquires all its locks before releasing any.
Wait-for graph
A graph with an edge from each waiting transaction to the one holding the lock it wants.
Wait-die / wound-wait
Timestamp-based deadlock prevention: older waits, younger dies / older wounds younger, younger waits.
Write-ahead logging (WAL)
A log record must reach stable storage before the data it describes reaches the database on disk.
