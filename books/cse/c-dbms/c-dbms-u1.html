1.1 Purpose of database systems versus file systems

A database is a collection of related data about one enterprise, such as a college, a bank or a railway. A database management system (DBMS) is the software that stores that data and lets many programs and people use it safely: it answers queries, enforces rules, controls who sees what, lets many users work at once and recovers the data after a crash. The DBMS together with its database is a database system. Before DBMSs, each department kept its own files and programs; each weakness of that approach is a job the DBMS was built to do. NITK lists this as "Differences between File System and Database System"; NITK and Manipal also list "Database System Applications", covered at the end of the chapter.

The file-processing approach

Picture a college in 1985. The fees office has a program that reads and writes fees.dat. The exam cell has its own program and its own marks.dat. The hostel office has a third program and hostel.dat. Each file holds the student's roll number, name and address, because each office needs them. This is a file-processing system: permanent records kept in operating-system files, and a separate application program for every task. Figure 1.1.1 sets it beside a database system.

Seven problems of file-processing systems

  1. Data redundancy and inconsistency. The same fact is stored in several files (redundancy). When it changes in one file and not in the others, the copies disagree (inconsistency): the exam cell posts a hall ticket to the old address.
  2. Difficulty in accessing data. A new question needs a new program. "List students from Madurai with fees due above ₹10,000" needs fields from two files, and no program yet joins them; the clerk waits for a programmer or does it by hand.
  3. Data isolation. Data is scattered over files in different formats (one office uses fixed-width records, another comma-separated), so writing any program that combines them is hard.
  4. Integrity problems. Rules such as "CGPA lies between 0 and 10" or "a balance never falls below ₹0" are buried inside the code of each program. Adding a new rule means finding and changing every program that writes the file.
  5. Atomicity problems. Some work must happen completely or not at all. Moving ₹5,000 from account A (₹20,000) to account B (₹8,000) is two writes. If the power fails after A becomes ₹15,000 but before B becomes ₹13,000, the total drops from ₹28,000 to ₹23,000: ₹5,000 has vanished, and plain files cannot undo the half-done change.
  6. Concurrent-access anomalies. Two clerks withdraw ₹500 and ₹1,000 from a balance of ₹10,000 at the same moment. Both programs read ₹10,000; one writes ₹9,500, the other ₹9,000. The final balance is ₹9,000 or ₹9,500 instead of ₹8,500. This is a lost update.
  7. Security problems. The hostel clerk should see room numbers but not marks. Files give coarse operating-system permissions on a whole file, not rules per field or per user, so access control is added program by program and is easy to miss.

A DBMS is not free: it needs licences or skilled staff, more memory and disk, and an administrator, and every operation pays for checking, locking and logging. A small single-user job (a sensor appending readings) is simpler with a plain file. The rule of thumb: when data is shared by several programs or users, must survive crashes, or must answer new questions, use a DBMS.

Database system applications. Banking and UPI payments, IRCTC train reservation, university admissions and results, airline booking, telecom call records and billing, online shopping carts, hospital records, Aadhaar authentication and stock exchanges all run on database systems. In every case many users read and change shared data at once, and errors cost money.

Worked example

Question. A college stores student data in three files: fees.dat and marks.dat hold all 4,000 students; hostel.dat holds the 1,500 hostellers. Every record repeats the student's name (40 bytes) and address (120 bytes). (a) How many bytes go on repeated copies of name and address? (b) In one semester 300 students change address. The fees office updates all 300. The exam cell updates 260; the 40 it misses are day scholars. Of the 300, 90 are hostellers and the hostel office updates only 50 of them. How many students now have conflicting addresses? (c) How would a database system avoid both problems? (6 marks)

Solution.

  1. Copies of name and address kept: 4,000 + 4,000 + 1,500 = 9,500. Copies needed: one per student = 4,000.
  2. Extra copies = 9,500 − 4,000 = 5,500. Each copy is 40 + 120 = 160 bytes.
  3. Redundant storage = 5,500 × 160 = 8,80,000 bytes (about 0.88 MB).
  4. Conflicts from the exam cell: 300 − 260 = 40 students. Conflicts from the hostel: 90 − 50 = 40 students. The two groups do not overlap (the 40 missed by the exam cell are day scholars).
  5. Students with conflicting addresses = 40 + 40 = 80, that is 80 ÷ 300 ≈ 26.7% of the changes.
  6. In a database system, name and address are stored once in a STUDENT table keyed by roll number; the fees, marks and hostel tables hold only the roll number. One update is seen by every office, so redundant bytes for name and address fall to 0 and the 80 conflicts cannot arise.

Exam traps

  • Redundancy is not inconsistency. Redundancy is the same data stored twice; inconsistency is the copies disagreeing. Redundancy causes inconsistency, but a question asking for both wants both defined.
  • A DBMS controls redundancy; it does not remove it all. Roll numbers repeat in every table that refers to a student, and replicas are kept for speed and safety on purpose.
  • Database, DBMS and database system are three things: the data, the software, and the two together (with users and applications).
  • Atomicity and concurrency are different problems. Atomicity is about one task cut off by a failure; a concurrency anomaly needs two users interleaving correctly written programs.
  • The favourite 8-mark question is "drawbacks of file-processing systems": write all seven, each with a one-line example.

1.2 Views of data and three-schema architecture

A DBMS hides how data is stored. The fees clerk wants to see fees due, not disk blocks and index pages. So the DBMS describes the same data at three levels: how it is stored, what it means for the whole organisation, and what each group of users sees. This layering is the three-schema architecture, proposed by the ANSI/SPARC study group in the 1970s. Its pay-off is data independence: one level can change without rewriting the programs that use the level above. NITT lists this as "Views of data" and "three-schema architecture of DBMS", NITK as "3 level architecture", and Manipal as "Database Schemas".

You need: the idea of a database and a DBMS (Chapter 1.1).

Three levels of data abstraction

  • Physical (internal) level: how the data is actually stored: record layout in bytes, blocks on disk, indexes, compression.
  • Logical (conceptual) level: what data is stored and how items relate, for the whole organisation: for example a STUDENT table with roll, name, date of birth, department, CGPA and fees due, and the rule that CGPA lies between 0 and 10. No storage details appear here.
  • View (external) level: the part of the database one user group needs, in the form it wants. The exam cell sees roll, name and CGPA; it never sees fees.

Silberschatz, Korth and Sudarshan call the levels physical, logical and view; Elmasri and Navathe, following ANSI/SPARC, call them internal, conceptual and external. They are the same three levels.

Schema and instance

A schema is the design of the database: the names, types and rules. An instance (or state) is the data stored at one moment. The schema changes rarely, by deliberate action of the database administrator; the instance changes with every admission, payment and mark entry. In programming terms, the schema is the variable's declaration and the instance is its current value. Each level has its own schema: one internal schema, one conceptual schema, and many external schemas (also called subschemas or views). Unit 2 defines schema and instance precisely for relations.

The three-schema architecture and its mappings

The DBMS keeps all three schemas in its catalogue and keeps two mappings between them. The external/conceptual mapping says how each view's fields come from the conceptual schema (a view's "age" is computed from the conceptual "dob"). The conceptual/internal mapping says where each conceptual field is stored and which index finds it. When a user asks a question in terms of a view, the DBMS rewrites it into the conceptual schema, then into an internal access plan, and turns the results back into the view's form. Figure 1.2.1 shows the layers for a college.

Data independence

Data independence is the ability to change the schema at one level without changing the schema at the next higher level, and so without changing application programs. There are two kinds.

  • Physical data independence: change the internal schema (add an index, compress records, move files to a new disk, change block size) without changing the conceptual schema. Only the conceptual/internal mapping is updated.
  • Logical data independence: change the conceptual schema (add a column, split a table, add a table) without changing the external schemas or the programs written against them. Only the external/conceptual mapping is updated.

Logical data independence is harder to achieve. Programs and views name conceptual fields directly, so removing or redefining a field that a view uses cannot be hidden. Physical changes, by contrast, are invisible to every query because queries never name blocks or indexes. Modern relational systems give strong physical independence and partial logical independence through SQL views (Unit 3).

Worked example

Question. The college in Figure 1.2.1 has 12,000 students. Each STUDENT record takes 200 bytes and a disk block holds 4,096 bytes; records do not span blocks. (a) How many blocks does the file use? (b) The DBA compresses records to 160 bytes. How many blocks now? (c) For each change below, name the schema that changes, the mapping that is updated, and whether the exam-cell program must change: (1) the compression; (2) adding a 40-byte email column; (3) splitting fees into a separate table FEE(roll, fee_due); (4) dropping the cgpa column. (8 marks)

Solution.

  1. (a) Records per block = ⌊4,096 ÷ 200⌋ = 20 (20 × 200 = 4,000 bytes; 96 bytes unused). Blocks = 12,000 ÷ 20 = 600 blocks.
  2. (b) Records per block = ⌊4,096 ÷ 160⌋ = 25 (25 × 160 = 4,000 bytes). Blocks = 12,000 ÷ 25 = 480 blocks, a saving of 120 blocks (20%).
  3. (c1) Compression changes only the internal schema; the conceptual/internal mapping is updated. The exam-cell program is unchanged: physical data independence.
  4. (c2) The email column changes the conceptual schema. The exam-cell view still selects roll, name and CGPA, so neither the view nor its mapping needs editing: logical data independence. (Records grow back to 200 bytes, so the file returns to 600 blocks; programs do not notice.)
  5. (c3) Splitting fees changes the conceptual schema. The accounts view is redefined as STUDENT joined with FEE on roll, so the external/conceptual mapping changes, but the accounts program still sees roll, name, fee_due: logical data independence. The exam-cell view is untouched.
  6. (c4) Dropping cgpa removes data the exam-cell view needs. No mapping can supply it, so the view and the exam-cell program must change. Logical independence has a limit: it hides additions and rearrangements, not deletions of data a view uses.

Exam traps

  • Swapping the two independences. Physical = internal changes hidden from the conceptual level; logical = conceptual changes hidden from the external level. Logical is the harder one.
  • Three-schema architecture is not three-tier architecture. The first is about levels of description of data; the second (Chapter 1.4) is about where client, application server and database run.
  • One internal and one conceptual schema, but many external schemas. Writing "three external schemas" as a rule is wrong; there are as many as there are user groups.
  • Schema versus instance: the schema is the design and changes rarely; the instance is the data and changes constantly.
  • The usual 13-mark question: "Explain the three-schema architecture with a neat diagram and define data independence." Draw Figure 1.2.1 with both mappings labelled.

This is not for the exam. Column stores and modern engines change the internal level radically, storing each column separately and compressing it, yet the same SQL runs unchanged: physical data independence at work. 1.3 Data models: hierarchical, network, relational, object-oriented

A data model is a set of concepts for describing a database: the structure of the data (types and relationships), the operations allowed on it, and the constraints it must obey. Every DBMS is built on one data model, and the model decides how relationships are stored and how queries are written. Four models matter for the exam: the hierarchical and network models of the 1960s and 1970s, which link records with pointers; the relational model, which links rows by matching values and runs most databases today; and the object-oriented model, which stores programming-language objects directly. NITT lists this as "data models", NITK as "Different database system models".

Kinds of data models

  • Conceptual (high-level) models describe data as users think of it: entities, attributes and relationships. The ER model of Chapters 1.5 to 1.8 is the main one.
  • Representational (implementation) models are what commercial DBMSs implement: hierarchical, network, relational, and object-oriented or object-relational.
  • Physical (low-level) models describe storage: record formats, ordering and access paths (Unit 6).
  • Semi-structured models such as XML and JSON let each item carry its own tags, so items of the same kind may have different fields.

Running example for all four: the CSE department offers DBMS and OS; Asha takes both, Ravi takes DBMS. Student–course is a many-to-many (M:N) relationship, and the way each model handles M:N is the key difference.

Hierarchical and network models

The hierarchical model arranges records in trees. Each parent–child link is one-to-many (1:N): a parent may have many children, but every child has exactly one parent. The root is the entry point, and a program reaches data by walking down from the root. IBM's IMS, built in the late 1960s for the Apollo space programme, is the classic example and still runs in some banks. Because a child has one parent, Asha must be stored twice to sit under both DBMS and OS (Figure 1.3.1a). A child cannot exist without its parent, and deleting a parent deletes its subtree.

The network model allows a record to belong to several parent–child links, so the records form a graph. Each link type is a set type with one owner record type and one member record type, still 1:N. An M:N relationship is stored through a link record (here, one enrol record per student–course pair) that is a member of two sets (Figure 1.3.1b). The model was standardised by the CODASYL Data Base Task Group (DBTG) in 1971, building on Charles Bachman's IDS; IDMS is a well-known product. Programs navigate one record at a time along pointers, with commands such as FIND and GET, so the code depends on the access path.

Relational and object-oriented models

The relational model, proposed by E. F. Codd of IBM in 1970, stores all data in tables (relations). There are no stored pointers between tables: a row of ENROL refers to a student by holding the student's roll number, and the DBMS matches equal values when asked (Figure 1.3.2c). Queries are declarative and work on whole sets of rows ("give me all courses of roll 2"), and the DBMS chooses the access path. This brings strong data independence, and it is why Oracle, MySQL, PostgreSQL, SQL Server and Db2 are all relational. Units 2 to 4 are about this model.

The object-oriented model stores objects as a program sees them: each object has a system-given object identifier (OID), attributes and methods; objects belong to classes with inheritance and encapsulation; and an object refers to another directly by its OID (Figure 1.3.2d). Nested and complex objects, such as a machine made of parts made of sub-parts, need no flattening into tables. The ODMG standard defined ODL (definitions) and OQL (queries). It suits CAD, engineering and multimedia data. The object-relational model keeps tables and SQL but adds user-defined types, inheritance and arrays, as in PostgreSQL and Oracle.

Worked example

Question. A department has 3 courses and 50 students, with 120 enrolments in all. A student record is 100 bytes and a course record 60 bytes. A network link record holds two 8-byte pointers; a relational ENROL row holds a 4-byte roll and an 8-byte course code. Find the bytes used under (a) the hierarchical model with course as parent, (b) the network model, (c) the relational model. (d) How many records change when one student who takes 3 courses changes phone number? (6 marks)

  1. (a) Course records: 3 × 60 = 180. Each enrolment puts a full student record under a course: 120 × 100 = 12,000. Total = 12,180 bytes.
  2. (b) Courses 180; students stored once: 50 × 100 = 5,000; link records 120 × 16 = 1,920. Total = 7,100 bytes.
  3. (c) COURSE 180; STUDENT 5,000; ENROL 120 × (4 + 8) = 1,440. Total = 6,620 bytes.
  4. (d) Hierarchical: the student has 3 copies, so 3 records change, and missing one leaves an inconsistency. Network and relational: 1 record.
  5. Conclusion: the tree spends 12,180 − 6,620 = 5,560 extra bytes (84% more than relational) on repeated students, and adds update risk. Both effects grow with every M:N pair.

Exam traps

  • Hierarchical = one parent per child. A parent may have many children; it is the child that has one parent. So M:N needs duplicated records (or IMS's virtual pointer records).
  • Network sets are still 1:N. The graph appears because a record type can be a member of several set types; M:N always goes through a link record.
  • Relational tables are linked by values, not pointers. Writing "the relational model uses pointers between tables" loses the mark.
  • ER is a conceptual model, not a DBMS product. No database "runs" the ER model; designs drawn in ER are mapped to the relational model (Chapter 1.9).
  • Object-oriented and object-relational are different: the second keeps tables and SQL.

1.4 Database languages, users and DBMS architecture

People talk to a DBMS in database languages: one part defines the schema, another reads and changes data, others control access and transactions. Different people use it in different ways, from a passenger booking a ticket to the administrator tuning the disks. Inside, the DBMS has two main parts, a query processor that turns requests into actions and a storage manager that moves data between disk and memory safely. Manipal lists "Database Languages" and "Database Architecture", NITT "components of DBMS", and NITK "Database system environment" and "types of Database Systems".

Database languages

  • Data definition language (DDL) defines and changes the schema: CREATE, ALTER, DROP, TRUNCATE. Its output is metadata (data about data), stored in the data dictionary or system catalogue. Elmasri and Navathe also name a storage definition language (SDL) for the internal schema and a view definition language (VDL) for external schemas; in SQL all three are part of one language.
  • Data manipulation language (DML) retrieves, inserts, deletes and updates data: SELECT, INSERT, UPDATE, DELETE. A procedural DML makes the user say what data is needed and how to get it, step by step (network-model FIND and GET, relational algebra). A declarative (non-procedural) DML asks only for what is needed (SQL). The retrieval part of a DML is called a query language.
  • Data control language (DCL) gives and takes away rights: GRANT, REVOKE.
  • Transaction control language (TCL): COMMIT, ROLLBACK, SAVEPOINT (Unit 3).

The SQL below (run in PostgreSQL, with a role exam_cell already created) uses all four; the last lines show the query's output.

BEGIN;                                                        -- TCL
CREATE TABLE student (roll INT PRIMARY KEY, name VARCHAR(40),
       cgpa NUMERIC(4,2) CHECK (cgpa BETWEEN 0 AND 10));      -- DDL
INSERT INTO student VALUES (101, 'Asha', 8.70), (102, 'Ravi', 7.95);   -- DML
GRANT SELECT ON student TO exam_cell;                         -- DCL
COMMIT;                                                       -- TCL
SELECT name FROM student WHERE cgpa > 8;                     -- DML query

Database users and the administrator

  • Naive (parametric) users use ready-made screens: an IRCTC passenger, a bank teller, a person at an ATM. They never see SQL.
  • Application programmers write those screens and programs in Java, Python or C#, sending SQL through interfaces such as JDBC.
  • Sophisticated users (analysts) write their own queries or use reporting and analysis tools. Elmasri and Navathe also name casual users, who query now and then, and stand-alone users with personal databases.
  • Database designers decide what data to store and draw the ER diagram (Chapters 1.5 to 1.9).
  • The database administrator (DBA) has central control: defines the schema and storage structures, changes them as needs grow, grants and revokes access, takes backups, watches disk space and tunes performance.

Components of a DBMS

Figure 1.4.1 shows the parts and the order in which a request passes through them.

  1. DDL interpreter: reads DDL statements and records the definitions in the data dictionary.
  2. DML compiler: parses a query and translates it into an evaluation plan of low-level steps. Because one query has many equivalent plans, it performs query optimisation, choosing the cheapest plan using statistics about the data (Unit 6).
  3. Query evaluation engine: executes the chosen plan.
  4. Authorization and integrity manager: checks the user's rights and the integrity constraints.
  5. Transaction manager: keeps the database consistent despite failures (recovery manager) and many users at once (concurrency-control manager) (Unit 5).
  6. File manager: allocates disk space and manages the files that hold the data.
  7. Buffer manager: brings disk blocks into main memory and decides which to keep, so that most requests are served without a slow disk read.

On disk live the data files, the data dictionary (metadata), the indices that find rows quickly, and statistical data used by the optimiser.

Where the DBMS runs: tiers and types

In a centralised system the DBMS and its users share one computer. In client–server systems the DBMS runs on a server. In a two-tier design the client program holds the screens and the business rules and talks to the database server directly. In a three-tier design the client (often a browser or mobile app) talks only to an application server, which holds the business rules and talks to the database (Figure 1.4.2). Three tiers are safer, because clients never touch the database, and they scale, because a few application servers share a small pool of database connections.

Database systems are also classed by number of users (single-user or multi-user), number of sites (centralised or distributed, Unit 6), data model (Chapter 1.3) and purpose (transaction processing for daily operations, or analytical data warehouses).

Worked example

Question. A university results portal has 20,000 students online at the peak. Each open database connection uses 5 MB of memory on the database server. (a) In a two-tier design every client holds one connection. How much server memory do connections need? (b) In a three-tier design, 8 application servers each keep a pool of 25 connections. Repeat. (c) Classify each statement and say who issues it: CREATE TABLE result(...); INSERT INTO result ...; SELECT * FROM result WHERE roll = 2117; GRANT SELECT ON result TO portal_app; COMMIT. (d) Trace the SELECT through the components of Figure 1.4.1. (8 marks)

  1. (a) Connections = 20,000. Memory = 20,000 × 5 MB = 1,00,000 MB, about 98 GB, just for connections.
  2. (b) Connections = 8 × 25 = 200. Memory = 200 × 5 MB = 1,000 MB, about 1 GB: one hundredth of (a). Requests queue briefly for a free pooled connection instead of each holding one.
  3. (c) CREATE TABLE: DDL, by the DBA. INSERT: DML, by the exam cell's application program. SELECT: DML query, sent by the portal on behalf of a naive user (the student). GRANT: DCL, by the DBA. COMMIT: TCL, by the application program after the upload.
  4. (d) The app server sends the SELECT. The DML compiler parses it, checks names in the data dictionary, and the optimiser uses statistics to choose the index on roll over a full scan. The authorization manager confirms portal_app may read result. The evaluation engine runs the plan, asking the buffer manager for the index and data blocks; blocks not in memory are read through the file manager. The row goes back to the app server, which formats the page.

Exam traps

  • DDL output is metadata. It goes into the data dictionary, not into the data files.
  • SQL is declarative; relational algebra and PL/SQL are procedural. Do not call SQL procedural because it has many steps in a long query.
  • The DML compiler optimises; the evaluation engine executes. Students often give optimisation to the engine.
  • The transaction manager has two halves: concurrency control and recovery. Name both.
  • Three-tier is about machines, three-schema about levels of data description. A question on one does not want the other.

1.5 ER model: entity sets, attributes and keys

The entity-relationship (ER) model, introduced by Peter Chen in 1976, describes an enterprise as entities (things), their attributes (properties) and the relationships among them, and draws them as a diagram that users and designers can both read. It is the standard tool for the first design step, before any table exists. This chapter covers entities, attributes and keys; Chapter 1.6 adds relationships. NITT lists this as "E/R Model", "Conceptual data modelling", "entities", "entity types" and "attributes"; NITK as "Entities", "Attributes and Entity sets" and "Keys"; SRM as "Keys, Attributes, Constraints"; Anna Univ's unit title begins with candidate and primary keys.

You need: data models (Chapter 1.3), where ER is the main conceptual model.

Where ER fits in database design

Design moves in four steps. Requirements analysis: talk to users and list the data and operations they need. Conceptual design: draw an ER diagram of that data, free of any DBMS detail. Logical design: convert the diagram into tables (Chapter 1.9) and refine them (Unit 4). Physical design: choose files and indexes (Unit 6). Manipal lists the first step as "Overview of the Design Process".

Entities, entity sets and attributes

An entity is a thing or object that can be told apart from all others: the student Asha, the course CS301, the hostel block B. An entity set is a set of entities of the same type that share the same properties: all students of the college. Elmasri and Navathe call the description (name and attributes) the entity type and the current collection the entity set. Entity sets may overlap: a teaching assistant is in both STUDENT and EMPLOYEE.

Each entity is described by attributes, and each attribute takes values from a domain (value set): CGPA from the real numbers 0 to 10, PIN code from six-digit numbers. Attributes are classified in three independent ways:

  • Simple or composite. A simple attribute cannot be divided (roll number). A composite attribute has parts: name = first, last; address = street, city, PIN.
  • Single-valued or multivalued. Date of birth has one value per student; phone numbers may have several, written {phone}.
  • Stored or derived. Date of birth is stored; age is derived from it and today's date, so it is computed when asked and never goes stale.

An attribute may be null when the value does not apply (a day scholar's room number) or is not known yet. A composite attribute whose parts can repeat, such as several addresses each with a street and city, is called a complex attribute.

Figure 1.5.1 uses Chen notation, which most Indian question papers expect: rectangle for an entity set, ellipse for an attribute, double ellipse for multivalued, dashed ellipse for derived, and the key underlined. The 7th edition of Silberschatz, Korth and Sudarshan instead lists attributes inside the rectangle, with braces { } for multivalued and parentheses ( ) for derived; either is correct if used consistently.

Keys of an entity set

Two entities in a set must differ in some attribute values, and a key says which attributes guarantee that.

  • A superkey is a set of one or more attributes whose values identify each entity uniquely. {roll_no} is a superkey; so is {roll_no, name}.
  • A candidate key is a minimal superkey: no proper subset of it is a superkey. {roll_no} is one; {roll_no, name} is not, because roll_no alone suffices.
  • The primary key is the candidate key the designer chooses as the main identifier. The others are alternate keys. A key with two or more attributes is a composite key.

Choose a primary key whose value is never null and rarely or never changes: a roll number, not a phone number. Keys describe every legal state of the entity set, so they come from the enterprise's rules, not from one sample of data. Unit 2 (Keys: super, candidate, primary and foreign keys) treats the same ideas for tables and adds foreign keys.

Exam traps

  • Every candidate key is a superkey; not every superkey is a candidate key. Minimal means no attribute can be removed, not "fewest attributes": {roll_no} and {college_code, serial} can both be candidate keys.
  • Keys come from rules, not from sample data. A column that happens to be unique in five rows is not therefore a key.
  • Composite versus multivalued: name (first, last) has parts; phone has several values. Draw them differently.
  • Superkey counting: with n attributes and exactly one single-attribute candidate key, there are 2ⁿ⁻¹ superkeys. With several keys, count the subsets that contain none of them and subtract.
  • Entity versus entity set: Asha is an entity; STUDENT is the entity set.

1.6 Relationship sets: cardinality, participation and roles

A relationship is an association among entities: Prof. Kumar advises Asha. A relationship set is a set of relationships of the same type, such as ADVISES, drawn as a diamond. Two constraints give a relationship set its meaning: the mapping cardinality (how many entities on the other side one entity can be linked to) and participation (whether every entity must take part). Roles name the ends of a relationship when the same entity set appears twice. These constraints decide the keys and the tables in Chapter 1.9. Anna Univ lists "Relationship Types & Roles", "Participation" and "Degree"; SRM lists "Mapping Cardinality"; NITK lists "Relationships and Relationship sets"; NITT "relationships" and "relationship types".

You need: entity sets and keys (Chapter 1.5).

Relationship sets, degree and descriptive attributes

Formally, a relationship set R among entity sets E₁, E₂, …, Eₙ is a subset of their Cartesian product: R ⊆ {(e₁, e₂, …, eₙ) | e₁ ∈ E₁, …, eₙ ∈ Eₙ}. Each tuple in R is one relationship instance. The degree of R is the number of entity sets that take part:

  • Unary (recursive), degree 1: one entity set related to itself, such as EMPLOYEE manages EMPLOYEE.
  • Binary, degree 2: the common case, such as STUDENT enrols in COURSE.
  • Ternary, degree 3: such as SUPPLIER supplies PART to PROJECT, where each fact needs all three.

A relationship can have its own descriptive attributes. In ENROLS, grade belongs to the pair (student, course), not to the student alone (who has many grades) or to the course alone (which has many students). Likewise since in ADVISES records when the advising began.

Roles and recursive relationships

The role of an entity is the part it plays in a relationship. Usually the entity set's name is enough, but in a recursive relationship the same set appears twice and the roles must be written on the lines. In MANAGES, one EMPLOYEE plays manager and the other worker; in PREREQ, one COURSE is the course and the other its prerequisite (Figure 1.6.2, lower half). Without role labels, (CS301, CS201) could mean either "CS301 needs CS201" or the reverse.

Mapping cardinalities

For a binary relationship set R between A and B, the mapping cardinality (cardinality ratio) is one of four kinds, pictured in Figure 1.6.1:

  • One-to-one (1:1): an entity in A is linked to at most one in B, and an entity in B to at most one in A. A department has one head; an employee heads at most one department.
  • One-to-many (1:N): an entity in A may be linked to many in B, but an entity in B to at most one in A. One department, many students.
  • Many-to-one (N:1): the mirror image: many students, one department each.
  • Many-to-many (M:N): no limit either way. Students and courses.

Participation, (min, max) and notation

Participation of an entity set E in R is total if every entity in E takes part in at least one relationship of R, and partial otherwise. Every student must belong to a department (total); not every instructor advises a student (partial). Total participation is drawn as a double line between the entity set and the diamond.

Three notations show cardinality, and examiners accept any one used correctly (Figure 1.6.2):

  • Chen labels: 1, N, M written on the lines. "INSTRUCTOR 1 — ADVISES — N STUDENT" means one instructor, many students.
  • Arrows (Silberschatz, Korth and Sudarshan): a directed line points to the "one" side; an undirected line means "many".
  • (min, max) on each line: each entity of the set next to the label takes part in at least min and at most max relationships. min = 0 means partial, min ≥ 1 means total. Korth writes the same as l..h, such as 1..1 or 0..*.

The primary key of a relationship set follows from its cardinality: for M:N, the union of both entity sets' primary keys; for 1:N, the primary key of the "many" side; for 1:1, either one.

Worked example

Question. PROFESSOR = {P1, P2, P3, P4}, STUDENT = {S1, …, S6} and ADVISES = {(P1, S1), (P1, S2), (P2, S3), (P2, S4), (P2, S5), (P3, S6)}. (a) How many pairs are possible, and what fraction does ADVISES use? (b) State the mapping cardinality. (c) State the participation of each set. (d) Give (min, max) for each, from this data. (e) What is the primary key of ADVISES? (f) S6 is now also advised by P1. What changes? (7 marks)

  1. (a) Cartesian product size = 4 × 6 = 24 pairs. ADVISES holds 6, so 6 ÷ 24 = 25% of them: a relationship set is a subset of the product.
  2. (b) Each student appears exactly once, so each student has at most one professor; P2 advises three. Cardinality is one-to-many from PROFESSOR to STUDENT (1:N).
  3. (c) All six students appear: STUDENT total (if the college requires an advisor). P4 appears nowhere: PROFESSOR partial.
  4. (d) STUDENT: each takes part exactly once, (1, 1). PROFESSOR: from 0 (P4) to 3 (P2), (0, 3) here; the design rule would be written (0, N).
  5. (e) In 1:N, the "many" side's key identifies each relationship: student_id. Check: six rows, six different student ids.
  6. (f) S6 now has two professors, so a student can have many professors and a professor many students: M:N. student_id no longer identifies a row (S6 appears twice); the key becomes (prof_id, student_id), and STUDENT's (min, max) becomes (1, N).

Exam traps

  • The arrow points to the "one" side in Korth's notation. For STUDENT–BELONGS_TO–DEPARTMENT (many students, one department each), the arrowhead is drawn at DEPARTMENT.
  • (min, max) labels sit at the opposite end from Chen's 1 and N. DEPARTMENT 1 — N EMPLOYEE becomes DEPARTMENT (0, N) — (1, 1) EMPLOYEE. Learn one example by heart.
  • Cardinality is about the maximum; participation is about the minimum. Total participation does not mean one-to-one.
  • Degree is not cardinality. Degree counts entity sets in the relationship; cardinality counts entities each can be linked to.
  • Put M:N attributes on the relationship. Grade on STUDENT or COURSE is wrong; on ENROLS is right.

1.7 Weak entity sets and ER diagrams

Some entities cannot be identified on their own. Passenger number 2 exists in thousands of train bookings; only "passenger 2 of PNR 4521873690" picks out one person. Such an entity set is a weak entity set: it has no primary key of its own and is identified through a related owner entity. This chapter defines weak entity sets, collects every ER symbol into one table, and then puts them together in a complete ER diagram, with the design choices an examiner asks about. Anna Univ lists "Weak Entities & Keys"; SRM lists "E-R Model Construction", "Case Study" and "Issues in E-R Model"; NITK "ER Design Issues"; NITT "E/R diagram notation" and "examples"; IITB "ER Diagrams".

You need: keys (Chapter 1.5) and cardinality and participation (Chapter 1.6).

Weak entity sets

A strong entity set has a primary key. A weak entity set does not have enough attributes to form one. Each weak entity is tied to one entity of an identifying (owner) entity set through an identifying relationship, and depends on it for existence: cancel the booking and its passengers go too.

  • The discriminator (Elmasri and Navathe: partial key) is the set of attributes that tells apart the weak entities of the same owner, such as serial_no 1, 2, 3 within a booking.
  • Primary key of a weak entity set = primary key of the owner + discriminator: (pnr, serial_no).
  • The weak entity set takes part totally in the identifying relationship, and the relationship is many-to-one from the weak set to the owner: every passenger has exactly one booking.
  • Notation: weak entity set in a double rectangle, identifying relationship in a double diamond, discriminator underlined with a dashed line, and a double line for the total participation.

Textbook examples are SECTION of a COURSE (sec_id, semester, year), PAYMENT of a LOAN (payment number) and DEPENDENT of an EMPLOYEE (dependent's name). Each could be given an artificial id of its own, but modelling it as weak records two facts at once: how it is identified, and that it cannot outlive its owner.

Building an ER diagram

  1. Entity sets: pick the nouns that have their own attributes and many instances (user, booking, train, passenger).
  2. Attributes and keys: list each set's attributes; mark the primary key, multivalued and derived attributes.
  3. Relationship sets: pick the verbs that link entity sets (books, is for, has) and their degree.
  4. Constraints: for each relationship, fix cardinality and participation from the stated rules.
  5. Weak entity sets: any set with no key of its own gets an owner, an identifying relationship and a discriminator.
  6. Check: no attribute should repeat another set's key (train_no inside BOOKING should be the relationship FOR instead), and every rule in the description should appear somewhere.

Design issues

  • Entity set or attribute? Phone is an attribute while only the number matters. If each phone needs its own details (type, whether verified), make PHONE an entity set.
  • Entity set or relationship set? Use a relationship for an action or link between entities. A booking has its own key and attributes and links to passengers, so it is an entity set, not just a relationship between USER and TRAIN.
  • Binary or n-ary? A ternary relationship records facts that three binaries cannot (Chapter 1.6). It can be replaced by an artificial entity set related to the three sets, which is what BOOKING does here.
  • Where do relationship attributes go? On an M:N relationship they must stay on the diamond; on a 1:N relationship they may move to the "many" side's entity set.

Worked example

Question. A railway app has users (user_id, name, one or more phone numbers). 1.8 Extended ER: specialization, generalization and aggregation

The basic ER model cannot say that every faculty member is an employee and every employee a person, with each level adding its own attributes; nor can it attach a relationship to another relationship. The extended (or enhanced) ER model, EER, adds these. Specialization and generalization build is-a hierarchies of entity sets with inheritance; aggregation lets a relationship set be treated as an entity set. Anna Univ lists "ISA hierarchies-EER Extensions" and "Specialization/Generalization"; SRM lists "Extended ER - Aggregation" and "Extended ER - Generalization, Specialization"; NITC lists the "Enhanced ER model"; Manipal lists "Extended E-R Features".

You need: entity sets and relationship sets (Chapter 1.5, Chapter 1.6).

Specialization and generalization

Specialization is top-down: start from an entity set and define subgroups that have extra attributes or relationships of their own. PERSON is specialised into EMPLOYEE (with salary) and STUDENT (with CGPA). The higher-level set is the superclass; the lower-level sets are subclasses. The link is drawn as a triangle labelled ISA ("is a"): an employee is a person.

Generalization is bottom-up: start from entity sets that share attributes and combine them into a higher-level set. A designer who finds CAR and TRUCK both with registration number, make and model creates VEHICLE above them. The diagram is the same as for specialization; only the direction of design differs. Generalization stresses what entity sets have in common, specialization how they differ.

Attribute inheritance: a subclass inherits every attribute and every relationship of its superclass, so a STUDENT has person_id and name without repeating them in the diagram. Hierarchies may go several levels deep (Figure 1.8.1). When a subclass has two superclasses, such as TEACHING_ASSISTANT ISA STUDENT and ISA EMPLOYEE, the structure is a lattice and the subclass inherits from both (multiple inheritance).

Constraints on a specialization

  • Membership: condition-defined or user-defined. Condition-defined (predicate- or attribute-defined) subclasses are fixed by a rule on an attribute: a student with CGPA ≥ 9 is a MERIT_STUDENT; an account with type = 'S' is SAVINGS. User-defined subclasses are assigned by a person: the principal assigns a teacher to a committee.
  • Disjointness: disjoint or overlapping. Disjoint: an entity belongs to at most one subclass (faculty or staff, not both), written "disjoint" or d. Overlapping: it may belong to several (a teaching assistant is student and employee), written o.
  • Completeness: total or partial. Total: every superclass entity must belong to at least one subclass (double line from the superclass to the ISA symbol). Partial: some may belong to none (a visitor is a PERSON but neither student nor employee).

Disjointness and completeness are independent, giving four combinations: disjoint-total, disjoint-partial, overlapping-total and overlapping-partial. Elmasri and Navathe draw a circle marked d or o instead of a triangle, and the 7th edition of Silberschatz, Korth and Sudarshan uses hollow arrowheads pointing to the superclass; the meaning is the same. Elmasri and Navathe also describe a category (union type): OWNER as a subclass of the union of PERSON, BANK and COMPANY.

Aggregation

Students work on projects (WORKS_ON, M:N), and a faculty member evaluates each student's work on a project, giving marks. The evaluation is about a (student, project) pair, which is a relationship, but ER relationships connect only entity sets. A ternary EVALUATES(student, project, faculty) would repeat every evaluated pair that WORKS_ON already holds, and nothing would stop an evaluation of a pair that never worked together.

Aggregation solves this: it treats a relationship set, together with the entity sets it connects, as one higher-level entity set. In the diagram a box is drawn around WORKS_ON with STUDENT and PROJECT, and the new relationship EVALUATES connects that box to FACULTY (Figure 1.8.2). Each evaluation now refers to an existing WORKS_ON instance.

Worked example

Question. A university's PERSON entity set has 1,200 entities: 950 are students and 180 are employees, and 70 people (teaching assistants) are both. The employees are 120 faculty and 60 staff, and no one is both. (a) State the disjointness and completeness of PERSON's specialization. (b) State them for EMPLOYEE's. (c) 300 students work on 80 projects through 450 (student, project) pairs; 200 pairs are evaluated, each by one faculty member. Compare the aggregation design of Figure 1.8.2 with a design that stores WORKS_ON plus a ternary EVALUATES(student, project, faculty), and with one that folds everything into a single ternary. (8 marks)

  1. (a) 70 people are in both subclasses, so it is overlapping. People in at least one subclass = 950 + 180 − 70 = 1,060. People in neither = 1,200 − 1,060 = 140, so it is partial.
  2. (b) 120 + 60 = 180, every employee, with no one in both: disjoint and total.
  3. (c) Aggregation: WORKS_ON holds 450 instances and EVALUATES 200, each pointing to an existing pair: 650 instances, no repetition.
  4. WORKS_ON plus a ternary: also 450 + 200 = 650 instances, but the 200 evaluated (student, project) pairs are stored twice, and an evaluation of a pair absent from WORKS_ON is not prevented.
  5. One ternary only: 450 instances, but 450 − 200 = 250 of them have no faculty yet, so the faculty part is empty (null) in 250 places, and "works on" can no longer be recorded independently of "is evaluated".
  6. Conclusion: aggregation is the only design with no repeated pairs, no nulls and a guarantee that every evaluation refers to real work.

Exam traps

  • Specialization versus generalization: same diagram, opposite direction. Write "top-down, stresses differences" and "bottom-up, stresses common features".
  • Disjointness and completeness are separate. "Disjoint" does not imply "total"; give both for every ISA.
  • The total double line goes from the superclass to the ISA symbol, not from the ISA to a subclass.
  • Aggregation is not generalization. Aggregation turns a relationship into an entity-like unit; generalization builds is-a hierarchies.
  • Do not redraw inherited attributes on subclasses; only the new ones.

1.9 Mapping ER diagrams to relational tables

An ER diagram is a plan; a relational DBMS stores tables. ER-to-relational mapping turns the plan into table schemas by a fixed set of rules: one for entity sets, one for each kind of attribute, one for each cardinality of relationship, and choices for specialization and aggregation. Applied in order, the rules give a correct first schema, which Unit 4 then checks with normalization. Anna Univ lists "Converting ER Diagrams to Relations-Handling M:N relationships"; SRM "Conversion of ER to Relational Table"; NITK "Converting ER diagrams to Database Schema"; NITC "ER to relational mapping"; Manipal "Reduction to Relational Schemas".

You need: Chapters 1.5 to 1.8. A foreign key is a column (or set of columns) in one table whose values must match the primary key of another table; Unit 2 (Integrity constraints and referential integrity) treats it fully.

Entity sets and attributes

  1. Strong entity set → one table with all its simple attributes. A composite attribute is flattened into its parts (name → first_name, last_name). A derived attribute is not stored; a query or view computes it. The primary key is the entity set's key.
  2. Multivalued attribute → a separate table holding the owner's key and the attribute: STUDENT_PHONE(roll, phone). Its primary key is both columns, and roll is a foreign key to STUDENT. Never store "98400 12345, 94440 67890" in one cell (Unit 4, first normal form).
  3. Weak entity set → a table with the owner's primary key, the discriminator and its own attributes: PASSENGER(pnr, serial_no, name, age). Primary key (pnr, serial_no); pnr is a foreign key to BOOKING, with deletes cascading. The identifying relationship gets no table of its own.

Relationship sets

  1. 1:N → put the primary key of the "one" side as a foreign key in the "many" side's table, with any relationship attributes: STUDENT(roll, name, dept_id). Each student has one department, so one column holds it; the department side could not, because it would need many values in one cell.
  2. 1:1 → put a foreign key in either table, preferably the side with total participation, so the column is never null: DEPARTMENT(dept_id, dname, head_emp_id). If both sides are total, the two tables may be merged.
  3. M:N → always a new table holding both primary keys and the relationship attributes: ENROLS(roll, code, grade). Its primary key is (roll, code); each part is a foreign key.
  4. n-ary (degree 3 or more) → a new table with the keys of all participating entity sets; the primary key is all of them, unless a side has cardinality "one", which can then be left out of the key.
  5. Recursive → a foreign key to the same table under the role name: EMPLOYEE(emp_id, name, manager_id), where manager_id refers to emp_id. A recursive M:N, such as PREREQ, becomes PREREQ(course_id, prereq_id).

PATIENT(patient_id, …); PATIENT_ALLERGY(patient_id, allergy); DOCTOR; WARD; ADMISSION(patient_id, admission_no, …, ward_no) with key (patient_id, admission_no) and ward_no a foreign key; CONSULTS(patient_id, doctor_id, date). 6 tables; name each primary and foreign key.

Apply Q10. EMPLOYEE(emp_id, pan, email, name, dob, dept). emp_id, pan and email are each unique. List the candidate keys, count the superkeys and choose a primary key with reasons. 8 marks

Candidate keys {emp_id}, {pan}, {email}. Subsets of 6 attributes: 64; subsets with none of the three: 2³ = 8; superkeys = 56. Primary key emp_id: issued by the company, never null, never changes; PAN is sensitive, email changes.

Analyze and evaluate

Analyze Q11. A food-delivery start-up keeps orders in spreadsheets shared by 30 staff in 3 cities. Evaluate moving to a DBMS: which file-system problems will it meet, how the three-schema architecture helps as it grows, and what client–server architecture it should use. 13 marks

Spans 1.1, 1.2 and 1.4. Problems: redundancy (customer address per order), lost updates when two staff edit, no atomic order-plus-payment, no field-level security, slow new reports. Three levels: views for kitchen, riders and accounts; storage tuned without changing apps. Three-tier with app servers and pooled connections; numbers for connection memory. Costs of a DBMS.

Analyze Q12. For "a supplier supplies a part to a project", compare a ternary relationship, three binary relationships and an aggregation-based design. When is each correct? 13 marks

Spans 1.6 to 1.8. Ternary records exactly which supplier gave which part to which project. Three binaries lose that fact (counter-example with data). Aggregation fits when one pair exists on its own (supplier can supply part) and a third set attaches to that pair. Tables for each and their keys.

Evaluate Q13. Evaluate the four options for mapping an ISA hierarchy to tables, using a hierarchy of 1,000 vehicles: 600 cars (seats), 300 trucks (load), 100 neither. 8 marks

Partial and disjoint. A: 3 tables, 1,000 + 600 + 300 rows, joins needed, always correct. B: invalid, 100 vehicles in no subclass would be lost. C: 1 table, 1,000 rows, nulls: seats null for 400, load null for 700 = 1,100 nulls. D: flags, suited only to overlapping. Choose A, or C if queries mostly read whole vehicles.

Evaluate Q14. A student's ER diagram stores train_no as an attribute of BOOKING, puts grade on STUDENT, underlines a weak entity's discriminator with a solid line and stores age. Identify each error, explain why it is wrong and correct it. 10 marks

train_no in BOOKING hides a relationship: draw FOR (BOOKING N:1 TRAIN). grade belongs to the M:N ENROLS, not STUDENT. A discriminator is a partial key: dashed underline; key = owner key + discriminator. age is derived: dashed ellipse, not stored, computed from dob.

Glossary

Aggregation
Treating a relationship set and its entity sets as one higher-level entity set so it can take part in another relationship.
Attribute
A property of an entity or relationship, with values from a domain.
Candidate key
A minimal superkey: no proper subset of it identifies entities uniquely.
Cardinality ratio
The maximum number of entities one entity can be linked to through a relationship: 1:1, 1:N, N:1 or M:N.
Composite attribute
An attribute made of parts, such as address = street, city, PIN.
Conceptual schema
The description of all data, relationships and constraints of the organisation, without storage details.
Data dictionary
The DBMS's store of metadata: table definitions, constraints, users and statistics.
Data independence
The ability to change the schema at one level without changing the next higher level or the programs.
Data model
A set of concepts for describing data structure, operations and constraints.
Database administrator (DBA)
The person with central control of the database: schema, storage, access rights, backups and tuning.
DBMS
Software that stores a database and lets many users define, query, update and protect it.
DDL, DML, DCL, TCL
Languages to define the schema, manipulate data, control rights and control transactions.
Derived attribute
An attribute computed from others when needed, such as age from date of birth.
Discriminator
The attributes that distinguish the weak entities of one owner; also called a partial key.
Entity set
A set of entities of the same type that share the same attributes.
Foreign key
Columns of one table whose values must match the primary key of another table.
Generalization
Bottom-up design that combines entity sets with common features into a higher-level entity set.
Identifying relationship
The relationship that links a weak entity set to its owner; drawn as a double diamond.
Instance
The data stored in the database at one moment.
Multivalued attribute
An attribute that can hold several values for one entity, such as phone numbers.
Participation
Whether every entity of a set must take part in a relationship (total) or need not (partial).
Primary key
The candidate key chosen as the main identifier of an entity set or table.
Relationship set
A set of relationships of the same type; a subset of the Cartesian product of the entity sets.
Schema
The overall design of the database, which changes rarely.
Specialization
Top-down design that defines subclasses of an entity set with extra attributes or relationships.
Superkey
Any set of attributes whose values identify each entity uniquely.
Three-tier architecture
Client, application server and database server on separate tiers, with business rules in the middle tier.
Weak entity set
An entity set without a primary key of its own, identified through an owner entity set.
