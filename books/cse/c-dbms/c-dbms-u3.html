3.1 SQL data definition and integrity constraints

SQL (Structured Query Language) is the standard language of relational databases. Its data definition language (DDL) creates, changes and removes the structure of the database: tables, their columns, the type of each column and the rules on the data. Those rules are integrity constraints: conditions the DBMS checks on every INSERT, UPDATE and DELETE, so a wrong row is refused at the door instead of being cleaned up later.

You need: Unit 2, Keys and Unit 2, Integrity constraints and referential integrity. This chapter writes those ideas in SQL.

The parts of SQL

SQL commands fall into four groups. Exams often ask you to classify a command, so learn this table.

GroupWhat it doesCommands
DDLdefines and changes structureCREATE, ALTER, DROP, TRUNCATE, RENAME
DMLreads and changes rowsSELECT, INSERT, UPDATE, DELETE
DCLgives and takes away rightsGRANT, REVOKE
TCLends or undoes transactionsCOMMIT, ROLLBACK, SAVEPOINT

Some books give SELECT its own group, DQL (data query language).

Data types and CREATE TABLE

Every column has a data type, which fixes the values it may hold. The common ones:

  • CHAR(n): exactly n characters, padded with spaces. VARCHAR(n): up to n characters (Oracle prefers the name VARCHAR2).
  • NUMBER(p,s) in Oracle, NUMERIC(p,s) or DECIMAL(p,s) in standard SQL: p digits in all, s of them after the decimal point. NUMBER(4,2) holds −99.99 to 99.99.
  • DATE and TIMESTAMP for dates and times (Chapter 3.7).

This unit uses one small college database. Figure 3.1.1 shows its four tables and their constraints. Here is the DDL for two of them, in Oracle-style SQL:

CREATE TABLE department (
  dept_id  VARCHAR(4)   PRIMARY KEY,
  dname    VARCHAR(30)  NOT NULL UNIQUE,
  block    CHAR(1),
  budget   NUMBER(10)   CONSTRAINT dept_budget_ck CHECK (budget > 0)
);

CREATE TABLE student (
  roll_no  NUMBER(6)    PRIMARY KEY,
  name     VARCHAR(40)  NOT NULL,
  dept_id  VARCHAR(4),
  cgpa     NUMBER(4,2)  CHECK (cgpa BETWEEN 0 AND 10),
  city     VARCHAR(20)  DEFAULT 'Chennai',
  CONSTRAINT stu_dept_fk FOREIGN KEY (dept_id)
      REFERENCES department (dept_id) ON DELETE SET NULL
);

The five constraints, and DEFAULT

  • NOT NULL: the column must have a value. name cannot be left empty.
  • UNIQUE: no two rows share a value in the column (or column set). NULLs are allowed: Oracle, PostgreSQL and MySQL allow many NULLs in a unique column, SQL Server only one.
  • PRIMARY KEY: UNIQUE plus NOT NULL, and only one per table. It is the row's identity.
  • FOREIGN KEY … REFERENCES: every non-null value must exist in the referenced column, which must be a primary key or unique. Oracle supports only ON DELETE CASCADE and ON DELETE SET NULL; there, changing a key that child rows still reference is always refused.
  • CHECK (condition): each row must not make the condition false. A NULL makes the condition unknown, and unknown passes.

DEFAULT is not a constraint but sits beside them: it fills a column the INSERT leaves out. A constraint written next to one column is a column-level constraint; one written after the columns, like stu_dept_fk, is table-level. A constraint on two or more columns, such as the composite key PRIMARY KEY (roll_no, course_id) of enrols, must be table-level. Naming a constraint with CONSTRAINT name puts that name in error messages and lets you drop it later.

Changing and removing structure

ALTER TABLE student ADD email VARCHAR(50);          -- new column, NULL in old rows
ALTER TABLE student MODIFY city VARCHAR(30);        -- Oracle, MySQL
ALTER TABLE student ALTER COLUMN city TYPE VARCHAR(30);   -- PostgreSQL
ALTER TABLE department ADD CONSTRAINT dept_block_ck
      CHECK (block IN ('A','B','C'));
ALTER TABLE department DROP CONSTRAINT dept_budget_ck;
ALTER TABLE student DROP COLUMN email;

Adding a constraint fails if existing rows already break it. Three commands remove things. DELETE FROM t is DML: it removes chosen rows (with WHERE) and can be rolled back. TRUNCATE TABLE t is DDL: it removes all rows but keeps the table, and in Oracle and MySQL cannot be rolled back. DROP TABLE t removes the table itself. A table that another table's foreign key references cannot be dropped until that key is dropped (Oracle: DROP TABLE department CASCADE CONSTRAINTS).

Worked example

Question (8 marks). The tables of Figure 3.1.1 are created as above. department holds CSE, ECE, MECH and CIV; student, course and enrols are empty. The statements below run in order. For each, say whether it succeeds; if not, name the constraint that stops it. State the contents of the changed rows at the end.

1  INSERT INTO student VALUES (101,'Anu','CSE',9.1,'Chennai');
2  INSERT INTO student VALUES (101,'Bala','CSE',7.8,'Madurai');
3  INSERT INTO student (roll_no,name,dept_id,cgpa) VALUES (108,'Hari','EEE',8.0);
4  INSERT INTO student VALUES (109,NULL,'ECE',8.2,'Salem');
5  INSERT INTO student VALUES (110,'Isha','ECE',10.5,'Trichy');
6  INSERT INTO student (roll_no,name,dept_id,cgpa) VALUES (111,'Jai','MECH',NULL);
7  DELETE FROM department WHERE dept_id = 'MECH';
8  UPDATE department SET dept_id = 'CS' WHERE dept_id = 'CSE';
  1. Statement 1: all values are legal and 101 is new. Succeeds.
  2. Statement 2: roll_no 101 already exists. Refused by the PRIMARY KEY.
  3. Statement 3: there is no department 'EEE'. Refused by the FOREIGN KEY stu_dept_fk.
  4. Statement 4: name is NULL. Refused by NOT NULL.
  5. Statement 5: 10.5 makes cgpa BETWEEN 0 AND 10 false. Refused by CHECK.
  6. Statement 6: cgpa is NULL, so the CHECK is unknown and passes; city is left out, so DEFAULT gives 'Chennai'. Succeeds: (111, 'Jai', 'MECH', NULL, 'Chennai').
  7. Statement 7: Jai refers to MECH, and the action is ON DELETE SET NULL. Succeeds: MECH is gone and Jai's row becomes (111, 'Jai', NULL, NULL, 'Chennai').
  8. Statement 8: Anu still refers to 'CSE', and changing a referenced key is refused (no ON UPDATE CASCADE). Refused by the FOREIGN KEY.

Answer: 3 statements succeed (1, 6, 7) and 5 are refused. At the end student holds Anu (CSE) and Jai (no department); department holds CSE, ECE and CIV. From Chapter 3.2 on, the book uses the full data listed at the start of that chapter.

Exam traps

  • PRIMARY KEY and UNIQUE are not the same: UNIQUE allows NULLs and a table may have many; it has only one primary key.
  • CHECK lets NULL through. To forbid both bad values and missing values, write NOT NULL as well.
  • Writing PRIMARY KEY after two separate columns tries to make two primary keys and fails; a composite key goes in one table-level clause.
  • TRUNCATE is DDL, not DML: no WHERE clause, and no rollback in Oracle or MySQL.
  • MySQL before 8.0.16 read CHECK constraints and then ignored them; on an old lab server, a "working" CHECK may not be checked at all.

3.2 Basic SQL queries: SELECT, FROM and WHERE

Almost every SQL query has the same three-part shape. FROM names the tables, WHERE keeps only the rows that satisfy a condition, and SELECT picks the columns to show. You say what you want, and the DBMS decides how to fetch it. The same WHERE clause also steers the three commands that change data: INSERT, UPDATE and DELETE.

The shape of a query

SELECT [DISTINCT] column-list     -- which columns
FROM   table-list                 -- which tables
WHERE  condition                  -- which rows
ORDER BY column [ASC | DESC], ... ;

Read a query in the order the DBMS logically runs it, not the order it is written: FROM → WHERE → SELECT → ORDER BY (Chapter 3.4 adds GROUP BY and HAVING between WHERE and SELECT). In relational algebra, SELECT A1, A2 FROM r WHERE P is ΠA1,A2(σP(r)). With two tables in FROM, SQL starts from their Cartesian product r × s, which is why a join condition goes in WHERE or ON (Chapter 3.5).

One difference from algebra matters: an SQL result is a multiset, so duplicate rows stay. SELECT DISTINCT removes them. SELECT * returns every column. A column may be an expression with an alias: SELECT dname, budget / 100000 AS budget_lakh FROM department shows CSE as 9 lakh.

Conditions in WHERE

  • Comparisons: = <> < <= > >=; strings go in single quotes: city = 'Chennai'.
  • Logic: NOT, then AND, then OR, in that order of binding. Use brackets when you mix AND and OR.
  • cgpa BETWEEN 7.5 AND 9.0 means cgpa >= 7.5 AND cgpa <= 9.0: both ends included.
  • dept_id IN ('ECE','MECH') means equal to any value in the list.
  • name LIKE 'C%': pattern match, where % stands for any run of characters (even none) and _ for exactly one.
  • dept_id IS NULL, IS NOT NULL: the only correct tests for a missing value.

Any comparison with NULL gives unknown, a third truth value besides true and false. WHERE keeps a row only when the condition is true; false and unknown rows are both dropped. So dept_id = NULL finds nobody, not even Gita.

Changing rows: INSERT, UPDATE, DELETE

INSERT INTO student (roll_no, name, dept_id, cgpa, city)
       VALUES (108, 'Hari', 'MECH', 7.5, 'Salem');
INSERT INTO toppers SELECT roll_no, name FROM student WHERE cgpa >= 9;
UPDATE student SET cgpa = cgpa + 0.2 WHERE roll_no = 104;
DELETE FROM enrols WHERE marks < 60;

INSERT can take a SELECT instead of VALUES and copy many rows at once (toppers is a two-column table made for this). UPDATE and DELETE touch every row that the WHERE clause makes true, and every row of the table if WHERE is missing.

Exam traps

  • = NULL is never true. Write IS NULL.
  • SELECT does not remove duplicates; relational algebra's Π does. Write DISTINCT when the question says "different" or "list of".
  • AND binds before OR: dept_id='CSE' OR dept_id='ECE' AND cgpa>8 means CSE, or (ECE and above 8).
  • A column alias made in SELECT cannot be used in WHERE, because WHERE runs first; it can be used in ORDER BY.
  • String comparison is case-sensitive in Oracle and PostgreSQL ('chennai' ≠ 'Chennai') but not under MySQL's default collation.

3.3 Set operations and nested subqueries

Hard questions are answered by building a query out of smaller queries. There are two ways. A set operation (UNION, INTERSECT, EXCEPT) joins the results of two whole queries, as with sets in school maths. A nested subquery is a complete SELECT written inside another query, usually in its WHERE clause, to test whether a value is in a set, to compare with a computed value, or to check whether any matching row exists.

You need: 3.2 Basic SQL queries and its data, and Unit 2, Set operations in algebra.

UNION, INTERSECT and EXCEPT

Let A be the roll numbers taking CS201 and B those taking CS202:

SELECT roll_no FROM enrols WHERE course_id = 'CS201'   -- A = {101, 102, 105}
UNION                                                  -- or INTERSECT, EXCEPT
SELECT roll_no FROM enrols WHERE course_id = 'CS202';  -- B = {101, 103, 106}

The two queries must be union-compatible: the same number of columns, with matching types in the same order. The result takes its column names from the first query, and one ORDER BY may follow at the very end. Oracle spells EXCEPT as MINUS. All three remove duplicate rows; UNION ALL keeps them and is faster because it skips the duplicate check. Figure 3.3.1 shows the results.

Subqueries with IN, ANY, ALL and EXISTS

  • IN: WHERE roll_no IN (SELECT roll_no FROM enrols WHERE course_id = 'CS202') finds Anu, Chitra, Farhan.
  • Scalar subquery, one value: WHERE cgpa > (SELECT AVG(cgpa) FROM student). The seven CGPAs add to 56.0, so the average is 56.0 / 7 = 8.0, and the answer is Anu, Chitra, Farhan (Esha's 8.0 is not greater). A scalar subquery that returns two rows is a run-time error.
  • ALL and ANY (also spelt SOME) compare with every value of a set. ECE CGPAs are {8.4, 6.9}. cgpa > ALL (ECE) means above 8.4: Anu, Farhan. cgpa > ANY (ECE) means above 6.9: everyone except Dev, 6 rows. = ANY is the same as IN, and <> ALL the same as NOT IN.
  • EXISTS (subquery) is true when the subquery returns at least one row; NOT EXISTS when it returns none. The SELECT list inside does not matter, so people write SELECT * or SELECT 1.

Correlated subqueries

A subquery is correlated when it uses a column of the outer query's current row. It then cannot be worked out once; logically it runs again for every outer row. "Students whose CGPA is above their own department's average":

SELECT s.name FROM student s
WHERE s.cgpa > (SELECT AVG(t.cgpa) FROM student t
                WHERE t.dept_id = s.dept_id);

The table aliases s and t tell the two copies of student apart. Figure 3.3.2 runs it row by row. A subquery that does not mention the outer row, like the overall average above, is non-correlated and runs once.

A subquery may also sit in FROM, where its result acts as a temporary table (a derived table), or be named up front with WITH name AS (SELECT …) to keep a long query readable.

Worked example

Exam traps

  • NOT IN over a subquery that can return NULL gives no rows at all. Prefer NOT EXISTS, or filter the NULLs out.
  • > ALL of an empty set is true for every row; > ANY of an empty set is false.
  • <> ANY is not NOT IN: it is true when the value differs from at least one member.
  • UNION removes duplicates; write UNION ALL when the question counts every row.
  • Calling every nested query "correlated": it is correlated only if the inner query uses a column of the outer row.

3.4 Aggregate functions and GROUP BY

An aggregate function turns a whole column of values into one value: how many, the total, the average, the smallest, the largest. GROUP BY first splits the rows into groups that share a value, so the aggregate gives one answer per group: average CGPA per department, students per course. HAVING then keeps only the groups that pass a test. Every report a college office prints, from pass percentages to fee collected per branch, is built this way.

You need: 3.2 Basic SQL queries and its data.

The five aggregate functions

On the 8 rows of enrols, whose marks add to 92 + 88 + 71 + 81 + 77 + 58 + 66 + 90 = 623:

FunctionReturnsValue on enrols
COUNT(*)number of rows8
COUNT(DISTINCT course_id)number of different non-null values3
SUM(marks)total623
AVG(marks)SUM ÷ number of non-null values623 / 8 = 77.875
MIN(marks), MAX(marks)smallest, largest58, 92

Two rules about NULL decide many exam answers. First, every aggregate except COUNT(*) skips NULLs: on student, COUNT(*) = 7 but COUNT(dept_id) = 6, because Gita's dept_id is NULL. Second, on an empty set of rows COUNT gives 0 and the others give NULL, not 0. MIN and MAX also work on text and dates (MIN(name) = 'Anu'); SUM and AVG need numbers.

GROUP BY and HAVING

SELECT   dept_id, COUNT(*) AS n, AVG(cgpa) AS avg_cg
FROM     student
GROUP BY dept_id
HAVING   COUNT(*) >= 2
ORDER BY avg_cg DESC;

The full logical order of a query is now FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. WHERE throws away rows before any group exists. GROUP BY puts rows with equal dept_id together; all NULLs form one group of their own. The aggregates are then computed once per group, and HAVING throws away whole groups. Figure 3.4.1 follows the query above.

Because the result has one row per group, SELECT may show only the grouping columns, aggregates, and constants. SELECT dept_id, name, AVG(cgpa) … GROUP BY dept_id is refused: the CSE group has three names, and SQL will not guess which one to print.

WHERE or HAVING?

Ask: does the test look at one row, or at a group? "Students with CGPA of at least 7" is a row test, so WHERE. "Departments whose average is above 8" is a group test, so HAVING. An aggregate inside WHERE, such as WHERE AVG(cgpa) > 8, is an error, because no groups exist yet when WHERE runs. A row test written in HAVING works on the grouping column but wastes effort, so put it in WHERE.

Worked example

Question (8 marks). (a) For each course give the number of students and the average, highest and lowest marks. (b) Show only courses whose average is above 70. (c) What changes if WHERE marks >= 60 is added? (d) For each department, count the students with CGPA of at least 7, showing only departments with at least 2 such students.

       MAX(marks) AS hi, MIN(marks) AS lo
FROM enrols
GROUP BY course_id
HAVING AVG(marks) > 70;          -- leave HAVING out for part (a)

  2. (b) HAVING AVG(marks) > 70 keeps CS201 (76.33) and CS202 (86.33); EC201 (67.50) is dropped.
  3. (c) WHERE runs first and removes the single row with 58. EC201 now holds only {77}: n = 1, avg 77.00, which passes HAVING. Result: CS201 76.33, CS202 86.33, EC201 77.00. One extra row filter changed which groups survive.
  4. (d) SELECT dept_id, COUNT(*) FROM student WHERE cgpa >= 7 GROUP BY dept_id HAVING COUNT(*) >= 2; WHERE removes Dev (6.9). Groups: CSE 3, ECE 1 (Chitra), MECH 1, NULL 1. Answer: CSE 3, one row.

Exam traps

  • COUNT(*) counts rows; COUNT(column) skips NULLs. On student they give 7 and 6.
  • AVG skips NULLs: for marks 80, NULL, 60, AVG = 140 / 2 = 70, not 140 / 3 = 46.67.
  • SUM over no rows is NULL, not 0. Write COALESCE(SUM(x), 0) when a zero is wanted.
  • An aggregate in WHERE is an error; a group condition belongs in HAVING.
  • Every non-aggregated column in SELECT must be in GROUP BY. (MySQL with its ONLY_FULL_GROUP_BY mode switched off accepts it and prints any one value; do not rely on that.)

3.5 SQL joins: inner and outer joins

A join puts side by side the rows of two tables that belong together, usually by matching a foreign key with the primary key it references. An inner join keeps only rows that found a partner; an outer join also keeps the rows that did not, filling the missing side with NULL. Joins answer every "show the student with the department name" question.

You need: Unit 2, Joins in algebra and the data of 3.2.

Inner join and its spellings

SELECT s.name, d.dname
FROM student s JOIN department d ON s.dept_id = d.dept_id;   -- INNER is optional

This returns 6 rows: every student with a department. Gita (dept_id NULL) and Civil (no students) are missing. The same result comes from the older form FROM student s, department d WHERE s.dept_id = d.dept_id, from JOIN department USING (dept_id), and from NATURAL JOIN, which matches every pair of columns with the same name and shows each such column once. An equi-join uses = in its condition; a theta join or non-equi join uses any other comparison. A CROSS JOIN has no condition and gives the Cartesian product: 7 × 4 = 28 rows. A self join joins a table with itself under two aliases.

Outer joins

  • student s LEFT OUTER JOIN department d ON …: every student; Gita appears with dname NULL. 7 rows.
  • RIGHT OUTER JOIN: every department; Civil appears with name NULL. 7 rows.
  • FULL OUTER JOIN: both kinds of leftovers. 8 rows. MySQL has no FULL JOIN; write a LEFT JOIN UNION a RIGHT JOIN.

Old Oracle code writes a left outer join as WHERE s.dept_id = d.dept_id(+): the (+) marks the side that may be missing.

Worked example

Question (6 marks). List every department with its number of students, including departments with none, in order of name.

SELECT d.dname, COUNT(s.roll_no) AS students
FROM department d LEFT JOIN student s ON s.dept_id = d.dept_id
GROUP BY d.dname
ORDER BY d.dname;
  1. The left table is department, so all 4 departments must survive. The join gives CSE × 3, ECE × 2, MECH × 1, and one padded row (Civil, NULL…) = 7 rows. Gita is not in it: she has no department to attach to.
  2. GROUP BY dname makes 4 groups. COUNT(s.roll_no) skips the NULL in Civil's padded row.
  3. Output: Civil 0, Computer Science 3, Electronics 2, Mechanical 1.
  4. With COUNT(*), Civil would wrongly show 1, because the padded row is still a row. With an inner join, Civil would vanish.

Exam traps

  • Forgetting the join condition gives the Cartesian product: 28 rows instead of 6.
  • After a LEFT JOIN, a condition on the right table placed in WHERE (WHERE d.block = 'C') removes the NULL-padded rows and silently turns it into an inner join; put it in ON to keep them.
  • NATURAL JOIN matches every same-named column. If both tables had a column called name, it would match on that as well.
  • Use COUNT(column of the optional side), not COUNT(*), when counting after an outer join.

3.6 Views in SQL

A view is a named query that you can use as if it were a table. The DBMS stores only the query's text in its data dictionary, not any rows; each time someone reads the view, the query runs again on the current base tables. Views exist for three reasons: to show each user only the rows and columns they should see, to hide a complicated query behind a simple name, and to keep old programs working when tables are reorganised (the external level of the three-schema architecture).

You need: Unit 1, Views of data and three-schema architecture, and 3.4 GROUP BY for the complex view.

Creating and using a view

CREATE VIEW cse_students AS
  SELECT roll_no, name, cgpa FROM student WHERE dept_id = 'CSE';

CREATE VIEW dept_stats (dept_id, n, avg_cg) AS
  SELECT dept_id, COUNT(*), AVG(cgpa) FROM student GROUP BY dept_id;

SELECT * FROM cse_students WHERE cgpa > 8;      -- Anu 9.1, Farhan 8.6
GRANT SELECT ON cse_students TO office_staff;
DROP VIEW dept_stats;

When a query names a view, the DBMS performs view expansion (also called query modification): it replaces the view name with its definition and runs the combined query on the base table. Figure 3.6.1 traces this. CREATE OR REPLACE VIEW changes a definition without dropping the grants on it. A view may be built on other views.

Types of view

  • Simple view: built on one table, with no DISTINCT, GROUP BY, aggregates or set operations. cse_students is one. It is usually updatable.
  • Complex view: uses a join, GROUP BY, aggregates, DISTINCT or computed columns. dept_stats is one. It is usually read-only.
  • Read-only view: declared so with WITH READ ONLY in Oracle.
  • Inline view: Oracle's name for a subquery in FROM; it has no stored name.
  • Materialized view: stores the result rows like a table and is refreshed on demand, on a schedule or at commit. It makes heavy reports fast but can be out of date between refreshes.

Some books also call a view that picks rows a horizontal view and one that picks columns a vertical view; cse_students is both.

Updating through a view

An INSERT, UPDATE or DELETE on a view must be passed to the base table, so it works only when each view row comes from exactly one base row. The usual rules: one table in FROM; no DISTINCT, GROUP BY, HAVING, aggregates or set operations; the changed columns are plain columns, not expressions; and for INSERT, every base column left out of the view must accept NULL or have a DEFAULT. WITH CHECK OPTION adds one more rule: a change through the view is refused if the new or changed row would not satisfy the view's WHERE clause. Complex views can be made updatable with INSTEAD OF triggers (Chapter 3.9).

Worked example

Question (8 marks). cse_students is recreated with WITH CHECK OPTION at the end of its definition. Starting from the data of Chapter 3.2, give the effect of each step.

1  SELECT * FROM cse_students ORDER BY cgpa DESC;
2  UPDATE cse_students SET cgpa = 8.0 WHERE roll_no = 102;
3  INSERT INTO cse_students VALUES (108, 'Hari', 8.2);
4  UPDATE student SET dept_id = 'ECE' WHERE roll_no = 106;
5  SELECT COUNT(*) FROM cse_students;
6  UPDATE dept_stats SET avg_cg = 9 WHERE dept_id = 'ECE';
  1. The view's query picks the CSE rows. Output: 101 Anu 9.1, 106 Farhan 8.6, 102 Bala 7.8.
  2. A simple view, and cgpa is a plain column: the change passes to student. 1 row updated; Bala's base row now has 8.0.
  3. The view has no dept_id, so the new base row would get dept_id NULL (and city 'Chennai' by default). NULL = 'CSE' is not true, so the row would be invisible through the view. Refused by WITH CHECK OPTION. Without the option it would be inserted and silently vanish from the view.
  4. This changes the base table directly: Farhan moves to ECE. The view stores no rows, so nothing else needs updating.
  5. The view re-runs on current data: Anu and Bala remain. Output: 2.
  6. avg_cg is an aggregate over two base rows; there is no single row to change. Refused: dept_stats is not updatable.

Exam traps

  • A view does not store data; only a materialized view does. "View = virtual table."
  • A plain view does not make a query faster: it is the same query run again. A materialized view can be faster, at the cost of staleness.
  • Without WITH CHECK OPTION, a row inserted or updated through a view can disappear from that view.
  • Any view with GROUP BY, DISTINCT or aggregates is not updatable, whatever its other columns are.

3.8 Transaction control: COMMIT, ROLLBACK and SAVEPOINT

A transaction is a group of SQL statements that must succeed or fail as one unit. When you send ₹1,000 by UPI, one account is debited and another credited; if the system stopped between the two, money would vanish. The transaction control language (TCL) lets the program decide the outcome: COMMIT makes all changes since the transaction began permanent, ROLLBACK undoes them all, and SAVEPOINT marks a point inside the transaction so that you can undo only the work after it.

You need: 3.2 for UPDATE, INSERT and DELETE. The theory behind this chapter, the ACID properties and log-based recovery, is in Unit 5.

Where a transaction begins and ends

In Oracle there is no "begin" command: a transaction starts with the first DML statement after the last one ended. It ends in one of these ways:

  • COMMIT: changes become permanent and visible to other users.
  • ROLLBACK: all changes since the last COMMIT are undone.
  • A DDL statement (CREATE, ALTER, DROP, TRUNCATE): Oracle and MySQL commit implicitly, so the work before it is committed too.
  • Leaving the session: a normal exit from SQL*Plus commits; a crash or a killed session rolls back.

MySQL, PostgreSQL and SQL Server work in autocommit mode by default: each statement is committed on its own unless you first write START TRANSACTION (or BEGIN). Oracle's SQL*Plus is the other way round; SET AUTOCOMMIT ON changes it.

Until you commit, you see your own changes but other sessions still see the old values, and the rows you changed stay locked. This is why a long uncommitted transaction can make other users wait. If one statement fails, for example on a CHECK constraint, Oracle undoes just that statement; earlier work in the transaction stays and still needs a COMMIT or ROLLBACK.

The three commands and their rules

COMMIT;
ROLLBACK;
SAVEPOINT s1;
ROLLBACK TO SAVEPOINT s1;     -- or ROLLBACK TO s1
  1. ROLLBACK TO s1 undoes every change made after s1, keeps s1 itself (you can roll back to it again), and erases savepoints made after s1. The transaction stays open; nothing is committed.
  2. COMMIT and plain ROLLBACK end the transaction and erase all its savepoints.
  3. Making a savepoint with a name already in use moves that name to the new point.
  4. A savepoint is only a bookmark: it makes nothing permanent.

Worked example

Question (8 marks). Table account(acc_no, holder, balance) holds A101 Ravi ₹5,000 and A102 Meena ₹2,000, committed. One session runs steps 1 to 11 of Figure 3.8.1 in Oracle. Give (a) the balances after step 7, (b) the committed state after step 9, (c) the final state, (d) what happens if step 7 is followed by ROLLBACK TO s2, and (e) the state after a restart if the server crashes just after step 8.

  1. Steps 1 and 2 move ₹1,000: A101 = 5000 − 1000 = 4000, A102 = 2000 + 1000 = 3000. s1 marks this state.
  2. Step 4 gives A102 = 3000 − 500 = 2500; s2 is marked; step 6 adds A103 with 1500.
  3. (a) ROLLBACK TO s1 undoes steps 4 and 6 and erases s2: A101 = 4000, A102 = 3000, no A103. The transaction is still open.
  4. (b) Step 8 gives A101 = 4000 + 200 = 4200. COMMIT makes A101 = 4200, A102 = 3000 permanent; total 7200 = 7000 + the ₹200 credit.
  5. (c) Step 10 deletes A102 inside a new transaction; step 11 undoes it. Final: A101 = 4200, A102 = 3000, the same as after step 9.
  6. (d) s2 was erased by the rollback to s1, so ROLLBACK TO s2 fails with an error ("savepoint never established" in Oracle). Data is unchanged.
  7. (e) Nothing had been committed, so recovery undoes steps 1 to 8: A101 = 5000, A102 = 2000. The half-done work is never seen.

Exam traps

  • ROLLBACK cannot undo anything that has been committed, including work committed implicitly by a DDL statement.
  • In Oracle, UPDATE …; CREATE TABLE …; ROLLBACK; keeps the update: the CREATE committed it.
  • ROLLBACK TO a savepoint does not end the transaction; you still need COMMIT or ROLLBACK.
  • In autocommit mode (the MySQL default), ROLLBACK after a single UPDATE does nothing: the UPDATE was already committed.
  • Savepoints after the target are erased; the target savepoint itself survives.

3.9 PL/SQL: cursors, stored procedures, functions and triggers

PL/SQL is Oracle's procedural extension of SQL: SQL statements placed inside blocks that also have variables, IF, loops and error handling, all run inside the database server. A cursor lets the block walk through a query's rows one at a time. Blocks stored under a name become stored procedures and functions, which programs call, and triggers, which the DBMS fires on its own when a table changes.

Blocks and cursors

A block has up to four parts: DECLARE (variables), BEGIN (statements), EXCEPTION (handlers) and END;. After every UPDATE, INSERT or DELETE, the implicit cursor attribute SQL%ROWCOUNT tells how many rows changed. For a query with many rows, an explicit cursor goes through four steps: DECLARE, OPEN (the query runs and its result, the active set, is ready), FETCH one row at a time into variables, and CLOSE. Its attributes are %FOUND, %NOTFOUND, %ROWCOUNT (rows fetched so far) and %ISOPEN. A cursor FOR loop, FOR r IN c LOOP … END LOOP, does the open, fetch and close for you. Figure 3.9.1 follows a cursor through the block of the worked example below.

Stored procedures and functions

CREATE OR REPLACE PROCEDURE raise_budget (p_dept IN VARCHAR2, p_pct IN NUMBER) AS
BEGIN
  UPDATE department SET budget = budget * (1 + p_pct/100) WHERE dept_id = p_dept;
  IF SQL%ROWCOUNT = 0 THEN
    RAISE_APPLICATION_ERROR(-20001, 'No such department');
  END IF;
END;
/
EXEC raise_budget('ECE', 10);          -- ECE: 700000 becomes 770000

CREATE OR REPLACE FUNCTION dept_avg (p_dept VARCHAR2) RETURN NUMBER AS
  v NUMBER;
BEGIN
  SELECT AVG(cgpa) INTO v FROM student WHERE dept_id = p_dept;
  RETURN ROUND(v, 2);
END;
/
SELECT dept_avg('ECE') FROM dual;      -- 7.65

Both are stored, compiled, in the database, so every application shares one tested copy. Parameters have a mode: IN (value passed in, the default), OUT (result passed back) or IN OUT. A function must RETURN one value and can be used inside a SQL expression; a procedure is called as a statement and hands back results through OUT parameters.

Triggers

CREATE OR REPLACE TRIGGER trg_cgpa_audit
AFTER UPDATE OF cgpa ON student
FOR EACH ROW
BEGIN
  INSERT INTO cgpa_log VALUES (:OLD.roll_no, :OLD.cgpa, :NEW.cgpa, SYSDATE);
END;
/

A trigger names its timing (BEFORE, AFTER, or INSTEAD OF for a view), its event (INSERT, UPDATE, DELETE) and its level: a row-level trigger (FOR EACH ROW) fires once per changed row and reads :OLD and :NEW; a statement-level one fires once per statement. For UPDATE student SET cgpa = cgpa + 0.1 WHERE dept_id = 'ECE', the row trigger above fires twice and logs (103, 8.4, 8.5) and (104, 6.9, 7.0). Triggers serve auditing, derived columns and rules too complex for CHECK.

Worked example

Question (6 marks). Write a PL/SQL block that prints, with a serial number, every student with CGPA of at least 8.5, highest first, and then the total. Dry-run it on the Chapter 3.2 data.

SET SERVEROUTPUT ON
DECLARE
  CURSOR c IS SELECT name, cgpa FROM student
              WHERE cgpa >= 8.5 ORDER BY cgpa DESC;
  v_name student.name%TYPE;     -- same type as the column
  v_cgpa student.cgpa%TYPE;
BEGIN
  OPEN c;
  LOOP
    FETCH c INTO v_name, v_cgpa;
    EXIT WHEN c%NOTFOUND;
    DBMS_OUTPUT.PUT_LINE(c%ROWCOUNT || '. ' || v_name || ' ' || v_cgpa);
  END LOOP;
  DBMS_OUTPUT.PUT_LINE('Total: ' || c%ROWCOUNT);
  CLOSE c;
END;

Exam traps

  • Put EXIT WHEN c%NOTFOUND straight after FETCH; placed after the print, the last row prints twice.
  • Reading c%ROWCOUNT after CLOSE raises INVALID_CURSOR; read it before closing.
  • SELECT … INTO must return exactly one row (NO_DATA_FOUND, TOO_MANY_ROWS); an aggregate always returns one, so dept_avg('CIV') returns NULL, not an error.
  • A trigger is never called with EXEC; it fires on its event. :NEW is empty in a DELETE trigger and :OLD in an INSERT trigger.

Takeaways

  1. Constraints (NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK) stop bad rows at the door; CHECK lets NULL through.
  2. Read a query in logical order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY.
  3. A comparison with NULL is unknown, and WHERE keeps only true rows: use IS NULL, and prefer NOT EXISTS to NOT IN.
  4. SQL keeps duplicates; DISTINCT, UNION, INTERSECT and EXCEPT remove them, UNION ALL keeps them.
  5. A correlated subquery is evaluated once per outer row; EXISTS tests for at least one row.
  6. Aggregates skip NULLs except COUNT(*); WHERE filters rows, HAVING filters groups.
  7. Outer joins keep unmatched rows with NULLs; count the optional side's column, not *.
  8. A view stores a query, not rows; it is updatable only when each view row is one base row.
  9. Nothing is permanent until COMMIT, but DDL commits implicitly; ROLLBACK TO a savepoint keeps the transaction open.
  10. PL/SQL cursors fetch one row at a time; exit right after FETCH on %NOTFOUND; triggers fire on events, never by call.

Glossary

Active set
The rows of a cursor's query after OPEN.
Aggregate function
A function that returns one value for a set of rows: COUNT, SUM, AVG, MIN, MAX.
Autocommit
A mode in which each statement is committed as soon as it succeeds.
CHECK constraint
A condition each row must not make false.
Correlated subquery
A subquery that uses a column of the outer query's current row, so it is evaluated once per outer row.
Cursor
A named pointer to the result of a query, used to process its rows one at a time.
DDL
Data definition language: commands that create, change and remove structure.
DML
Data manipulation language: SELECT, INSERT, UPDATE, DELETE.
Derived table
A subquery in FROM whose result is used as a table.
Foreign key
A column whose values must exist in a referenced primary or unique key.
GROUP BY
The clause that splits rows into groups of equal values for aggregation.
HAVING
The clause that keeps or drops whole groups after GROUP BY.
Implicit commit
A commit the DBMS performs on its own, for example before and after a DDL statement in Oracle.
Materialized view
A view whose result rows are stored and refreshed.
Multiset
A collection that may contain duplicates; SQL results are multisets.
Natural join
A join on all columns with the same name in both tables.
Outer join
A join that also keeps unmatched rows, padding the other side with NULL.
PL/SQL
Oracle's procedural language that combines SQL with variables, control flow and exception handling.
Referential action
What happens to referencing rows when a referenced row is deleted or updated: CASCADE, SET NULL, NO ACTION.
Savepoint
A named point inside a transaction that ROLLBACK TO can return to.
Scalar subquery
A subquery that returns exactly one value.
Self join
A join of a table with itself under two aliases.
Stored procedure
A named PL/SQL block stored in the database and called as a statement.
TCL
Transaction control language: COMMIT, ROLLBACK, SAVEPOINT.
Three-valued logic
SQL's logic of true, false and unknown, where unknown comes from NULL.
Trigger
A stored block that the DBMS runs automatically when a given event happens on a table or view.
Union-compatible
Two queries with the same number of columns and matching types, as set operations require.
View
A named, stored query used like a table; it holds no rows of its own.
WITH CHECK OPTION
A view clause that refuses changes producing rows the view cannot see.
