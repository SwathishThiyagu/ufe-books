2.1 Relational model: relations, tuples, schema and instance

The relational model, proposed by E. F. Codd of IBM in 1970, stores all data as relations: tables with named columns in which every cell holds one value. A database is a set of such tables, and every question is answered by combining tables by their values, never by following stored pointers. This one idea separates what the data means from how it sits on disk, which is why nearly every business system, from IRCTC ticket bookings to a bank's UPI ledger, runs on a relational DBMS.

You need: Unit 1, Data models: hierarchical, network, relational, object-oriented; and Unit 1, Mapping ER diagrams to relational tables, which produces the relations studied here.

The vocabulary of a relation

Every term below has a plain table word next to it. Use the formal word in an exam answer and the table word to remember it.

Formal termTable wordMeaning
RelationTableA set of tuples that all have the same attributes
TupleRowOne fact: one value for each attribute
AttributeColumn nameA named property, such as cgpa
DomainColumn typeThe set of values an attribute may take, such as decimals from 0.0 to 10.0
Degree (arity)Number of columnsHow many attributes the relation has
CardinalityNumber of rowsHow many tuples the relation holds right now

The formal definition is short. Take domains D₁, D₂, …, Dₙ. Their Cartesian product D₁ × D₂ × … × Dₙ is the set of every possible n-tuple ⟨v₁, v₂, …, vₙ⟩ with each vᵢ taken from Dᵢ. A relation on these domains is any subset of that product. So a relation is simply the chosen set of tuples that are true facts today. For a tuple t and an attribute A, the notation t[A] (or t.A) means the value of A in t.

What "a relation is a set" forces

Because a relation is a set, four properties follow, and examiners ask for them by name.

  1. No duplicate tuples. A set cannot hold the same element twice, so two identical rows can never both be in a relation.
  2. Tuple order does not matter. Shuffling the rows gives the same relation; there is no "first row".
  3. Attribute order does not matter when attributes are named, because a tuple is then a mapping from names to values. (In the pure mathematical definition with numbered positions, order is fixed; most textbooks use the named view.)
  4. Values are atomic. Each cell holds one value from its domain, not a list or a nested table. This is first normal form; see Unit 4, First, second and third normal forms.

One special value, null, marks a value that is unknown or does not apply, such as the phone number of a student who has none. Null is not zero and not an empty string; Chapter 2.8 shows why Codd made this a rule.

Schema and instance

The relation schema is the design: the relation's name, its attributes and their domains, written R(A₁, A₂, …, Aₙ), for example Student(roll_no, name, dept, cgpa). The relation instance r(R) is the set of tuples stored at one moment. A database schema is the set of all relation schemas plus their constraints; a database instance is the set of all current relation instances.

The schema changes rarely, and only through a data definition command such as ALTER TABLE. The instance changes with every insert, delete and update. A programming analogy helps: in C, the declaration int marks[60]; is like a schema, while the 60 values held in marks at 10:15 a.m. are like an instance. In the three-schema architecture of Unit 1, the schemas in this unit are logical (conceptual) schemas.

Worked example

Question (6 marks). The relation Enrol(roll_no, course, grade) has domains roll_no ∈ {101, 102, 103}, course ∈ {DBMS, OS} and grade ∈ {A, B, C, D}. Its instance today is (101, DBMS, A), (101, OS, B), (102, DBMS, B), (103, OS, C).
(a) State the degree and cardinality. (b) How many different tuples are possible, and how many different instances? (c) A rule says each student takes each course at most once. What is the largest possible cardinality? (d) The grade of 103 in OS is changed to B and (102, OS, A) is inserted. Did the schema or the instance change? Give the new degree and cardinality.

  1. Degree and cardinality. Three attributes, so degree = 3. Four tuples, so cardinality = 4.
  2. Possible tuples. Every tuple comes from the Cartesian product of the domains: |D₁| × |D₂| × |D₃| = 3 × 2 × 4 = 24 possible tuples.
  3. Possible instances. An instance is any subset of those 24 tuples. A set of 24 elements has 2²⁴ subsets, so there are 2²⁴ = 16,777,216 possible instances, counting the empty relation.
  4. Largest cardinality under the rule. Each (roll_no, course) pair may appear only once. There are 3 × 2 = 6 pairs, so at most 6 tuples. This rule makes {roll_no, course} a key (Chapter 2.2).
  5. After the changes. An update and an insert change only the instance; the schema is untouched. Degree stays 3. The update keeps the count, the insert adds one, so cardinality = 4 + 1 = 5.

Exam traps

  • A relation is a table; a relationship is an ER association between entities (Unit 1). Do not mix the words.
  • Degree is the number of columns and cardinality the number of rows. Swapping them is the most common one-mark slip.
  • An SQL table without a key can hold two identical rows (it is a multiset, or "bag"); a relation in the model cannot. Say this when asked how SQL differs from the model.
  • Null is neither 0 nor the empty string ''. A student with cgpa null has an unknown cgpa, not a cgpa of zero.
  • Count carefully: the number of possible tuples is a product of domain sizes; the number of possible instances is 2 raised to that product.

It breaks atomicity: a cell holds a list, not one domain value, so the table is not in first normal form and a query such as "who takes OS?" must cut strings apart. Fix: store one tuple per (roll_no, subject) pair, for example (101, DBMS), (101, OS), (101, CN).

The same relational idea now runs at every scale: SQLite inside every Android phone, PostgreSQL and MySQL behind most web apps, and distributed SQL systems such as Google Spanner and CockroachDB spread one logical schema across data centres. 2.2 Keys: super, candidate, primary and foreign keys

A key is a set of attributes whose values pick out exactly one tuple, the way a roll number picks out one student. Keys stop duplicate facts and let one table point to another. Every later chapter uses them.

Four definitions, each built on the last

  1. Superkey. A set K of attributes such that no two distinct tuples of any legal instance agree on all of K. In symbols: t₁[K] = t₂[K] ⇒ t₁ = t₂.
  2. Candidate key. A superkey with no proper subset that is also a superkey, that is, a minimal superkey. A relation may have several.
  3. Primary key. The one candidate key the designer chooses to identify tuples, underlined in the schema. The others become alternate keys. Prefer a key that is short, never null and never changes.
  4. Foreign key. A set of attributes in a relation R₁ whose values must equal the primary key of some tuple in a relation R₂, or be null. R₁ is the referencing relation and R₂ the referenced one. R₂ may be R₁ itself, as when Employee.manager_id refers to Employee.emp_id.

A key is a property of the schema, decided from what the data means. One instance can prove a set is not a key (two rows agree on it) but can never prove that it is.

Worked example

Question (5 marks). Student(roll_no, aadhaar, name, phone) has candidate keys {roll_no} and {aadhaar}. (a) How many superkeys does it have? (b) Enrol(roll_no, course, grade) has the single candidate key {roll_no, course}. How many superkeys? (c) Two rows of Student have name "Ravi". What does that tell you about {name}?

  1. Superkeys containing roll_no. The other 3 attributes may each be in or out: 2³ = 8 sets.
  2. Superkeys containing aadhaar. Likewise 2³ = 8 sets.
  3. Remove the double count. Sets containing both keys were counted twice: the other 2 attributes are free, 2² = 4 sets. Total = 8 + 8 − 4 = 12 superkeys.
  4. Enrol. Both roll_no and course must be present; only grade is free: 2¹ = 2 superkeys, {roll_no, course} and {roll_no, course, grade}. In general, n attributes with one candidate key of k attributes give 2ⁿ⁻ᵏ superkeys.
  5. The two Ravis. Two distinct tuples agree on name, so {name} is not a superkey, and hence not a candidate key.

Exam traps

  • "Minimal" means no attribute can be removed, not "fewest attributes". {roll_no} and a two-attribute key can both be candidate keys.
  • Every candidate key is a superkey; most superkeys are not candidate keys.
  • A primary key can never be null; a foreign key can be null unless declared NOT NULL.
  • Do not "find" a key by looking at sample rows. Rows can only rule a set out.

Check yourself

Remember Define a candidate key. 2 marks

A minimal superkey: a set of attributes that uniquely identifies tuples, with no proper subset that does.

Understand Why is every candidate key a superkey, but not the other way round? 2 marks

A candidate key is defined as a superkey that is also minimal. A superkey may carry extra attributes, such as {roll_no, name}, so it need not be minimal.

Apply R(A, B, C, D, E) has one candidate key {A, B}. How many superkeys? 2 marks

A and B fixed, C, D, E free: 2⁵⁻² = 2³ = 8.

Apply R(A, B, C) has candidate keys {A} and {B}. How many superkeys? 2 marks

With A: 2² = 4. With B: 4. With both: 2¹ = 2. Total 4 + 4 − 2 = 6.

Analyze Train(train_no, name, date, seats). Today no two rows share a name. Is {name} a candidate key? Is {train_no} enough if a train runs every day? 4 marks

No to both. Today's rows cannot prove a key; two trains could share a name later. If one row is stored per train per date, train_no repeats every day, so the candidate key is {train_no, date}.

Beyond the syllabus

Not for the exam. Many systems use a surrogate key, an auto-increment number or a UUID, instead of a natural key such as Aadhaar, partly because natural keys change and partly for privacy. Finding candidate keys from functional dependencies needs attribute closure; see Unit 4, Functional dependencies: Armstrong's axioms and closure.

2.3 Integrity constraints and referential integrity

An integrity constraint is a condition that every legal instance of the database must satisfy, such as "cgpa lies between 0 and 10" or "every employee's department exists". The constraints are declared once in the schema, and the DBMS checks them on every insert, delete and update, rejecting or repairing any change that would break one. This keeps bad data out no matter which program writes it. Referential integrity, the rule that a foreign key must point to a tuple that really exists, is the one examiners ask about most.

You need: Chapter 2.2, Keys, for primary and foreign keys.

The four standard constraints

  1. Domain constraint. Every value must come from its attribute's domain: the right type, inside the allowed range, and not null where NOT NULL is declared. Example: CHECK (cgpa BETWEEN 0 AND 10).
  2. Key constraint. No two tuples may have the same value of a candidate key. SQL declares this with PRIMARY KEY or UNIQUE.
  3. Entity integrity. No attribute of the primary key may be null. A tuple with a null key cannot be identified, and two nulls cannot even be compared.
  4. Referential integrity. Let FK in relation R₁ refer to the primary key PK of R₂. For every tuple t₁ in R₁, either t₁[FK] is null, or some tuple t₂ in R₂ has t₂[PK] = t₁[FK]. In algebra terms (Chapter 2.4), ignoring nulls: πFK(R₁) ⊆ πPK(R₂).

Beyond these four, a database can carry semantic (business) constraints, such as "seats booked on a train never exceed its capacity". These are written as CHECK conditions, assertions or triggers; see Unit 3, SQL data definition and integrity constraints, and Unit 3, PL/SQL: cursors, stored procedures, functions and triggers.

Which change can break which constraint

A classic long-answer question asks you to discuss constraint violations for each update operation. The table is the answer in one view.

OperationDomainKeyEntityReferential
Insert a tupleYesYesYesYes, if its FK value has no match in R₂
Delete a tupleNoNoNoYes, only when deleting from R₂ a tuple that R₁ still points to
Update a non-key attributeYesNoNoNo
Update a primary keyYesYesYesYes, old FK values in R₁ are left pointing at nothing
Update a foreign keyYesNo (unless the FK is part of the key)NoYes, if the new value has no match

What the DBMS does: referential actions

An insert into R₁ with an unmatched foreign key is simply rejected. A delete or key update in R₂ that would leave orphans in R₁ has a choice of responses, declared with the foreign key.

  1. RESTRICT or NO ACTION (the default): refuse the delete or update. NO ACTION checks at the end of the statement, RESTRICT at once; both reject.
  2. CASCADE: apply the same change to the referencing tuples, deleting them or copying the new key into them.
  3. SET NULL: set the foreign key of each referencing tuple to null.
  4. SET DEFAULT: set it to the column's default value, which must itself exist in R₂.

In SQL the choice sits on the foreign key clause:

CREATE TABLE Employee (
  emp_id   CHAR(2)     PRIMARY KEY,
  name     VARCHAR(30) NOT NULL,
  dept_id  CHAR(2)     REFERENCES Department(dept_id)
                       ON DELETE SET NULL
                       ON UPDATE CASCADE
);

Worked example

Question (8 marks). Use the instances of Figure 2.3.1, with emp_id the primary key of Employee and dept_id the primary key of Department. Treat each operation separately, starting from the original data. For each, name the constraint at risk, say whether the DBMS accepts it, and give the row counts afterwards.
(a) insert (E5, Kiran, D9) into Employee; (b) insert (E2, Priya, D1); (c) insert (null, Arun, D1); (d) insert (E6, Divya, null); (e) delete (D2, ECE) under RESTRICT, CASCADE and SET NULL in turn; (f) change D3 to D7 in Department with ON UPDATE CASCADE; (g) delete E1 from Employee.

  1. (a) D9 matches no dept_id in Department. Referential integrity is violated, so the insert is rejected. Counts stay Employee 4, Department 3.
  2. (b) E2 already exists. The key constraint is violated: rejected; counts 4 and 3.
  3. (c) The primary key would be null. Entity integrity is violated: rejected; counts 4 and 3.
  4. (d) A null foreign key is allowed, and E6 is new. Accepted: Employee 5, Department 3.
  5. (e) E2 and E3 refer to D2. RESTRICT: rejected, counts 4 and 3. CASCADE: D2, E2 and E3 all go, so Employee 2 (E1, E4), Department 2. SET NULL: D2 goes, E2 and E3 stay with dept_id null, so Employee 4, Department 2.
  6. (f) The key update cascades: E4's dept_id becomes D7. Accepted; counts 4 and 3, and no orphan remains.
  7. (g) No relation refers to Employee, so nothing can be orphaned. Accepted: Employee 3, Department 3.

Exam traps

  • Deleting from the referencing relation (Employee) never breaks referential integrity; deleting from the referenced relation (Department) can.
  • Entity integrity is "the primary key is never null"; referential integrity is "the foreign key matches or is null". Keep the two names straight.
  • SET NULL fails if the foreign key column is NOT NULL or is part of the primary key, as Takes.roll_no usually is.
  • A foreign key must refer to a primary key or UNIQUE column with the same domain; the column names may differ.
  • CASCADE on delete can wipe large amounts of history in one statement. Examiners like asking when it is the wrong choice.

Domain constraint, key constraint, entity integrity, referential integrity.

Remember State the referential integrity rule. 2 marks

Every foreign key value in the referencing relation is either null or equal to the primary key value of some existing tuple in the referenced relation.

Insert into the referencing relation, or update of its foreign key, with an unmatched value; delete from the referenced relation, or update of its primary key, while referencing tuples still exist.

Apply Takes(roll_no, cid) has 40 rows, 12 of them with cid = C3. Its cid references Course ON DELETE CASCADE. Course C3 is deleted. How many Takes rows remain? 2 marks

The 12 C3 rows are deleted with it: 40 − 12 = 28 rows.

Apply Employee dept_id values are {D1, D2, D2, D5}; Department dept_id values are {D1, D2, D3}. Check πdept_id(Employee) ⊆ πdept_id(Department). 2 marks

πdept_id(Employee) = {D1, D2, D5}. D5 is not in {D1, D2, D3}, so the inclusion fails: referential integrity is violated by the D5 row.

Analyze Orders(order_id, customer_id) refers to Customer. Which ON DELETE action would you choose when a customer closes an account, and why not CASCADE? 4 marks

RESTRICT (mark the customer inactive instead of deleting) or SET NULL. Orders are financial records needed for GST returns and refunds; CASCADE would silently delete them. RESTRICT keeps both the history and the link.

Beyond the syllabus

Not for the exam. PostgreSQL and Oracle allow a constraint to be declared DEFERRABLE INITIALLY DEFERRED, so it is checked at commit instead of after each statement; this is how two tables that refer to each other are loaded. The SQL standard's CREATE ASSERTION for constraints across tables exists on paper, but the major engines do not implement it, so triggers do that job. In microservice systems each service owns its own database, so foreign keys across services cannot be enforced by any DBMS and must be checked by the application. Search "deferrable constraints" and "referential integrity in microservices".

2.4 Relational algebra: select, project and rename

Relational algebra is a procedural query language: a small set of operators, each of which takes one or two relations and returns a new relation. Because every result is again a relation (the algebra is closed), operators nest into expressions just as + and × do in arithmetic. Every SQL query is translated into an algebra expression before it runs, so this is the language the query optimiser thinks in (Unit 6, Query optimization: cost estimation and heuristics). The basic set is select σ, project π, union ∪, set difference −, Cartesian product × and rename ρ. This chapter covers the three that work on one relation; Chapter 2.5 covers the rest.

You need: Chapter 2.1, relations as sets of tuples.

All examples use this instance of Student(roll_no, name, dept, cgpa): (101, Asha, CSE, 9.1), (102, Ravi, ECE, 7.8), (103, Meena, CSE, 8.4), (104, John, MECH, 6.9), (105, Priya, CSE, 7.5), (106, Karthik, ECE, 8.8).

Selection σ: keep some rows

σp(r) returns the tuples of r for which the predicate p is true. The predicate is built from comparisons of the form attribute θ constant or attribute θ attribute, where θ is one of =, ≠, <, ≤, >, ≥, joined by ∧ (and), ∨ (or) and ¬ (not). For example σdept='CSE' ∧ cgpa>8(Student) returns the tuples of Asha and Meena.

  • The degree is unchanged, and 0 ≤ |σp(r)| ≤ |r|, where |r| is the cardinality of r.
  • Selections commute and combine: σp(σq(r)) = σq(σp(r)) = σp ∧ q(r).
  • The predicate looks at one tuple at a time. It cannot compare two different tuples; that needs a product or join (Chapter 2.5).

Projection π: keep some columns

πA₁, …, Aₖ(r) returns, for each tuple of r, only the listed attributes, and then removes duplicate tuples, because the result must be a set. For example πdept(Student) produces CSE, ECE, CSE, MECH, CSE, ECE, which collapses to the 3 tuples {CSE, ECE, MECH}.

  • The degree becomes k, and |π(r)| ≤ |r|. Equality holds when the list contains a superkey, since then no two results can be equal.
  • Projections cascade: πL₁(πL₂(r)) = πL₁(r) when L₁ ⊆ L₂.
  • A selection can be moved below a projection only if the projection keeps every attribute the predicate uses.

Rename ρ: give a result a name

ρx(E) returns the result of expression E under the name x. ρx(B₁, …, Bₙ)(E) also renames its attributes, in order, to B₁, …, Bₙ. Rename changes no values and no row count. It is needed when one relation is used twice in the same query, as in "students with a higher cgpa than Ravi" (Chapter 2.5), and for naming intermediate results. Many books also allow assignment: CSE ← σdept='CSE'(Student) stores a result in a temporary relation called CSE.

Composing and reading an expression

Read an expression from the inside out. πname, cgpa(σdept='CSE'(Student)) first selects the CSE rows, then keeps two columns. In SQL this is SELECT DISTINCT name, cgpa FROM Student WHERE dept = 'CSE';. Note the naming clash: the SQL keyword SELECT does projection, and the WHERE clause does selection. An expression can also be drawn as a tree with relations at the leaves and operators above them; the optimiser rearranges that tree to run faster.

Worked example

Question (6 marks). On the Student instance above, write a relational algebra expression and give its result, degree and cardinality for: (a) the names of CSE students with cgpa above 8; (b) the departments that have at least one student; (c) roll numbers and names of students outside CSE, as a relation NonCSE with attributes id and sname.

  1. (a) Select, then project. σdept='CSE' ∧ cgpa>8(Student): check the three CSE rows. Asha 9.1 > 8 yes; Meena 8.4 > 8 yes; Priya 7.5 > 8 no. Two tuples remain. Then πname gives {Asha, Meena}: degree 1, cardinality 2.
  2. (b) Project only. πdept(Student) lists CSE, ECE, CSE, MECH, CSE, ECE. Removing duplicates leaves {CSE, ECE, MECH}: degree 1, cardinality 3 (down from 6).
  3. (c) Select, project, rename. ρNonCSE(id, sname)(πroll_no, name(σdept≠'CSE'(Student))). The selection keeps 102, 104 and 106. Result: (102, Ravi), (104, John), (106, Karthik) with attributes id and sname: degree 2, cardinality 3.

Second question (3 marks). Are πdept(σcgpa>8(Student)) and σcgpa>8(πdept(Student)) equal?

  1. First expression. cgpa > 8 keeps 101 (9.1, CSE), 103 (8.4, CSE) and 106 (8.8, ECE). Projecting dept gives {CSE, ECE}, cardinality 2.
  2. Second expression. πdept leaves a relation with only the attribute dept. The predicate cgpa > 8 names an attribute that no longer exists, so the expression is not valid. They are not equal; push a selection below a projection only when the projection keeps the predicate's attributes.

Exam traps

  • Algebra σ is SQL's WHERE; algebra π is SQL's SELECT list. "Select" means different things in the two languages.
  • π removes duplicates, so its cardinality can drop (6 to 3 above). An SQL SELECT without DISTINCT keeps them.
  • σ can never increase the row count, and π can never increase the degree.
  • A selection predicate cannot refer to an attribute that an inner projection has removed.
  • Writing σcgpa>8(Student) and then reporting only names is wrong; the result of σ has all four columns until you project.

Understand What does it mean that relational algebra is closed, and why does it matter? 2 marks

Every operator returns a relation, so the output of one operator can be the input of another. That lets simple operators nest into expressions of any size.

Understand Why can projection reduce the number of tuples? 2 marks

Dropping columns can make two different tuples identical on the remaining attributes, and the result is a set, so the duplicates collapse into one.

Analyze Is πA(πA,B(r)) equal to πA,B(πA(r))? Explain. 3 marks

The left side is valid and equals πA(r) by the cascade rule. The right side is invalid, because after πA the attribute B no longer exists. So they are not equal.

Analyze r has 1,000 tuples and {roll_no} is its primary key. What is |πroll_no(r)|, and what can you say about |πdept(r)|? 3 marks

Key values are all different, so πroll_no(r) has exactly 1,000 tuples. dept is not a key, so |πdept(r)| can be anything from 1 to 1,000; it equals the number of distinct departments.

Beyond the syllabus

Not for the exam. Type EXPLAIN before a query in PostgreSQL or MySQL to see the plan tree the optimiser built from your SQL: its nodes are algebra operators with a cost attached. Engines such as Apache Spark SQL and frameworks such as Apache Calcite rewrite queries as relational algebra trees in exactly this way. The extended algebra adds generalised projection with arithmetic, aggregation (see Unit 3, Aggregate functions and GROUP BY) and bag versions of every operator, which is what SQL really runs. Search "query plan EXPLAIN" and "extended relational algebra aggregation".

2.5 Set operations, Cartesian product and joins in algebra

The binary operators combine two relations. Set operations merge or compare relations of the same shape; the Cartesian product pairs every tuple of one relation with every tuple of the other; a join is a product followed by a selection, written as one operator.

You need: Chapter 2.4, σ, π and ρ.

Set operations

Two relations r and s are union-compatible when they have the same degree and the i-th attributes of both share a domain. Only then are these defined:

  • Union r ∪ s: tuples in r, in s, or in both, each once. |r ∪ s| = |r| + |s| − |r ∩ s|.
  • Set difference r − s: tuples in r but not in s. It is not commutative.
  • Intersection r ∩ s: tuples in both. It is derived, not basic: r ∩ s = r − (r − s).

Cartesian product and joins

The Cartesian product r × s joins every tuple of r with every tuple of s. Its degree is deg(r) + deg(s) and its cardinality |r| × |s|. Attributes with the same name are told apart by prefixes, as in Emp.did and Dept.did.

  • Theta join r ⋈θ s = σθ(r × s), for any condition θ. When θ uses only =, it is an equijoin; both copies of the compared attributes remain.
  • Natural join r ⋈ s: an equijoin on every attribute name the two relations share, keeping one copy of each. With no shared names it equals r × s.
  • Outer joins (left ⟕, right ⟖, full ⟗) also keep the tuples that found no partner, padding them with nulls; see Unit 3, SQL joins: inner and outer joins.

The set {σ, π, ∪, −, ×} is complete: every other operator, including ∩, every join and division (Chapter 2.6), can be written with these five.

Worked example

Question (6 marks). r(A, B) = {(1, a), (2, b), (3, c)} and s(A, B) = {(2, b), (3, d), (4, e)}. Find r ∪ s, r ∩ s, r − s and s − r. Then, for Emp and Dept of Figure 2.5.1, give the degree and cardinality of Emp × Dept, Emp ⋈Emp.did=Dept.did Dept and Emp ⋈ Dept.

  1. Intersection. Only (2, b) is in both, so r ∩ s = {(2, b)}, 1 tuple. (3, c) and (3, d) differ in B, so they are different tuples.
  2. Union. {(1, a), (2, b), (3, c), (3, d), (4, e)}: 3 + 3 − 1 = 5 tuples.
  3. Differences. r − s = {(1, a), (3, c)}, 2 tuples; s − r = {(3, d), (4, e)}, 2 tuples. Check: r ∩ s = r − (r − s) = {(2, b)}.
  4. Product. Degree 3 + 2 = 5; cardinality 3 × 2 = 6.
  5. Equijoin. Rows where the two did values match: 3 tuples, still degree 5.
  6. Natural join. The same 3 tuples with one did column: degree 4, cardinality 3.

Exam traps

  • ∪, ∩ and − need union-compatible relations; × and joins do not.
  • An equijoin keeps both join columns; a natural join keeps one.
  • A natural join matches every shared name. If both relations also have a column called name, rows are silently lost.
  • Comparing two rows of one relation needs ρ to make a second copy first.

2.6 Tuple relational calculus

Tuple relational calculus (TRC) is a non-procedural, or declarative, query language: you describe the tuples you want with a logical condition, and the system decides how to find them. A query has the form {t | P(t)}, read "the set of all tuples t for which the formula P(t) is true". It is first-order predicate logic applied to relations, proposed by Codd alongside the algebra, and SQL's SELECT … FROM … WHERE … EXISTS borrows its shape.

You need: Chapter 2.4 and Chapter 2.5, to compare each query with its algebra form.

The examples use Student(roll_no, name, dept, cgpa) from Chapter 2.4, plus Course(cid, title, dept) = {(C1, DBMS, CSE), (C2, OS, CSE), (C3, Networks, CSE), (C4, Signals, ECE)} and Takes(roll_no, cid) = {(101, C1), (101, C2), (101, C3), (102, C1), (102, C4), (103, C1), (103, C3), (105, C1), (105, C2), (105, C3)}.

Tuple variables, atoms and formulas

A tuple variable stands for one tuple of a relation, the way a loop variable stands for one array element. A formula is built from three kinds of atom:

  1. t ∈ r: t is a tuple of relation r. (Elmasri and Navathe write r(t).)
  2. t[A] θ s[B]: compare attribute A of t with attribute B of s, where θ is =, ≠, <, ≤, > or ≥. Some books write t.A.
  3. t[A] θ c: compare an attribute with a constant c.

Atoms combine with ∧ (and), ∨ (or), ¬ (not) and ⇒ (implies; P ⇒ Q means ¬P ∨ Q), and with two quantifiers:

  • ∃s ∈ r (Q(s)): there exists a tuple s in r for which Q(s) is true.
  • ∀s ∈ r (Q(s)): for every tuple s in r, Q(s) is true. It can always be rewritten as ¬∃s ∈ r (¬Q(s)).

A variable inside the scope of a quantifier is bound; one that is not is free. In a query {t | P(t)}, the result variable t must be the only free variable, and its attributes are exactly the ones P assigns.

Four patterns that cover most exam questions

  1. Selection. Whole tuples of CSE students with cgpa above 8: {t | t ∈ Student ∧ t[dept] = 'CSE' ∧ t[cgpa] > 8}.
  2. Projection. Only their names: {t | ∃s ∈ Student (s[dept] = 'CSE' ∧ s[cgpa] > 8 ∧ t[name] = s[name])}. Here t is a new tuple with the single attribute name, copied from s.
  3. Join. Names of students who took C2: {t | ∃s ∈ Student ∃k ∈ Takes (s[roll_no] = k[roll_no] ∧ k[cid] = 'C2' ∧ t[name] = s[name])}. The shared roll_no links the two relations.
  4. Negation. Students who took no course at all: {t | t ∈ Student ∧ ¬∃k ∈ Takes (k[roll_no] = t[roll_no])}.

The fifth pattern, "for all", is the one that separates good answers from average ones. It is worked in full below.

Safety and expressive power

The query {t | ¬(t ∈ Student)} asks for every tuple that is not a student. There are infinitely many such tuples, made of any values at all, so no system can return the answer. Such an expression is unsafe. An expression is safe when every value in its result comes from dom(P), the set of constants written in P plus the values in the relations P mentions. The quantifiers then only need to range over that finite set.

Codd's theorem (1972) states that safe tuple calculus, safe domain calculus (Chapter 2.7) and relational algebra can express exactly the same queries. A query language that can express every relational algebra query is called relationally complete; SQL is relationally complete and adds more, such as aggregation.

Worked example

Question (10 marks). Using Student, Course and Takes above: (a) write TRC for the names of students who took every CSE course; (b) evaluate it on the instance; (c) explain what goes wrong if ⇒ is replaced by ∧; (d) write the same query in relational algebra with division, and evaluate it.

  1. (a) The formula. {t | ∃s ∈ Student (t[name] = s[name] ∧ ∀c ∈ Course (c[dept] = 'CSE' ⇒ ∃k ∈ Takes (k[roll_no] = s[roll_no] ∧ k[cid] = c[cid])))}. Read it as: "s is a student, and for every course c, if c is a CSE course then s has a Takes row for c".
  2. (b) Evaluate. The CSE courses are C1, C2 and C3. Asha (101) has all three: pass. Ravi (102) lacks C2 and C3: fail. Meena (103) lacks C2: fail. John (104) and Karthik (106) have no Takes rows: fail. Priya (105) has all three: pass. Result: {Asha, Priya}, 2 tuples.
  3. (c) The ∧ mistake. With ∀c ∈ Course (c[dept] = 'CSE' ∧ …), every course must be a CSE course. C4 is ECE, so the condition fails for every student and the result is empty. Use ⇒ with ∀, and ∧ with ∃.
  4. (d) Division. For r(X, Y) and s(Y), r ÷ s is the set of X values that appear in r with every Y in s. Take r = Takes(roll_no, cid) and s = πcid(σdept='CSE'(Course)) = {C1, C2, C3}. The query is πname(Student ⋈ (Takes ÷ s)).
  5. Compute r ÷ s with basic operators. r ÷ s = πX(r) − πX((πX(r) × s) − r), with X = roll_no. πX(r) = {101, 102, 103, 105}, 4 values. πX(r) × s has 4 × 3 = 12 pairs. Removing the pairs present in Takes leaves the missing pairs (102, C2), (102, C3) and (103, C2). Their roll numbers are {102, 103}. So r ÷ s = {101, 102, 103, 105} − {102, 103} = {101, 105}.
  6. Finish. Joining with Student and projecting name gives {Asha, Priya}, the same answer as the calculus, as Codd's theorem promises.

Exam traps

  • ∀ goes with ⇒, ∃ goes with ∧. Swapping them gives an empty or wrong answer, as in part (c).
  • Leaving s without its ∃ makes s a second free variable, and the expression is no longer a valid query.
  • A top-level ¬, as in {t | ¬(t ∈ Student)}, makes the query unsafe. Always tie t to a relation first.
  • "Procedural" is the algebra (it says how); "non-procedural" or "declarative" is the calculus (it says what). Examiners ask this for 2 marks.
  • Notation varies: t ∈ Student or Student(t); t[name] or t.name. Any one is accepted if you stay consistent.

Analyze Compare tuple relational calculus with relational algebra. 5 marks

Algebra is procedural: an ordered sequence of operators that says how to compute the answer. TRC is declarative: a logical condition that says what the answer is. Beyond the syllabus

The Ingres research system of the 1970s used QUEL, a query language built directly on tuple calculus, before SQL won the market. Database theory studies these languages as first-order logic over finite structures; search "relational calculus first-order logic" and "Codd's theorem" to go further.

2.7 Domain relational calculus

Domain relational calculus (DRC) is the second form of relational calculus. Its variables stand for single attribute values, members of a domain, instead of whole tuples. A query has the form {⟨x₁, x₂, …, xₙ⟩ | P(x₁, x₂, …, xₙ)}: the set of value lists that make P true. QBE (Query-By-Example), designed at IBM by Moshé Zloof in the 1970s, is built on it, and so are the fill-in query grids of desktop tools.

You need: Chapter 2.6, Tuple relational calculus; this chapter only shows what changes.

Domain variables and atoms

The connectives ∧, ∨, ¬, ⇒ and the quantifiers ∃ and ∀ work exactly as in TRC. Only the atoms change:

  1. ⟨x₁, …, xₙ⟩ ∈ r: the values x₁ to xₙ, in the order of r's attributes, form a tuple of r. For Student(roll_no, name, dept, cgpa), ⟨r, n, d, g⟩ ∈ Student binds r to roll_no, n to name, d to dept and g to cgpa. A constant may stand in a position, as in ⟨r, n, 'CSE', g⟩.
  2. x θ y and x θ c: compare two domain variables, or a variable and a constant.

Every variable that is not in the result list must be bound by ∃ (written ∃r, d, g for ∃r ∃d ∃g). A join needs no equality: using the same variable in two atoms forces the values to be equal. Safety and power are as in TRC: safe DRC expresses exactly what relational algebra does.

Worked example

Question (6 marks). Using Student of Chapter 2.4 and Takes of Chapter 2.6, write DRC for (a) the name and cgpa of every ECE student; (b) the names of students who took C3. Evaluate both.

  1. (a) Formula. The result needs n and g; r and d must be bound: {⟨n, g⟩ | ∃r, d (⟨r, n, d, g⟩ ∈ Student ∧ d = 'ECE')}. Putting the constant in its position gives the shorter {⟨n, g⟩ | ∃r (⟨r, n, 'ECE', g⟩ ∈ Student)}.
  2. (a) Evaluate. The ECE rows are 102 and 106: {(Ravi, 7.8), (Karthik, 8.8)}, 2 tuples of degree 2.
  3. (b) Formula. {⟨n⟩ | ∃r, d, g (⟨r, n, d, g⟩ ∈ Student ∧ ⟨r, 'C3'⟩ ∈ Takes)}. The shared r links each student to their own Takes rows.
  4. (b) Evaluate. Takes rows with C3 have roll numbers 101, 103 and 105. Their names: {Asha, Meena, Priya}, 3 tuples.

Exam traps

  • Positions follow the attribute order. ⟨n, r, d, g⟩ ∈ Student would bind n to roll_no.
  • Each atom ⟨…⟩ ∈ r needs one variable or constant for every attribute of r, even ones you do not use.
  • Forgetting ∃ on r, d or g leaves free variables that are not in the result list: an invalid query.
  • DRC has nothing to do with the "domain constraint" of Chapter 2.3, though both use the word domain.

Beyond the syllabus

Not for the exam. Datalog, a rule language used in program analysis and in some data systems, is positional like DRC: answer(N) :- student(R, N, 'CSE', G), G > 8. It adds recursion, which neither calculus has. Search "Datalog" and "Query-By-Example Zloof".

2.8 Codd's rules for relational databases

By the 1980s many products called themselves "relational" while keeping their old pointer-based designs underneath. In 1985 Codd answered with a list of rules, published in two Computerworld articles, that a system must follow to deserve the name. They are called the twelve rules, but they are numbered 0 to 12, so there are thirteen. Together they protect the model's two promises: all data is reached through values in tables by one high-level language, and programs keep working when storage or structure changes.

You need: Chapter 2.1 and Chapter 2.3; also Unit 1, Views of data and three-schema architecture, for rules 8 and 9.

The thirteen rules

No.RuleWhat it demands
0Foundation ruleThe system must manage its databases entirely through its relational capabilities.
1Information ruleAll information, including table and column names, is stored as values in tables.
2Guaranteed accessEvery single value can be reached by table name + primary key value + column name, with no pointers or positions.
3Systematic treatment of nullsA null marks missing or inapplicable information, is distinct from zero and the empty string, and works the same for every data type.
4Dynamic online catalogThe description of the database (the catalog or data dictionary) is itself stored as tables and queried with the same language.
5Comprehensive data sublanguageAt least one language with a plain text syntax supports data definition, view definition, data manipulation, integrity constraints, authorisation and transaction boundaries.
6View updatingEvery view that is theoretically updatable can be updated by the system.
7High-level insert, update and deleteInsert, update and delete work on whole sets of rows in one statement, not just one row at a time.
8Physical data independencePrograms are unaffected by changes in storage or access methods.
9Logical data independencePrograms are unaffected by changes to tables that keep the same information, such as splitting a table.
10Integrity independenceIntegrity constraints are defined in the data sublanguage and stored in the catalog, not coded in programs.
11Distribution independencePrograms work the same whether the data sits on one machine or is spread over many.
12Non-subversion ruleIf a low-level, record-at-a-time interface exists, it cannot be used to bypass the integrity rules.

Five groups that make them easy to remember

Learning thirteen rules as a list is hard; learning five ideas is easy. Rule 0 is the foundation that the rest spell out. Rules 1 to 4 fix the structure: data, nulls and even the catalog are values in tables. Rules 5 to 7 fix the language: one language does everything, including updates on views and on whole sets of rows. Rules 8 to 11 promise independence: programs survive changes to storage, table structure, constraints and location. Rule 12 is protection: there is no back door around the rules.

Rules 8 and 9 are the three-schema architecture of Unit 1 written as a test. Physical independence (rule 8) lets the DBA add an index or move files without touching programs. Logical independence (rule 9) lets the DBA split a table and keep old programs running through a view with the old table's name.

Worked example

Question (8 marks). Student is the six-row table of Chapter 2.4, with one more row (107, Divya, ECE, null) for a student whose cgpa is not yet known. For each statement or event below, name the Codd rule it shows and give the result.

(a) SELECT column_name FROM information_schema.columns
    WHERE table_name = 'student';
(b) SELECT cgpa FROM Student WHERE roll_no = 103;
(c) UPDATE Student SET cgpa = cgpa + 0.1 WHERE dept = 'CSE';
(d) CREATE INDEX idx_dept ON Student(dept);   -- then rerun (c)
(e) SELECT name FROM Student WHERE cgpa IS NULL;
(f) ALTER TABLE Student ADD CHECK (cgpa BETWEEN 0 AND 10);
    UPDATE Student SET cgpa = 10.5 WHERE roll_no = 101;
  1. (a) Rule 4, online catalog. The table's own description is read with ordinary SQL from catalog tables. Result: 4 rows, roll_no, name, dept, cgpa.
  2. (b) Rule 2, guaranteed access. Table name Student, key value 103 and column cgpa reach one value: 8.4.
  3. (c) Rule 7, set-level update. One statement changes every CSE row: 101 from 9.1 to 9.2, 103 from 8.4 to 8.5, 105 from 7.5 to 7.6. 3 rows updated.
  4. (d) Rule 8, physical independence. The index changes how rows are found, not what the statement means. Statement (c) needs no change and still updates the same 3 rows; only its speed may change.
  5. (e) Rule 3, nulls. Result: Divya, 1 row. Writing WHERE cgpa = NULL instead returns 0 rows, because a comparison with null is "unknown", never true.
  6. (f) Rule 10, integrity independence. The constraint lives in the catalog, not in any program. The update to 10.5 breaks it, so it is rejected, whichever program sends it, and Asha's row keeps its old cgpa.

Exam traps

  • "Twelve rules" are numbered 0 to 12: there are thirteen. Write rule 0 too.
  • Rule 1 says data is stored as values in tables; rule 2 says each value can be reached by table, key and column. Do not merge them.
  • Rule 8 (physical: indexes, files) and rule 9 (logical: table structure) are the pair examiners most often swap.
  • Rule 10 puts constraints in the catalog; rule 12 stops low-level tools from going around them.
  • No commercial product satisfies all thirteen rules. Do not write that Oracle or MySQL "follows all twelve". And Codd's rules (1985) are not Codd's theorem (1972) of Chapter 2.6.

Check yourself

Remember State the information rule. 1 mark

All information in a relational database, including table and column names, is represented explicitly as values in tables.

In 1985, to test whether products sold as relational really were. They are numbered 0 to 12, so thirteen rules.

Understand Distinguish physical from logical data independence with one example each. 4 marks

Physical (rule 8): adding an index or moving data files does not change programs. Logical (rule 9): splitting Student into two tables and creating a view called Student keeps old programs running.

Understand Why should the catalog be stored as relational tables? 2 marks

So that users and tools can find out what tables, columns and constraints exist with the same query language they use for data, with no special interface.

Apply One UPDATE statement adds 5% interest to the 1,200 savings accounts among 5,000 accounts. Which rule does it use, and how many rows change? 2 marks

Apply A bulk-load utility writes rows straight into data files and skips the foreign key checks. Which rule is broken? 2 marks

Analyze Why do most SQL products only partly meet rule 6? 4 marks

Updating a view means turning the change into changes on the base tables. For a view with joins, aggregates or DISTINCT there may be many possible translations or none. Deciding this in general is hard, so products allow updates only on simple views (usually one table, no grouping) or through triggers written by hand.

Beyond the syllabus

Not for the exam. C. J. Date and Hugh Darwen's The Third Manifesto argues that SQL itself breaks the model, through duplicate rows and nulls, and proposes a stricter language. NoSQL databases drop several rules on purpose, such as a fixed schema and joins, to scale out cheaply (Unit 6, NoSQL databases: document, key-value and graph). NewSQL and distributed SQL systems try to meet rule 11 at internet scale. Search "The Third Manifesto" and "NewSQL".

Takeaways

  1. A relation is a set of tuples over named attributes: no duplicate rows, no row order, one atomic value per cell.
  2. The schema is the design and changes by DDL; the instance is today's data and changes with every insert, delete and update.
  3. Superkeys contain candidate keys, which contain the primary key; a foreign key must match a primary key or be null.
  4. Domain, key, entity and referential integrity are checked on every change; deleting a referenced row triggers RESTRICT, CASCADE, SET NULL or SET DEFAULT.
  5. σ keeps rows, π keeps columns and removes duplicates, ρ renames; σ, π, ∪, −, × form a complete set.
  6. A join is a product followed by a selection; a natural join matches every shared attribute name and keeps one copy.
  7. Tuple and domain calculus state what is wanted; in "for all" queries use ∀ with ⇒, and in algebra use division.
  8. Safe calculus and algebra are equally powerful (Codd's theorem); Codd's thirteen rules test whether a product is truly relational.

Remember Q4. State and explain Codd's rules for relational database systems. 16 marks

Why Codd wrote them (1985). All thirteen rules, 0 to 12, each with one line of meaning and an SQL example where possible (catalog query, key access, IS NULL, set-level UPDATE, index for physical independence, CHECK for integrity independence). Grouping into foundation, structure, language, independence, protection (Figure 2.8.1). No product satisfies all.

Understand Q5. Explain the unary operators of relational algebra with examples, and state the algebraic laws that apply to them. 8 marks

σ with predicates and connectives; π with duplicate removal; ρ for relations and attributes; closure. Laws: σ commutes and cascades into ∧; π cascades; σ moves below π only if π keeps the predicate's attributes. SQL correspondence and the SELECT naming clash.

Apply

Apply Q6. For Student(roll_no, name, dept, cgpa), Course(cid, title, dept) and Takes(roll_no, cid), write relational algebra for: names of CSE students; courses taken by Asha; students who took no course; pairs of students in the same department; students who took every CSE course. 10 marks

πname(σdept='CSE'(Student)); πcid(σname='Asha'(Student) ⋈ Takes); πroll_no(Student) − πroll_no(Takes); self-join with ρ and the condition S1.dept = S2.dept ∧ S1.roll_no < S2.roll_no; Takes ÷ πcid(σdept='CSE'(Course)). Evaluate each on the unit's instance: {Asha, Meena, Priya}; {C1, C2, C3}; {104, 106}; for example (101, 103); {101, 105}.

Apply Q7. r(A, B) = {(1, x), (2, y), (3, z), (4, x)} and s(A, B) = {(2, y), (4, y), (5, z)}. Compute r ∪ s, r ∩ s, r − s, s − r, and the degree and cardinality of r × s. 8 marks

r ∩ s = {(2, y)}, 1 tuple. r ∪ s = {(1, x), (2, y), (3, z), (4, x), (4, y), (5, z)}, 4 + 3 − 1 = 6 tuples. r − s = {(1, x), (3, z), (4, x)}, 3 tuples. s − r = {(4, y), (5, z)}, 2 tuples. r × s: degree 4, cardinality 4 × 3 = 12.

Apply Q8. Write the queries of Q6 in tuple relational calculus and in domain relational calculus, and evaluate the "every CSE course" query. 12 marks

Patterns of Chapter 2.6 (selection, projection, join, negation) and their DRC forms with positional variables and shared variables for joins (Chapter 2.7). For all: ∀c ∈ Course (c[dept] = 'CSE' ⇒ ∃k ∈ Takes (…)). Evaluation grid (Figure 2.6.1): {Asha, Priya}. State safety.

Apply Q9. R(A, B, C, D, E) has candidate keys {A} and {B, C}. List the candidate keys, choose a primary key with a reason, and count the superkeys. 8 marks

Superkeys containing A: 2⁴ = 16. Containing B and C: 2³ = 8. Containing A, B and C: 2² = 4. Total 16 + 8 − 4 = 20. Primary key {A}: one attribute, shorter to store in foreign keys. {B, C} becomes an alternate key, declared UNIQUE.

Apply Q10. Dept has 4 rows; Emp has 50 rows, 18 of them in department D2, with dept_id referencing Dept. Give the row counts of both tables after deleting D2 under RESTRICT, CASCADE and SET NULL, and after inserting an employee with dept_id D9. 8 marks

RESTRICT: rejected, Dept 4, Emp 50. CASCADE: Dept 3, Emp 50 − 18 = 32. SET NULL: Dept 3, Emp 50 with 18 null dept_ids. Insert with D9 (no such department): rejected by referential integrity, counts unchanged.

Analyze and evaluate

Analyze Q11. Compare relational algebra, tuple relational calculus and domain relational calculus. Discuss procedurality, variables, safety and expressive power, with one query written in all three. 13 marks

Spans Chapters 2.4 to 2.7. Algebra procedural, calculus declarative. Tuple variables against domain variables and positional atoms. Unsafe expressions and dom(P). Codd's theorem and relational completeness. One query, such as names of students who took C2, in all three, evaluated to the same answer.

Analyze Q12. Show that intersection, natural join and division can be expressed with σ, π, ∪, −, × and ρ. Verify the division formula on an instance. 12 marks

Spans Chapters 2.5 and 2.6. r ∩ s = r − (r − s). r ⋈ s = πL(σequalities(r × s)) with renaming. r ÷ s = πX(r) − πX((πX(r) × s) − r), evaluated on Takes and the CSE courses: 12 pairs, 3 missing, answer {101, 105}. Conclude that {σ, π, ∪, −, ×} is complete.

Analyze Q13. Design the keys and foreign keys for a train booking database with Train, Station, Passenger and Booking. Choose a referential action for each foreign key and justify it. 13 marks

Spans Chapters 2.2 and 2.3. Candidate keys (train_no; station code; passenger id or Aadhaar; PNR), composite keys where a train runs on many dates. Booking references Train, Passenger and both Stations. RESTRICT on Train and Station deletes (history matters); CASCADE on PNR changes is rare; SET NULL only for optional links. Explain entity integrity for each key.

Analyze Q14. "SQL databases are relational." Evaluate this claim using Codd's rules and the formal definition of a relation. 10 marks

Spans Chapters 2.1, 2.3 and 2.8. Meets: catalog tables, key access, one language, set-level updates, declared constraints, physical independence. Falls short: duplicate rows allowed (bags), three-valued null logic, limited view updating, bulk tools that skip checks, partial distribution independence. Conclusion: relational in practice, not fully by Codd's definition.

Glossary

Alternate key
A candidate key that was not chosen as the primary key.
Atomic value
A single, indivisible value from a domain; not a list or a nested table.
Attribute
A named column of a relation, such as cgpa.
Bound variable
A variable in a calculus formula that lies within the scope of ∃ or ∀.
Candidate key
A minimal superkey: no attribute can be removed without losing uniqueness.
Cardinality
The number of tuples in a relation instance.
Cartesian product
r × s: every tuple of r combined with every tuple of s.
CASCADE
A referential action that applies a delete or key update to the referencing tuples too.
Catalog
The tables that describe the database itself: its tables, columns, constraints and users. Also called the data dictionary.
Codd's theorem
Safe tuple calculus, safe domain calculus and relational algebra have equal expressive power.
Degree
The number of attributes of a relation; also called arity.
Division
r ÷ s: the values that appear in r together with every tuple of s; used for "for all" queries.
Domain
The set of values an attribute may take.
Domain relational calculus
A declarative query language whose variables range over attribute values.
Entity integrity
The rule that no attribute of a primary key may be null.
Equijoin
A theta join whose condition uses only equality; both join columns are kept.
Foreign key
Attributes of one relation whose values must match the primary key of another (or the same) relation, or be null.
Free variable
A variable in a formula not bound by any quantifier; in a query only the result variable may be free.
Natural join
r ⋈ s: an equijoin on all shared attribute names, keeping one copy of each.
Null
A marker for a missing or inapplicable value; not zero and not the empty string.
Primary key
The candidate key chosen to identify tuples; never null.
Referential integrity
Every foreign key value is null or matches an existing primary key value.
Relation
A set of tuples over a fixed list of attributes; a table in the relational model.
Relational algebra
A procedural query language of operators that take relations and return relations.
Relationally complete
Able to express every query that relational algebra can express.
Safe expression
A calculus expression whose result uses only values from dom(P), so it is finite.
Schema
The design of a relation or database: names, attributes, domains and constraints.
Superkey
A set of attributes whose values are never shared by two distinct tuples.
Tuple
One row of a relation: one value for each attribute.
Union-compatible
Two relations with the same degree and matching attribute domains, as ∪, ∩ and − require.
