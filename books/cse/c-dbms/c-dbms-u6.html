6.1 Disk storage and RAID

A database lives on non-volatile storage: magnetic disks and flash drives that keep their data through a Chennai power cut. RAM is fast but small and is wiped by a crash, so the DBMS keeps the database on disk and brings in fixed-size blocks only when a query needs them. A disk access takes milliseconds against about a tenth of a microsecond for RAM, so every later chapter counts cost in disk blocks. RAID (redundant array of independent disks) joins several disks into one store that is faster and survives a disk failure.

You need: Unit 1, Views of data and three-schema architecture; this chapter is its physical level.

The storage hierarchy

Storage media form a ladder from fast, small and costly to slow, large and cheap: CPU cache, RAM, flash (SSDs), magnetic disk (HDDs), then optical disks and tape. Primary storage (cache, RAM) is used directly by the CPU and is volatile. Secondary storage (flash, magnetic disk) is non-volatile and holds the online database. Tertiary storage (tape, optical) holds backups and archives. The DBMS moves data between RAM and disk in blocks (pages) of usually 4 KB to 16 KB, and a buffer manager keeps recently used blocks in RAM.

Inside a magnetic disk

A hard disk has one or more platters on a spindle that turns at a fixed speed such as 5400, 7200 or 15,000 rpm (revolutions per minute). Each surface is divided into concentric tracks, and each track into sectors, the smallest unit the disk reads or writes: 512 bytes on older disks and 4096 bytes on newer ones. A read-write head on an arm floats over each surface. All the arms move together, so the tracks under all the heads at one arm position form a cylinder. The time to read one block from the disk has three parts:

access time = seek time + rotational latency + transfer time
  • Seek time: moving the arm to the right track, a few milliseconds on average.
  • Rotational latency: waiting for the sector to come under the head. On average this is half a rotation, 60 / (2 × rpm) seconds.
  • Transfer time: block size ÷ transfer rate.

The first two terms are mechanical and the third is tiny, so reading blocks that lie one after another (sequential access) is far faster than jumping about (random access). A DBMS therefore stores the blocks of one file next to each other. An SSD has no moving parts, so its random reads cost tens of microseconds.

RAID: striping, mirroring and parity

Many disks together are fast but fail often: if one disk has a mean time to failure (MTTF) of 100,000 hours, an array of 100 disks loses some disk about every 1,000 hours, roughly every six weeks. RAID uses three tools:

  • Striping: split data across n disks so that they transfer in parallel. Block-level striping puts block i of a file on disk (i mod n) + 1.
  • Mirroring: keep an identical copy of every disk on a second disk.
  • Parity: store the XOR (⊕) of the data blocks of a stripe in one extra block. If any one block is lost, the XOR of the others rebuilds it.

Worked example

Question. A database server uses 7200 rpm disks with an average seek time of 8 ms and a transfer rate of 150 MB/s (1 MB = 10⁶ bytes). The block size is 4 KB (4096 bytes). (a) Find the average time to read one random block. (b) Find the time to read 1000 blocks placed randomly, and 1000 blocks placed one after another. (c) Six 4 TB disks are available: give the usable space under RAID 0, RAID 10, RAID 5 and RAID 6. (d) A RAID 5 stripe holds data blocks 1010, 0110 and 0011. Find the parity block, and rebuild the second block after its disk fails. [8 marks]

  1. One rotation = 60 s ÷ 7200 = 8.33 ms. Average rotational latency = 8.33 ÷ 2 = 4.17 ms.
  2. Transfer time = 4096 B ÷ 150,000,000 B/s = 0.0273 ms.
  3. (a) One random block = 8 + 4.17 + 0.0273 = 12.19 ms. The disk manages about 1000 ÷ 12.19 ≈ 82 random reads per second.
  4. (b) 1000 random blocks = 1000 × 12.19 ms = 12,190 ms ≈ 12.2 s.
  5. 1000 consecutive blocks need one seek and one rotational wait, then 1000 transfers: 8 + 4.17 + 1000 × 0.0273 = 8 + 4.17 + 27.3 = 39.5 ms (ignoring the short moves between adjacent tracks). Sequential reading is about 12,190 ÷ 39.5 ≈ 309 times faster.
  6. (c) RAID 0: 6 × 4 = 24 TB. RAID 10: 24 ÷ 2 = 12 TB. RAID 5: (6 − 1) × 4 = 20 TB. RAID 6: (6 − 2) × 4 = 16 TB.
  7. (d) Parity: 1010 ⊕ 0110 = 1100, then 1100 ⊕ 0011 = 1111. Rebuild the lost block from the survivors: 1010 ⊕ 0011 = 1001, then 1001 ⊕ 1111 = 0110, which is the lost block.

Exam traps

  • Rotational latency is half a rotation, not a full one: at 7200 rpm it is 4.17 ms, not 8.33 ms.
  • RAID 0 has no redundancy at all. One failed disk loses the whole array, so it is the fastest level and the least safe.
  • RAID 4 keeps parity on one disk; RAID 5 spreads it. The examiner's favourite: "why is RAID 5 preferred to RAID 4?" Because every write updates parity, and in RAID 4 that one disk becomes the bottleneck.
  • RAID is not a backup. A wrong DELETE is copied to every mirror at once; backups and the recovery log of Unit 5 are still needed.

Analyze A railway booking database does thousands of small updates per second. Compare RAID 5 and RAID 10 for it and recommend one. 6 marks

RAID 5 gives more space (n − 1 disks), but each small write costs four I/Os and a rebuild reads every other disk. RAID 10 gives half the space, but a write costs two I/Os, reads can use either copy and a rebuild copies one disk. For a write-heavy load, RAID 10 wins.

6.2 File organization and organization of records

A file is a sequence of records stored in disk blocks. File organization decides two things: how records are laid out inside a block, and where in the file a new record goes. The second choice fixes how fast every later search runs, so it is the first decision of physical database design.

You need: Chapter 6.1, blocks and why block reads are the unit of cost.

Fixed-length and variable-length records

Take Student(roll CHAR(8), name CHAR(30), dept CHAR(4), cgpa REAL), whose fields take 8 + 30 + 4 + 4 = 46 bytes. With fixed-length records, record i (counting from 0) starts at byte 46 × i, so finding it is pure arithmetic. Deleting a record leaves a hole. Either move the last record into the hole, or keep a free list: the file header holds the address of the first free slot and each free slot holds the address of the next, so an insert reuses a hole in one step.

Records become variable-length when a table has VARCHAR fields, nullable fields or several record types in one file. Such a record stores its fixed-size fields first, then an (offset, length) pair for each variable field, then a null bitmap with one bit per nullable field, and finally the variable data.

Inside a block, variable-length records use the slotted page structure (Figure 6.2.1). The block header holds the number of records, the end of the free space, and a slot array with one (offset, length) entry per record. Records are packed from the end of the block toward the header, so the free space stays in one piece in the middle. A pointer from outside, from an index for example, names the block and the slot number, not the byte offset. A record can therefore move inside its block, when the page is compacted after a delete, without breaking any pointer.

Blocking factor and spanned records

The blocking factor bfr is the number of records per block: bfr = ⌊B / R⌋, where B is the block size and R the record size, both in bytes. A file of r records then needs b = ⌈r / bfr⌉ blocks. The floor drops the part-record that does not fit; the ceiling counts the last, partly filled block. With unspanned records each record lies wholly in one block, and B − bfr × R bytes per block go unused. With spanned records a record may continue in the next block through a pointer, so no space is wasted but some records cost two block reads. Unspanned is the usual choice when R is much smaller than B.

Placing records in a file

  • Heap file: a new record goes wherever there is space, usually the last block. Insertion is cheap. A search on a key value is a linear search: b/2 blocks on average when the value exists, all b when it does not. Good for bulk loads and tables read in full.
  • Sequential (sorted) file: records are kept in order of a search key such as roll number. Equality search is a binary search over blocks, about ⌈log₂ b⌉ reads, and range queries and ORDER BY read neighbouring blocks. Insertion is costly: a record must go into its proper block, or into an overflow block chained from it when that block is full, and the file is reorganised (rewritten in order) from time to time, say at night.
  • Hashed file: a hash function of a key picks the block (chapter 6.5).
  • Multitable clustering file: records of two related tables are stored together, such as each department record followed by its employees. A join of the two reads few blocks, but scanning one table alone reads more.
  • B+ tree file: the leaves of a B+ tree hold the records themselves (chapter 6.4).

Worked example

Question. A Customer file has r = 30,000 fixed-length records of R = 100 bytes, block size B = 4096 bytes, unspanned. (a) Find the blocking factor, the unused bytes per block and the number of blocks. (b) How many block reads does an equality search on customer_id need as a heap file, and as a file sorted on customer_id? (c) If the records grew to 150 bytes, how many blocks would unspanned and spanned organisation need? [8 marks]

  1. bfr = ⌊4096 / 100⌋ = 40 records per block. Unused per block = 4096 − 40 × 100 = 96 bytes.
  2. b = ⌈30,000 / 40⌉ = 750 blocks.
  3. Heap file, customer_id present: on average 750 / 2 = 375 block reads; absent: 750.
  4. Sorted file: ⌈log₂ 750⌉ = 10 block reads, because 2⁹ = 512 < 750 ≤ 1024 = 2¹⁰.
  5. R = 150, unspanned: bfr = ⌊4096 / 150⌋ = 27 (27 × 150 = 4050), so b = ⌈30,000 / 27⌉ = ⌈1111.1⌉ = 1112 blocks.
  6. Spanned: total bytes = 30,000 × 150 = 4,500,000, so b = ⌈4,500,000 / 4096⌉ = ⌈1098.6⌉ = 1099 blocks, 13 fewer.

Exam traps

  • bfr uses the floor and b uses the ceiling. Writing "40.96 records per block" loses marks.
  • Binary search needs the file sorted on the attribute you search. A file sorted on customer_id does not help a search on city.
  • The heap cost b/2 holds only for a unique key that exists. For a non-key attribute (all matches wanted) or a missing value, all b blocks are read.
  • "Sequential file" means sorted on a key, not merely read in sequence.
  • Block reads are the exam's cost unit; real time also depends on whether the blocks lie next to each other (chapter 6.1).

Analyze A sensor table receives 10,000 inserts a minute and is read in full once a night for a report. Heap or sorted file? Justify. 4 marks

Heap. Inserts dominate, and a heap insert writes only the last block, while a sorted file would need overflow chains and frequent reorganisation. The nightly report reads every block anyway, so sorting buys nothing; if it needs order, one external sort at night (chapter 6.6) is cheaper.

Beyond the syllabus

Not for the exam. PostgreSQL stores every table as a heap file of slotted pages and moves very long values to a side table it calls TOAST. Analytics systems store data by column instead of by row (formats such as Apache Parquet and ORC), so a query that reads 3 of 50 columns reads about 3/50 of the bytes. Write-heavy stores such as RocksDB and Cassandra use log-structured merge trees, which append sorted runs and merge them later. Search "row store versus column store" next.

6.3 Indexing: primary, secondary and multilevel indexes

An index is a small sorted file of (search key, pointer) entries that lets the DBMS find records without scanning the data file, the way the index at the back of a textbook sends you straight to a page. Indexes differ in the field they are built on (the field the file is sorted by, or any other), in how many entries they hold (dense or sparse), and in how many levels they have.

You need: Chapter 6.2, blocking factor, sorted files and binary search over blocks.

Index terms

  • Search key: the attribute or attributes used to look up records. It need not be the primary key.
  • Index entry: a pair ⟨K, P⟩ of a key value K and a pointer P to a block or a record. Entries are kept sorted on K, so the index itself can be searched by binary search.
  • Dense index: one entry for every search-key value in the file. Sparse index: entries for only some values, usually one per data block, holding the key of the block's first record (the block anchor). A sparse index works only on a file sorted on that key: find the largest entry ≤ the wanted key, then search that block.
  • Fan-out (index blocking factor): fo = ⌊B / (V + P)⌋, where V is the key size and P the pointer size in bytes. An entry is much shorter than a record, so fo is much larger than bfr and the index has far fewer blocks than the file.

Primary, clustering and secondary indexes

  • Primary index: built on the ordering key field of a sorted file. It is sparse, one entry per data block, so it has b entries. A search is a binary search on the index, ⌈log₂ bᵢ⌉ reads for bᵢ index blocks, plus 1 read for the data block.
  • Clustering index: on an ordering field that is not a key, such as dept in a file sorted by dept. One entry per distinct value, pointing to the first block that holds it. Also sparse.
  • Secondary index: on any non-ordering field, such as pan_no in an Employee file sorted on emp_id. The data is not in pan_no order, so the index must be dense. On a non-key field such as city, each entry points to a block of record pointers, an extra level of indirection.

A file can be sorted only one way, so it has at most one primary or clustering index, but it can have many secondary indexes. A naming note: Silberschatz calls any index whose search key sets the file order a clustering index and every other index nonclustering or secondary, while Elmasri and Navathe use the three names above. Use your prescribed book's names in the exam.

Multilevel indexes

A large index is itself a sorted file, and binary search on it still costs ⌈log₂ bᵢ⌉ reads. Instead, build a sparse primary index on the index: the second level has one entry per first-level block. Repeat until a level fits in one block; that block is the top level. Each level divides the number of blocks by fo, so:

levels       t = ⌈log_fo(r₁)⌉        r₁ = entries in level 1
search cost  = t + 1 block reads      one per level, plus the data block

Binary search halves the search space with each read; a multilevel index divides it by fo, often 100 to 300. The B+ tree of chapter 6.4 is the dynamic version that stays balanced as the data changes.

Worked example

  2. Fan-out fo = ⌊4096 / (10 + 6)⌋ = 256 entries per index block.
  3. (a) ⌈log₂ 7,500⌉ = 13 reads (2¹² = 4096 < 7500 ≤ 8192).

  6. (d) Dense: 300,000 entries in ⌈300,000 / 256⌉ = ⌈1171.9⌉ = 1,172 blocks. Search = ⌈log₂ 1,172⌉ + 1 = 11 + 1 = 12 reads.

Exam traps

  • "Primary index" is not "any index on the primary key" in every book. In Elmasri's sense the file must be sorted on that field. Define the term you use.
  • A sparse index works only on a file sorted on that key; a secondary index must be dense.
  • A primary index has one entry per data block (b entries), not one per record (r entries).
  • Add 1 for the data block after the index search.
  • Use the ceiling at every level; the top level is the first that fits in one block.

Understand Why is a multilevel index faster than binary search on a single-level index? 4 marks

Analyze Why not create a secondary index on every column of a busy orders table? 4 marks

Every insert and delete, and every update of an indexed column, must also change each index: more block writes and longer transactions. Each index takes space. Indexes on columns with few distinct values (status, gender) are rarely chosen by the optimizer. Index the columns used in frequent WHERE and join conditions only.

Not for the exam. Real systems add composite indexes on several columns, covering indexes that answer a query without touching the table (index-only scans), bitmap indexes for data warehouses, and block-range (BRIN) indexes in PostgreSQL for huge tables in insertion order. Search engines use inverted indexes from each word to the documents containing it. Search "learned index" for research that replaces the index with a model.

6.4 B-trees and B+ trees

A B+ tree is a balanced multilevel index that reshapes itself as records are inserted and deleted, so every lookup costs the same few block reads and the file never needs rebuilding. It is the default index of almost every relational DBMS, from Oracle and SQL Server to MySQL and PostgreSQL. A B-tree is its older relative that keeps record pointers at every level.

You need: Chapter 6.3, multilevel indexes; binary search trees from your Data Structures course.

Structure of a B+ tree

Bayer and McCreight introduced B-trees in 1972 to keep a multilevel index balanced through small local changes instead of whole-file rebuilds, the weakness of ISAM. We use Silberschatz's convention: the order n is the largest number of pointers a node can hold.

  • Internal node: up to n pointers P₁ … Pₙ and n − 1 sorted keys K₁ < K₂ < … . Pointer Pᵢ leads to the subtree whose keys are ≥ Kᵢ₋₁ and < Kᵢ.
  • Leaf node: up to n − 1 (key, record pointer) pairs and one pointer to the next leaf, so the leaves form a sorted linked list.
  • At least half full: every internal node except the root has at least ⌈n/2⌉ pointers; every leaf at least ⌈(n − 1)/2⌉ keys. The root needs only 2 pointers.
  • Balanced: all leaves are at the same depth.

Every node below the root has at least ⌈n/2⌉ children, so a tree holding K keys has height at most ⌈log⌈n/2⌉(K)⌉. With n = 100 and one million keys that is ⌈log₅₀ 10⁶⌉ = ⌈3.53⌉ = 4 levels: any lookup reads at most 4 blocks. Some books count order in keys instead of pointers, so check your book's convention before you split a node.

Search, insertion and deletion

Search for key k: start at the root. In each internal node find the first key Kᵢ greater than k and follow the pointer to its left, or the last pointer if no key is greater. At the leaf, look for k. The cost is the height of the tree.

Insertion:

  1. Find the leaf where the key belongs. If it has fewer than n − 1 keys, insert in sorted order and stop.
  2. If the leaf is full, split the n keys: the first ⌈n/2⌉ stay, the rest move to a new leaf on the right, and the next-leaf pointers are relinked.
  3. Copy the smallest key of the new leaf up into the parent, with a pointer to the new leaf. The key stays in the leaf too.
  4. If the parent overflows, split it: the first ⌈(n + 1)/2⌉ pointers stay, the key just after them moves up (it stays in neither half), and the rest go right.
  5. If the root splits, make a new root with one key. The tree grows by one level, and only at the top, so all leaves stay at one depth.

Deletion: remove the key from its leaf. If the leaf still has at least ⌈(n − 1)/2⌉ keys, stop. Otherwise borrow a key from an adjacent sibling that can spare one and fix the separating key in the parent (redistribution). If neither sibling can spare one, merge the leaf with a sibling and delete the separator from the parent, which may make the parent underflow in turn. If the root is left with one child, that child becomes the root and the tree loses a level.

6.5 Static and dynamic hashing

Hashing computes where a record lives from its key: a hash function h maps the search key to one of M buckets, so an exact-match lookup costs about one block read however large the file grows. Static hashing fixes M when the file is created and degrades as the file grows; dynamic hashing (extendible and linear hashing) adds buckets one at a time as the data grows.

You need: Chapter 6.2, hashed files, and Chapter 6.3, index entries.

Static hashing

A bucket is a unit of storage, usually one disk block, that holds records or index entries. A hash function h maps every search-key value K to a bucket number 0 … M − 1, and a small table in the file header maps bucket numbers to disk addresses. To insert, compute h(K) and put the record in that bucket; to search, compute h(K) and read that one bucket. A hash file keeps records in the buckets; a hash index keeps ⟨key, pointer⟩ entries instead.

A good hash function is uniform (each bucket gets about the same number of keys) and random (the spread does not follow patterns in the keys). The usual exam choice is h(K) = K mod M with M a prime, so that keys sharing a pattern, such as all ending in 0, do not pile into one bucket.

Bucket overflow happens when the target bucket is full: the new record goes to an overflow block chained to that bucket (overflow chaining). It has two causes: too few buckets for the records, and skew, when many records share a key value or the function sends many keys to one bucket. Designers therefore make M about 20 percent larger than records ÷ bucket capacity. Static hashing still has two weaknesses. It cannot answer range queries, because the hash scatters neighbouring keys. And M is fixed: too small gives long chains as the file grows, too large wastes space, and changing M means rehashing every record.

Extendible hashing

  • A directory of 2d pointers to buckets, where d is the global depth. To find a key, take d bits of h(K) and follow that directory entry. This chapter uses the last d bits; some books use the first d bits, which works the same way.
  • Each bucket has a local depth d′ ≤ d: all its keys share their last d′ bits, and 2d − d′ directory entries point to it.
  • Full bucket with d′ < d: split it into two buckets of local depth d′ + 1, move each key by its next bit, and repoint half of its directory entries. The directory keeps its size.
  • Full bucket with d′ = d: first double the directory (d becomes d + 1, and each old entry is copied, so both copies point to the old bucket), then split as above.
  • A lookup reads the directory entry, usually held in memory, and one bucket, with no overflow chains. Deletion can merge a bucket with its "buddy" and halve the directory when every d′ < d.

Linear hashing

Linear hashing (Litwin, 1980) needs no directory. It starts with M buckets, the function h₀(K) = K mod M and a split pointer s = 0. Whenever an overflow occurs, bucket s, which need not be the one that overflowed, is split with h₁(K) = K mod 2M into buckets s and s + M, and s moves on by one. To find a key, compute h₀(K); if that number is less than s, the bucket has already been split, so use h₁(K). When all M buckets have been split, h₁ becomes the main function, M doubles and s returns to 0. Overflow chains still appear, but each is short-lived because its bucket's turn to split comes soon.

6.6 Query processing: parsing, translation and evaluation

Query processing is everything a DBMS does between receiving an SQL string and returning rows: check the query, translate it into relational algebra, choose an algorithm for each operation and run them. SQL says what you want; the query processor decides how to get it.

You need: Unit 2, Relational algebra: select, project and rename, and joins in algebra; Unit 3, Basic SQL queries; chapters 6.3 to 6.5 for indexes.

The three steps

  1. Parsing and translation. The scanner splits the text into tokens (keywords, names, constants); the parser checks the grammar and builds a parse tree. Validation then checks the system catalog: do the tables and columns exist, do the types match, may this user read them? Views are replaced by their definitions. The query becomes a relational algebra expression, drawn as a query tree whose leaves are tables and whose internal nodes are operators.
  2. Optimization. The optimizer lists equivalent expressions and algorithms and picks the plan with the lowest estimated cost, using statistics from the catalog (chapter 6.7).
  3. Evaluation. The query execution engine runs the chosen plan and returns the rows.

An evaluation plan is a query tree in which each node also names its algorithm, such as "use the B+ tree index on city" or "hash join on cust_id". For SELECT c.name FROM customer c JOIN orders o ON c.cust_id = o.cust_id WHERE c.city = 'Chennai' the algebra is πname(σcity='Chennai'(customer) ⋈ orders), and one plan is: index scan for the selection, hash join, then projection on the fly.

Measuring query cost

Disk access dominates, so cost is counted in block transfers and seeks:

cost = b × tT + S × tS
  b  = blocks transferred     tT = time to transfer one block
  S  = number of seeks        tS = average seek + rotational latency

With tT = 0.1 ms and tS = 4 ms, reading 1,000 blocks in one sweep costs 1,000 × 0.1 + 1 × 4 = 104 ms, but 1,000 random blocks cost 1,000 × (0.1 + 4) = 4,100 ms. CPU time and writing the final result are ignored, and many exam answers count block transfers only, so read the question. Notation: nᵣ rows and bᵣ blocks of relation r, M buffer blocks in memory, hᵢ height of a B+ tree index.

External merge sort first reads M blocks at a time, sorts them in memory and writes each out as a sorted run, giving ⌈bᵣ/M⌉ runs. In a join, r is the outer relation, read once, and s is the inner relation, read again for each row of r (nested loop) or each chunk of r (block nested loop). Hash join partitions both relations with the same hash function on the join attribute, so matching rows land in matching partitions, then builds an in-memory hash table on each partition of the smaller relation and probes it with the other.

Materialization and pipelining

In materialized evaluation each operator runs to completion and writes its result to a temporary relation on disk, which its parent then reads: simple, but every intermediate result is written and read again. In pipelined evaluation each operator hands rows to its parent as soon as it produces them, with no temporary files. Each operator offers open(), next() and close() (the iterator model), and the root keeps calling next() on its child. Sorting and the build phase of hash join are blocking: they must read all their input before producing a row, so a pipeline breaks there.

6.7 Query optimization: cost estimation and heuristics

Query optimization chooses, among the many equivalent ways to evaluate a query, one with a low estimated cost. It works in two ways at once: heuristic rewriting of the query tree, such as doing selections before joins, and cost-based choice of join order and algorithms using statistics kept in the catalog. A good optimizer turns hours into seconds without the user changing a word of the SQL.

You need: Chapter 6.6, evaluation plans and the cost of each algorithm; Unit 2, Set operations, Cartesian product and joins in algebra.

Equivalence rules

Two relational algebra expressions are equivalent if they give the same rows on every legal database. The optimizer rewrites a query with rules such as these, where E, E₁, E₂ are expressions, θ a condition and L a list of attributes:

  1. Cascade of selections: σθ1 ∧ θ2(E) = σθ1(σθ2(E)).
  2. Selections commute: σθ1(σθ2(E)) = σθ2(σθ1(E)).
  3. Cascade of projections: πL1(πL2(E)) = πL1(E) when L1 ⊆ L2.
  4. A selection over a product is a join: σθ(E₁ × E₂) = E₁ ⋈θ E₂.
  5. A selection moves below a join: σθ(E₁ ⋈ E₂) = σθ(E₁) ⋈ E₂ when θ uses only attributes of E₁.
  6. Joins commute and associate: E₁ ⋈ E₂ = E₂ ⋈ E₁, and (E₁ ⋈ E₂) ⋈ E₃ = E₁ ⋈ (E₂ ⋈ E₃).
  7. A projection moves below a join if it keeps the join attributes.

Heuristic optimization

  1. Split each conjunctive selection into a cascade of single selections (rule 1).
  2. Move each selection as far down the tree as it goes (rules 2 and 5), so rows are thrown away early.
  3. Combine a Cartesian product with the selection above it into a join (rule 4).
  4. Order the leaves so the most restrictive selections and joins, those with the smallest results, run first (rule 6), and avoid any Cartesian product.
  5. Push projections down, keeping the attributes later operators need (rules 3 and 7).
  6. Mark the subtrees that can be pipelined.

Heuristics are cheap and nearly always help, but they cannot tell which of two join orders is better. For that the optimizer needs numbers.

Cost-based optimization

The catalog keeps statistics for every relation r: nᵣ (rows), bᵣ (blocks), lᵣ (bytes per row), fᵣ (rows per block), V(A, r) (number of distinct values of attribute A), the minimum and maximum of A, and often a histogram of A. 6.8 Distributed and parallel databases

When one server is not enough, a database is spread over many machines. A parallel database uses many processors and disks, usually in one data centre, to run queries faster. A distributed database stores data at sites that may be far apart, such as a bank's data centres in Mumbai and Chennai, and lets users query it as one database.

Parallel databases

There are three architectures (Figure 6.8.1):

  • Shared memory: all processors share one memory and the disks over a bus. Communication is fastest, but the bus saturates beyond a few tens of processors.
  • Shared disk: each processor has its own memory, and all reach all disks over an interconnect. If a node fails, another takes over its work because the disks are shared; the disk interconnect becomes the bottleneck. Oracle RAC works this way.
  • Shared nothing: each node has its own processor, memory and disks and talks to the others only over the network. It scales furthest, because nodes have nothing to contend for; most data warehouses and NoSQL stores use it. A hierarchical design combines them, for example shared-nothing nodes that are each shared-memory machines.

Data is spread over the disks by partitioning: round-robin (row i goes to disk i mod n; an even spread, but every lookup must ask every disk), hash (a hash of a key picks the disk; an exact match goes to one disk) and range (key ranges, such as roll numbers 1 to 1000 on disk 0; good for range queries, but at risk of skew).

Two measures judge a parallel system. Speedup = Tsmall / Tlarge for the same task on N times the hardware; ideally N (linear speedup). Scaleup = time of a task on the small system ÷ time of an N-times task on the N-times system; ideally 1 (linear scaleup). Start-up costs, interference over shared resources and skew keep real systems below linear. Parallelism comes as interquery (many queries at once, for throughput) and intraquery: intraoperation, one sort or join split over all nodes, and interoperation, different operators of one plan running at once. A parallel hash join partitions both relations on the join attribute, so each node joins only its own pair of partitions.

Distributed databases

  • Homogeneous systems run the same DBMS at every site; heterogeneous (multidatabase) systems join different DBMSs through a middleware layer.
  • Fragmentation splits a relation. Horizontal fragments are row subsets chosen by a selection, such as the Chennai branch's accounts stored at Chennai; the relation is rebuilt by UNION. Vertical fragments are column subsets that each keep the key; the relation is rebuilt by a join on the key. Mixed fragmentation does both.
  • Replication keeps copies at several sites: reads are faster and survive a site failure, but every update must reach every copy.
  • Transparency: users need not know where fragments are (location), how a relation is split (fragmentation) or how many copies exist (replication).

Distributed query processing counts the bytes shipped over the network, often the largest cost. A semijoin r ⋉ s ships only the join column of s to r's site, keeps the rows of r that match, and ships just those back; it pays when few rows match.

A transaction that updates several sites must commit everywhere or nowhere. Two-phase commit (2PC) does this. Phase 1: the coordinator sends PREPARE; each participant writes its changes and a ready record to its log and votes READY or ABORT. Phase 2: if every vote is READY, the coordinator logs COMMIT and tells all to commit; otherwise it tells all to abort. Its weakness is blocking: a participant that voted READY must wait, holding its locks, if the coordinator fails before sending the decision. Finally, the CAP theorem (Brewer's conjecture, proved by Gilbert and Lynch in 2002) says that during a network partition a distributed system must give up either consistency or availability.

Worked example

Question. A railway database stores PASSENGER(pnr, name, train_no, …) at Chennai: 50,000 rows of 120 bytes. TRAIN(train_no, train_name, …) is at Delhi: 2,000 rows of 50 bytes. A user at Mumbai asks for every passenger's name with the train name. Each result row is 60 bytes and every passenger matches one train. (a) Compare three strategies by bytes shipped. (b) Which is best if the query is asked at Chennai? (c) A sort takes 100 minutes on one node and 12 minutes on 10 nodes: find the speedup. [10 marks]

  1. Sizes: PASSENGER = 50,000 × 120 = 6,000,000 B; TRAIN = 2,000 × 50 = 100,000 B; result = 50,000 × 60 = 3,000,000 B.
  2. Strategy 1, ship both relations to Mumbai and join there: 6,000,000 + 100,000 = 6,100,000 B.
  3. Strategy 2, ship PASSENGER to Delhi, join, ship the result to Mumbai: 6,000,000 + 3,000,000 = 9,000,000 B.
  4. Strategy 3, ship TRAIN to Chennai, join, ship the result to Mumbai: 100,000 + 3,000,000 = 3,100,000 B. Best (Figure 6.8.2).
  5. (b) At Chennai, ship TRAIN to Chennai and join; the result is already where it is wanted: 100,000 B.
  6. (c) Speedup = 100 / 12 = 8.33 on 10 nodes, below the linear 10, because of start-up, coordination and skew.

Exam traps

  • Speedup keeps the task fixed and adds hardware; scaleup grows the task and the hardware together.
  • Horizontal fragments are rebuilt by UNION, vertical ones by a JOIN on the key, so every vertical fragment must keep the key.
  • Two-phase commit (2PC) is not two-phase locking (2PL, Unit 5): 2PC makes a distributed transaction atomic; 2PL makes schedules serializable.
  • In distributed cost questions, count bytes shipped over the network unless told to count blocks.

6.9 NoSQL databases: document, key-value and graph

NoSQL ("not only SQL") is a family of databases that drop the fixed relational schema, and often some ACID guarantees, to scale out across many cheap servers and to store data in the shape the application uses: key-value pairs, JSON documents, wide columns or graphs. They grew from the needs of web companies in the 2000s, such as Amazon's Dynamo and Google's Bigtable, and now run shopping carts, app backends and recommendation engines.

You need: Chapter 6.8, partitioning, replication and CAP; Unit 5, ACID properties.

Why NoSQL, and BASE

A relational DBMS gives a fixed schema, joins and ACID transactions, and it grows mainly by moving to a bigger server (scaling up). At web scale that hits limits: one server has a ceiling, joins across machines are slow, and changing the schema of a billion-row table takes hours. NoSQL systems scale out instead. They partition (shard) data on a key across many servers, replicate each shard, keep the schema in the application (schema-on-read), and favour simple queries by key.

Many choose availability over strict consistency in the CAP sense and call themselves BASE: Basically Available, Soft state, Eventually consistent. Replicas may disagree for a moment after an update but converge once updates stop. Consistency is often tunable: with N copies of each item, a write waits for W replicas and a read asks R replicas. If R + W > N, every read set overlaps every write set, so a read sees the latest write.

Key-value and document stores

A key-value store offers get(key), put(key, value) and delete(key). The value is opaque: the store cannot search inside it, so every access needs the key. Redis commands, each followed by the server's reply:

SET cart:u42 "dosa:2,coffee:4"     → OK
EXPIRE cart:u42 1800               → (integer) 1
GET cart:u42                       → "dosa:2,coffee:4"

The cart now disappears 1,800 seconds (30 minutes) after the EXPIRE command, which suits an abandoned shopping cart.

A document store keeps self-describing documents, usually JSON (MongoDB stores a binary form called BSON), grouped in collections. Documents in one collection need not share fields, nested arrays and sub-documents are allowed, and queries and secondary indexes can use any field. The main design choice is embedding versus referencing: embed data that is read together and owned by one parent, such as the items of an order; reference data that many documents share or that grows without limit, such as the customer, by cust_id.

Graph databases

A graph database stores a property graph: nodes with labels and properties, such as Person {name: 'Asha'}, and directed relationships with a type and properties, such as FRIEND {since: 2021}. Each node keeps direct references to its relationships (index-free adjacency), so following an edge is a pointer hop and a query costs in proportion to the part of the graph it touches. The same question in SQL needs a self-join of a large Friend table for every hop.

Neo4j's query language, Cypher, draws the pattern with arrows. For the graph in Figure 6.9.1:

MATCH (a:Person {name: 'Asha'})-[:FRIEND]->()-[:FRIEND]->(f)
WHERE f <> a

Deepak is reached twice, through Bala and through Chitra; DISTINCT keeps one. Relational databases remain the better choice when the structure is stable, when a transaction must span many records (a bank ledger), and for ad-hoc joins and reports. Many applications use several stores side by side, which is called polyglot persistence.

Exam traps

  • NoSQL means "not only SQL", not "no SQL": Cassandra's CQL and several document stores offer SQL-like languages.
  • Eventual consistency is not "no consistency": replicas converge once updates stop.
  • Embedding duplicates data. If a restaurant's name is embedded in a million orders, renaming it means updating a million documents.
  • R + W > N makes a read see the latest write; it does not give multi-record ACID transactions.

Glossary

Block (page)
The fixed-size unit, usually 4 KB to 16 KB, in which data moves between disk and memory.
Seek time
Time to move the disk arm to the track that holds the wanted block.
Rotational latency
Time for the wanted sector to turn under the head; on average half a rotation.
RAID
Redundant array of independent disks: several disks used as one, with striping for speed and mirroring or parity for safety.
Parity block
The XOR of the data blocks of a stripe; it rebuilds any one lost block.
Blocking factor (bfr)
Number of whole records per block, ⌊B / R⌋.
Heap file
A file whose records are stored in no particular order.
Slotted page
A block layout with a header of (offset, length) slots and records packed from the end of the block.
Spanned record
A record allowed to continue from one block into the next.
Search key
The attribute or attributes an index is built on.
Dense index
An index with an entry for every search-key value in the file.
Sparse index
An index with entries for only some values, usually one per block; needs a sorted file.
Primary index
A sparse index on the ordering key of a sorted file.
Clustering index
An index on an ordering field that is not a key; in Silberschatz, any index whose key sets the file order.
Secondary index
A dense index on a field that does not set the file order.
Fan-out
Number of entries or child pointers per index node, ⌊B / (V + P)⌋.
ISAM
Indexed sequential access method: a static multilevel index with overflow chains.
B+ tree
A balanced multilevel index with all keys and record pointers in linked leaves.
Bucket overflow
A record hashing to a full bucket, stored in a chained overflow block.
Global and local depth
In extendible hashing, the bits used by the directory and the bits shared by one bucket's keys.
Query tree
A relational algebra expression drawn as a tree, with tables at the leaves.
Evaluation plan
A query tree annotated with the algorithm and index for every operation.
Pipelining
Passing rows from one operator to the next as they are produced, without temporary relations.
Left-deep join tree
A join order in which the right input of every join is a base relation.
Shared nothing
A parallel architecture in which each node has its own processor, memory and disks.
Fragmentation
Splitting a relation into row subsets (horizontal) or column subsets (vertical) stored at different sites.
Two-phase commit (2PC)
A protocol that makes a transaction commit at all sites or at none.
CAP theorem
During a network partition, a distributed system must give up consistency or availability.
BASE
Basically available, soft state, eventually consistent: the guarantees many NoSQL stores give instead of ACID.

  • Abraham Silberschatz, Henry F. Korth and S. Sudarshan, Database System Concepts, 7th ed., McGraw-Hill. Chapters on physical storage systems, data storage structures, indexing, query processing, query optimization, and parallel and distributed databases.
  • Ramez Elmasri and Shamkant B. Navathe, Fundamentals of Database Systems, 7th ed., Pearson. Chapters on disk storage and file structures, indexing structures, query processing and optimization, distributed databases and NoSQL systems.
  • Raghu Ramakrishnan and Johannes Gehrke, Database Management Systems, 3rd ed., McGraw-Hill. Parts on storage and indexing and on query evaluation.
  • Hector Garcia-Molina, Jeffrey D. Ullman and Jennifer Widom, Database Systems: The Complete Book, 2nd ed., Pearson. Chapters on secondary storage, index structures and query execution.

Original papers

  • D. A. Patterson, G. Gibson and R. H. Katz, "A Case for Redundant Arrays of Inexpensive Disks (RAID)", ACM SIGMOD, 1988.
  • R. Bayer and E. McCreight, "Organization and Maintenance of Large Ordered Indexes", Acta Informatica, 1972.
  • R. Fagin, J. Nievergelt, N. Pippenger and H. R. Strong, "Extendible Hashing: A Fast Access Method for Dynamic Files", ACM Transactions on Database Systems, 1979.
  • W. Litwin, "Linear Hashing: A New Tool for File and Table Addressing", VLDB, 1980.
  • P. G. Selinger and others, "Access Path Selection in a Relational Database Management System", ACM SIGMOD, 1979.
