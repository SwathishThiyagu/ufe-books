4.1 Need for normalization and good database design

Normalization is the step-by-step splitting of a badly designed table into smaller tables so that each fact is stored once. A table that mixes facts about students, departments and courses repeats the same value in many rows, and every repeated copy is a chance for the copies to disagree. Normalization uses the dependencies between attributes (Chapter 4.2) to find those repeats and remove them without losing any data.

You need: keys from Unit 2, Keys: super, candidate, primary and foreign keys, and table design from Unit 1, Mapping ER diagrams to relational tables.

Redundancy and the three anomalies

Take one table a college might build in a hurry: Result(roll_no, name, dept, hod, course, credits, grade), with primary key {roll_no, course}. Each row records one student in one course. But each row also carries facts about the student (name, dept), the department (hod) and the course (credits). Those facts repeat in every row they touch. Repetition of the same fact is called redundancy, and it causes three kinds of trouble, called anomalies.

  1. Update anomaly. A fact stored in many rows must be changed in all of them. When CSE gets a new head of department, every CSE row must change. Miss one and the table gives two answers to "Who heads CSE?"
  2. Insertion anomaly. A fact cannot be stored without an unrelated fact. A new course CS305 with 3 credits cannot be recorded until some student takes it, because roll_no is part of the primary key and a key attribute cannot be null.
  3. Deletion anomaly. Deleting one fact deletes another. If student 103 is the only one in CS303 and her row is deleted, the database also forgets that CS303 carries 2 credits.

What a good design looks like

Elmasri and Navathe give four informal guidelines, which most university question papers quote in some form:

  1. Give each table one clear meaning: one entity type or one relationship type, not a mix.
  2. Design so that no insertion, deletion or update anomaly can occur.
  3. Avoid attributes that are null in most rows; put them in a separate table.
  4. Join tables only on key and foreign-key pairs, so that a join never invents rows (spurious tuples, Chapter 4.6).

The formal goals follow from these. Every table should be in BCNF, or at least 3NF (Chapters 4.4 and 4.5). Every split should be lossless, so the join gives back the original table, and dependency preserving, so each rule can still be checked inside one table (Chapter 4.6). For Result, the good design is four tables: Student(roll_no, name, dept), Dept(dept, hod), Course(course, credits) and Result(roll_no, course, grade). Each fact now lives in exactly one row.

The price: more tables and more joins

A normalized schema has more tables, more foreign keys, and queries that need joins to rebuild a full row. Writes become cheaper and safer, because each fact is changed in one place. Reads that need many tables become a little dearer. Denormalization is the deliberate choice to keep a redundant copy, such as a stored order total or a reporting table, for read speed, with a trigger or a nightly job keeping the copy correct. The usual practice: normalize the transaction database to 3NF or BCNF, and denormalize only where a measured read cost demands it.

Worked example

Question (6 marks). A college stores all results in Result(roll_no, name, dept, hod, course, credits, grade). The CSE department has 120 students, and each takes the same 6 courses. (a) How many rows and cells does Result hold for CSE? (b) How many rows change when the HOD changes? (c) Split the table so that each fact is stored once, and count the cells again.

  1. Rows. One row per student per course: 120 × 6 = 720 rows. With 7 attributes, that is 720 × 7 = 5,040 cells.
  2. HOD change. The HOD's name sits in all 720 rows, so 720 rows must change. Likewise each student's name is stored 6 times and each course's credits 120 times.
  3. Split. Student(roll_no, name, dept): 120 rows × 3 = 360 cells. Dept(dept, hod): 1 row × 2 = 2 cells. Course(course, credits): 6 rows × 2 = 12 cells. Result(roll_no, course, grade): 720 rows × 3 = 2,160 cells.
  4. Total. 360 + 2 + 12 + 2,160 = 2,534 cells, a saving of 5,040 − 2,534 = 2,506 cells, about 50%.
  5. Anomalies gone. A new HOD is 1 row in Dept. A new course is 1 row in Course, with no student needed. Deleting a result row removes only a grade.
  6. Nothing lost. Joining Result with Student on roll_no, Student with Dept on dept and Result with Course on course gives back exactly the 720 original rows.

Exam traps

  • Normalization removes repeated facts, not data. The join of the new tables must give back the original table exactly.
  • An insertion anomaly is a fact you cannot store because part of the key would be null. It is not a duplicate-key error.
  • Marks go to the example: name each anomaly and show it on the table in the question.
  • Splitting on a non-key column, such as (roll_no, name) and (name, dept), creates spurious tuples. That is worse than redundancy.
  • "When would you denormalize?" is a favourite short question: for read-heavy reporting, with a mechanism that keeps the copy correct.

4.2 Functional dependencies: Armstrong's axioms and closure

A functional dependency (FD) X → Y says that the values of X fix the value of Y: any two rows that agree on X must agree on Y. In a college, roll_no → name is an FD; name → roll_no is not, because two students can share a name. FDs are the rules the whole unit is built on: they decide the keys, the normal form and every split. Armstrong's axioms derive new FDs from given ones, and attribute closure finds, in a few lines, everything a set of attributes determines.

You need: superkeys and candidate keys from Unit 2, Keys: super, candidate, primary and foreign keys.

The definition

Let R be a relation schema and X, Y sets of its attributes. The FD X → Y holds on R if, in every legal instance r of R, for any two tuples t₁ and t₂ of r: t₁[X] = t₂[X] implies t₁[Y] = t₂[Y]. X is the determinant (left side) and Y the dependent (right side). We write AB for the set {A, B}, and F for the set of FDs we are given.

  • An FD is a rule about what the data means, set by the designer. One instance can show that an FD fails (two rows with the same X and different Y), but no instance can prove that it holds.
  • An FD is trivial when Y ⊆ X, such as {roll_no, name} → name. It holds in every relation.
  • K is a superkey of R exactly when K → R, that is, K determines every attribute.

Armstrong's axioms

The closure of F, written F⁺, is the set of all FDs that follow from F. Three rules, published by W. W. Armstrong in 1974, generate F⁺:

  1. Reflexivity. If Y ⊆ X, then X → Y.
  2. Augmentation. If X → Y, then XZ → YZ for any set Z.
  3. Transitivity. If X → Y and Y → Z, then X → Z.

The axioms are sound (they never derive an FD outside F⁺) and complete (repeated use derives every FD in F⁺). Three more rules follow from them and save time:

  • Union: X → Y and X → Z give X → YZ. Proof: augment X → Y by X to get X → XY; augment X → Z by Y to get XY → YZ; transitivity gives X → YZ.
  • Decomposition: X → YZ gives X → Y and X → Z. Proof: YZ → Y by reflexivity, then transitivity.
  • Pseudotransitivity: X → Y and WY → Z give WX → Z. Proof: augment X → Y by W to get WX → WY, then transitivity with WY → Z.

Notice what is missing: no rule splits the left side. AB → C does not give A → C.

Attribute closure X⁺

Listing F⁺ is hopeless even for small schemas, because the trivial FDs alone grow exponentially with the number of attributes. Instead we compute the closure of an attribute set, X⁺: every attribute that X determines under F.

  1. Set result = X.
  2. For each FD V → W in F: if V ⊆ result, add W to result.
  3. Repeat step 2 until a full pass adds nothing. Then result = X⁺.

Closure answers three exam questions. X → Y is in F⁺ exactly when Y ⊆ X⁺. X is a superkey exactly when X⁺ = R. X is a candidate key when X⁺ = R and no proper subset of X has that property. A shortcut for finding keys: an attribute that appears on no right side must be in every key, and an attribute that appears only on right sides is in no key.

Worked example

Question (8 marks). R(A, B, C, D, E) has F = {A → BC, CD → E, B → D, E → A}. (a) Compute A⁺ and B⁺. (b) Find all candidate keys of R. (c) Prove A → E using Armstrong's axioms.

  1. A⁺. Start {A}. A → BC adds B, C: {A, B, C}. B → D adds D: {A, B, C, D}. CD → E adds E. A⁺ = {A, B, C, D, E} = R.
  2. B⁺. Start {B}. B → D adds D. No other left side (A, CD, E) is inside {B, D}. B⁺ = {B, D}.
  3. Single attributes. A⁺ = R, so {A} is a key. E⁺: E → A adds A, and then everything as for A, so {E} is a key. B⁺ = {B, D}, C⁺ = {C}, D⁺ = {D}: not keys.
  4. Pairs. Any set holding A or E is a superkey but not minimal, so test only pairs from B, C, D. {B, C}⁺ = R (Figure 4.2.1). {C, D}⁺: CD → E, E → A, A → BC gives R. {B, D}⁺ = {B, D}. Larger sets without A or E contain BC or CD, so they are not minimal.
  5. Answer (b). Candidate keys: {A}, {E}, {B, C}, {C, D}. Every attribute belongs to some key, so all five are prime attributes; Chapters 4.4 and 4.5 use this.
  6. Proof (c). (1) A → BC, given. (2) A → B and A → C, decomposition of (1). (3) B → D, given; A → D by transitivity of A → B and (3). (4) A → CD, union of A → C and A → D. (5) CD → E, given; A → E by transitivity of (4) and (5).

Exam traps

  • AB → C does not imply A → C or B → C. Only the right side may be split.
  • X → Y never gives Y → X. roll_no → name, but name does not determine roll_no.
  • "Which FDs hold in this table?" can only be answered as "which FDs these rows do not violate". Rows disprove FDs; they never prove them.
  • Keep looping until a full pass adds nothing: a late FD can make an earlier one fire.
  • A candidate key must be minimal. Here {A, B} is a superkey but not a candidate key, since A alone works.

Beyond the syllabus

Not for the exam. Data-profiling tools run FD discovery algorithms, such as TANE, to find every minimal FD that holds in a large dataset; data-cleaning systems use such rules to flag rows that break them. Query optimizers use FDs too: PostgreSQL lets a query select columns that are not in GROUP BY when it groups by the table's primary key, because the key determines them. Research extends FDs to approximate and conditional FDs, which hold for most rows or for a subset of rows. Search next: "functional dependency discovery", "conditional functional dependencies".

4.3 Minimal (canonical) cover of dependencies

A minimal cover of a set of FDs F is the smallest, cleanest set that says exactly the same thing as F. It is the input to the 3NF synthesis algorithm (Chapter 4.4).

You need: attribute closure X⁺ from Chapter 4.2.

Three tests and two names

  • Equivalent sets. F and G are equivalent when F⁺ = G⁺: each FD of G follows from F, and each FD of F follows from G.
  • Extraneous attribute. In X → B, an attribute A of X is extraneous if B ∈ (X − A)⁺, computed with the current set.
  • Redundant FD. X → B is redundant if B ∈ X⁺ computed with every FD except X → B.

A minimal cover (Elmasri and Navathe's term) is a set equivalent to F in which every right side is one attribute, no left side has an extraneous attribute, and no FD is redundant. A canonical cover Fc (Silberschatz's term) is the same set with FDs of equal left side merged by the union rule, so each left side appears once.

The algorithm

  1. Split every right side into single attributes (decomposition rule).
  2. For each FD with two or more attributes on the left, remove every extraneous attribute.
  3. Remove every redundant FD, one at a time.
  4. For a canonical cover, merge FDs that share a left side.

Do step 2 before step 3: shrinking a left side can turn an FD into a duplicate or make it redundant.

Worked example

Question (6 marks). R(A, B, C, D) has F = {A → BC, B → C, AB → D, D → C}. Find a minimal cover and the canonical cover.

  1. Split. A → B, A → C, B → C, AB → D, D → C.
  2. Extraneous in AB → D. Test B: A⁺ = {A, B, C, D} contains D, so B is extraneous; AB → D becomes A → D.
  3. Redundant FDs. A → B: A⁺ without it = {A, C, D}, no B, keep. A → C: A⁺ without it = {A, B, C, D}, has C, drop. B → C: B⁺ without it = {B}, keep. A → D: A⁺ without it = {A, B, C}, keep. D → C: D⁺ without it = {D}, keep.
  4. Minimal cover: {A → B, A → D, B → C, D → C}. Canonical cover: {A → BD, B → C, D → C}.
  5. Check. Under the cover, A⁺ = {A, B, C, D}, B⁺ = {B, C}, D⁺ = {C, D}: the same as under F.

Exam traps

  • Extraneous test: closure of the smaller left side, using all current FDs. Redundant test: closure of the left side, using all FDs except the one tested.
  • Remove extraneous attributes before redundant FDs, and recheck for duplicates.
  • A minimal cover is not unique; any correct one earns full marks if the tests are shown.
  • Name which you give: minimal (single right sides) or canonical (merged left sides).

4.4 First, second and third normal forms

Normal forms are a ladder of tests on a table's design. First normal form (1NF) asks that every cell hold one atomic value. Second normal form (2NF) asks that no non-key attribute depend on only part of a composite key. Third normal form (3NF) asks that no non-key attribute depend on another non-key attribute. Each rung removes one kind of redundancy from Chapter 4.1, and 3NF is the usual target for a transaction database.

You need: FDs, closure and candidate keys (Chapter 4.2); canonical cover (Chapter 4.3) for the synthesis algorithm.

First normal form: atomic values

A relation is in 1NF if the domain of every attribute is atomic: each cell holds one indivisible value, with no lists, sets or nested tables (repeating groups). Student(roll_no, name, phones) with phones = "98400 11111, 94440 22222" breaks 1NF. One fix stores one row per phone, which repeats the name. The better fix moves phones to StudentPhone(roll_no, phone). Atomic depends on use: an address kept as one string is atomic until the application must search by PIN code.

Second normal form: no partial dependency

An attribute is prime if it belongs to some candidate key, and non-prime otherwise. X → A is a full dependency if no proper subset of X determines A; otherwise it is partial. A relation is in 2NF if it is in 1NF and every non-prime attribute is fully dependent on every candidate key. A relation whose candidate keys are all single attributes is automatically in 2NF, since a single attribute has no smaller part.

Third normal form: no transitive dependency

A non-prime attribute A is transitively dependent on key K when K → X and X → A, with X not a superkey. A relation is in 3NF if, for every non-trivial FD X → A in F⁺, either X is a superkey or A is prime. This is the same as 2NF plus no transitive dependency of a non-prime attribute. William Kent's summary is easy to remember: every non-key attribute depends on "the key, the whole key, and nothing but the key".

Worked example

Question (8 marks). Result(roll_no, course, name, dept, hod, credits, grade) has F = {roll_no → name dept, dept → hod, course → credits, roll_no course → grade}. Find the key, the highest normal form, and a 3NF decomposition.

  1. Key. roll_no and course appear on no right side, so both are in every key. {roll_no, course}⁺ = all 7 attributes, so it is the only candidate key. Prime attributes: roll_no, course.
  2. 1NF. Every value is atomic: yes.
  3. 2NF. roll_no → name: a non-prime attribute depends on part of the key. Partial, so not 2NF. Highest normal form: 1NF.
  4. To 2NF. Move each partial dependency out with its determinant: Student(roll_no, name, dept, hod), Course(course, credits), Result(roll_no, course, grade). hod goes with roll_no because roll_no → dept → hod.
  5. To 3NF. In Student, roll_no → dept → hod, and dept is not a superkey while hod is non-prime: transitive. Split it into Student(roll_no, name, dept) and Dept(dept, hod).
  6. Answer. Four tables, as in Figure 4.4.1. Each split shares an attribute that is the key of one side, so it is lossless (Chapter 4.6).

The 3NF synthesis algorithm

  1. Find a canonical cover Fc of F (Chapter 4.3).
  2. For each FD X → Y in Fc, make a table with attributes X ∪ Y.
  3. If no table contains a candidate key of R, add one table holding a candidate key.
  4. Drop any table whose attributes all lie inside another table.

Every table produced is in 3NF, the decomposition is lossless, and every FD is preserved. On Result it gives exactly the four tables of Figure 4.4.1.

Exam traps

  • Prime means "in any candidate key", not just the primary key. Find all keys before you test 2NF or 3NF.
  • 2NF can fail only when some candidate key has two or more attributes.
  • 3NF allows X → A with X not a superkey when A is prime. That is why the third row of the table is in 3NF.
  • When you split, the determinant stays in both tables (dept is in Student and in Dept), or the join cannot rebuild the data.

4.5 Boyce-Codd normal form (BCNF)

Boyce-Codd normal form tightens 3NF to one rule: the left side of every non-trivial FD must be a superkey, or in plain words, every determinant is a key. 3NF allowed one exception, a non-key determinant whose right side is a prime attribute. BCNF removes that exception, and with it the last redundancy that FDs can cause. The price is that a BCNF split can lose a dependency. Raymond Boyce and Edgar Codd proposed it in 1974.

You need: 3NF and prime attributes (Chapter 4.4); closure and keys (Chapter 4.2).

Definition and test

R is in BCNF if, for every non-trivial FD X → Y in F⁺, X is a superkey of R. To test the original schema it is enough to check the FDs of F: compute X⁺ for each left side, and if some X⁺ ≠ R, R is not in BCNF. For a table produced by a split this shortcut fails, because FDs of F⁺ can hide inside it. There, test subsets X of the table: if X⁺ ∩ Ri contains more than X but not all of Ri, the table Ri violates BCNF.

Every BCNF relation is in 3NF. A 3NF relation can fail BCNF only when it has two or more composite candidate keys that overlap.

Where 3NF and BCNF part ways

Teaching(student, subject, teacher) follows two rules: each teacher teaches one subject (teacher → subject), and for each subject a student has one teacher ({student, subject} → teacher). The candidate keys are {student, subject} and {student, teacher}, so every attribute is prime and the table is in 3NF. But teacher is not a superkey, so teacher → subject breaks BCNF. The fact "Meena teaches DBMS" repeats once for every student Meena teaches. Splitting into TS(teacher, subject) and ST(student, teacher) removes the repeat and is lossless, but the rule {student, subject} → teacher now spans two tables, and neither can check it alone.

The BCNF decomposition algorithm

  1. Start with result = {R}.
  2. While some table Ri in result is not in BCNF, pick a non-trivial X → Y that holds on Ri with X not a superkey of Ri.
  3. Replace Ri by R₁ = X⁺ ∩ Ri and R₂ = Ri − (X⁺ − X). The two share X, and X is a key of R₁.
  4. Stop when every table is in BCNF.

The result is always lossless, because each split shares an attribute set that is a key of one side (Chapter 4.6). It is not always dependency preserving. So the designer chooses: BCNF removes all FD redundancy but may lose a rule; 3NF keeps every rule but may keep some redundancy. The usual advice is to aim for BCNF and fall back to 3NF when a needed dependency would be lost.

Worked example

Question (8 marks). R(A, B, C, D, E) has F = {A → BC, CD → E, B → D, E → A}, with candidate keys {A}, {E}, {B, C}, {C, D} (Chapter 4.2). (a) Is R in BCNF? (b) If not, decompose it into BCNF. (c) Is your decomposition dependency preserving?

  1. Test each FD. A⁺ = R, CD⁺ = R, E⁺ = R: these left sides are superkeys. B⁺ = {B, D} ≠ R: B → D violates BCNF. (R is still in 3NF, since D is prime.)
  2. Split on B → D. R₁ = B⁺ ∩ R = {B, D}. R₂ = R − (B⁺ − B) = R − {D} = {A, B, C, E}.
  3. R₁(B, D). Every two-attribute relation is in BCNF: whichever FD holds, its left side is a key.
  4. R₂(A, B, C, E). Project with closures: A⁺ ∩ R₂ = {A, B, C, E}, E⁺ ∩ R₂ = {A, B, C, E}, {B, C}⁺ ∩ R₂ = {A, B, C, E}, while B and C alone determine nothing else in R₂. Keys of R₂: {A}, {E}, {B, C}. Every non-trivial FD has a key on its left, so R₂ is in BCNF.
  5. Answer (b). {R₁(B, D), R₂(A, B, C, E)}, lossless because the shared attribute B determines all of R₁.
  6. Preservation (c). A → BC and E → A hold inside R₂, and B → D inside R₁. But C and D never sit in one table: under the projected FDs, {C, D}⁺ = {C, D}, so CD → E is lost. The decomposition is not dependency preserving; R itself, already in 3NF, keeps it.

Exam traps

  • In BCNF, "the right side is prime" is no excuse. Every non-trivial FD needs a superkey on the left.
  • To show "3NF but not BCNF" you need overlapping composite candidate keys. Find all keys first.
  • Checking only the FDs in F works for the original R, not for tables after a split: project F⁺ with closures.
  • BCNF decomposition: always lossless, not always dependency preserving. 3NF synthesis: always both.
  • Every relation with two attributes is in BCNF.

4.6 Decomposition: lossless join and dependency preservation

A decomposition replaces a relation R by smaller relations R₁, …, Rₙ whose attributes together make up R. Every normal form in this unit is reached by decomposing, so every split must pass two checks. Lossless join: joining the pieces gives back exactly the original rows, never extra ones. Dependency preservation: every FD can still be checked inside single pieces, without a join. The first is compulsory; the second is strongly wanted.

You need: attribute closure (Chapter 4.2) and natural join (Unit 2, Set operations, Cartesian product and joins in algebra).

Lossless join and spurious tuples

{R₁, R₂} is a lossless-join decomposition of R if, for every legal instance r of R, πR₁(r) ⋈ πR₂(r) = r. The join always contains every original row. A bad split adds extra rows, called spurious tuples. "Lossy" therefore means that we lose the knowledge of which rows were true, even though we get more rows back.

The binary test. When the only constraints are FDs, {R₁, R₂} is lossless exactly when R₁ ∩ R₂ → R₁ or R₁ ∩ R₂ → R₂ is in F⁺. In words: the shared attributes must be a superkey of at least one piece. Check it with one closure: (R₁ ∩ R₂)⁺ must contain all of R₁ or all of R₂.

Three or more pieces: the chase test

For n pieces, Elmasri and Navathe give a matrix test, often called the chase:

  1. Make a matrix with one row per piece Rᵢ and one column per attribute Aⱼ of R. Put aⱼ where Aⱼ ∈ Rᵢ, and a distinct bᵢⱼ elsewhere.
  2. For each FD X → Y: wherever two rows agree on all X columns, make their Y columns equal, choosing the a-symbol if either row has one.
  3. Repeat until nothing changes. The decomposition is lossless if some row has become all a's.

Example: R(A, B, C, D), F = {A → B, C → D}, pieces AB, CD, AC.

          A    B    C    D
  AB      a1   a2   b13  b14
  CD      b21  b22  a3   a4
  AC      a1   b32  a3   b34
A → B: rows AB and AC agree on A, so b32 becomes a2.
C → D: rows CD and AC agree on C, so b34 becomes a4.
Row AC is now a1 a2 a3 a4: lossless.

Dependency preservation

The projection Fᵢ of F on a piece Rᵢ is the set of FDs in F⁺ that use only attributes of Rᵢ. The decomposition is dependency preserving if (F₁ ∪ … ∪ Fₙ)⁺ = F⁺. Then every update can be checked inside one table; otherwise some rule needs a join on every insert. To test an FD X → Y without computing F⁺:

  1. Set result = X.
  2. For each piece Rᵢ: result = result ∪ ((result ∩ Rᵢ)⁺ ∩ Rᵢ), with the closure taken under F.
  3. Repeat step 2 until result stops changing. X → Y is preserved exactly when Y ⊆ result.

Shortcut: if X ∪ Y lies inside one piece, the FD is preserved at once.

Worked example

Question (8 marks). R(A, B, C, D, E) has F = {A → BC, CD → E, B → D, E → A}. (a) Is {(A, B, C), (A, D, E)} lossless? (b) Is {(A, B, C), (C, D, E)} lossless? (c) Is the decomposition in (a) dependency preserving?

  1. (a) R₁ ∩ R₂ = {A}. A⁺ = {A, B, C, D, E}, which contains R₁ = {A, B, C}. So A → R₁: lossless.
  2. (b) R₁ ∩ R₂ = {C}. C⁺ = {C}, which contains neither piece: lossy.
  3. (c) Easy FDs. A → BC lies inside (A, B, C); E → A lies inside (A, D, E). Both preserved.
  4. B → D. result = {B}. Piece ABC: B⁺ ∩ ABC = {B}. Piece ADE: {B} ∩ ADE is empty. No change, D ∉ result: not preserved.
  5. CD → E. result = {C, D}. Piece ABC: C⁺ ∩ ABC = {C}. Piece ADE: D⁺ ∩ ADE = {D}. No change, E ∉ result: not preserved.
  6. Answer. Decomposition (a) is lossless but loses B → D and CD → E. Compare the BCNF split of Chapter 4.5, {(B, D), (A, B, C, E)}, which is lossless and loses only CD → E.

Exam traps

  • Lossy means extra rows, not missing rows.
  • Sharing an attribute is not enough: the shared attributes must be a key of at least one piece.
  • An FD that fits in no piece can still be preserved through others: with F = {A → B, B → C, A → C} and pieces AB, BC, A → C follows from A → B and B → C.
  • The two properties are independent: a split can have both, one, or neither. {AB, CD} with F = {A → B, C → D} preserves both FDs yet is lossy.
  • For three or more pieces, use the chase, not the pairwise test.

4.7 Multivalued dependencies and fourth normal form

A multivalued dependency (MVD) X →→ Y says that, for each value of X, the set of Y values is independent of everything else in the row: every Y value pairs with every value of the remaining attributes. It appears when one table holds two independent one-to-many facts about the same thing, such as the teachers of a course and the textbooks of a course. FDs cannot see this redundancy, so a table can be in BCNF and still repeat data. Fourth normal form (4NF), defined by Ronald Fagin in 1977, removes it.

You need: BCNF (Chapter 4.5) and the lossless-join idea (Chapter 4.6).

The definition

Let X and Y be sets of attributes of R, and Z = R − X − Y. The MVD X →→ Y holds on R if, for every legal instance r and any two tuples t₁, t₂ of r with t₁[X] = t₂[X], r also contains tuples t₃ and t₄ with:

  • t₃[X] = t₄[X] = t₁[X];
  • t₃[Y] = t₁[Y] and t₃[Z] = t₂[Z];
  • t₄[Y] = t₂[Y] and t₄[Z] = t₁[Z].

In words: take two rows that agree on X and swap their Y parts; both swapped rows must already be in the table. Equivalently, for each X value the rows form the full cross product of its Y values and its Z values.

CourseInfo(course, teacher, book) shows it. DBMS is taught by Meena and Arjun and uses the books by Korth and by Navathe. Any teacher may use any book, so course →→ teacher, and the table needs all 2 × 2 = 4 combinations. No non-trivial FD holds, so the only key is all three attributes and the table is in BCNF. Yet adding a third book needs two new rows, one per teacher, and forgetting one breaks the pattern.

Rules worth knowing

  • Trivial MVD: X →→ Y is trivial if Y ⊆ X or X ∪ Y = R. It holds in every relation.
  • Every FD is an MVD: if X → Y then X →→ Y. The converse is false: a course has many teachers.
  • Complementation: if X →→ Y then X →→ R − X − Y. MVDs come in pairs, written X →→ Y | Z.
  • Lossless split (Fagin): {R₁, R₂} is lossless exactly when R₁ ∩ R₂ →→ R₁ − R₂. An MVD is precisely the condition for a lossless split into two.

Fourth normal form

R is in 4NF with respect to a set D of FDs and MVDs if, for every non-trivial MVD X →→ Y in D⁺, X is a superkey of R. Because every FD is an MVD, 4NF implies BCNF. To decompose: while some table Rᵢ has a non-trivial MVD X →→ Y (with X and Y disjoint) and X is not a superkey of Rᵢ, replace Rᵢ by (X ∪ Y) and (Rᵢ − Y). Each split is lossless by Fagin's rule.

Worked example

Question (8 marks). CourseInfo(course, teacher, book) has course →→ teacher. DBMS has 3 teachers and 4 books. (a) How many rows does DBMS need? (b) How many rows must be added for a fifth book? (c) Is the table in BCNF? In 4NF? (d) Decompose into 4NF, count the rows and check the join.

  1. (a) Every teacher pairs with every book: 3 × 4 = 12 rows.
  2. (b) The new book pairs with all 3 teachers: 3 rows. Missing any one breaks the swap rule.
  3. (c) No non-trivial FD holds (a course has many teachers and many books), so the only key is {course, teacher, book} and the table is in BCNF. course →→ teacher is non-trivial (teacher ⊄ {course}, and course ∪ teacher ≠ R) while course is not a superkey: not 4NF.
  4. (d) Split. CT(course, teacher): 3 rows. CB(course, book): 4 rows. Total 7 rows instead of 12, and a fifth book is 1 row in CB.
  5. Check. CT ∩ CB = {course}, and course →→ teacher = CT − CB, so the split is lossless. Joining on course pairs 3 teachers with 4 books: exactly the 12 original rows.
  6. Testing an instance. Rows (DBMS, Meena, Korth), (DBMS, Arjun, Navathe), (DBMS, Meena, Navathe): swapping the first two needs (DBMS, Meena, Navathe), present, and (DBMS, Arjun, Korth), missing. So course →→ teacher fails until that row is added.

Exam traps

  • X →→ Y does not mean X → Y. One course, many teachers.
  • MVDs come in pairs: course →→ teacher gives course →→ book.
  • An all-key table is always in BCNF but may fail 4NF. Do not stop at BCNF when the table has no FDs.
  • X →→ Y with X ∪ Y = R is trivial; it is never a 4NF violation.
  • An MVD is not a multivalued attribute (Unit 1). The MVD appears when two multivalued attributes of one entity are put in one table.

4.8 Join dependencies and fifth normal form

A join dependency (JD) says that a table can always be rebuilt by joining three or more of its projections, even when no split into two works. It captures a cyclic business rule among three attributes, such as: if a vendor supplies a material, the material is used at a site, and the vendor serves that site, then the vendor supplies that material to that site. Fifth normal form (5NF), also called project-join normal form (PJNF), removes the redundancy such rules cause. In real schemas it is rare, but it completes the ladder of normal forms.

You need: MVDs and 4NF (Chapter 4.7); lossless join (Chapter 4.6).

Join dependency

A JD on R, written *(R₁, R₂, …, Rₙ) with R₁ ∪ … ∪ Rₙ = R, holds if every legal instance r satisfies r = πR₁(r) ⋈ πR₂(r) ⋈ … ⋈ πRₙ(r). In other words, splitting into those n pieces is always lossless.

  • A JD is trivial if some piece Rᵢ is all of R.
  • An MVD X →→ Y is a JD with two pieces: *(X ∪ Y, X ∪ Z), where Z = R − X − Y. JDs extend MVDs to three or more pieces.
  • A JD is implied by the keys when the candidate keys alone guarantee it. The common case: every piece contains the same candidate key, as in *((roll_no, name), (roll_no, city)).

Fifth normal form

R is in 5NF if every non-trivial JD that holds on R is implied by the candidate keys of R. Ronald Fagin defined it in 1979. 5NF implies 4NF, because an MVD is a two-piece JD. In practice: a table in 4NF is in 5NF unless a cyclic three-way rule holds, and when it does, split the table into the pieces of the JD.

Take Supply(vendor, material, site) with the cyclic rule above. Its rows are (Ravi, cement, Port), (Ravi, steel, Metro), (Sri, cement, Metro) and (Ravi, cement, Metro). The fourth row is forced by the first three: Ravi supplies cement (row 1), cement is used at Metro (row 3), and Ravi serves Metro (row 2). This is the 5NF anomaly: inserting three facts obliges a fourth row, and deleting that row alone breaks the rule.

Worked example

Question (8 marks). Supply(vendor, material, site) holds the 4 rows above and obeys the cyclic rule. (a) Show that no split into two projections is lossless. (b) Show that the split into VM, MS and SV is lossless. (c) Give the highest normal form of Supply and its 5NF design.

  1. VM ⋈ MS on material: cement pairs Ravi and Sri with Port and Metro, steel pairs Ravi with Metro: 5 rows, one extra, (Sri, cement, Port). Lossy.
  2. MS ⋈ SV on site: Port gives (Ravi, cement, Port); Metro pairs steel and cement with Ravi and Sri: 5 rows, extra (Sri, steel, Metro). Lossy.
  3. VM ⋈ SV on vendor: Ravi gives 2 materials × 2 sites = 4 rows, Sri gives 1 × 1 = 1: 5 rows, extra (Ravi, steel, Port). Lossy. So no non-trivial MVD holds.
  4. (b) (VM ⋈ MS) ⋈ SV: of the 5 rows of step 1, only (Sri, cement, Port) lacks its pair (Port, Sri) in SV. It is dropped, leaving exactly the 4 original rows: lossless.
  5. (c) No FD holds, so the only key is {vendor, material, site}: BCNF. No MVD holds: 4NF. The JD *(VM, MS, SV) holds and no piece contains the key, so the keys do not imply it: 4NF, not 5NF.
  6. 5NF design: VM(vendor, material), MS(material, site), SV(site, vendor), with 3 rows each. Supply is now a view: the three-way join.

Exam traps

  • 4NF is about splits into two; 5NF is about splits into three or more that work when no split into two does.
  • A JD must hold for every legal instance, which means a business rule. One instance that happens to rebuild proves nothing.
  • Without the cyclic rule, Supply is already in 5NF, and splitting it would be lossy.
  • A JD whose pieces all contain the same candidate key is implied by that key and never breaks 5NF.

Takeaways

  1. Storing one fact in many rows causes insertion, deletion and update anomalies; normalization removes the repeats by splitting tables without losing rows.
  2. An FD X → Y means equal X values force equal Y values. Attribute closure X⁺ tells you whether X is a key and whether an FD follows from F.

  5. 1NF asks for atomic values, 2NF forbids partial dependencies, and 3NF requires each determinant to be a superkey unless the dependent attribute is prime.

  7. A split into two is lossless when the shared attributes determine one side; for more pieces, use the chase.
  8. MVDs and 4NF deal with two independent lists in one table; JDs and 5NF deal with cyclic three-way rules.

Examples: Student(roll_no, name, city) is in 1NF with atomic values; R(A, B, C, D) with {AB → C, B → D} is 1NF only; R(A, B, C) with {A → B, B → C} is 2NF only; Teaching, or R(A, B, C) with {AB → C, C → B}, is 3NF but not BCNF. Each form contains the next.

Understand Q4. Explain multivalued dependencies and fourth normal form with an example. Why does BCNF not remove all redundancy? 8 marks

Swap-rule definition with t₁ to t₄. CourseInfo (Figure 4.7.1): all-key, so BCNF, yet rows grow as teachers × books. Trivial MVDs, FD implies MVD, complementation. 4NF definition, the split into CT and CB, lossless by Fagin's rule.

Apply

Apply Q5. R(A, B, C, D, E, F) has F = {A → B, B → C, AD → E, E → F}. Find the candidate keys and the highest normal form, give a 3NF decomposition, and say whether it is in BCNF. 10 marks

A and D are on no right side; {A, D}⁺ = {A, B, C, D, E, F}, so {A, D} is the only key. A → B is partial: 1NF. F is already a canonical cover; synthesis gives (A, B), (B, C), (A, D, E), (E, F), and (A, D, E) holds the key. Every table's determinant is its key, so all four are in BCNF, lossless and dependency preserving.

Apply Q6. R(A, B, C, D, E) has F = {A → BC, B → C, AB → D, D → C}. Find the candidate key, a canonical cover, and the 3NF synthesis. 10 marks

E is on no side and A on no right side; {A, E}⁺ = R, so the key is {A, E}. Canonical cover (Chapter 4.3): {A → BD, B → C, D → C}. Tables (A, B, D), (B, C), (C, D); none contains {A, E}, so add (A, E). Final: (A, B, D), (B, C), (C, D), (A, E).

Apply Q7. R(A, B, C, D, E) has F = {A → BC, CD → E, B → D, E → A}. Use the chase to test whether {(A, B, C), (B, D), (C, D, E)} is lossless, and test dependency preservation. 8 marks

Rows ABC = a1 a2 a3 b14 b15; BD = b21 a2 b23 a4 b25; CDE = b31 b32 a3 a4 a5. B → D: rows ABC and BD agree on B, so b14 becomes a4. CD → E: rows ABC and CDE now agree on C, D, so b15 becomes a5. Row ABC is all a's: lossless. A → BC, B → D, CD → E each fit in a piece. E → A: result {E} grows to {C, D, E} through piece CDE, then nothing new from ABC or BD; A never appears, so E → A is lost.

Apply Q8. Student(roll_no, club, language): each of 200 students is in 3 clubs and speaks 2 languages, independently. Count the rows before and after a 4NF split, and show that the split is lossless. 8 marks

roll_no →→ club | language. Before: 200 × 3 × 2 = 1,200 rows. After: (roll_no, club) 600 + (roll_no, language) 400 = 1,000 rows. Shared attribute roll_no, and roll_no →→ club = R₁ − R₂, so lossless. A fourth club costs 2 rows before, 1 after.

Analyze and evaluate

Analyze Q9. R(A, B, C, D) has F = {AB → C, C → D, D → A}. Find all candidate keys and the highest normal form. Decompose into BCNF and name any lost dependency. Would you choose 3NF instead? 10 marks

B is on no right side. Keys {A, B}, {B, C}, {B, D}; every attribute is prime, so 3NF. C → D and D → A break BCNF. Split on C → D: C⁺ = {A, C, D} gives (A, C, D) and (B, C); in (A, C, D), D → A breaks BCNF, giving (A, D) and (C, D). Result (A, D), (C, D), (B, C): lossless, but AB → C is lost. R is already in 3NF with every FD enforceable, so keep it unless the repeated D → A facts are costly.

Evaluate Q10. Compare 3NF and BCNF: definitions, when they differ, the decomposition algorithms and their properties. Which would you choose for a college timetable database, and why? 12 marks

Definitions; the only difference is the "A is prime" exception. They differ only with overlapping composite keys. Teaching example and the lost {student, subject} → teacher (Figure 4.5.1). 3NF synthesis: lossless and preserving; BCNF decomposition: lossless, not always preserving (Chapter 4.6). A DBMS enforces keys cheaply but needs triggers for lost FDs. Choice with a reason, for example BCNF unless a rule would need a trigger on every insert.

Analyze Q11. A college keeps CollegeRecord(roll_no, name, phones, dept, hod, course, credits, grade), where phones holds a list. Normalize it step by step to BCNF, listing the FDs and keys at each step and checking each split. 16 marks

1NF: move phones to StudentPhone(roll_no, phone). FDs roll_no → name dept, dept → hod, course → credits, roll_no course → grade; key {roll_no, course}. 2NF: split out Student(roll_no, name, dept, hod) and Course(course, credits). 3NF: split Dept(dept, hod). BCNF: every determinant is now a key. Each split shares a key of one side, so it is lossless; all FDs preserved. Show the anomalies gone with the counts of Chapter 4.1.

Analyze Q12. Explain join dependencies and fifth normal form with an example. Why can a relation in 4NF still hold redundancy, and why is 5NF rare in practice? 10 marks

JD definition; MVD as a two-piece JD. Supply with the cyclic rule: each two-way join adds a spurious row, the three-way join is exact (Figure 4.8.1). Three facts force a fourth row: the 4NF table repeats information implied by the rule. 5NF definition, JDs implied by keys. Rare because genuine cyclic rules are rare.

Evaluate Q13. "A fully normalized database is always the best design." Evaluate this statement. 8 marks

For: no anomalies, each fact changed once, keys enforce the rules. Against: more joins, slower wide reads, BCNF may lose a dependency. Denormalization for read-heavy reporting and warehouses (star schema) with triggers or batch refresh to keep copies right. Conclusion: normalize the transaction database to 3NF or BCNF and denormalize only measured hot spots.

Analyze Q14. R(A, B, C, D, E) has F = {A → BC, CD → E, B → D, E → A}. Show that R is in 3NF but not BCNF. Compare the decompositions {(A, B, C), (A, D, E)} and {(B, D), (A, B, C, E)}. 10 marks

Keys {A}, {E}, {B, C}, {C, D} (Chapter 4.2); all attributes prime, so 3NF; B → D breaks BCNF. First split: lossless (A⁺ ⊇ ABC) but loses B → D and CD → E (Chapter 4.6). Second split: the BCNF result of Chapter 4.5, lossless, loses only CD → E. The second is better; keeping R in 3NF loses nothing at all.

Glossary

Anomaly
An insertion, deletion or update problem caused by storing one fact in many rows.
Armstrong's axioms
Reflexivity, augmentation and transitivity: rules that derive every FD implied by a set F.
Attribute closure (X⁺)
The set of all attributes functionally determined by X under F.
BCNF
Boyce-Codd normal form: every non-trivial FD has a superkey on its left side.
Candidate key
A minimal set of attributes whose closure is the whole relation.
Canonical cover
A minimal cover with FDs of equal left side merged, so each left side appears once.
Chase
A matrix test that decides whether a decomposition into any number of pieces is lossless.
Decomposition
Replacing a relation by projections whose attributes together make up the original.
Denormalization
Deliberately keeping a redundant copy of data to make reads faster.
Dependency preservation
Property of a decomposition whose projected FDs together imply all of F.
Determinant
The left side X of an FD X → Y.
Extraneous attribute
A left-side attribute of an FD that can be removed without changing F⁺.
First normal form (1NF)
Every attribute value is atomic: no lists, sets or nested tables.
Second normal form (2NF)
1NF with no non-prime attribute partially dependent on a candidate key.
Third normal form (3NF)
For every non-trivial X → A, X is a superkey or A is prime.
Fourth normal form (4NF)
For every non-trivial MVD X →→ Y, X is a superkey.
Fifth normal form (5NF)
Also PJNF: every non-trivial join dependency is implied by the candidate keys.
Full functional dependency
X → A where no proper subset of X determines A.
Functional dependency
X → Y: any two tuples equal on X are equal on Y.
Join dependency
*(R₁, …, Rₙ): every legal instance equals the join of its projections on the Rᵢ.
Lossless join
Property of a decomposition whose pieces always join back to exactly the original relation.
Minimal cover
An equivalent set of FDs with single-attribute right sides, no extraneous attributes and no redundant FDs.
Multivalued dependency
X →→ Y: for each X value, the Y values pair with every value of the remaining attributes.
Partial dependency
A non-prime attribute that depends on a proper subset of a candidate key.
Prime attribute
An attribute that belongs to at least one candidate key.
Redundancy
The same fact stored more than once.
Spurious tuple
A row produced by joining the pieces of a lossy decomposition that was not in the original.
Transitive dependency
K → X → A, where X is not a superkey and A is non-prime.
Trivial dependency
An FD X → Y with Y ⊆ X, or an MVD with Y ⊆ X or X ∪ Y = R; it holds in every relation.
