4.1 Compile-time versus run-time polymorphism

Polymorphism ("many forms") lets one name stand for several pieces of code: show(7) and show(7.5) run different functions, and shape->area() runs the circle's formula for a circle and the rectangle's formula for a rectangle. This chapter answers one question: when does the program decide which code a name means? If the compiler decides while it translates the source, it is compile-time polymorphism. If the decision waits until the program runs and looks at the actual object, it is run-time polymorphism. Every later chapter of this unit belongs to one of these two families, so this split is the map of the unit.

You need: inheritance and overriding from Unit 3 (Inheritance basics; Method overriding and the super keyword) and pointers from Unit 1 (Pointers and dynamic memory with new and delete).

Binding: tying a call to a body

Binding is the link between a function call in your source and the function body that actually runs. A call such as area(5) is only a name and some arguments; something has to choose which area it means.

Early binding (also called static binding) is done by the compiler. It looks at the name and at the declared types of the arguments and of the object, picks one function, and writes that function's address straight into the machine code. Nothing is left to decide at run time.

Late binding (dynamic binding) leaves the choice open. At run time the program inspects the actual object and only then jumps to the matching function. In C++ this happens only for virtual functions called through a pointer or a reference (chapter 4.5). In Java every ordinary instance method is bound late; in Python every method call is (chapter 4.9).

The two families

Compile-time polymorphism comes from three tools: function overloading, several functions with one name and different parameter lists (chapter 4.2); operator overloading, giving +, - or << a meaning for your class (chapter 4.3); and templates, one generic function written once and generated for each type (Unit 5, Function templates and template overloading). Run-time polymorphism comes from overriding: a derived class replaces a base-class method with its own version, and a call made through a base-class pointer or reference reaches the right version for the object.

Why a language offers both

Early binding is cheap and safe: a wrong call is a compile error, and the compiler can inline small functions. Its limit is that the code must name every type in advance. Late binding costs a little per call, but it lets old code work with classes written later. A billing loop that calls t->fare(km) on Ticket* pointers will charge correctly for a VandeBharat class added next year, without a single change to the loop. Java and Python bind late by default. C++ makes you ask for it with virtual, because its rule is that you should not pay for what you do not use.

Exam traps

  • Overloading versus overriding. Overloading (same name, different parameters) is compile-time; overriding (same signature in a derived class) is run-time. Swapping the two words costs marks.
  • virtual alone is not enough. Late binding needs a call through a pointer or reference. A call on an object, like E above, is bound early.
  • Templates are compile-time polymorphism, even though they "work for any type": the compiler generates one function per type.
  • Java has no virtual keyword. Its non-static, non-private, non-final methods are all late-bound already.

4.2 Function and method overloading

Function overloading means defining several functions with the same name but different parameter lists, so one natural name covers one job done on different inputs: the area of a circle, of a rectangle, of a triangle. At each call the compiler picks the right version from the arguments, so overloading is compile-time polymorphism. Java calls it method overloading. Constructor overloading is the same rule applied to constructors (Unit 2, Constructors: default, parameterized and copy).

What makes two functions different

The compiler tells overloads apart by their signature: the name plus the number, types and order of the parameters.

  • Different count: area(double r) and area(double l, double b).
  • Different types: print(int) and print(const char*).
  • Different order: put(int, char) and put(char, int).

These do not make a new signature: a different return type alone (int read() beside double read() is an error, because the call read() gives no hint), different parameter names, or a typedef of the same type. For member functions a trailing const does count, so get() and get() const are two overloads. Behind the scenes the compiler gives each overload a unique "mangled" name; with g++, bill(int) becomes _Z4billi and bill(double) becomes _Z4billd, where the last letters encode the parameter types. That is how the linker keeps them apart.

How the compiler picks: overload resolution

  1. Collect candidates: every visible function with that name.
  2. Keep the viable ones: those that accept this many arguments (counting default arguments) and whose parameters each argument can be converted to.
  3. Rank each argument's conversion on the ladder of Figure 4.2.1: an exact match beats a promotion (char or short to int, float to double), which beats a standard conversion (int to double, long to int), which beats a conversion through your own class (chapter 4.4), which beats the ellipsis ....
  4. Pick the best: a function wins if it is at least as good as every other for every argument and strictly better for at least one. If no single function wins, the compiler reports an ambiguous call. Nothing is left for run time.

Java: method overloading

Java applies the same idea to methods. A class can hold int add(int a, int b), double add(double a, double b) and String add(String a, String b): add(2, 3) gives 5, add(2.5, 3) gives 5.5 (the 3 widens to double), and add("UP", "I") gives "UPI". Java resolves in phases: first without boxing or varargs, then with boxing, then with varargs. So with m(long) and m(Integer), the call m(5) prints "long 5", because widening int to long is tried before boxing int to Integer.

Python: one function, flexible parameters

In Python a second def with the same name simply replaces the first. After def area(r) and then def area(l, b), the call area(5) fails with TypeError: area() missing 1 required positional argument: 'b'. Python gets the effect of overloading from one function with default values, keyword arguments and *args. A bare * in the parameter list makes every parameter after it keyword-only, so callers must name them. To choose an implementation by type, the standard library's functools.singledispatch picks one from the type of the first argument.

4.3 Operator overloading: unary and binary operators

Operator overloading lets the built-in operators work on objects of your own classes: a + b for two complex numbers, p == q for two points, cout << m for a money object. You write a function with the special name operator+, operator== or operator<<, and the compiler turns every use of that operator on your objects into a call to it. The same symbol + then means integer addition, string joining or complex addition, chosen from the operand types while compiling, so this is compile-time polymorphism.

You need: friend functions from Unit 2 (Inline functions and friend functions) and references from Unit 1.

The rules

  • Only existing operators can be overloaded; you cannot invent a new symbol such as **.
  • Precedence, associativity and the number of operands stay those of the built-in operator: a + b * c still multiplies first.
  • At least one operand must be of a class (or enum) type, so int + int can never be redefined.
  • These cannot be overloaded: :: (scope), . (member access), .* (pointer to member), ?: (conditional), sizeof and typeid.
  • These must be member functions, never friends: =, [], () and ->.

Unary operators: one operand

A unary operator such as -a, !a or ++a works on one object. Written as a member function it takes no parameter, because the operand is the object itself (*this). Written as a friend it takes one parameter.

The operators ++ and -- come in two forms, which the compiler tells apart by a dummy int. Complex& operator++() is prefix ++a: change the object, then return the object itself by reference. Complex operator++(int) is postfix a++: save a copy, change the object, return the old copy by value. The int is never used; it only marks the postfix form.

Binary operators: two operands

As a member function a binary operator takes one parameter; the left operand is the calling object, so a + b becomes a.operator+(b). As a friend (or any non-member) it takes two parameters, and a * b becomes operator*(a, b).

Use the friend form when the left operand is not your class. In 2 * b the left operand is an int, which has no member functions; in cout << c it is an ostream, a library class you cannot edit. For <<, return the stream by reference so that cout << a << b can chain.

Python and Java

Python's operators call "dunder" (double-underscore) methods: a + b calls a.__add__(b), -a calls a.__neg__(), a == b calls a.__eq__(b), and print(a) uses a.__str__(). If a.__add__ cannot handle b, Python tries the reflected b.__radd__(a); that is what lets sum(), which starts from 0, add your objects. Java does not let programmers overload operators at all: + on String is built into the language, and classes use methods such as add() and equals().

4.4 Type conversion between basic and user-defined types

C++ converts between built-in types on its own: assign 7 to a double and it becomes 7.0. For your own classes it cannot guess, so you tell it how by writing conversion routines. There are three situations: a basic type to a class (write a constructor that takes one argument), a class to a basic type (write a conversion function such as operator double()), and one class to another (write a constructor in the destination class or a conversion function in the source class). The compiler then calls these routines silently, which makes a class feel built in. Textbooks treat this right after operator overloading, often as "data conversion", because a conversion function is an operator function.

You need: built-in conversions and casts from Unit 1 (Operators, expressions and type conversion) and constructors from Unit 2.

Basic type to class: the converting constructor

A constructor that can be called with one argument is a converting constructor. Given Celsius(double d), all three statements below use it:

  • Celsius c(40); is direct initialisation.
  • Celsius c = 40; is copy initialisation: the compiler builds a Celsius from 40.
  • c = 37.0; is assignment: a temporary Celsius(37.0) is built and then copied into c.

In Celsius c = 40; the 40 is an int, so the compiler first applies the standard conversion int → double and then the constructor. A silent conversion may contain at most one user-defined step, with standard conversions before or after it.

Class to basic type: the conversion function

The routine is a member function named after the target type: operator double() const { return deg; }. Three rules: it must be a member, it has no return type written (the name already says it), and it has no parameters. After that, double d = c;, c + 5 and sqrt(c) all work. C++11 also allows explicit operator bool(), which lets if (file) work but rejects int n = file;.

explicit: stopping silent conversions

Silent conversions can hide mistakes. With a constructor Rupee(int paise), a call refund(5) to void refund(Rupee r) quietly builds Rupee(5), five paise, when the coder may have meant five rupees. Marking the constructor explicit Rupee(int paise) makes Rupee r = 5; and refund(5) compile errors (g++: "conversion from 'int' to non-scalar type 'Rupee' requested"), while Rupee r(5); and refund(Rupee(5)) still work. Make one-argument constructors explicit unless the conversion is natural, as double to Celsius is.

Java and Python

Java has no user-defined silent conversions. It converts through named methods such as Integer.parseInt("42"), String.valueOf(3.5) and toString(), plus the built-in autoboxing between int and Integer. Python's built-in functions call special methods: float(c) calls c.__float__(), int(c) calls __int__, str(c) calls __str__, and bool(c) calls __bool__. The other direction is just the constructor, Celsius(40). In both languages you always write the call; nothing converts behind your back.

4.5 Virtual functions and late binding

A virtual function is a member function declared with the keyword virtual in a base class, so that a call through a base-class pointer or reference runs the version belonging to the actual object, not the version named by the pointer's type. The choice is made while the program runs: late binding. This is how C++ gets run-time polymorphism, so that one loop over Shape* pointers computes the area of rectangles and circles correctly. Every syllabus lists virtual functions.

You need: overriding from Unit 3 (Method overriding and the super keyword) and the fact that a Shape* may hold the address of a Rect, which chapter 4.6 treats in full.

The problem virtual solves

Without virtual, the call p->area() with p declared as Shape* always runs Shape::area. The compiler binds from the pointer's declared type, because that is all it knows while compiling. The derived class's own area exists, but the pointer never reaches it.

Declaring and overriding

  1. In the base class, mark the function: virtual double area() const { return 0; }.
  2. In each derived class, define a function with the same name, the same parameter list, the same const and a compatible return type. Repeating virtual is optional; once virtual, always virtual down the hierarchy. Add override (C++11) after the parameter list so the compiler checks that a matching base virtual exists.
  3. Call it through a base pointer or reference: Shape* p = &r; p->area(); or void report(const Shape& s) { cout << s.area(); }.

The rules examiners ask for:

  • A virtual function must be a non-static member function; a static function has no object, so there is nothing to look up.
  • Constructors cannot be virtual; destructors can, and in a base class usually must be (chapter 4.8).
  • If a derived class does not redefine it, the base version is used.
  • A different signature does not override; it creates a new function that hides the base one.
  • A virtual function can be a friend of another class, and final (C++11) stops further overriding.

How late binding works: vtable and vptr

The C++ standard does not fix the mechanism, but every major compiler uses the same scheme:

  • For each class that has virtual functions the compiler builds one table, the vtable: an array of function addresses, one slot per virtual function. Rect's slot 0 holds the address of Rect::area; Circle's slot 0 holds Circle::area.
  • Every object of such a class carries a hidden pointer, the vptr, which its constructor sets to its own class's vtable.
  • A call p->area() is compiled as: read the vptr from the object, load slot 0 of that table, call the address found there.

The cost is one pointer per object and one indirect call. With g++ on 64-bit Linux, a class holding one int is 4 bytes; add one virtual function and it becomes 16 bytes (8-byte vptr, 4-byte int, 4 bytes of padding). The vtable itself exists once per class, not once per object.

Java and Python

In Java every non-static, non-private, non-final method is virtual automatically; Java calls this dynamic method dispatch. Shape s = new Circle(2); s.area(); runs Circle's area. Private, static and final methods are bound early. In Python every method is looked up on the actual object at each call (chapter 4.9), so overriding always behaves like a C++ virtual function.

4.6 Base class pointers to derived class objects

A pointer declared as Base* may hold the address of a Derived object, because under public inheritance every derived object contains a complete base part: a Teacher is a Staff member. Virtual functions (chapter 4.5) are built on this. Most syllabi teach it inside virtual functions, so this chapter is short.

What the pointer can see

  • Upcast is automatic. Staff* bp = &t; needs no cast when Teacher inherits publicly from Staff.
  • Only base members are reachable. bp->id works, but bp->periods is a compile error, because the compiler checks names against the pointer's type. Non-virtual calls also bind to the base version.
  • Downcast needs a cast. static_cast<Teacher*>(bp) is unchecked and correct only if bp really points to a Teacher. dynamic_cast<Teacher*>(bp) checks at run time and returns nullptr if it does not; it works only when the base class has at least one virtual function.
  • Java applies the same rules to references; a bad downcast throws ClassCastException. Python has no typed pointers: any name can refer to any object (chapter 4.9).

Pointer arithmetic: the trap

p + 1 moves the address forward by sizeof(*p), the size of the pointer's declared type. A Staff* walking an array of Teacher objects therefore steps 4 bytes when each element is 8 bytes long, and lands in the middle of an object.

4.7 Pure virtual functions and abstract classes

A pure virtual function is a virtual function with no body in the base class, written with = 0: virtual double fee() const = 0;. It says "every derived class must supply this". A class with at least one pure virtual function is an abstract class: you cannot create objects of it, but you can have pointers and references to it, and it can still hold data and ordinary functions. A derived class that gives a body to every inherited pure virtual function is a concrete class and can create objects.

You need: chapter 4.5 (virtual functions and the vtable).

Syntax and meaning

The = 0 is not "assign zero" and not "return zero". It is the pure specifier: it tells the compiler that this class has no body for the function, so this class's vtable slot has nothing real to call. Some base classes describe an idea with no sensible default. Every payment has a fee, but there is no general fee; every shape has an area, but no general formula. The old workaround, virtual double fee() const { return 0; }, is a dummy body that silently gives wrong answers whenever a derived class forgets to override it. Making the function pure turns that mistake into a compile error.

Rules of abstract classes

  • No objects. Payment p(2000); fails: g++ says "cannot declare variable 'p' to be of abstract type 'Payment'". Arrays of Payment, and passing or returning one by value, fail for the same reason.
  • Pointers and references are fine: Payment* p = &u; and void receipt(const Payment& p).
  • It can have data members, constructors, a (virtual) destructor, and ordinary functions that call the pure ones, such as total() calling fee().
  • Abstractness is inherited. A derived class that leaves even one pure virtual function without a body is abstract too.
  • A pure virtual function may still have a body defined outside the class and called explicitly as Payment::fee(). This is rare, except for a pure virtual destructor, which must have one (chapter 4.8).

4.8 Virtual destructors

When a derived object is deleted through a pointer to its base class, the base class's destructor must be virtual. If it is not, the C++ standard calls the behaviour undefined, and in practice only the base destructor runs: whatever the derived class owned (heap memory, an open file, a network connection) is never released. Declaring virtual ~Base() makes delete p find the actual object's destructor through the vtable, which runs the derived destructor first and then the base one.

You need: destructors from Unit 2 (Destructors and object lifetime), new and delete from Unit 1, and chapter 4.5.

The problem

Logger* p = new FileLogger; delete p; does two things: it calls a destructor, then frees the object's memory. Which destructor? The same rule as for any member function. If ~Logger() is not virtual, the compiler binds it from the pointer's type, so Logger::~Logger() runs and FileLogger::~FileLogger() never does. The 4096-byte buffer that the FileLogger allocated is never freed. Formally the whole delete is undefined behaviour; a silent leak is the usual symptom.

The fix and the order of calls

Write virtual ~Logger() in the base class. Now delete p works like this:

  1. Read the object's vptr and find the destructor slot in FileLogger's vtable.
  2. Run FileLogger::~FileLogger(); its body frees the buffer.
  3. The compiler then runs Logger::~Logger() automatically for the base part.
  4. Free the memory of the object itself.

Destructors run in the reverse order of constructors: the base constructor runs first and the derived one last; the derived destructor runs first and the base one last. Once the base destructor is virtual, every derived destructor is virtual too, even though the names differ.

When to make a destructor virtual

  • Rule of thumb: if a class has any virtual function, or is meant to be deleted through a base pointer, give it a virtual destructor.
  • Not for classes that are never bases. A value class such as Point { int x, y; } is 8 bytes; a virtual destructor adds a vptr and makes it 16 bytes with g++ on 64-bit, for no benefit.
  • Stricter rule from the C++ Core Guidelines: a base class destructor should be either public and virtual, or protected and non-virtual, so that nobody can delete through a base pointer at all.
  • Pure virtual destructor: virtual ~Shape() = 0; makes a class abstract when it has no other pure function, but it still needs a body, Shape::~Shape() {}, because every derived destructor calls it.

Why there are no virtual constructors

A constructor creates the object, including its vptr, so before it runs there is no vptr to look up; and to create an object you must already know its exact type. When you need a copy of an object known only through a base pointer, use a virtual function clone() that returns new Derived(*this). Books call this the "virtual constructor" idiom; it reappears with design patterns in Unit 6.

Java and Python

Neither language has destructors in the C++ sense; a garbage collector frees memory. Java's finalize() has been deprecated since Java 9, and files or sockets are closed with try-with-resources. Python has __del__, but cleanup should use a with statement. Because cleanup is not tied to a declared type, the problem of this chapter does not arise in either.

Leak without virtual: 1,000 × 4,096 bytes = 4,096,000 bytes; 4,096,000 ÷ 1,048,576 ≈ 3.9 MiB. A server that makes a logger per request loses memory steadily until it is restarted.

Exam traps

  • "Constructors can be virtual" is false; destructors can, constructors cannot.
  • A pure virtual destructor still needs a body. Without it the program fails to link.
  • virtual does not change the order: derived destructor first, then base.
  • Stack objects are safe either way. FileLogger f; always runs the right destructors; the problem is only delete through a base pointer.
  • delete[] on an array of derived objects through a base pointer is undefined even with a virtual destructor.

Remember What is a virtual destructor, and when is it needed? 2 marks

A base-class destructor declared virtual. It is needed whenever a derived object may be deleted through a base-class pointer, so that the derived destructor runs first.

Remember In what order do constructors and destructors run for a derived object? 2 marks

Constructors: base, then derived. Destructors: derived, then base.

Understand Why can a constructor not be virtual? 3 marks

Virtual dispatch reads the object's vptr, but the constructor is what sets the vptr; before it runs there is nothing to look up. Creating an object also requires its exact type to be known. The clone() idiom covers the need for a "virtual copy".

Understand Should class Point { int x, y; }, never used as a base, have a virtual destructor? 2 marks

Both print C B A. Virtualness is inherited, so ~B and ~C are virtual too; each delete starts at ~C through the vptr, and each destructor then calls its base's destructor.

Beyond the syllabus

Modern C++ code seldom calls delete by hand. A std::unique_ptr<Logger> deletes its object automatically, but it still needs the virtual destructor to delete a FileLogger correctly; std::shared_ptr happens to remember the right deleter even without one. Compilers can warn about the mistake: g++ and Clang have -Wdelete-non-virtual-dtor. The wider idea is RAII (resource acquisition is initialisation): tie every resource to an object's lifetime. Search "RAII" and "rule of zero". Not for the exam.

4.9 Duck typing and dynamic method lookup

Duck typing is Python's way of doing polymorphism without a shared base class: an object is acceptable wherever it has the methods the code calls. The name comes from the saying "if it walks like a duck and quacks like a duck, it is a duck". It works because Python finds every method by name, on the actual object, at the moment of the call; this is dynamic method lookup. A function that calls t.fare(km) works for a train ticket, a tatkal ticket and a cab, whether or not their classes are related. C++ students meet the same run-time idea as virtual functions (chapter 4.5), and Java calls it dynamic method dispatch.

You need: chapter 4.5, and overriding with super from Unit 3 (Method overriding and the super keyword).

Duck typing

Python variables and parameters carry no declared type, so a function says nothing about the class of its argument. It simply calls methods, and any object that has them will do. The built-in functions work the same way: len(x) works on anything with a __len__ method, a for loop works on anything with __iter__, and json.dump writes to any "file-like" object that has a write() method. If the method is missing, Python raises AttributeError when that line runs, not before.

Two coding styles follow. EAFP, "easier to ask forgiveness than permission", just makes the call and catches AttributeError if needed; it is the usual Python style. LBYL, "look before you leap", checks first with hasattr(x, "fare"). Checking isinstance(x, Ticket) instead defeats duck typing, because it rejects a Cab that would have worked.

Dynamic method lookup: how obj.method() is found

  1. Python looks in the object's own attribute dictionary, obj.__dict__; an attribute stored there hides a method of the same name.
  2. It then searches the classes of type(obj).__mro__, the method resolution order: the object's class first, then its base classes in a fixed order, ending with object.
  3. The first class that defines the name wins. That is why an override in a subclass hides the base version: the subclass comes earlier in the list.
  4. The function found is bound to the object (self = obj) and called. If no class defines the name, Python raises AttributeError.

This search happens at every call. Even a call made inside a base-class method, such as self.fare(km) inside Ticket.describe, starts again from the actual object's class. With multiple inheritance Python orders the classes by C3 linearisation: for class D(B, C) where both B and C inherit from A, the order is D, B, C, A, object, so D().who() finds B's version first.

Exam traps

  • Duck typing is not "no types". Python is strongly typed: "Auto" + 5 is still a TypeError. Types are checked at each operation, at run time.
  • Errors appear late. A misspelt method name fails only when that line runs; tests and type checkers such as mypy catch it earlier.
  • No overloading in Python. A second def with the same name replaces the first (chapter 4.2); do not confuse that with overriding.
  • super() follows the MRO, which with multiple inheritance may be a sibling class, not the parent you expect.
  • Favourite questions: "Explain duck typing with an example" and "How does Python resolve a method call? Explain the MRO."

Beyond the syllabus

Python 3.8 added typing.Protocol (PEP 544), "static duck typing": you describe the methods a type must have, and a checker such as mypy verifies callers before the program runs, with no inheritance needed. CPython 3.11's specialising interpreter (PEP 659) caches method lookups, so the search above is usually skipped on repeated calls. Search "structural typing" and "typing.Protocol". Not for the exam.

  1. Polymorphism is about when a call is bound: at compile time (overloading, operators, templates) or at run time (virtual functions, overriding, duck typing).

Glossary

Abstract class
A class with at least one pure virtual function still without a body; no objects can be created from it.
AttributeError
Python's run-time error when an object has no attribute or method of the name used.
Binding
Linking a function call to the function body that runs.
Concrete class
A class with every function defined, so objects can be created.
Conversion function
A member operator type() that converts an object to another type; no return type, no parameters.
Converting constructor
A constructor callable with one argument, used to convert that argument's type into the class.
Downcast
Converting a base pointer or reference to a derived one; needs static_cast or the checked dynamic_cast.
Duck typing
Accepting any object that has the methods the code calls, regardless of its class.
Dynamic method dispatch
Java's name for choosing an overridden method from the object's actual class at run time.
Early binding
Binding done by the compiler from declared types; also static binding.
explicit
Keyword that stops a constructor or conversion function from being used for silent conversions.
Late binding
Binding done at run time from the actual object; also dynamic binding.
Method resolution order (MRO)
The ordered list of classes Python searches when looking up a method.
Name mangling
The compiler's encoding of parameter types into a function's link name, which keeps overloads apart.
Object slicing
Copying a derived object into a base object, which keeps only the base part.
Operator function
A function named operator@ that gives an operator a meaning for a class.
override
C++11 specifier asking the compiler to check that a function really overrides a base virtual function.
Overload resolution
The compiler's choice of the best overload by ranking the conversions each argument needs.
Overloading
Several functions or operators with one name and different parameter lists.
Overriding
A derived class redefining a base method with the same signature.
Polymorphism
One name or interface standing for different code depending on the types involved.
Promotion
A safe widening such as char → int or float → double, ranked above other conversions.
Pure virtual function
A virtual function declared with = 0 and no body in its class.
Upcast
Treating a derived object through a base pointer or reference; implicit under public inheritance.
Virtual destructor
A base destructor declared virtual so that delete through a base pointer runs the derived destructor.
Virtual function
A member function whose calls through pointers or references are bound at run time.
vptr
The hidden pointer in each object of a polymorphic class that points to its class's vtable.
vtable
A per-class table holding the addresses of the class's virtual functions.
