3.1 Inheritance basics: base and derived classes

Inheritance defines a new class from an existing class. A derived object contains a base-class part and adds its own state or behaviour. Use public inheritance when a client can correctly treat the new object as an instance of the general type.

A relationship between types

A class describes state and operations; an object is an instance with its own state. In C++, the existing class is the base and the new class is the derived class. Java and Python often say superclass and subclass. These pairs describe the same direction of specialization, but their syntax and lookup rules differ. A StudentTicket is a kind of Ticket; a Ticket is not necessarily a StudentTicket. Draw the generalization arrow from the specific class towards the general class, not towards an individual object.

Suppose every ticket has a fare and can report that fare. A student ticket also stores a booking fee. Reusing the ticket's public fare operation avoids copying the fare representation into another class. It also keeps updates to that representation inside Ticket. A derived class is not a textual paste of the base definition. In C++, a complete derived object includes a base subobject, and language rules determine which members a particular expression can access.

What belongs in the base

Put properties shared by every valid subtype in the base contract. A contract includes what an operation promises, which inputs it accepts, and what remains true after it runs. If Ticket promises a nonnegative fare, StudentTicket should preserve that promise. Making inheritance compile does not establish a sound model. A subtype that rejects ordinary inputs accepted by the base can surprise a client even when every method has the expected name.

The useful question is whether existing base-class clients can use a derived object without learning special exceptions. This is substitutability. For example, a reporting function that reads Ticket::fare can read the base part of a StudentTicket. It will not automatically know about a separate total operation. This distinction prevents a common mistake: inheriting a class does not cause every base method to acquire the derived class's new meaning. Dynamic dispatch is a separate mechanism developed in Unit 4.

Keep the fare field private and expose a suitable public operation. StudentTicket need not know how Ticket stores that value. A protected field would permit direct derived-class access, but also tie derived implementations to the storage choice. Start with a narrow interface. Widen access only when a concrete design requires it. Inherited private state still exists inside the base subobject even though derived member functions cannot directly name that state.

Reading the C++ declaration

The declaration class StudentTicket : public Ticket names Ticket as a public base. Public inheritance permits an accessible conversion from a StudentTicket reference to a Ticket reference. The constructor initializer Ticket(f) chooses how to initialize the base part; it is not an ordinary assignment performed after construction. The booking fee belongs to StudentTicket and is initialized separately. Unit 2 explains ordinary constructors, while Chapter 3.4 extends their ordering rules across a hierarchy.

In the example, show receives a const Ticket reference. Reference passing preserves the original object instead of making a separate base value. Copying a derived object into a base object would retain only the base value, a problem called slicing when derived information matters. We avoid both slicing and dynamic allocation here so the relationship is visible without extra lifetime machinery. The base does not need a virtual destructor for these automatic objects; deleting through a base pointer is a separate issue.

A different relationship needs a different design. A Booking has a Ticket, but a Booking is not itself a Ticket. Store a ticket as a member when containment is the intended model. Chapter 3.9 distinguishes ownership from merely referring to an existing object. Code reuse alone cannot decide between these relationships; the meanings of the objects and the promises made to callers must decide.

Worked example

Use C++17 to create a student ticket with a fare of ₹120 and a booking fee of ₹15. Print the fare through a function accepting a base reference, then print the student's total. Save this complete program as basics.cpp. The total is fare plus fee, so 120 + 15 = ₹135. The reference call reads ₹120 because the base contract reports fare, not the extra fee.

#include <iostream>
class Ticket {
    int fare_;
public:
    explicit Ticket(int f) : fare_(f) {}
    int fare() const { return fare_; }
};
class StudentTicket : public Ticket {
    int fee_;
public:
    StudentTicket(int f, int fee) : Ticket(f), fee_(fee) {}
    int total() const { return fare() + fee_; }
};
void show(const Ticket& t) { std::cout << t.fare() << '\n'; }
int main() {
    StudentTicket t(120, 15);
    show(t);
    std::cout << t.total() << '\n';
}

3.2 Types of inheritance: single, multiple, multilevel, hierarchical, hybrid

Inheritance structures are classified by the shape of the class graph. The classification helps you predict how many base parts exist, where a name may come from, and which language rules you must check before writing a call.

Five graph shapes

Single inheritance means a class has one direct base. For example, StudentTicket derives directly from Ticket. Multilevel inheritance forms a chain: ElectricBus derives from Bus, and Bus derives from Vehicle. ElectricBus has one direct base and an indirect Vehicle base. Do not count the number of levels as the number of direct parents. A long chain can still use single inheritance at every step.

Hierarchical inheritance means several classes derive from the same base. Bus and Bicycle can both derive from Vehicle without deriving from each other. Shared ancestry does not imply an automatic conversion from Bus to Bicycle. Their common operations belong to Vehicle; their distinct operations remain with the specific types. A hierarchy should reflect stable common behaviour, rather than grouping classes only because they happen to store similarly named fields.

Multiple inheritance means one class has more than one direct base. A multifunction device may inherit a Scanner capability and a Printer capability. Both base parts belong to the device. This graph is not multilevel simply because several class names appear in its declaration. Count the immediate edges leaving the derived class. If there are two direct bases, it is multiple inheritance regardless of the depth above those bases.

Hybrid inheritance combines shapes. A diamond occurs when two direct bases share an ancestor: Device derives from Scanner and Printer, and both derive from Machine. The word hybrid is a descriptive syllabus category, not a separate C++ keyword. Whether the final object has one shared Machine base or two separate Machine bases depends on virtual inheritance. A drawing alone is insufficient unless its edge annotations also specify the language semantics.

Language boundaries

C++ supports multiple class inheritance. Python also supports several base classes, but resolves attribute lookup using a method resolution order rather than copying C++ base-subobject rules. Java classes extend at most one class while they may implement several interfaces. Therefore a Java class implementing Printable and Scannable has several capability contracts without multiple inheritance of class instance state. State the language before claiming that multiple inheritance is supported or forbidden.

The same conceptual diagram can require different implementations in different languages. A C++ device may contain two base subobjects; a Java device may store helper objects and implement interfaces; a Python device may use cooperative methods through super(). These alternatives do not produce identical initialization or name-lookup behaviour. Chapters 3.6 and 3.7 explain the distinctions needed to reason about diamonds and contracts without mixing language rules.

Trace the object, then the operation

Start an exam answer by drawing class names and directed generalization edges. Next list the direct bases of the final type. Then identify any repeated ancestor and decide whether the question specifies shared or separate state. Finally trace the particular method call, including qualification when two bases provide the same name. This sequence separates graph classification, object structure, and lookup into three manageable questions.

Our example has no repeated ancestor. Scanner stores a count of pages already scanned; Printer stores a count already printed. Device adds their public counts through a jobs operation. Three scanned pages plus five printed pages give eight operations. This is an operation count, not necessarily eight distinct physical sheets: the same sheet might have been scanned and printed. Naming the quantity prevents a mathematically correct sum from carrying a misleading interpretation.

Avoid building deep hierarchies merely to reuse small methods. Each extra level adds inherited assumptions and makes the complete object's behaviour harder to inspect. Independent helper objects may express a device's components more clearly. Nevertheless, multiple inheritance of small, clearly separated capabilities can be useful. The design question is whether inherited contracts remain understandable, not whether a particular graph shape is always good or always bad.

Worked example

Write a C++17 Device with Scanner and Printer as direct bases. Initialize the scan count to 3 and the print count to 5, then calculate the total number of operations. Save as shapes.cpp. The initializer list constructs both base parts, and jobs reads them through distinct accessors, so there is no competing name to resolve.

#include <iostream>
class Scanner {
    int scanned_;
public:
    explicit Scanner(int n) : scanned_(n) {}
    int scanned() const { return scanned_; }
};
class Printer {
    int printed_;
public:
    explicit Printer(int n) : printed_(n) {}
    int printed() const { return printed_; }
};
class Device : public Scanner, public Printer {
public:
    Device(int s, int p) : Scanner(s), Printer(p) {}
    int jobs() const { return scanned() + printed(); }
};
int main() {
    Device d(3, 5);
    std::cout << d.jobs() << '\n';
}

3.3 Public, private and protected inheritance

C++ inheritance access controls how a derived class exposes its base relationship. It is separate from the public, protected and private labels that control access to individual members. Answer visibility questions by considering both layers and the location of the caller.

Two independent decisions

A member access specifier belongs inside a class definition. A public member is available to ordinary callers who can name the object and operation; a protected member is restricted to the class, its friends, and eligible derived-class contexts; a private member is restricted to the declaring class and its friends. Inheritance access appears after the colon in a derived declaration. It controls the accessibility of inherited public and protected members through that derivation, and access to the derived-to-base conversion.

For public inheritance, a base public member remains public through the derived class, while a base protected member remains protected. For protected inheritance, both become protected. For private inheritance, both become private through that derivation. A private base member does not become accessible to derived member functions in any of these cases. It remains part of the base object's state and can still be manipulated by the base's own methods.

Read the matrix by selecting the original base-member category first, then the inheritance mode. For a public member: public derivation exposes it publicly, protected derivation restricts it to protected access, and private derivation restricts it to private access. For a protected member: public and protected derivation preserve protected accessibility, while private derivation makes it private through that path. For a private member: derived code has no direct access under any mode. This final row is the most common exam trap.

Who is asking for access?

Access is checked where an expression appears. Inside Savings, a call to the protected Account::bonus operation can be valid. The same call from main through a Savings object is invalid. This difference is not a runtime permission test or a changing object property; it is a compile-time language rule based on the declaration and the expression's context. Changing the object's numeric balance cannot make an inaccessible expression legal.

Protected access also has an object-expression restriction in C++. A derived class cannot use its derived-class privilege to access a protected base member through any arbitrary base object. Access through its own derived object is a different case. For introductory problems, trace whether the operation is on this object and avoid treating protected as a universal permission for every object of the base type. Friendship and more complicated inheritance paths add further cases, so do not generalize beyond the declaration shown.

With public inheritance, ordinary client code can bind an accessible, unambiguous base reference to a derived object. With private inheritance, the conversion is accessible within suitable member or friend contexts but not generally to external callers. Consequently private inheritance is not the usual way to advertise an is-a relationship to clients. It is sometimes used for implementation reuse when an ordinary contained helper cannot provide the required relationship.

Designing a narrow public surface

In the example, Account keeps the principal private and offers a protected bonus operation. Savings exposes only total. The bonus is a fixed ₹20 teaching value, not an interest rate or a banking product rule. External code does not need to see bonus merely because Savings uses it. The base accessor principal() is public and remains public under public derivation, while the raw principal field stays inaccessible to Savings itself.

A derived class can introduce its own public wrapper for an allowed inherited operation. That does not make every underlying member public. C++ also supports using-declarations in suitable access sections to expose selected accessible base names. Such a declaration cannot grant access to a private base member that the derived class cannot access in the first place. A deliberately small interface is easier to maintain than publishing every inherited helper.

Defaults deserve attention when a question omits an inheritance keyword. A class declaration uses private inheritance by default; a struct declaration uses public inheritance by default. This rule concerns the base list, while class and struct also have corresponding default member access rules inside their bodies. Write the keyword explicitly in teaching code. Java does not offer these three inheritance modes, and Python's underscore naming conventions do not implement the C++ matrix.

Worked example

In C++17, create Savings with a principal of ₹500. Its total adds a protected fixed bonus of ₹20. Save as access.cpp. Predict the output, then identify which expression would fail if main attempted s.bonus(). The valid arithmetic is 500 + 20 = ₹520; the forbidden call is an access error, not a different numeric result.

3.4 Constructors and destructors in derived classes

A derived object must establish its base and member subobjects before its constructor body can use them. Destruction unwinds that structure in reverse. These rules let resource-owning members remain valid for the portions of construction and destruction that depend on them.

Construction has a fixed order

For a complete C++ object, virtual bases are initialized first according to the language's traversal order. Direct nonvirtual bases follow in their base-list order. Nonstatic data members follow in declaration order inside the class. Only then does the derived constructor body run. The textual order of entries in a constructor initializer list does not change these rules. Write the list in actual construction order so readers do not have to mentally repair a misleading sequence.

If Base requires an integer constructor argument, Derived must supply a suitable argument through its initializer list unless another supported initialization arrangement provides it. Omitting an initializer normally asks for default initialization of the base. If no accessible appropriate default constructor exists, compilation fails. Calling a base constructor by name inside the derived constructor body would not initialize the already constructed base subobject; initialization must occur before that body begins.

Nonstatic data members have similar requirements. A reference member must be initialized to refer to an object, and a const member generally needs appropriate initialization rather than later assignment. If one member's initializer reads another member, the dependency must respect declaration order. For example, a buffer size should be established before a buffer initializer that uses it. Reordering the initializer-list text alone cannot fix a declaration-order dependency.

Destruction reverses the completed structure

For an ordinary successful construction, destruction starts with the derived destructor body. Then the members are destroyed in reverse declaration order, followed by direct bases in reverse construction order. Virtual bases of the most-derived object are destroyed after the other relevant subobjects. In the small example, Derived's body runs first, then its Member object is destroyed, then Base. This is why a derived destructor body can still rely on its member and base subobjects being present during that body.

An automatic object is destroyed when its enclosing scope ends normally, and also during applicable exception unwinding. The exact moment is a lifetime rule, not a garbage-collection guess. Owning resources through members whose destructors release them is called resource acquisition is initialization, or RAII. A file wrapper can close its file; a vector can release its allocation. The derived class then does not need to manually reproduce every member's cleanup logic.

If construction throws before completing the most-derived object, already constructed subobjects are cleaned up, but the destructor of the incomplete most-derived object does not run. This detail explains why acquiring a resource directly into a raw pointer and then throwing can leak it unless another completed owner manages that resource. Unit 5 develops exceptions; here the important habit is to tie resources to completed owning subobjects as early as possible.

Predict a trace before executing it

Mark the full object boundary, list its bases, list its members, and finally write its constructor body. For destruction, reverse the structural list while putting the derived destructor body first. Distinguish constructor output from an ordinary member-function call: both may print text, but only the former establishes a new object's lifetime. A local nested block in main makes the ending point unambiguous in an exam trace.

Virtual dispatch during construction or destruction also has special restrictions: a call does not behave as though a not-yet-constructed or already-destroyed more-derived part were available. Avoid calling overridable behaviour to establish essential invariants. Unit 4 covers virtual functions and virtual destructors in detail. In particular, deleting a derived object through a base pointer requires a suitable virtual base destructor for the ordinary polymorphic deletion case; inheritance alone does not provide one.

These C++ rules should not be copied into Java or Python answers. Java constructors can chain to superclass construction, but garbage collection is not the reverse-order deterministic destructor mechanism described here. Python context managers are the appropriate tool for predictable resource cleanup in many programs; relying on the timing of object finalization is a different matter. First identify the language, then identify the lifetime event.

3.5 Method overriding and the super keyword

Overriding supplies a specialized implementation of an inherited operation. A call through the general interface can then use the specialized behaviour. Python super() helps an overriding method extend the next implementation in the method resolution order without hard-coding a parent class name.

Replacing versus extending behaviour

An inherited method can already be called on a derived object when lookup finds it in a base. An overriding method is a new implementation of the same operation in the subclass. It can replace the inherited work entirely or perform additional work before or after delegating. For a fare calculation, a subclass might reuse the base fare and add a booking charge. Extending the calculation is different from defining an unrelated method with a new name.

Keep the operation's contract compatible with callers. If a base method accepts a distance in kilometres, a subclass should not silently reinterpret the same parameter as metres. If the base promises an integer number of rupees, returning a message string would surprise clients. Dynamic lookup makes the replacement possible; it does not prove that the replacement respects the contract. Explain both the lookup rule and the meaning of the result in a good exam answer.

In the Python example, Ticket.fare computes five rupees per kilometre. BookedTicket.fare calls super().fare(km) and adds a fee of twelve rupees. A client only needs to call fare with a distance. The object determines which implementation lookup finds first. The base calculation remains available without copying its formula, so changing the basic per-kilometre calculation need not require editing the subclass's arithmetic.

What super actually means

Inside an ordinary Python instance method, zero-argument super() uses the class context of that method together with its first argument, conventionally self. It searches after that class in the actual object's method resolution order. In a simple single-inheritance chain, this looks like calling the immediate parent. In a multiple-inheritance hierarchy, the next class may be a sibling reached through the shared resolution order. Chapter 3.6 gives a concrete cooperative diamond.

super() returns a proxy for lookup; it does not create a separate parent object. A delegated method still operates on the same self. If that method reads an instance attribute, it reads the current object's attribute under the language's attribute-lookup rules. Explicitly calling Ticket.fare(self, km) selects that particular implementation, whereas super().fare(km) participates in cooperative lookup. Use the latter when the hierarchy is deliberately designed for cooperation.

An overriding method that calls self.fare(km) to obtain its base result usually calls itself again. Without a terminating change, that recursion eventually fails instead of reaching the base operation. The fix is not to change the object's type temporarily; select the intended delegated implementation. Also remember to return the delegated result when the contract requires a value. Printing a value and returning a value are distinct operations in Python.

Compare language-specific rules

Java uses super.method(...) to select superclass behaviour and super(...) for constructor chaining under its constructor rules. Java's super is not Python's C3-based cooperative proxy. Java instance-method overriding is also subject to signature, accessibility and return-type rules; static methods are hidden rather than dynamically overridden. Use the Override annotation to ask the compiler to check an intended override. Constructor syntax and ordinary method delegation should be described separately.

C++ overrides require an inherited virtual function with an appropriate matching declaration. Writing override on the derived declaration asks the compiler to diagnose mismatches. A same-named nonvirtual function in a derived class does not create runtime overriding of a base nonvirtual call. C++ has no super keyword: a qualified call such as Base::f() can explicitly invoke the base implementation. Unit 4 treats virtual functions, overload sets and binding in depth.

Overloading is a different concept: several operations share a name but accept different parameter lists under the language's rules. Python does not create Java-style overload sets merely by defining the same method name twice in one class body; the later binding replaces the earlier one. Separate this from overriding across an inheritance relationship. A problem asking for both should include one example of each and explain when selection occurs.

3.6 Virtual base classes and ambiguity resolution

A diamond creates two inheritance paths to a shared ancestor. C++ virtual inheritance can make those paths share one base subobject. Python instead uses a consistent method resolution order for attribute lookup. These mechanisms address different questions and must not be treated as interchangeable.

State duplication and ambiguous names

Let Student and Employee both derive from Person, and let Assistant derive from Student and Employee. With ordinary nonvirtual C++ inheritance, Assistant contains a Person subobject through Student and another through Employee. An identifier stored in Person therefore has two storage locations. Accessing a person member without choosing a path can be ambiguous. Converting Assistant directly to Person can also be ambiguous because there is no unique Person subobject to select.

Qualification chooses a path for a particular expression. If the objects contain two distinct identifiers, a qualified Student path can select one while an Employee path selects the other. This resolves that name-use question but does not merge the storage locations. Do not claim that writing a qualified name repairs duplicated state. It may be exactly right when the two ancestor roles intentionally represent separate identities, but it is wrong when the model requires one shared person.

C++ virtual inheritance changes the object structure. Declaring both Student and Employee to inherit virtually from Person gives Assistant one shared virtual Person base along those virtual paths. The keyword virtual belongs on the inheritance edges that introduce the shared ancestor. Making only the final Assistant derivation virtual does not retroactively turn ordinary Person subobjects inside its bases into a single shared object.

The most-derived constructor owns shared initialization

The constructor of the most-derived class initializes the virtual base. In the example, Student would initialize Person with 10 when a standalone Student is created, and Employee would initialize it with 20 for a standalone Employee. When constructing Assistant, however, Assistant's Person(42) initializer supplies the shared identifier. The Person initializers written in the intermediate constructors do not initialize that virtual base for this complete object.

If Person has no default constructor, the most-derived Assistant must provide a valid initializer. Assuming that Student's initializer will handle it is a common compilation error. Virtual bases are initialized before the relevant nonvirtual bases and members. Chapter 3.4 explains lifetime order; here the key extra question is which constructor is responsible for the one shared base. Count complete objects and base subobjects separately before tracing the calls.

Virtual inheritance also does not automatically choose between two unrelated member functions. If Student and Employee both declare a label method, an unqualified label call may still need resolution even though Person is shared. Provide a final derived operation that expresses the desired behaviour, or qualify the intended base operation. Shared storage and competing operations are independent sources of confusion in a diamond.

Python lookup follows a linear order

Python computes a method resolution order, commonly called the MRO, using C3 linearization. For the simple classes A, B(A), C(A), and D(B, C), the order is D, B, C, A, object. It preserves relevant local ordering constraints while avoiding repeated lookup of a shared ancestor in that linearization. Inspect D.__mro__ when reasoning about a concrete hierarchy. Inconsistent constraints can make class creation fail rather than produce an arbitrary order.

If B's method calls super(), lookup continues after B in D's MRO and reaches C before A. If C also delegates and A supplies the terminating implementation, the cooperative chain can visit D, B, C and A once each for that operation. Every participant must use compatible signatures and cooperate deliberately. Directly calling A from both B and C can execute A's work twice, because explicit calls are not automatically deduplicated.

Do not transfer C++ layout claims to Python. Python's MRO tells you lookup order; it is not a recipe for creating C++-style duplicate base subobjects. Likewise, C++ virtual inheritance does not calculate Python's cooperative method sequence. An exam comparison should identify the actual problem first: duplicate base state, ambiguous C++ names, or the next Python method. Then apply the corresponding mechanism, and show a trace rather than merely naming a keyword.

3.7 Interfaces: defining and implementing them

An interface describes operations a client may rely on without committing that client to one implementation. Different classes can fulfil the same contract. The useful abstraction is a capability, such as quoting a charge, rather than a promise that every implementation stores its data in the same way.

Write the contract before the class

A contract names the operation, its inputs, its result and the conditions that make those results meaningful. A quote operation might accept a nonnegative integer amount in rupees and return the total charge in integer rupees. Merely requiring a method named quote does not enforce this meaning. One implementation could otherwise interpret its input as paise or include a percentage where another includes a fixed fee. State units and assumptions before presenting the implementation.

Clients should ask for the smallest useful capability. A checkout that only needs a quote should not depend on a large bank-account class with unrelated withdrawal, identity and reporting operations. Depending on the capability lets a fixed-fee implementation and a no-fee implementation be used by the same checkout. It also makes tests simpler because a small predictable implementation can exercise the client's decisions without contacting any payment service.

The implementation still owns its algorithm and representation. An interface reference or abstract base reference describes how the client can use an object; it does not change the object's concrete class. The client need not inspect that class name to invoke the required operation. If it repeatedly switches on concrete types, the interface may be missing an operation or the types may not actually share the intended contract.

Three ways to express a capability

In Java, an interface declaration such as interface Charge { int quote(int rupees); } defines an abstract instance operation. A class can declare implements Charge and provide a public quote method. Interface abstract methods are public, so an implementation cannot reduce their accessibility. A class can implement several interfaces while extending only one class. Modern Java interfaces can also contain default and static methods; they are not simply collections of empty declarations.

When two unrelated Java interfaces supply conflicting default implementations, the implementing class may need to override the method and choose its policy explicitly. Interface fields are constants under Java's rules, not per-object mutable instance storage. A default method can provide shared behaviour, but it does not turn the interface into an ordinary superclass with arbitrary instance fields. Avoid the outdated claim that every method in every Java interface must be abstract.

C++ has no dedicated interface keyword. A common convention is an abstract base class with public pure virtual operations and a virtual destructor when objects will be deleted polymorphically. A declaration ending in = 0 makes a virtual operation pure; it does not assign zero to a function pointer. Unit 4 covers abstract classes and virtual destructors. C++ implementation inheritance can also carry state, so the interface convention should be stated rather than assumed.

Python supports ordinary duck typing: a client can call the expected operation on any object that provides suitable behaviour. The abc module offers abstract base classes when explicit incomplete-implementation checks are wanted. Inheriting ABC and marking quote with abstractmethod prevents ordinary instantiation of a subclass that leaves that operation abstract. This check does not prove semantic correctness or validate every possible argument; the contract still needs examples and tests.

Follow one call through an abstraction

Our Python example gives Charge an abstract quote method. FixedFee and NoFee provide concrete implementations. checkout receives a payment object and an amount, then calls quote without testing the object's class. For an amount of ₹200, FixedFee adds ₹3 and returns ₹203, while NoFee returns ₹200. The same client function produces different valid totals according to the supplied policy.

The example assumes a nonnegative integer input. Production code should decide where to validate invalid amounts and how to report failure, then apply that decision consistently across implementations. Do not silently add unrelated checks to one implementation and call it equivalent. If a method may fail, its failure behaviour is part of the contract too. Unit 5 provides the exception-handling tools for making those choices explicit.

Worked example

Save this Python 3.12 example as interfaces.py. Quote the same ₹200 amount using two implementations. No real payment is attempted.

3.8 Packages, modules and member access

Packages and modules organize names and dependencies. They help readers locate code and let programs reuse definitions without placing every name in one global namespace. Organization and access control are related design concerns, but importing a name is not a universal permission to use every implementation detail.

Python files and package names

A Python module is an importable unit with its own namespace; a simple source module is a file such as fares.py. A regular package groups modules and normally includes an __init__.py file. Python also supports namespace packages without that file, but the regular-package layout is easier for this first example. If farepkg contains fares.py, the dotted name farepkg.fares identifies that module through its package context.

An import statement first finds or loads a module as needed, then binds names in the importing scope. With import farepkg.fares, code can use farepkg.fares.total. With from farepkg.fares import total, the local name total refers to the imported function. The second form does not copy the function's source into the caller and does not merge both module namespaces. Choose the form that keeps the origin of a name clear to a reader.

For ordinary imports in one interpreter process, loaded modules are cached in sys.modules, so importing the same module again does not normally rerun its top-level code. Deliberate reloading and unusual import arrangements are separate cases. Because the first import can execute top-level statements, avoid placing user prompts, network actions or lengthy computations there. Definitions and small configuration declarations make imports more predictable.

Run from a known package context

The worked layout contains run_fare.py beside a farepkg directory. That directory contains an empty __init__.py and fares.py. Run python3 run_fare.py from the directory containing the script. Python can then locate the adjacent regular package through its normal script search path. A file named like a standard library module can accidentally shadow that module, so select descriptive project-specific names instead of names such as json.py for unrelated code.

Inside a package, a relative import such as from .fares import total refers to a sibling module in that package. Relative imports depend on package context; directly executing a file nested inside the package is not always equivalent to running it as a module. For executable package modules, python3 -m package.module establishes the intended package context. State both the directory and the command when documenting a multi-file example.

A single leading underscore marks an internal Python name by convention. It does not prevent a determined caller from accessing that attribute. The optional __all__ declaration influences wildcard imports; it is not an access-control firewall. Double-leading-underscore names inside a class can be name-mangled to reduce accidental clashes, but that mechanism also is not security. Prefer explicit imports and a documented small public surface.

Java packages and module boundaries

Java uses package declarations to place types in named packages and imports to simplify references to accessible types. Public top-level classes can be referenced from other packages when the relevant visibility and module conditions are satisfied. A top-level class without public has package access. Private and protected are not ordinary access choices for top-level classes; they apply to members and certain nested declarations under Java's rules.

For Java members, public is broadly accessible, private is restricted to the enclosing top-level class context including its nested classes, and the absence of an access modifier gives package access. Protected permits same-package access and certain subclass access outside the package. In that outside-package subclass case, the qualifying reference is restricted; inheritance does not grant access through every arbitrary superclass instance. This resembles a common C++ exam trap but must be answered using Java's own rules.

Java's named module system adds dependencies and exports above the package level. A module declaration can require another module, and a module can export a package to make its accessible public API available under module-system rules. A Java module is therefore not simply another spelling of a Python source file. C++ namespaces and C++20 modules are also distinct mechanisms, not Java packages with alternate punctuation.

Separate naming from design

Splitting a program into many files does not automatically make its dependencies healthy. Put a cohesive responsibility in each module, keep imports directed where possible, and avoid cycles that depend on partially initialized state. For the fare example, the calculation module need not import the caller. The caller owns presentation, while the module supplies arithmetic. That one-way dependency makes the code reusable in a terminal program or another client.

3.9 Aggregation and composition

Aggregation and composition describe whole–part relationships instead of specialization. Both are forms of having or using another object. Composition expresses strong ownership of a part; aggregation describes a weaker association whose parts have an independent existence. The lifetime policy matters more than the spelling of a field.

Ask who owns the part

An Order owns its line items. A line records a quantity and a unit price for that order; removing the owning order should release its line-item storage. This is a natural composition relationship. A Customer, however, can exist before an order, place several orders and continue to exist after one order disappears. If an order merely refers to that separately managed customer, the relationship does not make the order responsible for destroying the customer.

UML draws a filled diamond at the whole end for composition and an open diamond at the whole end for shared aggregation. The diamond belongs at the owning or grouping object, not at the part. A generalization arrow for inheritance is a different symbol with a different meaning. An Order is not a Customer, and a Line is not an Order. Replacing a has-a association with public inheritance would make incorrect substitutability claims.

Shared aggregation's exact practical meaning varies between modelling conventions, so explain ownership in words as well as drawing the open diamond. A plain association can often communicate the same weak connection more clearly. For composition, say whether a part may be transferred, whether it can exist independently during transfer, and who finally destroys it. The central promise is a controlled ownership relationship, not an absolute rule that every part must be born at the same instant as its whole.

Express lifetime through C++ types

A value member naturally belongs to its containing object's lifetime. A vector of Line values owns its elements and releases their storage when the vector is destroyed. An owning smart pointer such as unique_ptr can also express exclusive ownership of a separately allocated part. Therefore composition does not require physically embedding every part's bytes directly in the whole. What matters is responsibility for the lifetime, even when storage is indirect.

A reference or non-owning pointer can express access to an independently owned object, but it creates a lifetime obligation. The referred object must remain alive for every use of that reference or pointer. In the example, Customer is created before Order and destroyed after it because local variables are destroyed in reverse construction order. The nested scope makes the order's shorter lifetime visible. A reference does not automatically prolong the customer object's lifetime in arbitrary arrangements.

A raw pointer by itself does not prove ownership. Some APIs use raw pointers for borrowing, and older code may use them for owning allocations. Read the class contract and cleanup behaviour. Likewise, shared_ptr provides shared ownership of a managed object; that does not automatically mean UML shared aggregation. Language memory-management tools and modelling relationships overlap, but their names are not interchangeable definitions.

Compare reuse choices

Inheritance reuses or specializes a base contract. Composition reuses a contained component by delegating operations to it. An Order delegates storage management to vector and asks each Line for its contribution to the total. It does not need to inherit from vector, because an order is not a general-purpose collection with every vector operation exposed to callers. This restriction helps maintain the rule that order lines are controlled through the order's API.

When choosing between designs, ask whether outside code must treat the whole as the part's type. If not, a member is usually the clearer starting point. Then ask who may replace the component and what happens when the whole is copied or moved. Value members copy their values under their copy semantics, while references continue to refer to an external object. Unit 2 introduces copy behaviour; ownership analysis explains why a shallow copy can be correct for a borrowed customer but wrong for a uniquely owned raw allocation.

Compute with the relationship in view

Each line contributes quantity multiplied by unit price. In the example, two notebooks at ₹30 contribute ₹60, and one pen set at ₹80 contributes ₹80. The total is ₹140. Customer identity is not part of this arithmetic, but the borrowed reference lets the order report whose purchase it represents. Keeping these responsibilities separate makes it easier to change customer details without rewriting price calculations.

The example uses positive integers and a small total that fits int. Real billing must define invalid quantities, rounding, taxes and overflow handling; those policies belong in a complete monetary contract. Do not mistake a teaching total for a production payment system. The ownership lesson remains the same: destroying Order releases its line values while leaving the independently owned Customer available for later use.

Analyze and evaluate

Compare C++ virtual inheritance and Python cooperative super in a diamond. 12 marks

Identify two separate questions: sharing an ancestor subobject in C++, and selecting the next method in Python. Show one shared Person through virtual edges and most-derived initialization. For D(B,C) with B(A) and C(A), write D, B, C, A, object. Explain how super in B reaches C on a D instance, and why hard-coded calls can duplicate work. Do not describe Python MRO as C++ memory layout.

Design an order with owned lines and an independently owned customer. 12 marks

Use composition for line values and a documented borrowed association for the customer. Draw a filled diamond at Order for lines and explain the weaker customer relation. Trace an order nested inside the customer scope. Compute three ₹25 items plus two ₹40 items as ₹155. Explain dangling-reference risk, why raw pointer spelling is insufficient to establish ownership, and why Order should not publicly inherit Customer.

Combine interface design with package boundaries for two charge policies. 12 marks

Specify quote(integer rupees) returning integer rupees. Place the stable capability and policy implementations in clear modules, and let the client depend on the operation rather than class-name tests. Use explicit imports without claiming imports bypass access restrictions. Compare fixed-fee and no-fee results for the same amount. Include contract tests for units and return types, and discuss how exposing internal constants would couple clients to implementation details.

Evaluate a design that uses private inheritance only to reuse storage. 12 marks

State that private inheritance restricts public base conversions and does not advertise ordinary public substitutability. Compare it with containing a storage helper and forwarding selected operations. Identify which base features truly require inheritance and which can be delegated. Discuss lifetime order, encapsulation and copy semantics. Prefer the design whose invariants and ownership can be stated clearly rather than asserting that either technique is always correct.

Glossary

Aggregation
A weak whole–part association with independently existing parts; state the exact ownership policy.
Base subobject
The part of a C++ derived object corresponding to a base class.
Composition
A strong ownership relationship in which a whole controls a part’s lifetime.
Contract
The inputs, outputs, invariants and failure promises that clients may rely on.
Cooperative method
A method designed to delegate along a shared method resolution order.
Delegation
Asking another implementation or contained object to perform work.
Diamond
Two inheritance paths from a derived class to a repeated ancestor.
Direct base
A class explicitly listed as an immediate base.
Encapsulation
Controlling access to representation through a defined interface.
Generalization
The modelling relationship from a specialized type to a more general type.
Interface
A capability contract that different implementations may fulfil.
Invariant
A condition that valid objects must preserve at the boundaries promised by their contract.
MRO
The ordered sequence Python uses for class-based attribute lookup.
Module
An organizational and import unit whose exact meaning depends on the language.
Name hiding
A declaration makes another same-named declaration unavailable through ordinary lookup in a context.
Namespace
A scope or mapping that associates names with declarations or objects.
Override
A specialized implementation of an inherited operation under the language’s overriding rules.
Package
A grouping and naming mechanism for code; Python and Java apply different rules.
Polymorphism
Using a common interface with behaviour selected according to the participating type or object.
RAII
C++ resource management that ties resource release to the lifetime of an owning object.
Slicing
Copying a derived value into a base value and losing the additional derived portion.
Substitutability
The ability to use a subtype where a base contract is expected without breaking that contract.
Virtual base
A C++ base shared along virtual inheritance paths within a complete object.
Borrowing
Access to an object without assuming responsibility for its lifetime.
