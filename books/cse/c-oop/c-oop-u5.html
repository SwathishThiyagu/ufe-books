5.1 Function templates and template overloading

A function template is a recipe for a whole family of functions. You write the logic once with a type name such as T standing in for the real type, and the C++ compiler writes the real int, double or char version for each call, before the program ever runs. Templates exist because the same steps (find the larger value, swap two values, add up an array) work for many types, and copying a function once per type copies its bugs too. You already use them: std::max, std::swap and std::sort are all function templates.

You need: function overloading (Unit 4, Function and method overloading) and how a C++ function is declared and called.

Writing a function template

Here is a template, in C++, that returns the larger of two values:

template <typename T>
T maxOf(T a, T b) {
    return (a > b) ? a : b;
}

The first line is the template header. T is a template type parameter: a name that stands for "some type, chosen later". The keywords typename and class mean exactly the same thing inside the angle brackets, so template <class T> is the same header. The body must work for every type you use; this one needs >.

The type you supply is the template argument. In maxOf<double>(3, 4.5) the parameter is T and the argument is double. A template can have several parameters (template <typename T, typename U>) and also non-type parameters, which are compile-time constants: with template <int N> int times(int x) { return N * x; }, the call times<3>(7) returns 21.

template <typename T>
void swapValues(T& a, T& b) { T temp = a; a = b; b = temp; }

int x = 3, y = 8;
swapValues(x, y);          // now x = 8, y = 3 (T = int)

How the compiler turns a template into functions

Making a real function from a template is called instantiation. It happens at compile time, in four steps:

  1. The compiler meets a call such as maxOf(7, 12).
  2. Template argument deduction: it matches each argument type against the parameter list. 7 is an int, so T = int; 12 is also an int, so the two agree.
  3. It writes int maxOf(int a, int b) by putting int wherever T appears, and compiles that like hand-written code.
  4. Every later call with two ints reuses this one instance. A call with two doubles makes a second instance.

A template that is never called produces no machine code. And deduction never converts types. In maxOf(3, 4.5) the first argument says T = int and the second says T = double, so GCC stops with "deduced conflicting types for parameter 'T' ('int' and 'double')". Name the type yourself, maxOf<double>(3, 4.5), and 3 is converted to 3.0 as for any ordinary call; the result is 4.5.

Because the compiler needs the body to instantiate it, a template's full definition goes in the header file that callers include, not in a separate .cpp file.

Overloading function templates

A template name can be overloaded in two ways: by another template with a different parameter list, such as a three-argument maxOf(T, T, T), or by an ordinary (non-template) function with the same name. When a call could match several of them, the compiler decides like this:

  1. Collect candidates: every ordinary function with that name, plus one instance from each template whose deduction succeeds.
  2. Rank them by the usual overloading rules: an exact match beats a promotion, which beats a conversion.
  3. If an ordinary function and a template instance match equally well, the ordinary function wins.
  4. If two template instances tie, the more specialised template wins (one taking T* beats one taking T for a pointer argument).

Why would you overload at all? Take string literals. maxOf("apple", "mango") on the plain template deduces T = const char*, and a > b then compares two memory addresses, not two words. An ordinary overload that calls strcmp fixes it, and rule 3 guarantees it is chosen. A third tool, explicit specialisation (template <> const char* maxOf<const char*>(const char* a, const char* b)), gives the same template a separate body for one type; it is not overloading, because no new function name or parameter list is added.

Exam traps

  • maxOf(3, 4.5) is a compile error, not 4.5. Deduction never converts; write maxOf<double>(3, 4.5) or pass 3.0.
  • The plain template on two string literals compares addresses, so the "larger" word can come out wrong. Overload or specialise for const char*, or use std::string.
  • "Difference between typename and class in a template header?" None: both declare a type parameter.

5.2 Class templates

A class template is a blueprint for a family of classes. You write a Stack, Queue or Pair once with a type parameter T, and the C++ compiler builds Stack<int>, Stack<double> and Stack<string> as separate classes when your code uses them. Class templates give you type-safe data structures without writing one class per type.

You need: 5.1 Function templates and constructors (Unit 2, Constructors).

Defining and using a class template

The header is the same as for a function template; it is placed before the class:

template <typename K, typename V>
class Pair {
public:
    K key;
    V value;
    Pair(K k, V v) : key(k), value(v) {}
    void show() const { cout << key << " = " << value << "\n"; }
};

Pair<string, int> p("MAS", 3);    // K = string, V = int
p.show();                          // prints: MAS = 3

Pair on its own is not a type; it is a template. Pair<string, int> is a type, a real class the compiler generated. Inside the class body you may write plain Pair to mean "this instance". Unlike a function call, a declaration usually has no arguments to deduce types from, so you write the template arguments in angle brackets.

Member functions defined outside the class

Long member functions are often written after the class. Each such definition must repeat the template header and name the class with its parameters:

template <typename T, int N>
bool Stack<T, N>::push(const T& x) { ... }

Read it as: "for any T and N, here is push of the class Stack<T, N>". Writing Stack::push is an error, because Stack alone names no class. Member functions are instantiated only when called, so a Stack of a type that cannot be printed still compiles as long as you never call a member function that prints.

Default arguments, non-type parameters and specialisation

  • Default template arguments: with template <typename T, int N = 4>, writing Stack<int> means Stack<int, 4>.
  • Non-type parameters such as N must be compile-time constants. int n = 4; Stack<int, n> s; fails because n is a variable.
  • Full specialisation: template <> class Stack<bool, 8> { ... }; supplies a completely different class for one argument list, for example one that packs 8 flags into a single byte. The standard library does this with std::vector<bool>.
  • Partial specialisation fixes only part of the arguments, for example template <typename T, int N> class Stack<T*, N> for all pointer types. Function templates cannot be partially specialised; class templates can.
  • Static members: each instance has its own copy, so Stack<int>::count and Stack<char>::count are two separate variables.

Why use a template instead of an ordinary class

There are three ways to get a stack for many types:

    T data[N];

public:
    Stack() : top(-1) {}
    bool push(const T& x);
    T pop()          { return data[top--]; }
    T peek() const   { return data[top]; }

};

5.3 Generics in Java

Generics let a Java class, interface or method take a type parameter, so the compiler can check that a List<String> holds only strings and that nothing needs a cast when you read from it. They arrived in Java 5 and the whole Collections Framework (ArrayList<E>, HashMap<K, V>) is built on them. The aim is the same as C++ templates; the mechanism is different: Java checks the types and then erases them, keeping one compiled class.

You need: 5.2 Class templates for the idea, and interfaces (Unit 3, Interfaces).

Generic classes and generic methods

class Box<T> {
    private T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}

Box<Integer> a = new Box<>(25);   // diamond <> lets javac infer Integer
int n = a.get();                  // no cast; unboxing gives 25

By convention type parameters are single capital letters: T type, E element, K key, V value. The empty <> on the right is the diamond operator (Java 7), which copies the type argument from the left side. Before generics a collection stored Object, every read needed a cast, and a wrong cast failed at run time with ClassCastException. Generics move that failure to compile time. Writing Box b = new Box(5); without a type argument creates a raw type: it compiles with a warning and loses all checking.

A generic method declares its own type parameter just before the return type, and the compiler infers it at each call:

static <T> void swap(T[] a, int i, int j) { T t = a[i]; a[i] = a[j]; a[j] = t; }

Bounded types and wildcards

A bounded type parameter restricts what T may be. In <T extends Number>, T must be Number or a subclass such as Integer or Double, and inside the method you may call Number methods like doubleValue(). The keyword is extends even for interfaces: <T extends Comparable<T>> means "T can be compared with another T".

One rule surprises everyone: List<Integer> is not a subtype of List<Number>, even though Integer is a subtype of Number. Generics are invariant. If the assignment were allowed, you could add a Double through the List<Number> view, and a later int x = ints.get(0) would break. Arrays are covariant (an Integer[] is a Number[]), and they pay for it with ArrayStoreException at run time. Wildcards give back flexibility safely:

  • List<?>: a list of some unknown type; you can read elements as Object.
  • List<? extends Number> (upper bound): any list of Number or a subclass. You can read a Number; you cannot add, except null.
  • List<? super Integer> (lower bound): a list of Integer, Number or Object. You can add an Integer; reads come back as Object.

Joshua Bloch's rule of thumb, "producer extends, consumer super" (PECS), says which to use: a list you only read from produces values, so use extends.

Type erasure and the restrictions it causes

The Java compiler checks every generic use, then erases the type parameters: T becomes its bound (Object, or Number for <T extends Number>), and casts are inserted where values come out. The JVM sees one ordinary Box class. Old pre-generics code keeps running, but no type argument exists at run time. Each of these is a compile error (checked with javac 21):.

  • No primitive type arguments: List<int> fails; use List<Integer> and let autoboxing convert.
  • No new T() and no new T[5] ("generic array creation"): the type to build is unknown at run time.
  • No static field of type T: one static variable is shared by Box<Integer> and Box<String>, so it cannot have both types.
  • No obj instanceof List<Integer>: at run time it is only a List.
  • A generic class cannot extend Throwable, because catch needs the exact type at run time.
  • f(List<String>) and f(List<Integer>) cannot both exist: "name clash ... have the same erasure".

Worked example

Question (8 marks). Write (a) a generic method that returns the largest element of any array whose type implements Comparable, and (b) a method that totals any list of numbers. Trace them on {42, 17, 93, 8}, {"Chennai", "Agra", "Pune"}, the fares [120, 250, 75] and [99.5, 0.5].

import java.util.*;

public class Gen {
    static <T extends Comparable<T>> T maxOf(T[] a) {
        T best = a[0];
        for (int i = 1; i < a.length; i++)
            if (a[i].compareTo(best) > 0) best = a[i];
        return best;
    }

    static double total(List<? extends Number> xs) {
        double sum = 0;
        for (Number n : xs) sum += n.doubleValue();
        return sum;
    }

    public static void main(String[] args) {
        Integer[] marks = {42, 17, 93, 8};
        String[] cities = {"Chennai", "Agra", "Pune"};
        System.out.println(maxOf(marks));
        System.out.println(maxOf(cities));
        System.out.println(total(List.of(120, 250, 75)));
        System.out.println(total(List.of(99.5, 0.5)));
    }
}

5.4 STL containers: vector, list, map

The Standard Template Library (STL) is the part of the C++ standard library built from templates. It has three pieces: containers that hold data, iterators that walk through them (next chapter), and algorithms such as sort and find that work through iterators. Every container is a class template, so vector<int> and vector<string> come from one source. The three you must know are vector, list and map. Each is a different data structure, so choosing one means choosing which operations are cheap.

You need: 5.2 Class templates; arrays, linked lists and binary search trees from your Data Structures course help.

vector: a growable array

A vector<T> keeps its elements side by side in one block of memory, like an array that can grow. So v[i] takes one step whatever the size: the address is the start plus i times the element size. Adding at the end with push_back is cheap; inserting or erasing in the middle shifts every later element, so it costs time proportional to n, written O(n).

Two numbers describe a vector: size, the elements it holds, and capacity, the room in the current block. When size reaches capacity, the next push_back allocates a bigger block, moves every element across and frees the old one. The new capacity is a multiple of the old (GCC's library doubles it), so the occasional big move averages out to a constant cost per push, called amortised O(1). Moving also means pointers and iterators into the old block become invalid.

Main members: push_back, pop_back, size, capacity, reserve(n), front, back, insert, erase, clear, empty. Element access comes in two forms: v[i] does no checking, while v.at(i) checks and throws std::out_of_range when i ≥ size (see 5.6).

list: a doubly linked list

A list<T> stores each element in its own node, with a pointer to the previous node and one to the next. Nodes can be anywhere in memory. Once you hold an iterator to a position, inserting or erasing there is O(1): only four pointers change, and nothing shifts. The price: there is no [], so reaching the k-th element takes k steps, and each element carries two extra pointers. A list also adds push_front, pop_front, remove(value), reverse and splice, and it has its own l.sort(), because the general std::sort needs to jump to any position.

map: sorted key-value pairs

A map<K, V> stores pairs of a key and a value, with unique keys kept in ascending order. Implementations use a balanced binary search tree (in practice a red-black tree), so find, insert and erase cost O(log n). Iterating visits keys in sorted order. Each element is a pair<const K, V>, read as p.first (key) and p.second (value).

  • m[key] returns the value for key, and if the key is missing it first inserts it with a default value (0 for int).
  • m.find(key) returns an iterator, or m.end() if absent, and never inserts; m.count(key) gives 0 or 1; m.erase(key) removes it.
  • multimap allows repeated keys (and has no []). unordered_map is a hash table: average O(1) look-up and no order.

5.5 Iterators: STL iterators and Python generators

An iterator is an object that points at one element of a collection and knows how to move to the next. Because every STL container hands out iterators with the same operations, one algorithm such as find or sort works on all of them, and the container's insides stay hidden. Python builds its for loop on the same idea, the iterator protocol, and a generator is the easiest way to make a Python iterator: a function that pauses at each yield.

You need: 5.4 STL containers, and Python functions and classes for the second half.

STL iterators

Every container has begin(), an iterator to the first element, and end(), an iterator one position past the last element. Together they mark the half-open range [begin, end): the first is included, the second is not. An empty container has begin() == end(), and the number of elements is end − begin. Three operations drive every loop: *it gives the element, ++it moves forward, and it != v.end() tests for the end. The range-based loop for (int x : v) is shorthand for exactly this loop.

Python iterators

In Python an iterable is any object whose __iter__ method returns an iterator; an iterator has a __next__ method that returns the next value or raises StopIteration when there are none. The built-ins iter(x) and next(it) call these methods. A for loop calls iter once, then next repeatedly, and stops quietly at StopIteration. A hand-written iterator class:

class Countdown:
    def __init__(self, n): self.n = n
    def __iter__(self): return self
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1

print(list(Countdown(3)))      # [3, 2, 1]

Java has the same idea in the Iterator<E> interface, with hasNext() and next(); the for-each loop works on any Iterable.

Generators

Writing a class with __next__ and saved state is tedious. A generator function does it for you: any function that contains yield returns a generator object when called, and its body does not start yet. Each next() runs the body up to the next yield, hands back that value and freezes the function, local variables included. When the body finishes, the generator raises StopIteration. A generator expression is the one-line form: sum(k * k for k in range(1, 5)) gives 1 + 4 + 9 + 16 = 30. Generators are lazy, so (k for k in range(10**9)) uses almost no memory, but they can be walked only once. yield from other hands out every value of another iterable.

5.6 Exception handling: try, catch and throw

An exception is an object a program throws when it meets an error it cannot deal with where it stands: a withdrawal larger than the balance, an index past the end, a file that is not there. throw raises it, try marks the code being watched, and catch handles it somewhere suitable. This keeps the normal logic free of error checks after every line, and unlike a return code, an exception cannot be ignored by accident: if nobody catches it, the program stops. C++, Java and Python all work this way, with small differences in syntax.

You need: functions and the call stack, and inheritance (Unit 3) for the exception class hierarchy.

Why exceptions

The older way to report an error is a special return value: −1, NULL, or a global error number. It has three problems. Callers forget to check it. Every call needs an if after it, which buries the real logic. And some functions have no return value to spare: a constructor returns nothing, and an overloaded + must return the sum. C++ exceptions handle synchronous errors, those caused by the statement being executed, such as bad input or a failed allocation. Asynchronous events such as a keyboard interrupt are outside the mechanism (Python, by contrast, turns Ctrl+C into a KeyboardInterrupt exception), and compile-time errors never reach run time at all.

try, throw and catch in C++

try {
    if (b == 0) throw "division by zero";   // throws a const char*
    cout << a / b;
} catch (const char* msg) {
    cout << "Error: " << msg;
}
  1. The statements inside try run normally.
  2. throw expression creates an exception object. It may be of any type: int, const char* or, best, a class object. Control leaves at once; the rest of the try block is skipped.
  3. If the throw happened inside a called function, that function ends immediately and its local objects are destroyed. This is stack unwinding, followed in detail in 5.7.
  4. The catch blocks after the try are tested in order. The first whose parameter type matches catches the exception. A match is the same type, a base class of the thrown class, or catch (...), which matches anything. No other conversions happen: a thrown int is not caught by catch (double).
  5. When the catch block ends, execution continues after the last catch. It never goes back to the throw point; this is called the termination model.
  6. If no catch matches anywhere up the call chain, std::terminate() ends the program.

Standard exception classes

The header <stdexcept> gives a ready hierarchy. At the top is std::exception with a virtual what() that returns the message. Below it, logic_error covers mistakes the program could have avoided (invalid_argument, out_of_range, length_error) and runtime_error covers problems found only while running (overflow_error, range_error). A failed new throws bad_alloc, and vector::at throws out_of_range. Catch them by constant reference, catch (const std::exception& e): one handler then catches every standard exception, with no copy and with what() giving the real message.

The same idea in Java and Python

Java uses the same keywords: try { ... } catch (ArithmeticException e) { ... } and throw new IllegalArgumentException("bad amount");, but only objects of class Throwable or its subclasses can be thrown (5.8). Python writes try:, except ZeroDivisionError as e: and raise ValueError("bad amount"). One difference matters in exams: Java and Python raise an exception for integer division by zero by themselves, while C++ does not. In C++, 10 / 0 with integers is undefined behaviour, so you must test and throw yourself.

5.7 Multiple catch clauses and exception propagation

One try block can be followed by several catch blocks, one for each kind of error, and exactly one of them runs. If the function where the error happens has no matching handler, the exception propagates: it leaves that function, then its caller, and so on up the call stack until some handler matches, destroying local objects on the way. This lets each error be handled at the level that knows what to do: a low-level function only reports the problem, and the code near the user decides whether to retry, show a message or stop.

You need: 5.6 try, catch and throw and the standard exception classes.

Multiple catch clauses

try {
    process(order);
} catch (const out_of_range& e) {      // most specific first
    ...
} catch (const logic_error& e) {       // its base class
    ...
} catch (const exception& e) {         // base of all standard exceptions
    ...
} catch (...) {                         // anything else, always last
    ...
}

The handlers are tested from top to bottom and the first match wins; the rest are skipped, even if they would also match. So order them from the most derived class to the most general. If logic_error came before out_of_range, every out_of_range would stop at the logic_error handler. In C++ that is legal and g++ only warns ("will be caught by earlier handler"); in Java it is a compile error ("exception NumberFormatException has already been caught"), because a handler that can never run is treated as a mistake.

Java 7 added the multi-catch: catch (IOException | SQLException e) runs the same code for either type. The alternatives must not be related by inheritance, and e cannot be reassigned. Python lists several except clauses, or groups types in a tuple: except (ValueError, TypeError) as e:.

Propagation and stack unwinding

Suppose main calls g, and g calls h, which throws. The search for a handler goes like this:

  1. Look for an enclosing try block in h. If one has a matching catch, handle it there.
  2. If not, h ends at once. Its local objects are destroyed in reverse order of creation, so their destructors run. Removing frames this way is called stack unwinding.
  3. Control arrives in g at the point of the call. If that call sits inside a try block, g's catch clauses are tested; otherwise g unwinds too.
  4. The search continues up to main. If nothing matches there, C++ calls std::terminate(); Java prints the stack trace and ends the thread; Python prints the traceback and exits.

Unwinding is why destructors matter. A file or lock held by a local object is released during unwinding, but memory obtained with new and held only in a raw pointer is not freed, so it leaks. In Java, unchecked exceptions propagate on their own, while checked ones must be declared with throws on every method they pass through (5.8).

Rethrowing and nested try blocks

Sometimes a function should notice an error, do something (log it, undo a half-finished step) and still let a higher level decide. Inside a catch block, a bare throw; rethrows the same exception object, keeping its real type. Writing throw e; instead throws a new copy of e as its declared type: if e is a const exception& holding an out_of_range, the copy is a plain exception and the detail is lost (checked with g++: what() then returns "std::exception"). Java's throw e; and Python's bare raise rethrow the same object.

A related pattern is translation: catch a low-level exception and throw a higher-level one that carries it as its cause, for example raise PaymentError("bad amount") from e in Python or new ServiceException("load failed", e) in Java. A nested try block sits inside another; if the inner catches do not match, the outer ones are tried next, which is the same search as propagation, just within one function.

5.8 Java's throw, throws and finally clauses

Java adds a keyword and a block to the exception tools of the last two chapters. throw raises one exception object; throws, written in a method header, declares the checked exceptions the method may pass on to its caller; and a finally block holds clean-up code that runs whether the try block succeeds, fails or returns early. Java's compiler also enforces a "catch or declare" rule for checked exceptions, which neither C++ nor Python has.

You need: 5.6 and 5.7.

The exception hierarchy: checked and unchecked

Every Java exception is an object of class Throwable or a subclass, as Figure 5.8.1 shows. Error covers problems in the JVM itself, such as OutOfMemoryError and StackOverflowError; programs should not catch these. Exception covers everything a program may handle, and it splits in two:

  • Checked exceptions: Exception and its subclasses outside the RuntimeException branch, for example IOException, FileNotFoundException and InterruptedException. They report conditions outside the program's control, like a missing file, and the compiler checks that they are handled.
  • Unchecked exceptions: RuntimeException and its subclasses (ArithmeticException, NullPointerException, ArrayIndexOutOfBoundsException, IllegalArgumentException, NumberFormatException), plus all Errors. They usually mean a bug, and the compiler does not force you to handle them.

Useful methods on any exception: getMessage() (the message text), toString() (class name and message), printStackTrace() (the call chain) and getCause() (the exception it wraps, if any).

throw and throws

throw is a statement that raises one exception object: throw new IllegalArgumentException("marks out of range: " + m);. throws is part of a method header and names exception classes the method may let escape:

static String firstLine(String path) throws IOException {
    try (BufferedReader br = new BufferedReader(new FileReader(path))) {
        return br.readLine();
    }
}

The catch-or-declare rule: if a method can raise a checked exception, it must either catch it or list it in throws; otherwise javac stops with "unreported exception IOException; must be caught or declared to be thrown". Every caller of firstLine now faces the same choice. Calling it on a missing file throws FileNotFoundException with a message such as "nofile.txt (No such file or directory)". An overriding method may not declare new or broader checked exceptions than the method it overrides.

finally and try-with-resources

A finally block after try (and its catches) runs in every case: when the try ends normally, when an exception is caught, when it is not caught (finally runs, then the exception keeps propagating), and even when the try or catch executes return, break or continue. It is skipped only if the JVM itself stops, for example through System.exit(). Use it to close files and database connections and to release locks. Never return from a finally block: it replaces the try's return value and silently discards any exception.

Java 7's try-with-resources, used in firstLine above, declares the resource in brackets after try; any object implementing AutoCloseable is closed automatically at the end, even after an exception, so no finally is needed. Python has try / except / else / finally, where else runs only if no exception occurred, and with open(...) as f: plays the role of try-with-resources.

Exam traps

  • throw raises; throws declares. Writing throws does not handle anything: it passes the exception to the caller.
  • Only checked exceptions must be caught or declared. Leaving ArithmeticException undeclared compiles; leaving IOException undeclared does not.
  • finally runs even after return; a return inside finally overrides it (try { return 1; } finally { return 2; } returns 2).
  • finally does not run after System.exit(0) inside the try.
  • Do not catch Error or Throwable in ordinary code; you would hide out-of-memory and stack-overflow failures.

5.9 User-defined exception classes

Library exceptions name general failures: runtime_error, IOException, ValueError. An application has failures of its own: insufficient funds, seat not available, OTP expired. A user-defined exception class gives each of these a name, so a caller can catch exactly that case, and fields to carry the details, such as how many rupees are missing. In C++, Java and Python alike you make one by inheriting from the language's exception base class.

You need: 5.6 to 5.8, and virtual functions (Unit 4, Virtual functions and late binding).

In C++

C++ lets you throw any type, but derive your classes from std::exception, usually through runtime_error or logic_error. Then one catch (const std::exception& e) still catches everything, and what(), a virtual function, returns your message. The simplest way is to pass the message to the base constructor and add your own fields:

class PaymentError : public runtime_error {           // base for this module
public:
    explicit PaymentError(const string& msg) : runtime_error(msg) {}
};

class InsufficientFunds : public PaymentError {
    int needed, available;
public:
    InsufficientFunds(int need, int have)
        : PaymentError("insufficient funds"), needed(need), available(have) {}
    int shortfall() const { return needed - available; }
};

If you override what() yourself, match the signature exactly, const char* what() const noexcept override, and return text stored in a member; returning c_str() of a local string hands back a pointer to memory that is already gone. Throw by value (throw InsufficientFunds(900, 700);) and catch by constant reference, most derived class first.

In Java

class InsufficientFundsException extends Exception {      // checked
    private final int shortfall;
    InsufficientFundsException(int needed, int available) {
        super("need Rs " + needed + ", have Rs " + available);
        this.shortfall = needed - available;
    }
    int getShortfall() { return shortfall; }
}

static void pay(int amount) throws InsufficientFundsException {
    if (amount > balance) throw new InsufficientFundsException(amount, balance);
    balance -= amount;
}

Extending Exception makes the class checked, so every caller must catch it or declare it. Extending RuntimeException makes it unchecked: class OtpExpiredException extends RuntimeException { OtpExpiredException(String m) { super(m); } }. With a balance of ₹1,200, pay(1500) caught as e gives e.getMessage() = "need Rs 1500, have Rs 1200" and e.getShortfall() = 300. Also provide a (String message, Throwable cause) constructor when you translate lower-level exceptions, and remember that an exception class cannot be generic (5.3).

In Python

class PaymentError(Exception):
    pass

class InsufficientFunds(PaymentError):
    def __init__(self, needed, available):
        super().__init__(f"need Rs {needed}, have Rs {available}")
        self.shortfall = needed - available

    raise InsufficientFunds(1500, 1200)

Inherit from Exception, never directly from BaseException, which also covers KeyboardInterrupt and SystemExit. By convention the name ends in Error.

Four design rules hold in every language. Create a class only when some caller will handle that case differently; otherwise a standard exception (invalid_argument, IllegalArgumentException, ValueError) is clearer. Carry data, not just text. Give each module one base class, so callers can catch broadly or narrowly. Keep the class simple, so that building it cannot itself fail.

Exam traps

  • A what() without const silently hides the base version instead of overriding it, and one without noexcept is a compile error ("looser exception specification"). Write const char* what() const noexcept override.
  • Never return c_str() of a local string from what(); store the message in a member or pass it to the base constructor.
  • In Java, extends Exception means checked: every caller must catch or declare it. Use RuntimeException for misuse that is a programming bug.
  • In Python, inherit from Exception, not BaseException.
  • Catch the specific class before its base: with PaymentError first, the ₹900 bill prints "payment refused: insufficient funds" and the shortfall is never shown (g++ only warns).

Glossary

Amortised O(1)
Average cost per operation stays constant over many operations, though a rare one (a vector reallocation) is expensive.
Bounded type
A Java type parameter restricted to a class and its subclasses, as in <T extends Number>.
Capacity
The number of elements a vector can hold before it must reallocate; at least its size.
Checked exception
A Java exception outside the RuntimeException branch that must be caught or declared with throws.
Class template
A blueprint from which the compiler generates a class for each set of template arguments.
Container
An STL class template that stores elements, such as vector, list or map.
Diamond operator
The empty <> in new Box<>(25), letting javac infer the type argument.
Exception
An object thrown to signal a run-time error and handled by a matching catch block.
Explicit specialisation
A separate template body for one specific type, introduced by template <>.
finally
A Java or Python block that runs on every exit from a try block.
Function template
A recipe from which the compiler generates a function for each type used.
Generator
A Python function containing yield; calling it returns a lazy, single-pass iterator.
Half-open range
[begin, end): includes the first position, excludes the last, so its length is end − begin.
Instantiation
The compiler's generation of real code from a template for given arguments.
Iterator
An object that refers to an element of a collection and can move to the next.
Iterator invalidation
An iterator becoming unusable after the container changes, as after a vector reallocation.
Multi-catch
Java 7 syntax that handles unrelated exception types in one block: catch (A | B e).
Propagation
An unhandled exception passing from a function to its caller, up the call stack.
RAII
Resource Acquisition Is Initialisation: tying a resource to an object so its destructor releases it.
Rethrow
Passing a caught exception on with throw; (C++), throw e; (Java) or raise (Python).
Stack unwinding
Removing stack frames and destroying their local objects while searching for a handler.
STL
Standard Template Library: the C++ containers, iterators and algorithms built from templates.
Template argument deduction
Working out template arguments from the types of a call's arguments.
Type erasure
Java's removal of type arguments after compile-time checking, leaving one class.
Unchecked exception
A Java RuntimeException or Error; the compiler does not require handling.

An exception class written for an application, derived from the language's exception base class.

The ? type argument in Java, optionally bounded by extends or super.
