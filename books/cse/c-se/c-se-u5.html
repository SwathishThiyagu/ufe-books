5.1 Test planning and test plan components

A test plan is the written agreement on what will be tested, how, by whom, when, and when testing stops. It exists because testing has many possible scopes and a fixed amount of time, money and people. Without a written plan, different teams assume different coverage and the project discovers gaps late. The plan has a master level plus level plans for unit, integration, system and acceptance testing. It is used wherever a release decision must be repeatable, from a UPI payment feature in a bank to a railway reservation module. It turns testing into a managed commitment.

You need the SRS from Unit 2 and test case design from Unit 4; the people side continues in 5.2.

The plan as an agreed baseline

A test plan fixes four things: what will be tested, how it will be tested, who does the work, and the rules for stopping. Testing can expand without limit, so the plan puts a boundary around a fixed budget of time, people and money. It also makes assumptions visible. If someone later says “we assumed payment failure paths were out of scope”, the plan is the record that prevents that claim.

Plans come at two levels. A master test plan covers the whole product and sets common rules. Level plans cover unit, integration, system and acceptance testing separately, because each has different items and exit rules. A unit plan may be a short wiki page; a system plan for a banking release is longer.

The plan is not the test case specification. The plan says what will be done and when testing stops. The test case specification gives the inputs, steps and expected results for each case. The plan is a living baseline: it is approved, put under version control (see 5.5), and revised when scope, build or risk changes.

Components in the usual order

Most plans follow this order:

  • Plan identifier and scope: name, version, product, what is in and out.
  • Test items: the documents, builds, interfaces and modules to be tested.
  • Features to be tested: the requirements and quality attributes that get test cases.
  • Features not tested: excluded items with a reason, such as a third-party KYC API tested by its vendor.
  • Test approach and levels: unit, integration, system, acceptance; techniques and automation scope.
  • Entry criteria: conditions before testing starts, such as code complete and a green CI build.
  • Exit criteria: measurable stopping rules, such as no open severity 1 or 2 defects and 100% requirement traceability.
  • Suspension and resumption: when to pause testing, for example a build that fails smoke tests, and what must be true to restart.
  • Environment, tools and test data: servers, browsers, devices, data sets and defect tracker.
  • Deliverables: test cases, logs, defect reports and the summary report.
  • Roles and responsibilities: who designs, runs, reviews and signs off.
  • Schedule: milestones and dependencies, not a detailed task list.
  • Risks and contingencies: what can break the plan and the backup action.
  • Approvals: names and dates of people who accept the plan.

Locating test items is the mapping step. Each test item is linked forward to the test cases that exercise it and backward to the requirement that created it. The two most-forgotten sections are features deliberately not tested and exit criteria; both prevent arguments at release time.

Attachments, traceability and revision

Attachments are part of the plan even when stored in a separate tool. The requirement-to-test traceability matrix, or RTM, is the central one. It has one row per requirement and columns for test case IDs, test level and status. Forward trace goes requirement → test case. Backward trace goes test case → requirement.

Traceability coverage = (requirements with at least one test case ÷ total requirements) × 100%. A requirement with no test case is a coverage hole. A test case with no requirement is either a defect in the test set or a valid extra check; record which.

The test case list is the index of cases, not the full case text. The defect workflow attachment fixes states such as new, open, fixed, retest and closed, plus severity definitions and who may close a defect. Together these attachments make the plan auditable: a reviewer can pick any requirement, follow it to a case and then to a result.

Treat the approved plan as a baseline. Re-baseline at entry, at each test cycle and whenever scope, build, team or risk changes. Record each change in the version history with a reason. At the end, compare actual exit results with planned exit criteria in the summary report (see 5.2). A plan written once and never revised is a historical document, not a management tool.

Worked example

Question. A UPI payment feature has 45 functional requirements. The team plans three full regression cycles inside an 18-day window with two testers. Average 3 test cases per requirement; about 30% of cases are automated. A tester runs 6 manual cases per day. Test cycle 3 is replaced by a 25-case smoke subset. Does the plan fit? Show the entry and exit criteria you would record.

  1. Total test cases = 45 × 3 = 135 cases.
  2. Automated cases ≈ 30% of 135 = 40.5, rounded down to whole cases = 40. Manual cases = 135 − 40 = 95.
  3. One full manual cycle = 95 ÷ 6 = 15.833 person-days ≈ 15.8 person-days.
  4. Three full cycles = 3 × 15.833 = 47.5 person-days. With two testers this is 47.5 ÷ 2 = 23.75 ≈ 23.8 days, so it misses the 18-day window.
  5. Smoke subset for cycle 3 = 25 ÷ 6 = 4.167 ≈ 4.2 person-days. New effort = 15.833 + 15.833 + 4.167 = 35.833 ≈ 35.8 person-days.
  6. With two testers, new duration = 35.833 ÷ 2 = 17.917 ≈ 17.9 days, which fits inside 18 days.
  7. Record entry criteria: feature complete, CI build green, smoke suite passing. Record exit criteria: no open severity 1 or 2 defects, 100% requirement traceability, and all 25 smoke cases pass in each cycle. Record the risk: cycle 3 no longer covers the full regression set; contingency is a full regression cycle before release if defect trends rise.

Answer. The reduced plan needs 35.8 person-days, or 17.9 days with two testers, and fits the 18-day window; three full cycles would need 47.5 person-days, or 23.8 days with two testers, and miss it.

Exam traps

  • Writing the plan once and never revising it; an approved plan is a baseline, not a stone tablet.
  • Confusing the test plan with the test case specification; the plan states scope, approach and stopping rules, while the test case specification gives inputs, steps and expected results.
  • Leaving out features deliberately not tested and exit criteria; these are the two most-forgotten sections and the two that cause release-time arguments.
  • Using “all defects fixed” as an exit rule with no severity and no count; define which severities block release and how many may remain open.
  • Forgetting suspension and resumption rules; a team that pauses testing without a written restart condition restarts on opinion.

5.2 Test management, test teams and reporting results

A test plan names roles and exit criteria. It only happens if real people are staffed, organised and reported on. Testing is done by humans inside an organisation, so someone must decide whether testers sit inside development teams or in a separate group, what each role owns, how new testers are trained, and how results reach the people who decide release. This chapter covers that people-and-reporting side: independence, team structures, roles and skills, the test process, and the reports a test manager writes.

You need: 5.1 Test planning and test plan components, which fixes roles, schedule and exit criteria.

Independence of testers and the friction it creates

Independence is separation between builders and testers. A developer testing their own code reads the requirement through their design and checks that the code does what they meant, not what the user asked for. Independence buys objectivity; it costs context, because an outsider needs time to learn the system.

  • The author tests their own code: fastest feedback, weakest independence.
  • Another tester inside the same team: shared context, mild independence.
  • A separate test group in the same company: its own reporting line, slower feedback.
  • An outsourced or offshore team: strongest independence on paper, largest context gap.

Friction is structural. A defect report is feedback on a developer’s work, and a tester’s day produces it. Two rules keep it healthy: write every defect about the product, stating what happened and what was expected; agree severity and priority definitions before the cycle. Testers who join requirement reviews prevent defects instead of only finding them (see Unit 2).

Never measure a tester by defects logged. That rewards trivial findings as much as data-loss bugs. Measure coverage of planned cases and defects that escaped to production (see 5.4 Test metrics and measurements).

Roles, skills and growing a testing group

  • Test manager: owns plan, budget, staffing and summary report; escalates risks.
  • Test lead: schedules cases, reviews test designs, mentors engineers.
  • Test engineer: designs and runs cases, logs and tracks defects to closure.
  • Automation engineer: builds the framework and scripts and wires tests into the pipeline (see 5.3 and 5.7).
  • Performance tester: builds load models, runs benchmarks and profiles results.
  • Domain expert: knows the banking, insurance or telecom rules; often part-time.

Skills that matter: domain knowledge; test design techniques (see Unit 4, Software Testing Strategies and Techniques); enough SQL and scripting to check data and build small tools; fluency with test and defect tools; writing a defect a stranger can reproduce; curiosity to try the unplanned case; and diplomacy, because every finding is someone’s work.

  1. Onboarding: one week on the product, process, defect workflow and test environments.
  2. Domain training: a walkthrough by the domain expert, then supervised testing of one module.
  3. Tool training: test management tool, defect tracker, version control and build pipeline.
  4. Mentoring: a senior tester reviews the newcomer’s first twenty test cases and defect reports.
  5. Certification: an entry-level testing certification (ISTQB Foundation is common) builds shared vocabulary, and does not replace practice.

The test process and the reports it produces

  1. Plan: scope, approach, roles, schedule and exit criteria (5.1).
  2. Design: test cases and test data derived from requirements and design.
  3. Execute: run each case and record pass, fail or blocked against the build identifier.
  4. Evaluate exit criteria: compare recorded numbers with the thresholds in the plan.
  5. Report: daily status, weekly progress, and the test summary report at the end.
  6. Closure: archive cases, logs and reports, and record lessons for the next release.

The daily status is short: cases run, passed, failed and blocked, plus the one blocker that needs a decision today. The weekly report adds progress against plan, defect trend by severity, open risks, and what the next week needs from other teams.

The test summary report is the release document. It carries scope and what was deliberately not tested, the build and environment tested, counts of executed, passed, failed and blocked cases, defect totals by severity with open, closed and deferred counts, the escaped-defect rate, each exit criterion with a met or not-met verdict, and a release recommendation.

A single defect report needs an identifier, a one-line title, the build and environment, steps to reproduce, expected and actual results, severity, priority, attachments such as logs and screenshots, the assignee and the status.

Worked example

Question. Write the numbers for the release 2.3 test summary report. During the cycle, 480 test cases were planned. Of these, 456 passed, 18 failed and 6 were blocked. The 18 failures plus 12 exploratory findings produced 30 defects: 12 at severity 1 or 2, 14 at severity 3, and 4 at severity 4. Of the 30, 27 are closed and 3 are deferred (all severity 3 or 4); the product owner accepts the deferral. Two defects escaped to production. The group is 1 test manager, 2 leads, 8 test engineers and 2 automation engineers. Compute pass rate, blocked rate, defect totals, leakage and spans, and recommend.

  1. Pass rate = 456 ÷ 480 = 95.0%.
  2. Blocked rate = 6 ÷ 480 = 1.25%.
  3. Defects = 18 failures + 12 exploratory findings = 30.
  4. Severity: 12 at severity 1 or 2, 14 at severity 3, 4 at severity 4; total 30.
  5. Status: 27 closed + 3 deferred = 30; none unclassified, but the 3 deferred defects are still open.
  6. Leakage = 2 ÷ (30 + 2) = 6.25%.
  7. Spans: test manager 1:2 (two leads); functional lead 1:8; automation lead 1:2. The two leads supervise 10 engineers between them, average 1:5.
  8. Exit criteria: pass rate ≥95% met at 95.0%; blocked ≤2% met at 1.25%; no open severity 1 or 2 defect met, because the 3 deferred defects are severity 3 or 4 and the product owner accepted the deferral.
  9. Recommendation: release 2.3; schedule the 3 deferred fixes for 2.4.

Answer. Pass rate 95.0% (96.2% of run cases), blocked rate 1.25%, 30 defects, 3 deferred severity 3–4 remain open, leakage 6.25%; spans manager 1:2, functional lead 1:8, automation lead 1:2; release 2.3 with deferred fixes in 2.4.

Exam traps

  • Believing an independent test group guarantees quality. It buys objectivity; quality still comes from the code, reviews and tests.
  • Measuring testers by defects logged. This rewards trivial defects and punishes prevention work.
  • Treating blocked cases as failures or passes. Blocked cases never ran; a pass rate of 456/480 = 95.0% and one of 456/474 = 96.2% measure different things; state the denominator.
  • Confusing severity with priority. Severity is impact on the product; priority is fixing order. A crash in a rarely used report can be severity 1 and priority 3.
  • Sending a summary report without the build identifier, so nobody can reproduce the numbers.

5.3 Test automation: scope, design and tools

Test automation means using software to run pre-written checks without a person clicking each step. It exists because regression suites grow while release cycles shrink. A manual suite that takes six person-hours per run becomes a bottleneck when the team releases every week. Automation is used for stable checks that repeat: smoke tests, regression tests, API checks, load tests and data-heavy validation. The decision is economic, not emotional: automate the tests that are run often and change rarely, after comparing build cost, run cost and maintenance against manual effort.

You need: Unit 4 test types and test case design, and 5.1, where the test plan fixes the automation scope.

Scope: what earns automation

Automation is code that runs a check without a person. It pays back when the same check runs many times. The test plan from 5.1 should list candidates before any tool is chosen. Automate checks that are stable, repeatable, high-volume, data-driven and part of regression or smoke suites. API checks and performance tests are strong candidates because they are fast and call little user interface.

Do not automate a feature whose rules change daily. Do not automate exploratory testing: its value is the human judgement that chooses the next step. Usability testing needs a person to judge confusion. A one-off migration check will not repay its build cost.

  • Good candidates: regression suite, smoke suite, API contract checks, load tests, data-driven validation, build verification.
  • Poor candidates: new user interface, exploratory sessions, usability review, one-off checks.

R = B ÷ (M − A)

R is break-even regression runs; B is build effort in person-hours; M is manual effort per run in person-hours; A is automated maintenance effort per run in person-hours. Automate when planned runs exceed R.

Design styles and the test pyramid

A design style is the shape of the test code. Linear scripts record steps in order; they are quick to start and costly to maintain. Modular scripts call reusable functions. Data-driven tests keep data in tables, and one script reads many rows. Keyword-driven tests give each action a word, so a non-programmer can write cases. Hybrid designs mix these. The page object model gives each web page a class; tests call page methods, not raw selectors. Behaviour-driven tests write steps in plain language and bind them to code.

The test pyramid sets the mix. Put many tests at unit level, fewer at API level, and few at UI level. Unit tests are fast and stable. API tests are slower but still robust. UI tests are slow, need a browser, and break when layout changes. A UI-heavy suite gives late, flaky feedback.

  • Unit layer: JUnit, TestNG or PyTest, milliseconds per test.
  • API layer: Postman collections, seconds per test.
  • UI layer: Selenium or Playwright for web; Appium for mobile, tens of seconds per test.
  • Behaviour layer: Cucumber scenarios for business-readable checks.

Tools, return on investment and maintenance

Choose a tool by criteria, not by fashion. Check language and platform support, licence cost, CI integration, reporting, community size and team skill. A tool the team cannot debug is a liability.

Return on investment has three parts. Build cost is the one-time effort to write the suite. Run cost is machine time and people time to execute it. Maintenance cost is the ongoing effort after a product change. Maintenance is the part teams underestimate: selectors break, test data ages, and waits fail. A suite that is not maintained becomes a false alarm generator.

Keep test code in version control with the product code. Review it like product code: names, structure, data handling and assertions. Run it in the pipeline from 5.6 and 5.7. A test that only runs on one engineer's laptop is not automation; it is a demo.

Worked example

Question. A 120-case regression suite is run 12 times a year. Manual cost is 6 person-hours per run. Automation needs 60 person-hours to build, then 2 person-hours per run for maintenance. Should the team automate? Find year-1 costs, break-even runs, and the three-year saving.

  1. Manual cost per run is 6 person-hours. Over 12 runs: 6 × 12 = 72 person-hours.
  2. Build cost is 60 person-hours. Maintenance is 2 person-hours per run. Year 1 automated cost: 60 + 2 × 12 = 84 person-hours.
  3. Year 1 difference: 84 − 72 = 12 person-hours more than manual, so automation loses in year 1.
  4. Break-even runs: R = 60 ÷ (6 − 2) = 15 runs. At 12 runs a year, time = 15 ÷ 12 = 1.25 years = 15 months.
  5. Over 3 years manual: 6 × 36 = 216 person-hours.
  6. Over 3 years automated: 60 + 2 × 36 = 132 person-hours.
  7. Saving: 216 − 132 = 84 person-hours. Decision: automate, because the suite will also grow and the product will be maintained for years.

Answer. Automate: the suite breaks even at 15 runs, about 15 months, and saves 84 person-hours over 3 years.

Exam traps

  • Automation does not replace manual testing; it repeats known checks. It finds regression, not new defects.
  • Forgetting maintenance cost: a suite with high maintenance may never break even.
  • Automating unstable features: the script churns with the feature and becomes waste.
  • An inverted pyramid: many slow UI tests and few unit tests, giving slow and flaky feedback.
  • Treating record-and-playback as design: it creates linear scripts that break on the first change.

5.4 Test metrics and measurements

A test team generates numbers all day: cases run, cases passed, defects raised, hours spent. A metric is one of those numbers, defined precisely so that it answers a question and helps someone decide — ship or wait, hire or automate, tighten exit criteria or relax them. Metrics appear in the daily test report, in the release go/no-go meeting, and in the retrospective that asks why defects escaped. The idea is simple: measure what you will act on, watch the trend rather than one reading, and never turn a measure into a target.

You need: 5.1 for exit criteria, which most of these metrics feed, and 5.2 for the report the numbers go into.

Base measures, derived metrics, goals

A base measure is a count taken directly from the work: test cases executed, defects logged, hours spent, failures observed. A derived metric is computed from two or more base measures, such as defects per thousand lines of code. Base measures are cheap and honest. Derived metrics carry an interpretation, so always state the formula beside the number.

  • Product metric: describes the software — defect density, coverage, availability.
  • Process metric: describes how the team works — test cycle time, automation coverage, defect removal efficiency.
  • Leading indicator: moves before the outcome, such as the open defect backlog in week 3. It lets you steer.
  • Lagging indicator: reports after the outcome, such as field failures in the first six months. It tells you whether steering worked.

Goal–Question–Metric (GQM) keeps a metric tied to a purpose. Start from a goal, write the questions that would show whether it is met, then pick the metric that answers each question.

  1. State the goal as purpose, object and focus: reduce escaped defects in the payments module before release.
  2. Write the questions: how many defects escaped last time, and at which stage?
  3. Name a metric and its raw data for each question: defect leakage, from defects found before and after release.
  4. Collect it, report it, and drop the metric if nobody changed a decision because of it.

Execution, coverage and pace

Execution progress answers the simplest question in test management: are we running the plan? A case counts as executed once it has a result — pass, fail or blocked. A blocked case cannot run because a build, environment or test data is missing; it is not a pass.

Test execution progress (%) = (executed ÷ planned) × 100

executed is the number of baseline test cases with any result; planned is the number in the approved baseline. Pass rate = (passed ÷ executed) × 100, and passed + failed + blocked = executed.

Coverage measures how much of the product the tests actually touched. Requirement coverage is the share of requirements with at least one passing test. Statement coverage is the share of executable statements the suite ran. Branch coverage is the share of decision outcomes taken; a decision has two outcomes, so it demands more than statement coverage on the same code.

Statement coverage (%) = (statements executed ÷ executable statements) × 100; Branch coverage (%) = (branches taken ÷ total branches) × 100

a branch is one outcome of a decision, the true side and the false side counted separately; a statement is one executable line. Requirement coverage has the same shape: requirements with a passing test ÷ total requirements × 100.

  • Automation coverage = automated cases ÷ total cases × 100 (see 5.3).
  • Test cycle time = hours from build ready to the test result signed off. Falling cycle time is what makes daily builds possible.

Defects, reliability and the backlog

Defect density normalises a defect count by size so two releases can be compared. Size may be KLOC, requirements or test cases — say which, and give the unit.

Defect density = defects ÷ size

defects is the count found in a stated phase, say system testing; size is thousands of lines of code (KLOC), number of requirements, or number of test cases. Write 6 defects/KLOC, not 6.

Defect removal efficiency, DRE (%) = (D_pre ÷ (D_pre + D_post)) × 100; Defect leakage (%) = (D_post ÷ (D_pre + D_post)) × 100

D_pre is defects found before delivery across all test phases; D_post is defects found after delivery, usually in the first months of use. The two percentages add to 100%.

Severity distribution is a short table — critical, high, medium, low — not a single index; two projects with 100 defects each can be very different. For the trend, plot cumulative defect arrival against cumulative closure; the vertical gap between the curves is the open backlog.

MTBF = total operating time ÷ number of failures; Availability (%) = (MTBF ÷ (MTBF + MTTR)) × 100

MTBF is mean time between failures in hours; MTTR is mean time to repair in hours; availability is the share of time the system is up.

Trends, variance and the danger of targets

One reading says little. Plot each metric against time and read the slope: a pass rate falling late in a cycle usually means risky late changes, not a suddenly poor team. Compare a release with its own past, not with another product.

Effort variance (%) = ((actual effort − planned effort) ÷ planned effort) × 100

schedule variance uses the same shape with days. Positive means overrun and negative means under; state the sign convention or the reader will guess wrong.

Two pitfalls break more metric programmes than anything else. First, when a metric becomes a target people optimise the number instead of the goal: demand 2 defects/KLOC and teams stop logging trivial defects, or split one defect into five. Second, comparing across dissimilar projects — a 15 KLOC web tool against a 500 KLOC embedded system — ignores domain, age and process. Compare trends within a project.

Worked example

Question. A release is 15 KLOC. Testing found 90 defects; the first six months after release found 10 more. Across installations the system ran 5000 hours with 8 failures. Of 1200 planned test cases, 900 passed, 180 failed and 60 were blocked. Compute defect density, defect removal efficiency, defect leakage, MTBF and test execution progress. Which number would you raise at the go/no-go meeting?

  1. Defect density = 90 ÷ 15 = 6 defects/KLOC.
  2. Total defects = 90 + 10 = 100, so DRE = (90 ÷ 100) × 100 = 90%.
  3. Leakage = (10 ÷ 100) × 100 = 10%, which checks as 100% − 90%.
  4. MTBF = 5000 ÷ 8 = 625 hours.
  5. Executed = passed + failed = 900 + 180 = 1080; a blocked case could not run, so the 60 blocked cases do not count. Progress = (1080 ÷ 1200) × 100 = 90%.
  6. Read together: density is unremarkable, but leakage of 10% says the exit criteria let too many defects through.

Answer. Density 6 defects/KLOC, DRE 90%, leakage 10%, MTBF 625 hours, execution progress 90%; leakage is the number to raise, because it shows the exit criteria were too loose.

Worked example 2

Question. A system runs 2000 hours with 4 failures; mean time to repair is 5 hours. Compute MTBF and availability.

  1. MTBF = 2000 ÷ 4 = 500 hours.
  2. Availability = (500 ÷ (500 + 5)) × 100 = (500 ÷ 505) × 100 = 99.01%.
  3. The repair time barely moves availability here; at MTTR = 50 hours it would fall to 90.9%.

Answer. MTBF is 500 hours and availability is 99.0%.

Exam traps

  • Quoting a metric without formula or unit: '6 defects' instead of '6 defects per KLOC' loses marks and misleads the reader.
  • Mixing DRE and leakage denominators. Both divide by (D_pre + D_post), not by D_pre alone, and they add to 100%.
  • Assuming a high defect count means a weak team. A team that logs many defects early usually delivers a cleaner release; a low count can mean poor reporting.
  • Turning a measure into a target: demand a density figure and the data improves, not the software.
  • Comparing coverage figures across projects; 80% branch coverage of a small script is not the same achievement as 80% of a payments engine.

5.5 Version control systems

A version control system (VCS) records every change to a project as an immutable snapshot, so any past state can be rebuilt exactly. It exists because software changes many times, by many people, and one wrong edit must not destroy months of work. Teams use it for history, undo, parallel work on branches, release baselines and an audit trail. Git is the common distributed VCS; a push or a tag is also what wakes the CI server.

You need: the idea of a baseline and change control from Unit 6, Software configuration management, and the test plan vocabulary from 5.1.

Snapshots, commits and the vocabulary

A version control system keeps a repository: the full stored history of a project. Your working copy is the set of files you edit on your machine. A commit is one immutable snapshot of the whole project tree, plus metadata: author, time, message and parent commit. A revision is one point in that history. A branch is a movable name that points to a commit; a tag is a fixed name, often used for a release. The mainline (also called trunk or main) is the branch the team treats as the shared line.

Changes are recorded as whole snapshots, not as a patch of each file. Git still stores files efficiently by keeping identical content once and by packing objects. For a reader, the important point is that any commit can rebuild the exact tree.

  • Merge: join two histories into one commit.
  • Conflict: Git cannot choose between two edits to the same region, so a person decides.
  • Baseline: a commit used as the fixed reference for a release or a test cycle.
  • Audit trail: the record of who changed what, when and why, read from commits.

id = H(tree, parents, author, message)

id is the commit name; H is a cryptographic hash such as SHA-1 in classic Git; tree is the root directory snapshot; parents are earlier commits, none for the first commit and two or more for a merge commit; author and message are metadata.

Centralised against distributed systems

A centralised VCS has one server that holds all history. Your client holds a working copy and asks the server for log, diff or old versions. CVS and Subversion work this way. Backup is in one place, but history needs the network, and branching can be costly.

A distributed VCS gives every clone the full history and all objects. Git and Mercurial work this way. You can log, diff, commit and branch offline. Push sends your commits to another repository; pull brings commits in. Every clone is also a backup.

Git internals at working level: a blob holds file content; a tree holds a directory listing that names blobs and subtrees; a commit points to one root tree and to its parent commits. The commit graph is a directed acyclic graph (DAG). Arrows point from a child commit to its parents, and a cycle cannot exist because a commit is named by the hash of its contents, including parent hashes. Editing old history changes later hashes.

Question. Merge branch feature/pay into main and predict the conflicts.   3. Compare E with B: feature changes line 4 and inserts 6 lines after base line 10.
  4. The insertion after line 10 and the change at line 15 touch different regions, so Git merges them automatically.
  5. Line 4 changed in both branches, so Git stops on that one region and writes conflict markers there.
  6. The developer edits line 4, runs git add app.py, then git commit. Git creates merge commit M with parents C and E.

Exam traps

  • A commit stores a snapshot of the whole tree, not a list of per-file differences. Git may store content efficiently, but the model is snapshot plus parent pointer.
  • Merge and rebase are not the same. Merge creates a commit with two parents; rebase replays commits on a new base and changes their ids.
  • pull is fetch plus integration. fetch only downloads commits and does not move your branch.
  • Never commit build output, local config or passwords. Add paths to .gitignore and keep secrets outside the repository.
  • A branch moves as new commits arrive; a tag stays on one commit. Do not use a branch name as a release baseline.

5.6 Continuous integration and continuous delivery

Continuous integration (CI) means every developer merges into the shared mainline at least daily, and every merge is proved by an automated build and test run. Continuous delivery keeps that mainline always releasable, so shipping is a business decision, not an engineering scramble. Continuous deployment sends every passing change to production automatically. The idea exists because late integration gives 'it works on my machine' surprises and long release nights. It is used wherever software ships often — a UPI app, an IRCTC booking service, a cloud product.

You need: 5.5 Version control systems, because a push to the mainline is the trigger, and 5.3 Test automation, which supplies the tests the pipeline runs.

Integration, delivery and deployment are three different promises

Continuous integration (CI) is a practice: every developer merges into the shared mainline at least once a day, and every merge is checked by an automated build and an automated test run. The mainline is the one branch the team shares. When the check fails, fixing it is the team's first job; a red mainline blocks everybody.

Integration is the hard part. Two branches kept apart for three weeks touch the same files, and someone must resolve the conflict by hand. Daily merges keep the difference small, so conflicts stay small too.

Continuous delivery means every change that passes the pipeline leaves the mainline releasable today. Which release goes out, and when, stays a business decision. Continuous deployment removes that decision: every passing change reaches production automatically.

The deployment pipeline

A deployment pipeline is the automated path a commit walks from push to production. Each stage is a check; stages run in fixed order and stop at the first failure.

  1. Commit: a developer pushes to the mainline; the push is the trigger.
  2. Build: compile and link, or build a container image; a broken build stops everything in minutes.
  3. Unit tests: seconds to minutes; catch most logic errors.
  4. Integration and acceptance tests: slower tests against a real database or service; split into parallel shards when they dominate the time.
  5. Package: write the artifact (jar, war, image) to an artifact repository under a unique version.
  6. Deploy to staging: an environment that mirrors production.
  7. Smoke tests: a short check that staging serves its main paths.
  8. Deploy to production, with automatic rollback if health checks fail.

Two rules make a pipeline useful. Fail fast: run the cheapest, fastest checks first, so a typo is caught in two minutes, not forty. Build once and promote: the artifact tested on staging is the one copied to production. A rebuild means you released something nobody tested.

T = Σ max(t₁ … tₖ)

T is pipeline wall-clock time in minutes; the sum runs over stages; t₁ … tₖ are run times in minutes of the k jobs running in parallel inside one stage, and max picks the longest.

Practices that keep the mainline releasable

  • Trunk-based development: branches live hours or a day, not weeks, and merge back to the trunk.
  • Pipeline as code: the pipeline definition is a file in the repository (Jenkinsfile, .gitlab-ci.yml, .github/workflows), reviewed and versioned like code.
  • Environment parity: staging has the same operating system, database version and configuration as production; every difference hides a defect.
  • Versioned database migrations: schema changes are scripts in the repository, applied by the pipeline, never typed by hand on a server.
  • Immutable artifacts: the same stored file moves from stage to stage, so staging and production run identical bytes.

DevOps is the culture and tooling that removes the wall between development and operations: one team owns the code, pipeline and running service. Jenkins, GitLab CI and GitHub Actions run build and test stages; Argo CD keeps a cluster in sync with the repository. Most pipelines run in the cloud, where a fresh test machine is minutes of provisioning, not a purchase order.

Releasing without downtime

Blue-green release: two identical environments, blue serving live traffic and green receiving the new version. When smoke tests pass, the router points at green; rollback points it back at blue in seconds.

Canary release: a small slice of traffic, for example 5% of requests, goes to the new version while the rest stays on the old one. If error rates rise, the canary is withdrawn before most users notice.

Feature flags separate deploy from release: code ships dark and a switch turns it on for chosen users. A flag lets unfinished work merge to the trunk safely. Rollback needs the previous artifact kept and one command to restore it; a pipeline that cannot roll back is not a delivery pipeline.

Worked example

Question. A team's pipeline runs stages in series: build 5 min, unit tests 8 min, integration tests 20 min, package 3 min, deploy to staging 2 min, smoke tests 3 min. (a) Find the total wall-clock time. (b) Integration tests are split into 4 equal parallel shards; find the new total. (c) Unit tests are then split into 2 equal shards; find the new total. (d) A manager suggests deleting the smoke stage instead. Comment with numbers.

  1. (a) Series total = 5 + 8 + 20 + 3 + 2 + 3 = 41 min.
  2. The pipeline time is the sum of stages because each waits for the one before it (T = Σ max(t₁ … tₖ) with one job per stage).
  3. (b) Shard length = 20 ÷ 4 = 5 min. New total = 5 + 8 + 5 + 3 + 2 + 3 = 26 min. Saving = 41 − 26 = 15 min.
  4. (c) Unit shard length = 8 ÷ 2 = 4 min. New total = 5 + 4 + 5 + 3 + 2 + 3 = 22 min, a further saving of 4 min.
  5. (d) Deleting smoke gives 26 − 3 = 23 min, saving 3 min, less than the 4 min won by sharding unit tests. It also removes the only check on deployed staging, so refuse; parallelise first, delete never.

Answer. 41 min in series, 26 min with four integration shards, 22 min after also splitting unit tests into two; the 3-minute smoke stage stays because it is the release gate.

Exam traps

  • Saying 'we do continuous integration' because a Jenkins server exists, while branches live for weeks. The practice is a daily merge into one green mainline.
  • Treating continuous delivery and continuous deployment as the same. Delivery means every change is releasable and a person chooses the moment; deployment ships without asking.
  • Rebuilding for production instead of promoting the tested artifact. The binary you release is then not the binary you tested.
  • Making the pipeline fast by deleting acceptance or smoke tests. Shorten by sharding and parallelising; a removed gate releases defects.
  • Reading fail fast as test less. It means cheapest checks run first so failure is reported in minutes, not that later checks are dropped.

5.7 Build and test automation pipelines

A build and test pipeline turns one commit into a tested, versioned artifact through a fixed series of stages. It exists because people forget steps, and because rebuilding separately for each environment creates differences that tests never see. The pipeline does the same work every time, in the same order, and stops at the first failure. Teams use it on every commit, from a small npm library to a large Maven or Gradle system, and read its duration and failure rate to decide where to improve.

You need: 5.6 continuous integration and continuous delivery and 5.5 version control systems.

What a build does

Build is the automated act of turning source files into a runnable or deployable artifact. A pipeline is the fixed order of stages that does this on a build server; the server is also called an agent or runner. A build tool knows how to compile and package one kind of project: Maven and Gradle for Java, Ant for older Java trees, npm for JavaScript, MSBuild for .NET.

The pipeline repeats the same steps for every commit, so a missing step is visible in the log, not remembered by a person.

  1. Fetch the source at one commit hash.
  2. Resolve dependencies from a local cache first, then from an artifact repository.
  3. Compile changed modules, then run unit tests and static analysis.
  4. Package the result and publish it once to the artifact repository with a version and build number.

An artifact repository is a versioned file store for build outputs and dependencies.

Stages that fail fast

A pipeline should fail at the cheapest point. Put the shortest tests first: compile the touched modules, run their unit tests, then static analysis. A failure at 90 s costs less than the same failure after a 30-minute full suite.

Run independent jobs as parallel shards. Split a test suite by package or class so four runners take four quarters; the slowest shard sets the stage time.

Keep a small smoke suite on every commit. Run the full suite nightly, because it is too slow to block every change. A smoke suite is a short set of tests for the main paths, not a random sample.

A flaky test passes and fails without a code change. Move it to a quarantine lane: it still runs, but its failure does not block the main line, and it has a deadline for a fix. Never delete it as the first response, because it may hide a real defect.

Agents are the machines that run jobs. A self-hosted runner is one you own; it can keep large caches and reach a private network. A cloud runner is rented and starts clean; it is simpler but may be slower to warm. Choose by cost, data rules and special hardware.

Versions, secrets and metrics

An artifact name such as 2.3.0-231 has two parts: 2.3.0 is the release version, 231 is the build number. Publish it once and make it immutable; nobody overwrites 2.3.0-231. Staging and production deploy that same file, so a test on staging proves something about production.

Build once and promote the same artifact from dev to staging to production, changing only configuration. Rebuilding at each stop can pick a newer dependency and differ from what was tested.

Passwords, API keys and signing keys stay out of the repository. The pipeline reads them from a secret store or from environment variables injected at run time. A secret in a commit stays in history; rotate it, then remove it.

A cache holds dependencies and compiled outputs between runs. Key it on the lock file so stale dependencies are not reused. A cache must be disposable: a bad cache should slow the build, not break it.

Store the commit hash in the artifact metadata. From a production artifact you can find the exact source and the pipeline run that produced it.

Track four metrics: pipeline duration from commit to artifact; failure rate as failed runs divided by total runs; mean time to repair from red build to green; and lead time for changes from commit to production. Use them to find a slow stage or a flaky suite, not to rank people.

5.8 Configuration management with Ansible playbooks

Configuration management keeps every server in a known state that is written as code. An Ansible playbook is a YAML file that declares packages, file contents and services for a group of hosts. It connects over SSH without an agent, compares the current state with the declared state, and changes only what differs. A delivery pipeline uses it to prepare test environments and to configure servers after release. The same file can run many times because it is idempotent: a second run with no drift reports no changes.

You need: deployment stage and environments from 5.6, and artifacts that get deployed from 5.7.

State written down, not a script

An imperative script lists commands: create user, copy file, restart service. Run it twice and some commands repeat: an appended line appears twice, a service restarts again. A declarative playbook lists the end state: package nginx present, file content equals template output, service running and enabled at boot. The module for each task checks the host and acts only when the host differs.

f(f(s)) = f(s)

f is one full playbook run and s is the state of a managed host; applying the run twice gives the same host state as applying it once.

The property that makes this safe is idempotency. Apply the playbook once or ten times and the machine ends in one state. A template that writes the whole file is idempotent; a shell command that appends a line is not.

Configuration drift is the gap between declared and actual state. A manual edit, a partial upgrade or a crashed process creates drift. A playbook run reports which tasks changed and which were already correct. Check mode performs the same checks and predicts changes without writing them, so a release manager can inspect a server before a real run.

Inventory, tasks and handlers

Ansible runs from a control node. The inventory file lists managed hosts and groups them by role, for example a group web with 12 addresses. YAML is a plain-text format that uses indentation for structure. A module is a built-in unit of work: apt or dnf installs a package, template renders a file, service controls a daemon. A task pairs a module with arguments and a name. A play maps a group of hosts to an ordered list of tasks. A playbook is one YAML file holding one or more plays.

Variables hold values that differ by host or environment. Gathered facts are variables Ansible reads from the host, such as ansible_processor_vcpus, the number of virtual CPUs. A Jinja2 template mixes fixed text with expressions like {{ 2 * ansible_processor_vcpus }}. A handler is a task that runs only when another task notifies it. The usual pattern writes a config file and notifies a reload handler, so a service reloads only when the file changes.

Roles group tasks, templates, variables and handlers into a reusable directory. Tags allow a partial run, for example only config tasks. Vault encrypts secret values so passwords are not plain text in the repository. Check mode is the dry run.

In the pipeline

A pipeline job checks out the playbook and reads the inventory for the target environment. It first runs a syntax check, then check mode, then the real run. For a test environment it provisions hosts, installs the runtime, writes configuration and starts the service. For a release it deploys the artifact from the pipeline, writes environment configuration and enables the service.

  1. Read the inventory for the target environment and run a syntax check.
  2. Run in check mode and review predicted changes.
  3. Apply the playbook for real; failed hosts stay in the recap.
  4. Deploy the versioned artifact from the pipeline before the release configuration run.
  5. Rerun after a fix; matching hosts report no changes.

Worked example

Question. A team must configure 12 web servers with one playbook. On a fresh host the play makes 3 changes: install nginx, write nginx.conf from a template, and start and enable the service. A handler reloads nginx only when the template output changes. (a) Find the total changes on the first full run. (b) Find the changes on a second run when no file changed. (c) Host 9 is unreachable on the first run: state the recap counts. (d) After the network is fixed, how many hosts does the rerun change, and how many changes are made on host 9?

  1. A fresh host needs 3 changes. For 12 hosts: 12 × 3 = 36 changes.
  2. Second run with unchanged files: every task finds the declared state, so each host makes 0 changes. Total is 12 × 0 = 0. The handler is not notified.
  3. Host 9 cannot be reached. Reachable hosts are 12 − 1 = 11. The recap shows 11 ok and 1 failed.
  4. After the fix, hosts 1–8 and 10–12 already match the declared state, so they make 0 changes. Only host 9 has the 3 missing changes. Changed hosts in the rerun = 1; changes on host 9 = 3.

Answer. First run: 36 changes; second run: 0 changes; with host 9 down: 11 ok and 1 failed; after the fix the rerun changes only host 9, with 3 changes on that host.

Exam traps

  • A YAML file full of shell tasks that append lines or restart services every run is not idempotent; the second run must report 0 changes.
  • Plain-text passwords in group variables are a leak; use vault, not a private Git branch.
  • Do not confuse state: present with state: latest; the first means installed, the second may upgrade and change the version.
  • A handler runs only when notified by a changed task; a task that reports ok does not reload the service.
  • Check mode predicts changes but does not prove the real run succeeds; permissions and package locks can still fail.

Check yourself

Remember What is idempotency in a playbook? 2 marks

A playbook is idempotent when applying it once or many times leaves the host in the same declared state. A second run with no drift reports 0 changes.

Understand Why is a template task more idempotent than a shell command that appends a line to a file? 3 marks

The template writes the whole file to match one declared content, so a rerun produces the same file. The append command adds the line again on every run, so the file grows and the state changes.

Apply Inventory group web has 8 hosts. A first run makes 4 changes per host and a second run makes 0. Find the first-run total changes. If 2 hosts are unreachable, state the ok and failed counts. 4 marks

First-run total = 8 × 4 = 32 changes. Reachable hosts = 8 − 2 = 6 ok; failed hosts = 2.

Analyze A playbook restarts nginx on every run even when nginx.conf is unchanged. What is wrong, and how does a handler fix it? 4 marks

The restart task is unconditional, so it is not idempotent and causes needless downtime. Move the restart into a handler and notify it from the template task; the handler runs only when the template output changes.

Remember How does Ansible connect to managed hosts, and what file lists those hosts? 2 marks

Ansible connects over SSH without installing an agent on the managed host. The inventory file lists hosts and groups them by role.

Analyze Why can shell: echo server_name >> app.conf fail the idempotency test on a rerun? 3 marks

The shell task always runs and appends another line, so the file differs after each run. It does not check the current content, and it reports a change every time.

Apply A template sets worker_processes = 2 × vCPU. The host fact gives 4 vCPU. What value is written? 2 marks

worker_processes = 2 × 4 = 8.

Takeaways

  1. A test plan earns its name only when entry criteria, exit criteria and suspension rules are written as measurable statements, not as wishes.
  2. Testing staffed as a small central team, as embedded testers, or as a shared pool each push risk ownership to a different place, so structure is a management decision, not an accident.
  3. Automate a test only when it will be run many times and rarely changed; the decision is a break-even calculation, not an enthusiasm.
  4. A metric is a decision aid; once it becomes a target, people optimise the number instead of the quality it was meant to stand for.
  5. Version control gives exact rebuilds of any past state, which is what makes bisecting a defect, reverting a bad release and auditing a change possible.
  6. Continuous integration is a habit plus a machine: merge to the mainline daily and let an automatic build and test run judge every merge.
  7. A pipeline should build the artifact once and promote the same bytes through every environment, so what you tested is what you release.
  8. Configuration management replaces hand-edited servers with a declared state that a playbook can recreate on any number of machines, every time.

Apply A regression suite of 300 cases takes 5 person-hours per manual run and is run 40 times a year. Automation costs ₹4,80,000 to build and ₹40,000 a year to maintain, and a run then needs 0.5 person-hour of attention. Glossary

Ansible inventory
A file listing the hosts and host groups that a playbook will act on, optionally with host-specific variables.
Audit trail
The ordered, tamper-evident history of commits, messages, authors and dates that shows who changed what and when.
Blue-green release
Running two identical production environments and switching traffic from the old one to the new one, so rollback means switching back.
Build tool
Software such as Maven, Gradle or Make that compiles sources, resolves dependencies and packages the artifact from a declared recipe.
Canary release
Sending a small share of live traffic to the new version first, watching error rates, then widening the share.
Configuration management
The practice of describing the required state of servers, packages, files and services in code and applying it repeatably.
Conflict
A merge situation where two branches changed the same lines of a file and a human must choose the final content.
Environment parity
Keeping staging and production close in operating system, versions, configuration and data shape, so tests predict real behaviour.
Feature flag
A configuration switch in the code that turns a feature on or off without redeploying, so deploy and release become separate acts.
Features not tested
A test plan section that records what is deliberately out of scope and why, so that no one assumes it was covered.
Flaky test
A test that passes and fails on the same code, usually due to timing, shared data or ordering, and which erodes trust in the whole suite.
Handler
An Ansible task that runs only when notified by another task, typically used to restart a service after a configuration change.
Immutable artifact
A build output that is never edited after creation; any change produces a new version with a new identifier.
Plan identifier
A unique name and version number given to a test plan so that reviewers and auditors can refer to an exact document.
Push
The command that sends local commits to a remote repository so other people can see and build them.
Regression suite
The set of tests rerun after every change to confirm that working behaviour has not been broken.
Release branch
A branch cut from the mainline to stabilise and patch one released version while new work continues on the trunk.
Risks and contingencies
The test plan section listing what could disrupt testing and the prepared response for each, such as a backup environment or a second test data set.
Smoke test
A small, fast set of checks that confirms the build is stable enough for deeper testing.
Test data
The inputs and preloaded records a test needs, prepared and versioned so that a run can be repeated exactly.
Test environment
The configured hardware, software, network and data on which tests run, ideally close to production.
Test execution report
A periodic record of which test cases ran, their results, and the defects raised, used to track progress during a phase.
Test summary report
The document issued at the end of a test phase that states results against exit criteria and gives a recommendation on release.
Traceability matrix
A table mapping each requirement to the test cases that cover it, used to show coverage and find untested requirements.
Trunk-based development
A branching style where developers commit to a single mainline in small, frequent changes, using short-lived branches at most.
