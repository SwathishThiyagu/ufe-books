3.1 Design process and software quality attributes

Design is where a software project stops describing the problem and starts deciding the shape of the solution. The requirements model — use cases, classes, data flow diagrams — goes in; a design model comes out: data structures, architecture, interfaces, components and the hardware they sit on. There is no single correct design, so we choose between candidate designs using quality attributes: maintainability, dependability, security, efficiency, acceptability. Every design decision buys one attribute and costs another, and a good design review names both sides. This chapter gives the process, the attributes, and the five elements of the design model.

You need Unit 2's functional and non-functional requirements and the analysis models, and Unit 1's view of where design sits in the life cycle — see 3.6 for the class model that feeds data design.

The design process: requirements model in, design model out

Analysis produced a requirements model: what the system must do, written as use cases, class models and data flow diagrams. Design reads that model and writes a design model: how the system will do it. Requirements say "book a seat". Design says which tables hold seats, which service takes the booking, which screen shows the seat map, and which server runs that service.

  1. Study the requirements model and mark the parts that force structure — volumes, peaks, external systems, legal rules.
  2. Choose the architecture: the large parts, their responsibilities and their connections.
  3. Design the data: tables, files, keys, indexes and the objects that sit on top of them.
  4. Design the interfaces: module-to-module signatures, and the boundary to the user and to other systems.
  5. Design each component: algorithms, internal data, error handling.
  6. Design deployment: which hardware node runs which component, and how nodes talk.
  7. Review the whole design against the quality attributes, and revise the parts that fail.

Design thinking has grown in layers, not by replacement. Modular design treats a program as functions with clean boundaries. Object-oriented design bundles data and behaviour into classes that hide their internals (3.2). Pattern-based design reuses named solutions such as MVC or observer (3.4). Aspect-oriented design pulls cross-cutting concerns such as logging and security checks out of every module and into one separate unit. Each layer gives the designer one more way to keep change local.

Quality guidelines and attributes

Several designs satisfy the same requirements, so we need a way to compare them. We compare them on quality attributes: the non-functional requirements of Unit 2, made concrete enough to shape a decision. Standards and textbooks use different names for the same ideas — ISO 25010 groups them as functional suitability, performance efficiency, compatibility, usability, reliability, security, maintainability and portability; McCall's older factor list splits them into product revision, product transition and product operations. Learn the ideas, not the list.

AttributeOne-line meaning
MaintainabilityThe cost of finding and fixing a fault or adding a feature later.
DependabilityThe system keeps working correctly when things go wrong — availability, reliability, safety.
SecurityData and functions are reachable only by those allowed to reach them.
EfficiencyThe work gets done within the time and memory budget on the given hardware.
AcceptabilityUsers can learn and use it, and the organisation can afford to run it.

Design guidelines sit on top of the attributes: a design should be hierarchical, modular, and made of distinct parts with clear boundaries; it should be traceable back to the requirements model; and it should be describable in a standard notation such as UML. The measurable forms of these guidelines — cohesion and coupling — are in 3.2.

No attribute is free. Encrypting card data buys security and costs response time and key management. Caching the seat map buys performance and costs memory and consistency. Running two copies of a service buys availability and costs money and deployment complexity. A design review therefore asks three questions: which attribute, which decision buys it, and which attribute that decision costs.

The five elements of the design model

  • Data design turns the data objects of the analysis model into tables, files, indexes and keys. It is the hardest element to change once live data exists.
  • Architectural design decides the large parts and their connectors. Styles such as layered, client-server and pipe-filter are catalogued in 3.3.
  • Interface design covers two edges: internal signatures between modules, and the external edge — the user interface (3.5) and links to other systems.
  • Component design goes inside each module: the algorithms, local data and error handling, built with the concepts of 3.2 and drawn in 3.6.
  • Deployment design maps components onto hardware nodes and says how nodes communicate; 3.8 gives the diagram for it.

The five elements are not produced in a fixed order. A peak-load figure in the requirements may force both the cache (data design) and the second server (deployment design) in the same meeting.

Worked example

Question. A ticket-booking site must be available 99.9 % of the year and must carry 40,000 users in the 10 a.m. booking window. (a) Name the two quality attributes. (b) How much downtime does 99.9 % allow in a 365-day year? (c) Give one design decision for each attribute.

  1. (a) Availability over a year is a dependability attribute (reliability in service). Carrying 40,000 users in a fixed window is a performance attribute (scalability and response time).
  2. Unavailable fraction = 100 % − 99.9 % = 0.1 % = 0.001.
  3. Hours in a 365-day year = 365 × 24 = 8760 h.
  4. Allowed downtime = 0.001 × 8760 h = 8.76 h.
  5. In minutes: 8.76 × 60 = 525.6 min, that is 8 h 45.6 min, about 8 h 46 min a year.
  6. (c) Availability: run two copies of the booking service behind a load balancer, so one server can fail without stopping bookings. Performance: keep the seat map in a cache and hold the seat lock in memory, so a page view does not hit the database.

Answer. Attributes are dependability (availability) and efficiency (performance/scalability); 99.9 % allows 8.76 h of downtime a year, about 8 h 46 min.

Exam traps

  • Writing quality attributes as a wish list. A full answer names the attribute, the design decision that buys it, and the attribute that decision costs.
  • Mixing the models: sentences beginning "the system shall ..." belong to requirements, not to a design answer.
  • Confusing architecture with component design. Architecture is the parts and their connectors; component design is what happens inside one part.
  • Percentage slips in availability: 99.9 % means 0.001 unavailable, not 0.01. Read the number of nines before multiplying.
  • Forgetting deployment design. A design that never says which machine runs what is incomplete in any exam that asks for the design model.

3.2 Design concepts: abstraction, modularity, functional decomposition

A design is good when each module hides its own information, does one job, and leans lightly on other modules. That unpacks into a small set of design concepts: abstraction, separation of concerns, functional decomposition, modularity, information hiding, cohesion and coupling. They exist because a program too big for one head must be cut into pieces a person — and a team — can hold. Every design uses them: a payroll system that splits gross pay from deductions, a UPI app that splits the payment screen from the bank call.

You need 3.1 (the design model and quality attributes) and Unit 2 (class-based requirements models).

Abstraction, separation of concerns and stepwise refinement

An abstraction keeps what matters for the current job and drops the rest. Procedural abstraction names a sequence of steps: a call to computeGst(amount) tells you what happens, not how. Data abstraction names a set of values and the operations on them: a Bill type hides whether amounts are stored in rupees or paise.

Separation of concerns says each part of the design should deal with one concern. The tax rule, the receipt layout and the database schema are three concerns. Mixing them in one class means a change to any one disturbs the other two.

Functional decomposition is the top-down act of splitting a system into functions, then splitting each function again. Stepwise refinement applies it until every piece is small enough to write as code. A payroll system, for example, splits into three functions, and its deductions function splits once more into PF and income tax. Stop refining when the next programmer finds the step obvious.

Modularity, information hiding and the cost of splitting

A module is a named unit of software with a clear interface. Modularity is the property of a system split into such units. Good modularity makes software easier to understand, test, debug, reuse, and build in parallel.

Splitting is not free. Every interface must be designed, documented and kept stable, and every call crosses a boundary. Too many tiny modules add calls, data passing and integration work for little gain.

Information hiding says a module should hide the design decision most likely to change: a file format, a data structure, a tax rule, a device driver. Callers see only the interface. When the hidden decision changes, callers do not.

Functional decomposition and modularity are not the same thing. Decomposition is the act of splitting; modularity is the property of the result.

Functional independence: cohesion and coupling

Two modules are functionally independent when each does one job and neither knows much about the other. Two measures describe it, and only one direction is good for each.

Cohesion looks inside a module and asks how strongly its parts belong together. Higher is better. The seven levels, worst to best, are:

ScoreLevelWhat the parts share
1CoincidentalNothing; they are bundled by accident
2LogicalA similar kind; a flag picks one
3TemporalThey run at the same time, e.g. startup
4ProceduralThey run in a fixed order
5CommunicationalThey work on the same data
6SequentialOne's output is the next one's input
7FunctionalAll parts serve one single job

Coupling looks between two modules and asks how much one depends on the other. Lower is better. From worst to best:

  • Content: one module edits another's internal data or jumps into its code.
  • Common: both read and write the same global variable.
  • Control: one passes a flag that steers the other's logic.
  • Stamp: one passes a whole record when a single field is used.
  • Data: only simple data items cross the interface.

Worst case: two modules both increment one global counter, so a bug in either corrupts both. Best case: a caller passes one amount in rupees and receives the tax back.

Object-oriented concepts and design classes

Object-oriented design replaces functions with objects. A class is a template holding attributes (data) and operations (behaviour). An object is one instance of a class. Encapsulation keeps an object's data private and reachable only through its operations, which is information hiding at object level. Inheritance lets a new class reuse and extend an old one: PermanentEmployee is an Employee. Polymorphism lets one operation name behave differently per class: printPayslip() works for permanent and contract staff.

A well-designed class is:

  • complete: it has every attribute and operation its responsibilities need;
  • sufficient: it has nothing extra, no unused field or just-in-case method;
  • primitive: each operation is easy to implement because it works directly on the class's own data (a method that must fetch data from five other classes is not primitive);
  • small and single-purpose: each operation does one thing, not five;
  • cohesive: all its parts serve one abstraction.

Refactoring is a small, behaviour-preserving change that improves structure: renaming a method, extracting a function, moving a field to the class it belongs to. It is done in tiny steps with tests run after each, so the design improves without breaking.

Aspects handle concerns that cut across many modules, such as logging or security. Instead of copying the same code into twenty classes, the concern is written once and woven in by the compiler or framework.

Worked example

Question. One class, Billing, does four jobs: it computes GST on an amount, prints a thermal receipt, writes a row into MySQL, and sends an SMS. Use the ranking where cohesion scores 1 (coincidental, worst) to 7 (functional, best) and coupling scores 1 (content, worst) to 5 (data, best). (a) Score Billing's cohesion. (b) Split Billing into four classes plus a controller; give the class count and the cohesion score of each new class. (c) Score the coupling Billing to GstCalculator. (d) Score the coupling Billing to BillRepository when the whole Bill object is passed, and say what to pass instead.

  1. The four jobs share no data and no order. They are tied only by living in one class, so cohesion is coincidental.
  2. Coincidental cohesion scores 1 on the 1 to 7 scale. This is the worst level.
  3. Split into GstCalculator (tax), ReceiptPrinter (format), BillRepository (storage), SmsNotifier (message). Each now does exactly one job.
  4. Functional cohesion scores 7 for each of the four new classes.
  5. Billing stays as a controller that calls all four, so the class count is 4 + 1 = 5.
  6. Billing to GstCalculator: one amount in rupees goes in, the tax amount comes back. Only simple data crosses, which is data coupling.
  7. Data coupling scores 5 on the 1 to 5 scale. This is the best level.
  8. Billing to BillRepository: the whole Bill object crosses while the repository needs only a few fields, which is stamp coupling.
  9. Stamp coupling scores 4. The fix is to pass only the simple data items the repository actually uses, such as billId and amount; that reaches data coupling, score 5. A narrowed Bill DTO cuts the damage but is still a record with several fields, so it stays stamp coupling.

Answer. Billing's cohesion is 1 (coincidental, worst); the split gives 5 classes, each with cohesion 7 (functional); Billing to GstCalculator is data coupling, 5 (best); Billing to BillRepository is stamp coupling, 4, and passing only billId and amount gives data coupling, 5.

Exam traps

  • Direction slip: high cohesion is good, high coupling is bad. Writing it the other way round is the most commonly lost mark in this chapter.
  • Functional decomposition and modularity are different: decomposition is the act of splitting, modularity is the property of the result.
  • Stamp versus control coupling: passing a whole employee record for one field is stamp coupling; passing a boolean that steers the other module's logic is control coupling.
  • Logical cohesion groups similar functions selected by a flag, while coincidental cohesion has no relation at all. Coincidental is worse, so it scores lower, not higher.
  • Sequential beats communicational: parts that feed one another (output of one is input of the next) score 6; parts that merely work on the same data score 5.

3.3 Architectural design and styles: layered, client-server, pipe-filter

Software architecture is the set of early, large decisions about a system: its main parts, how those parts talk, where data lives, and what runs on which machine. A style is a named template for those decisions, such as layered or client-server. Architecture matters because it fixes the qualities that are hard to add later — performance, security, modifiability — and because every later design choice must fit inside it. Booking apps, banking systems and compilers all carry an architecture whether or not anyone named it.

You need: 3.2 on modules and decomposition, and Unit 2 on non-functional requirements.

Architecture is chosen early, then checked

A subsystem is a group of modules that does one part of the job. The architecture names those subsystems and the rules for how they may interact.

  1. Take the structural elements from the requirements: use cases, data flow diagrams, entities, and the non-functional needs from Unit 2.
  2. Group the elements into subsystems, using high cohesion and low coupling from 3.2.
  3. Map the subsystems onto a named architectural style, or a mix of styles.
  4. Check the result against the quality attributes: performance, security, availability, modifiability, testability. If a check fails, change the grouping or the style.

Architecture is fixed early because the cost of change grows with time. A wrong module boundary can be repaired in a week; a wrong choice of tiers may need new servers, new contracts and a new deployment plan. The style also sets what is easy. A layered system makes a new screen easy and a tight real-time loop hard. A pipe-filter system makes a new processing step easy and an interactive undo button hard.

Data design is part of the same early work. Entities from the requirements model become tables. A primary key is a column, or a small set of columns, that uniquely identifies one row. A foreign key is a column that points to a primary key in another table. Normalisation is the process of removing repeated data so that one fact is stored once; third normal form is a common target. Good data design reduces update errors and makes queries predictable.

Three workhorse styles

  • Layered. Structure: code is grouped into layers. Each layer offers services to the layer above and uses the layer below. A layer is a logical group of code, not a machine. Helps: modifiability and testability, because a layer can be replaced if its interface stays. Hurts: performance, because a request may pass through several layers. Used in: enterprise web applications and business software.
  • Client-server. Structure: a client sends requests; a server holds shared data or services and sends replies. Helps: central control of data and security. Hurts: the server can become a bottleneck or a single point of failure. Used in: web applications, database-backed booking systems, and most network services.
  • Pipe-filter. Structure: a filter reads input, transforms it, and writes output. A pipe is a connector that carries data from one filter to the next. Helps: reuse and composition, because filters can be rearranged. Hurts: interactivity and latency, because data must flow through every stage. Used in: compilers, Unix-style command pipelines, and log or image processing.

Layer and tier are not synonyms. A layer is a logical group of code. A tier is a physical place where code runs. A design with three layers can be deployed in two tiers when the business-logic layer and the data-access layer run on one server.

Repository or blackboard style: components share one data store and read or write it as needed; it suits data-heavy, uncertain problems and gives weak control over flow. Event-driven style: components react to events instead of calling each other; it gives loose coupling but makes the overall flow hard to trace.

Case study: a seat-booking system on three tiers

Take a train seat-booking system. The requirements give these structural elements: a search screen, a seat map, a fare rule, a seat-lock rule, payment, ticket records, and train and seat data. Group the code into three layers — presentation, business logic and data access — and treat the database as the data tier that stores the tables.

The presentation layer holds screens and forms. The business-logic layer holds rules: a seat is locked for a few minutes during payment, a child fare is half the adult fare, and a cancellation is allowed only before departure. The data-access layer turns those rules into queries and maps rows to objects. The database is not a layer of code; it is the data tier, holding tables such as TRAIN, SEAT, BOOKING and PASSENGER, with primary keys and foreign keys.

Deploy this as three tiers: a browser or mobile app as the presentation tier; an application server running business logic and data access as the middle tier; and a database server as the data tier. The quality check matters. The seat-lock rule needs a transaction so two users cannot book the same seat. The layered split makes a new payment method easy to add in the business layer, and it lets a load balancer put two application servers behind the presentation tier. The cost is extra network hops, which is acceptable for a booking site but wrong for a fast in-memory game loop.

Worked example

Question. A log pipeline has three filters. Parse takes 4 ms per record, validate takes 6 ms, and format takes 2 ms. Records arrive at 100 per second. (a) What is the steady-state throughput of the pipeline? (b) What is the latency of one record? (c) Where is the bottleneck, and what does a second copy of that filter buy?

  1. Convert each filter time to seconds: parse = 0.004 s, validate = 0.006 s, format = 0.002 s.
  2. In steady state, a pipe-filter pipeline cannot process faster than its slowest filter. The slowest filter is validate at 0.006 s per record.
  3. Capacity = 1 ÷ 0.006 s = 166.7 records per second. Arrivals are 100 per second, which is below capacity, so the pipeline is not saturated: steady-state throughput = 100 records per second (arrival-limited) and the queue stays bounded.
  4. Latency of one record through an empty pipeline = 0.004 + 0.006 + 0.002 = 0.012 s = 12 ms. This is the minimum; under load a record also waits behind earlier records, so measured latency is higher.
  5. The bottleneck is validate. Two copies of validate working in parallel give validate 2 ÷ 0.006 s = 333.3 records per second, so parse (1 ÷ 0.004 s = 250 records per second) becomes the new bottleneck and the pipeline's capacity rises to 250 records per second.

Answer. Capacity is about 166.7 records per second; actual throughput is 100 records per second because arrivals are slower. Latency through an empty pipeline is 12 ms, higher under load. The bottleneck is validate; a second validate filter lifts validate to about 333.3 records per second, so parse becomes the bottleneck and the pipeline's capacity rises to 250 records per second.

Exam traps

  • Treating layer and tier as synonyms. A layer is logical code grouping; a tier is a physical runtime or deployment place. A 3-layer design can be 2 tiers.
  • Saying pipe-filter throughput is the sum of filter times. Sum gives latency, not throughput. Throughput is set by the slowest stage: throughput of a stage with n parallel copies = n ÷ (time per record of one copy of the slowest stage).
  • Calling any client-server system a 2-tier system. The label depends on where presentation, business logic and data actually run, not on the fact that a client calls a server.
  • Assuming architecture cannot change. It is fixed early because change is costly, not because change is impossible.

3.4 Design patterns: MVC, observer, adapter, facade

A design pattern is a named, reusable answer to a design problem that keeps returning. It is not code to copy. It is a small arrangement of roles and responsibilities that you adapt to your own classes. Patterns exist because designers kept meeting the same problems: one change must reach many screens, an old API must fit a new app, and a messy subsystem must look simple. A pattern is worth using only when its cost — extra classes, indirection, learning time — is smaller than the problem it removes. Four patterns common in web and Android apps follow.

You need: 3.2 for abstraction and information hiding, and 3.3 for where MVC usually appears.

Why patterns exist and the three families

A pattern has a name, a problem, a solution and consequences. The name lets a team say 'use an observer here' and share a design idea in three words. The consequences are the costs you accept. The Gang of Four (GoF) grouped patterns into three families.

FamilyWhat it decidesTwo examples
CreationalHow objects are madeSingleton, Factory Method
StructuralHow classes and objects fit togetherComposite, Proxy
BehaviouralHow objects share work and messagesStrategy, Command

Creational patterns hide construction choices. Structural patterns shape composition. Behavioural patterns organise communication. The four patterns below are not the whole catalog; they are the ones that appear most in design questions.

Use a pattern when the problem is recurring and the pattern's vocabulary helps the team. Do not force a pattern into a one-off class. Patterns are not frameworks; a library is code you call, a framework is code that calls your code (inversion of control), and a pattern is a design you apply.

MVC and observer

MVC splits an interactive application into three roles. The model holds data and business rules. The view draws the data. The controller receives user input, updates the model, and chooses a view. A button press goes to the controller, not straight to the model. The model does not know which views show it, so you can change the screen without changing the rules. Cost: more classes and a flow that jumps between three places, so a small screen may not need MVC. Some syllabi call MVC an architectural pattern because it organises the whole application, not one class.

Observer defines a one-to-many dependency. A subject holds a list of observers. Each observer registers by calling subject.attach(this); the subject keeps the observer in its list. When state changes, the subject calls notify() on every observer. In push, notify carries the new state as an argument. In pull, notify only says 'changed'; each observer calls getState() to fetch what it needs. Pull is flexible but costs extra calls. Push sends data that some observers may ignore. Cost: observers must be attached and detached correctly; a forgotten observer receives updates forever and can leak memory. Use it for stock feeds, news alerts, GUI event listeners and model-to-view updates.

Adapter and facade

Adapter converts the interface of one class into the interface a client already expects. The client calls its own method name; the adapter translates to the old method. In an object adapter, the adapter holds one instance of the old class and delegates. In a class adapter, the adapter inherits from the old class; in Java and C# this works only when the target is an interface (class Adapter extends Adaptee implements Target), because a class can extend only one class. Use an adapter when an old bank API has debitAcct(String account, int paise) but your app has pay(String account, double rupees). The adapter multiplies rupees by 100, converts to int, and calls debitAcct. Cost: one more object and a place where conversion bugs hide; rounding must be decided.

Facade gives one simple interface to a set of subsystems. A DashboardFacade may have loadSalesPanel(), loadStockPanel() and loadAlertsPanel(); each hides calls to many classes. A facade does not add new function. It only makes the same function easier to call. It reduces coupling for the client, but the subsystems still exist and can be used directly. Cost: if the facade becomes the only door, a missing method forces a change in the facade. Use it for dashboards, startup sequences and wrapping a library with many setup steps. Do not call it an adapter: an adapter changes one interface; a facade simplifies many. UI design patterns such as dashboard, wizard and breadcrumb are reusable screen layouts, not GoF patterns.

Worked example

Question. Question (6 marks). Pick the best pattern for each case and justify with the numbers. (a) A stock-price feed has 500 registered clients and must push every price change to all of them; the feed changes 20 times per second. Compare with polling every 100 ms. (b) A new app must call an old bank API whose method is debitAcct(String account, int paise). The app works in rupees, for example ₹250.75. (c) A dashboard screen has 30 subsystems behind it and the screen code should call one method per panel.

  1. (a) Pattern: observer. Subject = price feed, observers = 500 clients. Push messages per second = 20 × 500 = 10,000.
  2. Polling: 100 ms = 0.1 s, so each client polls 1 ÷ 0.1 = 10 times per second. For 500 clients, requests per second = 10 × 500 = 5,000. Push sends 10,000 update messages/s; polling sends 5,000 requests/s even when the price does not change.
  3. (b) Pattern: adapter. Convert ₹250.75 to paise: 250.75 × 100 = 25,075 paise. The adapter calls debitAcct(account, 25075).
  4. (c) Pattern: facade. One DashboardFacade with methods such as loadSalesPanel() hides the 30 subsystems. It adds no new function.

Answer. (a) observer, (b) adapter with 25,075 paise, (c) facade.

Exam traps

  • Adapter versus facade: an adapter changes one interface into the interface the client expects; a facade puts one simpler interface over many classes. 'Wraps many classes to make them easy' is facade.
  • MVC model is not the database. The model is data plus business rules; a database is one way to store it.
  • Observer notify() is not always the same as update(). In pull, notify only signals; getState() fetches the state.
  • A class adapter is not impossible in Java. It works when the target is an interface (extends Adaptee, implements Target); when the target is a class, Java needs an object adapter.
  • A facade adds no new business function. If it adds new behaviour, it is more than a facade.

3.5 User interface design

The user interface is the part of the software a person actually touches: the screens, the buttons, the messages. Everything else — the database, the architecture, the patterns in 3.4 — stays hidden. So users judge quality by the interface alone. Interface design is the activity that decides what appears on each screen, in what order, and which control the user presses. It is used wherever a human sits at the end of the software: a UPI payment screen, an IRCTC ticket booking, a hospital reception counter, a shop's billing terminal.

You need: 3.1 (usability as a quality attribute) and Unit 2 (use cases supply the tasks the interface must support).

The three golden rules

A user never sees your architecture. They see a screen, press a button, and decide whether the software is good. Usability — easy to learn, efficient to use, easy to remember — is a quality attribute, and the interface is where it is judged (see 3.1). Three rules cover most interface decisions.

  • Rule 1 — place the user in control. The user decides what happens next. Every long action has a Cancel, and nothing irreversible happens without a confirmation: show the bill, then take the money.
  • Rule 2 — reduce the user's memory load. The screen remembers, the user does not. Show a value the system already knows as read-only text instead of asking for it again, and offer a drop-down of valid choices instead of a blank box the user must fill from memory.
  • Rule 3 — make the interface consistent. The same thing looks and behaves the same everywhere. Use one word for one action on every screen — "Pay" everywhere, not "Pay" here and "Submit" there — and give each colour and icon one fixed meaning.

Each rule turns into concrete moves: a Cancel button, a read-only amount, a drop-down of states, one action word. Those moves are what earns marks. "Make it attractive and simple" is not an answer.

Analysis, then design, then evaluation

Four analyses come before any screen is drawn. Their input is the requirements model, above all the use cases of Unit 2.

  • User analysis — who uses it, and how skilled are they? A first-time customer, a clerk who uses it 200 times a day, a manager who opens it monthly. Experts want keyboard shortcuts; beginners want full labels.
  • Task analysis — what must the user do, in what order? Take each use case and list its steps: identify the account, see the amount, pay, get a receipt.
  • Content analysis — what is displayed on each screen: text, numbers, dates, photos, a chart? A 12-digit number needs spacing; a rupee amount needs two decimals.
  • Environment analysis — where is it used? A counter in bright sunlight, a crowded bus, a noisy shop floor, a quiet office. Light, screen size, network speed and interruptions all change the design.

Then comes the design step: choose the layout and the controls for each screen. Then evaluation: build a cheap prototype — paper or a clickable mock — put a real user in front of it, and count where they hesitate. Fix those places and evaluate again. The loop ends when the hesitation stops.

A modern graphical interface is built from a small set of controls. Each has one job and one rule of use.

Error messages and accessibility

An error message is the interface at its most stressful, so it needs the strictest rules.

  1. Say what happened, in plain language: "The consumer number must be 12 digits", not "ERR-4071".
  2. Say what to do next: "Check the number printed on your bill and type it again".
  3. Put the message next to the field that caused it, keep everything the user already typed, and never let a bare code be the whole message.

Accessibility means the interface still works for people with low vision, colour blindness, or no mouse. Three basics: body text at least about 16 px on a phone, with a contrast ratio of at least 4.5:1 for normal text; never let colour alone carry a meaning, so an error is red and has an icon and words; and every control reachable by keyboard alone, with a visible focus outline. Usability and accessibility testing is covered in Unit 4.

Worked example

Question. Exam traps

  • "Make it attractive and simple" scores nothing. Marks come from naming the analysis step, the golden rule, and one concrete control.
  • Do not count each field as one memory item. Count each distinct thing the user must recall — a number, an amount, a code read from an SMS.
  • Interface design is not GUI coding and not architectural design; it starts after the task and content are analysed.
  • A bare code as an error message ("Error 4071") is always wrong. Say what happened and what to do next.
  • Skipping environment analysis is a favourite slip: a screen that works in a quiet office fails at a counter in bright sunlight.

3.6 UML class diagrams

A class diagram is the static picture of an object-oriented system. It lists the classes, the data each class holds (attributes), the operations it offers, and the relationships between classes. It exists so that designers, programmers and testers share one view of the data model before code is written. You use it to check multiplicity, inheritance and ownership — for example, whether one order can have many order lines, or whether an account can survive without a branch. On a phone screen, read the boxes first, then the lines.

You need 3.2 Design concepts for classes and objects, and Unit 2 for class-based requirements models.

The class box and the UML frame

UML has three building blocks: things, relationships and diagrams. A class is a thing. A line between classes is a relationship. A class diagram is one diagram made of both. The class itself is drawn as a rectangle with three compartments: name, attributes, operations.

Visibility marks sit before each member. Use + for public, − for private, # for protected and ~ for package. Underline a static member; it belongs to the class, not to one object. Write an abstract class name in italics or add {abstract}. Mark an interface with «interface» and keep its name italic.

MarkMeaning
+public — any class can use it
−private — only this class can use it
#protected — this class and its subclasses
~package — classes in the same package

Attributes usually show a type: balance: Money. Operations show parameters and a return type: deposit(amount: Money): Boolean. The diagram is static: it shows what can exist, not the order in which calls happen. Message order belongs to 3.7 interaction diagrams.

Relationships carry the rules

An association is a solid line between classes. A role name at an end says what that end means, such as accountHolder. Multiplicity says how many objects at one end may link to one object at the other end. Write 1, 0..1, *, 1..*, or a range such as 2..4. Read each label from the class at the far end.

RelationshipSymbol
Associationsolid line, optional arrow for navigability
Aggregationhollow diamond at the whole
Compositionfilled diamond at the whole
Generalizationhollow triangle pointing to the parent
Dependencydashed arrow to the thing used
Realizationdashed line with hollow triangle to an interface

Aggregation means a part can live without its whole: a department has teachers, but a teacher still exists if the department closes. Composition means the part dies with its whole: an order line has no meaning after its order is deleted. Generalization is an is-a link; a savings account is an account. Dependency is a uses link and is weaker than association. Realization is a class promising to obey an interface.

Two exam slips are common. The hollow diamond is aggregation and the filled diamond is composition. A plain line with multiplicity is an association, not a dependency; dependency uses a dashed arrow.

From a paragraph to a finished diagram

  1. Underline the nouns in the requirement text. Keep the nouns that the system must remember; drop synonyms, outside systems and simple attributes.
  2. Write each class box with its name, attributes and operations. Add visibility marks. Underline static members and mark abstract classes or interfaces.
  3. Draw each relationship. Choose association for a lasting link, aggregation or composition for whole–part, generalization for is-a, dependency for uses, and realization for implements.
  4. Add role names and multiplicity at every end. Read each requirement sentence back against the diagram; fix any line that cannot answer how many.

An object diagram is a snapshot of one moment. It uses the same boxes, but object names are underlined and values are shown, such as ravi: Customer. Use it to test one example; use the class diagram to state the rules for all examples.

Worked example

Question. Draw the class diagram for a bank. A customer holds one or more accounts. An account may have two or more holders when it is a joint account. A branch has many accounts. Exam traps

  • A class diagram never shows time or message order. If your arrows carry a fixed sequence, you have drawn a sequence diagram, not a class diagram.
  • The hollow diamond is aggregation; the filled diamond is composition. A composition part dies with its whole.
  • Multiplicity is read at the far end. A line marked 1 .. 0..* means one object at this end links to zero or more at the other end; it does not mean the class has at most one object.
  • An abstract class and an interface are not the same. Both may have operations, but an interface has no state and is marked «interface».
  • Not every noun is a class. A name or amount that is stored inside one class is an attribute, not a separate box.

3.7 UML interaction diagrams: sequence and collaboration

An interaction diagram draws one scenario from a use case: which objects take part, what messages they send each other, and in what order. Two forms are covered here: the sequence diagram and the collaboration diagram, called the communication diagram in UML 2. UML 2 also has timing and interaction overview diagrams. The sequence diagram puts time down the page, so you read the story top to bottom. The collaboration diagram puts the same story on a web of links and carries the order in nested numbers. Teams use these diagrams to check a design against its use cases before any code is written.

You need 3.6 for the objects and the classes they come from, and Unit 2, Scenario-based modeling and use cases, for the scenarios themselves.

One scenario, two views

A use case says what the system does for an actor. A scenario is one path through that use case — the happy path, or one failure path. An interaction diagram draws one scenario as objects and the messages they exchange. It answers a question a class diagram cannot: at run time, who talks to whom, and in what order.

Three words carry the whole chapter. An object is one instance of a class from 3.6, written as name:Class with the whole name underlined, or as :Class when the name is not needed. A message is a request one object sends to another; it has a name, arguments and a direction. A link is a connection between two objects along which messages can travel. Links come from the associations in the class diagram.

One diagram shows one scenario, not every path. A use case with five scenarios gets five interaction diagrams, or one diagram with frames that select between the paths. Drawing everything at once gives a picture nobody can read.

Sequence diagram: time runs down the page

Each actor or object sits in a box across the top, with a dashed vertical line, the lifeline, hanging below it. Time runs downward, so a message drawn lower happens later. The left-to-right order of the boxes is free; the usual habit is actor on the left, the objects it drives to the right.

A message is an arrow from one lifeline to another, labelled with its name and arguments. The narrow rectangle on a lifeline is an activation bar: the object is busy handling a call while the bar is drawn. Bars nest, because a call made inside a call keeps the caller active.

ArrowMeaning
Solid line, filled arrowheadSynchronous call; the sender waits for the return
Solid line, open arrowheadAsynchronous call; the sender carries on without waiting
Dashed line, open arrowheadReturn, the reply to an earlier call

Objects can appear and disappear. A «create» message points at a box placed lower down, because that object did not exist earlier. A small X at the end of a lifeline marks destruction.

Frames group messages. A frame is a rectangle with a pentagon label in the corner. The alt frame has two or more operands separated by a dashed line, each carrying a guard in square brackets, and exactly one operand runs. The loop frame repeats its contents; write the count or the condition in the label, as in loop(3) or loop[while more items].

Collaboration diagram: numbering carries the order

A collaboration diagram draws the same objects as boxes joined by links. There is no time axis and no lifeline. Messages sit on or beside a link as small arrows, each labelled with a number that fixes its order.

The numbering is nested. The first message of the scenario is 1. A message sent while handling message 1 is 1.1; a message sent while handling 1.1 is 1.1.1. When message 1 is fully handled, the next top-level message is 2, and its sub-messages are 2.1, 2.2 and so on. The depth of the number is the depth of the call, and reading the numbers in order reproduces the top-to-bottom order of the sequence diagram.

  1. List the objects that take part and draw one box for each; link the pairs that exchange messages.
  2. Walk the sequence diagram from top to bottom. Give each new top-level message the next whole number 1, 2, 3 …
  3. When a message is sent while another is being handled, add a decimal level to the current number: 1.1, then 1.1.1, and so on.

To convert back, read the numbers in ascending order and draw each message as a new arrow, top to bottom.

A return is drawn dashed and is not a new call. Because the layout is free, a collaboration diagram stays compact when there are many objects; a sequence diagram is easier to follow when the story is long and full of returns.

Worked example

Question. Convert this sequence into a collaboration diagram: the user inserts a card (call 1), the ATM asks the bank to verify the PIN (call 1.1), the bank replies OK (return on 1.1), the user asks for ₹2,000 (call 2), the ATM debits the bank (call 2.1), the bank approves (return on 2.1), the ATM hands out the cash (return on 2). (a) Write the numbering. (b) How many links are there, and how many messages travel on each?

  1. Objects: User (an actor), ATM and Bank. Draw three boxes.
  2. Links: messages travel between User and ATM, and between ATM and Bank. No message goes directly from User to Bank, so there is no User–Bank link. That is 2 links.
  3. Number the first top-level call: 'insert card' is 1. Sent while handling it, 'verify PIN' is 1.1. The PIN reply is a return; draw it dashed and label it with the call it answers, 1.1.
  4. The first call is fully handled, so the next top-level call, 'withdraw ₹2,000', is 2. Inside it, 'debit ₹2,000' is 2.1. The approval is a return on 2.1, and the cash is a return on 2. Draw both dashed.
  5. Count messages per link. User–ATM: call 1, call 2 and the cash return on 2, that is 3 messages. ATM–Bank: call 1.1, its return, call 2.1 and its return, that is 4 messages.
  6. Check: 3 + 4 = 7 messages, the same seven arrows as the sequence diagram.

Exam traps

  • Drawing a time axis on a collaboration diagram, or leaving its links unnumbered. Collaboration means nested numbers on links and no time axis; on a sequence diagram time runs down the page, so numbers there are optional.
  • Treating a return as a new call. A return is a dashed arrow with an open arrowhead. A return closes the callee's activation bar. It never opens a new activation bar.
  • Drawing every scenario of a use case on one diagram. One interaction diagram holds one scenario; the rest need their own diagram or an alt frame.
  • Mixing up alt and loop. alt picks exactly one operand out of several; loop repeats the same operand.
  • Forgetting the guard condition in square brackets on alt operands, so the reader cannot tell when each branch runs.

Calls: 1 login, 1.1 check, 2 open report, 2.1 fetch data. The two database replies are returns, drawn dashed and labelled with the call they answer: reply on 1.1 and reply on 2.1. Depth follows calls only; the database check sits inside login and the fetch sits inside open report.

Apply Messages in a collaboration diagram: call 1 (A→B), call 1.1 (B→C), return on 1.1 (C→B), call 2 (B→A), call 2.1 (B→C). How many links are there, and how many messages travel on each? 4 marks

Two links. A–B carries calls 1 and 2, that is 2 messages. B–C carries call 1.1, its return, and call 2.1, that is 3 messages. Total 5 messages.

Analyze A student numbers the arrows 1 to 7 down the left side of a sequence diagram. Are the numbers needed, and where are message numbers required? 4 marks

The ordering is already carried by vertical position, so the numbers are optional and redundant: UML allows sequence numbers there, but they add nothing. Message numbers are required on a collaboration diagram, nested as 1, 1.1, 2, because it has no time axis.

Analyze During a withdrawal the ATM either dispenses cash or shows 'insufficient funds'. Which combined fragment do you use, and what goes in the brackets? Why is loop wrong here? 5 marks

alt, with two operands. Guards: [balance ≥ amount] on the first, [else] on the second. loop is wrong because only one branch runs once, not a repetition.

3.8 UML state chart, activity, component and deployment diagrams

Four UML diagrams answer four questions. A state chart: how does one object change over its life? An activity diagram: in what order do workflow actions run? A component diagram: how do software parts plug together through interfaces? A deployment diagram: which hardware runs which software? Class diagrams show structure but not behaviour over time; interaction diagrams show one scenario but not every state. These four complete the behavioural and physical views.

You need the notation from 3.6 and 3.7, and a use case scenario from Unit 2 to draw the flow.

State chart: one object over its life

A state chart draws the life of one object. A state is a condition held for a while: an order in Placed, a phone in Ringing. A transition is an arrow between states; it fires only when its event occurs. A guard is a condition in square brackets that must also be true. An action is work on the way, written after a slash.

Start is a filled black circle, the initial state (a pseudostate). End is a bullseye, the final state. A full label reads event [guard] / action, for example pay [amount ≤ balance] / debit.

A state may contain its own chart: a composite state. Preparing could hold Chopping and Cooking inside it, so the outer chart does not repeat every small step. An arrow into a composite state starts its inner chart at the inner initial state, which saves transitions.

Use a state chart for one object with a small, clear set of states and events: an order, an ATM session, a phone call, a lift. Do not use it for a workflow shared by many actors, which is an activity diagram, or to list a class's operations. Testers read state charts to derive test cases (Unit 4).

Activity: the order of actions in a workflow

An activity diagram is a flowchart of actions. A rounded rectangle is an action, one step of work. A filled circle is the initial node; the bullseye is the final node. A diamond with one arrow in and many out is a decision: each outgoing arrow carries a guard and exactly one is taken. A diamond with many in and one out is a merge, where split flows meet again.

A thick bar is a fork when one flow leaves it as several parallel flows, and a join when parallel flows arrive and wait for each other. A fork and join pair models work that truly happens at the same time, such as charging the card and reserving the stock together.

Swimlanes divide the diagram into columns, one per actor or department, and each action sits in the lane of whoever performs it. An IRCTC booking shows the passenger in one lane, the payment gateway in another, the booking service in a third, so responsibility is visible.

Use an activity diagram for a business process, the flow inside a use case, or an algorithm with decisions and parallel steps. Do not use it for the states of one object: it has no memory of state, only a sequence of actions.

Component: software parts and their plugs

A component is a replaceable piece of software that hides its internals and offers a defined set of interfaces. It is drawn as a rectangle with the keyword «component». It names something you could build, test and swap on its own, such as PaymentService or NotificationService.

A provided interface is a ball on a stick: what the component offers. A required interface is a socket, a half circle: what the component needs from others. A ball fitting into a socket means one component's offer satisfies another's need, and that picture gives the dependency direction.

A port is a small square on the component's edge. It is a distinct interaction point where a named set of interfaces is exposed. A PaymentService can expose a Card port and a UPI port, and clients depend only on the port they use.

Use a component diagram to show module-level architecture and who depends on whom, especially before planning builds (Unit 5). Do not use it for classes, attributes or method calls.

Deployment: which hardware runs what

A deployment diagram shows the physical side. A node is hardware or an execution environment, drawn as a 3-D box: an application server, a phone, a router, or a container or JVM running inside one. The stereotypes «device» and «execution environment» make the difference explicit.

An artifact is a real file that gets deployed: an executable, a JAR, a WAR, a config file. It is drawn as a rectangle with a small document icon and sits inside the node that runs it. One node may hold several artifacts, and one artifact may appear in two nodes if copied.

A communication path is a solid line between two nodes, labelled with its protocol: HTTP, TCP/IP, RMI, JDBC. The line is normally undirected; the protocol label is what matters. If you add an arrowhead, note that it shows the request direction, not a UML rule. A phone node holding the app artifact talks HTTP to an application-server node holding the WAR, which talks JDBC to a database node holding the schema artifact.

Use a deployment diagram to plan servers, protocols and networks, and to show a distributed system on one page. Do not put software classes inside nodes, and do not draw one for a single-laptop program with no network.

Worked example

Question. A food-delivery order moves Placed → Accepted → Preparing → Out for delivery → Delivered, and may be cancelled from any step before Out for delivery. (a) How many states and how many transitions does this state chart have? (b) What blocks a late cancellation?

  1. Main path named states: Placed, Accepted, Preparing, Out for delivery, Delivered = 5 named states.
  2. Add Cancelled = 6 named states. The initial pseudostate and final state are extra symbols drawn, not counted as named states. If an examiner counts both, 6 + 2 = 8 symbols are drawn.
  3. Forward transitions: Placed→Accepted, Accepted→Preparing, Preparing→Out for delivery, Out for delivery→Delivered = 4 transitions.
  4. Cancel transitions: Placed→Cancelled, Accepted→Cancelled, Preparing→Cancelled = 3 transitions. There is no arrow from Out for delivery.
  5. Total transitions = 4 forward + 3 cancel = 7.
  6. Part (b): the missing cancel arrow from Out for delivery blocks late cancellation; a transition exists only where drawn. A data guard such as [payment not captured] can also restrict an early cancel.

Answer. The chart has 6 named states and 7 transitions (4 forward and 3 cancel). The initial pseudostate and final state are extra symbols, not named states.

Exam traps

  • Mixing up activity and state charts. Many objects and one flow is an activity diagram; one object and many events is a state chart.
  • Putting classes inside deployment nodes. Nodes are hardware or execution environments; only artifacts go inside them.
  • Reversing ball and socket. The ball is the provided interface, the socket is the required interface.
  • Drawing a decision diamond with no guards, or drawing a decision where a fork is meant. Parallel work needs the thick bar, not the diamond.
  • Counting the initial pseudostate and the final state as ordinary states, which inflates the state count by two. The initial symbol is a pseudostate, and the bullseye only marks where the chart ends; count neither with the ordinary states.

Check yourself

Remember In a state chart, what do the filled black circle and the bullseye mean? 2 marks

The filled circle is the initial pseudostate, where the object starts. The bullseye is the final state, where its life ends.

Understand Why does a composite state reduce the number of transitions in a chart? 3 marks

Events handled inside the composite state are not drawn on the outer chart. The outer chart needs only one arrow into the composite state, and its inner initial state places the object correctly, so repeated arrows on the outer level disappear.

Apply A state chart has states Idle, Running, Paused, Stopped with transitions start (Idle→Running), pause (Running→Paused), resume (Paused→Running), stop (Running→Stopped), stop (Paused→Stopped). How many named states and transitions are drawn? 3 marks

Named states: Idle, Running, Paused, Stopped = 4. The initial pseudostate and final state are extra symbols if drawn. Transitions: start, pause, resume, stop, stop = 5.

Apply A web application runs in a browser, a web server holding app.war, and a database server. Name the nodes, the artifacts and one protocol on each communication path. 4 marks

Nodes: the client device, the web server, the database server. Artifacts: browser page files in the client, app.war in the web server, the schema in the database server. Protocols: HTTP between client and web server, JDBC (or TCP/IP) between web server and database.

Analyze A loan approval process involves three departments, two approvals that run at the same time, and one reject path. Which diagram do you choose, and why is the other candidate wrong? 5 marks

An activity diagram with swimlanes for the three departments, a fork and join for the two parallel approvals, and a decision diamond with guards for approve and reject. A state chart is wrong because the process spans many actors, not the life of one object.

Understand What does a ball fitting into a socket tell a designer that a plain arrow between two boxes does not? 2 marks

It names which interface is offered and which is needed, so the dependency direction and the contract are explicit.

Analyze Why can cancel not fire from Out for delivery in the order state chart? 4 marks

The three cancel arrows start only at Placed, Accepted and Preparing. A transition is legal only from the state where the arrow begins; the missing arrow from Out for delivery blocks it. A guard like [payment not captured] can test data, but a guard cannot name the current state to choose arrows.

Takeaways

  1. Design is the translation step: the requirements model says what is needed, the design model says how the software will be built, in five sub-models — data, architecture, interface, component and deployment.
  2. A design choice is never good in the abstract; it is good only when it satisfies the quality attributes that matter for that product.
  3. Abstraction and functional decomposition let you think about a large system at one level at a time, which is the only way a human can hold it in mind.
  4. High cohesion with low coupling is the one-line summary of a maintainable module structure.
  5. Architecture is the set of decisions that are expensive to change later, so it deserves the earliest and most careful thought.
  6. An architectural style is a named template — layered, client-server, pipe-filter — that brings known trade-offs you can argue about before you code.
  7. A pattern is worth using only when the problem it removes is bigger than the indirection it adds.
  8. User interface design starts with analysis of users, tasks, content and environment, then applies the three golden rules: user in control, low memory load, consistency.
  9. Each UML diagram answers exactly one question; drawing all of them for a small system wastes time, drawing none loses the design.

Remember and understand

Understand Define software design. Explain the five elements of the design model and state what each one contains. 10 marks

Understand Explain cohesion and coupling. List the types of each and state which type is desirable and why. 12 marks

Definitions of cohesion and coupling; Cohesion types from worst to best: coincidental, logical, temporal, procedural, communicational, sequential, functional; Coupling types from worst to best: content, common, control, stamp, data, routine call, non-cohesive; Goal: highest practical cohesion, lowest practical coupling; Trade-off: pushing coupling down can split one job across modules and hurt cohesion; Small example showing a change rippling when coupling is high.

Understand Describe the layered, client-server and pipe-and-filter architectural styles with a sketch, one example each, and one advantage and one drawback each. 13 marks

Layered: layers offer services downwards only; example: presentation-logic-data; advantage: replaceable layers; drawback: a request crosses many layers; Client-server: shared server, many clients, protocol as contract; example: a ticket-booking server; advantage: central data; drawback: server is a single point of failure; Pipe-filter: independent filters, pipes carry the stream; example: compiler passes or a log analyser; advantage: filters reused and reordered; drawback: poor fit for interactive dialogue; Correct symbols: boxes for components, arrows for allowed calls or data flow.

Understand State the three golden rules of user interface design and give two concrete rules or interface features that follow from each. 10 marks

Analyze and evaluate

Evaluate A railway reservation system must handle heavy peak load, stay correct on money and seats, and be maintained for years. Evaluate two architectural styles for it and recommend one with reasons tied to quality attributes. 13 marks

Analyze Compare the pipe-and-filter style with the layered style for a log-analysis tool and for an interactive banking app. Say which style fits each and why. 10 marks

Glossary

Abstraction
Ignoring detail that does not matter at the current level so that the problem can be described in a few essential ideas.
Activity diagram
A UML diagram of a workflow, showing actions, decisions, parallel splits and the start and end of the flow.
Adapter pattern
A pattern that converts the interface of a class into another interface the client expects.
Architectural style
A named, reusable template for the overall structure of a system, such as layered or client-server.
Artifact
A physical piece of deployed software, such as a jar, war, executable or configuration file, shown in deployment diagrams.
Association multiplicity
The number of objects of one class that may be linked to one object of another, written as 1, 0..1, 1..* or *.
Class diagram
A static UML diagram showing classes, their attributes and operations, and the relationships among them.
Client-server
An arrangement where a server provides shared data or services and many clients request them over a protocol.
Cohesion
The degree to which the operations inside one module serve a single, well-defined purpose.
Collaboration diagram
A UML interaction diagram that shows objects as a network with numbered messages instead of a time axis.
Component diagram
A UML diagram showing software components and the interfaces through which they plug together.
Coupling
The degree of dependence between modules, measured by how much one must know about another.
Deployment diagram
A UML diagram showing hardware nodes and which artifacts or components run on each node.
Design pattern
A named solution to a recurring design problem, described by intent, structure and consequences.
Facade pattern
A pattern giving one simplified front object over a set of interfaces in a subsystem.
Information hiding
Design rule that each module keeps its internal data and decisions private behind a published interface.
Layered architecture
An arrangement of layers where each layer serves the one above and uses only the one below.
Modularity
Splitting a system into separately buildable and testable units with clear boundaries.
MVC
Model-View-Controller: a pattern separating data and rules, display, and input handling.
Observer pattern
A pattern where a subject notifies a list of registered observers whenever its state changes.
Pipe-and-filter
An arrangement where independent filters transform a data stream passed between them by pipes.
Refactoring
Improving the internal structure of working code without changing what it does externally.
Separation of concerns
Design rule that each part of the software deals with one distinct kind of concern, such as display, rules or storage.
Sequence diagram
A UML interaction diagram with objects across the top and messages in time order down the page.
State chart diagram
A UML diagram showing the states one object can occupy, the events that move it, and its responses.
Swimlane
A partition in an activity diagram that shows which actor or department is responsible for each action.
