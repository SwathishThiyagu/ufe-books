2.1 Functional and non-functional requirements

A requirement is a statement of what the software must do, or of how well it must do it. The two families fail in different ways: 'the app lists matching books' can be shown on a screen, while 'results arrive within 2 seconds' has to be measured with a stopwatch. Separating them tells the team what to build and what to test. Every project uses this split — a hospital booking screen, a UPI payment page, an IRCTC search — and every SRS is organised around it.

You need Unit 1 (what software is, and why projects fail); the requirement list is the first artifact a project produces.

Functional and non-functional requirements

A requirement is a capability or a condition that the delivered software must satisfy. Two families exist because the two kinds of statement are checked in different ways.

A functional requirement (FR) is a service the system provides: the input it accepts, the output it returns, and what happens when something goes wrong. 'A student searches the catalogue by title, author or ISBN and the app lists matching books' is functional. The 'no match found' message belongs to the same FR.

A non-functional requirement (NFR) is a quality or a restriction on those services — how fast, how safe, how easy. 'Search results appear within 2 seconds' is non-functional. Some syllabi call NFRs quality attributes; those that restrict the solution, such as a fixed phone model, are also called constraints.

User requirements and system requirements

A user requirement is written in natural language for the customer, with no design detail: 'The librarian marks a book as lost.' A system requirement expands it into something a developer can build and a tester can check: which field changes, which roles may trigger it, how the fine is computed, and which error appears when the book is already marked lost. One user requirement often becomes several system requirements.

Both levels sit in the SRS (see 2.5) and both are gathered by talking to stakeholders (see 2.3).

Quality attributes and interface requirements

  • Performance: search answers in 2 s or less; 20 searches per second at peak.
  • Capacity: 50,000 book records stored.
  • Security: payment data travels over HTTPS.
  • Usability: a new student finds a book in 30 s without training.
  • Reliability: 99.5% uptime per month.
  • Portability: runs on Android 8 and above.

An interface requirement fixes how this system talks to another: 'the app calls the payment gateway over its REST API, over HTTPS'. Only a few universities examine interface specification as a separate heading; elsewhere it is listed under system requirements or under NFRs.

An NFR needs a number, a condition and a unit, or it cannot be verified. 'The app must be user-friendly' fails; 'a new student finds a book in 30 seconds' passes.

Worked example

Question. A university library app has five statements. R1: a student searches the catalogue and sees matching books. R2: search results appear within 2 seconds. R3: the system stores 50,000 book records, each with 4 KB of metadata. R4: the app runs on Android 8 and above. R5: payments go to the gateway over HTTPS. (a) Classify R1 to R5. (b) Compute the catalogue metadata storage in MB, taking 1 MB = 1024 KB. (c) At peak, 20 searches arrive per second and each must finish in 2 s; how many searches are in progress at once?

  1. R1 is functional and sits at user level: a service described in the student's own words.
  2. R2 is non-functional, performance: it constrains how well R1 runs, not what R1 does.
  3. R3 is non-functional, capacity: it limits stored data. Storage = 50,000 records × 4 KB = 200,000 KB.
  4. Convert: 200,000 KB ÷ 1024 KB per MB = 195.3125 MB, about 195.31 MB.
  5. R4 is non-functional, a portability or platform constraint. R5 is an interface requirement that also carries a security constraint (HTTPS).
  6. Searches in progress = arrival rate × time per search = 20 per second × 2 s = 40 searches.

Answer. R1 functional; R2 performance; R3 capacity; R4 platform constraint; R5 interface with a security constraint. Storage is 195.3125 MB (about 195.31 MB) and 40 searches are in progress at peak.

Exam traps

  • Calling 'results within 2 seconds' a functional requirement. It says how well search works, so it is a non-functional performance requirement.
  • Writing a design choice as a requirement: 'use MySQL' or 'use a hash table' describes the solution. State the need, and record a mandated technology as a constraint.
  • Leaving an NFR without a number. 'Fast', 'secure' and 'user-friendly' cannot be verified; give a threshold, a condition and a unit.
  • Mistaking capacity for function. 'Stores 50,000 records' is a limit on the system, not a service it offers.
  • Mixing levels. 'The student searches the catalogue' is a user requirement; the field list, sort order and error codes behind it are system requirements.

2.2 Requirements engineering process and feasibility study

Requirements engineering is the work that turns a need into agreed, testable requirements. It is a loop, not a one-time form: check feasibility, elicit needs, analyse them, write a specification, validate it, and manage every change. The loop exists because needs and constraints move while the project runs. Early checks stop a team from building a system that cannot be paid for, cannot be operated, or cannot be delivered on time. Indian teams use it in fee portals, UPI collections, IRCTC-style bookings and campus systems.

You need: 2.1 for requirement types and Unit 1 for life-cycle phases.

Process stages and their outputs

The process starts with feasibility: a short study that asks whether the project is worth starting. Its output is a feasibility report with a go, no-go or change-scope recommendation.

Elicitation gathers needs from users, sponsors, operators and rule owners. Output: interview notes, workshop records, source documents and a stakeholder list. 2.3 covers how to run it.

Analysis turns raw needs into consistent models and checks conflicts. Output: use cases, class models, data flow diagrams and a ranked list of non-functional targets. Links: 2.6, 2.7, 2.8.

Specification writes the agreed requirements in the SRS. Output: a reviewed document. 2.5 gives its shape.

Validation checks that the written requirements are the right ones. Output: review records, testable acceptance checks and defects sent back. 2.4 covers validation and change control.

Management runs beside every stage: it keeps versions, change requests, trace links and decisions visible. Some syllabi call the first five stages 'requirements development' and the side activity 'requirements management'.

Validation can send work back to elicitation or analysis; that feedback arrow is the loop.

Feasibility study: five checks

Feasibility asks whether a project can be done under its constraints. It is not a full business case: it does not price every alternative or forecast every year. It is a short, evidence-based screen before spending heavily.

  • Technical: can the team build it with known technology, skills and load? Compute peak rates, data volume and integration limits.
  • Economic: do benefits exceed costs? Use cost-benefit, payback and net benefit.
  • Legal: does it follow laws, contracts, audit rules, data protection and payment rules?
  • Operational: will users run it in real work? Check training, receipts, support, language and accessibility.
  • Schedule: can the required scope be delivered by the needed date? List the minimum scope and its risks.
annual net benefit = annual savings − annual operating cost − (one-time cost ÷ life in years); payback = one-time cost ÷ (annual savings − annual operating cost)

annual savings is the money saved each year; annual operating cost is gateway, SMS, support and maintenance; one-time cost is the initial build and purchase; life in years is the period over which that cost is spread; payback is the time to recover the initial cost from annual cash saving.

Use measured numbers, not wishes. A portal that saves clerk overtime but adds gateway fees can look good in a demo and weak in a ledger.

Reading the result

A project can pass one check and fail another. Report each axis separately: technical, economic, legal, operational and schedule. 'Technically feasible' is not the same as 'approved'.

Marginal economics needs a decision, not a vague answer. State the payback, the net benefit after capital, and the conditions that change the result. A short payback with a legal delay is still a schedule problem.

For the fee portal, the numbers say the build is possible and the return is thin. The team should trim scope, delay SMS receipts if allowed, or negotiate a lower gateway fee. A 3-month deadline with an unapproved audit rule is a no-go until the rule is settled.

Feasibility asks whether to start. Validation asks whether the written requirements are right. Keep the two reports separate so a weak business case is not hidden inside a good requirements document.

Worked example

Question. A college plans an online fee portal for 8,000 students. Each student pays twice a year. Peak load is 300 payments per hour. One-time budget is ₹6,00,000 over a 3-year life. Manual overtime costs ₹150 per clerk-hour and each payment needs 9 extra clerk minutes. Portal running costs: payment gateway ₹6 per payment, SMS receipt ₹1 per payment, maintenance ₹40,000 per year. Check technical, economic, schedule, operational and legal feasibility. Use the given numbers.

  1. Peak rate: 300 payments/hour ÷ 60 minutes/hour = 5 payments/minute. A web server handles this easily, so the technical check passes.
  2. Payments per year: 8,000 students × 2 payments/student = 16,000 payments/year.
  3. Manual overtime: ₹150/hour ÷ 60 = ₹2.50/minute. Each payment needs 9 minutes × ₹2.50/minute = ₹22.50 per payment. Annual manual cost = 16,000 × ₹22.50 = ₹3,60,000/year.
  4. Portal running costs: gateway 16,000 × ₹6 = ₹96,000/year; SMS 16,000 × ₹1 = ₹16,000/year; maintenance ₹40,000/year. Operating total = ₹96,000 + ₹16,000 + ₹40,000 = ₹1,52,000/year.
  5. Annual cash saving before capital = ₹3,60,000 − ₹1,52,000 = ₹2,08,000/year. Payback = ₹6,00,000 ÷ ₹2,08,000 = 2.88 years.
  6. Annual capital = ₹6,00,000 ÷ 3 = ₹2,00,000/year. Net annual benefit after capital = ₹2,08,000 − ₹2,00,000 = ₹8,000/year. Three-year net = 3 × ₹2,08,000 − ₹6,00,000 = ₹24,000.
  7. Schedule: 3 months for login, payment gateway, receipt, reconciliation and SMS is tight. A minimum scope is login, payment, receipt and reconciliation; SMS can follow.
  8. Operational and legal: parents need SMS receipts; payment data must follow college audit rules. Conclusion: technically feasible, economically marginal, schedule risky.

Answer. The portal is technically feasible at 5 payments/minute, economically marginal with payback 2.88 years and net ₹8,000/year after capital, and schedule-risky at 3 months; start only with the minimum scope and a legal/audit check.

Exam traps

  • Feasibility is only money. Technical, legal, operational and schedule checks can each stop a project.
  • Using peak load as average load. A portal that handles average traffic can fail at the fee-deadline hour.
  • Calling feasibility validation. Feasibility asks whether to start; validation asks whether the written requirements are right.
  • Forgetting running costs. Gateway fees, SMS and support can erase clerk overtime savings.
  • Treating the budget as an annual cost. A one-time ₹6,00,000 over 3 years is ₹2,00,000/year.

2.3 Requirements elicitation: stakeholders and collaborative gathering

Requirements elicitation is planned conversation with every person who affects or is affected by a system. It exists because no single manager knows how booking clerks handle a refund at 11 p.m., what a regulator checks, or where a passenger gives up. You identify stakeholders, map their interest and influence, and gather views in interviews, workshops, observation and prototypes. The output is a shared, recorded understanding, not a wish list. Some syllabi call this requirements gathering; 'capture' is misleading because users cannot hand over complete requirements.

You need: the process loop and feasibility check in Chapter 2.2, plus the split between functional and non-functional requirements in Chapter 2.1.

Stakeholders and the stakeholder map

A stakeholder is any person or group who affects the system or is affected by it. For a rail booking system, passengers buy tickets, booking clerks handle changes, finance officers reconcile money, IT operations keep the service running, and a regulator sets rules. Support staff, trainers, accessibility representatives and maintainers also matter. Missing an operator is a common failure: the software works in the demo but fails at the counter. Primary stakeholders use the system; secondary stakeholders support it; external stakeholders regulate or depend on it.

Build a stakeholder map. Interest is how much the outcome matters to the stakeholder. Influence is the power to change, fund, block or regulate the system. Place each name on the map. High-influence stakeholders need early engagement. High-interest stakeholders need frequent communication. A person can be high on both. For each stakeholder, record role, goal, interest level, influence level, contact, and what they can tell you. Use the map to plan who comes to which workshop, not to rank human worth. A regulator with low daily interest but high influence can still stop a release. An accessibility representative may have low formal power but high interest and legal weight.

Collaboration methods

Collaborative gathering means users, operators and analysts build the requirement together. The analyst does not arrive with a finished form. Use more than one method because each sees a different part of the work. An interview is a planned one-to-one conversation. Ask open questions, then ask for a recent real case. A workshop puts different stakeholders in one room. It is fast for exposing conflict, but needs an agenda, a facilitator and a written record.

A focus group is a discussion with similar users, such as six booking clerks. It shows shared norms, but can hide individual exceptions. A questionnaire reaches many people cheaply. Use closed answers for counts and a few open answers for reasons. Observation means watching work at the counter or on a phone. It reveals steps people forget to mention, such as checking a paper register before overriding a fare. Document analysis reads forms, refund rules, audit reports and complaint logs. Brainstorming generates many ideas before judging them. A prototype is a cheap mock screen or paper form; people react to what they can see. Choose methods by risk: observation for messy operator work, workshops for conflicting goals, questionnaires for wide user groups, prototypes when the interface is uncertain. No method proves completeness; combine them and check back.

First questions, workshop and work products

Start with three first questions. Who books, changes or cancels? What fails today? What must never happen? Ask for a recent example, the workaround used, and who pays when it fails. Write the speaker's role beside every answer. A passenger and a finance officer mean different things by 'safe'.

Use a timed agenda. For 12 people in 90 minutes: welcome and rules 10 min; first questions 20 min; conflict listing 30 min; resolution by ranking 20 min; recap and owners 10 min. Invite 4 passengers, 3 booking clerks, 2 finance officers, 2 IT operations staff and 1 accessibility representative. Put must-never items first. List conflicts in a visible table: issue, who wants what, why. Resolve by ranking, not by averaging. Mandatory rules come first; convenience features become later options. In the rail example, passengers want one-click booking, while finance wants OTP and an audit trail. Audit trail is mandatory; one-click becomes a remembered passenger profile after authentication. Record decision, owner and date, then pass it to validation and management.

Work products: stakeholder register, map, interview notes, workshop minutes, conflict log, question list, observation notes, document extracts, prototype feedback and first usage scenarios. Keep raw notes and a one-page summary. A scenario is one path through a task; write the main path and failure paths. Use case writing belongs to 2.6; SRS wording to 2.5. Call it elicitation, not capture. Capture suggests users can hand over complete requirements. In reality people know routines, not missing rules; stakeholders contradict each other; and new software changes the work. Elicitation is joint discovery: ask, observe, model, check back.

Exam traps

  • Listing only the paying customer. Operators, support staff, regulators and maintainers can block or break the system.
  • Treating 'requirements capture' as handover. Users cannot give complete requirements; ask, observe and check back.
  • Confusing interest with influence. A regulator may care little daily but can stop a release; a passenger may care deeply but cannot fund it.
  • Running a workshop without a timed agenda and conflict log. The loudest person wins and decisions disappear.
  • Interviewing only managers. The counter clerk knows the workaround that the manager's process diagram omits.

2.4 Requirements validation and requirements management

Validation asks one question: is this the system the customer actually needs? A careful read of the SRS catches an ambiguous, missing or conflicting requirement while the fix is still one sentence. Management keeps every later change visible: each requirement has a version, a baseline, a change record and links to design and tests. A UPI app that adds a cancellation fee two months after launch needs the old requirements intact and the new ones traceable.

You need the requirement types from 2.1 and the elicited stakeholder needs from 2.3.

Validation checks the right requirements

Validation asks whether the written requirements describe the system the user needs. Verification asks whether the built system matches them. Validation works on the document, before design; verification runs on code (Unit 4).

Four techniques find defects while a fix is still a sentence:

  • Inspection: three to five people read the SRS against a checklist and log each defect with its requirement number.
  • Prototyping: an unclear screen becomes a throwaway model shown to users; their reaction becomes the rewritten requirement.
  • Test-case generation: write one acceptance test per requirement; if no test can be written, the requirement is not testable.
  • Checklist: ambiguity (each requirement has only one possible reading), completeness (every input, output, error, constraint), consistency (no two requirements contradict), testability (something measurable, numbers carry units).

Baselines, change requests and traceability

A baseline is a reviewed SRS frozen under a version label, v1.0. After that it changes only through a numbered change request (CR) that states the change and its reason.

  1. Log CR-01 in the change register: date, requester, reason.
  2. Impact analysis: affected requirements, design modules, code units, test cases, effort in person-days, schedule.
  3. Change control board (product owner, lead designer, test lead) approves, rejects or defers.
  4. An approved change is edited in, re-reviewed and released as v1.1; the v1.0 baseline is kept.
  5. Traceability matrix and requirement status are updated.

Only a few universities examine the formal board procedure in detail.

A traceability matrix has one row per requirement and columns for design and test, so a change shows exactly which module and test must move. Status runs proposed, approved, implemented, verified.

Worked example

Question. An SRS holds 40 numbered requirements. A validation inspection logs 6 ambiguous requirements, 3 missing requirements and 2 conflicting pairs. After the first baseline, change request CR-01 asks for a cancellation fee; impact analysis traces it to 5 design modules. (a) How many defects must be fixed before the first baseline, and how many of the original requirements are clean? (b) State the management steps for CR-01.

  1. Defects = 6 ambiguous + 3 missing + 2 conflicting = 11.
  2. The 3 missing requirements are new and will be added. The 2 conflicting pairs touch 4 of the existing 40, so 6 + 4 = 10 of them carry defects and 30 are clean.
  3. Each defect is logged by requirement number, fixed by the author and re-inspected until the count is zero; the SRS is then baselined as v1.0 with 43 requirements.
  4. CR-01 is logged with ID, requester and reason, then costed by impact analysis over requirements, 5 design modules and new test case T-13.
  5. The board approves or rejects; on approval the SRS is re-reviewed, released as v1.1, and row R13 is added to the matrix.

Answer. 11 defects; 30 of the original 40 requirements were clean; v1.0 is baselined with 43 requirements. CR-01 touches 5 modules and, once approved, becomes v1.1 with R13 traceable to design and test.

Exam traps

  • Validation is not testing the code; running tests against code is verification (Unit 4).
  • A change accepted without impact analysis, or without a new baseline version, leaves design and tests silently out of date.
  • Do not mix the defect kinds: an ambiguous requirement exists but reads two ways, a missing one is absent, conflicting ones contradict each other.
  • Traceability matrix rows are requirements, not modules.

The board can only approve, reject or defer if it knows the cost: affected requirements, modules, tests, effort and schedule. Without it, approval is a guess and design and tests drift from the SRS.

Not for the exam. Industry keeps requirements in an issue tracker, so each item has an ID, a status field and links to commits and test runs, and the matrix is generated rather than drawn by hand. 2.5 Software requirements specification (SRS) document

An SRS is the written contract between the people who need a system and the people who build it. It states what the software must do, for whom, under what constraints, and how acceptance will be judged. It exists because memory fades, teams change and 'fast' means different things to a user and a tester. You use it before design, during testing and after release when a dispute starts. A good SRS is short enough to read on a phone and exact enough that two readers reach the same test.

You need the split between functional and non-functional requirements from 2.1 and the validation checklist from 2.4.

Purpose and section order

The SRS turns scattered notes into one controlled document. It answers four questions: what is in scope, who uses the system, what rules and limits apply, and what evidence proves the system is correct. It is not a sales brochure and not a design document.

A practical IEEE-style order is below. The order matters: a reader meets the problem before the numbered checks.

  • Introduction: purpose, scope, definitions, references.
  • Overall Description: product view, user classes, operating environment, constraints.
  • Specific Requirements: numbered functional and non-functional statements, each testable.
  • External Interfaces: user, hardware, software and communication interfaces.
  • Performance and Security: response times, load, access control, privacy, audit.
  • Quality Attributes: reliability, usability, maintainability and other -ilities with measures.
  • Acceptance Criteria: the check that closes each requirement.
  • Appendices: data dictionary, forms, index.

Only the Specific Requirements layer carries the weight. The other sections make those statements usable. If a section has no effect on a test, cut it.

Rules for writing requirements

Write one requirement per numbered line, using 'shall'. 'Shall' marks a binding requirement. 'Should' is a goal, and 'may' is an option. Number in a stable way: FR-01, FR-02 for functional; NFR-01, NFR-02 for non-functional. Never renumber after review; add FR-06 instead.

A requirement is verifiable when a tester can pass or fail it without asking the author. Replace vague words with a measure. 'The app shall be fast' fails. 'FR-01 The app shall show an alert within 30 s of an official outage message' passes: 30 s is a number and the clock start is named.

  • Correct: it matches a real need from a named stakeholder.
  • Unambiguous: one reading, one test.
  • Complete: no missing input, output, condition or error case.
  • Consistent: no two lines demand opposite behaviour.
  • Ranked: priority is marked, so low-value lines can wait.
  • Verifiable: a test exists and the result is pass or fail.
  • Modifiable: changes stay local because numbering is stable.
  • Traceable: each line links back to a source and forward to a test.

Use tables for data: an outage record can list time, area, message and source. Use diagrams only as support; the words carry the requirement. Use cases, class models and data flow diagrams get their own chapters: 2.6, 2.7, 2.8.

Review, acceptance and scope control

Review the SRS with users, testers and builders in the same room. Read each line and ask: can we test this, and do we know the source? A line with no source is a wish. A line with no test is unfinished.

Keep design out. 'Use Firebase' is a design choice; 'cache the last 10 outages for offline viewing' is a requirement. Keep the project plan out too: dates, effort and staffing belong in the plan, not in the SRS. The SRS says what must be true, not who will do it or when.

Acceptance criteria turn each requirement into a check. For an alert requirement, the criterion is: send an official outage message, wait 30 s, confirm one alert with the correct area. A change to any requirement goes through the change process in 2.4; the SRS stays the single visible version. The baseline is frozen at review; later edits are numbered versions. A reviewer signs the version they checked.

2.6 Scenario-based modeling and use cases

A use case is a goal-driven interaction between an actor and the system. An actor is a person, device or outside system with a goal; a scenario is one path through the use case. Teams use use cases to agree on what each actor must be able to finish before drawing screens or classes. They feed the SRS, acceptance tests and effort estimates. The idea appears in every UPI app: send money is a use case, while pay ₹500 after one wrong PIN is a scenario.

You need: 2.3 stakeholders and 2.5 SRS scope.

Actors, boundary and the use case idea

A use case names a goal that an actor reaches by interacting with the system. The primary actor starts it and wants the result: Customer at an ATM. A secondary actor helps but has no goal in this use case: the Bank's account system. Draw actors outside a system boundary and use cases inside; the boundary is the software under discussion, not the whole bank. A line from actor to use case means participation.

Use case versus scenario: Withdraw cash is the use case; withdraw ₹5,000 with a valid card is a scenario. Use case versus function: calculate interest is a function; open a fixed deposit is a use case because an actor has a goal and several steps are needed. Functions can implement parts of a use case.

One use case has a main success scenario, alternate flows that still reach the goal, and exception flows that block it. A wrong PIN once is an alternate flow; a wrong PIN three times is an exception. Exam marks sit in these flows, not in the oval.

Fully dressed use case

A fully dressed use case is a short structured record. It states name, goal, primary actor, secondary actors, trigger, preconditions, postconditions, main success scenario, alternate flows, exception flows and business rules. Table 1 is the ATM withdrawal record.

A business rule is an organisation policy the use case must obey, such as a daily withdrawal limit of ₹25,000. Keep each step as one actor action or one system response; name who does it.

Includes, extends and writing scenarios

An include is mandatory reuse: Withdraw cash includes Verify PIN, because every withdrawal must verify the PIN. An extend is optional addition at a named point: Print mini statement extends Withdraw cash only when the customer asks for it. Includes keep repeated steps in one place; extends keep optional behaviour out of the main flow. Do not draw an include for a single step that is not reused.

To write scenarios, start from the goal and write the main success path in numbered steps. Then ask two questions: what valid choice changes the path, and what can go wrong? Record the answers as alternate and exception flows. Add trigger, preconditions, postconditions and business rules. Link each use case to the SRS requirement it satisfies; see 2.5 SRS.

Worked example

Question. An ATM serves two customers today. Customer A has ₹12,000 in the account; Customer B has ₹4,200. Both ask for ₹5,000. The daily limit is ₹25,000 and neither has withdrawn today. The ATM has cash and the card is valid. Write the main success scenario for A, the exception for B, and state the actors, preconditions and numeric checks.

  1. Actors: Customer is primary; Bank is secondary. Preconditions: card valid, ATM has cash, network up, daily limit available ₹25,000.
  2. Customer A, main success: validate card, verify PIN, request ₹5,000. Balance check 12,000 ≥ 5,000 passes and daily check 5,000 ≤ 25,000 passes. Debit ₹5,000, so remaining balance = 12,000 − 5,000 = ₹7,000. Dispense ₹5,000, print receipt, eject card.
  3. Customer B, exception: request ₹5,000, balance 4,200 < 5,000. Shortfall = 5,000 − 4,200 = ₹800. Show 'insufficient balance', eject card, do not debit, do not dispense.
  4. Alternate flow: PIN wrong once or twice lets the customer re-enter PIN; no extra amount is debited.
  5. Postcondition for A: account debited by ₹5,000, cash and receipt delivered. Postcondition for B: no debit, no cash, card returned.

Answer. Customer A: balance ₹12,000 minus request ₹5,000 leaves ₹7,000; daily limit ₹25,000 is enough. Customer B: balance ₹4,200 against request ₹5,000 leaves a shortfall of ₹800, so no debit.

Exam traps

  • Drawing a use case oval for every screen or button. A use case is an actor goal, not a UI page.
  • Forgetting alternate and exception flows. Most exam marks sit in these flows, not the main path.
  • Swapping primary and secondary actors. Customer starts ATM withdrawal; Bank helps but has no goal in it.
  • Writing a scenario as the whole use case. One scenario is one path; the use case is the set of paths.
  • Leaving out preconditions, postconditions or business rules such as the ₹25,000 daily limit.

2.7 Class-based and behavioral requirements models

A class model names the things the problem talks about — patient, doctor, slot — and the links and rules between them. A behavioural model then shows how one thing changes state, or how several things exchange messages in one scenario. These models exist because prose hides gaps: a sentence like “patient books slot” does not say what a slot is, how many appointments a patient can hold, or what happens when a doctor cancels. Analysts draw them during requirements analysis, before design and code, to expose missing rules.

You need: scenarios from Chapter 2.6 and light UML notation from Unit 3.

Finding analysis classes

A class is a template for things that share data and behaviour. An object is one instance. In the hospital problem, Patient is a class; the patient with token A-17 is an object. An attribute is a named fact kept for each object, such as patientId or slotTime. An operation is a service the class offers, such as bookSlot or cancel.

Look for three kinds of analysis class. An entity class is a thing the business must remember. A boundary class is the interface between an actor and the system, such as BookingScreen. A control class coordinates one use case, such as AppointmentCoordinator. Do not turn every screen field into a class: a field is usually an attribute of an entity, and a button is usually an operation or part of a boundary.

  • Entity: Patient, Doctor, Slot, Appointment.
  • Boundary: BookingScreen, DoctorConsole.
  • Control: AppointmentCoordinator.

Some syllabi call this requirements modelling or analysis modelling. The model is conceptual; it is not yet a database schema.

Associations and multiplicity

An association is a link between classes that the business keeps. Each end has multiplicity: how many objects may take part. 1 means exactly one; 0..1 means zero or one; 0..* means zero or more; 1..* means at least one. The star is read “many”.

In the appointment model, Patient 1—0..* Appointment: one patient may have zero or more appointments. Doctor 1—0..* Slot: one doctor may own zero or more slots. Slot 1—0..1 Appointment: a slot may be free or may hold one appointment.

Generalization is an is-a link: Doctor is a Person. Aggregation is a whole-part link: a Ward has Patients, but a patient can exist without that ward. Do not use aggregation for every association. A data model uses entity, attribute, relationship and cardinality for the same facts; cardinality is another word for multiplicity. Draw multiplicities from business rules, not from what a screen shows today.

Behaviour over time

A state machine models one class over its life. A state is a condition the object can be in. An event is a happening that may cause a transition. A transition is an allowed move from one state to another. For Appointment, the states are requested, confirmed, cancelled and completed.

Transitions: requested → confirmed when the doctor accepts; requested → cancelled when patient or doctor cancels; confirmed → completed when the visit is done; confirmed → cancelled when the doctor cancels. Cancelled and completed are final for that appointment.

A sequence model shows one scenario as messages in time order: Patient → BookingScreen: book(slot); BookingScreen → Coordinator: check(slot); Coordinator → Slot: reserve(). An activity model shows a workflow with decisions: book slot → check slot free → create appointment or refuse. Use sequence for one scenario and activity for a process. Keep states as conditions, not actions.

Worked example

Question. A hospital appointment system has 3 doctors and 30 slots per doctor per day. A patient books a slot; a doctor can cancel. An appointment moves through requested, confirmed, cancelled and completed. Identify the core classes, multiplicities and the state machine, and count the slots per day.

  1. Read the nouns the business must remember. The core entity classes are Patient, Doctor, Slot and Appointment. BookingScreen is a boundary class and AppointmentCoordinator is a control class; they are not the core entities.
  2. Set multiplicities. One Patient links to 0..* Appointment. One Doctor links to 0..* Slot. One Slot links to 0..1 Appointment.
  3. Count slots per day: 3 doctors × 30 slots per doctor = 90 Slot objects per day. If every slot is booked, the system has at most 90 appointments per day.
  4. List states for Appointment: requested, confirmed, cancelled, completed. Count = 4.
  5. List allowed transitions: requested→confirmed when the doctor accepts; requested→cancelled when patient or doctor cancels; confirmed→completed when the visit is done; confirmed→cancelled when the doctor cancels. Count = 4.

Exam traps

  • Confusing a class with an object: Patient is a template; the patient with token A-17 is an object.
  • Making every screen field or button a class; prefer an attribute, an operation, or a boundary class.
  • Using actions as state names, such as “Cancel appointment” instead of cancelled; a state is a condition.
  • Reading 0..* as “one or more” or 1..* as “zero or more”; the star allows many, the leading number sets the minimum.
  • Using aggregation for every “has” link; aggregation is whole-part, not a general association.

2.8 Data flow diagrams and functional modeling

A data flow diagram (DFD) is a picture of movement. It shows the data that enters a system from outside, the processes that change it, the stores that keep it, and the data that leaves. It shows no order, timing or decisions. Analysts use it to check that every input is used and every output is produced, and to explain a system to a customer who does not read code. This chapter covers the four symbols, two levels, numbering and balancing.

You need 2.1 for what a functional requirement is, and 2.5 for the scope the diagram must stay inside.

Four symbols carry the whole notation

A DFD is a graph of four things: external entities, processes, data stores and data flows. It answers one question — where does each piece of data come from, what changes it, where is it kept, and where does it go? It is a functional model: it describes what the system does with data, not how fast or in what order. Draw it early, beside the use cases, because a customer who cannot read code can still read this.

  • Every data store is written by some process and read by some process.
  • Flows carry nouns: passenger details, payment status. A verb such as validate is a process, not a flow.
  • No arrow joins two external entities, or two stores. Data always passes through a process.

Levelling: context diagram, then level 1

You draw in levels, never a full system on one page. Level 0, the context diagram, is the whole system as a single process numbered 0, surrounded by the external entities that talk to it. It contains no data stores. Its only job is to fix the boundary: what is inside the software and what is outside.

Level 1 opens process 0 into real processes numbered 1, 2, 3. Their sub-processes are numbered 1.1, 1.2, 1.3, so the number names the parent. Two levels are enough for most requirement reviews.

  1. Draw the context diagram and list every flow that crosses the boundary.
  2. List the processes inside and number them 1, 2, 3.
  3. Draw each process box and connect it to the stores it reads or writes.
  4. Repeat the same external entities, and redraw every boundary flow exactly as the context diagram showed it.
  5. Count boundary flows at both levels; the two sets must match, name for name. Flows between two child processes, or between a child and a store, are new internal detail and are always allowed.
F_child(X) = F_parent(X) for every external entity X

F_parent(X) is the set of data flows between the system and external entity X in the parent diagram; F_child(X) is the same set in the child diagram. The two must be identical. Flows inside the child, whether process-to-process or process-to-store, are extra and always allowed. This identity is called balancing.

What the diagram cannot say, and what a CASE tool adds

A DFD has no decisions, no loops, no sequence and no timing. It cannot say "if the payment fails, do not issue the ticket", because that is control, not data. For control use a state or activity model (see 2.7) or the interaction diagrams of Unit 3. A DFD says what data must exist; it never says when.

Every flow and store name is defined once, with its fields, in a data dictionary, so "booking request" means the same five fields everywhere it appears. That keeps two analysts drawing the same diagram. CASE tools store the diagram in a repository and check it mechanically, flagging:

  • A process with inputs but no output, or the reverse.
  • A store that is never read, or never written.
  • A flow whose name is missing from the data dictionary.
  • A child diagram whose boundary flows do not match its parent.
  • Two different names given to the same data.

Worked example

Question. A rail reservation system has three external entities — Passenger, Railway Admin and Payment Gateway — four processes — Enquiry, Booking, Cancellation and Schedule Maintenance — and two data stores — Train Schedule and Ticket. Draw the context diagram and the level-1 DFD, number the processes, and show that the two levels balance. State how many data flows each diagram has.

  1. Context: one process, numbered 0, named Rail Reservation System, with the three entities outside it. No data stores. The four processes are hidden inside process 0.
  2. Passenger: three flows in (enquiry request, booking request, cancel request) and three out (train list, Ticket, refund status) = 6 flows.
  3. Railway Admin: schedule update in, update status out = 2 flows.
  4. Payment Gateway: payment request and refund request in, payment status and refund status out = 4 flows. Context total = 6 + 2 + 4 = 12 flows.
  5. Level 1 opens process 0 into 1 Enquiry, 2 Booking, 3 Cancellation and 4 Schedule Maintenance. The entities and all 12 boundary flows are redrawn unchanged.
  6. Internal flows are new. Maintenance writes Train Schedule (1). Enquiry reads Train Schedule (1). Booking reads Train Schedule (1). Booking writes Ticket (1). Booking sends a confirmation to Cancellation (1). Cancellation reads Ticket (1) and updates Ticket (1). Internal total = 7 flows.   7. Level-1 total = 12 boundary flows + 7 internal flows = 19 flows.

Answer. The context diagram has 12 data flows, the level-1 DFD has 19 data flows (12 boundary plus 7 internal), and the 12 boundary flows match exactly, so the two levels balance.

Exam traps

  • Drawing control inside a DFD: an arrow labelled "if seat available", or a retry loop. Conditions and order belong to an activity or state diagram.
  • Thinking a flow between two child processes is wrong. Booking sending a confirmation to Cancellation is legal internal detail. Only boundary flows must match the parent.
  • Unbalancing a child: adding a flow to Payment Gateway the parent never had, or losing "refund status" on the way down.
  • Drawing a read as a query arrow into the store plus a reply arrow back. A read is one arrow from the store to the process.
  • Showing data stores in the context diagram. Level 0 has one process and the external entities only.
  • Joining two stores, or two external entities, with an arrow. Data moves only through a process.
  • Naming a flow with a verb. "Validate booking" is a process; "validated booking" is the flow that leaves it.

It answers "which data stores does Booking write?" — the arrow to the Ticket store. It cannot answer "what happens if the payment fails?" — that is a decision, shown in a state or activity diagram.

Beyond the syllabus

Not for the exam. Modern data platforms still draw this diagram: a Kafka or Spark pipeline is described as sources, transformations and sinks, which is a DFD with the arrows renamed. Security engineers feed DFDs into STRIDE threat modelling, because each flow and store is a place to ask what an attacker could read or change. Legacy-modernisation teams redraw old systems as level-1 and level-2 DFDs before touching code. Useful search terms: context diagram, levelled DFD, data dictionary, STRIDE threat model.

2.9 Quality function deployment

Quality function deployment (QFD) is a planning method that starts with customer needs and ends with ranked technical responses. Customers say what they want: tasty food, quick service, low price. Engineers list how they can act: change the menu cycle, add serving counters. A relationship matrix rates how strongly each how supports each what. Importance weights turn those ratings into priority scores. The team builds what ranks high first. QFD is used in product design, services and software. Only a few universities teach it.

You need 2.1 Functional and non-functional requirements and 2.5 SRS scope; basic multiplication is enough.

Customer needs are the what

QFD begins with customer needs, called the whats. Collect them from users, not from one manager. In a hostel mess, students ask for tasty food, quick service and low price. Give each need an importance weight from 1 (barely matters) to 5 (must have). For the mess: taste 5, speed 3, price 4.

Next list technical responses, called the hows. These are things the team can change and measure, such as the menu cycle and the number of serving counters. Keep them at the design level; do not write a full solution.

Arrange needs as rows and responses as columns. This table, with importance and scores, is the house of quality. A need is a what; a response is a how. This is a different cut from functional vs non-functional requirements in 2.1: one customer need can lead to several functional and non-functional requirements, and a how is a design-level technical characteristic, not a requirement type. A vague need such as “good experience” is split into clear ones.

Relationship matrix and priority score

Each row-column cell gets a relationship score: 9 = strong, 3 = medium, 1 = weak, 0 = none. The score says how much the response supports that need. It is a rating, not rupees, days or a percentage.

P<sub>j</sub> = Σ<sub>i</sub> w<sub>i</sub> × r<sub>ij</sub>

Pj is the priority score of response j (unitless); wi is the importance weight of customer need i; rij is the relationship score between need i and response j. The sum runs over all needs i.

Do not add raw cells without weights. A 9 next to a weight-5 need counts more than a 9 next to a weight-3 need. Use 0 for no relationship; leave no cell blank.

Competitive assessment can compare your product with another product row by row. It is useful, but not needed for the basic score.

Read the ranking, not just the total

The weighted score ranks responses. Higher Pj means the response supports more important needs more strongly. Start engineering work there. Use the score to discuss priorities with customers and developers, not to prove satisfaction.

A score is relative to this matrix. Add a new response or change a weight, and the ranking can change. If a response column is all zeros, it supports no listed need; question why it is in the plan. If a need has all zero cells, no response addresses it; the requirement is at risk.

QFD does not estimate cost, effort or schedule. Those belong to cost estimation (see Unit 6, Effort and cost estimation). The correlation roof and full competitive analysis are for a quality-management course. A tie is broken by the more important customer need or by a separate cost review. In an exam, draw only the matrix asked.

Worked example

Question. A hostel mess has weights: tasty food 5, quick service 3, low price 4. Responses are menu cycle and counter count. Strengths: taste-menu 9, taste-counters 1; speed-menu 1, speed-counters 9; price-menu 3, price-counters 3. Compute both priority scores and rank.

  1. Weights: w_taste = 5, w_speed = 3, w_price = 4.
  2. Menu column: r_taste = 9, r_speed = 1, r_price = 3.
  3. Menu score = 5×9 + 3×1 + 4×3 = 45 + 3 + 12 = 60.
  4. Counter column: r_taste = 1, r_speed = 9, r_price = 3.
  5. Counter score = 5×1 + 3×9 + 4×3 = 5 + 27 + 12 = 44.
  6. 60 > 44, so menu cycle ranks first; scores are unitless.

Answer. Menu cycle ranks first with priority score 60; counter count scores 44.

Exam traps

  • Adding row or column cells without the customer importance weights.
  • Treating a relationship score as a cost, duration or percentage.
  • Marking every relationship 9, so the matrix cannot rank responses.
  • Confusing customer needs (what) with technical responses (how); a high score only sets priority, not satisfaction.

Check yourself

Remember In QFD, what are the what and the how? 2 marks

The what is a customer need; the how is a technical response the team can change.

Understand Why are importance weights needed in the relationship matrix? 3 marks

Weights make a strong relationship to an important need count more than the same strength for a minor need.

Apply Using the worked example, state the menu-cycle score and the rank of the response scoring 44. 3 marks

Menu cycle = 60; the response scoring 44 ranks second.

Analyze Why is a relationship score of 9 not a cost of ₹9 or 9 days? 4 marks

It is a strength rating; it carries no unit and is multiplied by an importance weight, not by money or time.

Understand What does a column of zeros mean? 2 marks

The technical response supports none of the listed customer needs, so its priority is zero.

Analyze A team writes 9 in every cell. What goes wrong? 4 marks

Every response gets the same score (9 × the sum of the weights), so the ranking cannot guide effort; it also hides weak relationships and wastes work.

Takeaways

  1. Separate what the system does (functional) from how well or under what limits it does it (non-functional); testability belongs to both.
  2. Requirements engineering is a loop, not a form: the same requirements are elicited, analysed, written, validated and then changed under control.
  3. A feasibility study is cheap insurance; it can end a project before large money is spent.
  4. Elicitation means talking to every affected group, because one manager's view never covers the whole problem.
  5. Validation asks 'did we write the right requirements?'; verification asks 'did we build the thing right?'.
  6. An SRS is useful only when each requirement can be tested, so write numbers with units, not adjectives.
  7. Use cases organise requirements around user goals; scenarios and state models fill in the paths and the order of events.
  8. A DFD shows data moving and being transformed; a class model shows things and their relationships; keep the two views consistent.

Glossary

Actor
A role played by a person, device or system that interacts with the system from outside its boundary.
Baseline
A formally agreed and versioned set of items that later changes must be measured against.
Class diagram
A structural model of classes, attributes, operations, associations and multiplicities.
Data flow diagram
A model of external entities, processes, data stores and data flows, with no control or timing shown.
Domain requirement
A requirement that comes from the rules and conventions of the application domain, not from a single user.
Elicitation
The activity of drawing out requirements from stakeholders and from documents and existing systems.
Feasibility study
A short assessment of whether a proposed system is worth building and can be built within limits.
Functional requirement
A statement of a service, input-output behaviour or function the system must perform.
House of quality
The QFD matrix of customer needs, technical responses and their scored relationships.
Inspection
A formal, role-based team review of a document against a checklist, with a logged defect list.
Levelling
Decomposing a DFD process into a child diagram whose flows match the parent's flows.
Non-functional requirement
A statement about quality, performance or constraint that applies to the system as a whole.
Quality function deployment
A structured method mapping customer needs to ranked technical responses.
Requirement
A capability the software must provide or a condition it must satisfy.
Requirements analysis
Classifying, modelling and negotiating requirements to remove conflict, overlap and gaps.
Requirements management
Controlling requirement identity, versions, change and links throughout the project.
Requirements negotiation
Agreeing which competing requirements will be met, ranked and possibly deferred.
Requirements validation
Confirming that the written requirements are the right ones and are checkable.
Scenario
One specific path through a use case, written with concrete values or as a narrative.
Sequence diagram
A behavioural model showing objects and the time-ordered messages they exchange.
SRS
The software requirements specification, the agreed document defining what the system must do and how it will be judged.
Stakeholder
Anyone who affects or is affected by the system, including indirect users and maintainers.
State diagram
A behavioural model of states, events, guards and actions for a single object or the whole system.
System requirement
A structured, precise and testable version of a user requirement written for developers.
Traceability matrix
A table linking each requirement to its source, design element, code and test cases.
Use case
A goal-driven interaction between external actors and the system, described by a main flow and alternates.
User requirement
A natural-language statement of what users need, written for customers to read and agree.
Viewpoint
One stakeholder's angle on the system, used to organise and cross-check requirements.
