1.1 Nature of software, application domains and myths

Software is more than code: it is programs, data and documents, and the kind of software decides how it is engineered. A meter's firmware, a bank's payroll and a UPI payment library are all software, yet each needs a different approach. This chapter defines software, contrasts it with hardware, lists the application domains, defines legacy software and corrects six common myths. Without this base, process models look like arbitrary ceremony; with it, each model is a sensible answer to a particular kind of product.

You need: Nothing; this opens the unit. The process models that follow are introduced in 1.4.

Software is programs, data and documents

Software is the collection of programs, data and documents that makes a computer useful. A program is a set of instructions. Data is everything the program reads or writes: a customer table, a settings file, a saved invoice. Documents describe the software: the requirement note, the design sketch, test cases, the user manual. Delete the documents and the program still runs, but nobody can change it safely. That is why the definition has three parts, not one.

Software is developed, not manufactured. A factory makes identical hardware units and the cost per unit falls as volume rises. Software is built once, at the cost of people's time, and each further copy costs almost nothing.

Hardware wears out from heat, dust and vibration, so its failure rate follows a bathtub curve: high at the start, low in the middle, high at the end. Software does not wear out; it deteriorates. Every change risks breaking something that worked, so the failure rate climbs with each modification unless the code is cleaned up. The cause is change, not use.

Software resembles other engineering products in the work it demands: requirements, design, review, estimation, standards and client acceptance apply to a bridge and to a payroll system alike. It differs in being intangible, having no spare parts and no manufacturing tolerance, being copied in seconds, and carrying almost all its cost in human effort rather than material.

Changing role, application domains and legacy software

The role of software has shifted. Custom code for one client on one machine has given way to four shapes. Product lines: one core sold to many customers by configuration. Software as a service: the customer pays a subscription and uses the vendor's running system, like a GST filing portal billed per return. Embedded systems: software inside a device, such as the firmware of an electricity meter. AI-enabled systems: behaviour learned from data, used in fraud checks and recommendations. Each shape pushes engineering a different way — reuse and configuration for product lines, timing and memory discipline for embedded, data and model quality for AI.

Application domains group software by who uses it and what it must do:

  • System software: operating systems, compilers, device drivers, file systems. It serves other software, not the end user directly.
  • Application software: payroll, inventory, booking, results portals. Web and mobile apps are the largest modern sub-class.
  • Engineering and scientific software: CAD, circuit simulation, weather and structural models; heavy floating-point computation.
  • Embedded software: firmware inside a device, reading sensors and driving actuators under real-time limits.
  • Product-line and reuse software: libraries, frameworks and components reused across products, such as a payment SDK.
  • Web and mobile applications: network-facing, many users and devices, short release cycles.
  • Artificial intelligence software: prediction and recommendation learned from data instead of written by hand.
  • Legacy software: defined next.

Legacy software is old software still in production and still business-critical. Ten or twenty years old, it runs on an outdated platform or language, few engineers understand it, the documentation is incomplete, and every change is risky. Organisations keep it because it works, it encodes years of business rules, and replacing it costs and risks more than maintaining it. A bank's core ledger is the usual example. The options are to wrap it, re-engineer it, or replace it phase by phase (see Unit 6, Software maintenance and re-engineering).

Software myths and their corrections

A myth is a belief that sounds obviously true and is false. Software myths survive because they excuse a shortcut already taken. They come from three groups: management, the customer, and the practitioner.

Group and mythReality
Management: adding programmers catches up a late projectLate additions add communication paths and training load; the project slips further.
Management: a general statement of the objective is enough to start codingMissing requirements surface later as rework, the costliest kind to fix.
Customer: requirements will keep changing, and change is easyChange is easy to request and costly to absorb; each change must be evaluated and tracked.
Customer: a working program is the whole productThe product also needs documents, test records and training material to be usable and maintainable.
Practitioner: once the program runs, the job is doneMaintenance begins at first delivery and lasts for most of the product's life.
Practitioner: the only deliverable is working codeDesign records, test cases and user documents are deliverables too.

Myths cost marks in two ways. A student who writes only the myth has answered half the question; the correction carries the marks. A team that believes a myth skips the work the myth denies — reviews, documents, change control — and pays for it later as rework.

Worked example

Question. A Chennai IT firm maintains 40 applications: 25 custom web apps for clients, 8 embedded firmware products for meter makers, 5 reusable payment libraries, and 2 payroll systems that are 12 years old. (a) Classify all 40 into application domains. (b) Identify the legacy systems. (c) The 2 payroll systems are maintained by 5 engineers, and the manager adds 3 more to catch up. Using communication paths n(n−1)/2 for a team of n people, compute the paths before and after, and state whether the myth 'adding programmers catches up a late project' holds.

  1. Check the inventory: 25 + 8 + 5 + 2 = 40. Nothing is left unclassified.
  2. The 25 custom web apps serve end users over a network: application software, web sub-domain.
  3. The 8 firmware products run inside a meter and talk to hardware: embedded software.
  4. The 5 payment libraries are built once and reused across products: product-line and reuse software.
  5. The 2 payroll systems are 12 years old, still in production and still business-critical: legacy software.
  6. Team before: n = 5, so paths = 5 × 4 ÷ 2 = 10.
  7. Team after: n = 8, so paths = 8 × 7 ÷ 2 = 28.
  8. Extra paths = 28 − 10 = 18. Each path must be kept in sync, and the 3 new engineers need training on code they did not write.
  9. The myth fails: the late project gains 18 communication paths and loses senior time to mentoring, so it usually finishes even later.

Answer. 25 application/web, 8 embedded, 5 product-line/reuse and 2 legacy applications, 40 in total; the payroll team's communication paths grow from 10 to 28, an extra 18, so adding programmers does not catch up a late project.

Exam traps

  • Writing 'software = program'. Software is programs plus data plus documents; the documents are what make maintenance possible.
  • Calling any old program legacy. Legacy means old software still in production and still business-critical; an unused program from two years ago is dead code, not legacy.
  • Saying software wears out. Hardware wears out; software deteriorates because of change.
  • Listing a myth without the correction. The marks are for the corrected reality, stated in one line.
  • Confusing 'developed, not manufactured' with 'free to produce'. Copying the second unit is nearly free; building the first one is not.

1.2 Software engineering practice and general principles

Software engineering is not a box of tools. It is a layered discipline: a quality focus at the base, a process above it, methods above that, and tools on top. Underneath sits a personal discipline called the essence of practice: understand the problem, plan a solution, carry out the plan, examine the result. General principles — simplicity, abstraction, modularity, separation of concerns, anticipating change — turn that discipline into decisions a team can defend. Teams use this structure on every sprint, and examiners test whether you can tell a tool from a process.

You need Chapter 1.1 for what software is and why different software types need different engineering effort.

Four layers: quality focus, process, methods, tools

Software engineering is drawn as a stack. The base is the quality focus: the team's commitment to a stated quality target, not just shipping code. Example: at most 2 defects per thousand lines of code (KLOC) at release. That number shapes later choices.

Above quality sits the process. A process is the framework of activities and their order: who plans, who reviews, when testing starts, what a phase or sprint must produce. A process is not a tool. It is the agreed way work moves.

Methods are the technical how: analysis techniques, design notations such as UML, review checklists, test-design techniques. Tools are software that supports process and methods: an IDE, Git, Jira, a CI server.

A tool with no process is a faster way to do the wrong thing. A process with no methods produces paperwork. The layers hold each other up.

The essence of practice

Under every process model, each engineer repeats four moves. They look simple; skipping one is the most common cause of rework.

  1. Understand the problem: name the user, what they must do, and what done means before writing code.
  2. Plan the solution: sketch design, data, interfaces and work order; record assumptions.
  3. Carry out the plan: build, test as you go, keep the plan visible and update it when facts change.
  4. Examine the result: compare output with the original need, not with your own code; collect review and test evidence.

Each step leaves a small artifact: a note, a sketch, a test, a review record. Those artifacts make work repeatable when a teammate leaves. Practice is not only a phase at the start; it repeats at every scale, from a two-hour bug fix to a year-long release. Whatever the model (see 1.5), these four moves are the content.

General principles

Principles are short rules that survive changes of process model.

  • Keep it simple: fewer moving parts for the same need, not fewer lines.
  • Provide value: an unused feature is cost, not progress.
  • Build for maintainability: someone else will change this code.
  • Separate concerns: one module, one reason to change.
  • Modularity: parts that can be built and tested alone.
  • Abstraction: hide detail behind a clear interface.
  • Anticipate change: isolate rates, formats and vendors likely to move.
  • Build quality in: reviews and tests belong to construction.
  • Think before coding: ten minutes of design can save a day of debugging.

Principles sometimes conflict; simplicity and anticipating change pull opposite ways. Write down the trade-off you chose.

Practice areas, ethics, and the tool trap

Practice groups into five areas. Communication elicits requirements. Planning sets scope, estimates, schedule and risk (Unit 6). Modeling produces analysis and design sketches (Units 2 and 3). Construction writes code, unit-tests and integrates. Deployment delivers, configures and supports the running system.

Ethics belongs to practice. Shipping a known safety defect, hiding test failures, or copying code without a licence breaks the discipline even when the code runs. Public safety, honest results, privacy and licence respect are the lines.

Tools sit on top because they are easiest to buy and least decisive. A team that buys five tools but defines no process has added five things to maintain, not five improvements. Tools support a process; they never define one.

Worked example

Question. A six-person team runs two-week sprints, so one sprint is 10 working days. The product is 25 KLOC and the release target is at most 2 defects per KLOC. The team uses Git and Jira, one code-review checklist, and one sprint process. Map each item to a layer. Compute the maximum allowed defects at release. The manager then buys 5 more tools: how many tools now, and which layer is still weak if no process changes?

  1. One sprint = 2 weeks × 5 working days = 10 working days.
  2. Tools layer = Git + Jira = 2 tools.
  3. Methods layer = code-review checklist = 1 method.
  4. Process layer = sprint process = 1 process.
  5. Quality target = 2 defects/KLOC × 25 KLOC = 50 defects allowed.
  6. After buying 5 tools: 2 + 5 = 7 tools. Process stays at 1; no process change, so the process layer is weak.

Answer. Layers: tools 2, methods 1, process 1, quality focus 50 allowed defects; after the purchase there are 7 tools and the process layer remains the weak one.

Exam traps

  • Calling a toolchain the software process. Git and Jira support a process; they do not say who reviews, when testing starts, or what done means.
  • Putting tools at the base. The base is quality focus; tools are the top layer.
  • Treating understand the problem as requirement gathering only. It also means agreeing what done looks like and what the user must be able to do.
  • Listing simplicity as write the fewest lines. Simplicity is fewer moving parts for the same need, not code golf.
  • Mixing methods with process. A checklist or UML diagram is a method; the sequence of activities is the process.

1.3 Software development life cycle and its phases

A software product does not appear in one jump. It moves through a life cycle: a set of phases, each with a purpose, a main output and a check before the next phase. This life cycle exists because a large product cannot be understood, built and trusted in one pass. It is used on every project, from a college fee portal to a railway reservation system, to plan effort, assign people and decide when work is good enough to move forward.

You need: 1.1 and 1.2; this chapter assumes software is programs, data and documents, and that engineering practice is layered.

What the life cycle is and how it starts

Software development life cycle (SDLC) is the set of phases a software product passes through, from the decision to build it to retirement. A phase is a group of related work with one main output and a check called an exit criterion. The check stops a weak output from moving forward.

Initiation decides whether the project should exist. Its output is a project charter: a short authorisation that names the sponsor, the goal, the rough budget and the scope boundary. People involved are the sponsor, product owner, project manager and a technical lead. Exit criterion: the charter is signed and the scope is agreed. A feasibility study starts here and continues into requirements: is the idea technically possible, is the benefit worth the cost, is it legal, and can it finish in time? Unit 2 covers requirements and feasibility in depth; Unit 6 covers charter and scheduling.

Requirements states what the system must do and how well it must do it. Output: software requirements specification (SRS). People: business analyst, users, test lead. Exit criterion: the SRS is reviewed and baselined, so later changes are controlled.

Design and construction: deciding how, then building

Design converts requirements into a plan for the software. It fixes the architecture (layers, services, data stores), the modules, their interfaces and the main data structures. Output: a design description, often with UML diagrams. People: architects, designers, database administrator. Exit criterion: a design review confirms that every requirement is covered and that quality attributes such as security and response time have a planned solution. Unit 3 teaches design and UML.

Construction writes the code and the unit tests for each module. Output: source code, a build and unit test results. People: programmers, a build engineer and testers who review unit tests. Exit criterion: the code compiles, unit tests pass and a code review is closed. Construction is not always the largest phase; a project that reuses a large platform may spend more effort on requirements and integration.

Design and construction can overlap. A team may design module A, start coding it, and design module B in parallel. Overlap is safe only when the interface between A and B is fixed early.

Testing, deployment, maintenance and repetition

Testing checks the assembled product at increasing scope: unit test checks one module, integration test checks modules together, system test checks the whole product against the SRS, and acceptance test checks that the customer will accept it. Output: test results, a defect log and a release recommendation. People: test engineers and, for acceptance, real users. Exit criterion: planned tests are run and defect levels meet the agreed threshold. Unit 4 covers the techniques.

Deployment moves the tested product into the user environment. Output: a release package, installation or migration steps and user training. People: release engineer, operations and support desk. Exit criterion: users can log in, complete a core task, and the support desk has the release notes.

Maintenance keeps the product useful after go-live. It covers corrective fixes, adaptive changes (a new tax rule or phone model), perfective improvements and preventive work. Output: patches and later releases. People: maintenance programmers and support staff. Exit criterion: the change is verified and the release is recorded.

Phases overlap and repeat. A change after go-live does not stop at code: it goes back to requirements, then design, construction and testing. The waterfall model draws phases as a strict sequence; incremental and spiral models repeat groups of phases. See 1.5.

Worked example

Question. A college fee portal is estimated at 200 person-days. The plan splits effort as requirements 15%, design 20%, construction 40%, testing 20% and deployment 5%. (a) Compute person-days per phase. (b) After go-live, a new fee rule is needed. Which phase does the work return to first, and why?

  1. Total effort T = 200 person-days.
  2. Requirements = 0.15 × 200 = 30 person-days.
  3. Design = 0.20 × 200 = 40 person-days.
  4. Construction = 0.40 × 200 = 80 person-days.
  5. Testing = 0.20 × 200 = 40 person-days.
  6. Deployment = 0.05 × 200 = 10 person-days.
  7. Check: 30 + 40 + 80 + 40 + 10 = 200 person-days, so the split uses the full estimate.
  8. A new fee rule changes what the system must do, so the work returns to requirements first. It then passes through design, construction, testing and deployment as needed. Maintenance is not only a code edit.

Answer. 30, 40, 80, 40 and 10 person-days; they sum to 200 person-days. The new fee rule sends work back to requirements first.

Exam traps

  • Assuming testing starts only after all coding ends. Unit, integration and system testing often overlap construction and design.
  • Treating phases as strictly sequential and never repeated. A requirement change after go-live sends work back to requirements, then design, construction and testing.
  • Confusing maintenance with bug fixing only. Maintenance also covers adaptive, perfective and preventive changes.
  • Mixing up phase outputs: requirements produces the SRS, design produces the design description, and construction produces code and unit test results.
  • Believing construction always takes the largest share of effort. Reuse-heavy or compliance-heavy projects can spend more on requirements, integration or testing.

1.4 Generic process framework and process models

Every software project does the same work: understand the need, plan, model, build and deliver. Only the amount and order change. The generic process framework gives a common skeleton: five framework activities plus umbrella activities that run across all of them. A team turns the framework into a real process by choosing a task set and a process model.

You need: 1.2 software engineering practice and principles and 1.3 SDLC phases.

Five framework activities

A software process is the set of activities that turns a user need into a delivered product. The generic process framework says every project contains the same five framework activities, whatever its size or style.

  • Communication: agree with the customer and other stakeholders on what to build. Output: a requirement list and scope notes. See Unit 2.
  • Planning: decide tasks, people, schedule and risks, and write a plan the team can track.
  • Modeling: build analysis models of what the software must do and design models of how it will do it. See Unit 3.
  • Construction: write the code and unit test it, so each piece works before it is joined to the rest.
  • Deployment: install the software, train users, collect feedback and support the release.

The five are a logical order, not a fixed calendar. A team returns to communication when a requirement is unclear, or to modeling after a defect. One full pass is one increment; a large product has many. 1.5 shows how models arrange these passes.

The framework is generic because it is tied to no single model. Waterfall, spiral and agile all contain these five activities; they differ in how often and in what order the activities run.

Tasks, task sets and work products

A framework activity is only a label; the real work is done by tasks inside it. A task set is the tasks a team selects for one project. For every activity it names the tasks, the work products produced, and the quality checks that decide whether a work product is acceptable.

ActivitySample taskWork product
CommunicationElicit needs from the operations teamRequirement list
PlanningEstimate effort for each featureProject schedule
ModelingDraw a use case for each actorUse-case model
ConstructionWrite and unit test one moduleSource code, test log
DeploymentRun a pilot with 20 usersRelease note, feedback list

The task set is chosen, not copied. A small internal tool with a familiar team needs few tasks and few reviews. A banking or medical system needs more tasks, more work products and heavier checks. Inside one project the task set can shrink for a low-risk increment and grow for a risky one. Choosing tasks by size and risk is the main judgement in process design.

Umbrella activities

Some work is needed during every activity, so it is called an umbrella activity. Common ones: project tracking and control, risk management, quality assurance, technical reviews, measurement, configuration management and documentation.

  • Tracking and control: compare actual progress, effort and defects with the plan, and correct drift.
  • Risk management: find risks, rate them, plan responses, review them. See Unit 6.
  • Quality assurance: set the process and standards, then check the team follows them. See Unit 4.
  • Technical reviews: walkthroughs and inspections of requirements, design, code and test plans, each held before the work product moves on.
  • Measurement: collect numbers such as effort per task, defect counts and test pass rate.
  • Configuration management: identify each work product, control changes, keep approved versions as baselines. See Unit 5.
  • Documentation: user guides, installation notes and technical notes for the next team.

The name comes from coverage. Configuration management runs in planning when the plan is baselined, in modeling when diagrams are versioned, in construction when branches are created, in deployment when the release is tagged. Quality assurance and measurement also touch every activity.

Umbrella activities are not a sixth phase and are never done once at the end. A project that skips them can still ship code, but it cannot rebuild an old release or prove it was reviewed.

Process patterns, assessment and model families

A process pattern is a named solution to a problem that keeps returning in the process itself. Five fields: name, context (where it applies), problem, solution (process steps to take) and consequences (result and trade-offs). A pattern named "requirements ambiguity" records what to do when a stakeholder cannot state a requirement clearly.

Process assessment checks a team's process against a reference model, grading maturity from ad hoc through managed and defined up to measured and continuously improved. The output is a list of weak areas; process improvement fixes them.

Prescriptive models fix the activities and their order up front; waterfall and incremental are prescriptive. Evolutionary models such as prototyping and spiral let the process grow with the product, covered in 1.5. The concurrent model treats every activity as a simultaneous state: inactive, awaiting changes, under development, under revision or done. Under revision means the work product is being changed after review comments. A design can sit under development while coding starts on the finished parts. Agile details are in 1.6.

Worked example

Question. A team defines a task set for one release: communication 6 tasks, planning 5, modeling 8, construction 12, deployment 4. It adds 3 umbrella tasks: a risk review, a quality assurance audit and a configuration baseline. Find the total tasks and construction's share. Also find the share if umbrella tasks are left out.

  1. Framework tasks = 6 + 5 + 8 + 12 + 4 = 35.
  2. Umbrella tasks = 3, so the whole task set = 35 + 3 = 38.
  3. Construction share = 12 ÷ 38 = 0.3158..., that is 31.6% to one decimal.
  4. Construction share of framework tasks only = 12 ÷ 35 = 0.3429..., that is 34.3% to one decimal.
  5. The shares differ because umbrella tasks add 3 to the denominator. Umbrella tasks are not a separate phase; they sit across the release.

Answer. The task set has 38 tasks (35 framework plus 3 umbrella), and construction holds 31.6% of them, or 34.3% if umbrella tasks are wrongly ignored.

Exam traps

  • Counting umbrella activities as a sixth sequential phase. They run across all five framework activities and never finish in one go.
  • Treating framework activities as SDLC phases. Framework activities are the everyday work inside each increment; SDLC phases describe the whole product life, as in 1.3.
  • Assuming a task set is fixed. It is chosen per project and can change each increment, by size and risk.
  • Mixing up process patterns and design patterns. A process pattern is about how work is organised; a design pattern is about software structure, as in Unit 3.
  • Using the wrong denominator in the construction-share question. The share of the whole task set divides by all tasks, umbrella tasks included.

1.5 Waterfall, incremental and spiral models

Every project must do the same SDLC phases: requirements, design, build, test. A process model decides the order, how often each phase repeats, and when the user first sees working software. Waterfall runs the phases once, in sequence. Incremental runs them once per slice of the product. Spiral runs them in repeated loops, and each loop starts with an explicit risk analysis. The choice turns on two questions: how stable the requirements are, and how much risk the project carries. A fixed-scope tax system and a new consumer app need different answers.

You need: 1.3 for the SDLC phases and 1.4 for what a process model is.

Waterfall: one pass, documents at every step

In the waterfall model the phases run one after another, once. Requirements end before design begins, design ends before coding begins, coding ends before testing begins. Each phase closes with a written document (a requirements specification, a design document, a test plan) that the next phase works from. The model is document-driven: paper, not conversation, carries the work forward.

This suits work where the requirement is already fixed and must be provable: a statutory report, a payroll layout set by law, a contract with fixed price and fixed scope. The documents also create review gates, which safety-critical projects want.

  • The user runs working software only near the end, so a misread requirement surfaces at test time, when fixing it means redoing design and code.
  • A change reopens signed documents, so change is costly by design.
  • An unclear requirement blocks every later phase, because no phase starts until the previous one is approved.

Some syllabi call waterfall the linear sequential model or the classic life cycle. Some group waterfall, incremental and spiral as prescriptive process models, because each prescribes when an activity happens.

Incremental and evolutionary models

The incremental model cuts the product into slices called increments, ordered by priority. Each increment passes through all the phases and ends with tested, working software delivered to the user. The first increment is the core; later ones add features on top. Feedback arrives early, so a misread requirement is caught before it spreads through the whole product.

Increments must fit together. The architecture, interfaces and data design have to be settled before increment 1 ships, otherwise increment 3 cannot reuse increment 1's code. Incremental means staged delivery, not absent design.

Evolutionary models assume requirements will move. In prototyping, a quick throwaway version shows the user what the system could be; the reactions sharpen the requirement, and the prototype is then discarded.

The spiral model (Boehm) repeats the phases in loops. Each loop covers one part of the product and has four sectors:

  • Objectives: what this loop must achieve, and its constraints.
  • Risk analysis: find the biggest risks and cut them, by prototyping the hard part, simulating the load, or buying instead of building.
  • Engineering: build and test this loop's part of the product.
  • Evaluation: the customer reviews the result and plans the next loop.

The loop grows wider as its cost grows. Spiral is built for large, risky work: a banking core, a control system, a new platform.

Spiral against incremental, and the Unified Process

Spiral and incremental both deliver in parts. The difference is the risk step. An incremental project can leave risk analysis out; a spiral loop cannot. Remove risk analysis and spiral becomes ordinary iterative development.

The Unified Process (UP) is iterative and incremental, organised in four phases. Inception sets scope, business case and feasibility. Elaboration fixes the architecture baseline and retires the main risks. Construction builds the rest and beta-tests. Transition takes user acceptance and deploys. Each phase holds several iterations, and each iteration is a small full pass through requirements, design, code and test. Architecture gets early attention, which plain incremental often lacks.

Worked example

Question. A payroll system is delivered in 4 equal increments. Each increment takes 3 weeks to build and 1 week to test. Plan A (waterfall) builds the code for all four increments first, then tests the whole system for 4 weeks, one week per increment. Plan B (incremental) builds and tests each increment before starting the next. Find (a) the week the first tested increment reaches the user under Plan B, (b) the week all testing ends under Plan B, (c) the week building ends under Plan A, (d) the week all testing ends under Plan A.

  1. Length of one incremental cycle = 3 weeks build + 1 week test = 4 weeks.
  2. Increment 1: build weeks 1 to 3, test week 4. First tested increment ready at the end of week 4.
  3. Increment 2: build weeks 5 to 7, test week 8.
  4. Increment 3: build weeks 9 to 11, test week 12.
  5. Increment 4: build weeks 13 to 15, test week 16. Plan B total = 4 increments × 4 weeks = 16 weeks.
  6. Plan A building = 4 increments × 3 weeks = 12 weeks, so weeks 1 to 12.
  7. Plan A testing = 4 increments × 1 week = 4 weeks, so weeks 13 to 16. Plan A total = 12 + 4 = 16 weeks.
  8. Both plans end testing in week 16, but Plan A has no tested software before week 16, while Plan B has a running payroll module from week 4.
  9. A spiral plan would keep the same 16 weeks of engineering but insert risk analysis into each loop, raising effort while lowering the chance of a late surprise.

Answer. Incremental delivers its first tested increment at week 4 and ends testing at week 16; waterfall ends building at week 12 and also ends testing at week 16, with nothing tested before then.

Worked example 2

Question. A team uses 5 increments. Each takes 2 weeks to build and 1 week to test. Under incremental delivery, when does increment 3 reach the user, and when does all testing end? Under waterfall with the same numbers (build everything, then test one week per increment), when does testing end?

  1. Increment length = 2 + 1 = 3 weeks.
  2. Increment 1 ends week 3, increment 2 ends week 6, increment 3 ends week 9.
  3. All five increments end at 5 × 3 = 15 weeks, so testing ends week 15.
  4. Waterfall building = 5 × 2 = 10 weeks, so weeks 1 to 10.
  5. Waterfall testing = 5 × 1 = 5 weeks, so weeks 11 to 15. Testing ends week 15.
  6. Similar total effort, very different feedback: incremental has a tested slice at week 3.

Answer. Increment 3 reaches the user at week 9, incremental testing ends at week 15, and waterfall testing also ends at week 15 with nothing tested before week 11.

Exam traps

  • Saying spiral is only 'waterfall repeated'. Every loop must contain an explicit risk-analysis step; without it the model is just iterative development.
  • Calling incremental a form of waterfall. In incremental each increment ends with tested, deliverable software; waterfall tests only after all building is done.
  • Assuming incremental means no upfront design. The architecture and interfaces must be planned first, or later increments cannot reuse earlier code.
  • Confusing the four spiral sectors (objectives, risk analysis, engineering, evaluation) with the SDLC phases. The sectors repeat inside every loop.
  • Confusing UP phases (inception, elaboration, construction, transition) with the SDLC phases. Each UP phase contains several full passes through requirements, design, code and test.

Process maturity frameworks grade how well an organisation runs a model, not which model it picks. 1.6 Agile development and Extreme Programming

Agile development builds software in short repeated increments, with the customer close to the team and able to change the plan between increments. It exists because waterfall projects deliver late and handle change badly. Agile is used in product companies, client projects, and banks or government systems where requirements move. Extreme Programming (XP) is one agile process that adds engineering practices such as test-first coding, pair programming and refactoring, so fast change does not lower quality.

You need 1.4 for the generic process framework and 1.5 for waterfall and incremental delivery; agile is an incremental model with specific values.

Agile values and principles

Waterfall asks the customer to approve all requirements before coding. The customer sees the system at the end. If a rule changes in month eight, the team learns after design is signed off. Agile answers with a small working part every few weeks and a customer who says whether it is right.

The Agile Manifesto (2001) states four values. The right-hand items still matter; the left-hand items matter more.

  • Individuals and interactions over processes and tools.
  • Working software over comprehensive documentation.
  • Customer collaboration over contract negotiation.
  • Responding to change over following a plan.

Principles follow: deliver in short increments, welcome changing requirements, business people and developers talk daily, working software is the main measure of progress, keep design simple, and self-organising teams decide how work is done.

A story point is a relative size estimate for one feature, agreed by the team, not a unit of time. Velocity is a planning number, not a progress measure.

velocity = story points finished ÷ number of iterations

velocity is average story points completed per iteration; for one fixed-length iteration it is just the points finished in that sprint.

Use velocity for the next two or three iterations only. It is not a target to raise by pressure.

Scrum: roles, artifacts and events

Scrum is the most widely used agile framework. It keeps one list of work and runs fixed-length sprints, usually 2 to 4 weeks.

Three roles. The product owner owns the backlog and decides priority and value. The Scrum master removes blockers and guards the process; this is not the team's manager. The team, usually five to nine people, does design, coding and testing.

Three artifacts. The product backlog is the ordered list of everything wanted, written as user stories. The sprint backlog is the subset committed for the current sprint. The increment is working, tested software from the sprint.

Four events. Sprint planning selects backlog items and a sprint goal. The daily scrum is a 15-minute stand-up: done, next, blockers. The sprint review shows the increment to stakeholders. The retrospective picks one improvement.

Two rules protect the rhythm. Sprint length stays fixed. Once a sprint starts, only the product owner may change its goal, and only if the sprint has become pointless.

Extreme Programming practices

XP has twelve practices, best learned in groups.

  • Planning: planning game (customer writes stories, team estimates, together they pick the next release), small releases, on-site customer.
  • Design: simple design, metaphor (one shared story of the system), refactoring.
  • Coding: test-first development, pair programming, coding standards, collective ownership.
  • Integration: continuous integration (merge and build many times a day).
  • Sustainable pace: a 40-hour week, because tired developers write defects.

Test-first development, now test-driven development (TDD), runs a short cycle. Write a test for the next small behaviour and watch it fail (red). Write the least code that passes (green). Refactor with the test as a safety net. Tests pile up into a regression suite, which makes refactoring and continuous integration safe.

In pair programming two developers share one machine. One drives (types), one navigates (thinks ahead, questions design), and they swap. It is continuous code review. Pairing costs some raw speed and repays it in fewer defects and faster knowledge spread. Collective ownership and rotation stop code depending on one person.

A practical project may mix: a short up-front study of the highest-risk requirements, then agile increments. Agile is not a licence to skip planning or documentation; it plans every iteration and documents what users, auditors or new team members actually need.

Worked example

Question. A team runs 2-week sprints with velocity 10 story points per sprint. Backlog: login 5, search 8, report 3, payment 13, help 2. The team adopts XP pair programming, and the coach estimates a 20% drop in capacity. How many 2-week sprints are needed for the whole backlog, and how many weeks?

  1. Total backlog = 5 + 8 + 3 + 13 + 2 = 31 story points.
  2. Old velocity = 10 points per 2-week sprint.
  3. Pair programming leaves 1 − 0.20 = 0.80 of capacity.
  4. New velocity = 10 × 0.80 = 8 points per sprint.
  5. Sprints = ceil(31 ÷ 8) = ceil(3.875) = 4 sprints.
  6. Check: 3 sprints give 24 points, leaving 7; 4 sprints give 32 points.
  7. Calendar time = 4 sprints × 2 weeks = 8 weeks.
  8. Ranking comes from the product owner, not the estimates. Suppose the product owner ranks payment and login highest, then search, report, help. The team builds in that order, splitting any story too large for one sprint, so if it stops after 3 sprints the most valuable features are already delivered; size and value are different.

Answer. The backlog is 31 story points; at velocity 8 the team needs 4 sprints, that is 8 weeks, and must not promise delivery in 3 sprints.

Worked example 2

Question. A team has velocity 12 points per 2-week sprint. It adopts TDD and pair programming, cutting capacity by 25%. The backlog totals 60 points. How many sprints are needed?

  1. Capacity fraction = 1 − 0.25 = 0.75.
  2. New velocity = 12 × 0.75 = 9 points per sprint.
  3. Sprints = ceil(60 ÷ 9) = ceil(6.67) = 7 sprints.
  4. Check: 6 sprints give 54 points, short by 6; 7 sprints give 63 points.

Answer. 7 sprints of 2 weeks, that is 14 weeks.

Exam traps

  • Saying agile means no plan and no documentation. Agile plans every sprint and writes documents users, auditors or new members need.
  • Confusing the product backlog with the sprint backlog. The product backlog is everything wanted; the sprint backlog is the fixed subset for the current sprint.
  • Thinking velocity can be raised by pressure. It is a measured average for short-term planning; treating it as a target corrupts estimates.
  • Believing pair programming means two people type the same line. One drives, one navigates, and they swap.
  • Calling the Scrum master the team's manager. That role removes blockers; the product owner owns priority and value.

1.7 Reasons for software project failure

Software project failure means the product misses agreed cost, schedule, quality or user need. Causes are mostly people, process and requirement conditions, not only technical bugs. They include unclear or changing requirements, scope creep, unrealistic deadlines, poor estimation, weak stakeholder involvement, inadequate testing, technical debt, poor communication, skill gaps, risk neglect, silver-bullet thinking and management pressure. Only a few universities teach this as a separate topic. Spot causes early, before blame replaces diagnosis.

You need: the process view in 1.4, and the delivery choices in 1.5 and 1.6.

Causes cluster by area

Failure can look like one late milestone. The cause is the earlier condition that produced it. Requirements causes: unclear requirements, changing requirements and scope creep. Scope creep means small additions accepted without changing time, cost or staff. Management causes: unrealistic deadlines, poor estimation, weak stakeholder involvement, poor communication, risk neglect, silver-bullet thinking and management pressure. Silver-bullet thinking expects a new tool to fix a process problem. Engineering causes: inadequate testing, technical debt and skill gaps. Technical debt means shortcuts that make later changes costly.

These causes interact. A fixed deadline with changing scope forces overtime. Overtime raises defects. A rising defect backlog weakens testing. Poor communication hides the change from testers and managers. Skill gaps make estimation worse. Management pressure then pushes the team to report progress instead of risk. Requirements, management and engineering causes often appear together. The figure groups representative causes; the list above is the full set. A useful review asks which branch is active, not which person is slow.

Symptoms, root causes and prevention

A symptom is visible: a slipped milestone, a defect backlog, sustained overtime, unresolved decisions or unclear ownership. A root cause is the earlier condition: no scope control, no test capacity or a missing decision owner. Fixing a symptom alone fails. Adding testers in month 5 may not clear a large untested build; freezing scope may. Ask what changed earlier and who owns the decision. Symptom lists are not cause lists; a missed date is evidence, not explanation.

Track early warning signs: open defects rising faster than fixes, planned dates moving with no scope change, requirements marked to be decided near build, overtime becoming normal, and two people or nobody owning a component. Act when two signs appear together.

Use a blame-free retrospective. Ask what in the process allowed the error, not who to punish. People hide bad news when blame is likely, so warning signs arrive late. Record one or two process changes with owners and dates. Late hiring adds training and communication load.

Worked example

Question. A project has 8 developers, 1 tester, a 6-month deadline and 120 requirements. By month 4, 30 requirements have changed, testing starts in month 5, and 2 developers leave. Give the change percentage, tester-to-developer ratio, remaining developers and testing window, then name three failure causes and one early warning sign.

  1. Change percentage = (30 ÷ 120) × 100 = 25.0%.
  2. Tester-to-developer ratio = 1 ÷ 8 = 0.125 tester per developer.
  3. Remaining developers = 8 − 2 = 6. Staff loss = (2 ÷ 8) × 100 = 25.0%.
  4. Testing window = 6 − 5 + 1 = 2 months.
  5. Causes: changing requirements, weak testing capacity and staff loss. Early warning: testing starts in month 5 with a large untested build. Mitigation: re-baseline scope, add test capacity earlier and re-plan with 6 developers.

Answer. The change is 25.0%, the ratio is 0.125 tester per developer, 6 developers remain, the testing window is 2 months, and late testing with a large untested build is the early warning.

Exam traps

  • Blaming failure only on 'bad programmers'; requirements, schedule and testing capacity are usually stronger causes.
  • Treating a symptom as a root cause: a slipped milestone is evidence, not the cause.
  • Calling all change scope creep; managed change control is different from unapproved additions.
  • Forgetting test capacity: one tester for eight developers is a planning cause, not a testing-team failure.

Long answers here are scored on definitions plus comparison: expect questions that ask you to compare two process models or justify a model choice for a given project, so always name the model's phases, its feedback path and its risk handling.

Remember and understand

Remember Define software. Explain why software is described as programs, data and documents, and list four application domains with one example each. 10 marks

Definition covering programs, data, documents; Why documents matter: maintenance, handover, testing; Four domains: application, embedded, engineering/scientific, AI or product-line; One concrete example per domain; Note that domain decides practices (e.g. embedded needs timing and memory limits).

Understand Explain software engineering as a layered technology. What does each layer contribute, and what happens when a layer is missing? 10 marks

Four layers: quality focus, process, methods, tools; Quality focus at the base; process as the glue that holds layers; Methods: analysis, design, construction, testing techniques; Tools: CASE, IDE, version control support; Consequence of missing process layer: tools and methods used ad hoc, poor quality and control.

Understand Describe the generic process framework and explain any five umbrella activities with an example of each. 12 marks

Five framework activities: communication, planning, modeling, construction, deployment; Definition and purpose of each; Five umbrella activities: tracking and control, risk management, quality assurance, configuration management, measurement; Concrete example per umbrella activity; Point that the framework is adapted, not followed literally.

Understand Explain the phases of the software development life cycle and state the main deliverable of each phase. 12 marks

Initiation/feasibility, requirements, design, coding, testing, deployment, maintenance; Deliverables: feasibility report, SRS, design document, source code, test reports, release; Overlap and feedback between phases; Maintenance as the longest and costliest phase; Verification and validation placement.

Understand List the common software myths held by managers, customers and practitioners, and explain why each is dangerous. 8 marks

Management myths: more people, more tools, buying hardware fixes it; Customer myths: a general goal is enough, requirements can change freely; Practitioner myths: work is done when code runs, quality is tested in later; Effect: wrong estimates, poor requirements, late discovery of defects; Correct view: process, measurement and early quality work.

Remember Explain the waterfall model with a diagram, and list its advantages and limitations. 10 marks

Sequential phases with named deliverables; Feedback generally one phase back; Advantages: simple, documented, milestone-based, good for stable requirements; Limitations: change is costly, working software appears late, risk discovered late; Where it still fits: well-understood, contract-driven, safety-critical projects.

Apply

Apply A retail bank wants a UPI payment feature. Rules from the regulator change every few months and the first release is needed in four months. Choose a process model, and justify it against one alternative. 13 marks

Identify characteristics: changing external rules, need for early release, high transaction safety; Pick incremental or agile, or an incremental core plus prototype for risky parts; Show how requirements changes are absorbed per increment; Reject pure waterfall because of frozen early requirements; Mention umbrella activities: risk management, configuration management, quality assurance; Add regular releases and regression testing.

Apply Take one framework activity — say construction — for a hostel mess billing app built by a four-person team, and write its task set. 10 marks

Name the framework activity and the project context; List concrete tasks in order; Deliverables of each task; Quality checks applied before moving on; Milestone or review point; How the task set differs from a large safety-critical project.

Apply A small team of five developers agrees to follow Extreme Programming. Describe at least six XP practices they would adopt and how each is carried out day to day. 12 marks

Planning game and user stories with on-site customer; Small releases, short iterations; Test-first development and automated unit tests; Pair programming and collective code ownership; Continuous integration; Refactoring and simple design; Metaphor/system metaphor optional; Note: XP needs discipline and customer availability.

Apply An insurance company must move a 15-year-old claim-processing system to a new platform. Explain how you would treat this legacy software, and how reuse could reduce the effort. 12 marks

Definition of legacy software and its business value; Why not simply discard: embedded business rules, undocumented behaviour; Steps: inventory, reverse engineering, restructuring, reengineering, retirement decision; Reuse: reuse of business rules, data and tested modules; product-line thinking; Risk of skipping documentation and regression testing; Cost-benefit note.

Analyze and evaluate

Analyze Analyse why software projects fail. Group the causes under people, process and requirements, and suggest one preventive step for each group. 13 marks

People: skill gaps, high turnover, unclear roles, poor communication, unrealistic schedules; Process: no defined process, no tracking or measurement, skipped reviews, weak configuration management; Requirements: vague scope, unmanaged change, missing stakeholders; Technical causes as a smaller category, not the whole story; One preventive step per group: training and roles, process with milestones and reviews, requirements baseline with change control; Order-of-magnitude statement that most failures are management and requirement failures.

Evaluate Compare the incremental and spiral models. For a large, high-risk defence project, which would you recommend, and why? 13 marks

Both are evolutionary or repeated-delivery in nature; Incremental: each increment adds usable functionality; no explicit risk step; Spiral: four quadrants per loop — objectives, risk analysis, engineering, customer evaluation; Spiral risk analysis suits high-risk projects; also supports prototypes and staged commitment; Incremental simpler to manage and delivers usable features sooner; Recommendation for defence project: spiral, with justification on risk exposure and evaluation gates; Note spiral's overhead and need for risk expertise.

Evaluate A team adopts agile practices but the project still fails. Evaluate the likely reasons and state what agile does and does not guarantee. 12 marks

Agile assumes customer availability, discipline and small co-located teams; Failure causes: no product owner decisions, no automated tests, no definition of done, poor estimation; Umbrella activities still needed: tracking, configuration management, quality assurance; Agile does not remove the need for requirement clarity, architecture for large systems, or documentation where required; Large or regulated systems need scaling and contracts that allow change; Conclusion: practices help, but people and process causes remain decisive.

Evaluate Assess the suitability of the waterfall model for a safety-critical embedded product such as a railway signalling controller, and contrast it with an agile approach. 13 marks

Embedded domain traits: timing, memory limits, hardware dependence, certification needs; Waterfall strengths here: documented phases, traceability, formal reviews and verification at each stage; Weakness: late feedback on real hardware, change expensive; Agile strengths: early feedback, continuous testing; weaknesses: certification evidence and hardware dependency; Hybrid suggestion: planned phases with iterative prototyping and continuous integration in later stages; Criteria: cost of change, need for traceability, external safety standards.

Glossary

Backlog
The ordered list of work items or features still to be built, reordered as priorities change.
Continuous integration
Merging each developer's work into the shared build many times a day, with automated tests run on every merge.
Feasibility study
An early check of whether the proposed system is technically, economically and operationally workable.
Framework activity
One of the five broad work areas of the generic process framework: communication, planning, modeling, construction, deployment.
Increment
The piece of usable functionality added to the product by one iteration.
Iteration
One pass through the development activities that produces a tested, runnable result.
Pair programming
Two developers working at one machine, one writing code and the other reviewing as it is written.
Process assessment
Examination of an organisation's process against a reference model to find improvement priorities.
Process model
A simplified, organised description of how a project will move through the lifecycle phases.
Project charter
A short authorising document that states the project's purpose, scope, objectives and key people.
Prototype
A partial or rough working version built to learn about requirements or technical risk before full development.
Refactoring
Improving the internal structure of working code without changing what it does.
Requirements engineering
Eliciting, analysing, specifying and validating what the software must do.
Risk management
Identifying, analysing, planning for and monitoring events that could harm the project.
Software configuration management
Identifying, controlling and recording changes to work products so versions and variants stay under control.
Software engineering
The application of a systematic, disciplined, quantifiable approach to the development, operation and maintenance of software.
Software process
The set of activities, their ordering, and the constraints and resources that produce a software product.
Software project tracking and control
Comparing actual progress and cost against the plan and taking corrective action.
Software quality assurance
Planned activities and checks that give confidence the process and product meet agreed standards.
SRS
Software requirements specification: the agreed written statement of required behaviour and constraints.
Stakeholder
Any person or group affected by the system or able to influence its requirements.
Umbrella activity
Project-wide work such as tracking, risk management, quality assurance, configuration management and measurement that applies in every phase.
Validation
Checking that the right product was built — that it meets the user's real need.
Verification
Checking that the product was built correctly according to its specification.
