4.1 Testing principles, defects and test cases

Testing compares what a program should do with what it actually does, under conditions you control and can repeat. It exists because people make mistakes and those mistakes reach the user as wrong behaviour. A test case records the inputs, the steps and the expected result, so the comparison is repeatable and someone else can verify your verdict. Banks run such cases before raising a withdrawal limit, IRCTC before a tatkal window, a phone maker before an update. Testing can show that defects exist. It can never show that none are left.

You need Unit 2 requirements engineering, because every test case traces back to a stated requirement; the verification versus validation split is covered in 4.2.

Error, fault, failure: three words, one chain

A person makes a mistake. That is an error. Because of the error, something wrong stays in the product: a line of code, a rule in the design, a value in a configuration file. That wrong thing is a fault. Some syllabi call it a defect, and programmers say bug. When the software runs and control reaches the fault, the user sees wrong behaviour. That event is a failure.

The chain error → fault → failure tells you where to look. A failure is only a symptom. Testing sees failures, debugging walks back to the fault, and the fault walks back to the error, which may be a rushed review or a rule nobody taught the developer. Not every fault becomes a failure: code that never runs cannot fail. And one fault can cause many failures, so twenty red test results may mean one broken function, not twenty broken features.

A test case is one controlled comparison. It carries an ID, a purpose naming the requirement it checks, preconditions, test data, the steps to follow, the expected result, the actual result, and a status of pass or fail. A set of test cases is a test suite. The test oracle is whatever supplies the expected result: the SRS, a domain expert, a hand calculation, or the output of the previous version.

Unscripted testing from personal experience, with nothing written down, is ad-hoc testing. It can find a defect quickly. It is not repeatable, it has no expected result to compare against, and it cannot be counted, so it supplements scripted cases and never replaces them.

The principles that stop wrong beliefs

Seven principles appear in almost every text. Each one attacks a belief that makes teams test badly.

  • Testing shows the presence of defects, not their absence. Passing tests raise confidence; they do not prove correctness.
  • Exhaustive testing is impossible. You cannot try every input combination, so you pick a small set by risk, as in 4.4.
  • Test early. A defect caught in a requirements review costs far less to fix than the same defect caught in production.
  • Defects cluster. A small number of modules hold most of the defects. Spend the effort there and keep retesting them.
  • The pesticide paradox. The same tests used again and again stop catching new defects. Review the suite and add cases every cycle.
  • Testing is context dependent. A hospital infusion pump and a college fest website need different depth and different tests.
  • The absence-of-errors fallacy. A product can be free of known defects and still be useless, because it solves the wrong problem.

Specifying a test case

Write each test case so that another engineer can run it next month without asking you anything. This template is common.

Beginners skip the expected result. Without it there is nothing to compare and the run produces no information. Keep one behaviour per test case, so a failure points to one place. When a case fails, the defect report carries the test case ID, build version, environment, steps to reproduce, expected and actual results, and any log or screenshot. Some teams then hold a defect bash: a fixed one- or two-day session where a group attacks one module and logs everything found. That suits clustered defects, because everyone digs in the same hot area.

Worked example

Question. A savings account holds ₹5,000 and the ATM holds enough cash. Write test cases TC1 and TC2 for withdrawal, run TC1, and decide the status when the ATM gives ₹2,000 in cash but the screen shows a balance of ₹3,500.

  1. Read the rule from the requirement: a withdrawal succeeds when the amount is less than or equal to the balance and the ATM has cash; otherwise the ATM shows 'Insufficient balance' and gives no cash. On success the balance is reduced by the amount and a receipt is printed.
  2. TC1 test data: amount = ₹2,000, balance = ₹5,000. Check the rule: 2,000 ≤ 5,000, so the withdrawal is allowed.
  3. TC1 expected result: cash out = ₹2,000; new balance = ₹5,000 − ₹2,000 = ₹3,000; receipt printed.
  4. TC2 test data: amount = ₹6,000, balance = ₹5,000. Check the rule: 6,000 > 5,000, so the withdrawal is refused.
  5. TC2 expected result: message 'Insufficient balance'; cash out = ₹0; balance stays ₹5,000.
  6. Run TC1. Actual: cash out = ₹2,000 (correct), balance shown = ₹3,500.
  7. Compare: cash matches, balance does not. Difference = ₹3,500 − ₹3,000 = ₹500 too high.
  8. Verdict: TC1 fails, because one expected value differs. The failure points to the balance update or display, not to the cash dispenser, which behaved correctly.
  9. TC2 has not been run yet. A failure in TC1 says nothing about TC2, which keeps its own status until run.

Exam traps

  • Writing a test case with inputs and steps but no expected result. With nothing to compare, no run can produce a pass or a fail, and the examiner marks the case incomplete.
  • Using one failure as proof that the whole program is broken. A failure is a symptom, a fault is the cause, and one fault commonly causes many failures.
  • Mixing up the chain. A programmer typing < instead of ≤ is the error; the wrong line left in the code is the fault; the wrong interest calculated at run time is the failure. Exams ask exactly this.
  • Treating 'all tests passed' as 'no defects'. Testing shows presence, not absence, and exhaustive testing is impossible, so a clean run only means your chosen cases found nothing.
  • Calling an ad-hoc exploration a test case. It has no fixed steps and no oracle, so it cannot be counted, rerun, or added to a regression suite.

4.2 Verification vs validation; quality assurance vs quality control

Verification asks one question: are we building the product right? It compares the SRS, the design and the code against what was written down, and nothing is executed. Validation asks a different question: are we building the right product? It runs the software against the user's real need. Quality assurance prevents defects by shaping the process, while quality control detects defects in the product that already exist. These four labels place every quality activity in a project, so a team knows whether a defect should be caught by a review or by a test, and whether money should go into the process or into more testing.

You need: the SDLC phases (see Unit 1, Software and Process Models) and the idea of a test case from Chapter 4.1.

Verification: are we building the product right?

Verification compares a work product with the document or standard it must satisfy. Work products are the SRS, the design models, the code and the test plans. A person reads and compares; no code runs. Because nothing executes, verification is called static.

It exists because defects are cheap early and costly late. A wrong sentence in the SRS takes minutes to fix in a review and weeks to fix after release. A two-hour review of a 60-requirement SRS that finds 9 defects usually saves far more than two hours of later testing.

The static techniques, from least to most formal:

  • Desk check: the author rereads their own work against a checklist. Some syllabi call this a deskcheck.
  • Walkthrough: the author presents the document to two to four colleagues, who ask questions and note problems.
  • Review: a small team with fixed roles (moderator, author, recorder, reviewers) reads against a checklist and records every defect found.
  • Inspection: the most formal review, with entry and exit criteria and collected data.

A code review checks one extra thing: that the code follows the team's coding standards (naming, indentation, comment rules, error handling) and matches the design. Review procedure and roles are in Unit 6.

Validation and the V-model

Validation compares the running product with the user's real need. It needs execution, so it is dynamic. Its levels are unit, integration, system and acceptance testing (see Chapter 4.5 and Chapter 4.6).

Why both are needed: a team can verify perfectly — every design matches the SRS, every line matches the design — and still fail, because the SRS itself described the wrong product. Verification catches did we build it as specified; validation catches was the specification right.

The V-model links the two. Every development phase has a matching test level, planned while that phase runs: requirements match acceptance testing, design matches system and integration testing, code matches unit testing. The left arm of the V is verification of each work product; the right arm is validation at that level.

Take the requirement "a user pays a bill in under 30 seconds". Verification checks that the SRS states it, measures it in seconds and makes it testable. Only running the app with real users shows whether they actually manage it.

Quality assurance and quality control

Quality assurance (QA) is process-oriented and preventive. It builds a way of working that keeps defects out: coding standards, review rules, test policy, training, checklists, process audits and the metrics that show whether the process works. QA acts before the product exists.

Quality control (QC) is product-oriented and detective. It examines an output — a document, a build, a release — for defects already in it. Reviews of deliverables and all testing are QC.

They are not synonyms and not alternatives. QA decides that every code change needs a review before merge and that a build must pass 40 payment tests. QC is the review and the test run on one specific build. When QC finds three failing payment tests, that evidence goes back to QA, which strengthens the weak process step that let the defects in.

Question. A UPI app must let a user pay a ₹250 chai bill in under 30 seconds. Records for one release: (i) a review of the SRS (60 requirements) found 9 defects; (ii) a design review found 6 defects; (iii) a code review of 2400 lines found 15 defects; (iv) 10 users each tried once — 8 finished under 30 s with times 21, 23, 25, 27, 22, 24, 26, 24 s, and 2 took 38 s and 45 s; (v) 114 of 120 code changes were reviewed before merge; (vi) 40 payment tests ran on the release build and 37 passed. Classify each record, then compute the percentage of users meeting the target, the mean time of those users, the review coverage and the test pass rate.

  1. Classify by the question asked. (i), (ii), (iii) read documents and code against the SRS and design, and nothing runs: verification. (iv) runs the product with real users against the 30-second need: validation. (v) is a rule about how work is done before merge: QA. (vi) inspects the built release for defects: QC.
  2. Verification defects caught before any test ran: 9 + 6 + 15 = 30 defects.
  3. Target met: 8 of 10 users, so 8 × 100 ÷ 10 = 80.0%.
  4. Sum of the successful times: 21 + 23 + 25 + 27 + 22 + 24 + 26 + 24 = 192 s. Mean = 192 ÷ 8 = 24.0 s, which is below the 30 s limit.
  5. The two failures at 38 s and 45 s did not meet the need. Validation is not passed, so the 45 s path gets a defect report and the release is not accepted.
  6. Review coverage (QA evidence): 114 × 100 ÷ 120 = 95.0%. Six changes merged without review — an assurance gap to fix in the process.
  7. Test pass rate (QC evidence): 37 × 100 ÷ 40 = 92.5%. The 3 failures are QC findings that go back to QA as process feedback.

Answer. Verification: (i)–(iii), 30 defects found without running code. Validation: (iv), 80.0% of users met the 30-second target with mean 24.0 s. QA: (v), 95.0% review coverage. QC: (vi), 92.5% test pass rate.

Exam traps

  • Saying testing is the only form of validation. Reviews and inspections also test documents; they are verification.
  • Saying quality assurance and quality control are synonyms. QA is preventive and process-oriented; QC is detective and product-oriented.
  • Claiming verification needs the code to run. Verification can be done on paper; validation cannot.
  • Confusing requirements validation (checking that the SRS states the right need, from Unit 2) with product validation (checking that the running software meets that need).
  • Writing desk check and deskchecking as two different techniques. They are the same technique, spelled two ways in different syllabi.

4.3 White-box testing: basis path and control structure

White-box testing designs test cases by looking inside the code. The tester draws the control flow graph, counts its independent paths, and chooses inputs that make each path run. This finds unreachable code, wrong conditions and missing branches that black-box tests can miss. It is used at unit level, on safety-critical modules, and wherever coverage must be measured. The main method here is basis path testing; control structure testing adds condition, data flow and loop checks.

You need Chapter 4.1 for test cases, and basic programming control structures such as if, while and switch.

From code to a control flow graph

White-box testing is also called structural, glass-box or clear-box testing. The tester reads the source code and designs tests from its control flow. This differs from black-box testing, which uses only the specification.

A control flow graph (CFG) is a directed graph. A node is a statement or a block of statements that always execute together. An edge is a transfer of control from one node to another. The entry node is where execution starts; the exit node is where it stops. A decision node has two or more outgoing edges, one per outcome.

Coverage measures how much of the CFG the tests touch.

  • Statement coverage: every node runs at least once.
  • Branch or decision coverage: every edge out of every decision node runs at least once.
  • Condition coverage: each basic condition inside a compound decision takes both true and false.
  • Path coverage: every path from entry to exit runs. Loops can make this infinite, so full path coverage is rarely possible.

Statement coverage can reach 100 percent while a false branch is never taken. Branch coverage is stronger, but it still does not prove that every part of a compound condition was tested.

Cyclomatic complexity and a basis set

Cyclomatic complexity V(G) measures the number of independent paths through a CFG.

V(G) = E − N + 2P

E is the number of edges; N is the number of nodes; P is the number of connected components, usually 1, so 2P is usually 2.

V(G) is the size of a basis set, not the total path count. A basis is a small set of paths from which every other path can be built by adding or removing loop iterations. A loop can give infinitely many paths, but V(G) stays finite.

  1. Draw the CFG and number its nodes and edges.
  2. Count E, N and P, then compute V(G).
  3. Choose one baseline path from entry to exit.
  4. Add one new edge at a time until you have V(G) paths; each new path must be independent.
  5. Choose an input that forces each path to run.

For a structured program with one connected component, V(G) also equals the number of binary decisions plus one. Three independent paths means three tests in the basis set.

Control structure testing

Control structure testing widens white-box testing beyond basis paths. It checks the internal structure of decisions, data and loops.

  • Condition testing: test each basic condition and each AND/OR combination. Watch short-circuit evaluation: in a && b, b is not evaluated when a is false.
  • Data flow testing: follow each variable from its definition to its uses. A define-use pair is a place where a variable is set and a later place where it is read. Undefined or dead values show up here.
  • Loop testing: for a loop that can run 0 to n times, test skip (0), once, twice, a typical value, n−1, n, and n+1 if the code allows it. For nested loops, test the inner loop with the outer at minimum and maximum.

A few advanced syllabi add symbolic execution, which runs code with symbol values, and model checking, which exhaustively checks a state model. Both are beyond this chapter.

Worked example

Question. A module runs: read n; if n > 0 then s = n + 1 else s = −n; if s > 10 then print 'large' else print 'small'. (a) Draw its CFG and count nodes and edges. (b) Compute V(G). (c) List three basis paths and give one input for each.

  1. Nodes: 1 read n; 2 decision n > 0; 3 s = n + 1; 5 s = −n; 6 decision s > 10; 7 print large; 9 print small; 10 end. The node numbers skip 4 and 8; only these eight nodes exist, so N = 8.
  2. Edges: 1→2, 2→3 (T), 2→5 (F), 3→6, 5→6, 6→7 (T), 6→9 (F), 7→10, 9→10. So E = 9.
  3. The graph is one connected component, so P = 1. V(G) = 9 − 8 + 2 × 1 = 3.
  4. Baseline path 1-2-3-6-7-10. Input n = 12: n > 0 is true, s = 13, s > 10 is true, output is large.
  5. Path 1-2-5-6-9-10. Input n = −5: n > 0 is false, s = 5, s > 10 is false, output is small.
  6. Path 1-2-3-6-9-10. Input n = 5: n > 0 is true, s = 6, s > 10 is false, output is small.

Answer. V(G) = 3 independent paths; the three inputs are n = 12, n = −5 and n = 5.

Exam traps

  • V(G) is the size of a basis set, not the total number of paths. A loop can give infinite paths while V(G) stays small.
  • Forgetting the +2P term, or using E − N + 1 for a single component. The standard formula gives E − N + 2 when P = 1.
  • 100 percent statement coverage can still miss a false branch; it does not guarantee branch coverage.
  • 100 percent branch coverage does not guarantee condition coverage. For if (a > 0 && b < 5), the tests a = 5, b = 3 (true) and a = −1, b = 3 (false, short-circuited on a) give both branch outcomes, yet b < 5 is true in both tests, so it never takes the value false.

4.4 Black-box testing: equivalence partitioning, boundary values

Black-box testing designs test cases from the written specification only, without looking at the code. You treat the program as a closed box: feed it inputs, read the outputs, compare with what the specification promised. It exists because most defects a user suffers are visible behaviour — a wrong total, a missing check, a wrong message — and because these tests survive a rewrite. Two techniques choose the inputs. Equivalence partitioning groups inputs that should behave alike, and boundary value analysis tests the edges of those groups. Functional testers use both on booking forms, UPI screens and login pages.

You need: Chapter 4.1 for test cases and expected results, and Unit 2 (the SRS) for the input rules this chapter turns into tests.

The black box view

The specification is the only source. A black-box test case is an input plus the output the specification promises for it. You never read the code, so the same tests still work after the code is rewritten.

Black-box testing is also called functional, specification-based or behavioural testing. White-box testing (Chapter 4.3) measures how much code a test suite executes. Black-box testing measures how much of the specification the suite checks.

The input domain is the set of all values one input item can receive. The output domain is the set of all results the program can produce. A specification states both as rules: age is an integer from 1 to 120; a PIN is exactly four digits.

Strength: it catches wrong visible behaviour — a wrong fare, a missing validation, a wrong message. Weakness: it cannot say which lines of code no test reached. Use both kinds.

Equivalence partitioning

Inputs in the same class should be handled the same way: same validation, same route through the rules, same kind of output. If one value in the class finds a defect, the others probably would too. So one representative value per class is enough.

  1. List every input item and its rule from the specification.
  2. Split each input domain into valid classes (accepted) and invalid classes (rejected).
  3. Give each class an ID, C1, C2 and so on, and pick one representative value from each.
  4. For a single input item, write one test case per class with its expected output, so the count equals the number of classes. With several input items, cover all valid classes of one input in the same case where possible, and use one case per invalid class; the count is the largest number of valid classes for any one input plus the total number of invalid classes.
  5. For invalid classes use one invalid value per test case.
  • Range a to b: one valid class (a to b), two invalid classes (below a, above b).
  • A list that accepts up to n items gives three classes: 0 items, 1 to n items, and more than n items.
  • A yes/no input where both answers are allowed gives two valid classes, true and false. False is an invalid class only when the rule requires yes, for example a terms-and-conditions box that must be ticked.
  • A set of allowed codes: one valid class per code, plus one invalid class for any other code.

Boundary value analysis

Defects cluster at the edges of a class. A programmer writes age ≥ 1 and age ≤ 120, or slips and writes > 1. The middle of the range almost never fails; the values at and just outside the limit do.

a−1, a, a+1, b−1, b, b+1

a is the lowest accepted value and b the highest; a−1 and b+1 are the values just outside the valid range.

With a = 1 and b = 120 the values are 0, 1, 2, 119, 120, 121. Some syllabi call the extra outer values a−1 and b+1 robustness testing.

Boundaries also sit inside a range wherever behaviour changes. The age rule changes at 60, so 59, 60 and 61 are boundary values too. Testing 60 alone does not show whether 59 wrongly gets the discount.

Partition first, then take the boundaries of each class. Do not drop the invalid classes: test 0 and 121, not only 1, 2, 119 and 120.

Decision tables for combined rules

When two or more rules interact, a decision table lists the conditions and the action for every combination. Two yes/no conditions give 2² = 4 rules, so at least four test cases.

Worked example

Question. A railway booking form accepts a passenger's age as an integer from 1 to 120. A passenger aged 60 or more gets the senior discount. (a) List the equivalence classes. (b) List the boundary values for the range 1 to 120. (c) Give test cases for the ages 0, 1, 2, 59, 60, 61, 119, 120 and 121, with the expected result for each.

  1. Read the rules: valid age is an integer from 1 to 120, and the discount starts at 60. Behaviour changes at three places: 1 (start of the valid range), 60 (discount start) and 120 (end of the range).
  2. (a) Classes: C1 = age below 1, invalid, rejected. C2 = 1 to 59, valid, accepted without discount. C3 = 60 to 120, valid, accepted with discount. C4 = age above 120, invalid, rejected. That is 4 classes.
  3. (b) Boundaries of 1 to 120: 1−1 = 0, 1, 1+1 = 2, 120−1 = 119, 120, 120+1 = 121.
  4. Internal boundary at 60: 60−1 = 59, 60, 60+1 = 61.
  5. (c) The nine values 0, 1, 2, 59, 60, 61, 119, 120, 121 are all different, so they give 9 test cases.
  6. Expected results: 0 rejected; 1, 2 and 59 accepted without discount; 60, 61, 119 and 120 accepted with discount; 121 rejected.
  7. Each of the nine cases checks what the specification fixes: the form accepts or rejects the age, and for 60 to 120 it shows the senior discount message.

Answer. Four equivalence classes and nine boundary test cases: 0 and 121 rejected, 1, 2 and 59 accepted without discount, 60, 61, 119 and 120 accepted with the senior discount.

Exam traps

  • Testing only a middle value of a valid range and never testing the invalid classes, so nothing is learnt about rejection.
  • Missing an internal boundary such as 60 when the requirement has two rules; 60 is a boundary, not just the ends 1 and 120.
  • Writing the boundary list off by one: for 1 to 120 it is 0, 1, 2, 119, 120, 121, not 1, 2, 119, 120 and not 0, 1, 120, 121.
  • Putting two invalid values in one test case; the first rejection can stop the check, so the second is never exercised.
  • Mixing up the two techniques: equivalence partitioning takes any representative of a class, boundary value analysis deliberately takes the edges.

4.5 Unit testing and integration testing

Unit testing checks one module alone, using a driver to call it and stubs to replace the modules it calls. Integration testing checks whether modules work together, using a chosen order and interface tests. Both exist because defects hide at two places: inside a module and at the boundary between modules. A unit test gives a fast, repeatable pass or fail for one small piece of code. Integration testing then finds wrong parameter order, missing data, incompatible types and timing faults that a unit test cannot see. The same harness ideas appear in everyday work: a payment module is tested with a fake bank, then joined to the real billing flow.

You need: Chapter 4.1 for test cases and defects, Chapter 4.4 for black-box test design, and Unit 3 coupling for interfaces.

Unit testing and the test harness

Unit testing checks one module, class or function on its own. The unit is the smallest part that can be compiled and called. A defect found inside one small module is cheap to locate; a defect that escapes into the full product is costly.

Unit test planning lists the units to test, each unit's inputs and outputs, the test data, and the expected result. Designing unit tests uses the detailed design of the module: its interface, data structures and logic. Black-box tests come from the specification; white-box tests come from the code, as Chapter 4.3 and Chapter 4.4 explain. A unit test case has an input, a precondition, the call, and the expected output.

A test harness is the software that runs a unit test. A driver is a small program that calls the unit under test, passes inputs and records the result. A stub is a fake module that the unit calls; it returns fixed, simple values. Some syllabi call the harness a unit test harness. The driver replaces the caller; the stub replaces a called module. Do not swap them: the driver calls the unit, the stub is called by the unit.

The harness runs the tests, compares actual with expected, and records pass or fail. A failure is logged with the input, expected value, actual value and a defect report. A unit test should not use a real database, network or payment gateway. Such a test is slow, hard to repeat, and it tests more than one unit. Replace those external parts with stubs.

Integration testing strategies

Integration testing checks whether modules work together. A unit can pass alone and still fail when it calls another module with a different parameter order, a missing field or a different data type. Integration testing finds these interface defects and checks that the assembled build matches the design.

Big-bang integration puts all modules together and tests the whole. It is quick to start and hard to debug: when one test fails, many modules could be the cause. It suits very small systems only.

Top-down integration starts with the top control module. Modules below it are replaced by stubs. Test the top, replace one stub with the real module, then the next. It needs stubs, not drivers. It finds control and interface problems early. A low-level module may be tested late.

Bottom-up integration starts with the lowest modules. Each low-level module is called by a driver that supplies inputs. Test the bottom, combine with the next level, and use a driver until the top exists. It needs drivers, not stubs. It finds low-level defects early, but the top control logic is tested late.

Sandwich or hybrid integration combines top-down and bottom-up. The top is tested downward with stubs; the bottom is tested upward with drivers; the two meet in a middle layer. It balances early testing of control and low-level code.

Incremental builds add one module or a small group at a time and rerun the integration tests after each build. This shows which build introduced a failure. Integration test planning chooses the order, the interfaces to test, the stubs and drivers needed, and the data for each interface. Record pass or fail for each interface test, not just for the whole build.

Interface defects and integration test planning

Integration tests focus on interfaces. Common interface defects are: wrong parameter order, where calculateGST(rate, amount) is called with the arguments reversed; missing data, where a field is absent or null; incompatible types, where a string "18" is passed where an integer 18 is expected; and timing, where one module expects data before another module produces it. A wrong parameter order can produce a plausible but wrong answer, so interface tests need boundary values and exact expected outputs.

Designing integration tests follows the chosen order. For each pair of modules, list the values passed, the values returned, and the error cases. For top-down order, write stubs with fixed returns. For bottom-up order, write drivers that call the lower module. For sandwich order, prepare both. The test data should include normal values, boundary values and invalid values.

Integration test planning names the modules, the build order, the interfaces in each build, the stubs and drivers, the test environment, and the pass/fail record. Keep the unit tests and rerun them after integration repairs; that is regression testing, covered in Chapter 4.7. Unit testing answers 'does this module work alone?' Integration testing answers 'do these modules work together?' System testing, which checks the whole product against requirements, comes in Chapter 4.6.

Worked example

Question. A module calculateGST(amount, rate) returns amount × rate ÷ 100. Billing calls calculateGST and Invoice. (a) Design a unit test for calculateGST with amount = ₹1,000 and rate = 18. State the driver call and expected result. (b) In top-down integration, Billing is tested first with a stub Invoice returning ₹1,180. Billing computes total = invoice amount + GST on that amount at 18%. Find the GST and total. (c) Name one driver and one stub here, and say what unit versus integration testing checks.

  1. Unit inputs: amount = ₹1,000, rate = 18. Expected GST = 1,000 × 18 ÷ 100 = ₹180.
  2. Driver call: calculateGST(1000, 18). Compare actual with ₹180; pass if equal, else log the defect.
  3. Integration: Billing is the unit under test. The Invoice stub returns ₹1,180. Billing calls calculateGST(1180, 18). GST = 1,180 × 18 ÷ 100 = ₹212.40.
  4. Total = 1,180 + 212.40 = ₹1,392.40.
  5. Driver: the integration test driver that calls Billing. Stub: Invoice returning ₹1,180. Unit testing checks calculateGST alone; integration testing checks Billing's calls to calculateGST and Invoice, including argument order and return values.

Answer. Unit expected GST is ₹180; integration GST is ₹212.40 and total is ₹1,392.40. The driver calls the unit; a stub is called by the unit under test (here Billing calls the Invoice stub). Unit testing checks calculateGST alone; integration testing checks Billing with Invoice.

Exam traps

  • Swapping driver and stub: a driver calls the unit under test; a stub is called by the unit under test.
  • Using a real database, network or payment gateway inside a unit test; replace it with a stub so the test is fast and isolated.
  • Treating top-down integration as needing drivers: top-down needs stubs; bottom-up needs drivers.
  • Assuming a module that passes its unit test will pass integration; interface defects appear only when modules are joined.
  • Testing only normal values at interfaces; wrong parameter order and incompatible types often show up on boundary or invalid values.

4.6 System testing, acceptance testing and debugging

System testing checks the complete product against its requirements. Acceptance testing checks whether the customer will actually use it. Debugging finds and repairs the cause after a failure. These steps exist because unit and integration tests check parts, not the whole journey or user fit. A team uses them before releasing a UPI app, an IRCTC booking flow or banking software. System testing catches end-to-end gaps; acceptance testing gives the customer a measurable gate; debugging turns a reported failure into a repaired fault.

You need: Chapter 4.5 on unit and integration testing, and Unit 2 on requirements.

System testing the whole product

System testing checks the complete, integrated product against the requirements. Unit and integration tests check parts; system testing checks the whole journey. A test case has preconditions, steps and one expected outcome, which you may check with several assertions. Scenario testing designs system tests from end-to-end user stories. For a UPI app: log in, add a beneficiary, transfer ₹500 from account A (balance ₹2,000) to account B (balance ₹1,000), and check both balances. The single outcome is that the transfer completes and money is conserved: A = ₹1,500, B = ₹1,500 and total money = ₹3,000.

System testing also checks system qualities. Recovery: cut power during a transfer and restart; the app must not debit twice. Security: a user without login must not see another user's balance. Performance, stress, configuration and usability tests are in Chapter 4.8. Documentation testing checks the user guide, help text and error messages against the real screen. If help says 'tap Send Money' but the button says 'Pay', the document has a defect. System testing is verification at product level: the product must satisfy the requirements written in the SRS. Whether the product meets the user's real need is judged later, by acceptance testing. See Chapter 4.2.

Acceptance testing with users and contracts

Acceptance testing asks whether the customer will use the product. The customer, not the developer, judges it. User acceptance testing (UAT) uses real users on realistic tasks. In the example, 20 users each make 3 transfers; at least 18 of 20 must complete all 3 without help. That is 18 ÷ 20 = 90% of users.

  • Alpha testing happens at the developer's site. Intended users try the product while developers watch and record problems.
  • Beta testing happens at the user's site with real data and less control. Some syllabi call these alpha-beta tests.
  • Contract acceptance runs tests written in the contract.
  • Regulation acceptance checks rules from a regulator, such as a central bank's rules for a payment app.

Acceptance criteria must be measurable. 'Works well' is not a criterion. '18 of 20 users finish 3 transfers without help' is a criterion. UAT verifies fitness for use; it is not a hunt for coding faults. Alpha and beta are acceptance tests, not system tests.

Debugging: from failure to fix

Debugging is not testing. Testing finds a failure: actual behaviour differs from expected behaviour. Debugging finds the fault that caused the failure and repairs it. A fault is the defect in the code; a failure is what the user sees. The loop is: reproduce the failure, diagnose the cause, repair the code, then run regression tests. Regression testing is in Chapter 4.7.

  • Brute force: add print statements or logging, read memory dumps, and narrow the place where values go wrong.
  • Backtracking: start at the failure and walk backwards through the code until the first wrong value appears.
  • Cause elimination: list possible causes, design a test for each, and remove causes one by one.

A defect bash is a short, focused session where the whole team hunts for as many defects as possible in the running product. It is a group testing activity that feeds the debugging loop; it is not a separate test level. Program analysis tools inspect code statically or at run time. Symbolic execution runs code with symbols instead of numbers. Model checking explores system states against a property. Only a few universities teach the proofs; know the idea: automated help to locate faults.

Worked example

Question. A UPI app must transfer money between two accounts. System test: transfer ₹500 from account A (balance ₹2,000) to B (balance ₹1,000); expected A = ₹1,500 and B = ₹1,500. Write the debugging steps and the regression test to run after the fix.

  1. System test: start A = ₹2,000, B = ₹1,000. Transfer ₹500. Expected A = 2,000 − 500 = ₹1,500; B = 1,000 + 500 = ₹1,500; total = 1,500 + 1,500 = ₹3,000.

  3. Failure: app says success but B stays ₹1,000. Reproduce with the same starting balances and the same ₹500 transfer; record A and B after each step.
  4. Diagnose: trace the transfer path; find where the debit commits but the credit does not. A likely cause is that the credit update fails or is not committed, and the error is ignored.
  5. Repair: put debit and credit in one transaction; commit only when both succeed; on error roll back and show a failure message.
  6. Regression: rerun the original ₹500 transfer, the failed-credit case, a double-transfer test, and the chosen old tests from Chapter 4.7.

Exam traps

  • Fixing only the success message when the balance update is wrong. That hides the symptom and leaves the fault.
  • Calling beta testing a system test. Beta testing is acceptance testing at the user's site.
  • Using UAT as a hunt for coding faults. Unit, integration and system tests find code faults; UAT judges fitness for use.
  • Treating a defect bash as a test level. A defect bash is a focused group search for failures; diagnosis and repair come afterwards, followed by regression tests.

4.7 Regression testing

Regression testing reruns tests that already exist, after a change, to show that behaviour which was not meant to change still works. Software is coupled: fixing a refund bug can quietly break invoice calculation, because both call the same tax function. A regression test suite is the kept set of tests used for this check. Every team that ships a second version does this, whether it reruns everything overnight or picks the twelve tests that touch the code that changed. The choice of what to rerun is the engineering decision.

You need: Chapter 4.1 for what a test case and an expected value are, and Chapter 4.6 for where debugging starts after a failure.

What regression testing is and why it exists

Regression testing is rerunning tests that already exist, after a change, to check that behaviour which was not meant to change still works. The change may be a bug fix, a new feature, a refactor, an upgraded library or a new database. A fault found this way is a regression defect: something that used to work and now does not.

It exists because software is coupled. Invoice generation and refund processing both call the same tax function. A developer changes that function to round down, to settle a refund complaint. Invoice totals now come out one rupee low. Nothing in the refund story mentions invoices, so no new test covers it; only an old invoice test can catch it.

A regression test suite is the subset of tests the team keeps, runs and maintains for this purpose. It is not every test ever written; it is the set whose protection is worth its running cost. Tests enter when new behaviour becomes important and leave when the behaviour is removed.

Retest-all is the simplest selection strategy: run every test you have. It is safe by construction, because nothing is skipped. Its cost is the full suite. Five hundred tests finishing in six minutes is cheap enough to run on every change; a system suite that takes nine hours is not, and it delays every release.

Choosing which tests to rerun

Selection has two parts: which tests to rerun, and in what order. Some syllabi call the whole activity regression test selection.

  • Retest-all: every test, no analysis. Strongest guarantee, highest cost.
  • Random selection: k tests picked at random. Cheap and fast, with no guarantee; useful as a research baseline that smarter methods must beat.
  • Safe selection: a set guaranteed to contain every test the change could make fail, so fault detection equals retest-all. It needs coverage data (which test runs which line) plus a diff of what changed.
  • Impact analysis: read the version diff to find changed modules, walk the call graph upward to their callers, and select the tests that touch any of them. Practical and widely used, but not proven safe.

Order matters when time runs out. Prioritise by risk (money, safety, data loss) and by how often the feature is used. Login, search, add to cart and payment run first; the quarterly report export runs last. If a run is stopped at twenty minutes, the tests that did run should be the valuable ones.

Keeping the suite correct when expected outputs change

The expected output is part of the test. When a requirement changes on purpose, the old expected output becomes wrong, and a correct program starts to look broken. Updating the test is part of the change, not an afterthought.

  1. Decide whether the old expectation is still a requirement, or was deliberately replaced.
  2. If it was replaced, change the expected value in the same commit as the code.
  3. Name the test after the requirement, so the reason for the value is visible, such as invoice_gst_12_percent.
  4. Add tests for the new behaviour, including boundary values (Chapter 4.4).
  5. Delete tests for behaviour that no longer exists; a suite full of stale tests gets ignored.

Smoke testing is a different, smaller thing. A smoke test is a quick check that a new build is not broken: it starts, a user can log in, the main page loads. A passing smoke test says the build deserves deeper testing; it is not a regression suite, and five smoke tests say very little about invoice arithmetic. A failing smoke test means stop and fix the build.

Running the suite automatically after every commit, and the version control that makes the diff possible, belong to Unit 5. Here the question is only what to rerun and why.

Worked example

Question. An online store changes the GST rate on invoices from 18% to 12%. The full test suite has 500 tests, the regression suite has 80 tests, and impact analysis selects 12 tests that touch invoice calculation. One regression test uses a taxable amount of ₹1,000 and expects tax of ₹180. (a) Which tests should be rerun for this change, and in what order? (b) Which test must be updated, and to what value? (c) Why is retest-all not always the best choice here?

  1. Classify the change: 18% to 12% is a deliberate requirement change, so failures in tests that hard-code 18% are expected, not defects.
  2. Old expected tax: 1000 × 0.18 = ₹180. That is the value stored in the old test.
  3. New expected tax: 1000 × 0.12 = ₹120.
  4. Old invoice total: 1000 + 180 = ₹1,180. New invoice total: 1000 + 120 = ₹1,120.
  5. Update the invoice test: expected tax ₹180 → ₹120, expected total ₹1,180 → ₹1,120. This edit ships with the rate change.
  6. Rerun set: the 12 impact-selected tests, because they touch invoice calculation. Order them by risk: GST invoice, checkout total, payment amount, then refund recalculation.
  7. If those 12 pass and time allows, run the 80-test regression suite. Retest-all of 500 is the fallback when risk is high or the whole suite is cheap.
  8. Cost ratio: 500 ÷ 12 = 41.7, so impact selection runs about 41.7 times fewer tests than retest-all.

Answer. Rerun the 12 impact-selected tests with the GST invoice test first, update its expected tax from ₹180 to ₹120 and its total from ₹1,180 to ₹1,120, then escalate to the 80-test suite or the full 500 only if risk or a cheap suite justifies it; impact selection runs about 41.7 times fewer tests.

Exam traps

  • Rerunning a stale expected value after a deliberate requirement change, so a correct program is reported as failing. Check whether the expectation or the code is wrong before filing a defect.
  • Calling every rerun a regression test without a selection reason. Regression testing is defined by why the test is chosen, not by the fact that it ran twice.
  • Treating a passing smoke test as a regression suite. Smoke proves the build is alive; it does not prove invoice arithmetic.
  • Assuming impact analysis is safe. It is a practical approximation; only coverage-based safe selection has the same fault-detection power as retest-all.
  • Updating the code only and forgetting to add tests for the new behaviour, so the new 12% path is never checked.

When the suite is cheap enough to run in the time available, when the change touches a widely used core module so almost everything is impacted, when safety or money is at stake and a missed regression is unacceptable, and when no reliable coverage data exists to support safe selection. Selection methods earn their complexity only when these conditions fail.

Beyond the syllabus

Not for the exam. Regression test selection is an active research area: safe selection algorithms need coverage maps that are expensive to maintain, so industry often approximates with test impact analysis inside build tools. Large monorepos select tests from the dependency graph of packages rather than from source lines. Machine-learning selectors rank tests by historical failure patterns. Flaky tests, which pass and fail without any code change, are the main practical obstacle to trusting any selection. Search for 'regression test selection', 'test impact analysis' and 'flaky tests'.

4.8 Performance, stress, configuration and usability testing

Non-functional testing measures qualities, not features. Performance testing asks how fast the system answers under expected load. Stress testing asks what happens beyond capacity and whether the system recovers. Configuration testing asks whether one product works across hardware, operating systems, browsers and networks. Usability testing asks whether real users can finish their tasks, including users who need a keyboard, a screen reader, large text or high contrast. A ticket site that is correct but takes 8 seconds on a booking day fails its users. These tests turn qualities into numbers you can check.

You need: Chapter 4.1 for expected versus actual behaviour, and Chapter 4.6 for system testing; Unit 3, User interface design for usability goals.

Performance testing and load testing

Performance testing is the umbrella term for measuring speed and capacity under a stated workload. Response time is the time from sending a request to receiving the full reply, in seconds. Throughput is the number of completed requests divided by the observation time, in requests per second. Resource use covers CPU percentage, memory in MB and network in Mbps. Within it, load testing runs the system at the anticipated load, including the expected peak such as 10,000 virtual users on a ticket site; stress testing (Section 2) goes beyond that peak.

Throughput = completed requests ÷ observation time

completed requests is the count finished in the window; observation time is the window length in seconds; throughput is in requests per second.

A virtual user is a software thread that sends requests like a person, with think time — the seconds a person spends reading before the next click. Report the 95th percentile response time: 95% of requests were faster than this value. The average hides the slow users who complain.

  1. Define the target: 95% of searches under 3 s at 10,000 virtual users.
  2. Build a workload mix: 70% search, 20% seat view, 10% payment.
  3. Ramp up virtual users and hold the peak for 10 minutes.
  4. Record response time, throughput, errors, CPU and memory.
  5. Compare with the target and with the previous release.

Stress testing and recovery

Stress testing pushes beyond the expected peak until the system breaks or degrades. It answers three questions: where is the breaking point, does the system fail safely, and does it recover? For the ticket site, a stress run uses 20,000 virtual users. Response time is 5.6 s and some requests fail. A safe system queues work or shows a wait page; it does not lose a payment.

Recovery is part of the test. Drop the load back to 5,000 users and check that response time returns to 1.4 s and no data is corrupted. A soak test holds a moderate load for hours to find memory leaks and disk filling. Stress is not the same as performance: performance checks the target, stress checks the limit and the way back.

Configuration, compatibility and internationalisation testing

Configuration testing runs the same tests on a matrix of supported environments: hardware (phone, tablet, desktop), operating system versions, browser versions, screen sizes and network speeds such as 4G and throttled 3G. A full matrix is too large, so choose by risk or use pairwise combinations. Compatibility testing checks versions and devices, including older Android versions still in use.

Internationalisation testing checks language, currency, date and number formats. The same number is grouped ₹1,23,456.78 in India (lakh grouping: 1,23,456) and 123,456.78 in the US (thousand grouping). The currency symbol is also part of the locale; the actual amount depends on the exchange rate. A date 03/04/2025 means 3 April in India and 4 March in the US. German text may be 30% longer than English and break a button. Test the locale, not just the translation.

Usability and accessibility testing

Usability testing watches real users, not developers, attempt representative tasks. A moderator gives a task: “Book a train ticket from Chennai to Bengaluru for tomorrow.” Record completion rate, time on task, errors and satisfaction. In the example, 8 of 10 users complete a booking in 2 minutes; the two failures show where the form confuses people. Think-aloud asks users to speak their thoughts as they work.

Accessibility testing checks that people with disabilities can use the product. Keyboard only: every action is reachable without a mouse. Screen reader: images have text alternatives and form fields have labels. Contrast: normal text is at least 4.5:1 against its background. Text size: the layout survives 200% zoom. Captions make video usable without sound. Accessibility is usability testing with a specific user group and specific checks.

Exam traps

  • Stress testing is not the same as load testing: stress goes beyond the expected peak and checks recovery.
  • A response-time average hides slow users; use the 95th percentile for the target.

  • A usability test with developers or with one colleague is not a usability test; use representative real users.

4.9 Testing object-oriented, web and mobile applications

Object-oriented, web and mobile systems fail in ways that plain functions do not. An object can dispatch to a subclass, a web page depends on a session stored on a server, and a mobile app loses the network when a call arrives. This chapter shows tests that follow those mechanisms: class trees for OO code, browser and session paths for web apps, and device plus network conditions for mobile apps. The ideas extend the functional test design from Chapters 3 and 4 and the configuration testing from Chapter 8.

You need: Chapter 4.1 for test cases, 4.4 for input partitions, 4.5 for unit and integration levels, and Unit 3 UML class diagrams for inheritance.

Object-oriented testing follows the class tree

Some syllabi call this testing OO systems and website testing; the tests still follow the same mechanisms. Object-oriented testing checks a method, a class, a cluster of classes and the whole system. Method testing is unit testing of one operation. Class testing checks all methods plus the object's state. Cluster testing checks classes that collaborate. System testing checks the complete OO product. See 4.5 for the unit and integration levels.

Inheritance means a subclass gets methods from its parent and may override them. A test suite for a subclass must run all inherited tests that still apply, then its own tests. Testing only the base class misses changes in the child.

Polymorphism means a variable of base type can hold any subclass object. One call can run different methods. Test each actual type, not just the base type. The figure shows Payment with subclasses UPI and Card.

State-based testing is for objects with memory. Test a legal sequence and an illegal sequence. A payment object must not pay twice after a timeout. Use the state chart from Unit 3 to list states and events.

Web tests cover content, links, forms and sessions

A web app splits into the browser page, server code and a database. A web test must check content, links, forms, cookies and sessions, navigation, browser compatibility, basic security and performance.

  • Content: text, price and currency are correct.
  • Links: no broken link and no wrong destination.
  • Forms: mandatory fields, field rules and boundary values from 4.4.
  • Cookies and session: HTTP has no memory, so the server sends a cookie with a session id. Test login, logout, timeout, back button and two tabs.
  • Navigation: back, forward and refresh must not repeat a payment or show stale data.
  • Browser compatibility: run the same tests on Chrome and Firefox, and on the versions you support.
  • Security basics: validate input, keep passwords out of URLs, and do not expose the session id.
  • Performance: use 4.8 for load and stress tests.

Mobile tests cover device, network and interruption

A mobile app runs on many devices and OS versions. Use a device and OS matrix. Test high-risk combinations, not every device. A ₹500 payment may work on one phone and fail on another with low memory.

  • Network: Wi-Fi, 4G, weak signal and lost network during payment. Check retry and no double debit.
  • Interruptions: incoming call, SMS, notification, battery low, low memory, screen rotation, background and foreground.
  • Location: permission denied, stale GPS and no GPS.
  • Install and update: fresh install, upgrade with old data and uninstall.
  • Usability: touch target size, font size, offline message and error recovery.

Configuration testing from 4.8 gives the matrix method. A device is a configuration; each scenario with input and expected result is a test.

Worked example

Question. A payment system has base class Payment with method pay(amount). UPI and Card extend Payment and override pay(). A test creates Payment[] p = {new UPI(), new Card()}; p[0].pay(₹500) must use UPI and p[1].pay(₹500) must use Card. A web login form is tested on Chrome and Firefox with one valid login and one wrong password. A mobile app is tested on 4 devices with network lost once during a ₹500 payment. Write one OO test, one web test and one mobile test. Count the concrete test cases.

  1. OO polymorphism: there are 2 actual types, UPI and Card. Case 1 calls p[0].pay(500) and checks that UPI.pay ran. Case 2 calls p[1].pay(500) and checks that Card.pay ran. Count = 2.
  2. Web login: browsers = 2 (Chrome, Firefox). Form cases = 2 (valid login, wrong password). Web cases = 2 × 2 = 4. On each browser, a valid login must create a session cookie; a wrong password must not.
  3. Mobile payment: devices = 4. Network-loss cases per device = 1. Mobile cases = 4 × 1 = 4. For each device, cut the network after the ₹500 request; expect an error or retry and only one debit.
  4. Total concrete cases = 2 + 4 + 4 = 10.

Answer. The example gives 2 OO polymorphism cases, 4 web login cases and 4 mobile network-loss cases, for 10 concrete test cases in total.

Exam traps

  • Testing only the base class and not each subclass. The override in UPI or Card can fail while Payment passes.
  • Treating polymorphism as one test. One call can run different methods; test each actual type that the variable can hold.
  • On web, checking only that the page loads. Test form rules, session cookie, logout, timeout and the back button.
  • On mobile, testing one device on Wi-Fi only. Add network loss during payment and at least one interruption such as a call.
  • Counting a device or browser as a test without input and expected result. A device is a configuration; a scenario is a test.

Check yourself

Remember Define method testing, class testing, cluster testing and system testing for OO software. 2 marks

Method testing checks one operation. Class testing checks all methods plus object state. Cluster testing checks collaborating classes. System testing checks the complete OO product.

Understand Why must a subclass test suite include inherited tests? 3 marks

The subclass inherits behaviour that users still depend on. If the subclass changes shared state or overrides a method, old base behaviour can break. Inherited tests catch that regression; subclass tests add new behaviour.

Apply Payment is the base class. UPI and Card override pay(). An array holds one UPI object and one Card object. How many polymorphism test cases are needed for pay(₹500), and what does each assert? 4 marks

Two cases. Case 1 calls pay(500) on the UPI object and asserts UPI.pay ran. Case 2 calls pay(500) on the Card object and asserts Card.pay ran. A base-only test does not prove either override.

Apply A login form is tested on 3 browsers with 2 form cases: valid login and wrong password. How many web test cases are there? 3 marks

3 browsers × 2 form cases = 6 web test cases. Each valid login must create a session cookie; each wrong password must not.

Analyze A mobile payment app fails only on 4G during payment. Which test conditions should be added? 4 marks

Add network handover from Wi-Fi to 4G, weak 4G signal, network loss after the request, and retry after reconnection. Check one debit only, clear error message and no duplicate payment.

Analyze Why is testing a web app on Chrome only and a mobile app on one Android device risky? 4 marks

Browser engines and device OS versions differ in JavaScript, layout, permissions, memory and network handling. A path that works on one configuration can fail on another. Use a small risk-based matrix, not one configuration.

Understand What is state-based testing for an object? 3 marks

It tests sequences of calls that change the object's state. Test a legal sequence and an illegal sequence, such as paying twice after a timeout, using a state chart.

Remember List four web session checks. 2 marks

Login creates a session, logout ends it, timeout ends it, and the back button after logout must not show protected data. Also check that a second tab uses the same session correctly.

Takeaways

  1. Testing compares expected and actual behaviour; passing tests never proves that defects are absent.
  2. Verification checks the specification, validation checks the user need; QA works on the process, QC on the product.
  3. White-box testing uses control flow; basis path testing gives a small set of independent paths to cover.
  4. Black-box testing uses the specification; equivalence partitioning and boundary values choose efficient inputs.
  5. Unit testing needs drivers and stubs; integration testing needs an order and interface checks.
  6. System testing checks the whole product; acceptance testing checks whether the customer will use it.
  7. Debugging finds and repairs the cause after a failure; it is not the same as testing.
  8. Regression testing after every change protects unchanged behaviour.
  9. Non-functional tests measure speed, capacity, configuration fit and ease of use.
  10. OO, web and mobile systems need tests for state, sessions, devices and networks.
