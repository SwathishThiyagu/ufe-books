6.1 Management spectrum and project planning

Software project management is the work of turning a goal into a plan that a team can follow and correct. It uses four linked views: people, product, process and project. Some syllabi call them the four P's. The views are not phases; they are lenses on the same job. A one-page plan joins them: what is in scope, who does it, how it is built and checked, and what it may cost in time and money. Teams use this in small college builds and in large paid projects, because a schedule without scope or people is guesswork.

You need Unit 1, Foundations: Software and Process Models, especially process models and the reasons projects fail.

The four views

The management spectrum says a manager looks at four things at once. Skipping one view hides a problem that appears later as delay or rework.

  • People: the roles, skills and communication the work needs. A team of six may have one Android developer, one tester, one designer and three developers. Name who owns each task.
  • Product: the scope and features of what is built. Write what the first release includes and what it leaves out.
  • Process: the tasks and reviews that turn requirements into tested software. A weekly build and a review at week 5 are process choices.
  • Project: the plan and control that keep scope, schedule and cost visible. A spend check at week 6 is a project control.

The four P's are views of one project, not four phases. People do product work through a process under project control. Change one view and the plan changes. If a tester is missing, product scope may shrink; if scope grows, the process needs more reviews and the project needs more money.

From views to a one-page plan

The plan is one page, not a binder. It states the boundary and the checks that prove the work is done.

  1. Write the product scope: first-release features, deferred features and the acceptance test.
  2. Check feasibility: technical, schedule and cost. A payment gateway has a different cost from a static menu page.
  3. List tasks from the process: design, build, test and review. Add an owner to each task.
  4. Estimate effort and cost with decomposition (breaking work into tasks) or COCOMO (an empirical cost model); see 6.3.
  5. Schedule tasks and find the critical path, the longest chain of dependent tasks that sets the finish date; see 6.4.
  6. Write the risk plan: top risks, probability, impact and response; see 6.5.
  7. Set the baseline and control: weekly status, approved changes and replanning; see 6.2 for metrics and 6.6 for version control of work products.

A one-page plan is enough for a small team because it names the scope, the tasks, the dates, the money and the person who checks each item. Detailed charts come later.

Control and replanning

Control compares plan with fact. The approved plan is the baseline; the status gives actual values. A variance is a difference that needs a decision.

planned spend by week k = B × k ÷ N

B is total budget in rupees; N is number of weeks; k is the week number from 1 to N; spend is in rupees.

This assumes an even spend across weeks; if spend is uneven, add the weekly planned amounts up to week k instead.

For B = ₹40,000 and N = 10, planned spend by week 6 is 40,000 × 6 ÷ 10 = ₹24,000. If actual spend is ₹29,000, the project is ₹5,000 over the planned spending line — a cost overrun, not progress. Spending above plan only looks acceptable if the work finished is also ahead; here the manager must check scope or cost.

Control points differ by view. People: a skills gap or an overloaded member. Product: a new feature that was not in scope. Process: a review that finds many defects. Project: spend, date or a missed milestone. Each control point needs an owner, a date and a pass condition. If a check fails, replan the one page; do not hide the failure in a status report.

Monitoring is not the same as testing. Testing checks the product; monitoring checks the plan. A weekly build can pass tests while the schedule slips.

  • Treating the four P's as phases; they are views used together on one project.

6.2 Software measurement and metrics for process and project

Software measurement replaces opinion with numbers. A team says the project is going well; a metric says it has used 15% more effort than planned and removed 80% of its defects before release. Measurement matters because plans, reviews and estimates improve when someone records what actually happened. Teams size bids, track sprints, judge whether a build is safe to release, and check whether a process change worked.

You need: 6.1 Management spectrum and project planning for the plan these numbers measure, and the process framework from Unit 1 (see Unit 1, Foundations: Software and Process Models).

Measure, metric and indicator

A measure is a number produced by a counting rule you write down before you count. Defects found in review is a measure. The rule fixes what counts as a defect, which reviews are included, and the unit. Without a written rule, two people counting the same project produce two numbers and then argue about the numbers instead of the project.

A metric is a measure with a scale and a purpose: a ratio, a rate, or a count per unit of size. Some syllabi state it as the degree to which a system, component or process possesses a given attribute. Defects per KLOC is a metric; 1,200 defects is only a measure. An indicator is a small set of metrics read together to answer one management question, such as whether this build is safe to ship.

  1. Name the metric and the question it answers, in one sentence.
  2. Write the counting rule: what is counted, what is excluded, and the unit (defects per KLOC, hours, rupees).
  3. Name the data source and the person who records it.
  4. State the threshold and the action: at what value does the team change something?

Process, project and product metrics

Software metrics fall into three domains, and mixing them is the commonest error here. Process metrics belong to the organisation and outlive any single project; they show whether the way of working is improving. Project metrics belong to one project and are read while it runs. Product metrics describe the artefact being built: its size, defects, complexity and behaviour.

Process metrics include defect removal efficiency, review rate in pages per hour, rework as a percentage of total effort, and phase containment, which is the percentage of defects injected in a phase that are also removed in that same phase: defects found in phase i ÷ defects injected in phase i × 100%.

DRE = D_before ÷ (D_before + D_after) × 100%

DRE is defect removal efficiency; D_before is defects found before delivery (reviews plus testing); D_after is defects reported by users after delivery. A value near 100% means few defects escaped.

Project metrics include effort variance, schedule variance, cost variance and change requests per phase. They are reviewed weekly and answer whether the plan from 6.1 still holds.

EV = (E_actual − E_planned) ÷ E_planned × 100%

EV is effort variance; E_actual is person-days used; E_planned is person-days planned. A positive value is an overrun, a negative value is an underrun.

Product metrics include defect density, mean time between failures, cyclomatic complexity and response time under load. Defect density normalises defects by size so two products compare.

Defect density = D ÷ S

D is defects counted in a stated window; S is product size in KLOC (thousands of lines of code) or in function points. The unit is defects per KLOC or per function point, and it must be stated.

Goals, leading indicators and quality attributes

The goal-question-metric idea, usually written GQM, keeps measurement honest. You state a goal with a purpose, an issue, an object and a viewpoint; derive three to five questions that would tell you whether the goal is met; then choose one metric per question. A metric that answers no question is dropped, because every count costs effort and invites argument.

Leading indicators move before the outcome, so you can still act: requirement churn, review coverage, open high-severity defects, build success rate. Lagging indicators report after the fact: post-release defects, final cost overrun, customer-reported outages. A dashboard needs both. The leading number tells the team what to change this week; the lagging number confirms whether last month's change worked.

Quality attributes are measured through the questions they answer; reliability uses mean time between failures and availability.

MTBF = MTTF + MTTR;  Availability = MTTF ÷ (MTTF + MTTR) × 100%

MTTF is mean time to failure; MTTR is mean time to repair; MTBF is mean time between failures; availability is the fraction of time the system is usable. Times are in hours.

Worked example

Question. A team planned 200 person-days of effort and used 230. Reviews and testing found 120 defects before delivery; users reported 30 more in the first six months after release. The product size is 25 KLOC. Compute (a) effort variance as a percentage of plan, (b) defect removal efficiency, and (c) defect density per KLOC.

  1. Data: E_planned = 200 person-days, E_actual = 230 person-days, D_before = 120 defects, D_after = 30 defects, S = 25 KLOC.
  2. Effort variance: 230 − 200 = 30 person-days over plan; (30 ÷ 200) × 100% = 15%. Positive means an overrun.
  3. Total defects that ever appeared: 120 + 30 = 150 defects.
  4. DRE = 120 ÷ 150 × 100% = 80%. One defect in five escaped to users.
  5. Defect density = 150 ÷ 25 = 6 defects per KLOC.
  6. Split for insight: 120 ÷ 25 = 4.8 per KLOC before release; 30 ÷ 25 = 1.2 after.

Answer. Effort variance is 15% over plan, DRE is 80%, and defect density is 6 per KLOC (4.8 before release, 1.2 after).

Exam traps

  • Using a product metric as a process metric. Defect density describes the product; DRE describes how well the process removed defects. Label the domain first.
  • Computing DRE with review defects only. Leaving out the 30 post-release defects gives 120 ÷ 120 = 100%, hiding every escaped defect.
  • Sliding the base of effort variance. Divide by E_planned, not E_actual: 30 ÷ 230 gives 13.0%, not 15%. Keep the sign: positive is overrun.
  • Mixing units in defect density. 150 defects ÷ 25,000 lines = 0.006 defects per line, which is the same as 6 defects per KLOC. The error is writing that answer as "per KLOC"; divisor and unit must match. State the unit every time.
  • Treating a lagging indicator as leading. Post-release defect counts tell you what already happened; they cannot change this week's build.

6.3 Effort and cost estimation: COCOMO and decomposition

Effort and cost estimation predicts how many person-months a project needs and what it will cost before code exists. It exists because budgets and delivery dates must be set early, when uncertainty is high. The work is split into small pieces, each piece is sized, and the sizes are combined. Basic COCOMO then converts size in KLOC into effort and duration. Indian teams use this in fixed-price contracts with clients and in project approval notes.

You need Chapter 6.2 for measurement terms and the requirements material in Unit 2 for sizing.

Decomposition: size the parts, not the whole

Decomposition means breaking the project into small parts, sizing each part, and adding the sizes. It gives a defendable estimate instead of one guess.

  • Problem-based estimation decomposes by user function: login, search, payment, report.
  • Process-based estimation decomposes by lifecycle activity: requirements, design, code, test, deployment.
  • Use-case estimation weights actors and use cases by complexity and technical factors, then converts the weighted total to effort using past projects.
  • LOC is delivered source lines of code; KLOC is thousands of LOC.
  • Function points measure function from inputs, outputs, queries, files and interfaces, so they are language-independent. Some versions multiply this unadjusted total by a value adjustment factor built from 14 general system characteristics such as performance and data communication.

Each method gives a low, likely and high value. Reconciliation compares the methods, checks assumptions, and adopts a supported range. Do not average blindly; a gap usually exposes a missing task or a wrong size.

Basic COCOMO: from KLOC to effort

Basic COCOMO is an empirical model: it fits past projects, not physics. It needs size in KLOC.

E = a × (KLOC)<sup>b</sup>; D = c × E<sup>d</sup>

E is effort in person-months; KLOC is thousands of delivered source lines; D is duration in calendar months; a, b, c, d are mode constants.

For organic mode, a = 2.4, b = 1.05, c = 2.5 and d = 0.38. Organic means a small, familiar, stable project. Semidetached and embedded modes use different constants because they carry more constraints.

Duration, staff and the estimate review

Duration and staff come after effort. D = c × Ed gives calendar months, and average staff = E ÷ D. A 26.9 person-month job over 8.7 months needs about 3.1 full-time people on average. The team is rarely constant: it is small during requirements and larger during construction, so use the average for budgeting and a schedule for daily work; see Chapter 6.4. Cost is effort times a blended rate that includes salary, overhead and tools. Report an estimate as a range with assumptions: size basis, mode, rate date, contingency. Re-estimate when requirements change. COCOMO is a starting model; calibration to local data improves it.

6.4 Project scheduling

A schedule turns estimated effort into dated tasks, arranged in the order the work must happen. Estimation (see 6.3) says how much work exists; scheduling says when each piece starts and ends. The chain of tasks that fixes the finish date is the critical path, and it is what a project manager watches every week. Every plan, sprint board and release calendar is a schedule. Get the ordering wrong and the team is busy but late.

You need: effort and cost estimation from 6.3, plus the process models of Unit 1 to know which phases exist to be scheduled.

From effort to dated tasks

A work breakdown structure (WBS) splits the project into tasks small enough to estimate, assign and finish, usually one to ten person-days each. Each task then carries two different numbers. Effort is the total human work, counted in person-days. Duration is the space the task takes on the calendar, counted in working days.

Effort and duration are not the same. Two testers on a task estimated at 6 person-days need more than 3 days, because they must talk, share one build and wait for each other. Divide effort by people only when the work splits cleanly.

Duration ≈ Effort ÷ People

Effort is in person-days; People is the number assigned to the task; Duration is in working days. Add roughly 10–20% for coordination when People is more than 1.

  • Finish-to-start: B cannot start until A finishes. This is the common case.
  • Start-to-start: B may start once A has started, after some lag.
  • Finish-to-finish: B cannot finish until A finishes.
  • Start-to-finish: B cannot finish until A starts. Rare, used for some handovers.

Dependencies come from technology (testing needs code), from people (one database expert shared by two tasks) and from the customer (sign-off before release). Each dependency is an arrow in the schedule network.

Network, forward pass and the critical path

Tasks drawn as nodes with dependency arrows between them form a network. A path is any chain of tasks from the start of the project to its end. The project duration is the length of the longest path by duration, not the path with the most tasks. Two passes find it.

  1. Forward pass: the earliest start (ES) of a task is the largest earliest finish among its predecessors; a task with no predecessor has ES = 0.
  2. Earliest finish: EF = ES + duration.
  3. Project duration T = the largest EF anywhere in the network.
  4. Backward pass from T: the latest finish (LF) of a task is the smallest latest start among its successors; for the last task, LF = T.
  5. Latest start: LS = LF − duration.
  6. Slack of a task = LS − ES = LF − EF; tasks with zero slack are critical.

Slack = LS − ES = LF − EF

ES is earliest start, EF is earliest finish, LS is latest start, LF is latest finish, all in working days; Slack is the number of days the task can slip without moving the finish date.

The critical path is the chain of zero-slack tasks from start to finish. It controls the finish date: every day it slips, the project slips by one day. A task with slack can use those days freely, up to the slack, without touching the date.

E = (O + 4M + P) ÷ 6

O, M and P are the optimistic, most likely and pessimistic durations in days; E is the expected duration used in the network in place of a single guess. This is the PERT three-point estimate.

Gantt charts, milestones and tracking

A Gantt chart draws one horizontal bar per task on a calendar axis. The bar starts at the earliest start, its length is the duration, and dependent bars sit end to end. Critical bars are usually coloured differently. Anyone can read it in ten seconds, which is why it appears in every status meeting.

Milestones are zero-duration markers for a finished event: design frozen, user acceptance signed off. They give checkpoints without pretending a review consumes no time. Level the schedule when one person is booked on two tasks in the same week; move the task with slack, never the critical one.

A schedule is a prediction, so it must be tracked. Every week, for each task, record the actual start, the actual finish if reached, and the remaining duration. Compare with the baseline. A task with 30% of its duration left and only two days before its latest finish needs action now: reassign people, cut scope, or accept a slip and re-plan the rest of the network.

Timeboxing reverses the usual logic: fix the end date, then fit the work inside it. If the box fills, drop the lowest-priority requirements instead of extending the date. An agile sprint of two to four weeks is a timebox. Report a slipping critical path into 6.5 as a project risk, and hand fixed release dates to 6.9.

Question. A module is broken into six tasks. A takes 3 days and starts first. B takes 4 days after A. C takes 2 days after A. D takes 5 days after B. E takes 3 days after C. F takes 2 days and starts after both D and E finish. Find the project duration, the critical path, and the slack of tasks C and E.

  1. Forward pass, task A: no predecessor, so ES = 0 and EF = 0 + 3 = 3 days.
  2. Task B: ES = EF of A = 3, EF = 3 + 4 = 7 days. Task C: ES = 3, EF = 3 + 2 = 5 days.
  3. Task D: ES = EF of B = 7, EF = 7 + 5 = 12 days. Task E: ES = EF of C = 5, EF = 5 + 3 = 8 days.
  4. Task F has two predecessors: ES = max(EF of D, EF of E) = max(12, 8) = 12, EF = 12 + 2 = 14 days. Project duration T = 14 days.
  5. Backward pass. F: LF = 14, LS = 14 − 2 = 12. D: LF = LS of F = 12, LS = 12 − 5 = 7. E: LF = 12, LS = 12 − 3 = 9.
  6. B: LF = LS of D = 7, LS = 7 − 4 = 3. C: LF = LS of E = 9, LS = 9 − 2 = 7. A: LF = min(LS of B, LS of C) = min(3, 7) = 3, LS = 3 − 3 = 0.
  7. Slack = LS − ES. A: 0. B: 3 − 3 = 0. C: 7 − 3 = 4 days. D: 7 − 7 = 0. E: 9 − 5 = 4 days. F: 12 − 12 = 0.
  8. The zero-slack chain is A, B, D, F, and its lengths add to 3 + 4 + 5 + 2 = 14 days, which matches T.

Answer. Project duration is 14 days; the critical path is A → B → D → F; tasks C and E each have 4 days of slack.

Exam traps

  • Choosing the path with the most tasks. The critical path is the longest by duration; eight 1-day tasks take 8 days, two tasks of 5 days take 10.
  • Confusing effort with duration. A 20 person-day task with 2 people is not 20 days on the calendar, and it is usually more than 10.
  • Starting a task at the earlier predecessor's finish. With two predecessors, ES is the maximum of their earliest finishes, never the minimum or the average.
  • Adding slacks along one chain. Tasks in series share the same float, so two tasks showing 4 days each give the path 4 days, not 8.
  • Reading a Gantt bar's length as effort. The bar shows duration only; effort sits in the estimate behind it.

Earned schedule tracks time rather than cost. Schedulers and agile boards implement these ideas, so the network maths stays the same underneath. 6.5 Risk management: identification, projection, RMMM

A software project can fail for reasons nobody wrote down: a key developer resigns, a payment API changes, a server dies the night before a demo. Risk management is the practice of writing those reasons down early, ranking them by how likely and how costly they are, and deciding in advance what to do about each one. It exists because decisions taken in a panic cost far more than decisions taken in a calm meeting. Teams use it from the first estimate to the day the product is released.

You need: 6.1 for the four management views and 6.4 for dated tasks, because risk impact is measured in the same person-weeks your schedule uses.

Reactive and proactive strategies, and the three risk families

A reactive team waits for the problem, then fights it. A key developer resigns on Monday and the whole week goes into reading her code. Reactive work is expensive: dates slip, fixes are rushed, and the same problem returns on the next project.

A proactive team looks for trouble while there is still time to act. It lists the risks, ranks them, writes the response, and re-checks the list every few weeks. One short meeting with the team and the tech lead usually finds the top ten risks in an afternoon.

Software risks fall into three families. Write the family next to every risk; it shows whether the list is one-sided.

  • Product risks: the thing being built. Scope creep, vague requirements, a size estimate that is half of reality.
  • Process risks: how the team works. Resignations, an unrealistic schedule, reviews skipped under deadline pressure, a test environment that arrives late.
  • Technology risks: the tools used. A first project on a new message queue, a bank sandbox that is not ready, a third-party payment API that changes without notice.

Risk identification and risk projection

Identification is a search, not a guess. Brainstorm with the whole team. Walk down a checklist of the three families. Read the postmortem of the last project. Ask each lead one question: what keeps you awake about this release? Write every risk as one sentence that names the cause and the effect, for example: the payment gateway may change its response format before release. Aim for ten to twenty risks, not two.

Projection gives each risk two numbers. Probability P is the chance that it happens, written as a value between 0 and 1. Impact I is the loss if it happens, in person-weeks of effort or in rupees. The two combine into risk exposure.

RE = P × I

RE is the risk exposure in person-weeks; P is the probability of the risk, 0 ≤ P ≤ 1; I is the impact if the risk occurs, in person-weeks.

Refinement splits a coarse risk into a sharper one. The coarse risk "a developer leaves" becomes "the only developer who understands the reconciliation module leaves before the March freeze". The sharper version gives an honest P and an honest I. New risks appear as the project moves, so the cycle repeats.

RMMM: mitigation, monitoring and management

Each high-ranked risk gets three actions. Mitigation works before the risk fires: it lowers P, or lowers I, or both. Monitoring watches for the trigger so the team is not surprised. Management, which some syllabi call contingency, is what the team does after the risk has happened.

  1. Write the ranked risk table with P, I and RE for each risk.
  2. For each risk above the cut-off line, write the mitigation action, its owner and its cost.
  3. Write the trigger that shows the risk is now real, for example two failed integration tests in a row.
  4. Write the monitoring plan: who checks what, how often, and where the finding is recorded.
  5. Write the management plan: the steps taken once the trigger fires.
  6. Compare the mitigation cost with the expected loss. Spend only where the numbers justify it.

The RMMM plan is one written document: the risk table, the mitigation action, owner and cost per risk, the trigger, the monitoring method and frequency, and the contingency steps. A risk with RE of 1.2 person-weeks does not deserve 3 person-weeks of prevention. Keep the plan under version control, so the approved version is the one people follow; see 6.6.

Worked example

Question. A team lists three risks for a release. R1: the key developer leaves, probability 0.2, impact 6 person-weeks. R2: the payment API changes, probability 0.4, impact 3 person-weeks. R3: a server outage, probability 0.1, impact 10 person-weeks. Compute the risk exposure of each risk, rank them, and write one full RMMM entry for the top risk.

  1. Use RE = P × I, with P as a fraction between 0 and 1 and I in person-weeks.
  2. R1: RE = 0.2 × 6 = 1.2 person-weeks.
  3. R2: RE = 0.4 × 3 = 1.2 person-weeks.
  4. R3: RE = 0.1 × 10 = 1.0 person-weeks.
  5. Rank by RE: R1 and R2 tie at the top with 1.2 person-weeks each, and R3 is third with 1.0 person-weeks.
  6. R1 entry, mitigation: work in pairs on the reconciliation module and keep a written handover note, which lowers P from 0.2.
  7. R1 entry, monitoring: the tech lead checks the handover note and the pair rotation once a month, and records the status in the risk table.
  8. R1 entry, management (contingency): a backup developer who has read the handover note takes over the module within one week if the developer resigns.

Answer. The exposures are R1 = 1.2, R2 = 1.2 and R3 = 1.0 person-weeks, so R1 and R2 tie at the top; R1 is handled by pair programming plus a written handover note, monthly monitoring, and a named backup developer.

Exam traps

  • Writing probability as 20 or 40 instead of 0.2 or 0.4. RE then comes out a hundred times too large.
  • Mixing units in the impact column: some risks in rupees, some in person-weeks. Convert everything to one unit before multiplying.
  • Swapping mitigation and management. Mitigation acts before the risk fires and lowers P or I; management is the contingency run after the trigger fires.
  • Adding P and I instead of multiplying them. RE is a product, so a risk with P = 1.0 and I = 2 person-weeks scores lower than one with P = 0.5 and I = 8 person-weeks.
  • Treating identification as a one-time kickoff task. The list must be revisited each cycle, and whenever scope, staff or technology changes.

The high-probability risk will most likely happen, so mitigation that lowers P or spreads the work is worth paying for early. 6.6 Software configuration management

Software configuration management (SCM) is the set of practices that keeps every work product under control. A work product can be code, a requirements document, a test case, a build script or a database schema. SCM gives each such item a name and a version, stores it, and allows a change only through an approved route. It exists because many people edit shared products and because a released product must be rebuilt exactly. You meet SCM in every version control system, every change request, and every CI/CD pipeline that builds from a tagged commit.

You need: 6.1 for the project plan, and Unit 5 for version control and CI/CD basics.

Configuration items and baselines

A configuration item (CI) is any work product that SCM treats as a unit. Typical CIs are a source file, a requirements section, a test plan, a build script and a release note. Each CI has an identifier, a version and an owner. A version is one saved state of the CI; version 1.2 is not better than 1.1, it is a later state.

A baseline is an approved, frozen set of CI versions. It is the reference for later work. If baseline B1 holds login 1.0, SRS 1.0 and test plan 1.0, a developer may change a private copy, but the baseline stays fixed. A change enters the baseline only after approval. Write it as B1 = {login 1.0, SRS 1.0, test plan 1.0}. The braces list the CIs and versions; the numbers after each name are versions.

Baselines stop uncontrolled drift. A tester can report a defect against B1 and know exactly which code and documents were tested. A build can be repeated from B1 years later. Without a baseline, the latest version changes every hour and nobody can say what was tested or released.

Change control, status accounting and audit

A change request (CR) is a written request to change a baseline. It states the CI, the reason, the proposed new version and any linked defects. Impact analysis estimates affected CIs, effort and risk before a decision. The change control board (CCB) is a small group that approves or rejects the CR. The CCB does not usually write the code; it guards the baseline.

  1. Record CR-07 with the requested change and its reason.
  2. Analyse impact: which CIs, test cases and releases are affected.
  3. Send the CR to the CCB for approve or reject.
  4. If approved, make the change in a branch, review and test it.
  5. Update the affected CIs and write a new baseline.
  6. Tell affected teams and record the decision.

Status accounting is the record of each CI and CR through its life: open, under review, approved, implemented, released or rejected. It answers what happened to CR-07. Configuration audit checks reality against records. A functional audit asks whether the delivered item meets requirements; a physical audit asks whether the correct versions, documents and build inputs are present. Audit catches a release that was built from an unrecorded local change.

Version control, build records and CI/CD

Version control stores each CI and its history. It supports branches for parallel work and tags for baselines. A tag such as B2 is a fixed name for a set of versions. The repository alone is not SCM; it is the storage layer for SCM records. See Unit 5, Version control systems.

A build record lists the source versions, compiler or tool versions, dependencies and commands used for one build. A release record lists the CIs delivered to users, the approved CRs, test evidence and the rollback version. These records make a build reproducible and an audit possible.

In CI/CD, each pipeline run should start from a recorded commit or tag and write its result to an artifact repository. A pipeline that builds from a developer's uncommitted folder breaks SCM. A pipeline that tags every release and stores the build record makes SCM automatic. The pipeline does not replace the CCB; it enforces the approved baseline and records what it built. See 6.9 for the release package and rollback plan.

Worked example

Question. Baseline B1 has login module 1.0, SRS 1.0 and test plan 1.0. CR-07 is approved and changes login to 1.1 and test plan to 1.1. Write baseline B2 and say how many items changed.

  1. List B1: login = 1.0, SRS = 1.0, test plan = 1.0.
  2. Apply the approved CR to login: login changes from 1.0 to 1.1.
  3. Apply the approved CR to the test plan: test plan changes from 1.0 to 1.1.
  4. SRS is not in the CR, so SRS stays at 1.0.
  5. Write B2: login = 1.1, SRS = 1.0, test plan = 1.1.
  6. Compare B1 and B2: login changed and test plan changed. Count = 2 items.

Answer. B2 has login 1.1, SRS 1.0 and test plan 1.1; 2 items changed.

Exam traps

  • Treating version control as the whole of SCM. SCM also covers change control, status accounting and audits.
  • Calling the latest version a baseline. A baseline is an approved frozen set, not whatever was saved last.
  • Letting the CCB skip impact analysis. The board needs affected CIs, effort and risk before it approves or rejects.
  • Confusing status accounting with configuration audit. Status accounting reports history; audit checks that records match the real product.
  • Ignoring build and release records. Without them a release cannot be rebuilt or audited.

6.7 Software quality assurance and technical reviews

Quality is built in while work is done, not inspected in at the end. Software quality assurance (SQA) is the planned set of activities — standards, reviews, audits and measurements — that checks the process, not just final code. Technical reviews are the cheapest: a small group reads a design or module and logs defects before any test case is written. Below: the SQA process, three review types and their roles, and the numbers that show whether a review paid off.

You need verification and validation, QA versus QC (Unit 4, Software Testing Strategies and Techniques), and measurement ideas in 6.2.

The SQA process, and QA versus QC

SQA looks at how software is built; quality control (QC) looks at the product: testing a build, timing a response, running a static analyser. Both are needed. QC asks "does this product meet its specification?" SQA asks "is our process capable of producing such a product?"

The SQA group does five kinds of work.

  • Plan. Write the SQA plan: which work products are reviewed, by whom, against which standard, and when; it sits inside the project plan of <a href="#chapter-6.1">6.1.
  • Standards. Keep a short list the team follows — naming rules, coding style, document templates, review checklists.
  • Reviews and audits. Chair technical reviews; audit whether the documented process was followed on a real project.
  • Records. Log defects, review hours and test results so trends are visible, not just single numbers.
  • Configuration. Ensure every reviewed product is baselined and change-controlled, as in <a href="#chapter-6.6">6.6.

Process standards say how work must be done; ISO 9001 and CMMI maturity levels (1 to 5) are examples, and suppliers claim conformance to win contracts. Product standards say what a deliverable looks like, such as an SRS template or Java style guide.

An SQA group that only writes documents and never reads a real design is decoration. Its authority comes from one power: it can stop a work product moving to the next phase until the review record is closed.

Technical reviews: informal review, walkthrough and inspection

A technical review is a structured reading of a work product by people other than the author — requirements, design, code, test plans or user documents — before testing. Three forms are common.

Informal review. A colleague reads your code or design at the desk. No agenda, no record. Cheap and useful for a 50-line function; useless as evidence.

Walkthrough. The author leads the group through the document step by step; the group asks questions and notes problems. Its purpose is education as much as detection: new members learn the design, and the author often spots errors while explaining. A formal defect list is not mandatory.

Inspection. The most formal form, with defined roles. A moderator schedules and runs it; the product is walked through by the moderator or a nominated reader, not the author, who stays silent except to answer questions of intent. Three to six reviewers prepare alone with a checklist; a recorder writes down every defect. The flow is planning, overview, preparation, inspection meeting, rework, follow-up.

  • Moderator plans the meeting, keeps time, decides pass or rework.
  • Author supplies material, answers intent questions, fixes defects.
  • Reviewer prepares in advance and hunts defects against the checklist, not style preferences.
  • Recorder logs each defect with location, type and severity.

A checklist stops reviewers drifting. Typical lines: is every requirement traceable to a design element? are all inputs validated? are error paths handled? are units named consistently? Ten to twenty items grown from past defects beat a hundred-line list nobody reads.

Each defect goes into a log with id, location (page, section, line), description, type (missing, wrong, extra), severity and status. The log is the review's output and proof.

Metrics for software quality

Reviews produce numbers that say whether to keep reviewing this way.

R = L ÷ H

R is review rate in lines per hour; L is product size in lines; H is total reviewer-hours = number of reviewers × hours each spent. Typical inspection rates are 100–200 lines of code per hour, slower for design. Above that, detection falls sharply.

D = (Dr + Dt) ÷ K

D is defect density in defects per KLOC; Dr is defects found in review; Dt is defects found later in testing; K is size in KLOC. Counting only review defects flatters the process.

E = D<sub>r</sub> ÷ (D<sub>r</sub> + D<sub>t</sub>) × 100%

E is review effectiveness, the share of all defects the review caught. If a review finds 20 and testing later finds 4, E = 20 ÷ 24 × 100% = 83.33%. High E means reviews do work testing would otherwise do, and a review defect costs a fraction of one caught in system test.

Worked example

Question. A 4,000-line module is inspected over 20 reviewer-hours. The inspection finds 20 defects; testing later finds 4 more in the same module. Compute review rate, defect density after all defects, and review effectiveness.

  1. Rate: R = L ÷ H = 4,000 ÷ 20 = 200 lines per hour, at the top of the normal 100–200 band.
  2. K = 4,000 ÷ 1,000 = 4 KLOC.
  3. Total defects = 20 + 4 = 24.
  4. D = 24 ÷ 4 = 6 defects per KLOC.
  5. E = 20 ÷ 24 × 100% = 83.33%.

Answer. Review rate = 200 lines per hour, defect density = 6 defects per KLOC, and review effectiveness = 83.33%.

Exam traps

  • SQA is not testing. Testing is QC on the product; SQA checks process and work products and runs alongside testing.
  • Walkthrough and inspection differ: inspection is formal with roles, preparation and a defect log.
  • Review rate divides lines by reviewer-hours, not calendar hours. Five reviewers for 4 hours is 20 reviewer-hours, so 4,000 lines gives 200 lines per hour, not 1,000.
  • Review effectiveness uses review plus later testing defects. Dividing by review defects alone always gives 100%.
  • Defect density is per KLOC. Reporting 0.006 per line when 6 per KLOC is expected loses marks even with right arithmetic.

6.8 Software maintenance and re-engineering

Software maintenance is the work done on a system after delivery to keep it useful. It exists because a live system faces new platforms, new rules, defects and user needs. Re-engineering is the larger step: when patching an old system costs too much, engineers recover its design, improve its structure and rebuild it. Maintenance and re-engineering are used in payroll, banking, ticketing and government systems that must keep running while they change.

You need: the software life cycle from Unit 1, quality assurance from 6.7, and configuration control from 6.6.

Four kinds of maintenance

Maintenance is not only bug fixing. Textbooks divide it into four types by why the change is made. Maintenance cost is the effort and money spent on changes after delivery.

  • Corrective maintenance fixes defects found after delivery. Example: a UPI payment fails when the amount has two decimal places.
  • Adaptive maintenance changes the system for a new environment or rule. Example: move to a new database, or support a new tax rule.
  • Perfective maintenance improves what the user can see or feel, such as speed, usability or a new report. It changes the product even when no defect exists.
  • Preventive maintenance improves future work. Example: rewrite a confusing module before it causes defects, or add tests to a fragile area.

The same change can look like two types. A new tax rule is adaptive; a faster screen is perfective. The label matters because managers budget and plan each type differently. For long-lived systems, maintenance can be the largest part of total cost. Each change needs analysis, code, test and release. Units are hours or rupees.

Maintenance process and impact analysis

A change request starts the maintenance process. The team records the request, classifies it, and estimates the work. Next comes impact analysis: find every module, database field, interface and test that the change can affect. A small code edit can break a report, a batch job or another team's API.

  1. Record the change request and classify its maintenance type.
  2. Find affected modules, data, interfaces and tests.
  3. Estimate effort, risk and schedule.
  4. Approve or reject the change.
  5. Implement the change on a branch.
  6. Run regression tests and review the result.
  7. Release the change and update records.

Impact analysis uses traceability links from requirements to design to code and tests. Configuration management from 6.6 supplies versions and baselines. After the change, regression testing from Unit 4 checks old behaviour. Release management from 6.9 moves the change to production.

S = (R<sub>old</sub> − R<sub>new</sub>) × H; P = C ÷ S

S is yearly saving in hours; Rold is old change requests per year; Rnew is new count after re-engineering; H is hours per request; P is payback in years; C is re-engineering effort in hours.

The payback P is used later when deciding whether to re-engineer.

Legacy systems and re-engineering

A legacy system is an old system that still runs important work but is hard to change. It may have missing documentation, old languages, tight coupling and no tests. It is risky to discard because business rules live only in its code.

Options are: keep patching, re-engineer, replace, or retire. Re-engineering has three technical steps: reverse engineering (recover design), restructuring (improve structure without changing behaviour) and rebuilding on the new platform. Reverse engineering reads code and recovers modules, data, interfaces and rules. Restructuring, also called refactoring, improves internal structure without changing behaviour. Rebuilding changes the system to a new form: new language, new platform, new database or new architecture.

The figure adds the starting legacy system and the resulting new system, so it shows five boxes but only three re-engineering steps. Re-engineering is not always a big-bang rewrite. Teams often move one module at a time and keep the old system live until the new one is proven. This lowers risk but needs careful interfaces.

Worked example

Question. A payroll system gets 500 change requests a year; each costs 8 hours. Re-engineering costs 3,000 hours and is expected to cut requests to 100 a year. Compute yearly saving and payback in years and months.

  1. Old yearly effort = 500 × 8 = 4,000 hours per year.
  2. New yearly effort = 100 × 8 = 800 hours per year.
  3. Yearly saving S = 4,000 − 800 = 3,200 hours per year. Check: (500 − 100) × 8 = 3,200.
  4. Payback P = re-engineering effort ÷ yearly saving = 3,000 ÷ 3,200 = 0.9375 years.
  5. In months: 0.9375 × 12 = 11.25 months.

Answer. Yearly saving is 3,200 hours per year; payback is 0.9375 years, about 11.25 months.

Exam traps

  • Calling every change corrective maintenance. Maintenance also adapts to new platforms and improves future work.
  • Saying reverse engineering changes behaviour. It recovers design; restructuring changes structure without changing behaviour.
  • Using payback = saving ÷ cost. Correct payback = one-time cost ÷ yearly saving.
  • Treating preventive and perfective maintenance as the same. Preventive reduces future risk; perfective improves current user-visible quality.
  • Writing that maintenance ends at delivery. Maintenance starts after delivery and continues while the system is live.

6.9 Product release management

A release is a controlled, versioned package of changes. It moves tested code from staging to production and carries a plan to undo it if something breaks. Releases exist because users need stable software while developers keep changing it. Mobile apps, UPI payment gateways and IRCTC booking updates ship this way. Only a few universities teach release management as a separate topic; most fold it into configuration management or DevOps. This chapter follows one release cycle.

You need: 6.6 Software configuration management and 6.4 Project scheduling; Unit 5 covers CI/CD pipelines.

Release scope and version numbers

Release scope is the list of changes approved for one release. Anything outside the list waits for the next release. Configuration management supplies the baseline; the release is a labelled snapshot of that baseline.

A version number has three parts: MAJOR.MINOR.PATCH. MAJOR changes when the API breaks old clients. MINOR changes when a feature is added and old clients still work. PATCH changes for a backward-compatible bug fix. A build that only counts commits is not a release.

After feature freeze, no new features enter. The team builds a release candidate (RC), such as 2.5.0-rc1. Testers run the full regression suite on it. If it passes sign-off, the same build becomes the release. If it fails, the team fixes defects and builds rc2; the version number does not jump to 2.6.0 for an RC fix.

The gate, production and rollback

The release gate is a checklist that must pass before production. Items include all tests green, regression suite passed, security scan clean, database migration tested, release notes written, rollback rehearsed, and an on-call engineer available. QA and the product owner sign off.

Staging is a copy of production. Deploy to staging first, run smoke tests, then deploy the identical build to production. A smoke test checks login, one payment and one read path, not every feature.

Monitoring starts immediately: error rate, response time and order failures. If a threshold breaks, rollback. Rollback means redeploying the previous version, not debugging in production. Keep the last release artefact ready. Database changes must be backward compatible so old code still runs.

Release notes tell users what changed, the version and known issues. Feature flags let code ship dark: the feature is in production but switched off until a flag is enabled. A flag can be a kill switch during an incident.

Worked example

Question. Current release is 2.4.1. The next release adds a backward-compatible feature. After that, a backward-compatible bug fix ships. Then a breaking API change ships. Give the three version numbers under semantic versioning.

  1. Current version: MAJOR = 2, MINOR = 4, PATCH = 1.
  2. Backward-compatible feature: increment MINOR and reset PATCH to 0. New version 2.5.0.
  3. Backward-compatible bug fix: increment PATCH. New version 2.5.1.
  4. Breaking API change: increment MAJOR and reset MINOR and PATCH to 0. New version 3.0.0.

Answer. The three versions are 2.5.0, then 2.5.1, then 3.0.0.

Exam traps

  • Calling every build a release. A version number must signal compatibility, not just count commits.
  • Bumping MAJOR for a bug fix. A fix that keeps old clients working is a PATCH.
  • Skipping the release candidate and deploying straight from a developer branch.
  • Planning rollback after failure. Rollback must be rehearsed before production.
  • Confusing release notes with commit logs. Release notes address users, not developers.

Takeaways

  1. People, product, process and project are not four separate jobs; the plan is where all four meet.
  2. A measurement is useful only when it changes a decision, so pick few metrics and define them once.
  3. Decomposition gives an estimate you can defend task by task; an empirical model gives a fast cross-check.
  4. The critical path controls the finish date; adding people to a late critical task can make it later, not earlier.
  5. Risk management is cheap when done early and impossible when done after the risk has hit.
  6. A baseline is a promise: nothing changes in it without a recorded, approved request.
  7. Reviews find defects at the stage where they are cheapest to fix, which is before any test runs.
  8. Maintenance is not one activity but four, and preventive maintenance is what keeps the other three from growing.
  9. Re-engineering is chosen when the yearly cost of patching exceeds the one-time cost of rebuilding, not because the code is old.
  10. A release is a decision, not a copy: version, test in staging, ship with a rollback plan, then record it.

Glossary

Adaptive maintenance
Changing working software so it keeps working after a change in its environment, such as a new operating system or tax rule.
Change control board
The small group that approves or rejects change requests against a baseline.
Corrective maintenance
Fixing defects found in software that is already in use.
Decomposition
Splitting the whole product or job into smaller parts that can each be estimated, assigned and tracked.
Delphi estimation
Asking several experts to estimate separately and anonymously, then repeating until the estimates converge.
Earned value analysis
Comparing planned cost of work scheduled, actual cost spent and planned cost of work completed to show schedule and cost health.
Inspection
A formal review with defined roles, checklists, preparation time, a defect log and exit criteria.
Lines of code (LOC)
A size measure counting delivered source lines; KLOC means thousands of lines.
Moderator
The person who plans and runs a review meeting, keeps it on the product and not on the author.
Perfective maintenance
Adding features or improving performance and maintainability at the user's request.
PERT chart
A network diagram of tasks and their dependencies, used to find the critical path.
Preventive maintenance
Changing software that still works, to stop future defects, for example by restructuring a fragile module or adding checks.
Proactive risk strategy
Identifying risks before they occur and acting on them; the reactive strategy waits for the problem and then fires.
Re-engineering
Rebuilding an existing system, usually starting from reverse engineering, to improve its structure without changing what it does.
Recorder
The review team member who writes down every defect found, but does not suggest fixes during the meeting.
Reverse engineering
Reading existing code and data to recover design and requirements information that was never documented.
Risk projection
Estimating the probability and the impact of each identified risk so risks can be ranked.
Risk refinement
Breaking a broad risk into smaller, checkable conditions and attaching a measurable indicator to each.
Semantic versioning
A numbering scheme MAJOR.MINOR.PATCH where the major number rises for incompatible changes and the patch number for backward-compatible fixes.
Software configuration management (SCM)
The discipline of identifying work products, controlling their versions and approving their changes.
Software quality assurance (SQA)
The set of planned process activities, standards, reviews and audits that give confidence the product will meet its quality goals.
Staging environment
A copy of the production setup where a release is tested before real users see it.
Version control
A tool and practice that records every saved change to a file and lets any earlier version be recovered.
Walkthrough
An informal review where the author leads colleagues through a work product and they ask questions.
