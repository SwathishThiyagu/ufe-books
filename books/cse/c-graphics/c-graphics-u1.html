1.1 History and applications of computer graphics

Computer graphics turns a numerical model into a picture. The model may be a car body, a metro line, a tumour in a scan, or a cricket ball in flight. Software computes what the picture should contain, and hardware puts coloured dots on a screen. The opposite job, starting from a picture already captured and improving or measuring it, is image processing. This chapter fixes that difference, sketches how screens moved from vector drawing to raster grids and GPUs, and surveys the main application areas.

From model to picture

Computer graphics starts with a model: numbers that describe shape, position, colour, camera and light. A car door is a set of surfaces. A metro line is a list of stations and segments. A cricket ball is a moving point with a trail. The renderer converts the model into pixel colours. The display puts those colours on the screen, one frame after another.

  • Modelling builds the numerical description.
  • Rendering computes the colour of each pixel from the model, camera and lights.
  • Display stores the finished frame in a framebuffer and lights the screen.

A pixel is one addressable dot on the screen. Resolution is the number of pixels across and down, such as 1080 × 1920. A framebuffer is the memory that holds one frame. Colour is stored as numbers, often three bytes for red, green and blue (see colour models). A raster display refreshes a grid of pixels in order. A vector display draws only the lines in its display list (see raster versus vector graphics and display devices).

A short history

Sketchpad, built by Ivan Sutherland, is usually named as the first interactive drawing program. A user drew with a light pen and the program stored constraints, so a line stayed attached to a corner. It showed that a person could manipulate a model directly on a screen.

Early screens were vector, also called calligraphic or random scan. The electron beam moved only along the lines to be drawn. Lines were sharp, but filled areas were hard and the number of lines was limited. Raster screens won once memory became cheap. A raster screen sweeps every line, stores colours in a framebuffer, and can fill any shape. Colour depth grew from a few bits to 24 bits per pixel and beyond.

The graphics processing unit, or GPU, arrived to feed the raster screen. It has many small cores that colour vertices and fragments in parallel. Programming moved from fixed functions to shaders. APIs such as OpenGL expose this pipeline (see graphics programming with OpenGL).

Applications, sorted by task

CAD and product design. A bracket, a gearbox or a phone case is modelled as surfaces and solids. The designer rotates it, checks clearance, and renders a catalogue image. Modelling is heavy; rendering may be real time during design or offline for advertising.

GIS and metro maps. Roads, water lines, metro routes and stations are stored as vector data with coordinates. The renderer draws them at any zoom. A metro map is mostly vector graphics: lines, stations and labels, not a photograph.

Medicine. A CT or MRI scanner reconstructs slices from measurements. That reconstruction is image processing. Graphics then renders a 3D volume so a surgeon can plan a cut, rotate the view and see a tumour behind bone. Modelling comes from scan data, and rendering adds lights and cut planes.

Weather radar. Radar measures reflectivity, a number for each direction and range. A colour map turns those numbers into an image, and a sequence of images becomes a loop. This is visualisation: measured data in, picture out. Cleaning noise from the radar image is image processing.

Film and cricket. Film uses modelling, rendering and compositing. Cricket broadcast overlays such as a pitch map or wagon wheel are drawn from tracked ball and shot data, then rendered over the live video.

User interfaces and games. Icons, buttons and windows are small drawings. Games render a 3D scene at 30 to 120 frames per second and display it. The next frame must be ready before the screen asks for it.

Question. A phone screen is 1080 pixels wide and 1920 pixels high. Each pixel uses 3 bytes, one each for red, green and blue.   5. In MB/s = 373,248,000 ÷ 1,000,000 = 373.248 MB/s.

Exam traps

  • Graphics versus image processing: graphics synthesises a picture from a model; image processing starts with a captured picture and analyses or improves it. A CT reconstruction is image processing; a 3D view of the same scan is graphics.
  • Bytes versus bits: 3 bytes per pixel is 24 bits per pixel, not 3 bits. Frame rate multiplies bytes, not bits, unless you convert.
  • Model versus picture: a vector model can be rendered at any resolution; a rendered raster frame is fixed at its pixel grid. Do not say the model has pixels.
  • Sketchpad is usually named as the first interactive drawing program, not the first graphics program and not the first raster display.
  • Applications are not only film and games: CAD, GIS, medicine and weather radar are graphics too. The examiner often asks for three non-entertainment uses.

1.2 Raster graphics versus vector graphics

A picture on a phone can be stored in two ways. A raster image keeps a colour value at every point of a grid; a vector image keeps a list of shapes and lets software make the grid when needed. The choice decides file size, how the picture scales, and what tools can edit it. Photos, screenshots and scanner output are raster. Logos, fonts and engineering drawings are often vector. This chapter explains both models, the terms pixel, resolution, aspect ratio and bit depth, and the memory a full-screen bitmap needs.

You need: Chapter 1.1 for the difference between building an image from a model and processing a picture already captured.

Pixels, resolution and bit depth

A raster image is a rectangular grid. Each grid cell is a pixel, the smallest addressable colour cell. A 5 × 5 bitmap has 25 pixels. In the figure, 1 means ink and 0 means paper, so the 1s draw the letter L.

The resolution of a raster image is its width × height in pixels. A 1920 × 1080 screen has 1920 columns and 1080 rows. Resolution is a count, not a physical size; pixel density, usually pixels per inch (ppi), fixes the printed size. Aspect ratio is width ÷ height. For 1920 × 1080 it is 1920 ÷ 1080 = 1.778, the 16:9 shape.

Bit depth is the number of bits used for one pixel. At b = 1 bit, a pixel has 2 possible values. At b = 8 bits it has 28 = 256 values. At b = 24 bits it has 224 = 16,777,216 values, about 16.7 million colours.

M = W × H × b ÷ 8

M is memory in bytes; W is width in pixels; H is height in pixels; b is bit depth in bits per pixel.

For 1920 × 1080 at 24 bits per pixel, M = 1920 × 1080 × 24 ÷ 8 = 6,220,800 bytes. At 106 (1,000,000) bytes per MB this is 6,220,800 ÷ 1,000,000 = 6.22 MB, before compression or an alpha channel. Some software uses 220 = 1,048,576 bytes per MB, and then the same image shows as 6,220,800 ÷ 1,048,576 ≈ 5.93 MB; the byte count does not change, only the unit.

How a vector image works

A vector image stores objects, not pixels. An object can be a line between (x1, y1) and (x2, y2), a circle with a centre and radius, a polygon, or a path. Each object carries stroke width, fill colour and sometimes a transform. Coordinates use real numbers, so no grid is fixed in the file.

A renderer reads the objects and colours pixels for the current output. At a larger size it recomputes coordinates and fills the new grid. A circle stays a circle because its equation is evaluated again; the edge is not stretched from old pixels. On a 300 dpi printer, a 4 cm diameter can use 472 dots across, and the renderer places the curve at that detail.

Vector file size grows with the number and complexity of objects, not with print size. A detailed road map with many paths can be larger than a simple bitmap. A photograph of the same road is normally raster because a camera samples light at a grid.

Outline fonts store letter shapes as curves; the screen rasterises each glyph. That is why text printed large stays crisp. Common raster formats are PNG, JPEG and GIF. SVG is a common vector format. PDF can hold both.

Do not mix dpi and ppi. dpi is printer dots per inch; ppi is image pixels per inch. Printed ppi = pixel width ÷ printed width in inches. A display is a raster device. Even a vector logo is rasterised for the screen. The vector source is kept because the same file can be sent to a phone or a banner printer.

Worked example

Question. A logo is a circle of radius 2 cm. (a) Find its diameter in inches. (b) How many dots span the diameter on a 300 dpi printer? (c) The same logo is also stored as a 100 × 100 pixel bitmap and printed 4 cm wide. Find the printed resolution in ppi and explain the jagged edge.

  1. Diameter d = 2 × radius = 2 × 2 cm = 4 cm.
  2. Use 1 in = 2.54 cm. d = 4 ÷ 2.54 = 1.574803... in, rounded to 1.5748 in.
  3. Dots across the diameter = d × 300 dpi = 1.5748 × 300 = 472.44, so about 472 dots.
  4. Bitmap printed width = 4 cm = 4 ÷ 2.54 = 1.5748 in.
  5. Printed ppi = 100 pixels ÷ 1.5748 in = 63.499... ppi, rounded to 63.5 ppi.
  6. At 63.5 ppi one pixel is 1 ÷ 63.5 = 0.01575 in ≈ 0.4 mm wide. The curve is drawn as 100 steps across, so the eye sees a jagged edge.

Exam traps

  • A vector file is not always smaller than a raster file. A detailed vector map with thousands of path points can be larger than a small bitmap; photographs are almost always raster.
  • dpi is printer dots per inch; ppi is image pixels per inch. A 300 dpi printer does not turn a 63.5 ppi bitmap into a sharp 300 ppi image.
  • Scaling a bitmap up does not add detail. Interpolation makes it smoother but cannot recover edges that were never sampled.
  • Resolution is a count of pixels, not a physical size. A 1920 × 1080 phone screen and a 1920 × 1080 television have the same pixel count but different ppi.
  • A file extension is not proof of content: PDF can hold vector shapes and raster images; SVG is vector but can embed a raster image.

1.3 Display devices: raster scan and random scan systems

Most screens today are raster displays: a grid of picture cells called pixels, visited row by row many times each second. An older random scan display draws only the lines in its display list, like a pen tracing a drawing. The designs differ in memory, cost and flicker. They explain why a monitor needs a frame buffer and a refresh rate. Only a few universities teach this display hardware in depth. The idea sits under every image on a phone, laptop or TV.

You need: Chapter 1.2 for pixels versus stored shapes.

Raster scan: sweeping every row

In a raster scan system the screen is a grid of picture cells called pixels. The display visits the grid row by row, left to right, then returns to the top. One horizontal pass is a scan line. The return from bottom right to top left is vertical retrace. One complete screen image is a frame. The number of complete redraws each second is the refresh rate, in hertz (Hz); 60 Hz means 60 passes per second.

On a cathode ray tube (CRT), an electron gun at the back sends a beam toward the screen. Deflection coils bend the beam across and down. The beam hits phosphor, which glows briefly. The picture must be redrawn before it fades; too slow a refresh gives flicker. Interlacing splits one frame into two fields: even rows, then odd rows. It halves the signal rate but can show combing on motion.

The bitmap lives in a frame buffer, memory holding a colour for every pixel. A display processor turns geometry from the CPU into pixels. A video controller reads the buffer in row order and sends the signal to the monitor. Frame size is image width in pixels × image height in pixels × bytes per pixel. The figure shows the chain.

Random scan: drawing only the listed lines

A random scan display, also called a vector or calligraphic display, stores a display list of line segments. The electron beam moves to one endpoint, draws that line, then jumps to the next. It draws only listed lines and leaves blank space untouched. The order is arbitrary; random scan does not mean random pixels.

The beam still comes from an electron gun and is bent by deflection coils in a CRT. Each line is a continuous stroke, so wireframe edges look smooth and line art needs little memory. Every listed line is redrawn on every refresh. A long list takes longer, so refresh rate falls and flicker appears. Random scan is poor for filled regions and photographs. Precision deflection hardware can cost more than a simple raster monitor. Typical uses are oscilloscopes and wireframe CAD.

Flat panels and the comparison

An LCD (liquid crystal display) is a flat panel with a grid of cells and a backlight. Each cell controls how much light passes; red, green and blue filters form subpixels. The panel stores pixel values and refreshes them row by row, so it is a raster system without an electron beam. An OLED (organic light-emitting diode) display has pixels that emit their own light. Black pixels switch off, so contrast is high and dark scenes use less power. Both still need a frame buffer and a video controller.

LCD is usually cheaper at large sizes; OLED costs more but gives deeper black. A CRT can flicker at low refresh; LCD backlights can flicker under some dimming methods, and OLED under pulse-width dimming. A fixed pixel grid is sharpest at native resolution and blurs when scaled. High refresh reduces motion blur. Random scan has no fixed grid, so lines stay smooth, but it cannot store a photograph efficiently.

1.4 Color models such as RGB, CMY and HSV

A monitor makes colour by adding light. A printer makes it by subtracting ink. A person choosing a shade thinks in hue. So one colour needs more than one set of numbers. RGB stores the three lights a screen shows. CMY stores the three inks a printer lays down. HSV re-describes the same RGB triple as hue, saturation and value. Every colour picked in a paint program, web page or phone theme is stored in one model and converted to another before it reaches the device.

You need: Chapter 1.2 for a pixel holding a colour value, and Chapter 1.3 for how that value reaches the screen.

RGB: colour by adding light

A screen pixel is three tiny lights: red, green and blue. None on gives black; all three full gives white. Colour is made by adding light, so this is additive mixing. Red plus green gives yellow, red plus blue magenta, green plus blue cyan.

Each channel is 8 bits, value 0 to 255. Three channels make 24 bits per pixel, 2²⁴ = 16,777,216 colours, called 24-bit colour or true colour. Shorthand writes the bytes as hex #RRGGBB, so #FF8000 means R = 255, G = 128, B = 0.

Treat R, G and B as three axes from 0 to 1. Every colour sits inside or on the unit cube. Black is (0, 0, 0) at one corner, white (1, 1, 1) at the opposite. The primary corners are red, green and blue; the other three are yellow, cyan and magenta. Grey lies on the diagonal from black to white, where R = G = B.

  • 0 means the light is off, 255 means full brightness.
  • Equal R, G and B give a grey; 255, 255, 255 is white and 0, 0, 0 is black.
  • Screens, phones and projectors are RGB devices. Each has its own gamut, the set of colours it can show, and colours outside it are approximated.

CMY and CMYK: colour by subtracting ink

Paper looks white because it reflects light. Ink absorbs some wavelengths and reflects the rest. Cyan ink absorbs red, so the eye sees cyan. Magenta absorbs green; yellow absorbs blue. This is subtractive mixing, and the model is CMY.

CMY is the exact inverse of RGB on the 0 to 1 scale:

C = 1 − R, M = 1 − G, Y = 1 − B

R, G and B are red, green and blue on 0 to 1; C, M and Y are cyan, magenta and yellow on the same scale. Multiply by 255 to write bytes.

Printing all three inks on top should give black, but real inks are impure. The mixture is a muddy dark brown, wets the paper and spends three cartridges to darken one spot. Printers add black ink K, giving CMYK. Remove the common part first:

K = min(C, M, Y), C′ = (C − K) ÷ (1 − K)

K is black ink from 0 to 1; C′ is cyan left after black is removed, and M′ and Y′ are computed the same way. If K = 1 the paper is fully black, so set C′ = M′ = Y′ = 0 and skip the division.

HSV: hue, saturation and value

RGB is easy for a machine and awkward for a person. To make orange lighter you must raise R, G and B together and keep their ratios in step. HSV splits the same information into three things people talk about.

  • Hue H is the colour name, an angle in degrees. 0° is red, 60° yellow, 120° green, 180° cyan, 240° blue, 300° magenta, and 360° is red again.
  • Saturation S is purity, 0 to 1. At S = 0 the colour is grey; at S = 1 it is full strength.
  • Value V is brightness, 0 to 1. At V = 0 the colour is black, whatever H and S say.

Put greys on a vertical axis and let hue run around it as an angle. You get a hexcone: black at the bottom point, white at the top of the axis, pure hues around the top rim. Any colour is a point inside. A dark muddy red sits low and near the axis; a bright orange sits high and near the rim.

V = max,   S = Δ ÷ max,   H = 60° × (((G − B) ÷ Δ) mod 6) if max is R

R, G and B are scaled to 0 to 1; max and min are the largest and smallest of the three; Δ = max − min. If max is G use 60° × ((B − R) ÷ Δ + 2), and if max is B use 60° × ((R − G) ÷ Δ + 4). If max = 0 set S = 0; if Δ = 0 set H = 0.

  1. Divide each byte by 255 to get R, G and B on 0 to 1.
  2. Take V as the largest of the three, and Δ as largest minus smallest.
  3. Divide Δ by V to get S; if V is 0, S is 0.
  4. Find the largest channel, apply its hue formula, and keep H in 0° to 360°.

Worked example

Question. A framebuffer pixel has 24-bit RGB value (255, 128, 0). Convert to CMY in 0–1 and bytes, then to HSV with hue in degrees, S and V on 0–1. Name the colour.

  1. Scale: R = 255 ÷ 255 = 1, G = 128 ÷ 255 = 0.50196, B = 0.
  2. C = 1 − R = 0, M = 1 − G = 0.49804, Y = 1 − B = 1.
  3. In bytes: (0, 127, 255).
  4. max = 1 (R), min = 0, Δ = 1. V = 1, S = 1 ÷ 1 = 1.
  5. Largest is R: H = 60° × (((G − B) ÷ Δ) mod 6) = 60° × 0.50196 = 30.12°.
  6. H = 30.1°, S = 1, V = 1 is bright orange, matching #FF8000.

Answer. CMY = (0, 0.498, 1) on 0–1, or (0, 127, 255) as bytes; HSV = (30.1°, 1, 1), a bright orange.

Exam traps

  • CMY is the inverse of RGB, not a reordering: M = 1 − G, never 1 − Y. Forgetting the subtraction shows the model is not understood.
  • Hue is an angle from 0° to 360°, not a 0–255 channel. Do not divide it by 255 without stating the scale.
  • S and V differ. V = 1, S = 0 is white; V = 1, S = 1 is a pure hue. Pale pink has high V and low S.
  • Grey has no hue. When max = min, set H = 0; do not call the division by zero an error in the formula.
  • Equal C, M, Y do not print black, which is why K exists. When K = 1 the division is undefined, so set C′ = M′ = Y′ = 0.

1.5 Graphics programming with OpenGL

OpenGL is a standard application programming interface (API) for drawing 2D and 3D graphics. A program describes shapes once, and the same calls run on many graphics cards. OpenGL behaves as a state machine: settings stay until you change them, and vertices move through the pipeline stages until they become coloured fragments in a framebuffer. Games, CAD tools and phone map apps rely on it. Only a few universities teach this depth.

You need: raster scan displays and RGB colour.

API, context and viewport

OpenGL is a library of function calls for drawing. Your program calls it; the graphics driver turns those calls into commands for the GPU. It does not open a window or read image files; a toolkit such as GLFW or GLUT does that.

A context holds the state for one window and one thread. It stores the current colour, line width, bound buffers, active shader program and viewport. Create the context first; every later call acts on it.

The viewport is the pixel rectangle inside the window where the picture appears. glViewport(x, y, width, height) sets it, in pixels, with the origin at the bottom-left.

OpenGL is a state machine because these settings persist. glColor3f(1, 0, 0) sets red; every vertex drawn after it is red until another colour call. That saves calls but causes bugs: state set for one object silently colours the next.

The pipeline, stage by stage

Vertices enter at the top and leave as pixels. Each stage has one job.

  1. Vertex fetch reads attributes such as position, colour and normal from GPU buffers.
  2. Vertex shader runs once per vertex and outputs the clip-space position.
  3. Primitive assembly groups vertices into points, lines or triangles.
  4. Clipping cuts geometry outside the view volume and adds new vertices at the boundary.
  5. Rasterizer finds the pixels each primitive covers and makes one fragment per covered pixel.
  6. Fragment shader runs per fragment and returns its colour; the depth value is interpolated from the vertices by the rasterizer.
  7. Depth and stencil tests accept or reject a fragment; blending then merges the accepted colour with what is already in the framebuffer.
  8. Framebuffer stores the surviving colour and depth values.

The figure shows six of these eight stages, leaving out clipping and the per-fragment tests for space. The rasterizer is the hinge: before it, geometry in floating-point coordinates; after it, fragments that carry interpolated colour and depth. Several fragments may map to one screen pixel; the depth test keeps the nearest. Fragments rejected at the tests never touch the framebuffer.

Buffers, shaders and swapping

Modern OpenGL (version 3.2 and later, core profile) removed fixed-function drawing. The old style, glBegin(GL_TRIANGLES) … glVertex3f(x, y, z) … glEnd(), sent one vertex per call and is deprecated; old tutorial code no longer runs.

Now vertices sit in a vertex buffer object (VBO) in GPU memory, and a vertex array object (VAO) records the attribute layout and which buffer each attribute comes from. Shaders are small programs in GLSL, compiled and linked at run time into a program object.

Double buffering keeps the picture steady. The front buffer is what the screen shows; you draw into the back buffer, then swap them, typically once per refresh (60 Hz). Without a swap you see an unfinished frame; without clearing the back buffer, old frames smear into new ones.

Exam traps

  • OpenGL does not draw in world coordinates: the vertex shader and viewport transform first. glVertex3f(1,0,0) is not pixel (1,0).
  • State persists. Colour, line width and bound buffers stay until changed, so one object's settings leak into the next.
  • glBegin and glEnd are missing from the core profile; old tutorial programs fail on current drivers.
  • A fragment is not a pixel. Several fragments can cover one pixel, and the depth test keeps only one.
  • Swapping is not drawing. Without a swap you see one buffer only; without clearing the back buffer you see trails.

1.6 Output primitives: points and lines (DDA, Bresenham)

A raster screen can light only whole pixels, so a mathematical line must be converted into a short list of grid points. That conversion is called line rasterisation, or scan conversion. DDA and Bresenham are two classic ways to choose those points. DDA steps along the longer axis with small floating increments and rounds each position. Bresenham makes the same choice using only integers, so it is fast and exact. Both appear inside drawing libraries, CAD tools, map renderers and the line stage of a graphics pipeline.

You need: Chapter 1.2 for pixels and raster grids, plus basic coordinate geometry.

DDA: move in equal steps

DDA stands for digital differential analyser. It treats a line as a path with many equal steps. For a line from (x₀, y₀) to (x₁, y₁), first find Δx = x₁ − x₀ and Δy = y₁ − y₀. The number of steps is N = max(|Δx|, |Δy|). The step sizes are xinc = Δx/N and yinc = Δy/N. Start at (x₀, y₀). At each step, plot the pixel nearest to the current real point: round(x) and round(y). Then add xinc to x and yinc to y.

  1. Compute Δx, Δy and N = max(|Δx|, |Δy|).
  2. Set xinc = Δx/N and yinc = Δy/N.
  3. Set x = x₀, y = y₀ and plot round(x), round(y).
  4. Repeat N times: x = x + xinc, y = y + yinc, then plot round(x), round(y).

For a shallow line, |Δx| ≥ |Δy|, so N = |Δx|. Each step moves x by 1 or −1 and y by the slope m = Δy/Δx. For a steep line, N = |Δy|; y moves by 1 and x moves by 1/m. DDA is simple, but it uses division and floating-point addition. On long lines the small rounding errors can accumulate. The final endpoint may be missed, so plot it explicitly.

Bresenham: one integer decision

Bresenham's algorithm keeps the same idea but replaces the real y by an integer decision. Take a line with 0 ≤ m ≤ 1 and x₀ < x₁. Write Δx = x₁ − x₀ and Δy = y₁ − y₀. At each x, the next pixel is either east at (x+1, y) or diagonal at (x+1, y+1). The algorithm needs only to decide which one is closer to the true line.

p₀ = 2Δy − Δx

Δx and Δy are positive differences in the first octant; p₀ is the first decision value.

If p < 0, choose east and set p = p + 2Δy. If p ≥ 0, choose diagonal and set p = p + 2Δy − 2Δx. The quantity p is a scaled signed distance from the midpoint between the two candidate pixels to the line. Only its sign matters, so no division is needed. All values stay integers.

Pseudocode.

procedure Bresenham(x0, y0, x1, y1)
  dx = x1 - x0
  dy = y1 - y0
  p = 2*dy - dx
  x = x0
  y = y0
  plot(x, y)
  while x < x1
    if p < 0
      x = x + 1
      p = p + 2*dy
    else
      x = x + 1
      y = y + 1
      p = p + 2*dy - 2*dx
    plot(x, y)

For other octants, use symmetry. If |Δy| > |Δx|, swap the roles of x and y, run the same steps, then swap back. If the line goes left or down, run the algorithm with positive differences and reverse the sign of each step when plotting. The decision rule does not change.

All octants, endpoints and aliasing

A line can point in any of eight octants. The first octant has 0 ≤ m ≤ 1 and x increasing. The other octants are mirror images: change signs, or swap x and y. This symmetry lets one small routine handle every direction. The swapped-axis case is the steep-line case: step y by 1 and decide x. When p = 0 the midpoint lies exactly on the line; the rule chooses diagonal, which is one valid tie-break.

Always plot the final endpoint, even when the loop stops early. A missing last pixel makes a line look one pixel short, and joining lines can show gaps. DDA can also drift because of floating-point rounding; Bresenham avoids that drift by keeping p integer. Anti-aliasing is the later technique that softens jagged edges; this chapter only names it. Clipping, which cuts a line to a window, is covered in Unit 2. The same decision idea returns for circles in Chapter 1.7.

1.7 Circle and ellipse generating algorithms

A circle drawn on a pixel grid never matches the true curve exactly. For each column the rasteriser picks the row whose centre lies closest to the curve. The midpoint circle algorithm finds that row with one integer decision variable and no square roots, then copies one octant into the other seven. Ellipses need two decision variables, one for each region.

You need: Chapter 1.6 for the pixel grid, the rasterising idea and integer decision variables.

Eight-way symmetry: compute one octant, copy seven times

A pixel is a small square. The true circle x² + y² = r² passes between pixel centres almost everywhere, so the rasteriser marks the pixel whose centre is nearest the curve. Here r is the radius in pixels.

A circle centred at (xc, yc) has eight-way symmetry: if (x, y) lies on it, so do (y, x), (−x, y), (x, −y) and the rest. Compute one octant and copy it eight times.

Pseudocode.

putpixel(xc + x, yc + y);  putpixel(xc - x, yc + y);
putpixel(xc + x, yc - y);  putpixel(xc - x, yc - y);
putpixel(xc + y, yc + x);  putpixel(xc - y, yc + x);
putpixel(xc + y, yc - x);  putpixel(xc - y, yc - x);

The octant runs from (0, r) to (r/√2, r/√2), where x = y. There the slope has magnitude at most 1, so x rises by 1 every step and y either stays or falls by 1. No column is skipped, so the arc has no gaps. Stop once x is greater than y.

The midpoint circle algorithm

We are at pixel (x, y) and x is about to become x + 1. Two candidates: E = (x + 1, y), one step east, and SE = (x + 1, y − 1), one step south-east. Exactly one is nearer the true circle.

Write f(X, Y) = X² + Y² − r²: zero on the circle, negative inside, positive outside. Test the midpoint M = (x + 1, y − ½). If M is inside, the curve passes above M and E is nearer; otherwise SE is nearer.

Set p_k = f(x_k + 1, y_k − ½). Comparing one p with the next cancels the halves and leaves integers only:

p₀ = 1 − r;  if p_k < 0 then p_{k+1} = p_k + 2x_{k+1} + 1;  else p_{k+1} = p_k + 2x_{k+1} − 2y_{k+1} + 1

p₀ is the first decision value; r is the radius in pixels; p_k is the decision value at step k; x_k, y_k are the current pixel; x_{k+1} = x_k + 1 always, and y_{k+1} = y_k when p_k < 0, else y_{k+1} = y_k − 1.

Only integer addition and doubling appear — no square root, division or floating point. Some books call this Bresenham's circle algorithm; the pixels chosen are the same.

  1. Read r. Set x = 0, y = r, p = 1 − r.
  2. Plot the eight symmetric pixels of (x, y).
  3. If x ≥ y, stop.
  4. Apply the update rule to get the new p and the new (x, y).
  5. Repeat from step 2.

Midpoint ellipse: two regions, two decision variables

An ellipse centred at the origin satisfies x²/a² + y²/b² = 1, where a is the semi-axis along x and b the semi-axis along y, both in pixels. It has four-way symmetry, so one quadrant is enough.

Near the top the ellipse is flat, so x should step; near the right end it is steep, so y should step. The quadrant splits into two regions.

Region 1 starts at (0, b): step x by 1 and choose between (x + 1, y) and (x + 1, y − 1). Region 2 begins where the slope magnitude reaches 1, that is where 2b²x = 2a²y; there step y by 1 and choose between (x, y − 1) and (x + 1, y − 1).

p1₀ = b² − a²b + a²/4;  p2₀ = b²(x₀ + ½)² + a²(y₀ − 1)² − a²b²

p1₀ is the first decision value of region 1; p2₀ is the first decision value of region 2, computed at the last point (x₀, y₀) of region 1; a and b are the semi-axes in pixels.

  • Region 1: if p1_k < 0 take (x + 1, y) and p1_{k+1} = p1_k + 2b²x_{k+1} + b²; else take (x + 1, y − 1) and p1_{k+1} = p1_k + 2b²x_{k+1} − 2a²y_{k+1} + b².
  • Region 2: if p2_k > 0 take (x, y − 1) and p2_{k+1} = p2_k − 2a²y_{k+1} + a²; else take (x + 1, y − 1) and p2_{k+1} = p2_k + 2b²x_{k+1} − 2a²y_{k+1} + a².
  • Stop region 2 when y reaches 0, then mirror the quadrant into the other three.

The products grow fast: for a = b = 1000, a²b² = 10¹², which overflows a 32-bit int. Store decision values in 64-bit integers; the updates still need only addition and doubling.

1.8 Scan conversion and polygon filling algorithms

Scan conversion is the step that turns a polygon described by vertices into coloured pixels on a raster grid. The renderer must answer two questions: which pixels lie inside the shape, and how to fill them quickly. It exists because displays store colour per pixel, not per mathematical edge. The same code fills a menu button, a map region in a phone app, or a cricket-field graphic. The main tools are inside tests, scan-line filling with an edge table and active edge table, and seed-based boundary and flood fill. Horizontal edges and self-intersections cause most errors.

You need: Chapter 1.6 and Chapter 1.7.

Inside tests decide membership

Scan conversion, also called rasterisation, chooses the pixels that represent a shape. A scan line is one horizontal row of pixels at a fixed y. A span is the run of pixels filled between two boundary crossings on that scan line.

An inside test answers whether a point is inside a polygon. The even-odd rule sends a ray from the point to infinity and counts boundary crossings. Odd count means inside; even means outside. The nonzero winding rule uses directed edges. Each crossing adds +1 if the edge goes upward and −1 if it goes downward, or the reverse if you are consistent. The sum is the winding number. A point is inside when the winding number is not zero.

For a simple polygon both rules agree. They differ for self-intersecting polygons and overlapping contours. Even-odd alternates inside and outside; nonzero can keep an overlap filled. The choice is a drawing-model decision, not a rounding detail.

Scan-line fill with edge and active edge tables

Scan-line fill avoids testing every pixel separately. It processes one scan line at a time and fills spans. The intersection of an edge from (x₀, y₀) to (x₁, y₁) with scan line y is:

x = x₀ + ((y − y₀)/(y₁ − y₀)) × (x₁ − x₀)

x is the crossing x-coordinate; y is the current scan line; (x₀, y₀) and (x₁, y₁) are the edge endpoints; the fraction (x₁ − x₀)/(y₁ − y₀) is the inverse slope.

  1. Build an edge table: bucket each non-horizontal edge by its lower y endpoint. Store y_max, the x at that lower endpoint, and the inverse slope.
  2. Keep an active edge table (AET) of edges crossing the current scan line, sorted by x.
  3. At each y, add new edges from the edge table. Remove edges whose y_max is reached.
  4. Sort AET by x. Pair crossings 1–2, 3–4, and so on. Fill between each pair.
  5. Increase y by 1. Update each active x by adding the inverse slope.
  6. Repeat until the AET and edge table are empty.

The AET makes the work proportional to the number of crossings, not the screen area. Coherence helps: neighbouring scan lines usually have similar crossings, so the sorted order changes little.

Boundary fill, flood fill and coherence

Boundary fill starts from a seed pixel inside a region. It colours the seed, then looks at its neighbours. A neighbour is filled only if it is not the boundary colour and not already the fill colour. Flood fill starts from a seed and fills connected pixels that have the same original colour as the seed. It does not need a boundary colour, so it is common in paint tools.

Both algorithms need a seed strictly inside the region, not on the border. Use an explicit stack or queue in real code; deep recursion can overflow. A 4-connected fill checks up, down, left, right. An 8-connected fill also checks diagonals and can leak through a one-pixel diagonal gap in a boundary.

Span coherence fills a whole horizontal run at once, then pushes seeds for the runs above and below. This reduces repeated neighbour checks and is the practical version used in painting software.

Concave and self-intersecting polygons

Concave polygons can produce four, six or more crossings on one scan line. The sorted-pair rule still works: fill between crossing 1 and 2, 3 and 4, and so on. Do not assume one span per scan line. After sorting, use the same pair rule as for a convex polygon; the only change is that more pairs appear.

Self-intersecting polygons expose the difference between the two inside tests. Under even-odd, the overlap may be empty while the outer lobes are filled. Under nonzero, the overlap can be filled when the winding numbers add instead of cancel.

Two implementation details prevent common errors. Skip horizontal edges when computing intersections; they do not cross a scan line cleanly. Handle a vertex shared by two edges with a half-open rule: count the edge whose lower endpoint is the vertex, and skip the edge whose upper endpoint is the vertex. This avoids counting a vertex twice.

Worked example

Question. A polygon has vertices (1,1), (9,1), (7,7) and (3,7). Use the scan-line rule that a pixel at integer centre x is filled when x lies inside the span. Find the span and the number of filled pixels at y=4 and y=6.

  1. At y=4 the active non-horizontal edges are the left edge (1,1) to (3,7) and the right edge (9,1) to (7,7). The bottom and top edges are horizontal, so they are skipped.
  2. Left intersection at y=4: x = 1 + ((4 − 1)/(7 − 1)) × (3 − 1) = 1 + (3/6) × 2 = 2.0.
  3. Right intersection at y=4: x = 9 + ((4 − 1)/(7 − 1)) × (7 − 9) = 9 + (3/6) × (−2) = 8.0.
  4. Span at y=4 is x=2.0 to x=8.0. Integer centres inside are 2, 3, 4, 5, 6, 7, 8, so 7 pixels are filled.
  5. Left intersection at y=6: x = 1 + ((6 − 1)/(7 − 1)) × 2 = 1 + (5/6) × 2 = 2.667, rounded to three decimals.
  6. Right intersection at y=6: x = 9 + ((6 − 1)/(7 − 1)) × (−2) = 9 + (5/6) × (−2) = 7.333, rounded to three decimals.
  7. Span at y=6 is x=2.667 to x=7.333. Integer centres inside are 3, 4, 5, 6, 7, so 5 pixels are filled.

Answer. At y=4 the span is x=2.0 to x=8.0 and 7 pixels are filled; at y=6 the span is x=2.667 to x=7.333 and 5 pixels are filled.

Exam traps

  • Horizontal edges do not cross a scan line cleanly; including them breaks the even-odd parity count.
  • A shared vertex counted twice changes inside/outside; use the half-open rule for vertices.
  • A seed placed on the boundary colour makes boundary fill stop at once; put the seed strictly inside.
  • Rounding intersection x values before pairing can leave a one-pixel gap or fill one pixel too many.
  • An 8-connected flood fill can leak through a diagonal gap in a boundary that a 4-connected fill would respect.

1.9 Digital images: sampling, representation and visual perception

An image on a screen begins as light from a scene. A digital image stores that light only at finitely many grid points, each rounded to a finite set of values. Sampling chooses the points; quantisation chooses the values. The eye then rebuilds edges and contrast from this sparse data, often adding effects that are not in the pixels. This chapter explains how the grid, the number of levels and human vision together decide whether an image looks sharp, smooth or banded. It sits under every raster display, camera and image file.

You need: the raster grid idea from Chapter 1.2 and the RGB/HSV vocabulary from Chapter 1.4.

Sampling, quantisation and reconstruction

A continuous image gives a colour at every point (x, y). A digital image keeps values only on a rectangular grid. Each grid point is a sample; the stored value at that point is a pixel. Sampling is the choice of grid points. Quantisation is the rounding of each sample to a finite set of levels. A grey image with bit depth b stores integer levels from 0 to 2b − 1, where 0 is black and the maximum is white. An 8-bit grey image therefore has 0 to 255, or 256 levels. A colour image stores one level per channel, commonly red, green and blue.

N = W × H

N is the number of pixels; W is the width in pixels; H is the height in pixels.

bytes = N × C × b ÷ 8

N is the pixel count; C is the number of channels (1 for grey, 3 for RGB); b is the bit depth per channel; bytes is the uncompressed storage size.

Spatial resolution is the pixel count W × H. Bit depth controls how many levels each sample can take. The display reconstructs an image by spreading each sample over a small area; a larger pixel looks smoother but hides detail. A fine pattern that falls between samples can reappear as a false coarse pattern. This is aliasing.

ppi means pixels per inch: image pixels mapped to a physical inch. dpi means dots per inch: printer marks per inch. They are related but not the same. A 72 ppi file can be printed small and look sharp. Computer graphics creates samples from a geometric model; image processing changes samples that already exist. Both share the same grid, as Chapter 1.1 separates them.

Changing the grid: nearest and bilinear

Resizing asks for values between stored samples. Interpolation supplies them. Nearest-neighbour takes the closest sample. It is fast and keeps every original value, but edges become blocky when enlarged. Bilinear interpolation takes the four nearest samples and weights them by distance. For position (x, y) inside a cell, let a be the horizontal fraction and b the vertical fraction, both from 0 to 1. The four corners are I00, I10, I01 and I11.

I(x, y) = (1 − a)(1 − b)I<sub>00</sub> + a(1 − b)I<sub>10</sub> + (1 − a)bI<sub>01</sub> + abI<sub>11</sub>

I(x,y) is the interpolated value; a and b are fractions across the cell; I00 is the top-left sample, I10 top-right, I01 bottom-left, I11 bottom-right.

Bilinear gives smooth ramps but softens edges. Averaging is a related operation: shrinking by two replaces each 2 × 2 block with its mean, as the figure shows. This lowers spatial resolution and cannot restore the lost detail.

What the eye reports

The retina has two main receptor types. Rods are numerous, work in dim light and do not signal colour. Cones need more light, give colour and carry fine detail. Cones are concentrated in the fovea, so acuity, the ability to resolve fine detail, is highest at the centre of gaze and falls towards the periphery. A display can show a sharp centre and a soft edge and the eye will accept it if the centre is where attention lies.

Brightness is not judged linearly. The eye responds roughly logarithmically, so equal steps in stored grey value do not look equally spaced. Displays add a nonlinear transfer, called gamma, between code value and light. Without correction, mid-grey looks too dark or too bright.

Lateral inhibition in the retina sharpens edges. At a step from dark to light, the eye sees a dark band just before the step and a light band just after. These are Mach bands. Simultaneous contrast is the related effect where the same grey patch looks lighter on a black background than on a white one. The eye reports contrast and edges, not absolute pixel values. Anti-aliasing uses this: it softens a jagged edge with intermediate samples, and the eye reads a smoother line than the raw grid contains.

Worked example

Question. A passport photograph measures 4 cm by 3 cm. It is scanned at 300 ppi. Use 1 inch = 2.54 cm. Find the pixel width, pixel height, total pixel count, and uncompressed storage for 24-bit colour and 8-bit grey. Give bytes and KiB, with 1 KiB = 1024 bytes. Round each pixel dimension to the nearest whole pixel.

  1. Width in inches = 4 ÷ 2.54 = 1.574803 in.
  2. Width in pixels = 1.574803 × 300 = 472.4409, nearest whole pixel = 472.
  3. Height in inches = 3 ÷ 2.54 = 1.181102 in.
  4. Height in pixels = 1.181102 × 300 = 354.3307, nearest whole pixel = 354.
  5. Total pixels = 472 × 354 = 167,088 pixels.
  6. 24-bit colour uses 3 bytes per pixel because 24 ÷ 8 = 3 bytes. Storage = 167,088 × 3 = 501,264 bytes.
  7. In KiB = 501,264 ÷ 1024 = 489.515625 KiB ≈ 489.5 KiB.
  8. 8-bit grey uses 1 byte per pixel. Storage = 167,088 × 1 = 167,088 bytes.
  9. In KiB = 167,088 ÷ 1024 = 163.171875 KiB ≈ 163.2 KiB.

Answer. Pixel size is 472 × 354, total 167,088 pixels; 24-bit colour needs 501,264 bytes (489.5 KiB) and 8-bit grey needs 167,088 bytes (163.2 KiB).

Exam traps

  • Pixel count is not physical size. A 72 ppi image can be printed small and sharp; the same file printed large looks soft. ppi belongs to the file-to-device mapping, not to the pixel array alone.
  • ppi and dpi are not the same. ppi counts image pixels per inch; dpi counts printer ink dots per inch, and one pixel may need several dots.
  • 24-bit colour is 8 bits per channel, not 24 bits per channel. Storage uses 3 bytes per pixel, not 24 bytes.
  • Equal steps in stored grey value are not equal steps in perceived brightness; the eye is roughly logarithmic and displays add gamma.
  • Aliasing is not blur. Blur removes high frequencies; aliasing folds them to false low frequencies.
