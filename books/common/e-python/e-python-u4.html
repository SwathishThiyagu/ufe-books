4.1 Classes and objects: attributes and methods

A class is a Python recipe for making objects. It groups data, called attributes, with actions, called methods. An object is one value built from that class. Each object keeps its own state while sharing the class's code. This idea exists because real programs handle many similar things: bank accounts, students, buttons, orders. You write the rules once in the class and create as many objects as needed. The example here is a BankAccount class with two objects, Asha and Ravi.

You need: Unit 1 variables and data types; Unit 2 functions and parameters.

Class, object, attribute and method

A class is a template written with the keyword class. An object is a concrete value created by calling the class name, like BankAccount('Asha', 5000). The class says what every bank account has and can do; each object holds actual values.

Data stored on an object are attributes. Actions are methods. In BankAccount, bank_name = 'SBI' is a class attribute: one value shared by all accounts. holder and balance are instance attributes: each object has its own copy. Asha's balance and Ravi's balance are separate numbers.

__init__ is the setup method. Python runs it when a new object is created. It receives the new object as self and stores starting values. Full constructor details are in 4.2. For now, read __init__ as the place that gives each object its first state.

Some syllabi call this the blueprint and instance relationship. The class is the blueprint; an instance is one building made from it. The figure shows one class and two instances.

Methods and self

A method is a function defined inside a class. Its first parameter is self. When you call a1.deposit(1500), Python passes a1 as self and 1500 as amount. The method then changes a1.balance only.

def deposit(self, amount): followed by self.balance = self.balance + amount is correct. def deposit(amount): is wrong for an instance method: there is no self, so the object cannot be reached. Python may raise TypeError or treat amount as a local name. self is not a keyword; it is a normal parameter name, but every Python programmer uses self by convention.

Use dot notation to read or write attributes: a1.balance, a2.holder. To call a method, use parentheses: a1.deposit(1500). Writing a1.deposit without parentheses names the method but does not run it.

__str__ is a special method that returns a readable string for an object. print(a1) uses it. A simple version is return self.holder + ': ' + str(self.balance). This chapter previews it; related special methods appear in 4.6.

Rules for a simple class: use a Capitalised name, add a short docstring, list class attributes, write __init__ to set instance attributes, and give every instance method self first. Keep methods small.

Class attributes, instance attributes and lookup

Python looks up a1.bank_name in two places. First it checks the object's own attributes. If the name is not there, it checks the class. So a1.bank_name finds the shared 'SBI' from BankAccount.

If you assign a1.bank_name = 'HDFC', Python creates an instance attribute on a1. It does not change a2.bank_name and it does not change BankAccount.bank_name. This is a common exam point: assignment through an object creates or updates that object's attribute.

Instance attributes are for state that differs per object: holder, balance, roll number, cart items. Class attributes are for constants or defaults shared by all objects: bank name, minimum balance rule, category label.

Methods also live on the class. Two objects share the same method code, but each call binds self to a different object. That is why a1.deposit(1500) changes Asha's balance and a2 stays at 1200. Access control with private attributes is covered in 4.3.

Exam traps

  • Missing self: def deposit(amount): inside a class cannot reach the object. Every instance method takes self first; otherwise calls fail or variables stay local.
  • Calling BankAccount.deposit(1500) on the class skips the object, so self is missing. Call a1.deposit(1500).
  • Class attribute versus instance attribute: a1.bank_name = 'HDFC' creates an attribute on a1 only. It does not update a2 or the class.
  • Forgetting parentheses: a1.deposit gives a bound method, not a call. Use a1.deposit(1500).
  • Forgetting self. in __init__: balance = balance creates a local name; the object has no balance attribute.

4.2 Constructors, destructors and the self keyword

A class is only a plan; the objects made from it need a starting state. Python gives every class a special method, __init__, that runs automatically the moment an object is created, so attributes such as a balance or a roll number are never missing. A second special method, __del__, runs when the object is about to be removed. Inside both, the parameter self holds the particular object being worked on. These three pieces — creation, the self link, and destruction — explain why an object behaves like a small self-contained machine, and they appear in every Python library you will read.

You need: 4.1 Classes and objects and Unit 2 (functions, arguments and default values).

__init__: the initializer that runs on creation

c1 = Counter(5) does two jobs. Python first builds a blank object of the class — that step is __new__, and you almost never write it. Then Python calls Counter.__init__(c1, 5). The code inside __init__ runs before the assignment finishes, so c1 is never a half-built object with missing attributes.

The usual shape is def __init__(self, n): self.n = n. __init__ is the initializer: a special method whose name carries two underscores on each side (a dunder name), which Python calls for you. Some syllabi call it the constructor. Strictly, Python splits the work — __new__ creates, __init__ initialises — but the split matters only in rare cases such as subclassing immutable types.

Parameters work as in any function. Defaults are common: def __init__(self, name, balance=0) lets you write Account("Ravi") and get a zero balance. A default value is computed once, when the class body runs, not once per object. So a mutable default such as items=[] is shared by every object of that class. Write items=None and set self.items = [] inside the method.

__init__ must return None. A bare return, or no return at all, is fine. Writing return self.n raises TypeError: __init__() should return None, not 'int' at the moment of creation. Otherwise it is an ordinary method: c1.__init__(9) runs it a second time and overwrites attributes.

self: the object's handle inside the method

When you write c1.deposit(100), Python really runs Counter.deposit(c1, 100). The object itself is pushed in as the first argument, so the parameter named self receives it. That is the whole meaning of self: the object on which the method was called.

self is not a keyword. Any name works and the program still runs. Every Python programmer writes self, so you should too.

Leaving it out is the classic mistake. def deposit(amount): inside the class gives TypeError: deposit() takes 1 positional argument but 2 were given when you call c1.deposit(100) — the call passes two values (the object and 100) while the definition accepts one.

Two objects keep two separate states. After c1 = Counter(5) and c2 = Counter(7), the attribute c1.n is 5 and c2.n is 7; inside the method, self is whichever object came in. Use self.attr for the object's own attribute, Counter.count for a shared class variable, and self.method() to call a sibling method. Nothing is hidden, so you always see which object is being changed.

Object lifetime: reference counting, __del__ and del

An object lives from creation until the last reference to it disappears. A reference is a name or container slot pointing at it: c1, a list element, a function argument. CPython counts them; sys.getrefcount(c1) reports the count, one higher than you expect because the argument itself is a reference.

When the count reaches zero, Python calls __del__(self), the destructor, once, and then frees the memory. An object trapped in a reference cycle that nothing outside points to is left to the garbage collector, which also runs __del__ — later, and in an order you did not choose.

del c1 removes the name, not the object. If b = c1 still exists, no destructor runs; the object survives until b goes too. In the example below, del c1 drops the only reference, so __del__ fires at that exact line.

The timing of __del__ is therefore not fixed. It may run at interpreter shutdown, after your last print, possibly in an unexpected order. It is a fine place to decrement a counter or write a log line. It is a poor place to close a file or release a lock: use with or try/finally instead (see Unit 5, Exceptions, Files and Modules).

Exam traps

  • Treating __del__ as guaranteed cleanup. Its timing is not fixed, it may run at interpreter shutdown, and it is unsafe for closing files or releasing locks.
  • Saying __init__ creates the object. __new__ creates it; __init__ only fills in attributes, and it must return None.
  • Confusing del c1 with destruction. del removes one name; the object dies only when its reference count reaches zero.
  • Forgetting self in a method definition, then misreading the error TypeError: method() takes 1 positional argument but 2 were given.
  • Using a mutable default in __init__, such as items=[]. One list is created once and shared by every object of the class.

4.3 Encapsulation and abstraction; accessors and mutators

Encapsulation means an object keeps its data to itself and lets the outside world reach it only through methods. Abstraction means those methods promise what they do, not how. Together they keep a class safe to change: a caller cannot push an impossible value into an object, and the class can rewrite its insides without breaking any caller. Every Python library you use — a UPI payment object, a datetime, a pandas DataFrame — is built this way. This chapter covers the three visibility levels, accessors and mutators, validation, and @property.

You need: classes and objects (4.1) and the self keyword and __init__ (4.2).

Encapsulation: three levels of visibility

Encapsulation bundles an object's data with the methods that use that data, and hides the data from outside code. The object's state is written only by its own methods. Callers ask for what they need through methods. Creating attributes and methods is in 4.1.

Python has no enforced private fields. It has three naming levels that every Python reader interprets the same way.

The double underscore is called name mangling. Inside class Temperature, the line self.__celsius = 25 is rewritten by Python to self._Temperature__celsius = 25 before the code runs. This is a rename, not a lock: reading t._Temperature__celsius from outside works fine. The rename exists so that a subclass reusing the same attribute name does not accidentally overwrite the parent's data.

A single underscore is a promise, a double underscore is a rename, and neither is a security feature. That is why Python encapsulation is called encapsulation by convention.

Accessors and mutators

An accessor, or getter, is a method that returns one attribute. A mutator, or setter, is a method that changes one attribute. Some syllabi call mutators setters; the two words mean the same thing.

Why not let callers write t.celsius = 25 directly? Because plain assignment cannot refuse a bad value. The lowest possible temperature is -273.15 °C, absolute zero. A setter can check that rule before storing.

  1. Store the value in a private attribute: self.__celsius = 0 in __init__.
  2. Write def set_celsius(self, value): and put the check first: if value < -273.15: raise ValueError("below absolute zero").
  3. Only after the check passes, assign: self.__celsius = value.
  4. Write def get_celsius(self): returning self.__celsius.
  5. Callers use only these two methods, never the attribute.

Order matters. If you assign first and check afterwards, the bad value is already inside the object when the exception is raised, and the object is left in an impossible state.

The figure follows two calls on one object. set_celsius(25) passes the check and stores 25. set_celsius(-300) fails the check, raises ValueError, and leaves the stored 25 untouched.

@property: attributes with a guard

Writing get_x and set_x for every attribute is noisy. The @property decorator lets a method be used like an attribute: t.celsius = 25 instead of t.set_celsius(25).

Python program.

class Temperature:
    def __init__(self):
        self.__celsius = 0

    @property
    def celsius(self):
        return self.__celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("below absolute zero")
        self.__celsius = value

t = Temperature()
t.celsius = 25
print(t.celsius)

Output

25

Two rules make properties work. The setter is registered with @celsius.setter, where celsius must match the getter's name exactly. A property with only the getter is read-only: t.celsius = 30 then raises AttributeError.

Abstraction: what, not how

Abstraction shows the caller what a method does and hides how. len(my_list) returns a count; you neither know nor care whether Python reads a stored length or loops. t.set_celsius(25) guarantees a valid temperature; the caller never sees __celsius, the check, or the mangled name.

The public methods of a class form its interface. Everything behind them — private attributes, helper methods, the internal layout — can be rewritten next month and no caller notices. That freedom is the practical payoff of encapsulation plus abstraction.

Abstract base classes push the idea further by forcing subclasses to supply certain methods; see 4.7. Inheritance itself is in 4.4.

4.4 Inheritance: single, multiple and hierarchical; super()

Inheritance lets a new class reuse the attributes and methods of an existing class. The existing class is the base class, parent class or superclass. The new class is the derived class, child class or subclass. The child gets the parent's members and can add its own. This avoids copying the same code for every related type. Python supports single, multiple and hierarchical inheritance. The built-in super() calls the next class in the method resolution order, usually the parent, so constructors can chain. Frameworks, GUI toolkits and banking models use inheritance to share common behaviour.

You need: 4.1 classes and objects, 4.2 constructors and self, and 4.3 encapsulation.

Single and hierarchical inheritance

Write class Student(Person):. The parentheses mean Student is a child of Person. Person is the base class; Student is the derived class. This is single inheritance: one direct parent. The child inherits name and any methods Person defines. It may add roll. The relation is an is-a relation: a Student is a Person. A Person is not necessarily a Student.

Hierarchical inheritance has one base class and many child classes. Person can be the base for Student and Teacher. Student adds roll; Teacher adds subject. Both reuse the name handling in Person. A child can also be a parent for another class, as in class Monitor(Student). That is multilevel inheritance: Person → Student → Monitor. Keep the chain short; deep chains make code hard to follow.

The child does not copy the parent code. Python looks in the child first, then in the parent. If the child defines no __init__, it uses the parent constructor. If the child defines its own __init__, the parent part is not initialised unless the child calls the parent constructor. Overriding is in 4.5.

  • class Child(Base): creates single inheritance.
  • isinstance(obj, Base) is True for a child object; issubclass(Child, Base) is True for the class.

Multiple inheritance and method lookup

Multiple inheritance lists more than one parent: class C(A, B). C gets attributes and methods from A and B. Python searches C, then A, then B, following the method resolution order (MRO). The MRO is the class search order for attributes; full C3 details are in 4.5. If both parents define a method with the same name, the left parent wins unless the child overrides it.

isinstance(obj, C) returns True if obj is an instance of C or any child of C. issubclass(D, C) returns True if D is C or a child of C. These checks are common in validation and framework code.

Multiple inheritance is useful for mixins: small classes that add one behaviour. It can create diamond-shaped graphs. Use it only when the is-a relation is clear for every parent. Multilevel inheritance is a chain, not a fan-in: class C(B), class B(A).

super() and constructor chaining

super() gives access to the next class in the MRO. In single inheritance, super().__init__(name) calls Person.__init__ from Student.__init__. This initialises self.name before Student stores self.roll. Without the call, s.name does not exist and reading it raises AttributeError.

  2. Define Student(Person).__init__(self, name, roll). First call super().__init__(name).
  3. Then store self.roll = roll. Create s = Student('Ravi', 23).
  4. In multiple inheritance, super() calls the next class in the MRO, not every parent. Cooperative classes pass arguments along the chain.

The explicit form hard-codes one parent. super() with no arguments works inside an instance method. It uses the current class and self to find the next class. 4.5 Method overriding and method resolution order

Overriding lets a subclass replace a parent method with its own body. Python does not guess which body to run: it scans a fixed list of classes, the method resolution order (MRO), and takes the first match. In a diamond, where two parents share one grandparent, the MRO and super() make each class run once. You need this to read library code, to combine mix-in classes, and to predict the output of inheritance questions in exams.

You need: 4.4 Inheritance, where a subclass reuses a parent class and super() calls the next class in the MRO.

Overriding: same name, new body

A subclass may define a method with the same name as a parent method. For subclass objects the subclass body runs; the parent method is shadowed, not deleted. This is method overriding.

Account.withdraw(amount) moves money out. SavingsAccount(Account) overrides withdraw to check a minimum balance first, then calls super().withdraw(amount). Account().withdraw still uses the old body.

Matching is by name only; the parameter list does not matter. A subclass method with different parameters still overrides. super() searches the next class in the MRO, not just the direct parent.

Use it when the operation is the same but the rule differs: a savings account and a fixed deposit both expose interest(), at different rates. 4.6 covers how the call site then picks the right body at runtime.

Reading the MRO

Each class stores its lookup order in a tuple named __mro__. For the figure, D.__mro__ is (D, B, C, A, object). Python builds it by C3 linearization. Two rules matter: a class comes before its parents, and the bases keep their left-to-right order.

Lookup scans the tuple left to right, stops at the first class that has the name, and raises AttributeError if no class has it.

B comes before C because D(B, C) lists B first. A comes after both as their shared parent and appears once only. Write D(C, B) instead and the order becomes D, C, B, A, object.

object is the root of every class, so it is last in the chain.

Diamonds and cooperative constructors

D inherits B and C; both inherit A. That shape is the diamond problem: a naive depth-first walk of the parents reaches A twice, so A's state is set twice.

super() prevents it. super() means "the next class after the current one in the object's MRO", not "my parent". Inside B, the class after B is C, so super() reaches C; then C's super() reaches A. A runs once, last.

This is cooperative multiple inheritance. Each __init__ does its own work and calls super().__init__() so the chain continues. Every class in the chain must call it; one class that skips it silently cuts off the rest.

Mix-ins use this: LoggingMixin, RetryMixin, small classes adding one behaviour, combined with a real base class. Pass keyword arguments along the chain so each class takes what it needs.

4.6 Polymorphism, operator overloading and duck typing

Polymorphism lets one operation name work on different types. In Python the object's class chooses the method at runtime, so a single call like shape.area() runs the right code for a circle or a rectangle. Operator overloading applies the same idea to symbols: writing m1 + m2 can call your own __add__ method. Duck typing goes further and asks only for a method name, not a class. These ideas make Python code short and flexible, and they appear in libraries, calculators, money and unit classes, and menu-driven programs.

You need: 4.1 to 4.5, plus lambda, map, filter and reduce from Unit 2.

Polymorphism by overriding

Polymorphism means one operation name can be used with objects of different classes. The caller writes shape.area() and does not test the class. Python looks at the object's class and runs that class's area() method. The method body is chosen when the call runs, not when the code is written. This is dynamic dispatch. 4.5 shows the lookup order.

Built-in functions are already polymorphic. len('abc') is 3, len([1, 2, 3]) is 3, and len({'a': 1}) is 1. Each type supplies its own __len__. A user function total_area(shapes) can loop and call shape.area() on each item; it works for Circle, Rectangle, or any object with an area() method. A subclass that overrides a parent method changes the behaviour for its own objects while the call site stays the same. Some syllabi call this dynamic polymorphism.

Operator overloading with special methods

Operator overloading gives an operator such as + or < a meaning for your class. Python translates the symbol into a call to a special method with two leading and two trailing underscores. Writing m1 + m2 calls m1.__add__(m2) and uses the returned object. The original objects are not changed; __add__ should build and return a new object. __sub__ and __mul__ work the same way. __eq__ defines ==, __lt__ defines <, __str__ defines what print() shows, and __len__ defines len(). Defining __eq__ also lets lists of your objects compare correctly. Python does not change the operator for other classes; only objects of your class use your method.

Duck typing and functions as first-class objects

Duck typing means Python cares about the methods an object has, not its class name. If a function calls obj.quack(), any object with a quack() method works, even if it does not inherit from a Duck class. A missing method is not caught when the function is defined. It fails only when the call runs, with AttributeError. This is why polymorphism in Python does not require a common base class.

Functions are first-class objects. You can store them in a dict, pass them as arguments, and return them. A lambda is a small unnamed function: square = lambda x: x * x. Unit 2 covers map, filter and reduce. Here note that methods are attributes, so bound methods can also be stored. A jump table maps keys to callables: ops = {'+': add, '-': sub}; ops[choice](a, b). This replaces a long if-elif chain and is common in calculators, menu programs and interpreters.

4.7 Abstract classes and interfaces

An abstract base class is a class written as a contract only. It lists method names that every subclass must provide, and Python refuses to create an object of the class itself. It exists because related classes often share a name and a promise but not a body: every shape has an area, yet no generic shape has one formula. Without the contract, a subclass that forgets area() silently returns the parent's version and the program keeps printing wrong numbers. The tool for this in Python is the abc module. Payment gateways, plugin systems and framework code use it to force every new implementation to answer the same calls.

You need: 4.4 Inheritance for subclassing, 4.5 Method overriding and MRO for replacing a parent method, and 4.3 Encapsulation and abstraction for properties.

The problem: a promise with no body

Suppose Shape is a parent class whose area() returns 0. Circle overrides it correctly. A new class Triangle is written in a hurry and the override is forgotten. Triangle().area() returns 0, no error appears, and the grader marks the answer wrong. Nothing in the code warned the programmer that area() had to be overridden.

An abstract base class (ABC) fixes this. It is a class that states a contract: which method names a subclass must supply. Two rules come with it. First, the ABC itself cannot be instantiated, so Shape() raises a TypeError. Second, any subclass that does not implement every required method is itself abstract and also cannot be instantiated. The word abstract means "no complete implementation here", base means "subclasses build on it", and it is still an ordinary class.

The check runs when an object is created. The error appears on the line that calls Shape(), not on the line that defines the class and not at import. That timing is the whole point: a forgotten method turns into a loud failure instead of a quiet wrong answer.

Writing an ABC with abc.ABC

Both tools come from the standard abc module, so no install is needed. ABC is a helper class that switches the check on when you inherit from it. abstractmethod is a decorator: a function that marks the method below it as required.

  1. Write from abc import ABC, abstractmethod.
  2. Declare the parent as class Shape(ABC):. Inheriting from ABC is what enables the check.
  3. Put @abstractmethod immediately above each required method, for example def area(self):.
  4. Give the body pass or raise NotImplementedError. It never runs for the ABC; it runs only if a subclass calls super().area().
  5. Define each subclass normally, using the same method name, and write the real formula.
  6. Create objects of the subclasses only. Calling the ABC raises TypeError.

Two details matter. @abstractmethod without ABC (directly or through another ABC) does nothing, because the check lives in the ABC machinery, not in the decorator. And a subclass of a subclass is checked too: the requirement travels down the chain through the method resolution order.

Abstract properties and interface-style classes

A property, from 4.3, is a method reached like an attribute. To make a property compulsory, stack two decorators with @property on top and @abstractmethod directly below. The order is fixed; swapping it raises an error while the class is being created.

Python program.

Its only job is the contract, so some syllabi call these interfaces. Because Python allows multiple inheritance, one class can accept several contracts at once: class SmartKettle(Heatable, Timer) must implement both heat() and start_timer(), and the MRO decides which parent wins where real code exists. Many programmers name such classes with an -able ending: Printable, Comparable, Serializable.

4.8 Iterators, generators and decorators

An iterator gives you items one at a time. A generator builds an iterator from a function that pauses at yield. A decorator wraps a function or class to add behaviour without editing its body. These three ideas share one theme: control over when and how code runs. Python uses them in for loops, file reading, web routing, logging and testing. They also explain why some objects can be looped over only once.

You need Unit 2 functions, 4.1 instance methods, and 4.7 for @abstractmethod as a decorator.

Iterable versus iterator

An iterable is an object that can produce an iterator. A list, tuple, string and dictionary are iterables. An iterator is the object that actually walks through the items. An iterable has __iter__(), which returns an iterator. An iterator has __next__(), which returns the next item or raises StopIteration when no items remain.

A for loop uses this protocol. First it calls iter(seq) to get an iterator. Then it calls next() on that iterator until StopIteration is raised. The loop hides the exception and stops normally.

Python program.

nums = [10, 20]
it = iter(nums)
print(next(it))
print(next(it))
print(list(it))

Output

10
20
[]
  • A list is iterable but not an iterator: it has no __next__.
  • An iterator is usually its own iterable: its __iter__ returns self.
  • Once an iterator is exhausted, it stays exhausted.

Generators produce iterators

A generator function contains yield. Calling it does not run the body. It returns a generator object, which is an iterator. Each next() runs the body until the next yield, returns that value, and freezes all local variables. The next next() resumes at the same point.

Python program.

g = (i * i for i in range(1, 4))
print(next(g))
print(next(g))

Output

1
4

When the function finishes, the generator raises StopIteration. A generator is lazy: it computes only the item you ask for. A generator expression builds one without a named function, as shown above.

Some syllabi call generators resumable functions.

Decorators wrap callables

A decorator is a higher-order function: it takes a function and returns a new function. The @decorator line is shorthand. Writing @log above def f() means f = log(f).

Python program.

import functools

def logged(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        print("calling", fn.__name__)
        return fn(*args, **kwargs)
    return wrapper

@logged
def add(a, b):
    return a + b

print(add(2, 3))

Output

calling add
5

The wrapper usually accepts *args, **kwargs so it can wrap any function. It should call the original function and return its result. Forgetting return turns every decorated function into one that returns None. functools.wraps copies __name__, __doc__ and other metadata from the original to the wrapper.

Decorating a method works the same way. The wrapper receives self as its first positional argument, so *args passes it through. A class decorator takes a class and returns a class; it can add or replace methods.

Worked example

Question. Write a generator squares(n) that yields i*i for i in 1..n. Set g = squares(4). Print next(g), next(g), list(g), then list(g) again. Give the output.

Python program.

def squares(n):
    for i in range(1, n + 1):
        yield i * i

g = squares(4)
print(next(g))
print(next(g))
print(list(g))
print(list(g))
  1. Calling squares(4) creates the generator g but does not run the body yet.
  2. The first next(g) starts the loop with i = 1 and yields 1, so it prints 1.
  3. The second next(g) resumes with i = 2 and yields 4, so it prints 4.
  4. The first list(g) consumes the remaining values i = 3 and i = 4, giving 9 and 16, so it prints [9, 16].
  5. The generator is now exhausted. The second list(g) gets StopIteration immediately and prints [].

Dry run

second next(g)paused after i = 14
first list(g)paused after i = 2[9, 16]
second list(g)exhausted[]

Output

Answer. The output is 1, then 4, then [9, 16], then [].

Exam traps

  • A generator is one-pass. A second list(g) after exhaustion gives [], not the same values again.
  • next() on an exhausted iterator raises StopIteration; a for loop catches it silently.
  • Calling a generator function does not execute its body. The first next() starts it.
  • A decorator wrapper that forgets return returns None, so the decorated function loses its result.
  • A list is iterable but not an iterator; iter(list) is the iterator.

Takeaways

  1. A class is a blueprint and an object is one built instance; each object keeps its own instance attributes while methods are shared.
  2. __init__ runs automatically after creation to set up state, self is the hidden first argument that binds a call to one object, and __del__ runs when the object is destroyed.
  3. Encapsulation protects state behind accessor and mutator methods; name mangling with __ discourages direct access but does not forbid it.
  4. Inheritance lets a subclass reuse a parent, and super() reaches the next class in the MRO so parent code still runs.
  5. Overriding replaces a parent method, and Python finds the method by walking the class's MRO, which C3 linearization builds left to right.
  6. Polymorphism and duck typing mean Python decides which method body to run from the object itself at runtime, not from a declared type.
  7. An abstract base class fixes the interface and blocks instantiation until subclasses implement every abstract method.
  8. Iterators, generators and decorators let you produce values lazily and wrap behaviour without editing the original function.
