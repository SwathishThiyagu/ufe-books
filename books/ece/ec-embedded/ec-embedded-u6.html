6.1 Embedded C programming

Embedded C is C used to control hardware directly. It keeps C syntax and relies on the standard fixed-width types from the stdint.h header, together with volatile register accesses, bit masks and interrupt functions. A register is a small hardware location; memory-mapped I/O places it at a fixed address. You read or write it through a pointer. This matters in every microcontroller: setting a GPIO pin, clearing a flag, starting an ADC, or handling a timer interrupt. Some syllabi call this C programming for 8051 or ARM. Hosted C on a laptop hides hardware; embedded C exposes it.

You need: Unit 2 for 8051 and ARM registers; Unit 3 for GPIO and interrupts.

Fixed-width types and memory-mapped registers

Standard C types like int can change width between compilers. Embedded C uses <stdint.h>: uint8_t is an unsigned 8-bit integer, int16_t is signed 16-bit, uint32_t is unsigned 32-bit. The width is fixed, so register layouts stay correct.

A hardware register is a memory word wired to a peripheral. Memory-mapped I/O gives it an address. In C, cast that address to a pointer and dereference: volatile uint8_t *p = (volatile uint8_t *)0x40000000;. Here p holds the register address, *p is the byte in the register.

volatile tells the compiler the value may change outside normal code, so every read and write must reach memory. Without volatile, an optimiser can cache a status flag in a register and loop forever. const says your code will not write the object; volatile const uint32_t *status is common for read-only status registers.

Hosted C assumes an operating system, files and printf. Embedded C often has no OS, a small standard library, and a startup file. It talks to addresses, not devices.

Bit masks and special function registers

A bit mask is a number with 1s only where you want action. For bit n, (1 << n) has a single 1 at position n and 0 everywhere else. Bit numbering is usually 0 for least significant bit (LSB).

PORT |= (1 << n); PORT &= ~(1 << n); PORT ^= (1 << n); test = (PORT >> n) & 1;

PORT is the register byte; n is the bit number, 0 for LSB; << shifts left; ~ flips all bits; |, &, ^ are bitwise OR, AND, XOR; test is 0 or 1.

In 8051 C, special function registers (SFRs) are accessed with compiler keywords: sfr P1 = 0x90; sbit LED = P1^3; P1 is the port register at SFR address 0x90; LED names bit 3. In ARM C, use a volatile pointer to the GPIO register. Writing the whole byte, as in P1 |= 0x08, is a read-modify-write: read the byte, change bits, write back. Writing one sbit, as in LED = 1, uses an atomic bit instruction such as SETB or CLR, not a byte read-modify-write. On ARM the pointer write is a read-modify-write of the register.

C program.

#include <stdio.h>
#include <stdint.h>
int main(void) {
    uint8_t port = 0xA5;
    uint8_t set_mask = 0x08;
    uint8_t clear_mask = 0xDF;
    port |= set_mask;
    printf("after set: 0x%02X\n", port);
    port &= clear_mask;
    printf("after clear: 0x%02X\n", port);
    return 0;
}

Output

after set: 0xAD
after clear: 0x8D

Interrupts, startup and compiler extensions

An interrupt service routine (ISR) is a function the hardware calls when an event occurs. In C it is marked with a compiler extension, such as __interrupt or __attribute__((interrupt)). The ISR must be short: set a flag, copy a byte, clear the interrupt source. It must not call printf or block.

Reentrancy means a function can be called again before an earlier call finishes. An ISR and main can share a variable; mark it volatile. If a 16-bit variable is changed in main and read in an ISR on an 8-bit CPU, the read can see half-updated bytes. Disable interrupts around the access or use an atomic type.

Startup code runs before main. It sets the stack pointer, copies initialised data from flash to RAM, clears zeroed data, and calls main. Inline assembly uses __asm volatile ("nop"); for exact instructions. Compiler extensions add SFR names, interrupt vectors and pragmas. The cross-compiler and linker are covered in 6.2.

Worked example

Question. PORT1 holds 0xA5. Write C using a volatile pointer to set bit 3 and then clear bit 5. Give the two mask values and the final byte.

  1. 0xA5 in binary is 1010 0101. Bit 3 is the fourth bit from the right, value 0x08.
  2. Set bit 3: mask = 1 << 3 = 0x08 = 8. Write *p |= 0x08. OR: 1010 0101 | 0000 1000 = 1010 1101 = 0xAD = 173.
  3. Clear bit 5: mask = ~(1 << 5) & 0xFF = 1101 1111 = 0xDF = 223. Write *p &= 0xDF.
  4. AND: 1010 1101 & 1101 1111 = 1000 1101 = 0x8D = 141.

Answer. Set mask is 0x08 (8), clear mask is 0xDF (223), and the final byte is 0x8D (141).

Exam traps

  • Forgetting volatile on a memory-mapped register: the optimiser may keep the old value in a CPU register.
  • *p |= 0x08 & 0x20 is wrong for two masks: bitwise AND binds before OR, so 0x08 & 0x20 is 0. Use *p |= (0x08 | 0x20).
  • Using = instead of |= or &= in a read-modify-write line: = overwrites the whole port.
  • Assuming bit 0 is the leftmost bit in a diagram: standard C numbering starts at the least significant bit.
  • Treating a 16-bit read-modify-write as atomic on an 8-bit CPU: an interrupt between byte accesses can corrupt the value.

6.2 Development tools: IDE, cross-compiler, linker, debugger

A desktop cannot execute firmware for a small microcontroller directly. The desktop is the host; the microcontroller is the target. A cross-toolchain runs on the host, translates C into target machine code, links the pieces at target addresses, and keeps symbol information for the debugger. An IDE wraps this toolchain with an editor, build buttons and a debug view. Every firmware project uses this flow: a sensor node, a motor controller, or an LPC4088 board. Some syllabi call these 'software development tools' or 'ARM development tools'.

You need Chapter 6.1 for C source and Unit 1 for flash, SRAM and memory maps.

Host, target and the cross-compiler

The host is the computer that runs the editor and compiler; the target is the microcontroller that runs the firmware. A native compiler produces code for the host itself. A cross-compiler produces code for another instruction set. A common GCC name is arm-none-eabi-gcc: 'arm' is the target family, 'none' means no operating system, and 'eabi' is the target binary interface. Define the prefix once; every tool in the chain uses it.

The cross-compiler reads C source, checks types, expands macros, and writes assembly for the target. The assembler then converts that assembly into an object file, usually .o. The object file contains machine code, data, and a symbol table. Symbols are names such as main, UART_Init or a global variable, with their section and offset. The object file is relocatable: addresses are not final because the compiler does not know where the linker will place each section. That placement is the linker's job.

  • Compiler: C source to target assembly.
  • Assembler: target assembly to relocatable object.
  • Linker: objects and libraries to an executable.

Linker, linker script and memory regions

The linker joins object files and library code, resolves symbol references, and assigns final addresses. It follows a linker script, a text file with two main parts. MEMORY declares the target memory regions: flash from 0x00000000, size 256 KB; SRAM from 0x20000000, size 64 KB. SECTIONS says which input sections go into which region. Common output sections are .text for code and constants, .data for initialised variables, and .bss for zero-initialised variables.

Flash holds .text and the initial values of .data. RAM holds .data after the startup code copies the values from flash, plus .bss after startup zeroes it. Startup code sets the stack pointer where the architecture requires it, copies .data, zeroes .bss, and jumps to main. It is written in assembly or C with a special section name, and the vector table points to its reset handler. Stack and heap live in RAM and must be reserved in the linker script.

After linking, the map file lists every section and symbol with addresses and sizes. Read it to check that flash and RAM are not overfull. The linker does not run on the target; it only prepares the image.

ELF, HEX, BIN, libraries, make and the IDE

The linker writes an ELF file. ELF is Executable and Linkable Format; it holds code, data, section addresses and symbols. A HEX file, such as Intel HEX, is ASCII records of bytes and addresses for programmers that cannot use ELF. A BIN file is a raw memory image with no address or symbol information. Debuggers prefer ELF because source lines and variable names are present.

Library code is stored in archives, often .a files, and the linker pulls only the object files needed. The C library may be newlib or a smaller embedded variant. A makefile lists source files, flags and output names, and rebuilds only what changed. An IDE supplies an editor, project settings, a build button and a debugger front end; under the button it runs make or an equivalent builder. The IDE is convenience, not a separate compiler.

Programming and debugging the target

An in-system programmer writes the image into the target flash while the chip stays on the board. Many microcontrollers have a ROM bootloader that accepts data over UART, USB or CAN. On an LPC4088-style part, holding a boot pin and using the vendor ISP tool is one example. Other boards use JTAG or SWD pods. The connection needs correct target voltage, ground and clock; a wrong adapter setting gives 'no target' errors.

A debugger connects to the target's debug port, halts the CPU, reads registers and memory, sets breakpoints and single-steps. For source-level debugging it loads the ELF file so addresses map back to C lines and variable names. It can also program flash through the same connection. The debugger is not the same as a simulator; a simulator runs on the host with no board. See Chapter 6.3 for that trade-off.

Worked example

Question. A microcontroller has 256 KB flash starting at 0x00000000 and 64 KB SRAM starting at 0x20000000. A program has .text 40 KB, .data 8 KB and .bss 12 KB. The stack and heap are not included in these figures. Does the program fit? State what goes in flash and in RAM, and the free space in each.

  1. Flash holds .text and the initial values of .data: 40 KB + 8 KB = 48 KB.
  2. Flash free = 256 KB − 48 KB = 208 KB.
  3. RAM holds .data after copying and .bss after zeroing: 8 KB + 12 KB = 20 KB.
  4. RAM free = 64 KB − 20 KB = 44 KB.
  5. Both 48 KB ≤ 256 KB and 20 KB ≤ 64 KB, so it fits. Reserve part of the 44 KB free RAM for stack and heap.

Answer. The image uses 48 KB of flash and 20 KB of RAM, leaving 208 KB flash and 44 KB RAM free; it fits.

Exam traps

  • Putting .data only in RAM and forgetting that its initial values occupy flash; startup code copies them.
  • Counting .bss in flash. .bss has no stored bytes; startup code zeroes RAM.
  • Ignoring stack and heap in the RAM budget, then calling a 64 KB RAM part full at 60 KB of .data plus .bss.
  • Treating a BIN file as if it contained addresses and symbols; ELF and HEX carry address information.
  • Thinking the linker script is executed by the target; it is read by the host linker.

6.3 Simulators, emulators and in-circuit debugging

A simulator, an emulator and an in-circuit debugger all let you watch and control target code, but they trade realism for visibility and cost. A simulator runs a model of the microcontroller (MCU) on your laptop. An emulator uses hardware that replaces or mimics the MCU. An in-circuit debugger (ICD) uses debug logic inside the real chip, reached through JTAG or SWD. You use these tools to find startup faults, inspect registers and memory, set breakpoints and step through code before or during board testing.

You need: Chapter 6.2 for executables and symbols, and Unit 3 for on-chip peripherals.

Simulator: the MCU as a host program

A simulator is a host program that models the microcontroller. It keeps a model of the CPU registers, condition flags, memory map, timers, interrupt controller and some peripherals. It loads the same executable and symbol file produced by the cross-toolchain (Chapter 6.2). No target board is needed. You can set breakpoints, single-step, read and write memory, watch variables, and inject UART bytes or ADC values. This makes it cheap and repeatable for checking startup code, control flow and arithmetic before hardware exists.

The model is not the chip. Peripheral behaviour is approximate, electrical faults do not appear, and instruction timing may ignore flash wait states, DMA contention or caches. A simulator can count instructions, but its clock is not the target clock. Use it for logic bugs, not for final timing or signal-integrity tests.

t<sub>sim</sub> = (N<sub>inst</sub> × CPI) ÷ f<sub>CPU</sub>

tsim is simulated execution time in seconds; Ninst is the number of instructions executed; CPI is the average cycles per instruction; fCPU is the clock frequency in hertz.

Emulator and in-circuit debug

An emulator uses hardware to stand in for the microcontroller. A pod contains a matching MCU or an FPGA that mimics the MCU internals. An emulator pod connects to the target socket (or a dedicated emulation header) so that it takes the place of the MCU. An in-circuit debugger, by contrast, needs only the small JTAG or SWD header on the board. Because the pod runs the code, the target board can keep its real connectors, sensors and power supply. Full in-circuit emulators replaced the CPU with a special bond-out chip; modern designs more often use on-chip debug logic already present in the MCU.

On-chip debug (OCD) reaches that logic through JTAG (Joint Test Action Group, a multi-wire test and debug port) or SWD (Serial Wire Debug, a two-wire ARM debug port). A probe connects the host to the chip. Basic operations are halt, run, single-step one instruction, set breakpoints, set watchpoints, read or write memory and program flash. A breakpoint stops before an instruction executes. A watchpoint stops when code reads or writes a chosen address. Trace records program flow without halting, using on-chip trace hardware; it is the tool for faults that disappear when the CPU stops. In ARM CoreSight chips the block that gives the probe access to the bus and memory is called the debug access port (DAP); the whole on-chip debug logic is usually just called the debug interface. Only a few universities go deeper into trace hardware.

Startup code is a common target. Break at the reset vector, then step through stack-pointer setup, clock configuration, copying initialized data from flash to SRAM, clearing .bss and calling main. A fault here often shows as a dead board with no output. JTAG also supports boundary scan, but that board-level test is Chapter 6.8.

Choosing the tool and its limits

Choose by the question you are asking. A simulator answers 'is the logic right?' An emulator answers 'how does the code behave with this board and bus?' In-circuit debug answers 'what is the real chip doing now?'

Real-time limits matter. Halting the CPU stops instruction execution. On most MCUs the timers, serial ports and watchdog keep running unless the debugger freezes them, so interrupts are serviced late and the watchdog can reset the board. Hardware breakpoints are few because they use comparator registers. Software breakpoints write a special instruction into memory, so they fail in ROM or flash unless the debugger can erase and rewrite the flash. Use trace or a spare pin for timing bugs, and use the simulator for long deterministic runs.

Worked example

Question. A loop runs 1000 times. Each iteration executes 8 instructions. The target runs at 16 MHz with CPI (cycles per instruction) 1.5. Find the time from loop start to a breakpoint placed after the loop.

  1. One iteration executes 8 instructions.
  2. Total instructions = 1000 × 8 = 8000 instructions.
  3. Total cycles = 8000 × 1.5 = 12,000 cycles.
  4. Clock frequency = 16 MHz = 16,000,000 cycles per second.
  5. Time = 12,000 ÷ 16,000,000 = 0.00075 s.
  6. Convert to milliseconds: 0.00075 × 1000 = 0.75 ms.

Answer. The loop takes 12,000 cycles and 0.75 ms to reach the breakpoint after the loop.

Exam traps

  • Simulator time is not target time. A simulator may count instructions correctly but miss flash wait states, DMA contention, cache misses or interrupt latency.
  • A software breakpoint needs writable memory. It fails in ROM or flash unless the debugger supports flash patching; a hardware breakpoint uses a comparator instead.
  • An emulator is hardware that replaces or mimics the MCU; a simulator is software on the host. The words are not interchangeable in an exam answer.
  • Halting the CPU for a breakpoint changes interrupt timing and can trigger the watchdog. Bugs that depend on real-time behaviour may need trace, not a halt.
  • JTAG debug and JTAG boundary scan share a port but do different jobs. Debug controls program execution; boundary scan tests board nets and pins, as in Chapter 6.8.

6.4 Embedded development life cycle (EDLC)

The embedded development life cycle (EDLC) is the ordered set of stages a firmware product passes through from the first customer need to the last field update: requirements, specification, architecture, implementation, integration and test, maintenance. It exists because embedded code is hard to change once it ships — a controller soldered into a washing machine or a braking ECU in a car cannot be patched like a phone app. Each stage hands over a written deliverable that gets reviewed, so mistakes are caught while they are still cheap. Every firmware project, from a UPI payment terminal to a smart meter, runs some version of it.

You need: Chapter 6.1 for the coding stage, Chapter 6.3 for target testing, and Unit 1 for design metrics such as cost, power and time-to-market.

The stages and what each one delivers

Each EDLC stage takes the previous stage's output, adds detail, and produces a deliverable. A review checks that deliverable before the next stage starts. This is the cheap place to catch an error: a wrong requirement fixed during coding costs hours, and the same error found after a product recall costs crores.

  • Requirements: what the system must do, in the customer's words. Deliverable: a numbered requirement list with quantities (response within 10 ms, battery life 6 months).
  • Specification: the same needs written so they can be checked. Deliverable: a functional specification with inputs, outputs and limits.
  • Architecture: block diagram of hardware and software, processor choice, task split. Deliverable: an architecture document.
  • Implementation: writing and unit-testing the modules, as in Chapter 6.1.
  • Integration and test: joining modules on the real board and proving the system meets the specification.
  • Maintenance: fixing defects and adding features after release.

The planned schedule adds the stage durations. This gives the delivery date the customer sees.

T_total = T_req + T_spec + T_arch + T_impl + T_int + T_test

T_req, T_spec, T_arch, T_impl, T_int, T_test are the calendar weeks planned for each stage on the project Gantt chart; T_total is the time from project start to customer delivery, not the total person-effort. The sum holds only when the stages run one after another. When two adjacent stages overlap by n weeks, subtract n weeks once from the sum. Maintenance is left out because T_total is measured up to customer delivery.

Life cycle models and how they differ

Waterfall runs the six stages once, in sequence, with a review gate between each pair. It suits projects where the requirements are stable and the product is safety-critical, such as an infusion pump. Its weakness is that any late change forces the team back up the chain.

The V-model is waterfall bent into a V. The left leg decomposes the design: requirements, then specification, then architecture, then module design. The right leg integrates and tests upward. The rule that defines the V is that each test level is planned as soon as its matching design level is written: module design pairs with unit test, architecture with integration test, specification with system test, and requirements with acceptance test. Test planning therefore starts in week one, not after coding.

Spiral repeats the whole cycle in risk-driven loops. Each loop ends with a prototype and a risk review, so the riskiest part (often new hardware) is proved first. It fits products where both the chip and the software are new, a situation covered in Chapter 6.5.

Agile uses short iterations of one to four weeks, each ending in runnable code, and lets requirements change between iterations. It fits consumer IoT products. It is used less for certified safety software, where every change must be re-verified before release.

Verification, quality assurance and maintenance

Verification asks whether the product is being built right: does each artifact match the specification it was derived from? For a test level in the V-model, that is the design level it is paired with. Reviews, inspections and unit tests are verification. Validation asks whether the right product is being built: does the finished system meet the customer's need? Acceptance tests and field trials are validation. A design can pass every verification step and still fail validation if the requirement itself was wrong.

Integration joins tested modules into the full system. Big-bang integration switches everything on at once and makes a fault hard to locate. Top-down integration starts at the main control flow and replaces missing lower modules with stubs, small dummy routines that accept the call and return a fixed value. Bottom-up integration starts at the leaf modules, the lowest-level drivers and hardware-access routines, and tests them with drivers, small test programs that call the module under test and supply its inputs. Sandwich integration does both ends and meets in the middle. Whichever is chosen, integration is a planned stage with its own schedule, not an afternoon at the end.

  • Configuration management keeps every file under version control and tags each release, so the exact binary shipped to a customer can be rebuilt later.
  • A traceability matrix maps each requirement to a design section, a code module and a test case; a blank cell is a defect in the process.
  • Documentation covers the requirement list, architecture, test plan, test results and release note.
  • Maintenance is corrective (fix defects), adaptive (new hardware or OS), perfective (new features) and preventive (clean-up). It usually costs more than the original development, and its change requests re-enter the life cycle at the requirements stage.

Worked example

Question. A team plans firmware for a smart water meter. Planned durations: requirements 2 weeks, specification and architecture together 3 weeks, coding 6 weeks, integration 3 weeks, system test 2 weeks. (a) Find the total schedule in a pure waterfall. (b) The team starts integration one week before coding ends, so coding and integration overlap by 1 week, with no change to the other stages. Find the new total and the percentage saving.

  1. List the stage durations in order: 2, 3, 6, 3, 2 weeks.
  2. Waterfall total: T_total = 2 + 3 + 6 + 3 + 2.
  3. Add: 2 + 3 = 5; 5 + 6 = 11; 11 + 3 = 14; 14 + 2 = 16. So T_total = 16 weeks.
  4. An overlap of 1 week means that week is counted once instead of twice, so subtract it once: 16 - 1 = 15 weeks.
  5. Percentage saving = 1 week / 16 weeks × 100 = 6.25 percent.

Answer. Waterfall total is 16 weeks; with a 1-week overlap between coding and integration the total becomes 15 weeks, a saving of 6.25 percent.

Exam traps

  • Treating testing as one final phase. Integration and system test are separate planned stages with their own weeks, and in the V-model their planning starts with the matching design stage.

  • Confusing verification with validation. Verification compares an artifact with the specification it was derived from (in the V-model, the design level it is paired with); validation compares the product with the customer's need.
  • Overlapping schedules twice. An overlap of n weeks subtracts n weeks once from the sum, not once for each of the two stages.
  • Assuming a shorter total means a cheaper project. Overlap adds coordination effort even when calendar weeks fall.

6.5 Hardware-software co-design

Hardware-software co-design is the practice of deciding early which parts of an embedded system run as custom hardware and which run as software on a processor. The decision is made together, not one side after the other, because speed, power, chip area, flexibility and time-to-market all pull in different directions. A camera pipeline, a car braking controller and a UPI payment terminal all face the same choice: put a function in a fast fixed circuit or in a programmable CPU. Co-design makes that split visible before detailed design starts.

You need: Chapter 6.4 for the design stages and Unit 1 for processor choices.

The co-design flow

Co-design starts with a specification that states what the system must do, at what rate, with what latency and within what power budget. The specification is executable: a model produces test data that both hardware and software teams can use. Partitioning follows. Each function is placed in custom hardware, in software on a processor, or in a mix. The split is recorded with reasons, because late changes cost money and time. Interface design comes next: data width, handshake signals, memory map, interrupt lines and driver boundary.

  1. Write an executable specification with rate, latency and power targets.
  2. Partition functions into hardware and software; record why for each function.
  3. Define the interface contract: data width, handshake, memory map and interrupts.
  4. Design hardware by synthesis or FPGA mapping; compile software with a cross-toolchain in parallel.
  5. Co-simulate both sides with shared test vectors.
  6. Integrate on the target board and test the complete system.

Partitioning trade-offs

Some syllabi call this HW/SW co-design. Five axes decide the split: speed, power, area, flexibility and time-to-market.

  • Speed: custom hardware can run many operations in parallel; software runs one instruction stream on a CPU.
  • Power: a fixed datapath often uses less energy per operation than fetch-and-execute software, but only if it stays busy.
  • Area: hardware consumes chip area or FPGA logic; software reuses one processor for many functions.
  • Flexibility: software can be patched after shipping; fixed hardware cannot, unless it is reconfigurable.
  • Time-to-market: hardware design, verification and mask costs add months; software changes are cheaper.

A hardware accelerator is a fixed datapath that replaces a hot loop. An application-specific instruction set processor (ASIP) is a CPU with custom instructions for one domain. A reusable block licensed from a vendor or taken from a library is an IP core. Platform-based design starts from a validated processor, bus and memory base, then adds blocks. These choices reduce risk, but they also add interface cost. A fast accelerator still needs a FIFO, DMA or bus transfer, a driver and verification. Formal partitioning algorithms exist, but only a few universities teach them; most teams use profiling plus experience. FPGA details appear in Chapter 6.7, and power techniques in Chapter 6.9.

Interfaces, co-simulation and integration

The interface contract is the boundary between the two designs. It fixes data width, clock domain, transfer rate, handshake protocol, register map and interrupt behaviour. A wrong width or a missing ready signal can make a correct accelerator useless. On-chip buses such as those in Unit 4 carry the data; the driver in software must match the hardware registers exactly.

Co-simulation runs the hardware model and the compiled software model together. Shared test vectors check that both sides agree on timing and data. Integration then follows a fixed order: boot the processor, test the bus, test each register, run a small transfer, then run the full workload. This order finds interface faults before they hide inside application code.

Worked example

Question. A 640×480 camera runs at 30 frames/s. Each pixel needs 20 operations. A 200 MIPS CPU runs the filter in software. Find the operation rate and the CPU load. If an FPGA accelerator does 1 operation per cycle at 100 MHz, how many parallel units are needed? Treat one operation as one instruction for this estimate.

  1. Pixels per frame = 640 × 480 = 307,200 pixels.
  2. Operations per frame = 307,200 × 20 = 6,144,000 operations/frame.
  3. Operation rate = 6,144,000 × 30 = 184,320,000 operations/s.
  4. CPU capacity = 200 MIPS = 200,000,000 operations/s.
  5. CPU load = (184,320,000 ÷ 200,000,000) × 100% = 92.16%.
  6. One FPGA unit capacity = 1 operation/cycle × 100,000,000 cycles/s = 100,000,000 operations/s = 100 Mops/s.
  7. Units needed = ceil(184,320,000 ÷ 100,000,000) = ceil(1.8432) = 2 units.

Answer. The filter needs 184,320,000 operations/s, which is 92.16% CPU load; two 100 Mops/s FPGA units are needed.

  • Choosing hardware only for speed while ignoring interface cost, verification effort and loss of flexibility.
  • Treating MIPS as operations per second without checking the instruction mix; one operation may need several instructions.
  • Forgetting to round up when buying parallel accelerator units; 1.84 units means 2 units.
  • Assuming co-design means hardware first and software later; the split must be decided before both detailed designs.
  • Ignoring data-rate multiplication: resolution and frame rate both raise the operation rate.

6.6 Applications: automotive, smart sensors and driver assistance

Automotive embedded systems control the car with electronic control units (ECUs), sensors and in-vehicle buses. They must meet hard deadlines, stay safe when a part fails, and cost little. Smart sensors do filtering and calibration locally. Driver-assistance systems build a pipeline: sensors, conditioning, fusion, perception, decision and actuator. Adaptive cruise control uses radar to keep a time gap from the car ahead. In dense traffic, cut-ins and mixed vehicle sizes make latency and false alarms visible.

You need: Chapter 6.5 for partitioning, Unit 3 for sensors and ADCs, and Unit 4 for CAN and LIN buses.

ECUs and in-vehicle networks

An electronic control unit (ECU) is a small computer with a microcontroller, power supply, input protection and output drivers. It runs fixed-period control loops: read sensors, compute, drive actuators, repeat. Engine, brakes, steering and body functions use separate ECUs.

CAN (Controller Area Network) is a multi-master broadcast bus. Nodes send frames with identifiers; lower identifiers win arbitration. CAN is used for fast control signals. LIN (Local Interconnect Network) is a cheaper single-wire bus for switches, mirrors and seats; it is not for safety-critical braking. Software must handle bus timeouts, checksums and missing frames. A late brake command is a fault, not a slow response.

In a car, wiring length and weight matter. A shared bus replaces many point-to-point wires. Each ECU needs a communication stack and a watchdog. The control loop period is chosen from the physical process: a current controller may run faster than a temperature controller. The designer checks worst-case execution time plus bus delay against the deadline.

Smart sensors and signal conditioning

A smart sensor contains the sensing element, signal conditioning, an analog-to-digital converter (ADC), a small processor and a bus interface. Signal conditioning amplifies a weak signal, removes noise with a filter, and protects against voltage spikes. The processor converts raw counts to engineering units, for example metres or degrees Celsius.

Calibration removes offset and gain error. A simple model is y = a·x + b. Here x is the raw reading, y is the corrected value, a is the gain and b is the offset. The values of a and b are found during factory test and stored in non-volatile memory. At run time the sensor applies them before sending data. A smart sensor can also flag saturation, open circuit or out-of-range readings. This reduces the load on the ECU and shortens the wire from the sensing point.

Smart sensors send data over I2C, SPI or CAN. The ECU then trusts the sensor's status bits and plausibility checks.

The driver-assistance pipeline

Driver assistance uses several sensors because no single sensor is enough. Radar measures range and relative speed and works in rain and darkness. Camera reads lane marks, signs and objects but needs light. Lidar builds a 3D point cloud with direct distance. Ultrasonic covers short parking distances. Conditioning filters each raw signal and rejects invalid pulses. Fusion combines the estimates with weights or probabilistic filters. Perception turns fused data into objects, lanes and free space. Decision plans speed and path. Actuator commands throttle, brake or steering.

T<sub>gap</sub> = d ÷ v<sub>host</sub>; TTC = d ÷ (v<sub>host</sub> − v<sub>target</sub>); D = v<sub>host</sub> × T<sub>desired</sub>

d is the measured distance in metres; vhost is host speed in m/s; vtarget is the car-ahead speed in m/s; Tdesired is the wanted time gap in seconds; Tgap is the time gap in seconds; TTC is the time to collision in seconds; D is the desired gap in metres.

Time gap Tgap is how long the host takes to reach the present position of the car ahead. Time to collision TTC is how long until the gap closes. Latency matters: sensor exposure, ADC conversion, CAN transfer, fusion, decision and actuator delay all add to reaction time. The gap must include them.

Functional safety and a case study

Functional safety asks what happens when a sensor, ECU or bus fails. Common measures are a watchdog timer, memory and program-flow checks, end-to-end protection on CAN frames, redundant sensors and a safe fallback state. A plausible but wrong reading is dangerous; software compares radar range with camera size and vehicle speed. Standards such as ISO 26262 define safety levels, but the exam idea is simple: detect faults, fail safely, and keep the driver informed.

Case study: adaptive cruise control. Radar tracks a car 40 m ahead. Host speed is 25 m/s and target speed is 20 m/s. The host computes time gap 1.6 s, closing speed 5 m/s, time to collision 8 s. A 2 s desired gap at 25 m/s is 50 m. Since 40 m is less than 50 m, the controller reduces throttle or applies a mild brake. It does not wait for TTC to reach zero. The same loop runs repeatedly; each cycle rechecks the gap.

Worked example

Question. An adaptive cruise control radar measures a car 40 m ahead. The host car travels at 25 m/s and the car ahead at 20 m/s. Find (a) the time gap, (b) the relative speed, (c) the time to collision, and (d) the distance for a desired 2 s gap. State the control action if the desired gap is larger than the measured gap.

  1. Identify the data: measured distance d = 40 m, host speed vhost = 25 m/s, target speed vtarget = 20 m/s, desired time gap Tdesired = 2 s.
  2. Time gap Tgap = d ÷ vhost = 40 m ÷ 25 m/s = 1.6 s.
  3. Relative speed = vhost − vtarget = 25 m/s − 20 m/s = 5 m/s.
  4. Time to collision TTC = d ÷ relative speed = 40 m ÷ 5 m/s = 8 s.
  5. Desired gap D = vhost × Tdesired = 25 m/s × 2 s = 50 m.
  6. Compare: measured gap 40 m is less than desired gap 50 m, so the controller should reduce throttle or apply a mild brake.

Answer. Time gap = 1.6 s, relative speed = 5 m/s, time to collision = 8 s, desired 2 s gap = 50 m; since 40 m < 50 m, the controller should reduce throttle or brake.

  • The desired gap uses host speed and desired time, not the measured gap and not relative speed.
  • Ignoring sensor, CAN and actuator latency makes a gap look safe when the reaction is late.
  • Radar gives range and relative speed; camera gives size, class and lane. Fusion does not remove the need for calibration.
  • LIN is a low-cost body bus, not a replacement for CAN in braking or steering.

6.7 FPGA- and GPU-based embedded computing

An FPGA is a chip whose digital logic you configure after manufacture. A GPU is a chip with thousands of small arithmetic lanes. Both add parallel hardware to an embedded system when a CPU cannot meet time or energy limits alone. You see them in camera pipelines, radar, motor control, medical imaging and edge machine learning. This chapter shows how each platform computes, what limits it, and how a designer splits work among FPGA, GPU and CPU.

You need Chapter 6.5 for partitioning and Unit 1 for processor choices.

FPGA fabric and design flow

An FPGA contains configurable logic blocks. A look-up table (LUT) is a small memory that implements a logic truth table; a k-input LUT stores 2ᵏ bits. A flip-flop (FF) stores one bit on a clock edge. A DSP slice is a hard block with a multiplier, adder and accumulator for multiply-accumulate (MAC) work. Block RAM (BRAM) is on-chip memory made of fixed RAM blocks.

  1. Write the circuit in HDL, usually Verilog or VHDL. HDL describes concurrent hardware, not a sequential program.
  2. Simulate the HDL to check behaviour before hardware exists.
  3. Synthesise: map HDL to LUTs, FFs, DSP slices and BRAM.
  4. Place-and-route: choose physical sites and wire routes.
  5. Run timing analysis; the slowest path sets the maximum clock.
  6. Load the bitstream, the binary file that configures LUTs, routing, BRAM and I/O.

All configured blocks run at once. A soft CPU core is built from LUTs and FFs. A hard CPU core is fixed silicon, such as an ARM core beside the fabric. Use an FPGA when a fixed CPU misses latency or throughput, when you need custom interfaces, or when a data path repeats the same operation on streams. Costs are long compile times, high design effort and fabric power.

GPU execution model

A GPU has many small cores. Single instruction multiple thread (SIMT) means one instruction is issued to many threads. A thread is one sequence of instructions. A warp is a group of threads, often 32, that share one instruction. Branch divergence means threads in a warp take different paths, so the paths run in turn and some lanes idle.

CUDA and OpenCL express a kernel: the function each thread runs. A grid is a set of blocks; a block is a set of threads. An embedded GPU module is a small board with GPU, RAM, power conversion and cooling. It may share memory with the CPU or use local RAM.

arithmetic intensity = operations ÷ bytes moved

operations is the work count; bytes moved is memory traffic between off-chip RAM and the GPU.

Low arithmetic intensity makes the kernel memory-bound: cores wait on data, so adding cores does not cut latency. High clock and many active lanes raise temperature. The module then throttles, so measured time is not peak time. See Chapter 6.9 for power budgets.

Choosing and combining them

Start from the data flow. Put fixed, low-latency, per-pixel work on the FPGA: debayer, threshold, packing, FFT front end. Put dense, regular maths on the GPU: convolution, matrix multiply, image filtering. Keep control, exceptions and I/O on the CPU. The figure shows this order for a camera pipeline.

Avoid extra copies. Interface bandwidth can dominate total time. Measure worst-case latency with real data and thermal throttling. Some syllabi call this embedded computing on FPGAs and embedded GPU design. Test assembled boards with Chapter 6.8 methods.

6.8 Testing: boundary scan and in-circuit testing

A soldered board can fail even when every chip is good: a joint is open, a net is shorted, or a pin is not connected. Boundary scan and in-circuit testing find these faults after assembly. Boundary scan uses a small test port and a chain of cells at each pin, defined by IEEE 1149.1, often called JTAG. In-circuit test uses physical probes on test points. Both are board-level tests, used in factories and repair benches before software is allowed to trust the hardware.

You need: Chapter 6.2 for debug interfaces and Unit 3 for digital I/O.

Board faults after assembly

Testing a bare chip is not enough. After reflow, a board can have an open joint, a solder bridge between two nets, a missing resistor, a bent pin, or a part placed the wrong way. A net is one copper connection that should join a set of pins. A test point is a small pad or via that a probe can touch. These faults are mechanical and chemical, not software bugs. Board-level tests look for them before firmware runs. The two common methods are boundary scan, which uses logic inside chips, and in-circuit test (ICT), which uses physical probes. Both answer a simple question: are the pins joined as the schematic says? This check belongs to the integration and testing stage of the EDLC.

JTAG boundary scan: TAP, registers and instructions

IEEE 1149.1 adds a test access port (TAP) to a chip. The TAP uses five signals. TCK is the test clock. TMS is the test mode select, sampled on TCK to move a small state machine. TDI is test data in and TDO is test data out. TRST is an optional test reset; when absent, a TMS sequence resets the TAP. The TAP controller is the state machine. It loads an instruction into the instruction register (IR). The instruction connects a chosen data register between TDI and TDO. Two data registers matter here. The boundary-scan register (BSR) has one cell for each device pin. A cell can capture the pin value, or drive the pin. Cells of all chips on a board are wired as one long shift register, the scan chain. A test vector is a bit pattern shifted through the chain; the captured bits are shifted out and compared with the expected pattern.

t<sub>shift</sub> = N<sub>bits</sub> ÷ f<sub>TCK</sub>

tshift is the time to shift one vector in seconds; Nbits is the total number of boundary-scan cells in the chain; fTCK is the TCK frequency in hertz.

Common instructions are: BYPASS, which puts one bypass cell in the chain so other devices can be reached quickly; IDCODE, which reads the device identity; SAMPLE, which captures pin values during normal operation without driving them; and EXTEST, which drives pins from the BSR to test board nets. Only a few syllabi teach the full 16-state TAP machine. For exams, know that TCK and TMS move through states such as Capture-DR, Shift-DR and Update-DR.

In-circuit test, flying probe and design for test

In-circuit test (ICT) checks an assembled board with physical probes. A bed-of-nails fixture has spring-loaded pins, one per test point, pressed on the board at once. A flying probe machine moves one or two probes to each test point in turn; it needs no custom fixture but is slower. ICT can measure resistance, capacitance, shorts and opens, and can power a small part of the board. It can also program flash or run a simple functional check.

Design for test (DFT) makes these checks possible: keep test points accessible, avoid hidden nets under parts, add boundary-scan chains, and provide a way to isolate buses. Coverage is the fraction of the intended faults that a test can detect. High coverage does not mean zero escapes. Built-in self-test (BIST) puts pattern generators and checkers inside a chip. It can test memory and logic at speed, but BIST does not see a cracked solder joint; boundary scan and ICT do that.

Worked example

Question. A board has a scan chain of 4 devices. Each device has 32 boundary-scan cells. TCK runs at 1 MHz. Ignore capture and update overhead. (a) How many bits are in one test vector? (b) How long does one vector take to shift in? (c) For 1000 vectors, what is the total shift test time?

  1. Total cells = 4 × 32 = 128 cells. One cell holds one bit in the scan path, so one vector = 128 bits.
  2. TCK = 1 MHz = 1,000,000 clocks per second. One bit per clock, so shift time = 128 ÷ 1,000,000 s = 0.000128 s = 128 µs.
  3. For 1000 vectors, total shift time = 1000 × 128 µs = 128,000 µs = 128 ms.

6.9 Power management and low-power design

Power management keeps an embedded system within its battery and thermal budget. The idea is simple: run fast only when work exists, slow or stop the clock when it does not, and remove power from blocks that are idle. Low-power design matters in every battery device, from a UPI payment terminal to a smart water meter, and in mains-powered boxes that must stay cool. This chapter shows where power goes, the four main levers, and the software habits that turn a correct design into a long-running one.

You need: Chapter 6.5 for hardware-software trade-offs and Unit 3 for timers and interrupts.

Where the power goes

A CMOS chip burns power in three ways. Dynamic power charges and discharges circuit capacitance every clock cycle. Short-circuit power flows briefly when both transistors in a gate conduct during a transition. Leakage power flows even with no switching, through transistors that are never fully off.

Pdyn = C V2 f

Pdyn is dynamic power in watts (W); C is the effective switched capacitance in farads (F), already including the activity factor; V is supply voltage in volts (V); f is clock frequency in hertz (Hz).

Total power is Ptotal = Pdyn + Psc + Pleak. Short-circuit power is proportional to f and rises very steeply with supply voltage, roughly as (V − 2VT)3 f, where VT is the transistor threshold voltage, so it is more sensitive to V than dynamic power. Leakage is Pleak = V Ileak, and Ileak rises strongly with temperature, so a hot board can waste more than a cool one.

Voltage and frequency are linked: a higher clock needs a higher supply to meet timing. When V rises with f, dynamic power grows faster than f. A common model is V ∝ f, giving P ∝ f³. The figure plots the numerical fit P(mW) = [f(MHz)]³ / 1000 for f from 10 MHz to 100 MHz: at 10 MHz, P = 1 mW; at 50 MHz, P = 125 mW; at 100 MHz, P = 1000 mW. This fit assumes V ∝ f and a particular capacitance; it is used only to show the f³ shape.

Four levers

Four mechanisms cover most low-power design. Some syllabi call the whole topic power management.

  1. Dynamic voltage and frequency scaling (DVFS): software picks an operating point (V, f) from a table. Use high f to meet a deadline; drop to low f when the load is light. The governor must know worst-case execution time at each point.
  2. Clock gating: stop the clock to an idle block while keeping its power on. The block holds state and wakes in a few cycles. Good for peripherals and CPU cores between short idle gaps.
  3. Power gating: cut the supply to a block with a power switch. Leakage falls to near zero, but the block loses state and needs a wake-up sequence. The saved energy must exceed the entry and exit cost.
  4. Sleep modes: the chip defines levels such as sleep (CPU clock stopped, peripherals alive), deep sleep (core powered off, SRAM retained) and standby (almost everything off, only the real-time clock and wake logic alive). Deeper modes save more current but lose more state and take longer to wake.

A wake source brings the system out of sleep. Common sources are an external interrupt pin, a timer or RTC alarm, a watchdog, a comparator, or a radio receive event. Choose the deepest mode whose wake sources and retained state still meet the response time. A door sensor can use standby and wake on a pin; a motor controller needs a shallow sleep because it must react in microseconds.

Clock gating and power gating are often automatic in hardware. Software must enable them and must not leave unused peripherals clocked. On many microcontrollers, an unused ADC or UART clock costs more than the CPU's own sleep current.

Low-power software

Software decides how long the hardware stays awake. The first rule is interrupt-driven I/O: polling a flag every millisecond keeps the CPU and bus clock running. An interrupt lets the CPU sleep and wake only when data arrives. See Unit 3 for interrupt latency and priorities.

The second rule is sleep on idle. When the ready queue is empty, the idle task should enter the deepest safe sleep mode, not spin in a loop. In an RTOS, tickless idle removes the periodic scheduler tick so the CPU can stay asleep for long stretches; Unit 5 covers the scheduler side.

The third rule is peripheral clock control. Turn on a peripheral's clock only while it is used, then gate it. Configure every unused pin to a defined level: drive it as an output at a fixed level, or make it an input with the internal pull-up or pull-down enabled (and disable the input buffer where the part allows it). Never leave a pin floating with its pull-up disabled, because a floating input can draw current. Switch off external parts too: an LED, a sensor and a radio can each dominate the budget.

The fourth rule is batching and duty cycling. Measure a sensor once per minute instead of once per second, and send one burst of radio packets instead of many small ones. Compute energy per task: Etask = P × t.

Etask = C V2 N

Etask is dynamic energy per task in joules (J); N is the number of clock cycles the task needs. Lowering f lowers power but the task takes longer; with V fixed, dynamic energy per task stays the same, so the real saving comes from lowering V.

Worked example

Question. A microcontroller runs at 3.3 V. It draws 10 mA in active mode and 10 µA in sleep. It is active 1% of the time and asleep 99% of the time. A 1000 mAh battery powers it. Find the average current and the battery life in hours and days. Ignore wake-up energy and regulator loss.

  1. Convert sleep current to milliamperes: 10 µA = 10 ÷ 1000 mA = 0.01 mA.
  2. Active share of average current: 0.01 × 10 mA = 0.1 mA.
  3. Sleep share of average current: 0.99 × 0.01 mA = 0.0099 mA.
  4. Average current: Iavg = 0.1 mA + 0.0099 mA = 0.1099 mA.
  5. Battery life in hours: t = 1000 mAh ÷ 0.1099 mA = 9099.18 h.
  6. Battery life in days: 9099.18 h ÷ 24 h/day = 379.13 days.

Answer. Average current is 0.1099 mA and the battery lasts about 9099 h, or 379 days.

Exam traps

  • Mixing mA and µA: 10 µA is 0.01 mA, not 0.1 mA. A factor of 10 changes battery life by 10.
  • Using average current alone: wake-up energy, radio start-up and regulator loss can dominate when the duty cycle is very small.
  • Treating leakage as constant: leakage rises with temperature and supply voltage, so a hot device may miss its battery target.
  • Confusing power with energy: halving f halves dynamic power but doubles run time; energy per task is unchanged if V is fixed.
  • Leaving peripherals clocked or pins floating: the CPU may sleep while an LED, pull-up or unused UART still drains current.

Takeaways

  1. Embedded C differs from desktop C mainly in discipline: fixed-width types, volatile on every hardware register, masks instead of bit-fields, and short interrupt routines.
  2. A cross-toolchain is compiler plus assembler plus linker plus libraries, and the linker script and startup code are as important as the C source because they place code in physical memory.
  3. Simulators are cheap and fully visible but slow and unrealistic; emulators and in-circuit debuggers are realistic but costly, so real projects use both at different stages.
  4. The EDLC puts a review gate between stages, which catches interface and timing mistakes before they become expensive board re-spins.
  5. Co-design exists because the hardware-software split fixes cost, power and schedule early; changing it late throws away most of the design.
  6. Automotive and driver-assistance systems add hard real-time deadlines and safety requirements, so their software is tested at unit, integration and system level.
  7. FPGAs give true parallel hardware with deterministic timing, while GPUs give high throughput for regular data-parallel work at the cost of higher power and programming effort.
  8. Boundary scan tests the board, not the program: it finds open and short nets and missing solder without a bed-of-nails fixture.
  9. Low-power design attacks both terms of the power budget: dynamic power through voltage, frequency and clock gating, and static power through power gating and sleep states.

Glossary

Bootloader
A small program that runs at reset, optionally updates the main firmware, and then jumps to the application.
Breakpoint
A debugger setting that halts the processor when execution reaches a chosen address.
Duty cycling
Running a node active for a short time and asleep for the rest, so average power falls in proportion to the active fraction.
Embedded system
A computer built into a larger device to perform a dedicated function under real-time constraints.
Firmware
Software stored in non-volatile memory on the embedded device and rarely or never changed by the user.
FPGA
Field-programmable gate array: a chip whose logic and wiring are configured after manufacture to form custom digital circuits.
GPU
Graphics processing unit: a processor with many simple cores that executes the same instruction over large data arrays.
Hardware-in-the-loop (HIL)
Testing where real controller hardware runs against a simulated plant so that timing and I/O are realistic.
Host
The desktop or laptop machine on which you compile and debug, as opposed to the target that runs the code.
In-circuit testing (ICT)
Board test using probes or boundary-scan cells to check nets and component connections after assembly.
Latency
The delay between an event and the response to it, measured in microseconds or milliseconds.
Leakage power
Power drawn by a transistor that is off, caused by sub-threshold and gate leakage currents; it grows as devices shrink.
Memory-mapped I/O
A scheme where peripheral registers appear at ordinary memory addresses, so normal load and store instructions drive the hardware.
Memory-mapped register mask
A bit pattern used with AND, OR and XOR to change selected bits of a register and leave the rest untouched.
Microcontroller
A single chip containing a processor core, flash, RAM and peripherals such as timers, serial ports and converters.
MISRA C
A published set of coding rules for C that avoids constructs with unreliable or undefined behaviour, used in safety-related embedded software.
Scan chain
Two or more JTAG devices daisy-chained from TDI to TDO so that one port reaches all of them.
SoC
System on chip: a processor, memory and several peripherals integrated on one die.
Special function register (SFR)
A hardware register inside a microcontroller that controls a peripheral or holds its status.
TAP controller
The 16-state machine inside a JTAG device that sequences instructions and data through the scan chain on the clock TCK.
Target
The actual embedded processor or board for which the program is built and on which it runs.
Watchdog timer
A counter that resets the processor if the software fails to clear it within a fixed period, recovering from hangs.
Watchpoint
A debugger setting that halts the processor when a chosen memory location is read or written.
Worst-case execution time (WCET)
The longest time a code path can take on the target, used to prove a real-time deadline is met.
