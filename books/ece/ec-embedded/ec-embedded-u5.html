5.1 OS basics: kernel, kernel space and user space

The kernel is the part of an operating system that is allowed to touch hardware. It decides which task runs next, hands out memory, passes messages between tasks, keeps timers and drives peripherals. Every other program, called a user task, must ask the kernel through a system call. That rule exists because one faulty task must not be able to overwrite another task's memory or reprogram a timer. The CPU enforces the rule with privilege levels. Many RTOSes offer this design. FreeRTOS's ARMv7-M MPU port lets tasks run unprivileged against a privileged kernel; Linux calls the two sides kernel space and user space.

You need: Unit 2 (ARM modes, registers and stack pointers) and Unit 1 (hardware and software architecture of an embedded system).

What the kernel owns

Five jobs belong to the kernel:

  • Scheduling: pick the next task from the ready queue (see 5.4).
  • Memory: hand out RAM blocks and, where the hardware allows, set protection.
  • Inter-task communication: semaphores, mutexes and queues (see 5.6).
  • Time: the tick timer, software timers, delays.
  • Devices: drivers that write peripheral registers (see 5.7).

The words are not fixed. A bare scheduler does only the first job. An executive adds communication, timers and interrupt plumbing. A kernel adds memory protection and drivers. Datasheets use the names loosely, so read the feature list, not the label.

Three layers sit on the board. Firmware is the code fixed to the hardware: bootloader, startup file, board support package. The OS is the kernel plus its libraries; the compiled kernel in flash, with its data, is the kernel image. The application is your tasks. In a build that enables the split, firmware and OS run privileged in kernel space and the application runs unprivileged in user space. Without that option every task runs privileged too, and the protection described in Section 3 is absent.

Privilege and the system call path

ARM Cortex-M cores that implement the nPRIV bit, namely ARMv7-M and ARMv8-M (Cortex-M3, M4, M7, M23, M33), give the CPU two privilege levels. In thread mode, bit 0 (nPRIV) of the CONTROL register decides whether code runs privileged or unprivileged. Cores based on ARMv6-M, such as Cortex-M0 and Cortex-M0+, have no nPRIV bit: thread mode is always privileged, so they cannot run a user/kernel split. Handler mode, entered on any exception, is always privileged. A multitasking RTOS also splits the stacks: the main stack pointer (MSP) serves the kernel and handlers, the process stack pointer (PSP) serves each task (see 5.3).

Unprivileged code cannot mask interrupts, cannot reach the interrupt controller, cannot select or write the main stack pointer, and cannot reach registers the MPU has fenced off. It can run instructions and touch its own memory.

The gateway is one instruction, SVC (supervisor call; other CPUs call it a trap or a software interrupt).

  1. The task puts the call number and arguments in registers and executes SVC.
  2. The CPU saves the context, switches to handler mode on the MSP, and runs the SVC handler from the vector table.
  3. The handler reads the call number, checks the arguments, and calls the kernel function.
  4. Exception return restores the task's context and drops back to unprivileged thread mode.

Kernel space is not a memory chip. It is a set of addresses plus a rule that only privileged code may use them. The same physical SRAM can be mapped into either space, and a user buffer can sit next to kernel data.

Monolithic, microkernel, and why small RTOSes keep the split

A monolithic kernel puts every service in one privileged image: scheduler, drivers, file system, network stack. A call from one service to another is a plain function call, so it is fast. One bug in any service can take down the system.

A microkernel keeps only scheduling, memory and message passing inside; drivers and file systems become user tasks that talk by messages. A driver crash is recoverable, and the kernel is small enough to test. The cost is two privilege changes and a message copy per service call.

Most RTOSes are monolithic but tiny, so that argument rarely bites. The split still matters. An unprivileged task cannot disable interrupts or reprogram the tick timer, so a runaway loop cannot wreck the timing of other tasks. With an MPU (memory protection unit: a few region registers, no address translation) the kernel can also fence off its own RAM. Without an MMU or MPU the rule still holds for instructions, just not for memory. Only a few universities teach the MPU case in detail; it is the same idea at coarser granularity.

Worked example

Question. A user task on an ARM Cortex-M RTOS runs unprivileged in thread mode on the process stack pointer. It must send 10 bytes to a UART. The kernel's serial write accepts at most 4 bytes per system call, and the library splits the 10 bytes into chunks of at most 4 bytes. Trace the path up to the moment the last byte reaches the UART data register, and count the system calls, the privilege changes and the writes to the data register.

  1. The task calls uart_write(buf, 10). This is an ordinary function call inside unprivileged thread mode: 0 privilege changes. Bytes still pending: 10.
  2. The library cannot touch UART registers. It loads the call number and arguments into r0-r3 and executes SVC.
  3. The CPU takes the exception, saves the context, enters handler mode on the MSP, and runs the SVC handler. Privilege change 1: up.
  4. The handler calls the kernel serial write, which checks the buffer, copies min(10, 4) = 4 bytes into the kernel ring buffer, programs the UART control registers and returns.
  5. Exception return restores the task on the PSP, unprivileged again. Privilege change 2: down. Bytes pending: 10 - 4 = 6.
  6. Second system call: 4 more bytes accepted, 2 more privilege changes. Bytes pending: 6 - 4 = 2.
  7. Third system call: 2 bytes accepted, 2 more privilege changes. Bytes pending: 0.
  8. System calls: ceil(10 / 4) = 3. Privilege changes: 2 per call, so 2 x 3 = 6.
  9. The kernel UART driver then writes 1 byte per transmit-empty interrupt: 4 + 4 + 2 = 10 writes to the UART data register.

Exam traps

  • Saying kernel space is "where the kernel is stored in flash". It is an address range plus a privilege rule; the same physical RAM can be mapped into either space.
  • Assuming every embedded OS has an MMU. Many have only an MPU, and some have neither; the privilege split still works for instructions.
  • Confusing SVC (a request from a task, executed in thread mode) with an interrupt (raised by hardware, handled in handler mode). Both enter handler mode, but only SVC is a system call.
  • Thinking a normal function call to a driver changes mode. Only the trap instruction does; the library function on this side of it runs unprivileged.
  • Mixing up kernel, executive and scheduler. A bare scheduler does only the next-task choice; the other two names promise more.

5.2 Tasks, processes and threads

A program sitting in flash does nothing. The unit the scheduler actually runs is the task. An operating system separates the passive program from the running process, and inside a process it separates threads that share memory from the stack each one owns. Real-time operating systems use the word task for this schedulable unit because their world is small: one address space, many small stacks, a fixed priority each. Get the vocabulary and the task control block right, and the rest of the RTOS — scheduling, switching, queues — has something concrete to act on.

You need: 5.1 for the kernel boundary and privilege, and Unit 1 for memory types and sizes.

Program, process, thread, task

A program is a file of instructions in flash. It is passive: nothing happens until something runs it.

A process is a program in execution. It owns an address space — its code, global data, heap and stack — plus open files and a process ID. The kernel keeps processes apart, so one cannot read another's memory (see 5.1).

A thread is a flow of control inside a process. All threads of one process share code, global data, heap and open files. Each thread privately owns a stack, a program counter and registers — its context. Some syllabi call a thread a light-weight process.

A task is the unit the scheduler runs. Real-time operating system (RTOS) literature prefers this word. A small RTOS usually builds one address space and many stacks, so its tasks look like threads: private stack and context, shared data. That is why an RTOS API says 'create a task', not 'create a process'. From here, task means that schedulable unit.

The TCB and four task states

The kernel stores one task control block (TCB) per task. Some syllabi say PCB, for process control block. The TCB is the kernel's record of everything needed to stop the task and later resume it.

  • Stack pointer: top of the task's saved stack.
  • Program counter: address of the next instruction.
  • Saved registers: general registers and status flags.
  • State: ready, running, blocked or terminated.
  • Priority: the scheduler's rank for this task.
  • Stack base and size: limits used for overflow checks.
  • Owner or ID: which task or process this TCB belongs to.

Ready means runnable and waiting for the CPU. Running means currently on the CPU. Blocked means waiting for an event: a timer, a queue, a semaphore. Terminated means finished or killed.

Legal transitions are: dispatch (Ready → Running); preemption or time slice ends (Running → Ready); waits for event (Running → Blocked); event occurs (Blocked → Ready); exit (Running → Terminated). A blocked task never jumps straight to Running; it must rejoin the ready queue. A task waiting on a semaphore sits in Blocked (5.6).

Threads: shared space, private stack

Threads of one process share the address space. A switch between two of them is cheaper than a process switch: the memory map, page tables or MPU regions stay the same. It is not free — registers and stack pointer are still saved and restored (5.3).

Sharing is also a risk. A wild pointer in one thread corrupts the heap for every thread in that process. Process isolation gives no protection inside a process.

User-level threads are scheduled by a library; the kernel sees one process. Switching is fast, but one blocking system call blocks all threads, and two threads cannot use two cores. Kernel-level threads are scheduled by the kernel: one blocking call blocks only that thread, and they run in parallel on several cores, at a higher switch cost.

Stack sizing: add the deepest call chain, the largest local array, the saved context, and the worst nested interrupt frames. Too small overwrites the neighbouring task's memory. Too large wastes RAM (5.8).

Static creation at compile time needs no heap and is deterministic. Dynamic creation at run time needs heap and a checked return value. A function is reentrant if two tasks can call it at once safely: only locals and parameters, no mutable globals or statics, no non-reentrant library calls.

Task models: periodic, sporadic, aperiodic

Real-time work describes tasks by when they are released and how long they need.

  • Periodic: released every period T, with worst-case execution time C and relative deadline D. Typical constraint C ≤ D ≤ T.
  • Sporadic: irregular releases, but a known minimum gap between them; the deadline is still hard.
  • Aperiodic: irregular, no minimum gap; often soft.

Release time r is the instant a task becomes ready. Its absolute deadline is r + D. The numbers r, C, D and T let a scheduler decide order; that decision is 5.4.

U = Σ (Cᵢ / Tᵢ)

Cᵢ is the worst-case execution time of task i in milliseconds; Tᵢ is its period in milliseconds; U is a pure fraction. One CPU with U > 1 cannot meet every deadline.

Worked example

Question. An RTOS keeps a 96-byte TCB per task and gives each task a 512-byte stack. Six tasks must run on a chip with 4 KB of RAM. (a) How many bytes do the tasks need in total? (b) What fraction of that is TCB overhead? (c) How much RAM is left for the kernel and heap?

  1. Memory per task = TCB + stack = 96 B + 512 B = 608 B.
  2. Total task memory = 6 × 608 B = 3648 B.
  3. Total RAM = 4 KB = 4 × 1024 B = 4096 B.
  4. TCB portion = 6 × 96 B = 576 B. Fraction = 576 ÷ 3648 = 0.1579 = 15.79%.
  5. Same result per task: 96 ÷ 608 = 0.1579.
  6. RAM left = 4096 B − 3648 B = 448 B.

Answer. The six tasks need 3648 bytes, TCBs are 15.79% of task memory, and 448 bytes remain for kernel and heap.

Exam traps

  • Writing 'each thread has its own address space'. Threads share the process address space; only the stack and registers are private.
  • Calling a thread switch free. It is cheaper than a process switch because the address space does not change, but registers are still saved and restored.
  • Mixing up program and process. A program is a passive file; a process is that program in execution, with an address space and state.
  • Taking TCB overhead as a fraction of total RAM instead of task memory. Here it is 576 ÷ 3648, not 576 ÷ 4096.

5.3 Multitasking, multiprocessing and context switching

A CPU core executes one instruction stream at a time, yet an embedded product must answer a key press, refresh a display and read a sensor without missing deadlines. Multitasking creates that illusion on one core by switching rapidly between tasks. Each switch saves the running task's context and restores another's. Multiprocessing gets true parallelism by adding cores. The switch does no useful work, and real-time designers count its cost in microseconds, because that cost is subtracted from every deadline.

You need: task states and the contents of a TCB from 5.2, and the register file, pipeline and cache from Unit 2, Processor Architectures.

Concurrency is not parallelism

Two tasks are concurrent when their executions overlap in time; they are parallel when their instructions run on hardware at the same instant. One core gives concurrency only. The kernel runs task A for a slice, stops it, runs task B, and repeats. At a slice of a few milliseconds a human sees A and B as simultaneous; the CPU sees them strictly one after another. Some syllabi call this time slicing.

Deadlines still get met because the interleaving is bounded. If every slice is at most q and every switch costs at most s, a ready task never waits longer than the slices of the tasks ahead of it plus one switch per slice. The scheduler computes a worst-case response time and compares it with the deadline.

Two policies decide when a switch happens. Preemptive multitasking lets the kernel take the CPU away at a timer tick, or as soon as a higher-priority task becomes ready. Cooperative multitasking lets a task keep the CPU until it calls a yield function; switching is cheap because no timer is needed, but one task that never yields stalls everything. Hard real-time kernels are almost always preemptive.

The context switch, step by step

The context is everything the CPU needs to resume a task exactly where it stopped: the program counter (PC, the address of the next instruction), the stack pointer (SP), the general-purpose registers, the status register, and any floating-point registers the task uses. With an MMU, the page-table base register is part of it. The kernel keeps this in the task control block (TCB). Some syllabi call the whole operation a dispatch or a task switch.

  1. A timer interrupt or a system call transfers control to the kernel.
  2. The hardware, or the kernel's entry code on cores that do not do it in hardware, pushes the PC and status register on the current task's stack; the kernel then saves the remaining registers.
  3. It writes the current SP into that task's TCB. The context is now safe: stack plus SP.
  4. The scheduler picks the next task (the rule is in 5.4), and the kernel loads its TCB and sets SP from it.
  5. It pops the registers from the new stack, then the status register and the PC.
  6. The return-from-interrupt instruction jumps to the restored PC, and the new task continues.

The switch latency is the time from the last useful instruction of the old task to the first useful instruction of the new one. A preemptive kernel adds it to interrupt latency on the path to a woken task.

t_switch = t_reg + t_sched + t_cache + t_tlb

t_reg is the register and stack save/restore time; t_sched is the scheduler's decision; t_cache is the stall while the new task's code and data come from memory; t_tlb is the flush and refill of the translation lookaside buffer, present only when tasks have separate address spaces. On a small microcontroller t_switch is a few microseconds; on a cached application processor the last two terms dominate and it grows by an order of magnitude.

Interrupts inside an RTOS

Peripheral interrupts arrive asynchronously. The hardware saves the minimum, the ISR saves the registers it uses, does a short job, and returns. In an RTOS the ISR usually does not do the real work: it clears the peripheral flag, moves data to a buffer, and signals a task, for example by giving a semaphore (see 5.6).

  • Short ISRs matter because an ISR may run with interrupts masked and blocks every lower-priority interrupt; a long ISR adds latency to the whole system.
  • Deferred work runs in a task that the ISR unblocks, so heavy processing competes for the CPU under the scheduler like any other work.
  • Nested interrupts let a high-priority interrupt preempt a low-priority ISR, to a bounded depth.
  • Many kernels switch tasks on return from interrupt, so a woken high-priority task runs before the interrupted low-priority task resumes.

Multiprocessing: AMP and SMP

In asymmetric multiprocessing (AMP) each core runs its own OS image or bare-metal program and owns a fixed job: core 0 runs the control loop, core 1 runs the communication stack. There is no shared ready queue. In symmetric multiprocessing (SMP) one OS manages all cores with a shared ready queue, and any task may run on any core; the scheduler balances load.

AMP is simpler and more predictable, because timing analysis is done per core; it is common in a system-on-chip that pairs an application core running Linux with a small core handling real-time I/O. SMP gives throughput, but the kernel must lock its own data structures, and keeping caches coherent costs cycles. Adding cores does not by itself meet a deadline: a task that must respond in 50 µs still needs a free core and an interrupt path that is not blocked.

Worked example

Question. A single-core CPU runs two tasks under preemptive round robin with a time quantum of 4 ms. Task A needs 7 ms of CPU time and task B needs 6 ms. Both are ready at time 0 and the scheduler alternates A, B, A, B. Every context switch costs 1 ms and occurs at each slice boundary where work remains. Draw the schedule until both tasks finish, and find (i) the finishing time, (ii) the CPU time lost to switching, (iii) the switching overhead as a percentage.

  1. t = 0 ms: A runs min(4, 7) = 4 ms, 3 ms left; clock 4 ms.
  2. Switch 1 ms → t = 5 ms.
  3. t = 5 ms: B runs min(4, 6) = 4 ms, 2 ms left; clock 9 ms.
  4. Switch 1 ms → t = 10 ms.
  5. t = 10 ms: A runs min(4, 3) = 3 ms and finishes (7 ms used); clock 13 ms. B still needs 2 ms.
  6. Switch 1 ms → t = 14 ms.
  7. t = 14 ms: B runs min(4, 2) = 2 ms and finishes (6 ms used); clock 16 ms. No switch after the last task.
  8. Useful CPU time = 7 + 6 = 13 ms; elapsed = 16 ms.
  9. Switching time = 16 - 13 = 3 ms = 3 switches x 1 ms.
  10. Overhead = 3 / 16 x 100 = 18.75 %.

Answer. The last task finishes at 16 ms; useful CPU time is 13 ms, 3 ms is lost to three context switches, and the overhead is 18.75 %.

Exam traps

  • Multitasking does not make one core faster. Useful work stays 13 ms; interleaving adds 3 ms of switching.
  • Concurrency is not parallelism: interleaved tasks on one core are concurrent; parallelism needs two cores at the same instant.
  • Do not add a switch after the final task; that gives 4 switches, 4 ms lost and 17 ms, all wrong.
  • Switch latency and interrupt latency are different measurements; a switch that wakes a task adds to the interrupt path.
  • A cooperative task that runs long is not a scheduling bug; a preemptive kernel would have interrupted it at the tick.

5.4 Task scheduling: round robin, priority, rate monotonic, EDF

Scheduling is the rule that picks the next task from the ready queue. The rule matters because a wrong pick can make a hard deadline slip even when the CPU has spare time. A real-time operating system exposes the rule as a policy: FIFO, round robin, fixed priority, rate monotonic or earliest deadline first. The same tasks can pass or fail under different policies. This chapter compares the policies and gives the numbers an examiner expects: utilisation, response time and the rate-monotonic bound. It is used in motor control, airbag controllers, robot arms and any system where late is wrong.

You need: 5.2 for period, execution time and deadline, and 5.3 for context switching and preemption.

Metrics and simple policies

Every scheduler needs a rule and a way to judge it. CPU utilisation is the fraction of time spent doing useful work, U = busy time / total time. Throughput is tasks completed per second. Turnaround time is from arrival to completion. Response time is from release to completion of a job; Rᵢ stands for the worst-case response time of task i, measured in ms. Waiting time is time spent ready but not running. Jitter is the variation in a periodic task's completion time from one job to the next; control loops care about it.

Naming differs between books. Some operating-systems texts call the arrival-to-first-run interval response time, because interactive programs care about how fast the first reply appears. This chapter follows the real-time convention: response time runs to completion, so it can be compared directly with the deadline.

First in, first out (FIFO) runs tasks in arrival order until each finishes. It is simple but a long task blocks every short one: poor response time. Round robin gives each ready task a fixed slice called the time quantum, then moves it to the back of the queue. A small quantum improves response time but spends more time in context switches (see 5.3). A large quantum behaves like FIFO. Both treat all tasks alike, which is wrong when one task has a hard deadline.

Fixed priority and rate monotonic

Fixed-priority preemptive scheduling gives each task a priority and always runs the highest-priority ready task. A higher-priority task that becomes ready preempts a lower one. Priority can come from importance (an airbag task outranks a radio task) or from timing. Rate monotonic (RM) chooses timing: a shorter period T gets higher priority. Deadline monotonic (DM) is the general form: a shorter relative deadline D gets higher priority; RM is DM when D = T.

U = Σ Cᵢ / Tᵢ

Cᵢ is execution time of task i in ms; Tᵢ is its period in ms; U is a dimensionless fraction.

For n periodic tasks with deadlines equal to periods, the RM utilisation bound is U ≤ n(2^(1/n) − 1). Values: n = 1 gives 1.000, n = 2 gives 0.828, n = 3 gives 0.779, and the limit as n grows is ln 2 ≈ 0.693. If U is at or below the bound, every deadline is met. The bound is sufficient, not necessary: a schedule above it may still pass.

U ≤ n(2^(1/n) − 1)

n is the number of periodic tasks with deadlines equal to periods; the right side is the RM utilisation bound.

When the bound fails, use the response-time test. For each task i, Rᵢ = Cᵢ + Σ ⌈Rᵢ/Tⱼ⌉ Cⱼ over higher-priority tasks j. Find the smallest Rᵢ that satisfies it; the task passes if Rᵢ ≤ Dᵢ. Solve it by iteration: start at Rᵢ = Cᵢ and substitute the current value on the right until the number stops changing. For T3 in the example the equation reads R₃ = 2 + ⌈R₃/4⌉·1 + ⌈R₃/5⌉·2. Start at R₃ = 2 ms: 2 + 1·1 + 1·2 = 5 ms. Put R₃ = 5 ms: 2 + 2·1 + 1·2 = 6 ms. Put R₃ = 6 ms: 2 + 2·1 + 2·2 = 8 ms. Put R₃ = 8 ms: 2 + 2·1 + 2·2 = 8 ms. The value repeats, so R₃ = 8 ms, and 8 ms ≤ 10 ms.

Rᵢ = Cᵢ + Σ ⌈Rᵢ / Tⱼ⌉ Cⱼ

Rᵢ is worst-case response time of task i in ms; j runs over higher-priority tasks; ⌈x⌉ rounds x up to an integer.

Earliest deadline first

Earliest deadline first (EDF) is preemptive and dynamic: at every release or completion, the ready task with the earliest absolute deadline runs. No fixed priority is stored. For periodic tasks with deadlines equal to periods, EDF is optimal on one CPU: if U ≤ 1, EDF meets all deadlines. If U > 1, no scheduler can meet all deadlines because the tasks demand more CPU time than exists.

EDF's rule follows the deadline, so a task that becomes urgent immediately wins. That flexibility is useful when periods vary. The cost is overhead: the scheduler must compare deadlines on every event. EDF also has no natural way to favour a critical task; a slightly earlier non-critical job will run first. Fixed priority is easier to analyse and cheaper to implement; EDF uses the CPU better near full load. The choice is a design decision, not a law. Many small RTOSs offer fixed priority; EDF appears in research and in some advanced controllers.

Worked example

Question. Three periodic tasks are released together at t = 0 with deadlines equal to their periods: T1 has C = 1 ms and T = 4 ms, T2 has C = 2 ms and T = 5 ms, T3 has C = 2 ms and T = 10 ms. (a) Compute the total utilisation. (b) Apply the rate-monotonic bound for n = 3. (c) Draw the rate-monotonic schedule up to t = 10 ms and state whether every deadline is met.

  1. 1. Utilisation: U = C1/T1 + C2/T2 + C3/T3 = 1/4 + 2/5 + 2/10 = 0.25 + 0.40 + 0.20 = 0.85.
  2. 2. Rate-monotonic bound for n = 3: n(2^(1/n) − 1) = 3(2^(1/3) − 1) = 3(1.2599 − 1) = 0.7798.
  3. 3. Rate-monotonic priority: T1 (T = 4 ms) is highest, T2 (T = 5 ms) is middle, T3 (T = 10 ms) is lowest.
  4. 4. Schedule: 0–1 ms T1; 1–3 ms T2; 3–4 ms T3; 4–5 ms T1; 5–7 ms T2; 7–8 ms T3; 8–9 ms T1; 9–10 ms idle. T3 needs 2 ms in total, so its run is split into 3–4 ms and 7–8 ms.

Answer. U = 0.85; the RM bound for n = 3 is 0.7798; the schedule 0–1 T1, 1–3 T2, 3–4 T3, 4–5 T1, 5–7 T2, 7–8 T3, 8–9 T1, 9–10 idle meets every deadline, so the bound is sufficient but not necessary.

Exam traps

  • Treating U ≤ n(2^(1/n) − 1) as a necessary condition. It is only sufficient; the worked example has U = 0.85 and still meets every deadline.
  • Applying the rate-monotonic bound when D ≠ T. Use deadline monotonic priority and the response-time test instead.
  • Assuming EDF is always the better practical choice. EDF needs deadline comparisons on every event and has no natural way to reserve the CPU for one critical task.
  • Confusing response time with waiting time. Waiting time is time ready but not running; response time runs to completion.
  • Using period in place of execution time in U. Utilisation uses Cᵢ/Tᵢ, with both quantities in the same unit.

5.5 Hard and soft real-time systems; RTOS versus GPOS

A real-time system is judged by its worst case, not its average. If a late result is a failure, the system is hard real-time; if it is useless but harmless, firm; if it only lowers quality, soft. An RTOS puts a provable upper bound on event-to-reaction time. A GPOS shares the CPU fairly for throughput and accepts occasional long delays.

You need 5.3 for switch cost and 5.4 for how a scheduler picks the next task.

Deadlines, worst case and slack

A deadline is the latest instant by which a task's result must be ready. Each task has a worst-case execution time (WCET): the longest time its code can take on its slowest path, counting all branches and cache misses. Slack is the spare time.

slack = deadline − R

R is the task's worst-case response time from event to output (defined fully in section 2). A negative slack means the deadline is missed. Use deadline − WCET only when the task starts immediately with no latency or scheduling delay.

Hard real time: a missed deadline is a failure, and the damage is unbounded. An airbag controller must fire within tens of milliseconds of the crash pulse. Fire late and the occupant is already against the dashboard. There is no retry.

Firm real time: a late result is worthless, but throwing it away costs nothing else. A video decoder that misses a frame deadline drops that frame. The picture stutters once and continues.

Soft real time: a late result is still useful; only quality drops. A UPI receipt that appears 300 ms after the tap annoys the user, but the money has moved. A game at 45 frames per second instead of 60 is still playable.

Determinism means the same event under the same load gives the same bounded response every run. Jitter is the spread between the shortest and longest response time. A system with a 1 µs average and a 50 ms worst case cannot meet a deadline shorter than 50 ms; whether it is real-time depends on the deadline. Real time means meeting the deadline, not having low jitter.

The latency chain

Response time is a sum of stages, and each stage is taken at its worst case, never its average.

  1. Interrupt latency L_int: hardware event to the first ISR instruction; finish the current instruction, vector fetch, register save.
  2. ISR body L_isr: first ISR instruction to the last, including the ISR's own work.
  3. Scheduler latency L_sch: end of ISR to choosing the highest-priority ready task.
  4. Context switch T_sw: save the old task's registers and restore the new task's.
  5. Time to effect T_eff: task's first instruction to the GPIO, PWM or CAN write that matters.

R = L_int + L_isr + L_sch + T_sw + T_eff

R is worst-case response time; L_int is interrupt latency; L_isr is ISR body time; L_sch is scheduler latency; T_sw is one context switch; T_eff is time to effect. All in µs here.

Every stage is a budget line. If the total fits inside the deadline, the design is sound. The figure shows a chain adding to 14 µs against a 20 µs deadline.

What an RTOS gives you that a GPOS does not

An RTOS bounds the worst case. Its scheduler is preemptive and priority-based, so a high-priority task runs as soon as it is ready. Kernel calls have documented upper bounds. Priority inheritance bounds the time a low-priority lock holder can block a high-priority task by giving the holder the higher priority for the critical section. The kernel is small, often a few KB to tens of KB, and usually has no MMU, so no page faults and memory comes from fixed pools.

A GPOS favours fairness and throughput. It time-slices among users and daemons, uses demand paging, and offers rich file systems, networks and drivers. Any feature can inject millisecond delays: a page fault from flash or a file-system flush can turn a 2 µs wake-up into tens of ms. Fine for a phone, fatal for an airbag.

Worked example

Question. A motor must start within 20 µs of a button press. Interrupt latency is 2 µs, ISR body 1 µs, scheduler 5 µs, switch 2 µs and time to effect 4 µs. (a) Is the deadline met, and what is the slack? (b) Which stage should you attack first if the deadline were 12 µs?

  1. Write the five costs: L_int = 2 µs, L_isr = 1 µs, L_sch = 5 µs, T_sw = 2 µs, T_eff = 4 µs.
  2. Add them: R = 2 + 1 + 5 + 2 + 4 = 14 µs.
  3. Slack = deadline − R = 20 − 14 = 6 µs. The deadline is met with 6 µs spare, 30% of the budget unused.
  4. Part (b): with a 12 µs deadline, R = 14 µs exceeds it by 2 µs, so slack is −2 µs and the deadline is missed. At least 2 µs must go.
  5. Find the biggest stage: scheduler at 5 µs, 5 ÷ 14 ≈ 36% of the chain. Attack it first.
  6. A ready-queue bitmap or letting the ISR select the motor task directly can cut scheduler latency to 3 µs. New R = 2 + 1 + 3 + 2 + 4 = 12 µs, slack 0 µs — exactly met, no margin left.
  7. For more margin, cut T_eff (4 µs) next, the largest remaining. Then cut the 3 µs scheduler or the 2 µs ISR entry, then the 2 µs switch, and last the 1 µs ISR body.
  8. A system exactly on the deadline is risky: a temperature rise or cache miss makes it late. Keep about 20% margin.

Answer. R = 14 µs, so the 20 µs deadline is met with 6 µs slack; against 12 µs the chain is 2 µs late, and the 5 µs scheduler stage should be attacked first.

Exam traps

  • Calling any fast system real-time. Hard real time means a bounded worst case: 1 µs typical with a 50 ms worst case still misses a 10 ms deadline.
  • Adding average stage times instead of worst-case times.
  • Confusing latency with jitter, or response time with throughput.
  • Thinking a soft deadline is not a deadline. A miss costs quality, not correctness.
  • Forgetting T_eff. Interrupt and switch are wasted if the task then takes 40 µs to reach the pin write.

5.6 Inter-task communication: semaphores, mutexes, queues

Tasks rarely live alone. One task reads a sensor while another averages it; an interrupt hands a byte to a task; two tasks update a shared counter. Without rules, their reads and writes interleave and data is lost. Inter-task communication gives three tools: a semaphore signals an event, a mutex protects a shared resource, and a queue carries data from producer to consumer. Every RTOS uses them in drivers, control loops and logging.

You need: 5.2 tasks, 5.3 preemption and the context switch, and 5.4 priorities.

Race conditions and critical sections

A race condition is a result that depends on the exact interleaving of two tasks. Suppose two tasks both run count = count + 1. Each reads the old value, adds one in a register, and writes back. If both read before either writes, one update is lost. The operation is not atomic: it cannot be split and still give the same result. A critical section is code that touches shared data and must run as if no other task is running. The shared data may be a variable, a buffer, a peripheral register or a file.

Two protections exist. First, disable interrupts around the section: mask interrupts, run the few instructions, unmask. On one core this stops the scheduler tick and every ISR, so no other task can enter. It is simple and fast, but it adds interrupt latency; keep it to microseconds. On a multicore chip it does not stop a task on another core. Second, take a lock: a kernel object. If another task holds the lock, the caller blocks and the scheduler runs other work. A lock works across cores and for longer sections.

  • Use one lock for one shared object; name the lock after the data.
  • Keep the critical section short; no slow I/O or unbounded loops inside.
  • Release the lock on every path, including error returns.
  • Do not disable interrupts for a long computation; measure the added latency.

Semaphores and mutexes

A semaphore is a kernel object with a count and a wait list. take() (also wait, P) checks the count: if it is greater than 0, decrement and continue; otherwise block the task. give() (signal, V) increments the count and unblocks one waiter. A binary semaphore has count 0 or 1; a counting semaphore starts at N and tracks N identical resources. Any task or ISR may give a semaphore; only a task may take one, because an ISR cannot block.

A mutex is a lock with an owner. Only the task that took it may give it. The kernel records the owner, so it can detect a recursive take by the same task and can apply priority inheritance. A recursive mutex counts how many times the owner took it; the owner must give it the same number of times. Use a mutex for mutual exclusion and a semaphore for signalling. A binary semaphore is not a mutex because it has no owner.

W_H ≤ R_L + ε

W_H is the wait of high-priority task H before it gets the mutex; R_L is the remaining time owner L needs inside its critical section; ε is kernel overhead for blocking, wake-up and a context switch. This bound holds with priority inheritance and one mutex; nested mutexes add each holder's remaining section.

Priority inversion: low-priority L holds a mutex; high-priority H waits; medium-priority M preempts L. H now waits for M even though M needs no lock. If new medium tasks keep arriving, the wait grows without limit: unbounded priority inversion. With inheritance, L runs at H's priority until it releases the mutex, so M cannot preempt; H waits at most R_L plus kernel overhead.

Deadlock is a cycle of tasks each waiting for a resource held by the next. Its four conditions are mutual exclusion, hold and wait, no preemption, and circular wait. Break one: acquire locks in a fixed global order, use timeouts, or use one lock. Starvation is different: a runnable task never gets the CPU or the lock because others keep winning. FIFO wait lists and priority aging reduce it.

Queues, mailboxes and event flags

A message queue is a FIFO buffer of fixed-size items managed by the kernel. send(q, item) copies the item into the queue; receive(q, item) copies it out. A bounded queue has capacity N. A producer blocks when the queue is full, and a consumer blocks when it is empty; both calls may take a timeout. The kernel copies the item, so the sender can reuse its buffer immediately. This is the producer-consumer pattern.

A mailbox is a queue with one slot. Some syllabi call a queue a message buffer and a mailbox a one-slot queue. Event flags are bits in a word; a task waits for any or all selected bits to be set. A pipe is a byte-stream queue, often used between a task and a driver. ISR-safe calls exist: sendFromISR() never blocks; if the queue is full it returns an error or drops the item. A semaphore give from an ISR also uses a FromISR call. A take is never called from an ISR.

Worked example

Question. A low-priority task L holds a mutex and has 3 ms of its critical section left. A medium-priority task M becomes ready and needs 12 ms of CPU; at that instant, before M runs, high-priority task H blocks on the same mutex. Ignore context-switch time. Compute H's waiting time (a) with no priority inheritance, and (b) with priority inheritance.

  1. L holds the mutex with 3 ms of critical section remaining. H is blocked on that mutex.
  2. Without inheritance, the scheduler sees M at medium priority and L at low priority. M preempts L and runs for its full 12 ms.
  3. L resumes and finishes its remaining 3 ms, then releases the mutex.
  4. H waits for M's 12 ms plus L's 3 ms: 12 + 3 = 15 ms before H can take the mutex.
  5. With inheritance, L runs at H's priority while H waits. M, at medium priority, cannot preempt L.
  6. L finishes its 3 ms, releases the mutex, and H takes it. H waits 3 ms. M runs later.
  7. H's wait is 15 ms without inheritance and 3 ms with inheritance.

Answer. H waits 15 ms without priority inheritance and 3 ms with priority inheritance.

Exam traps

  • Using a binary semaphore as a mutex. A semaphore can be given by any task and has no owner, so priority inheritance cannot be applied to it; a mutex records its owner and can be inherited.
  • Calling a blocking take or blocking send from an ISR. ISRs must use FromISR variants that never block; if the object is full or empty, the call returns an error or drops the item.
  • Thinking priority inheritance removes the wait. It only bounds the wait by the owner's remaining critical section; a long section or a chain of nested mutexes still delays the high-priority task.
  • Forgetting to release a mutex on an error path. The next task blocks forever, which is deadlock, not priority inversion.
  • Treating interrupt disable as a universal lock. On a multicore chip it does not stop another core; long masking also increases interrupt latency and can miss deadlines.

5.7 Device drivers and board support packages

A device driver is the small kernel layer that turns a peripheral's registers into ordinary calls such as open, read and write. A board support package (BSP) is the matching board layer that sets clocks, memory map, console and timer so one operating system can boot on one board. Drivers hide hardware detail from applications; BSPs hide board detail from the kernel. You meet both in every phone, router, car ECU and UPI terminal that runs an embedded OS.

You need: 5.1 for kernel space, Unit 3 for interrupts, DMA and timers, and Unit 4 for SPI, I2C and CAN.

Driver skeleton and driver classes

A driver is kernel code. The application calls read(); the kernel routes the call to the driver that owns the device. The driver's init routine runs at boot: it probes the hardware, maps registers, requests the interrupt line and sets control bits. open() and close() track use, read() and write() move data, input/output control (ioctl()) handles odd controls, and the interrupt service routine (ISR) runs when the device signals.

Registers are memory-mapped: each appears at a fixed address. A C pointer to a register must be volatile, so the compiler reads the hardware again instead of reusing an old value. The pointer also needs the correct width: an 8-bit register must not be read as 32 bits.

Drivers fall into three classes. A character driver moves a byte stream and supports read/write, as for a UART or ADC. A block driver moves fixed-size blocks and keeps a cache, as for flash or an SD card. A network driver moves packets and does not use read/write files, as for Ethernet. Bus drivers for I2C and SPI carry addresses and data bytes, and CAN drivers carry frames; the device driver above them turns those transfers into read, write and ioctl.

Polling, interrupts, DMA and the two halves

Three methods move data. Polling has the CPU loop on a status bit; it is simple and has no interrupt latency, but it burns cycles. An interrupt lets the device signal the CPU; the CPU is free until the event. Direct memory access (DMA) lets a controller copy a block while the CPU does other work; the CPU sets up the transfer and takes one completion interrupt.

The usual driver splits work into a fast top half and a deferred bottom half. The top-half ISR copies one sample, clears the interrupt flag and wakes a task. The bottom-half task converts, filters, logs or sends the sample. A ring buffer is a circular array with a write head and a read tail; the ISR writes at the head, the task reads at the tail.

f_cpu = t_transfer ÷ T_sample

f_cpu is the fraction of CPU time used by transfers; t_transfer is the time to move one sample, in seconds; T_sample is the sample period, in seconds.

Memory device drivers

Flash memory reads like RAM but cannot be overwritten like RAM. A write can only clear bits from 1 to 0. To set bits back to 1, the driver must erase a whole erase block, often 4 KB or 64 KB. So an update is read-modify-erase-write, and the driver must keep a copy of the block in RAM. Erase blocks are large: changing one byte can cost one full erase. Flash cells wear out after a limited number of erase cycles, so a flash driver uses wear levelling: it moves logical blocks to different physical blocks so no single block is erased too often.

EEPROM is byte-writable but slow. A page write loads a small page buffer, then the chip runs an internal write cycle, often about 5 ms. The driver must poll the acknowledge bit or wait before the next write. Writes that cross a page boundary wrap inside the page, so the driver splits them at page edges. A memory driver also reports erase-block size and page size upward, because the file system needs them.

What a BSP contains

A board support package (BSP) is the code that makes one OS run on one board. It contains the boot code that runs first, clock and phase-locked loop (PLL) setup for the CPU and buses, a UART console for early messages, a timer tick for the scheduler, interrupt-controller setup, the memory map, a linker script that places code and data in memory, and board configuration such as pin multiplexing and bus speeds.

BSP and driver split the work. The BSP says which UART exists, at which address, with which clock. The UART driver then implements open, read, write and the ISR using those facts. A new board with the same chip usually needs a new BSP, not a new driver.

Some systems describe hardware in a device tree: a data file that lists devices, addresses and interrupts, so one kernel image can boot on several boards. Only a few universities teach them; for this chapter, treat a device tree as a board description read at boot. The bootloader and kernel image build belong to 5.9.

5.8 Memory management in embedded OS

An embedded OS often runs on a fixed pool of RAM and no memory management unit (MMU), so memory management is less about virtual addresses and more about bounded use. The linker fixes where code and globals live; the stack and heap share the rest. A hard real-time task cannot wait while a general heap walks a long free list. The practical tools are a clear memory map, fixed-size block pools, small-heap first-fit or best-fit, and stacks that are sized and guarded. These tools appear in motor-control loops, sensor nodes, and automotive ECUs.

You need: Unit 1 on ROM, flash, SRAM and DRAM; and 5.1 on kernel space.

Memory map and static allocation

A microcontroller memory map starts at low addresses in flash. The vector table holds reset and interrupt addresses, then text (code) and rodata (constants and strings). RAM holds .data (initialised globals and static variables), .bss (zero-initialised globals), the heap, free RAM, and the stack at the top. The heap grows up; the stack grows down. The linker script fixes these regions at build time.

Static allocation reserves memory when the program is linked. A global array, a task control block, or a message-queue buffer has a size known at build time. There is no allocator call at run time, no fragmentation, and the worst-case memory use is visible in the map file. The cost is fixed capacity: if a queue is full, the design must block, drop, or overwrite according to policy.

Dynamic allocation takes memory from a heap at run time. It helps when message sizes vary or when objects appear and disappear. A general malloc keeps a free list, splits blocks, and coalesces neighbours. Its run time depends on the list length, and its worst case can be unbounded. In a hard real-time loop, a task that calls malloc may miss its deadline. It can also fail after long uptime because of fragmentation.

  • Static: size fixed at link time, allocator time zero, no fragmentation.
  • Dynamic: size chosen at run time, allocator time variable, fragmentation possible.

Fixed pools, first-fit and best-fit

A fixed-size block pool divides a RAM region into N blocks of B bytes. A free list or bitmap records which blocks are free. Allocation takes one free block; free returns it. Every request is rounded up to B bytes, so a 100-byte request from 128-byte blocks uses 128 bytes. The unused 28 bytes are internal fragmentation. There is no external fragmentation because all blocks are the same size.

On a small variable-size heap, first-fit scans from the start and takes the first free block large enough. It is fast but may leave large blocks at the end. Best-fit scans the whole free list and takes the smallest adequate block. It reduces immediate waste but is slower and can leave tiny holes. Both can suffer external fragmentation: enough total free memory exists, but no single gap is large enough.

Allocator timing matters as much as space. A fixed pool has O(1) allocation and free. First-fit is O(k) in the number of free blocks before the chosen block; best-fit is O(k) over all free blocks. A two-level allocator such as TLSF (two-level segregated fit) keeps a bitmap of size classes and gives bounded behaviour; only a few syllabi teach its bitmaps. For most exam answers, state that fixed pools are bounded and general heaps are not.

Stacks, protection and leaks

Each task owns a stack. Size it from the worst-case call chain, local arrays, saved context, and the deepest interrupt service routine (ISR) nesting. If interrupts use the current task stack, add the largest ISR frame plus any nested ISRs. If the CPU has a separate interrupt stack, size that separately. Stack painting writes a known pattern at start-up; the high-water mark shows peak use.

A canary is a magic word at the stack boundary, checked by the kernel on each switch. If it changes, the task overflowed. A guard region is an unmapped or memory-protection-unit (MPU) protected area next to the stack; a write there faults immediately. Canaries are cheap but detect after the write; guard regions catch sooner and cost MPU regions.

An MPU gives a few protection regions with base, size, and access permissions. It does not translate addresses and has no demand paging. An MMU translates virtual addresses to physical addresses and enables isolation and demand paging. Demand paging can trigger a page fault and a flash or disk read, so its worst-case latency is large and variable. A hard RTOS either disables paging, pins pages, or avoids an MMU. Only a few syllabi teach MPU region programming in detail.

A leak is an allocation that is never freed. Reference counting frees an object when its count reaches zero; cycles need a cycle collector or manual breaking. In long-running embedded devices, leaks show as slowly falling free memory and eventual allocation failure.

Worked example

Question. A fixed-pool allocator has 8 blocks of 128 bytes. Four tasks request 100, 40, 90 and 60 bytes in that order, and each request is rounded up to a whole block. (a) How many blocks are used? (b) How many bytes are allocated in total? (c) What percentage of the allocated space is wasted?

  1. Each request is ≤ 128 bytes and > 0, so after rounding each needs exactly 1 block.
  2. Blocks used = 4 requests × 1 block = 4 blocks (out of 8).
  3. Allocated bytes = 4 blocks × 128 bytes/block = 512 bytes.
  4. Requested bytes = 100 + 40 + 90 + 60 = 290 bytes.
  5. Wasted bytes = 512 − 290 = 222 bytes (internal fragmentation).
  6. Waste percentage = (222 ÷ 512) × 100 = 43.359375% ≈ 43.36%.

Answer. 4 blocks are used, 512 bytes are allocated, 222 bytes are wasted, and 43.36% of the allocated space is wasted.

Exam traps

  • Do not assume malloc is constant-time. A general heap may walk a free list, so its worst case is unbounded; real-time code uses fixed-size pools.
  • Internal fragmentation is waste inside an allocated block; external fragmentation is free gaps between allocated blocks. A pool has internal waste but no external fragmentation.
  • Stack sizing must include ISR frames and nested interrupts. A task stack that fits normal calls can still overflow on an interrupt.
  • An MPU is not an MMU. An MPU checks permissions on physical regions; an MMU translates virtual to physical addresses and can page.
  • A canary detects overflow only when the kernel checks it; a guard region faults on the write. Do not claim a canary prevents the overwrite.

5.9 Embedded Linux, bootloaders and FreeRTOS

A bootloader is the first code that runs after reset and the last code that hands control to an operating system. On a powerful board it can load a full Linux kernel with a network stack and file system. On a small microcontroller it can start a tiny real-time kernel such as FreeRTOS in a few milliseconds. The choice follows the deadline and the feature list, not fashion. This chapter follows the boot chain from ROM code to application and compares the two families.

You need: Chapter 5.1 for kernel and user space, Chapter 5.5 for hard versus soft real time, Chapter 5.7 for drivers and board support, and Chapter 5.8 for bounded RAM.

Embedded Linux: layers and images

Linux splits the machine into user space and kernel space. Applications and the C library run in user space. A request such as reading a file becomes a system call, the controlled entry into the kernel. The kernel then uses one of its subsystems: the scheduler picks the next task, the memory manager maps pages, the virtual file system (VFS) gives one interface to FAT, ext4 or flash file systems, the network stack handles TCP/IP, and device drivers talk to peripherals. See Chapter 5.1 for that boundary and Chapter 5.7 for drivers.

An embedded kernel image is compressed. A zImage is a compressed kernel that decompresses itself in place. A uImage is the same kernel wrapped in an older U-Boot header that carries a load address and a checksum. The kernel needs a root file system: the directory tree holding /bin, /etc, device nodes and your program. It may sit on a flash file system such as JFFS2 (journalling flash file system, version 2) or UBIFS (unsorted block image file system), or in a small initramfs packed into RAM. Chapter 5.8 explains the RAM budget.

Plain Linux optimises average throughput and fairness, so an interrupt may wait. PREEMPT_RT is a kernel patch set that makes most kernel code preemptible and shortens the worst-case latency. It gives good soft real time, not a hard guarantee; a missed deadline that fails the product still needs an RTOS, as Chapter 5.5 explains.

Boot chain: ROM code to application

Power-on is a chain because each stage must fit in the storage the previous stage can read. The processor starts at a fixed address in on-chip ROM code. That code knows only a few ways to load the next stage: serial port, SD card, NAND flash or SPI flash. It loads a secondary loader, often called SPL (secondary program loader). The SPL sets up DRAM, because DRAM needs a trained controller before it can hold a large program.

U-Boot is the full bootloader. It initialises clocks, DRAM, storage and sometimes the network. It reads a kernel image from flash, eMMC, SD card or a TFTP server, places it at the correct address, passes a device tree (a hardware description) and a kernel command line, and jumps to the kernel. At naming level, common commands are printenv, setenv, fatload, tftp, bootz and bootm. U-Boot is not the operating system; it exits before Linux runs.

The kernel mounts the root file system and starts init (or systemd), the first user-space process. init starts services and finally your application. The figure gives a typical board: ROM code 20 ms, secondary loader 80 ms, U-Boot 900 ms, kernel decompression and init 1.4 s, root file system and application 2.5 s. Total is 4.9 s. U-Boot and the root file system dominate, so a fast-start product attacks those two first.

FreeRTOS: a small priority kernel

FreeRTOS is a free, open-source real-time kernel for microcontrollers. The main distribution has no memory management unit (MMU) support, so all tasks share one address space; this is normal on a Cortex-M board. A task is an independent thread with its own stack and priority. The scheduler runs the highest-priority ready task, and tasks of equal priority share the CPU by round robin if time slicing is enabled. A task blocks with vTaskDelay, waits on a queue, or waits on a semaphore; while it waits, lower-priority tasks run.

Queues carry fixed-size items between tasks or from an interrupt. Semaphores signal an event, and a mutex protects a shared resource with priority inheritance. Software timers run callback functions from a timer service task, not from the hardware tick interrupt, so they are not for microsecond deadlines. Chapter 5.6 gives the rules for these objects.

The kernel is configured in FreeRTOSConfig.h. Key items are configMAX_PRIORITIES (number of priority levels), configTICK_RATE_HZ (tick frequency), configMINIMAL_STACK_SIZE (words on many ports), configTOTAL_HEAP_SIZE (bytes for pvPortMalloc) and configUSE_PREEMPTION. A Cortex-M port needs port.c, portmacro.h and the configuration header. It uses SysTick for the tick, PendSV for context switching and SVC to start the first task. A minimal build is a few kB of flash and about 1 kB of RAM plus task stacks; a typical build with queues and timers is roughly 6–12 kB of flash.

Choosing the kernel for the deadline

Start from the deadline, not the feature list. A motor current loop at 10 kHz needs a deterministic RTOS on a microcontroller. A payment terminal that draws a screen, uses Wi-Fi and updates over the air usually needs Linux, because the network stack, file systems and drivers already exist. Exam traps

  • Saying Linux cannot be used in embedded systems because it is not hard real-time. Most products need only soft real time; the real trap is promising a hard deadline on plain Linux.
  • Calling U-Boot the operating system. U-Boot is a bootloader that loads the kernel and then exits.
  • Treating zImage and uImage as different kernels. uImage is the same kernel plus a U-Boot header.
  • Forgetting that a kernel without a root file system and init cannot start the application.
  • Confusing initramfs with JFFS2 or UBIFS. initramfs lives in RAM; JFFS2 and UBIFS live on flash.

Takeaways

  1. The kernel is the only code that touches hardware, and every other program reaches hardware through a system call.
  2. A process owns an address space; threads of that process share it and cost only a stack plus a register context each.
  3. Context switching is pure overhead, so an RTOS keeps it short and predictable rather than merely fast on average.
  4. Rate monotonic scheduling is the fixed-priority rule for periodic tasks, and its utilisation bound tells you whether the set is safe.
  5. EDF can schedule any set with utilisation at or below 1, but a transient overload makes it misbehave far worse than RM.
  6. A hard real-time system fails when a deadline slips; an RTOS is engineered to bound the worst case, not the average.

Low-priority task L holds a mutex; high-priority task H blocks on it; medium task M preempts L and H waits for M; Show the unbounded wait on a timeline; Solution 1: priority inheritance, so L runs at H's priority while holding the lock; Solution 2: priority ceiling, so the lock is taken at the ceiling priority; Note the difference between a mutex (with inheritance) and a binary semaphore (without ownership); Cost: inheritance adds code to the scheduler and complicates the ready queue.

Apply Describe a context switch on a Cortex-M class microcontroller in an RTOS, and explain how switch latency is measured. 10 marks

Trigger: SysTick or an ISR makes a higher-priority task ready; kernel sets the pend bit; Hardware stacks the caller-saved registers automatically on exception entry; Kernel saves the remaining registers and the stack pointer into the current TCB; Scheduler picks the highest-priority ready task and loads its stack pointer from its TCB; Return from exception restores the new task's registers; cycle count of these steps gives switch latency; Measure by toggling a GPIO pin at entry and exit of the switch and reading the pulse on a scope.

Apply Write the structure of two FreeRTOS tasks that pass a sensor reading through a queue and signal completion with a semaphore from an ISR. 12 marks

Declare a queue handle and a binary semaphore handle before the scheduler starts; Producer task reads the sensor and calls the queue send with a finite block time; Consumer task blocks on the queue receive and processes the value; ISR uses the FromISR variants and requests a yield if a higher-priority task was woken; Use a mutex, not a binary semaphore, for shared data with priority inheritance; Mention stack sizing per task and that ISRs must stay short; defer work to a task.

Apply Design memory management for a board with 64 KB RAM and no MMU. Compare a fixed-block pool with malloc and show how fragmentation arises. 10 marks

No MMU means no protection between tasks; every pointer is physical; malloc gives variable-size blocks and suffers external fragmentation over long runtimes; Fixed-block pool: carve RAM into blocks of a few sizes at start-up; allocation is a list pop, so time is constant; Use static allocation for task stacks, queues and buffers wherever the count is known; Show a worst-case figure: a 512-byte block pool with 20 blocks gives a hard ceiling on memory use; Determinism: allocation and free must complete in bounded time for real-time use.

Analyze and evaluate

Analyze Describe the boot sequence of an embedded Linux board from power-on to a running shell, and place the bootloader, kernel image, initramfs and root file system in it. 13 marks

On-chip ROM code reads the boot mode pins and loads a first-stage loader from flash or SD card; First-stage loader sets clocks and DRAM, then loads U-Boot; U-Boot loads the kernel image and device tree into DRAM, passes the command line, and jumps; Kernel decompresses, initialises memory and drivers, then mounts initramfs as a temporary root; init runs, the real root file system is mounted from eMMC or flash, and services start; Mention JFFS2 for raw NOR flash, UBIFS for NAND with UBI, and that both survive power loss; Note recovery: a serial console and a bootloader prompt are the field-service path.

Evaluate A team must choose between FreeRTOS on a microcontroller and embedded Linux on an applications processor for a UPI payment terminal. Justify a recommendation. 13 marks

List requirements: secure key handling, display and network stack, deadline for the card reader, cost per unit, power, field updates; FreeRTOS: few KB of RAM, microsecond-class bounded latency, small BSP, but no memory protection and a thin TCP/IP and file stack; Linux: full networking, TLS, file systems, driver base, but seconds-long boot unless tuned, and worst-case latency needs PREEMPT_RT; Cost check in rupees per board and the RAM and flash each option forces; Risk check: certified security module, update mechanism, and a bootloader that can recover from a failed update; Give a clear verdict with the condition that would reverse it.

Evaluate A prototype uses malloc inside an interrupt handler, a binary semaphore in place of a mutex, and a long polling loop inside an ISR. Assess the risks and propose a corrected design. 12 marks

malloc in an ISR: unbounded time and possible lock contention, so latency is not bounded; memory should be preallocated; Binary semaphore for shared data: no ownership and no priority inheritance, so priority inversion is unbounded; use a mutex; Long ISR: blocks all lower and equal priority interrupts, adds jitter to every task; split into top half and deferred task; Corrected design: ISR captures the value, signals a task, returns; the task does the work; Add measurement: GPIO pulse widths to record ISR and switch latency; State the verification step: timeline analysis or a worst-case execution time measurement before release.

Analyze Explain the layers of a board support package and how a device driver written for one board becomes a standard interface for application code. 10 marks

BSP layers: boot code and clock and pin setup, memory map, interrupt controller setup, peripheral drivers, and the OS adaptation layer; Driver exposes open, read, write, ioctl on a device node or a handle, hiding register bit-fields; Example: an application sends characters to a UART without knowing the baud divisor register; Porting cost: to move to a new board you change the BSP, not the application; Kernel versus user space: a kernel driver runs privileged and can be reached from a task by a system call; Mention device tree as the data-driven alternative on embedded Linux.

Glossary

Board support package
The board-specific collection of boot code, clock, pin, memory and driver code that lets an OS run on that board.
Bootloader
A small program that initialises the board, loads a kernel image into memory and transfers control to it.
Context
The complete saved state of a task, comprising program counter, stack pointer, CPU registers and status flags.
Context switch
The act of saving one task's context and restoring another's, which consumes CPU time without doing application work.
Determinism
The property that an operation completes within a known worst-case bound, not merely quickly on average.
Device driver
Code that translates a peripheral's registers and interrupts into a standard interface for the rest of the system.
Earliest deadline first
A dynamic-priority rule that always runs the ready task whose absolute deadline is nearest.
Fragmentation
The loss of usable memory when free space is split into pieces too small to satisfy a request.
Hard real-time
A class of system in which missing a deadline is a functional failure and may be unsafe.
Jitter
The variation in the time a task takes to respond or in the period between successive runs.
Kernel
The privileged core of an operating system that manages CPU, memory and devices and is entered only through controlled entry points.
Message queue
A bounded first-in-first-out buffer used to pass data between tasks or from an interrupt to a task.
Mutex
A lock that only its owner may release, allowing the kernel to apply priority inheritance.
Preemption
Forcibly removing a running task from the CPU when a higher-priority task becomes ready or a time slice expires.
Priority inheritance
A protocol in which a task holding a lock runs at the priority of the highest task waiting for it.
Priority inversion
A situation where a high-priority task waits behind a low-priority task that is itself delayed by a middle-priority task.
Process
A program in execution that owns a private address space, open files and one or more threads.
Rate monotonic scheduling
A fixed-priority rule assigning higher priority to tasks with shorter periods.
Round robin
A scheduling rule that gives each ready task of equal priority a fixed time slice in turn.
Semaphore
A counter with wait and signal operations used to signal an event or guard a counted resource.
Soft real-time
A class of system in which a missed deadline only reduces quality of service.
System call
A software trap by which a user task requests a kernel service such as a file write or a device operation.
Task
A schedulable unit of work, usually a single thread with its own stack, priority and control block in an RTOS.
Thread
An execution path within a process that shares the process address space but has its own stack and register state.
User space
The unprivileged execution mode and memory region where application tasks run, isolated from hardware registers.
Utilisation
The fraction of CPU time demanded, U = Σ(Cᵢ/Tᵢ) for execution time C and period T.
