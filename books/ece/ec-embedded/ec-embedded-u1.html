1.1 Embedded systems: definition, characteristics and applications

A laptop runs whatever program you install. An embedded system runs one program, fixed at manufacture, hidden inside a product with a job: a washing machine, a glucometer, a car's engine control unit. That single job decides the memory it may use, the power it may draw and the rupees it may cost. This chapter defines the term, lists the characteristics that follow, and maps the application areas.

A computer hidden inside a product

An embedded system is a computer built into a larger device to do one dedicated job. The computer is not the product: nobody buys a washing machine for its controller. Some syllabi call it a dedicated computer or a special-purpose computer.

The contrast is the general-purpose computer. On a laptop the user chooses the program. In an embedded system the program is firmware: machine code plus fixed data in ROM or flash, running from the instant power is switched on. The user cannot install another program; changing behaviour means flashing the chip. Memory choice for firmware is covered in 1.7.

The idea is old. The Apollo guidance computer of the 1960s flew a spacecraft on a fixed program held in about 36,000 words of read-only memory, with about 2,000 words of working memory. Today a ₹2,000 kitchen appliance carries a microcontroller with far more compute.

Characteristics that follow from one dedicated job

Fix the job and a chain of consequences follows. These are the properties an examiner means by the specialties of embedded systems.

  • Single function. One task, or a small fixed set of tasks, for the life of the product.
  • Tight hardware-software coupling. The code is written against one board, one memory map, one pin layout. Porting it means rewriting large parts.
  • Constrained resources. Memory counted in kilobytes, power in milliwatts, cost in rupees per unit, size in millimetres. Cost bites hardest, because the product ships in lakhs.
  • Reactive. It waits on inputs and answers them; it is not a batch job that runs to completion.
  • Often real-time. A deadline must be met. Real-time does not mean fast — it means a late answer is a wrong answer. An ABS controller must release brake pressure within milliseconds of a wheel locking.
  • Little or no user interface. A few LEDs, a seven-segment display, one button.
  • Firmware fixed at manufacture. Updates happen by flashing the chip, not by clicking install.
  • Long life and high reliability. An electricity meter runs for 15 years; a pacemaker must never need a reboot.

Not every system carries every property. A hobby board with a screen is embedded by function and general-purpose by interface. The list is a checklist, not a gate. How these properties are traded is the subject of 1.3.

Sensing, deciding, acting

Most embedded systems touch the physical world at two ends. At the input end sits a sensor: a device that converts a physical quantity into an electrical signal. The LM35 gives 10 mV for every 1 °C. An LDR drops its resistance when light falls on it. An IR sensor gives a voltage that says an object is in front of it. The input end may instead be a keypad, as on a washing machine, or a network link, as on a set-top box.

Signal conditioning stands between sensor and processor: amplify a millivolt signal to volts, filter noise, protect the pin from over-voltage. The processor then digitises the result with an ADC (Unit 3), runs the firmware, and decides.

At the output end sits an actuator: a device that converts an electrical signal into physical action — a DC motor turns, a relay contact closes, a solenoid valve opens, a buzzer sounds. A processor pin gives a few milliamps at 3.3 V; a motor wants hundreds of milliamps at 12 V. The driver is the switch in between: a transistor, a relay module, an H-bridge. Some systems drive only a display or a network link and no actuator, like a data logger.

The loop is sense, decide, act, repeat — thousands of times a second. Many systems also carry a network link so that the decision can be reported or corrected from outside (Unit 4).

Exam traps

  • Small size does not make a system embedded. A laptop, or a Raspberry Pi running a desktop, is general-purpose however portable it is.
  • Real-time does not mean fast. A 1 ms deadline met on an 8-bit microcontroller is real-time; a fast server that misses its deadline is not.
  • 'Embedded' is not another word for 'microcontroller'. The definition is about a dedicated function inside a product; the chip may be a microprocessor, a DSP, an SoC or an FPGA.
  • Sensor and actuator are opposites. An LM35 or LDR is a sensor; a buzzer, relay or solenoid valve is an actuator. Swapping them loses the whole mark.
  • The favourite definition question expects three elements: dedicated function, computer inside a larger product, and fixed firmware.

1.2 Classification of embedded systems

Classification puts an embedded system into a named group so you can talk about it, pick tools for it, and judge whether a design fits. Three independent axes do most of the work: complexity, timing strictness, and physical form or connectivity. A washing-machine controller and an airbag controller can both be small boxes, yet only the airbag is hard real-time. These labels appear in datasheets, job interviews, and design reviews to set expectations before code is written.

You need: Chapter 1.1 for the definition and example devices.

Complexity and word size

The first axis asks how much computing the product needs. Word size — the number of bits the processor handles in one go, such as 8-bit or 32-bit — is a useful proxy. It sets the address range, the arithmetic width, and how much memory the chip can easily reach. A small system uses an 8-bit microcontroller unit (MCU), a few kilobytes (KB) of flash for the program, and no operating system. A medium system uses a 16-bit or 32-bit processor and a small real-time operating system (RTOS) to manage several tasks. A large system uses a 32-bit or 64-bit system-on-chip (SoC), megabytes of RAM, and an embedded Linux or Android stack.

The table shows the usual split. Some syllabi call the classes small, medium and large; others call them type A, type B and type C. The names change, the idea does not: match the computing class to the job, not to fashion.

Word size is not a quality score. An 8-bit controller can be the correct and cheaper answer for a fixed job.

Timing: hard, firm, soft

The second axis asks what happens when the system is late. A deadline is the latest time by which a result must be ready. In a hard real-time system, a missed deadline is a system failure. An airbag that fires 20 ms after the deadline, or an anti-lock braking system (ABS) that misses a 5 ms control loop, has failed in the safety sense. Hard does not mean fast in everyday terms; it means the deadline is not negotiable.

  • Hard: miss = failure. Examples: airbag, ABS, pacemaker.
  • Firm: late result is worthless but harmless. Example: one dropped video frame.
  • Soft: late result is still useful, only degraded. Example: a sluggish display refresh.

The complexity class and the timing class answer different questions. A small 8-bit MCU that must cut power within 10 ms of an over-current trip is hard real-time; a 64-bit tablet that feels fast is soft real-time. A device can be medium complexity and hard real-time, as the ABS example shows. Keep the two labels separate in an exam answer.

Form, connectivity, and other labels

The third axis describes where the computer sits and how it talks. A standalone system is one box that works alone, such as a digital wristwatch. A distributed or networked system has many nodes sharing a bus or a wireless link; a bank branch 4G router, a car with controller area network (CAN) nodes, and a sensor mesh are examples. A mobile system is carried by a person or vehicle and usually runs on a battery, so power and size dominate.

Two more labels appear in syllabi. By generation, systems are called 4-bit, 8-bit, 16-bit, 32-bit or 64-bit, following the processor word size. By implementation platform, systems are microcontroller-based (MCU), digital signal processor-based (DSP), field-programmable gate array-based (FPGA) or SoC-based. Chapter 1.5 explains how those platforms are chosen.

Use only the axes the question asks for. If a question says 'classify', name the axis first, then the class, then the reason. 'Medium, hard real-time, because a 5 ms loop miss loses braking control' is a complete answer.

1.3 Design metrics and design challenges

A design is judged by numbers: what one unit costs, how fast it answers, how much power it draws. These numbers are design metrics, or figures of merit. Every project has several at once, and a change that improves one usually worsens another. Engineers use the metrics to compare two architectures before building either one. The same list explains the hard choices of embedded design: fitting a deadline, a battery and a price into one small board.

You need Chapter 1.1 and Chapter 1.2: the device class tells you which metrics dominate.

Unit cost and NRE

Unit cost is the money to make one finished device. It has two parts. NRE (non-recurring engineering) is the one-time cost of design, tooling and masks, in rupees. Recurring cost is the parts plus assembly for each unit, also in rupees. If q units are built, the unit cost is NRE/q + recurring cost. The division is the point: NRE is paid once and spread over the whole run.

unit cost = NRE / q + recurring cost

NRE is the one-time design cost in rupees; q is the number of units built; recurring cost is the parts and assembly cost per unit in rupees.

At q = 200, an SoC (system on chip) with NRE ₹5,00,000 and recurring ₹300 costs 500000/200 + 300 = ₹2,800. At q = 2,000 the same design costs ₹550. The recurring cost did not change; the NRE share fell. An FPGA (field-programmable gate array) design with NRE ₹1,00,000 and recurring ₹800 costs ₹1,300 at 200 units and ₹850 at 2,000. The two lines cross at 800 units: below that the FPGA wins, above it the SoC wins.

Speed, energy and the other metrics

Performance is not one number. Throughput is work done per second, in operations per second. Latency is the time from an input to the matching output, in milliseconds (ms) or microseconds (µs). Deadline margin is the spare time before a required deadline; a margin of zero passes only if nothing goes wrong.

P = C·V²·f

P is dynamic power in watts; C is the switched capacitance in farads; V is the supply voltage in volts; f is the clock frequency in hertz.

Static power is leakage, drawn even when the clock is stopped. Energy is power multiplied by time; battery life = energy available / average power. Size and weight matter in a wearable or a drone. Flexibility is how easily the function changes in the field. Reliability is the chance of working for a stated time. Safety is doing no harm when it fails. Security is resisting an attacker. Maintainability is the cost of diagnosis and repair. Correctness is doing the specified job for every allowed input. Each metric has a unit; a claim without a unit is not a specification.

Design challenges and the trade-off rule

The first design challenge is the hardware-software split: which functions go in fixed hardware, which in software on a processor. Fixed hardware is fast and low power but cannot change; software is flexible but slower. The second is meeting deadlines with the cheapest legal part: a part that is fast enough but has little flash or RAM is not legal. Code must fit in flash memory and data in RAM, with room for later fixes. A battery device needs a power budget: sum the current of every block, multiply by voltage to get total watts, then multiply the average watts by the required run time to get energy in watt-hours and compare that with the battery's energy rating. Choosing a processor before good compilers exist is a real risk; check that a compiler, debugger and libraries are available before committing. Testing a board with no screen or keyboard needs a debug port, a test fixture or boundary scan. Field firmware upgrade needs a bootloader and a safe recovery path if power fails during the update. Safety and security add verification cost.

Of cost, performance and power you can usually improve two at the expense of the third. A faster clock raises throughput and power. A cheaper part may miss a deadline. Rising IC design cost makes platform choice a business decision: a high-NRE chip is sensible only if the volume is large enough to spread it.

Worked example

Question. Design A uses an SoC: NRE ₹5,00,000, recurring cost ₹300 per unit. Design B uses an FPGA: NRE ₹1,00,000, recurring cost ₹800 per unit. (a) Find the unit cost of each at 200 units. (b) Find the unit cost of each at 2,000 units. (c) Find the quantity at which they are equal.

  1. Unit cost formula: unit cost = NRE/q + recurring cost.
  2. At q = 200 units: Design A = 500000/200 + 300 = 2500 + 300 = ₹2,800. Design B = 100000/200 + 800 = 500 + 800 = ₹1,300. B is cheaper by ₹1,500.
  3. At q = 2,000 units: Design A = 500000/2000 + 300 = 250 + 300 = ₹550. Design B = 100000/2000 + 800 = 50 + 800 = ₹850. A is cheaper by ₹300.
  4. Equal-cost quantity: 500000/q + 300 = 100000/q + 800. Subtract 300: 500000/q = 100000/q + 500. Subtract 100000/q: 400000/q = 500. q = 400000/500 = 800 units.

Answer. At 200 units the FPGA costs ₹1,300 per unit against ₹2,800 for the SoC; at 2,000 units the SoC costs ₹550 against ₹850; the two are equal at 800 units, so build on the FPGA below 800 units and on the SoC above 800 units.

Exam traps

  • Forgetting to divide NRE by quantity and treating it as a per-unit cost; NRE is paid once, so at quantity q its share is NRE/q.
  • Comparing unit costs at different quantities, or at quantity 1; the fair comparison is at the same q.
  • Mixing power and energy: P = C·V²·f is power in watts; battery life uses energy, so divide available energy by average power.
  • Using throughput as latency: throughput counts operations per second, latency is the delay of one operation from input to output.
  • Assuming a lower recurring cost always wins; at low volume a higher-NRE design can cost far more per unit.

1.4 Hardware and software architecture of embedded systems

An embedded system is a hardware platform plus a layered software stack. The hardware executes instructions and touches sensors and actuators; the software decides what to do. Where you draw the line between them is a design decision: a checksum can be a software loop or a hardware block. The usual stack is hardware, device drivers, middleware and application software. Each layer talks only to the layer below through a defined interface. This structure appears in a smart electricity meter, a washing machine and a car engine controller. It lets you change one layer without rewriting the rest.

You need Chapter 1.1 for what an embedded system is, and Chapter 1.3 for the metrics the architecture must meet.

Hardware architecture

Hardware architecture is the set of physical blocks that execute instructions and touch the outside world. The processor core fetches and executes instructions. Program memory is usually flash: it keeps code when power is off. Data memory is SRAM: it holds variables and the stack while the program runs. A clock oscillator supplies the timing square wave; without it the core does not step. The reset circuit puts the processor into a known start state. The power supply converts the input to a regulated rail, and brown-out detection holds the processor in reset when the rail sags below a safe value. Peripherals are on-chip helpers: timers count time and generate waveforms, UART shifts bits for serial links, ADC converts an analogue sensor voltage to a number, and GPIO pins are general-purpose digital inputs and outputs. An internal bus carries addresses, data and control signals between the core, memories and peripherals. Outside the chip sit sensors, actuators and connectors. A classic microprocessor such as the 8086 brings out address, data and control buses as pins; a microcontroller keeps the same blocks inside one package.

  • Power-on reset: the supply has just risen.
  • External reset: a button is pressed.
  • Watchdog reset: software failed to service the watchdog.
  • Brown-out reset: the supply dipped below a safe level.

A pull-up resistor holds a line at logic high when nothing drives it. A pull-down holds it at logic low. A high-Z (floating) pin is not a logic level at all. Unused inputs get a pull-up or pull-down so they never float. Unit 3 and Unit 5 cover reset timing and watchdog use in detail.

Software architecture

Software architecture is a stack of layers. At the bottom is the hardware. The first software layer is the device drivers. They write and read hardware registers: set a GPIO pin high, load a timer count, read a UART data register. They hide register addresses from the rest of the code. Drivers are usually packaged with startup code and clock and memory initialisation as a board support package (BSP). Above the drivers is middleware: an RTOS or scheduler that decides which task runs next, protocol stacks such as a meter-reading protocol, a file system, and maths or graphics libraries. These are reusable services, not the product's own logic. At the top is application software, which holds the product's decisions: when to close a relay, how to compute a bill, what to show on the LCD. Communication software can sit side by side with application software above middleware: it moves bytes to a modem or a network, while the application decides what those bytes mean.

The rule is: a layer talks only to the layer below, through a defined interface. The application calls a middleware function; middleware calls a driver function; the driver writes a register. No layer reaches across. This lets you change the MCU and rewrite only the BSP.

Drawing the line and the tools

Where the hardware-software line falls is a design decision. A cyclic redundancy check (CRC) can be a software loop or a hardware block. Hardware is faster and uses less CPU time; software is cheaper to change and needs no extra silicon. Fixed, heavy, repeated work goes to hardware; changing policy stays in software. This partition is called hardware-software co-design; Unit 6 takes it further.

  • An IDE is the editor, project manager and debugger in one window.
  • A compiler translates C into the target instruction set; a cross-compiler runs on a PC but produces code for the MCU.
  • A simulator runs the program on the PC with a model of the MCU, so no board is needed.
  • An emulator or in-circuit debugger probes the real MCU and lets you stop at a breakpoint and read registers.
  • MCU internals — memory map, special function registers and interrupt vectors — are what the compiler and debugger must know.

Worked example

Question. A smart electricity meter is built from an energy-measurement IC, a 32-bit MCU with 64 KB flash and 8 KB SRAM, a real-time clock, an LCD, an IR port, a UART to a modem, and a push button. (b) Assign the software layers. (c) Find the current through the pull-up and the power it wastes while the button is pressed.

The MCU also contains the processor core, 64 KB flash and 8 KB SRAM. The LCD, IR port, modem, push button and 10 kΩ pull-up connect to the MCU. The clock oscillator, reset circuit and 3.3 V supply feed the MCU.
  2. Software application layer: tariff and billing logic. It decides the price per unit and the bill.
  3. Software middleware layer: the meter-reading protocol and RTC-based scheduling. These are reusable services above the drivers.
  4. Software BSP layer: drivers for the measurement IC, UART, LCD and IR port. These read and write registers.
  5. Button open: no current flows through the 10 kΩ resistor, so the input is held at 3.3 V, logic high. Button pressed: the input is 0 V and the resistor has 3.3 V across it.

Exam traps

  • Calling the RTOS 'the application'. The RTOS is middleware; the application holds the billing, control or display logic.
  • Drawing a hardware block diagram with no clock, reset and power block. A processor without these three does not run.
  • Saying a pull-up sets a line to logic low. A pull-up sets logic high; a pull-down sets logic low.
  • Treating high-Z as a third logic level. It is no level, so unused inputs need a pull-up or pull-down.
  • Writing that application software writes registers directly. It calls middleware or a driver through a defined interface.

1.5 Processor choices: microprocessor, microcontroller, DSP, SoC

Two systems can do the same job with chips from different families. The processor is chosen by the pattern of arithmetic the workload repeats, by how much memory it needs, by the power budget and by how many boards you will build. A microprocessor is a CPU alone and needs chips around it. A microcontroller is a whole small computer on one die. A DSP is shaped for multiply-accumulate. An SoC puts a complete system, radio included, on one die. This chapter shows which one fits which workload.

You need the hardware blocks from chapter 1.4 and the cost, power and time-to-market metrics from chapter 1.3.

Microprocessor and microcontroller

A microprocessor is a CPU on its own chip. Its address bus, data bus and control lines come out on pins, so RAM, ROM, timers and I/O ports must be separate chips wired to it. The 8086 is the classic teaching example; an ARM Cortex-A in a phone is the modern one. The board is bigger and costs more, but you are free to attach any amount of DRAM, any flash and any peripheral chip.

A microcontroller (MCU) puts the CPU, flash program memory, SRAM, timers, serial ports, an ADC and GPIO on one die. A complete system then needs no extra chips beyond a crystal and a few passives. The 8051, PIC16 and ARM Cortex-M are the standard families.

Why the MCU exists: fewer chips means a smaller board, lower cost, lower power, fewer solder joints to fail, and predictable timing because program and data memory sit on-chip. The price is fixed supply. You get the flash and RAM the part was built with, and the peripherals it was built with, and nothing more.

  • Pick a microprocessor when the job needs an operating system, megabytes of DRAM, a display, or heavy general computing.
  • Pick a microcontroller when the job is sensors, keys, motors and control loops at kilohertz to low megahertz rates.
  • Memory sizing for either choice is covered in chapter 1.7.

DSP: a processor shaped for multiply-accumulate

Audio, video, motor control, radar and biomedical signals all run the same sum: y[n] = Σ h[k] · x[n − k], for k = 0 to N − 1. Each output sample needs N MAC operations. A MAC is one multiply plus one add; it counts as one MAC but two arithmetic operations.

A general CPU spends several cycles and several instructions per MAC. A DSP is built to do one MAC per cycle, using these blocks:

  • A hardware MAC unit that computes a × b + c in a single cycle.
  • Separate program and data buses (Harvard organisation, see chapter 1.6) so an instruction and its two operands arrive in the same cycle.
  • A barrel shifter that scales a value by any number of bits in one cycle.
  • Saturating arithmetic: an overflow clips to the largest value instead of wrapping round. A wrapped audio sample is heard as a loud click.
  • Address generators that update circular-buffer pointers with no extra instruction, plus zero-overhead loops for the filter inner loop.

A digital signal controller (DSC) is an MCU with DSP features added: a MAC unit and DSP addressing modes on a flash microcontroller that also has ADC and PWM. Motor control drives use them, because the same chip runs the control loop and the fast current loop.

SoC, ASIC and FPGA: the whole system on one die

A SoC (system on chip) holds a complete system on one die: one or more CPU cores, a GPU, a DRAM controller, a radio for Wi-Fi or Bluetooth, an audio codec, USB, and camera interfaces. A phone processor is the standard case. Short on-chip wires give high speed at low energy per operation, but nothing can be changed after the chip is manufactured.

Two production routes exist for a custom SoC. An ASIC fixes the design in silicon: the mask set costs a large one-time payment called NRE (non-recurring engineering), but the cost per chip is very low once volume is high. An FPGA is logic configured after manufacture: no mask cost, so NRE is essentially zero and time-to-market is short, but each board costs more and burns more power. High volume and low power point to ASIC; small volume and changing requirements point to FPGA or a ready-made module.

Worked example

Question. An audio filter computes a 256-tap FIR filter at a sampling rate of 48 kHz. (a) How many multiply-accumulate operations per second does it need? (b) Can a 30 MHz MCU with no hardware MAC run it if each MAC costs 4 cycles? (c) What minimum DSP clock speed is needed at 1 MAC per cycle?

  1. One output sample needs one MAC per tap, so 256 MACs per sample.
  2. The filter produces 48,000 samples per second (48 kHz = 48,000 samples/s).
  3. Required rate = 256 × 48,000 = 12,288,000 MAC/s, that is about 12.288 M MAC/s.
  4. On the MCU, each MAC takes 4 cycles, so the cycles needed = 12,288,000 × 4 = 49,152,000 cycles/s, which is a 49.152 MHz clock.
  5. The MCU runs at 30 MHz = 30,000,000 cycles/s. MACs it can do = 30,000,000 ÷ 4 = 7,500,000 MAC/s = 7.5 M MAC/s.
  6. 7.5 M MAC/s is less than the 12.288 M MAC/s required, so the 30 MHz MCU cannot keep up; it supplies only 7.5 ÷ 12.288 ≈ 0.61 of the load.
  7. A DSP does 1 MAC per cycle, so its clock must be at least 12.288 MHz. Pick 25 MHz to leave margin for loading samples, storing output and the rest of the code.

Answer. The filter needs 12,288,000 MAC/s (about 12.288 M MAC/s); the 30 MHz MCU manages only 7.5 M MAC/s and is too slow (it would need 49.152 MHz); a DSP clocked at 12.288 MHz or more, for example 25 MHz, can run it.

Exam traps

  • Comparing a DSP and an MCU on MIPS alone. A DSP does one MAC per cycle in hardware; an MCU needs several cycles and several instructions per MAC. Convert both to MMAC/s before you compare.
  • Calling a microcontroller a small microprocessor. A microprocessor is a CPU with no memory; a microcontroller is a complete system with memory and peripherals on the die.
  • Forgetting that one MAC is two arithmetic operations (one multiply, one add). A 12.288 M MAC/s filter is doing about 24.6 million arithmetic operations per second, which is why the FLOPs figure looks twice as large.
  • Confusing MHz with M MAC/s. MHz is millions of cycles per second. M MAC/s = MHz ÷ cycles per MAC, so a 4-cycle MAC at 100 MHz gives 25 M MAC/s, not 100.
  • Quoting only the ASIC cost per chip and ignoring NRE. At low volume the NRE spread over few boards makes the ASIC far more expensive than an FPGA, even though each ASIC die costs less.

1.6 RISC vs CISC; Harvard vs von Neumann

Every processor answers two separate questions. How much work can one instruction do — is it RISC or CISC? And do instructions and data travel over the same path — von Neumann or Harvard? The first choice sets decode logic, code size and pipeline friendliness. The second sets whether an instruction fetch and a data read can share a clock cycle. Picking either badly costs speed, silicon area or pins. All four combinations ship in real chips: the 8086 is CISC with one bus, the 8051 is CISC with Harvard memory, and most ARM microcontrollers are RISC with Harvard buses.

You need Chapter 1.5 — the terms microprocessor, microcontroller and DSP mean little until you can see which instruction set and which memory layout each one uses.

Instruction set style: RISC and CISC

An instruction set is the list of operations a CPU can be told to do. Two styles dominate.

CISC (Complex Instruction Set Computer) makes each instruction do a lot. Instruction length varies, from one to six bytes on the 8086. There are many addressing modes, and arithmetic can take a memory operand directly, as in ADD [2000h], AX. Control is microcoded: one instruction is broken into several small internal steps. A line of C becomes few instructions, so code stays compact — valuable when flash is small and costly. The 8086 and the 8051 are CISC.

RISC (Reduced Instruction Set Computer) makes each instruction do one small thing. All instructions have the same length, usually 4 bytes on a 32-bit core. The load-store rule says only LOAD and STORE touch memory; arithmetic works on registers only. Many general registers, 16 or 32, keep operands on chip. Most instructions finish in one clock, so a pipeline can start a new instruction every cycle. The price is more instructions per line of C: a = b + c becomes load b, load c, add, store a. ARM, MIPS and RISC-V are RISC.

Memory organisation: von Neumann and Harvard

von Neumann. One memory holds both instructions and data, reached through one set of address, data and control lines. The CPU fetches an instruction, then reads or writes a variable: same wires, one job at a time. It is simple and cheap, one memory chip and one bus. Code and data share one address space, so a program can treat code as data — read a constant table held with the instructions, or patch its own instructions. The cost is time. While the bus fetches an instruction it cannot carry a data word, so the CPU waits. That limit is the von Neumann bottleneck. The 8086 uses this organisation.

Harvard. Program memory (flash, instructions only) and data memory (RAM, variables and stack) are separate, each with its own buses and address space. A fetch from flash and a read of a variable happen in the same clock cycle, so bandwidth doubles at the same clock. The price is more pins and wires, more silicon, and two address spaces — reading a table stored in flash needs a special instruction. Almost every microcontroller (8051, PIC, AVR) uses Harvard, and so do most DSPs, because a DSP inner loop wants one instruction fetch and two operand reads in every cycle.

Modified Harvard. One main memory, but separate instruction and data caches next to the CPU, so the core still fetches and loads in the same cycle. ARM Cortex-A application processors work this way.

The two choices are independent

The RISC/CISC question is about how an instruction is encoded and decoded. The Harvard/von Neumann question is about where instructions and data live and how many buses serve them. Nothing links the two answers. All four combinations ship:

  • CISC with von Neumann: the 8086.
  • CISC with Harvard: the 8051, microcoded variable-length instructions over separate program and data memory.
  • RISC with Harvard: ARM Cortex-M microcontrollers.
  • RISC with von Neumann: small RISC-V cores placed in an FPGA with one shared memory.

One sentence proves the independence: the 8051 is CISC with Harvard memory, so neither label can imply the other.

Read a datasheet this way. If the instructions are mostly a fixed four bytes, the core is probably RISC — though some RISC cores such as ARM Thumb-2 mix 16-bit and 32-bit encodings. If code and variables sit at different address ranges with different bus widths, the memory is Harvard. Then check what actually sets speed: clock frequency, pipeline depth, bus width and flash wait states. A 100 MHz RISC core that spends five cycles on every flash access (one transfer plus four wait states) delivers 20 million instructions per second, the same as a 20 MHz CISC core with single-cycle fetch. Design metrics decide which trade you want.

Worked example

Question. A microcontroller CPU runs from a 20 MHz bus clock, and every 16-bit transfer on a bus takes exactly one bus cycle. (a) What is one bus cycle time? (b) On a von Neumann machine, how long does it take to fetch a 16-bit instruction and then read a 16-bit operand from memory? (c) How long on a Harvard machine with two independent 20 MHz buses? (d) What is the speedup, and how many such instruction-plus-operand pairs can each machine complete per second?

  1. Bus cycle time T = 1 / f = 1 / (20 × 10⁶ Hz) = 50 × 10⁻⁹ s = 50 ns.
  2. von Neumann: the fetch and the operand read share one bus, so they run one after the other: 50 ns + 50 ns = 100 ns per pair.
  3. von Neumann throughput = 1 / (100 ns) = 10 × 10⁶ = 10 million pairs per second.
  4. Harvard: the fetch goes out on the instruction bus while the operand read goes out on the data bus in the same cycle, so the pair takes max(50 ns, 50 ns) = 50 ns.
  5. Harvard throughput = 1 / (50 ns) = 20 × 10⁶ = 20 million pairs per second.
  6. Speedup = 100 ns ÷ 50 ns = 2.

Answer. One bus cycle is 50 ns; the instruction-plus-operand pair takes 100 ns on von Neumann and 50 ns on Harvard, a speedup of 2×, giving 10 million and 20 million pairs per second.

Exam traps

  • Saying RISC means Harvard and CISC means von Neumann. The 8051 is CISC with Harvard memory, and ARM Cortex-M is RISC with Harvard buses. The choices are independent.
  • Saying CISC is slow and RISC is fast. Clock frequency, pipeline depth, bus width and memory wait states decide speed; a RISC core waiting on slow flash loses to a simple CISC core.
  • Reading Harvard as 'twice the memory'. Harvard means two address spaces and two buses, not double capacity — a Harvard microcontroller usually has far less RAM than flash.
  • Saying modified Harvard has two main memories. It has one main memory with separate instruction and data caches close to the core.
  • Unit slips in bus timing: at 20 MHz one cycle is 1 ÷ (20 × 10⁶) = 50 ns, not 20 ns and not 20 µs.

1.7 Embedded memory: ROM, flash, SRAM, DRAM

Memory in an embedded system is not one big pool. It is a set of technologies placed where each fits: ROM (read-only memory) or flash for code that must survive power-off, SRAM (static random-access memory) for fast working data, DRAM (dynamic random-access memory) for large cheap working data, and NAND flash or an SD card for bulk storage. Four questions decide the choice: volatile or not, writable in the field or not, how fast, and how many bits per rupee. The answers show up as fixed addresses in the memory map, and that map is what the processor sees at reset.

You need Chapter 1.4 for the hardware block diagram and Chapter 1.6 for separate program and data memories.

Volatile memory and the ROM family

Volatile memory loses its contents when power is removed. SRAM and DRAM are volatile. Non-volatile memory keeps its contents without power. ROM and flash are non-volatile. The ROM family is read-mostly: mask ROM is programmed at the factory with a fixed pattern and is cheapest at high volume. PROM (programmable ROM) is programmed once by the user. EPROM (erasable PROM) is programmed electrically and erased by ultraviolet light through a quartz window; it is slow to erase and now rare. EEPROM (electrically erasable PROM) is erased and written electrically, byte by byte, and has limited endurance. OTP (one-time programmable) behaves like PROM inside a cheap package. Endurance is the number of erase/write cycles a cell or block survives before it may fail. Mask ROM has no field writes, so endurance does not apply. EEPROM may endure about 10⁵ to 10⁶ byte writes. ROM and flash hold the program because it must start after a power cut.

Flash: NOR, NAND and wear

Flash is EEPROM-like but erased in blocks or sectors, not byte by byte. A write is erase-then-program. You cannot overwrite one byte in the middle of a block. NOR flash allows random access and execute-in-place (XiP), so a processor fetches instructions directly from it; it holds code. NAND flash is page-addressed: reads and writes use pages, erases use larger blocks. It is denser and cheaper per bit than NOR, so it holds bulk data. NAND needs bad-block management and a file system or flash translation layer. Endurance is typically 10⁴ to 10⁵ erase cycles per block. That rules out logging every millisecond into on-chip flash: 1000 writes/s would wear a 10⁴-cycle block in about 10 s. Buffer logs in RAM, batch them, or use an SD card.

SRAM, DRAM and the memory map

SRAM stores one bit in a six-transistor cell. It holds data while powered, needs no refresh, and is fast, but it uses many transistors per bit, so density is low and cost per bit high. It is used for registers, on-chip RAM, and caches. DRAM stores one bit as charge on a capacitor with one access transistor. The capacitor leaks, so every row must be refreshed (read and rewritten). DRAM is dense and cheap per bit, slower than SRAM, and used as main memory. SDRAM (synchronous DRAM) is clocked with the bus; DDR (double data rate) SDRAM transfers on both clock edges. A typical microcontroller (MCU) memory map puts flash at address 0 because the reset vector (the first instruction address after reset) lives there. On-chip SRAM sits above it. Peripheral registers (control and data registers for timers, ports, and so on) sit at fixed addresses. The processor fetches code from flash, keeps variables and stack in SRAM, puts large frame buffers in DRAM, and keeps logs and firmware images in NAND or an SD card.

Choosing memory by four questions

Ask four questions in order. First, must the data survive power-off? If yes, choose ROM, flash, EEPROM, NAND, or an SD card; if no, SRAM or DRAM. Second, must it be written in the field? Mask ROM and OTP cannot; flash and EEPROM can, with block or byte granularity. Third, how fast? Registers and SRAM answer in one cycle; DRAM is slower; NOR flash reads fast but erase and program are slow. Fourth, how many bits per rupee? SRAM is costliest, DRAM cheaper, NAND cheapest per bit. The rule: code in flash, variables and stack in SRAM, large frame buffers in DRAM, logs and firmware images in NAND or an SD card. A small MCU with 64 KB flash and 8 KB SRAM cannot hold an 8-hour millisecond log.

Worked example

Question. A battery-powered data logger has 12 KB of program code and 1 KB of constant lookup tables. It samples a sensor every 1 ms, 4 bytes per sample, and must keep 8 hours of samples while powered off. Its MCU has 64 KB flash and 8 KB SRAM. (a) How much flash is needed for code and tables? (b) How many bytes are produced in 8 hours? (c) Can the whole log live in on-chip memory? Explain.

  1. Flash for code and tables = 12 KB + 1 KB = 13 KB. The 64 KB flash is enough; 51 KB remains free.
  2. Sample rate = 1 sample per 1 ms = 1000 samples/s.
  3. 8 hours in seconds = 8 × 3600 s = 28,800 s.
  4. Samples = 1000 samples/s × 28,800 s = 28,800,000 samples.
  5. Bytes = 28,800,000 samples × 4 bytes/sample = 115,200,000 bytes.
  6. In decimal MB = 115,200,000 ÷ 1,000,000 = 115.2 MB. In MiB (1 MiB = 1,048,576 bytes) = 115,200,000 ÷ 1,048,576 = 109.86 MiB, about 110 MiB.
  7. 8 KB SRAM = 8192 bytes; 8192 ÷ 4 = 2048 samples, about 2.048 s at 1 ms. The 64 KB flash holds 65,536 ÷ 4 = 16,384 samples, about 16.4 s, and repeated writes wear the block. The log needs NAND flash or an SD card.

  • Flash is not byte-writable like EEPROM: erase the whole block, then program it.
  • SRAM is volatile even though it needs no refresh; DRAM is volatile and needs refresh.
  • EPROM is erased by ultraviolet light; EEPROM is erased electrically, byte by byte.
  • NOR and NAND are both flash but not interchangeable: NOR for execute-in-place code, NAND for bulk data with bad-block management.
  • KB and KiB differ: 115,200,000 bytes is 115.2 MB but 109.86 MiB.

Check yourself

Remember What does volatile mean? Name two volatile memory types. 2 marks

Contents vanish when power is removed. SRAM and DRAM are volatile.

Remember Which ROM type is erased by ultraviolet light? 2 marks

EPROM.

Understand Why must flash be erased in blocks before programming? What does that mean for changing one byte? 4 marks

Erase sets a block to 1s, then program writes 0s. Changing one byte requires copying the block, erasing, and rewriting it.

Apply A NOR flash block has endurance 10⁴ erase cycles. A logger erases one block every 2 s. How long until 10⁴ cycles? 4 marks

10⁴ × 2 s = 20,000 s = 5.56 h.

Apply An MCU has 32 KB flash and 4 KB SRAM. Code is 20 KB and constants 2 KB. Free flash? Can a 100 KB log fit on-chip? 4 marks

Free flash = 32 − (20 + 2) = 10 KB. No, 100 KB log does not fit; use external NAND or SD.

Analyze Why do many MCUs put flash at address 0 and the stack in SRAM? 6 marks

The reset vector is at address 0 and must be non-volatile; flash keeps it without power. The stack changes constantly, so it needs fast writable SRAM, not flash.

Analyze Give two reasons NAND flash is a poor choice for execute-in-place code. 6 marks

NAND is page-addressed, not random-access byte addressable, so fetch is slow and complex. It has bad blocks and needs a translation layer, so direct execution is unreliable.

Understand Why does DRAM need refresh but SRAM not? 3 marks

DRAM stores charge on a capacitor that leaks. SRAM uses cross-coupled transistors that hold state while powered.

Beyond the syllabus

Not for the exam. Modern MCUs often use embedded flash with ECC and store firmware images in external QSPI NOR or eMMC. Wear levelling and flash translation layers spread erase cycles so an SD card survives logs. Universal Flash Storage (UFS) and eMMC are common in phones and automotive clusters. Emerging non-volatile memories such as MRAM and ReRAM aim to combine SRAM speed with flash non-volatility. Takeaways

  1. An embedded system is a dedicated computer inside a product, shaped by real-time limits and constrained resources.
  2. Sorting by complexity, timing and form or connectivity gives a useful classification without making one axis better than another.
  3. Design metrics such as cost, power, size, speed, reliability and time-to-market compete, so each choice is a trade-off.
  4. The hardware platform and layered software stack must be designed together, with a deliberate hardware-software boundary.
  5. Processor choice follows the workload: microprocessor for general computing, microcontroller for control with integrated peripherals, DSP for signal arithmetic, SoC for integration.
  6. RISC versus CISC and Harvard versus von Neumann are separate choices that affect instruction throughput, memory traffic and cost.
  7. Memory selection is driven by volatility, field writability, speed and bits per rupee, and each type has a fixed role in the memory map.
  8. Good answers connect definitions and block diagrams to a concrete small system: sensors, signal conditioning, processor, memory, communication and actuators.

Glossary

Actuator
A device that converts an electrical control signal into physical action such as motion, heat or light.
ASIC
Application-specific integrated circuit fixed for one function, with high one-time design cost and low unit cost at volume.
CISC
Complex instruction set computer with many complex, often variable-length instructions.
DMA
Direct memory access, a controller that moves data without the CPU handling every byte.
DSP
A processor optimised for repeated multiply-accumulate operations on digitised signals.
Edge AI
Running machine-learning inference locally on the device, close to the sensor.
EPROM
Erasable programmable read-only memory erased by ultraviolet light and rewritten offline.
Firmware
Program stored in non-volatile memory that controls the embedded hardware.
Flash memory
Non-volatile, electrically erasable and field-writable memory for code and data.
FPGA
Field-programmable gate array whose digital logic is configured after manufacture.
Harvard architecture
A memory organisation with separate instruction and data memories and paths.
High-Z
A high-impedance output state that disconnects a pin from the bus so another device can drive it.
Interrupt
An asynchronous signal that makes the processor jump to a service routine.
Microcontroller
A single chip with processor, memory and peripherals for control applications.
Microprocessor
A processor chip that needs external memory and peripherals to form a system.
Modified Harvard
A memory organisation with separate instruction and data caches or paths but one unified address space.
NRE
Non-recurring engineering cost, the one-time cost of designing and tooling a chip.
Pull-down
A resistor tying an input to ground when nothing else drives it.
Pull-up
A resistor tying an input to supply voltage when nothing else drives it.
Reset
A hardware event that puts the processor into a known start state.
SDRAM
Synchronous dynamic RAM clocked with the bus for high-density volatile storage.
Sensor
A device that converts a physical quantity into an electrical signal.
SoC
System on chip integrating processor, memory, peripherals and interfaces on one die.
SRAM
Static RAM built from flip-flops, fast and volatile, used for caches and small data.
Timer
A counter peripheral that measures time or generates periodic events.
von Neumann architecture
A memory organisation that stores instructions and data in one memory with shared address and data paths.
