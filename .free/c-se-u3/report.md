## Reviewer notes (after any revision)

- ch 1 [low] Worked example 1, step 1: "Availability ... is a dependability attribute (reliability in service)" blurs two separate ideas that the chapter's own table lists side by side under dependability. Availability is the fraction of time the system is up; reliability is the chance it runs without failing for a stated period. A student can read the bracket and use the words as synonyms in an answer.
- ch 1 [low] Figure caption: It says architectural design is picked out because "the next chapter builds on it", but Section 3 points architectural styles to 3.3 while the next chapter (3.2) is the modular/object-oriented design material. The caption and the cross-references disagree.
- ch 1 [low] Lead and Section 2, first paragraph: "Every design decision buys one attribute and costs another" is put as a law. Some decisions are neutral or improve two attributes at once; the useful rule is that a reviewer must look for the trade-off, not assume exactly one of each.
- ch 2 [high] Quiz Q3: The answer says the class has coincidental cohesion, score 1. But the four jobs form a pipeline: rows read from the CSV are the input to validation, the validated rows are what gets written to the two tables, and the report is mailed from what was written. The parts share data and run in a fixed order, so this is not the 'bundled by accident' case of the worked example. Under the chapter's own table, coincidental (1) is the wrong level.
- ch 2 [low] Worked example 1, step 9 / answer: The suggested fix passes a multi-field Bill DTO. A record with several fields is still a record, so strictly the coupling stays stamp coupling; the quiz answer to Q4 fixes the same defect by passing one simple item, which reaches data coupling. The two answers pull in different directions.
- ch 2 [low] Section 4, list of well-designed class properties: The gloss for 'primitive' is not the standard meaning. In the usual class-design guidelines, primitive operations are operations that are simple to implement because they have direct access to the class's underlying data; 'each operation does one small thing' describes small, focused operations instead, and a student repeating it in an exam will lose the mark.
- ch 2 [low] Figure caption: 'Each stop down the tree is one round of stepwise refinement' — 'stop' should be 'step'; as written it reads as if the tree stops there.
- ch 3 [high] Worked example 1, step 3 and answer: The example conflates capacity with throughput. It computes 1 ÷ 0.006 s = 166.7 records/s, then admits the arrival rate is only 100/s and the queue does not grow — but still reports throughput as 166.7 records/s. In steady state the pipeline leaves at the arrival rate, so the actual throughput is 100 records/s. 166.7 is the maximum capacity, not the throughput. As written, step 3 contradicts its own sentence.
- ch 3 [high] Quiz Q4: Same capacity-versus-throughput error. The answer says throughput = 1 ÷ 0.010 = 100 records/s while also noting arrivals are 80/s. If arrivals are 80/s and capacity is 100/s, the steady-state throughput is 80 records/s; 100/s is only the capacity.
- ch 3 [low] Exam traps, second bullet: "the slowest stage divided by the number of parallel copies" is garbled and gives the wrong quantity (a time divided by a count is not a rate).
- ch 3 [low] Quiz Q7 answer: It lists "sometimes network hops" as a cost of a layer boundary, but layers are logical; network hops appear only when layers are split across tiers. This repeats the layer/tier confusion the chapter warns against in trap 1.
- ch 3 [low] Section 3, case study grouping: The database is listed as one of the four layers, but the chapter defines a layer as a logical group of code. A database is stored data, not code, and later the same paragraph places it as the data tier, which reads as inconsistent counting (four layers, three tiers).
- ch 3 [low] Worked example 1, step 4: The 12 ms answer is the sum of service times, which is the latency only when the record passes through an empty pipeline. Under real arrivals there is queueing in front of the slow stage, so a student may think 12 ms always holds.
- ch 3 [low] Lead and Section 1: The sentence defining software architecture appears twice, almost word for word ("early, large decisions about a system: its main parts, how those parts...").
- ch 4 [high] Section 1, last paragraph: The framework definition is reversed. Saying 'a framework is code you call' contradicts the standard library-versus-framework distinction, where the framework calls your code (inversion of control, 'don't call us, we'll call you'). Code you call is a library.
- ch 4 [low] Section 2, observer paragraph: 'Each observer calls attach(subject)' is ambiguous and reads the wrong way round: attach is a method on the subject, and the observer passes itself.
- ch 4 [low] Quiz Q5: The value 19,999 is correct in rupees-to-paise arithmetic, but the recipe given in Section 3 (multiply by 100, then convert to int) gives 19,998 in Java/C# because 199.99 is not exactly representable as a double (199.99 × 100 = 19998.999999999996). A student who follows the recipe literally gets a wrong paise value.
- ch 4 [low] Beyond section: Spring's JdbcTemplate is standardly cited as an example of the Template Method pattern, not of facade; listing it beside InputStreamReader under 'adapter and facade' muddles the classification.
- ch 5 [low] Quiz Q7: The answer says consistency is broken twice and treats 'eight buttons of the same colour and size' as a consistency fault. Identical-looking buttons for different actions are a lack of visual hierarchy, not a violation of 'the same thing looks and behaves the same everywhere'; only the 'Save'/'Update' clash actually breaks the consistency rule. A student repeating 'visual weight = consistency' would lose marks.
- ch 5 [low] Figure caption: The caption says 'evaluation is a step inside design, not something done after it', but Section 2 describes design first, then evaluation, with the loop returning to design. The two statements pull in opposite directions and can confuse a student about the order of steps.
- ch 5 [low] Section 3, scroll bar row: 'Below the fold' is print and web jargon; inside a resizable window there is no fold, so the rule reads oddly.
- ch 6 [high] Worked example 1, step 2 and step 6: The multiplicities contradict the requirement text and each other. The question says 'A customer holds one or more accounts', but step 2 writes 'One customer may hold 0..* accounts'. The joint-account rule is then turned into a multiplicity of 2..* at the Customer end, which would mean every account, including an ordinary single-holder account, has at least two holders. Step 6 is worse: it lists 'Customer 1 .. 0..* Account' and 'Account 2..* .. 1..* Customer' for the same association, and the second expression is written in the reverse order to the chapter's own near..far convention (it reads as each customer having 2..* accounts).
- ch 6 [high] Quiz Q3: The question asks for the multiplicity on the Account end (how many accounts one customer may hold), but the answer gives 'Account end: 2..* customers', which is the Customer-end multiplicity, and a wrong value at that. The second sentence of the answer then gives the Account-end value (1..* or 0..*), so the answer contradicts itself.
- ch 6 [high] Worked example 1, steps 3 and 4: 'Account 1..1 Branch' and 'Transaction 1..1 Account' read under the chapter's own near..far convention (near multiplicity .. far multiplicity) say that each branch has exactly one account and each account has exactly one transaction. Both are false and they clash with the correct expressions written just before them.
- ch 6 [high] Figure, Order–Payment edge: The edge is drawn dashed. In UML a dashed line is a dependency, but the caption and the label 1 .. 0..1 describe a lasting association ('an order may have one payment'). A student copying this figure will draw a dependency where an association is meant.
- ch 6 [high] Figure, OrderLine–Item edge: The label '1..* .. 1' puts 1..* at the OrderLine end, which says every item is referenced by at least one order line. An item may sit in the catalogue with no orders at all.
- ch 6 [high] Beyond: 'UML 2.5 notation adds association classes and qualified associations' is wrong. Both have been part of UML since the 1.x versions; they are not additions of UML 2.5.
- ch 6 [low] Quiz Q7: The answer names a 'collaboration diagram'. That is the UML 1.x name; UML 2 calls it a communication diagram. Students writing the old name in an exam may lose marks.
- ch 6 [low] Worked example 1, step 6: The answer announces 'the four multiplicity expressions' for what are only three associations, and it never states the Branch and Transaction end values as part of the final answer.
- ch 7 [high] Section 3, Worked example steps 3–4, Quiz Q4 and Q5: Returns are given their own deeper numbers (1.1.1 for the PIN reply, 2.1.1 for the approval). This makes a return look like a call nested inside the call it answers. A student copying this numbering will show a return as a new nested call in the exam.

- ch 7 [low] Section 3, third bullet of the steps list: The bullet starts as a numbering rule but ends with 'To go back, read the numbers in order and draw the arrows top to bottom', which is about converting a collaboration diagram back into a sequence diagram. Dropped inside a numbering step, it reads as if it were part of the numbering rule.
- ch 7 [low] Exam traps, second bullet: 'It gets no new activation bar of its own on the caller' is unclear. A return ends the activation of the object that was handling the call; it does not start an activation anywhere.
- ch 7 [low] Quiz Q6: The question asks 'what should replace the numbers?', but the answer never says what replaces them; it only says the numbers are redundant.
- ch 8 [high] Worked example 1, steps 2 and 6 and the answer line: The state count contradicts the chapter's own exam trap. Step 2 adds the final state to get 7 states, yet the trap says counting the initial and final symbols as ordinary states is a mistake. The initial state is also drawn on such a chart but is silently not counted, so the same rule is applied to one symbol and not the other. A student cannot tell whether the answer is 6 or 7.
- ch 8 [high] Worked example 1, step 6 (repeated in Quiz Q7): The guard [state ≠ Out for delivery and state ≠ Delivered] is wrong in principle. A guard is evaluated when the event occurs on a transition that is already drawn from a particular source state; it cannot test which state the object is leaving. Which states allow cancel is decided by where the three cancel arrows start (Placed, Accepted, Preparing), not by a guard. Also, part (b) asks what blocks a late cancellation, and the true answer is that no cancel arrow leaves Out for delivery.
- ch 8 [high] Quiz Q7: The answer repeats the invalid guard [state ≠ Out for delivery and state ≠ Delivered] and claims it is what restricts cancel to the early states. This teaches a wrong UML rule: legal source states come from the arrow's origin, guards only test data values.
- ch 8 [high] Exam traps, last bullet: It calls both the filled circle and the bullseye 'pseudostates'. In UML the initial symbol is a pseudostate, but the final state (bullseye) is a State, not a pseudostate. The trap as written states a wrong definition.
- ch 8 [low] Section 3, port paragraph: 'one component offers the same interface in two forms, say a card gateway and a UPI gateway behind one port' is confusing: two different gateways are two different interfaces or two different ports, not one interface in two forms.
- ch 8 [low] Section 4, communication path: 'Arrowheads show who starts the conversation' is a local convention, not standard notation; a plain UML communication path is an undirected line between nodes.
