## Reviewer notes (after any revision)

- ch 1 [high] Quiz Q5: The answer reverses the Ricart–Agrawala reply rule. P2's own timestamp 9 is larger, so P2's own request is later; the rule says defer only when your own timestamp is smaller. P2 must reply at once. The given answer ('P2 defers: its own timestamp 9 is larger') also contradicts the chapter's own exam trap 'a larger own timestamp means reply now'.
- ch 1 [low] Lead sentence: 'Ricart–Agrawala removes RELEASE and replies only to older requests' can be read as saying newer requests never receive a reply. In fact a newer request is deferred and gets its reply when the process leaves the CS.
- ch 2 [high] Lead paragraph: The lead says the cost is one message per entry when every process is busy. That contradicts the chapter's own formula C = (N − 1) + 1 = N: with N processes each entry costs N messages, not one. The comparison also switches units, pitting 'per entry' for this algorithm against 'per process' for reply-based schemes.
- ch 2 [high] Section 2 and Worked example 1, step 3: The chapter never states the rule that fills Q, and the trace in step 3 uses a rule the algorithm does not have. A holder that is not requesting and receives REQUEST(2,1) with RN[2] = LN[2] + 1 must send the token to P2 at once, so Q is never [2,4,3]. Requests enter Q only when the holder is inside the critical section and cannot forward immediately, or when the token is in transit.
- ch 2 [high] Section 3, first two sentences: It is false that a duplicate token never serves a process twice for the same request number. Suppose i requests with RN[i] = 1 and the good copy grants it, so that copy holds LN[i] = 1. The stale copy still holds LN[i] = 0. When the stale copy reaches i, RN[i] = 1 = LN[i] + 1 passes the test and i enters again for the same request.
- ch 2 [high] Quiz Q6 answer: The answer repeats the same wrong claim: 'The LN inside each copy still prevents a second grant to the same process for the same request number.' A stale copy with a smaller LN[i] will pass the test RN[i] = LN[i] + 1 for a request already granted by the other copy.
- ch 2 [high] Quiz Q5 answer: The conclusion is right but the reason is wrong. RN[i] = 7 does not imply LN[i] = 7; if the request numbered 7 has not been granted yet, LN[i] is still 6 or less. The answer teaches a false fact about the two arrays.
- ch 2 [low] Section 1 and Quiz Q1: The chapter says the token 'also travels with the holder's copy of RN' and Q1 counts RN as token state. In the standard algorithm the token is only the pair (Q, LN); RN stays at each process. Travelling copies of RN add nothing, and a receiver that overwrote its own RN with them could lose a request that reached it but not the sender.
- ch 2 [low] Section 1 versus Section 2 and Exam trap 1: Section 1 and trap 1 say LN is written by the process that has 'just finished' or 'just used' the token, but step 2 correctly sets LN[i] = RN[i] before entering the critical section. A student may write LN at exit instead of at entry.
- ch 3 [high] Exam traps, bullet 1: The trap says 'Only a probe whose third field equals its own initiator proves a cycle.' In the convention the chapter itself defines, the third field is always the initiator, so every probe satisfies this test, including probe(P1, P2, P1) sent at the very start, which proves nothing. The test contradicts section 2, bullet 4 and worked example step 4, where the deciding field is the second one.
- ch 3 [high] Quiz Q3 answer: The answer justifies detection with 'The third field equals P1 at the end'. Under the chapter's convention the third field of every probe is P1, so this is not the deciding condition and contradicts worked example 1, which checks the second field.
- ch 3 [low] Section 2, bullet 5 ('Pk declares a deadlock and reports every process named in the returned probes'): A probe carries only three fields, so the returned probe probe(i, Pk, Pk) names only the sender and the initiator. The initiator cannot list the other cycle members from it, and the sentence suggests it can.
- ch 3 [low] Section 2, definition of probe(i, j, k): Most standard treatments write the CMH probe as probe(initiator, sender, receiver). This chapter uses probe(waiting process, waited-on process, initiator). Both work, but a student moving between this book and a textbook will mix the fields, which is exactly what happened in the exam trap.
- ch 3 [low] Section 1, table, Communication model row: In the communication model a process waits only for messages. The example makes the client wait for a lock, which is a resource wait, so it is not a pure communication-model wait.
- ch 4 [low] Section 2, round rule bullet ('After each round, a process keeps the value that appears in a majority...'): The rule is undefined when no value has a strict majority, and that case really occurs. With N = 2f+1 and f crashes a process can receive exactly two values, one 1 and one 0 (for example N = 3, f = 1, one process crashed, the two survivors propose different values). The student has no instruction for this tie, so the described algorithm is incomplete.
- ch 4 [low] Section 2, first and third bullets: The bullets mix two different algorithms. 'Every process sends the set of values it knows' describes flooding/relaying of sets, which is agreed by taking the minimum, while 'keeps the value that appears in a majority' describes single-value majority voting, where each process sends only its current value and never a set. A student cannot tell which one to implement, and counting a majority over sets is not well defined.
- ch 4 [low] Section 2, opening paragraph and 'Why f+1 rounds?': The round-based majority algorithm is presented without saying that it needs the synchronous model. The rounds only terminate, and a crashed process's silence only counts as a missing value, if message delay and process speed are bounded. Section 4 mentions this, but a reader of Section 2 alone will think the algorithm works in any timing model.
- ch 5 [high] Section 2, the rollback rule: The rule as written states the conclusion in its own premise and then contradicts itself. It says "if process j has to roll back to a checkpoint taken before it received a message m ... then j's checkpoint holds an orphan and is invalid. Process j rolls back further." If j has already rolled back to a checkpoint before the receive, no receive of m is in that checkpoint, so it cannot be an orphan; and "rolls back further" then makes no sense. The cause (j's current checkpoint contains the receive, the sender's chosen checkpoint misses the send) and the effect (j must discard that checkpoint and go back to one before the receive) are swapped. A student cannot follow the domino chain from this sentence.
- ch 5 [low] Figure and worked example: The C3,1 bar runs from t = 11 to t = 12.5, so the write is still in progress when P1 crashes at t = 12. The worked example treats C3,1 as a completed checkpoint taken at t = 11 that P3 rolls back from, and never mentions an interrupted write. Figure and text disagree.
- ch 5 [low] Section 4, first paragraph: "Piecewise deterministic, meaning its state changes only when a message arrives" is not the standard definition. A process also changes state during local computation; what makes it piecewise deterministic is that every nondeterministic event is a message reception and the execution between such events is deterministic. As written, a student could think a process doing long local computation does not fit the model.
- ch 5 [low] Section 3, last paragraph: "Communication-induced, or quasi-synchronous, checkpointing" treats two terms as exact synonyms. Quasi-synchronous checkpointing is a family inside communication-induced checkpointing (checkpoints grouped into quasi-synchronous intervals); equating them will confuse a student who meets both names in an exam question.
- ch 5 [low] Beyond: "Databases use logging rather than rollback, in the redo and undo style of ARIES" is misleading: ARIES does roll back (undo) uncommitted transactions; what it avoids is rolling back to an old checkpoint of the whole database. The phrase as written suggests databases never undo work.
- ch 6 [high] Section 1, state machine replication paragraph: The sentence 'Two debits in different orders can leave different balances' is false under the arithmetic model the chapter itself uses (balance = starting balance minus the sum of debits, and addition/subtraction commute). A student will take an untrue rule into the exam. Order only matters when operations are not commutative, for example when a debit is rejected for insufficient funds.
- ch 6 [low] Section 1, quorum formula: The definition 'q is the smallest member count' is unclear and reads as if q were the number of members present, not the number needed to agree.
- ch 6 [low] Quiz Q3: The answer term 'noncommutative state' is loose; state is not commutative or noncommutative, the operations are.
- ch 6 [low] Section 2, ordering paragraph: The reference 'covered in Unit 4' does not follow the chapter's own style (plain '5.4', '5.7' elsewhere, and none of these are chapter links), so a phone reader cannot jump to it and the pointer is easy to misread.
- ch 7 [low] Section 3, client-centric list: The text says 'Three are standard', but the standard client-centric (session) guarantees number four: read-your-writes, monotonic reads, monotonic writes and writes-follow-reads. Monotonic writes is missing, so a student may believe only three exist.
- ch 7 [low] Section 3, replicated-write paragraph and read repair: 'Replicated-write has no primary' is immediately followed by 'Version numbers give a total order per item'. With no primary and no coordinator, two concurrent writes can both claim the same version, so the numbers do not by themselves give a total order.
- ch 7 [low] Section 3 and Quiz Q7: Section 3 says reads 'may be local' under remote-write, yet Q7 claims remote-write makes read-your-writes easy. A local read from a stale replica breaks read-your-writes just as in local-write, so the two statements pull against each other.
- ch 7 [low] Section 2, opening paragraph: 'Every step down removes an ordering constraint' is not true of the lower entries: weak and release consistency do not simply delete ordering, they replace it with explicit synchronisation operations, and eventual consistency replaces it with a convergence promise.
- ch 7 [low] Section 3, last paragraph: The reference '(Unit 4)' does not say which chapter covers vector clocks and is not a link, so a student on a phone cannot jump to it.
