- ch 1 [low] Beyond section: There is no standard tool called 'the Java race detector', so the name gives a student nothing to search for. The pairing with ThreadSanitizer suggests a tool that a reader cannot find.
- ch 2 [high] Exam traps, first bullet: The conclusion (waiting on turn==i is wrong) is right, but the stated reason is false. With turn==i written in the wait, if both flags are true only one process passes: Pi passes when turn==j, and turn cannot equal j for both i=0 and i=1 at once. Both processes never pass together in that state, so the given explanation misleads students about how the failure happens.
- ch 2 [high] Quiz Q6 answer: The answer says that when both flags are true both conditions can be false. They cannot: with both flags true exactly one of the two conditions is false, exactly as in the correct version. The answer gives a wrong justification for a correct conclusion.
- ch 2 [high] Quiz Q2 answer: The last sentence, 'Waiting on turn==i would let both pass', is technically wrong. With turn==i and both flags true, exactly one process still passes; the mutual-exclusion failure of that variant needs one process to test before the other sets its flag.
- ch 2 [low] Exam traps, second bullet: The claim that initializing turn to i 'breaks the tie' is not true. Both processes always write turn before testing, so the value at test time is the last value written; the initial value of turn cannot affect who enters.
- ch 3 [low] Section 2, atomicity paragraph (and repeated in Quiz Q3 answer): The race is described as 'one permit is lost'. With S = 1 and two concurrent waits, both read 1 and both write 0, so a decrement is lost and two processes enter the critical section — the permit is not destroyed, the count under-decrements and mutual exclusion breaks. A student may read 'permit lost' as 'one resource disappears'.
- ch 3 [low] Section 2 vs Worked example 1, step 5 and answer: Section 2 correctly says the semaphore definition does not promise FIFO wake-up, but step 5 says 'the queue is first-in-first-out, so P2 wakes' and the answer key fixes P2 as the one who enters. That contradicts the earlier caveat and would lose marks if an examiner is strict.
- ch 3 [low] Section 3, bounded buffer pseudo code: A '[shown output]' block follows pseudo code, but pseudo code produces no output, so the reader is left looking for something that does not exist.
- ch 4 [high] Section 1: The chapter says the monitor removes the semaphore bug of 'forgetting to signal, or signalling the wrong semaphore'. The monitor only automates the lock/unlock around the shared data. The programmer still writes every x.wait and x.signal on condition variables, so forgetting a signal (for example a consumer forgetting notEmpty.signal()) or signalling the wrong condition variable is still a real bug inside a monitor.
- ch 4 [high] Worked example 1, answer line: The answer says 'notFull had 1 waiter at step 3'. In the listed steps, step 3 is 'P inserts B' where notFull = {}. The single waiter appears at step 4, 'P tries C', where notFull = {P}. A student checking the steps against the answer will think the steps are wrong.
- ch 4 [high] Quiz Q4: The question assumes a lost signal can put a process to sleep forever, and the answer says the process 'stays blocked even if the condition is now true'. That contradicts the chapter's own while-loop rule. In a correct monitor program, a wait and the predicate test are atomic under the monitor lock: a waiter blocks only while the predicate is false, and the predicate can only become true inside the monitor, by a process that then signals. So a signal with no waiter is harmless and cannot cause permanent sleep. The answer also mixes the variables: a producer signals notFull, but it is consumers who wait on notEmpty.
- ch 4 [low] Lead: The lead says monitors are used 'in the pthread condition-variable pattern', but the Beyond section correctly says pthread_cond_wait with a mutex is not a full language monitor. The two statements contradict each other.
- ch 5 [high] Section 1, bullet on multi-instance boxes: It says a box shows one dot per free instance, so two held printers out of three leave one dot. This contradicts the bullet earlier in the same section (one dot per instance) and contradicts the standard graph model, where every instance always keeps its dot and an assignment edge starts at that dot when the instance is held. Under the chapter's own rule, a box with 3 instances and 2 held would wrongly appear to have only 1 instance.
- ch 5 [high] Quiz Q2 answer: The second sentence, 'An unmarked or filled dot shows that instance is currently assigned', is garbled and wrong. Dots do not change appearance with allocation; allocation is shown only by an assignment edge leaving the dot.
- ch 5 [high] Section 2, priority/two-case paragraph: The second case, a process holding a lock that is never scheduled again while others wait, is labelled a deadlock. Under the chapter's own definition (a set of processes each waiting for a resource held by another member of the set) and under the four conditions, this is indefinite blocking or starvation, not deadlock: the holder is not waiting for anything, so no circular wait exists. A student will carry away a wrong test for deadlock.
- ch 5 [high] Exam traps, last bullet (starvation is not deadlock): 'A deadlocked one cannot be helped by adding more of the same resource' is false. If two processes each hold one of two printers and each wants a second, adding a third printer lets one request be granted and the deadlock clears. Adding instances can break a deadlock; what cannot help is waiting longer.
- ch 5 [high] Beyond: 'Rust's borrow checker goes further and rejects some lock misuse at compile time' is wrong for lock-ordering deadlocks. Rust's compiler prevents data races through ownership; a lock-order deadlock between two threads compiles cleanly and hangs at run time.
- ch 6 [high] Worked example 1, step 5: The arithmetic uses the resource's number as if it were a count. P2 holds one resource, R2. Writing '2 - 1 = 0' says P2 held two resources, which contradicts steps 3 and 4 and the answer line.
- ch 6 [low] Section 1, Detection: A wait-for cycle proves deadlock only when every resource type has a single instance. With multiple instances a cycle can exist without deadlock, so the sentence is too broad as written.
- ch 6 [low] Exam traps, global numbering trap: The wording is easy to misread. The rule is about the order of requests, not about which resources a process may hold.
- ch 7 [high] Quiz Q3 and Q7 (answers): Both answers explain unsafe as 'the processes may still request resources in an order that lets them finish' / 'request and release resources in a favourable order'. That contradicts the chapter's own definition: a safe sequence is an order in which every process finishes if each takes its remaining maximum claim, so if no safe sequence exists, no request order lets all processes finish at their maxima. The standard reason an unsafe state may still escape deadlock is that processes often do not request their declared maximum (and may release held resources early), not that a finishing order exists.
- ch 7 [low] Section 1, claim-edge paragraph: The last sentence says the request is refused 'if adding a claim edge would create a cycle'. A request does not add a claim edge; the claim edge already exists (drawn when the process starts) and the request converts it into a request edge. The cycle check is made when the request edge would be turned into an assignment edge.
- ch 7 [low] Section 1, bullet list (Deadlocked): 'Deadlocked: a cycle of waits exists' reads as if a cycle is enough to prove deadlock. With several instances of a resource, a cycle is necessary but not sufficient, so a student can wrongly call a cyclic-but-completable state deadlocked.

In a wait-for graph a process is drawn waiting only when no instance of that type is free, so a free instance cannot be the reason the cycle clears. The real reason is a process outside the cycle that holds another instance of the requested type and can release it.
