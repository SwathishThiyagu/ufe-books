## Reviewer notes (after any revision)

- ch 1 [high] Section 2, paragraph on attributes: "In a link element, href gives the destination and target=\"_blank\" opens it in a new tab." The chapter has already used link as the void element that attaches a stylesheet. That element has no target attribute and does not open anything in a new tab. The element that does this is the a (anchor) element. A student will carry the wrong model into the link/stylesheet discussion.
- ch 1 [high] Section 2 (comments) and exam trap 4: "A comment ... never appears in the tree" and "Neither is an element and neither appears in the tree." Comments do appear in the DOM tree as comment nodes, and they are visible in the Elements panel the chapter tells students to open. The claim contradicts the chapter's own Inspect instruction.
- ch 1 [low] Section 1, paragraph on head: "Four things live there" is followed by five items: title, meta charset, meta viewport, link, and then the script element. The count does not match the list.
- ch 1 [low] Section 2, void elements; repeated in quiz Q2 answer: "Their content arrives through attributes, so there is nothing to close." This is true of img, input, meta and link, but br and hr carry no data at all; their attributes only tune the element (for example the line break itself, or the rule's width).
- ch 1 [low] Section 2, paragraph on comments: "Written with the mark, two dashes, text, two dashes, mark" never says which mark, so the reader cannot actually type a comment from this description.
- ch 1 [low] Section 2 (quoted values) and exam trap 2: Two small gaps. First, "Quotes may be dropped only when the value has no spaces" is incomplete: an unquoted value also may not contain \" ' = < > or a backtick, and may not be empty. Second, "closing a void element" is ambiguous: the self-closing slash in <img /> or <br /> is valid HTML and not an error; only a separate end tag such as </img> is wrong.
- ch 1 [low] Quiz Q7: Two symptoms are stated wrongly. A page with no title shows the file name or the URL on the tab, not "Untitled". And a wrong declared character set produces garbled characters (Ã¢â€š¹ and the like), not empty boxes; boxes mean the font lacks the glyph.
- ch 2 [low] Section 1, text formatting: The subscript and superscript examples are written as plain 'H2O' and 'x2'. The whole point of the sentence is the effect of the tags, and a student can read 'x2' as x times 2.
- ch 2 [low] Section 3, tables: 'colspan=2 makes one cell cover two columns to its right' is ambiguous. A student can read it as the cell's own column plus two more columns, giving three columns.
- ch 2 [low] Section 3, images: Saying alt is 'required' without the exception can confuse students who see alt="" in real pages.
- ch 2 [low] Figure, price table grid: The last row lists three cells, 'Sum', an empty cell, and '70'. The empty cell appears as its own box, so the figure does not visually show the colspan=2 merge that the caption and aria text describe.
- ch 2 [low] Worked example 1, steps 1 to 3: The tags are written without angle brackets, so the text runs together (for example 'captionStationery bill/caption', 'tdPen'). A student cannot see where the tag name ends and the content begins.
- ch 3 [low] Lead: The lead says "HTTP can carry only text" and uses that as the reason forms become name=value pairs. HTTP bodies carry arbitrary bytes; a file upload sends binary. The real reason is the HTML form data model is text: controls hold string values.
- ch 3 [low] Section 1, URL-encoding paragraph: "any character outside plain ASCII becomes a percent sign plus two hex digits" is wrong per character. The character is first encoded as UTF-8 bytes, and each byte becomes one %XX triplet. A rupee sign becomes three triplets, not one.
- ch 3 [low] Section 3, attribute list, value: "value — the value sent when the user changes nothing" is misleading. In a text field the value attribute is the default text, and anything the user types is sent instead; in a radio or checkbox it is the value sent when the control is checked, not a fallback for an untouched field.
- ch 3 [low] Section 3, attribute list, required: "required — the form cannot be sent while the field is empty" does not cover checkboxes and radio groups, where the condition is not emptiness but not being checked or chosen.
- ch 3 [low] Section 2, datalist paragraph: datalist is described as attaching to "a text input" only. The list attribute works on several input types, including search, url, email, tel, number, range and color.
- ch 3 [low] Section 2, choice bullet: "checkbox for many of many" is unclear wording; a reader cannot tell what is being chosen from what.
- ch 4 [low] Section 1 (landmark sentence): The list says header, nav, main, aside and footer are landmarks without the caveat that a header or footer nested inside an article, section or aside is not a landmark. The same section already tells students a header may repeat inside an article, so a student can build a nested header and wrongly call it a banner landmark. The list also omits the search/form landmarks without saying the list is only the common ones.
- ch 4 [low] Section 2 (preload bullet): The bullet reads 'preload: hint, none, metadata or auto', which mixes the meaning ('a hint') with the attribute values. A student may write preload='hint'.
- ch 4 [low] Section 2 (track / captions bullet): 'kind= captions gives sound descriptions and speech for deaf viewers' invites confusion with the separate kind='descriptions', which is audio description of visual content. Captions carry dialogue plus important non-speech sounds, not 'sound descriptions'.
- ch 4 [low] Quiz Q5: The answer allows only sections for the comment blocks. The HTML standard itself lists a user-submitted comment as one of the classic examples of an article, so a student who answers 'each comment is an article' is following standard textbooks and would be marked wrong here.
- ch 4 [low] Section 1 (heading 'Named regions and their rules'): figure, details, time, mark, progress and meter are listed under a heading about named regions, but none of them is a landmark region. A student may come away thinking figure or progress is read as a page region.
- ch 5 [high] Section 1, and repeated in Exam traps (fifth bullet): The chapter says a missing semicolon makes the browser 'silently discard the rest of that block'. That is not how CSS error recovery works. The parser reads the value up to the next semicolon (or the closing brace), finds one invalid declaration, throws that single declaration away, and then carries on with the remaining declarations. It also contradicts the earlier advice to put a semicolon after 'the last one included' — a missing semicolon before } is legal, not fatal.
- ch 5 [high] Section 1, units table, % row: The 'One unit is' column says one % is 'half the parent's width'. One percent is one hundredth of the parent's value for that property; 50% is half the parent's width.
- ch 5 [high] Quiz Q6: The answer reverses the two selectors. It says the first rule has 1 on the id counter and the second has 0. In the question, the first rule is p.note = (0,0,1,1) with id counter 0, and the second is #intro p = (0,1,0,1) with id counter 1. The conclusion (#intro p wins) is right, but the stated reason is backwards and would lose marks.
- ch 5 [low] Quiz Q4, answer: The three counters are listed without saying which selector each belongs to, so a student has to guess that (0,0,0,1) is p, (0,0,0,2) is div p and (0,0,1,0) is .note.
- ch 6 [low] Section 1, opening sentence: "Every element generates a rectangular box" is too absolute: an element with display: none generates no box at all, and a non-replaced inline element generates line boxes where vertical padding and borders paint without changing line height. A student reading this literally will be confused by display: none later.
- ch 6 [low] Exam traps, fifth bullet: "Only margins accept negative values" is over-broad and reads as a rule about all of CSS, not about the box model. Properties outside the box model (text-indent, letter-spacing, top/left on positioned boxes, transform) do take negative values.
- ch 6 [low] Section 2, border-box paragraph: The border-box explanation and the content-width formula cover width only. Students then apply the same subtraction wrongly to height, or do not know it behaves the same way.
- ch 6 [low] Section 3, margin: auto and margins: Two small points that exam answers often need are missing: percentage margins and padding are resolved against the width of the containing block (even for top and bottom), and margin: auto on the vertical axis computes to 0 for block boxes in normal flow.
- ch 6 [low] Section 3, first paragraph on display: "display decides how a box treats width and vertical margins" is vague and slightly misleading; display decides what kind of box is generated (block-level, inline-level, or none), which then decides how width and vertical margins apply.
- ch 7 [high] Section 2: Backgrounds, opening sentence: It says the background layer is painted behind content and padding, 'stopping at the border'. By default the background painting area is the border box: the background is painted underneath the border as well, out to the border's outer edge. A student who trusts this sentence will be surprised when a dashed or semi-transparent border shows the background colour running under it.
- ch 7 [low] Section 2: Backgrounds, 'Six longhand properties': The current backgrounds specification defines eight longhands; the chapter lists six and silently leaves out background-clip and background-origin, yet states the count as a fact.
- ch 7 [low] Worked example 1, step 6: The hue result ends with a garbled fragment '≈ 9.i', so the final number of the step is unreadable.
- ch 7 [low] Beyond, first sentence: The CSS function name is written 'colour-mix()'. Function names in code are never translated; the real spelling is color-mix().
- ch 8 [high] Section 2, the order paragraph: The text says order: 2 'also moves it for screen readers and Tab order'. That is false. order changes only the visual order; the accessibility tree and keyboard Tab sequence still follow the HTML source. The next sentence and the Q7 answer both state the correct rule, so the chapter contradicts itself.
- ch 8 [high] Exam traps, fourth bullet (z-index / stacking contexts): The trap says a child cannot paint above 'a sibling of its parent that has a lower stacking context'. A sibling with a lower stacking context is painted below, so the child would paint above it. The real limit is a sibling of the parent that paints above the parent, i.e. a sibling with a higher z-index or a later stacking context. As written the rule says the opposite of what happens.
- ch 8 [low] Exam traps, fourth bullet, first clause: 'z-index does nothing on a static-positioned box' clashes with Section 1, which correctly says z-index also works on flex and grid items. A static flex item does respond to z-index.
- ch 8 [low] Section 4, srcset sentence: srcset is described as picking 'by pixel density' only. With width descriptors the browser also needs the sizes attribute and picks by the layout width the image will occupy, which is the usual responsive case.
- ch 8 [low] Section 3, minmax sentence: minmax(150px, 1fr) is said to set 'a floor and a ceiling'. The 1fr maximum is flexible, not a ceiling; the track can still grow past it when the container is wide.
- ch 9 [high] Quiz Q6 (and its answer): The markup the question is about has been lost. The question reads 'A student writes AB' and the answer ends 'Wrap both columns in a .' — the container div and the two col-* divs are missing, so the student cannot see what was written and cannot tell what to wrap.
- ch 9 [low] Section 2, exam trap 1 and Q6 answer: 'Columns may stack at half width' is not what happens. Outside a row the flex properties are ignored (Bootstrap 5 keeps each column at one-third width, Bootstrap 4 falls back to full width) and the gutter padding is gone, so the columns simply stop behaving as a grid row. 'Half width' is invented and will confuse a student who tries it.
- ch 9 [low] Section 1 formula and Worked example 1: The formula defines W as the row content width, but the example substitutes 960 px, which is the container content width. A real row is wider than the container content box by the two negative margins, and every column also carries half-gutter padding, so the true box widths are not exactly 320/640/960 px.
