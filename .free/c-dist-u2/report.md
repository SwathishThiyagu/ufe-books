## Reviewer notes (after any revision)

- ch 1 [high] Figure spec: The marks keys are '1' and '3', so the figure marks the values 1 and 3. The caption and aria say the off-diagonal pair 2 and 4 is marked. The figure would show the wrong pair.
- ch 1 [high] Lead / Section 1 / Worked example 1 / traps / Q2: The chapter defines b[i][j]=a[j][i] as a separate output, but then describes swapping cells inside a (in-place transpose), says diagonal cells do no read or write, and gives 6 reads and 6 writes for n=3. These are two different algorithms. For separate b, diagonal 1,5,9 must be copied, so n=3 needs 9 reads and 9 writes. For in-place, exact off-diagonal reads/writes are n(n−1), not n², and n=3 gives 6. The n² claims in the lead, traps and Q2 are inconsistent with the worked example.
- ch 1 [high] Section 2 / Q7: The recipe 'Transpose swaps B and C, and transposes A and D recursively' is wrong if B and C are swapped as whole blocks. The true block transpose is [[A^T, C^T], [B^T, D^T]], so B and C must also be transposed. Swapping B and C unchanged leaves them untransposed and gives a non-transpose.
- ch 1 [low] Section 2 / Q7: The cut into n/2×n/2 blocks and the answer log₂ n levels assume n is a power of two. For general n, n/2 is not an integer block size and log₂ n is not an integer. The number of block-exchange levels also depends on the hypercube processor layout, not just n.
- ch 1 [low] Section 2: The statement that the total number of elements moved stays n² is not exact. In the off-diagonal recursive exchange, diagonal elements never move, so the count is n(n−1), not n². For n=3 that is 6, not 9.
- ch 2 [high] Exam traps, first trap: The trap says a student who writes speedup S = n when p = n² is wrong, and blames fan-in and broadcast. But at p = n² each processor owns one whole output cell and does n multiply-adds, so the ideal speedup against one processor is n² = p, not n. The chapter's own model gives S = n³/(n + log n²), close to n². As written the trap teaches a value wrong by a factor of n, and the reason given (fan-in per dot product) does not apply when one processor owns a whole cell.
- ch 2 [high] Quiz Q4: Both the question and the answer are wrong. The question asks why the speedup is not n at p = n², and the answer says S is below n. With p = n² the ideal speedup is p = n², and the chapter's formula gives S ≈ n², which is far above n. The answer contradicts the formula in Section 3.
- ch 2 [low] Section 2, mesh paragraph: The schedule described (each round, broadcast a[i][k] along row i and b[k][j] down column j) is not Cannon's algorithm. Cannon's algorithm skews the initial alignment of the blocks and then uses nearest-neighbour circular shifts of A left and B up; it uses no row or column broadcast. Calling the broadcast schedule Cannon's will confuse students who meet the real algorithm later.
- ch 2 [low] Section 2, third processor budget: 'The time is O(n³/p) only when the cells divide evenly' is too strong. With p ≤ n², the busiest processor holds ⌈n²/p⌉ cells, so its time is ⌈n²/p⌉·n, which is still O(n³/p + n) = O(n³/p). Uneven division changes the constant, not the order.
- ch 2 [low] Figure: The figure is drawn with 0-based indices (index_from 0) but the row is labelled 'B col 1' while showing B's first column [5,7] (index 0), and it is matched to c₁₁, which uses 1-based subscripts. A student can read 'col 1' as the second column and expect [6,8].
- ch 2 [low] Worked example 1, step 9: The setup gives four processors, one per cell of C, but step 9 says x is broadcast 'to both processors' without saying which two. With n = 2 the matrix-vector product needs two processors (one per row of A), not four.
- ch 3 [high] Section 3, last sentence: The claim that bitonic sorting uses prefix sums inside its merge step is wrong. The bitonic merge is a fixed compare-exchange network; prefix sums are not part of it. A student who writes this in an exam loses marks.
- ch 3 [low] Lead, definition of prefix sums: 'the running total of all elements before it' describes an exclusive scan, but the formula in Section 2 (y_i = x₀ + … + x_i) is an inclusive scan that includes x_i itself. The two statements contradict each other.
- ch 3 [low] Lead, 'Both ideas use the same doubling trick': For broadcast the number of processors holding the value doubles; for scan no processor count doubles — what doubles each step is the length of the input block each running total covers. Calling both 'the number of processors holding useful information doubles' is misleading.
- ch 3 [low] Quiz Q6: The answer writes 'T_p = O(1000 + 10) = O(1010)'. O(1010) is O(1) as notation, so the line is meaningless and a student may copy it as a result.
- ch 3 [low] Section 3, total work claim: 'The total work is O(n)' counts only the block scans and the offset additions. The block totals are prefix summed by doubling, which costs about p⌈log₂ p⌉ additions, so strictly W = O(n + p log₂ p). The O(n) claim needs a condition on p.
- ch 3 [low] Section 2, first line: 'also called scan or all-sums' — 'all-sums' is not standard; the usual name is 'all-prefix-sums'.
- ch 4 [high] Section 1, formula line T_p = Θ(log n), W = p · T_p = Θ(n): The equality W = p · T_p is false here. The line itself sets p = n, so p · T_p = n · Θ(log n) = Θ(n log n), not Θ(n). The two claims contradict each other, and a student who copies W = p·T_p into an answer loses marks.

- ch 4 [low] Exam traps, fourth bullet: The bullet points the wrong way. Reading the p per-block answers in one step is cheap on a PRAM, so the block-split time really is Θ(log(n/p)); the full answer including the combine step is Θ(log(n/p) + log p) = Θ(log n), not something smaller. As written, the trap suggests that adding the combine step makes the time longer than O(log n), which is the opposite of what happens.
- ch 5 [high] Quiz Q7: The answer says bitonic sort 'is shallower but uses more comparators' than odd-even transposition. This is false. For 8 keys bitonic uses 24 comparators while odd-even transposition uses 28, and in general bitonic size O(n log² n) is far smaller than the n(n−1)/2 comparators of the odd-even network. The answer also contradicts the worked example, where both networks have 6 comparators for n = 4.
- ch 5 [high] Section 3 (hyperquicksort) and Quiz Q6: The text says the median of the processors' local medians 'becomes the pivot, so the two halves are equal'. That is wrong. Only the true global median splits the data into two exactly equal halves. The median of the local medians gives each processor an approximately even split, so each subcube receives about half the keys, not exactly half. Q6 repeats the same claim.
- ch 5 [low] Section 2, odd-even merge sentence: 'Odd-even merge sort has the same depth and size with a simpler merge' is too loose. Batcher's odd-even mergesort has the same depth, but it uses fewer comparators than bitonic sort (same O(n log² n) order, smaller constant). The odd-even merge network is usually considered more intricate than the bitonic merge network, not simpler.
- ch 5 [low] Section 2, enumeration sort: The step from 'all comparisons run together' to 'O(n) time' is not explained. With n² processors every pair is compared in one step, but each key still has to add up its n comparison results, and that summation is what sets the time (O(log n) with a tree, O(n) if each key's n results are added serially). As written, O(n) with n² processors looks inconsistent.
- ch 5 [low] Section 1, 0-1 principle: 'test 16 binary inputs, not one array' reads oddly; a beginner may think a 0/1 array is the only thing to test.
- ch 5 [low] Section 2, bitonic sort: The key term 'bitonic' is used but never defined, so the sentence 'makes a sequence rise then fall' is easy to misread as describing the whole algorithm rather than the sequences it builds.
- ch 6 [high] Quiz Q5: The answer claims the processor-time product matches the serial arithmetic cost. It does not: with O(n²) processors and about n log n parallel steps, processor-time product is O(n³ log n), which is a factor log n above the serial O(n³). So the algorithm is not work-optimal in the standard sense; only its flop count equals the serial one.
- ch 6 [low] Section 2, sentence starting 'With O(n²) processors the arithmetic work is O(n³)': The term 'work-optimal in arithmetic' is not a standard term and can mislead, because work is normally parallel time × processors, which here is O(n³ log n), so the algorithm is not work-optimal.

- ch 7 [low] Exam traps, first bullet: The trap says Borůvka may add an edge whose two ends are already in one component. - ch 7 [low] Section 1 formula box and Quiz Q7: The O(n²) per-round cost with an adjacency matrix holds only for the round that scans rows to find each vertex's cheapest neighbour. Pointer-jumping rounds touch only the parent array and cost O(n) whatever the storage, so 'work per round = O(n²)' and 'a matrix round scans n² cells' overstate every round.
- ch 7 [low] Section 2, paragraph on Prim and Kruskal: 'Their parallel versions ... still need a global order' is not right for Prim. Parallel Prim keeps a priority queue of frontier edges and grows one tree; it does not need the edges in a single sorted global order the way Kruskal does.
