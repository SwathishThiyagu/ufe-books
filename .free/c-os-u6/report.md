## Reviewer notes (after any revision)

- ch 1 [low] Section 3, fail-safe defaults bullet: The bullet states as fact that 'a newly created file is readable by its owner only', but on a normal Linux system the default umask lets new files be created world-readable (for example 644), so a student who tests this in the lab sees the opposite of what the text says.
- ch 1 [low] Section 3, list of seven principles: The list does not include complete mediation (every access to every object must be checked), yet the figure and the worked example both rely on exactly that idea: the process cannot reach the file without passing the check. A student asked for the standard design principles may lose marks for leaving it out.
- ch 2 [high] Worked example 1, steps 6–8 and the answer; the figure; exam trap 3; quiz Q4: The chapter says the kernel writes the saved set-user-id back into the effective uid when the process exits, so the process 'returns to D1'. There is no such restore on exit. exec of a setuid file replaces the process image; the rights of uid 0 last only for the life of that image, and when the image finishes the process terminates. On a normal shell run the shell never entered D2 at all: the shell forks a child, the child execs passwd in D2 and dies. The saved set-user-id exists so the program itself can call setuid(1000) to drop to D1 temporarily and setuid(0) to regain D2 while it is still running.
- ch 2 [low] Worked example 1, steps 1, 2 and the answer: Step 1 and step 2 use /usr/bin as the object, but the question names the file /usr/bin/passwd. A directory and a file are different objects, and the setuid bit sits on the file, not on the directory.
- ch 2 [low] Section 2, 'The switch back is automatic': 'restores them when the privileged program exits' is loose for a guarded procedure or a system call. Control comes back when the protected procedure returns, not when a program exits; a student may read it as process termination.
- ch 3 [high] figure: The caption says D1's read on F1 and D3's read-write on F4 are marked, but the mark indices are inconsistent with that: for D1 the mark is on index 1, which is F2 (rw) under 0-based counting or F1 under 1-based counting; for D3 the mark is on index 3, which is F4 under 0-based counting or F3 (empty, '-') under 1-based counting. Under either counting convention one of the two marks sits on the wrong cell, so the figure contradicts its own caption.
- ch 3 [high] section 2 (and its reuse in section 3): 'Global table: keep the whole matrix' contradicts the standard textbook meaning. In the standard protection chapter, the global table (also called an authorization table) is an ordered list of (domain, object, rights-set) triples holding only the non-empty entries, so it is not a dense D×O array. The chapter's later claim in section 3 that a global table needs 1,000,000 cells then compares a dense array against sparse lists, which is not the textbook comparison.
- ch 3 [low] section 1, last sentence: 'Only a few universities teach this topic in depth' is misleading filler: the access matrix is standard core content in almost every operating systems syllabus, so a student may wrongly treat it as optional or niche.
- ch 3 [low] section 2, lock and key bullet: It says each object has 'a lock, a bit pattern' (singular). With one lock per object, only domains holding that one matching key could ever access it, and the scheme could not distinguish read from write rights. Standard treatments give each object a list of locks, one per right or per sharing set, and describe lock-and-key as a compromise between access lists and capability lists, not purely a compressed access list.
- ch 4 [high] Section 3, back-pointers bullet: The pointer direction is stated backwards. The bullet says each copy of the right keeps a pointer back to the file's entry, and that to revoke the system follows the pointers and deletes every copy. Pointers from copy to object lead the wrong way: following them from a copy cannot find the other copies. This contradicts worked example 1 step 2, where the bob entry itself carries four pointers to the copies, and contradicts the standard description of the scheme.
- ch 4 [high] Worked example 1, step 1 and step 5, and Quiz Q4 part (a): The example counts access-list revocation as a complete 1 step even though the stem says bob's read right has already been copied into P1, P4, P9 and P12. Deleting the bob entry stops future checks only. The four processes already hold the right (for example open file descriptors) and keep reading the payroll file. A student reads '1 step' as 'the four copies die', which is exactly the confusion the chapter warns about elsewhere. The same flaw is in Q4, where 6 processes are said to hold the right and the answer is still 1 step.
- ch 5 [high] section 3, sentence 'AccessController tests the current domain.': This contradicts the sentence two lines earlier and the standard behaviour. AccessController.checkPermission does not test only the current (caller's) domain; it walks the whole call stack and checks every ProtectionDomain on it, failing if any one lacks the permission. A student reading 'tests the current domain' will think only the immediate caller is checked, which is wrong and would also make the earlier stack-inspection sentence meaningless.
- ch 5 [low] section 1, sentence 'The rights are read, write, execute, or copy.' followed by 'The amplify right lets the holder add rights.': The list of rights is presented as complete, then a fifth right (amplify) appears without warning. A student may think amplify is one of the four, or may not see how it differs from copy.
- ch 5 [low] section 2, sentence 'the kernel cannot find the child's copy by scanning P's list': This reads as if scanning P's list might have found the child's copy under other circumstances. Scanning P's list only ever returns P's own entries; that is exactly why copies are untraceable.
- ch 6 [high] Worked example 1, step 7: The numbers in the ratio line are wrong. 62⁸ is 218,340,105,584,896, that is 2.18 × 10¹⁴ (or 21.8 × 10¹³), not 22.09 × 10¹³. As written, 22.09 × 10¹³ ÷ 2.09 × 10¹¹ gives about 10.6, not the 1046 printed in the same line, so a student following the arithmetic gets a contradiction.
- ch 6 [low] Section 1, definitions paragraph: The threat row mixes two standard terms. Textbooks separate a threat (a potential violation of security, the thing that could go wrong) from the threat agent or attacker (the person who may cause it). Writing 'A threat is who might use it' teaches the weaker meaning and can cost marks in a definition question.
- ch 7 [low] Section 3, centralized mutual exclusion bullet: Says the centralized scheme costs 'two messages per entry'. Standard textbook counting includes the release message, so the usual figure is three messages per entry (request, grant, release). A student writing 'two' can lose marks against a key that says three.
- ch 7 [low] Quiz Q8 answer: 'but only one machine is affected' is unclear: the crashed coordinator is one machine, but the effect is that every process is blocked, so the sentence can be misread.
- ch 7 [low] Section 2, vector clock paragraph: n appears in 'a vector V of n counters' without being defined at that point.
- ch 8 [high] Section 2 (write policy) and worked example 1, step 4: The chapter says write-through makes the staleness window 'near zero' and that 'write-through or a callback shrinks the window'. Write-through only makes the server copy current for the client that is writing. It does nothing for a reader that already holds an old cached block, which is exactly the situation in the worked example (the server copy changed, the client copy is 30 s old). Only validation — a callback, a lease, or a check on use/open — shortens that window.
- ch 8 [low] Exam traps, bullet 1: 'A faster cache widens the staleness window' is not right. Staleness depends on the hit ratio (how often the server is contacted) and on the validation interval, not on how fast the cache is. A fast cache can even be validated more often.
- ch 8 [low] Exam traps, bullet 4: Saying a file handle 'is not a capability with rights' is misleading. Because a stateless server needs no other state, possession of the handle is enough to access the file, so the handle works much like a capability; this is a known weakness of NFS-style access control. The intended contrast is with a client-side open-file descriptor.
- ch 9 [high] Quiz Q6: The stated answer is wrong. With the DACL ordered allow exam full control, then deny bob write, bob's write is GRANTED: the access check walks the ACEs in order and stops at the first ACE whose SID is in bob's token and whose mask covers the requested right. The allow ACE for group exam comes first and includes write, so the later deny is never reached. The answer teaches the opposite, and it contradicts Section 2's own sentence 'A deny ACE therefore beats any later allow'.
- ch 9 [high] Exam traps, trap 3: 'Deny ACEs are evaluated before allow ACEs' is not the Windows rule. ACEs are evaluated in DACL order, first match wins. A deny beats an allow only because the system normally stores deny ACEs ahead of allow ACEs, not because denies are checked in a separate earlier pass. As written, a student will answer a DACL with allow-then-deny incorrectly, as Q6 shows.
- ch 9 [low] Section 3, side-by-side table, 'order' row: 'ACEs in order; deny checked first' contradicts 'in order' and repeats the wrong rule from Q6.
- ch 9 [low] Section 1, special bits: The sticky bit description is incomplete: on /tmp, the directory's owner and root can also delete files, not only the file's owner.
