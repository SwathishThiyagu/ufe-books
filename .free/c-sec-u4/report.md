## Reviewer notes (after any revision)

- ch 1 [low] Section 3, hybrid encryption paragraph: "TLS works this way" is no longer accurate. Modern TLS (1.3) does not have the sender encrypt a random session key with the receiver's public key; the two sides agree the session key with an (elliptic-curve) Diffie–Hellman exchange. Only older TLS versions used RSA key transport.
- ch 1 [low] Section 1, trapdoor permutation sentence, and Exam trap 5: "A bijection, meaning every y has exactly one x" describes only the one-to-one half. A bijection from X to Y must also be onto: every y in Y must be the image of some x. As written, a student can call any injective function a permutation.
- ch 1 [low] Figure and Worked example 1 (n = 55, e = 3, d = 27): The figure and the example say reversing x³ mod 55 without the trapdoor is infeasible, but the modulus is 55, so a student can list all 55 outputs and invert by hand in a minute. With tiny numbers the security claim is false; only the arithmetic is being illustrated.
- ch 2 [high] Section 1, last line on Carmichael value: The conclusion is right but the reason given is backwards. 'Any d with e·d ≡ 1 (mod λ(n)) also decrypts, because λ(n) divides φ(n)' does not follow: λ | φ only shows that a d which is an inverse mod φ is also an inverse mod λ (the opposite direction). A student copying this reason learns wrong logic.
- ch 2 [low] Figure spec (edges): The arrow leaving the node labelled 'Private d' and entering 'Public key (e, n)' is labelled 'publish'. Read literally that says d is published, which is exactly the secret.
- ch 2 [low] Figure caption: 'Notice that n alone is published while its two prime factors are destroyed' conflicts with the public pair (e, n) stated everywhere else in the chapter; it reads as if e is secret.
- ch 2 [low] Worked example 1, step 4: d = 27 is correct mod φ(n) = 40, but it is not the smallest working exponent for this key: λ(n) = lcm(4, 10) = 20, so d = 7 also decrypts (14⁷ mod 55 = 9). Students meet the trap 'every d ≡ e⁻¹ mod λ(n) decrypts' just below and may think something is wrong.
- ch 2 [low] Section 3, first paragraph: 'An attacker holds n, e and c and wants d' misstates the goal (the attacker wants m), and 'no method better than factoring is known' is stated too strongly: recovering d from (e, n) is as hard as factoring, but breaking RSA by recovering m is not proven to be equivalent to factoring.
- ch 2 [low] Section 3, timing bullet: 'constant-time code and random blinding hide them' is loose: constant-time code does not hide the bits of d, it removes any dependence of the running time on them.
- ch 3 [high] Beyond: The claim that TLS 1.3 dropped classical finite-field Diffie-Hellman is wrong. TLS 1.3 still supports ephemeral finite-field DH through the standardised ffdhe2048/3072/4096/6144/8192 groups; what it removed was static (non-ephemeral) DH and RSA key transport, not FFDHE itself.
- ch 3 [low] Section 2: The symbol g is reused with a different meaning. Section 1 defines g as a primitive root of the full group mod p, but here g = h² mod p is a generator of the order-q subgroup only, so it is not a primitive root of the full group. A student may think both statements describe the same number.
- ch 3 [low] Quiz Q4: "It also removes the smooth part of p − 1 that Pohlig-Hellman would exploit" is loose: with p = 2q + 1 the only factors of p − 1 are 2 and q, so there is no long smooth part to remove.
- ch 3 [low] Figure: The two dashed messages 'K = Bᵃ = 2' (Alice to Bob) and 'K = Aᵇ = 2' (Bob to Alice) are drawn as network messages, which can suggest that K is transmitted. K is never sent.
- ch 4 [low] Figure, nodes f (and the section 3 / Q5 phrasing): The two notes drop the modulus: 's = 19⁶ = 2' and 'm = 14 × 12 = 7' read as false arithmetic (14 × 12 is 168, not 7). A student copying the figure will lose the mod‑23 step.
- ch 4 [low] Section 3, first paragraph after the bullets (also Q5 wording): 'the ciphertext holds two numbers modulo p, so it is twice the size of the message' is loose: each of C1 and C2 is about the size of p, so the expansion is roughly two modulus lengths, not two message lengths. A 100‑bit message under a 2048‑bit p expands about forty times.
- ch 4 [low] Exam traps, item 5: The range rule says m must satisfy 1 ≤ m ≤ p−1, then the same bullet discusses m = 0, which sits outside that range. Readers may think 0 is a legal encoding.
- ch 5 [high] Quiz Q6: The answer says certificate pinning stops an attacker who has stolen the server's valid certificate and private key. If the app pins that same key or CA, the stolen original certificate still passes; pinning only rejects a different certificate for that host, such as a mis-issued one.
- ch 5 [high] Section 2, certificate pinning sentence: The sentence says pinning blocks a stolen-but-valid certificate. That is only true for a different valid certificate, such as a mis-issued one; it does not block use of the original certificate and private key stolen from the server.
- ch 5 [high] Section 2 (chain check) and Quiz Q1: Modern HTTPS hostname verification uses the subjectAltName extension, not the Subject common name. The text says the browser checks the subject name against the typed host and Q1 repeats this, so a student may think a CN-only certificate is accepted.
- ch 5 [low] Worked example 1, steps 1-4, and Quiz Q3: A certificate does not carry the hash h. The verifier computes h from the certificate fields; the certificate carries only the signature s and the signed fields. The examples say 'carries hash value h'.
- ch 6 [low] Section 2, closing sentence: "Short digests are one reason MD5 and SHA-1 failed" is misleading. MD5 and SHA-1 were broken by cryptanalytic attacks on their compression functions that produced collisions far below the birthday bound; digest length was not the cause of the break, it only leaves a thin margin today.
- ch 6 [low] Section 1, the property chain: "Second preimage resistance implies preimage resistance" is stated as a general fact, but it does not hold for every hash function; it is true only for random-oracle-like functions. Some textbooks add this caveat, so a sharp student may be confused when they meet it.
- ch 6 [low] Section 4, password storage bullet: Keeping salt plus H(salt ‖ password) with a fast hash such as SHA-256 is exactly the practice password crackers exploit; the bullet reads like a recommendation. The Beyond note mentions Argon2, but the use-list itself should not suggest plain salted SHA-256.
- ch 6 [low] Section 4, hash tables and deduplication bullet: A cryptographic digest is a poor bucket index. In-memory hash tables use cheap non-cryptographic hashes because speed matters and attackers are not the concern; mixing the two in one bullet can mislead.
- ch 7 [high] Section 2, CBC-MAC paragraph: The forgery condition is stated backwards: 'Given tags for messages of equal length, an attacker can splice blocks and forge a tag for a longer message.' CBC-MAC over messages of one fixed length is secure; the attack needs a tag for a shorter message that is a prefix of the forged longer one. Read together with the preceding 'Requirement' sentence, the paragraph contradicts itself and the student learns the wrong condition.
- ch 7 [high] Section 4, Encrypt-and-MAC bullet: Encrypt-and-MAC is described as 'tag the plaintext, then encrypt plaintext and tag', which is exactly the MAC-then-encrypt description given in the next bullet. Two different schemes are given the same definition. In encrypt-and-MAC the tag is computed over the plaintext but sent unencrypted next to the ciphertext (the SSH style); the tag is not encrypted.
- ch 7 [low] Worked example 1, step 6 (part c): The stated reason is muddled: 'a receiver seeing blocks 7, 4 and tag 0 cannot tell whether block 5 was the key or message data.' The receiver knows K, so it is not confused; and no concrete forgery is shown for the toy hash, even though it is easy to show here.
- ch 7 [low] Section 3, truncation sentence: 'Keep at least half of n and never below 80 bits' is presented as a hard rule. Half of n is a sensible rule of thumb, but NIST guidance allows truncation down to 32 bits (security falls to about 2^t), and deployed protocols do use 80-bit and shorter tags. The 80-bit floor is advice, not a standard limit.
- ch 8 [high] Section 2, sentence defining s: The range of the signature is written "0 ≤ s e mod n", which is not a valid condition and mixes the range with the public exponent. A student will read it as s·e mod n and not as the size limit on s.
- ch 8 [low] Section 2 and Section 3, formulas inside running text: Exponents are not marked up in the prose: "s = hd mod n", "(hd)e = hde", "se mod n", "s1 = h1d mod n", "(s1 s2)e = h1 h2 mod n" all read as multiplication. The failure is worst in Section 3, where the multiplication step looks like it follows from s1·s2·e = h1·h2, which is false.
- ch 8 [low] Section 1, existential forgery definition: The sentence ends "...and a valid signature, any message", which contradicts the definition just given: in an existential forgery the attacker does not get to pick the message.
- ch 8 [low] Quiz Q5, answer: The answer says "Existential: any new valid pair", which by the word "any" describes a universal forgery, the opposite of the intended meaning.
- ch 8 [low] Section 4, ElGamal signature: The inverse k⁻¹ exists only if gcd(k, p − 1) = 1; the text says only to use a safe random k, which is too vague for a scheme where the modulus of the inverse is p − 1 and not a prime.
- ch 9 [low] Section 1, zero-knowledge definition: The formal definition says the simulator uses 'only x and V's randomness'. That is the honest-verifier definition: it only works when the verifier's messages are determined by its coins. For general zero knowledge against a verifier that may deviate, the simulator must also be given the verifier's strategy (black-box access) and be allowed to rewind it. As written, the paragraph just after it ('Honest-verifier zero knowledge is the weaker version') contradicts the definition above it.
- ch 9 [low] Worked example 1, steps 4 and 5: Step 5 says 'The other two edges have different colours', which is true only if the cheating prover uses both colours (two vertices one colour, the third the other colour). If it colours all three vertices with colour 1, all three edges are monochromatic and it passes with probability 0. The 2/3 figure is the best case for the cheat, so the step should state it as an upper bound.
- ch 9 [low] Exam traps, fourth trap: 'For the triangle with only two colours, exactly one of the three edges is monochromatic' is stated as always true. It holds only when the cheat actually uses both colours; a prover that colours all three vertices the same has three monochromatic edges. The pass probability 2/3 is the maximum over cheats, not the value for every two-colour attempt.
