## Reviewer notes (after any revision)

- ch 1 [low] Section 3, last paragraph: The causal link is loose: 'The server needs the password in usable form to verify such an answer, so this exchange normally runs inside TLS.' A student reads this as 'TLS is needed because the server stores the password', which is not the reason. The real reason is that H(password ‖ R) can be offline-guessed once R and the answer are on the wire, so the answer must be protected in transit (and the server-side storage problem is a separate weakness).
- ch 1 [low] Section 2, slow hashes paragraph: 'In bcrypt the cost is a power of two, so cost 12 means 2¹² = 4096 rounds of key setup' is imprecise: the cost parameter is an exponent (a small integer), not a power of two; the work done is 2^cost iterations.
- ch 1 [low] Quiz Q4: Q4 repeats Worked example 1 with the same hash, same password and same nonce, so it tests nothing new and students can copy the worked answer. Only the replay part (b) is dropped.
- ch 2 [high] Quiz Q8: The answer says the damage from a compromised KDC is bounded by 'the need to stay inside the clock skew window on fresh authenticators'. That is not a limit at all. An attacker who controls the KDC knows every long-term and session key and knows the correct current time, so any authenticator it builds for a forged ticket is inside the window by construction. The clock skew check constrains honest clients with bad clocks, not an attacker who holds the keys.
- ch 2 [low] Figure caption: The caption says the timestamp 10:04 'appears in both authenticators', but the text has just stated that a fresh authenticator is made for every single request. A student may conclude the same authenticator is reused between the TGS and the server, which would defeat replay protection.
- ch 2 [low] Section 2, AS-REQ bullet, and Section 3: The AS-REQ bullet lists the pre-authenticator as if it is always in the first request, and Section 3 says the client 'must' pre-authenticate. In V5 the pre-authentication mechanism is an extensible framework, not part of the core exchange; many KDCs first answer an AS-REQ that has no pre-authenticator with a KDC_ERR_PREAUTH_REQUIRED error, and only the resent request carries the encrypted timestamp.
- ch 3 [low] Section 1 (AH description): The text says AH adds a MAC over the IP header and payload. In transit some IPv4 header fields change (TTL, header checksum, DSCP/ECN, flags, fragment offset), so the MAC cannot cover the whole header; it covers the immutable header fields plus the payload.
- ch 3 [low] Section 1 and the figure (ESP tunnel fields): The list 'outer IP header, ESP header, encrypted inner packet, ESP trailer, ESP authentication data' never says which parts are encrypted, so a student can read the ESP trailer as being in clear. In fact padding, pad length and next header (the trailer) are encrypted; only the ESP header and the authentication data travel in clear.
- ch 3 [low] Lead: 'It authenticates the sender' is loose: the receiver learns that the packet was built by whoever holds the SA key. In tunnel mode that is the peer gateway, not the original host, and with ESP the identity of the original host is not proven.
- ch 3 [low] Section 2 (sequence number): The chapter says the sequence number is 32-bit and increments per packet but does not say what happens when it would wrap. The sender must never reuse a sequence number under the same SA keys.
- ch 4 [high] Section 1, TLS record: The record payload limit is written as "at most 214 bytes (16,384 bytes)". 214 and 16,384 are not the same number, so the student cannot tell which is right. The intended value is 2^14 = 16,384 bytes and the superscript was lost.
- ch 4 [high] Section 1, formula block: "The output is 48 bytes" sits after two formulas. Only the master secret is 48 bytes. The key_block length is not fixed; it depends on the cipher suite (MAC key sizes, cipher key sizes, IV sizes), so a student may answer "key_block = 48 bytes" in an exam.
- ch 4 [low] Section 1, TLS 1.2 handshake paragraph: Finished is described as "a MAC over the handshake transcript under the new keys". TLS 1.2 computes verify_data with the master secret and the handshake hash; the new record keys encrypt the message but do not produce verify_data. The wording makes the two sound the same.
- ch 4 [low] Figure (sequence spec): The figure shows only the server's Finished, and places it before any client Finished. In the TLS 1.2 full handshake the client sends ChangeCipherSpec and Finished first, then the server replies with ChangeCipherSpec and Finished, and only then comes application data.
- ch 4 [low] Section 2, TLS 1.3: "TLS 1.3 allows only ephemeral Diffie-Hellman or elliptic-curve DH" is too strong. TLS 1.3 also allows PSK-only key establishment (psk_ke) with no (EC)DHE, which the later resumption paragraph itself implies. The statement is only true for a full handshake.
- ch 5 [high] Exam traps, third bullet: The trap says S/MIME and PGP protect the body only and that the Subject line always stays in clear text. This is wrong for the normal enveloped modes. In S/MIME, application/pkcs7-mime with smime-type=enveloped-data wraps the whole MIME entity, so the Subject can travel encrypted inside it (subject hiding). PGP/MIME does the same inside its multipart/encrypted part. A student who writes 'subject is never protected' loses marks.
- ch 5 [low] Section 2, first paragraph: 'Each user holds a public-key pair (RSA, or ElGamal and DSA), one symmetric cipher (AES, CAST, IDEA), one hash (SHA-256)' suggests a user owns a cipher and a hash. A user owns keys; the cipher and hash are chosen per message from the set the software supports, and the message header names the choice. 'ElGamal and DSA' is also garbled: DSA signs, ElGamal encrypts.
- ch 5 [low] Worked example 1, step 1: Ks = 0x7A is a one-byte key. The text says 'A session key is one byte here', but a reader can still carry away the idea that PGP session keys are 8 bits. Real PGP session keys are 128 or 256 bits.
- ch 5 [low] Section 3, SPF and DMARC sentences: SPF is described as checking 'the domain' without saying which one. SPF checks the envelope sender (MAIL FROM / Return-Path), not the visible From: header that the user reads. That is exactly why DMARC adds alignment, and the chapter's Q7 reasoning depends on it.
- ch 6 [high] Section 3, paragraph 1: The sentence "It rejects unsigned or altered answers as bogus" is stated without qualification. A validating resolver only marks an answer bogus when the zone is signed (a DS exists in the parent). For an unsigned zone the answer is accepted as "insecure". As written, a student will conclude that every unsigned DNS answer on the Internet is rejected, which is false.
- ch 6 [low] Quiz Q4: The answer gives the right mechanism but does not state the condition that makes an unsigned reply bogus. Tagged on its own, it teaches that any unsigned A record is rejected.
- ch 6 [low] Section 2, last paragraph: "NSEC and NSEC3 let a signed zone prove that a name does not exist without a signature on a fake not-found message" is garbled and reads as if NSEC records carry no signature.
- ch 6 [low] Figure: The .in node is labelled "DS", but the DS for .in lives in the root zone, not in .in. The label contradicts the exam trap that says the DS record lives in the parent and the DNSKEY in the child.
- ch 6 [low] Worked example 1: Only the TTL is used to decide when the cached answer expires. A real validator caches for the smaller of the TTL and the time left on the RRSIG, so a signature close to expiry can shorten the cache life. The example is not wrong but the rule is missing.
- ch 7 [low] Section 3, PTK formula: The PRF input is written as PRF(PMK, ANonce, SNonce, AP MAC, Client MAC). The standard also mixes in a label string and orders the two MAC addresses and the two nonces by Min/Max, so a student who later reads the standard will see a different input list and think the book is wrong.
- ch 7 [low] Section 3, handshake step 3 and figure: Step 3 says the AP 'sends the GTK with a MIC'. It does not say the GTK travels encrypted, so a reader may think the group key is sent in clear.
- ch 7 [low] Quiz Q5: "PMK from the PSK passphrase and SSID" blurs two different things: the passphrase (8 to 63 characters) and the PSK, which is the 256-bit PMK itself, obtained by stretching the passphrase with PBKDF2 using the SSID as salt.
- ch 8 [low] Section 1 flow and Figure: The exchange stops at Access-Accept and 'Port open'. The final EAP message of the standard flow is missing: the authenticator sends EAP-Success to the supplicant after Access-Accept (and EAP-Failure after Access-Reject). The figure label 'Identity?' also hides the real frame name, EAP-Request/Identity.
- ch 8 [low] Worked example 1, answer: 'normal traffic on that port belongs to zero VLANs' can be read as if the port has no VLAN configured at all. Strictly, the port simply is not authorized to forward data traffic in any VLAN; in some deployments it is parked in a restricted guest VLAN.
- ch 8 [low] Section 2 and Section 3 ('See TLS', 'see IPsec', 'see user authentication'): Cross-references to other chapters are written as plain text, so a student reading on a phone cannot jump to them, unlike the linked references elsewhere in the series.
- ch 9 [low] Section 4 (Defences that hold), pseudo-code block: The code block is followed by a '[shown output]' placeholder that is empty, so the defence is never demonstrated and the reader cannot see the result of binding. The variable 'hash' is also used without being defined.
- ch 9 [low] Section 1, cookies and SameSite: 'SameSite (not sent on cross-site requests by default)' is too broad. The browser default is SameSite=Lax, which still sends the cookie on top-level cross-site GET navigations; it blocks cross-site POSTs and subresource requests.
- ch 9 [low] Figure (sequence diagram) and its caption: The figure's DB message is labelled only 'SELECT * FROM users', which hides the injected WHERE clause that is the whole point of the attack. The caption also says the app 'logs the attacker in as admin', while worked example 1 says the code accepts the first user row; taken together the two statements disagree.
