## Reviewer notes (after any revision)

- ch 1 [low] worked example 1, steps 2 and 3: The model adds the network cost serially to the compute time, which silently assumes that no message overlaps with computation. In a real split, a machine can send and receive while it computes, so 22.5 s is an upper bound, not the typical time. A student may treat the sum as exact.
- ch 1 [low] worked example 1, step 2: The wording mixes units: the job 'exchanges 5000 messages', but the cost is given per 'message round trip'. A round trip is a request plus a reply, so it is not clear whether 5000 counts individual messages or request-reply pairs. The arithmetic is right only if 5000 is the number of round trips.
- ch 1 [low] Section 2, transparency table: The list stops at seven types of transparency. The standard reference-model list has an eighth, persistence transparency (hiding whether a resource lives in memory or on disk, and whether it survives a restart). Since the text calls these 'the common types', the omission looks like an error rather than a choice.
- ch 1 [low] Quiz Q3: The answer blames ordering difficulty only on clock drift. Drift is part of it, but even perfectly synchronised clocks would not fix ordering, because message delay is unpredictable, so 'A sent before B' cannot be read from timestamps alone. A student repeating only 'drift' misses the main reason.
- ch 1 [low] Section 3, architectural models: Client-server, peer-to-peer and three-tier are presented as three models of the same kind, but three-tier is a multi-tier form of client-server (presentation, logic and data tiers), not a separate family. A student may write them as three parallel alternatives in an exam.
- ch 2 [high] Section 2, last paragraph; repeated in Exam trap 2 and Quiz Q6: The chapter says 'Sender and receiver must agree on the combination' and that 'a blocking receive cannot be matched by a non-blocking send without extra buffering', teaching this pairing as a bug. Standard texts list all four blocking/non-blocking combinations as legal, and non-blocking send on the sender side with blocking receive on the receiver side is the common, recommended pairing (for example Isend plus Recv). The two sides choose their primitives independently; no agreement is needed. The only thing non-blocking send requires is that a buffer exists, which every real system provides.
- ch 2 [high] Figure caption and spec: The caption says 'The blocking path finishes the send only after the matching receive takes the message', which is the definition of a synchronous (rendezvous) send, not a blocking send. Section 2 correctly defines a blocking send as returning when the sender may safely reuse its buffer, which can be as soon as a copy is made. The figure contradicts the chapter's own definition.
- ch 2 [low] Figure spec: The message labelled 'recv; send returns' is marked dashed, but the caption says the dashed arrow is the asynchronous self-arrow. Two dashed arrows appear for one explanation.
- ch 2 [low] Worked example 1, step 6 and answer: The slowdown ratio is written as 7.204968944099379, which is 16 digits for inputs given to two significant figures. Students may copy that precision into answers.
- ch 2 [low] Section 1: The comparison stays implicit: the chapter never states the cost trade-off that exam questions usually ask for. Shared memory avoids copying data but needs coherence and does not cross a network; message passing needs an explicit copy and a system call per transfer but scales across machines.
- ch 3 [high] Lead: The lead defines IPC as exchange between processes 'on different machines', but Section 1 then lists pipes and shared-memory segments, which are same-machine mechanisms. The definition contradicts the chapter's own list and the standard textbook meaning of IPC.
- ch 3 [low] Figure, RPC path: The dashed return edge starts at the server procedure, but the text says the server stub marshals the result. The diagram should show the result leaving the server stub, and the reply passing back through the network to the client stub.
- ch 4 [low] Figure spec: Internal events are encoded as messages from a process to itself (from P1 to P1, P2 to P2, P3 to P3). In sequence-diagram notation a self-arrow conventionally means a message sent to oneself, so a reader can mistake the internal steps for messages, which contradicts the text saying internal events are not messages. All entries also have dashed set to false, so the internal markers will look the same as real messages.
- ch 4 [low] Section 2: The claim 'A late message cannot arrive after the round ends: its delay is bounded by Δ' only holds if the round is at least Δ long, but round length is never stated. A student can conclude that any round automatically contains every message of that round.
- ch 5 [low] Section 2, NTP hierarchy: "Secondary servers at stratum 2 and below take time from a higher level" is ambiguous: a stratum 2 server actually takes time from a server with a lower stratum number, and a student may read "higher level" as a higher stratum number.
- ch 5 [low] Exam traps, fourth bullet: "Treating Cristian's correction as exact; it is exact only when the two one-way delays are equal" contradicts the first bullet, which also requires the server's processing time to be zero. With equal one-way delays d and server processing time p, the estimate is off by p/2.
- ch 5 [low] Section 2, last sentence before the figure: "Where no such bound is acceptable, use logical clocks" suggests logical clocks are a stronger substitute for real time. Logical clocks give only causal ordering and carry no real-time value, so a student may think they solve the accuracy problem.
- ch 5 [low] Section 1, definition of skew: The definition matches the distributed-systems textbooks, but tools such as ntpd and chrony print "offset" for the time difference and "skew" (or frequency) for the rate difference, so a student reading tool output will be confused.
- ch 6 [high] Worked example 1, step 9 and the answer line: The question asks 'Which pairs are concurrent?' but the answer gives only two pairs, the ones with equal timestamps (a with c, g with send m1). That implies concurrency can be read off equal timestamps, which is the exact mistake the chapter warns against. In this run many more pairs are concurrent: a with f, a with g, c with f, c with g, send m1 with f, send m1 with g, receive m1 with f, receive m1 with g, send m2 with f, and send m2 with g. A student will leave the example believing 'concurrent means equal timestamps'.
- ch 6 [high] Quiz Q3: The question conflicts with the chapter's own trap 'The timestamp of a send is taken after the increment for that send event, not before'. If P1's clock is 7 and then the send event happens, the clock becomes 8 and message m carries t = 8, so P2 should end at max(3, 8) + 1 = 9, not 8. The answer 8 is only right if 7 is already the timestamp carried inside m, which the question does not say.
- ch 6 [low] Quiz Q4 answer: The sentence 'The timestamps are compatible with x → y, with y → x being impossible, or with x and y being concurrent' presents 'y → x being impossible' as if it were a third possible outcome, so the alternatives are muddled.
- ch 7 [high] Section 2, theorem statement and both directions of the proof: The inequality is missing in three places, so the central theorem is unreadable: 'a → b if and only if V(a) .', 'If a → b, prove V(a)  by induction', and 'Second direction. If V(a) , let a be the k-th event'. As printed, the statement and both proof directions have a blank where the comparison should be, so a student cannot see what is being proved.
- ch 7 [low] Exam traps, third trap: The sentence 'Strict  is needed' has the symbol dropped, so the trap does not say which strict comparison is meant.
- ch 7 [low] Exam traps, first trap: The claim that a cause 'can look concurrent with its effect' is not what the missing increment produces. If the receiver only takes the component-wise maximum, the receive vector is always greater than or equal to the sender's vector, never incomparable with it. The real failure is that the receive can get exactly the same vector as the send (when the receiver's own entry adds nothing), so the effect looks like the very same event instead of a strictly later one.
- ch 8 [high] Figure and its lead-in sentence (the ₹200 marker example): The marker story shown in the figure cannot happen with A as initiator. A sends ₹30, then records ₹70 (after the send), then sends a marker on channel A→B. FIFO guarantees the ₹30 message reaches B before that marker. So when B's first marker arrives from A, B has already added the ₹30 and records ₹130, and the channel A→B state is empty. The figure's 'B records ₹100' plus '₹30 in channel' is impossible under the stated assumptions; the total would still be ₹200 but as 70 + 130 + 0, not 70 + 100 + 30.
- ch 8 [low] Section 1, third paragraph: 'the cut is still consistent only when the channel state holds that message': This contradicts the chapter's own definition two paragraphs earlier. A cut with the send inside and the receive outside is consistent by definition; the message is simply in transit across the cut. What needs the channel state is the reconstructed global state (the total), not the consistency of the cut.
- ch 8 [low] Exam traps, third bullet: The wording is self-contradictory: a message that arrives after the marker on its own channel is outside the snapshot altogether and belongs nowhere. The intended trap is the message that arrives after the process recorded its state (its first marker) but before the marker on its own channel.
- ch 8 [low] Quiz Q2 answer: 'Markers travel with normal messages' can be read as markers riding along inside application messages. Markers are separate control messages that use the same channels in FIFO order.
- ch 8 [low] Section 2, bullet list of receiver rules: The list states the rule only for the first marker. It never says what a process does when a marker later arrives on another incoming channel, so a student may not see how channels other than the first one get closed.
- ch 9 [low] Section 3, total order paragraph: The text says total order has 'two common implementations' but only the sequencer is described. The second one is never named, so a student looks for something that is not there and may think a replicated sequencer is the only alternative.
- ch 9 [low] Section 3, sentence on sequencer failure: 'members run an agreement round to choose the next number' is muddled. Consensus is used to agree on the ordering of messages, or to choose a new sequencer after a failure, not to pick the next sequence number for each message.
- ch 9 [low] Figure and worked example 1: The figure shows m2 going only from P2 to P3. Group communication sends every message to every member, and m2's vector (1,1,0) was built after P2 delivered m1. As drawn, a student may think causal order is defined over ordinary point-to-point messages between selected pairs.
