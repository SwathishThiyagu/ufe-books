## Reviewer notes (after any revision)

- ch 1 [low] Section 1, paragraph on the name and extension: The sentence 'UNIX-like systems store a type with the file and check the bytes' mixes two different mechanisms. The inode stores only a coarse type (regular, directory, device, and so on). For a regular file, the 'type' a program cares about (PDF, PNG, ELF binary) is not in the inode; it is detected from a magic number in the first bytes of the content, and it is the program or a tool such as file(1), not the kernel, that makes the decision.
- ch 1 [low] Section 2 (delete/close bullets) and Quiz Q8: The chapter builds the open-count model and then says delete 'removes the name and frees the blocks' and that delete frees the blocks 'so the name no longer exists'. When a deleted file is still open somewhere, the name goes but the blocks are held until the last close drops the open count to zero. The two statements contradict the open-count rule taught a few lines earlier.
- ch 1 [low] Section 2, read(fd, buf, n) bullet: The bullet says read copies n bytes and advances the offset by n. A read returns the number of bytes actually transferred, which can be less than n near end of file, for a pipe or terminal, or after a signal. A student may assume read always returns n bytes and miss short reads in exam answers and code.
- ch 2 [high] Figure caption; Worked example 1 (steps 2–6, dry run, answer): The example counts a 1 ms directory read for the 'home' component even though the root directory is already cached. Looking up 'home' reads the root, so its cost is 0 ms. With root cached only two disk reads remain: home (to find ravi) and ravi (to find notes.txt). The stated 3 ms and 4 ms are one read too high; the dry run's first row and cumulative totals are wrong.
- ch 2 [high] Quiz Q3: The answer repeats the off-by-one read. With the root cached, /a/b/c.txt needs two directory-block reads (a to find b, b to find c.txt), not three. Without the root cache it needs three reads (root to find a, a to find b, b to find c.txt), not four.
- ch 2 [low] Section 1 formula: T_start and T_read(first component) can both mean the same read of the root or current directory. If T_start is nonzero and the sum also includes reading the directory that holds the first component, the root/current read is counted twice.
- ch 2 [low] Section 3, last paragraph: The clause 'except that a small directory may itself be a file with entries' is unclear and can suggest a directory stores file contents. A directory is a file whose data blocks hold directory entries; it does not store file data.
- ch 3 [low] Section 1, unmount paragraph: The list 'an open file, current directory, or working directory inside' repeats the same idea twice; a student may wonder whether 'current directory' and 'working directory' are two different things.
- ch 3 [low] Worked example 1, step 4: Step 4 mentions unmount, but no unmount happens in this example, and 'may see stale data' is misleading: the process reads the live contents of the hidden local file (inode 101), not stale data. Mounting only redirects name lookup; it does not change files already open.
- ch 4 [low] Section 1, first paragraph: "An inode table, or a file allocation table (FAT), stores per-file metadata" blurs two different things. In FAT the per-file metadata (name, attributes, first cluster, size) sits in the directory entries; the FAT itself holds only the cluster-to-cluster links. A student can end up believing FAT keeps an inode-like table of file records.
- ch 4 [low] Section 3, first paragraph: "Many descriptors can point to the same inode, and each descriptor has its own offset" is not always true. The offset lives in the open file description, not in the descriptor. After fork or dup, two descriptors share one open file description and therefore share one offset.
- ch 4 [low] Section 1, last paragraph: "For a read of n bytes at offset o, the next offset is o + n" holds only when n bytes are actually returned. Near or past end of file, read returns fewer bytes, and the offset advances by the number returned, not by the requested n. The chapter's own exam trap states the correct rule, so the two statements disagree.
- ch 4 [low] Section 3, second paragraph: "An ext4 read calls ext4's inode operations" is imprecise. Reads and writes are dispatched through the file object's file operations (which reach the file's address-space operations); inode operations handle lookup, create, unlink and similar name/metadata work.
- ch 4 [low] Section 2, second paragraph: "At the end, the VFS has the target inode. open then creates a file object for that inode" skips the dentry. Path lookup produces the final dentry (and through it the inode), and the file object points to that dentry, which is also what the dentry cache stores.
- ch 5 [high] exam traps, fourth bullet: The chapter states that contiguous allocation suffers both kinds of fragmentation but 'linked allocation suffers neither in data blocks'. Linked allocation does avoid external fragmentation, but the last block of a linked file can still be only partly filled, so fixed-size blocks leave internal fragmentation there too. A student will write 'linked has no internal fragmentation' and lose marks.
- ch 5 [low] figure spec: The Index row has five cells ('30' plus four data blocks) while the other rows have four, and show_index labels columns 0 to 4. So logical block 2 appears in column 2 for Contig and Linked but in column 3 for Index, and the emphasised cells do not line up down the table. The marks are correct per cell, but the picture misleads.
- ch 5 [low] section 2, FAT variant: 'one entry per disk block' is not exact for FAT: the table has one entry per cluster, and a cluster is one or more blocks/sectors. A student may write that FAT entries map 1:1 with disk blocks.
- ch 6 [high] Section 1, bitmap size example: The superscripts are lost or wrong: 'N = 228 blocks' and 'B = 225 bytes = 32 MB' are inconsistent. For 1 TiB with 4 KiB blocks, N = 2²⁸ blocks and B = 2²⁵ bytes = 32 MiB. For decimal 1 TB with 4 KB blocks, the bitmap is about 30.5 MB, not 32 MB.
- ch 6 [low] Section 1, bitmap formula: B = N / 8 gives a fractional byte count when N is not a multiple of 8. A bitmap must use whole bytes.
- ch 6 [high] Section 2, table, Exam trap 4, Quiz Q4: A linked free list does not need O(F) pointer steps to allocate one free block. The head pointer gives the first free block; allocation from the head is O(1), with one read to get the next pointer. O(F) traversal is for finding a particular free block or checking whether block j is free. Q4's premise and answer are therefore wrong.
- ch 6 [high] Section 2, counting definition, Quiz Q6: Counting is confused with grouping. Standard counting stores the address of the first free block and the count of contiguous free blocks that follow it; an entry is address plus count. It does not store 'a few free-block addresses plus a pointer to the next group block'; that describes grouping.
- ch 7 [low] Section 2, first paragraph after the IRQ discussion: The sentence 'The handler address comes from two tables' is inaccurate. The vector is a small integer sent by the interrupt controller, not a table; only the IDT is a table. A student may think the vector is itself a lookup table.
- ch 7 [low] Section 3, formula Npoll ≤ ⌊T / tpoll⌋ + 1: The formula uses ≤ while Npoll is defined as the maximum number of polls. A maximum should be stated with equality; with ≤ the formula does not give the maximum, it only gives an upper bound.
- ch 7 [low] Section 2, opening sentence: The cross-reference 'Unit 1 covers the CPU side' is plain text, not a chapter link, so a reader on a phone cannot jump to it, and the unit numbering may not match the reader's syllabus.
- ch 8 [high] Quiz Q1 (answer), compared with Section 1: Section 1 places the four layers below read() as system-call interface, I/O subsystem, device driver and interrupt handler, with the user process above them. The Q1 answer instead counts 'user-space I/O' as one of the four and says the interrupt handler 'sits with the driver', so the quiz contradicts the text the student just read. A student would not know whether the interrupt handler is a layer or not.
- ch 8 [low] Section 2, paragraph on waiting modes: 'Nonblocking keeps the CPU busy' is too broad. A nonblocking call by itself does not burn CPU; cost appears when the process polls in a loop. As written, students may think nonblocking I/O always wastes CPU.
- ch 8 [low] Section 3, hit-ratio formula: The formula T = h × T_cache + (1 − h) × T_device assumes a cache miss costs only the device access time. On a real miss the cache is also probed first, so the miss term is (T_cache + T_device). The chapter never states this assumption, and the worked examples then look like exact truth.
- ch 9 [low] Section 3, the four bullets after the C-LOOK bullet: The algorithm list continues, without any break, into four procedure steps ('Write the service order...', 'Subtract each consecutive pair...', 'Add the absolute differences...', 'Divide by the number of requests...'). On a phone a student reads these as more disk-scheduling algorithms rather than as the method for computing head movement.
- ch 9 [low] Worked example 1, step 8 (and the matching claim about bounded wait): 'No request waits longer than one sweep' is loose. In SCAN a request that arrives just after the head has passed its cylinder waits until the head travels to the far end and comes back, which is about two one-way sweeps, not one.
- ch 9 [low] Quiz Q4 answer: The first sentence is correct, but the second is a loose reason: only the exact end cylinder is passed once per cycle; other 'edge' cylinders are still passed twice per cycle, the two passes being close together. The standard reason for SCAN's non-uniformity is that the time between two successive passes at a cylinder depends on that cylinder's position (2c one way, 2(199 − c) the other way), while in C-SCAN every cylinder sees the same fixed cycle of sweep plus return.
- ch 9 [low] Beyond: 'Real drives hide geometry behind a flash translation layer' mixes two technologies. A flash translation layer maps logical blocks to flash pages on SSDs; a magnetic disk hides its geometry behind a logical block address translation inside the drive firmware (as Section 1 already said).
